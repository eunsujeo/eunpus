# 온보딩 문서 작성 가이드라인

## 문서의 성격

온보딩 문서는 신입 교육 과정이나 제품 사용 설명서가 아니다. **이 팀이 업무에서 공통으로 사용하는 개념, 용어, 구조, 상태, 책임 경계를 기록한 문서**다.

독자에게 무엇을 배워야 하는지 안내하지 않는다. 문서를 읽는 방법을 설명하지도 않는다. 주제의 정의와 관계를 바로 제시하고, 우리 시스템에서 그 개념을 어떻게 해석하는지 기록한다.

## 문서에 포함하는 내용

- 개념의 정의와 적용 범위
- 구성요소 사이의 관계와 책임 경계
- 상태와 상태 전이
- 요청·이벤트·데이터가 이동하는 흐름
- 프로토콜 또는 벤더 모델과 우리 시스템 모델의 대응 관계
- 구현 시 보존해야 하는 식별자·필드·불변조건
- 정상 흐름과 함께 구분해야 하는 실패·대기·결과 불명 상태
- 팀에서 채택한 해석·설계 기준과 아직 확정되지 않은 항목

## 문서에 넣지 않는 내용

- “처음 볼 때는”, “먼저 이해해야 한다”, “외우기보다” 같은 독서 안내
- “읽고 나면 설명할 수 있어야 하는 것” 같은 학습 목표
- “왜 이 문서를 읽어야 하는가”를 설명하는 문단
- 독자를 가르치는 질문형 제목: “어디서부터 봐야 하나”, “쉽게 이해하는 방법”
- 제품 홍보 문구와 근거 없는 장점 요약
- 같은 내용을 쉬운 말, 표, 다이어그램으로 반복하는 불필요한 중복
- 별도의 `참고 자료` 목록

도메인에서 실제로 중요한 이유와 인과관계는 기록한다. 예를 들어 “왜 DvP가 두 자산을 한 트랜잭션으로 묶는가”는 개념 설명이다. 반면 “왜 DvP부터 읽어야 하는가”는 독서 안내이므로 넣지 않는다.

## 문서 시작 방식

제목은 개념이나 관계를 직접 이름 붙인다.

```text
권장: Canton Network의 거래 공개 범위
권장: Party와 Participant의 관계
권장: 출금 상태와 원장 반영 시점

지양: Canton Network, 어디서부터 봐야 하나
지양: Party를 쉽게 이해하기
지양: 먼저 알아야 할 세 가지
```

첫 문단은 2~4문장 안에서 다음을 밝힌다.

1. 대상 개념이 무엇인가
2. 다른 개념과 구분되는 경계가 무엇인가
3. 우리 시스템에서 어떤 의미로 사용하는가

```text
지양:
Canton을 처음 볼 때는 Party와 Participant부터 외우기보다 한 가지 차이를 먼저 잡는 편이 쉽다.

권장:
Canton은 기관 간 거래 내용을 전체 네트워크에 공개하지 않는다.
거래와 관계된 Party를 호스팅하는 Participant만 해당 거래에 필요한 원장 데이터를 받아 검증한다.
```

## 용어 사용

### 정의한 뒤 사용한다

본문과 다이어그램을 포함해 용어가 처음 등장하는 위치에서 의미를 알 수 있어야 한다. 다이어그램에서 먼저 사용하고 아래 문단에서 뒤늦게 정의하지 않는다.

```text
지양: 거래 View
권장: 거래에 필요한 원장 데이터
```

`Transaction View`가 문서의 주제가 되는 지점에서 다음처럼 정의한 뒤 `View`로 줄여 쓴다.

```text
Canton은 하나의 트랜잭션을 권한 범위에 따라 여러 부분으로 나눈다.
각 부분을 Transaction View라고 한다.
```

### 공식 용어와 팀 용어를 구분한다

- 프로토콜·API의 고유명사는 원문 표기를 유지한다: `Party`, `Participant`, `Contract ID`.
- 첫 등장에서는 한국어 설명을 붙인다: `원장 신원인 Party`, `Party를 호스팅하는 Participant`.
- 프로토콜 원문 상태와 내부 공통 상태를 같은 이름으로 덮어쓰지 않는다.
- 벤더마다 의미가 다른 이름은 어느 API 또는 제품의 표현인지 적는다.

### 모호한 대명사와 조건을 쓰지 않는다

`이것`, `해당`, `필요한 경우`, `지정한 경우`만으로 조건을 표현하지 않는다. 주체·위치·대상을 문장 안에 둔다.

```text
지양: 지정한 경우 감독기관에도 전달
권장: Daml 계약에서 감독기관을 Observer로 포함한 경우 해당 거래 내용을 전달
```

## 사실과 팀의 판단을 구분한다

문서에는 서로 다른 성격의 내용이 섞인다. 문장에서 근거 주체를 드러낸다.

| 구분 | 기록 방식 | 예시 |
|---|---|---|
| 프로토콜 사실 | 주체와 동작을 단정적으로 기술 | Participant는 호스팅 Party에게 공개된 활성 Contract를 저장한다. |
| 벤더 동작 | 제품·API·버전을 함께 기술 | Fireblocks 관리형 연결에서는 지원 Network와 Party 모델을 계약 기준으로 확인한다. |
| 팀 기준 | `우리 시스템에서는`, `팀 기준으로`를 명시 | 우리 시스템에서는 제출 접수와 원장 완료를 별도 상태로 관리한다. |
| 미확정 항목 | 가정과 확인 조건을 함께 기록 | Omnibus Party 사용 여부는 Memo 귀속 검증 결과에 따라 확정한다. |

외부 사실처럼 보이는 문장에 내부 설계 결정을 섞지 않는다. 팀의 선택이 바뀌어도 프로토콜 설명까지 다시 쓰지 않도록 경계를 분리한다.

## 문서 구조

모든 문서가 같은 목차를 가질 필요는 없다. 내용에 맞는 항목만 사용한다.

1. 개념 또는 시스템 경계
2. 구성요소와 관계
3. 상태·데이터·처리 흐름
4. 우리 시스템과의 대응 관계
5. 실패·예외·결과 불명 처리
6. 운영 또는 구현 시 확인할 항목

한 문서는 하나의 핵심 관계를 다룬다. 다음 중 둘 이상이 독립적으로 길어지면 문서를 나눈다.

- 개념 정의
- 데이터 필드
- 상태 전이
- 입출금 흐름
- 운영·장애 대응
- 벤더 연동

## 다이어그램

다이어그램은 본문을 읽지 않아도 주체와 관계를 해석할 수 있어야 한다.

### 화살표에 반드시 포함할 것

- 무엇이 이동하는가
- 누가 보내고 누가 받는가
- 조건이 있다면 어디에서 정한 조건인가

```text
지양: 기관 A -- 거래 View --> 기관 B
권장: Transaction -- 거래 당사자에게 원장 데이터 전달 --> 기관 A·B Participant

지양: -- 지정한 경우 --> 감독기관
권장: -- Daml 계약의 Observer인 경우 거래 내용 전달 --> 감독기관 Participant
```

### 서로 다른 관계를 한 그림에 섞지 않는다

- 가시성 그림은 누가 데이터를 받는지 보여준다.
- 전송 구조 그림은 Participant와 Synchronizer 사이의 실제 전달 경로를 보여준다.
- 책임 경계 그림은 시스템별 정본과 소유 책임을 보여준다.

개념상 관계를 실제 네트워크 호출처럼 그리지 않는다. 기관 A에서 기관 B로 직접 향하는 화살표는 직접 통신으로 오해될 수 있으므로, 전달 주체나 거래 객체를 가운데 둔다.

### 상태를 구분한다

- 대기, 성공, 실패, 결과 불명을 서로 다른 노드나 라벨로 표시한다.
- `Submit`과 `Commit`, `Detect`와 `Credit`처럼 시점이 다른 동작을 합치지 않는다.
- 일부 성공이 허용되지 않는 흐름은 실패 시 전체 결과도 함께 표시한다.

## 표와 필드

- 표의 각 열은 하나의 질문에 답한다.
- 상태 표에는 원문 상태, 내부 상태, 고객 영향 중 필요한 축을 구분한다.
- 필드 표에는 이름뿐 아니라 소유 시스템, 필수 여부, 멱등성·감사 용도를 기록한다.
- 프로토콜 필드와 내부 DB 필드를 같은 표에서 다룰 때 출처 열을 둔다.
- 값이 환경·버전·계약에 따라 바뀌면 고정값처럼 쓰지 않는다.

## 애니메이션

애니메이션은 시간 순서가 개념의 일부일 때만 사용한다.

- 트랜잭션 전달, Contract 상태 전이, DvP처럼 순서가 중요한 흐름에 사용한다.
- 용어 정의, 책임 경계, 데이터 필드에는 정적 다이어그램이나 표를 사용한다.
- 자동 재생을 기본값으로 두지 않는다.
- 한 장면은 4~7단계로 제한한다.
- 단계 제목은 실제 상태나 동작을 사용한다.
- 애니메이션 없이도 내용을 확인할 수 있도록 정적 다이어그램과 본문을 유지한다.
- Confluence와 HTML 가져오기에서 스크립트가 제거돼도 핵심 정보가 남아야 한다.

## 문장과 제목

- 설명형 평서문과 능동태를 기본으로 한다.
- 한 문장에 새로운 개념을 여러 개 도입하지 않는다.
- 제목은 `개념`, `상태`, `관계`, `흐름`, `책임`을 직접 나타낸다.
- `쉽게`, `먼저`, `핵심`, `한눈에`, `알아보기` 같은 편집자 표현은 의미가 없으면 제거한다.
- 강조는 결론이나 불변조건에만 사용한다.
- 영어를 나열하기보다 한국어 설명과 공식 용어를 함께 쓴다.

## 문서 메타데이터와 배치

온보딩 카드에 표시되는 문서는 다음 Frontmatter를 사용한다.

```yaml
---
title: 문서 제목
status: Done
date: YYYY-MM-DD
view: grid
group: 카드 묶음
---
```

- `title`은 카드만 보고 주제를 알 수 있게 작성한다.
- `group`은 상태가 아니라 개념 묶음을 나타낸다.
- 파일명 앞의 숫자는 같은 묶음 안의 순서에만 사용한다.
- 문서 간 링크는 상대 경로로 작성한다.
- 별도의 `참고 자료` 절은 만들지 않는다. 확인이 필요한 외부 사실은 해당 문장 가까이에 출처를 연결하거나 소스 저장소에서 관리한다.

## 검토 체크리스트

- [ ] 첫 문장이 독서 안내가 아니라 개념의 정의 또는 사실로 시작하는가
- [ ] 문서 제목이 질문이나 학습 순서가 아니라 대상을 직접 가리키는가
- [ ] 모든 공식 용어가 사용 전에 정의됐는가
- [ ] 다이어그램의 화살표에 주체·데이터·조건이 드러나는가
- [ ] 프로토콜 사실, 벤더 동작, 팀 기준, 미확정 항목이 구분되는가
- [ ] 제출·완료, 탐지·반영, 승인·서명처럼 다른 시점을 합치지 않았는가
- [ ] 실패·대기·결과 불명 상태가 정상 흐름과 함께 설명되는가
- [ ] 애니메이션이 없어도 같은 개념을 확인할 수 있는가
- [ ] `참고 자료`, 학습 목표, 독서 방법 문단이 없는가
- [ ] 상대 링크, Mermaid, HTML 내보내기에서 동일하게 읽히는가
