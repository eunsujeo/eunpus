# 트래블룰

트래블룰의 규제 배경부터 VASP 입출금 흐름, 솔루션 도달성, Fireblocks 연동과 우리 게이트 설계까지 한 번에 정리한다.

## 1. 10초 요약

트래블룰은 온체인 규칙이 아니다. 가상자산사업자(VASP)가 고객의 가상자산을 다른 VASP 로 옮길 때, **송금인·수취인의 신원 정보를 자산과 별개의 오프체인 채널로 주고받도록 법이 요구**하는 자금세탁방지(AML) 규제다. 은행 간 송금에서 SWIFT 메시지에 송·수취인 정보를 실어 보내던 규칙을 가상자산에 옮겨온 것이다.

- 국제 기준은 FATF 권고 16호다. 중심 의무는 송·수신인 정보를 **획득·보유·전송**하는 것이다. 거래 상대방의 제재 대상 여부 심사나 일반적인 기록 보관은 권고 16호 하나의 요구가 아니라, 다른 FATF 권고를 포함한 AML/CFT 체계 전반에서 함께 걸리는 의무다.
- 한국의 현행 정보 제공 의무는 **송신 VASP 중심**이다. 수신 거래소에도 정보 확보 의무를 부과하는 것은 2026년 정책 방향(9장)이며 아직 확정 시행이 아니다.
- 실무에서 이 규제는 두 지점에 나타난다: **출금은 보내기 전에 상대와 정보를 대조**하고, **입금은 정보가 안 맞으면 잔고 반영을 미룬다**. 다만 이 두 문장은 법 조문이 아니라 거래소 실무와 솔루션 동작의 요약이다(4장).

## 2. 규제 배경 — FATF 에서 특금법까지

FATF 권고 16호는 원래 전신송금(wire transfer)의 정보 투명성 규칙이었고, 2019년에 가상자산과 VASP 로 적용이 확대됐다. 한국은 이를 특정금융정보법(특금법) 시행령 **제10조의10(가상자산이전 시 정보제공)** 으로 받아 2022년 3월 25일부터 시행했다.

- **임계값**: 시행령 제10조의10 제1호가 "1백만원 이상에 상당하는 가상자산을 이전하는 경우"로 정한다. 원화 환산 기준은 금융정보분석원장 고시에 위임돼 있다.
- **제공 정보**: 송금인·수취인의 성명과 지갑 주소 등 시행령이 정한 신원 정보를 수취 VASP 에 제공해야 한다.
- **100만원 미만 분할 송금**: 임계값 아래로 쪼개 보내는 행위는 별도 규제 영역(의심거래 모니터링)에서 걸린다. 예를 들어 업비트는 "100만원 미만 입출금이 반복되면 이상 입출금으로 반려될 수 있다"고 안내한다. 이것은 거래소 운영 기준이지 트래블룰 조문 자체는 아니다.

국가별 도입 속도는 고르지 않다. FATF 의 2025년 6월 점검 기준으로 117개 관할권 중 85곳이 트래블룰 입법을 마쳤지만, 50곳은 아직 집행·감독 조치를 시작하지 못했다. 이 시차 때문에 한쪽 VASP 만 의무를 지는 비대칭 구간이 생기고, 해외 상대와의 이전에서 실무 문제가 된다.

참고로 FATF 는 2025년 6월 권고 16호 자체를 개정했다(지급 투명성 개편, 변경 사항은 2030년 말까지 효력 발생 예정). 이 문서가 다루는 국내 현행 제도는 그 이전 기준 위에 서 있다.

글로벌 임계값 비교는 부록 A 에 있다. 한국의 100만원은 FATF 권고치(USD/EUR 1,000)와 비슷한 수준이고, EU 는 임계값 없이 전 구간에 적용한다.

## 3. 주고받는 데이터 — IVMS101

VASP 끼리 주고받는 신원 메시지의 데이터 표준은 **IVMS101** 이다. 2020년 발표된 국제 표준이고, 현행판은 IVMS 101.2023 (Issue 1 FINAL)이다.

- 메시지는 Originator(송금인) / Beneficiary(수취인) / OriginatingVASP / BeneficiaryVASP / TransferPath / PayloadMetadata 여섯 객체로 구성된다.
- 필드 이름 규칙까지 표준이 정한다: 엔티티·컴포넌트는 대문자 카멜케이스, 하위 요소는 소문자 카멜케이스.
- 주요 솔루션(VerifyVASP·CODE·Notabene)은 모두 IVMS101 을 데이터 표준으로 쓴다. **갈리는 것은 데이터가 아니라 통신 아키텍처** — 상대를 어떻게 찾고, 메시지를 어떤 경로로 암호화해 보내는가다.
- 단, 표준과 제품 구현은 같지 않다. 예를 들어 VerifyVASP 의 API 스키마는 표준 대비 필드명과 확장 필드가 다르다. 연동 개발 시 표준 문서가 아니라 해당 솔루션의 스키마 문서를 봐야 한다.

전체 필드 정의는 표준 원문 PDF 를 참조한다.

## 4. 실무 두 흐름 — 출금과 입금

이 장은 법 조문이 아니라 **국내 거래소 실무와 솔루션 동작**의 서술이다. 업비트 공식 가이드와 각 솔루션 공식 문서를 근거로 한다.

### 4.1 출금 — 보내기 전에 대조한다

국내 거래소의 VASP 향 출금은 대체로 이 순서를 지난다.

1. **원화 환산 판정** — 출금 신청 시점의 시세로 환산해 100만원 이상이면 트래블룰 대상으로 지정한다. (여기까지가 법이 정한 기준)
2. **수취처 입력** — 이용자가 목적지 VASP 를 고르고 수취인 실명을 입력한다. 업비트 기준으로 개인 회원은 받는 사람 이름, 법인 회원은 법인명과 대표자 이름이다. (거래소 운영정책 — 거래소마다 다를 수 있다)
3. **VASP 간 신원 대조** — 송신 측이 신원 정보를 수취 VASP 로 보내고, 수취 측이 자기 KYC 데이터베이스와 성명 일치 여부를 확인한다. (법이 요구하는 정보 제공을 솔루션이 구현하는 지점)
4. **일치 시에만 온체인 전파** — 일치(Match) 응답이 와야 출금을 승인하고 블록체인에 전파한다. 불일치면 거절한다. (법은 정보 제공을 요구하고, "일치 확인 후 전파"는 오송금·위반을 막기 위한 실무 관행이다)

솔루션 공식 문서의 흐름도 같은 뼈대다. VerifyVASP 는 사전 검증 요청 → 비동기 검증 결과 → 유효 시 온체인 실행 → 트랜잭션 해시를 수취 측에 보고하는 순서를, CODE 는 VASP 목록 조회 → 주소 소유 확인 → 암호화된 이전 승인 요청 → 승인 후 온체인 → 결과 보고 순서를 정의한다.

### 4.2 입금 — 정보가 안 맞으면 잔고에 안 태운다

입금은 세 갈래로 갈린다. 업비트 가이드 기준:

| 갈래 | 조건 | 처리 |
|---|---|---|
| 즉시 반영 | 100만원 미만 / 연동 VASP 발 정상 식별 메시지 / 사전 등록된 본인 개인지갑 발 | 잔고 반영 |
| 입금대기 | 위 조건 밖의 100만원 이상 (미연동 사업자 발, 미등록 개인지갑 발 등) | 잔고 반영 차단, 계류 |
| 해제 또는 반환 | 입금대기 건에 대해 증빙 제출·심사 | 통과 시 반영, 준수 불가 판정 시 반환 |

핵심은 **온체인 입금 확정과 잔고 사용 가능이 별개**라는 것이다. 블록체인에서 확정된 입금이라도 트래블룰 대조를 통과하지 못하면 이용자 잔고로 풀리지 않는다. 이 구분은 8장의 우리 설계에서 그대로 이어진다.

## 5. 개인지갑은 다른 경로

메타마스크 같은 개인지갑(self-hosted wallet)과의 이전에는 상대 VASP 가 없으므로 **VASP 간 IVMS101 교환이 일어나지 않는다**. 그렇다고 트래블룰 시스템이 개인지갑을 아예 모르는 것은 아니다 — 두 층위를 구분해야 한다.

- **솔루션·벤더 구현 층위**: 목적지가 VASP 인지 개인지갑인지 판별하는 단계가 흐름에 들어 있다. 예를 들어 Fireblocks 의 사전 검증 API 는 대상 주소를 임계값 미만 / 개인지갑(NON_CUSTODIAL) / 트래블룰 대상으로 분류해 응답하고, Notabene 는 개인지갑 소유 증명 방식 4종(서명·자기 신고·소액 이체·화면 캡처)을 정의하며 그중 서명 증명만 소유 관계를 "입증됨(PROVEN)"으로 올린다.
- **국내 규제 대응·거래소 운영정책 층위**: 국내 거래소는 개인지갑을 사전 등록(화이트리스트)한 본인 지갑에 한해 자유로운 입출금을 허용한다. 업비트는 2026-08-18 기준 메타마스크(PC·모바일)·카이아·팬텀·폴카닷·케플러 5종의 등록을 지원하고, 등록 전에 들어온 입금은 폐기하지 않고 등록 완료 후 반영한다. 지원 지갑 목록과 등록 절차는 거래소마다 다르다.

즉 개인지갑 통제의 방어선은 트래블룰 망이 아니라 **각 VASP 가 자체 관리하는 등록부**다.

## 6. 솔루션 지형

이 장의 회원·규모 수치는 모두 **2026-08-18 기준**이며 수시로 바뀐다.

### 6.1 국내 두 진영

국내 시장은 두 진영으로 나뉜다. 업비트 계열이 쓰는 **VerifyVASP** 와, 빗썸·코인원·코빗 합작의 **CODE** 다. 2022년 3월 트래블룰 시행 직후에는 두 망이 연동되지 않아 진영 간 이전이 막혔다가, **2022년 4월 25일 상호 연동이 이루어져 4대 거래소 간 100만원 이상 입출금이 재개**됐다.

두 가지를 구분해야 한다.

- **기술적 상호운용**: CODE 공식 문서는 VerifyVASP·GTR·Sygna 와의 연동을 명시한다. 단 "VerifyVASP 솔루션 연동 거래소는 한국 국내 거래만 지원하며, 한국 밖 거래소와의 거래는 불가"라고 못박는다.
- **개별 도달성**: 망이 연동돼 있어도 특정 상대 VASP 와 실제로 입출금이 되는지는 각 회원사의 내부 심사·정책에 따라 별도로 정해진다. "상호 연동 완료 = 모든 회원과 거래 가능"이 아니다.

### 6.2 VerifyVASP

| 항목 | 내용 |
|---|---|
| 운영 주체 | 람다256 (두나무 계열) 이 개발·운영 |
| 연동 방식 | 각 VASP 인프라에 설치하는 Enclave 서버 + API. 메시지는 종단간 암호화되고 중앙 서버는 복호화 없이 중계만 한다 |
| 규모 | 회원 VASP 150+ · 30+ 관할권 (자사 공식 표기) |
| 특징 | 국내 최대 거래소(업비트) 진영. 해외 도달은 제한적(6.1 참고) |

### 6.3 CODE

| 항목 | 내용 |
|---|---|
| 운영 주체 | 빗썸·코인원·코빗 합작법인 |
| 연동 방식 | REST API + 페이로드 종단간 암호화(X25519·XSalsa20-Poly1305 계열, libsodium 권장)와 전 요청 서명. 선택형 암호화 서버 모듈(Cipher) 제공 |
| 특징 | VerifyVASP·GTR·Sygna 와 기술 연동 명시 |

### 6.4 해외: Notabene

Notabene 는 특정 망이 아니라 **프로토콜 비종속 게이트웨이**를 지향하는 SaaS 다. 자사 문서에서 TRP·OpenVASP·TRUST·TRISA·Sygna Bridge·VerifyVASP 등 여러 프로토콜을 다루며, "활성 VASP 가 있고 프라이버시·보안 요건을 충족하는 프로토콜을 지원한다"는 접근을 밝힌다. 2026-08-18 기준 이 목록에 CODE 와 GTR 은 없다. Fireblocks 의 기본 트래블룰 파트너이기도 하다(7장).

### 6.5 해외 기타

- **TRUST** — Coinbase 주도의 미국계 폐쇄형 연합. 2025년 초 기준 125개 이상 VASP 참여(2차 출처 기준).
- **GTR (Global Travel Rule)** — Binance 등 대형 거래소들이 참여하는 얼라이언스. Binance·OKX·Bybit 등이 멤버로 표기된다.
- **Sygna** — CoolBitX 계열의 상용 컴플라이언스 플랫폼(Bridge 가 트래블룰 제품).
- **TRISA** — 인증기관(CA) 모델을 쓰는 P2P 오픈소스 프로토콜.
- **TRP / OpenVASP** — 비영리 OpenVASP 협회가 유지하는 오픈 표준.

### 6.6 선택 기준 — 도달성부터

솔루션을 비교할 때 우리는 기능표보다 먼저 **도달성** — "우리 고객이 주고받을 상대 VASP 가 어느 망에 있는가" — 를 본다. 어떤 솔루션이 기술적으로 우수해도 상대가 그 망에 없으면 규제 의무를 이행할 수 없기 때문이다. 도달성이 유일한 기준은 아니지만, 충족하지 못하면 나머지 비교가 무의미해지는 첫 번째 필수 조건이다. 그리고 6.1 에서 본 대로, 망 차원의 도달성과 개별 상대와의 실제 거래 가능 여부는 또 별개로 확인해야 한다.

## 7. Fireblocks 는 어디까지 해주나

이 장은 전부 **Fireblocks 의 구현** 서술이다 (2026-08-18 기준).

- **활성화**: 트래블룰 기능은 워크스페이스에서 기본 비활성이며, Customer Success Manager 를 통해 활성화한다(별도 계약 범위).
- **통합 방식은 두 가지이며 배타적이라고 단정할 수 없다.** 다만 정책과 API 가 다르므로 한 흐름으로 섞어 읽으면 안 된다.

**Notabene 직접 통합**

- Notabene 계정의 API key·Secret·VASP DID를 Fireblocks 에 등록하는 기존 파트너십 경로다.
- 거래 한 건은 OFAC 제재 주소 대조(사용자 정책보다 먼저, 우회 불가) → AML 스크리닝 → 트래블룰 스크리닝 순서로 돈다. AML 에서 이미 고위험 판정이면 트래블룰 데이터 교환은 보통 진행되지 않는다.
- 정책은 ① Transaction Screening Policy(무엇을 검사할지)와 ② Post-Screening Policy(결과별 조치)의 2단이다. 출금은 Post-Screening 에서 Accept 가 떨어져야 비로소 서명할 수 있다.
- 입금 지연 30초(최대 7일)·출금 지연 0초(최대 90분)이며, **장애 시 우회(Skip on failure)가 기본 On** 이다. 스크리닝 실패·무응답을 통과시키는 이 기본값은 8장의 우리 결정과 반대 방향이다.
- 트래블룰 메시지는 암호화되어 Notabene 에 보관되고 Fireblocks 는 복호화 키를 갖지 않는다. 입금 건에 메시지가 없으면 Fireblocks 가 빈 메시지를 만들어 스크리닝을 시작한다.

**TRSupport (구 TRLink)**

- 여러 트래블룰 제공자를 같은 API 표면으로 연결하는 제공자 중립 통합 레이어다. 현재 통합 가이드는 Sumsub 과 GTR 을 명시한다.
- 정책은 ① Screening Policy, ② Missing Travel Rule Message Policy, ③ Post-screening Policy의 **3단**이다. 두 번째 정책이 트래블룰 메시지가 없을 때의 처리 방식을 별도로 정한다.
- 정적 문서만으로 실제 활성 파트너를 확정해서는 안 된다. 파트너 목록 API의 응답 예시에는 Notabene 이 나타나므로, 도입 시점에는 API 응답과 계약·워크스페이스 설정을 함께 확인한다.

KYT/AML 제공자는 Chainalysis·Elliptic 등이며, 공개된 Fireblocks 통합 문서에서 **VerifyVASP 직접 통합은 확인되지 않는다.**

## 8. 우리 설계

이 장은 법도 벤더 동작도 아닌 **우리 시스템의 결정**이다. 근거는 내부 설계 문서이며, 결정의 배경 사실만 각주를 단다.

- **우리는 트래블룰 게이트를 블록체인 매니저 밖, 업무 서비스층에 두기로 했다.** 판단은 트래블룰 솔루션이, 블록체인 연동은 매니저가, 순서 강제는 코어가 맡는다. 매니저는 규제 내용을 다시 판단하지 않고 승인 산출물을 운반해 거래를 제출한다.
- **첫 번째 방어선은 코어의 거래 상태 머신이다.** 검증 승인이 나기 전에는 출금 건이 매니저로 넘어가지 않는다.
- **두 번째 방어선은 서명 직전 검증이다.** API Co-signer 의 Callback Handler 가 대응하는 출금 요청의 존재·만료·승인 상태와 트래블룰 통과 여부를 다시 대조한다. 직접 호출이나 버그로 첫 번째 방어선을 우회한 거래도 여기서 서명을 만들지 못하게 한다.
- **우리는 fail-close 를 선택했다.** 검증 서비스 장애 시 외부 이체를 중단한다. Fireblocks 의 기본값(장애 시 우회 On)과 반대이므로, Fireblocks 를 쓰는 구간에서도 이 설정을 의식적으로 맞춰야 한다.
- **국내·해외 병행 라우팅.** 국내 상대는 국내 망으로, 해외 상대는 Notabene 계열로 라우팅한다. 배경: 국내 망(VerifyVASP)이 Fireblocks 제공자 목록에 없어서(7장), 국내 트래블룰 게이트는 벤더 표면 밖에서 우리가 직접 연동해야 한다.
- **입금은 온체인 확정과 가용 전이를 분리한다.** 블록체인 확정이 끝나도 컴플라이언스 통과 전에는 잔고를 사용 가능 상태로 올리지 않는다 (4.2 의 입금대기와 같은 구조).
- **개인지갑 등록부는 자체 DB 로 관리한다.** Fireblocks 의 Address Registry 는 블록체인 주소를 법인·LEI·트래블룰 제공자 정보에 연결하는 법인 식별 기능이지, 개인지갑 소유 증명을 보관하는 화이트리스트가 아니기 때문이다.
- **실패 자금 처리는 단계별로 다르다.** 출금 사전 검증 실패·상대 거부는 온체인 제출 전이므로 잠근 고객 잔액을 다시 가용화한다. 온체인 제출 뒤 실패한 출금은 블록체인 매니저의 실패 상태에 따라 복구한다. 소명에 실패한 입금은 가용 전이를 보류하지만, 이를 원 송출처로 반환하는 실행 경로는 아직 설계하지 않았다.

## 9. 2026 정책 방향 — 아직 확정이 아니다

이 장의 내용은 **미확정 정책**이다. 발표·입법 절차가 진행 중이며, 문장마다 출처 성격(정부 원문 / 언론 보도)을 구분해 적는다.

**금융위원회가 2026년 2월 5일 발표한 자금세탁방지 업무 수행계획**(정부 원문)은 트래블룰에 대해 세 방향을 밝혔다. 원문 표현은 모두 "~할 예정"이다.

1. 국내 거래소 간 적용 대상을 **100만원 미만 거래까지 확대**
2. 송신 거래소뿐 아니라 **수신 거래소에도 정보를 확보할 의무를 부과**
3. 개인지갑·해외사업자와의 **스테이블코인 거래에 위험기반접근에 따른 대응조치 의무를 부과**

확대의 배경으로 금융위 입법예고 보도자료는 "국내 가상자산사업자 간 이전거래의 60%(2025년 하반기, 건수 기준)가 100만원 미만"이라는 통계를 든다.

**진행 경과** (2026-08-18 기준):

- 개정 특금법(법률)은 2026-02-19 공포됐고 2026-08-20 시행 예정이다(금융위 보도자료 기준).
- 시행령·감독규정 개정안은 2026-03-30~05-11 입법예고를 거쳐 **2026-08-11 국무회의에서 의결**됐다(언론 보도 기준). 단 **트래블룰 확대(100만원 기준 폐지)와 개인지갑·해외사업자 규제는 8월 20일이 아니라 시행령 공포 후 6개월 뒤 적용**으로 보도됐다. 정확한 적용일은 공포된 대통령령 부칙으로 확인해야 한다.
- 입법예고 원안에 있던 "1,000만원 이상 해외 이전 일률 보고" 는 업계 의견 수렴 후 각 사업자의 위험평가 관리 방식으로 완화 조정됐다(언론 보도 기준).
- 입법예고 기간에 DAXA 소속 27개사가 연대 의견서를 제출해 검증 의무 부담과 해외 연동 축소를 우려했다(언론 보도 기준).

**규제 공백이 실제 분쟁이 된 사례**: 서울행정법원은 2026년 4월 9일 두나무(업비트)에 대한 FIU 의 3개월 영업 일부정지 처분을 취소했다. 100만원 이상 거래에는 미신고 사업자와의 거래를 차단할 명시 규제가 있지만 **100만원 미만 거래에는 구체적 규제가 없었으므로**, 사후에 조치가 부족했다는 이유만으로 고의·중과실을 인정할 수 없다는 취지다(언론 보도 기준, 판결문 원문 미확인). 100만원 미만 확대 추진과 맞닿아 있는 판결이다.

**요약하면**: "무엇이 바뀔지"의 방향은 정부 원문으로 확인되지만, "언제부터 어떤 조문으로"는 이 문서 기준일 현재 확정되지 않았다. 온보딩 후 실무에 들어갈 때는 반드시 그 시점의 공포된 법령을 다시 확인하라.
