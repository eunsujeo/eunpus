기존 발표자료는 폐기했다. 다음 작업에서는 웹 문서를 여러 장으로 나누는 방식이 아니라, 발표자가 말할 여백과 한 장의 메시지가 분명한 슬라이드를 처음부터 다시 만든다.
이 계획은 발표 목적, 이야기 순서, 시각 원칙과 검토 절차를 정한다. 실제 슬라이드 HTML은 아직 만들지 않는다.

## 1. 발표 목적

- **대상** — Canton을 처음 접하는 기획자·개발자·의사결정자.
- **발표 시간** — 10~15분.
- **한 문장 목표** — 청중이 “Canton은 프라이빗 체인을 하나 더 만든 것이 아니라, 거래별로 공개 범위를 달리하면서 기관들이 하나의 네트워크에서 거래하게 만든 구조”라고 설명할 수 있어야 한다.
- **범위** — 정의, 등장 배경, 퍼블릭·전통적 프라이빗 체인과의 차이, 핵심 구성요소, 한 거래가 확정되는 흐름.
- **제외** — 토큰 표준 상세, 운영 명령, API, 구축 절차, 수수료 수치, 수탁사별 연동 사양. 필요하면 별도 기술편으로 분리한다.

## 2. 이야기 순서

| 장 | 한 장의 질문 | 핵심 메시지 | 주된 표현 |
|---:|---|---|---|
| 1 | 모두가 검증하려면 모두가 봐야 할까? | 발표 전체를 관통하는 질문을 먼저 던진다. | 제목과 하나의 대비 장면 |
| 2 | 퍼블릭 블록체인은 어떻게 신뢰를 만드나? | 모든 노드가 같은 원장을 받아 검증하는 전역 복제가 신뢰의 기반이다. | 하나의 거래가 전체 노드로 퍼지는 그림 |
| 3 | 기관 거래에서는 무엇이 문제가 되나? | 금액·상대·시점·계약 조건의 전역 노출은 기관의 사업 기밀과 충돌한다. | 2장의 같은 그림에서 노출 정보만 강조 |
| 4 | 전통적 프라이빗 체인은 무엇을 해결했나? | 접근을 제한해 프라이버시는 얻지만 네트워크가 사일로로 나뉜다. | 서로 연결되지 않은 원장 섬 |
| 5 | Canton은 질문을 어떻게 바꿨나? | 원장을 통째로 공개하거나 가두지 않고 거래별 당사자에게 필요한 뷰만 전달한다. | 하나의 거래가 서로 다른 뷰로 분해되는 대표 그림 |
| 6 | 퍼블릭·프라이빗·Canton은 무엇이 다른가? | 차이는 공개/비공개 이분법이 아니라 데이터 배포와 검증 범위다. | 세 모델의 동일 축 비교 |
| 7 | 누가 무엇을 맡나? | Party는 주체, Participant는 거래 검증·보관, Synchronizer는 순서·확정을 조정한다. | 역할 3개만 남긴 구조도 |
| 8 | 거래 한 건은 어떻게 확정되나? | 제출 → 당사자별 뷰 → 순서화 → 관련 참여자 검증 → 확인 → 커밋으로 진행된다. | 한 방향 흐름 애니메이션 |
| 9 | 그래서 어디에 적합한가? | 기관 간 자산·계약·DvP처럼 연결성과 기밀성이 동시에 필요한 거래에 맞는다. | 두 기관의 원자적 정산 사례 |
| 10 | Canton을 한 문장으로 말하면? | 거래별 공개 범위와 검증 주체를 설계하는 기관용 네트워크다. | 첫 질문에 대한 짧은 답 |

## 3. 시각 방향

### 핵심 장치

발표 전체에서 **같은 거래 한 건**을 반복해서 사용한다. 2장에서는 모든 노드에 복제되고, 4장에서는 폐쇄된 원장 안에 갇히며, 5장에서는 당사자별 뷰로 나뉜다. 청중은 매번 새로운 도식을 해석하지 않고 데이터가 전달되는 범위의 차이만 비교한다.

### 색과 활자

| 역할 | 값 | 사용 원칙 |
|---|---|---|
| 깊은 남색 | `#101C3C` | 제목·핵심 구조 |
| 종이색 | `#F5F8FC` | 기본 배경 |
| 코발트 | `#2C5BFF` | 거래와 활성 흐름 |
| 시안 | `#27C2D1` | Canton의 선택적 연결 |
| 슬레이트 | `#667085` | 보조 설명 |
| 경고색 | `#D97706` | 노출·충돌을 설명할 때만 제한 사용 |

- 제목은 **Pretendard Variable 700~800**, 본문은 **Pretendard 400~600**, 식별자와 단계 표기는 **IBM Plex Mono**를 쓴다.
- 한 장에는 제목 하나, 결론 문장 하나, 주 시각 요소 하나만 둔다.
- 본문은 가급적 40단어 이내로 제한하고 나머지 설명은 발표자 노트로 옮긴다.
- 카드 격자, 장식용 배지, 의미 없는 번호와 그라데이션은 사용하지 않는다.

## 4. 화면 규격과 동작

- 기본 화면은 16:9이며 회의실 프로젝터에서 읽히는 크기를 우선한다.
- HTML 한 파일로 만들고 외부 CDN·웹폰트에 의존하지 않는다.
- 키보드, 클릭, 터치 이동과 전체화면을 지원한다.
- 인쇄 시 각 슬라이드가 PDF 한 페이지에 정확히 들어가야 한다.
- 애니메이션은 8장의 거래 흐름 한 곳에 집중하고 `prefers-reduced-motion`을 지원한다.
- 블록체인 매니저에서는 `캔톤네트워크 → 발표자료`에 단일 문서 뷰로 연결한다.

## 5. 제작 순서

1. **스토리보드** — 10장의 제목·결론 문장·발표자 멘트를 텍스트로 먼저 확정한다.
2. **핵심 3장 시안** — 2장(퍼블릭), 5장(Canton), 8장(거래 흐름)만 만들어 서사와 시각 언어를 검증한다.
3. **전체 제작** — 시안 승인 후 나머지 장을 같은 규칙으로 확장한다.
4. **발표 리허설** — 10~15분 안에 설명되는지 확인하고 화면의 설명문을 덜어낸다.
5. **배포 검증** — 데스크톱·모바일·프로젝터 비율, 키보드·터치·전체화면·PDF를 확인한 뒤 블록체인 매니저에 배포한다.

## 6. 세 번의 리뷰

| 차수 | 검토 대상 | 통과 기준 |
|---:|---|---|
| 1차 | 내용과 서사 | 퍼블릭 → 프라이빗 → Canton → 동작 방식이 끊기지 않고 이어진다. |
| 2차 | 시각과 발표성 | 각 장을 3초 안에 훑어 핵심을 파악할 수 있고, 발표자가 말할 여백이 있다. |
| 3차 | 기술과 배포 | 깨진 글꼴·잘림·스크롤이 없고 입력 방식과 PDF 출력이 모두 동작한다. |

각 리뷰에서 수정 목록을 먼저 기록한 뒤 반영한다. 같은 장을 즉흥적으로 여러 번 덧붙이지 않는다.

## 7. 완료 조건

- 10장 모두 한 장에 하나의 주장만 담는다.
- 2·4·5장이 같은 거래를 사용해 세 모델의 차이를 직접 비교한다.
- 6장의 비교 축과 7~8장의 용어가 저장소의 Canton 개념 문서와 일치한다.
- 발표자 노트를 제외한 본문만 읽어도 흐름이 이어진다.
- 10~15분 리허설과 세 차례 리뷰를 통과한다.
- 최종 HTML과 PDF가 블록체인 매니저에서 동일한 내용으로 열린다.
