Canton 원장이 참여자 노드의 PostgreSQL 에 영속된다는 구조에서 나오는 운영 질문을 모았다. 개념 12장은 원장이 **어떻게 동작하는가**를 설명하는 문서라 **누가 어떤 절차로 운영하는가**는 다루지 않는다.

아래 항목이 **Canton 에 그 기능이 없다는 뜻이 아니다.** 우리가 가진 자료에서 확인되지 않아 물어야 한다는 뜻이다. 답을 채우기 전까지는 설계 전제로 쓰지 않는다.

## 출발점 — 로컬 DB 를 조작하면 어디까지 되나

이 문서가 나온 질문이다. 개념 문서에서 확인되는 범위는 이렇다.

| | 근거 |
|---|---|
| **안 된다** — 내 DB 를 고쳐 없던 자산을 만들어 상대에게 인정받기 | 공유 컨트랙트는 당사자 노드 모두에 동일 사본으로 남는다 ([6장](../개념/06-architecture.md)) · 상태 변경은 이해관계자가 검증·confirm 해야 확정된다 ([3장](../개념/03-transaction-view.md)·[8장](../개념/08-transaction-flow.md)) · 순서는 시퀀서의 암호화 스트림이 기준이다 (6장) |
| **된다** — 나를 차단, 내 데이터 노출, 로컬 파티면 내 이름으로 서명, 내가 보는 화면을 속이기 | [11장](../개념/11-trust-model.md) ① 내 밸리데이터는 "가장 센 신뢰" 영역 · 로컬 파티는 키를 노드가 보관한다 ([4장](../개념/04-parties-and-components.md)) |

11장이 완화책으로 외부 파티(자기수탁)·다중 호스팅·직접 운영·KMS/HSM 을 든다. 외부 파티로 키를 직접 쥐면 위 표의 "내 이름으로 서명"이 사라진다.

정리하면 **원장의 권위는 DB 가 아니라 다자 확인을 거친 합의 결과에 있고, DB 는 그 결과의 로컬 사본이다.** 조작은 남을 속이는 데 쓰이지 못하고, 내 노드가 나를 상대로 하는 쪽에서만 문제가 된다.

여기서 다음 질문이 남는다 — 그 로컬 사본이 손대졌는지 **내가 어떻게 아는가.**

## 확인이 필요한 것

### Q1. 로컬 원장의 변조를 어떻게 탐지하나

내 노드 DB 가 손대졌는지 확인할 수단이 제품에 있는가. 상대 노드와 사본이 어긋났을 때 **어느 시점에 드러나고 무엇을 근거로 판정**하는가. 어긋남이 확인된 뒤의 복구 경로는 무엇인가.

우리 자료 상태 — 개념 12장에서 머클 루트·자체 감사·정합성 점검에 해당하는 서술이 **0건**이다. 11장이 완화책으로 "서명된 감사 추적"을 한 번 언급하지만 형식과 검증 방법은 없다.

### Q2. 백업과 복구 절차

참여자 노드 내부 PostgreSQL 은 원장·시퀀서 클라이언트·토폴로지·밸리데이터 앱 **네 스토어**로 나뉜다 (6장). 백업을 어느 단위로 뜨며, 스토어 사이 시점이 어긋난 백업으로 복구하면 어떻게 되는가. 복구 후 시퀀서 스트림을 offset 이후부터 재생해 따라잡는 절차가 표준으로 있는가.

우리 자료 상태 — 백업·복구 서술 **0건**. 6장이 "오프라인이던 노드는 자기 offset 이후를 재생해 따라잡는다"고 적지만 이는 정상 운영 중 단절을 말하는 것이고, 백업 복구를 다룬 것이 아니다.

### Q3. 보존 연한과 pruning 정책

6장에 "디스크 절약을 위해 오래된 보관(archived) 이벤트는 pruning 할 수 있지만 활성 컨트랙트(ACS)는 남는다" 한 줄이 있다. 여기서 더 필요한 것 — pruning 의 단위·주기·되돌릴 수 있는지, 이해관계자 사이에 pruning 시점이 달라도 되는지, 그리고 **금융 규제의 기록 보존 요구와 어떻게 맞추는지.**

우리 자료 상태 — 위 한 줄이 전부다. 정책·절차 **0건**.

### Q4. 용량 산정

상태 변경이 보관+생성이라 **append-only 로 쌓인다** (6장). 거래량 대비 증가율, ACS 와 이벤트 로그의 비율, PQS 조회용 DB 까지 포함한 전체 산정 기준이 필요하다.

우리 자료 상태 — 용량·스토리지 산정 **0건**.

### Q5. 노드 업그레이드와 스키마 마이그레이션

내부 스토어 스키마가 Flyway 로 **버전마다 바뀌는 구현 세부**라고 6장이 적는다. 업그레이드 중 노드 가용성은 어떻게 되는가, 롤백이 가능한가, 상대 노드와 버전이 다른 기간에 거래가 되는가.

우리 자료 상태 — Flyway 를 쓴다는 서술뿐. 절차·제약 **0건**. 11장 ⑤는 프로토콜 업그레이드를 거버넌스 신뢰 항목으로 다루지만 내 노드의 운영 절차와는 다른 이야기다.

### Q6. 가용성과 다중 호스팅

11장이 완화책으로 "여러 밸리데이터로 다중 호스팅"을 들고 4장도 "한 파티를 여러 노드가 함께 호스팅할 수 있다(복원력)"고 적는다. 실제로 어떻게 구성하며, 한 노드가 죽었을 때 그 파티가 계속 거래할 수 있는가, 노드 사이 동기화는 어떻게 이뤄지는가.

우리 자료 상태 — 가능하다는 언급만 있고 구성·운영 방법 **0건**.
