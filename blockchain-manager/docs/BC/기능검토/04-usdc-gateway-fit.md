**USDC Gateway 는 검토 중이고 아직 설계에 넣지 않았다.** 이 문서는 **고객자산(옴니버스)에 붙일 경우** 우리 쪽에서 손대야 하는 것과 정해야 할 것을 모은다. [운영 설계](07-usdc-gateway-operating.md)는 회사자산 vault 를 먼저 두는 안이라 아래 항목 대부분이 그 단계에서는 걸리지 않는다 — 고객자산 쪽을 다시 볼 때의 재료다. 벤더 기능 자체의 성질은 [기능](02-usdc-gateway.md), 어느 vault 에 붙이는지는 [배치](03-usdc-gateway-placement.md).

## vault 넷과 Gateway 잔액

| 어디 | 하는 일 | 핫인가 |
|---|---|---|
| 고객 vault | 고객 입금 수신. 보관처가 아니다 | 핫 |
| **옴니버스 vault** | sweep 이 모이는 보관처 | 핫 |
| **출금 풀 vault** | 타VASP 송금이 나가는 창구. 복수 vault round-robin | 핫 |
| **Gateway 잔액** | 체인 변환용 완충. 자금은 Circle 컨트랙트에 있다 | **도입 시 정할 것** — 총자산합에는 반드시 들어간다 |
| 콜드월렛 | 현 설계에 없음 | 콜드 |

앞의 셋은 20% 규제의 핫으로 센다 — [sweep](../설계/06-sweep.md) 밴드S 산식에 그렇게 들어가 있다. **Gateway 잔액은 그 산식 밖이다.** 채택하면 핫으로 세는 것이 우리 제안이지만, 벤더 문서는 제품의 인출 방식만 설명하고 규제 산식에서의 분류를 다루지 않는다. 규제·정책 확인 대상이다.

### 두 밴드의 대상이 다르다

| | 대상 | 왜 |
|---|---|---|
| **밴드S** — 핫 비율 | 고객 vault + 옴니버스 + 출금 풀 | 총자산합이 100% 여야 규제 비율이 맞는다. Gateway 잔액은 도입 시 추가 판단 |
| **밴드C** — BC자산별 재고 | **출금 풀** | 타VASP 송금이 나가는 곳의 재고를 본다 |

같을 이유가 없다. 밴드S 는 규제 분모라 전부 덮어야 하고, 밴드C 는 나갈 수 있는지를 보므로 나가는 곳만 본다.

| 이동 | 밴드S | 밴드C |
|---|---|---|
| 옴니버스 → 출금 풀 | 불변 | **증가** — 재고 보충 |
| Gateway 인출 → 출금 풀 *(도입 시)* | 분자 판단에 달림 | **증가** — 재고 보충 |
| 옴니버스 → Gateway *(도입 시)* | 분자 판단에 달림 | 불변 — 둘 다 밴드C 밖 |

## Gateway 는 재고 보충 수단이다

[브릿지 — 문제](../../블록체인매니저/브릿지/01-problem.md)의 밴드C 는 타VASP 로 나갈 재고를 BC자산별로 관리한다. Gateway 는 그 재고를 채우는 자리에 놓인다.

**인출 목적지는 출금 풀 vault 로 두는 것이 안이다.** 밴드C 하한이 미달인 BC자산을 목적지 체인으로 지정해 채운다. 타VASP 송금은 지금대로 출금 풀에서 나간다. 브릿지교환·콜드교환에 이은 세 번째 보충 수단이다.

옴니버스로 받아 거기서 출금 풀로 나누는 선택지가 남아 있다 — 자기 vault 를 인출 목적지로 지정할 수 있는지가 미확인이라 아직 못 고른다(아래 "확인해야 풀리는 것").

따라오는 것 셋.

- **소스 체인을 지정 못 하는 것이 문제되지 않는다.** 인출로 줄어드는 것은 Gateway 잔액이고, 우리가 정해야 하는 값(어느 BC자산을 채울지)은 목적지 쪽이라 그대로 우리 손에 있다.
- **예치 확정 대기가 고객 송금에 안 걸린다.** Gateway 잔액이 아직 확립되지 않았으면 일부 체인은 약 13~19분이 필요한데([참고](99-circle-gateway.md)), 재고 보충은 미리 하는 일이라 그 대기가 송금 흐름 밖에 있다. 이미 확립된 잔액을 Fireblocks 로 인출하는 데 걸리는 시간은 실측이 필요하다.
- **기존 출금 경로를 안 건드린다.** 타VASP 송금은 출금 풀에서 TAP·gasless·컴플라이언스 게이트를 그대로 지난다.

## Gateway 잔액은 재고가 아니라 완충이다

Gateway 잔액은 출금 풀이 아니므로 밴드C 밖이다. 체인별 내역이 없어서가 아니다 — 잔액 조회가 `balanceBreakdown` 으로 체인별 내역을 준다([기능](02-usdc-gateway.md)).

재고로 못 세는 이유는 **그 구성을 우리가 통제하지 못하기 때문**이다. 인출할 때 소스 체인을 지정하는 자리가 없어 어느 체인 몫이 줄어들지 벤더가 정한다. 어느 BC자산으로 쓸지는 **인출해서 출금 풀에 들어온 순간** 정해진다.

그래서 Gateway 잔액은 **재고가 아니라 재고로 바꿀 수 있는 완충**이고, 인출이 밴드C 를 실제로 늘린다.

## 옴니버스 ↔ 출금 풀 이동 정책

**이 이동이 곧 밴드C 보충이다.** 밴드S 는 안 바뀌고 밴드C 만 늘어난다. 브릿지교환·콜드교환·Gateway 인출과 나란히 놓이는 네 번째 경로이고, 상대가 우리 옴니버스라 가장 싸고 빠르다.

| 정해야 할 것 | 지금 상태 |
|---|---|
| 트리거 | **밴드C 하한 미달**. 별도 기준이 필요 없다 |
| 판정 주체 | 값이 온체인 잔액뿐이라 매니저가 알 수 있다. 밴드S 처럼 코어 판정이 필요한지는 정해진 것이 없다 |
| **옴니버스에 그 BC자산이 없으면** | 이 경로로는 못 채운다. 브릿지교환·콜드교환·Gateway 인출로 넘어가는 판단이 절차에 필요하다 |
| **복수 출금 풀에 어떻게 배분하나** | 출금 풀은 round-robin 복수 vault 다. **재고가 없는 풀을 round-robin 이 고르면 그 출금이 실패한다.** 풀마다 채울지, 고를 때 잔액을 볼지 |
| 되돌리는 방향 | 출금 풀 초과분을 옴니버스로 되돌릴지, 콜드로 뺄지. 콜드 계층이 아직 없다 |
| 가스 | [대납 적용 범위](../설계/02-bcm-flow.md) 표에 이 이동이 없다. 내부이체처럼 다루면 "미확정 — 켜지 않는다" 라 옴니버스에 native 자산이 있어야 성립한다 |
| 이벤트 | 4 토픽 중 어디로 가는지 없다. 대사에는 잡혀야 한다 |
| 승인 절차 | 아래 참조 |

## 운영 영역 — 층 셋으로 갈린다

옴니버스와 출금 풀을 **다른 vault 로 두는 것은 확정**이다. 운영을 어디까지 나누느냐가 남는다.

| 층 | 상태 |
|---|---|
| **벤더 정책(TAP)** | **분리 강제.** 옴니버스는 나가는 목적지가 전부 고정이라 화이트리스트로 잠근다. 출금 풀은 고객이 지정한 임의 주소라 한도로만 통제한다. 한 정책 묶음에 넣으면 둘 중 하나가 망가진다 |
| **시스템** | **이미 분리.** 출금 이벤트 파티션 키가 출금 풀 accountId 이고, 대사도 항을 갈라 센다. 다만 `sys_acnt_role_dvcd` 에 두 역할 값이 없어 표현할 자리가 없다 |
| **사람·절차** | **열려 있다.** 문서에 운영 주체·승인자가 정의된 적이 없다 |

벤더가 이미 주는 경계가 하나 있다 — **엔드포인트 권한**이다([기능](02-usdc-gateway.md)).

| 동작 | 허용 역할 |
|---|---|
| 활성화·비활성화·자동 입금 설정/변경/중지 | Admin · Non-Signing Admin · Signer · Approver |
| 조회 | 위 + Editor · Viewer |

읽기는 Viewer 까지 열리고 쓰기는 Approver 이상이다. 사람 층을 나눌 때 이 등급을 그대로 쓸 수 있다.

사람 층이 [출금 흐름](../설계/02-bcm-flow.md)의 피해 상한과 맞물린다. 백엔드를 장악당해도 피해가 출금 풀 재고에서 캡되는데, **재고를 채우는 권한과 출금을 내는 권한이 같은 손에 있으면 그 상한은 숫자만 남는다.**

**Gateway 인출이 곧 재고 보충 행위**라 이 승인 절차를 탄다. [기능](02-usdc-gateway.md)의 자동 입금은 옴니버스 → Gateway 방향이라 경계 안이고, 벤더가 문서화한 자동화는 입금뿐이다.

## 한도 — 20% 계산에서 무엇으로 셀지

Gateway 잔액은 각 체인의 Circle 컨트랙트에 있어 **우리 vault 잔액이 아니다.** Circle 은 이 컨트랙트를 비수탁으로 규정하고 7일 무신뢰 인출 경로를 둔다([참고](99-circle-gateway.md)).

**두 판단을 나눠야 한다.**

| | 도입하면 |
|---|---|
| **총자산합**(분모) | **반드시 포함.** 고객자산이므로 빼면 분모가 100% 가 안 되고 비율 자체가 틀린다 |
| **핫월렛합**(분자) | **판단 대상.** 핫 · 콜드 · 별도 항목 중 무엇으로 볼지 |

분자 쪽 **제안은 핫으로 세는 것이다.** 인출이 API 호출로 끝나 사람 손이 필요 없다는 점이 근거인데, **Fireblocks 인출에 실제로 얼마나 걸리는지는 실측 전이다.**

이 제안대로면 **Gateway 로 옮겨 두는 것이 20% 한도를 늘려 주지 않는다.** 옮겨도 핫월렛합이 그대로다. 반대로 핫에서 빼면 한도가 늘어나는 셈이 되므로 규제 판단이 필요하다.

잔액 값은 [Gateway 전용 조회 API](02-usdc-gateway.md) 로 가져온다. 일반 vault 조회에도 나타나는지는 확인되지 않았다.

다만 **응답 스키마가 문서마다 다르다** — API 가이드·Overview 는 두 필드를 준다고 하고 OpenAPI 에는 없다([기능](02-usdc-gateway.md)). 실측으로 가려야 이 절의 계산 입력이 확정된다.

## 감지 — 우리가 낸 거래가 웹훅으로 돌아온다

Gateway 입금·출금·승인은 모두 표준 Fireblocks 거래라 **다른 전송과 똑같이 웹훅을 낸다.** 그래서 감지가 세 종류를 구분해야 한다.

| 종류 | 무엇 | 구분 못 하면 |
|---|---|---|
| 고객 입금 | 외부 → 고객 vault | — |
| Gateway 입금 | 옴니버스 vault → 같은 vault 의 Gateway 지갑 | 우리가 옮긴 것을 고객이 새로 넣은 것으로 센다 |
| 승인 | 첫 Gateway 입금에 앞서 Fireblocks 가 자동 생성하는 `APPROVE`. 거래 목록에는 별도 항목으로 뜨지만 웹훅의 목적지·금액 필드 형태는 확인 안 됨 | 자금 이동이 아닌 거래가 파이프라인에 흘러든다 |

**정할 것 — 무슨 필드로 가르나.** 후보는 `subType: VIRTUAL_ACCOUNT`, 거래 종류(`APPROVE`), 제출자(`USDC Gateway Depositor`)다. 다만 **Gateway 입금·출금이 `networkRecords` 와 웹훅에 어떤 형태로 오는지 확인된 것이 없다**([기능](02-usdc-gateway.md)). 실측 전에는 구분 규칙을 확정할 수 없다.

## 완료 판정 — `COMPLETED` 를 가용 잔액으로 읽으면 안 된다

입금 거래의 `COMPLETED` 는 **우리 워크스페이스 확정 정책**을 기준으로 나므로 **Circle 잔액 반영보다 먼저 표시될 수 있다.** Circle 쪽 예치 확정은 Base·이더리움 계열에서 약 13~19분이 걸린다([참고](99-circle-gateway.md)).

**정할 것 — 브릿지에 쓸 수 있는 잔액의 근거를 무엇으로 두나.** 거래 상태로는 알 수 없으므로 잔액 조회 API 를 별도로 봐야 한다. 조회 주기와 그 값을 어디에 보관할지가 남는다.

## 자동 입금과 재고 관리가 서로 밀 수 있다

고객 vault 에 자동 입금을 켜면 sweep 과 같은 잔액을 두 주체가 노린다 — 이건 [배치](03-usdc-gateway-placement.md)에서 옴니버스에만 활성화하기로 해 없앴다.

남는 것은 옴니버스 쪽이다. **자동 입금이 옴니버스의 온체인 USDC 를 다 쓸어 담으면 출금 풀을 온체인 전송으로 채울 잔액이 남지 않는다.** 그때는 Gateway 인출로만 채우게 된다. `balanceThreshold` 를 얼마로 둘지가 곧 둘 중 어느 쪽을 기본 경로로 둘지를 정하는 것이라, 위 이동 정책과 같이 정한다.

## 정책·운영

- 입금에 **룰 두 개**가 필요하다 — 승인용과 전송용. 없으면 활성화돼 있어도 막힌다.
- 자동 입금을 켜면 **initiator 를 `USDC Gateway Depositor` 로 둔 룰**이 하나 더 필요하고, 이 서비스 유저는 서명을 못 하므로 별도 서명자를 지정해야 한다.
- 화이트리스트를 쓰는 구성이면 **체인마다 Gateway 컨트랙트 주소를 등록**하고 admin quorum 승인을 받는다.
- **승인 거래는 쓰는 체인 수만큼** 나온다. 활성화는 vault 당 1회지만 승인은 `(주소, 체인)` 마다 1회다.

## 자산 범위

**USDC 전용이다.** 원화 SC 에는 못 쓴다. 브릿지 수단이 자산마다 갈리므로, 다루는 BC자산 목록이 확정돼야 이 장의 판단이 어디까지 적용되는지 정해진다([브릿지 — 선택지](../../블록체인매니저/브릿지/02-options.md)).

## 확인해야 풀리는 것

| 미확인 | 어떻게 확인 | 무엇이 걸려 있나 |
|---|---|---|
| Gateway 입금·출금의 기록·웹훅 형태 | 실측 | 감지 구분 규칙 |
| 자동 입금 시 `APPROVE` 의 initiator | 실측 또는 벤더 문의 | 승인용 정책 룰 구성 |
| 활성화가 웹훅을 내는지 · vault 조회에 보이는지 | 실측 | 활성화 여부를 무엇으로 아는가 |
| 출금 실패 시 자금 위치와 상태 | 실측 또는 벤더 문의 | 실패 처리 절차 |
| 벤더를 통했을 때의 실제 소요 시간 | 실측 | 브릿지 가용 시점 판단 |
| Gateway 가 결속된 **같은 vault** 를 인출 목적지로 지정할 수 있는지 | 실측 또는 벤더 문의 | 인출을 그 vault 로 받아 거기서 나눌 수 있는지. **다른 vault 와 일회성 주소는 공식 예제로 확인됐다** |

실측은 워크스페이스에서 기능이 켜져야 가능하다.

## 정하는 순서

1. **밴드C 상한·하한 값** — 하한은 출금이 나갈 수 있는 최소, 상한은 한 번에 나갈 수 있는 최대다. **상한이 곧 피해 상한은 아니다** — 권한 분리·기간당 누적 한도·보충 승인이 함께 서야 성립한다([브릿지 — 문제](../../블록체인매니저/브릿지/01-problem.md))
2. **복수 출금 풀 배분 규칙** — 밴드C 를 풀별로 볼지 합으로 보고 배분만 나눌지. round-robin 이 고를 때 잔액을 보게 할지
3. **운영 영역 분리** — 재고를 채우는 권한과 출금을 내는 권한을 나눌지
4. 가스·이벤트·되돌리는 방향

전부 브릿지 밖의 결정이다. Gateway 는 그 위에 얹히는 보충 수단이라, 이 순서가 서면 따라 정해진다.
