벤더 정책(Fireblocks Policy Editor·Compliance)의 편집·게시를 대행하는 별도 서비스의 범위·경계 결정을 기록한다.
본격 설계 전의 시드 문서 — 확정된 결정과 열린 결정만 담는다.

## 무엇을 하는 서비스인가

Admin 백엔드의 정책 작업을 벤더 API 로 대행한다.

```
Admin 백엔드 ──(정책 편집·게시 요청)──▶ 정책 관리 서비스 ──(Policy Editor API)──▶ Fireblocks
```

대행하는 작업 (벤더 API 표면 기준):

- 활성 정책·검증 결과 조회, 활성 드래프트 조회 (Policy Editor)
- 드래프트 규칙 갱신, 게시 요청 (Policy Editor)
- AML·트래블룰 스크리닝 정책 조회 (Compliance)

## 왜 블록체인 매니저와 분리하나

거래 제출 자격과 정책 편집 자격을 **프로세스·배포·운영 권한부터 분리**한다. 한 서비스에 두 자격이 함께 있으면, 그 서비스가 장악됐을 때 정책을 완화하고 그 정책으로 거래를 제출하는 것까지 한 경로에서 가능해진다.

- 블록체인 매니저의 벤더 API user 는 **거래 제출 역할로 한정**한다.
- 정책 편집용 벤더 API user 는 이 서비스에만 둔다.
- 얇은 프록시로 유지한다 — 규칙 구조는 벤더 특화 그대로 운반하고, 이 서비스는 인증(Admin 백엔드만 호출)·감사 로깅·자격 관리만 한다.

## 경계

- **게시 발효는 벤더 거버넌스가 최종 관문** — 게시 요청까지가 이 서비스의 일이고, 발효는 Admin Quorum + Owner 승인(벤더 쪽 사람 승인)으로 완결된다.
- 서명 직전 검증(Callback Handler)·TAP 강제는 이 서비스와 무관 — [블록체인매니저 6장](../../블록체인매니저/설계/06-withdrawal.md) 소관.
- 업무 승인 체계(누가 어떤 한도를 승인하나)는 백엔드(Admin) 도메인 — 이 서비스는 벤더 정책의 운반만 한다.

`approve + transferFrom` sweep 정책도 같은 경계를 따른다. 고객 vault의 approve 허용 범위와 운영 계정의 batch Contract Call 규칙은 이 서비스가 편집·게시 요청하지만, 거래 제출은 블록체인 매니저, calldata 최종 검증은 Co-signer Callback, 컨트랙트 pause·운영자 변경은 보안 관리자 multisig가 맡는다. 한 주체가 정책 완화와 자금 이동을 함께 수행하지 않는다([sweep 권한 정책](../../BC/설계/06-sweep.md#보안-권한-정책)).

## 열린 결정

1. **코드베이스** — 완전 별도 서비스 vs 블록체인 매니저와 같은 코드베이스의 별도 배포 단위. 자격·배포 분리는 어느 쪽이든 확보된다.
2. **블록체인 매니저 운영 값 주입 채널** — boost 대기 임계·최대 시도 같은 값을 설정 배포로 줄지, 이 서비스에 얹을지.
