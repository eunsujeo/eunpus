매니저 안의 어떤 장치도 매니저 자신이 죽은 것은 못 잡는다 — 막힘 점검은 "tx 가 막힘"을 보지 "수신이 멈춤"을 보지 않고, 매니저 안에서 올리는 경보는 매니저가 죽는 순간 같이 멈춘다.
그래서 **안 = 행동**(막힘 점검·자동 boost·경보 발신 — 4·6장), **밖 = 감시**(살아 있나·벤더가 정상인가 — 이 장)로 가른다.

## 매니저 밖(모니터링 시스템)이 보는 신호

| 신호 | 무엇을 말하나 | 판정 |
|---|---|---|
| **heartbeat** (주기 작업별 — 막힘 점검 등 — 실행 완료 시각을 블록체인 매니저 DB 에 기록) | 각 주기 작업이 **살아서 돌고 있나** | now − heartbeat 가 주기의 몇 배(예: 5분)를 넘으면 **정지 경보**. 작업별로 기록해야 막힘 점검만 조용히 죽은 것도 잡는다. tx 가 없어도 매 주기 갱신되므로 오경보 없음. |
| **웹훅 수신 생존** (마지막 수신 시각 · 수신 오류율 — 매니저가 메트릭으로 내보냄) | 수신 엔드포인트가 **알림을 받고 있나** | 마지막 수신이 임계를 넘게 오래되면 **수신 정지 의심 경보** — 조용한 시간대일 수 있으니 벤더 status·대사와 함께 본다. 서명 검증 실패 급등은 별도 경보(위조 시도·설정 불일치). |
| **판정 적체** (수신 적재 대비 publish 지연 깊이) | 수신은 되는데 처리가 **밀리고 있나** | 임계 초과면 **밀림 경보**(4장 입금 폭주). |
| **벤더 호출 오류율·지연 — 429 포함** (매니저가 메트릭으로 내보냄) | 벤더·네트워크가 **정상인가** · rate limit 에 **몰리고 있나**(4장) | 급등이면 **벤더 장애 경보** — Admin 이 체인 비활성 같은 운영 스위치를 판단한다(6장). 429 잦음은 호출량·한도 조정 신호. |
| **벤더 status 공지** (모니터링이 직접 확인 — 매니저 경유 없음) | 벤더가 **알린 장애·점검** | 공지 발생 시 경보. 매니저가 죽어도 이 감시는 산다. |
| **컨슈머 오프셋 랙** (큐가 제공하는 토픽별 소비 지연 지표) | **백엔드 컨슈머**가 멈추거나 밀리나 — 매니저가 멀쩡히 publish 해도 원장이 밀릴 수 있다 | 토픽별 랙 임계 초과면 **소비 밀림 경보** — 아래 복구 절의 "컨슈머가 멈춘 동안"을 잡는 신호가 이것이다. |

이 경보들은 모니터링 시스템에서 사람·운영으로 바로 간다 — 원장·정산 컨슈머가 소비하는 데이터 토픽(4장)과는 무관하다.

## 모니터링 시스템 자체는

이 설계가 정하는 건 도구가 아니라 **조건**이다 — 회사에 쓰는 모니터링(메트릭 수집·대시보드·알림)이 이미 있으면 거기에 이 장의 신호 여섯을 규칙으로 등록하고, 없으면 이 조건을 만족하는 구성을 하나 마련한다(무엇을 쓸지는 운영 결정). 조건 셋:

- **장애 도메인 분리** — 매니저·백엔드와 같은 인프라(클러스터·호스트)에 두지 않는다. 같이 죽는 감시는 이 장의 존재 이유를 없앤다.
- **신호 접근 경로** — 메트릭은 수집(scrape/push)으로, heartbeat 는 매니저 DB **읽기 전용 계정**으로, 컨슈머 랙은 큐가 주는 지표로, 벤더 status 는 외부 확인으로. 어느 것도 매니저 코드를 거치지 않는다.
- **알림 경로 독립** — 경보 발송(온콜 호출)이 매니저·백엔드 인프라 장애와 함께 죽지 않는 수단일 것.

## 복구는 자동이다

- **매니저(수신기) 재시작 → 재전송으로 따라잡는다** — 다운 구간의 알림은 벤더 재시도가 잇고, 그래도 놓친 것은 재기동 후 재전송(resend) 호출로 다시 받는다. 멱등이라 겹쳐 받아도 안전하다(4장).
- **백엔드 컨슈머가 멈춘 동안도 마찬가지** — 큐는 durable 해서 이벤트가 큐에 남고, 오프셋은 원장 반영 성공 후에만 커밋되므로 재기동하면 마지막 커밋 지점부터 이어서 소비한다.
- 즉 정지의 피해는 유실이 아니라 **지연**이고, 감시의 몫은 그 지연을 빨리 아는 것이다.
