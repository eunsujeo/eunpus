매니저 안의 어떤 장치도 매니저 자신이 죽은 것은 못 잡는다 — 막힘 점검은 "tx 가 막힘"을 보지 "폴링이 멈춤"을 보지 않고, 매니저 안에서 올리는 경보는 폴링이 죽는 순간 같이 멈춘다.
그래서 **안 = 행동**(막힘 점검·자동 boost·경보 발신 — 4·6장), **밖 = 감시**(살아 있나·벤더가 정상인가 — 이 장)로 가른다.

## 매니저 밖(모니터링 시스템)이 보는 신호

| 신호 | 무엇을 말하나 | 판정 |
|---|---|---|
| **heartbeat** (주기 작업별 — 감지·막힘 점검 각각 — 실행 완료 시각을 블록체인 매니저 DB 에 기록) | 각 주기 작업이 **살아서 돌고 있나** | now − heartbeat 가 폴 주기의 몇 배(예: 5분)를 넘으면 **정지 경보**. 작업별로 기록해야 막힘 점검만 조용히 죽은 것도 잡는다. tx 가 없어도 매 주기 갱신되므로 오경보 없음. |
| **커서 랙** (now − 커서 lastUpdated) | 처리가 **밀리고 있나** | 임계 초과면 **밀림 경보**. 단 커서는 갱신된 tx 가 있어야 앞으로 가므로, 조용한 시간대엔 자연히 커진다 — **heartbeat 와 함께 봐야** 오경보를 거른다. |
| **벤더 호출 오류율·지연** (매니저가 메트릭으로 내보냄) | 벤더·네트워크가 **정상인가** | 급등이면 **벤더 장애 경보** — Admin 이 체인 비활성 같은 운영 스위치를 판단한다(6장). |
| **벤더 status 공지** (모니터링이 직접 확인 — 매니저 경유 없음) | 벤더가 **알린 장애·점검** | 공지 발생 시 경보. 매니저가 죽어도 이 감시는 산다. |

이 경보들은 모니터링 시스템에서 사람·운영으로 바로 간다 — 원장·정산 컨슈머가 소비하는 데이터 토픽(4장)과는 무관하다.

## 복구는 자동이다

- **매니저(폴링) 재시작 → 커서부터 따라잡는다** — 멈춘 동안의 변경분이 페이지네이션으로 전부 소진되고 멱등 upsert 라 겹쳐 받아도 안전하다(4장).
- **백엔드 컨슈머가 멈춘 동안도 마찬가지** — 큐는 durable 해서 이벤트가 큐에 남고, 오프셋은 원장 반영 성공 후에만 커밋되므로 재기동하면 마지막 커밋 지점부터 이어서 소비한다.
- 즉 정지의 피해는 유실이 아니라 **지연**이고, 감시의 몫은 그 지연을 빨리 아는 것이다.
