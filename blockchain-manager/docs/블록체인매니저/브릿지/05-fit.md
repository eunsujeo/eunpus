USDC Gateway 를 쓰면 우리 쪽에서 손대야 하는 것과 아직 안 정한 것을 모은다. 벤더 기능 자체의 성질은 [3장](03-usdc-gateway.md), 어느 vault 에 붙이는지는 [4장](04-gateway-placement.md).

## vault 넷과 Gateway 잔액

| 어디 | 하는 일 | 핫인가 |
|---|---|---|
| 고객 vault | 고객 입금 수신. 보관처가 아니다 | 핫 |
| **옴니버스 vault** | sweep 이 모이는 보관처 | 핫 |
| **출금 풀 vault** | 타VASP 송금이 나가는 창구. 복수 vault round-robin | 핫 |
| **Gateway 잔액** | 체인 변환용 완충. 자금은 Circle 컨트랙트에 있다 | 핫 |
| 콜드월렛 | 현 설계에 없음 | 콜드 |

넷 다 즉시 쓸 수 있어 20% 규제의 핫으로 센다([sweep](../../BC/설계/06-sweep.md) 밴드S 산식).

**옴니버스 → 출금 풀 이동은 밴드S 도 밴드C 도 바꾸지 않는다.** 밴드S 는 셋을 한 칸으로 세고, 밴드C 도 옴니버스와 출금 풀의 합을 센다. 어디에 얼마를 둘지의 **운영 배분** 문제다.

## Gateway 는 재고 보충 수단이다

[1장](01-problem.md)의 밴드C 는 타VASP 로 나갈 재고를 BC자산별로 관리한다. Gateway 는 그 재고를 채우는 자리에 놓인다.

**Gateway 인출 목적지는 출금 풀 vault 로 둔다.** 밴드C 하한이 미달인 BC자산을 목적지 체인으로 지정해 채운다. 타VASP 송금은 지금대로 출금 풀에서 나간다. 브릿지교환·콜드교환에 이은 세 번째 보충 수단이다.

따라오는 것 셋.

- **소스 체인을 지정 못 하는 것이 문제되지 않는다.** 인출로 줄어드는 것은 Gateway 잔액이고, 우리가 정해야 하는 값(어느 BC자산을 채울지)은 목적지 쪽이라 그대로 우리 손에 있다.
- **13~19분이 송금에 안 걸린다.** 재고 보충은 미리 하는 일이라 고객 송금의 지연이 아니다.
- **기존 출금 경로를 안 건드린다.** 타VASP 송금은 출금 풀에서 TAP·gasless·컴플라이언스 게이트를 그대로 지난다.

## Gateway 잔액은 밴드C 로 셀 수 없다

Gateway 잔액은 **핫으로 세지만 BC자산에 배정할 수는 없다.** 체인 구분이 없는 단일 숫자이기 때문이다. 두 밴드가 이 지점에서 갈린다.

| | 밴드S — 핫 비율 | 밴드C — BC자산별 재고 |
|---|---|---|
| 단위 | 원화환산 총액의 % | 자산별 절대 수량 |
| Gateway 잔액 | **센다** | **못 센다** — 어느 BC자산인지 정해지지 않았다 |

그래서 Gateway 잔액은 **밴드C 의 재고가 아니라 재고로 바꿀 수 있는 완충**이다. 인출해서 출금 풀에 들어온 순간 BC자산이 정해지고, 그때부터 밴드C 가 센다.

**Gateway 인출이 밴드C 를 실제로 늘리는 이유가 이것이다.** 밴드C 밖에 있던 잔액이 안으로 들어온다. 옴니버스 → 출금 풀 이동은 이미 안에 있는 것을 옮기는 것이라 값이 안 변한다.

## 옴니버스 ↔ 출금 풀 이동 정책

이 이동은 밴드S·밴드C 어느 값도 바꾸지 않는다. 그래도 필요하다 — **출금은 출금 풀에서 나가므로 재고가 거기 있어야 실제로 나간다.** 밴드C 합이 하한을 넘어도 그 몫이 옴니버스에만 있으면 출금이 안 된다.

| 정해야 할 것 | 지금 상태 |
|---|---|
| 트리거 | 밴드C 가 아니다 — 합은 그대로다. **출금 풀의 실제 잔액**을 봐야 하는데 그 기준이 없다 |
| 판정 주체 | 값이 온체인 잔액뿐이라 매니저가 알 수 있다. 밴드S 처럼 코어 판정이 필요한지는 정해진 것이 없다 |
| **복수 출금 풀에 어떻게 배분하나** | 출금 풀은 round-robin 복수 vault 다. **재고가 없는 풀을 round-robin 이 고르면 그 출금이 실패한다.** 풀마다 채울지, 고를 때 잔액을 볼지 |
| 되돌리는 방향 | 출금 풀 초과분을 옴니버스로 되돌릴지, 콜드로 뺄지. 콜드 계층이 아직 없다 |
| 가스 | [대납 적용 범위](../../BC/설계/02-bcm-flow.md) 표에 이 이동이 없다. 내부이체처럼 다루면 "미확정 — 켜지 않는다" 라 옴니버스에 native 자산이 있어야 성립한다 |
| 이벤트 | 4 토픽 중 어디로 가는지 없다. 대사에는 잡혀야 한다 |
| 승인 절차 | 아래 참조 |

## 운영 영역 — 층 셋으로 갈린다

옴니버스와 출금 풀을 **다른 vault 로 두는 것은 확정**이다. 운영을 어디까지 나누느냐가 남는다.

| 층 | 상태 |
|---|---|
| **벤더 정책(TAP)** | **분리 강제.** 옴니버스는 나가는 목적지가 전부 고정이라 화이트리스트로 잠근다. 출금 풀은 고객이 지정한 임의 주소라 한도로만 통제한다. 한 정책 묶음에 넣으면 둘 중 하나가 망가진다 |
| **시스템** | **이미 분리.** 출금 이벤트 파티션 키가 출금 풀 accountId 이고, 대사도 항을 갈라 센다. 다만 `sys_acnt_role_dvcd` 에 두 역할 값이 없어 표현할 자리가 없다 |
| **사람·절차** | **열려 있다.** 문서에 운영 주체·승인자가 정의된 적이 없다 |

사람 층이 [출금 흐름](../../BC/설계/02-bcm-flow.md)의 피해 상한과 맞물린다. 백엔드를 장악당해도 피해가 출금 풀 재고에서 캡되는데, **재고를 채우는 권한과 출금을 내는 권한이 같은 손에 있으면 그 상한은 숫자만 남는다.**

**Gateway 인출이 곧 재고 보충 행위**라 이 승인 절차를 탄다. [3장](03-usdc-gateway.md)의 자동 입금은 옴니버스 → Gateway 방향이라 경계 안이고, 벤더가 문서화한 자동화는 입금뿐이다.

## 한도 — Gateway 잔액도 20% 안에서 센다

Gateway 잔액은 각 체인의 Circle 컨트랙트에 있어 **우리 vault 잔액이 아니다.** 그래도 **핫으로 센다** — 인출이 API 호출 한 번이라 즉시 쓸 수 있는 자산이기 때문이다. Circle 은 이 컨트랙트를 비수탁으로 규정하고 7일 무신뢰 인출 경로를 둔다([참고](99-circle-gateway.md)).

따라서 **Gateway 로 옮겨 두는 것이 20% 한도를 늘려 주지 않는다.** 옮겨도 핫월렛합이 그대로다.

잔액 값은 [Gateway 잔액 조회 API](03-usdc-gateway.md) 로 따로 가져와야 한다 — vault 잔액 조회에는 안 잡힌다.

## 감지 — 우리가 낸 거래가 웹훅으로 돌아온다

Gateway 입금·출금·승인은 모두 표준 Fireblocks 거래라 **다른 전송과 똑같이 웹훅을 낸다.** 그래서 감지가 세 종류를 구분해야 한다.

| 종류 | 무엇 | 구분 못 하면 |
|---|---|---|
| 고객 입금 | 외부 → 고객 vault | — |
| Gateway 입금 | 옴니버스 vault → 같은 vault 의 Gateway 지갑 | 우리가 옮긴 것을 고객이 새로 넣은 것으로 센다 |
| 승인 | 옴니버스 vault → Gateway 컨트랙트, 금액 없음 | 금액 없는 거래가 파이프라인에 흘러든다 |

**정할 것 — 무슨 필드로 가르나.** 후보는 `subType: VIRTUAL_ACCOUNT`, 거래 종류(`APPROVE`), 제출자(`USDC Gateway Depositor`)다. 다만 **Gateway 입금·출금이 `networkRecords` 와 웹훅에 어떤 형태로 오는지 확인된 것이 없다**([3장](03-usdc-gateway.md)). 실측 전에는 구분 규칙을 확정할 수 없다.

## 완료 판정 — `COMPLETED` 를 가용 잔액으로 읽으면 안 된다

입금 거래의 완료는 **우리 워크스페이스 확정 정책**으로 나고, Circle 잔액 반영은 그 뒤다. Base·이더리움 계열은 **13~19분**이 걸린다([참고](99-circle-gateway.md)).

**정할 것 — 브릿지에 쓸 수 있는 잔액의 근거를 무엇으로 두나.** 거래 상태로는 알 수 없으므로 잔액 조회 API 를 별도로 봐야 한다. 조회 주기와 그 값을 어디에 보관할지가 남는다.

## 자동 입금과 재고 관리가 서로 밀 수 있다

고객 vault 에 자동 입금을 켜면 sweep 과 같은 잔액을 두 주체가 노린다 — 이건 [4장](04-gateway-placement.md)에서 옴니버스에만 활성화하기로 해 없앴다.

남는 것은 옴니버스 쪽이다. **자동 입금이 옴니버스의 온체인 USDC 를 다 쓸어 담으면 출금 풀을 온체인 전송으로 채울 잔액이 남지 않는다.** 그때는 Gateway 인출로만 채우게 된다. `balanceThreshold` 를 얼마로 둘지가 곧 둘 중 어느 쪽을 기본 경로로 둘지를 정하는 것이라, 위 이동 정책과 같이 정한다.

## 정책·운영

- 입금에 **룰 두 개**가 필요하다 — 승인용과 전송용. 없으면 활성화돼 있어도 막힌다.
- 자동 입금을 켜면 **initiator 를 `USDC Gateway Depositor` 로 둔 룰**이 하나 더 필요하고, 이 서비스 유저는 서명을 못 하므로 별도 서명자를 지정해야 한다.
- 화이트리스트를 쓰는 구성이면 **체인마다 Gateway 컨트랙트 주소를 등록**하고 admin quorum 승인을 받는다.
- **승인 거래는 쓰는 체인 수만큼** 나온다. 활성화는 vault 당 1회지만 승인은 `(주소, 체인)` 마다 1회다.

## 자산 범위

**USDC 전용이다.** 원화 SC 에는 못 쓴다. 브릿지 수단이 자산마다 갈리므로, 다루는 BC자산 목록이 확정돼야 이 장의 판단이 어디까지 적용되는지 정해진다([2장](02-options.md)).

## 확인해야 풀리는 것

| 미확인 | 어떻게 확인 | 무엇이 걸려 있나 |
|---|---|---|
| Gateway 입금·출금의 기록·웹훅 형태 | 실측 | 감지 구분 규칙 |
| 자동 입금 시 `APPROVE` 의 initiator | 실측 또는 벤더 문의 | 승인용 정책 룰 구성 |
| 활성화가 웹훅을 내는지 · vault 조회에 보이는지 | 실측 | 활성화 여부를 무엇으로 아는가 |
| 출금 실패 시 자금 위치와 상태 | 실측 또는 벤더 문의 | 실패 처리 절차 |
| 벤더를 통했을 때의 실제 소요 시간 | 실측 | 브릿지 가용 시점 판단 |
| Gateway 인출 목적지로 자기 vault 를 지정할 수 있는지 | 실측 또는 벤더 문의 | 인출을 옴니버스로 받고 거기서 출금 풀로 나눌 수 있는지 |

실측은 워크스페이스에서 기능이 켜져야 가능하다.

## 정하는 순서

1. **출금 풀에 얼마를 두나** — 밴드C 와 별개 기준이 필요하다. 이 값이 곧 침해 시 피해 상한이다
2. **복수 출금 풀 배분 규칙** — 풀마다 채울지, round-robin 이 고를 때 잔액을 볼지
3. **운영 영역 분리** — 재고를 채우는 권한과 출금을 내는 권한을 나눌지
4. 가스·이벤트·되돌리는 방향

전부 브릿지 밖의 결정이다. Gateway 는 그 위에 얹히는 세 번째 보충 수단이라, 이 순서가 서면 따라 정해진다.
