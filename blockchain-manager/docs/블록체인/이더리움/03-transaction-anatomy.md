지금까지 트랜잭션을 블록 밖에서만 봤다. 이 글은 안쪽을 본다 —
필드 전체, 순번(nonce)과 바꿔치기, 가스 견적, 그리고 발신자 주소가 서명에서 복원된다는 것까지.

## 1. 필드 한 장

이더리움 트랜잭션(EIP-1559 형식 기준)의 필드 전체다.

| 필드 | 뜻 |
|---|---|
| chainId | 어느 체인용인지 (이더리움 메인넷 1, Base 8453 …) |
| nonce | 발신 계정의 전송 순번 — 2절 |
| to | 수신 주소. 컨트랙트 호출이면 컨트랙트 주소 ([2장](02-erc20.md)) |
| value | 보내는 ETH 수량 (wei) |
| data | 컨트랙트 호출 내용 — 4절. 단순 ETH 송금이면 비어 있다 |
| gasLimit | 이 트랜잭션이 쓸 수 있는 가스 상한 — 3절 |
| maxPriorityFeePerGas | 팁 상한 (제안자 몫) |
| maxFeePerGas | 가스 단가 총 상한 (baseFee + 팁 포함) |
| 서명 (yParity·r·s — 통칭 v·r·s) | 발신자의 개인키 서명 — 5절 |

눈에 띄는 공백이 하나 있다. **`from` 필드가 없다.** 발신자 주소는 적는 것이 아니라 서명에서 계산으로 복원된다(5절). 그래서 발신자를 속인 트랜잭션은 만들 수 없다.

## 2. nonce — 순번과 바꿔치기

nonce 는 그 계정이 지금까지 보낸 트랜잭션 수다(0부터). 다음 트랜잭션은 반드시 다음 번호를 달아야 하고, 체인은 **한 계정의 트랜잭션을 번호 순서대로만** 포함한다.

이 단순한 규칙에서 실무의 두 상황이 나온다.

- **막힘** — 팁을 낮게 준 nonce 12 가 mempool 에서 안 뽑히면, 그 뒤에 보낸 13·14 도 전부 12 를 기다리며 선다. 한 건의 저가 수수료가 그 계정의 출금 전체를 세운다.
- **바꿔치기** — 같은 nonce 로 트랜잭션을 다시 보내면 노드가 기존 것을 교체해 준다. 조건은 수수료를 충분히 올리는 것이다. 몇 % 부터 받아 주는지는 프로토콜이 아니라 노드 소프트웨어의 정책인데, 가장 널리 쓰이는 구현체인 geth 의 기본값이 10% 라 실무 기준선처럼 통용된다. 같은 내용에 수수료만 올리면 **가속**이다. **취소**는 내용을 아무 효과 없는 것(to = 내 주소, value = 0, data 비움)으로 바꿔 nonce 를 소모해 버리는 것이다 — 토큰 출금이라면 원래 것도 value 는 0 이었으므로, 실질적으로 빠지는 것은 data 의 컨트랙트 호출이다. 어느 쪽이든 취소 트랜잭션 자체의 가스비는 낸다. 멈춘 출금을 다루는 표준 방법이 이 두 가지다.

```anim
nonce-replace
```

같은 nonce 의 두 트랜잭션이 둘 다 포함되는 일은 없다. 하나가 포함되는 순간 nonce 가 소모되어 나머지는 무효가 된다. [1장](01-finality.md) 3절에서 reorg 로 mempool 에 돌아간 트랜잭션이 "다시 담기지 못하고 탈락"하는 흔한 원인도 여기에 있다 (그 사이 같은 nonce 가 다른 트랜잭션으로 소모된 경우).

바꿔치기하면 **txHash 도 새로 생긴다** — 가속처럼 내용이 같아도 서명이 새로 되므로 다른 트랜잭션이다. 원래 해시로 receipt 를 조회하면 영원히 나오지 않으므로, 교체 가능성이 있는 출금의 추적은 txHash 하나가 아니라 **(계정, nonce) 기준**이어야 한다.

## 3. 가스 — 견적과 상한

가스는 실행량의 단위다. 트랜잭션에는 상한(gasLimit)을 걸어 보내고, 실제 소모량(gasUsed)은 receipt 에 남는다.

- **견적** — 보내기 전에 노드에 실행을 모의해 달라고 요청한다(eth_estimateGas). 지갑들은 이렇게 gasLimit 을 자동으로 채운다.
- **단가** — 내는 단가는 `baseFee + 팁` 인데, 두 상한에 걸린다: 팁은 maxPriorityFeePerGas 까지, 전체는 maxFeePerGas 까지. baseFee 가 올라 maxFeePerGas 를 넘으면 포함되지 못하고 기다린다 ([0장](00-block-lifecycle.md) 2절의 수수료 구조).
- **정산** — 안 쓴 가스는 청구되지 않는다. 반대로 실행이 실패해도(revert, 가스 부족) **소모한 만큼은 지불한다.** [2장](02-erc20.md) 3절의 "실패한 트랜잭션도 가스를 소모한 채 블록에 남는다"는 동작이 여기서 나온다.

## 4. data — 호출의 인코딩

[2장](02-erc20.md)에서 `data = transfer(B, 100000000)` 라고 쓴 것의 실제 바이트 구조다.

| 구간 | 내용 | 예 (USDC 전송) |
|---|---|---|
| 앞 4바이트 | **함수 선택자** — `keccak256("transfer(address,uint256)")` 의 앞 4바이트 | `0xa9059cbb` |
| 다음 32바이트 | 첫 인자: 받는 주소 (앞을 0으로 채움) | `0x000…b0b1…` |
| 다음 32바이트 | 둘째 인자: 수량 | `0x000…05f5e100` (= 100,000,000) |

토큰이 무엇이든 ERC-20 의 transfer 호출은 전부 `0xa9059cbb` 로 시작한다 (approve 는 `0x095ea7b3`, transferFrom 은 `0x23b872dd` — 함수마다 선택자가 하나씩). 익스플로러의 "Input Data" 칸에서 이 구조를 그대로 볼 수 있다. 트랜잭션 해시(txHash)에는 이런 의미 구조가 없다 — 전체를 통째로 해시한 지문일 뿐이다.

## 5. 서명 — 발신자는 계산 결과다

트랜잭션의 마지막 조각이 서명이다. 만들어지는 순서로 보면:

1. 위 필드들을 채운 트랜잭션 본문을 만든다
2. 발신자의 **개인키로 본문에 서명**한다 (서명값 v·r·s 가 트랜잭션에 붙는다)
3. 서명까지 붙은 전체를 해시한 값이 **txHash** 다 ([2장](02-erc20.md)의 정의)
4. 노드는 서명에서 공개키를, 공개키에서 **발신자 주소를 복원**한다 — 이것이 from 이다

서명에는 chainId 가 포함되어 한 체인용 서명을 다른 체인에 다시 제출하는 재사용이 막힌다. 본문이 한 바이트라도 바뀌면 서명 검증이 실패하므로 서명된 트랜잭션은 내용 변조가 불가능하다.

**개인키는 잔액을 가진 것이 아니라 서명할 수 있는 것이고, 서명이 곧 자금 이동의 전부다.** 커스터디·MPC 가 지키는 대상이 정확히 이 서명 능력이다.
