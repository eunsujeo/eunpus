2026년 7월, 하드웨어 지갑 Coldcard 의 시드 생성 난수가 의도보다 훨씬 약했다는 사실이 공개됐다.
암호 알고리즘이 깨진 게 아니라 **빌드 설정 한 줄 때문에 난수원이 바뀌어** 있었고, 5년간 아무도 몰랐다.
바탕 개념은 [0장 시드와 엔트로피](00-seed-and-entropy.md).

> **근거 구분** — 근본 원인·영향 범위는 제조사(Coinkite) 공식 문서에서 확인한 사실이다. 피해 규모는 언론 보도이며 공식 권고문에는 없다. 이 문서는 그 둘을 섞지 않는다.

## 무슨 일이 있었나

| | |
|---|---|
| 공개 | 2026-07-30 Coinkite 보안 권고 |
| 내용 | 특정 펌웨어에서 생성된 시드의 유효 엔트로피가 의도(128비트)보다 크게 낮아, 개인키를 무작위 대입으로 재현할 수 있다 |
| 피해 (언론 보도) | 약 594 BTC(당시 약 3,800만 달러)가 단일서명 주소 약 500개에서 인출 — 일부 보도는 25분 만에 벌어졌다고 전한다 |
| 되돌릴 수 있나 | **없다.** 펌웨어를 고쳐도 이미 만들어진 시드의 엔트로피는 소급해서 늘 수 없다 |

영향 받는 펌웨어 (공식 권고):

- **Mk2 / Mk3** — 4.0.1 ~ 4.1.9
- **Mk4 / Mk5** — 표준 5.6.0 미만 · Edge 6.6.0X 미만
- **Q** — 표준 1.5.0Q 미만 · Edge 6.6.0QX 미만
- TAPSIGNER · OPENDIME · SATSCARD 는 해당 없음

## 근본 원인 — 의도한 난수원이 조용히 바뀌었다

제조사 기술 문서가 밝힌 경위는 네 단계다.

**① 마이그레이션**
2021년 3월, Bitcoin Core 의 libsecp256k1 으로 옮기는 작업 중 시드 생성 경로가 **하드웨어 TRNG 대신 MicroPython 의 소프트웨어 대체 PRNG** 를 타게 됐다. (그 대체 구현 자체는 2018년 5월부터 코드에 있었지만, 시드에 영향을 준 것은 이 마이그레이션부터다.)

**② 빌드 설정의 어긋남**
개발자는 `MICROPY_HW_ENABLE_RNG` 를 **0으로 설정**해 두 구현을 모두 끄려 했다. 그런데 코드의 가드가 `#ifndef` — **정의됐는지만 검사하고 값은 보지 않는다**. 0으로 정의한 것은 "정의됨"이므로 소프트웨어 대체 구현이 그대로 컴파일에 포함됐다.

**③ 링커가 잡아주지 못함**
두 구현의 **함수 시그니처가 같아서** 잘못된 쪽이 연결돼도 빌드는 정상 성공했다. 컴파일 오류도, 경고도 없었다.

**④ 결과 — 엔트로피 붕괴**

| 기기 | 실제 엔트로피 | 왜 |
|---|---|---|
| Mk2 / Mk3 | **약 40비트** | PRNG 가 장치 상태·타이밍 위주로만 시드됨 — 추측 가능한 값들 |
| Mk4 / Mk5 / Q | **약 72비트** | 보안 요소(SE1·SE2)의 엔트로피가 섞여 일부 보완 — 그래도 128비트 목표에 크게 미달 |

40비트는 후보가 약 1.1조 개다. [0장](00-seed-and-entropy.md)에서 본 대로 이는 **일반 장비로 전수 탐색이 가능한 크기**이고, 공격은 시드 후보 생성 → 주소 파생 → 체인 잔액 조회 → 인출 순으로 **완전히 오프라인에서** 진행된다.

## 왜 5년 동안 못 잡았나

가장 중요한 대목이다. 하드웨어 TRNG 코드는 **컴파일된 바이너리 안에 실제로 들어 있었다.** 검토자들은 그 코드를 확인했지만, 여러 서브모듈에 걸쳐 **심볼이 실제로 어디로 해석되는지, 시드 생성에서 그 코드에 호출이 닿는지(call reachability)를 끝까지 검증하지 않았다.**

즉 "올바른 구현이 존재한다"는 확인과 "올바른 구현이 실제로 실행된다"는 확인은 다른 일이고, 이 사건은 그 틈에서 났다.

## 살아남은 경로

공식 권고가 안전하다고 인정한 경우:

- **주사위 50회 이상** 을 독립적으로, 노출 없이 입력했다면(Add Dice Rolls) 주사위 입력만으로 128비트 이상이 기여된다. 99회 이상이면 약 256비트. → 기기의 난수를 신뢰하지 않는 절차가 유일하게 방어에 성공했다.
- **강하고 고유한 BIP-39 passphrase** 는 독립 방어층이라 이번 공격 물결을 피할 수 있다. 다만 공식 권고는 **임시 방어로 보고 마이그레이션을 권한다**.

대응은 하나뿐이다 — 고쳐진 펌웨어를 확인하고, **새 시드를 생성**하고, 백업을 검증한 뒤 소액으로 시험하고 나머지를 온체인으로 옮긴다.

## 수탁 설계 관점의 시사점

우리는 Fireblocks MPC 를 쓰므로 자체 니모닉 생성 경로가 없다. 그래도 이 사건이 남기는 질문은 그대로 유효하다.

| 교훈 | 우리에게 옮기면 |
|---|---|
| **"콜드 = 안전"이 깨졌다** | 오프라인 보관은 "공격자가 기기·네트워크로 들어온다"는 위협만 막는다. 키 생성 자체가 약하면 콜드도 소용없다 — 콜드월렛 계층을 설계할 때 보관 위치보다 **키가 어떻게 만들어졌는지**가 먼저다 ([sweep 설계](../../BC/설계/06-sweep.md)의 콜드 계층 논의) |
| **키 생성 품질은 벤더 신뢰 문제** | 우리는 시드를 만들지 않지만, 벤더가 만든다. "벤더의 키 생성·난수 품질을 우리가 무엇으로 확인하나"는 남는 질문이다 — 감사 리포트·인증 외에 우리가 직접 검증할 수단은 사실상 없다 |
| **코드가 있다 ≠ 그 코드가 실행된다** | 서명 직전 검증(Callback Handler)처럼 "이 관문이 정말 그 경로에서 도는가"는 배포된 산출물에서 실행 경로로 확인해야 한다. 코드 리뷰만으로는 부족하다 |
| **정적 검토로 안 잡히는 결함이 있다** | 난수·키 관련은 **출력물 자체를 통계로 검사**하는 방어가 최후 수단이다. 우리 쪽에서는 주소·키 발급 결과의 중복·분포 점검이 같은 계열의 장치가 된다 |
| **소급 복구가 불가능한 사고 유형** | "키가 오염됐다"는 판정이 내려지면 남는 대응은 전량 이전뿐이다. 그 절차(새 vault 발급 → 고객 주소 재고지 → 전량 이동 → 대사)를 미리 갖고 있는지가 사고 대응 역량이다 |
