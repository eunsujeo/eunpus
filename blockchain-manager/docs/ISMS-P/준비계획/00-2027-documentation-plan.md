2027년 ISMS-P 심사를 목표로 문서, 실제 통제, 운영 증적을 함께 준비한다. 기존 `blockchain-manager/docs/`의 지갑·트래블룰·운영 설계는 근거 자료로 재사용하되, 승인된 사내 정책과 실제 운영 증적으로 간주하지 않는다.

## 1. 목표와 완료 기준

심사 준비의 완료 기준은 문서를 많이 만드는 것이 아니다. 적용되는 각 인증기준에 대해 다음 다섯 가지를 연결해 설명할 수 있어야 한다.

1. 회사가 지켜야 할 원칙을 승인된 정책으로 정했다.
2. 담당자와 수행 방법을 절차서에 정했다.
3. 시스템과 업무에 통제를 실제로 적용했다.
4. 정해진 주기대로 수행한 기록을 남겼다.
5. 점검에서 발견한 문제를 시정하고 경영진이 결과를 확인했다.

현재 기준선은 KISA의 `ISMS-P 인증기준 안내서(2023.11)`로 삼는다. 이 기준은 관리체계 수립 및 운영 16개, 보호대책 요구사항 64개, 개인정보 처리 단계별 요구사항 21개로 구성된다. 2027년 심사 전에는 개정 고시와 최신 안내서가 있는지 다시 확인하고 통제항목 표를 갱신한다.

- [KISA ISMS-P 인증기준 안내서 게시 페이지](https://isms-p.or.kr/ntcn/rcsrm/selectGnrlRcsrmList.do?rcsrmMenuCd=1001&searchKeyword=ISMS-P+%EC%9D%B8%EC%A6%9D%EA%B8%B0%EC%A4%80+%EC%95%88%EB%82%B4%EC%84%9C)
- [KISA 인증 절차와 인증범위 안내](https://isms-p.or.kr/cert/aply/selectCertPrcdDetail.do)

## 2. 먼저 확정할 범위

문서 작성에 앞서 아래 항목을 확정한다. 범위가 바뀌면 자산 목록, 위험평가, 개인정보 흐름, 협력사 목록과 거의 모든 절차서가 다시 바뀐다.

| 결정 항목 | 확인할 내용 | 책임자 | 목표 시점 |
|---|---|---|---|
| 인증 종류 | 최종 요구가 ISMS인지 ISMS-P인지, 요구 근거와 제출처 | 준법·정보보호 | 착수 1주 |
| 심사 유형 | 예비인증 또는 본인증, 최초심사 목표 월 | 준법·정보보호 | 착수 1주 |
| 법인과 서비스 | 인증서에 들어갈 법인, 서비스명, 도메인과 앱 | 경영진·서비스 책임자 | 착수 2주 |
| 조직 범위 | 개발, 운영, 보안, 고객지원, 준법, 인사와 협력사 | 정보보호 책임자 | 착수 2주 |
| 시스템 범위 | 운영·개발·DR 환경, 관리자 시스템, CI/CD, 로그, 백업 | 기술 책임자 | 착수 2주 |
| 수탁 경계 | 고객 자산, 개인키·키 조각, 서명과 복구의 책임 주체 | 지갑 책임자·준법 | 착수 2주 |
| 개인정보 범위 | KYC, 회원, 트래블룰, 임직원, 접속기록의 처리 흐름 | 개인정보 보호책임자 | 착수 3주 |
| 외부자 범위 | Fireblocks, 클라우드, 트래블룰, AML·KYT와 운영 협력사 | 구매·보안·준법 | 착수 3주 |

인증범위 문서에는 논리 구성도뿐 아니라 물리적 위치, 네트워크 경계, 운영 조직, 외부 연계와 제외 대상을 함께 표시한다. 제외 대상에는 사유와 인증범위에 영향을 주지 않는다는 근거를 남긴다.

## 3. 문서와 증적의 보관 원칙

`blockchain-manager/docs/ISMS-P/`에는 다음 자료를 둔다.

- 개인정보나 비밀값을 포함하지 않은 정책·표준·절차의 정본
- 인증범위, 통제항목 대응표, 문서 목록과 증적 목록
- 지갑·키 관리·출금·트래블룰의 통제 설계
- 실제 증적의 보관 위치, 소유자, 대상 기간과 검토 상태를 기록한 색인

다음 원본은 이 Git 저장소에 넣지 않는다.

- 임직원·고객·트래블룰 개인정보가 포함된 목록과 화면 캡처
- 운영 계정, 권한 내역, 방화벽 규칙, IP와 상세 네트워크 설정
- API key, 인증서, private key, seed, MPC key share와 복구 자료
- 취약점 상세 결과, 침해사고 조사 자료와 운영 로그 원문
- 계약서, 인사 기록, 교육 참석자 서명과 승인 기록 원본

원본 증적은 회사가 지정한 접근 통제 저장소에 보관한다. Git 문서에는 `증적 ID`, `보관 위치`, `소유자`, `생성 주기`, `보존 기간`, `최근 검토일`만 기록한다. 증적 저장소가 정해지기 전에는 임의의 개인 드라이브를 사용하지 않는다.

## 6. 단계별 실행 계획

심사 목표 월을 `T`로 두고 역산한다. 본인증 준비에는 문서 승인뿐 아니라 실제 운영 기록이 필요하므로 통제 적용과 증적 수집을 늦추지 않는다.

| 기간 | 작업 | 주요 산출물 | 통과 조건 |
|---|---|---|---|
| 지금~T-10개월 | 범위와 책임자 확정 | 인증범위, 조직도, 시스템·개인정보·외부자 목록 | 경영진이 범위와 예산 승인 |
| T-10~T-8개월 | 현황 및 차이 분석 | 101개 통제항목 대응표, 미비점 목록, 조치계획 | 모든 항목의 적용 여부와 책임자 확정 |
| T-8~T-6개월 | 정책·절차 작성 및 승인 | 관리체계·보호대책·개인정보 문서 1차본 | 문서별 소유자·승인자·시행일 명시 |
| T-7~T-4개월 | 기술·업무 통제 적용 | IAM, 로그, 백업, 취약점, 키·출금 통제 | 미적용 통제에 승인된 보완 일정 존재 |
| T-6~T-3개월 | 반복 운영과 증적 수집 | 월간·분기 점검, 교육, 권한 검토, 복구·사고 훈련 | 증적 누락과 정책·현실 불일치 제거 |
| T-3~T-2개월 | 내부감사와 경영진 검토 | 내부감사 보고서, 시정조치, 경영진 검토 기록 | 중대 미비점 종결 또는 공식 위험 수용 |
| T-2~T-1개월 | 모의심사와 신청 준비 | 인터뷰 답변표, 표본 증적 묶음, 인증 명세서 | 항목별 문서·담당자·증적을 즉시 제시 가능 |
| T | 인증심사와 보완 | 심사 대응 기록, 결함 보완계획과 완료 증적 | 기한 안에 보완조치 제출·확인 |

심사일이 2027년 상반기라면 위 일정을 그대로 수행할 시간이 부족할 수 있다. 이 경우 범위를 먼저 좁히고, 예비인증 적용 가능 여부와 심사 일정을 인증기관·전문가에게 확인한 뒤 병렬로 진행한다.

## 7. 첫 4주 작업

### 1주차 — 책임과 요구사항 고정

- 경영진 후원자, 정보보호 책임자, 개인정보 보호책임자와 실무 PM을 지정한다.
- ISMS-P 요구 주체와 법적·계약상 근거, 목표 심사월을 문서로 확인한다.
- 주 1회 추진회의와 의사결정 기록 방식을 정한다.
- 문서 승인·개정·폐기 규칙과 증적 저장소를 정한다.

### 2주차 — 인증범위 초안

- 서비스, 조직, 사업장, 클라우드 계정, 네트워크와 외부 연계를 그린다.
- 운영·개발·시험·DR 환경과 관리자 접근 경로를 구분한다.
- 고객 자산과 키의 생성·서명·복구·폐기 책임을 주체별로 표시한다.
- 범위에서 제외하려는 시스템의 연계와 제외 근거를 기록한다.

### 3주차 — 목록과 흐름 작성

- 정보자산, 개인정보, 계정·권한, 외부자·위탁사 목록을 작성한다.
- 개인정보가 수집되어 이용·제공·보관·파기되는 흐름을 그린다.
- 입금, 출금, 스윕, 키 복구, 트래블룰, 고객지원의 주요 업무 흐름을 정리한다.
- 기존 문서를 통제항목 대응표에 연결하고 빠진 근거를 표시한다.

### 4주차 — 차이 분석과 우선순위

- 101개 항목을 `충족`, `일부 충족`, `미충족`, `해당 없음`으로 평가한다.
- 자산 손실, 개인정보 유출, 미신고 영업과 심사 실패로 이어질 미비점을 우선 처리한다.
- 통제별 책임자, 예산, 완료일과 필요한 운영 증적을 확정한다.
- 다음 8주 동안 작성할 문서와 적용할 기술 통제를 승인받는다.

## 8. 우선순위

다음 항목은 문서 작성과 시스템 개선을 동시에 시작한다.

1. 인증범위와 수탁·개인정보 처리 경계
2. 키 생성·보관·서명·복구·폐기와 비상 접근
3. 운영자·개발자·벤더 계정의 최소 권한, 다중 인증과 정기 검토
4. 출금 정책, 다중 승인, 주소 허용목록과 비상 정지
5. 로그 수집, 시간 동기화, 변경 방지, 보존과 정기 검토
6. 개인정보 수집·제공·위탁·국외 이전·보유·파기
7. 보안 개발, 변경 승인, 취약점과 패치 관리
8. 백업·복구, Co-signer 장애, 벤더 장애와 재해복구 훈련
9. 침해사고 및 가상자산 탈취 대응과 신고·통지 판단 절차
10. 내부감사, 시정조치와 경영진 검토

## 9. 문서별 완료 조건

모든 정책·절차 문서는 다음 항목을 포함해야 완료로 본다.

- 목적, 적용 범위와 제외 범위
- 용어와 관련 법령·상위 정책
- 책임자, 수행자, 승인자와 역할 분리
- 정상 절차, 예외·긴급 절차와 금지 사항
- 수행 주기와 기한
- 생성해야 할 기록과 보존 기간
- 위반·실패 시 보고 및 시정 방법
- 시행일, 문서 소유자, 승인자, 버전과 변경 이력
- 연결된 인증기준 ID와 관련 시스템

내용이 실제 시스템과 다르거나 담당자가 수행 방법을 설명하지 못하면 문서가 있어도 완료로 처리하지 않는다.

## 10. 역할 분담

| 역할 | 책임 |
|---|---|
| 경영진 후원자 | 범위·예산·위험 수용 승인, 경영진 검토 |
| 정보보호 책임자 | ISMS-P 관리체계, 위험평가, 내부감사와 심사 총괄 |
| 개인정보 보호책임자 | 개인정보 처리 근거·흐름·권리·파기·침해 대응 |
| 서비스 책임자 | 지갑 서비스 범위, 고객·업무 흐름과 운영 절차 |
| 기술 책임자 | 인프라, IAM, 개발·배포, 로그, 백업과 취약점 통제 |
| 지갑·키 책임자 | MPC·Co-signer, 서명 정책, 복구와 비상 통제 |
| 준법·법무 | 가상자산사업자 의무, AML·트래블룰, 계약과 위수탁 검토 |
| 인사·총무 | 입·퇴사, 교육, 서약, 물리보안과 방문자 관리 |
| 내부감사자 | 구축 담당자와 독립된 관점의 적합성·이행 점검 |

한 사람이 여러 역할을 맡는 소규모 조직이라면 승인과 실행, 개발과 운영, 정책 변경과 자산 이전이 한 사람에게 집중되지 않도록 대체 통제를 정한다.

## 11. 주요 점검 관문

- **범위 승인 관문**: 인증범위와 제외 근거를 경영진·준법·기술 책임자가 함께 승인한다.
- **문서 기준선 관문**: 정책과 절차의 상충, 미확정 책임자와 빈 수행 주기를 제거한다.
- **운영 개시 관문**: 문서대로 통제가 적용됐는지 확인한 날부터 반복 증적을 수집한다.
- **내부감사 관문**: 표본을 정해 문서, 시스템 설정, 인터뷰와 증적을 교차 확인한다.
- **심사 신청 관문**: 최신 기준 재확인, 미결 미비점, 증적 기간과 인증 명세서를 최종 검토한다.

## 12. 현재 열린 결정

1. ISMS-P를 요구한 기관과 정확한 근거 문서는 무엇인가.
2. 최초심사 목표 월과 예비인증·본인증 중 대상은 무엇인가.
3. 인증 주체가 지갑 운영 법인, 합작법인 또는 고객사 중 어디인가.
4. Fireblocks Workspace·Co-signer·Policy Server의 실제 운영 주체는 누구인가.
5. 회원·KYC·트래블룰 개인정보를 어느 시스템과 국가에서 처리하는가.
6. 운영 환경, DR 센터와 사무실 가운데 인증범위에 들어갈 물리적 위치는 어디인가.
7. 정책 정본, 승인 기록과 민감한 심사 증적을 보관할 시스템은 무엇인가.

이 결정이 끝나기 전에는 조직명, 보존 기간, 담당 제품과 통제 구현을 확정된 사실처럼 문서에 쓰지 않는다.
