VerifyVASP 는 사전 허가형(비동기), Notabene 은 벤더 게이트형(동기), 개인지갑은 레지스트리 조회 — 시나리오마다 호출 모양이 다르다.
이 차이를 게이트의 공통 단계 4개와 판정 어휘 하나로 접고, 망별 차이는 어댑터가 흡수한다 — 망이 추가·교체돼도 출금·입금 업무 코드는 그대로다.

## 왜 접어야 하나

국내·해외·개인지갑을 업무 코드가 직접 분기하면(if 국내 … else if 해외 … else 개인지갑 …), 망이 추가되거나 연동 방식이 바뀔 때마다 출금 유스케이스를 고치게 된다. 매니저가 벤더 원어를 TxStatus 다섯으로 번역해 백엔드를 보호하는 것과 같은 원리로 — **게이트도 망 원어를 공통 어휘로 번역해 업무 코드를 보호한다**.

## 왜 매니저(BCM)와 나누나

규제 판단과 온체인 실행은 도메인이 달라 나눈다.

- **판단은 게이트, 실행은 BCM, 순서는 코어(Service 백엔드 유스케이스·상태 기계).** 게이트(트래블룰 솔루션)가 승인·거부·보류를 판단하고, 코어가 "검증 승인 전엔 못 보낸다"는 순서를 강제하고, BCM 은 전달받은 걸 재검증 없이 실행한다. BCM 을 신뢰 경계 밖 단순 실행기로 두면 "검증 없이 전송" 사고가 구조적으로 막힌다.
- **BCM 은 규제를 모른다 — 운반만.** BCM 은 트래블룰 산출물을 실어 나르기만 하고 내용을 파싱·판단하지 않는다. 규제 로직을 실행 경로에 섞으면 특금법·VASP 마스터가 바뀔 때마다 온체인 컴포넌트를 손봐야 한다.
- **벤더·장애 격리.** BCM 은 커스터디(Fireblocks), 게이트는 트래블룰 솔루션(VerifyVASP·Notabene)을 각각 추상화한다. 트래블룰 솔루션 장애 시 외부 이체만 fail-close 하고 온체인·내부 거래는 정상 — 장애 도메인이 분리된다.

게이트를 구체적으로 어디에 두는지(백엔드 모듈)와 그 근거는 아래에서 다룬다.

## 게이트를 어디에 두나 — 세 안 검토

트래블룰 호출을 어디로 보낼지 세 안을 검토했다.

| 안 | 결정 | 이유 |
|---|---|---|
| **① 블록체인 매니저 경유** — 트래블룰 호출을 매니저 오퍼레이션으로 넣거나 프록시 | **아니오** | 매니저는 **자산이 움직이는 경로**의 관문이다. VerifyVASP 는 커스터디 벤더와 무관한 별도 망이고(교체 축이 다름), 평문 PII 가 매니저를 지나게 되며, VerifyVASP 수신 API 는 **인바운드**라 매니저의 아웃바운드 구조와 맞지 않다 |
| **② 별도 컴플라이언스 매니저 서비스** | **지금은 아니오** | 아래 근거 셋 — 승격 조건만 명시해 둔다 |
| **③ 백엔드 안의 모듈** | **결정** | 출금 상태 기계·고객 데이터 옆이 제자리 |

②를 지금 안 하는 근거 셋:

1. **출금 상태 기계는 주인이 하나** — "접수 → 승인 → 트래블룰 확인 중 → 제출"은 한 흐름이다. 가운데 상태를 다른 서비스 DB 로 떼면 이중 처리·복구 문제를 서비스 경계에서 다시 열게 된다.
2. **수신 질문의 답은 고객 데이터다** — VerifyVASP 가 물어 오는 것은 "이 주소가 당신 고객 실명 소유인가"다. 판단·적재는 백엔드가 해야 한다(수신 컴포넌트는 얇은 전달자 — 아래 구도).
3. **PII 격리는 Enclave 가 이미 한다** — 암호화 키·PII 보관은 벤더가 강제하는 별도 배포물(Enclave) 안이다. 격리를 위해 서비스를 만들 이유가 없다.

```
Service 백엔드
├─ 출금·입금 유스케이스 (상태 기계의 단일 주인)
├─ 트래블룰 게이트 — 모듈 (아래 TravelRuleChannel 포트)
│    ├─ VerifyVASP 어댑터 ──→ Enclave 서버 (벤더 강제 별도 인프라 · PII 는 여기)
│    ├─ Notabene 어댑터  ──→ Fireblocks validate 계열 (전용 API user — 아래)
│    └─ 개인지갑 어댑터   ──→ Address Registry
└─ (내부 API) 고객 실명·계정 확인 · 대기함 적재 — 수신 컴포넌트가 위임해 온다

트래블룰 수신 컴포넌트 — 별도 배포 (얇게)
└─ Enclave 가 호출하는 VASP API 구현 (Verify User · Verify User Account · Callback · Check Transaction Status)
   검증·변환만 하고 판단·적재는 백엔드 내부 API 로 위임 — 상태 주인은 백엔드 유지
```

인바운드 사슬은 **중앙 서버 → (우리 인프라의) Enclave → 수신 컴포넌트 → 백엔드 내부 API** 다. 아웃바운드에는 대응물이 없다 — 아웃바운드의 관문 역할(키·PII 암호화·중앙 통신)은 **Enclave 가 이미 하므로**, 게이트는 모듈로 두고 사이에 컴포넌트를 더 끼우지 않는다. 공개 HTTPS 를 받는 것은 Enclave(벤더 요건)이고, 수신 컴포넌트를 Service 백엔드와 분리하는 이유는 트래픽 성격(기관 간 콜백 vs 고객 요청)·배포 주기·장애 격리가 다르기 때문이다. 단 **얇게** 둔다 — 여기에 업무 판단이 쌓이면 기각한 ②(별도 서비스)가 뒷문으로 들어온다.

**서비스로 승격하는 조건**은 셋 중 하나가 생길 때다 — ① 두 번째 소비자(다른 상품·계열사가 같은 트래블룰 스택 사용) ② 조직 분리(컴플라이언스 전담팀의 독립 배포 주기) ③ 감사·규제의 물리 격리 요구. 포트 뒤의 모듈은 서비스로 떼어내도 호출자가 안 바뀌므로, 지금 모듈 경계를 긋는 것이 그 미래를 싸게 사는 방법이다. 이 구성요소들이 물리적으로 어디 앉는지는 12장 물리 배치.

## Fireblocks 스크리닝 호출 — 전용 API user 로 직접

Notabene 어댑터의 `validate`·`validate/full` 은 Fireblocks API 지만, **블록체인 매니저를 경유하지 않고 게이트 모듈이 직접 호출한다**. 관문 원칙은 이렇게 정밀해진다 — **블록체인 매니저 = 자산이 움직이는 경로의 단일 관문**(제출·폴링·조회). 스크리닝 검증은 자산 불이동 + 평문 PII 동반이라 처음부터 그 관문의 일이 아니다.

- **전용 API user, 스크리닝 권한만** — 만능 자격증명 하나보다 좁은 자격증명 둘이 안전하다. 권한 구성은 확인 항목(6장 미확정).
- **PII 접촉면 최소화** — validate/full 의 평문 PII 가 블록체인 매니저를 지나지 않는다.
- **rate limit 은 API user 단위**라 전용 user 는 매니저 폴링과 한도를 나누지 않는다. 429 는 어댑터 자체 백오프.

## 공통 단계 4개 — 모든 망이 이 틀에 들어간다

| 단계 | VerifyVASP (국내) | Notabene (해외 · 벤더 경유) | 개인지갑 |
|---|---|---|---|
| **① 상대 판별** (route) | 회원망 조회 (List VASP API — 공식 확인) | 기본 경로 | Address Registry 에 등록된 주소인가 |
| **② 사전 확인** (check) | 주소 소유 확인(동기) + PII 사전 승인(User Verification — **비동기**: UUID 즉시, 결과는 Callback) | `validate` → `validate/full` — **동기** | 등록·소유 인증 조회 — **동기** |
| **③ 제출 동봉물** (attachment) | 없음 — 사전 승인 자체가 통과 증적 | `travelRuleMessage` — 매니저 제출 요청의 `travelRule` 필드에 실림 | 없음 |
| **④ 사후 보고** (report) | tx hash 보고 (Report Transaction Result — Enclave 가 UUID 에 매핑) | 없음 — 벤더가 이미 안다 | 없음 |
| **입금 판정** (checkDeposit) | 수신 API 응답·tx hash 대조 기록 | 벤더가 판정 완료 — 동결이면 애초에 REJECTED 계열로 옴 | Address Registry 조회 |

```kotlin
// 트래블룰 게이트 포트 — 망 어댑터(VerifyVASP · Notabene · 개인지갑)가 구현
interface TravelRuleChannel {
  fun checkWithdrawal(w: WithdrawalIntent): TrVerdict   // ② 동기 망은 즉답, 비동기 망은 PENDING 후 콜백·조회로 갱신
  fun attachmentOf(w: WithdrawalIntent): TravelRule?    // ③ 매니저 제출 요청의 travelRule 필드에 실린다 — 없으면 null
  fun reportSubmitted(w: WithdrawalIntent, txHash: String)  // ④ 필요 없는 망은 아무것도 안 한다
  fun checkDeposit(d: DepositCandidate): TrVerdict      // 입금 가용 전이 게이트의 판정 재료
}

enum class TrVerdict {
  NOT_REQUIRED,  // 임계 미만·면제 — 정보 교환 없이 진행
  APPROVED,      // 통과 — 제출(출금)·가용 전이(입금) 진행
  PENDING,       // 확인 중 — 비동기 승인 대기 (시간 규칙은 4장)
  REJECTED,      // 거절 — 출금 반려·입금 보류
}

// 라우터 — ① 상대 판별. 규칙(회원 목록·주소 등록부)은 정책 데이터라 코드 수정 없이 바뀐다
fun channelOf(counterparty: Destination): TravelRuleChannel
```

## 세 어휘 대응 — 원어를 TrVerdict 로 접는다

게이트가 접는 일은 곧 세 어휘(Fireblocks `validate` type·2장 / Notabene 판정 상태·4장 / 망별 원어)를 우리 `TrVerdict` 하나로 번역하는 것이다. 업무 코드는 왼쪽 4개만 본다.

| 우리 `TrVerdict` | Fireblocks validate · Notabene 판정 | VerifyVASP (비동기) | CODE (동기) | 개인지갑 |
|---|---|---|---|---|
| `NOT_REQUIRED` | validate `BELOW_THRESHOLD`·`NON_CUSTODIAL` · Notabene `Saved` | 임계 미만·면제 | 임계 미만(원화 판정) | 정보 교환 없음 |
| `APPROVED` | Notabene `Completed` → Post-Screening Accept | User Verification 승인 (Callback 도착) | Asset Transfer Authorization 승인 | Address Registry 등록·소유 인증 |
| `PENDING` | Notabene `Pending` (Wait) | UUID 접수 · Callback 대기 | (동기라 드묾) | — |
| `REJECTED` | Notabene `Rejected`·`Failed`·`Blocking Time Expired` | 상대 거절 · PENDING 만료 | 상대 거절 | 미등록·미인증 |

## 비동기를 기본으로 — 출금에 "트래블룰 확인 중" 상태 하나

VerifyVASP 의 사전 승인은 상대 VASP 의 응답(사람 심사일 수도 있다)을 기다리는 비동기라, 출금 상태에 **트래블룰 확인 중** 단계가 필요하다. 동기 망(Notabene 의 validate·개인지갑 조회)도 같은 상태를 즉시 통과하는 것으로 접는다 — 상태 기계를 망별로 두 벌 만들지 않는다.

```
출금 접수 → 업무 승인 → 트래블룰 확인 중 ──APPROVED·NOT_REQUIRED──→ 제출 (매니저 submitTransaction)
                              │
                              ├─REJECTED──→ 반려 — 잠긴 금액 가용 복귀 · 고객 안내
                              └─PENDING 만료(4장 시간 규칙)──→ 반려 — 같은 처리
```

- 이 상태는 **매니저 앞의 업무 단계**다 — 매니저 TxStatus(블록체인매니저 4장)와 무관하고, 제출 전이라 온체인엔 아무것도 없다.
- 제출 후의 ④ 사후 보고는 매니저 응답(TxRef)·확정 이벤트에 이어 붙인다 — 실패해도 재시도할 뿐 출금 흐름을 막지 않는다.

## 입금 합류점 — 가용 전이 게이트 하나, 판별은 역방향

6장의 "복수 망 대조" 합류점을 이 어휘로 확정한다. 가용 전이 조건은 망과 무관하게 하나다:

```
가용 전이 = 확정 임계 도달 (매니저 이벤트 · 블록체인매니저 4장)
          AND 입금 판별 = APPROVED 또는 NOT_REQUIRED
```

입금은 출금과 판별 방향이 반대다 — 출금은 목적지를 미리 알고 망을 고르지만(라우터), 입금은 **도착한 뒤 source 와 대조 재료로 역판별**한다. 우선순위로 가른다:

| 순서 | 판별 재료 | 판정 |
|---|---|---|
| 1 | 벤더 동결(REJECTED 계열)로 도착 | 게이트에 안 온다 — 기존 동결 처리(블록체인매니저 5장) |
| 2 | **VerifyVASP 사전 요청 대기함**과 대조 일치 — 수신 API 가 쌓아 둔 사전 요청·tx hash 보고와 주소·금액 매칭 (7.3) | 국내 — APPROVED |
| 3 | source 가 **Address Registry** 등록·소유 인증 주소 | 개인지갑 — APPROVED |
| 4 | **벤더(Notabene) 스크리닝 통과** 상태로 도착 | 해외 — APPROVED. 단 "국내 상대인데 VerifyVASP 보고가 안 온 건"이 여기 섞일 수 있다 — 통과로 볼지 보류로 볼지는 **정책 결정**(4장) |
| 5 | 어느 것도 아님 | **PENDING — 가용 보류**. 먼저 **Check Transaction Status 로 능동 조회**(송신측 검증 유무 확인 — 공식 확인) 후, 그래도 안 풀리면 소명·사후 등록·반환 정책 (7.4) |

- 2~3 은 우리 기록과의 대조라 확실하고, 4 가 정책이 걸리는 자리다 — 벤더 통과를 어디까지 믿을지가 국내 규제 의무(수신 정보 확보)와 부딪힌다.
- 기본값은 보류다 — **명시적으로 확인된 것만 가용**으로 보낸다(화이트리스트 방식). PENDING 의 만료·해소는 4장 시간 규칙.

## 이 설계가 값을 내는 곳

| 바뀌는 일 | 손대는 곳 |
|---|---|
| 망 추가 (예: **CODE 직접 연동** — 상호연동 실효가 부족하면 · 6장 비교 표) | 어댑터 1개 + 라우팅 규칙 — CODE 는 사전 승인이 동기라 어댑터가 오히려 단순 |
| VerifyVASP 연동 방식 변화 (직접 연동 B 확정 — 6장) | VerifyVASP 어댑터 내부만 |
| 같은 상대가 두 망 모두 회원 — 우선순위 변경 | 라우터 정책 데이터만 |
| 임계·면제 기준 변경 | 어댑터의 NOT_REQUIRED 판정만 |
