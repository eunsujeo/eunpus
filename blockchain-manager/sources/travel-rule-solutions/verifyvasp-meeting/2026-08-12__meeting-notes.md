# VerifyVASP 담당자 회의록 정리

- 회의일: 원문 미기재
- 기록 수령일: 2026-08-12
- 자료 성격: VerifyVASP 담당자 설명을 정리한 내부 회의록
- 검증 상태: 회의 발언을 보존한 자료이며, 법령·규제기관 원문이나 제품 계약 문서로 독립 검증하지 않음

## 1. 트래블룰과 은행권 확대에 관한 설명

VerifyVASP 측은 다음과 같이 설명했다.

- VASP 신고수리제는 FATF 권고 15 이행의 결과이고, 트래블룰은 FATF 권고 16에 해당한다.
- 권고 15 미이행은 국가 블랙리스트와 국가 신용에 영향을 줄 수 있다고 설명했다.
- 트래블룰의 기원으로 미국 BSA를 언급했고 9·11 이후 강화됐다고 설명했다.
- 가상자산 이전은 상대가 금융기관이라는 보장이 없으므로 `상대방 확인 → 수취인 확인 → 확인된 곳에만 전송`하는 절차가 필요하다.
- 현재 SWIFT는 수취인 본인확인을 하지 않아 사기 거래가 발생할 수 있는 구조라고 평가했다.
- 개정된 FATF 권고 16에 따라 은행권도 2030년까지 수취인 확인 체계를 이행해야 한다는 견해를 제시했다.
- DBS가 B2B·기관 거래를 중심으로 VerifyVASP를 이용하는 고객이며 SWIFT와 PoC를 진행 중이라고 설명했다.

위 내용 중 FATF 개정 내용·시행 일정, DBS 고객 관계, SWIFT PoC 현황은 회의 발언으로만 기록하며 별도 확인이 필요하다.

## 2. VerifyVASP 운영 구조에 관한 설명

### 출금

1. 사전 승인된 상대를 선택한다.
2. 고객 동의를 받는다.
3. 정보를 E2E 암호화해 상대에게 전달한다.
4. 상대 VASP가 자체 DB와 수취인 정보를 대조한다.
5. 확인된 경우에만 온체인 출금을 실행한다.

출금 전 확인은 실시간 처리가 필요하다고 설명했다.

### 입금

입금은 자금 도착 자체를 통제할 수 없으므로 다음과 같이 처리한다고 설명했다.

1. 온체인 입금을 감지해도 잔고 반영을 보류한다.
2. 자금 출처를 확인한다.
3. TXID를 이용해 상대에게 거래를 조회한다.
4. 확인이 끝난 뒤 잔고에 반영한다.

공개 개발자 문서에서 확인되는 `Check Transaction Status`의 입력은 `verificationUuid`다. 따라서 회의에서 언급한 TXID 기반 상대 조회가 VerifyVASP 단독 기능인지, CODE 상호연동이나 별도 운영 절차인지 추가 확인이 필요하다.

### 상대 VASP 승인과 실사

- 상대 VASP는 사전 승인이 필요하다.
- 실사 자료는 Wolfsberg CBDDQ를 준용하고, 위험도에 따라 3개월·6개월·12개월 주기로 재실사한다고 설명했다.
- 신규 가입사가 생기면 회원사에 안내하고, 연결을 희망하는 양측의 승인을 받은 뒤 기초자료를 전달한다.
- VerifyVASP는 기초자료를 전달하지만 실사 판단은 각 VASP가 책임진다고 설명했다.

### 암호화와 데이터 보관

- 거래 건마다 키페어를 생성하고, 수신 VASP 인프라 안에서만 복호화한다고 설명했다.
- VerifyVASP 중앙 구간은 메시지를 메모리에서 처리한 뒤 폐기하며 개인정보를 저장하지 않는다고 설명했다.
- 공개 개발자 문서에서는 공개키 운용 단위를 `PerVasp`, `PerAddress`, `PerVerification` 중 선택할 수 있다고 설명한다. 따라서 회의의 "거래 건마다 키페어"는 실제 도입 설정 또는 운영 방침인지 확인이 필요하다.
- 중앙 서버의 무저장 설명은 각 VASP가 운영하는 Enclave 전용 DB의 검증정보·키 저장과 구분해야 한다.

### 통신 방식

- 트래블룰 정보 교환은 오프체인으로 처리한다고 설명했다.
- CODE가 온체인 방식을 시도했다가 철회했다고 언급하면서, 트래블룰은 실시간 처리와 무분쟁이 필요하지만 블록체인은 이에 맞지 않는다는 견해를 제시했다. 이 내용은 CODE 공식 자료로 별도 확인하지 않았다.

### 처리 실적에 관한 설명

다음 수치는 VerifyVASP 측이 회의에서 제시한 값이며 독립 검증하지 않았다.

| 항목 | 회의 발언 |
|---|---:|
| 일 처리금액 | 4.5조원 |
| 최대 처리건수 | 20만건 |
| 건당 금액 | 3만~4만달러 |
| 거절 비율 | 9% |
| 글로벌 시장점유율 | 90% |

체인 오입력에 따른 자산 소실 방지, 사칭 보이스피싱 소멸, 해외 OCR 오독 방지를 운영 효과로 설명했다.

## 3. 국내 규제와 네트워크에 관한 견해

### 100만원 미만 거래

VerifyVASP 측은 FATF 원문이 전건 정보 교환을 요구하고 소액 거래에는 검증만 면제하는데, 한국은 트래블룰 자체를 면제한 것으로 해석했다고 설명했다. 그 결과 다음 문제가 생긴다는 견해를 제시했다.

- 개인정보 최소수집 원칙 때문에 사업자가 자율적으로 정보를 수집하기 어렵다.
- 99만원 단위 분할 송금으로 우회할 수 있다.
- 상대 VASP를 확인하기 어렵다.
- 시세 변동 때문에 거래별 임계값 판정이 불안정하다.

두바이·한국·필리핀을 면제 운영 국가로 언급했고, 국내 개정이 추진 중이나 통과되지 않았으며 업비트는 자율적으로 전건 이행한다고 설명했다. 이 내용은 규제기관 원문과 각 사업자 정책으로 별도 확인해야 한다.

제재 대상 거래에는 위험기반접근으로 우회할 수 없고, 상대를 확인한 뒤 전송하는 방법 외에는 대안이 없다는 견해를 제시했다.

### CODE 상호연동

VerifyVASP 측은 다음과 같은 비대칭 위험을 설명했다.

- `업비트 → VerifyVASP → CODE → 빗썸` 방향에서는 VerifyVASP 관점에서 CODE가 회원사이므로 문제가 없다고 보았다.
- `빗썸 → CODE → VerifyVASP → 업비트` 방향에서는 빗썸이 VerifyVASP에 정보 제공을 동의하지 않은 경우 빗썸 측 위험이 생길 수 있다고 설명했다.

이 설명은 현재 계약·동의 구조와 실제 상호연동 정책으로 확인해야 한다.

업비트는 VerifyVASP만 사용한다고 설명했다. VerifyVASP는 회원사의 실사 결론을 대신 내리지 않고 기초자료만 제공하며, SWIFT RMA처럼 양 당사자가 직접 1:1로 관계를 설정하는 구조와도 차이가 있다고 설명했다.

### LEI

FATF가 상대방 확인에 LEI를 사용할 수 있도록 명시했으며, 국내 LEI 발급기관으로 한국예탁결제원을 언급했다. 규정 적용 범위와 국내 발급기관 현황은 공식 원문으로 별도 확인해야 한다.

## 4. 은행 스테이블코인 적용에 관한 설명

VerifyVASP 측은 은행 간 스테이블코인 전송도 트래블룰 대상이라는 견해를 제시했다. 국내 은행 간 전송이라도 가상자산 이전은 remittance와 동일하게 취급되며, 기준은 특정 기술이나 벤더가 아니라 교환해야 할 정보 목록이라고 설명했다.

- 국내 은행 간에는 암호화 파일 등 합의한 수단을 사용할 수 있다.
- 해외로 확장할 때는 상대 기관이 사용하는 수단에 맞춰야 한다.
- 어떤 전송 방식이든 FATF가 요구하는 정보는 포함해야 한다.
- 망분리 환경에서는 DMZ를 통과할 정보 규격을 최소화하고, 고정 문자열·고정 길이 전문을 사용하는 방안을 논의했다. JSON 불허는 회의에서 제시된 당행 설계 판단이며 VerifyVASP 제품 요구사항으로 확인된 내용은 아니다.
- VerifyVASP는 AWS 한국 리전을 운영하며 국내 사업자의 첫 접점은 국내 서버, 해외 상대 거래는 싱가포르를 경유한다고 설명했다.

은행 간 스테이블코인 전송의 구체적 법적 의무, 전송 정보 목록, 적용 시점은 FATF·국내 법령·감독기관 원문으로 별도 확정해야 한다.

## 5. 산업 전망에 관한 견해

레거시 금융과 가상자산 산업은 규제 체계 면에서 수렴할 것이며, 금융권의 시장 규모로 외연이 확대될 것으로 전망했다. `규제 차익은 혁신이 아니다`라는 입장을 제시하면서, 라이선스와 규제 준수 역량을 갖춘 소수 사업자가 시장을 확보할 것으로 보았다.

## 6. 문서 반영 시 적용 규칙

- 제품 구조·운영 흐름은 `VerifyVASP 측 회의 설명`으로 인용한다.
- 수치·고객·PoC·시장점유율은 `벤더 제시값`으로 표기하고 용량 산정이나 도입 결정의 확정 근거로 사용하지 않는다.
- 법령·규제 해석은 현행 법제 문서를 덮어쓰지 않고 `VerifyVASP 측 견해`로만 기록한다.
- 공식 개발자 문서와 다른 설명은 차이를 함께 적고 확인 과제로 남긴다.
