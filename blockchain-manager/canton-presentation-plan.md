# Canton Network 발표자료 — 제작 계획

> 칸반 관리 대상이 아닌 참고 문서다 (`claude-code-loops-guide.md` 와 같은 위치). 발표자료 카드는
> `docs/캔톤네트워크/발표자료/` 에 있고 슬라이드 실물은 `app/public/canton-slides.html` 이다.
> 이 문서는 그 슬라이드를 만들 때 정한 목적·서사·시각 규칙과 스토리보드를 남긴 것이며, 슬라이드를 고칠 때 먼저 읽는다.
>
> 작성 2026-09-17 · 스토리보드와 색 규칙 2026-09-21 추가 · 10장 제작 완료 2026-09-21

기존 발표자료는 폐기했다. 다음 작업에서는 웹 문서를 여러 장으로 나누는 방식이 아니라, 발표자가 말할 여백과 한 장의 메시지가 분명한 슬라이드를 처음부터 다시 만든다.
이 계획은 발표 목적, 이야기 순서, 시각 원칙과 검토 절차를 정한다.

## 1. 발표 목적

- **대상** — Canton을 처음 접하는 기획자·개발자·의사결정자.
- **발표 시간** — 10~15분.
- **한 문장 목표** — 청중이 “Canton은 프라이빗 체인을 하나 더 만든 것이 아니라, 거래별로 공개 범위를 달리하면서 기관들이 하나의 네트워크에서 거래하게 만든 구조”라고 설명할 수 있어야 한다.
- **범위** — 정의, 등장 배경, 퍼블릭·전통적 프라이빗 체인과의 차이, 핵심 구성요소, 한 거래가 확정되는 흐름.
- **제외** — 토큰 표준 상세, 운영 명령, API, 구축 절차, 수수료 수치, 수탁사별 연동 사양. 필요하면 별도 기술편으로 분리한다.

## 2. 이야기 순서

| 장 | 한 장의 질문 | 핵심 메시지 | 주된 표현 |
|---:|---|---|---|
| 1 | 모두가 검증하려면 모두가 봐야 할까? | 발표 전체를 관통하는 질문을 먼저 던진다. | 제목과 하나의 대비 장면 |
| 2 | 퍼블릭 블록체인은 어떻게 신뢰를 만드나? | 모든 노드가 같은 원장을 받아 검증하는 전역 복제가 신뢰의 기반이다. | 하나의 거래가 전체 노드로 퍼지는 그림 |
| 3 | 기관 거래에서는 무엇이 문제가 되나? | 금액·상대·시점·계약 조건의 전역 노출은 기관의 사업 기밀과 충돌한다. | 2장의 같은 그림에서 노출 정보만 강조 |
| 4 | 전통적 프라이빗 체인은 무엇을 해결했나? | 접근을 제한해 프라이버시는 얻지만 네트워크가 사일로로 나뉜다. | 서로 연결되지 않은 원장 섬 |
| 5 | Canton은 질문을 어떻게 바꿨나? | 원장을 통째로 공개하거나 가두지 않고 거래별 당사자에게 필요한 뷰만 전달한다. | 하나의 거래가 서로 다른 뷰로 분해되는 대표 그림 |
| 6 | 퍼블릭·프라이빗·Canton은 무엇이 다른가? | 차이는 공개/비공개 이분법이 아니라 데이터 배포와 검증 범위다. | 세 모델의 동일 축 비교 |
| 7 | 누가 무엇을 맡나? | Party는 주체, Participant는 거래 검증·보관, Synchronizer는 순서·확정을 조정한다. | 역할 3개만 남긴 구조도 |
| 8 | 거래 한 건은 어떻게 확정되나? | 제출 → 당사자별 뷰 → 순서화 → 관련 참여자 검증 → 확인 → 커밋으로 진행된다. | 한 방향 흐름 애니메이션 |
| 9 | 그래서 어디에 적합한가? | 기관 간 자산·계약·DvP처럼 연결성과 기밀성이 동시에 필요한 거래에 맞는다. | 두 기관의 원자적 정산 사례 |
| 10 | Canton을 한 문장으로 말하면? | 거래별 공개 범위와 검증 주체를 설계하는 기관용 네트워크다. | 첫 질문에 대한 짧은 답 |

## 3. 시각 방향

### 핵심 장치

발표 전체에서 **같은 거래 한 건**을 반복해서 사용한다. 2장에서는 모든 노드에 복제되고, 4장에서는 폐쇄된 원장 안에 갇히며, 5장에서는 당사자별 뷰로 나뉜다. 청중은 매번 새로운 도식을 해석하지 않고 데이터가 전달되는 범위의 차이만 비교한다.

### 색과 활자

| 역할 | 값 | 사용 원칙 |
|---|---|---|
| 깊은 남색 | `#101C3C` | 제목·핵심 구조 |
| 종이색 | `#F5F8FC` | 기본 배경 |
| 코발트 | `#2C5BFF` | 거래와 활성 흐름 |
| 시안 | `#27C2D1` | Canton의 선택적 연결 |
| 슬레이트 | `#565F73` | 보조 설명. 시안 채움 위에서도 4.5:1 을 넘기려고 처음 잡았던 `#667085` (4.35:1) 보다 한 단계 어둡게 바꿨다 |
| 경고색 | `#D97706` | 노출·충돌을 설명할 때만 제한 사용 |

- **운영체제 기본 서체 스택**을 쓴다. 4절이 웹폰트를 금지하므로 Pretendard·IBM Plex Mono 지정은 쓰지 않는다. 심으려면 base64 로 넣어야 하는데 파일이 수 MB 가 된다.
- 한 장에는 제목 하나, 결론 문장 하나, 주 시각 요소 하나만 둔다.
- 본문은 가급적 40단어 이내로 제한하고 나머지 설명은 발표자 노트로 옮긴다.
- 카드 격자, 장식용 배지, 의미 없는 번호와 그라데이션은 사용하지 않는다.

### 색을 쓰는 규칙 (2026-09-21 시안에서 실측 후 확정)

- **시안은 획과 면에만 쓰고 글자에는 쓰지 않는다.** 밝은 배경 위 시안 글자는 2.03:1 로 회의실에서 읽히지 않는다.
- **결론 문장은 남색으로 쓰고 강약은 굵기로만 준다.** 매 장의 핵심 한 줄을 슬레이트(4.67:1)로 두면 제목(15.73:1)과 격차가 지나치게 벌어져, 프로젝터에서 가장 중요한 줄이 가장 먼저 흐려진다.
- **모델 구분을 색조에만 얹지 않는다.** 코발트와 시안은 둘 다 파랑이라 옅은 틴트로 깔면 같은 색면으로 보인다. 퍼블릭(2장)은 윤곽만, Canton(5장)은 채움으로 나눈다. 받는 쪽은 채움 농도로 세 단계를 준다 — 서명자는 채움, 관찰자는 옅은 채움, 아무것도 받지 않는 쪽은 점선 윤곽.
- 본문 글자는 어느 배경 위에서든 4.5:1 이상을 유지한다. 채움 위에 글자를 올릴 때는 합성된 배경색으로 다시 잰다.

## 4. 화면 규격과 동작

- 기본 화면은 16:9이며 회의실 프로젝터에서 읽히는 크기를 우선한다.
- HTML 한 파일로 만들고 외부 CDN·웹폰트에 의존하지 않는다.
- 키보드, 클릭, 터치 이동과 전체화면을 지원한다.
- 인쇄 시 각 슬라이드가 PDF 한 페이지에 정확히 들어가야 한다.
- 애니메이션은 8장의 거래 흐름 한 곳에 집중하고 `prefers-reduced-motion`을 지원한다.
- 블록체인 매니저에서는 `캔톤네트워크 → 발표자료`에 단일 문서 뷰로 연결한다.

## 5. 제작 순서

1. **스토리보드** — 10장의 제목·결론 문장·발표자 멘트를 텍스트로 먼저 확정한다.
2. **핵심 3장 시안** — 2장(퍼블릭), 5장(Canton), 8장(거래 흐름)만 만들어 서사와 시각 언어를 검증한다.
3. **전체 제작** — 시안 승인 후 나머지 장을 같은 규칙으로 확장한다.
4. **발표 리허설** — 10~15분 안에 설명되는지 확인하고 화면의 설명문을 덜어낸다.
5. **배포 검증** — 데스크톱·모바일·프로젝터 비율, 키보드·터치·전체화면·PDF를 확인한 뒤 블록체인 매니저에 배포한다.

## 6. 세 번의 리뷰

| 차수 | 검토 대상 | 통과 기준 |
|---:|---|---|
| 1차 | 내용과 서사 | 퍼블릭 → 프라이빗 → Canton → 동작 방식이 끊기지 않고 이어진다. |
| 2차 | 시각과 발표성 | 각 장을 3초 안에 훑어 핵심을 파악할 수 있고, 발표자가 말할 여백이 있다. |
| 3차 | 기술과 배포 | 깨진 글꼴·잘림·스크롤이 없고 입력 방식과 PDF 출력이 모두 동작한다. |

각 리뷰에서 수정 목록을 먼저 기록한 뒤 반영한다. 같은 장을 즉흥적으로 여러 번 덧붙이지 않는다.

## 7. 완료 조건

- 10장 모두 한 장에 하나의 주장만 담는다.
- 2·4·5장이 같은 거래를 사용해 세 모델의 차이를 직접 비교한다.
- 6장의 비교 축과 7~8장의 용어가 저장소의 Canton 개념 문서와 일치한다.
- 발표자 노트를 제외한 본문만 읽어도 흐름이 이어진다.
- 10~15분 리허설과 세 차례 리뷰를 통과한다.
- 최종 HTML과 PDF가 블록체인 매니저에서 동일한 내용으로 열린다.

## 부록 — 스토리보드 (10장 확정본, 2026-09-21)

계획 5절의 1단계 산출물이다. 각 장은 제목 하나, 결론 문장 하나, 주 시각 하나로 제한한다. 본문에 없는 설명은 발표자 노트로 내린다.

용어와 단계는 저장소의 Canton 개념 문서를 따른다. 2절 표의 8장 흐름은 "제출 → 당사자별 뷰 → 순서화" 순으로 적혀 있었으나, [8. 트랜잭션 흐름](docs/캔톤네트워크/개념/08-transaction-flow.md)은 **제출 → 순서화 → 분배 → 확인 → 커밋** 순이다. 스토리보드는 개념 문서를 따랐다.

### 1장 — 모두가 검증하려면 모두가 봐야 할까?

- **결론 문장** — 없음. 질문만 남긴다.
- **시각** — 제목과 대비 장면 하나.
- **노트** — 15분 동안 이 질문 하나를 따라갑니다. 답부터 말하면 "아니오"입니다. 그런데 지금까지는 왜 그래야 했는지부터 봐야 합니다.

### 2장 — 퍼블릭 블록체인은 어떻게 신뢰를 만드나?

- **결론 문장** — 모든 노드가 같은 원장을 받아 각자 검증한다. 신뢰는 거기서 나온다.
- **시각** — 거래 한 건(기관 A → 기관 B, 100)이 모든 노드로 복제된다.
- **노트** — 중개자를 믿는 대신 전원이 같은 것을 보고 각자 확인합니다. 이 구조가 퍼블릭 체인의 힘입니다. 이 거래 한 건을 발표 내내 따라다니겠습니다.

### 3장 — 기관 거래에서는 무엇이 문제가 되나?

- **결론 문장** — 그 힘의 대가는 완전한 투명성이다. 금액·상대·잔액·타이밍이 전부 드러난다.
- **시각** — 2장과 같은 그림에서 노출되는 정보만 경고색으로 강조한다.
- **노트** — 거래 패턴만 모아도 포지션과 전략이 역산됩니다. 기관 금융에서는 강점이 아니라 결격 사유입니다. 주소는 익명이라 "KYC 통과한 상대와만 거래" 같은 요건을 강제하기도 어렵습니다.

### 4장 — 전통적 프라이빗 체인은 무엇을 해결했나?

- **결론 문장** — 접근을 막아 프라이버시는 얻었지만 망이 섬으로 갈라졌다.
- **시각** — 서로 연결되지 않은 원장 섬들. 같은 거래가 한 섬 안에 갇혀 있다.
- **노트** — 참여자를 제한하면 내용은 가려집니다. 대신 다른 컨소시엄과는 거래가 안 됩니다. 상대할 기관마다 망을 하나씩 만들 수는 없습니다.

### 5장 — Canton은 질문을 어떻게 바꿨나?

- **결론 문장** — 원장을 통째로 공개하지도 가두지도 않는다. 거래별로 당사자에게 필요한 뷰만 간다.
- **시각** — 같은 거래가 당사자별 뷰로 나뉜다. 무관한 제3자는 0건.
- **노트** — 같은 거래인데 노드마다 받는 게 다릅니다. 기관 A와 B는 자기 뷰를, 감독기관은 관찰 뷰를 받고 무관한 제3자는 아무것도 받지 않습니다. 가운데 Synchronizer도 내용을 못 읽습니다.

### 6장 — 퍼블릭·프라이빗·Canton은 무엇이 다른가?

- **결론 문장** — 차이는 공개냐 비공개냐가 아니라 데이터가 어디까지 가고 누가 검증하느냐다.
- **시각** — 세 모델을 같은 축(데이터 배포 범위·검증 주체·망 연결성)으로 비교한다.
- **노트** — 표를 읽지 말고 축만 보십시오. 퍼블릭은 전원 배포·전원 검증·연결 유지, 프라이빗은 컨소시엄 배포·컨소시엄 검증·섬, Canton은 이해관계자 배포·이해관계자 검증·연결 유지입니다.

### 7장 — 누가 무엇을 맡나?

- **결론 문장** — 파티는 주체, 밸리데이터는 저장과 검증, Synchronizer는 순서와 확정이다.
- **시각** — 역할 세 개만 남긴 구조도.
- **노트** — 밸리데이터는 자기 파티가 이해관계자인 컨트랙트만 저장합니다. 전체 사본을 든 주체가 어디에도 없습니다. Synchronizer는 시퀀서와 미디에이터로 나뉘고 상태도 자산도 쥐지 않습니다.

### 8장 — 거래 한 건은 어떻게 확정되나?

- **결론 문장** — 제출 → 순서화 → 분배 → 확인 → 커밋. 커밋은 즉시 확정되고 되돌림이 없다.
- **시각** — 한 방향 흐름. 발표자료에서 애니메이션은 이 장에만 쓴다.
- **노트** — 순서화 요청은 암호화된 채로 갑니다. 시퀀서는 내용을 못 읽고 순서만 매깁니다. 분배에서 각자 자기 뷰만 받습니다. 확인은 서명자만 하고 관찰자는 열람만 합니다. 커밋은 결정적입니다. 확률적 최종성이 아니라 그 자리에서 끝납니다.

### 9장 — 그래서 어디에 적합한가?

- **결론 문장** — 연결성과 기밀성이 동시에 필요한 기관 간 거래. 대표가 DvP다.
- **시각** — 두 기관의 원자적 맞교환.
- **노트** — 자산과 대금이 한 거래에서 같이 넘어가거나 둘 다 안 넘어갑니다. 그러면서 각 기관은 자기 다리만 봅니다. 기존에는 이 둘을 동시에 얻을 수 없었습니다.

### 10장 — Canton을 한 문장으로 말하면?

- **결론 문장** — 거래별로 공개 범위와 검증 주체를 설계하는 기관용 네트워크다.
- **시각** — 1장 질문에 대한 짧은 답.
- **노트** — 질문으로 돌아갑니다. 모두가 검증하려면 모두가 봐야 하는가. 아니오, 이해관계자가 검증하면 됩니다.
