# 블록체인 인덱서 구현과 운영에 대한 심층 분석 보고서

*보고서 작성일 2026-06-01. 본 markdown 은 raw PDF 의 pdftotext extract 후 fact mining + 재구성.*

## Executive summary

블록체인 인덱서 = **ETL + 질의 가속 레이어**. 원장에 순차 기록되는 블록·트랜잭션·이벤트·상태 변화를 애플리케이션이 읽기 쉬운 형태로 추출 → 스키마화 → DB/검색 인덱스 적재 → GraphQL/SQL/REST/gRPC 로 제공. Polkadot 문서는 "블록체인 데이터용 검색 엔진" 으로 비유 (source: `docs.polkadot.com/parachains/integrations/indexers/`).

**4 가지 본질적 필요성**: ① 성능 (다중 블록·과거 상태·집계 질의는 직접 RPC 로 비효율), ② UX ("지금 막 발생" + "역사 집계" 동시 요구), ③ 데이터 접근성 (도메인 schema · 페이징 · 전문검색), ④ 분산성 (잘못 설계하면 application 계층에서 다시 중앙화). The Graph 는 네트워크형 indexer market + slashing + signed receipt 로 보완 (source: `thegraph.com/docs/en/indexing/overview/`).

## Key Concepts

### 1. 4 구현 패턴 (반복되는 실무 패턴)

| 패턴 | 메커니즘 | 대표 사례 | 장점 | 단점 |
|---|---|---|---|---|
| **(P1) 풀노드 기반 pull** | JSON-RPC / WebSocket / tracing API / 내부 framework 에서 직접 read | Geth · Reth · nearcore · NEAR Indexer | 정합성 · 분산성 | 노드 운영 · 스토리지 부담 |
| **(P2) 이벤트 스트리밍** | validator 내부 plugin 또는 pub/sub 으로 push | Solana Geyser · Yellowstone gRPC · Ethereum WebSocket subscribe · Kafka | 저지연 | 재전송 · 중복 · reorg 처리 중요 |
| **(P3) 트랜잭션·이벤트 스캔** | 체인 전체 훑되 handler filter · topic filter · address filter · dictionary 로 선택 | EVM logs · SubQuery dictionary · Blockscout catchup | 선택적 필터링 효율 | filter 설계 의존도 |
| **(P4) 상태 스냅샷 / 데이터 레이크** | 원시 체인 데이터를 파일 · 오브젝트 스토리지 · gRPC 스트림으로 외부화 | NEAR Lake · Firehose | 대량 재처리 · 병렬화 쉬움 | 외부 공급자 의존도 |

→ 실무에서는 보통 **2~3 패턴 조합** (예: The Graph = Firehose 병렬 + Graph Node pull + Postgres 적재).

### 2. 참조 아키텍처 (5 대표 사례의 공통 요소)

```
체인 데이터 소스 (Full Node · Archive · Geyser · Firehose · S3 Lake)
        ↓
데이터 수집기 (RPC Poller · WebSocket · gRPC · File Reader)
        ↓
체크포인트 · 리오그 관리자 (Cursor · Block Confirmation · Rollback)
        ↓
파서/디코더 (ABI / IDL / Schema decode)
        ↓
정규화 이벤트 로그 (Append-only Raw Store) ← 핵심: immutable
        ↓                     ↓
Projection Workers       Stream Bus (Kafka, optional)
(Balances · Transfers ·         ↓
 NFTs · Search Docs)     백업 · 복구 · 재동기화
        ↓
저장 계층:
  · 기준 (PostgreSQL — system of record)
  · 캐시/상태 (RocksDB · Redis)
  · 검색 (Elasticsearch · OpenSearch)
        ↓
Query API (GraphQL · REST · SQL · gRPC)
        ↓
게이트웨이 / WAF / Rate Limit / 모니터링 (Prometheus · Grafana)
```

**핵심 원칙**: 수집 단계와 질의 단계 분리. Graph Node = 전용 query node + dedicated indexing node + Postgres shard. Blockscout = indexer mode / API mode / webapp mode 분리. Solana = validator 와 무거운 RPC 질의 분리를 위해 Geyser 외부화 (source: `docs.anza.xyz/validator/geyser`).

### 3. 데이터 모델 — 공통 5 entity + 도메인 projection

원시 블록 구조 복사 ❌ → 체인 공통 entity + 도메인 entity 분리.

**공통 layer**: `Block` / `Transaction` / `Log/Event` / `StateChange` / `Checkpoint`
**도메인 layer**: `TokenTransfer` / `NFTTransfer` / `PoolSwap` / `AccountBalance` / `OrderBookFill` etc.

GraphQL schema 예시 (EVM · Substrate · NEAR · Solana 공통 적용 가능):

```graphql
type Block @entity {
  id: ID!
  chainId: String! @index
  height: BigInt! @index(unique: true)
  hash: Bytes! @index(unique: true)
  parentHash: Bytes! @index
  timestamp: Date! @index
  status: String! @index  # processed / confirmed / finalized
}

type Transaction @entity {
  id: ID!
  block: Block! @index
  hash: Bytes! @index(unique: true)
  from: Bytes @index
  to: Bytes @index
  nonce: BigInt
  success: Boolean! @index
  gasUsed: BigInt
  feePaid: BigInt
}

type Event @entity {
  id: ID!
  tx: Transaction! @index
  block: Block! @index
  contractOrProgram: Bytes @index
  topic0: String @index
  eventName: String @index
  logIndex: Int @index
  payload: JSON
}

type StateChange @entity {
  id: ID!
  block: Block! @index
  account: Bytes! @index
  key: String! @index
  value: JSON
}

type MaterializedBalance @entity {
  id: ID!
  account: Bytes! @index
  asset: Bytes! @index
  balance: BigInt! @index
  asOfBlock: BigInt! @index
}

type Checkpoint @entity {
  id: ID!
  worker: String! @index(unique: true)
  lastProcessedHeight: BigInt! @index
  lastFinalizedHeight: BigInt! @index
  cursor: String
  updatedAt: Date! @index
}
```

### 4. 비기능 요구사항 8-axis

| 요구사항 | 의미 | 권장 전술 | 지표 |
|---|---|---|---|
| **일관성·정합성** | reorg / 미확정 / 중복 수신에도 결과 불변 | block confirmation 정책, append-only raw log, idempotent upsert, cursor 저장, rollback/replay | rollback 성공률, data drift 건수 |
| **지연시간** | UX 에 보이는 최신성 | 소스별 commitment 분리, hot projection 우선, cache/streaming | head lag, p95 ingest latency |
| **처리량** | 고 TPS · 대규모 백필 | filter/dictionary, parallel worker, Kafka partitioning, bulk write | blocks/s, tx/s, rows/s |
| **확장성** | 체인 수 · projection 수 · 질의량 증가 | API/Indexer 분리, query node 분리, DB sharding, table partitioning | shard 별 QPS, DB wait time |
| **보안** | 데이터 위조 · DoS · 오염 방지 | signed receipts, WAF/API gateway, query complexity 제한, 최소 포트 노출 | invalid proof 비율, rate-limit hit |
| **프라이버시** | 오프체인 enrichment · 운영 로그 노출 최소화 | query receipt/log 분리, TLS, 접근제어 | PII 항목 수, 암호화 범위 |
| **운영성** | 백업 · 재동기화 · 장애 복구 | raw log 보존, snapshot 백업, 재처리 파이프라인, Prometheus/Grafana | RPO, RTO, replay 시간 |
| **마이그레이션** | 스키마 변경 시 서비스 중단 최소화 | schema migration flag, blue/green projection, versioned API | migration 시간, rollback 가능 여부 |

### 5. 5 대표 사례 비교

| 사례 | 데이터 원천 | 핵심 패턴 | 공개 수치 / 설정값 | 강점 | 한계 |
|---|---|---|---|---|---|
| **The Graph** | Graph Node + Firehose/Substreams | entity projection + sharding + query node | 일부 subgraph sync 100x+, Prometheus endpoint, Postgres sharding | 분산형 indexer 네트워크, 표준 GraphQL | Postgres 의존, 대규모 변환은 Substreams 설계 필요 |
| **NEAR** | nearcore Indexer / 과거 Lake / ReadRPC | full-node stream + state/tx indexer 분리 | 3.8s min / 5–7s avg, Lake 6–8s avg, $500+/mo vs $20/mo, Explorer mainnet 3TB | 체인 직접 읽기, 상태변화 모델 명확 | Lake 2026-03-24 중단, 일부 공개 수치 역사적 |
| **Polkadot/Substrate + SubQuery** | RPC + dictionary + filter | selected block scan + GraphQL | worker threads 최대 4배, batch-size 100, default block confirmations 200 (EVM) | 멀티체인, filter/dictionary 최적화 | RPC 품질 의존, 운영 지식 필요 |
| **Solana** | Geyser / Yellowstone / WebSocket | validator-side streaming | slot 400–600ms, plugin 예시 `threads=20 batch_size=20` | 초저지연, validator/RPC 분리 | 고 TPS · 대용량, 운영 리소스 큼 |
| **Ethereum + Blockscout** | JSON-RPC / eth_subscribe / tracing / archive | realtime + catchup + secondary fetchers | path archive ~2TB or 6.5TB, hash archive 20TB+, sync 약 2주 ~ 수개월 | explorer/API 운영성, historical/tracing 강함 | 스토리지·컴퓨트 비용 큼 |

### 6. 기술 스택 비교 (오픈소스)

| 기술 | 주 용도 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|---|
| **The Graph / Graph Node** | Subgraph 기반 인덱싱·GraphQL 질의 | 분산형 indexer 네트워크, query node 분리, Postgres shard, Prometheus/Grafana | GraphQL/entity 모델 중심이라 자유로운 변환에 제약, Postgres 의존 | dApp 용 공개 API, 표준 이벤트 중심 도메인 |
| **Firehose / Substreams** | 대규모 병렬 추출·변환 | sub-second live streaming, fork-aware streaming, cursor resume, 병렬 실행, 일부 subgraph 100x+ | 도입 복잡도 · 학습 비용, 별도 저장/서빙 계층 설계 필요 | 대규모 백필, 멀티프로젝션, 고성능 ETL |
| **SubQuery** | 멀티체인 인덱서 SDK + GraphQL | EVM·Substrate·NEAR 등 폭넓은 지원, filter/dictionary, worker thread, schema migration, query protection | 프레임워크 복잡도, 고급 운영은 여전히 Postgres/RPC 품질에 좌우 | 멀티체인, 빠른 개발, 자체 호스팅 또는 네트워크 배포 |
| **Blockscout** | EVM 탐색기 / 인덱서 | realtime + catchup 이중 인덱서, 다수 secondary fetcher, API/UI/Indexer 분리, 체인 특화 fetcher | explorer 성격이 강해 범용 데이터 웨어하우스에는 가공 필요 | 탐색기, API, verification, 멀티 EVM 운영 |
| **Kafka** | 스트림 버스, 재처리, 역압 제어 | partition 병렬성, offset replay, retention/compaction, replication/idempotence | 운영 복잡도, broker/partition 설계 필요 | high-volume event bus, fan-out 파이프라인 |
| **PostgreSQL** | 기준 저장소, GraphQL 백엔드 | 강한 SQL, 파티셔닝, jsonb, 보조 인덱스, 운영 성숙도 | 쓰기 폭주·대규모 전문검색 약점, shard 운영 난이도 | 대부분의 인덱서의 system of record |
| **RocksDB** | 로컬 상태 저장 · 고속 KV | LSM 기반 고성능, SSD 친화적, 임베디드, 저지연 | 운영형 질의엔진 아님, 직접 API/관리 기능 적음 | state store, cache, checkpoint |
| **Elasticsearch** | 검색 · 분석 · 전문검색 | shard 기반 확장, JSON documents, aggregations, full-text search | 기준 저장소로 쓰기엔 정합성 관리 부담 | 탐색기 검색, 로그 분석, 랭킹·검색 UI |

### 7. 워크로드별 추천 조합

- **고성능 분석형**: Firehose/Substreams + Kafka + PostgreSQL + Elasticsearch
- **dApp API형**: Graph Node 또는 SubQuery + PostgreSQL + Redis 캐시
- **탐색기형**: Blockscout (이미 secondary fetcher · verification 마이크로서비스 보유)
- **초저지연 Solana형**: Geyser/Yellowstone + Kafka 또는 직접 Postgres + 로컬 KV 캐시

**선택 기준 한 줄 요약**: "백필·재처리 핵심 → streaming/file-first / 운영 단순성 → framework + Postgres-first / 검색 UX → search engine 보조 인덱스 / 탐색기 → Blockscout / 검증 가능한 분산 질의 → The Graph"

### 8. 보안 · 공격면 6 가지

1. **데이터 위조 / 오염** — 첫 방어선은 "검증 가능한 소스" (자체 풀노드, signed receipt). Ethereum 공식: "풀노드가 가장 trustless / private / censorship resistant" (source: `ethereum.org/developers/docs/nodes-and-clients/light-clients/`).
2. **Replay & reorg** — `append-only raw log + idempotent projection + checkpoint + rollback` 조합. Firehose fork-aware streaming + cursor resume, SubQuery 자동 롤백, Solana commitment 분리.
3. **DoS / query 폭주** — Solana 공식: shared public RPC 는 production 불가, 429/403 발생 (source: `solana.com/docs/rpc`). SubQuery 권장: API gateway · WAF · rate limit · TTL cache · 최소 포트 노출.
4. **Off-chain enrichment 오염** — query receipt/log 분리, TLS, 최소 정보 보관.
5. **운영자 실수 → schema 불일치** — schema version vs API version 분리.
6. **DB / Storage 자원 고갈** — head lag, DB disk, RPC rate limit 모니터링 부재 시 악화.

### 9. 비용 모델 (AWS 공식 단가 직접 인용)

```
월 총비용 =
  노드 컴퓨트 (풀노드/아카이브/인덱서/API)
+ DB 스토리지 (핫)
+ 오브젝트 스토리지 (백업/레이크)
+ 스트림 버스 비용 (Kafka 등)
+ 네트워크 egress
+ 모니터링/로그 저장
+ 운영 인력비
```

**공식 단가 인용**:
- AWS gp3: **$0.08/GB-month** (source: `aws.amazon.com/ebs/general-purpose/`)
- AWS S3 Standard: **$0.023/GB-month**, PUT/COPY/POST/LIST **$0.005/1,000 requests** (source: `docs.aws.amazon.com/solutions/.../cost-example-1.html`)

**Ethereum archive 스토리지 비용 (단순 계산)**:
- Geth path-based archive 2TB: **~$163.84/월**
- Geth path-based archive 6.5TB: **~$532.48/월**
- Geth hash-based archive 20TB: **~$1,638.40/월**

→ compute·snapshot·백업·egress 제외. Ethereum archive 기반 인덱서는 **스토리지만으로 중형 SaaS 한 대 비용**.

**S3 백업 예시**: 1TB 백업 스냅샷 = $23.55/월 저장료만. 단, 작은 파일 다수 또는 대량 egress 시 요청·전송 비용이 저장료 초과 가능.

**3-tier 예산 모델**:
- **경량**: 특정 컨트랙트/프로그램 이벤트만 — private RPC + indexer app + Postgres 수백 GB. 컴퓨트보다 DB 저장/쿼리 비용 중심.
- **중간**: 멀티프로토콜 API · explorer-lite · search — full node 또는 managed stream + Kafka optional + Postgres 1–3TB + ES. DB IOPS · 인덱스 수 · query traffic 중심.
- **중량**: Ethereum explorer/analytics · Solana low-latency — archive/full node cluster + streaming + 대형 DB + search + backup. archive storage · sustained compute · egress 비용 큼.

**비용 최적화 3 원칙**:
1. raw 와 projection 분리 → projection 재생성 가능 → backup 주기 공격적으로 단축
2. 필요한 블록만 read → dictionary · topic/address filter · startBlock 최적화
3. archive node 무조건 self-host 금지 → 초기엔 private archived RPC 또는 lake/firehose 공급자 사용

### 10. 설계 체크리스트 (11 항목)

- [ ] 데이터 원천이 명확한가 (자체 풀노드 / archive RPC / Firehose / Geyser / lake 중 무엇?)
- [ ] API 반환 확정 수준 명시했는가 (`latest` 와 `finalized` 구분?)
- [ ] raw append-only 로그를 보존하는가 (projection 만 저장하지 않음?)
- [ ] reorg/replay 시나리오 테스트, checkpoint + rollback 로직 있는가
- [ ] 필요한 블록만 읽도록 filter/dictionary/startBlock 최적화했는가
- [ ] 기준 저장소와 검색 저장소 분리했는가 (Postgres ≠ Elasticsearch 역할)
- [ ] query plane 만 외부 공개, WAF/rate limit/query complexity 제한 두었는가
- [ ] DB 파티셔닝 + 주요 보조 인덱스 (`height`, `timestamp`, `contract`, `account`) 설계했는가
- [ ] schema migration 전략 (online migration · dual-write · backfill · rollback) 정했는가
- [ ] 모니터링 항목 + SLO 정의 (head lag · query p95)
- [ ] 비용 모델에서 storage 와 egress 각각 계산, archive node 정말 필요한지 검증했는가

## Limitations (보고서 §"Open questions" 인용)

- 일부 프로젝트는 통합 처리량 · CPU/메모리 · p99 질의 지연 같은 운영 수치를 공식 문서에 상세 공개 안 함 → 공개 구조·설정값·스토리지 요구치 중심으로 비교
- Solana / Blockscout 의 end-to-end 처리량은 워크로드 의존성이 커서 자체 벤치마크 필요
- 비용 표는 공급자·리전·예약 정책에 따라 달라짐 — 본문 수치 중 스토리지 비용만 공식 단가 기반 하한선
