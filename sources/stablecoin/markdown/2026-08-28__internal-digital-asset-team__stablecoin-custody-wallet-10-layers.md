  별

  라이선스 — 특금법상 보관·관리업(VASP) 신고 + 디지털자산기본법(2028.1Q 시행 가정) 수탁업 인가
  대비
  키 관리 — Fireblocks(이하 파블) MPC 전제, 과도기 구조(파블 코리아 AWS 서울 리전 / 당행
  키관리존 / DMZ / PrivateLink) 기준
  취급 자산 — USDC·USDT 등 달러 스테이블코인, 향후 원화 스테이블코인 추가가 가능한 발행사 무관
  설계
  일정 — 기본법 시행 역산, 2027년 중 기반 구축·규제 심사 완료 목표
  ※ 본 자료는 구조·사실관계·쟁점 정리 목적이며, 특정 구조의 채택 여부나 사업 추진 여부에 대한 평
  가·판단을 포함하지 않음. 당행 내부 시스템의 명칭·경계·담당은 IT 영역 협의로 확정하며, 본
  문의 시스템 구분은 일반적인 은행 IT 구분에 따른 가정

1 · 참고 모델

CEX 지갑 구조와 스테이블코인 수탁 지갑의 차이
국내 거래소가 공개 자료·검사 결과·사고 사례를 통해 드러낸 구조는 아래 형태로 수렴 — 스테이블코
인 수탁 지갑의 출발점이자 차이를 드러내는 비교 기준
 CEX 지갑 표준형
 요소             CEX 표준형

 지갑 등급          고객별 입금주소 → 집금 지갑 → 핫(출금) → 웜 → 콜드(에어갭) — 콜드 80% 요건
                이후 핫은 당일 출금 예상량+버퍼 수준으로 축소, 콜드→핫 보충이 정기 업무
 계정 모델          옴니버스 + 내부 원장 — 고객 잔고는 DB 원장에만 존재, 체인상은 풀(pool). 입금은
                주소↔고객 매핑으로 크레딧, 매매는 원장만 이동, 출금은 핫 풀에서 송출
 키·서명           핫 = HSM 또는 MPC + 정책 기반 자동 서명(한도 이내), 초과 시 다중 승인. 콜드 =
                멀티시그·하드웨어 서명기·물리 분리·2인 세레모니 — 대형사는 자체 구축, 은행 출자
                커스터디(KODA·KDAC·BDACS 등)는 공급사 MPC 결합
 체인 연결          체인별 풀노드 이중화 + 외부 RPC 백업, 입금 감지 색인기, 체인별 확정 수 정책, 리오
                그 롤백 — 토큰은 컨트랙트 주소 화이트리스트로만 인식
 출금 처리          요청 → 2FA/지연출금 → 한도·속도·FDS → 트래블룰(100만원↑) → 승인 → 서명
                → 전파 → 확정 → 원장 확정 — 지연 거래 교체, 논스 관리, 가스 급등 시 보류
 준법감시·운영        KYC/실명계좌, KYT 입금 평가·오염자금 격리, 출금주소 사전등록, STR — 리밸런싱,
                가스 토큰 관리, 보험·준비금(핫 5%), 24시간 감시, DR
CEX 지갑의 본질은 수백 종 자산·수십 체인을 다루는 범용성이며, 지갑은 매매 엔진의 부속 시스템 — 스테
이블코인 수탁 지갑은 소수 토큰 표준을 깊게 다루는 보관·이전·결제 시스템으로, 원장이 은행 계정계형이어
야 하는 점에서 갈림
 설계 전제가 달라지는 지점
 항목           CEX 지갑                 스테이블코인 수탁 지갑
 자산 범위        수백 종, 네이티브 코인 다수       USDC·USDT·(향후 KRW) 소수 — 전부 토큰 표준

① 키 관리·서명 계층
자산 통제권의 물리적 실체 — 이 계층의 침해는 나머지 9개 계층을 무력화하므로 설계 기준은 「단일

  에 분산. 서명은 셰어 보유자 간 프로토콜로만 생성되고 완전한 개인키는 재구성되지 않음
  키 계층 — MPC 루트 → BIP32 파생으로 볼트·자산·주소 단위 키 도출. 주소 수만 개를 만들어도 백업
  대상은 루트 셰어 하나
 등급 구조와 콜드 80% 요건
  핫 정책 이내 자동 서명(집금·소액 출금) / 웜 온라인이나 사람 쿼럼 승인 필수(대액 출금·리밸런싱) / 콜
  드 정보통신망 분리 환경
  이용자보호법 시행령의 콜드 요건은 「정보통신망과 분리된 환경 보관」 — 온라인 co-signer가 셰어
  를 보유하는 MPC 볼트의 충족 여부는 감독 해석 확인이 선행 과제
  확인 전 보수적 설계 — 콜드 등급을 별도 오프라인 서명 체계(에어갭 MPC 또는 오프라인 HSM, 서명
  요청·결과를 QR·전용매체로 이동)로 두고 파블은 핫·웜 담당의 이중 구조
  콜드 출금은 지정 시간창·2인 동시 참여·물리 접근통제 하에서만 — Solana는 blockhash 만료(약
  60~90초)로 durable nonce 없이 오프라인 서명이 사실상 불가, 체인별 콜드 절차가 다름을 초기 설
  계에 반영

정책 엔진(TAP)
룰 매칭 순서 — 발신 볼트 → 목적지(화이트리스트/일회성/임의) → 자산 → 금액(건별·기간 누적) →
개시자 → 결과(자동허용/쿼럼승인/차단)
기본 거부(default deny), 마지막 룰은 전면 차단 — 정책 변경 자체가 관리자 쿼럼 대상
금액 등급 예시 — 소액 자동 / 중액 1인 승인 / 대액 2인 승인+콜백 검증 / 임계 초과 차단 후 별도 절차.
화이트리스트 외 목적지는 금액 무관 승인 강제
콜백 핸들러 — 당행 구축 영역
API co-signer가 서명 직전 행내 핸들러를 호출 → 핸들러가 행내 원장에서 「실제 요청·승인된 건인
지, 목적지·금액·자산이 일치하는지」를 독립 조회 후 승인/거부
콘솔·API 키가 탈취되어도 행내 DB에 없는 거래는 서명 불가 — Bybit(2025.2, 서명 화면 위변조로 약
15억 달러 유출)의 교훈이 정확히 이 지점: 서명자는 화면이 아닌 원문 데이터를 검증해야 함

백업·복구·출구
복구 키트 — 워크스페이스 소유자의 RSA 키+패스프레이즈로 암호화된 셰어 백업. 공급사 장애·이탈
시 오프라인 도구로 개인키 재구성 가능 → 실질적 출구 수단
RSA 키·패스프레이즈는 분리 보관(HSM·금고·인적 분할), 연 1회 이상 복구 리허설 정례화
