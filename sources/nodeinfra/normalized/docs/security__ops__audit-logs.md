# 감사 로그

감사 추적은 **두 계층**으로 구성됩니다.

- **Layer 1 — 작업별 TEE 영수증**: 모든 원장 변경 작업은 엔클레이브가 서명한 영수증을 동반합니다. 가짜 원장 엔트리로 자금을 탈취하려는 시도를 **실시간으로 차단**합니다.
- **Layer 2 — 해시 체인 + 주기적 TEE 체크포인트**: 원장 전체가 SHA-256 해시 체인으로 연결되며, 엔클레이브가 주기적으로 체인 헤드에 서명합니다. **사후 변조 탐지**와 **특정 시점 상태 증명**을 제공합니다.

두 계층은 서로를 보완합니다. Layer 1은 실시간 사기 방어, Layer 2는 감사 증거 — 둘 다 필요합니다.

## Layer 1 — 작업별 TEE 영수증

모든 원장 변경 작업은 엔클레이브가 서명한 영수증과 함께 기록됩니다:

- **Withdraw / Sweep** — 체인 트랜잭션의 Ed25519 서명이 영수증 역할 (`실행 키`)
- **Transfer** — 엔클레이브 `verify_and_authorize` 영수증이 트랜잭션 행에 저장
- **Deposit** — 원장 엔트리가 검증된 온체인 deposit(chaindb)과 대조

### 구조적 불변 조건

- **외래 키 제약** — 원장 엔트리는 반드시 영수증이 있는 작업 레코드를 참조합니다. 고아 엔트리는 **구조적으로 불가능**합니다.
- **정합성 체크 작업** — 원장 ↔ 작업 레코드 ↔ 온체인 상태를 짧은 주기로(권장: 60초 이하) 대조하며, 불일치 시 즉시 알림.

### Layer 1이 막는 공격

- **가짜 내부 credit 삽입** — DB 쓰기 권한을 가진 공격자가 가짜 “10M USDC credit” 엔트리를 삽입하려 해도, 대응하는 작업 레코드가 없거나 영수증이 없음 → 정합성 체크에서 즉시 탐지.
- **체인 서명 위조** — `실행 키`는 엔클레이브 밖으로 나간 적이 없음 → 불가능.

## Layer 2 — 해시 체인 + TEE 체크포인트

계정별 원장 엔트리가 SHA-256 해시 체인으로 연결되며(각 엔트리의 `prev_hash` = 이전 엔트리 해시), 엔클레이브가 주기적으로(예: 1시간마다 또는 100개 엔트리마다) 체인 헤드에 서명합니다:

```
sig = EnclaveSign(chain_head_hash ‖ account_id ‖ entry_count ‖ timestamp)
```

서명에는 MRENCLAVE가 함께 기록되어 어떤 엔클레이브 이미지가 서명했는지 검증 가능합니다.

### Layer 2가 제공하는 것

- **사후 변조 탐지** — 과거 엔트리를 수정하면 해시 체인이 깨지고, 마지막 체크포인트가 더 이상 일치하지 않습니다.
- **특정 시점 상태 증명** — 감사관이 “2026-04-15 14:00 UTC 기준 원장 상태는?”이라고 질문하면, 서명된 체크포인트로 답변할 수 있습니다.
- **비부인성** — 서명된 체크포인트 시점의 원장 내용을 운영자가 부인할 수 없습니다.

### Layer 2가 하지 않는 것 (중요)

**Layer 2는 실시간 사기를 막지 않습니다.** 체크포인트 사이에 공격자가 일관된 가짜 엔트리(뒤따르는 해시까지 재계산)를 삽입하면, 다음 체크포인트는 그 변조된 체인 헤드에 서명합니다. 엔클레이브는 체크포인트 시점에 주어진 체인 헤드를 서명할 뿐, “올바른 체인 헤드가 무엇이어야 하는지”를 독립적으로 알지 못하기 때문입니다.실시간 방어는 **Layer 1**이 담당합니다. 외래 키 제약과 정합성 체크로, 가짜 엔트리는 생성 즉시 영수증 부재로 탐지됩니다.

## 위협 모델

| 위협 | Layer 1 (작업 영수증) | Layer 2 (체인 + 체크포인트) |
| --- | --- | --- |
| 공격자가 체인 인출 트랜잭션 위조 | 차단 (실행 키엔클레이브 전용) | — |
| 공격자가 가짜 내부 credit · transfer 삽입 | 차단 (영수증 없음 → 정합성 체크 알림) | — |
| 공격자가 과거 엔트리 사후 수정 | — | 탐지 (체인 끊김 + 체크포인트 불일치) |
| 공격자가 과거 엔트리 사후 삭제 | — | 탐지 |
| 공격자가 엔트리 재정렬 | — | 탐지 |
| 운영자가 과거 기록 부인 | 영수증 증거 | 서명된 체크포인트 |
| 감사관의 독립적 시점 증명 요구 | 영수증별 가능 | 체크포인트 단위 암호학적 증명 |

## 감사관 검증 절차

1. DCAP 원격 증명으로 엔클레이브 공개키 확보 (MRENCLAVE 바인딩)
2. 원장 엔트리와 작업 레코드의 영수증을 조회, 엔클레이브 공개키로 서명 검증
3. 체크포인트 테이블에서 원하는 시점의 서명된 체인 헤드를 조회
4. 원장 엔트리로부터 해시 체인을 재구성하여 체크포인트의 체인 헤드와 일치하는지 확인
5. 연속된 두 체크포인트 사이의 모든 엔트리가 영수증을 가진 작업을 참조하는지 확인
