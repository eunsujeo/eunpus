번역됨||CSM  [오후 3:30]
The rawTx field is only available in the signing stage because the approval stage happens before serialization. The main reason for that is approvals (especially manual approvals) can take time and until a transaction is approved fees can change so we serialize transactions only after approval stage is completed. If you want manual approvals during the signing stage you can do so using the callback handler’s RETRY mechanism. Currently, the callback handler can get up to 20 retries every ~3 minutes (total ~1 hour), so while the callback is returning RETRY to the cosigner, you can implement a manual approvals logic on your server.

The challenge isn't around re-sending the same transaction with the same nonce. The issue is that we can't serialise the transaction until approvals have been received. If we serialise the transaction before approvals are received, there is a risk that on-chain fees change between when the transaction is submitted for approval and the time that all approvals are received (this could be many, many hours). Therefore the TxByHash can only be sent at signing stage.

Remember that this is only for transactions that are submitted with a gas fee that is too low. Have you considered automatically canceling the TX by the API and the resubmitting using a different nonce?

스레드에 댓글 남김:Hi @CSM
In the current architecture, the JV and the operator are not within the same trust boundary, and due to communication restrictions imposed by the bank, direct API calls between the two entities (the JV system and the bank’s blockchain system)  are not possible.

As a result, whatto cannot rely on the dropTransaction response generated on the JV side.

Additionally, we assume a zero-trust model between the two entities. Any inter-entity communication cannot be implicitly trusted.

However, the Callback Handler payload can be trusted because it is generated and signed by Fireblocks, and therefore cannot be modified or forged by the JV.

Therefore, we would require an approval mechanism that provides a verifiable linkage between the original transaction and the corresponding dropTransaction/boostTransaction request (e.g., through explicit inclusion of originalTxId, replaceTxByHash, or equivalent immutable identifiers in the callback payload), without requiring direct API trust between the JV and the operator.

Key Share Backup & Geo-Dispersal

MPC Architecture & Key Share Distribution
Fireblocks uses a secure Multi-Party Computation (MPC) architecture for wallet key management:

For each signing device on your side (could be mobile device and/or API Co-Signer):
One key share is generated on your device.
Two key shares are generated on separate Fireblocks-managed Intel SGX servers.
These Fireblocks-managed servers are hosted across geo-redundant multi-cloud infrastructure (AWS, Azure, GCP), ensuring resilience and global dispersal of key shares.  


Backup and Recovery Solutions
Fireblocks provides a comprehensive backup and recovery program, including:

A Disaster Recovery Kit, delivered during onboarding, enabling you to securely back up and recover the key shares—even if you lose access to all of them or Fireblocks suspends operations.
Data backups are conducted daily (and at additional intervals for critical assets), with backups encrypted at rest and in transit. Restorations are tested at least annually in dedicated environments to verify recovery integrity. Backup files are stored in geographically distinct data centers.
Key share recovery mechanisms include:
Soft Key Recovery: Device- or key share-specific recovery (e.g., lost device). Requires at least one accessible key share (existing Owner/Admin user).
Hard Key Recovery: Restoration of the whole wallet in catastrophic scenarios (e.g., all devices inaccessible, Fireblocks permanently out of service). Requires more rigorous processes which can be managed in-house, or outsourced to partners including Station70/Coin Cover   
Geographic Redundancy: The combination of customer device shares and Fireblocks’ secured, cloud-agnostic infrastructure ensures key shares are not only logically, but also geographically, separated to withstand regional failures or cloud provider outages.   


Compliance and Testing

Fireblocks is ISO 22301 (Business Continuity Management) certified and undergoes annual SOC2 Type 2 audits, including backup and recovery processes.
Regular DR and BCP testing is documented; the last noted Disaster Recovery test was completed successfully with zero adverse findings. Tests involve measuring start-to-stop recovery times and outcomes
