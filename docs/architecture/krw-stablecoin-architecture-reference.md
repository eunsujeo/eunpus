# 원화 스테이블코인 아키텍처 — Reference (K-STAR 컨소시엄 제안서 기반)

> **본 문서의 위치**: Fireblocks 같은 **SaaS custody** 와 대비되는 영역 — 규제 적합성을 전제로 한 **법정통화 연동 스테이블코인의 직접 구축 / 컨소시엄 발행** reference. 단일 1차 자료(K-STAR 컨소시엄 「원화 스테이블코인 아키텍처 제안서」, 2026-02-13, Final, 165p)를 합성하되, **이 제안서의 지갑·커스터디·서명·정책·컴플라이언스 설계가 Fireblocks 의 어떤 개념에 매핑되는지** 를 함께 reasoning 한다.
>
> **1차 자료 정체**: 카이아 DLT 재단(주저자)·람다256·안랩블록체인컴퍼니·오픈에셋 공동 작성. 검토진에 KAIST·서강대·서울대 교수, JPYC 대표, 변호사 등. 배포등급 Limited.
>
> **출처 표기**: 본 문서의 모든 fact 진술은 `(§장.절)` 로 1차 자료의 절 번호를 인용한다. 출처 없는 단정은 LLM 일반 지식이며 `[unverified]` 로 분리한다.

> **본 문서가 답하는 핵심 질문**
> 1. 왜 스테이블코인 설계는 "토큰 설계" 가 아니라 "결제 인프라 설계" 인가?
> 2. 규제의 *what*(의무)을 운영의 *how*(집행 메커니즘)로 바꾸는 통제는 무엇인가?
> 3. 기관용 지갑/커스터디/서명 구조는 Fireblocks MPC·정책엔진·co-signer 와 어떻게 대응되는가?
> 4. 발행·상환·정합성·준법·거버넌스가 하나의 감사 가능한 흐름으로 이어지는 구조는?
> 5. SaaS(Fireblocks) / 설치형 WaaS / 직접구축(본 제안서) 의 trade-off 는?

## 0. 핵심 명제 (10초 이해)

1. **스테이블코인 = 지급결제 인프라.** 일정 규모를 넘으면 토큰 상품이 아니라 지급·정산·송금 인프라로 기능한다 (§1.1, §2). 따라서 PFMI(금융시장인프라 원칙) 수준의 거버넌스·운영리스크·복원력·감사가능성이 요구된다 (§4.1).
2. **신뢰는 절차와 데이터로 강제한다.** 준비자산-발행량 정합성, 준법 신호의 거래흐름 내재화, 모든 조치의 재현 가능한 로그 — 사람의 선의가 아닌 시스템으로 (§요약, §3.2.1).
3. **규제 *what* → 운영 *how*.** 주요국(US GENIUS / EU MiCA / SG SCS / JP PSA / UK BoE) 규제는 의무를 정하지만 구현은 정하지 않는다. 본 제안서는 그 간극(권한분리·다자승인·운영모드·대사·감사로그)을 메우는 것이 목적 (§1.1.3, §2.3).
4. **권한은 분리·다자승인·감사로 격리한다.** 단일 키 단독 행사 금지. 민감 권한(발행/소각/정책변경/복구)은 MPC/멀티시그 M-of-N 공동서명으로만 (§3.4.4, §3.6.2, §4.2.2).
5. **준법은 사전통제(Pre-emptive Control)** — 정책 위반 거래는 서명 이전 단계에서 생성·서명되지 않도록 차단 (§3.6.2). 이것이 Fireblocks Policy Engine(TAP)의 핵심과 동일한 사상.

## 1. 왜 "토큰" 이 아니라 "인프라" 인가 (§1, §2)

### 1.1 framing 전환

- 스테이블코인이 결제·송금용으로 일정 규모 이상 확산되면 "토큰 상품" → "지급결제 인프라" 로 성격이 전환된다 (§1.1). 핵심 질문이 *"어떤 토큰"* 에서 *"어떤 신뢰·상환·감독·복원·위기통제 체계를 갖춘 결제 인프라"* 로 이동 (§요약).
- 동시 충족해야 할 3 축 (§요약, §1.3.2):
  1. **안전성·신뢰** — 준비자산 1:1 담보 + 시스템적 정합성 강제
  2. **규제 적합성·감독가능성** — 준법(KYC/제재/이상거래/동결)이 거래흐름·권한구조에 내재화
  3. **활용성·운영복원력** — 다양한 채널 + 장애/위기 시 안전하게 멈추고·제한하고·복구

### 1.2 4 핵심 정책 산출물 (§요약)

> 기술 아키텍처와 별개로, 제도권 신뢰를 위해 명시해야 할 정책 문서:

| 산출물 | 내용 |
|---|---|
| **상환 약관 (Monetary Contract)** | 채무자/권리자, 표준 상환 절차, 지연·보류·거절 조건, 파산절연·준비자산 법적 분리 |
| **정량적 준비자산 정책 규칙 (Quantitative Reserve Policy Rule)** | 허용 자산군·만기·집중도·유동성 버퍼·금지행위(담보제공·재담보·대차) |
| **상환 유동성 프레임워크 (Redemption Liquidity Framework)** | 평시/스트레스 유동성 원천, cut-off·대기열, SLA·수수료, 비상 조치 (§4.2.4) |
| **매크로 가드레일 (Macro Guardrails)** | 단계적 롤아웃, 발행·유통 한도, 채널/경로 한도 + 트리거 기반 확대·제한 |

### 1.3 주요국 규제의 공통 원칙 (§2.1)

US GENIUS Act / EU MiCA(ART·EMT) / SG MAS SCS / JP 개정 PSA(전자지급수단) / UK FSMA+BoE 가 법제 배경은 달라도 수렴하는 5 공통점 (§2.1):
① 발행 인가·허가(책임 주체 확정) ② 100%에 가까운 고품질 준비자산 1:1 담보 ③ 상시 1:1 상환권 ④ 준비자산 분리보관 + 정기 공시·외부검증 ⑤ 시스템적 규모 도달 시 결제시스템 수준 감독.
한국은 가상자산법(1단계 시행) + 스테이블코인 2단계 입법 준비 단계, 은행 51%+ 컨소시엄 발행 방안 거론 (§2.1.6).

## 2. 토큰 레벨 통제 요구사항 (§2.3) — Fireblocks 가 흡수하는 영역과의 대비

글로벌 스테이블코인(USDT/USDC)은 단순 ERC-20 이 아니라 **관리자 통제 함수**를 토큰 계약에 내장한다 (§2.3.2):

| 토큰 | 핵심 통제 함수 (§2.3.2 표 2.3/2.4) |
|---|---|
| **USDT (EVM)** | `addBlackList`/`removeBlackList`, `destroyBlackFunds`(블랙리스트 잔액 소각), `deprecate`(구 계약 비활성·위임) |
| **USDC (EVM)** | `owner`(역할 재지정), `pauser`, `blacklister`, `masterMinter`(minter·발행한도 관리), `minter`(권한 내 mint/burn), `rescuer`(오전송 ERC-20 회수) |

도출되는 3 축 토큰 요구사항 (§2.3.2):
1. **통제 함수**(동결/블랙리스트, 비상정지)의 존재 — ★ 체인 레벨이 아니라 **토큰 계약 자체의 관리자 권한**으로 수행 (체인 코드 변경 아님; 업그레이드도 Proxy 패턴/deprecate)
2. **발행·소각 권한의 역할 기반 분리** + 한도·승인·로그 명확화
3. **예외 복구**(오전송 회수 등) + 거버넌스

허가형(Permissioned) 구현 2 층위 (§2.3.3): (1) 네트워크 레벨(노드/검증 참여 제한 — 컨소시엄·내부 체인) vs (2) **토큰(자산) 레벨**(체인은 퍼블릭, 보유·수신·전송을 KYC/KYB 완료 주소로 토큰 계약이 강제). 본 제안서는 사회적 지급결제 인프라를 전제하므로 주로 (2)를 다룸. SG-Forge **EURCV**(화이트리스트 → MiCA 적용 후 완화) 가 "전송 규칙은 고정이 아니라 전략·리스크에 따라 조정 가능한 설계 선택지" 임을 보여줌 (§2.3.3).

> **Fireblocks 대비** — Fireblocks 는 이 토큰 레벨 통제(mint/burn 권한, freeze)를 **워크스페이스 정책 + co-signer + MPC** 로 흡수해 customer 에게 추상화한다. 본 제안서의 직접구축 모델은 동일 통제를 **토큰 컨트랙트 함수 + 오프체인 결재 연동**으로 자체 구현. 자세한 매핑은 §6.

## 3. 구현 아키텍처 (§3) — WaaS 핵심

### 3.1 4 레이어 + 참여자 경계 (§3.1)

**4 아키텍처 레이어** (§3.1.3):
1. **네트워크·접근·조회 인프라** — RPC/노드, Explorer/Index, 오라클, 브릿지
2. **스마트컨트랙트(토큰)** — 발행/소각, 전송제한, 비상통제 (RBAC)
3. **발행·상환·정합성 집행(발행 및 관리 시스템)** — 온체인을 운영으로 잇는 오프체인 집행
4. **컴플라이언스·데이터·리포팅** — 준법 신호 → 정책 집행 → 근거·결과 데이터 → 리포팅/감사

**참여자/시스템 경계** (§3.1.4) — 단순 조직도가 아니라 권한·데이터·연동의 경계선: 발행자(법적책임) / 운영주체 / 준비자산 수탁기관 / 상환창구·지급연동 / 유통채널(거래소·은행·PG·플랫폼) / 준법·보안 / 데이터·리포팅 / 외부검증·감사 / 체인·인프라 운영.

### 3.2 핵심 플로우 (§3.2)

**발행** (§3.2.2): 요청접수 → 적격성·한도 검증(KYC/KYB) → 대금수령 확인(오프체인 입금증빙) → 정책·제재 검증 + 직무분리 다자승인 → 온체인 `mint()` → 기록·대사.

**상환** (§3.2.3): 요청접수 → 토큰 동결/회수 → 준법/Hold/이상거래 체크 → **원화 지급** → 온체인 `burn()` → 기록·대사. ★ **지급-소각 순서 안전장치**: 원화 지급 최종 확정 전에는 토큰이 소각되지 않도록(순서 뒤바뀜 방지).

**운영 모드 전환·이상대응** (§3.2.4): 탐지/경보 → 평가/분류 → 거버넌스 승인 → 모드 전환(Restricted/Emergency) → 통제 집행(`pause()`/`freeze(address)`) → 복구/재개 → 사후보고. `pause`(전체 전송 중단)는 시스템적 사고 시 거버넌스 승인 하 예외 통제로만 한정.

### 3.3 발행 및 관리 시스템 (§3.3)

- **거래 참조값(요청 ID)** 으로 (i)채널 요청 (ii)오프체인 정산/지급 (iii)온체인 실행 (iv)내부 원장 반영을 단일 조회로 연결 (§3.3.3). ★ **멱등성**: 동일 요청 재처리 시 중복 발행/이중지급 방지 — "한 건은 한 번만 완료 처리" (§3.3.4, §3.3.5).
- 준비자산 정합성 확인(§3.3.6) + 대사 엔진(정상/확인필요/불일치 산출, 예외목록 분리)(§3.3.7).
- 승인 게이트(Gate): 고위험 행위는 승인 요건 충족 시에만 실행 (§3.3.8). 기록·근거자료(§3.3.9), 비상통제(§3.3.10), 외부 인터페이스(유통채널/지급정산/코어뱅킹·ERP/준비자산/준법보안/데이터)(§3.3.11).

### 3.4 블록체인 및 스마트컨트랙트 (§3.4)

**네트워크 선택 기준** (§3.4.2, 표 3.2): 확정성(Finality)·TPS(수초 내 확정, 수천~수만 TPS), 가스비 안정성(가스 추상화/스테이블코인 가스 — Circle Arc, Tether Plasma 예시), Validator 신뢰성·발행사 거버넌스 참여(체인 주권), 고가용성(99.99~99.999%), EVM 호환성, 생태계(오라클/MPC 월렛/모니터링), 국내 협업 접근성, 프라이버시 옵션(ZKP/TEE).

**네트워크 아키텍처 4 옵션** (§3.4.3, 표 3.3): ① 퍼블릭 L1 단독 ② 퍼블릭 L1 + 전용 L2(소버린 롤업) ③ 퍼블릭 L1 + 이더리움 L2 + 크로스체인 브릿지 ④ 퍼블릭 L1 + 전용 스테이블체인 L1. 권장: 퍼블릭 L1 기반 + 모듈식 확장(필요 시 L2/전용체인).

**스마트컨트랙트 핵심 기능 6종** (§3.4.4, 표 3.4):
① mint/burn + 준비자산 연계(납입 확인 후 mint, 지급 완료 후 burn, `emit Mint/Burn` 로그) ② 권한통제(Role)·다중서명(`mint`=Minter, `pause`=Pauser; 직무분리; **MPC 지갑/HSM 키 분산**) ③ 긴급중지(`pause`)·지갑동결(`freeze`/`blacklist`) — 사유코드/승인요건/적용범위/해제조건 스펙 충족 시만 ④ 업그레이드·변경관리(Proxy 또는 deprecate; 멀티시그 통제; 1:1 교환 보장) ⑤ 온체인 전송제한(Allow/Deny 리스트; **단계적 개방** 전략) ⑥ 멀티체인·브릿지(체인별 컨트랙트 + 중앙 발행량 조정; **Circle CCTP** 식 burn/mint 자동화; 공식 브릿지 화이트리스트; 비공식 래핑 토큰 상환 제외 고지; **리스크 버짓 + 서킷브레이커**; Wormhole 해킹 교훈).

### 3.5 필수 인프라 (§3.5) — 인덱서 reference 와 정합

- **노드** (§3.5.2): 전용 노드, RPC 기반 외부 연계, **아카이브 노드**(감사·과거 데이터 재현), 24/365 HA. → [[docs/architecture/blockchain-indexer-architecture-reference]] 의 raw-immutable 보존과 정합.
- **블록탐색기** (§3.5.3): 자산보유·거래 증명. 단 상용 탐색기 수준의 전체 조회는 불필요 — 발행 플랫폼 운영·규제/감사 대응 범위로 한정(인덱싱 포함). 람다256 전용노드, KaiaScan 예시.
- **브릿지** (§3.5.4): 원칙적으로 발행사 직접 **burn/mint** 모델 전제. lock/unlock(래핑) 경로는 상환 보증 범위·한도·비상차단 사전 정의·고지 시에만. CCTP 참고.
- **오라클** (§3.5.5): 발행사 업무 특성상 **선택사항**. 도입 시 "데이터 정의–송신–온체인 반영" 전 과정 통제.

### 3.6 지갑·커스터디·서명 구조 (§3.6) — ★ Fireblocks 정중앙 대응

**기관용 지갑** (§3.6.2) — 5 핵심:
1. **RBAC** — 단일 계정/단일 키 운영 금지. 발행/소각/정산/정책변경/비상통제를 역할로 세분. 지갑 유형: 유통채널 운용지갑 / 발행 운영지갑 / 준비자산 수탁·상환 지갑 / 일반 사용자 지갑 / 프로그램·서비스 지갑(가맹점·정산·수수료·브릿지·오케스트레이션).
2. **다자 승인 + 분산 키 관리** — 발행·소각·정책변경은 **MPC(Multi-Party Computation) 또는 멀티시그 공동서명**. 컨소시엄 내 특정 기관 임의 개입 차단.
3. **정책 엔진 + 컴플라이언스 강결합** — 모든 트랜잭션은 **서명 이전 단계**에서 AML·제재·이상거래·한도·운영모드 기준으로 사전 검증. 정책 위반 거래는 **기술적으로 생성·서명되지 않음** = 사전통제(Pre-emptive Control).
4. **Hot/Warm/Cold 분리** — Cold 는 물리·논리 분리 환경, 비상/사전정의 절차로만 사용.
5. **감사 추적성** — 온체인 트랜잭션 + 오프체인 승인·정책 로그 결합.

**기관용 지갑 구현** (§3.6.2):
- **MPC-TSS 하이브리드** — 신뢰 정점(Root of Trust). 단일 개인키 미생성, 키 조각(Secret Shares)을 발행사·수탁은행·제3 감사기관에 분산, **임계값 T-of-N** 서명. 외부해킹·내부자공모 차단.
- **HSM 기반 Cold/Hot 혼합 운용** (국내 규제·금융 키관리 관행 고려).
- **SoD 결재 시스템 연동** — 온체인 서명 프로세스를 ERP/전산원장 결재(기안-검토-승인)와 API 결합. "기술적 서명 권한" = "법적 의사결정 권한" 일치.
- **실시간 대사** — 오라클로 신탁계좌 현금잔액 ↔ 온체인 발행량 실시간 대사. (출처: 안랩블록체인컴퍼니 소개자료 그림 3.15~3.17)

**개인용 지갑** (§3.6.3): 자기주권형 탈중앙 지갑이 아니라 "지급결제 인프라 말단의 **보호된 접근 계층**". 규제준수-UX 균형(위험기반 차등), 주소 수준 통제(커스터디 지갑은 동결 가능), 분실·오류 보호(즉시 회수 아닌 거래보류·추가인증·분쟁처리), 기관용 지갑과 책임 경계 분리(발행·소각·정책 권한 없음).

### 3.7 컴플라이언스·보안 인프라 (§3.7)

- **KYT**(Know Your Transaction, §3.7.2): 온체인 자금흐름 추적 — 해킹자금·다크웹·믹서 이력 식별. 위험 거래 시 경보+근거데이터 → 정책엔진·지갑·관리자콘솔 연동 "조치 요청".
- **KYB**(§3.7.3): 파트너(유통사/결제사/가맹점) 법인등기·UBO·제재 검증 + 화이트리스트 접근제어.
- **AML**(§3.7.4): KYT/KYB + 기존 금융데이터 결합, STR/CTR 선별, FATF·트래블룰 준수.
- **FRAML**(§3.7.5, 차세대 통합): FDS(이상거래) + AML 을 사일로 분리 운영하던 한계 극복 — 데이터 융합 + 동적 프로파일링(평소 패턴 + 제재리스트 → 리스크 스코어) + 즉각 대응. ★ 자동 차단·동결은 사유코드·승인요건·오탐대응 스펙 하 제한적 허용(경보 후 수동확인 기본값).

### 3.8 데이터 분석·대시보드 (§3.8)

글로벌 사례(§3.8.2): Circle(일일 발행량·준비자산·월간 명세서·Circle Account 대시보드), Tether(분기 Transparency), TRM Labs/Chainalysis(발행 전 지갑 스크리닝·이동추적·고위험 식별·동결).
구현 7요소 (§3.8.3): ① 온체인 데이터 수집·저장(Mint/Burn/Transfer/수수료/정책액션 이벤트 **인덱싱**, ETL, 체인별 식별자) ② 온·오프체인 연계(요청 ID/주소-고객 ID 매핑) ③ 컴플라이언스·이상거래 모니터링(KYT; pause/freeze 는 스펙 충족 시·경보후 수동확인 기본) ④ 운영 대시보드(현황/리스크/세부조회; MFA; 조회 로깅) ⑤ 권한계층·접근제어(감독기관 포털; 외부는 읽기전용·API키·rate limit) ⑥ 행위 로그·감사 ⑦ 개인정보보호(해시/마스킹, 최소수집·목적제한, 온체인 주소 가명→승인 시만 실명매핑).

### 3.9 상호운용성 (§3.9)

연계(Link) 리스크 관리가 핵심 — "연동된 상태에서 동일 기준으로 기록·처리·통제되는가" (§3.9.1). 글로벌 사례(§3.9.2): Circle CCTP(중앙 burn/mint), Wormhole 래핑 해킹 교훈, SWIFT ISO 20022 다체인 실험, JPM Coin·Partior. 기능설계(§3.9.3): API/SDK(REST/RPC, rate limit), 다중체인 통합관리(확정성 시차 조정 — Ethereum 수분 vs Kaia 1초), UX 통일(단일 잔액·주소), 데이터 불일치 검증(체크섬/해시), 연계 지연·실패 처리(롤백/재시도), 연계대상 한정(화이트리스트), 시나리오별 대응.

### 3.10 스테이블코인 오케스트레이션 레이어 (§3.10) — 온체인 FX

다통화 스테이블코인 + 복수 램프를 통합 조율하는 중앙 엔진 (CLS 다자간 PvP 결제, Circle EURC, SG Ubin+/SGX 비유). 5 모듈 (§3.10.2): ① 유동성·컨틴전시(풀 관리, 비상재원, 지연큐 — 온체인 "최종대부자" 기능) ② 다통화 통합 발행·유통·청산 ③ 온체인 FX·유동성 허브(통화쌍 풀, PvP **Atomic Swap**, DEX/AMM 연계) ④ 슈퍼앱 + SDK/API ⑤ 거래 확정성 관리·위험통제(롤백, 운영모드 전환, KRI 모니터링).

### 4.2 참여자 8 + 운영 규정 (§4.2)

**8 참여자** (§4.2.1, 표 4.2): ①발행전담법인(발행·소각·상환 최종책임, 정합성 보증) ②준비자산 수탁기관(분리보관·증빙) ③상환창구(Paying Agent) ④유통채널(KYC/KYB·1차 CS·한도) ⑤준법/모니터링(AML·제재·동결/차단/해제) ⑥데이터/인프라(리포팅·지표·경보) ⑦외부감사/검증(독립 검증·보고) ⑧체인/인프라 운영(가용성·장애대응).
글로벌 역할분리 예시(§4.2.1, 표 4.3): **USDC**(Circle 발행, 준비자산 BlackRock 운용·BNY Mellon 커스터디, Circle Mint 상환, Big Four 감사), **USDP**(Paxos Trust, Segregated·Bankruptcy Remote, NYDFS 감독, KPMG).

**3 핵심 운영 원칙** (§4.2.2): **권한 집중 방지 / 집행 가능한 통제 / 감사 가능한 증빙**.

**4 운영 모드** (§4.2.2, §4.2.3 표 4.4): **Normal / Restricted / Emergency / Halt(중단)**. 모드별 발행·상환·전송·동결·정책변경·커뮤니케이션·필수기록을 사전 매트릭스로 정의. 전환은 사유코드(트리거)+승인+로그.
- 민감 권한(§4.2.2 ②): M-of-N 멀티시그/MPC 공동서명, 승인-집행-사후검증 분리.
- 정합성(§4.2.2 ③): 준비자산↔온체인 유통량 정기 대사, 불일치 시 발행제한·상환우선·운영자확인.
- 준법 조치(§4.2.2 ⑥): 사유유형별(법집행/법원/제재/내부) 승인체계·해제조건 분리, 증빙·로그.

**SLA·보고** (§4.2.4): 상환 처리 목표시간, RTO, 동결/해제 처리 목표시간. 상환 유동성 프레임워크(평시·스트레스 단계조치·cut-off·대기열·부분지급·KRI). 보고는 "정합성 보고" + "리스크 보고" 분리. 정기공시 최소요건 = 투명성·추적성·설명가능성.

### 4.3 운영 거버넌스 (§4.3)

의사결정 기구(§4.3.1): 운영·정책 / 리스크·준법 / 변경관리 / 비상대응. **RACI 매트릭스**(§4.3.1 표 4.5)로 채널관리·운영모드전환·민감권한·준법조치·기술변경·정합성·공시별 R(집행)/A(최종승인)/C(협의)/I(통보) 구분.
정책변경(§4.3.2): 정상 변경(사유·영향·롤백·커뮤니케이션, Changelog, 공시) vs 긴급 변경(사후승인+사후보고·증빙).
기록·감사·이해상충(§4.3.3): 모든 의사결정 Audit Trail, 이해상충 주체 제척(사전신고·회의록·표결제외), 내부통제+외부감사 정기.

### 4.4 리스크 모델 (§4.4)

5 리스크 분류(§4.4.1): 준비자산/유동성, 운영/보안, 준법/규제, 네트워크/스마트컨트랙트, 상호운용성(브릿지/멀티체인). 각 범주 KRI + 경계(T1)/비상(T2) 트리거 → 자동/표준 조치(§4.4.2 표 4.6). 대응 플레이북 정상/경계/비상/중단 (§4.4.3 표 4.7).

| 단계/규모 | PoC, 1억원 범위 | 상업화 접근, 발행 10억원+ (2025-12) |
| 준비자산 | 법정화폐 100%, 우리은행 분리계좌, 은행 API 실시간 검증·월 증명·반기 감사 | USDC 100%, 온체인 증명 실시간·월 Attestation·반기 감사 |
| 스마트컨트랙트 | ERC-20, Proxy, **발행중단(Issuance Freeze)** 사후조치, 거버넌스 접근권한 | ERC-20, Proxy, **컨트랙트 내 트래블룰**(VASP-to-VASP 미준수 거래 기본 거부), 이중통제 멀티시그 |
| 지갑·커스터디 | **모든 지갑 BDACS 관리·동결 가능**, KYC 화이트리스트, **VASP 라이선스 보유**, MPC + 에어갭 콜드월렛, ISMS·ISO 27001 | 지갑단위 통제 미존재, 기관 온보딩 + Allow/Deny, **VASP 미보유**, 콜드 80%+·핫 5%+/보험 |
| 상호운용성 | 아발란체·폴리곤·BNB·Arc, 컴플라이언스 브리지(체인 간 KYC 상태 유지), 유동성풀 미형성, CBDC·RWA 지향 | Base, **LayerZero OFT**, Aerodrome KRWQ-USDC 풀·Uniswap KRWQ-FRXUSD 풀 |

요지(§7.1.2): **KRW1 = 전통 금융권 제도 정합성·연계 우선** PoC / **KRWQ = 온체인 투명성·Web3 연계로 상업 사용성 우선 후 제도권 단계 통합**. 둘 다 거버넌스·유즈케이스 구체성은 개괄 수준 한계 (§7.1.3).

### 5.2 해외: JPYC(일본) vs PHPC(필리핀) (§7.2.4 표 7.4)

| 항목 | **JPYC** (일본, 자금이동업) | **PHPC** (필리핀, Coins.ph) |
|---|---|---|
| 준비자산 | 1:1, 법정화폐+단기국채(개정법상 JGB 최대 50%), 신탁 분리보관 | 1:1, 법정화폐+단기국채, EMI 규정상 고객자금 별도예치, **다중은행 분산예치** |
| 스마트컨트랙트 | ERC-20 Proxy, blacklist/pause/**rescue**, RBAC·멀티시그·**Master Minter**(일 100만엔 한도) | ERC-20, **deprecate+upgradedAddress**(레거시 패턴), blacklist/pause, OpenZeppelin RBAC·멀티시그·**타임락** |
| KYC/라이선스 | 마이넘버 실명, 자금이동업 2종, 비수탁형 | 플랫폼 KYC·온체인 AML·트래블룰·Elliptic 추적, VASP+EMI 이중인가, 내부 수탁(MPC+에어갭)/외부 비수탁 |
| 배포·확장 | 이더리움·아발란체·폴리곤, Uniswap, JPYC Pay/카드 | 로닌·폴리곤, Katana DEX, 송금·게임(Ronin) |

소결(§7.2.5): 일본 = **제도 선행형**(발행사 유형 중심 인허가 후 시장개방), 필리핀 = **샌드박스 실증형**(시범발행-졸업-확장). 양국 모두 **컨소시엄/멀티-이슈어 모델** 관찰 — 한국 은행권·핀테크 연합 발행 옵션과 맥 일치.

## 6. 3-way 비교 — SaaS(Fireblocks) / 설치형 WaaS / 직접구축(본 제안서)

> Architecture Reasoning Mode: 본 제안서는 **직접구축/컨소시엄** 모델의 1차 자료다. Fireblocks 와 개념 매핑 + uncertainty boundary.

### 6.1 개념 매핑 — 본 제안서 ↔ Fireblocks

| 본 제안서 (§) | Fireblocks 대응 | 비고 |
|---|---|---|
| MPC-TSS T-of-N 키 분산 (§3.6.2) | [[vendors/fireblocks/mpc]] MPC-CMP, key share 분포 | 본 제안서는 발행사·수탁은행·감사기관 3주체 분산; Fireblocks 는 3-cloud 분할 (★ 분산 *주체* 가 다름 — 기관 간 vs 인프라 간) |
| 서명 이전 정책 사전검증 (§3.6.2) | [[vendors/fireblocks/policy-engine]] / [[vendors/fireblocks/tap]] | 동일 사상 = Pre-emptive Control. Fireblocks First-Match 정책 ordering 과 대비 |
| SoD 결재-서명 연동, 다자승인 (§4.2.2) | [[entities/fireblocks/cosigner]] co-signer + Q+O 승인 | 본 제안서는 ERP 결재 결합; Fireblocks 는 워크스페이스 승인 quorum |
| `freeze`/`blacklist`/`pause` (§3.4.4) | Fireblocks workspace freeze / 자산 동결 | 본 제안서는 **토큰 컨트랙트 함수** 직접 구현; Fireblocks 는 정책+API |
| Hot/Warm/Cold 분리 (§3.6.2) | Fireblocks Hot/Cold (Air-gapped) | HSM 혼합은 [[vendors/fireblocks/security]] Thales Luna(Stage 38)와 대비 |
| 인덱싱·대시보드 (§3.8) | Fireblocks webhook/lifecycle events | [[docs/architecture/blockchain-indexer-architecture-reference]] 참조 — 직접구축은 ETL·아카이브노드 자체 운영 |

### 6.2 3-way trade-off

- **SaaS (Fireblocks)**: 토큰 통제·MPC·정책을 vendor 가 흡수, 빠른 구축. 단 발행사가 요구하는 **규제 책임주체·준비자산 정합성·상환약관·감독기관 포털**은 vendor 가 제공하지 않음 → 발행/관리 시스템·컴플라이언스·거버넌스는 별도 구축 필요. (본 제안서 §3.3, §4 영역)
- **설치형 WaaS**: 키관리·정책은 자체 통제, 인프라는 제품화. 컨소시엄 다기관 키 분산(§3.6.2)을 vendor 제품 위에 얹을 수 있는지가 관건.
- **직접구축(본 제안서)**: 토큰 컨트랙트·발행관리·컴플라이언스·거버넌스 전부 자체 설계 → 정책 통제력·제도 정합성 극대화, 단 구축·운영 부담 최대. 본 제안서가 권장하는 모델 = **공통 레일 + 전문 파트너 협업 단계적 고도화** (§8.2).

> **uncertainty boundary**: 본 제안서는 **권고 아키텍처**이며 특정 vendor 구현이 아니다. Fireblocks 매핑은 *개념 대응* 이지 두 시스템이 상호호환된다는 의미가 아니다. 한국 스테이블코인 제도(2단계 입법)는 미확정 (§2.1.6) — 발행주체·감독 프레임 확정 시 본 reference 의 참여자 구조(§4.2)가 바뀔 수 있음.
