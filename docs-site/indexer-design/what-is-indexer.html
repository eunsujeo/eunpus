1. 인덱서란 무엇인가

정의, 데이터 변환의 본질, 인덱서 vs 노드 vs RPC 의 차이

1.1 정의

블록체인 인덱서는 원장에 순차적으로 기록되는 블록·트랜잭션·이벤트·상태 변화를 애플리케이션이 읽기 쉬운 형태로 추출하고, 스키마화하여, 데이터베이스/검색 인덱스에 적재한 뒤, GraphQL·SQL·REST·gRPC 같은 질의 인터페이스로 제공하는 데이터 인프라 계층이다.

Polkadot 문서는 이를 "블록체인 데이터용 검색 엔진" 으로 비유한다. The Graph, SubQuery, Blockscout, NEAR, Solana 생태계의 공식 문서도 모두 같은 방향의 ETL + 질의 가속 레이어로 설명한다.

1.2 인덱서의 4 가지 본질적 기능

모든 인덱서는 다음 4 가지 기능을 갖는다.

(1) 블록 · 트랜잭션 색인 (Indexing)

블록 hash · 트랜잭션 hash · 주소 · 자산 · 상태 별로 빠르게 조회 가능하게 구조화. RPC 의 "tx hash → tx body" 외에 "주소 → 받은 tx 목록" 같은 reverse lookup 도 제공.

(2) 이벤트 · 로그 색인 (Event log indexing)

Smart contract 가 emit 하는 event 를 address · topics · logIndex 단위로 구조화. ERC-20 의 Transfer(from, to, value) 가 대표적.

(3) 상태 스냅샷 · 히스토리 (State snapshot)

특정 블록 높이의 잔고 / contract state 를 재현하거나 즉시 조회. 과거 시점 잔고 조회는 archive node 가 사실상 필요.

(4) 알림 · 스트리밍 (Notification)

새 블록 / 로그 / 입금 / 상태 변경을 push 방식으로 전달. Webhook, WebSocket, Server-Sent Events 등.

1.3 인덱서 · 노드 · RPC 의 차이

혼동되기 쉬운 3 가지 컴포넌트를 정확히 구분한다.

컴포넌트역할제공 형태
블록체인 노드 P2P 네트워크에 참여, 블록 검증, state 보관 설치형 software (geth, reth, bitcoin-core)
RPC endpoint 노드의 API surface — block/tx/state 조회, tx 제출 HTTP + WebSocket endpoint (포트 8545 등)
인덱서 RPC 또는 노드 내부에서 데이터 read → 변환 → 자체 DB 적재 → query API 제공 커스텀 service + DB + (선택) API

예시

  • "Ethereum mainnet 의 최신 블록 번호" → 노드 RPC (eth_blockNumber) 한 번이면 됨. 인덱서 불필요.
  • "address 0xABC 가 지난 30 일간 받은 USDC 입금 목록" → 노드 RPC 만으로는 30일치 블록 스캔 (수 분). 인덱서 필요.
  • "USDC 컨트랙트의 모든 Transfer event 를 받아 자체 분석 DB 에 적재" → 인덱서 필요.

1.4 인덱서가 출력하는 데이터의 3 가지 형태

(a) 정형 row (relational)

Postgres / MySQL 의 row. 가장 일반적. SQL 로 query.

blocks(number, hash, parent_hash, timestamp, status)
transactions(hash, block_number, from, to, value, gas_used)
events(tx_hash, log_index, contract, topic0, payload)

(b) 문서 (document)

JSON 형태로 ElasticSearch / OpenSearch / MongoDB 에 적재. 전문 검색 + 집계 강점.

{
  "tx_hash": "0xabc...",
  "block_number": 19345678,
  "transfers": [
    { "from": "0x...", "to": "0x1a2b...", "asset": "USDC", "amount": "100" }
  ],
  "tags": ["large", "exchange-flow"]
}

(c) 시계열 (time-series)

InfluxDB / TimescaleDB. 가격 추이, TPS, 수수료 통계 등.

1.5 인덱서가 NOT 하는 것

흔히 오해되는 영역. 인덱서는 다음을 하지 않는다.

  • 키 관리 · 서명 — 별도 wallet/HSM/MPC 영역.
  • 트랜잭션 broadcast — 노드 RPC 또는 별도 broadcaster 의 역할.
  • 합의 (consensus) — 노드의 역할. 인덱서는 chain truth 를 관찰만 함.
  • 가격 결정 — 외부 oracle / market data 영역.
  • 거래 매칭 · 정산 — 거래소 매칭 엔진의 영역.

인덱서는 읽기 전용 (read-only) 데이터 변환 레이어. write 는 블록체인이 한다.

Figure 1-1. 인덱서는 "노드 → DB → API" 의 read path 에 위치. write path (UI → Wallet → Broadcaster → Node) 는 별개.

핵심 — read path 와 write path 가 분리. 인덱서가 망가져도 write (송금) 는 가능. write 가 막혀도 read (조회) 는 가능. 이 분리가 시스템 가용성의 기초.

1.7 다음 페이지

지금까지가 "인덱서가 무엇인지" 의 정의. 다음 2. 요구사항 에서는 — 인덱서를 만들거나 도입할 때 어떤 요구사항을 명시해야 하는지 (성능 · 정합성 · 보안 · 운영 등 8 가지 axis) 를 본다.
