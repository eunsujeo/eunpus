Vendor adapter 설계

4 adapter 가 각각 Port 를 어떻게 구현하는가 — 데이터 source / 통신 model / capability / 한계.

기초안내

4 adapter 의 핵심 통신 model:

  • FireblocksAdapter — REST API + JWKS-signed webhook v2 + externalTxId idempotency
  • BitGoAdapter — REST API + webhook + BitGo-specific transaction object
  • NodeInfraAdapter — vendor 측 on-prem API + 자체 webhook 또는 polling
  • OwnAdapter — full node 직접 + 내부 Kafka + Postgres + Temporal
다음 단계 — FireblocksAdapter 의 핵심 매핑

가장 먼저 구현하는 adapter. Fireblocks 공식 docs 가 가장 풍부.

FireblocksAdapter.subscribeDeposits

class FireblocksAdapter implements WalletIndexerPort {
  async subscribeDeposits(handler: (e: DepositEvent) => Promise<void>) {
    // 1. Fireblocks v2 webhook receiver 등록
    app.post('/fb/webhook', async (req, res) => {
      // 2. JWKS 서명 검증
      if (!verifyJWKS(req.body, req.headers['fireblocks-signature'])) {
        return res.status(401).end();
      }

      // 3. IP allowlist 검증
      if (!isFireblocksIP(req.ip)) {
        return res.status(403).end();
      }

      // 4. 빠른 2xx 응답 (Fireblocks 권고)
      res.status(200).end();

      // 5. 큐 적재 후 비동기 처리
      await internalQueue.enqueue(req.body);
    });

    // 6. 큐 consumer 가 DepositEvent 로 변환
    internalQueue.consume(async (raw) => {
      if (raw.type !== 'TRANSACTION_CREATED' &&
          raw.type !== 'TRANSACTION_STATUS_UPDATED') return;
      if (raw.data.source.type !== 'EXTERNAL') return;  // 입금만

      const event: DepositEvent = {
        idempotencyKey: `fb:tx:${raw.data.id}`,
        walletId: raw.data.destination.id,
        asset: this.mapAsset(raw.data.assetId),
        amount: BigInt(raw.data.amount),
        txHash: raw.data.txHash,
        blockNumber: raw.data.blockInfo?.blockHeight ?? 0,
        blockHash: raw.data.blockInfo?.blockHash ?? '',
        observedAt: new Date(raw.timestamp),
        confirmedAt: this.deriveConfirmedAt(raw.data),
        confirmationCount: raw.data.numOfConfirmations,
        source: 'webhook',
      };

      await handler(event);
    });
  }

  private deriveConfirmedAt(data: any): Date | null {
    // Fireblocks DCCP 정책의 최종 COMPLETED 상태
    if (data.status === 'COMPLETED') return new Date(data.lastUpdated);
    return null;
  }
}

핵심 매핑:

  • Fireblocks data.id → Port idempotencyKey (prefix fb:tx:)
  • Fireblocks numOfConfirmations + status → Port confirmedAt
  • Fireblocks blockInfo → Port blockNumber + blockHash
  • Webhook 순서 비보장 → 큐 적재 후 처리 (Fireblocks 공식 권고)
심화 · 4 adapter 비교 + 한계

FireblocksAdapter — capability

capabilities(): AdapterCapabilities {
  return {
    vendor: 'fireblocks',
    supportsWebhook: true,
    supportsBatchWithdrawal: true,         // destinations 배열
    supportsCustomConfirmationPolicy: true,  // DCCP (Support 경유)
    supportsBalanceAsOf: false,            // ★ 미지원 (vendor 비공개)
    supportsAddressScreening: true,         // AML 연동
    supportedChains: ['ethereum', 'bitcoin', /* 100+ */],
    internalTxDetection: 'trace_api',       // 추정 (Stage 36 transaction-objects.md)
    webhookOrdering: 'not_guaranteed',
    reorgHandling: 'automatic',             // vendor 가 흡수
  };
}

한계:

  • getBalanceAsOf(blockNumber) 미지원 — 회계 마감 시점 잔고는 자체 mirror 에서 재계산해야 함
  • Indexer 내부 visibility 없음 — head lag / sync 상태 등 limited
  • Custom confirmation policy 변경 = Fireblocks Support 경유 (self-service ✗)

Adapter 의 공통 책임

모든 adapter 는 다음을 직접 구현:

  1. Idempotency key prefix 통일 — fb: / bg: / ni: / own:
  2. Asset 매핑 — vendor 의 asset ID ↔ Port 의 {chain, symbol, contract}
  3. Webhook 순서 보정 — vendor 가 보장 안 하면 adapter 가 큐 + sequence 처리
  4. Reorg-as-event 변환 — vendor 가 revert event 안 보내면 adapter 가 periodic reconciliation 으로 감지
  5. Health check — vendor 측 endpoint + 자체 ingestion lag 측정
