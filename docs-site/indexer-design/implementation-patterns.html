3. 4 구현 패턴

pull / streaming / scan / data lake — 모든 인덱서는 이 4 패턴의 조합이다

3.1 4 패턴 한눈에 보기

패턴메커니즘대표 사례특성
(P1) Pull (full node 기반) 노드의 JSON-RPC / WebSocket / tracing API / 내부 framework 에서 직접 read Geth, Reth, nearcore, NEAR Indexer 정합성 ↑ 분산성 ↑ / 노드 운영 부담 ↑
(P2) Streaming (event push) validator/노드가 외부로 push (WebSocket / Geyser / Kafka) Solana Geyser, Ethereum eth_subscribe, Yellowstone gRPC 지연 ↓ / 재전송·중복·reorg 처리 필요
(P3) Scan (filter + dictionary) 체인 전체를 훑되 filter / topic / dictionary 로 선택적으로 처리 EVM logs scan, SubQuery dictionary, Blockscout catchup 유연 / filter 설계 의존
(P4) Data Lake (file/object storage) 원시 체인 데이터를 파일 / S3 / gRPC stream 으로 외부화 NEAR Lake (deprecated), Firehose, Coinbase ChainStorage 대량 재처리 / 병렬화 쉬움 / 외부 의존

3.2 (P1) Pull 패턴 상세

가장 단순한 패턴. 인덱서가 노드에 주기적으로 RPC 호출.

// Pull 패턴의 기본 loop (의사 코드)
loop:
  current = node.eth_blockNumber()
  for blockNum in (lastProcessed+1 .. current):
    block = node.eth_getBlock(blockNum, fullTx=true)
    logs  = node.eth_getLogs({fromBlock: blockNum, toBlock: blockNum})
    process(block, logs)
    lastProcessed = blockNum
    save_cursor(blockNum)
  sleep(2s)  // 블록 주기 따라

장단점

장점단점
가장 간단. 구현 / 디버깅 쉬움polling 간격만큼 지연
RPC 표준만 사용 — 어떤 클라이언트 / vendor RPC 든 OKRPC 호출 수가 처리량을 결정 (RPC throttling 시 lag)
cursor 기반 재시작이 자연스러움tx receipt 추가 조회 시 N+1 호출 문제

적합 워크로드

  • 소규모 / MVP — 빠른 출시
  • RPC 만 사용 가능한 환경 (자체 노드 없음)
  • 지연 SLO 가 느슨 (수 초 ~ 수십 초 OK)

3.3 (P2) Streaming 패턴 상세

노드가 새 블록 / 이벤트를 발생 즉시 외부로 push. 인덱서는 consumer.

주요 메커니즘

  • Ethereum WebSocket — eth_subscribe('newHeads') / eth_subscribe('logs', filter)
  • Solana Geyser plugin — validator 내부의 plugin interface. accounts / slots / blocks / transactions 를 Postgres / Kafka / gRPC 로 push
  • Yellowstone gRPC — Geyser 위에 표준화된 gRPC stream
  • Firehose — sub-second live streaming + fork-aware + cursor resume
// Streaming 패턴의 consumer (의사 코드)
node.subscribe('newHeads', (block) => {
  processNewBlock(block);
  // logs 도 subscribe 한 경우 별도 handler
});

node.subscribe('logs', { address: USDC_CONTRACT, topics: [TRANSFER] }, (log) => {
  processLog(log);
});

장단점

장점단점
최소 지연 (sub-second 가능)연결 유지 / 재연결 / 중복 처리 부담
RPC quota 절약 (push 라 호출 수 적음)WebSocket 의 reliability 가 낮음 — 끊김 잦음
이벤트 필터링이 노드 측에서 가능reorg 시 같은 이벤트 다시 전송 (removed=true) → idempotency 필수

중요 — 재연결 + 중복 처리

WebSocket 이 끊긴 사이 발생한 이벤트는 놓침. 보통 P2 + P1 hybrid 로 운영 — 끊김 감지 시 P1 (pull) 로 backfill 후 재구독.

3.4 (P3) Scan 패턴 상세

체인 전체를 훑되 filter / dictionary 로 처리할 블록만 선택.

핵심 — Dictionary

SubQuery 가 대중화한 개념. "필요한 이벤트가 있는 블록 높이 목록" 을 GraphQL 로 미리 받아와서 나머지 블록은 skip.

// 일반 scan — 모든 블록 처리
for block in (0 .. head):
  process(block)  // 대부분 빈 블록도 처리

// Dictionary 기반 scan
relevant_blocks = dictionary.query({
  events: ['Transfer'],
  contracts: [USDC, USDT, ...]
})
// e.g., relevant_blocks = [100, 234, 1056, 1057, ...]

for block in relevant_blocks:
  process(block)  // 99% 의 빈 블록 skip

장단점

장점단점
처리 블록 수 대폭 감소 (10-100배)filter 설계가 잘못되면 누락
backfill 속도 빠름새 이벤트 type 추가 시 backfill 다시
RPC quota 절약dictionary 서비스 의존

3.5 (P4) Data Lake 패턴 상세

raw 블록 데이터를 파일 / object storage / 표준 stream 으로 외부화. 인덱서는 그 파일에서 read.

주요 메커니즘

  • Firehose (StreamingFast) — 블록을 protobuf 파일로 저장 + sub-second live stream
  • NEAR Lake (deprecated 2026-03-24) — JSON 파일을 S3 로 dump
  • Coinbase ChainStorage — S3 + DynamoDB 에 raw block 적재, ELT 방식
  • Substreams — Firehose 위의 병렬 처리 framework

장단점

장점단점
병렬 처리가 자연스러움 (file = partition)외부 storage 의존 (S3 outage 영향)
backfill / 재처리 비용 ↓ (cold storage)실시간성은 P2 보다 약함
여러 consumer 가 같은 raw data 공유도입 복잡도 ↑

3.6 실무 — 패턴 조합

현실의 모든 production 인덱서는 2-3 패턴의 조합이다.

사례조합이유
The Graph P1 (Graph Node pull) + P4 (Firehose) + P3 (Substreams filter) 안정성 (P1) + 백필 속도 (P4) + 선택적 처리 (P3)
Coinbase ChainStorage P1 (load-balanced 노드 cluster) + P4 (S3 + DynamoDB lake) 대규모 + 정합성
SubQuery P1 (RPC) + P3 (dictionary) multi-chain + 효율
Solana 인덱서 P2 (Geyser) + P1 (RPC backup) 초저지연 + 재연결 대비
Blockscout P2 (eth_subscribe realtime) + P1 (catchup indexer) 실시간 + 누락 보정

3.7 패턴 선택 — 한 줄 기준

패턴 선택 가이드
  • Pull (P1) — 기본. 어떤 워크로드든 P1 으로 시작 가능. 작게 만들고 키워라.
  • Streaming (P2) — 지연 SLO 가 5 초 미만이면 추가.
  • Scan (P3) — 특정 컨트랙트 / 토큰만 추적할 때. Backfill 비용 절감용.
  • Data Lake (P4) — 대규모 분석 / 멀티 consumer / 장기 보존 시.
