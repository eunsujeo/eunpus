6. Reorg · Finality

인덱서가 가장 어려워하는 부분 — 시나리오와 애니메이션으로 이해

6.1 한 줄 요약

Reorg (chain reorganization) = "이미 확정된 줄 알았던 블록이 chain head 교체로 사라지는 사고". Finality = "이 시점 이후로는 reorg 가 불가능한 안전 지점".

강조해야 할 점 — 일반 시스템에서는 commit 된 데이터가 사라지는 것은 비상 사태지만, 블록체인의 reorg 는 정상 운영의 일부다. Ethereum mainnet 에서 1-block reorg 는 자주 발생한다. 인덱서는 reorg 를 예외가 아닌 정규 동작으로 다뤄야 한다.

6.2 왜 일어나는가

블록체인은 분산 합의 시스템. 여러 노드가 동시에 새 블록을 만들 수 있다.

  • (a) proposer A 가 블록 N+3 을 만들어 broadcast
  • (b) 동시에 proposer B 가 다른 블록 N+3' 을 만들어 broadcast
  • (c) 네트워크의 일부는 A 의 N+3 을, 다른 일부는 B 의 N+3' 을 먼저 받음
  • (d) 잠시 두 chain 이 공존. 더 긴 (또는 더 무거운) chain 이 canonical 로 결정

탈락한 쪽의 블록 = orphan block (고아 블록) — canonical chain 에서 떨어져 나간 블록. orphan 안에 들어있던 트랜잭션은 mempool 로 돌아가거나 영영 사라질 수 있다.

6.4 시나리오 정리 — 무엇이 일어났나

위 6 단계가 보여주는 것:

  1. Step 0 — 안정 상태. 인덱서는 일상 운영.
  2. Step 1 — 입금 tx 가 블록 N+3 (19,345,678) 에 proposed. 인덱서 입장에서 "입금 발견, 1 conf".
  3. Step 2 — 다른 proposer 가 동시에 N+3' 을 만들어 broadcast. 네트워크에 두 chain head 존재. 일부 노드는 A 를, 다른 노드는 B 를 본다.
  4. Step 3 — Fork chain 이 더 빠르게 자라남 (N+4'). 이제 fork 가 더 길다 (length 2 vs 1). longest-chain rule 에 의해 fork 가 canonical 후보가 됨.
  5. Step 4 — Reorg 발생! 원래 chain 의 N+3, N+4 → orphan. fork 의 N+3', N+4' → canonical. 입금 tx 는 orphan block 에 있었음 → mempool 로 돌아감.
  6. Step 5 — 입금 tx 가 새 canonical chain 의 N+5 에 다시 proposed. 인덱서가 다시 "입금 발견".

6.5 인덱서가 reorg 를 처리하는 5 가지 접근

(1) Confirmation 정책 — 충분히 기다리기

가장 단순. "block N 의 이벤트는 chain head 가 N+K 에 도달 하기 전까지는 read API 에 노출 안 함" (즉 K 번의 confirmation 이 쌓이기 전까지). K 는 체인 별 다름.

체인일반 confirmation 권장이유
Bitcoin3 (일반) ~ 6 (고액)10분 × 6 = 60분 대기
Ethereum PoS32 ~ 64 (epoch 1-2)finality 까지 약 13-26분
Polygon PoS~ 256checkpoint 까지 약 30분
Solana1 (confirmed) ~ 32 (finalized)commitment level 정책

장점 — 구현 가장 간단.

단점 — 사용자가 느린 confirmation 까지 기다림.

(2) Add/Remove event sequence (Coinbase ChainStorage 방식)

블록을 overwrite 하지 않고, 추가 (+) / 제거 (-) 이벤트의 sequence 로 적재. 인덱서 DB 는 이 sequence 를 따라가며 자체 row 를 INSERT / DELETE.

핵심 규칙:

  • + block N → 인덱서 DB 에 그 블록의 tx 들을 INSERT
  • - block N → 인덱서 DB 에서 그 블록의 tx 들을 DELETE

아래 시나리오 — §6.3 의 reorg 시나리오와 동일. 0xa 계열 chain 이 canonical 이었다가 0xb 계열 chain 이 더 길어지면서 canonical 이 교체되는 상황. 블록 번호는 같지만 hash 가 다르면 다른 블록.

T1 — 0xa 계열 canonical
Raw event log (append-only)
+ block 19345678 (0xa4) [deposit tx]
+ block 19345679 (0xa5)
+ block 19345680 (0xa6)
인덱서 DB (token_transfers)
INSERT (block=19345678, hash=0xa4, deposit tx)
T2 — 0xa 계열 orphan 됨
Raw event log (− 이벤트 append)
− block 19345680 (0xa6)
− block 19345679 (0xa5)
− block 19345678 (0xa4)
인덱서 DB (반영)
DELETE WHERE block=19345678 AND hash=0xa4
(다른 두 블록엔 tx 없어 no-op)
T3 — 0xb 계열 canonical
Raw event log (새 chain append)
+ block 19345678 (0xb4)
+ block 19345679 (0xb5)
+ block 19345680 (0xb6)
+ block 19345681 (0xb7) [deposit re-mined]
인덱서 DB (반영)
INSERT (block=19345681, hash=0xb7, deposit tx)

주의 — block_number 만 봐서는 안 됨. T1 의 (19345678, 0xa4) 와 T3 의 (19345678, 0xb4) 는 같은 block_number 지만 다른 hash 즉 다른 블록. T2 의 - (19345678, 0xa4) 는 같은 0xa4 가 canonical 에서 빠졌다는 통보 (블록 자체가 사라진 게 아니라 canonical chain 에서 제외됨).

핵심 — raw log 는 수정 ✗, 오로지 append. 인덱서 DB 는 + / − 이벤트를 받아 단순한 INSERT / DELETE 만 적용. 결과적으로 인덱서 DB 의 최종 상태는 새 canonical chain 과 자동으로 일치.

장점 — raw log 는 완전한 audit trail (모든 + / − 가 timestamp 와 함께 보존). 새로운 인덱서 / 분석 consumer 가 같은 log 를 처음부터 replay 하면 동일 상태 재구성 가능.

단점 — consumer (인덱서 DB write 로직) 가 INSERT / DELETE 양쪽을 idempotent 하게 처리해야 함 (같은 + 이벤트 두 번 받아도 row 중복 ✗).

(3) Soft-delete + 재계산 (Reverted flag)

row 를 삭제하지 않고 reverted=true 로 표시. 새 블록 hash 의 row 추가. read API 는 WHERE reverted = false 필터.

Before — token_transfers
block_num=19345678, hash=0xa4, reverted=false
readWHERE reverted=false → 1 row 노출
Reorg 시점
block_num=19345678, hash=0xa4, reverted=TRUE
UPDATE 기존 row 의 reverted=true marking
After — 새 block 적재
block_num=19345678, hash=0xa4, reverted=TRUE
block_num=19345678, hash=0xb4, reverted=false
readWHERE reverted=false → 새 row 만 노출

Row 는 두 가지 hash 가 공존하지만 read query 가 reverted=false 만 보므로 사용자에게는 항상 canonical 데이터만 노출. orphan row 도 보존되어 audit / 분석 가능.

장점 — query 가 단순 (filter 하나만).

단점 — 모든 projection 에 reverted flag 필요 + 모든 read 에 WHERE 조건 강제.

(4) Snapshot-and-rollback

finalized 가 아닌 모든 데이터를 별도 schema 에 staging. finality 도달 시 main schema 로 commit. reorg 시 staging 만 rollback.

T1 — Pending
staging
block N (0xa4)
block N+1 (0xa5)
main
(비어있음 — finality 대기)
T2 — Reorg!
staging — orphan 만 삭제
DELETE block_hash=0xa4
DELETE block_hash=0xa5
main — 영향 없음
(여전히 비어있음)
T3 — Finality 도달
staging → main commit
block N (0xb4) → main
block N+1 (0xb5) → main
main — finalized 데이터
block N (0xb4)
block N+1 (0xb5)

핵심 — main schema 에는 finalized 데이터만 들어감. read API 가 main 만 보면 reorg 영향을 절대 안 받음 (대신 finality 시간 만큼 데이터 노출 지연).

장점 — main 은 항상 finalized, 정합성 보장 가장 강함.

단점 — staging vs main 두 schema 의 schema 일관성 부담 + finality 시간만큼 read API 지연.

(5) Replay-from-cursor

raw log 를 cursor 와 함께 보관. reorg 시 affected block 부터 projection 만 다시 돌림.

T1 — Reorg 전
N-1 N N+1 (0xa5) N+2 (0xa6)
↑ projection cursor
T2 — Reorg 감지! orphan block 발견 (N+1, N+2 가 새 chain 에서 다른 hash)
N-1 N N+1 (0xa5) N+2 (0xa6) N+1 (0xb5) N+2 (0xb6)
↑ cursor rewind to N (orphan 직전)
T3 — 새 canonical 로 replay
N-1 N N+1 (0xa5) N+2 (0xa6) N+1 (0xb5) N+2 (0xb6)
↑ cursor 가 새 canonical 의 tip 까지 진행

Raw log 는 모든 block (orphan 포함) 을 보관. Projection 의 cursor 를 reorg point 직전으로 rewind 한 뒤 새 canonical chain 만 따라가며 다시 적용. projection 의 read model 은 자동으로 최신 canonical state 로 수렴.

장점 — projection 이 여러 개라도 동일 패턴 적용. 새 projection 추가 시도 같은 메커니즘.

단점 — replay 시간이 reorg depth 에 비례 (10-block reorg 면 10 block 분 replay).

5 방식 trade-off 비교

방식핵심 메커니즘장점단점대표 사용 사례
(1) Confirmation 정책 K conf 쌓일 때까지 read API 에 노출 안 함 구현 가장 단순. projection schema 변경 없음 사용자가 K 만큼 기다림 (Bitcoin = ~60 분) 거의 모든 거래소 / 지갑. Bitcoin K=3~6 표준, Upbit / Bithumb / Coinone / Korbit 의 minimum_deposit_confirmations, Fireblocks DCCP
(2) Add/Remove sequence raw log 에 + / − 이벤트 append 완전한 audit trail. consumer 가 자기 속도로 consumer 가 add/remove 둘 다 idempotent 처리 Coinbase ChainStorage — 공식 blog Part 1 에 "block overwrite ✗, add/remove event sequence" 명시
(3) Soft-delete + Reverted flag row 보존 + reverted=true marking read query 단순 (filter 하나) 모든 projection 에 flag 필요. 모든 read 에 WHERE 강제 The Graph / Graph Node entity versioning, SubQuery 자동 rollback, Blockscout 의 internal tx
(4) Snapshot-and-rollback staging + main 두 schema. finality 시 main commit main 은 항상 finalized — 정합성 가장 강함 두 schema 의 일관성 부담 + read 지연 Firehose / StreamingFast — finalized vs unfinalized 분리, Ethereum finalized tag 활용, 금융 / 컴플라이언스 영역
(5) Replay-from-cursor cursor rewind + 새 chain replay projection 늘어나도 같은 패턴 적용 replay 시간 = reorg depth 에 비례 Kafka 기반 인덱서 (offset 으로 cursor), Firehose cursor-based resumption, SubQuery worker checkpoint, Korbit Kafka event sourcing + Temporal

6.6 체인 별 finality 모델

finality 의 정의가 체인마다 다르다. 인덱서는 이 차이를 알아야 한다.

체인 / 합의Finality 모델인덱서 의미
Bitcoin (PoW) Probabilistic — N block 이 쌓일수록 reorg 확률 ↓ K=6 정도면 실용적 finality
Ethereum (PoS, Gasper) Deterministic — finalized 블록 표시 명시 finalized tag query 가능. ~ 2 epoch.
Solana 3 commitment level — processed / confirmed / finalized API 가 commitment 별 명시. finalized = supermajority + lockout.
Cosmos / Tendermint Instant finality — 한 블록 commit 되면 final K=1 충분. reorg 거의 없음.
Polkadot BABE (block production) + GRANDPA (finality) 분리 2 level. confirmed (BABE) / finalized (GRANDPA).
Optimistic Rollup (Optimism, Arbitrum) L1 commit + challenge window (7 days) L2 finality 와 L1 finality 분리. trustless finality 는 7 일.
ZK Rollup (zkSync, StarkNet) proof 가 L1 에 commit 되면 final ~ 수 시간 ~ 일 단위

6.7 인덱서가 API 로 노출해야 할 것

read API 응답에 confirmation level 을 명시. 사용자가 own risk tolerance 에 따라 선택.

GET /api/transfers?account=0x1a2b...&min_confirmations=6

6.8 흔한 실수

  1. 1 conf 만으로 confirmed 처리 — reorg 발생 시 cleanup 비용 큼. 최소 6+ confirmation.
  2. reorg 시 row UPDATE — audit log 손실. 항상 새 row + reverted flag.
  3. projection 의 cursor 와 raw log 의 cursor 혼동 — 별도 관리.
  4. finality 정의를 API 에 안 노출 — consumer 가 "이 데이터 안전한가" 판단 불가.
  5. orphan 블록 의 tx 영구 삭제 — 같은 tx 가 mempool 거쳐 새 block 에 다시 들어올 수 있음.
