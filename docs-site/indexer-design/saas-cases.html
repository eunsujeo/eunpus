Subgraph manifest 예시

# subgraph.yaml
specVersion: 0.0.7
dataSources:
  - kind: ethereum
    name: USDC
    network: mainnet
    source:
      address: "0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48"
      abi: USDC
      startBlock: 6082465
    mapping:
      kind: ethereum/events
      apiVersion: 0.0.7
      language: wasm/assemblyscript
      entities: [Transfer, Holder]
      eventHandlers:
        - event: Transfer(indexed address, indexed address, uint256)
          handler: handleTransfer
      file: ./src/mapping.ts

개발자가 작성하는 것:

  • subgraph.yaml — manifest (체인, contract 주소, startBlock, event handler)
  • schema.graphql — entity 정의 (Postgres table 로 변환)
  • mappings.ts — event → entity 변환 (AssemblyScript)

Substreams — 병렬 처리 layer

출처 — The Graph blog.

  • Firehose 기반 raw block stream 위에 병렬 변환
  • 일부 subgraph 100x+ sync 가속
  • fork-aware streaming + cursor-based resumption

Economic model — GRT 토큰

  • 인덱서는 GRT 를 staking
  • 잘못된 데이터 / 잘못된 인덱싱 시 slashing
  • Query fee + indexing reward 를 GRT 로 받음
  • ★ The Graph hosted service 는 deprecated — decentralized network 만 운영
  • ★ Alchemy Subgraphs hosted 는 2025-12-08 sunset

10.6 Firehose / StreamingFast — raw block stream 인프라

인덱서의 source layer (= 인덱서 자체가 아니라 인덱서 위에 올라가는 인프라).

핵심 특성

출처 — Firehose docs.

특성설명
제공 형태블록체인 데이터를 파일 기반 + streaming-first 로 추출 / 저장
Live streamingSub-second latency
Historical access과거 block 도 파일로 즉시
Reorg 처리Fork-aware streaming — reorg 시 revert event emit
ResumptionCursor-based — consumer crash 후 정확한 시점 resume
파일 포맷protobuf 기반 binary

Substreams — Firehose 위의 병렬 처리

  • Substreams = Firehose 위의 병렬 ETL framework
  • The Graph 와 통합 — subgraph 가 Substreams 위에 build 가능
  • 일부 subgraph 100x+ sync 가속 (Firehose 의 file 기반 source 덕분)

★ Firehose 는 인덱서 자체가 아니라 인덱서의 source layer. The Graph / Substreams / 자체 인덱서 가 Firehose 위에 build.

10.11 상황 별 선택 가이드

상황 별 권장
  • MVP / 빠른 검증 — Alchemy 또는 QuickNode Build tier. 1 일 안에 동작 가능.
  • dApp / DEX — The Graph subgraph. 표준 GraphQL.
  • 탐색기 (Etherscan 류) — Blockscout 자체 호스팅.
  • 커스터디 / 수탁 — Fireblocks / BitGo (vendor lock-in 수용 시) 또는 자체 구축 (sovereignty 우선 시).
  • 고성능 ETL / 분석 — Firehose + Substreams + 자체 분석 stack.
  • 강한 망분리 환경 — 설치형 (on-prem) 또는 자체 구축.
  • 대형 거래소 — 자체 구축 (Coinbase ChainStorage 패턴 차용).

10.12 SaaS 사용 시 주의사항

  1. SLA 명문화 — vendor 의 freshness / latency / availability SLA 확인. 환불 조항.
  2. 장애 대응 경로 — vendor outage 시 fallback (다른 vendor / 자체 RPC).
  3. 데이터 export — 종속에서 벗어날 때 마이그레이션 path. raw data export 가능 여부.
  4. Idempotency 의무 — at-least-once delivery 의 vendor 가 많음. consumer 가 처리.
  5. Quota 관리 — monthly quota 초과 시 throttling 또는 부과금. 모니터링 필수.
  6. Vendor schema 변경 — vendor 의 API breaking change. 보통 deprecation notice 가 있지만 짧을 수 있음.
