사용 vs 미사용 비교

RPC 직접 호출 만으로 수탁형 지갑을 만들면 어떤 문제가 생기는가. 인덱서가 그 5 가지 문제를 어떻게 풀어내는가.

기초안내

한 줄로: "인덱서 없음 = Alice 의 잔고 화면이 30 초 걸리거나 틀린 숫자를 본다".

다음 5 가지 영역이 모두 무너진다: 응답 속도 · 이력 조회 · 실시간 알림 · 체인 재조직 처리 · 비용.

다음 단계 — Alice 시나리오로 비교

같은 상황, 두 가지 구현. Alice 가 입금 후 앱을 켰을 때 무엇이 다른가.

Case A — 인덱서 없이 RPC 직접

14:00:18 Alice 앱 열기 → 백엔드가 Ethereum RPC 에 요청.

14:00:19 eth_getBalance 응답 — Wei 단위 raw 숫자만.

14:00:20 입금 내역 조회 시작. eth_getLogs 로 Transfer 이벤트 검색.

14:00:35 Alchemy RPC 의 응답 크기 제한 (1만 logs) 에 걸려 30일 한 번에 못 가져옴. 일주일 단위로 4 번 chunked 호출.

14:01:10 다 모았지만 USDC contract 의 logs 만 봐서는 "Alice 의 입금" 인지 모름. 모든 Transfer 이벤트 의 to 주소를 검사해 Alice 의 주소와 매칭.

14:01:25 화면 그리기 완료. 총 67 초.

14:02:00 새로 들어온 입금? 백엔드가 polling 으로 60 초마다 다시 RPC 호출.

Case B — 인덱서 있음

14:00:18 Alice 앱 열기 → 백엔드가 인덱서 DB 에 요청.

14:00:19 Postgres 한 번 query 로 잔고 + 입금 내역 + pending 모두 조회. 응답 < 100ms.

14:00:19 화면 그리기 완료. 총 1 초.

14:01:00 새 입금 발생 시 인덱서가 webhook 으로 백엔드에 push. 백엔드는 Alice 의 앱에 push notification.

심화 · 5 가지 문제와 인덱서의 해결
문제RPC 만 쓸 때인덱서가 푸는 방식
1. 응답 속도 매 화면마다 수십 개 RPC 호출. 1 화면 30 초 ~ 분 단위. Postgres / Redis 등 미리 만든 read model. 100ms 이내.
2. 이력 조회 eth_getLogs 응답 크기 / 블록 범위 제한. 30 일 history 도 chunked + 시간 오래 걸림. 이미 indexed 된 모든 입출금을 ts/주소 인덱스로 즉시 조회.
3. 실시간 알림 Polling 으로 새 입금 감지. 60 초 간격이면 최대 60 초 지연 + 비용. Webhook / WebSocket push. 1-2 초 지연.
4. Reorg (체인 재조직) 같은 트랜잭션이 다시 들어오거나 사라짐. RPC 응답에서 removed=true 처리 직접 구현. 인덱서가 reorg 를 자동 처리 (예: add/remove event sequence). 백엔드는 final state 만 본다.
5. 비용 Hosted RPC (Alchemy / QuickNode) 호출 수 폭증 → 월 비용 급증. RPC 호출은 인덱서 sync 시에만. App 트래픽 ↔ RPC 호출 decoupling.

특히 KR 은행 도입 시 중요한 영역

Reorg 처리 (#4) 는 단순 성능 문제가 아니라 회계 정합성 문제 다. Alice 의 입금이 confirmed 됐다고 잔고를 +100 했는데 reorg 로 사라지면 — 잔고를 -100 해야 한다. 이걸 자동 처리하지 못하면 회계 마감 단계에서 매번 수작업 보정. 본 wiki 의 회계 · 원장 설계 와 직결.

실시간 알림 (#3) 도 KR 규제 관점에서 중요. 금융위 2026 의 "5분 주기 상시 대사" 요건은 polling 만으로는 충족이 어려움 — 인덱서의 push 기반 통보가 사실상 필수.
