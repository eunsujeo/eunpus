S5 · 학습 PATH

Vendor 풍경

Fireblocks / BitGo / NodeInfra / 자체구축 — 각자 평면 1, 2 의 어디까지 흡수해주는가.

기초안내

4 가지 path 의 indexer 책임 분담 (한 줄 요약):

  • Fireblocks (SaaS) — 평면 1 + 평면 2 일부 흡수. customer 는 webhook 만 받음.
  • BitGo (수탁형 인프라) — 평면 1 흡수, 평면 2 의 일부 (자체 BigInt 라이브러리 등). 공개 적음.
  • NodeInfra (설치형 WaaS) — 평면 1 의 노드 운영 흡수. 평면 2 는 customer 측.
  • 자체구축 (Direct-build) — 모든 평면 customer. 가장 큰 통제력 + 가장 큰 운영 부담.
다음 단계 — Alice 의 입금이 각 path 에서 어떻게 처리되나

Path 1: Fireblocks SaaS

Fireblocks 가 자체 운영하는 AWS Public VPC (Node Infrastructure) 의 노드 클러스터가 블록 N 을 read. Fireblocks 내부 indexer 가 Alice 의 deposit 을 감지. Customer (KR 은행) 의 webhook URL 로 push.

Webhook payload: { vaultAccountId, asset, amount, blockInfo, numOfConfirmations, ... }

은행은 자체 평면 3 (원장 워크플로) 에서 confirmation policy 충족 확인 → 잔고 +100.

Path 2: BitGo (커스터디 인프라)

BitGo 의 내부 indexer (자체 "Generic Indexer" 라이브러리, 단일 스레드 EVM 파이프라인) 가 블록 N 을 read. CREATE2 forwarder 기반 dynamic wallet 에 입금 도착.

BitGo API 로 customer 가 입금 이력 조회 또는 webhook 으로 push.

은행은 자체 평면 3 에서 잔고 반영.

Path 3: NodeInfra (설치형 WaaS / on-prem)

은행이 자체 IDC 에 NodeInfra 의 NodeWallet 인프라 설치. NodeWallet 내부의 블록체인 노드가 직접 블록 N read.

NodeWallet 의 indexer 기능이 평면 1, 2 의 일부 (해당 vendor 의 책임 범위) 흡수. Customer 가 vendor 측 API 또는 DB 에서 fact 조회.

은행은 자체 평면 3 + 회계 / KR 규제 처리.

Path 4: 자체구축 (Direct-build)

은행이 직접 Ethereum / BTC / Solana 등의 풀노드 (또는 archive node) 운영. 4 가지 구현 패턴 (pull / streaming / scan / lake) 중 선택.

자체 indexer 가 raw event → 도메인 schema 변환 → Postgres / Kafka 적재.

모든 평면 customer 책임. 가장 큰 sovereignty + 가장 큰 운영팀 필요.

각 path 의 trade-off

Fireblocks (SaaS)

  • 장점 — 100+ 체인 즉시 지원, webhook 표준 (JWKS / IP allowlist / externalTxId idempotency), 운영 인력 최소
  • 단점 — Vendor lock-in, customer 측 indexer 내부 visibility 없음, 비용 (large workspace 시 $$$)
  • KR 은행 적합도 — 가장 빠른 출시. 단 망분리 / 자체 audit 영역에서 별도 평면 2 mirror 필요

BitGo

  • 장점 — 다중서명 표준, 보험 (BitGo Trust), 은행 친화적 product 라인
  • 단점 — Internal 구현 공개 적음, KR 은행 specific 적합도 검증 필요
  • KR 은행 적합도 — Fireblocks 의 대안. 다만 본 wiki 의 reference 가 거의 없음 (Stage 41-44 의 hypothesis-tier 에만 일부)

NodeInfra (설치형 WaaS)

  • 장점 — 망분리 환경에 적합 (KR 은행 핵심 요구), 자체 IDC 에 설치, 데이터 sovereignty
  • 단점 — 운영 책임 customer (HW / OS / 네트워크 / DR), 라이센스 비용
  • KR 은행 적합도 — KR 은행 망분리 의무 충족. 본 wiki NodeWallet 은행 도입 참조

자체구축 (Direct-build)

  • 장점 — 완전 sovereignty, vendor 종속 ✗, 장기적 비용 우위 가능
  • 단점 — 모든 평면 customer 운영. 풀노드 / archive node / indexer / 도메인 매핑 / projection / API 모두 직접
  • KR 은행 적합도 — 대형 은행 / 거래소만 적합. 본 wiki vendor-neutral reference 가 이 path 의 reference

★ 그래서 추상화가 필요한 이유

위 4 path 의 평면 1, 2 가 모두 다르다. 은행이 어떤 path 를 선택하든 평면 3 (원장 · 워크플로) 은 동일 해야 한다 (회계 / 규제 / 정책 일관성).

그래서 평면 1, 2 와 평면 3 사이에 vendor-neutral abstraction layer 가 필요. Spec path (06 ~ 09) 에서 이 abstraction 의 설계와 구현을 다룬다.

핵심 시나리오 — KR 은행이 처음에는 Fireblocks 로 출시 → 1 년 후 NodeInfra 로 망분리 강화 → 2 년 후 자체구축으로 전환 → 비용 절감 → 다시 Fireblocks 의 BCM 으로 hybrid. 평면 3 의 코드 / 워크플로 / 회계 정책은 한 줄도 안 바뀌어야. 이게 추상화의 ROI.
