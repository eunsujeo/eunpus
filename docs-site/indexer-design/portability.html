12. 벤더 교체 · 포트 설계

자체 인덱서로 시작했다가 Fireblocks 나 다른 벤더로 갈릴 수 있다면 — 무엇을 숨기고 무엇을 내 것으로 남길까
본 페이지의 성격

아래 인터페이스·의사코드는 설명용 저자 설계다. 적용 전 자신의 환경에서 검증하라. 다만 두 종류의 사실은 공개 근거에 기반한다 — (1) Fireblocks 의 인덱서 기능 범위(webhook + 내 vault 잔액·트랜잭션 이력 조회 API + 입출금 confirmation 정책 — 단 커스텀 가공·임의 조건 조회는 자체)는 본 가이드 10. vendor 와 별도 위키의 검증된 사실,(2) 거래소의 AML 처리 방식(Chainalysis 등 외부 vendor 위탁)은 9. 자체 인덱서 운영 의 공개 자료(공식 docs·tech blog) 근거다.

12.1 문제 — 지금은 자체, 나중엔 벤더일 수 있다

수탁형 지갑 서비스를 만들 때 자주 나오는 상황 — 지금은 자체 인덱서로 시작하지만, 나중에 Fireblocks 같은 관리형 지갑 서비스로 갈아타거나, Alchemy·QuickNode 같은 데이터 인프라 벤더로 수집만 위탁할 수도 있다. 이때 "인덱서를 통째로 버리고 새로 붙인다" 고 생각하면 교체 비용이 폭발한다.

핵심 통찰은 이것이다 — 인덱서 전체를 교체 단위로 보지 마라. 인덱서 안은 이미 성격이 다른 두 부분으로 갈린다. 벤더마다 달라지는 앞단(수집) 과 어떤 벤더를 써도 내 것으로 남는 뒷단(원시 로그 → 가공 → 조회 API). 그래서 교체란 "앞단 어댑터 하나를 갈아끼우는 일" 이 되어야 한다.

12.2 교체선은 어디에 긋나 — 파서와 원시 로그 사이

4. 참조 아키텍처 의 8 계층을 "교체 관점" 으로 다시 보면, 벤더 의존성이 어디서 끊기는지가 분명해진다.

계층벤더 의존성교체 시 운명
(1) Source · (2) Collector벤더마다 다름
(RPC? webhook? gRPC? 파일?)		★ 포트 뒤로 격리할 부분
(3) Reorg/Finality · (4) Parser부분 의존벤더가 확정·디코딩을 보장하면 축소
(5) 원시 이벤트 로그무관영원히 내 것 (재처리의 근거)
(6) 가공 · (7) 저장 · (8) 조회 API무관영원히 내 것 (조회·이력·집계)

즉 교체선은 (4) 파서와 (5) 원시 로그 사이에 긋는다. "외부에서 어떻게 가져오든, 일단 내 원시 로그의 표준 스키마(5. 데이터 모델의 공통 entity)로 들어오면 그 다음은 벤더와 무관" 이 되도록 만든다. 원시 로그가 절대 삭제·수정되지 않는다는 원칙(4.3 절의 read/write 분리)이 이 교체 가능성의 토대다.

12.3 단일 포트 — ChainDataSource

수집부만 추상화한 좁은 인터페이스를 하나 둔다. 이 포트가 출력하는 타입을 이미 정의해 둔 내 표준 스키마로 고정하는 것이 핵심이다 — 어댑터가 무엇이든 출구는 같은 RawBlock·ParsedEvent(4.4 절) 하나다.

interface ChainDataSource {
  // 과거 채우기(backfill) — 벤더가 임의 블록 범위 조회를 주는가?
  fetchBlockRange(from, to): AsyncIterable<RawBlock>

  // 실시간 — pull 폴링? WebSocket? webhook 콜백?
  subscribe(filter): AsyncIterable<RawBlock | ChainEvent>

  // 재시작 지점 (cursor / offset / watermark)
  cursor(): Cursor
}

지갑 서비스 백엔드(게이트웨이·멱등·오케스트레이션·내부 장부)는 이 포트 하나에만 의존한다. 같은 발상을 지갑 서비스 전체 규모로 다룬 글이 지갑 서비스 컴포넌트 가이드의 벤더 추상화 다 — 거기서는 서명·전파까지 포함한 더 넓은 seam(WalletProvider)을 다루고, 본 페이지는 그중 인덱서 수집부를 한 단계 안쪽에서 본다.

12.4 어댑터 3종 — 같은 포트, 내부만 다름

// (A) 자체 구축 — 지금 만든 것. 노드 RPC/WebSocket 직접 (3장 P1+P2 하이브리드)
class SelfNodeSource implements ChainDataSource {
  fetchBlockRange(a, b) = node.getBlocks(a, b)          // pull 백필
  subscribe(f)          = node.subscribe('logs', f)     // WebSocket push
}

// (B) Fireblocks — 관리형. webhook 을 수집 소스로 흡수
class FireblocksSource implements ChainDataSource {
  subscribe(f)          = webhooks.on('TRANSACTION_STATUS', toRawEvent)
  // fetchBlockRange = 내 vault 트랜잭션 이력 API (전체 체인 아닌 내 워크스페이스 범위)
}

// (C) 타 데이터 벤더 — Alchemy / QuickNode / Firehose 등
class AlchemySource implements ChainDataSource {
  fetchBlockRange(a, b) = alchemy.getAssetTransfers(a, b)
  subscribe(f)          = alchemy.ws.on('mined', f)
}

12.5 벤더가 못 대체하는 건 "수집" 이 아니라 "내 조회 모델"

여기서 흔한 오해를 바로잡아야 한다. "Fireblocks 를 쓰면 인덱서가 통째로 필요 없어진다" 는 틀렸다. Fireblocks 의 인덱서 커버리지는 부분적이다 — 내 vault 로 들어온 입금/확정을 webhook 으로 밀어 주고, 내 vault 범위의 잔액 조회(total / available / locked / pending / frozen)·트랜잭션 이력 조회·확정 정책(DCCP)까지 제공한다. 다만 그 조회는 Fireblocks 의 고정된 데이터 형태이고 인덱서 내부는 들여다볼 수 없는 black-box 다 — 커스텀 가공(도메인 매핑·집계·검색 인덱스)과 임의 조건 조회는 그대로 내 몫이다.

두 가지를 분리해서 봐야 한다.

기능무엇벤더로 대체되나
전체 이력 조회내 주소의 과거 입출금·잔액·집계를 임의 범위로 조회 (이력 화면·장부 대사·감사·월별 명세)부분만. Fireblocks 도 내 vault 의 잔액·트랜잭션 이력 조회 API 를 준다. 하지만 형태가 고정이라 커스텀 가공·임의 집계는 내 조회 모델이 필요 — 그 모델은 webhook·이력 API 로 채울 수 있어 노드는 없어도 된다.
임의 주소 조회내가 관리하지 않는 주소(입금 송신자 등)의 위험도·이력인덱서의 문제가 아님 → 12.6 의 별도 포트로.
정리 — 교체 불가의 진짜 대상

벤더가 못 대체하는 건 "노드 직접 수집" 이 아니라 내 조회 모델이다. Fireblocks 로 가면 수집 소스는 webhook 으로 갈아끼우면 되지만, 이력·집계 조회 API 는 어느 벤더를 쓰든 내가 유지한다. 이것이 하이브리드의 진짜 이유다 — 임의 주소 조회 때문이 아니라.

12.6 임의 주소 · AML 은 인덱서가 아니라 별도 포트 — ScreeningProvider

내가 관리하지 않는 주소를 조회해야 하는 경우는 사실상 둘뿐이다 — 컴플라이언스(자금세탁방지·트래블룰·제재 스크리닝) 와 온체인 자금 흐름 추적. 그리고 공개 자료가 있는 거래소들은 이것을 자체 인덱서로 만들지 않는다.

거래소는 어떻게 하나 — 외부 vendor 위탁

9. 자체 인덱서 운영 에서 본 6 개 거래소의 공통 패턴 하나가 "AML 은 외부 vendor 통합, Chainalysis 가 가장 자주 등장" 이다.

거래소AML 처리 방식 (공개 자료)
Korbit입금 감지(자체) → AML 스크리닝(Chainalysis, 실시간) → 잔고 반영 또는 계류 → 반환. 이 다단계 흐름을 Temporal 워크플로로 관리(외부 API 실패 시 재시도, 장기 계류 타이머).
CoinoneAML 정보를 배치 프로그램으로 처리 (Replica DB 동기화 → 배치 가공).
공통6 사 모두 AML 은 외부 vendor 로 위탁 — 인덱서 "안" 이 아니라 입금 워크플로의 "다음 단계" 에 배치.

요점 — 인덱서는 "내 주소 입금 감지" 까지만 하고, 임의 주소 스크리닝은 인덱서 밖의 독립 단계다. 그러니 이것도 별도 포트로 뺀다.

interface ScreeningProvider {            // 인덱서·ChainDataSource 와 무관한 별도 포트
  screenAddress(addr, direction): Promise<RiskVerdict>   // Chainalysis 등
}

// AML 의무가 아직 없으면 — 비워두는 구현으로 시작
class NoopScreening implements ScreeningProvider {
  screenAddress(_, _) = { risk: 'UNKNOWN', allow: true }
}

12.7 교체를 망치는 함정 3 가지

교체 가능성을 살리려면 처음 설계에 못박아 둬야 하는 것들이다.

교체 안전 3 원칙
  • 스키마를 벤더 용어로 오염시키지 마라 — 원시 로그의 ParsedEvent 에 벤더 고유 식별자(예: Fireblocks 트랜잭션 id)가 새면 그 순간 교체 비용이 폭발한다. 벤더 식별자는 어댑터 내부 매핑 테이블에만 둔다.
  • 벤더 무관 canonical key 로 멱등성을 잡아라 — (chainId, blockNumber, txHash, logIndex) 를 유일 키로 고정(4.4 절). 자체 노드 → Fireblocks → Alchemy 어느 소스로 같은 이벤트가 중복 유입돼도 원시 로그가 깨지지 않는다.
  • 두 소스를 동시에 켜고 점진 전환하라 — 위 canonical key 덕분에 교체 중 기존 소스와 새 소스를 잠시 함께 돌려(shadow ingest) 결과를 대조한 뒤 끊을 수 있다. 한 번에 갈아끼우지 않는다.

12.8 정리

"자체로 시작했다가 벤더로 갈릴 수 있다" 는 상황의 답은 세 개의 포트로 요약된다.

  • ChainDataSource — 수집만 추상화. 자체 노드 ↔ Fireblocks webhook ↔ 타 벤더를 어댑터로 교체. 출력은 내 표준 스키마로 고정.
  • 내 조회 모델(원시 로그 → 가공 → 조회 API) — 포트가 아니라 영원히 내 자산. 어떤 벤더를 써도 이력·집계는 내가 유지한다.
  • ScreeningProvider — 임의 주소·AML 은 인덱서가 아니라 별도 포트. 거래소들이 Chainalysis 로 위탁하듯, 입금 워크플로의 독립 단계로. 의무가 미정이면 비워 둔다.

이렇게 두면 "Fireblocks 로 교체" 든 "Alchemy 로 교체" 든 어댑터 하나를 새로 쓰는 일이 되고, 원시 로그·가공·조회 API 는 그대로 남는다. 단 — Fireblocks 는 인덱서를 통째로 대체하지 못하므로(임의 조회·이력은 자체), 교체 후에도 내 조회 모델은 살아남는다는 걸 전제로 설계한다.
