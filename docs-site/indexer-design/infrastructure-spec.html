11. 인프라 · 스펙

HW · OS · 네트워크 · DB · 스토리지 의 구체 sizing + 3 규모별 reference + 물리 토폴로지

인덱서 인프라는 워크로드 규모 와 SLO 수준 에 따라 spec 이 크게 달라진다. 본 페이지에서는 Small / Medium / Large 3 규모를 정의하고, 각 규모별 물리 토폴로지 · HW spec · OS tuning · 비용 모델 을 제시한다. 모든 수치는 reference 일 뿐이며 실제 도입 시 워크로드 측정 후 조정.

11.1 3 규모 분류

인덱서를 운영하는 규모를 다음 3 단계로 분류. 각 단계의 reference spec 을 본다.

규모워크로드 예시처리량 (events/s)월 인프라 비용운영 인력
Small (경량) 특정 contract / token 이벤트만, 1 chain, 단일 application ~ 50 $100 - $800 0.5 - 1 FTE
Medium (중간) 멀티 protocol API, explorer-lite, 2-3 chain 500 - 2,000 $800 - $5,000 2 - 5 FTE
Large (대규모) 전체 chain analytics, Ethereum explorer, Solana low-latency, multi-chain custody 5,000 - 50,000+ $3,000 - $30,000+ 10 - 30 FTE

11.3.5 핵심 운영 포인트

  • i4i 인스턴스의 NVMe 는 instance store — 인스턴스 종료 시 데이터 손실. EBS snapshot 백업 필수 또는 두 노드 운영.
  • Postgres primary 만 write. replica 는 read 전용 → API 서버에서 read 분산.
  • MSK 3 broker 를 AZ 별 1 개씩 분산 → 1 AZ 장애에도 producer/consumer 가능.
  • 외부 RPC fallback 은 자체 노드 down 시 자동 전환. health check + circuit breaker 필수.

11.5.5 노드 운영 관행

  • archive node 는 항상 2 대 운영 (rotation backup) — sync 재시작 시 1 주일 이상 걸리므로
  • snapshot — daily EBS snapshot 또는 LVM snapshot. corruption 시 복구 시간 단축
  • monitoring — sync status, peer 수, latest block, db size, disk IOPS
  • 업그레이드 — hard fork 일정 추적. 보통 4-6 개월 마다 클라이언트 업그레이드

11.6 DB sizing 가이드

11.6.1 PostgreSQL

인덱서의 핵심 DB. 다음 항목으로 sizing.

  • RAM — hot data 의 1.5x 권장. shared_buffers = RAM 의 25%, effective_cache_size = RAM 의 75%.
  • CPU — read 가 많으면 cores ↑. write heavy 면 fewer cores + faster cores.
  • Disk IOPS — write 빈도에 비례. gp3 default 3,000 IOPS 도 부족할 수 있음. 16,000 IOPS 까지 provisioned.
  • Disk throughput — gp3 default 125 MB/s. 대규모 backfill 시 1,000 MB/s 까지.
  • Storage — 1 년치 events + 잔고 + history. 일반적 multi-chain 인덱서 ~ 1-5 TB.
  • connection pool — PgBouncer 권장. max_connections 보통 200-500.

핵심 튜닝 파라미터 예시 (db.r7g.xlarge, 32 GB RAM 기준):

shared_buffers = 8GB                   # 25% of RAM
effective_cache_size = 24GB            # 75% of RAM
work_mem = 32MB                        # per query operation
maintenance_work_mem = 2GB             # for VACUUM, CREATE INDEX
max_wal_size = 16GB                    # write-heavy workload
checkpoint_completion_target = 0.9
random_page_cost = 1.1                 # NVMe SSD
effective_io_concurrency = 200         # NVMe
max_worker_processes = 8
max_parallel_workers = 8
max_parallel_workers_per_gather = 4
autovacuum_vacuum_scale_factor = 0.05  # 자주 vacuum (write heavy)

11.6.2 ClickHouse

OLAP 분석용. 다음 특징:

  • columnar storage — 압축률 5-10x (zstd / lz4)
  • 분산 query — shard 자유
  • MergeTree engine — partition 별 background merge
  • Postgres 대비 분석 query 10-100x
  • partition by toYYYYMM(block_time) — 월 단위 hot/cold 관리 용이

Coinbase 가 사용하는 사례 — Delta Lake / ClickHouse 둘 다.

11.6.3 Elasticsearch / OpenSearch

검색 + 집계용.

  • Index 당 ~ 50 GB shard size 권장
  • 각 shard 1 primary + 1 replica
  • master node 3 개 (HA, dedicated)
  • data node — 검색 query 부하에 비례
  • JVM heap = RAM 의 50%, 최대 30 GB (compressed oops 한계)
  • refresh_interval = 30s (실시간성 양보, indexing throughput 향상)

11.6.4 Redis

hot cache + rate limiting + dedup.

  • maxmemory-policy = allkeys-lru (cache 용도)
  • persistence — RDB snapshot + AOF (durability 필요 시)
  • cluster mode — 데이터 ≥ 50 GB 또는 throughput ≥ 100K ops/s 시
  • 대형 hash 사용 시 hash-max-ziplist-entries 조정

11.7.3 디스크 / 파일시스템

  • 파일시스템 — XFS 또는 ext4. Postgres + geth + Kafka 모두 XFS 권장 (대용량 + 동시 쓰기 안정).
  • mount options — noatime,nodiratime 으로 메타데이터 IO 감소.
  • I/O scheduler — NVMe 는 none 또는 mq-deadline. SATA SSD 는 mq-deadline.
  • swappiness — DB / Kafka 서버는 vm.swappiness = 1 (절대 swap 금지).
  • Transparent Huge Pages — Postgres + Redis 는 never 권장 (latency spike 방지).

11.7.4 NUMA

32 vCPU 이상의 큰 인스턴스 (Solana validator 등) 는 NUMA topology 영향 큼. Postgres 는 numactl --interleave=all 권장. Kafka 는 broker 별로 CPU pinning.

11.7.5 컨테이너 환경

Kubernetes 사용 시 — node 의 sysctl 은 pod 에 자동 적용되지 않음. securityContext.sysctls 명시 또는 initContainer 로 설정. cgroup memory limit 은 JVM / Postgres / Redis 의 max heap 보다 충분히 크게.

11.9.3 복구 시나리오

  • 노드 디스크 손상 — backup 노드로 즉시 전환 (1 분). 원노드는 snapshot 에서 복구 (수 시간).
  • Postgres primary 장애 — read replica 를 promote (5-10 분). PITR 로 5 분 전 시점 복구 가능.
  • 전체 region 장애 — DR region 의 cold standby 를 활성화 (30 분 - 2 시간). 라우팅 변경 (Route 53).
  • 인덱서 로직 버그 — projection table truncate → raw_logs 에서 replay (수 시간 ~ 1 일).
  • chain reorg + 누락 — cursor 를 N 블록 뒤로 이동, 재처리 (수 분).

11.9.4 백업 검증

  • 월 1 회 — Postgres backup 을 staging 에 restore + sanity query
  • 분기 1 회 — DR region failover drill (route 변경, 트래픽 일부 실제 전환)
  • backup 메타데이터 (last_successful_backup, size, duration) 를 Prometheus metric 으로

11.11 성장 경로

Small → Medium → Large 의 자연스러운 성장 trigger.

  1. Small → Medium — 트래픽이 외부 RPC 의 Growth tier ($49) 초과 시. 자체 노드 + Kafka 도입.
  2. Medium → Large — 1 chain 만으로 부족 / 분석 / 백필 부담 증가 / multi-region 필요 시. Archive node + ClickHouse + 다중 region.

각 단계 전환 시 marker (지표 기준):

  • 외부 RPC 의 월 비용 ≥ $500 → 자체 노드 검토 (보통 ROI 1-2 개월)
  • Postgres ≥ 80% CPU 지속 → read replica 또는 sharding 검토
  • p95 latency ≥ SLO 의 80% 지속 1 주 → 다음 tier 검토
  • 1 chain 당 backfill 시간 ≥ 1 주 → archive node + parallel worker 검토

11.12 운영 체크리스트

신규 인덱서 배포 체크리스트
  1. 모든 secret 이 KMS / Secrets Manager 에 있는가
  2. 모든 컴포넌트의 backup / restore 절차 테스트했는가
  3. RPO / RTO 측정값이 목표 이내인가
  4. Synthetic canary tx 가 동작하는가
  5. 모든 11 지표 (8.2 절) 가 수집되고 알람 임계가 있는가
  6. Reorg 시나리오 테스트 통과했는가 (testnet 에서)
  7. Schema migration runbook 이 있는가
  8. 외부 RPC quota 알람이 80% / 95% 에 있는가
  9. DB connection pool size + work_mem 튜닝됐는가
  10. WAF + rate limit 활성화됐는가
  11. Multi-region 또는 multi-AZ 인가
  12. Postgres autovacuum 모니터링 + 튜닝됐는가
  13. Kafka retention 정책이 적용됐는가
  14. Health check endpoint 가 있는가
  15. Postmortem template 가 있는가
  16. OS 튜닝 (sysctl, ulimit, THP) 이 적용됐는가
  17. 노드 backup 노드 (HA) 가 hot-standby 인가
  18. 망분리 환경이면 firewall rule + 단방향 통신 audit 됐는가

11.13 마치며

본 가이드는 블록체인 인덱서의 vendor-neutral reference. 핵심 결론:

  1. 인덱서는 "블록체인 → 자체 read model" 의 ETL + projection layer.
  2. 4 패턴 (pull / streaming / scan / lake) 의 조합으로 만든다.
  3. 참조 아키텍처는 7 계층. raw event log 가 source of truth.
  4. Reorg + finality 가 가장 어려운 부분. confirmation 정책 + soft-delete + replay 의 조합으로 해결.
  5. SaaS / 자체 구축 의 trade-off — 출시 속도 vs sovereignty.
  6. 운영의 11 가지 핵심 지표를 항상 측정.
  7. 비용은 워크로드 + 규모에 따라 $280/월 ~ $30,000/월. 인력은 0.5 FTE ~ 30 FTE.
  8. OS · kernel · 파일시스템 튜닝 없이는 HW 성능의 30-50% 만 활용.
  9. RPO/RTO 는 거래 시스템보다 느슨하지만, 노드 재 sync 비용은 크다 — backup 노드 + snapshot 필수.
