인덱서는 필수인가

"인덱서를 도입해야 하나" 가 아니라 "어느 평면 까지 직접 만들어야 하나" 가 올바른 질문이다.

기초안내

한 줄로: "수탁형 지갑을 운영한다면 인덱서적 기능은 필수. 다만 어디까지 vendor 에게 넘기느냐가 결정 사항."

S3 의 3 평면 분류로 보면:

  • 평면 1 (원시 수집) — vendor 가 흡수 가능. 직접 안 만들어도 됨.
  • 평면 2 (파생 인덱서) — 일부만 vendor 가 흡수. 도메인 fact 는 customer 측.
  • 평면 3 (원장 · 워크플로) — 100% customer. 절대 vendor 가 못 함.
다음 단계 — Use case 별 분석

같은 "수탁형 지갑" 안에서도 use case 마다 인덱서 의존도가 다르다.

Alice 의 잔고 화면 (지갑 UI)

  • 평면 1 — vendor webhook 만으로 충분. Optional (직접 인덱싱 불필요)
  • 평면 2 — vendor 가 도메인 매핑 일부 제공 (vault → wallet). Should-have
  • 평면 3 — 잔고를 표시하려면 confirmed vs pending 구분 필요. Must-have

회계 마감 (월 / 일 단위)

  • 평면 1 — vendor 가 reorg event 까지 webhook 으로 통보해주면 OK. Optional
  • 평면 2 — 도메인 fact 가 audit-grade evidence 가 되려면 자체 저장 필요. Must-have
  • 평면 3 — 이중부기 분개 / 정정 entry / 마감 procedure. Must-have (회계법인 검증)

AML / Travel Rule 컴플라이언스

  • 평면 1 — vendor 가 Chainalysis / Elliptic 실시간 연결 제공. Optional
  • 평면 2 — counterparty address 매핑 + 위험 점수 자체 저장 (감사 evidence). Should-have
  • 평면 3 — AML alert 워크플로 + 100만원 미만 트래블룰 (금융위 2026). Must-have

금감원 검사 / 외부 감사 대응

  • 평면 1 — vendor 측 raw evidence 제공 (Fireblocks audit log). Optional
  • 평면 2 — customer 측 mirror 보관 (vendor 종속 위험 회피). Must-have
  • 평면 3 — incident 시 원인 분석 / 정정 evidence chain. Must-have

실시간 입금 알림 + push notification

  • 평면 1 — vendor webhook (Fireblocks v2). Optional
  • 평면 2 — webhook payload 의 idempotency + ordering 보정. Should-have
  • 평면 3 — Alice 에게 보낼 push notification 의 timing 결정 (confirmed 시점). Must-have

핵심 invariant — 평면 3 은 항상 customer

왜 vendor 가 평면 3 을 흡수할 수 없는가:

  • 회계 표준 종속성 — K-IFRS 적용, KR 세법, 감사인 의견. Vendor 가 KR 회계 standard 를 안 따른다.
  • 규제 책임 — 금융위 / 금감원 검사 응답은 은행이 직접. vendor 의 audit log 만으로는 부족.
  • 자체 정책 — 출금 한도 / VIP 대우 / 일별 마감 timing — 각 은행마다 다름.

평면 2 의 "Must" vs "Should"

회계 마감 + 외부감사 대응이 필요하면 평면 2 의 도메인 fact (Alice 입금의 source chain + tx hash + confirmation count) 를 자체 mirror 저장 해야 한다. Vendor 측 데이터만 의존하면:

  • Vendor outage 시 감사 불가
  • Vendor 종속 — 가격 / 정책 변경 시 협상력 ↓
  • 장기 보관 (5 년 + 영구 audit) 정책이 vendor 와 다를 수 있음

평면 1 의 "Optional" 의 의미

Optional 이라고 vendor 에 100% 위임해도 안전한 건 아니다. Vendor 가 평면 1 을 잘못 처리하면 (예: reorg 미처리) 평면 2/3 의 정합성도 무너진다. 따라서:

  • Vendor 의 평면 1 SLA 명문화 (reorg 처리 시간, lag SLA)
  • Customer 측 sanity check (vendor 가 보낸 데이터의 sample 검증)
  • 장기적으로 multi-vendor 전략 (single point of failure 회피)
