7.1 성능 목표 정의 + 측정 방법

"성능" 은 하나의 숫자가 아니다. 다음 4 가지를 분리해서 정의한다.

축측정 단위전형 목표측정 방법
Ingest throughput blocks/sec, events/sec Ethereum 1 block/12s · Solana > 100 events/s · 백필 시 10-100x 일정 시간 (5분) 동안 처리된 block 수 / 초
Ingest latency (head lag) 새 블록 proposed → 인덱서 적재까지의 초 P2 (streaming) 1-2s · P1 (pull) 5-15s block.timestamp 와 ingested_at 의 차이 분포 (P50/P95/P99)
Query latency API 응답 p95 (ms) 점 query < 100ms · range query < 500ms · 집계 < 2s request → response 시간. middleware / DB / cache 별 breakdown
Query throughput QPS 요구사항 별 · 1k QPS 이상 시 read replica + 캐시 load testing (k6, Locust 등)

인덱서 성능에서 특이한 점 — write rate 가 외부 (블록체인) 에 의해 결정된다. 인덱서가 그 외부 write rate 를 따라잡지 못하면 lag 가 누적되며, lag 가 커질수록 read API 의 데이터 신선도 (freshness) 가 떨어진다.

7.2 Ingest throughput 의 한계

인덱서의 ingest 속도를 결정하는 3 가지 bottleneck.

(1) RPC source 의 응답 속도

외부 RPC (Alchemy 등) 사용 시 — block fetch 당 100-500ms latency + monthly quota. 자체 노드 사용 시 — 노드의 disk IOPS + state 검색.

실측 reference:

  • Alchemy / Infura — 단일 RPC 호출 ~ 50-200ms (region / endpoint 의존)
  • 자체 geth full node (i4i.xlarge 기준) — eth_getBlockByNumber ~ 10-30ms
  • eth_getLogs — 응답 크기 제한 10,000 logs (Alchemy / Infura). 큰 범위는 chunked 호출 필요

(2) Parser / Decoder CPU

ABI 디코딩, address 매핑, decimals 적용 등. CPU-bound. 보통 single-thread per chain. 멀티스레딩 시 ordering 보장 필요.

실측 reference:

  • EVM ABI decode — 단일 event 당 10-50µs (Rust / Go) 또는 50-200µs (TypeScript)
  • 대량 event (USDC Transfer 1만건) 의 decode + Postgres bulk insert — 1-3 초 (mid-tier CPU)

(3) Storage write

Postgres INSERT 속도 + index update. bulk write (COPY) 와 single-row INSERT 의 차이가 10-50x.

실측 reference:

  • Postgres single INSERT — 0.5-2ms (RTT 포함, gp3 SSD)
  • Postgres COPY — 50,000-200,000 rows/sec (binary format, gp3)
  • ClickHouse async insert — 1,000,000+ rows/sec

7.3 처리량 확장 전술

(a) Filter / Dictionary — 처리할 블록 줄이기

SubQuery 가 보여준 패턴. "관심 있는 이벤트가 있는 블록만" 처리. 빈 블록 / 무관 블록 skip.

// 일반 scan
for block in 0..head:  // 모든 블록
  process(block)

// Dictionary 기반
relevant = dictionary.blocks_with_events(
  contracts=[USDC, USDT, WETH],
  events=['Transfer'],
)
for block in relevant:  // 10-100배 적음
  process(block)

SubQuery 공개 문서 — worker thread 와 dictionary 조합으로 최대 4 배 가속.

(b) Parallel workers — block range 별 병렬

백필 시 block range 를 N 등분해서 worker N 개가 병렬 처리. ordering 이 필요한 projection (예: 잔고) 은 마지막에 sequential merge.

// 백필 — 10 worker 병렬
range = [0, 19_345_678]
chunks = split(range, 10)  // 각 1.9M 블록
for chunk in chunks:
  worker.enqueue(chunk)
// 각 worker 가 자기 chunk 의 events 를 raw log 에 적재
// projection 은 raw log 의 cursor 따라 sequential

(c) Bulk write — Postgres COPY

single INSERT 대신 COPY 또는 multi-row INSERT.

// Bad: 1 row per INSERT
for event in events:
  INSERT INTO events VALUES (...);  // 1000 events = 1000 RTT

// Good: COPY
COPY events FROM STDIN;
...binary data...
\.  // 1000 events = 1 RTT

30-100x 빠름.

(d) Stream bus — Kafka / Redpanda

ingestion 과 projection 분리. ingestion 은 raw event 만 Kafka 로 publish, projection worker 들이 각자 consume.

// Producer (ingestion)
for event in chain_stream:
  kafka.produce('raw-events', event, key=event.chainId)

// Consumer (projection)
kafka.consume('raw-events', group='balance-projection', handler=updateBalance)
kafka.consume('raw-events', group='transfer-projection', handler=updateTransfers)
kafka.consume('raw-events', group='nft-projection', handler=updateNFT)

장점 — 새 projection 추가 시 consumer 만 추가. raw log 가 자연스러운 replay source.

(e) Sharding — chain 별 / block range 별

대규모 인덱서는 chain 별 또는 block range 별 sharding.

Sharding 전략분할 기준적합 시점운영 부담
Chain 별Ethereum / Polygon / Solana 가 각자 shardmulti-chain 인덱서, 트래픽 분리 OK낮음 (chain 별 독립 운영)
Block range 별같은 chain 의 0-10M / 10-20M 별로백필 + 시계열 분석 heavy중간 (cross-shard query 의 routing)
Tenant 별SaaS 인덱서의 customer 별multi-tenant SaaS높음 (tenant migration, noisy neighbor)
Contract 별특정 contract 의 이벤트 별대형 contract (USDC, WETH) 의 throughput hot높음 (hot contract 분포 모니터링)

7.4 Query latency 확장 전술

(a) 인덱스 설계

가장 흔한 query 패턴에 맞춰 index. PostgreSQL 의 핵심:

-- 주소 별 transfer 목록 (시간 역순)
CREATE INDEX idx_transfers_to_time
  ON token_transfers (chain_id, contract, to_addr, ts DESC)
  WHERE reverted = false;  -- partial index

-- block range query
CREATE INDEX idx_events_block_range
  ON events (chain_id, contract, block_num)
  WHERE reverted = false;

-- JSON 필드 검색 (gin)
CREATE INDEX idx_events_args
  ON events USING gin (args_json);

(b) Materialized view

흔한 집계는 미리 계산.

-- 일별 transfer 집계
CREATE MATERIALIZED VIEW daily_transfers AS
SELECT
  chain_id,
  contract,
  date_trunc('day', ts) AS day,
  COUNT(*) AS count,
  SUM(amount) AS volume
FROM token_transfers
WHERE reverted = false
GROUP BY chain_id, contract, day;

CREATE UNIQUE INDEX ON daily_transfers (chain_id, contract, day);

-- 매일 1회 refresh
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_transfers;

(c) Read replica + 캐시

Postgres read replica 1-N + Redis 캐시. hot path (잔고 조회) 는 캐시 우선.

// Pseudo-code: balance lookup
func getBalance(account, asset) {
  cached = redis.get(`balance:${account}:${asset}`)
  if (cached) return cached  // hit

  result = postgresReadReplica.query(...)
  redis.setex(`balance:${account}:${asset}`, 10, result)  // 10s TTL
  return result
}

캐시 전략 디테일

전략패턴장점주의
TTL 기반10s 만료 후 다시 fetch구현 단순stale data (블록 변동 시 최대 10s 지연)
Event-driven invalidation해당 wallet 의 transfer event 시 cache 삭제fresh 보장invalidation 누락 = 영구 stale
Write-throughprojection worker 가 DB 와 cache 동시 write최신성 + 단순 read2-phase write 의 정합성 부담
Stampede 방지cache miss 시 lock 또는 stale-while-revalidatebackend 폭주 방지lock overhead

(d) Search engine — Elasticsearch / OpenSearch

전문 검색 / 복잡한 boolean filter 는 ES 가 Postgres 보다 빠름. 인덱서가 ES 에도 별도 projection.

(e) OLAP 분리 — ClickHouse

대규모 집계 (예: 1년치 거래량) 는 ClickHouse 가 압도적. Coinbase 같은 대형 인덱서가 사용.

7.6 Backpressure / Flow control

인덱서가 외부 source (블록체인 / RPC) 보다 느려지면 lag 가 누적된다. Backpressure = 빠른 producer 와 느린 consumer 사이의 부하 조절 메커니즘.

Backpressure 가 없을 때의 실패 모드

  1. OOM — 처리 못한 event 가 메모리 큐에 누적 → process killed
  2. Disk overflow — Kafka / 큐의 retention 초과 → 오래된 event 삭제 → 데이터 손실
  3. Cascade failure — 한 projection 이 느려서 Kafka consumer lag → broker 부하 → 다른 consumer 영향

Backpressure 전술

전술메커니즘적합 위치
Bounded queue큐 크기 제한 — 가득 차면 producer 가 waitparser → DB write 사이
Adaptive batching처리량 따라 batch size 동적 조정 (1 ~ 1000)RPC 호출 / DB COPY
Token bucket일정 rate 로 token 발급 → consumer 가 token 가져가서 처리외부 RPC 호출 rate limit
Circuit breakerdownstream 실패 N 회 시 차단 → 일정 시간 후 half-open외부 vendor (Alchemy / Chainalysis) 호출
Kafka consumer lag SLOlag > 임계 시 알람 + auto-scaleKafka consumer group
Priority queuefinality 임박 / 사용자 활동 wallet 우선 처리projection scheduling

예시 — Adaptive batching

// 처리량 측정 → batch size 동적 조정
let batchSize = 100;
let lastDuration = 0;

while (true) {
  const events = await queue.popN(batchSize);
  const start = Date.now();
  await processBatch(events);
  const duration = Date.now() - start;

  // 목표 batch duration = 500ms
  if (duration < 250 && batchSize < 1000) batchSize *= 2;
  if (duration > 1000 && batchSize > 10) batchSize /= 2;
}

7.7 백필 (backfill)

새 인덱서 시작 시 또는 새 projection 추가 시 — 처음부터 다시 처리. 백필이 production traffic 보다 부하 크다.

전형적 백필 비용

체인현재 블록 (2026-06)RPC 호출 수 (block 별 5 호출 가정)완료 시간 (1 worker, 100ms/RPC)
Bitcoin~ 850,0004.25M~ 5 일
Ethereum~ 19.3M96.5M~ 112 일
Polygon~ 60M300M~ 347 일
BSC~ 45M225M~ 260 일

이 표가 보여주는 — single worker 로는 절대 안 됨. 백필은 항상 병렬 + filter + bulk write.

백필 가속 전술

  1. Range 분할 + 병렬 worker — 10-100 worker 동시 처리. Ethereum 백필 ~ 1 일.
  2. Filter / dictionary — 빈 블록 skip. 추가 10-100x.
  3. Raw block file 활용 — Firehose / cryo (Paradigm) 같은 도구로 raw block 을 파일로 export 후 로컬에서 처리. RPC 호출 줄임.
  4. Archive node 직접 read — 자체 archive node 의 LevelDB 직접 read (geth 의 chaindata).
  5. Stream-first 도구 — Substreams (The Graph) — 일부 subgraph 100x+ sync.

백필 운영 — 모니터링 / 일시 정지 / 재개
