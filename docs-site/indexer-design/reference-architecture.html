Figure 4-1. 참조 아키텍처 — 8 계층. 흐름은 왼쪽 (블록체인 원천) 에서 오른쪽 (Query API) 으로. 각 계층 안의 항목은 그 계층의 독립 컴포넌트들.

이 아키텍처는 event sourcing + CQRS 구조다. Raw Event Log (5) = append-only event store, Projection Workers (6) + Storage (7) = materialized view 의 read model, Query API (8) = query side. Source / Collector / Reorg manager 가 이 구조의 앞단에 있는 이유는 event 의 source 가 자체 application 이 아니라 외부 blockchain 이기 때문 — 합의 / reorg / 외부 RPC 의 추가 처리가 필요하다.

4.2 컴포넌트 별 책임

8 컴포넌트의 역할 / 입력 / 출력 / 운영 지표를 한 표로. 데이터는 (1) Source → ... → (8) Query API 순서로 흐른다.

컴포넌트역할 (한 줄)입력출력운영 지표
(1) Source
데이터 원천		 blockchain raw data 의 source (P2P 합의) block · tx · log · state change sync 상태, peer count, head lag
(2) Collector
수집		 Source 에서 데이터 fetch (4 구현 패턴 P1-P4 중 하나) Source 의 raw untyped block / tx / log stream fetch latency, error rate, retry
(3) Reorg / Finality Manager cursor 관리, confirmation 추적, reorg 감지 + rollback signal block + parent hash chain cursor / reorg event / finality event reorg depth, finality lag
(4) Parser / Decoder raw bytes → 도메인 schema (ABI · IDL · contract metadata 사용) untyped event typed event (예: Transfer{from,to,value}) unknown ABI 비율, decode 실패 수
(5) Raw Event Log
★ append-only		 모든 parsed event 를 immutable 보관 (재처리의 source of truth) typed event append-only log (Kafka / Postgres / object storage) log size, retention 정책 준수
(6) Projection Workers raw event → 도메인 별 read model 변환 (여러 worker 가 같은 raw 를 각자 다르게) raw log indexed row (잔고, transfer 이력, NFT 소유, 검색 index, 시계열 등) replay duration, projection lag
(7) Storage projection 결과 저장 (역할 별 서로 다른 storage) projection 출력 (read API 의 source) DB size, query latency, write throughput
(8) Query API storage 의 데이터를 외부 애플리케이션에 노출 storage read REST / GraphQL / SQL / gRPC / Webhook push QPS, p95 latency, 5xx 비율

주요 디테일

(1) Source 의 선택지 — full node (geth · reth · bitcoin-core) · archive node · third-party RPC (Alchemy · Infura · QuickNode) · Geyser plugin · Firehose · S3 lake. 선택 기준은 3. 4 구현 패턴 참조.

(3) Reorg Manager 의 핵심 데이터 — 모든 블록의 (block_number, block_hash, parent_hash) chain 을 추적해야 reorg 를 감지 가능. 자세한 처리 전략은 6. Reorg · Finality 페이지 참조.

(4) Parser 의 운영 이슈 — unknown ABI (등록 안 된 contract), proxy contract (logic contract 의 ABI 사용 필요), 새 event signature 추가 (코드 deploy 없이 ABI 만 업데이트) 대응 필요.

(5) Raw Event Log 의 ★ 핵심 원칙 — raw log 는 절대 삭제 / 수정 ✗. projection 만 disposable. 이 원칙이 깨지면 새 projection 추가 시 replay 불가 + audit trail 손실.

(6) Projection 의 운영 패턴 — 새 projection 추가 시 raw log 의 처음부터 replay. 같은 raw event 가 여러 projection (잔고 + 시세 + 검색) 의 source 가 됨.

(7) Storage 의 종류 별 선택 — 역할 별 서로 다른 storage 가 표준 패턴:

저장소역할전형적 사용
PostgreSQLsystem of record잔고, transfer history, contract metadata
Rediscache + 상태최근 N 블록 hot cache, watermark
Elasticsearch / OpenSearch검색 + 집계주소 / tx 전문 검색, 대시보드 집계
ClickHouseOLAP 분석대규모 시계열, 분석 query
RocksDB / Pebble임베디드 KV내부 state, checkpoint
S3 / GCScold storageraw log 백업, 오래된 snapshot

(8) Query API 의 책임 — 단순 데이터 노출 뿐 아니라 auth · rate limit · query complexity 제한 · pagination · caching 까지 포함.

4.3 read / write 분리 — 가장 중요한 원칙

이 아키텍처에서 가장 중요한 invariant 한 가지:

★ read / write 분리

인덱서가 만드는 모든 storage 는 read-only. 인덱서가 자체 storage 에 write 할 때, 그 write 의 source 는 항상 raw event log → projection 의 deterministic 변환이어야 한다.

운영 중 storage 의 row 를 직접 UPDATE 하지 않는다. 보정이 필요하면 raw event 를 추가하고 projection 을 다시 돌린다.

이 원칙이 깨지면 reorg / replay 시 정합성이 무너진다.

4.4 컴포넌트 간 인터페이스

Collector → Reorg manager

type RawBlock = {
  number: BlockNumber
  hash: BlockHash
  parentHash: BlockHash
  timestamp: Timestamp
  txs: RawTx[]
  logs: RawLog[]
}

Reorg manager → Parser

type ChainEvent =
  | { type: 'NewBlock', block: RawBlock, confirmations: number }
  | { type: 'BlockFinalized', blockNumber: BlockNumber }
  | { type: 'Revert', orphanedBlock: BlockHash, fromBlock: BlockNumber }

Parser → Raw Event Log

type ParsedEvent = {
  // canonical key (idempotency)
  chainId: ChainId
  blockNumber: BlockNumber
  blockHash: BlockHash
  txHash: TxHash
  logIndex: number

  // typed payload
  eventName: string         // e.g., 'Transfer'
  args: Record<string, any> // decoded
  raw: Bytes                // 원본 보존
}

Raw → Projection

각 projection worker 가 raw log 의 own cursor 를 가짐. Kafka offset, Postgres LSN 같은 형태. 새 projection 추가 시 cursor 를 0 으로 시작.

Projection → Storage

idempotent upsert. 같은 event 를 두 번 처리해도 결과 같음.

// 예 — 잔고 projection
INSERT INTO balances (account, asset, balance, as_of_block)
VALUES ($account, $asset, $newBalance, $blockNumber)
ON CONFLICT (account, asset)
  DO UPDATE SET
    balance = EXCLUDED.balance,
    as_of_block = EXCLUDED.as_of_block
  WHERE EXCLUDED.as_of_block > balances.as_of_block;
  -- block number 가 더 큰 update 만 적용 (out-of-order 방어)

4.5 운영 평면 분리

참조 아키텍처는 다음 3 평면으로 운영 분리 가능. 각자 별도 deploy / scale.

평면컴포넌트scale 특성
Ingestion plane Source · Collector · Reorg manager · Parser · Raw Log source 처리량에 비례. blockchain TPS 가 결정.
Projection plane Projection Workers · Storage write projection 수에 비례. 새 read model 추가 시 worker 추가.
Serving plane Storage read · Query API · Webhook 애플리케이션 트래픽에 비례. 가장 가변적.

The Graph 가 "indexing node" 와 "query node" 를 별도 process 로 운영하는 것이 정확히 이 분리. Blockscout 도 indexer / API / UI 를 별도 모드로 운영 가능.
