8. 운영 · 모니터링

지표 · SLO · 알람 · Dashboard · Incident response · Postmortem · DR · 보안

8.1 운영의 4 가지 흔한 장애

인덱서 운영 중 가장 자주 발생하는 4 가지. 모두 모니터링 부재 시 악화.

  1. 체인 헤드 추격 실패 — head lag 누적. UX 에 즉시 보임.
  2. DB 디스크 고갈 — backfill 또는 retention 부족.
  3. RPC rate limit — 외부 vendor 의 monthly quota 초과.
  4. Reorg 후 projection 불일치 — raw 는 OK 인데 projection 정합성 깨짐.

8.2 필수 모니터링 지표

다음 11 가지 지표를 항상 측정 + 알람. 임계는 3 단계 (warn / critical / page).

지표의미warncriticalpage
head_lag_seconds 최신 chain head - 인덱서 cursor 의 시간 차 > 30s > 120s > 5분 (지속)
finalized_lag_blocks chain finalized block - 인덱서 finalized 처리 block > 50 blocks > 200 blocks > 1000 blocks
ingest_rate_blocks_per_sec 초당 처리 블록 수 체인 자연 속도의 90% 50% 10% (catchup 실패)
rpc_error_rate RPC 호출 실패율 (timeout / 4xx / 5xx) > 1% > 5% > 20% (지속 5분)
rpc_quota_remaining 외부 vendor 의 남은 quota (CU 또는 호출) < 30% < 10% < 1% (즉시)
db_connection_wait DB connection pool wait time p95 > 50ms > 200ms > 1s (지속)
db_disk_free_pct DB 디스크 여유율 < 30% < 15% < 5% (즉시 page)
kafka_consumer_lag 각 projection consumer 의 Kafka lag > 1k msgs > 10k msgs > 100k msgs
projection_replay_duration 새 projection 의 backfill 진행 ETA 의 1.2x 1.5x 2x
reorg_depth 발생한 reorg 의 depth (blocks) > 3 > 10 > 50 (대규모 reorg)
query_p95_ms read API 의 p95 응답 시간 > 200ms > 1000ms 5xx rate > 1%

위 11 지표 중 블록체인 specific 한 것은 head_lag_seconds, finalized_lag_blocks, reorg_depth 3 가지뿐 — 나머지 (DB / Kafka / API / quota) 는 일반 백엔드 SRE 지표와 동일하다.

8.3 SLO 정의 예시

각 axis 별 SLO 를 명문화. 다음은 mid-size 인덱서의 typical SLO.

service: blockchain-indexer
slos:
  - name: ingest_freshness
    objective: 99% of blocks indexed within 10s of proposal
    measurement: head_lag_seconds < 10
    window: 28d rolling
    error_budget: 1% (~ 6.7 hours/month)

  - name: query_latency
    objective: 95% of point queries < 100ms
    measurement: query_p95_ms < 100
    window: 7d rolling

  - name: query_availability
    objective: 99.9% successful query responses
    measurement: 5xx_rate < 0.1%
    window: 30d rolling

  - name: data_correctness
    objective: zero finalized data drift events per month
    measurement: count(finalized_drift_alerts) = 0
    window: 30d rolling

SLO / SLI / SLA 의 구분

용어의미예시
SLI (Indicator)실제 측정 지표head_lag_seconds 의 P95 값
SLO (Objective)충족해야 할 목표"99% of blocks within 10s"
SLA (Agreement)SLO 위반 시 보상 / 환불 조항이 있는 고객 계약"99.9% 미달 시 월 사용료 10% 환불"
Error budgetSLO 의 허용 실패 시간99% → 월 ~7.2시간 실패 OK

8.6 장애 시나리오 + Runbook

(1) RPC source down

증상: rpc_error_rate > 50%, head_lag 증가
원인 후보:
  - 외부 RPC vendor outage
  - 네트워크 문제
  - quota 초과

조치:
  1) status page 확인 (Alchemy/QuickNode/Infura)
  2) fallback RPC 전환 (multi-RPC 구성 시 자동)
  3) quota 초과면 임시 plan 업그레이드
  4) 자체 노드 사용 가능하면 전환

(2) 인덱서 lag 누적

증상: head_lag_seconds 가 증가하기만 함
원인 후보:
  - 블록당 처리 시간이 블록 주기보다 느림
  - DB write bottleneck
  - parser bug (특정 event 처리 무한 loop)

조치:
  1) 최근 deploy 확인. rollback 검토
  2) parser CPU 사용량 확인
  3) DB slow query 확인
  4) worker scale up
  5) 임시 — 일부 event filter 강화

(3) DB 디스크 고갈

증상: db_disk_free_pct < 10% (critical)
원인 후보:
  - 백필이 예상보다 많이 적재
  - retention 정책 부재
  - autovacuum 실패

조치:
  1) 즉시 — 오래된 partition DROP
  2) ANALYZE + VACUUM 실행
  3) 디스크 확장 (managed DB 는 reboot 없이)
  4) 장기 — partitioning + retention 정책

(4) Reorg 후 projection 불일치 (data drift)

증상: 잔고 합계 != 사용자 잔고 합
원인 후보:
  - reorg 시 projection 의 일부 row 만 revert
  - dual-write 중 일관성 깨짐
  - projection 의 idempotency bug

조치:
  1) 영향 block range 식별
  2) raw_event_log 기준으로 affected projection 재계산
  3) projection 의 cursor 를 영향 block 직전으로 rewind
  4) replay 실행
  5) postmortem — idempotency 강화

(5) Webhook delivery 실패

증상: webhook consumer 에서 처리됐는데 인덱서 측 webhook_sent 없음
원인 후보:
  - consumer endpoint 5xx
  - signature 검증 실패
  - consumer 의 idempotency 처리 부재

조치:
  1) consumer 의 receive log 확인
  2) retry queue 확인
  3) signature key rotation 여부
  4) 30 일 retry budget 내 재전송

(6) Kafka consumer lag 폭증

증상: kafka_consumer_lag > 100k msgs
원인 후보:
  - consumer process crash 후 재시작 안 됨
  - consumer 가 단일 message 처리에 너무 오래 걸림
  - partition 수 부족 → consumer 병렬화 한계

조치:
  1) consumer process 상태 확인 (crashloop?)
  2) slow consumer 의 message 별 처리 시간 logging
  3) 임시 — 더 빠른 consumer 추가 (group 확장)
  4) 장기 — partition 수 증가 + consumer 병렬

8.10 Synthetic monitoring — 가장 신뢰할 만한 health check

인덱서가 "동작하는 것 같지만 실제로는 틀린 데이터" 인 경우가 있다. 진짜 동작 확인은 canary tx.

// 5 분마다 실행
function syntheticCheck() {
  // 1. 모니터링 전용 wallet 에서 small transfer 전송
  const tx = wallet.sendSmall(CANARY_DEST, 0.001 USDC);

  // 2. 일정 시간 후 인덱서에 해당 transfer 가 나타나는지 polling
  const start = Date.now();
  while (Date.now() - start < 60_000) {
    const found = await indexer.query({
      from: wallet.address,
      to: CANARY_DEST,
      after: tx.blockNumber,
    });
    if (found.length > 0) {
      metrics.recordCanarySuccess(Date.now() - start);
      return;
    }
    await sleep(5_000);
  }

  // 3. 60초 안에 못 찾으면 alert
  metrics.recordCanaryTimeout();
  alert.send('Canary tx not indexed within 60s');
}

8.11 Backup / DR

백업 대상

  1. Raw event log — 가장 중요. 손실 시 전체 재인덱싱 (수 일 ~ 수 주).
  2. Postgres 의 read model — projection 의 복구 source. PITR (Point-In-Time Recovery) 권장.
  3. 체크포인트 / cursor — DB 손실 시 어디서 resume 할지.
  4. Schema 정의 — 코드 + DB schema 의 버전 일치.

RPO / RTO 목표

대상RPORTO
Raw event log0 (즉시 backup 또는 replication)1 시간 (다른 region 에 standby)
Postgres projection5 분 (WAL archiving)1 시간 (replica 로 failover)
전체 service5 분4 시간 (DR region 활성화)

DR 시나리오 — 전체 region 손실

  1. Raw event log 가 multi-region 에 replicated → 손실 0
  2. 다른 region 의 standby 인덱서가 raw log 로부터 projection 재생성
  3. DNS / load balancer 가 DR region 으로 cutover
  4. 예상 복구 시간 — 4 시간 (projection 의 fresh 시점에 따라)

DR drill — 정기 훈련

실제 DR 시 처음 해보면 실패 확률 높음. 정기 훈련 필수.

주기훈련 종류
분기Backup 으로부터 신규 환경 복구. RPO/RTO 측정 후 SLO 비교.
반기DR region 으로 traffic cutover 5 분간 (Game Day)
연간전체 region failover. 실제 production traffic 전환 + 정상 동작 검증.
