2. 요구사항

왜 필요한가 + 8 가지 비기능 요구사항 + 정의해야 할 SLO

2.1 왜 인덱서가 필요한가 — 4 가지 본질적 이유

인덱서는 "있으면 좋은 것" 이 아니라 일정 규모 이상의 블록체인 애플리케이션에서는 필연적으로 등장하는 계층이다. 그 이유를 4 가지로 정리한다.

(1) 성능 — 블록체인 데이터는 본질적으로 순차적

블록체인 데이터는 시간 순서대로 append-only 로 쌓인다. 다중 블록을 가로지르는 query, 과거 state, 집계 query 를 직접 RPC 로 수행하면 매우 느리다.

구체 예시:

  • "주소 X 의 30 일 입금 내역" — Ethereum 의 12 초/블록 × 30 일 = 약 216,000 블록 스캔. eth_getLogs 의 응답 크기 제한 (Alchemy 10,000 logs / Infura 10,000) 때문에 chunked 호출 필요. 총 응답 시간 수십 초 ~ 분 단위.
  • "USDC contract 의 최근 100만 건 Transfer" — 블록당 평균 100 건 가정 시 10,000 블록 = 약 33 시간 분량 데이터. 단일 RPC 응답 불가.
  • "특정 컨트랙트의 모든 internal transaction" — trace API + archive node 필요.

(2) UX — "지금 막" + "역사 전체" 동시 요구

지갑/거래소 UI 는 두 가지를 동시에 제공해야 한다.

  • 실시간 — 방금 들어온 입금 (1-2 초 이내 알림)
  • 역사 집계 — 지난 1 년 거래량, 자산별 holding 추이

RPC 만으로는 두 요구를 모두 동시에 만족시키기 어렵다. 인덱서가 한 곳에서 처리.

(3) 데이터 접근성 — 원시 RPC ≠ 도메인 schema

RPC 가 답하는 것은 "트랜잭션 raw bytes" 단위. 애플리케이션이 원하는 것은 "특정 사용자의 USDC 입금 내역" 같은 도메인 query.

변환 + 인덱싱 없이는 도메인 query 불가능. 예 — USDC contract 의 Transfer event 의 topics[2] (recipient address) 를 자체 user/wallet DB 와 매칭, USDC 의 6 decimals 적용 (raw 100,000,000 → 100.00), tx timestamp 를 KR 시간대 변환 등.

(4) 분산성 — 외부 RPC 의존도 vs 자체 운영 비용

인덱서를 잘 설계하면 외부 hosted RPC (Alchemy 등) 의존도가 낮아진다. 잘못 설계하면 vendor 한 곳에 모든 데이터 권력이 집중. 인덱서 전략 = 위험 모델 + 신뢰 모델의 일부, 단순 성능 문제가 아니다.

2.2 8 가지 비기능 요구사항 (NFR)

인덱서를 만들거나 도입할 때 정의해야 할 8 가지 axis. 모든 항목에 측정 가능한 SLO 가 있어야 한다.

요구사항의미측정 지표 (SLO 후보)
일관성 · 정합성 reorg, 미확정 블록, 중복 수신에도 결과가 틀리지 않아야 함 rollback 성공률, data drift 건수, double-credit 발생률
지연시간 UX 에 보이는 최신성. 새 블록 → 인덱서 적재 → 애플리케이션 인지 head lag p50/p95/p99, ingest latency
처리량 고 TPS 체인 + 대규모 backfill 대응 blocks/sec, tx/sec, events/sec, backfill 완료 시간
확장성 체인 수 · projection 수 · query 량 증가 대응 shard 별 QPS, DB connection wait, autoscale 반응 시간
보안 데이터 위조 · DoS · 오염 방지 invalid proof 비율, rate-limit hit, sanctioned address 매칭 false positive
운영성 백업, 재동기화, 장애 복구 RPO (목표 복구 시점), RTO (목표 복구 시간), replay 시간
마이그레이션 schema 변경 시 서비스 중단 최소화 migration 시간, rollback 가능 여부, dual-write 기간
비용 인프라 + 운영 인력 비용 월별 cloud cost, vendor 라이센스, FTE 수

2.3 각 요구사항의 디테일

(1) 일관성 · 정합성

가장 어려운 요구사항. 다음 3 가지 시나리오에서 결과가 틀리지 않아야 한다.

  • Reorg — chain head 가 다른 fork 로 교체. confirmed 라고 본 tx 가 사라짐. 자세한 처리는 6. Reorg · Finality 페이지.
  • 미확정 (pending) 블록 — Solana 의 processed commitment 처럼 아직 final 이 아닌 데이터.
  • 중복 수신 — 같은 webhook 이 재시도로 두 번 들어옴. Adapter / consumer 에서 idempotency 처리 필요.

권장 전술: append-only raw log + idempotent upsert + cursor 저장 + rollback/replay. raw log 는 절대 삭제하지 않고, projection 만 disposable 로 다룬다.

(2) 지연시간

"새 블록이 인덱서에 반영되기까지" 의 시간. 체인마다 다른 자연적 lower bound 가 있다.

체인블록 주기이상적 인덱서 lag
Bitcoin~ 10 분< 30 초
Ethereum~ 12 초< 5 초
Polygon~ 2 초< 1 초
Solana~ 400-600 ms (slot)1-2 slot

지연을 줄이는 핵심 — pull 대신 push (WebSocket / Geyser / Firehose), commit 직후 메모리 cache 우선 반영.

(3) 처리량

두 가지 worst case 를 견뎌야 한다.

  • 실시간 burst — Solana mainnet 의 peak TPS ~ 수천. Ethereum 도 NFT mint 시 5,000+ tx/block 가능.
  • Backfill — 신규 체인 추가 시 genesis 부터 다시 sync. Ethereum mainnet 전체 = 약 2 TB (path-based archive). 신규 인덱서 startup 시 수일 ~ 수주.

권장 — filter / dictionary 로 처리 블록 수 감소, parallel worker, Kafka partitioning, bulk write.

(4) 확장성

"체인 수 / projection 수 / query 량" 의 증가에 대응. 핵심 패턴 — read/write 분리. The Graph 의 query node ↔ indexing node 분리 권장이 그 예.

(5) 보안

인덱서의 주요 공격면:

  • 데이터 위조 / 오염 — 잘못된 RPC 결과 또는 악성 노드
  • Replay · reorg 악용 — 같은 tx 가 다른 결과로 처리되도록 유도
  • DoS / query 폭주 — query API 가 backend 를 무너뜨림
  • 운영자 실수 — schema migration 실수로 잘못된 데이터 적재

권장 — 다중 RPC source + signed receipt (해당 시), WAF + rate limit + query complexity 제한, schema version 분리.

(6) 운영성

실패 복구 시나리오 — DB 손실, Kafka offset 손실, RPC 노드 손실, 인덱서 process crash, schema 손상.

RPO/RTO 의 현실적 목표:

  • RPO < 1 분 (raw event 손실 ≤ 1 분치)
  • RTO < 1 시간 (전체 service 복구)
  • Backfill replay < 24 시간 (전체 history 재구성)

(7) 마이그레이션

schema 변경 = 곧바로 전체 재인덱싱이어선 안 된다. dual-write + backfill + cutover 패턴이 표준. 인덱서 release 시 항상 rollback 경로를 갖춰야.

(8) 비용

3 종류의 비용을 분리해서 본다.

  • 인프라 — 노드 compute, DB storage, stream bus, egress. Ethereum archive 만으로 월 $500-$2,000.
  • 외부 vendor — Alchemy/QuickNode 사용 시. 트래픽 따라 월 수백 ~ 수만 달러.
  • 운영 인력 — 인덱서 운영 SRE / DBA. FTE 1-5 명 (규모에 따라).

2.4 우선순위 결정

8 가지를 다 동시에 최고로 만들 수는 없다. 워크로드 별 우선순위:

2.5 흔한 실패 모드

인덱서 운영 중 가장 자주 발생하는 4 가지 장애:

  1. 체인 헤드 추격 실패 — RPC source 가 느려져서 인덱서 lag 가 누적. UX 에 즉시 보임.
  2. DB 디스크 고갈 — backfill 도중 / log retention 부족으로 인덱서 DB 가 디스크 한계 도달. write 실패.
  3. RPC rate limit — Alchemy 같은 외부 vendor 의 monthly quota 초과 → 429.
  4. Reorg 후 projection 불일치 — raw 는 잘 처리됐는데 projection 의 보정이 빠짐. 잔고 / 집계 값이 틀림.

4 가지 모두 모니터링 부재 시 악화. 8. 모니터링 페이지 에서 자세히.
