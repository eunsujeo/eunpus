수탁형 지갑에서의 역할

"인덱서" 는 하나의 컴포넌트가 아니다. 수탁형 지갑 안에서는 3 개의 분리된 평면으로 작동한다.

기초안내

수탁형 지갑에서 인덱서는 3 개 평면 (plane) 으로 나뉜다.

  1. 원시 수집 평면 — 블록체인 노드에서 raw 블록 / 트랜잭션 / 로그를 가져온다.
  2. 파생 인덱서 평면 — 그 데이터를 도메인 schema 로 변환 (예: "Alice 의 입금").
  3. 원장 · 워크플로 평면 — 입금 인정 / 잔고 반영 / AML / 출금 승인을 처리.

이 3 평면이 분리되어야 하는 이유는 한 가지: "블록체인이 본 것" 과 "은행이 인정하는 것" 은 다르다.

다음 단계 — Alice 시나리오로 3 평면

14:00:15 Alice 의 입금이 블록 N 에 mined. (블록체인 truth)

평면 1 (원시 수집) — 인덱서가 블록 N 을 read. "주소 0x1234 로 USDC 100 들어옴" 이라는 raw event 를 본 다.

평면 2 (파생 인덱서) — 0x1234 는 어느 vault 의 어느 wallet 인가? DB lookup. "Alice 의 vault, USDC 입금 주소 1" 로 매핑.

평면 3 (원장 · 워크플로) — 이제 인정할 시점인가? Confirmation 1 회만으로 잔고 반영? AML 검증은? Alice 의 출금 한도 영향은? — durable workflow 가 결정.

이 3 평면이 분리되지 않으면:

  • 블록체인이 reorg 했는데 (평면 1 이 revert) 잔고가 이미 반영됨 (평면 3) → 회계 불일치
  • AML 검증 (평면 3) 이 느려서 평면 2 의 입금 대기열이 쌓임 → indexer 가 막힘
  • 새 vendor 로 교체 (평면 1) 시 평면 2/3 도 함께 다시 만들어야 함 → vendor lock-in

본 wiki 의 deposit / withdrawal flow 와 회계 · 원장 설계 가 이 3 평면 분리를 전제로 작성됐다.

심화 · 3 평면 의 운영 디테일

평면 1 — 원시 수집

역할
블록체인 노드에서 raw 블록 / 트랜잭션 / 로그 read. 4 가지 구현 패턴 (풀노드 pull / 이벤트 스트리밍 / 트랜잭션 스캔 / 데이터 레이크) 중 선택.
출력
"블록 N 에 트랜잭션 T 가 있다, hash X, logs Y, status Z" 의 raw event.
운영 지표
Head lag · 동기화 속도 · reorg 감지 · 노드 가용성.
책임
vendor 흡수 가능 영역. Fireblocks / BitGo / NodeInfra 가 customer 에게 안 보임.

평면 2 — 파생 인덱서

역할
raw event → 도메인 schema 변환. Address attribution (어느 wallet?), asset normalization (USDC on ETH vs Avalanche), confirmation count tracking.
출력
"vault V 의 wallet W 의 USDC 잔고 +100, confirmation 1/12" 의 도메인 fact.
운영 지표
Address attribution miss rate · 도메인 schema migration · query latency.
책임
vendor 가 일부 흡수 (예: Fireblocks 의 webhook payload), 나머지는 은행 customer 측.

평면 3 — 원장 · 워크플로

역할
"인정" 결정. Confirmation policy 충족 → 잔고 반영. AML 검증 → 잠정 hold 또는 confirm. 출금 승인 / 환급 / 재시도 워크플로.
출력
이중부기 분개 (차변 / 대변) + state transition + audit log.
운영 지표
이중부기 정합성 · 워크플로 lag · AML alert 처리 시간 · 마감 timing.
책임
전적으로 은행 customer 측. vendor 가 흡수 못 함 (회계 / KR 규제 / 자체 정책).

"observation 이 곧 deposit 이 아니다" — 입금 감지 vs 잔고 반영 분리

가장 흔한 운영 실수: 평면 1 의 raw event 를 그대로 평면 3 에 반영. → reorg 시 잔고 -100 처리, AML 검증 실패 시 잔고 차감, 회계 마감 시 불일치.

올바른 분리:

  1. 평면 1 raw event → 평면 2 에 도메인 fact 로 기록 (read-only)
  2. 평면 3 의 워크플로 가 정책 (confirmation / AML / 시간) 충족 시 → pending balance 에 +100
  3. 최종 finality + 모든 검증 통과 시 → confirmed balance 에 +100 (이중부기 분개)

Fireblocks 공식 권고도 동일 — incoming transaction 웹훅만 믿지 말고, balance update 웹훅 + block height 교차검증.

왜 이 모델이 KR 은행 도입에 적합한가

  • 금융감독원 검사 대응 — 각 평면의 audit log 가 분리되어 incident 시 원인 (chain truth? indexer bug? policy?) 추적 용이
  • vendor 교체 안전성 — 평면 1 vendor (Fireblocks → NodeInfra) 가 교체돼도 평면 2/3 의 schema / 워크플로는 그대로
  • 회계 정합성 — 평면 3 의 이중부기는 평면 1/2 의 변동 (reorg) 과 무관하게 보정 가능 (compensating entry)

이 3 평면 모델이 다음 페이지 (S4) "필수인가" 의 답을 갖는다 — 평면 3 은 모든 은행이 필수, 평면 1 은 vendor 가 처리하면 customer 가 안 만들어도 됨.
