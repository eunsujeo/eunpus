0. Overview

블록체인 인덱서가 무엇이고, 왜 필요하고, 어떻게 만드는가

본 가이드는 블록체인 인덱서 의 reference 문서다. 인덱서는 블록체인 데이터를 애플리케이션이 사용할 수 있는 형태로 변환하는 데이터 인프라 레이어다. Coinbase, Korbit, The Graph, Alchemy, QuickNode, Fireblocks 등이 모두 자체 인덱서를 운영하거나 SaaS 형태로 제공한다.

0.1 한 화면으로 보는 인덱서

대부분의 블록체인 애플리케이션 (지갑, 거래소, 분석 도구) 은 다음과 같은 구조를 갖는다. 사용자는 "블록체인" 을 직접 보지 않는다 — 인덱서가 변환해준 데이터를 본다.

0.2 인덱서가 없으면 무엇이 안 되는가

"왜 그냥 RPC 호출만으로 안 되는가?" 가 자주 나오는 질문이다. 답은 4 가지로 요약된다.

영역RPC 만 쓸 때의 한계인덱서가 해결하는 방식
성능 30일 입금 내역 = 블록 216,000 개 스캔. 분 단위 응답. 이미 indexed table 에서 SQL 한 번 = 50ms.
도메인 매핑 "이 주소가 어느 사용자의 지갑인가" 는 chain 이 모른다. address → user / vault / wallet 매핑 자체 DB 보관.
이벤트 push RPC 는 pull. polling 60 초마다 = 최대 60 초 지연. webhook / WebSocket / Kafka 로 1-2 초 push.
Reorg 처리 같은 트랜잭션이 사라지거나 다시 들어옴. 애플리케이션이 직접 대응. 인덱서가 reorg 를 흡수, 애플리케이션은 final state 만 본다.

0.4 핵심 용어 (10초 정의)

용어의미
블록트랜잭션 batch + parent hash. 평균 12 초 (Ethereum) / 10 분 (BTC) 마다 생성.
트랜잭션상태 변경 요청 (token 이동, contract 호출 등). 서명 + nonce + payload.
Mempool아직 블록에 안 포함된 pending 트랜잭션 pool.
JSON-RPC블록체인 노드의 표준 API (HTTP POST). eth_getBalance, eth_getLogs 등.
WebSocket subscribe새 블록 / 새 이벤트 push 받는 채널.
Confirmationtx 가 포함된 블록 뒤로 쌓인 블록 수. 많을수록 reorg 위험 ↓.
SlotEthereum PoS 의 블록 생성 단위 = 12 초. 매 slot 마다 한 validator 가 블록 propose.
EpochEthereum PoS 의 finality 처리 단위 = 32 slots = 384 초 (~ 6.4 분). validator 들이 매 epoch 마다 vote (attestation).
Finality이 시점 이후 reorg 불가능. Ethereum PoS 는 보통 2 epoch (~ 12.8 분) 후 finalized.
Reorgchain head 가 다른 fork 로 교체. confirmed tx 가 사라질 수 있음.
Full node최신 state + 최근 트랜잭션 보관. ~ 1 TB.
Archive node모든 과거 state 보관. ~ 2-20 TB.
EVMEthereum Virtual Machine. smart contract 실행 환경.
Gastx 처리 비용. 사용자가 지불.
Nonce주소 별 tx sequence 번호. 0 부터 +1.
axis(영어 단어) 어떤 것을 보는 관점 / 차원. "8 가지 axis" = "8 가지 관점".
SLOService Level Objective. 시스템이 충족해야 할 측정 가능한 목표 (예: p95 latency < 100ms, 99.9% availability). SLI (지표) 로 측정, SLA (계약) 와 구분.
