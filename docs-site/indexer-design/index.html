블록체인 인덱서 — 수탁형 지갑 설계 가이드

KR 은행이 수탁형 지갑을 만들 때 인덱서가 왜 필요하고, 어떤 역할을 하며, vendor 가 바뀌어도 흔들리지 않는 추상화는 어떻게 만들어야 하는가.

본 사이트는 두 가지 path 로 나뉩니다.

학습 path (S1 ~ S5) 는 vendor 와 무관한 일반 원리. "왜 인덱서가 필요한지" 부터 "수탁형 지갑에서 어떤 역할인지" 까지 단계별로 따라갑니다.

Spec path (Spec 1 ~ 4) 는 KR 은행이 실제로 도입할 때 적용하는 abstraction library 설계 spec. Fireblocks / BitGo / NodeInfra / 자체구축 4 가지 path 모두에서 작동하는 통합 인터페이스를 정의합니다.

기초안내

본 가이드의 등장인물은 한 명입니다.

Alice — KR 은행 X 의 개인 고객. 미국에서 USDC 100 을 받아 KR 은행 X 의 수탁형 지갑으로 입금합니다. 은행 앱을 켜서 잔고를 확인하고, 며칠 후 일부를 다른 사람에게 송금합니다.

Alice 가 보는 모든 숫자 (잔고, 입금 내역, 송금 상태) 의 뒤에는 인덱서 가 있습니다. 인덱서가 없으면 그 숫자들은 존재하지 않습니다 — 또는 너무 느려서 사용할 수 없습니다.

학습 Path — 왜 / 어떻게 / 누가

  • S1 왜 인덱서가 필요한가 Alice 가 잔고를 본다 — RPC 만으로 충분한가?
  • S2 사용 vs 미사용 비교 RPC 만 쓸 때의 5 가지 문제, 인덱서가 해결하는 방식
  • S3 수탁형 지갑에서의 역할 3 평면 분리 — 원시 수집 / 파생 / 원장·워크플로
  • S4 인덱서는 필수인가 use case 별 Must / Should / Optional 분석
  • S5 Vendor 풍경 Fireblocks / BitGo / NodeInfra / 자체구축 의 책임 분담

Spec Path — Abstraction Library 설계

  • Spec 1 추상화 설계 원리 왜 추상화가 필요한가 — vendor lock-in 회피 + 자체구축 path
  • Spec 2 기능 spec Must-have / Should-have / Nice-to-have 분류
  • Spec 3 Vendor adapter 설계 Fireblocks / BitGo / NodeInfra / 자체구축 4 adapter
  • Spec 4 구현 가이드 TypeScript interface + retry + idempotency + reorg + 망분리
심화 · 사용 시 주의

본 사이트는 학습 가이드 + 설계 spec 이지, vendor 공식 문서가 아닙니다. Fireblocks / BitGo / NodeInfra 의 구체 동작은 vendor 공식 docs 와 Solutions Engineer 검증을 최종 source of truth 로 사용하세요.

본 wiki 의 Fireblocks 도입 수탁형 지갑 reference 와 수탁형 지갑 — DB 구조와 상태 흐름 이 함께 활용되도록 설계됐습니다.
