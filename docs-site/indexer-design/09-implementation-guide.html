기초안내

구현 시 신경 써야 할 7 가지 영역:

  1. Idempotency 강제 (모든 deposit / withdrawal 호출)
  2. Retry 정책 (exponential backoff + max 30 일)
  3. Reorg-safe event handling
  4. Capability negotiation 분기
  5. Multi-adapter 운영 (vault → adapter 매핑)
  6. 망분리 환경 적용 (KR 은행 필수)
  7. Audit / observability
다음 단계 — 핵심 구현 패턴

1. Idempotency 강제 — Outbox 패턴

// 모든 deposit / withdrawal 처리는 outbox 거쳐서
async function handleDepositEvent(event: DepositEvent) {
  await db.tx(async (tx) => {
    // ① outbox 에 등록 (idempotency key UNIQUE 제약)
    try {
      await tx.execute(
        `INSERT INTO deposit_outbox (idempotency_key, event_json, status)
         VALUES (?, ?, 'pending')`,
        [event.idempotencyKey, JSON.stringify(event)],
      );
    } catch (e) {
      if (isUniqueViolation(e)) return;  // 이미 처리됨
      throw e;
    }

    // ② 평면 3 의 도메인 워크플로 호출
    if (event.confirmedAt) {
      await creditLedger(tx, event.walletId, event.amount);
    }

    // ③ outbox 상태 완료로
    await tx.execute(
      `UPDATE deposit_outbox SET status='completed' WHERE idempotency_key=?`,
      [event.idempotencyKey],
    );
  });
}

Adapter 에서 같은 event 가 두 번 와도 (Fireblocks webhook 재시도) outbox 의 UNIQUE 제약으로 차단.

2. Multi-adapter 라우팅

class IndexerRouter implements WalletIndexerPort {
  constructor(private adapters: Map<string, WalletIndexerPort>) {}

  async getBalance(walletId: WalletId, asset: Asset) {
    const adapter = await this.resolveAdapter(walletId);
    return adapter.getBalance(walletId, asset);
  }

  private async resolveAdapter(walletId: WalletId) {
    const w = await db.wallet.find(walletId);
    return this.adapters.get(w.adapterName) ?? error('unknown adapter');
  }
}

한 은행이 여러 adapter 동시 운영 가능. wallets.adapter_name column 으로 어느 adapter 가 담당하는지 저장.

3. Capability 분기 — 회계 마감 시

async function getClosingBalance(walletId: WalletId, asset: Asset,
                                  closingBlock: number) {
  const adapter = await router.resolveAdapter(walletId);
  const caps = adapter.capabilities();

  if (caps.supportsBalanceAsOf) {
    return adapter.getBalanceAsOf(walletId, asset, closingBlock);
  }

  // Fallback: 이벤트 합산
  const events = await db.depositEvents.findByWallet(walletId,
    { upToBlock: closingBlock });
  return events.reduce((acc, e) => acc + e.amount, 0n);
}

Retry 정책

const retryPolicy: RetryPolicy = {
  initialDelayMs: 1000,
  maxDelayMs: 60_000,
  backoffMultiplier: 2.0,
  maxAttempts: 7,
  maxDurationMs: 30 * 24 * 60 * 60 * 1000,  // 30일 (Fireblocks v2 기준)
  retryableErrors: ['NETWORK', 'VENDOR_5XX', 'RATE_LIMITED'],
  giveUpAction: 'alert',  // PagerDuty / Slack
};

Fireblocks v2 의 webhook 재시도 정책 (최대 30 일) 과 정렬. 자체구축 path 도 동일 정책 적용 권장.

Reorg-safe ledger 처리

이미 confirmed 처리한 deposit 이 vendor 측 reorg revert 로 사라진 경우:

async function handleDepositRevertEvent(revertEvent: DepositRevertedEvent) {
  await db.tx(async (tx) => {
    // ① 원래 event 찾기
    const original = await tx.depositEvents.find(revertEvent.idempotencyKey);
    if (!original) throw error('reverting unknown deposit');

    // ② 평면 3 의 보정 분개 (compensating entry)
    await reverseLedger(tx, original.walletId, original.amount, {
      reason: 'reorg_revert',
      originalEventKey: revertEvent.idempotencyKey,
      revertedAtBlock: revertEvent.blockNumber,
    });

    // ③ 원래 outbox row 상태 변경
    await tx.depositEvents.markReverted(revertEvent.idempotencyKey);

    // ④ 감사 / 알림
    await audit.log('DEPOSIT_REVERTED', revertEvent);
    await alert.notify('reorg_revert', revertEvent);
  });
}

회계 정합성: 정정 entry 는 새 row 로 기록 (기존 row 수정 ✗). 본 wiki 회계 · 원장 설계 의 reversal entry 패턴.

Migration / vendor 전환 procedure

Phase 1 (Fireblocks 만) → Phase 2 (Fireblocks + NodeInfra 병행) → Phase 3 (NodeInfra 만) 전환:

  1. Phase 2 시작 — 새 vault 는 NodeInfra adapter, 기존 vault 는 Fireblocks adapter. wallets.adapter_name 으로 분기.
  2. Mirror data export — Fireblocks 의 transaction history 를 OwnAdapter 의 mirror DB 로 백필.
  3. 이중 동작 검증 — 새 deposit 이 Fireblocks + NodeInfra 양쪽에서 같은 결과 (cross-check).
  4. Vault migration — 기존 vault 의 자산을 NodeInfra vault 로 sweep. wallets.adapter_name 업데이트.
  5. Fireblocks decommission — Phase 3.

이 procedure 가 가능한 이유: 평면 3 (ledger 워크플로) 의 코드는 단 한 줄도 안 바뀜. 이게 추상화의 정확한 가치.

Testing 전략

  • Adapter contract test — 모든 adapter 는 동일한 contract test suite 통과 필수 (port 의 의미 통일 보장)
  • Mock adapter — 평면 3 단위 테스트 용. Mock 이 실제 adapter 와 같은 contract.
  • Reorg simulation — adapter 가 revert event 를 emit 했을 때 평면 3 의 보정 분개 검증.
  • Idempotency stress — 같은 event 1000 회 반복 emit, 1 회만 처리됐는지 검증.
  • Multi-adapter swap — 같은 vault 에 Fireblocks → Own adapter 로 swap 시 평면 3 결과 일치.

마지막 — 이 abstraction 의 ROI 정리

이 abstraction library 가 만들어주는 것:

  1. Vendor lock-in 회피 — 평면 3 코드는 vendor 무관. 협상력 ↑ / 비용 통제력 ↑
  2. Multi-vendor 동시 운영 — Fireblocks (Hot wallet) + NodeInfra (Cold wallet) + Own (대량 출금 전용) 분산 가능
  3. 회계 / 감사 일관성 — 평면 3 의 evidence chain 이 vendor 무관하게 동일
  4. 점진적 마이그레이션 — vault 단위로 vendor 전환 가능. Big-bang 없음.
  5. 자체구축 path 보호 — 사업 성장 시 sovereignty 확보 (대형 거래소 / 큰 은행 전환 가능)
