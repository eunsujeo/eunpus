SPEC 1 · LIBRARY DESIGN

추상화 설계 원리

Fireblocks / BitGo / NodeInfra / 자체구축 4 path 모두에서 작동하는 single library — adapter pattern + ports & adapters 아키텍처.

기초안내

이 abstraction library 의 한 줄 요약:

"평면 3 (원장 · 워크플로) 의 코드가 vendor 와 무관하게 동작하도록, 평면 1, 2 를 통일된 interface 뒤에 숨긴다."

이름은 WalletIndexerPort 라고 하자. 어떤 vendor 를 쓰든 WalletIndexerPort 의 같은 method 를 호출하면 같은 의미의 결과가 돌아온다.

다음 단계 — Alice 입금 시 코드 비교

추상화 없이 Alice 의 입금을 처리하는 코드:

// Vendor lock-in 코드
if (vendor === 'fireblocks') {
  const webhook = parseFireblocksWebhook(req.body);
  if (verifyJWKS(webhook.signature)) {
    if (webhook.type === 'TRANSACTION_CREATED' &&
        webhook.data.status === 'CONFIRMED') {
      await creditBalance(webhook.data.destination.id,
                          webhook.data.amount);
    }
  }
} else if (vendor === 'bitgo') {
  const event = parseBitGoEvent(req.body);
  // 완전히 다른 schema...
} else if (vendor === 'nodeinfra') {
  // 또 다른 schema...
}

추상화 있을 때:

// Vendor-agnostic 코드
const event: DepositEvent = await indexerPort.nextDepositEvent();
if (event.confirmedAt) {
  await creditBalance(event.walletId, event.amount);
}

코드의 본질이 다르다. 위는 "Fireblocks 의 어떤 webhook type 인가" 라는 vendor schema 의 문제. 아래는 "deposit 이 confirmed 됐는가" 라는 도메인 의 문제.

심화 · 설계 원리 5 가지

1. Hexagonal architecture (Ports & Adapters)

평면 3 (도메인) 이 중심에 있고, 평면 1, 2 (vendor 측) 는 외부. 그 사이를 Port (인터페이스) 가 분리.

┌─────────────────────────────────────────────────────┐
│   평면 3 — 원장 · 워크플로 (DOMAIN, vendor 무관)      │
│                                                       │
│   - creditBalance(walletId, amount)                  │
│   - submitWithdrawal(walletId, dest, amount)         │
│   - reconcileLedger(asOfBlock)                       │
│                                                       │
└──────────────────┬──────────────────────────────────┘
                   │ depends on
                   ▼
        ┌──────────────────────────┐
        │ WalletIndexerPort        │  ← 추상 인터페이스
        │   .nextDepositEvent()    │
        │   .getBalance(walletId)  │
        │   .getConfirmations(tx)  │
        │   .submitTransaction()   │
        │   .registerWallet()      │
        └──────────┬───────────────┘
                   │ implemented by
        ┌──────────┴──────────┬─────────┬────────────┐
        ▼                     ▼         ▼            ▼
  ┌──────────┐         ┌──────────┐ ┌─────────┐ ┌─────────┐
  │Fireblocks│         │  BitGo   │ │NodeInfra│ │  Own    │
  │ Adapter  │         │ Adapter  │ │ Adapter │ │ Adapter │
  └──────────┘         └──────────┘ └─────────┘ └─────────┘

2. 의미 통일 — "Confirmed" 의 정의

각 vendor 의 "confirmed" 의 의미가 다르다. Adapter 의 첫 번째 책임 = 의미 통일.

VendorVendor 측 "confirmed" 의미Port 의 통일 정의
FireblocksDCCP 정책에 따라 chain 별 N-confirmation 도달 시 status = `COMPLETED`"은행 정책 confirmation policy 충족 + AML 통과 + reorg risk acceptable"
BitGoVendor 의 default confirmation policy
NodeInfraVendor 측 정책 또는 customer 측 정책
자체구축Customer 가 직접 결정

Port 의 DepositEvent.confirmedAt 는 위 통일 정의 의 시점. 평면 3 은 이 시점에서만 잔고를 반영하면 된다.

3. Idempotency 강제

모든 event 는 idempotency key 를 가진다. Port 의 모든 method 가 같은 key 로 두 번 호출되면 같은 결과.

interface DepositEvent {
  idempotencyKey: string;  // e.g., "fb:tx:abc123" 또는 "btc:hash:def456:vout:0"
  walletId: WalletId;
  asset: Asset;
  amount: BigInt;
  txHash: string;
  blockNumber: number;
  confirmedAt: Date | null;  // null = pending
}

Vendor 별 idempotency key 생성 규칙:

  • Fireblocks — webhook 의 data.id (Fireblocks transaction ID)
  • BitGo — BitGo 의 internal tx ID
  • NodeInfra — vendor 측 unique ID
  • 자체구축 — {chainId}:{txHash}:{logIndex} 직접 생성

4. Reorg-safe event ordering

Adapter 가 vendor 측 reorg 처리를 흡수해 final event 만 도메인에 전달. 평면 3 은 reorg 의 존재를 모르고 작동.

예외: 이미 confirmed 처리된 event 가 vendor reorg 로 reverted 된 경우 — Port 가 별도의 DepositRevertedEvent 를 emit. 평면 3 은 compensating entry (반대 분개) 로 보정.

5. Capability negotiation

모든 vendor 가 모든 기능을 지원하진 않는다. Adapter 는 자신의 capability 를 명시:

interface AdapterCapabilities {
  supportsWebhook: boolean;
  supportsBatchWithdrawal: boolean;
  supportsCustomConfirmationPolicy: boolean;
  supportedChains: ChainId[];
  internalTxDetection: 'trace_api' | 'log_only' | 'none';
}

평면 3 은 startup 시 indexerPort.capabilities() 를 호출하여 — 지원 안 되는 기능 사용 시 명시적 fallback 또는 에러.

왜 이게 KR 은행 도입에 맞는가

  • Phase 1 출시 — Fireblocks adapter 만 구현. 빠른 출시 (3 개월).
  • Phase 2 망분리 강화 — NodeInfra adapter 추가. 평면 3 코드 변경 ✗.
  • Phase 3 자체구축 — Own adapter 추가. 평면 3 코드 변경 ✗. 일부 vault 만 own, 나머지는 Fireblocks 유지 (multi-vendor).
  • 회계 / 감사 일관성 — 평면 3 은 vendor 변경 무관하게 동일 evidence chain 생성.
