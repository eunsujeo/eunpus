왜 인덱서가 필요한가

Alice 가 USDC 100 을 받았다. 은행 앱을 켜면 잔고가 보인다. 그 사이에 무엇이 있는가.

기초안내

블록체인은 "원장" 이다. Alice 가 받은 USDC 가 실제로 있는 곳은 Ethereum 의 블록 N 의 트랜잭션 T. 은행 앱이 그 숫자를 직접 가져오려면 매번 블록체인 노드에 RPC 호출을 해야 한다.

그런데 Alice 의 잔고 화면 하나에 필요한 정보는 — 입금 내역 / 현재 잔고 / 진행 중인 출금 / 환산 KRW. 이걸 RPC 만으로 만들면 1 화면에 수십 번의 RPC 호출 이 일어나고, 그 중 일부는 (예: 과거 입금 내역) 분 단위로 걸린다.

인덱서가 이 문제의 해답이다. 인덱서는 블록체인의 truth 를 빠르게 조회 가능한 DB 로 미리 변환 해두는 계층이다.

다음 단계 — Alice 의 시나리오

14:00 (UTC) — Alice 의 친구가 미국 거래소에서 USDC 100 을 Alice 의 입금 주소 0x1234...abcd 로 전송. 트랜잭션이 Ethereum mempool 에 들어감.

14:00:15 — 트랜잭션이 블록 N 에 포함되어 mined. 블록체인 truth = "주소 0x1234 의 USDC 잔고 + 100".

14:00:18 — Alice 가 KR 은행 앱을 켠다.

이 시점에 앱이 화면 하나를 그리려면 다음 질문에 답해야 한다.

  1. 이 사용자의 입금 주소가 어떤 vault 의 어떤 wallet 에 속하는가? (mapping)
  2. 그 wallet 의 현재 잔고는? (balance)
  3. 최근 30 일 입금 내역은? (history)
  4. 방금 들어온 USDC 100 의 confirmation 수는? (status)
  5. USDC 100 의 현재 환산 KRW 는? (price feed)
  6. 진행 중인 출금이 있는가? (pending)
  7. AML/sanctions 검증은 통과했는가? (compliance)

이 7 가지를 모두 블록체인 RPC 호출만으로 만들면 — 1 번에는 자체 DB 매핑이 필요하고, 2-4 번은 eth_getBalance + eth_getTransactionByHash + eth_getTransactionReceipt 등 여러 번 호출, 3 번 (30 일 history) 은 30 일치 블록 모두 스캔 이라는 의미가 된다. 응답 시간 = 수 분.

심화 · 운영 디테일

왜 RPC 만으로는 부족한지의 4 가지 본질적 이유:

1. 성능 — 블록체인 데이터는 순차적

블록체인 데이터는 본질적으로 순차적 + 분산. 다중 블록 / 과거 상태 / 집계 질의를 직접 RPC 로 수행하면 느리고 비쌈. Polkadot 공식 문서: "복잡한 교차 블록 질의는 수일 ~ 수주 걸릴 수 있다."

2. UX — "지금 막" + "역사 전체" 동시 요구

지갑 UI 는 실시간 알림 (방금 들어온 입금) 과 역사 집계 (지난 30 일 출금 합) 를 동시에 보여줘야 한다. 인덱서가 없으면 둘은 별개 시스템이 된다.

3. 데이터 접근성 — 원시 RPC ≠ 도메인 schema

Ethereum 의 JSON-RPC 는 "트랜잭션 raw bytes" 단위로 답한다. "Alice 의 USDC 입금 내역" 같은 도메인 query 는 추가 변환 + 인덱싱 없이는 불가능.

4. 분산성 — 외부 RPC 의존도 vs 자체 운영 비용

이 axis 는 양날의 검. 인덱서를 잘 설계하면 외부 호스티드 RPC 의존도가 낮아지고, 잘못 설계하면 vendor 한 곳에 모든 데이터 권력이 집중된다. 인덱서 전략 = 위험 모델 + 신뢰 모델의 일부, 단순 성능 문제가 아니다.

요약

Alice 의 잔고 화면 하나가 빠르게 그려지는 것은 은행 시스템 안에 미리 만들어진 read model 이 있기 때문. 그 read model 을 만들고 유지하는 계층이 인덱서다. 다음 페이지에서 인덱서 없이 만들면 어떤 문제가 생기는지 구체적으로 본다.
