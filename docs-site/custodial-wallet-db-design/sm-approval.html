16. Approval State Machine (TAP(?))

Policy 3 action · first-match · Unanimous-Veto(?) · 3-tier governance · 5 default policies
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 3 Action Semantics: Allow (자동 승인) · Approved by (지정된 user/group 승인) · Block (차단)
  • First-Match Principle: top-to-bottom scan + 첫 match 에서 중단 · 모든 Policy 의 마지막 rule = block-all (default-deny)
  • Rule Ordering: time-period rule 이 single-tx rule 보다 앞 · overlap 시 더 strict 한 rule 이 앞
  • Approvers Unanimous-Veto Rule: 1 명 reject = 즉시 REJECTED (다수결 아님)
  • 3-Tier Governance: Admin Quorum (workspace-level) → Approval Group (action-level 위임) → Policy "Approved by" sub-quorum (rule-level)
  • 5 Default Policy Rules: 신규 workspace 자동 적용 — Transfer 1/2 (whitelisted NFT/USD), Contract Call (whitelisted contract), Approve (Web3 Approve), All Policies block-all
  • Custom Policy 도입 = default 즉시 삭제 (one-way replacement). 모든 custom 삭제 시 default 복원

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • approval_requests · approval_decisions 두 테이블의 구체 schema
  • approval_requests.subject_type ENUM 의 6 값 정형화 (tx / add_user / edit_user / policy_change / admin_quorum_change / whitelist_address)
  • approval_decisions.mobile_device_sig 의 BLOB 형식 — Fireblocks 내부 mobile-signed bytes
  • finalized_at set-once + Sticky Terminal 패턴 (BEFORE UPDATE trigger 강제)

3 Action Semantics — Policy rule 의 3 action

Policy rule 매칭 시 발효되는 action 은 3 종 — 단순한 통과 / 추가 승인 요청 / 차단.

Action의미State 전이
Allow자동 approve → designated signer 로 forwardSUBMITTED → QUEUED (PENDING_AUTHORIZATION 우회)
Approved by지정 user / user group 이 approve / deny. 모든 associated role 이 authorized approver 여야 함SUBMITTED → PENDING_AUTHORIZATION (collecting)
Block자동 차단SUBMITTED → BLOCKED (violated rule number 표시)

First-Match Principle

  • Policy 를 top-to-bottom scan
  • 첫 match 에서 scan 중단 + action 실행
  • 모든 Policy 의 마지막 rule = block-all (default, 삭제 불가) → default-deny architecture

Rule Ordering (most restrictive first)

  • Time-period based rule 먼저 (cumulative limit 가 single-tx rule 보다 앞)
  • Overlap 시 더 strict 한 rule 먼저 (예: $10M+ 2-approval rule 이 $1M+ 1-approval 보다 앞)

Approval State Machine

stateDiagram-v2
  [*] --> EVALUATING : tx submitted
  EVALUATING --> AUTO_APPROVED : action = Allow
  EVALUATING --> COLLECTING : action = Approved by
  EVALUATING --> BLOCKED : action = Block (rule violation)
  EVALUATING --> BLOCKED : no rule match (default block-all)

  COLLECTING --> APPROVED : threshold met
  COLLECTING --> REJECTED : 1 reject (Unanimous-Veto)
  COLLECTING --> EXPIRED : 2h timeout (PENDING_AUTHORIZATION)
  COLLECTING --> EXPIRED : 7-day timeout (Add user flow)

  AUTO_APPROVED --> [*]
  APPROVED --> [*]
  REJECTED --> [*]
  BLOCKED --> [*]
  EXPIRED --> [*]

⚠️ Approvers Unanimous-Veto Rule

transaction-lifecycle.md, p.6 직접 인용:

"If at least one person chooses to reject a transaction, the transaction is rejected."

Approval group 의 N 명 중 1 명이라도 reject 하면 즉시 fail. 다수결이 아니라 만장일치 (unanimous) 필수 — 한 명의 거부권이 곧 veto.

3-Tier Governance — 거버넌스 3 계층

승인 메커니즘이 한 가지가 아니라 3 단계 위계로 작동합니다. 위에서 아래로 갈수록 더 작은 범위에 위임:

Admin Quorum  (workspace-level default)
  └── Approval Group  (action-level 위임, 12 actions)
        └── Policy "Approved by" sub-quorum  (rule-level 위임, user group 기반 N-of-M)

Fireblocks 의 how-policies-work.md, p.4 직접 인용:

"you can also define approval quorums within a group as part of the Approved by action... requires any two members of a user group called Management to approve."

즉 같은 Policy 안에서도 rule 마다 다른 group + 다른 threshold (N-of-M) 를 지정 가능. workspace 의 Admin Quorum 과 별개로 정밀 통제.

5 Default Policy Rules — 신규 workspace 의 출발선

모든 신규 workspace 가 자동 적용받는 5 가지 default rule:

  1. Transfer Policy 1: Allow NFT transfer → whitelisted address
  2. Transfer Policy 2: Allow 모든 USD amount, 모든 asset → whitelisted address
  3. Contract Call Policy: Allow contract call → whitelisted smart contract
  4. Approve Policy: Allow Web3 Approve tx
  5. All Policies (마지막, 삭제 불가): Block any tx not explicitly allowed

→ Custom Policy 도입 = default 즉시 삭제 (one-way replacement). Custom 전부 삭제 시 default 복원.

DB Schema

6.1 approval_requests — 승인 요청 본체

CREATE TABLE approval_requests (
  id                  BINARY(16) PRIMARY KEY,
  workspace_id        BINARY(16) NOT NULL,
  subject_type        ENUM('transaction','add_user','edit_user','policy_change','admin_quorum_change','whitelist_address') NOT NULL,
  subject_id          BINARY(16) NOT NULL,
  matched_rule_id     BINARY(16),                       -- first-match rule
  action              ENUM('allow','approved_by','block') NOT NULL,
  state               ENUM('EVALUATING','COLLECTING','AUTO_APPROVED','APPROVED','REJECTED','BLOCKED','EXPIRED') NOT NULL,
  threshold           INT,                              -- N of M
  collected_approvals INT NOT NULL DEFAULT 0,
  created_by          BINARY(16) NOT NULL,              -- 요청 시작한 user
  created_at          DATETIME(6) NOT NULL,
  expires_at          DATETIME(6) NOT NULL,             -- 2h (tx) / 7-day (add_user)
  finalized_at        DATETIME(6),                      -- ★ set-once
  KEY (workspace_id, state),
  KEY (expires_at)
);
컬럼자료형역할
idBINARY(16) PK요청의 고유 식별자
workspace_idBINARY(16) FK요청이 속한 workspace
subject_typeENUM (6 값)승인 대상의 종류. transaction tx 승인 / add_user·edit_user 사용자 관리 / policy_change Policy 변경 / admin_quorum_change Quorum 자체 변경 / whitelist_address 화이트리스트 등록
subject_idBINARY(16)승인 대상의 id (해당 subject_type 에 맞는 테이블 row)
matched_rule_idBINARY(16) nullable FKfirst-match 로 매칭된 policy_rules 의 id (tx 의 경우). 다른 subject_type 은 NULL
actionENUM (3 값)매칭된 rule 의 action — Allow (즉시 통과) / Approved by (승인 수집) / Block (차단)
stateENUM (7 값)승인 state machine 의 현재 상태. EVALUATING → (분기) → 종착. Figure 7 참조
thresholdINT nullableN-of-M 의 N. action='approved_by' 일 때만 set
collected_approvalsINT현재까지 누적된 approve 결정 수 — threshold 와 비교해서 APPROVED 도달 여부 판단
created_by · created_atBINARY(16) · DATETIME(6)요청 시작한 user + 시각. set-once
expires_atDATETIME(6)만료 시각. tx 는 2h, add_user 는 7-day. scheduled job 이 만료된 row 를 EXPIRED 로 전이
finalized_atDATETIME(6) nullable종착 상태 (APPROVED / REJECTED / BLOCKED / EXPIRED / AUTO_APPROVED) 도달 시각. set-once + Sticky Terminal — 이후 state 변경 불가 (BEFORE UPDATE trigger 강제)

6.2 approval_decisions — 개별 approver 의 결정 (append-only)

-- ★ append-only — 한 번 결정한 row 는 절대 변경/삭제 안 됨
CREATE TABLE approval_decisions (
  id                BINARY(16) PRIMARY KEY,
  request_id        BINARY(16) NOT NULL,
  approver_user_id  BINARY(16) NOT NULL,
  decision          ENUM('approve','reject') NOT NULL,
  mobile_device_sig BLOB NOT NULL,                    -- ★ set-once, append-only
  decided_at        DATETIME(6) NOT NULL,
  UNIQUE KEY (request_id, approver_user_id)           -- 1 user = 1 decision per request
);
컬럼자료형역할
idBINARY(16) PK결정 이벤트의 고유 식별자
request_idBINARY(16) FK이 결정이 속한 approval_requests
approver_user_idBINARY(16) FK결정한 approver
decisionENUM (2 값)approve 또는 reject. Unanimous-Veto Rule 에 의해 reject 1 개로 즉시 전체 REJECTED
mobile_device_sigBLOBapprover 의 mobile device 에서 MPC share 로 서명한 bytes. byte-equal cross-DB binding (audit 평면과 일치) + set-once + append-only — 결정을 사후 바꿀 수 없음
decided_atDATETIME(6)결정 시각
UNIQUE (request_id, approver_user_id)—한 approver 가 같은 request 에 두 번 결정 불가
Sticky Terminal · Set-once · Append-only — 변경 불가성 강제

승인 평면의 핵심 audit 속성은 "결정한 것은 절대 바꿀 수 없다" 입니다. 세 가지 trigger 가 협업:

  • Sticky Terminal: approval_requests.state 가 종착 상태 (APPROVED / REJECTED / BLOCKED / EXPIRED / AUTO_APPROVED) 도달 시 BEFORE UPDATE trigger 가 이후 모든 state 변경 거부
  • Set-once: finalized_at, mobile_device_sig 같은 audit-critical 컬럼은 NULL → 값 한 번만 허용
  • Append-only: approval_decisions 전체 — 한 번 INSERT 된 row 는 UPDATE / DELETE 절대 불가
