8. 9 User Role Permission Matrix

9 role × initiate / approve / sign / MPC(?) 키 보유 + 5 라벨 vocabulary
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 9 가지 role: Owner · Admin · Non-Signing Admin (NSA) · Signer · Approver · Editor · Viewer · Security Auditor · Security Admin
  • 각 role 의 4 가지 권한 동사 보유 여부: initiate (작업 시작) · approve (승인) · sign (서명) · MPC key 보유
  • 5 라벨 vocabulary: Q (Admin Quorum 승인 필요) · Q+O (Quorum + Owner) · AG (Approval Group) · NS (designated signer 필수) · TL (token wallet 생성 제약)
  • Owner 의 특수성: workspace 당 1 명 · Fireblocks Support 영상 통화로만 임명 · MPC key provisioning 단독 권한 · 2FA reset / device 재등록 / role transfer 모두 Support 경유
  • NSA / Editor 의 designated signer 패턴: MPC key 가 없어도 Policy 가 designated signer 를 지정한 경우 initiate 가능

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • roles · role_permissions 두 테이블의 schema (Fireblocks 자료는 표 형태이고 schema 는 명시 없음)
  • role_id 를 VARCHAR(32) 자유 텍스트가 아니라 ENUM 9 값으로 정형화하는 것도 가능 (운영 선호)
  • role_permissions.label 의 ENUM 7 값 (Y / N / Q / Q+O / AG / NS / TL) 정형화

ERD(?) — Governance & Policy 평면의 관계

8. Role + 9. Admin Quorum + 10. Policy · TAP 의 11 테이블이 어떻게 묶이는지. 이 cluster 는 workspace → vault → wallet 같은 hierarchy 가 아니라 workspace 의 governance 평면 — 누가 무엇을 할 수 있는지 (role) · 누가 모여서 결정하는지 (admin_quorum / approval_group) · 무엇이 차단되는지 (policy) 의 3 축으로 구성됩니다.

DB Schema

3.1 roles — 9 개 정적 lookup

-- 권한 매트릭스를 정적 lookup 으로 둠 (9 개 row, 수정 빈도 거의 0)
CREATE TABLE roles (
  id            VARCHAR(32) PRIMARY KEY,  -- 'owner', 'admin', 'nsa', 'signer', ...
  name          VARCHAR(64) NOT NULL,
  holds_mpc_key BOOLEAN NOT NULL,
  can_initiate  BOOLEAN NOT NULL,
  can_approve   BOOLEAN NOT NULL,
  can_sign      BOOLEAN NOT NULL,
  can_participate_in_admin_quorum BOOLEAN NOT NULL
);
컬럼자료형역할
idVARCHAR(32) PKrole 식별자 (예: owner, admin, nsa, signer, approver, editor, viewer, security_admin, security_auditor). users.role_id 가 FK 로 참조
nameVARCHAR(64)사람이 읽는 정식 이름 (예: "Non-Signing Admin")
holds_mpc_keyBOOLEAN이 role 의 사용자가 MPC key share 를 보유하는지. 위 9 Role 표의 "MPC 키" 컬럼
can_initiateBOOLEANtx / user 변경 등 작업을 시작할 수 있는지
can_approveBOOLEAN승인 단계에서 yes/no 를 줄 수 있는지
can_signBOOLEANMPC 서명에 참여할 수 있는지
can_participate_in_admin_quorumBOOLEANAdmin Quorum 의 member 가 될 자격이 있는지

3.2 role_permissions — 세부 action 별 라벨 매트릭스

CREATE TABLE role_permissions (
  role_id    VARCHAR(32) NOT NULL,
  action     VARCHAR(64) NOT NULL,  -- 'add_user', 'change_policy', 'delete_user', ...
  label      ENUM('Y', 'Q', 'Q+O', 'AG', 'NS', 'TL', 'N') NOT NULL,
  PRIMARY KEY (role_id, action),
  FOREIGN KEY (role_id) REFERENCES roles(id)
);
컬럼자료형역할
role_idVARCHAR(32) FK위 roles 의 id 참조
actionVARCHAR(64)구체 action 이름 (예: add_user, change_policy, delete_user, add_whitelisted_address 등). 권한표의 각 행에 해당
labelENUM (7 값)Y 단독 허용 / N 불허 / Q Admin Quorum 필요 / Q+O Quorum + Owner / AG Approval Group / NS designated signer 필수 / TL 특정 chain (Algorand · Ripple · Solana · Stellar) 의 token wallet 생성 제약
PRIMARY KEY (role_id, action)—같은 role 의 같은 action 중복 등록 방지

Owner 의 특수성

  • 임명: Fireblocks Support 영상 통화 신원 확인만
  • Provision MPC signing keys 권한 단독
  • Workspace(?) 당 1명 unique — DB UNIQUE constraint
  • Transfer Owner: Console 자체로 불가, Support 경유. 부재 시 Board resolution + stakeholder quorum 으로 지명
  • 2FA reset / device 재등록 / role transfer 모두 Fireblocks Support 영상 통화 필수

NSA / Editor 의 Designated Signer 패턴

NSA 와 Editor 는 MPC key 가 없는 role 이지만, Policy 가 designated signer (서명 책임자) 를 지정한 transaction 타입에서는 자기는 서명 안 하고도 tx 를 initiate 할 수 있습니다 — 시작 → 다른 사람이 서명. 단 internal exchange transfer (workspace 내부의 거래소 계정 간 이동) 같은 일부 type 은 이 패턴에서 제외. 자세히는 10. Policy · TAP(?) 의 NS 라벨 절.
