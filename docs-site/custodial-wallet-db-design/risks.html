23. Risks Register

Fireblocks 자료에서 명시된 10 가지 risk + DB 설계상 mitigation
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 아래 10 가지 risk 각각이 Fireblocks 의 운영/보안 문서에 명시되어 있음 (운영팀이 사전에 인지해야 할 영역)
  • 각 risk 의 본질적 원인 — Owner SPOF · passphrase loss · API credential exposure · device 분실 · DR online execution · co-signer compromise · EVM nonce · BTC 25-chain · BCM 자격 차이 · incoming reject lock

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • 각 risk 의 Severity 등급 — Fireblocks 가 공식 등급을 매기지 않음, 본 페이지가 운영 우선순위 결정에 도움 되도록 추정 부여
  • risk_markers 테이블의 schema — risk 상태를 추적·해소까지 audit 하는 패턴
  • owner_recovery_events 같은 mitigation 의 DB 표현 (Fireblocks 자체 구현은 미명시)

Risk Catalog — 10 가지 운영 risk

Fireblocks 운영에서 사전 인지·대비가 필요한 risk 목록. Severity 는 운영 우선순위 (저자 추정), DB-level mitigation 은 본 docs-site 의 schema 가 어떻게 그 risk 를 추적·완화하는지.

RiskSeverityDB-level mitigation
Owner SPOF — 2FA(?) reset · device 재등록 · Owner transfer 모두 Fireblocks Support 영상 통화 필수 (Console 불가). Owner 한 명에게 의존하는 single point of failure🔴 Criticalowner_recovery_events append-only(?) log + multi-admin escalation procedure
Recovery passphrase 분실 — passphrase 분실 시 cloud backup 해독 불가, key share 영구 손실 가능🔴 Critical월 1회 periodic verification (Owner/Admin/Signer) + 3-fail lockout. DB 에는 passphrase 자체 저장 안 함 (forbidden storage)
API credential 노출 — API key 또는 CSR(?) private key 노출 시 자동 서명. 도난된 자격증명이 인터넷 어디서나 사용 가능🔴 CriticalIP allowlist (/32 CIDR 만) + immediate revoke (Owner 즉시) + audit log
Mobile device 분실 — Primary MPC(?) key share 손실. 재등록 절차 진행 중 운영 정체🟠 HighRe-enroll device (2-day window × 2 단계 — Owner + 사용자) + recovery from cloud backup. 일반 user 는 재발급 가능, Owner 는 별도 절차
SPOC(?) at DR — Disaster Recovery 절차가 online machine 에서 실행되면 private key "considered exposed and compromised". 한 번의 실수가 key compromise🔴 CriticalDR Recovery Utility 는 offline-only 강제 — 4 secrets 모두 air-gapped 머신 2 대 환경에서만 사용. recovery_events.air_gapped_machine_*_attested 컬럼이 schema 차원에서 attestation 기록
Co-signer compromise — Customer 측 key share 가 compromise 되어도 Fireblocks 의 safeguards 가 작동 (single failure 가 즉시 자금 손실로 이어지지 않음)🟠 HighFireblocks 의 safeguards — Policy enforcement (tx amount threshold · destination integrity 검증) 가 customer share 손상에도 차단 역할
EVM(?) nonce(?) 충돌 — 동시 withdrawal 시 nonce gap → 후속 tx 전부 stuck. transactions.chain_nonce 컬럼이 stuck detection 의 schema-level key🟡 MediumMultiple withdrawal vault round-robin + nonce 직렬화 (vault account(?) 단위). 5. Wallet 의 round-robin 도식 참조
Canton OFFER orphan — 2-step transfer 의 OFFER 가 ACCEPT/REJECT/WITHDRAW 없이 무기한 pending. recipient 가 응답 안 하면 자금 lock 상태 지속🟡 Mediumtransactions.canton_action='OFFER' + state='Pending 3rd Party' 의 timeout 정책 + scheduled job 이 만료된 OFFER 를 자동 WITHDRAW (sender 가 회수)
Relay vault 고갈 — Gasless / sponsored tx 의 relay (Gas Station 또는 third-party) 의 fee asset 잔액 부족 시 모든 sponsored tx 가 fail. relay 가 same-tenant 면 자산 충전, third-party 면 contract 재협상 필요🟡 Mediumtransactions.paid_by_relay=true + relay_vault_id 별 balance threshold monitoring. Gas Station 의 gasThreshold alert 와 동일 패턴. relay_type='THIRD_PARTY' 의 경우 별도 escalation lane
MEV routing bypass — routing_type='MEV' 가 보장이 아니라 best-effort. Private mempool 이 거부하면 public mempool 로 fallback 되면서 MEV bot 노출 가능. broadcasting 시 customer 가 routing 보장 받지 못함🟡 Mediumtx-level routing audit + MEV 실패 시 alert. broadcast_attempts 에 actual mempool path 기록. high-value tx 는 NODE_ROUTER 로 customer-controlled node 사용 권장
Bitcoin 25-chain limit — unconfirmed input chain 이 25 개 도달 시 추가 tx 차단 (Bitcoin Core default policy)🟡 MediumMultiple withdrawal vault + 사전 confirmation 대기. EVM 의 nonce 와 비슷한 chain-side bottleneck
BCM dependency — Hosted MPC customer 만 BCM (Business Continuity Module) 자격 — SaaS-only 는 BCM 불가🟡 MediumSaaS customer 는 mobile + 2 Fireblocks share 의 가용성에 의존. Fireblocks 인프라 장애 시 영향. Hosted MPC variant 로 이전 시 BCM 적용
Incoming rejected freeze — Incoming tx 가 AML 거절 시 자산이 chain 상 도착해 있지만 Admin unfreeze 까지 lock. 잘못된 차단 시 자금 회수까지 시간 소요🟡 MediumAdmin escalation path + unfreeze audit. 22. AML 의 rejected_incoming_assets 테이블이 lock 추적 + Admin 의 unfreeze 결정 기록

DB Schema — risk_markers

위 risk 들의 상태를 workspace 단위로 추적하는 운영 테이블. risk 가 감지되면 row INSERT, 해소 시 resolved_at SET — Open risk 의 visibility 확보 + 운영팀의 우선순위 결정 자료.

CREATE TABLE risk_markers (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  risk_type       VARCHAR(64) NOT NULL,  -- 'owner-spof', 'passphrase-stale', ...
  severity        ENUM('low','medium','high','critical') NOT NULL,
  detected_at     DATETIME(6) NOT NULL,
  detected_by     BINARY(16) NOT NULL,
  resolved_at     DATETIME(6),
  resolved_by     BINARY(16),
  resolution_note TEXT,
  KEY (workspace_id, risk_type, severity)
);
컬럼자료형역할
idBINARY(16) PKrisk marker 의 고유 식별자
workspace_idBINARY(16) FKrisk 가 속한 workspace
risk_typeVARCHAR(64)위 catalog 의 10 가지 risk type (예: owner-spof, passphrase-stale, api-credential-exposed). 운영 시 ENUM 으로 정형화 권장
severityENUM (4 값)위 catalog 의 Severity 컬럼 — low / medium / high / critical
detected_at · detected_byDATETIME(6) · BINARY(16)risk 가 감지된 시각 + 감지한 actor (운영팀 / 자동 system check). set-once
resolved_at · resolved_byDATETIME(6) nullable · BINARY(16) nullablerisk 가 해소된 시각 + 해소한 actor. NULL = 여전히 open. set-once when set
resolution_noteTEXT nullable해소 과정에 대한 자유 텍스트 기록 — audit 시 무엇을 어떻게 처리했는지 확인용
