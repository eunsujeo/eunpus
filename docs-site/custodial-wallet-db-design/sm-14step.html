15. 14-Step Transaction Flow

tx 가 user 입력부터 chain broadcast 까지 거치는 14 단계 + 각 step 의 DB row 매핑
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 14 step: User tx request → JWT 검증 → balance / AML / Travel Rule → Policy Engine → Secure Vault → Co-Signer ceremony → broadcast 의 canonical 흐름
  • SGX 격리 서비스 4 종: Auth Engine · Policy Engine · Secure Vault · Co-Signer Engine — 모두 Azure SGX enclave 안에서만 동작
  • Co-Signer 분포: Co-Signer 1/2 = Fireblocks SGX, Co-Signer 3 = customer-side
  • Zero-trust handoff: 모든 service-to-service 호출에 derived cert 검증 — internal network 라도 매번 신뢰 재확인
  • Step 10 의 Callback Handler 가 attached 인 경우 외부 검증 callback 가능 (optional)

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • 각 step 의 DB row 매핑 (오른쪽 표) — Fireblocks 가 정확히 어느 service 가 어느 row 를 만드는지는 미명시, 본 매핑은 14-step 흐름 + 다른 페이지의 schema 를 종합한 추정
  • service_handoff_events 테이블 패턴 — zero-trust handoff 의 audit event 화 (Fireblocks 가 내부적으로 어떻게 영속화하는지는 미명시)

Zero-Trust Handoff 가 DB 에 미치는 영향

각 service handoff 마다 derived cert 검증 — service-to-service 호출 자체가 audit event. service_handoff_events 테이블 (append-only) 에 from_service / to_service / cert_chain_hash / occurred_at 기록.
