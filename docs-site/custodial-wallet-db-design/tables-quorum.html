9. Admin Quorum(?) · Approval Group(?)

Q · Q+O · AG 라벨의 영속화 + Owner counting rule + 7-day expiry
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • Admin Quorum: workspace 당 1 개. Owner / Admin / NSA / Security Admin 4 role 이 멤버 자격. threshold N-of-M 으로 다수결 승인
  • Owner Counting Rule: Q / Q+O 흐름에서 Owner 의 승인은 mandatory + threshold count 에 포함될 수 있음
  • Approval Group (AG): 일부 작업을 Owner 없이 위임 가능. Settings 에서 작업별 Owner 요구 토글
  • 7-day expiry: Add user 같은 요청은 mobile 로 Owner + Quorum 에 전달, 7 일 안에 threshold 미충족 시 자동 expire
  • Edit user 는 Approval groups 로 흐름 customize 가능 (정확한 범위는 자료 미명시)

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • admin_quorums · admin_quorum_members · approval_groups · approval_group_members 의 구체 schema
  • approval_groups.action 을 VARCHAR 자유 텍스트로 둔 선택 (ENUM 으로 정형화 가능)
  • 7-day expiry 를 approval_requests.expires_at 컬럼 + scheduled job 으로 강제하는 패턴 — 실제 Fireblocks 내부 구현은 다를 수 있음

Admin Quorum — workspace 의 의사결정 정족수

회사의 이사회 정족수 (quorum) 개념을 그대로 옮긴 것. 어떤 결정 — 예: 신규 사용자 추가, Policy 변경, Whitelist 등록 — 은 한 명의 관리자가 단독으로 못 하고 여러 관리자가 동의해야 진행됩니다. 그 "여러 명" 을 정의하는 것이 Admin Quorum.

구성 — workspace 당 정확히 1 개의 quorum 이 있고, 그 안에 멤버 사용자들이 포함됩니다. 멤버 자격은 Owner · Admin · NSA · Security Admin 4 role 만 (sign / viewer / auditor 등은 멤버가 될 수 없음). Threshold 는 N-of-M 형태 — 예: "5명 중 3명 승인" / "10명 중 5명 승인".

1.1 admin_quorums — workspace 의 quorum 설정

CREATE TABLE admin_quorums (
  id             BINARY(16) PRIMARY KEY,
  workspace_id   BINARY(16) NOT NULL UNIQUE,  -- workspace 당 1개 강제
  threshold      INT NOT NULL,                 -- N of M (Owner 포함 가능)
  created_by     BINARY(16) NOT NULL,          -- 최초 생성 actor (보통 workspace 의 Owner)
  created_at     DATETIME(6) NOT NULL,
  modified_by    BINARY(16) NOT NULL,          -- 마지막 변경의 initiator. ★ 변경 자체는 Q+O 승인 필요
  modified_at    DATETIME(6) NOT NULL,
  FOREIGN KEY (workspace_id) REFERENCES workspaces(id)
);
컬럼자료형역할
idBINARY(16) PKquorum 의 고유 식별자
workspace_idBINARY(16) UNIQUE이 quorum 이 속한 workspace. UNIQUE — workspace 당 quorum 1 개 강제
thresholdINT승인이 필요한 멤버 수 (N-of-M 의 N). 예: 멤버 5 명 중 3 명 승인 필요 → threshold=3
created_byBINARY(16)최초 quorum 을 생성한 user (보통 workspace 의 Owner). set-once
created_atDATETIME(6)quorum 최초 생성 시각. set-once
modified_byBINARY(16)마지막 변경 (멤버 추가/제거 또는 threshold 조정) 을 시작한 user. ★ 변경 자체는 Q+O 라벨 — Owner 단독으로 못 바꿈, 현재 Quorum 의 N-of-M + Owner 승인이 모두 필요한 self-amending 패턴. 즉 이 컬럼은 "누가 변경을 시작했는가" 의 initiator 이고, 실제로 승인한 quorum 의 audit 은 별도 approval_requests 평면에서 추적
modified_atDATETIME(6)마지막 변경 적용 시각

1.2 admin_quorum_members — 누가 quorum 의 멤버인지 (junction · grant/revoke 패턴)

CREATE TABLE admin_quorum_members (
  id          BINARY(16) PRIMARY KEY,
  quorum_id   BINARY(16) NOT NULL,
  user_id     BINARY(16) NOT NULL,
  granted_by  BINARY(16) NOT NULL,            -- 멤버로 추가한 initiator (Q+O 흐름)
  granted_at  DATETIME(6) NOT NULL,
  revoked_by  BINARY(16),                      -- 제거 시 set, set-once
  revoked_at  DATETIME(6),                     -- 제거 시각, NULL = 현재 active
  KEY (quorum_id, user_id),
  KEY (quorum_id, revoked_at),
  FOREIGN KEY (quorum_id) REFERENCES admin_quorums(id),
  FOREIGN KEY (user_id) REFERENCES users(id)
);
컬럼자료형역할
idBINARY(16) PKgrant 이벤트의 surrogate PK. 같은 user 가 revoke 후 재추가되면 새 row INSERT — 이력 보존
quorum_idBINARY(16) FK어느 quorum 의 멤버인지
user_idBINARY(16) FK멤버 사용자. role 은 Owner / Admin / NSA / Security Admin 중 하나여야 함 (application-layer 검증)
granted_byBINARY(16)이 멤버 추가를 시작한 user (Q+O 흐름의 initiator). set-once
granted_atDATETIME(6)멤버로 추가된 시각. set-once
revoked_byBINARY(16) nullable멤버에서 제거를 시작한 user. NULL = 현재 active. set-once when set
revoked_atDATETIME(6) nullable제거 시각. NULL = 현재 active. set-once when set
KEY (quorum_id, user_id)—"이 user 가 이 quorum 의 멤버였던 이력 전부" 조회 인덱스 (PRIMARY 가 아니어서 같은 (quorum, user) 의 grant/revoke 사이클 다중 row 가능)
KEY (quorum_id, revoked_at)—"이 quorum 의 현재 active 멤버" 조회 인덱스 (WHERE revoked_at IS NULL)

Owner Counting Rule — Owner 의 승인은 mandatory + count 에도 포함

add-users.md, p.1 직접 인용 (공식 확인)

Q 또는 Q+O 흐름에서 Owner 의 승인은 mandatory 이며 threshold count 에 포함될 수 있다. 예: threshold 가 3 of 5 일 때:

  • 2 Admins + Owner = 충족 (Owner 카운트 포함)
  • 3 Admins = 미충족; Owner 의 추가 승인 전까지 거부

Approval Group (AG) — Owner 없이 위임 가능한 작업

Admin Quorum 이 "거의 모든 중요한 결정에는 Owner 가 반드시 들어가야 함" 인 반면, Approval Group 은 일부 작업을 Owner 없이도 처리할 수 있도록 위임하는 별개 메커니즘입니다. 예: 운영팀 매니저 3 명이 모이면 사용자 삭제 가능 (Owner 호출 없이). 작업별로 별도 group 을 정의하고 각 group 에 requires_owner 토글을 둡니다.

설정 위치 — Console 의 Settings > Quorums > Approval groups 에서 작업 → group 매핑과 Owner 요구 여부를 조정.

2.1 approval_groups — 작업별 위임 group 정의

CREATE TABLE approval_groups (
  id             BINARY(16) PRIMARY KEY,
  workspace_id   BINARY(16) NOT NULL,
  action         VARCHAR(64) NOT NULL,  -- 'delete_user', 'edit_user', ...
  requires_owner BOOLEAN NOT NULL,
  threshold      INT NOT NULL,
  created_by     BINARY(16) NOT NULL,
  created_at     DATETIME(6) NOT NULL,
  modified_by    BINARY(16) NOT NULL,
  modified_at    DATETIME(6) NOT NULL,
  FOREIGN KEY (workspace_id) REFERENCES workspaces(id)
);
컬럼자료형역할
idBINARY(16) PKgroup 의 고유 식별자
workspace_idBINARY(16) FK이 group 이 속한 workspace
actionVARCHAR(64)이 group 이 위임받은 작업 (예: delete_user, edit_user). 정형화한다면 ENUM 가능
requires_ownerBOOLEAN이 group 의 결정에 Owner 가 반드시 참여해야 하는지 토글. FALSE 면 그룹 자체 threshold 만으로 처리 — 즉 AG 의 핵심 가치
thresholdINTgroup 멤버 중 몇 명이 승인해야 충족되는지 (N-of-M 의 N)
created_by · created_atBINARY(16) · DATETIME(6)group 최초 생성 actor + 시각. set-once
modified_by · modified_atBINARY(16) · DATETIME(6)마지막 변경 (threshold 조정 · requires_owner 토글 · 멤버 외 속성 변경) actor + 시각

2.2 approval_group_members — group 의 멤버 (junction · grant/revoke 패턴)

CREATE TABLE approval_group_members (
  id          BINARY(16) PRIMARY KEY,
  group_id    BINARY(16) NOT NULL,
  user_id     BINARY(16) NOT NULL,
  granted_by  BINARY(16) NOT NULL,
  granted_at  DATETIME(6) NOT NULL,
  revoked_by  BINARY(16),
  revoked_at  DATETIME(6),
  KEY (group_id, user_id),
  KEY (group_id, revoked_at)
);
컬럼자료형역할
idBINARY(16) PKgrant 이벤트의 surrogate PK. revoke 후 재추가 시 새 row INSERT — 이력 보존
group_idBINARY(16) FK어느 approval group 의 멤버인지
user_idBINARY(16) FK멤버 사용자
granted_by · granted_atBINARY(16) · DATETIME(6)멤버 추가 actor + 시각. set-once
revoked_by · revoked_atBINARY(16) nullable · DATETIME(6) nullable제거 actor + 시각. NULL = 현재 active. set-once when set
KEY (group_id, revoked_at)—"이 group 의 현재 active 멤버" 조회 인덱스 (WHERE revoked_at IS NULL)

Add user 흐름의 7-day Expiry

새 사용자 추가 요청은 단순히 "Owner 가 클릭" 만으로 끝나지 않습니다 — Owner + Admin Quorum 멤버 각자의 mobile app 에 push 알림이 가고, 각자 mobile 에서 서명 (mobile MPC key share) 으로 승인해야 합니다. 그런데 모든 사람이 항상 즉시 응답하지는 않으므로 제한 시간 (7일) 안에 threshold 가 충족되지 않으면 요청이 자동으로 expire — 즉 "잊혀진 채 영원히 pending" 상태를 막는 안전장치.

schema 측 표현 — approval_requests 테이블에 expires_at = created_at + 7 day 를 set 하고, scheduled job 이 그 시각을 지난 pending 요청을 자동으로 expired 처리.

Edit user 의 Customize

Edit user (사용자 정보 수정) 는 위 Approval groups 로 흐름을 customize 가능 — 즉 어떤 그룹이 승인하면 진행할지, Owner 가 들어가야 할지 등을 Settings 에서 조정. 정확한 customize 범위 (어떤 field 가 어떤 권한이 필요한지) 는 Fireblocks 자료에 명시되어 있지 않습니다.

Putting It Together — 2 시퀀스

위 schema 가 실제 운영 흐름 안에서 어떻게 작동하는지 — Add user (Q 흐름, 7-day expiry) 와 Approval Group 위임 (AG 흐름, Owner 없이 처리) 의 두 시나리오로.

3.1 Add user 흐름 — Q (Admin Quorum) + 7-day expiry

sequenceDiagram
  autonumber
  actor Initiator as 👤 Owner / Admin / NSA
  actor Owner as 👤 Owner
  actor Quorum as 👥 Admin Quorum
(M 명 멤버)
  participant Console as 🖥️ Fireblocks Console
  participant FB as 🛡️ Fireblocks Core
  participant Job as ⏰ Scheduled job

  Initiator->>Console: "Add user" 요청
(email + role)
  Console->>FB: approval_requests INSERT
(expires_at = +7day, status='pending')
  Console->>Owner: mobile push
  Console->>Quorum: mobile push (M 명 전체)

  Note over Owner,Quorum: 각자 mobile app 에서 검토 + 서명

  loop 7일 안에 승인 누적
    Owner->>Console: 승인 (mobile 서명)
    Quorum->>Console: 멤버 1 명씩 승인
  end

  alt threshold + Owner counting rule 충족
    Console->>FB: users INSERT (type='console' 또는 'api', status='pending')
    FB->>FB: approval_requests.status = 'approved'
    Console->>Initiator: 사용자 초대 메일 발송
    Note over FB: 신규 사용자가 초대 수락하면 users.activated_at SET
  else 7일 expire
    Job->>FB: pending 요청 sweep
    FB->>FB: approval_requests.status = 'expired'
    FB->>Console: 요청 자동 취소
    Console->>Initiator: "요청이 만료되어 사용자가 추가되지 않았습니다" 알림
  end
Figure 22. Add user — Q (Admin Quorum) 흐름 + 7-day expiry. 핵심: ① 요청은 즉시 적용되지 않고 approval_requests 에 expires_at = +7day 와 함께 pending 으로 들어감. ② Owner + Quorum 멤버 각자 mobile 에서 서명 누적 — Owner Counting Rule 에 의해 Owner 의 승인은 mandatory + threshold count 에도 포함. ③ threshold 충족 시 users INSERT (status='pending'), 사용자가 초대를 수락하면 activated_at SET 으로 active 전환. ④ 7일 동안 미충족 시 scheduled job 이 자동으로 expired 처리 — pending 이 영원히 남아 운영자 confusion 을 일으키지 않도록.

3.2 Approval Group 위임 흐름 — AG (Owner 없이 처리)

sequenceDiagram
  autonumber
  actor Initiator as 👤 Admin / NSA 등
  actor AG_Members as 👥 Approval Group
(이 작업 위임받은 그룹)
  participant Console as 🖥️ Fireblocks Console
  participant FB as 🛡️ Fireblocks Core

  Note over Initiator,FB: 사전 설정 — Settings / Quorums / Approval groups
action='delete_user', requires_owner=FALSE, threshold=2, members=[...]

  Initiator->>Console: "Delete user X" 요청
  Console->>FB: action='delete_user' 의 approval_groups 조회
  FB->>FB: 해당 group 의 requires_owner = FALSE 확인

  alt requires_owner = FALSE (AG 위임)
    Console->>AG_Members: mobile push (Owner 제외)
    AG_Members->>Console: threshold 명 승인 (mobile 서명)
    Console->>FB: users.deleted_at = now()
(soft delete)
    Console->>Initiator: 삭제 완료
    Note over Initiator,FB: Owner 가 잠들어 있어도 운영 가능
  else requires_owner = TRUE (Q+O 와 사실상 동일)
    Console->>FB: 일반 Q+O 흐름으로 fallback
  end
Figure 23. Approval Group 위임 — AG (Owner 없이 가능) 흐름. 핵심 가치: ① 일상 운영 작업 (사용자 삭제 / edit / 정책 미세 조정 등) 까지 Owner 가 매번 들어가야 한다면 Owner 가 병목이 됨 — 야간/주말 운영 지연 + Owner mobile 분실 시 마비. ② Approval Group 으로 작업별 위임이 가능해서 Owner 가 없어도 운영팀 자체로 처리. ③ 단 requires_owner 토글이 TRUE 면 사실상 Q+O 와 같은 흐름 — Settings 에서 작업별로 정책적으로 결정. 보안과 운영 편의 사이의 trade-off 를 group 단위로 세밀 조정하는 메커니즘.
