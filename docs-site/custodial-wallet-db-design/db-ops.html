25. DB 운영 (MySQL)

Replication · Outbox · Idempotency · UUID · Partitioning · Retention · Migration Governance
본 페이지의 출처 — 일반 운영 best practice + 저자 정리

이 페이지는 Fireblocks 자료가 아니라 본 docs-site 의 다른 페이지들 (DB 분할 7 개 / append-only / set-once / cross-DB binding 등) 에서 도출된 운영 권장사항을 일반 MySQL 운영 best practice 와 묶어서 정리한 것입니다.

다른 페이지의 schema 의 운영 요구사항 — 그대로 받아들여도 안전 (본 docs-site 의 자체 규약)

  • ledger / audit DB 의 zero-tolerance — semi-sync (loseless) replication 필수
  • Outbox pattern — multi-DB transaction 이 불가능하므로 single-DB transaction + outbox 로 cross-DB eventual consistency
  • Append-only / set-once 의 DB-level 강제 — trigger 로 application layer 우회 차단 (24. Storage Discipline)
  • Cross-DB binding — 다른 DB 의 source row 와 byte-equal CBOR encoding 일치 (20. Audit Log)

일반 MySQL 운영 best practice (public domain) — 참고용

  • UUID 저장은 UUID_TO_BIN(UUID(), 1) 의 16-byte time-ordered BINARY 권장
  • Idempotency 는 INSERT IGNORE + UNIQUE constraint + 별도 SELECT 조합
  • PostgreSQL 의 RETURNING / ON CONFLICT / jsonb / partial index 등은 MySQL 에서 별도 우회 패턴
  • 고-growth 테이블의 RANGE partitioning + regulatory retention (7~10년)
  • Schema migration governance — trigger 변경은 charter-class, 테이블 drop 절대 금지

Outbox Pattern (cross-DB consistency)

Multi-DB transaction 불가능 → outbox 로 eventual consistency.

-- ledgerdb 의 한 transaction 안에서
START TRANSACTION;
  -- 1. business operation
  INSERT INTO ledger_entries (...) VALUES (...);

  -- 2. outbox row (같은 DB transaction)
  INSERT INTO outbox (id, target_db, target_aggregate, payload_cbor, created_at, ...)
  VALUES (UUID_TO_BIN(UUID(), 1), 'auditdb', 'audit_events', ?, NOW(6), ...);
COMMIT;

-- 별도 worker:
-- outbox row 를 target DB 로 idempotent replicate
-- INSERT ... ON DUPLICATE KEY UPDATE id=id  (no-op merge)

Outbox pattern — multi-DB transaction 이 불가능한 환경에서 cross-DB eventual consistency 를 어떻게 보장하는가. 핵심 invariant: ① business operation 과 outbox 가 같은 DB transaction — 하나라도 실패하면 둘 다 롤백, "내가 했다고 알린 일은 반드시 실제 일어난 일" 의 보장. ② worker 의 idempotent replicate — 같은 outbox row 가 두 번 처리돼도 target DB 의 ON DUPLICATE 제약이 no-op 만들어 부작용 없음. ③ byte-equal CBOR binding — source 의 payload 와 target 의 row 가 binary 일치해야 cross-DB 일관성 검증 통과. 이 3 단계가 source / target DB 가 분리되어 있어도 "두 DB 가 같은 사실을 본다" 의 cryptographic 보장.

Idempotency SQL Pattern

-- 1. INSERT IGNORE 로 중복 시 무시 (reference_id 는 UNIQUE)
INSERT IGNORE INTO withdrawals (id, reference_id, ...)
VALUES (UUID_TO_BIN(UUID(), 1), ?, ...);

-- 2. 항상 같은 row 를 반환 (신규 / 기존 무관)
SELECT id FROM withdrawals WHERE reference_id = ? LIMIT 1;

-- 단일 transaction 안에서 두 쿼리 모두 실행하면
-- "first writer wins, 이후는 동일 row 반환" 보장 (reference_id UNIQUE 전제).

UUID 저장 권장

  • UUID_TO_BIN(UUID(), 1) — 16-byte BINARY, time-ordered swap
  • String UUID 보다 50% 작고, B-tree index locality 향상

Audit-Reviewable Schema 의 7 기준

  1. 모든 mutable 컬럼은 audit trail 동반
  2. 모든 append-only 테이블은 DB-level enforcement (trigger)
  3. Hash chain integrity 가 외부 검증 가능 (SGX(?)/DCAP(?) + signed checkpoint)
  4. Cross-DB binding 이 evidence chain 으로 입증
  5. Set-once 컬럼이 명시됨
  6. Runtime-only / forbidden 영역의 schema 부재가 검증됨
  7. State machine sticky terminal 이 DB-level 강제
