7. API Key · CSR(?) · 2FA(?) · SSO(?) · IP Allowlist

5 자격증명 평면의 영속화 — login + API call 시 인증과 권한을 어떻게 영속화하는가
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다. 미리 구분해두면 어떤 부분을 그대로 받아들이고 어떤 부분은 본인 환경에서 검증할지 판단이 쉬워집니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 5 자격증명 평면: API Key · CSR · 2FA · SSO · IP Allowlist 가 각각 다른 layer 에서 작동
  • API Key: API user 당 1 개 · Rename 시 key 불변 · Delete 즉시 invalid (진행 중 tx 실패)
  • CSR: RSA 4096 X.509(?), customer-side 에서 생성 (Fireblocks 는 private key 모름)
  • 2FA: 모든 Console user 필수, TOTP(?) authenticator (Google / Microsoft / LastPass / Yubico 등), 본인 reset 불가
  • SSO: service provider 는 Auth0, email domain 기반 authorization, 9 IdP (Google / Entra / Okta / OpenID Connect(?) / PingFederate / SAML(?) 2.0 / SAML 3.0 / ADFS(?) / LDAP(?))
  • IP Allowlist: API user 별 + workspace 별 두 평면, /32 CIDR(?) (single IP) 만 허용
  • Fireblocks 자체 문서에 "권한표 vs 본문" inconsistency 존재 — 2FA reset / IP Allowlist 수정 권한 등에서 권한표는 "Owner + Security Admin", 본문은 "Owner only" 로 다르게 적힘 (어느 게 맞는지는 본 자료로 결정 불가)

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • 8 테이블 (api_keys · csrs · user_2fa · twofa_reset_events · sso_configs · sso_authorized_domains · api_user_ip_allowlists · workspace_ip_allowlists) 의 구체 schema
  • TOTP(?) secret 과 SSO client secret 을 HSM(?)-wrapped key reference 로 저장하는 형태 (plaintext 절대 금지)
  • twofa_reset_events 의 append-only 패턴 (reset 이력 audit)
  • sso_authorized_domains 를 별도 junction 으로 둔 선택 (sso_configs 의 array 컬럼 회피)
  • idp_type ENUM 9 값으로 정형화 (Fireblocks 자료는 자유 텍스트일 수 있음)
  • WebAuthn(?) / FIDO2(?) / hardware key 같은 password-less 2FA 방식 지원 여부 — Fireblocks 자료에 명시 없음, 본 schema 는 TOTP 만 가정

API Key — API user 의 통신 인증

API user 가 Fireblocks REST API 를 호출할 때 자신을 식별하는 비밀 값. API user 1 명당 정확히 1 개 의 API key 가 발급되며 (Fireblocks 정식 표현: "Each API user has an associated API key"), Console 의 API users list 에서 마우스 hover 로 복사할 수 있습니다.

중요한 운영 동작 3 가지:

  • Rename 후에도 key 자체는 불변 — 사용자 이름만 바뀔 뿐 같은 key 로 계속 호출 가능. 운영 시스템 측 비밀 키 교체 필요 없음
  • Delete 시 즉시 무효화 — 별도 유예 기간 없이 그 순간부터 모든 통합이 끊김. 진행 중인 tx 가 실패하고 새 서명 요청도 거부됨
  • IP Allowlist 가 없으면 위험 — 도난된 API key 는 인터넷 어느 머신에서나 사용 가능하므로, key 유출 자체를 차단하기 어렵다면 호출 가능한 IP 자체를 좁히는 것 이 마지막 방어선. 자세히는 아래 IP Allowlist 절

CSR — API user 의 cert 발급 요청

API key 가 "이 호출이 누구인지" 를 가리키는 단순 토큰이라면, CSR (Certificate Signing Request) 은 그 신원을 cryptography 차원에서 증명할 수 있도록 발급되는 X.509(?) 인증서 의 발급 요청입니다 — RSA 4096 비트 키 크기를 사용합니다.

핵심 설계 — private key 는 customer 측에서 생성해서 로컬에만 보관합니다 (보통 fireblocks_secret.key 파일). Fireblocks 는 public key 만 받아서 cert 를 발급하므로, Fireblocks 도 customer 의 private key 를 모르는 신뢰 모델입니다. 만약 Fireblocks 가 private key 를 가지고 있다면 customer 신원을 위장해서 API 호출이 가능해지지만, 이 설계 덕에 그게 불가능.

예외 — Sandbox 환경에서는 학습 편의를 위해 브라우저에서 자동 생성 (Fireblocks 가 임시 private key 를 발급해 즉시 다운로드). 본 운영에서는 사용 금지.

인증서 체인 구조 — Fireblocks 는 자체 Root CA → Intermediate CA → end cert (leaf) 의 3 단 chain 을 운영합니다. 위 CSR 으로 발급된 cert 가 leaf (가장 말단), 그 위로 intermediate, 그 위로 root 가 신뢰의 끝.

CREATE TABLE csrs (
  id                BINARY(16) PRIMARY KEY,
  subject_cn        VARCHAR(255) NOT NULL,
  public_key_pem    TEXT NOT NULL,
  fingerprint_sha256 BINARY(32) NOT NULL UNIQUE,
  signed_by_intermediate_cert_id BINARY(16) NOT NULL,
  end_cert_pem      TEXT,                              -- Core Services 가 sign 후 set
  signed_at         DATETIME(6),
  expires_at        DATETIME(6) NOT NULL,
  uploaded_by       BINARY(16) NOT NULL,                -- CSR 을 upload 한 user (= API user 추가 initiator)
  uploaded_at       DATETIME(6) NOT NULL                -- ★ 이 row 의 created_at semantic
);
컬럼자료형역할
idBINARY(16) PKCSR 의 고유 식별자
subject_cnVARCHAR(255)cert 의 Common Name — 누구의 cert 인지를 가리키는 식별자 (예: API user 이름)
public_key_pemTEXTcustomer 가 보낸 public key 의 PEM 인코딩. 짝인 private key 는 customer 만 보유
fingerprint_sha256BINARY(32) UNIQUEpublic key 의 SHA-256 지문. 같은 key 가 중복 등록되지 않도록 UNIQUE
signed_by_intermediate_cert_idBINARY(16)이 leaf cert 를 서명한 intermediate cert 의 id. 체인 추적용

uploaded_atDATETIME(6)customer 가 CSR 을 업로드한 시각. 이 row 의 created_at 과 같은 의미 — CSR 업로드 의미가 더 직관적이라 이름 보존. set-once

2FA — Console user 의 2 단계 인증

password 만으로는 부족하므로 추가 인증을 의무화 — Fireblocks 는 모든 Console user 가 TOTP(?) (Time-based One-Time Password, 시간 기반 일회용 비밀번호) authenticator app 을 등록하도록 강제 합니다. Google Authenticator / Microsoft Authenticator / LastPass Authenticator / Yubico Authenticator 등이 지원되며, 모두 같은 원리로 작동합니다 — 등록 시 서버와 app 이 같은 secret 을 공유하고, 그 secret + 현재 시각 을 함께 계산해서 30 초마다 새로 6 자리 코드를 발급 (서버도 같은 계산을 해서 일치 여부 검증). 따라서 서버-app 의 시간 동기화가 필요.

참고 — WebAuthn(?) / FIDO2(?) (password 자체를 없애는 인증 표준 — 보안 키나 지문 / Face ID 로 로컬에서 private key 서명) 같은 하드웨어 보안 키 지원 여부는 Fireblocks 자료에 명시되어 있지 않아, 본 schema 에서는 TOTP 만 가정합니다.

왜 TOTP secret 을 HSM(?) 안에 두는가

TOTP 의 secret (서버 - 사용자 사이에 공유하는 seed) 이 한 번 유출되면 공격자가 그 사용자의 2FA 코드를 무한히 생성할 수 있으므로, 사실상 password 만큼 민감한 비밀입니다. 따라서 DB 에 plaintext 저장은 금지 — HSM 안에 보관하고 DB 에는 그 key 의 reference 만 둡니다. 이 reference 로 HSM 에 "이 사용자의 TOTP 코드 검증" 을 요청하면 HSM 내부에서 secret 을 꺼내지 않고 검증해서 결과만 반환합니다.

Reset 운영:

  • 본인 reset 불가 — 자신의 2FA 를 자신이 푸는 것은 보안 의미 없음 (이미 password 만 알면 푸는 셈). 따라서 다른 사람에게 reset 을 요청해야 함
  • 표준 절차: 사용자 → Owner 또는 Security Admin 에게 요청 → 관리자가 reset 실행 → 사용자 이메일로 확인 메일 → 재로그인 + 새 authenticator 등록
  • Owner 본인의 reset 은 누구에게 요청? — Fireblocks Support 에 별도 절차로 요청 (via_support 플래그가 이 케이스를 마크)
⚠️ Fireblocks 자체 문서의 inconsistency

2FA reset 권한이 누구에게 있는지에 대해 권한표와 본문이 일치하지 않습니다. 권한표는 "Owner + Security Admin" 으로 적혀 있고, 본문 산문 설명은 "Owner only" 로 적혀 있어 어느 쪽이 운영 진실인지 본 자료로 결정할 수 없습니다. 실제 운영 시 Fireblocks Support 에 확인 권장.

CREATE TABLE user_2fa (
  user_id           BINARY(16) PRIMARY KEY,
  -- ★ TOTP secret 은 plaintext 저장 금지. HSM-wrapped 만.
  secret_hsm_keyref VARCHAR(128) NOT NULL,
  enrolled_at       DATETIME(6) NOT NULL,
  last_used_at      DATETIME(6),
  KEY (last_used_at)
);

-- ★ append-only — 모든 reset 이력은 audit
CREATE TABLE twofa_reset_events (
  id                BINARY(16) PRIMARY KEY,
  target_user_id    BINARY(16) NOT NULL,
  actor_user_id     BINARY(16) NOT NULL,
  reset_at          DATETIME(6) NOT NULL,
  via_support       BOOLEAN NOT NULL DEFAULT FALSE,    -- Owner 본인 reset 은 Support 경유
  KEY (target_user_id)
);

SSO — 사내 IdP 에 로그인 위임

Console user 가 회사의 다른 시스템 (Google Workspace · Microsoft 365 · Okta 등) 에 이미 로그인할 때 쓰는 계정으로 Fireblocks 도 로그인하는 메커니즘. password 를 별도로 외울 필요 없이 사내 IdP(?) 가 신원을 보장해주는 방식.

중요한 분리 — SSO 는 "로그인 authorization" 만 처리합니다. 즉 "이 사람이 회사 직원인가 + 진짜 그 사람 맞는가" 의 검증까지만 사내 IdP 에 맡기고, "그 사람이 Fireblocks workspace 의 어떤 role 인가" 는 별도 평면 — Owner / Admin 이 Console 에서 user 를 추가하고 role 을 부여하는 — 에서 관리합니다. SSO 로 로그인하더라도 workspace 에 user 로 등록되어 있지 않으면 접근 불가.

Service provider 는 Auth0(?) (callback URL: auth.fireblocks.io/login/callback). 즉 Fireblocks ← Auth0 ← 회사 IdP 3 단 체인. 변경 (IdP 추가 / 교체) 은 Fireblocks Support 경유 + Workspace Owner 승인 필요 — Console UI 에서 자유롭게 바꿀 수 없음.

Authorization 메커니즘 — email domain 기반. workspace 의 SSO 설정에 등록된 domain (예: company.com) 의 email 로만 로그인 가능. 동일 IdP 에 있더라도 다른 domain 의 user 는 차단.

9 IdP 지원 — Fireblocks 가 self-setup (Console 에서 자체 설정) 을 허용하는 것과 Support 경유만 가능한 것이 갈립니다:

CREATE TABLE sso_configs (
  id                BINARY(16) PRIMARY KEY,
  workspace_id      BINARY(16) NOT NULL UNIQUE,        -- workspace 당 1개의 SSO 설정
  idp_type          ENUM('google','entra','okta','oidc','pingfederate','saml2','saml3','adfs','ldap') NOT NULL,
  callback_url      VARCHAR(255) NOT NULL,             -- auth.fireblocks.io/login/callback
  client_id         VARCHAR(255),

  KEY (sso_config_id, removed_at)
);

컬럼자료형역할

IP Allowlist — 호출 가능한 IP 자체를 제한

아무리 API key 와 cert 가 안전해도 그 자격증명이 어디선가 유출되면 도난당한 key 로 인터넷 어디서나 호출이 가능합니다. 마지막 방어선으로 호출이 허용되는 IP 주소 자체를 화이트리스트로 좁히는 것 — 그게 IP Allowlist 입니다. 등록되지 않은 IP 에서 들어온 호출은 자격증명이 맞아도 거부.

두 layer 가 별도 존재:

  • API user 별 (per-API-user) — 각 API user 마다 자기만의 허용 IP 목록. customer 의 운영 서버 IP 만 등록하는 식. 본 페이지의 api_user_ip_allowlists 테이블
  • Workspace 별 (Console 접근용) — 사람이 Console UI 에 로그인할 수 있는 IP 자체를 제한 (예: 오피스 IP, VPN 출구 IP). 본 페이지의 workspace_ip_allowlists 테이블

두 평면 모두 CIDR(?) 표기의 /32 만 허용 — single IP 강제. /24 같은 범위 전체 허용은 안 됨. 이유: range 를 허용하면 "회사 망 전체" 같은 넓은 범위가 등록되어 사실상 의미 없어지므로, 정확히 어느 머신인지 한 대씩 지정하도록 강제.

⚠️ Fireblocks 자체 문서의 inconsistency

IP Allowlist 수정 권한이 누구에게 있는지에 대해 권한표는 "Owner + Security Admin", 본문 산문 설명은 "Only workspace Owners" 로 다르게 적혀 있어 본 자료로 결정 불가. (2FA reset 권한과 동일 패턴) 실제 운영 시 Fireblocks Support 에 확인 권장.

CREATE TABLE api_user_ip_allowlists (
  id          BINARY(16) PRIMARY KEY,
  api_user_id BINARY(16) NOT NULL,
  cidr        VARCHAR(18) NOT NULL,              -- /32 only
  added_by    BINARY(16) NOT NULL,                -- Owner 또는 Security Admin
  added_at    DATETIME(6) NOT NULL,
  removed_by  BINARY(16),                         -- 제거 actor. set-once when set
  removed_at  DATETIME(6),
  KEY (api_user_id, removed_at)
);

CREATE TABLE workspace_ip_allowlists (
  id           BINARY(16) PRIMARY KEY,
  workspace_id BINARY(16) NOT NULL,
  cidr         VARCHAR(18) NOT NULL,              -- /32 only
  added_by     BINARY(16) NOT NULL,                -- Owner (workspace 평면은 Owner 전용)
  added_at     DATETIME(6) NOT NULL,
  removed_by   BINARY(16),                         -- 제거 actor. set-once when set
  removed_at   DATETIME(6),
  KEY (workspace_id, removed_at)
);

Putting It Together — 5 자격증명이 실제로 어떻게 작동하는가

지금까지 본 5 평면이 운영 흐름 안에서 어떻게 묶여 작동하는지 3 가지 대표 시나리오로. 본 페이지의 schema 가 다른 페이지 (특히 6. Users · 9. Admin Quorum) 와 어떻게 cross-cut 되는지도 함께 보입니다.
