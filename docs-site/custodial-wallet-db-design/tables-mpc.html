11. MPC(?) Key Share Distribution

MPC-CMP(?) 프로토콜 · 3-share 분포 · key lifecycle
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • MPC-CMP 프로토콜: Canetti–Makriyannis–Peled (2020) 의 threshold ECDSA, 4 라운드 (3 라운드는 pre-processed) · 마지막 라운드 air-gapped 가능 · 3 종 algorithm 지원: MPC_ECDSA_SECP256K1 (BTC / EVM) · MPC_EDDSA_ED25519 (Solana / XLM / ALGO) · MPC_ECDSA_SECP256R1 (P-256, FIPS-compliant HSM 호환)
  • Default SaaS MPC 의 3-share 분포: 1 customer-side (mobile 또는 API Co-signer) + 2 Fireblocks Azure SGX
  • Hosted MPC variant: customer 가 3 share 전부 보유 (1 Primary + 2 Guard, 모두 SGX), Fireblocks 는 cryptographic 참여 없음
  • Threshold 구조: within-group 3/3, across-group 1/N OR — 모든 signing user 의 set 은 Owner 의 set 에서 derived
  • Key share derivation 이벤트 4 종: Add user (Owner 단독 승인) · Re-enroll device (Owner 재승인 + 사용자 재등록, 각 2-day window) · Device migration (self-service, PIN+passphrase+biometric) · Co-signer pairing (Owner 가 승인)

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • key_lifecycle 테이블의 schema (Fireblocks 가 내부 audit 을 정확히 어떻게 영속화하는지는 미명시)
  • 이 schema 가 auditdb (별도 DB) 에 위치하는 분리 선택 — 키 자체는 DB 어디에도 저장 안 함 (forbidden storage), event 이력만 audit-grade 로 보존

MPC-CMP — Fireblocks 가 쓰는 MPC 프로토콜

여러 당사자가 각자 키 조각만 들고 협력해서 서명하는 다양한 MPC 프로토콜 중 Fireblocks 는 MPC-CMP 를 사용합니다. Canetti–Makriyannis–Peled 가 2020 년에 발표한 threshold ECDSA 알고리즘 (NIST 2020 / ACM CCS 2020) 이고, 이름의 약자가 각 저자 (CMP) 의 머리글자.

핵심 특성:

  • 3 종 signing algorithm 지원 — 같은 MPC 인프라로 처리 가능:
    • MPC_ECDSA_SECP256K1 — Bitcoin, EVM 전반 (Ethereum / Polygon / BSC / Arbitrum / Optimism / …)
    • MPC_EDDSA_ED25519 — Solana, Stellar, Algorand, Cardano (일부), TON
    • MPC_ECDSA_SECP256R1 — NIST P-256 curve, FIPS-compliant HSM 호환 chain (enterprise / regulated environment)
    세 algorithm 이 API `SigningAlgorithm` enum 의 정식 3 값. Public key 의 `algorithm` 필드 와 derivation path (BIP-32) 가 algorithm 별로 분기
  • 4 라운드 (그중 3 라운드는 pre-processed) — 이전 세대 GG18 protocol 이 8 라운드였던 것에 비해 약 800% 빠름. 즉 서명 한 번에 네트워크 왕복이 1 번이면 충분 (pre-processed 단계는 미리 계산 가능)
  • 마지막 라운드 air-gapped 가능 — 인터넷 연결 없이 (예: QR code 전달) 마지막 서명 단계를 처리할 수 있어 진정한 air-gapped wallet 운영 가능
  • Universally composable + proactive security + accountability — 학술적으로 검증된 보안 속성. 특히 "어느 party 가 정상이 아니었는지 사후에 식별 가능" (accountability) 가 institution 운영에 중요
  • Additive Secret Sharing — share 조합이 단순 덧셈만으로 작동, perfect secrecy. "The secret itself never exists in one place" — 전체 키가 어느 시점에도 한곳에 모이지 않는다는 것이 이 protocol 의 핵심 보안 가정

DB Schema — key_lifecycle (auditdb · append-only)

중요한 설계 결정: 키 material 자체는 DB 의 어떤 컬럼에도 저장하지 않습니다 (forbidden storage 영역) — plaintext 도 cipher 도 안 됨. 본 테이블은 키의 "어떤 event 가 언제 일어났는가" 만 audit-grade 로 기록. 그래서 별도 auditdb (audit 전용 DB) 에 위치하고 BEFORE UPDATE / DELETE trigger 로 append-only 가 강제됩니다.

-- 키 자체는 forbidden storage. row 는 lifecycle event 만 기록.
CREATE TABLE key_lifecycle (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  user_id         BINARY(16) NOT NULL,
  key_set_id      BINARY(16) NOT NULL,        -- 한 user 의 3-share set 식별자
  event_type      ENUM('provisioned', 're-enrolled', 'migrated', 'revoked', 'backup-verified') NOT NULL,
  actor_user_id   BINARY(16) NOT NULL,         -- 이 event 를 trigger 한 user
  approved_by_owner_user_id BINARY(16),         -- provisioning 은 Owner 단독 승인 필수
  occurred_at     DATETIME(6) NOT NULL,
  source_aggregate VARCHAR(64),                  -- 'add-user', 'device-migration', ...
  -- ★ append-only — BEFORE UPDATE / DELETE 트리거로 강제
  KEY (workspace_id, user_id, occurred_at)
);

-- 절대 컬럼 X: private key, MPC share material, recovery passphrase, RSA private key
-- → 어떤 컬럼에도 plaintext 또는 cipher 로도 저장 금지
컬럼자료형역할
idBINARY(16) PKevent 의 고유 식별자
workspace_idBINARY(16) FKevent 가 속한 workspace
user_idBINARY(16) FK이 key share 의 소유 user
key_set_idBINARY(16)한 user 의 3-share set 식별자 (key material 자체는 아님 — 그건 forbidden). 서로 다른 share 들이 같은 logical key 에 속함을 표시
event_typeENUM (5 값)provisioned 최초 share 생성 / re-enrolled 페어링 재발급 / migrated 새 기기로 이전 / revoked share 폐기 / backup-verified 복구 가능 여부 확인 (월 1회 알림 시점 등)
actor_user_idBINARY(16) FK이 event 를 trigger 한 user — 대부분 share 소유자 본인 (device migration / re-enroll 같은 self-service)
approved_by_owner_user_idBINARY(16) nullableOwner 의 승인이 필요한 event (예: provisioned · re-enrolled · co-signer pairing) 에서만 set. device migration 처럼 self-service path 는 NULL
occurred_atDATETIME(6)event 발생 시각
source_aggregateVARCHAR(64) nullable이 event 가 어느 상위 흐름에서 비롯됐는지 (예: add-user, device-migration, re-enrolling-api-user). cross-DB 추적용

Key Share Derivation 이벤트 — 4 가지 흐름

새 key share 가 생성되거나 기존 share 가 새 디바이스로 옮겨가는 운영 시나리오는 4 가지. 각각 승인 강도가 다릅니다.

이벤트승인 강도schema 매핑
Add user (signing role)Owner 단독 MPC key share derivation 별도 승인 필요event_type='provisioned' + approved_by_owner_user_id set
Re-enroll deviceOwner 재승인 (2-day window) + 사용자 재등록 (2-day window) 둘 다 필요event_type='re-enrolled' + approved_by_owner_user_id set
Device migration사용자 본인 self-service — 관리자 승인 없이 PIN+passphrase+biometric 3중 인증event_type='migrated' + actor_user_id = 본인, approved_by_owner_user_id NULL
Co-signer pairingOwner 가 Co-signer key shares 승인event_type='provisioned' + source_aggregate='co-signer-pairing'
