10. Policy & TAP(?) Rules

2 component · 3 action · designated signer · DCCP(?) · Whitelist vs OTA
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • Policy 가 workspace 의 primary security control 이라는 위상 (아래 직접 인용 callout)
  • Policy rule 의 2 component: Parameters (initiator / source / destination / asset 등) + Actions (Allow / Approved by / Block)
  • 3 평면: Fireblocks Policy (TAP) · DCCP (입금 confirmation) · AML Transaction Screening Policy
  • Designated Signer 메커니즘: NSA / Editor 가 MPC key 없이도 designated signer 가 지정된 tx 타입을 initiate 가능 (internal exchange transfer 제외)
  • Second Authorizer: NSA / Approver 를 두 번째 authorizer 로 지정 가능
  • User Group: 다수 사용자를 single rule 에 매핑 / rule-level sub-quorum (예: "Management 그룹의 2 명 승인")
  • Policy 변경 = Q+O (Admin Quorum + Owner) 필수, mobile 서명 누적
  • Whitelist vs OTA 의 방어 차이: whitelist 는 Admin Quorum 의 address-level 사전 승인, OTA 는 그게 없어 Policy 가 사실상 유일한 자동 방어선

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • policies · policy_rules · policy_change_log · user_groups · user_group_members 5 테이블의 구체 schema
  • policy_rules.parameters_cbor 를 CBOR(?) 단일 BLOB 로 저장하는 선택 (대안: 컬럼 분해)
  • policies.version + active_at + superseded_at 의 monotonic version 패턴
  • policy_change_log.mobile_app_approval_sigs 의 정확한 형식 (개별 서명 list vs aggregated)
Policy = Primary Security Control (Fireblocks 직접 인용)

"Policies are your primary security control in your workspace(?)." — Fireblocks 의 공식 문서 (about-policies.md, p.1) 가 명시한 Policy 의 위상. 단순한 부가 기능이 아니라 보안 모델의 first-class spine 이며, 다른 보안 평면 (Admin Quorum / IP allowlist / 2FA 등) 이 모두 갖춰져도 Policy 가 부실하면 결국 자금이 새어 나갈 수 있음.

Policy Rule 의 2 Component — Parameters 와 Actions

Policy rule 하나는 "어떤 상황에서 (Parameters) 무엇을 할지 (Actions)" 의 IF-THEN 구조입니다.

  • Parameters (= Scope) — 어떤 tx 에 이 rule 이 적용되는지의 조건. 보통: initiator (누가 시작한 tx) · source (어느 vault 에서) · destination (어디로) · asset (어떤 자산) · amount (금액 범위) 같은 characteristic 들의 조합
  • Actions — 위 조건이 매칭되면 어떻게 처리할지. 3 종: Allow (그대로 통과) / Approved by (지정된 user/group 의 승인을 받고 통과) / Block (차단). 자세히는 16. Approval State

종류역할평가 시점

Designated Signer 메커니즘 — NS 라벨이 뜻하는 것

NSA · Editor 는 MPC(?) key 가 없어 본인이 직접 서명할 수 없는 role 입니다. 그러나 Policy 가 그 tx type 의 서명자를 미리 지정해두면 NSA / Editor 가 "내가 시작할 테니 지정된 사람이 서명해라" 식으로 tx 를 initiate 할 수 있습니다 — 그 패턴을 NS 라벨로 부릅니다.

Fireblocks 공식 정의:

  • NSA: "can initiate transactions when the Policy assigns a designated signer"
  • Editor: "can also initiate certain transactions if the Policy defines another user capable of signing as a designated signer for that transaction type"
  • 적용 범위: NSA / Editor 는 internal exchange transfer 를 제외한 모든 tx 를 designated signer 흐름으로 initiate 가능

schema 측 표현 — policy_rules.designated_signer_user_group_id 컬럼이 어느 user group 이 그 rule 의 designated signer 인지 가리킴. NS 라벨이 적용된 rule 은 이 컬럼이 set.

Second Authorizer — 두 번째 승인자

Policy rule 의 Action 이 "Approved by" 일 때, 첫 번째 승인자 외에 두 번째 승인자를 별도로 정의 가능합니다. Non-Signing Admin / Approver 가 second authorizer 자격이 있고, Owner 의 책임 범위에 이 지정 권한이 포함됩니다. 4 eyes principle (두 사람이 함께 봐야 진행) 을 구현하는 메커니즘.

User Group in Policy — 그룹 단위 매핑

  • 다수 사용자를 single rule 에 매핑 — 한 명씩 일일이 적지 않고 "Management 그룹" 같은 추상을 사용. 팀 변경 시 group 멤버만 갱신하면 되고 rule 자체는 안 건드림
  • Initiator + Approved by 양쪽에 사용 가능 — "이 그룹이 시작" / "저 그룹이 승인" 식으로 결합
  • Sub-quorum (rule-level N-of-M): "requires any two members of a user group called Management to approve" — group 안에서 다시 정족수를 정함. Admin Quorum 의 workspace-wide quorum 과 별개로 rule 안에서만 작동하는 작은 quorum

변경 거버넌스 — Policy 자체를 누가 바꿀 수 있는가

Policy 가 보안의 spine 이므로 Policy 자체의 변경은 가장 엄격하게 통제됩니다.

  • 변경 라벨 = Q+O — Admin Quorum(?) + Owner 양쪽 모두 승인 필요. 즉 단일 Admin 의 단독 변경 불가
  • 편집 권한: Owner + Admin-level user (NSA 포함) 가 Console 에서 rule 을 작성. 실제 적용는 assigned approval group 의 승인 단계를 거친 후
  • mobile app 승인 필수 — Console 에서 변경 시도하면 Owner + Quorum 멤버에게 mobile push 가 가고, 각자 mobile 에서 서명 (MPC share) 을 모아 threshold 충족 시 적용. policy_change_log 에 모든 서명이 저장되어 audit 가능

Premium Features — Raw Signing · Mint · Burn

일부 고급 기능 (Raw Signing / Mint / Burn) 은 별도 premium 구매가 필요합니다. 본 docs-site 의 4. Vault 페이지의 "Vault Structure Best Practices" 절에서 본 Mint/Burn/Pause/Deploy/Upgrade segregated vault 권장과 정합 — 이런 권한이 있는 사람이 작업할 수 있는 별도 vault 를 두는 게 안전.

Whitelist vs OTA — Policy 의 방어 차이

외부로 송금 가능한 destination 은 두 종류 — 사전 등록된 whitelist 와 일회용 OTA. 둘은 보안 의존도가 다릅니다:

Address pathPolicy 의 역할
Whitelisted addressAdmin Quorum 이 등록 시점에 address-level 사전 승인. Policy 는 그 위에 추가 rule (cap · approver · cumulative limit) 적용. 즉 Policy 가 부실해도 등록 자체가 quorum 통과한 destination 이므로 1 차 방어선이 있음
One-Time Address (OTA)Address-level Admin Quorum 없음 — 그때그때 사용하고 버리는 destination 이므로 사전 승인 단계가 없음. Policy 가 사실상 유일한 자동 방어선 (preselected user/group/vault, threshold approval). Policy 가 허술하면 그대로 송금 가능 → Policy 설계의 가장 중요한 case

DB Schema

9.1 policies — workspace 별 Policy 본체 (versioned)

CREATE TABLE policies (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  policy_type     ENUM('transfer','contract-call','approve','dccp','aml') NOT NULL,
  version         INT NOT NULL,                        -- monotonic
  created_by      BINARY(16) NOT NULL,                  -- 이 version 변경을 시작한 actor (Q+O 흐름의 initiator)
  active_at       DATETIME(6) NOT NULL,                -- ★ set-once when activated (= 이 row 의 created_at semantic)
  superseded_at   DATETIME(6),                          -- 다음 version 활성화 시각
  KEY (workspace_id, policy_type, version)
);
컬럼자료형역할
idBINARY(16) PKPolicy 의 고유 식별자 (version 별로 별도 row)
workspace_idBINARY(16) FK이 Policy 가 속한 workspace
policy_typeENUM (5 값)Policy 의 종류. transfer=일반 송금 rule / contract-call=smart contract 호출 / approve=ERC-20 approve / dccp=입금 confirmation 정책 / aml=AML screening 정책
versionINT단조 증가 (monotonic). Policy 변경 시 version+1 의 새 row INSERT, 이전 row 는 superseded_at set
created_byBINARY(16)이 version 변경을 시작한 actor (Q+O 흐름의 initiator). 실제 승인한 quorum 은 policy_change_log.approved_by_quorum_request_id 에서 cross-ref. set-once
active_atDATETIME(6)이 version 이 활성화된 시각. set-once — 변경 불가. 이 row 의 created_at 과 같은 의미 — Policy 의 "활성" 개념이 더 직관적이라 이름 보존
superseded_atDATETIME(6) nullable다음 version 이 활성화돼서 이 version 이 더 이상 유효하지 않게 된 시각. NULL = 현재 활성 version

9.2 policy_rules — Policy 안의 개별 rule (per-version immutable)

CREATE TABLE policy_rules (
  id              BINARY(16) PRIMARY KEY,
  policy_id       BINARY(16) NOT NULL,
  rule_number     INT NOT NULL,                        -- first-match ordering
  parameters_cbor BLOB NOT NULL,                       -- initiator / source / destination / asset / amount
  applicable_operations SET('TRANSFER','CONTRACT_CALL','PROGRAM_CALL','TYPED_MESSAGE','RAW','MINT','BURN'),
                                                       -- ★ 어느 operation 에 적용. NULL = 모든 operation 에 적용
  action          ENUM('allow','approved_by','block') NOT NULL,
  designated_signer_user_group_id BINARY(16),          -- NS 흐름의 signer set
  approvers_user_group_id         BINARY(16),          -- Approved by 의 group
  approvers_threshold             INT,                  -- sub-quorum N
  approvers_logic                 ENUM('AND','OR') DEFAULT 'OR',  -- multi-group approval 간 logic (Authorization data model)
  allow_initiator_as_approver     BOOLEAN DEFAULT FALSE,           -- AuthorizationInfo.allowOperatorAsAuthorizer
  time_window_seconds             INT,                  -- velocity limit window
  cumulative_usd_cap              DECIMAL(38, 2),       -- velocity limit cap
  created_by      BINARY(16) NOT NULL,                  -- 이 rule 을 만든 actor (= policy version 의 initiator)
  created_at      DATETIME(6) NOT NULL,                 -- = 속한 policies.active_at
  UNIQUE KEY (policy_id, rule_number)
);
컬럼자료형역할
idBINARY(16) PKrule 의 고유 식별자
policy_idBINARY(16) FK이 rule 이 속한 Policy
rule_numberINTrule 평가 순서 (1, 2, 3 …). Policy 는 first-match — 위에서 아래로 평가하며 처음 매칭되는 rule 의 action 을 적용
parameters_cborBLOBrule 의 조건 (Parameters): initiator / source vault / destination / asset / amount range 등. CBOR 로 binary 직렬화 — 자유로운 구조 + byte-deterministic audit 가능
applicable_operationsSET (7 값)★ Fireblocks API operation body parameter 의 7 enum 중 어느 operation 에 본 rule 이 적용되는지. TRANSFER (default 자금 이동) / CONTRACT_CALL (EVM smart contract method) / PROGRAM_CALL (Solana program) / TYPED_MESSAGE (EIP-191 / EIP-712 / TIP-191 / BTC personal message) / RAW (off-chain raw signing) / MINT · BURN (Stellar / Ripple / EVM 의 token supply 변경). NULL = 모든 operation 에 적용
actionENUM (3 값)매칭 시 어떻게 처리할지. allow 그대로 통과 / approved_by 지정된 사람의 승인을 받고 통과 / block 차단
designated_signer_user_group_idBINARY(16) nullableNS 라벨이 적용된 rule 에서 어느 user group 이 designated signer 인지 지정. NULL = NS 흐름 미적용
approvers_user_group_idBINARY(16) nullableaction='approved_by' 일 때 누가 승인해야 하는지의 group
approvers_thresholdINT nullable그 group 안에서 sub-quorum N (예: "그룹의 2 명 승인" → 2). 단순 1 명 승인이면 NULL 또는 1
approvers_logicENUM('AND','OR')★ Authorization data model (Fireblocks API AuthorizationInfo.logic) — multiple authorization groups 간 boolean logic. OR (default) = 어느 group 이든 threshold 충족하면 승인 / AND = 모든 group 이 threshold 충족해야 승인. Stage 8 의 within-group 3/3 + across-group 1/N OR pattern 의 schema 표현
allow_initiator_as_approverBOOLEAN★ AuthorizationInfo.allowOperatorAsAuthorizer — initiator (transaction 시작한 user) 가 approver 가 될 수 있는지. default false (separation of duties 의 기본 원칙)
time_window_secondsINT nullablevelocity limit (속도 제한) 의 시간 window. 예: 600 = 10 분
cumulative_usd_capDECIMAL(38,2) nullabletime_window_seconds 안의 누적 USD 한도. 위 두 컬럼이 함께 작동해서 "10 분 안에 $50,000 초과 송금 시 차단" 같은 rule 표현
created_byBINARY(16)이 rule 을 만든 user — 즉 속한 policy version 의 변경을 시작한 actor. set-once
created_atDATETIME(6)이 rule 의 생성 시각. policy_rules 는 per-version immutable — 같은 rule 이 다음 version 에서 바뀌면 UPDATE 가 아니라 새 row INSERT 되므로 modified_by/at 가 별도로 필요 없음. set-once
UNIQUE (policy_id, rule_number)—같은 Policy 안에서 rule_number 중복 방지

9.3 policy_change_log — Policy 변경 이력 (append-only)

-- ★ append-only — 모든 Policy 변경의 audit trail
CREATE TABLE policy_change_log (
  id                            BINARY(16) PRIMARY KEY,
  policy_id                     BINARY(16) NOT NULL,
  prev_version                  INT,
  new_version                   INT NOT NULL,
  diff_cbor                     BLOB NOT NULL,           -- rule add/remove/edit 의 diff

  changed_at                    DATETIME(6) NOT NULL,
  mobile_app_approval_sigs      BLOB NOT NULL            -- mobile 서명 집합

컬럼자료형역할
idBINARY(16) PK이벤트 고유 식별자
policy_idBINARY(16) FK변경된 Policy
prev_versionINT nullable변경 전 version 번호. 최초 생성이면 NULL
new_versionINT변경 후 version 번호

changed_by_user_idBINARY(16)변경을 시작한 사용자 (Owner 또는 Admin-level)

mobile_app_approval_sigsBLOBOwner + Quorum 멤버 각자의 mobile 서명 집합. byte-equal cross-DB binding 으로 audit 평면과 정합

9.5 user_group_members — group 의 멤버 (junction · grant/revoke 패턴)

CREATE TABLE user_group_members (
  id         BINARY(16) PRIMARY KEY,
  group_id   BINARY(16) NOT NULL,
  user_id    BINARY(16) NOT NULL,
  granted_by BINARY(16) NOT NULL,
  granted_at DATETIME(6) NOT NULL,
  revoked_by BINARY(16),
  revoked_at DATETIME(6),
  KEY (group_id, user_id),
  KEY (group_id, revoked_at)
);
컬럼자료형역할
idBINARY(16) PKgrant 이벤트의 surrogate PK. revoke 후 재추가 시 새 row INSERT
group_idBINARY(16) FK어느 user_group 의 멤버인지
user_idBINARY(16) FK멤버 사용자
granted_by · granted_atBINARY(16) · DATETIME(6)멤버 추가 actor + 시각. set-once
revoked_by · revoked_atBINARY(16) nullable · DATETIME(6) nullable제거 actor + 시각. NULL = 현재 active. set-once when set
KEY (group_id, revoked_at)—"이 user_group 의 현재 active 멤버" 조회 인덱스 (WHERE revoked_at IS NULL)

BLOCKED rule number — tx 가 차단됐을 때 어느 rule 이 trigger 했는가

tx 가 BLOCKED status 에 도달했을 때, 어느 rule 이 차단했는지 추적 가능해야 운영자가 "왜 차단됐는지" 즉시 알 수 있습니다. transactions.blocked_by_rule_id + blocked_by_rule_number 컬럼이 그 정보를 저장 — 사용자는 console UI 에서 "Rule #3 (cumulative cap exceeded) 가 차단" 같이 명확히 볼 수 있음.
