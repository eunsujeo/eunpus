22. AML(?) · Travel Rule(?)

14-step 의 Step 5b/5c — AML provider 통합 · incoming reject lock · 별도 정책 평면
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • AML Provider 3 사 통합: Chainalysis · Elliptic · Notabene — Fireblocks 가 명시적으로 지원
  • 14-step Flow 의 Step 5b · 5c: 5b = AML screening (Transaction Manager → Screening Service → AML Provider), 5c = Travel Rule check. 두 검증 모두 통과 후에야 Policy Engine (Step 6) 진입
  • 3 정책 평면 분리: Fireblocks TAP (일반 tx rule) · AML Transaction Screening Policy · DCCP (confirmation 정책) — 같은 "policy" 이름이지만 별개 메커니즘
  • Workspace-level AML default 2 종: fail-on-unknown (모르는 destination 차단) vs pass-on-unknown (통과). Multi-workspace 가 필요한 이유 중 하나
  • Outgoing vs Incoming Rejected 차이: outgoing 은 즉시 재시도 가능, incoming 은 Admin unfreeze 까지 자금 lock
  • 변경 권한: AML / Travel Rule connections 및 policies 의 add/modify 는 Owner / Admin / NSA 3 role

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • aml_providers · aml_screening_results · travel_rule_records · rejected_incoming_assets 4 테이블의 구체 schema
  • api_credential_hsm_keyref 패턴 — AML provider API 자격증명을 HSM-wrapped 로 저장하는 보안 모델 (Fireblocks 내부 구현은 미명시)
  • raw_response_cbor 보존 — vendor response 원본 그대로 audit 위해 보존하는 패턴
  • rejected_incoming_assets 테이블 — Admin unfreeze 까지 lock 된 자산을 schema 차원에서 추적하는 별도 테이블 패턴

KR Travel Rule + 5년 기록보존 — Stage 37 확정 fact

KR 임계값 (Stage 37 ingest)
  • Travel Rule 임계 = 100만원 이상 (특금법 시행령 §10조의10). 한국 송·수신인 이름 정보 전송 의무. 실패 시 출고 차단. (source: KR_Custodial_Wallet_Compliance_Guide.pdf p.4 §31 · 1차: law.go.kr lspttninfSeq=82843)
  • 기록보존 최소 5년 (특금법 §5조의4). KYC 사본, 로그, 승인흐름, 모니터링 결과, 차단·해제 근거. (source: 동 p.4 §27 · 1차: law.go.kr lsiSeq=252787)
  • FATF 글로벌 임계 = $1,000 / EUR 1,000. 미국 FinCEN = $3,000. EU TFR 2023/1113 = 모든 거래 (2024-12-30 시행).
  • 신규 서비스 AML 위험평가 (특금법 §5 + 시행령 §9) — 신규 토큰·자산 등록 전 product risk committee. 코빗 NFT 신규지원 전 미실시 655건이 2025-12 종합검사에서 적발. (source: 동 p.5 §34, p.7 §48)

→ travel_rule_records 테이블의 threshold_satisfied 컬럼은 100만원 (KR) / $3,000 (US) / $1,000 (FATF) 등 jurisdiction 별 임계값을 별도 컬럼으로 분리 권장. 5년 archive 는 모든 AML evidence 테이블의 retention policy.

AML Provider 통합 — 3 사 지원

Fireblocks 는 외부 AML / Travel Rule 솔루션을 자체 구축하지 않고 통합 (integration) 방식으로 지원합니다. transaction-lifecycle.md p.4 다이어그램에 명시된 지원 provider:

  • Chainalysis — AML 분석
  • Elliptic — AML 분석
  • Notabene — Travel Rule 메시지 exchange

14-step Flow 안의 위치

AML / Travel Rule 검증은 tx 흐름의 어디에 끼어드는지 — 15. 14-Step Flow 의 Step 5b / 5c.

  • Step 5b — AML screening: Transaction Manager → Screening Service → AML Provider (Chainalysis / Elliptic)
  • Step 5c — Travel Rule check: Transaction Manager → Screening Service → Travel Rule Provider (Notabene)
  • 두 검증 모두 통과해야 다음 단계인 Policy Engine (Step 6) 으로 진입

3 정책 평면 분리 — 같은 "Policy" 이름이지만 다른 메커니즘

Fireblocks 는 "policy" 라는 단어를 3 개의 다른 시스템에 씁니다. 헷갈리지 않게 명확히 분리:

  • Fireblocks Policies (TAP(?)): 일반 tx 단위 rule (이 페이지 와 별개, 10. Policy · TAP 참조)
  • AML Transaction Screening Policy: AML provider 통합 — 본 페이지의 주제. 14-step Step 5b 에서 작동
  • DCCP(?): confirmation 횟수 정책 — 또 다른 평면. 18. Deposit 참조

Workspace-level AML Default — fail-on-unknown vs pass-on-unknown

workspace 단위로 "모르는 destination 을 어떻게 처리할지" 의 default 정책을 정합니다. 이 차이가 multi-workspace 운영이 필요한 이유 중 하나 — 같은 조직 안에 더 엄격한 workspace 와 더 유연한 workspace 를 동시에 운영하려면 분리가 필요.

  • fail-on-unknown: AML provider 가 모르는 destination 은 차단 — 보수적, 신원 명확한 거래만 진행
  • pass-on-unknown: 모르는 destination 은 통과 — 유연하지만 미식별 자금이 흘러갈 수 있음

Incoming Reject 의 Lock 상태 — Outgoing 과 다른 처리

⚠️ Outgoing vs Incoming Rejected — 자금 처리가 정반대
  • Outgoing rejected: 우리가 보낸 출금이 거절 → 자산이 우리 vault 에 그대로 있어 즉시 재시도 가능
  • Incoming rejected: 외부에서 들어온 입금이 AML 거절 → 자산이 이미 chain 상 우리 주소에 도착해 있지만 Admin 이 unfreeze 할 때까지 사용 불가. rejected_incoming_assets 테이블이 이 lock 을 추적

즉 incoming rejected 는 자금을 돌려보내는 게 아니라 lock 상태로 두고 Admin 의 후속 판단을 기다림. 운영팀이 별도 처리 path (zip line 운영 등) 필요.

변경 거버넌스

AML / Travel Rule 의 connection / policy 를 추가하거나 수정하는 권한 — Fireblocks 권한표의 다음 두 행에 해당:

  • Add or modify AML connections and policies: Owner / Admin / NSA ✓
  • Add or modify Travel Rule connections and policies: Owner / Admin / NSA ✓

즉 Editor / Signer / Approver / Viewer 등 일반 role 은 AML 설정에 손댈 수 없음.

DB Schema

6.1 aml_providers — workspace 가 통합한 AML provider 설정

CREATE TABLE aml_providers (
  id                        BINARY(16) PRIMARY KEY,
  workspace_id              BINARY(16) NOT NULL,
  provider_name             ENUM('chainalysis','elliptic','notabene') NOT NULL,
  endpoint_url              VARCHAR(255) NOT NULL,
  api_credential_hsm_keyref VARCHAR(128) NOT NULL,    -- ★ HSM-wrapped, never plaintext
  default_policy            ENUM('fail-on-unknown','pass-on-unknown') NOT NULL,
  enabled_by                BINARY(16) NOT NULL,
  enabled_at                DATETIME(6) NOT NULL,
  disabled_by               BINARY(16),
  disabled_at               DATETIME(6),
  UNIQUE KEY (workspace_id, provider_name)
);
컬럼자료형역할
idBINARY(16) PKprovider 통합 설정의 고유 식별자
workspace_idBINARY(16) FK이 통합이 속한 workspace. UNIQUE 와 결합되어 한 workspace 가 같은 provider 를 중복 통합 못 함
provider_nameENUM (3 값)Chainalysis · Elliptic · Notabene 중 하나
endpoint_urlVARCHAR(255)provider 의 API endpoint
api_credential_hsm_keyrefVARCHAR(128)HSM-wrapped API 자격증명 reference — plaintext 절대 저장 안 함
default_policyENUM (2 값)fail-on-unknown 모르는 destination 차단 / pass-on-unknown 통과
enabled_by · enabled_atBINARY(16) · DATETIME(6)활성화한 actor + 시각. set-once
disabled_by · disabled_atBINARY(16) nullable · DATETIME(6) nullable비활성화 actor + 시각. NULL = 현재 활성

6.2 aml_screening_results — 각 tx 의 AML 평가 결과 (append-only)

-- ★ append-only
CREATE TABLE aml_screening_results (
  id                BINARY(16) PRIMARY KEY,
  transaction_id    BINARY(16) NOT NULL,
  provider_id       BINARY(16) NOT NULL,
  direction         ENUM('incoming','outgoing') NOT NULL,
  risk_score        DECIMAL(5, 2),
  risk_category     VARCHAR(64),                       -- ★ provider 의 risk category 이름 (예: "Darknet Market", "Mixer")
  category_id       INT,                                -- ★ Chainalysis 등 provider 의 numeric category ID
  external_id       VARCHAR(128),                       -- ★ provider 측 screening result ID (cross-system trace)
  matched_alert     VARCHAR(256),                       -- ★ matched rule 에 해당하는 alert 이름
  matched_rule_id   BINARY(16),                         -- ★ AML Post-Screening Policy rule (FK)
  matched_prescreening_rule_id BINARY(16),              -- ★ AML Transaction Screening Policy rule (Pre-Screening)
  bypass_reason     VARCHAR(256),                       -- ★ bypass 처리 시 reason (예: "whitelisted internal", "amount below threshold")
  decision          ENUM('allow','block','manual-review','bypass') NOT NULL,  -- bypass 추가
  raw_response_cbor BLOB NOT NULL,                    -- vendor response 보존
  screened_at       DATETIME(6) NOT NULL,
  KEY (transaction_id),
  KEY (provider_id, screened_at),
  KEY idx_external_id (provider_id, external_id)        -- provider 측 lookup
);
컬럼자료형역할
idBINARY(16) PKscreening 이벤트 식별자
transaction_idBINARY(16) FK심사 대상 tx
provider_idBINARY(16) FK이 심사를 수행한 AML provider
directionENUM (2 값)incoming 입금 심사 / outgoing 출금 심사
risk_scoreDECIMAL(5,2) nullableprovider 가 산정한 위험 점수. provider 마다 scale 다름 (보통 0~100)
decisionENUM (3 값)최종 판단 — allow 통과 / block 차단 / manual-review 수동 검토 필요
raw_response_cborBLOBprovider 의 raw response 원본 (CBOR 직렬화) — 사후 audit 가능하도록 가공 전 데이터 그대로 보존
screened_atDATETIME(6)심사 시각

6.3 travel_rule_records — Travel Rule 메시지 교환 (append-only)

-- ★ append-only — Travel Rule message 보존 (counterparty exchange)
CREATE TABLE travel_rule_records (
  id                    BINARY(16) PRIMARY KEY,
  transaction_id        BINARY(16) NOT NULL,
  provider_id           BINARY(16) NOT NULL,
  direction             ENUM('outbound','inbound') NOT NULL,
  originator_info_cbor  BLOB NOT NULL,                 -- VASP info
  beneficiary_info_cbor BLOB NOT NULL,
  vasp_message_id       VARCHAR(128),
  status                ENUM('pending','sent','acked','rejected') NOT NULL,
  verdict               ENUM('ACCEPT','REJECT','ALERT','WAIT','FREEZE','CANCEL'),  -- ★ provider screening verdict
  exchanged_at          DATETIME(6) NOT NULL,
  KEY (transaction_id)
);
컬럼자료형역할
idBINARY(16) PKTravel Rule 레코드 식별자
transaction_idBINARY(16) FK대상 tx
provider_idBINARY(16) FKTravel Rule provider (보통 Notabene)
directionENUM (2 값)outbound 우리가 counterparty 에게 보냄 / inbound counterparty 에게서 받음
originator_info_cborBLOB송금자의 VASP (가상자산 사업자) 정보 — 이름 / 주소 / 식별번호 등
beneficiary_info_cborBLOB수취인의 VASP 정보
vasp_message_idVARCHAR(128) nullableprovider 가 발급한 메시지 id (cross-VASP 추적용)
statusENUM (4 값)pending 발송 전 / sent 발송 / acked counterparty 가 ACK / rejected counterparty 거절. message exchange protocol 의 transport 상태
verdictENUM (6 값) nullable★ Fireblocks API TravelRuleScreeningResult.verdict 의 정식 6 종 — ACCEPT 통과 / REJECT 차단 / ALERT 경고 (운영자 확인) / WAIT 대기 (자동 escalation) / FREEZE 동결 (asset lock) / CANCEL 취소. status 가 transport-layer 라면 verdict 는 application-layer 판단. WAIT / FREEZE 는 manual escalation lane
exchanged_atDATETIME(6)메시지 교환 시각

6.4 rejected_incoming_assets — Admin unfreeze 대기 자산 추적

-- Incoming reject 의 asset lock 추적
CREATE TABLE rejected_incoming_assets (
  id                  BINARY(16) PRIMARY KEY,
  transaction_id      BINARY(16) NOT NULL UNIQUE,
  asset_wallet_id     BINARY(16) NOT NULL,
  amount_decimal      DECIMAL(38, 18) NOT NULL,
  rejected_at         DATETIME(6) NOT NULL,
  unfreeze_attempts   INT NOT NULL DEFAULT 0,
  unfrozen_at         DATETIME(6),                     -- ★ set-once
  unfrozen_by_user_id BINARY(16),                      -- Admin
  KEY (asset_wallet_id, unfrozen_at)
);
컬럼자료형역할
idBINARY(16) PKlock 추적 row 식별자
transaction_idBINARY(16) UNIQUE FK거절된 incoming tx. UNIQUE — 한 tx 의 lock 은 한 row 만
asset_wallet_idBINARY(16) FK자산이 도착해 있는 asset wallet
amount_decimalDECIMAL(38, 18)lock 된 자금의 양
rejected_atDATETIME(6)AML 거절 시각 = lock 시작
unfreeze_attemptsINTunfreeze 시도 횟수 — 운영팀이 검토 후 진행/거부한 횟수
unfrozen_atDATETIME(6) nullableAdmin 이 최종 unfreeze 한 시각. set-once. NULL = 여전히 lock
unfrozen_by_user_idBINARY(16) nullableunfreeze 를 실행한 Admin (audit 의 핵심 — "누가 lock 을 풀었나")

  Note over TM,DB: 14-step Step 5 — AML + Travel Rule 검증 (Step 5b / 5c)

  TM->>SS: tx + direction (outgoing/incoming) 전달

  par 5b — AML screening
    SS->>AML: source · destination · amount 전달
    AML->>AML: blockchain analytics + sanctions check
    AML->>SS: risk_score + decision (allow/block/manual-review)
    SS->>DB: aml_screening_results INSERT (raw_response_cbor 보존)
  and 5c — Travel Rule check
    SS->>TR: originator_info + beneficiary_info 메시지
    TR->>TR: VASP counterparty 와 exchange
    TR->>SS: status (sent/acked/rejected)
    SS->>DB: travel_rule_records INSERT
  end

  alt 두 검증 모두 allow
    SS->>TM: 통과
    TM->>PE: Step 6 진입 (Policy Engine 평가)
  else AML block (outgoing)
    SS->>TM: blocked
    TM->>DB: transactions.status = BLOCKED
  else AML block (incoming)
    Note over TM,DB: ⚠️ Incoming 거절은 특수 처리
    SS->>TM: blocked
    TM->>DB: rejected_incoming_assets INSERT (asset lock 시작)
    TM->>DB: transactions.status = REJECTED
    Note over DB: 자산이 chain 상 도착해 있음
Admin unfreeze 까지 사용 불가
  else AML manual-review
    SS->>TM: 수동 검토 큐로 routing
    Note over TM: 운영팀 별도 검토 후 manual decision
  end

FSPM(?) — Fireblocks Security Posture Management

Security Auditor / Security Admin 의 권한 영역인 Security Center 화면 + findings 관리 기능. AI 기반 attack simulator 와 security finding 들을 통합 관리. 다만 본 자료에는 entity-grade 명세 (어떤 finding 이 어떤 schema 로 영속화되는지) 가 충분히 제공되어 있지 않아 본 페이지의 schema 범위는 위 4 테이블까지로 한정.
