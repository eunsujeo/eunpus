5. Wallets · Addresses · Asset Wallet

정식 매핑 — 3 asset 패턴 · whitelisted address · chain 별 특이 제약

Vault → Asset Wallet → Address 의 관계도 (chain 별 3 패턴 포함) 는 3. Workspace 페이지의 Figure 16 에서 cluster 전체 hierarchy 와 함께 다룹니다 — 본 페이지는 그 도식의 마지막 단계 (asset_wallets → addresses 의 chain × asset 패턴) 를 schema 차원에서 풀어쓰는 데 집중.

DB Schema

⚠️ 본 페이지의 테이블이 분포하는 DB — 3 개 DB 횡단

본 페이지는 wallet · address 도메인을 다루지만, 등장하는 테이블은 3 개 DB 에 분산되어 있습니다. 운영 query 시 어느 DB 에 접속해야 하는지 사전 확인 필수.

DB소속 테이블이유
walletdb (대다수)asset_wallets · addresses · asset_wallet_public_keys · whitelisted_addresses · one_time_addresses · chains · network_connections · exchange_accounts · fiat_accounts지갑 metadata + 외부 counterparty registry(?) — mutable. 외부 system 매핑이지만 workspace-level 의 거버넌스 (Admin Quorum 승인) 대상이라 providerdb 가 아닌 walletdb 에 위치

잘 헷갈리는 부분: fiat_accounts · exchange_accounts · network_connections 가 "외부 system 매핑" 이라 providerdb 로 갈 거 같지만 walletdb 에 위치합니다 — workspace-level Admin Quorum 승인 대상이라 governance 평면과 같은 DB. providerdb 는 AML provider · IdP 같은 infrastructure-level 외부 시스템에만 쓰입니다. 자세한 분기 근거는 2. DB 분할.

CREATE TABLE asset_wallets (
  id                BINARY(16) PRIMARY KEY,
  vault_account_id  BINARY(16) NOT NULL,
  chain             VARCHAR(32) NOT NULL,            -- 'BTC', 'ETH', 'SOL', ...
  asset_id          VARCHAR(64) NOT NULL,            -- 'BTC', 'ETH', 'USDC_ETH', ...
  asset_pattern     ENUM('utxo', 'account-no-tag', 'account-tag') NOT NULL,
  permanent_address VARCHAR(128),                    -- UTXO 만 set
  created_by        BINARY(16) NOT NULL,             -- "Add asset wallet" 을 누른 user
  created_at        DATETIME(6) NOT NULL,
  UNIQUE KEY (vault_account_id, asset_id),
  KEY (chain)
);

CREATE TABLE addresses (
  id              BINARY(16) PRIMARY KEY,
  asset_wallet_id BINARY(16) NOT NULL,
  address_string  VARCHAR(128) NOT NULL,
  legacy_address  VARCHAR(128),                      -- BTC/LTC/BCH legacy format (Segwit Bech32 ↔ legacy)
  tag_or_memo     VARCHAR(64),                       -- chain-specific 분기자:
                                                      --   XRP destination tag / EOS·HBAR·XDB memo /
                                                      --   XLM memo_text / ALGO notes / Fiat bank transfer description
  eos_account_name VARCHAR(64),                       -- ★ EOS account-based 식별자 (Fireblocks API CreateVaultAssetResponse.eosAccountName)
  description     VARCHAR(256),                      -- 사람이 읽는 주소 설명 (선택)
  address_type    ENUM('deposit', 'change', 'permanent') NOT NULL,
  derivation_index INT,                              -- UTXO 의 deposit address index (= bip44AddressIndex)
  bip44_change    TINYINT,                            -- BIP44 change path level (UTXO change address)
  customer_ref_id VARCHAR(128),                      -- AML provider 가 funds owner 식별용 (선택)
  deactivated_at  DATETIME(6),
  created_at      DATETIME(6) NOT NULL,              -- ★ system-generated (cryptographic derivation), 인간 actor 없음 — created_by 컬럼 없음
  KEY (asset_wallet_id, address_type),
  UNIQUE KEY (address_string, tag_or_memo)
);

-- ★ asset_wallet 단위 BIP32 root key + derivation 메타. 실제 public key 만 보관 (private 은 forbidden storage)
CREATE TABLE asset_wallet_public_keys (
  asset_wallet_id BINARY(16) PRIMARY KEY,             -- 1:1 with asset_wallets
  algorithm       ENUM('MPC_ECDSA_SECP256K1','MPC_EDDSA_ED25519','MPC_ECDSA_SECP256R1') NOT NULL,
  public_key      VARBINARY(65) NOT NULL,             -- compressed (33B SECP256K1) / 32B Ed25519 / 65B uncompressed
  derivation_path JSON NOT NULL,                       -- BIP32 derivation path array (예: [44, 0, 0, 0, 0])
  created_at      DATETIME(6) NOT NULL
);

-- ★ UTXO unspent inputs cache (M-cache). UTXO 자산의 input 선택 / consolidation 운영용
CREATE TABLE unspent_inputs (
  id              BINARY(16) PRIMARY KEY,
  asset_wallet_id BINARY(16) NOT NULL,
  tx_hash         VARCHAR(128) NOT NULL,              -- UTXO 가 들어 있는 tx hash
  vout_index      INT NOT NULL,                        -- 그 tx 의 output 위치
  address_string  VARCHAR(128) NOT NULL,
  amount_decimal  DECIMAL(38, 18) NOT NULL,
  confirmations   INT NOT NULL,                        -- chain 측 confirmation 수
  status          ENUM('unconfirmed','confirmed','spent','reserved') NOT NULL,
  spent_in_tx_id  BINARY(16),                          -- 사용된 tx 의 id (spent 상태일 때 set)
  refreshed_at    DATETIME(6) NOT NULL,
  KEY (asset_wallet_id, status),
  UNIQUE KEY (tx_hash, vout_index)
);

★ asset_wallet_public_keys 는 Fireblocks API vault-objects.PublicKey (publicKey + algorithm + derivationPath) 와 정합. asset_wallet 별 root public key 를 보관해서 (a) audit 시 address 가 정말 그 키에서 derived 됐는지 검증 가능, (b) external 시스템에 public key 공개 시 standardized. Private key 자체는 forbidden storage — MPC share 분포 spine 외에는 어떤 형태로도 영속화 금지.

★ unspent_inputs 는 Fireblocks API vault-objects.UnspentInputsData 와 정합. UTXO 의 input 선택 (`InputsSelection.inputsToSpend` / `inputsToExclude`) 운영 + `consolidate-utxos` workflow 의 schema 표현. Confirmation 수 추적으로 DCCP (Deposit Control and Confirmation Policy) 와도 연동. M-cache class — canonical source 는 chain 의 mempool/UTXO set.

-- ★ M-cache class — canonical source = blockchain. derived/refreshed values. CREATE TABLE asset_balances ( asset_wallet_id BINARY(16) PRIMARY KEY, -- 1:1 with asset_wallets total DECIMAL(40, 20), -- VaultAsset.total — 전체 잔액 (cache) available DECIMAL(40, 20), -- = total − lockedAmount, 사용 가능 amount pending DECIMAL(40, 20), -- pending tx 의 cumulative staked DECIMAL(40, 20), -- staked funds (DOT 등 일부 chain only) frozen DECIMAL(40, 20), -- ★ workspace AML policy 가 freeze 한 amount (per-asset, workspace freeze 와 별개) locked_amount DECIMAL(40, 20), -- outgoing tx, broadcast 전 묶인 amount block_height BIGINT, -- cache 시점의 chain block 높이 block_hash VARCHAR(128), -- 그 시점의 block hash (reorg 감지용) updated_at DATETIME(6) NOT NULL, KEY (updated_at) );

★ asset_balances 는 M-cache class — canonical source 는 blockchain, DB 는 view 캐시. `frozen` 은 AML policy 의 per-asset 동결 (workspace-level freeze 와 별개 의미). `balance` 라는 단일 컬럼 대신 7-way 분해 (total / available / pending / staked / frozen / locked_amount + block 정보) — Fireblocks API 의 VaultAsset schema 와 정합. 운영 측 query 는 보통 available 을 사용하고, audit 은 total 과 block_hash 로 reorg-aware 검증.

Whitelisted Address — Vault 외부 송금 대상 목록

Vault address 는 workspace 안의 vault 가 보유한 address (입금·출금·잔액 보관·on-chain 식별 모두 거기), whitelisted address 는 외부로 송금할 목적지 를 Admin Quorum(?) 승인으로 사전 등록해둔 화이트리스트. 두 개념은 가리키는 대상이 다름.

Type의미workspace(?) 잔액 표시
Internal같은 workspace 의 다른 user/team 의 외부 wallet표시
External외부 organization 의 wallet표시 안 됨
Contract / ProgramEVM smart contract 주소 또는 Solana Program ID (base58). 자산 수령 wallet 이 아닌 callable 대상 — DApp interaction (DEX swap / DeFi staking / NFT mint 등) 출금에 사용. Solana 의 user wallet / token account 는 Contract 아님 (Internal/External 로 등록)—
 
CREATE TABLE whitelisted_addresses (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  type            ENUM('internal', 'external', 'contract') NOT NULL,
  asset_id        VARCHAR(64) NOT NULL,
  address_string  VARCHAR(128) NOT NULL,
  tag_or_memo     VARCHAR(64),
  label           VARCHAR(128),
  status          ENUM('PENDING','APPROVED','ACTIVE','REJECTED','EXPIRED') NOT NULL DEFAULT 'PENDING',  -- ★ ConfigChangeRequestStatus
  activation_time DATETIME(6),                         -- ★ cooling-off period 종료 시각 — 그 시각 이후 ACTIVE
  customer_ref_id VARCHAR(128),                        -- AML provider 가 owner 식별용 (선택)
  created_by      BINARY(16) NOT NULL,                -- 등록 request 를 시작한 user (initiator)
  approved_by_quorum_id BINARY(16) NOT NULL,          -- Admin Quorum approval 의무
  approved_at     DATETIME(6) NOT NULL,
  KEY (workspace_id, type)
);

CREATE TABLE one_time_addresses (
  -- OTA = whitelist 우회 path. Address-level quorum 없음, Policy 가 유일한 방어선
  -- ★ row 는 사용 시점에 INSERT 됨 — used_at 이 created_at semantic 과 동일
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  used_in_tx_id   BINARY(16) NOT NULL,
  address_string  VARCHAR(128) NOT NULL,
  used_at         DATETIME(6) NOT NULL
);

-- ★ Fireblocks P2P Network counterparty registry
-- destination_type='NETWORK_CONNECTION' 의 실제 peer 정보
CREATE TABLE network_connections (
  id                    BINARY(16) PRIMARY KEY,
  workspace_id          BINARY(16) NOT NULL,
  network_connection_id VARCHAR(32) NOT NULL,        -- Fireblocks API 의 connection ID
  local_network_id      CHAR(8) NOT NULL,            -- Fireblocks NetworkId (8 chars)
  local_network_name    VARCHAR(128) NOT NULL,
  remote_network_id     CHAR(8) NOT NULL,
  remote_network_name   VARCHAR(128) NOT NULL,
  is_discoverable       BOOLEAN NOT NULL DEFAULT FALSE,
  -- Routing policy (3 scheme)
  crypto_routing_scheme ENUM('DEFAULT','CUSTOM','NONE') NOT NULL,
  fiat_routing_scheme   ENUM('DEFAULT','CUSTOM','NONE'),
  -- CUSTOM scheme 일 때만 set
  custom_crypto_dst_type ENUM('VAULT','EXCHANGE'),
  custom_crypto_dst_id   VARCHAR(64),
  custom_fiat_dst_id     VARCHAR(64),                -- FIAT_ACCOUNT
  created_by            BINARY(16) NOT NULL,
  approved_by_quorum_id BINARY(16) NOT NULL,         -- counterparty 등록은 quorum-gated
  approved_at           DATETIME(6) NOT NULL,
  status                ENUM('PENDING','ACTIVE','PAUSED','REMOVED') NOT NULL DEFAULT 'PENDING',
  KEY (workspace_id, status),
  UNIQUE KEY (workspace_id, network_connection_id)
);

-- ★ Exchange account registry (destination_type='EXCHANGE_ACCOUNT' 의 실제 계좌)
CREATE TABLE exchange_accounts (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  provider        VARCHAR(64) NOT NULL,              -- 'BINANCE', 'COINBASE', 'KRAKEN' 등
  account_label   VARCHAR(128) NOT NULL,
  api_credentials_encrypted_id BINARY(16),           -- 외부 key vault 의 reference (절대 plaintext 금지)
  status          ENUM('PENDING','ACTIVE','PAUSED','REMOVED') NOT NULL,
  created_by      BINARY(16) NOT NULL,
  approved_by_quorum_id BINARY(16) NOT NULL,
  approved_at     DATETIME(6) NOT NULL,
  KEY (workspace_id, status)
);

-- ★ Fiat account registry (destination_type='FIAT_ACCOUNT' 의 실제 계좌)
CREATE TABLE fiat_accounts (
  id                  BINARY(16) PRIMARY KEY,
  workspace_id        BINARY(16) NOT NULL,
  provider            VARCHAR(64) NOT NULL,          -- 'SIGNATURE_BANK', 'BCB_GROUP', 'CIRCLE_USDC' 등
  account_label       VARCHAR(128) NOT NULL,
  account_identifier  VARCHAR(128),                  -- IBAN / routing number 등 (민감 시 별도 vault 권장)
  currency            CHAR(3) NOT NULL,              -- ISO 4217 (USD/EUR/KRW 등)
  status              ENUM('PENDING','ACTIVE','PAUSED','REMOVED') NOT NULL,
  bank_transfer_desc  VARCHAR(256),                  -- Fireblocks API 의 fiat tag 와 정합
  created_by          BINARY(16) NOT NULL,
  approved_by_quorum_id BINARY(16) NOT NULL,
  approved_at         DATETIME(6) NOT NULL,
  KEY (workspace_id, status, currency)
);

★ network_connections 는 Fireblocks P2P Network 의 counterparty registry — destination_type='NETWORK_CONNECTION' 의 실제 peer 정보. 4 routing scheme (`DEFAULT`/`CUSTOM`/`NONE` × crypto/fiat) 가 Fireblocks API NetworkConnectionRoutingPolicy 와 정합. counterparty 등록은 Admin Quorum 승인 강제 (legal counterparty 책임).

★ exchange_accounts / fiat_accounts 는 외부 자산 channel 의 registry. API credentials / account number 같은 민감 정보는 본 schema 에 plaintext 저장 금지 — 별도 key vault 의 reference id 만 보관. Currency (ISO 4217) 는 fiat account 의 1차 분기 key.

본 schema 의 범위 밖 — 후속 검토 위치

아래 두 항목은 whitelisted_addresses 단독으로는 다루지 않고, 다른 평면에서 처리하도록 분리합니다. 이 페이지의 schema 를 단순하게 유지하기 위함.

  • Method whitelist (Contract type 의 함수 호출 제어) — Contract address 만 등록하면 "어떤 contract" 는 막아도 "그 contract 의 어떤 함수를 어떤 인자로" 는 못 막음. DApp interaction 출금 운영 시 method/function selector + argument constraint whitelist 가 한 layer 더 필요. → 10. Policy 의 Policy rule 평면
  • Approver-level audit trail (N-of-M 의 specific signatures) — 본 schema 의 approved_by_quorum_id 는 quorum 자체의 id 만 가리키므로 "그 시점에 누가 sign 했는지" 의 trail 이 없음. Quorum membership 이 시간에 따라 바뀌므로 historical signer trail 은 별도 audit 평면에서 보존 필요. → 20. Cross-DB Audit 의 approval_decisions (approver 별 mobile_device_sig) + audit_events hash chain 패턴

Chain 별 특이 제약 — DB schema 에 어떻게 흡수되는가

Asset 패턴 (UTXO / account / account+tag) 위에 한 layer 더. 각 chain 마다 다른 디테일 제약 — 최소 잔액, 최소 송금 금액, account 활성화 보증금, trust line, token wallet 권한 등 — 을 Fireblocks 가 어떻게 schema 컬럼으로 흡수하는지 정리. 마지막 컬럼 "DB 에 미치는 영향" 이 핵심.

chains Lookup Table — chain-level static config 의 single source-of-truth

위의 "Chain 별 특이 제약" 표의 거의 모든 행이 가리키던 home. 각 chain 의 type/모델/최소값/플래그/제약값을 한 row 로 모아둠. asset_wallets 등 다른 테이블이 chain 단위 설정을 읽을 때 JOIN/lookup 대상.

CREATE TABLE chains (
  id                       VARCHAR(32) PRIMARY KEY,    -- 'BTC','ETH','XRP','XLM','SOL',...
  display_name             VARCHAR(128) NOT NULL,
  type                     ENUM('utxo','evm','non_evm_account','cosmos_sdk') NOT NULL,
  account_model            ENUM('utxo','account_no_tag','account_with_tag') NOT NULL,
  min_tx_amount            DECIMAL(40,20),             -- chain 의 최소 송금 금액 default
  base_reserve_minimum     DECIMAL(40,20),             -- 활성 유지를 위한 최소 잔액
  requires_activation      BOOLEAN NOT NULL DEFAULT FALSE,   -- Stellar / Polkadot / Near 등
  activation_minimum       DECIMAL(40,20),             -- 활성화 보증금 (예: 1 XLM)

운영 노트 — chain config 의 변경 경로

  • 제약 값 변경 (예: BTC 가 mempool default 를 25 → N 으로 변경) : UPDATE + change_events 1 row + 20. Cross-DB Audit 의 hash chain

Figure 20. 단일 vault 의 sequential bottleneck (EVM nonce gap · BTC 25-chain) vs 분산 round-robin. 위 — 한 tx 가 막히면 뒤가 다 멈춤. 아래 — 같은 출금 흐름을 N 개의 독립 vault 로 분산하면 한 vault 가 정체돼도 나머지는 정상 진행. Solana 는 다름 — per-vault 5 는 hard stuck 이 아니라 soft throttle (Submitted 대기). 1 vault 로도 운영 가능, burst > 5/vault 일 때만 보조용 round-robin.
EVM (Ethereum · Polygon · Arbitrum 등)
같은 주소에서 출금하는 tx 는 0, 1, 2, 3 … 순서 번호 (nonce(?)) 를 반드시 순서대로 처리합니다. 한 tx 가 멈추면 (수수료 부족으로 채굴자가 안 집어감 등) 그 뒤 번호의 tx 가 전부 대기 상태로 묶입니다. 출금 vault 가 하나라면 그 vault 의 출금 전체가 멈춥니다.
→ 출금 전용 vault 를 여러 개 두고 돌아가며 사용하면 (round-robin), 한 vault 가 막혀도 나머지로 출금이 계속 흐릅니다.
Bitcoin
아직 block 에 확정되지 않은 tx 는 Bitcoin 네트워크의 임시 보관소 (mempool) 에 쌓입니다. 한 tx 의 잔돈 (change) 을 다음 tx 의 입력으로 이어 쓰는 chain 이 25 개에 도달하면, 26 번째 tx 는 네트워크가 거부합니다 (Bitcoin Core 기본 설정(?)). block 확정까지 평균 10 분, 그 사이 빠르게 연속 출금하면 한 vault 가 25 limit 에 부딪혀 출금이 막힙니다.
→ 출금 vault 를 여러 개로 분산해서 각각의 chain 이 25 에 부딪히지 않도록.
Solana
제약이 두 단계입니다.
  • vault 한 개당 동시 5 tx: 6 번째 출금 요청은 "Submitted" 상태로 줄을 서고, 최대 2 시간 안에 처리되지 않으면 자동 취소됩니다.
  • workspace 전체에서 동시 600 tx: 한 workspace 안의 모든 vault 의 진행 중 tx 합이 600 개를 넘으면 추가 요청을 안 받습니다.
EVM/BTC 와 결정적으로 다른 점 — 5 를 초과해도 tx 가 막히는 게 아니라 "기다리는" 상태일 뿐입니다 (앞 tx 가 끝나면 자동으로 다음 차례로). 즉 출금 vault 1 개로도 충분히 운영 가능합니다.
→ vault 여러 개로 나누는 것은 짧은 시간에 출금 요청이 갑자기 한꺼번에 몰릴 때 (예: 정각마다 일괄 자동 출금이 도는 운영에서 한 vault 의 5 한도를 넘길 가능성이 있는 경우) 에만 보조적으로 의미가 있습니다.
