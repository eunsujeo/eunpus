21. Lifecycle Events (Add / Edit)

User · Device · Owner identity 의 생성·수정·역할변경·삭제·재인증·이전
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • Add/Edit 의 거버넌스 비대칭: Add/Edit 는 mobile 비동기 + 7-day expiry 의 Q (Owner + Admin Quorum) 흐름, Delete 는 기본 Owner-only 즉시 처리 (mobile approval 없음)
  • User 의 6 lifecycle event: Add (Console/API/signing role) · Edit (name/email) · Role change (Console 직접 불가) · Delete (default/위임)
  • Device 의 6 lifecycle event: Re-enroll · Device migration · 2FA reset (타인/Owner 본인) · Recovery passphrase reset (Admin·Signer/Owner)
  • Workspace 의 4 lifecycle event: Freeze (모든 role Viewer 강제) / Unfreeze (Owner only via Support) / Transfer Owner (양 Owner 영상 통화, 3-5 영업일) / Owner 부재 시 Board resolution
  • Owner-only via Support 경유 의 4 가지: Owner 본인 2FA reset · Workspace unfreeze · Recovery passphrase reset · Owner transfer — 영상 통화 신원 확인 필수, Console UI 로 직접 불가

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • lifecycle_events · user_setup_progress 두 테이블의 구체 schema
  • event_type VARCHAR 의 자유 텍스트 정형화 (운영 시 ENUM 권장)
  • via_support_ticket 컬럼 — Fireblocks Support 경유 증빙을 schema 차원에 기록하는 패턴 (Fireblocks 내부에서 어떻게 표현하는지는 미명시)
  • signing_role_extra_approval BOOLEAN — MPC key share derivation 의 별도 Owner 승인 여부를 column 으로 정형화

핵심 비대칭

Add/Edit vs Delete 의 거버넌스 비대칭

Add / Edit: 모바일 기반 비동기 승인 (Q = Owner + Admin Quorum(?)), 7-day expiry
Delete: 기본 Owner-only, 즉시, mobile approval 없음

DB Schema

4.1 lifecycle_events — user / device / workspace 의 lifecycle 이력 (append-only)

-- ★ append-only — lifecycle 이력은 audit-grade
CREATE TABLE lifecycle_events (
  id                          BINARY(16) PRIMARY KEY,
  workspace_id                BINARY(16) NOT NULL,
  event_type                  VARCHAR(64) NOT NULL,        -- 'user-add', 'user-edit', 'user-delete',
                                                           --  'device-re-enroll', 'device-migration',
                                                           --  '2fa-reset', 'passphrase-reset',
                                                           --  'workspace-freeze', 'workspace-unfreeze',
                                                           --  'owner-transfer'
  target_aggregate_type       VARCHAR(64) NOT NULL,        -- 'user', 'device', 'workspace'
  target_aggregate_id         BINARY(16) NOT NULL,
  actor_user_id               BINARY(16),                  -- self-service 면 target 와 같음
  via_support_ticket          VARCHAR(64),                 -- Fireblocks Support 경유 증빙
  approval_request_id         BINARY(16),                  -- Q / Q+O 흐름의 approval
  signing_role_extra_approval BOOLEAN NOT NULL DEFAULT FALSE, -- MPC derivation 별도 승인 여부
  initiated_at                DATETIME(6) NOT NULL,
  completed_at                DATETIME(6),                 -- ★ set-once
  KEY (workspace_id, event_type, initiated_at),
  KEY (target_aggregate_id)
);
컬럼자료형역할
idBINARY(16) PK이벤트 고유 식별자
workspace_idBINARY(16) FK이벤트가 속한 workspace
event_typeVARCHAR(64)10+ 종류의 lifecycle 이벤트 (user-add, device-re-enroll, 2fa-reset, workspace-freeze 등). 운영 시 ENUM 으로 정형화 권장
target_aggregate_type · target_aggregate_idVARCHAR(64) · BINARY(16)이벤트의 대상 — user / device / workspace 중 하나의 entity
actor_user_idBINARY(16) nullable이벤트를 실제 trigger 한 user. self-service path (device migration 등) 면 target_aggregate_id 와 같음. Support 경유 이벤트는 NULL 가능
via_support_ticketVARCHAR(64) nullableFireblocks Support 경유 시 ticket 번호 (Owner 본인 2FA reset · workspace unfreeze · Owner transfer 등 4 케이스). NULL = Support 경유 아님
approval_request_idBINARY(16) nullable FKQ / Q+O 흐름을 거친 이벤트의 approval_requests 참조. self-service / Support-경유 path 는 NULL
signing_role_extra_approvalBOOLEANsigning role 추가 시 Owner 가 MPC key share derivation 을 별도 승인했는지 — 일반 user add 와 signing user add 를 구분하는 플래그
initiated_atDATETIME(6)이벤트 시작 시각. set-once
completed_atDATETIME(6) nullable이벤트 완료 시각. set-once. NULL = 진행 중 (예: 7-day Q approval 의 pending)

4.2 user_setup_progress — user 의 초기 setup 4 단계 추적

CREATE TABLE user_setup_progress (
  user_id             BINARY(16) PRIMARY KEY,
  invited_at          DATETIME(6) NOT NULL,
  mobile_paired_at    DATETIME(6),
  mpc_key_approved_at DATETIME(6),                     -- ★ Owner 의 별도 승인
  activated_at        DATETIME(6),                     -- ★ set-once
  expires_at          DATETIME(6) NOT NULL             -- 7-day expiry
);
컬럼자료형역할
user_idBINARY(16) PK / FK이 setup 의 user. user 1 명당 1 row (PK 가 user_id 자체)
invited_atDATETIME(6)① 초대 메일 발송 시각. set-once
mobile_paired_atDATETIME(6) nullable② mobile app 등록 + 페어링 완료 시각. NULL = 아직 mobile setup 안 됨
mpc_key_approved_atDATETIME(6) nullable③ signing role 의 경우 Owner 가 MPC key share derivation 을 별도 승인한 시각. 일반 role 은 NULL
activated_atDATETIME(6) nullable④ 모든 setup 완료, user 가 active 상태로 전환된 시각. set-once. NULL = pending
expires_atDATETIME(6)invited_at + 7-day. 이 시각까지 setup 미완료 시 자동 expire — pending row 가 영구 남지 않도록

Status 전이

users.status:
  pending → active        (initial setup 완료)
  active  → deleted       (즉시 박탈, row 유지)
  active  → frozen-viewer (workspace freeze 시 implicit)
  frozen-viewer → active  (Owner unfreeze via Support)
