2. DB 분할

"한 DB 에 다 넣지 않는다" — 데이터 종류별로 DB 7 개로 쪼개는 이유

Fireblocks 가 cloud 를 3 개로 쪼개는 이유와 같다 — 한 곳에 다 넣으면 한 군데 사고가 전체로 번진다.
DB 도 같은 원리로 7 개로 쪼갠다. 기준은 두 가지:

① 누가 쓰는 DB 인가 (ownership)

한 DB 는 한 service 만 write. 다른 service 는 못 씀. 권한 escalation (한 service 가 다른 도메인을 침범) 사고 차단.

② 데이터가 어떻게 변하는가 (mutability)

잔액 같은 변경 데이터, 감사 log 같은 append-only 데이터, chain event 같은 read-mostly 데이터 는 운영 방식이 달라서 같이 두면 둘 다 비효율.

Fireblocks vs 본 reference

Fireblocks 는 internal DB 구조를 공개하지 않는다. 본 페이지의 7-DB 분할은 Fireblocks 의 6 system component / 3-cloud 분할 원칙을 "DB 단위로 옮기면 이렇게 된다" 의 직접 구축 가이드 (hypothesis).

각 DB 의 책임 / 데이터 / 도메인 cluster 매핑

각 DB 가 (1) 어떤 책임을 지는지, (2) 어떤 테이블이 들어가는지, (3) 데이터 변경 패턴이 무엇인지, 그리고 (4) 본 docs-site 의 8 도메인 cluster (A–H) 중 어느 cluster 가 그 DB 를 사용하는지를 한 표에 묶었습니다. 운영 query / 권한 분리 / debugging 시 "내가 보는 cluster 의 데이터가 어느 DB 에 있는가" 의 단일 참조.

매핑이 알려주는 운영 함의

  • A. Architecture (1–2) · H. Cross-cutting & Ops (24–26) — 자체 테이블 없는 meta cluster. A 는 전체 구조를 설명하고, H 는 column 단위 규약 (7 storage class) 을 정의 — 어느 DB 의 column 이든 본 규약을 따름
  • 1-DB cluster (단순 query): C (Users) → walletdb · E (Crypto) → auditdb — 한 DB 에서 모든 query 끝
  • 2–3 DB cluster (cross-DB read 필요): B (Workspace) · D (Governance) · G (Audit) — Reconciliation Service 또는 application layer 가 cross-DB join 책임
  • ★ 4-DB 횡단 cluster (F. Transaction): tx 한 건의 full audit 은 chaindb (tx 본체) → approverdb (승인) → auditdb (서명) → ledgerdb (정산) 4 DB 를 순회. CBOR byte-equal binding + cross-DB reconciliation 이 본 cluster 의 핵심 — 한 DB 에 row 가 있으면 다른 DB 에도 정합되는 row 가 반드시 존재한다는 invariant

Reconciliation Service 의 cross-DB read 흐름

⚠️ Fireblocks 미명시 — direct-build reference 의 hypothesis

본 service 는 직접 구축 시 권장 architecture 의 일반 패턴 (cross-DB 정합성 검증을 위한 별도 read-only service).
Fireblocks vendor 자료에는 "Reconciliation Service" component 이름으로 명시되지 않음 — "Daily reconciliation report" 만 언급. Fireblocks 가 이를 별도 service 로 운영하는지 미공개.

분할의 5 가지 근거

근거의미 + 구체 예시
① 민감도 격리
(Sensitivity isolation)

같은 DB 에 두면 안 되는 두 종류:

  • 핵심 자료: 서명 키 조각 · 정책 규칙 · 승인 결정 · 감사 log → 유출 시 자산 손실 직결
  • 외피 자료: 사용자 이름·email · 지갑 이름표 · UI 표시용 잔액 cache → 유출돼도 자산 직접 손실 없음

예시: 신규 직원이 사용자 이름 검색 query 를 만들다가 실수로 같은 DB 의 audit log 를 삭제하는 사고. 두 데이터를 다른 DB 에 두면 권한 자체가 분리됨.

② 변경 패턴 분리
(Mutability isolation)

append-only DB (auditdb) 와 mutable DB 는 운영 방식이 다르다:

  • append-only DB: 매일 row 가 추가만 됨 → partition 끊고 archive 하는 운영. vacuum / lock 거의 필요 없음
  • mutable DB: row 가 자주 update / delete → autovacuum · index 재구성 자주 필요. row locking 패턴 다름

예시: 같은 DB 에 두면 audit log 의 무거운 write 부하가 사용자 metadata 의 빠른 query 를 막을 수 있다.

③ 사고 범위 축소
(Blast-radius reduction)

한 DB 가 corrupt 되거나 해킹당해도 다른 DB 는 무사. 전체 시스템이 동시에 죽지 않는다.

예시: providerdb (AML provider 연동) 가 SQL injection 으로 뚫려도 ledgerdb (잔액) 와 auditdb (audit log) 는 별개 DB 라서 그대로 안전.

④ 운영 권한 분리
(Operational separation)

각 service 의 DB 계정이 자기 DB 만 접근 가능. 한 service 가 다른 도메인을 침범할 수 없음.

예시: Broadcast Service (chain 에 tx 보내는 역할) 의 코드가 버그로 ledger entries 를 조작하려 해도 권한 자체가 없어서 실패. 같은 DB 였으면 가능했을 일.

⑤ 외부 감사 단순화
(Audit separation)

외부 감사관이 auditdb 한 곳만 read-only 로 보면 됨. 다른 DB 에 있는 고객 PII (개인정보) 는 볼 필요 없음 → privacy 보호 + 감사 범위 명확.

예시: 분기별 SOC 2(?) 감사 때 감사관에 walletdb 의 사용자 email 까지 노출하지 않아도 됨.

대가 (Trade-offs) — 7 개로 쪼개면 무엇이 어려워지는가

제약의미 + 해결책
① DB 끼리 직접 연결 불가
(Cross-DB FK 불가)

같은 DB 안에서는 users.workspace_id REFERENCES workspaces.id 같은 foreign key 제약으로 "존재하지 않는 workspace 의 사용자" 를 막을 수 있다. 다른 DB 사이엔 이 제약을 못 건다.

해결: application code 에서 검증 + Reconciliation Service 가 정기적으로 일관성 확인 (예: walletdb 의 user 가 가리키는 workspace 가 실제 존재하는지).

② 여러 DB 에 동시 commit 불가
(Multi-DB transaction 불가)

"approval 통과 → audit log 기록" 을 한 transaction 으로 묶을 수 없음. approverdb 에 결정 저장 후 auditdb 에 기록하는 도중 시스템이 죽으면 audit log 가 누락될 위험.

해결: outbox pattern(?). 같은 DB 의 transaction 으로 "결정 + outbox 행" 두 개를 함께 쓰고, worker 가 outbox 를 읽어 다른 DB 로 비동기 복제. 결과적으로 eventual consistency 보장.

③ 운영 복잡도 증가

7 개 DB 인스턴스 = 7 배의 backup / 모니터링 / 권한 관리 / version upgrade.

해결: 자동화 도구 (Terraform / Ansible) + monitoring dashboard 표준화 + 작은 institution 은 1 개 DB + schema 분리 로 시작해서 점진 분할. 25. DB 운영 참조.

Storage class (column 동작) ≠ DB split (table location)

두 축이 직교합니다. 한 column 은 두 라벨을 동시에 가집니다:

  • Location (어느 DB): walletdb / ledgerdb / approverdb / auditdb / chaindb / providerdb / recondb
  • Behavior (column 어떻게 변하나): M-mut / M-cache / A-row / A-set (set-once) / A-chain / R-only / F-bid

예시:

  • transactions.tx_hash = chaindb location + A-set (set-once) behavior — chaindb 에 저장되지만 broadcast 시점에 1회만 set, 이후 변경 불가
  • asset_balances.total = ledgerdb location + M-cache behavior — ledgerdb 에 저장되지만 canonical source 는 blockchain (stale 가능, refresh 필요)
  • audit_events.current_hash = auditdb location + A-chain behavior — auditdb 에 저장, hash chain 으로 변조 불가
  • MPC private key share = F-bid behavior — 어느 DB 에도 저장 금지 (location 없음)
