20. Audit Log

Append-only hash chain(?) + SGX(?)-signed checkpoint · cross-DB binding
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • workspace event 를 log / track / audit / export 할 수 있는 기능 제공
  • 구체 기록되는 이벤트 예시: IP allowlist 추가/수정/활성화/비활성화 · Recovery passphrase verification 알림 · 검증 결과 · risk status
  • 접근 권한: Owner / Admin / NSA / Security Auditor / Security Admin 5 role 이 audit log view 가능

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • 위 외 모든 lifecycle event 도 audit 기록 — Fireblocks 자료에 모든 event type 이 enumerate 되어 있지 않아 광범위 기록한다는 가정
  • Hash chain + SGX-signed checkpoint 의 영속화 모델 — institution-grade audit 의 표준 패턴이지만 Fireblocks 가 정확히 이렇게 구현했는지는 미명시
  • Cross-DB binding 패턴 — event_payload_cbor 가 다른 DB 의 source row 와 byte-equal CBOR encoding 일치해야 cross-DB 일관성 입증 가능 (audit 평면의 핵심 invariant)
  • audit_events · audit_checkpoints 두 테이블의 구체 schema

ERD(?) — Audit · Compliance · Risk cluster (cross-cutting)

Fireblocks 의 Audit Log 기능

Fireblocks 가 제공하는 audit 기능은 workspace event 를 log / track / audit / export 의 4 가지 동사로 처리. 즉 단순 저장이 아니라 외부로 export 가능한 형태로 보존되고, audit 절차에서 추적·검증 가능.

Fireblocks 자료에서 명시적으로 확인된 기록 대상 이벤트:

  • IP allowlist 추가 · 수정 · 활성화 · 비활성화
  • Recovery passphrase verification 알림 / 결과 / risk status
  • (그 외 lifecycle 이벤트 — user 추가/삭제, vault 변경, policy 변경 등 — 은 자료에 명시되지 않았지만 광범위 기록 가정. 21. Lifecycle Events 와 cross-cut)

접근 권한

Fireblocks 권한표 (user-roles 의 "View all workspace settings including audit logs" 행) 에 따라 audit log 열람 권한은 다음 5 role 에 부여:

  • Owner · Admin · Non-Signing Admin (NSA) · Security Auditor · Security Admin

특히 Security Auditor 와 Security Admin 은 read-only / 관리 권한이 audit 에 특화된 role — 운영팀과 보안팀이 분리된 조직에서 보안팀만 audit 검토하도록 권한 분리 가능.

DB Schema

4.1 audit_events — append-only hash chain 의 본체

-- ★★ append-only — BEFORE UPDATE / BEFORE DELETE 트리거로 강제 (24. Storage Discipline 참조)
CREATE TABLE audit_events (
  id                    BINARY(16) PRIMARY KEY,
  partition_key         VARCHAR(64) NOT NULL,             -- e.g., workspace_id + month
  seq                   BIGINT NOT NULL,                  -- per-partition monotonic
  event_type            VARCHAR(64) NOT NULL,             -- 'user-add', 'tx-broadcast', ...
  event_domain          VARCHAR(64) NOT NULL,             -- 'user', 'transaction', 'policy', ...
  source_aggregate_type VARCHAR(64) NOT NULL,
  source_aggregate_id   BINARY(16) NOT NULL,
  source_db             VARCHAR(32) NOT NULL,             -- 'walletdb', 'ledgerdb', ...
  event_payload_cbor    BLOB NOT NULL,                    -- ★ byte-equal cross-DB binding
  prev_hash             BINARY(32) NOT NULL,              -- prior seq 의 current_hash
  current_hash          BINARY(32) NOT NULL,              -- SHA256(prev_hash || payload || seq)
  actor_user_id         BINARY(16),
  occurred_at           DATETIME(6) NOT NULL,
  UNIQUE KEY (partition_key, seq),
  KEY (event_domain, occurred_at),
  KEY (source_aggregate_id)
);
컬럼자료형역할
idBINARY(16) PKevent 의 고유 식별자
partition_keyVARCHAR(64)hash chain 의 partition 식별자 (예: workspace_id_2026-05). 너무 긴 chain 한 줄은 verify 가 느리므로 partition 단위로 분할 — 보통 workspace + 월 조합
seqBIGINT같은 partition 안에서 단조 증가하는 순번 (1, 2, 3 …). UNIQUE 강제로 같은 seq 의 두 row 가 생길 수 없음
event_typeVARCHAR(64)구체 event 종류 (예: user-add, tx-broadcast, policy-change)
event_domainVARCHAR(64)event 의 도메인 ('user', 'transaction', 'policy', 'vault' 등). domain 별 audit 조회에 사용
source_aggregate_type · source_aggregate_idVARCHAR(64) · BINARY(16)이 event 가 어느 외부 cluster 의 어떤 row 와 binding 되어 있는지. 예: type='approval_decision', id=. cross-DB lookup 의 key
source_dbVARCHAR(32)source row 가 어느 DB 에 있는지 (walletdb / ledgerdb / approverdb 등). 본 cluster 의 DB 분할 모델과 정합
event_payload_cborBLOB★ byte-equal cross-DB binding. CBOR(?) 직렬화 — 다른 DB 의 source row 를 같은 CBOR 로 encoding 했을 때 byte 단위로 일치해야 함. 일치 안 하면 cross-DB 일관성 위반 즉시 감지
prev_hashBINARY(32)같은 partition 의 이전 seq row 의 current_hash. 첫 row 는 0x00...00
current_hashBINARY(32)SHA256(prev_hash || event_payload_cbor || seq). 이 값이 chain 의 다음 row 의 prev_hash 가 됨 — 변조 즉시 감지의 핵심
actor_user_idBINARY(16) nullable이 event 를 trigger 한 user. 시스템 자동 event 는 NULL 가능
occurred_atDATETIME(6)event 발생 시각

4.2 audit_checkpoints — SGX-signed 주기적 checkpoint

-- ★ append-only — SGX/TEE 가 주기적으로 서명
CREATE TABLE audit_checkpoints (
  id              BINARY(16) PRIMARY KEY,
  partition_key   VARCHAR(64) NOT NULL,
  last_seq        BIGINT NOT NULL,
  checkpoint_hash BINARY(32) NOT NULL,              -- = last seq 의 current_hash
  sgx_signature   BLOB NOT NULL,                    -- enclave signature
  sgx_mrenclave   BINARY(32) NOT NULL,              -- enclave measurement
  signed_at       DATETIME(6) NOT NULL,
  UNIQUE KEY (partition_key, last_seq)
);
컬럼자료형역할
idBINARY(16) PKcheckpoint 의 고유 식별자
partition_keyVARCHAR(64)이 checkpoint 가 속한 hash chain partition
last_seqBIGINT이 checkpoint 가 봉인하는 마지막 event 의 seq. 다음 checkpoint 는 이 seq + 1 부터 시작
checkpoint_hashBINARY(32)last_seq 의 current_hash 와 동일. 즉 chain 의 그 시점까지 모든 event 가 hash 안에 누적되어 있음
sgx_signatureBLOBSGX enclave 안에서 checkpoint_hash 를 enclave private key 로 서명. 운영자가 chain 을 통째로 재작성해도 이 서명이 없으면 무효
sgx_mrenclaveBINARY(32)서명한 enclave 의 measurement (코드 해시). 외부 감사자가 known-good 값과 비교해 enclave integrity 검증
signed_atDATETIME(6)SGX 가 서명한 시각

Hash Chain 동작

seq=1: prev=0,  current = SHA256(0  || payload_1 || 1)
seq=2: prev=h1, current = SHA256(h1 || payload_2 || 2)
seq=3: prev=h2, current = SHA256(h2 || payload_3 || 3)
...

중간 row 변조 시 뒤의 모든 hash 가 깨짐 → 변조 감지

SGX-Signed Checkpoint 의 의미

  • 운영자가 hash chain 을 통째로 재계산해서 위조하더라도, SGX enclave(?) 의 서명이 없으면 외부 감사자에게 무효
  • MRENCLAVE(?) 가 known-good 값과 일치해야 enclave integrity 확보
  • 외부 감사자는 SGX attestation(?) 또는 DCAP(?) 으로 enclave 검증 가능

Cross-DB Binding

audit_events 의 event_payload_cbor 가 다른 DB 의 source row (예: approval_decisions, signing_events, transactions) 와 byte-equal CBOR encoding 일치해야 함. 이로써 cross-DB 일관성도 cryptographically 입증.

-- 검증 query (외부 감사자)
SELECT
  a.partition_key,
  a.seq,
  a.event_payload_cbor,
  (SELECT cbor_encode(approver_user_id, decision, decided_at, mobile_device_sig)
   FROM approverdb.approval_decisions
   WHERE id = a.source_aggregate_id) AS source_payload,
  a.event_payload_cbor = source_payload AS payload_matches
FROM auditdb.audit_events a
WHERE a.event_domain = 'approval'
  AND a.partition_key = ?;

Append-only Enforcement

Application code 가 evolve 하더라도 DB 가 거절해야 의미가 있음. 24. Storage Discipline 의 trigger 패턴 참조.

Hash chain + SGX checkpoint cycle. 핵심 3 단계: ① event 발생 시 자동 chain 연결 — 새 row 의 current_hash = SHA256(이전 hash || payload || seq) 이라 운영자가 중간 row 를 바꾸면 그 뒤 모든 hash 가 깨짐. ② 주기적 SGX checkpoint — enclave 안에서만 알 수 있는 private key 로 chain 의 현재 head 를 서명. 운영자가 chain 을 통째로 재작성해도 enclave 서명 없이는 무효. ③ 외부 감사자가 cryptographic 검증 — chain 재계산 + checkpoint 서명 검증 + DCAP attestation 으로 enclave 코드 무결성까지. 이 3 단계 가 institutional-grade audit 의 cryptographic 보장이며, 운영자도 자기 audit log 를 조작할 수 없게 만드는 것이 핵심.
