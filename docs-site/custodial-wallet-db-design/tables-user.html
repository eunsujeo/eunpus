6. Users (Console / API / Mobile)

2 user type · 9 role · mobile device 의 secure enclave(?) host
본 페이지의 출처 — 어디까지가 Fireblocks 정의이고, 어디부터가 추정인가

이 페이지의 내용은 두 갈래입니다. 미리 구분해두면 어떤 부분을 그대로 받아들이고 어떤 부분은 본인 환경에서 검증할지 판단이 쉬워집니다.

Fireblocks 공식 문서에 정의된 사실 — 그대로 받아들여도 안전

  • 사용자가 Console user / API user 두 종류로 나뉜다는 점, 그리고 같은 9 role 매트릭스 를 둘 다 공유한다는 점
  • API user 의 lifecycle 4 가지 — Add · Re-enroll · Rename · Delete 각각의 actor 와 승인 요건
  • Mobile app 의 MPC(?) key share 가 device 의 secure enclave 에 보관되며 iCloud / Google Cloud 백업 불가
  • Device migration 이 user self-service (PIN + passphrase + biometric 3중 인증, 관리자 승인 없이 진행)
  • 3 비밀 layer (PIN · mobile app passphrase · recovery passphrase) 가 각각 다른 역할
  • Re-enroll 의 pairing token 이 1 시간 유효, owner / user 각각 2-day window 안에 승인
  • Owner uninstall = Key Share Recovery 필수 (단순 재설치로 회복 불가), 일반 user 는 재등록만으로 회복
  • 한 mobile device 가 여러 user / workspace 와 linked 될 수 있음 (각각 별도 재등록 필요)

저자가 합리적으로 추정해서 그린 설계 — 참고용, 본인 환경에서 검증 권장

  • users · mobile_devices · mobile_device_events · device_user_links 네 테이블의 구체 schema
  • 9 role 의 정확한 식별자/저장 형식 (본 schema 는 role_id VARCHAR(32); 운영 시 ENUM 또는 별도 lookup 으로 정형화 권장)
  • mobile_device_events.owner_approval_at / user_approval_at 두 컬럼으로 2-day window 를 표현하는 방식 — 별도 approval_requests 평면을 안 쓰는 단순화 선택

User Type — Console user 와 API user

사람이 직접 console UI 에서 작업하는 사용자와, 자동화 / 외부 시스템이 REST API 로 호출하는 사용자가 있습니다 — Fireblocks 는 이 둘을 Console user 와 API user 로 명시적으로 구분합니다. 운영 표면 (어떻게 로그인하고 어떻게 호출하는가) 은 다르지만, 권한 매트릭스는 동일한 9 role 을 둘 다 공유합니다 — 어느 type 이든 같은 role 을 받으면 같은 일을 할 수 있다는 의미.

9 role — 권한 매트릭스의 모든 행이 이 9 값 안에서 결정
  1. Owner — workspace 의 최상위 책임자. 1 workspace = 1 Owner
  2. Admin — Quorum 멤버가 될 수 있는 관리자급
  3. Non-Signing Admin (NSA) — 관리는 하지만 서명 권한 없음
  4. Signer — tx 서명 가능 (mobile MPC share 보유)
  5. Approver — tx 승인 가능 (서명은 다른 사람)
  6. Editor — 설정 / vault / address 편집 가능
  7. Viewer — 읽기 전용
  8. Security Admin — 보안 설정 전담
  9. Security Auditor — audit log 열람 전담

users 테이블 — Console / API user 통합

Console user 와 API user 가 같은 9 role 매트릭스를 공유하므로 한 테이블에 type 컬럼으로 구분해서 저장합니다. 비밀번호 hash 는 본 테이블에 저장하지 않음 — Console user 의 인증 정보는 외부 IdP / Auth0 가 관리하고, API user 는 별도 X.509 cert + API key 평면에서 관리됩니다 (→ 7. Auth Credentials).

CREATE TABLE users (
  id              BINARY(16) PRIMARY KEY,
  workspace_id    BINARY(16) NOT NULL,
  type            ENUM('console', 'api') NOT NULL,
  role_id         VARCHAR(32) NOT NULL,                -- 9 role 중 하나
  status          ENUM('pending', 'active', 'deleted') NOT NULL,
  first_name      VARCHAR(64),
  last_name       VARCHAR(64),
  email           VARCHAR(255),                        -- workspace 내 UNIQUE
  created_by      BINARY(16) NOT NULL,                 -- "Add user" 요청을 시작한 관리자
  created_at      DATETIME(6) NOT NULL,
  modified_by     BINARY(16) NOT NULL,                 -- 마지막 변경 (role/email/name 등) actor
  modified_at     DATETIME(6) NOT NULL,
  activated_at    DATETIME(6),                          -- initial setup 완료 시각
  deleted_at      DATETIME(6),                          -- soft delete (audit 위해 row 유지)
  UNIQUE KEY (workspace_id, email),
  KEY (workspace_id, type, status)
);

-- Console user 의 SSO / password 정보는 외부 (IdP / Auth0). DB 는 email + type 만.
-- 본 테이블에는 password hash 저장 X. SSO 사용 시 IdP 가 password 관리.

UNIQUE (workspace_id, email)—한 workspace 안에서 email 중복 방지

API User Lifecycle — 추가 · 재등록 · 이름 변경 · 삭제

API user 는 사람이 아닌 시스템이라 등록·교체·해제 절차가 Console user 와 다릅니다. Fireblocks 가 정의하는 4 가지 lifecycle event 와 각각의 운영상 의미:

Add — 신규 API user 추가
실행자: Owner / Admin / Non-Signing Admin 중 1 명이 시작.
승인: Owner + Admin Quorum(?) 모두 거쳐야 함 — Console user 추가와 동일한 flow.
절차: CSR(?) (RSA 4096) 을 외부 (혹은 운영 서버) 에서 생성해서 Console 에 upload → Co-signer(?) setup. 즉 새 API user 는 단순 추가가 아니라 인증서 발급 + 서명 인프라 페어링 까지의 큰 작업.
Re-enroll — Co-signer 재등록
언제: 초기 Co-signer setup 이 실패했거나 / 다른 머신으로 페어링을 옮기거나 / Callback Handler(?) endpoint 가 바뀐 경우.
실행자: "Admin-level users" (Owner / Admin / NSA).
승인: Owner 승인 + key share approval (별도 단계).
운영 주의: 재등록 시 발급되는 pairing token 은 1 시간만 유효. 그 안에 Co-signer 머신에서 페어링 완료해야 함 — 늦으면 다시 발급받아야 함.
Rename — 이름만 변경
실행자: "Admin-level users".
승인: Owner + Admin Quorum.
중요: API key 자체는 불변 — 이름 변경 후에도 같은 key 로 계속 호출 가능. 운영 시스템 측 secret rotation (비밀 키 교체) 필요 없음.
Delete — 영구 삭제
실행자: Owner 단독 (mobile 승인 단계 없음).
즉시성: 승인 절차 없이 즉시 적용 — 보안상 빠른 차단이 가능하도록.
영향: API key 가 그 순간부터 invalid 처리되어 진행 중인 tx 들이 실패하고 새 서명 요청은 거부됩니다. 주의: API user 만 삭제될 뿐 Co-signer 머신의 페어링 정보는 자동 정리되지 않음 — 별도 unpair 작업이 필요.

Mobile Device — MPC key share 의 1 차 보관소

Fireblocks 의 자산 서명에는 여러 곳에 흩어진 MPC key share 가 필요하고, 그 중 사용자 측 share 는 사용자의 mobile app 에 보관됩니다 (Owner / Signer / Approver 등 mobile-required role 의 경우). 이 share 는 device 의 secure enclave(?) — 즉 메인 OS 가 침해되어도 외부에서 메모리 접근이 불가능한 하드웨어 격리 영역 — 에 hardware-encrypted 상태로 저장.

중요한 운영상 주의점 — iCloud / Google Cloud 백업 불가. secure enclave 의 내용은 device 본체를 떠날 수 없도록 OS 가 강제하므로, 보통의 앱 데이터처럼 클라우드에 백업되지 않습니다. 즉 device 분실 / 초기화 = key share 소실 이고, 이를 복구하려면 별도의 recovery 절차 (→ 13. Recovery & Backup) 가 필요합니다.

5.1 mobile_devices — 등록된 device 의 현재 상태

CREATE TABLE mobile_devices (

5.2 mobile_device_events — device lifecycle 이벤트 (append-only)

-- ★ append-only — 모든 device 변경 이벤트의 trail
CREATE TABLE mobile_device_events (
  id                BINARY(16) PRIMARY KEY,
  device_id         BINARY(16) NOT NULL,
  event_type        ENUM('registered', 're-enrolled', 'migrated', 'uninstalled', 'biometric-changed') NOT NULL,
  actor_user_id     BINARY(16) NOT NULL,                -- 이벤트를 trigger 한 user (보통 device 소유 user 본인)
  owner_approval_at DATETIME(6),                       -- 2-day window 1 (quorum-gated event 일 때만)
  user_approval_at  DATETIME(6),                       -- 2-day window 2
  occurred_at       DATETIME(6) NOT NULL
);
컬럼자료형역할
idBINARY(16) PK이벤트 고유 식별자
device_idBINARY(16) FK어느 device 의 이벤트인지
event_typeENUM (5 값)registered 최초 등록 / re-enrolled 페어링 재발급 / migrated 새 기기로 이전 / uninstalled 앱 제거 감지 / biometric-changed OS 의 지문/Face ID 가 변경됨 (보안 신호)
actor_user_idBINARY(16) FK이 이벤트를 trigger 한 user — 대부분 device 소유 본인 (예: re-enroll / migrated 의 self-service path). registered 시는 등록을 진행한 user. uninstalled / biometric-changed 처럼 OS-level 감지 이벤트의 경우 device 소유자로 표시
owner_approval_atDATETIME(6) nullableOwner 가 이 이벤트를 승인한 시각. re-enroll / migrated 같은 quorum-gated 이벤트에서만 set, 2-day window 안에 채워져야 함
user_approval_atDATETIME(6) nullable해당 user 본인이 자기 device 등록을 확인한 시각. 위와 별개의 2-day window
occurred_atDATETIME(6)이벤트 발생 시각

3 비밀 Layer — PIN · App passphrase · Recovery passphrase

Fireblocks mobile app 사용자가 외워야 하는 비밀 정보는 세 종류입니다. 각각 다른 layer 의 보안을 담당하므로 절대 혼동하지 말 것:

PIN — app 잠금 해제용 단순 비밀번호
4~6 자리 숫자. 매번 app 을 켤 때 입력. 분실해도 device 본인 인증 (PIN + passphrase + biometric) 으로 재설정 가능.
Mobile app passphrase — app-level 추가 비밀
PIN 위에 한 layer 더 얹는 별도 비밀번호. 시스템 차원의 추가 보호 — 다른 기기에서 등록 검증 / migration 등의 핵심 동작에서 함께 요구. PIN 보다 길고 강한 비밀.
Recovery passphrase — cloud backup 의 암호화 키
위 두 가지와 결이 완전히 다름. cloud 에 백업되는 일부 데이터를 암호화하는 마스터 키 입니다. 분실하면 cloud backup 을 풀 수 없게 되어 복구 불가. 가장 안전하게 별도 보관해야 하는 비밀. 자세히는 13. Recovery & Backup.

Device Migration — 기기 교체 (self-service)

사용자가 새 폰으로 바꾸면 mobile app 도 옮겨야 합니다. Fireblocks 는 이 절차를 사용자 본인이 직접 처리하도록 설계 — 관리자 승인 절차 없이 (운영팀 개입 없이) 다음 3 중 인증만으로 진행:

  1. PIN 입력
  2. Mobile app passphrase 입력
  3. 새 기기의 biometric (지문 / Face ID) 인증

왜 관리자 승인을 요구하지 않을까 — 3 중 인증을 모두 통과한 사람은 "본인 확인이 충분히 되었다" 로 간주하는 것이 Fireblocks 의 운영 모델. 즉 운영팀이 한밤중에 device 교체 승인을 처리할 필요가 없어 사용자 경험이 매끄러워지지만, 그 대신 PIN / passphrase / biometric 중 하나라도 새지 않도록 사용자가 단단히 관리해야 한다는 책임이 따릅니다.

Linked Users / Linked Workspaces — 한 폰에 여러 신원

실무에서 한 사람이 여러 신원을 가지는 경우가 많습니다 — 예: 컨설팅 펌의 직원이 client A 의 workspace 와 client B 의 workspace 둘 다 접근해야 하거나, 같은 회사 안에서 production workspace 와 staging workspace 를 동시에 운영하거나. Fireblocks 는 한 mobile device 가 여러 user / 여러 workspace 와 동시에 link 되는 것 을 지원합니다.

다만 link 마다 별도 재등록 필요 — 즉 새 workspace 를 같은 폰에 연결할 때마다 그 workspace 의 enrollment 절차를 새로 거쳐야 합니다. 한 device 가 자동으로 모든 workspace 권한을 상속받지는 않음 (보안상).

6.1 device_user_links — device × user × workspace 의 junction (grant/revoke 패턴)

CREATE TABLE device_user_links (
  id           BINARY(16) PRIMARY KEY,
  device_id    BINARY(16) NOT NULL,
  user_id      BINARY(16) NOT NULL,
  workspace_id BINARY(16) NOT NULL,
  granted_by   BINARY(16) NOT NULL,                 -- link 를 설정한 user (보통 본인)
  granted_at   DATETIME(6) NOT NULL,
  revoked_by   BINARY(16),                           -- unlink 한 user. NULL = 현재 active
  revoked_at   DATETIME(6),
  KEY (device_id, user_id),
  KEY (workspace_id, revoked_at)
);
컬럼자료형역할
idBINARY(16) PKlink 이벤트의 surrogate PK. revoke 후 재 link 시 새 row INSERT — 이력 보존
device_idBINARY(16) FK어느 mobile device 인지
user_idBINARY(16) FK그 device 에 연결된 user
workspace_idBINARY(16)그 user-device link 가 속한 workspace. 같은 사람이 두 workspace 에 별도 user 로 있을 수 있어 명시 컬럼
granted_by · granted_atBINARY(16) · DATETIME(6)link 설정 actor + 시각 (보통 본인이 enrollment 절차로 link). set-once
revoked_by · revoked_atBINARY(16) nullable · DATETIME(6) nullableunlink (예: device migration / uninstall) actor + 시각. NULL = 현재 active. set-once when set
KEY (device_id, user_id)—"이 device 가 이 user 와 link 됐던 이력 전부" 조회
KEY (workspace_id, revoked_at)—"이 workspace 에 현재 active 한 device link" 조회 (WHERE revoked_at IS NULL)

Uninstall 비가역성 — Owner 와 일반 user 의 차이

Mobile app 을 OS 차원에서 삭제하면 secure enclave 안의 key share 도 함께 사라집니다. 클라우드 백업이 안 되므로 (위 "Mobile Device" 절 참조) 이는 비가역적인 손실입니다 — 회복하려면 별도 절차를 거쳐야 합니다.

일반 user (Signer / Approver / Editor 등)
App 을 다시 다운로드해서 재등록 (re-enroll) 절차를 거치면 정상 복귀. 그동안의 share 는 폐기되고 새 share 가 발급됩니다. 자산은 안전 — 그 user 의 share 가 없어도 다른 멤버들의 share 로 서명이 가능한 구조이기 때문.
Owner
훨씬 강력한 절차 — Key Share Recovery 가 반드시 필요합니다. 단순 재설치만으로는 회복 불가. 왜? — Owner 의 share 는 거버넌스의 spine 이라서 다른 멤버로 대체될 수 없고, 만약 분실되면 workspace 자체가 위험에 빠지기 때문. Recovery 절차는 recovery passphrase + Disaster Recovery 서비스가 함께 동원되는 운영급 작업 (→ 13. Recovery & Backup).

★ 운영상 주의점 — Owner 의 mobile device 는 일반 user 와 다른 등급으로 관리되어야 합니다. 폰 분실 시 즉시 운영팀 통지 + 백업 device 확보 같은 별도 운영 절차 (체크리스트) 를 미리 정해두는 것이 안전.
