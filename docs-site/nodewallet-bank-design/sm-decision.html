10. 결정 라이프사이클

Allow / Held / Deny — 정확히 하나의 결정. monotone + sticky + 24h TTL + fail-closed
출처

compliance__decision-lifecycle.md 전체 — 가장 dense 한 single-source. compliance__rules__approval-tier.md §Held 의 외부 해소.

3 verdict + shadow_mode 없음

결정의미coordinator 동작
Allow (wire 형식 AutoApprove)모든 활성 규칙 통과. 승인자가 승인 키로 co-sign.엔클레이브에 전달 → 체인 서명
Deny한 개 이상 규칙 위반. triggered_rules 에 위반 규칙 기록.호출자에 400 반환, 체인 서명 단계 미도달
Held자동 결정 불가. 요청을 held_* 표에 보관 후 폴링으로 재평가./v1/poll 폴링 루프 진입

shadow_mode (관찰 전용) 가 없다 — 모든 Deny 는 실제 차단. enum 측면에서는 내부 Verdict (rule 단위) 와 PolicyDecision (전체 결정) 두 enum 이 있고, Allow 는 wire 직렬화 시 AutoApprove.

상태 머신

stateDiagram-v2
  [*] --> EVALUATING: /v1/evaluate
  EVALUATING --> DENY: 1 rule = Deny
(short-circuit)
  EVALUATING --> HELD: 1 rule = Held
(short-circuit)
  EVALUATING --> AUTO_APPROVE: 모든 rule pass
  HELD --> RE_EVALUATING: /v1/poll (next tick)
  RE_EVALUATING --> DENY: any rule Deny
(sticky, terminal)
  RE_EVALUATING --> AUTO_APPROVE: all pass
(sticky, terminal)
  RE_EVALUATING --> HELD: still Held AND age < 24h
  RE_EVALUATING --> DENY_TTL: age >= 24h
(TTL exceeded → Deny)
  AUTO_APPROVE --> [*]: signing path
  DENY --> [*]: 400 to caller
  DENY_TTL --> [*]

4 가지 핵심 성질

Sticky decision (단방향성)
한번 AUTO_APPROVE 또는 DENY 로 전환되면 다시 HELD 로 돌아가지 않는다. DB trigger 가 강제. monotone 상태 머신.
Set-once approver 서명
auth_approver_sig / auth_approver_pubkey 컬럼은 한번 INSERT 되면 변경 불가. 동일 요청에 대해 서로 다른 두 서명이 존재할 수 없다.
24h TTL
폴링은 기본 24시간까지. 그 안에 Allow/Deny 로 결정되지 않으면 coordinator 가 Deny 처리. 영업일 기준이 아닌 absolute hardcode.
Idempotent
(initiator_pubkey, nonce) 키로 중복 호출 방지 (initiator_nonce_seen 표). SDK 가 강제하는 reference_id 가 nonce 와 매핑.

수동 승인 버튼이 없는 이유 (NodeInfra 자기서술)

Held 는 운영자가 콘솔의 "승인" 버튼을 눌러 해제하지 않는다. NodeInfra docs 는 두 이유를 명시 (source: compliance__decision-lifecycle.md §수동 승인 없는 이유):

  1. 권한 분리 — 정책 엔진이 정책 키를 가지므로, 운영자가 정책 엔진의 결정을 우회할 수 있다면 정책 엔진의 의미가 무너진다. 운영자가 결정을 바꾸려면 규칙 자체를 수정해야 한다 (변경은 policy_change_log 에 남는다).
  2. 결정론적 재평가 — 동일 입력 + 동일 규칙 set → 동일 결정. Held 가 풀리려면 시간 (address_cooldown) · 규칙 변경 (approval_tier 한도 상향) · 외부 상태 (velocity_window 의 시간 경과) 중 하나가 바뀌어야 한다.

이것이 approval_tier 의 SINGLE_APPROVE / QUORUM_2_OF_3 가 외부 승인 채널을 거쳐 규칙을 일시 수정한 뒤 폴링이 자동 해소되는 방식으로 동작하는 이유.

fail-closed — 의도된 안전 기본값

승인자가 다음 상황에 처하면 Deny 로 처리 (fail-open 아님):

  • DB 연결 실패
  • 규칙 평가 중 panic 또는 PolicyError
  • 필수 EvaluationContext field 누락
  • HSM 응답 실패 (승인 키 co-sign 실패)
  • 호출자 서명 검증 실패
"운영 관점에서는 승인자 장애 = 출금 정지. 이는 의도된 안전 기본값" (source: compliance__decision-lifecycle.md)

      Coord->>Approver: /v1/poll(request_id)
      Approver->>Approver: 재평가 (현재 rule set)

Held 발화 규칙 — 단 2 종

10 rule 중 Held 를 반환하는 것은 다음 2 종 (source: compliance__decision-lifecycle.md §Held 자동 결정 보류):

규칙Held 발화 조건
address_cooldown출금 주소가 최근에 처음 사용됐고 금액이 threshold 초과 — 일정 시간 후 자동 해소
approval_tier금액 구간이 수동 승인 모드 (SINGLE_APPROVE/QUORUM_2_OF_3) 에 해당 — 운영자의 별도 채널 승인 필요

임시 AUTO 변경 후 복원 — Held 해소의 정석 패턴

vendor docs 가 명시하는 패턴 (source: compliance__rules__approval-tier.md §Held 의 외부 해소):

  1. 외부 의식 (운영자 회의 · 키 의식 · 별도 시스템 승인) 으로 결정
  2. 임시로 approval_tier 행을 수정해 해당 구간을 AUTO 로 — policy_change_log 에 변경 자동 기록
  3. coordinator 폴링이 다음 평가에서 Allow 받음
  4. 평가 통과 후 즉시 approval_tier 를 원래대로 복원 — 역시 기록

변경 자체가 영구 감사 흔적. 외부 의식의 evidence (서명된 회의록 · 별도 시스템 로그) 와 묶이면 sound 한 감사 추적이 가능. 단점은 타이밍 race — A가 AUTO 로 바꾸자마자 B 가 별도 출금을 시도하면 B 도 통과. 의식 절차가 운영자 행동 약속에 의존.

은행 도입 시 결정해야 할 것

  • 승인자 HA — fail-closed 가 의도된 동작이지만 정상 운영 중 가용성은 높여야 한다. active-passive 또는 active-active + 정족수 합의.
  • 24h TTL 의 영업적 의미 — 영업일 종료 직전 Held 가 다음 영업일 같은 시간까지 폴링 → Deny. 운영자 모니터링이 영업시간 외에도 가능하도록.
  • 외부 의식 evidence 보존 — 운영자 회의록 서명 · email 보존 · video 등. 보존 매체는 WORM 권장.
  • 임시 AUTO 변경 권한 분리 — 정책 변경 권한자 ≠ 운영 권한자 ≠ approval ceremony 참여자.
  • fail-closed 알람 — 승인자 장애 = 출금 정지 → 사고 escalation 절차.
