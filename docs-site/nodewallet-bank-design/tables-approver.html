policy_rules — 규칙 schema

모든 규칙은 다음 모양 (source: pm-db-design-notes.md 섹션 5):

{
  "rule_type": "<10종 중 하나>",
  "flow_type": "withdrawal" | "transfer" | "deposit",
  "mint": "<NATIVE_SOL or SPL mint>" | "*",
  "priority": <integer>,
  "config": { /* rule-specific JSON */ }
}

config 는 rule_type 별로 schema 가 다르다. 자세히는 9. 10 Policy Rules 페이지.

policy_decisions — append-only 해시체인

모든 평가 결과는 policy_decisions 에 INSERT 되며, prev_hash 로 해시체인을 형성한다. prevent_mutation() trigger 가 UPDATE/DELETE 를 raise — superuser 가 아닌 application user 권한으로는 우회 불가 (source: pm-db-design-notes.md).

컬럼의미
request_id요청 UUID — cross-DB join key
verdictAUTO_APPROVE / REJECT / HELD (★ enum 정확 명칭 docs 단편 — wire 에서는 "AutoApprove")
triggered_rules위반 규칙 list (JSON array) — Deny 시 충전 (예: [{"rule_name": "address_list"}])
auth_approver_sigset-once — 승인 키의 Ed25519 서명. INSERT 후 UPDATE 불가.
auth_approver_pubkeyset-once — 서명 검증용 공개키
decided_at결정 시각 (트래블룰 보고서용)
prev_hash이전 행의 hash — SHA-256 chain
hash이 행의 hash (= SHA256(prev_hash ‖ 다른 컬럼들))
amount / mint트래블룰 리포트 export 용 (source: compliance__regulations__travel-rule.md)

★ 모든 컬럼 정확 명세는 vendor docs 단편 (예: auth_approver_sig 만 명시). 위 컬럼명은 docs 에 나온 식별자를 그대로 사용하고, 그 밖은 ★ Hypothesis.

held_* — set-once 강제

두 표 (held_deposits / held_withdrawals) 의 공통 구조 — Held 의 자동 결정 보류 큐:

컬럼규칙
decisionHELD → AUTO_APPROVE 또는 DENY 로 단방향 전환 (sticky). 같은 행에 두 번째 INSERT 시도 불가, 다른 값으로의 UPDATE 불가 — trigger 강제.
auth_approver_sigset-once. decision = AUTO_APPROVE 가 set 되는 동일 트랜잭션 안에만 INSERT 가능.
auth_approver_pubkeyset-once. 동일.
payload (request 의 amount/destination/mint)immutable — 처음 INSERT 후 변경 불가.
age_started_at최초 Held 시각 — 24h TTL 계산 기준.
reasonHeld 사유 (예: "requires single-operator approval").

★ 24h 가 hardcode 인 것은 compliance__decision-lifecycle.md 에 명시 ("폴링은 기본 24시간까지"). 테넌트별로 다르게 두려면 product extension 필요.

velocity_windows — 슬라이딩 윈도우

velocity_window 룰이 사용하는 카운터. INSERT-only 로 매 거래 증분을 기록하고, 평가 시 윈도우 안의 row 만 합산 (source: pm-db-design-notes.md 1.2 절).

-- ★ 추정 schema (docs 미명시 세부)
CREATE TABLE velocity_windows (
  id            BIGSERIAL PRIMARY KEY,
  tenant_id     UUID NOT NULL,
  account_id    UUID NOT NULL,
  mint          TEXT NOT NULL,
  ts            TIMESTAMPTZ NOT NULL,
  amount        BIGINT NOT NULL,   -- lamports
  request_id    UUID NOT NULL
);
-- 평가는 (account_id, mint, ts >= now() - INTERVAL '<window_seconds> sec') 합산
-- INSERT-only — prevent_mutation 트리거

address_first_use — 쿨다운 trigger

address_cooldown 룰이 "이 destination 이 최초인지 + 마지막 사용 후 얼마나 지났는지" 를 본다. INSERT-only.

-- ★ 추정 schema
CREATE TABLE address_first_use (
  account_id     UUID NOT NULL,
  destination    TEXT NOT NULL,
  first_seen_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (account_id, destination)
);

condition_sets · condition_set_items

VASP 화이트리스트 / 블랙리스트 / address group 의 컨테이너 + 멤버. address_list 룰의 config.condition_set_id 가 이 표를 참조. admin 가능, 변경은 policy_change_log 에 기록.

INSERT INTO condition_sets (id, name, set_type, description) VALUES

policy_change_log — 누가 언제 무엇을 바꿨는가

모든 policy_rules · condition_sets · condition_set_items 변경이 trigger 로 자동 INSERT 된다 (append-only). 외부 의식으로 Held 를 해소하는 패턴 (예: approval_tier 를 임시 AUTO 로 → 폴링 통과 → 원복) 에서 변경 증거가 영구히 남는 핵심 표.

컬럼의미
actionCREATE / UPDATE / DELETE
created_by변경 주체 (운영자 ID)
old_data / new_data변경 전/후 JSON
changed_at변경 시각
table_name / row_id★ 어느 표의 어느 행이 바뀌었는지

initiator_nonce_seen — 멱등성

(initiator_pubkey, nonce) 를 unique key 로 가지는 표. 매 요청의 첫 진입에서 INSERT 시도 → unique violation 이면 중복 요청으로 거부. SDK 가 강제하는 reference_id 가 이 nonce 와 매핑 (★ Hypothesis — 정확 매핑 docs 미명시).

approverdb 안의 10 표 관계 — 정책 정의 (rules + condition_sets) · 결정 사슬 (decisions + held_*) · 평가 카운터 (velocity + address_first_use) · 변경 로그 · 멱등성. 모든 mutable 변경은 policy_change_log 에 자동 trigger.

은행 도입 시 결정해야 할 것

  • parition strategy — policy_decisions · velocity_windows 는 monotone 증가 — 시간 partition (일/월) + 오래된 partition 의 cold archive 정책.
  • 24h Held TTL — hardcode. 영업일 기준으로 동작하려면 운영팀이 영업종료 직전 Held 가 24h 후 (다음 영업일) DENY 처리되는 것을 인지해야 한다.
  • policy_change_log retention — VACPA 등 한국 규제는 거래 기록 5년 보존 등 요건이 있다. 변경 로그는 audit table 과 함께 동일/장기 retention 권장.
  • condition_set 큐레이션 절차 — VASP 주소 import 는 외부 데이터 (소스: aml-sanctions-coverage.md internal) 의존. 큐레이션 sources 와 import 주기를 운영팀이 정해야 한다.
