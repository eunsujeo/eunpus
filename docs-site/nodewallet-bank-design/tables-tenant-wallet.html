테넌트 = 은행 내부 sub-unit

NodeWallet 의 "테넌트" 는 외부 SaaS 의 고객이 아니라 은행 안의 sub-unit이다. 계열사 / 부서 / 상품군 단위로 격리 운영 (source: vendor-specific-patterns.md P1.2):

  • 은행 그룹사 (지주 → 시중은행 · 카드사 · 증권사 · 캐피탈) 가 한 그룹사 NodeWallet 배포 안에서 각 자회사를 별도 테넌트로 운영
  • 또는 한 은행 안의 리테일 / 기업 / 자산관리 / WM 같은 사업부별 격리
  • 또는 신상품 (스테이블코인 X / 스테이블코인 Y) 별 격리

테넌트 모델은 DB schema 의 first-class. retrofit 이 아니라 day-1 에 결정해야 — tenant_id 가 거의 모든 표의 컬럼이 된다.

테넌트 등록 (register_enclave)

vendor docs 는 register_enclave 시점에 enclave 가 SPKI-hash 와 blob_hash 를 원장 (=ledgerdb 의 append-only 영역으로 추정) 에 기록한다고 명시 (source: security__architecture__tenant.md).

표 (★ 추정)용도주요 컬럼
tenants테넌트 메타데이터tenant_id · name · created_at · status (active/suspended)
tenant_keys테넌트별 3-key 의 공개키 등록tenant_id · key_role (initiation/approval/execution) · pubkey · spki_hash · registered_at
tenant_enclave_registrationsregister_enclave 이벤트 — append-only 원장tenant_id · enclave_pubkey · spki_hash · blob_hash · mrenclave · registered_at

★ Hypothesis: docs 는 "원장에 기록" 표현만 사용. 별도 표인지 ledgerdb 의 ledger_entries 의 한 종류인지 명시 없음. 은행 도입 시 NodeInfra 와 confirm 필요.

wallets 표 (★ 추정 schema)

CREATE TABLE wallets (
  id              UUID PRIMARY KEY,
  tenant_id       UUID NOT NULL,
  wallet_type     TEXT NOT NULL CHECK (wallet_type IN ('user', 'omnibus', 'gas_payer')),
  derivation_path TEXT NOT NULL,    -- BIP-44, m/44'/501'/account'/change/index
  solana_address  TEXT NOT NULL UNIQUE,
  customer_ref    TEXT,             -- 은행 측 고객 식별자 (user wallet 만)
  created_at      TIMESTAMPTZ NOT NULL,
  -- DB-level invariant: per (tenant_id, wallet_type='omnibus') 정확히 1개
  -- 마찬가지로 per (tenant_id, wallet_type='gas_payer') 정확히 1개
  UNIQUE (tenant_id, wallet_type)
    WHERE wallet_type IN ('omnibus', 'gas_payer')
);

DB 무결성 제약으로 "테넌트당 정확히 1 omnibus + 1 gas_payer" 가 enforce 된다 (source: dev__architecture.md §자금 흐름). SDK 가 user wallet 만 만들 수 있는 이유.

BIP-44 derivation

모든 wallet 의 주소는 sealed master key 에서 BIP-44 경로로 파생 (source: security__keys__tee-enclave.md §엔클레이브 내부 흐름):

m / 44' / 501' / account' / change / index
            ↑     ↑
            |     +-- Solana SLIP-44 (501)
            +-- BIP-44 purpose

★ 추정: tenant_id → account' 의 매핑 + wallet_type/index → 별도 파생
       정확한 매핑은 docs 미명시 (vendor 내부 구현)

SGX 엔클레이브가 경로 검증을 수행 — 허용된 경로 외 임의 경로 서명 요청은 거부.

SPKI-hash 바인딩 — 테넌트 경계 검증

매 서명 요청은 다음 검증을 통과해야 한다 (source: security__architecture__tenant.md):

  1. 요청 payload 의 tenant_id 추출
  2. tenant_keys 표에서 해당 tenant_id 의 개시 키 SPKI-hash 조회
  3. 요청 서명자의 공개키 SPKI-hash 와 대조 — 불일치 시 거부
  4. 승인자 단계: 같은 검증을 승인 키 측에서 다시
  5. 엔클레이브 단계: 같은 검증을 실행 키 측에서 다시

3 키 모두에서 교차 검증되므로 한 키 탈취로는 다른 테넌트 자금 이동 불가.

은행 도입 시 결정해야 할 것

  • 테넌트 granularity — 그룹사 단위 / 사업부 단위 / 상품 단위. 너무 잘게 쪼개면 운영 부담, 너무 크게 묶으면 격리 약화.
  • customer_ref 명명 — 은행의 고객번호 / 계좌번호 / 휴대폰 번호 등 어느 식별자를 user wallet 의 customer_ref 로 둘지. KYC 시스템과의 join key.
  • omnibus 단일 / 다중 — NodeInfra default 는 테넌트당 1 omnibus. hot/warm/cold 다층 보관은 product extension. 은행 정책상 cold storage 가 필요하면 별도 설계.
  • 가스대납 잔액 모니터링 — gas-payer 의 SOL 잔액이 임계 미만이면 출금/스윕이 멈춘다. SDK polling 또는 외부 모니터링 + 자동 충전 로직 필요.
  • 테넌트 라이프사이클 — provisioning 은 docs 에 있지만 suspend / deprovisioning 은 미명시. 사고 시 테넌트 freeze 절차를 NodeInfra 와 합의.
