8. HSM · SGX · 키 수명주기

HSM (FIPS 140-3 L3) + Intel SGX = 두 독립 신뢰 도메인 — 한 쪽 침해가 다른 쪽으로 전파되지 않는다

실행 키의 마스터는 HSM 에서 최초 1회만 생성되어 RSA-OAEP wrap 으로 enclave 에 전달 → enclave 가 MRENCLAVE 봉인. 이후 운영 중에는 HSM 접근 없이도 동작. 그래서 "실행 키 전용 HSM 은 프로비저닝 후 오프라인 전환 가능" 이 NodeInfra 의 권장 운영 패턴 (source: security__keys__hsm.md §다중 HSM 배치 권장).

HSM — 3 파티션 구조

NodeInfra default 는 단일 HSM + 3 파티션 (비용/운영 부담이 가장 적음). 더 강한 격리가 필요하면 키별 독립 HSM 권장.

파티션접근 서비스운영 시 HSM 접근활성화 쿼럼 예시
개시 키Spring + Java SDK매 개시 서명3-of-5 (보수적)
승인 키승인자매 co-sign3-of-5 (높은 가치)
실행 키엔클레이브 (provisioning 시만)provisioning 시에만4-of-7 (최상위 민감도, 마스터 키 세레머니)

m-of-n 쿼럼은 파티션 활성화 + 키 관리 작업 (생성/삭제/백업/로테이션) 시점에 적용. 매 트랜잭션 단위의 쿼럼은 HSM 이 아닌 애플리케이션 계층의 3-키 다중서명으로 구현된다.

다중 HSM + vendor diversity (권장 구성)

단일 HSM 의 펌웨어 취약점 · 관리자 침해 · 물리적 사고가 다른 키로 전파되지 않게 하려면:

  • 키별 독립 HSM — 단일 HSM + 파티션 의 격리보다 강함
  • 공급사 다양화 — 예: 개시 · 승인 키는 Thales Luna, 실행 키는 Utimaco
  • 네트워크 분리 — 각 HSM 을 서로 다른 VLAN · 관리 네트워크에
  • 실행 키 전용 HSM 오프라인 — provisioning 후 cold storage 로 보관 가능

PKCS#11 세션 모델은 파티션 경계와 HSM 경계를 동일하게 다룬다 — 단일 HSM 에서 다중 HSM 으로 전환 시 NodeWallet 코드 변경 없음, 배포 설정 (PKCS#11 slot 매핑) 만 조정.

PKCS#11 인터페이스

  • 모든 HSM 접근은 PKCS#11 v2.40 / v3.0 표준
  • Java SDK 는 Sun PKCS#11 provider 사용 (JDK crypto bridge)
  • 서비스별로 다른 slot 과 session — 한 서비스의 session 은 다른 파티션에 접근 불가

SGX 엔클레이브 — 실행 키의 두 번째 도메인

Intel SGX (Software Guard Extensions) 는 CPU 수준에서 격리된 실행 영역을 제공한다. NodeWallet 의 체인 서명 로직은 SGX 엔클레이브 안에서만 실행되며, 호스트 OS / 하이퍼바이저가 침해되어도 EPC 메모리는 보호 (source: security__keys__tee-enclave.md).

마스터 키 provisioning 의식 (RSA-OAEP wrap)

sequenceDiagram
  participant HSM as HSM (실행 키 마스터)
  participant Enc as SGX Enclave
  participant Disk as Disk (sealed blob)

  Enc->>Enc: 일회성 RSA keypair 생성 (enclave 메모리 내)
  Enc->>HSM: enclave 의 RSA 공개키 + DCAP 증명 전달
  HSM->>HSM: 마스터 키 생성 (HSM 내부)
  HSM->>HSM: enclave RSA 공개키로 RSA-OAEP wrap
  HSM->>Enc: wrapped master key (암호문)
  Enc->>Enc: RSA-OAEP 복호화 (enclave 내부)
  Enc->>Enc: EGETKEY 로 sealed blob 생성 (MRENCLAVE 봉인)
  Enc->>Disk: sealed_blob 저장
  Note over HSM,Enc: 평문 마스터 키가 HSM 밖으로
노출되는 시점은 enclave 내부뿐

엔클레이브 내부 서명 흐름

  1. 요청 검증 — MRENCLAVE 로 세션이 바인딩되어 있는지 확인
  2. 마스터 키 언실 — 디스크의 sealed_blob 을 EGETKEY 로 언실하여 평문 마스터 키를 엔클레이브 메모리에 로드
  3. BIP-44 파생 — 요청된 지갑 경로 (m/44'/501'/account'/change/index) 로 서명 키 파생
  4. 경로 검증 — 파생 경로가 허용된 범위 내인지 (임의 경로 서명 차단)
  5. Ed25519 서명 — 트랜잭션에 서명
  6. 즉시 제로화 — 마스터 키 + 파생 키 + 중간값을 모두 엔클레이브 메모리에서 제거
  7. 반환 — 서명값만 호스트로 반환

호스트 침해 시나리오

공격자가 엔클레이브를 실행하는 호스트 OS 를 완전히 장악해도:

  • 메모리 추출 불가 — SGX EPC 메모리는 CPU 내부 암호화로 RAM 덤프 불가
  • 실드 블롭 재사용 불가 — sealed_blob 은 MRENCLAVE 에 봉인되어 다른 이미지로 언실 불가 (EGETKEY 가 거부)
  • 재생 공격 불가 — 엔클레이브가 세션별 nonce 를 발행하고, 요청에 포함된 nonce 를 검증

감사 로그 이벤트 type (auditdb.key_lifecycle)

  • key.generated — 키 생성, 생성 세레머니 참여자 서명
  • key.sealed — 봉투 보관 위치, 봉인 해시
  • key.activated — 활성화 시각, 활성화 승인자
  • key.rotation.started — 로테이션 개시, 병행 기간 설정
  • key.rotation.completed — 신규 키 단독 활성
  • key.revoked — 폐기 사유 (정기 / 긴급 / 탈취 의심)

폐기 조건

  • 탈취 의심 — 이상 징후 탐지 시 즉시 폐기 + 신규 키로 로테이션
  • 정기 로테이션 — 조직 정책에 따른 주기적 교체 (연 1회 권장)
  • 하드웨어 교체 — HSM 모듈 교체 시 기존 키 폐기
  • 인증 만료 — FIPS 인증 주기 만료 시 재생성

SoftHSM2 production 금지 (deployment-discipline invariant)

SDK 의 mode=production 설정은 SoftHSM2 (software HSM) 를 적극적으로 차단한다. 운영 배포 시 인증된 HSM 만 사용 가능 — operator error 방지의 구조적 가드 (source: vendor-specific-patterns.md P8.2).

은행 도입 시 결정해야 할 것

  • HSM 모델 — Thales Luna Network 7 (운영 권장) vs PCIe vs Utimaco. 한국 시장 표준은 Thales 가 강세.
  • vendor diversity — 단일 vendor의 monoculture risk 회피. 비용과 운영 인력 trade-off.
  • m-of-n 임계값 — 각 키의 활성화 쿼럼. 운영 인력 size 와 ceremonial 부담 균형.
  • SGX-capable HW 조달 — Intel SGX 지원 CPU + DCAP 인프라. 망분리 환경에서 Intel PCS attestation 의 internal mirror.
  • MRENCLAVE rotation 절차 — 이미지 빌드 → DCAP 재증명 → master key re-wrapping → 운영 전환의 ceremony 매뉴얼. 이전 MRENCLAVE 값은 forever 보존 (historical 검증용).
  • 키 로테이션 주기 — 연 1회 권장 vs FIPS 인증 주기 vs 정책. 각 키의 trade-off (서명 트래픽 vs 의식 부담) 별로 다른 주기 가능.
  • 실행 키 HSM 의 cold 전환 — provisioning 후 오프라인 보관 시점과 절차. 재provisioning 시 cold HSM 재오픈 ceremony.
