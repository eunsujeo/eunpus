각 경계는 서로 다른 인증 수단을 적용한다. 한 경계를 뚫었다고 다음 경계로 그대로 진입할 수 없다.

경계별 인증 요구

경계통과 수단검증 내용
클라이언트 → 격리 구역TLS 1.3 + API 키 서명 (Ed25519, 60초 timestamp) + mTLS요청이 등록된 운영자에게서 왔고, 변조되지 않았으며, 정책을 통과함
격리 구역 → TEECBOR IPC (stdin/stdout) + DCAP 원격 증명MRENCLAVE 가 일치하는 엔클레이브 이미지만 통과

★ Hypothesis: DMZ → 격리구역 경계는 docs 본문에 직접 enumerate 되어 있지 않지만 망분리 IDC 의 표준 layout 상 별도 mTLS 핸드오프가 일어난다고 추정. NodeInfra 의 4-축 격리에서 명시되는 것은 (1) 클라→격리 (2) 격리→TEE 두 단계. 그 이전의 DMZ는 은행 표준 망분리 layer.

키별 보관 위치

키보관접근 방식탈취 시 영향
개시 키HSM 파티션Spring 백엔드 + Java SDK 가 PKCS#11 로 호출요청 위조 시도 — 승인자가 정책 위반으로 차단, 승인 키 co-sign 없음
승인 키HSM 파티션 (별 파티션)승인자가 PKCS#11 로 호출정책 우회 시도 — 유효한 개시 키 서명 없이는 요청 자체가 도달하지 않음
실행 키SGX sealed blob (디스크)엔클레이브가 EGETKEY 로 언실 — HSM 접근 불요체인 서명 시도 — 개시 서명 없이는 서명 대상 요청 자체가 생성되지 않음

한 경계를 뚫었을 때 무엇이 남는가

클라이언트만 뚫리면
승인자의 승인 키 공동 서명이 없으면 엔클레이브가 요청 자체를 거부 (source: security__architecture__trust-boundaries.md).
격리 구역까지 뚫려도
엔클레이브는 CBOR IPC 로만 통신하며, MRENCLAVE 가 일치하는 이미지만 서명을 수행할 수 있다. DCAP 원격 증명을 거치지 않은 세션은 거부.
엔클레이브 호스트가 뚫리면
SGX EPC 메모리는 CPU 내부 암호화로 RAM 덤프 불가. sealed_blob 은 MRENCLAVE 에 봉인되어 있어 다른 이미지로 언실 불가 (EGETKEY 가 거부).
HSM 자체가 탈취되면
FIPS 140-3(?) Level 3 물리 방호로 키 추출 불가. 실행 키는 HSM 밖 (SGX sealed) 에 있어 HSM 손실 시에도 서명 서비스는 계속 동작.

테넌트 경계 — 한 계열사가 다른 계열사를 건드릴 수 없다

NodeWallet 의 "테넌트" 는 외부 고객이 아니라 은행 내부의 sub-unit (계열사 · 부서 · 상품군) 이다 (source: vendor-specific-patterns.md P1.2). 한 배포 안에 다수의 테넌트를 격리 운영한다.

탈취 시나리오다른 테넌트 영향막히는 지점
테넌트 A의 개시 키 탈취없음테넌트 B 의 payload 는 A 키로 서명 불가 — SPKI 바인딩이 거부
테넌트 A의 승인 키/실행 키 탈취없음키 자체가 테넌트별이라 다른 테넌트 서명에 사용 불가
테넌트 A의 운영자 키 탈취없음A 내에서도 승인 키 co-sign 필수 — 서비스 격리가 중첩 방어
테넌트 A의 정책 우회 시도없음승인자가 테넌트별 정책으로 판단, 다른 테넌트 정책에 영향 없음
공용 서비스 (Approver · Enclave) 호스트 탈취없음HSM 물리 방호 + SGX MRENCLAVE 봉인으로 키 추출 불가

구조적 강제 방법: 테넌트 등록 (register_enclave) 시점에 엔클레이브가 해당 테넌트 공개키의 SPKI-hash 와 blob_hash 를 원장에 append-only 로 기록. 매 서명 요청마다 payload 의 tenant_id 와 이 해시를 대조 — 다른 테넌트 키로 서명된 요청은 구조적으로 거부된다 (source: security__architecture__tenant.md).

★ Hypothesis — DR/HA 와 경계 보존

  • 스탠바이 Coordinator/Approver 가 다른 격리 구역에 있는지, 같은 격리 구역의 다른 호스트인지는 docs 미명시 — 은행이 결정.
  • HSM 의 cluster mirroring (Thales Luna 의 HA group) 사용 여부도 docs 미명시. 단일 펌웨어 취약점 전파를 막으려면 vendor-diversity 권장.
  • 망분리 환경에서 SGX 의 DCAP 검증을 위한 Intel PCS(?) 접근은 보통 망분리 위반 — 캐시된 collateral 을 internal mirror 로 두는 운영 패턴이 필요. docs 는 운영 매뉴얼 수준의 detail 을 다루지 않는다.
