6. ledgerdb · chaindb

잔액과 온체인 사건 — 두 DB 의 정합성이 핫월렛 무결성의 근간
출처

pm-db-design-notes.md §1.2 (ledgerdb / chaindb 명시), security__ops__audit-logs.md (해시체인 · 체크포인트), compliance__architecture.md (한계 — 잔액은 ledger 책임).

★ ledgerdb / chaindb 의 정확한 컬럼은 public docs 단편 — 일부는 ★ Hypothesis. 내부 design doc (deposit_verification.md) 이 reference 되지만 vendor 가 onboarding 시 별도 제공.

ledgerdb — 잔액 + 해시체인

ledgerdb 의 핵심 표는 per-account ledger 엔트리 + 주기적 enclave-signed checkpoint. 각 계정마다 독립된 SHA-256 해시체인이 흐른다 (per-account, not global — source: pm-db-design-notes.md §4.1).

표 (추정 이름)용도주요 컬럼mutability
ledger_entries계정별 잔액 변경 — debit / credit · sweep · transfer · withdrawid · account_id · mint · amount · direction · action_ref (FK to signing_events) · prev_hash · hash · created_atappend-only 의도 + FK 제약
ledger_checkpoints주기적 (1h 또는 100 entries) 체인 헤드 서명account_id · chain_head_hash · entry_count · timestamp · enclave_sig · mrenclaveappend-only
account_balances (★ 옵션)현재 잔액 read-model — Coordinator 의 EvaluationContext 사전계산 sourceaccount_id · mint · balance · updated_atmutable (read model)

★ account_balances 가 materialized view 인지 별 표인지 또는 in-memory cache 인지는 docs 미명시. NodeInfra 는 "잔액 일관성 보장 책임을 원장 트랜잭션 경계에 둔다" 만 명시.

per-account 해시체인 공식

entry.hash      = SHA-256(entry.prev_hash ‖ account_id ‖ mint ‖ amount ‖ direction ‖ action_ref ‖ created_at)
entry.prev_hash = 같은 account 의 직전 entry 의 hash
checkpoint.sig  = EnclaveSign(chain_head_hash ‖ account_id ‖ entry_count ‖ timestamp)

per-account 가 per-global 보다 parallelizable. 다만 account 간 transfer 의 cross-account 정합성은 별도 메커니즘 필요 (FK to signing_events 가 그 역할).

FK 제약 — 고아 entry 의 구조적 불가능

ledger_entries 는 반드시 영수증이 있는 작업 레코드를 참조한다 (action_ref → signing_events.id 또는 transfer 의 verify_and_authorize 영수증). 고아 엔트리는 구조적으로 불가능 — DB 가 거부 (source: security__ops__audit-logs.md).

-- ★ 추정 schema
CREATE TABLE ledger_entries (
  id            BIGSERIAL PRIMARY KEY,
  tenant_id     UUID NOT NULL,
  account_id    UUID NOT NULL,
  mint          TEXT NOT NULL,
  amount        BIGINT NOT NULL,
  direction     TEXT NOT NULL CHECK (direction IN ('credit', 'debit')),
  action_ref    UUID NOT NULL,   -- signing_events.id 또는 transfer 영수증 id
  prev_hash     BYTEA,
  hash          BYTEA NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  FOREIGN KEY (action_ref) REFERENCES signing_events(id)
  -- ★ 단일 DB 면 FK, 분리 시 application-level 검증
);

실제로 ledgerdb 와 auditdb 가 별도 instance 면 FK 가 cross-DB 라 직접 강제 불가 — application layer 의 정합성 체크 (60초 이하 권장 cadence) 가 대체.

정합성 체크 (reconciliation)

NodeInfra 는 "원장 ↔ 작업 레코드 ↔ 온체인 상태를 짧은 주기 (권장 60초 이하) 로 대조하며, 불일치 시 즉시 알림" 이라고만 명시 (source: security__ops__audit-logs.md §Layer 1).

  • 방향 1: ledger_entries 의 action_ref → signing_events 가 모두 있는지 (고아 검출)
  • 방향 2: signing_events.tx_hash → chaindb.chain_events 가 confirmed 인지 (체인 비-제출 검출)
  • 방향 3: 같은 (account, mint) 의 잔액 = Σ ledger_entries.amount 인지 (read-model drift 검출)

chaindb — 온체인 사건 ingest

Solana RPC(?) 를 폴링 / WS 구독으로 받아온 deposit / withdrawal 이벤트 + 검증 결과를 append-only 로 저장. signing_events.tx_hash ↔ chain_events.tx_hash 로 cross-DB join.

표 (추정)용도주요 컬럼
chain_events모든 관심 트랜잭션의 chain ingesttx_hash · block_slot · confirmed_at · raw_payload · source (slot finalized status)
deposit_verifications입금 검증 결과tx_hash · destination · token_mint · amount · status (verified / suspicious / failed) · verified_at
chain_observer_cursor (★)마지막 처리 slot — 재시작 시 resume 지점cursor_slot · updated_at

입금 검증 — 노드월렛이 차단하지 않는다

중요한 비-책임 (source: compliance__architecture.md §한계와 비책임):

승인자는 입금을 차단할 수 없다 — 입금 트랜잭션은 이미 체인에 실행된 사건. flow_type=deposit 규칙은 입금 후 후속 스윕의 정책 결정에 적용된다.

입금 자체의 검증 (지갑 주소 매칭 · 토큰 종류 · 금액 정확성 · finality 확인) 은 chaindb 의 deposit_verifications 단계에서 처리. 의심스러운 입금은 후속 스윕을 Held 시킨다.

Sweep — 입금된 자금의 omnibus 이동

Solana 의 SPL token / Native SOL 입금은 사용자 지갑 → omnibus(?) 지갑으로 sweep. NodeWallet 의 sweep 은 출금과 동일한 3-key 서명 경로를 거친다 (source: security__architecture__multisig.md §작업별 차이) — internal shortcut 없음.

sequenceDiagram
  participant Chain as Solana
  participant Observer as Chain Observer
  participant ChainDB as chaindb
  participant Verify as Deposit Verifier
  participant Coord as Coordinator
  participant Ledger as ledgerdb
  participant Audit as auditdb

  Chain->>Observer: token transfer event
  Observer->>ChainDB: chain_events INSERT
  Observer->>Verify: enqueue verify
  Verify->>Verify: 지갑 주소 + token mint + amount 검증
  Verify->>ChainDB: deposit_verifications INSERT (status=verified)
  Verify->>Coord: trigger sweep eligibility (flow=deposit 룰 평가)
  Coord->>Ledger: ledger_entries INSERT (credit, user 계정)
  Note over Coord: sweep 은 별도 3-key 트랜잭션 (sm-deposit-withdrawal 참고)

ERD — ledgerdb · chaindb 그리고 cross-DB

erDiagram
  ledger_entries }o--|| signing_events : "action_ref (cross-DB)"

은행 도입 시 결정해야 할 것

  • finality 기준 — Solana 는 confirmed / finalized 두 단계. 입금 ack 를 어디서 줄지 + sweep eligibility 조건. NodeInfra docs 미명시 — 보통 finalized 권장.
  • account_balances 일관성 — Coordinator 의 EvaluationContext 사전계산이 stale 잔액을 보면 잘못된 Allow 가능. NodeInfra 는 "race condition 처리는 잔액-원장 트랜잭션 경계 안" 이라고 명시 — 실제 구현 패턴 (예: SELECT FOR UPDATE / serializable / version column) 은 은행이 결정.
  • RPC redundancy — 단일 Solana RPC 노드 의존은 가용성 risk. 운영자 RPC 클러스터 + 자체 노드 + 외부 RPC fallback.
  • reconciliation cadence — 60초 권장이지만 실제 cadence + 불일치 시 alert routing 은 은행이 결정.
