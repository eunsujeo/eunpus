작업별 3-key 사용 차이

작업개시승인실행 (체인)설명
Withdraw✓✓✓체인 트랜잭션. 3-key 전부.
Sweep✓✓✓출금과 동일한 3-key 의식. internal shortcut 없음 — 체인 관점에서 sweep 도 withdrawal.
Unsafe-send✓✓✓★ 가스대납 충전 등 administrative 체인 작업. docs 단편.
Transfer✓✓—내부 원장 이동. 체인 서명 없음. 엔클레이브의 verify_and_authorize 영수증이 Layer 1 감사에 기록.
Deposit———관찰 경로. 체인 이벤트를 chaindb 가 수집·검증. 사용자 잔액 credit 후 sweep 이 별도 3-key 의식.

키 탈취 시나리오 (vendor 자기서술)

탈취된 키공격자가 할 수 있는 것막히는 지점
개시 키만요청 위조 시도승인자가 정책 위반으로 차단 → 승인 키 co-sign 없음 → 엔클레이브에 도달 못함
승인 키만정책 우회 시도유효한 개시 키 서명 없이는 요청 자체가 도달하지 않음 (SPKI 검증)
실행 키만체인 서명 시도개시 서명 없이는 서명 대상 요청 자체가 생성되지 않음 (엔클레이브 IPC 거부)
HSM 전체 탈취개시 키 · 승인 키 접근 시도FIPS 140-3 Level 3 물리 방호 — 탈취되어도 키 추출 불가. 실행 키는 SGX 봉인으로 HSM 과 독립.
SGX 호스트 탈취실행 키 서명 시도sealed blob 은 MRENCLAVE 봉인 — 다른 이미지로 언실 불가. EPC 메모리는 CPU 내부 암호화.

SigningPayload v1 의 검증 경로

모든 payload 는 다음 단계를 거쳐 3 위치에서 검증된다 (source: security__architecture__tenant.md):

  1. Coordinator — TLS mTLS + API 키 서명 검증 + 60초 timestamp + tenant_id ↔ 개시 키 SPKI-hash 검증 + (initiator_pubkey, nonce) 멱등성 검사
  2. Approver — tenant_id 로 승인 키 선택 + 정책 평가 + co-sign + decision append-only INSERT
  3. Enclave — DCAP 세션 검증 + tenant_id ↔ 실행 키 SPKI 검증 (3 번째 교차) + 세션 nonce 검증 + BIP-44 경로 검증 + Ed25519 서명

3 위치에서의 SPKI 교차검증이 테넌트 격리의 핵심. 한 위치만 우회되어도 다른 두 위치에서 거부.

왜 MPC 가 아니라 3-key multisig 인가

NodeInfra docs 의 자기서술적 근거 (★ Hypothesis 정리, source: vendor-specific-patterns.md P2.1):

  • auditability — MPC 는 분산 share 에서 하나의 서명. 각 share 의 기여를 사후 검증하기 어렵다. 3-key 는 3개 별도 서명 이 모두 보존 → 누가 무엇을 서명했는지 명백.
  • FIPS 정합성 — HSM (FIPS 140-3 Level 3) 의 물리 방호로 키 추출 불가. MPC 의 분산 share 는 FIPS 인증 모델 안에서 단순히 표현 안 됨.
  • 한국 인증 — KCMVP · 보안기능확인서 등 한국 조달 인증이 HSM-기반 아키텍처에 align.
  • 운영 분리 — HSM 파티션 + m-of-n 운영자 쿼럼은 금융기관의 전통적 권한 분리 모델과 매핑이 직관적.

은행 도입 시 결정해야 할 것

  • SDK 통합 — Spring Boot Auto-Config 사용 vs 수동 설정. type-safe 도메인 모델 (SolanaAddress · WalletId · TokenId) 사용 강제.
  • reference_id 생성 전략 — UUID v4 / v7 / 자행 거래번호. 60초 timestamp 와의 결합.
  • Sweep cadence — 사용자 입금이 즉시 sweep 되나, batch 로 모아 sweep 하나. 후자가 fee 절감하지만 사용자 출금 시 지연.
  • Transfer vs Withdraw 정책 분리 — internal transfer 는 체인 fee 없고 더 freely 허용. 그러나 거액 internal 이체도 audit 필요.
  • 3-key 작업의 SLA — 정상 출금의 end-to-end 시간 (개시 → 승인 → 실행 → Solana 확정) 의 95p / 99p latency 목표.
