signing_events — 결정과 서명을 한 행에 묶는 cross-DB 증거

이 표가 노드월렛 감사 설계의 핵심이다. 한 체인 서명 이벤트마다 INSERT 되며, approver_decision_rationale 에 approverdb 의 PolicyDecision 을 CBOR 로 byte-deterministic 하게 재포함한다. 두 DB 가 독립적으로 변조되어도 결정 ↔ 서명 link 가 보존됨 (source: compliance__architecture.md 시간·증거 격리).

왜 CBOR 재포함이 강한가: CBOR 은 byte-deterministic — 같은 PolicyDecision 객체는 항상 같은 바이트 시퀀스. approverdb 의 결정 컬럼이 사후 변조되면 CBOR re-encode 와 signing_events 의 저장 CBOR 이 불일치 → 즉시 탐지. cross-DB tamper-evidence (source: vendor-specific-patterns.md P4.2).

key_lifecycle — 5 상태 전환 이벤트

모든 키의 5 단계 수명주기 (생성 → 봉인 → 활성 → 교체 → 폐기) 가 이 표에 append (source: security__keys__lifecycle.md):

event_type의미증인 / 증거
key.generatedHSM 내부 키 생성생성 세레머니 참여자 서명 (m-of-n 운영자 쿼럼)
key.sealed키 봉투 (sealed blob) 물리 보관소 격납봉투 서명 + 보관 위치 기록
key.activated활성 — 실제 서명에 사용 시작활성화 명령 + 감사 로그
key.rotation.started신규 키와 이전 키가 동시 유효 (병행 기간)로테이션 개시 승인
key.rotation.completed신규 키 단독 활성 → 이전 키 폐기
key.revokedHSM 에서 제거, 재사용 불가폐기 사유 (정기 / 긴급 / 탈취 의심) + 확인 증인

append-only 강제 — prevent_mutation()

3 표 모두에 같은 패턴의 trigger 적용 (source: pm-db-design-notes.md):

-- ★ 추정 구현 — vendor docs 는 trigger 의 존재만 명시
CREATE FUNCTION prevent_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'append-only: % not allowed on %', TG_OP, TG_TABLE_NAME;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER signing_events_no_update
  BEFORE UPDATE OR DELETE OR TRUNCATE ON signing_events
  FOR EACH STATEMENT EXECUTE FUNCTION prevent_mutation();

감사관 검증 절차 (source: security__ops__audit-logs.md)

  1. DCAP 원격 증명 — 엔클레이브 공개키 확보 (MRENCLAVE 바인딩)
  2. 영수증 서명 검증 — signing_events.chain_sig 를 엔클레이브 공개키로 검증
  3. 시점별 상태 증명 — 체크포인트 테이블 (ledgerdb) 에서 원하는 시점의 서명된 체인 헤드 조회
  4. 해시체인 재구성 — 원장 엔트리로부터 SHA-256 chain 을 다시 만들어 체크포인트의 체인 헤드와 일치 확인
  5. FK 정합성 — 연속된 두 체크포인트 사이의 모든 ledger 엔트리가 영수증을 가진 action 을 참조하는지 확인

은행 도입 시 결정해야 할 것

  • retention — 한국 금융권 규제는 거래 기록 5년 또는 그 이상. auditdb 의 row 크기 × 일평균 거래 수 × 5년 → 저장 sizing 추정.
  • cold archive — WORM(?) 스토리지로 일정 기간 후 이관. append-only trigger 와 충돌하지 않도록 read-replica + 외부 sink 로 ship.
  • DCAP collateral 캐시 — 망분리 환경에서 Intel PCS 접근 어려움. internal mirror 의 collateral refresh 주기 결정.
  • MRENCLAVE rotation 절차 — 이미지 교체는 master_key_operations 의 re-provisioning 으로 기록. rotation 빈도 + 검증 자동화 도구.
절대 금지

auditdb 의 어떤 행이라도 UPDATE / DELETE 가 성공하면 (예: application user 에 권한이 잘못 부여되어) 2-layer 감사 보증이 일부 무너진다. 운영 권한 검증을 release / migration 마다 자동 테스트로 강제할 것 (★ 권장).
