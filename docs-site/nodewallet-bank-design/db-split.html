3. 4-DB 분할

approverdb · auditdb · ledgerdb · chaindb — 단일 DB 로 lifecycle 전체를 못 보게 한다
출처

pm-db-design-notes.md 섹션 1, compliance__architecture.md 데이터 모델, security__ops__audit-logs.md.

왜 4개로 쪼개나

축 1 — 책임 분리: 정책 / 서명 / 잔액 / 체인 이벤트는 서로 다른 mutability profile 과 접근 패턴을 갖는다. 한 DB 에 묶으면 한 침해가 4 영역 모두를 건드린다.
축 2 — 증거 사슬: 결정 (approverdb) 과 서명 (auditdb) 이 분리되어 있어야 한 쪽 변조로 두 쪽을 합리화하는 공격이 어렵다. signing_events 가 approver_decision_rationale 로 결정 CBOR 을 재포함하면 두 DB 가 cross-bound.
축 3 — 평가 hot path: Approver 는 ledger 를 직접 조회하지 않는다. Coordinator 가 미리 계산한 EvaluationContext 만 받는다 — Approver 단순화 + ledger 일관성 부담은 ledger 트랜잭션 경계 안에서만 유지.

DB 엔진 — vendor 미명시

NodeInfra docs 는 PostgreSQL / MySQL 등 DB 엔진을 명시하지 않는다. prevent_mutation() trigger 함수의 패턴은 PostgreSQL 의 PL/pgSQL 또는 MySQL 의 stored function 으로 구현 가능. 한국 금융권 표준은 보통 Oracle / MySQL / Tibero 인데 NodeInfra 가 어느 것을 default 로 두는지는 onboarding 시 확인 필요 (★ Hypothesis).

운영 규칙 (DB 분할이 효과를 가지려면)

  1. cross-DB 트랜잭션 없음 — 4 DB 는 각자 commit. 한 요청이 여러 DB 에 쓸 때는 outbox/saga 패턴.
  2. append-only trigger 는 우회 불가 — superuser 도 우회하지 못하도록 application user 권한을 분리.
  3. backup 정책 차이 — auditdb 는 forensic 용도라 매우 긴 retention · WORM 권장. approverdb 는 운영 중 자주 변경되므로 더 짧은 retention 도 가능.
  4. schema migration — NodeInfra release 가 schema 변경을 동반하면 4 DB 모두에 migration. 단방향 (rollback 어려움) — append-only 데이터를 안전하게 다루는 도구가 필요.
반-패턴

"빠른 시작" 명목으로 4 DB 를 하나의 schema 에 몰아넣으면 — 결정과 서명이 한 BEGIN/COMMIT 안에 묶이는 순간 cross-DB tamper-evidence 가 무너진다. 같은 인스턴스 안에 두더라도 4 schema · 4 user · 4 권한 으로 분리하는 것이 최소 보존선.
