9. 10 Policy Rules

closed set 10종 + priority + short-circuit + 3-verdict (Allow / Held / Deny)
출처

compliance__rules__*.md (각 rule 개별 페이지), compliance__decision-lifecycle.md §우선순위 평가, pm-db-design-notes.md §5 (10 rule catalog).

평가 알고리즘 — priority + short-circuit

활성 규칙은 priority 오름차순으로 평가된다. 첫 번째 Deny 또는 Held 에서 즉시 반환 — 뒤따르는 규칙은 평가하지 않는다 (source: compliance__decision-lifecycle.md).

fn evaluate(request) -> PolicyDecision:
    ctx = compute_evaluation_context(request)  // coordinator pre-computes
    rules = active_rules.snapshot()  // ArcSwap atomic snapshot
    sorted = rules.sorted_by(priority asc)
    for rule in sorted:
        verdict = rule.evaluate(request, ctx)
        if verdict in [Deny, Held]:
            return verdict  // short-circuit
    return Allow

우선순위 설계 가이드 (NodeInfra docs 권장)

  • 10-19 — 사고 대응 (global_halt). 다른 모든 검사를 우회해야 하므로 최저값.
  • 20-39 — 정적 차단 (address_list denylist · time_window). DB 조회가 가볍거나 없음.
  • 40-59 — 한도 (per_tx_amount_limit · daily_withdrawal_limit · velocity_limit).
  • 60-79 — 동적 차단 (address_cooldown · velocity_window). DB 조회 필요.
  • 80-99 — 수동 게이트 (approval_tier). 위에서 다 통과한 경우만 의미.
  • 100+ — 커스텀 (expression).

같은 priority 끼리는 평가 순서가 보장되지 않는다 — 의존 관계가 있는 규칙은 priority gap 으로 분리.

10 rule 상세

1. global_halt — 전체 차단 (사고 대응)

{
  "rule_type": "global_halt",
  "flow_type": "withdrawal",  // 또는 "*"
  "priority": 10,
  "config": { "message": "긴급 점검 — 전체 출금 정지 (티켓 #2026-05-22-001)" }
}

모든 거래를 즉시 Deny. 사고 발생 시 가장 먼저 활성화하는 kill-switch.

2. address_list — 주소 화이트/블랙리스트

{
  "rule_type": "address_list",
  "flow_type": "withdrawal",
  "mint": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v", // USDC mint
  "priority": 30,
  "config": {
    "condition_set_id": "vasp-allowlist-kr",
    "mode": "whitelist"
  }
}

VASP 화이트리스트 패턴 (트래블룰 첫 단계). mode 가 whitelist 면 list 외 destination 차단, blacklist 면 list 안 destination 차단.

3. time_window — 영업시간 제한

{
  "rule_type": "time_window",
  "flow_type": "withdrawal",
  "priority": 35,
  "config": {
    "start_hour": 9,
    "end_hour": 18,
    "timezone": "Asia/Seoul",
    "days_of_week": [1, 2, 3, 4, 5]  // 월-금
  }
}

영업시간 외 / 휴일 출금을 차단. EFTA 의 영업시간 운영 의무에 대응.

4. per_tx_amount_limit — 건당 절대 한도

{
  "rule_type": "per_tx_amount_limit",
  "flow_type": "withdrawal",
  "mint": "NATIVE_SOL",
  "priority": 45,
  "config": { "max_amount_lamports": 100000000000 }  // 100 SOL
}

위에 어떤 정책이 있어도 절대 넘을 수 없는 상한. approval_tier 와 조합 — 상한 안에서 구간별 승인 강도 차등.

5. daily_withdrawal_limit

{ "config": { "max_daily_lamports": 500000000000 } }  // 500 SOL/일

코디네이터가 미리 계산한 daily_withdrawal_total (오늘 누적 출금) 과 비교. 누적이 max 를 넘으면 Deny.

6. velocity_limit — 일일 건수

{ "config": { "max_count_per_day": 100 } }

오늘 누적 출금 건수 가 max 이상이면 Deny. 횡령형 다발 인출 차단.

7. velocity_window — 슬라이딩 윈도우

{
  "config": {
    "window_seconds": 600,    // 10 분
    "max_count": 5,
    "max_amount_lamports": 1000000000
  }
}

velocity_windows 표의 최근 N 초간 row 를 합산하여 건수 또는 금액 둘 중 하나라도 초과 시 Deny. 단시간 burst 차단.

8. address_cooldown — 신규 주소 쿨다운 (Held 발화)

{
  "config": {
    "threshold_lamports": 5000000000,   // 5 SOL
    "cooldown_seconds": 7200            // 2 시간
  }
}

주소가 address_first_use 표에 처음 등장 (또는 cooldown 미경과) 이면서 금액이 threshold 초과 → Held. cooldown 경과 후 자동 해소. 사회공학으로 새 주소를 받아 즉시 거액 이체하는 패턴 차단.

9. approval_tier — 금액 구간별 수동 승인 (Held 발화)

// 0 ~ 5 SOL : 자동 승인
{ "config": { "min_amount_lamports": 0, "max_amount_lamports": 5000000000, "approval_mode": "AUTO" } }

// 5 ~ 50 SOL : 단일 승인 — Held
{ "config": { "min_amount_lamports": 5000000001, "max_amount_lamports": 50000000000, "approval_mode": "SINGLE_APPROVE" } }

// 50 SOL 초과 : 2-of-3 의식 — Held
{ "config": { "min_amount_lamports": 50000000001, "max_amount_lamports": 9223372036854775807, "approval_mode": "QUORUM_2_OF_3" } }

amount 가 구간에 들면 approval_mode 에 따라 동작 (source: compliance__rules__approval-tier.md):

  • AUTO → Allow
  • SINGLE_APPROVE → Held (단일 운영자 외부 승인 필요)
  • QUORUM_2_OF_3 → Held (3인 중 2인 의식 승인 필요)

콘솔 폼 매핑: dropdown 의 auto → AUTO, single → SINGLE_APPROVE, dual → QUORUM_2_OF_3 (source: compliance__rules__approval-tier.md §콘솔 폼 매핑). i64::MAX = 9223372036854775807 을 상한으로 두면 "그 이상 전체" 표현. 구간이 겹치면 priority 같을 때 어느 행이 매치되는지 보장 안 됨 — +1 차이로 엄격 분리.

Held 의 외부 해소 패턴

콘솔에 "승인 버튼" 이 없는 이유 (★ 권한 분리 + 결정론적 재평가). Held 해소는 다음 절차:

  1. 외부 의식 (운영자 회의 · 별도 시스템 승인 · 키 의식)
  2. approval_tier 행을 임시 AUTO 로 수정 (policy_change_log 에 기록됨)
  3. coordinator 폴링이 다음 평가에서 Allow → 정상 진행
  4. 평가 통과 즉시 approval_tier 를 원래대로 복원 (역시 policy_change_log 에 기록)

변경 자체가 영구 감사 흔적 — old_data / new_data 가 모두 보존된다. 외부 의식의 evidence (서명된 회의록 등) 와 묶이면 sound 한 감사 추적.

10. expression — 커스텀 룰 (escape valve)

{
  "rule_type": "expression",
  "flow_type": "withdrawal",
  "priority": 110,
  "config": {
    "action": "DENY",
    "conditions": [
      { "field": "amount", "operator": "gte",
        "value": { "type": "int", "value": 1000000 } },
      { "field": "destination", "operator": "not_in",
        "value": { "type": "string_list", "value": ["UpbitHot1...", "BithumbHot1..."] } }
    ]
  }
}

field/operator/value DSL 로 임의 조건. 모든 condition 이 true 면 action 발화. closed 10 종 으로 표현 안 되는 케이스의 escape valve.

한계: 현재 expression 페이지가 404 — vendor docs 의 명시적 spec 미비 (source: inventory.md §4.3.4). DSL 의 operator 목록 / 지원 type / type coercion 은 onboarding 시 확인 필요.

EvaluationContext — 코디네이터가 계산하는 상태값

승인자는 ledger 를 직접 조회하지 않는다. coordinator 가 미리 계산해서 넘긴다 (source: compliance__decision-lifecycle.md):

pub struct PolicyContext {
    pub flow_type: FlowType,         // Withdrawal / Deposit / Transfer
    pub request_id: Uuid,
    pub wallet_id: Uuid,
    pub destination: String,
    pub amount: i64,                 // lamports
    pub fee: i64,
    pub mint: String,                // "NATIVE_SOL" 또는 SPL mint
    pub context: EvaluationContext,
}

pub struct EvaluationContext {
    pub daily_withdrawal_total: Option<i64>,  // 오늘 누적 출금
    pub daily_withdrawal_count: Option<i64>,  // 오늘 누적 건수
    pub account_balance: Option<i64>,         // 현재 잔액
}

필수 field 가 None 이면 규칙은 PolicyError 를 반환하고 fail-closed (Deny) 처리.

Hot reload (ArcSwap)

  1. Admin API 또는 콘솔이 policy_rules 를 INSERT/UPDATE/DELETE
  2. DB trigger 가 policy_change_log 에 INSERT (created_by · old_data · new_data)
  3. 승인자의 loader 태스크가 변경 감지 → 새 규칙 집합 build → ArcSwap 으로 원자적 교체
  4. 다음 /v1/evaluate 호출부터 새 규칙 적용

일관성 보장: 평가 중인 단일 요청은 평가 시작 시점의 규칙 스냅샷을 끝까지 사용. 절반은 옛 규칙 / 절반은 새 규칙 race 는 발생하지 않는다.

은행 도입 시 결정해야 할 것

  • 규칙 카탈로그 design — flow_type × mint 조합으로 어떤 룰을 어느 priority 에 두는지. NodeInfra 권장 priority 대역 안에서 자행 룰 배치.
  • condition_set 큐레이션 — VASP 화이트리스트의 source · 검증 절차 · update cadence.
  • approval_tier 구간 설계 — 자행의 거래 분포 + 자행의 운영자 capacity 에 맞춰 AUTO / SINGLE / QUORUM 구간 결정.
  • 운영자 외부 의식 채널 — Held 해소를 위한 외부 승인 절차의 evidence 보존 방식 (회의록 서명 · 별도 시스템 로그 · email + 보존된 PDF 등).
  • 긴급 freeze 절차 — global_halt 활성화 권한 + 활성/해제 ceremony.
