13. 2-Layer 감사

Layer 1 (실시간 사기 방어) + Layer 2 (사후 변조 탐지) — 둘 다 필수, 어느 하나도 충분하지 않다
출처

security__ops__audit-logs.md 전체 (가장 dense single source). compliance__architecture.md §시간·증거 격리.

두 Layer 의 분담

Layer방어 시점메커니즘막는 공격
Layer 1실시간작업별 TEE 영수증 + FK 제약 + 60초 이하 정합성 체크가짜 ledger entry · 체인 서명 위조
Layer 2사후SHA-256 prev_hash 해시체인 + 주기적 enclave-signed checkpoint과거 entry 수정 · 삭제 · 재정렬

vendor docs 가 명시: "둘 다 필요하다" — Layer 1 은 사후 변조에 약하고, Layer 2 는 실시간 사기에 무력. 한 쪽만으로는 보증 사각지대.

Layer 1 — 작업별 TEE 영수증

모든 원장 변경 작업이 엔클레이브가 서명한 영수증과 함께 기록된다:

작업영수증 형태
Withdraw / Sweep체인 트랜잭션의 Ed25519 서명 = 영수증 (실행 키)
Transfer (internal)엔클레이브 verify_and_authorize 영수증을 signing_events 에 저장
Deposit원장 엔트리가 검증된 온체인 deposit (chaindb) 과 대조 — 입금 entry 의 reference 가 chain_events 행

구조적 불변 — FK 제약

ledger_entries 는 반드시 영수증이 있는 작업 레코드를 참조한다. 고아 엔트리는 구조적으로 불가능 — DB FK 가 거부 (source: security__ops__audit-logs.md §Layer 1).

-- 같은 DB 라면 직접 FK
ALTER TABLE ledger_entries
  ADD CONSTRAINT fk_action_ref
  FOREIGN KEY (action_ref) REFERENCES signing_events(id);

-- DB 가 분리되어 있다면 application 단의 정합성 체크 (60초 이하 권장)

정합성 체크 (Reconciliation) — 60초 이하 권장

vendor docs 가 권장: "원장 ↔ 작업 레코드 ↔ 온체인 상태를 짧은 주기 (60초 이하) 로 대조하며, 불일치 시 즉시 알림":

  • ledger_entries.action_ref → signing_events 존재 여부
  • signing_events.tx_hash → chaindb.chain_events 일치 + finality
  • account_balances = Σ ledger_entries.amount (drift 검출)
  • deposit_verifications.status=verified → 대응 ledger credit 존재

Layer 1 이 막는 공격

공격막히는 지점
가짜 internal credit 삽입 (예: DB write 권한자가 "10M USDC credit" entry 삽입)대응하는 작업 레코드가 없거나 영수증이 없음 → 정합성 체크에서 즉시 탐지
체인 서명 위조실행 키가 엔클레이브 밖으로 나간 적이 없음 → 불가능

Layer 2 — 해시체인 + 체크포인트

계정별 ledger entry 가 SHA-256 해시체인으로 연결되며, 엔클레이브가 주기적으로 체인 헤드에 서명:

entry.hash       = SHA-256(entry.prev_hash ‖ entry.fields...)
entry.prev_hash  = 같은 account 의 이전 entry 의 hash

checkpoint.sig   = EnclaveSign(chain_head_hash ‖ account_id ‖ entry_count ‖ timestamp)
checkpoint.mrenclave = 어느 엔클레이브 이미지가 서명했는지

체크포인트 cadence

vendor docs 명시: 1시간 또는 100 entries 중 먼저 도달하는 시점 (source: security__ops__audit-logs.md §Layer 2). 트래픽이 적은 계정도 시간 보장, 많은 계정도 count 보장.

Layer 2 가 제공하는 것

  • 사후 변조 탐지 — 과거 entry 를 수정하면 해시체인이 깨지고, 마지막 체크포인트가 더 이상 일치하지 않는다.
  • 특정 시점 상태 증명 — "2026-04-15 14:00 UTC 기준 원장 상태?" 에 서명된 체크포인트로 답변.
  • 비부인성 — 서명된 체크포인트 시점의 원장 내용을 운영자가 부인할 수 없다.

Layer 2 가 하지 않는 것 (중요한 한계)

vendor 자기서술: Layer 2 는 실시간 사기를 막지 않는다

체크포인트 사이에 공격자가 일관된 가짜 entry (뒤따르는 해시까지 재계산) 를 삽입하면, 다음 체크포인트는 그 변조된 체인 헤드에 서명한다. 엔클레이브는 체크포인트 시점에 주어진 체인 헤드를 서명할 뿐, "올바른 체인 헤드가 무엇이어야 하는지" 를 독립적으로 알지 못하기 때문. 실시간 방어는 Layer 1 의 FK 제약 + 정합성 체크가 담당.

위협 모델 매트릭스

감사관 검증 절차 (5 단계)

  1. DCAP 원격 증명 — 엔클레이브 공개키 확보 (MRENCLAVE 바인딩)
  2. 영수증 서명 검증 — 원장 entry / 작업 레코드의 영수증을 엔클레이브 공개키로 검증
  3. 체크포인트 조회 — 원하는 시점의 서명된 체인 헤드
  4. 해시체인 재구성 — 원장 entry 로부터 chain 을 다시 만들어 체크포인트의 chain head 와 일치 확인
  5. FK 정합성 확인 — 연속된 두 체크포인트 사이의 모든 entry 가 영수증을 가진 action 을 참조

MRENCLAVE rotation 의 감사 흔적

이미지 교체 시 새 MRENCLAVE 가 발생. 모든 새 체크포인트는 새 MRENCLAVE 로 서명되며, 이전 MRENCLAVE 의 체크포인트는 historical 검증용으로 영구 보존되어야 한다. 이전 MRENCLAVE 값 분실 = 그 기간 감사 검증 불가.

은행 도입 시 결정해야 할 것

  • auditdb retention — 한국 금융권: 거래 기록 5년 + 자금세탁 의심 30년 등. signing_events 의 row 크기 + 일평균 트랜잭션 + 5-30년 → 저장 sizing.
  • WORM archive — auditdb 의 row 를 일정 기간 후 WORM 스토리지로 ship. append-only trigger 와 충돌 없도록 외부 sink (Kafka → S3 / Glacier).
  • DCAP collateral — 망분리 환경에서 Intel PCS 접근 어려움 → internal mirror 의 refresh 주기.
  • 감사관 access — read-only role + view 로 entry / receipt / checkpoint 노출. CBOR PolicyDecision 디코더 도구 제공.
  • MRENCLAVE registry — 모든 deployed MRENCLAVE 의 hash 와 release notes 를 영구 보존.
  • reconciliation alert routing — 60초 이하 cadence 의 불일치를 어디로 (SIEM · SOAR · ChatOps · email).
