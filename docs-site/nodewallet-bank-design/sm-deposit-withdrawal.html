12. 입금 · 출금 흐름

4 종 작업의 lifecycle — 입금 (관찰) · sweep (3-key) · 출금 (3-key) · 내부 transfer (2-key + 영수증)
출처

security__architecture__multisig.md 작업별 차이 (4 작업 종류), compliance__architecture.md 한계와 비책임 (입금 차단 불가), security__ops__audit-logs.md Layer 1 (작업별 영수증).

입금 (Deposit) — 관찰 경로

입금 트랜잭션은 이미 체인에 실행된 사건이라 노드월렛이 차단할 수 없다 (source: compliance__architecture.md 한계와 비책임). 관찰 + 검증 + 사용자 잔액 credit + 후속 sweep eligibility 판단만 수행.

sequenceDiagram
  participant Customer as 사용자
  participant Chain as Solana
  participant Obs as Chain Observer
  participant ChainDB as chaindb
  participant Verify as Deposit Verifier
  participant Coord as Coordinator
  participant App2 as Approver
  participant Ledger as ledgerdb

  Customer->>Chain: USDC 전송 (사용자 지갑 주소로)
  Chain-->>Chain: confirmed → finalized
  Obs->>Chain: poll / WS 구독
  Chain-->>Obs: token transfer event
  Obs->>ChainDB: chain_events INSERT
  Obs->>Verify: trigger verify
  Verify->>Verify: 주소 매칭 + token mint + 금액 검증
  Verify->>ChainDB: deposit_verifications INSERT (status=verified)
  Verify->>Coord: deposit ack
  Coord->>App2: /v1/evaluate (flow_type=deposit, 후속 스윕 정책)
  alt Allow (정상 입금)
    App2-->>Coord: AutoApprove
    Coord->>Ledger: ledger_entries INSERT (credit, 사용자 계정)
    Coord->>Coord: sweep 큐에 enqueue (별도 worker)
  else Held (의심 입금)
    App2->>App2: held_deposits INSERT
    Note over Coord: 후속 sweep 보류 — 영업 채널 검토 후 해소
  else Deny
    App2->>App2: policy_decisions INSERT (REJECT)
    Note over Coord: 사용자 잔액 credit 안 함 → 운영 alert
  end

Sweep — 사용자 지갑 → omnibus

vendor docs 가 명시: "Sweep 은 출금과 동일한 서명 경로를 따른다" (source: security__architecture__multisig.md 작업별 차이). 체인 관점에서 sweep 도 한 트랜잭션의 source 가 사용자 지갑이므로 withdrawal 과 같은 보안 envelope.

sequenceDiagram
  participant Worker as Sweep Worker
  participant SDK as Java SDK
  participant HSM_A as HSM (개시 키)
  participant Coord as Coordinator
  participant App2 as Approver
  participant HSM_B as HSM (승인 키)
  participant Enc as SGX Enclave
  participant Solana
  participant GasW as Gas-payer Wallet

  Worker->>SDK: sweep(userWalletId, omnibusWalletId, mint)
  SDK->>HSM_A: 개시 서명
  Note over SDK,Coord: 이하 sm-signing 의 3-key 시퀀스와 동일
  SDK->>Coord: signed request
  Coord->>App2: /v1/evaluate (flow_type=deposit 의 후속 스윕)
  App2->>HSM_B: 승인 키 co-sign
  Coord->>Enc: CBOR IPC
  Enc-->>Coord: 실행 키 서명 (Ed25519)
  Note over Coord,Solana: gas-payer 가 SOL 수수료 대납
  Coord->>Solana: submit (fee_payer = gas-payer wallet)
  Solana-->>Coord: tx_hash
  Coord->>Coord: ledgerdb + auditdb INSERT

출금 (Withdraw) — 가장 풍부한 경로

전체 3-key 시퀀스는 11. 3-key 서명 흐름 의 success path 다이어그램 참고. 여기서는 출금 lifecycle 의 macro 상태 머신을 정리.

stateDiagram-v2
  [*] --> REQUESTED: SDK.withdraw()
  REQUESTED --> SDK_SIGNED: 개시 키 PKCS#11 서명
  SDK_SIGNED --> EVALUATING: Coordinator → Approver
  EVALUATING --> DENIED: 1 rule = Deny
  EVALUATING --> HELD: 1 rule = Held
  EVALUATING --> APPROVED: 모든 pass + 승인 키 co-sign
  HELD --> EVALUATING: 폴링 재평가
  HELD --> DENIED_TTL: 24h 경과
  APPROVED --> ENCLAVE_VERIFIED: DCAP 세션
  ENCLAVE_VERIFIED --> CHAIN_SIGNED: 실행 키 서명 + 제로화
  CHAIN_SIGNED --> SUBMITTED: Solana submit
  SUBMITTED --> CONFIRMED: tx_hash + finalized
  SUBMITTED --> FAILED: 체인 reject
  CONFIRMED --> [*]
  DENIED --> [*]
  DENIED_TTL --> [*]
  FAILED --> [*]

Multi-destination?

NodeInfra docs 는 Solana 의 single-destination 트랜잭션을 기준으로 설명. Solana 의 token transfer instruction 은 multi-output 을 지원하지만 NodeWallet 이 multi-dest 트랜잭션 (한 요청에 여러 destination) 을 노출하는지는 ★ Hypothesis — docs 미명시. 보통 batch withdrawal 은 별도 N 개 요청으로 처리하는 것이 idempotency · auditability · partial failure 처리에 유리.

내부 transfer — 체인 서명 없음 + 엔클레이브 영수증

같은 테넌트 안의 ledger account 간 이동. vendor docs 명시 (source: security__architecture__multisig.md 작업별 차이):

Transfer: 내부 원장 이동. 개시 키 + 승인 키만 서명하고, 체인 서명 대신 엔클레이브 verify_and_authorize 영수증이 감사 로그 Layer 1 에 기록된다.
sequenceDiagram
  participant App as Spring Backend
  participant SDK as Java SDK
  participant Coord as Coordinator
  participant App2 as Approver
  participant Enc as SGX Enclave
  participant Ledger as ledgerdb

  App->>SDK: transfer(fromAccount, toAccount, amount, mint)
  SDK->>Coord: signed (개시 키)
  Coord->>App2: /v1/evaluate (flow_type=transfer)
  App2->>App2: 승인 키 co-sign
  App2-->>Coord: AutoApprove
  Coord->>Enc: CBOR IPC (verify_and_authorize)
  Enc->>Enc: 검증 후 영수증 발급 (체인 서명 없음)
  Enc-->>Coord: verify_and_authorize receipt
  Coord->>Ledger: ledger_entries INSERT × 2 (debit + credit)
  Coord->>Coord: auditdb signing_events INSERT (operation=transfer, chain_sig=NULL, enclave_receipt set)
  Coord-->>SDK: transfer_id

flow_type 별 정책 적용

한 룰의 flow_type 으로 적용 범위를 분리:

  • withdrawal — 외부 destination 으로 출금 (Withdraw). 가장 많은 룰이 적용되는 경로.
  • transfer — 내부 ledger 이동.
  • deposit — 입금 후 sweep 정책 (입금 자체는 차단 불가).
  • * — 모든 flow.

gas-payer 잔액 관리

모든 체인 트랜잭션 (sweep / withdraw / unsafe-send) 은 gas-payer 지갑의 SOL 잔액을 소모. 잔액이 임계 미만이면 트랜잭션 submit 실패 → 출금 정지. 운영 패턴:

  • SDK / 외부 모니터 가 gas-payer 잔액을 폴링
  • 임계 미만 시 alert + admin 채널 충전
  • 충전은 별도 출금 (omnibus → gas-payer) 또는 외부 SOL 입금 (외부 거래소 → gas-payer 주소)
  • ★ Hypothesis: 충전 자체도 3-key 의식 (omnibus 가 source 면 withdraw 와 동일 경로)

★ 미명시 — 추가 설계 영역

  • partial failure — Solana submit 후 chain reject (예: insufficient SOL · invalid recent_blockhash) 시 ledger 의 debit 을 어떻게 reverse 할지. vendor docs 미명시. signing_events 는 append-only 이므로 reversal entry 패턴 추정.
  • retry 정책 — 일시적 RPC 실패 시 같은 reference_id 로 retry → idempotency 표가 거부 → 다른 reference_id 필요? 또는 timer-based?
  • chain reorg — confirmed → finalized 사이의 reorg 가능성. NodeInfra docs 가 finality 처리를 명시하지 않음. 보통 finalized 권장.
  • SPL token decimal mismatch — USDC 는 6 decimal, NATIVE_SOL 은 lamports (9 decimal). 룰의 max_amount_lamports 가 mint=* 일 때 decimal 다른 토큰에 의미 흐림 — token 별 룰 권장.
