3-key 가 sequential 인 것이 핵심. 개시 → 승인 → 실행 중 하나라도 빠지면 체인 서명이 안 나간다. 잔액·일일누적 같은 상태는 Approver 가 직접 조회하지 않고 Coordinator 가 미리 계산해서 넘긴다 (Approver hot path 단순화).

vendor docs 가 명시한 3-component 구분 (source: compliance__architecture.md):

컴포넌트역할소유자
컴플라이언스 포털규칙 등록·전환 · 결정/지갑 조회 · 활동 로그컴플라이언스팀 (admin / operator / auditor)
승인자 (정책엔진)규칙 평가 · HSM 승인 키 co-sign · Held 큐 관리자동 (운영자 개입 없음)
코디네이터평가 컨텍스트 사전계산 (잔액·일일누적) · 승인자 호출 오케스트레이션자동

4-축 격리 (vendor 자기서술)

NodeInfra 는 "4-축 격리" 라는 용어로 보안 boundary 를 정리한다 (source: compliance__architecture.md §4-축 격리 안에서의 위치):

  1. 서비스 격리 — 승인 키는 개시 키·실행 키와 분리된 HSM 파티션. 승인자 호스트 탈취 시에도 PKCS#11(?) 외부로 키 자체는 노출되지 않는다.
  2. 키 격리 — HSM 파티션 + SGX sealed blob 의 dual key-custody 도메인.
  3. 테넌트 격리 — 테넌트별 3-key 세트 + SPKI-hash 바인딩 + payload tenant_id 교차검증 (3 키 모두에서).
  4. 시간·증거 격리 — 모든 결정은 policy_decisions 의 해시체인에 기록되고, 후속 signing_events 행이 approver_decision_rationale 로 결정 CBOR(?) 을 재포함 → 결정과 서명 사이가 사후 변조 불가능한 cross-DB 증거로 묶인다.

은행 도입 시 결정해야 할 것 (이 페이지 범위)

  • 망분리 깊이 — HSM/Enclave 호스트를 추가 VLAN 으로 또 분리할지. NodeInfra 권장: 별도 management network.
  • HSM 토폴로지 — 단일 HSM + 3 파티션 (기본) vs 키별 독립 HSM (권장). 후자가 단일 펌웨어 취약점 전파를 막는다 (source: security__keys__hsm.md §다중 HSM 배치 권장).
  • 벤더 다양화 — 예: 개시·승인 키는 Thales Luna, 실행 키는 Utimaco — 단일 vendor 의 monoculture risk 회피.
  • 물리적 DB 분리 — 4 DB 를 4 instance 로 둘지, 1 instance 의 4 schema 로 둘지. NodeInfra docs 는 separate DB 를 전제로 한 cross-DB join 패턴.
  • Coordinator HA — Coordinator 는 load-bearing 컴포넌트. 장애 시 출금 정지 → 핫/콜드 스탠바이 설계.
  • Approver HA — fail-closed 원칙상 Approver 장애 = 출금 정지가 의도된 동작. HA 로 가용성은 높이되 fail-open 으로 가지 않도록.
설명 없는 부분 (★ Hypothesis)

vendor docs 는 컴포넌트별 binary 패키징 형태 · 배포 단위 (k8s pod / systemd / Docker) · OS 권장사항 · 네트워크 ACL 세부 · DB 엔진 (Postgres vs MySQL) 을 명시하지 않는다. 위 다이어그램의 컴포넌트 모듈성은 docs 의 텍스트로부터 추정한 것이며, 실제 배포 단위는 NodeInfra 와 onboarding 시 확인해야 한다.
