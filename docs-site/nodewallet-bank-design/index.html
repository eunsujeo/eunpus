은행 관점에서 핵심은 키 소유권 + 망분리 대응 + 정책 실행 위치. 한국 금융 IT 환경의 망분리 규제 + KCMVP/보안기능확인서 조달 요건이 SaaS 형 MPC 솔루션을 사실상 배제하기 때문에 설치형 HSM+SGX 가 채택된다.

핵심 invariant (어겨선 안 되는 보안 속성 5개)

  1. 개시 ≠ 승인 ≠ 실행 — 3개의 독립 서비스가 각자의 HSM/TEE 키로 서명해야 체인 트랜잭션이 나간다. 어느 하나라도 빠지면 거부 (source: security__architecture__multisig.md).
  2. HSM 키 ≠ SGX 키 — 개시·승인 키는 HSM 파티션, 실행 키는 SGX-sealed blob. 두 key-custody 도메인이 독립. HSM 전체 탈취도 실행 키에 영향 없음 (post-provisioning 이후 HSM 오프라인 가능).
  3. 테넌트 A 키 탈취 ≠ 테넌트 B 영향 — 테넌트별 3-키 세트 + SPKI-hash(?) 바인딩 + 매 payload 의 tenant_id 검증. 한 계열사 키 탈취가 다른 계열사로 전파되지 않는다 (source: security__architecture__tenant.md).
  4. shadow_mode(?) 없음 + fail-closed — 모든 Deny 는 실제 차단으로 집행. DB/HSM/서명검증 실패는 모두 Deny 로 매핑. 승인자 장애 = 출금 정지 는 의도된 안전 기본값 (source: compliance__decision-lifecycle.md).
  5. Layer 1 ≠ Layer 2 감사 — 둘 다 필수 — Layer 1 (TEE 영수증 + FK 제약) 은 실시간 사기 방어, Layer 2 (해시체인 + 엔클레이브 서명 체크포인트) 는 사후 변조 탐지. 어느 한 쪽만으로는 불충분 (source: security__ops__audit-logs.md).
Source-first 원칙

본 site 의 모든 fact 는 docs.nodeinfra.com 의 41 페이지 (Mintlify password-gated; 사용자 인증 후 ingest, sources/nodeinfra/) 가 출처. NodeInfra 미명시 항목은 "★ Hypothesis" 로 명확히 분리한다. 추정을 fact 로 옮기지 않는다.

은행이 운영해야 하는 컴포넌트 (NodeInfra 가 만들지 않는 부분)

  • HSM 클러스터 — Thales Luna / Utimaco / YubiHSM2 중 선택. 3-key 다중서명을 위해 3 파티션 또는 3 HSM. m-of-n(?) 운영자 쿼럼 정의.
  • SGX-capable HW — Intel CPU + SGX + DCAP(?) 원격 증명 인프라. MRENCLAVE(?) 이미지 관리.
  • 4개 DB — approverdb · auditdb · ledgerdb · chaindb. NodeInfra 권장은 물리적 분리.
  • Spring backend — 은행 자체 비즈니스 로직. Java SDK + Spring Boot Auto-Configuration 으로 통합.
  • 망분리 — 한국 금융 IT 표준. 내부망 격리 구역에 모든 컴포넌트 배치.
  • 모니터링 · 하드닝 — OS/네트워크 hardening + 보안 모니터링은 customer-운영 책임.

NodeInfra 는 SW + 운영 매뉴얼 + 인증 패키지를 제공한다. SaaS 가 아니므로 벤더 phoning-home 없음, 모든 trust state (키 · 정책 · 감사) 가 은행 perimeter 안에 머문다.
