은행 Fireblocks Cold Wallet 도입 — 수탁형 지갑 reference

은행이 수탁형 지갑 (custodial wallet) 을 운영할 때 Fireblocks Cold Wallet workspace 를 어떻게 배치·운영할지를 정리한 reference. 출처는 모두 Fireblocks Help Center 공식 문서.

본 페이지의 출처 — 어디까지가 공식 사실이고, 어디부터가 저자 추정인가

Fireblocks Cold Wallet 전용 공식 문서 15 건 중 일부는 본 문서가 원문 정밀 인용을 확보하지 못한 상태이다. 본 문서는 다음 두 등급으로 구분한다:

  • 공식 문서에 정의된 사실 — 그대로 받아도 안전 (출처 명시)
  • 저자가 합리적으로 추정한 운영 권장 — 참고용, 본인 환경 검증 권장 (공식 보강 필요)

10 초 요약

  • Cold Wallet 은 별개 workspace product. Hot workspace 와 별도 구매·별도 인프라. (출처: Fireblocks 공식 문서 — Account and Wallet Structure · Vault Structure Best Practices)
  • Workspace 축: Hot/Cold × Mainnet/Testnet 두 직교 축. Cold workspace = "cold wallet 보유, offline storage". (출처: Fireblocks 공식 문서 — Account and Wallet Structure)
  • Approval Group 미지원. Cold Wallet workspace 의 모든 governance 결정은 Admin Quorum 단독 (Risk-G07). (출처: Fireblocks 공식 문서 — Approval Groups)
  • Multi-workspace 6 trigger 중 #6 = "Cold Wallet 분리 (offline regulation 충족)". KR 은행은 이 trigger 가 사실상 강제. (출처: Fireblocks 공식 문서 — Vault Structure Best Practices)
  • Hot ↔ Cold rebalancing 은 별도 P2P 경로로 수행 (Fireblocks 공식 문서 "Connecting Cold Wallet with hot workspaces via P2P"). (출처: Fireblocks 공식 문서)
  • MPC share 분포 모델, device type, signing 절차 — 공식 원문 정밀 인용 미확보 (Q-M05, Q-D-cold).

은행 입장에서 본 3-way 비교

은행 (수탁업자) 이 디지털 자산을 보관할 때 선택 가능한 3 가지 배치 모델. 실제 운영은 대부분 Hybrid (Hot + Cold 병행).

권장 — Hybrid

은행 환경에서 합리적 default 는 ② Hybrid. Hot workspace 가 사용자 입출금 / 일일 운영을 담당하고, Cold workspace 가 (?) bulk reserve 를 담당하며, 정기적 rebalancing 으로 Hot workspace 의 risk exposure 를 제한한다. (출처: Fireblocks 공식 문서 — Vault Structure Best Practices: "Cold Wallet workspace 별도 구매 + rebalancing 권장")

핵심 invariant (5)

  1. Workspace separation — Cold 와 Hot 은 항상 별도 workspace. (출처: Fireblocks 공식 문서 — Vault Structure Best Practices)
  2. Admin Quorum-only governance — Cold workspace 에 approval group 위임 경로 없음. (출처: Fireblocks 공식 문서 — Approval Groups · Risk-G07)
  3. Owner-direct critical ops — user delete, 2FA reset 등 일부 operation 은 Owner Console-direct 만 가능 (Cold 특수 규칙). (출처: Fireblocks 공식 문서 — Admin Quorum)
  4. Support-mediated user add — Cold Wallet workspace 의 user / API key 추가는 Fireblocks Support 경유 필수. (출처: Fireblocks 공식 문서 — "Adding users to a Cold Wallet workspace")
  5. Signature quota monitoring — Cold Wallet 의 "Less than 10% remaining signatures" 이벤트가 Audit Log 의 명시적 모니터링 대상. (출처: Fireblocks 공식 문서 — Audit Log 카테고리)

은행이 Cold Wallet 을 도입하는 이유 — 4 가지

  1. 규제 (KR 특금법 / VACPA) — 가상자산업감독규정 9조: 이용자 가상자산의 80% (경제적 가치 기준) 를 인터넷과 분리하여 보관. 시행령 위임 "≥70%" 범위 내 금융위 정함. (출처: KR 컴플라이언스 가이드 · law.go.kr admRulSeq=2100000244180)
  2. Risk segregation — Hot workspace 의 attack surface (API key 도난, mobile device 분실, SaaS outage) 와 격리. (출처: Fireblocks 공식 risk register)
  3. Audit & 감독 대응 — bulk reserve 의 cold-side 격리가 외부 감사 / 금감원 점검 / 회계 reporting 의 표준 요건
  4. Insurance underwriting — 디지털 자산 보험의 보험료가 cold storage 비율에 강하게 의존. 저자 추정 — 공식 문서 미명세, 산업 표준

이 문서가 다루지 않는 것

  • Fireblocks 내부 MPC share 분포의 정확한 구조 (Cold variant) — 원문 정밀 인용 미확보 (Q-M05)
  • Cold device 의 하드웨어 사양 — Fireblocks 공식 문서명 ("Cold Wallet Device Requirements") 은 존재, 본 문서의 원문 인용 미확보
  • 구체적 signing ceremony 절차 — 공식 문서명 ("Signing transactions with your Cold Wallet device") 은 존재, 본 문서의 원문 인용 미확보
  • KR 특금법의 cold storage 비율 외 추가 수치 — KR 법령 별도 검증 필요
  • 다른 vendor (BitGo, Anchorage 등) 의 cold wallet — 본 문서는 Fireblocks 한정
