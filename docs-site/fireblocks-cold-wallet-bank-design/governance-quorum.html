3. Admin Quorum 단독 거버넌스 — Cold Wallet 의 핵심 제약

Cold Wallet workspace 의 가장 중요한 governance 제약은 Approval Group 미지원. 모든 거버넌스 결정이 Admin Quorum 단독에 집중된다. 은행 도입 시 운영 부담의 70% 가 여기서 발생.

본 페이지의 출처

공식 문서에 정의된 사실

  • Approval Group 미지원 (Risk-G07) — Fireblocks 공식 문서
  • Owner Console-direct 특수 규칙 — Fireblocks 공식 문서
  • Audit Log 의 "Less than 10% remaining signatures" 이벤트 카테고리 존재 — Fireblocks 공식 문서
  • Support 경유 user/API key 추가 — Fireblocks Cold Wallet cluster 문서명에 명시

저자가 합리적으로 추정한 운영 권장 — 참고용

  • Cold variant 의 9-role 적용 매트릭스 (Q-CW04 open)
  • Signature quota 의 정확한 limit (Q-CW01 open)
  • 완화 방안의 구체 수치 (threshold ≥ 2, Admin ≥ 3 등)

3.1 Risk-G07 — Approval Group 미지원

Fireblocks 의 거버넌스는 보통 두 plane 으로 분리된다:

  • Admin Quorum (?) — workspace-wide 결정 (threshold 변경, user / role 변경 등)
  • Approval Group (?) — 특정 use case 별 위임 그룹 (예: Treasury op 용 별도 quorum)

하지만 Cold Wallet workspace 에서는 Approval Group 자체가 미지원:

"Cold Wallet workspace 는 approval group 미지원 → Admin Quorum 단독 → Cold Wallet 의 governance flexibility 축소. Workspace config 변경마다 quorum 전체 동의 필요. Hot 보다 운영 부담 증가."

(출처: Fireblocks 공식 문서 — Approval Groups)

운영 의미 — 모든 결정이 Admin Quorum 전체

Hot workspace 에서는 "Treasury withdrawal" 같은 use case 를 별도 Approval Group 에 위임 가능 (예: Treasury Admin 2명 quorum). Cold 에서는 모든 workspace-level 결정에 Admin Quorum 전체 가 동의해야 한다 → Admin 한 명의 부재가 governance halt 로 직결.

3.3 Cold workspace 특수 규칙 — 4 가지 액션 분류

Fireblocks 공식 Admin Quorum 문서가 Cold Wallet workspace 에 대해 다음 4 가지 액션 분류를 명시:

액션 분류Cold Wallet 처리
Owner + Admin approval 액션
(add users, provisioning signing devices 등)		 Fireblocks Support 경유 필수
Admin 삭제 시 pending request outstanding cancel + new submit (기존 pending 모두 취소 후 재제출)
Other workspace config Non-Signing Admin (NS-Admin) approve 가능
user delete · reset 2FA Owner-only Console direct

(출처: Fireblocks 공식 문서 — Admin Quorum: Cold Wallet workspace 특수 규칙)

→ 일부 critical operation 은 Admin Quorum 도 거치지 않고 Owner 가 Console 에서 직접 수행. 이는 Hot workspace 의 일반 패턴과 다름.

운영 함정 — "outstanding cancel + new submit" 의 의미

Cold workspace 에서 Admin 을 삭제할 때, 그 Admin 이 관련된 모든 pending request 가 자동 취소되며, 필요 시 새로운 request 로 처음부터 다시 제출해야 한다. 즉 Admin 삭제 시점에 진행 중이던 트랜잭션 · 정책 변경 · governance change 는 전부 재시작. 은행은 Admin 삭제 전 모든 pending request 의 사전 완료 권장.

(출처: Fireblocks 공식 문서 — Approval Groups: 4 UI categories + Cold Wallet 미지원)

→ Hot workspace 에서 4 카테고리 별 별도 quorum 위임이 가능하지만, Cold workspace 에서는 4 카테고리 모두에 Admin Quorum 전체 동의 필요. 운영 부담의 정량적 차이가 여기서 결정됨.

3.4 Support-mediated user operations

Cold Wallet workspace 의 사용자 / API key 추가는 Fireblocks Support 경유 필수. (출처: Fireblocks 공식 문서 — Cold Wallet cluster: "Adding users to a Cold Wallet workspace" / "Adding API keys to a Cold Wallet workspace")

구체적 절차는 공식 문서 본문 미적재 상태이지만, Hot workspace 의 패턴과 유사하다면:

  1. 은행 IT 가 Fireblocks Support ticket 생성
  2. Support 가 신원 확인 (video call 등 — Hot workspace 의 Owner-touching 절차 패턴)
  3. Support 측에서 user provision request 시작
  4. Admin Quorum mobile approval (7-day window 가정 — 추정)
  5. User 가 mobile device 등록 (Cold variant device 사양 미명세)
은행 운영 영향

은행은 보통 Hot workspace 의 user provision 을 IT / Admin 셀프서비스로 운영 가능하지만, Cold workspace 는 모든 user 추가 / 삭제가 Fireblocks Support 응답 시간에 직접 종속된다. SLA / 대응 시간은 Fireblocks 계약 시 별도 확인 필요.

3.5 Risk-G06 의 Cold 적용 — 초기 bootstrap

Hot workspace 의 Risk-G06: "워크스페이스 첫 생성 시 threshold = All Admins, 이때 Owner 단독 active". (출처: Fireblocks 공식 문서)

→ Cold workspace 생성 시에도 동일 invariant 적용으로 가정 (추정). 즉 Cold workspace bootstrap = Owner 단독 → 첫 Admin 추가 시까지의 짧은 윈도우에 Owner 가 모든 변경의 sole approver.

3.5b Mobile Approval 의 device 사양 — Cold 은 별도 앱

Cold workspace 의 Admin Quorum approval 은 mobile app 에서 수행 (Hot 와 동일 가정). 단 다음이 중요:

  • "Cold Wallet 은 별도 앱" — 일반 Fireblocks mobile app 과 별개의 app (출처: Fireblocks 공식 문서 — Mobile Device Minimum Requirements)
  • 일반 Fireblocks mobile app 의 OS 최소 사양 (Hot 기준):
    • iOS 16.6+ (non-jailbroken) + App Store + biometric capability
    • Android 8.1+ (64-bit) + Google Play Store + biometric capability
    (출처: Fireblocks 공식 문서 — Authentication · Mobile App)
  • Cold Wallet 별도 앱의 동일 사양 적용 여부 / 별도 device 요구 여부 — 공식 미명세 (Q-CW09 — 신규 Open Q)
  • iOS 11.0–14.0: 일반 mobile app 은 동작하나 업데이트 불가 — Cold 별도 앱의 동일 정책 여부 미명세
은행 운영 결정 — Cold workspace 의 mobile device 정책
  1. Hot 와 Cold 앱을 같은 device 에 설치 vs 별도 device — Cold 의 "별도 앱" 의미는 동일 OS 안에서 2 개 app 으로 분리. 별도 device 운영 시 보안 격리 강화 가능.
  2. Cold approver 의 device 분실 / 재발급 절차 — Cold 의 mobile re-enrollment 정책 미명세. Fireblocks Support 협의 필요.
  3. Cold 별도 앱의 OS update 정책 — 일반 mobile app 의 grace period 와 동일한지 미명세.

3.6 Audit Log 의 Cold Wallet 이벤트

Audit Log 의 카테고리 catalog 에 명시된 Cold Wallet 전용 이벤트:

"Wallets (Vault Account + Workspace Key Backup + Gas Station + Cold Wallet 'Less than 10% remaining signatures')"

(출처: Fireblocks 공식 문서 — Audit Log 20+ 이벤트 카테고리)

→ Cold Wallet 의 signature quota 모니터링 이 정식 audit log 카테고리. 이는 Cold device 가 제한된 signature 사용 횟수 를 가질 가능성을 시사한다 (정확한 limit 은 공식 문서 미명세).

은행 운영 알림 권장

"Less than 10% remaining signatures" 이벤트는 cold device 의 sign capacity 가 임계점에 도달함을 의미. 은행은 이 이벤트를 최우선 alert 로 등록 (SIEM, Slack 등). 즉시 device 재provisioning 또는 추가 device 배치 필요.

3.8 은행 운영을 위한 거버넌스 권장

  1. Admin Quorum threshold ≥ 2 — Owner SPOF (Risk-S08) 완화
  2. API Admin 보유 시 threshold ≥ 3 — Risk-G01 (API Admin = quorum −1) 완화
  3. Cold workspace 의 Admin 인원 = 최소 — Default visibility 함정 + Support 경유 부담 최소화 균형
  4. Owner 의 mobile device + recovery passphrase 별도 안전 보관 — Cold 의 Owner Console-direct 의존성
  5. 이사회 결의 절차 사전 정의 — Owner 부재 시 transfer 의 KR 은행 거버넌스 통합
  6. Signature quota 모니터링 — "Less than 10%" 이벤트의 자동 alert
  7. Fireblocks Support SLA 계약 명시 — Cold workspace user 추가 응답 시간이 운영 critical path
