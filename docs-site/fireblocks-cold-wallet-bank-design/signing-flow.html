5. Cold Wallet Signing — 사실 + 추정

Cold Wallet 의 transaction signing 절차. 공식 본문 미적재 비중이 가장 큰 영역이며, 은행은 도입 전 Fireblocks 와 직접 협의 권장.

본 페이지의 출처

공식 문서에 정의된 사실

  • Hot workspace 의 MPC-CMP 3-endpoint signing (1 mobile + 2 Fireblocks SGX) — Fireblocks MPC-CMP 공식 문서
  • Audit Log 의 "Less than 10% remaining signatures" 이벤트 카테고리 — Fireblocks Audit Log catalog
  • Cold Wallet cluster 의 문서명들 (Signing transactions / Provisioning / Device Requirements 등) — Fireblocks Help Center
  • "Hot, Warm, and Cold signing workflows" + air-gap transport (USB · SFTP · data diodes) — Fireblocks 공식 블로그 (2025-09-23)
  • Fireblocks KeyLink ↔ Thales Luna HSM 통합 — Fireblocks 공식 블로그 (2025-09-23)

저자가 합리적으로 추정한 운영 권장 — 참고용

  • Cold signing 의 정확한 절차 (Cluster catalog 의 본문 미적재로 상세 미확정)
  • 3 가지 가설 (H1 / H2 / H3) 의 share 분포
  • "Less than 10%" 이벤트의 의미 (Cold device 별 sign quota 유한 가능성)
  • 은행 운영 권장 (Signer device redundancy, 사전 alert, 영상 기록 등)
2025-09-23 vendor 공식 발언 — Hot / Warm / Cold 3-mode

Fireblocks 공식 블로그 "Enterprise Digital Asset Security with Fireblocks and Thales" (2025-09-23, by Adam Levine SVP) 가 "Hot, Warm, and Cold signing workflows" 의 3-mode signing 을 vendor 공식 framing 으로 명시. 또한 Cold workflow 의 air-gap transport 가 USB · SFTP · data diodes 임을 발언. 이로써 본 페이지의 "별도 hardware" 추정이 보강된다 — 단 "Warm" 의 정확한 기술 정의는 여전히 미명세.

관련 통합: Fireblocks KeyLink ("secure middleware layer") 가 Thales Luna HSM (FIPS 140-3 Level 3 + Common Criteria 인증, PQC readiness) 와 결합.

5.1 공식 문서 사실 (확정)

  • Cold Wallet cluster 에 Signing transactions with your Cold Wallet device 가 별도 문서로 존재. "3-share signing 의 Cold variant" 로 분류됨.
  • Cold Wallet cluster 에 Cold Wallet Mobile Key Share Backup and Recovery 가 별도 문서. Hot 의 "1 mobile + 2 Fireblocks SGX cloud" 모델과의 비교점.
  • Owner cold device 와 Signer cold device 의 provisioning 절차가 별도 문서로 분리 (Provisioning an Owner's Cold Wallet Device + Provisioning a Signer's Cold Wallet Device).
  • Cold Wallet Device Requirements 가 별도 문서 — device 사양이 별도 명세 (본문 미적재).
  • Audit Log 의 "Cold Wallet 'Less than 10% remaining signatures'" 이벤트.

(출처: Fireblocks 공식 문서 — Cold Wallet cluster · Audit Log)

5.2 Hot wallet signing 의 기본 모델 (비교 baseline)

Hot workspace 의 MPC-CMP signing 은 공식 본문이 적재됨:

  • 3-endpoint signing: Customer mobile (또는 SGX) + 2 Fireblocks Azure SGX
  • Mobile + 2 cloud + cloud-based mediator
  • MPC share 의 한 share 는 mobile secure enclave, 두 share 는 Fireblocks Azure SGX cloud
  • 3 algorithm 지원: ECDSA SECP256K1 / EdDSA Ed25519 / ECDSA SECP256R1

(출처: Fireblocks 공식 문서 — MPC-CMP · Security Aspects of Signing with the Fireblocks Mobile App)

5.3 Cold Wallet signing 의 추정 흐름

Cold 의 정확한 모델은 공식 본문 미적재로 인해 추정만 가능. 3 가지 큰 가설:

가설Share 분포Trade-off
H1 — Hot 와 동일 (mobile + 2 cloud) 1 mobile + 2 Fireblocks SGX. 단 "cold" 의미는 Fireblocks 측의 air-gap 운영 (cold facility) 또는 별도 console plane. "Cold Wallet 은 별도 앱" fact 와 충돌 — H1 가능성 낮음.
H2 — 별도 cold device + 2 cloud 1 air-gapped device (mobile 아닌 별도 hardware) + 2 Fireblocks SGX. Hot 의 mobile 대신 cold-specific device. Cold device 가 일반 모바일 아닌 hardware. Audit log 의 "remaining signatures" 가 이 device 의 sign capacity 일 가능성.
H3 — 별도 cold device + air-gap manual Customer side 가 multiple cold device, Fireblocks 의 cloud share 도 cold mode 운영. Manual ceremony. 가장 strict. Hosted MPC 와 유사한 sovereign key 모델. 일반 cold wallet customer 적용 가능성 낮음.
힌트 — "Less than 10% remaining signatures" 의 함의 (저자 추정)

이 audit log 이벤트가 정식 카테고리로 존재한다는 것은 device 별 sign quota 가 유한함을 시사. Hot workspace 의 mobile signing 에는 이런 quota 가 없으므로 (mobile re-enroll 만으로 복구 가능), Cold device 는 별도 hardware 일 가능성이 높다 (H2 가설에 가까움).

5.3b Cold Wallet 은 별도 mobile app — 공식 사실

중요 — Cold Wallet 은 일반 Fireblocks mobile app 과 별개의 앱

Fireblocks Mobile Device Minimum Requirements 직접 인용:

"Cold Wallet 은 별도 앱"

(출처: Fireblocks 공식 문서 — Mobile Device Minimum Requirements)

이 사실의 함의:

  • Cold workspace 의 signer / approver 는 일반 Fireblocks mobile app 이 아닌 Cold 전용 별도 app 을 사용
  • 별도 앱이 iOS / Android mobile 인지, 별도 device 의 firmware 인지는 공식 미명세 (Q-D-cold)
  • "Hot/Warm/Cold signing workflows" 의 vendor framing (2025-09-23) 과 정합 — Cold 가 별도 plane
  • 일반 mobile app 의 iOS 16.6+ / Android 8.1+ 사양이 Cold 별도 앱에 동일 적용되는지 미명세 (Q-CW09 신규)

→ 이 사실은 가설 H2 (별도 cold device + 2 cloud) 와 H3 (별도 cold device + air-gap manual) 둘 다와 정합. H1 (Hot 와 동일 mobile + 2 cloud) 는 "별도 앱" fact 와 충돌하므로 가능성 낮음.

5.4 Provisioning — Owner vs Signer cold device

Cluster catalog 는 Owner cold device 와 Signer cold device 의 provisioning 을 별도 문서로 분리:

  • Provisioning an Owner's Cold Wallet Device
  • Provisioning a Signer's Cold Wallet Device

→ Owner 와 Signer 의 cold device 가 서로 다른 procedure 또는 다른 device class 일 가능성 (추정). Hot 에서는 Owner / Signer 가 동일 mobile app 사용. Cold 는 distinction 강조됨.

5.8 은행 운영 권장 (signing plane)

  1. Cold device 의 redundancy — single Signer device 의 SPOF 회피. 최소 Signer device 2 개 (별도 인원 보유)
  2. Signature quota 사전 alert — "Less than 10%" 이전 (예: 30%, 20%) 에 사전 alert
  3. Provisioning ceremony 영상 기록 — Audit + 감독 대응 요건
  4. Signing 물리적 환경 — Cold signing 은 별도 secure room 운영 (네트워크 격리, 영상 감시)
  5. Signing 인원의 분리 — KR 특금법의 "이해상충 방지" 요건 충족 (Cold Signer ≠ Approver ≠ Reviewer)
  6. DR ceremony 사전 rehearsal — Cold device 분실 시 backup 으로부터 복구. Testnet 에서 rehearsal 권장 (production keys 로 reconstruction test = compromise 가정 — Hot 의 invariant 가 Cold 에도 동일 적용 추정)

5.9 미확정 사항 정리 (→ Risks & Open Questions 참조)

본 페이지의 모든 추정 항목은 7. Risks & Open Questions 에 정리. 주요 미확정:

  • Q-M05 — Cold Wallet MPC share 분포 (H1 / H2 / H3 중 어떤 모델인가)
  • Cold device = mobile 인가 별도 hardware 인가
  • Cold device 의 signature quota 가 정확히 몇 개인가
  • Signing ceremony 의 정확한 단계 (QR? USB? air-gap?)
  • Cold side SGX 가 Hot 의 SGX 와 별도 facility 인가
  • Cold ↔ Hot rebalancing 시 어느 쪽 signing 이 발동
