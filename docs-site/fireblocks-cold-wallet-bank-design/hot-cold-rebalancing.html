4. Hot ↔ Cold Rebalancing — P2P 자산 이동

Hot workspace 의 working balance 와 Cold workspace 의 bulk reserve 간 자산 이동. Fireblocks 는 두 workspace 간 P2P 연결을 통해 manual rebalancing 을 지원한다.

Hot ↔ Cold workspace 간 양방향 rebalancing. 노랑 = Hot / 파랑 = Cold. "P2P" 의 정확한 transport (internal vs on-chain) 는 공식 본문 미적재.

"P2P" 라는 표현은 두 가지 해석 가능 (공식 본문 검증 필요):

  • 해석 A — Hot 과 Cold 두 workspace 가 동일 Customer Domain 안에서 internal off-chain transfer 가능 (자산이 on-chain 으로 안 나가고 Fireblocks 내부 ledger 만 이동)
  • 해석 B — On-chain tx 가 발생하나 Fireblocks Console UI 가 "P2P" abstraction 으로 추상화 (양측 workspace 의 deposit address 가 사전 whitelisted)

은행 입장에서는 해석 B 로 가정하는 것이 안전. 즉 rebalancing 은 on-chain tx 로 fee + confirmation time + audit trail 발생.

4.4 Rebalancing 거버넌스 — 두 측의 거버넌스가 모두 발동

양 workspace 의 governance 가 각자 발동한다 (저자 추정):

단계발동 거버넌스특징
① Cold 측 출금 (Cold → Hot) Cold workspace 의 Admin Quorum Approval Group 미지원 → 전체 Admin Quorum 동의 필요
② Hot 측 수취 (passive — incoming deposit, governance 미발동) Webhook event 만 발생
③ Hot → Cold (대량 자산 인계) Hot workspace 의 거버넌스 (Approval Group 또는 Admin Quorum) Policy rule 로 destination = Cold workspace 의 사전 whitelisted address 검증
④ Cold 측 수취 (passive) Cold side 의 deposit 으로 처리
은행 권장 — Whitelist 사전 등록

양 workspace 의 deposit address 를 사전에 whitelist 로 상호 등록. Policy rule (TAP) 에서 "to = whitelisted_cold_addresses" 인 출금만 일반 rebalancing flow 로 처리, 그 외는 더 strict. 이렇게 하면 ② / ④ 의 passive deposit 만으로 두 workspace 간 정기적 rebalancing 이 운영 가능.

4.5 Round-Robin Withdrawal vault 의 적용

Fireblocks 의 round-robin withdrawal vault 권장은 chain-specific bottleneck 회피 목적 (EVM nonce / Bitcoin 25-chain). (출처: Fireblocks 공식 문서 — Account and Wallet Structure)

Chain단일 withdrawal vault 의 위험Hot → Cold rebalancing 적용
EVM-based (ETH, USDC 등)nonce 순차 — 한 tx 가 stuck → 전체 queue 정체 Hot 측에 multiple withdrawal vault, round-robin 으로 Cold 로 송금
Bitcoinunconfirmed input → 25 subsequent tx 까지만 chain 가능 Hot 측 multiple withdrawal vault, 25-chain limit 우회

→ 은행이 일일 batch 로 Hot → Cold rebalancing 을 운영하면, 1회 batch 의 양이 chain capacity 와 매칭되어야.

4.6 Rebalancing 정책 권장

  1. 주기 — 일 1회 또는 임계점 기반
    • Hot 의 잔액 > X% → Cold 로 추출
    • Hot 의 잔액 < Y% → Cold 에서 보충
  2. 금액 한도
    • 1회 rebalancing 최대 금액
    • 일일 누적 금액
    • Cold → Hot 이 Hot → Cold 보다 strict (출금 위험 더 큼)
  3. 승인 quorum
    • Hot 측: Treasury Approval Group 위임 가능
    • Cold 측: Admin Quorum 전체 강제 (Risk-G07)
  4. Whitelist 양방향 사전 등록 — Policy rule (TAP) destination 검증
  5. Audit Log 양측 보존 — Hot 의 출금 + Cold 의 입금 reconciliation
  6. Confirmation 임계 — Cold 측 수취 확인 후 internal ledger 반영 (~12 conf for BTC, ~30 conf for ETH 권장)

4.7 Rebalancing 의 실패 시나리오

실패 종류완화 방법
Cold side Admin Quorum 동의 지연 (Admin 부재) Admin 인원 ≥ 3 유지 / 비상 근무 schedule
Hot side stuck tx (EVM nonce) Round-robin withdrawal vault + nonce gap reset 절차
Network outage (chain congestion) Rebalancing 임계점에 buffer 추가 (예: Hot 의 잔액이 0 직전까지 가지 않도록)
Cold device signature quota 소진 "Less than 10% remaining signatures" 사전 alert → device 재 provisioning
Wrong address (whitelist 오류) Policy TAP 양측 모두 whitelist 강제, 변경에 Admin Quorum 동의
