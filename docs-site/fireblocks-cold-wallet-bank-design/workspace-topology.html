2. Workspace 토폴로지 — 은행 Cold Wallet 배치

Fireblocks 의 Vault Structure Best Practices 의 다중 workspace 패턴을 은행 환경에 매핑. 은행은 보통 4–5 workspace 로 시작한다.

공식 문서에 정의된 사실

  • 5-level 계층 (Customer Domain → Workspace → Vault Account → Asset Wallet → Deposit Address) — Fireblocks 공식 문서
  • Default visibility 정책 — Fireblocks 공식 문서

  • Cold workspace 에서 Sweep-to-omnibus vs Segregated 의 적용성
  • Cold workspace 의 round-robin 의미

2.1 권장 workspace 구성 — Bank Baseline (저자 추정)

Fireblocks Vault Structure Best Practices 의 3-workspace 분리 패턴 (>$10M tokenization) + Cold Wallet 분리를 합친 형태.

#WorkspaceTypeNetwork역할Approval Group
1AdministrativeHotMainnet smart contract deploy / upgrade, role allocation지원
2OperationalHotMainnet 일일 입출금, sweeping, gas station 운영지원
3Custodial (Hot)HotMainnet 고객 자산 working balance 보관지원
4Custodial (Cold)ColdMainnet 고객 자산 bulk reserve (cold storage)미지원 — Admin Quorum 단독

(출처: Fireblocks 공식 문서 — Vault Structure Best Practices: 3-workspace 분리 + Cold 별도)

왜 Custodial 을 Hot / Cold 둘로 쪼개나

Fireblocks Vault Structure BP 의 권장은 "Cold Wallet 분리" (workspace 단위). 은행은 동일 고객 자산을 "hot balance" (실시간 처리용) 와 "cold reserve" (대량 보관용) 두 plane 으로 운영하며, plane 간 자산 이동은 P2P rebalancing 으로 수행한다. (출처: Fireblocks 공식 문서 — Vault Structure Best Practices)

2.2 5-Level 계층의 Cold workspace 내부 구조

Cold workspace 내부도 Hot 과 동일한 5-level 계층을 따른다는 가정 (5-level 구조 자체는 공식 문서 fact, workspace type 직교는 저자 추정). 

Customer Domain (bank)
└── Workspace [4: Custodial-Cold]      ← 본 페이지 대상
    ├── Vault Account "BTC-Reserve"
    │   └── Asset Wallet (BTC)
    │       └── Deposit Address × N (UTXO multi-address)
    ├── Vault Account "ETH-Reserve"
    │   └── Asset Wallet (ETH)
    │       └── Deposit Address × 1 (account-based single)
    └── Vault Account "USDC-Reserve"
        └── Asset Wallet (USDC, ERC-20)
            └── Deposit Address × 1

(출처: Fireblocks 공식 문서 — Account and Wallet Structure: 5-level 계층, Asset Type → Address 매핑)

2.3 Segregated vs Sweep-to-omnibus — Cold workspace 에서는 어떻게?

Fireblocks 의 2 vault 구조 패턴 (Segregated / Sweep-to-omnibus). (출처: Fireblocks 공식 문서 — Vault Structure Best Practices)

Hot workspaceCold workspace
Sweep-to-omnibus End user 입금 → Intermediate vault → Omnibus → Withdrawal pool. Gas Station 자동. 저자 추정 — Cold 에서는 Sweep 의 의미가 약함. Cold 으로의 sweep 은 운영 시간 단위의 batch rebalancing.
Segregated Per-client vault. Settlement on-chain atomic. 저자 추정 — Cold 의 segregated 는 사용 빈도 낮음 (대량 보관 목적과 충돌)
은행 권장 (Cold) — 대형 omnibus vault 1–N 개 (BTC / ETH / 안정자산 별 1 omnibus reserve). 사용자 단위 분리 안 함.

2.4 Default visibility 함정 — workspace 단위 격리

Fireblocks 의 default 모든 user 가 모든 vault 가시성 정책이 Cold workspace 에도 동일 적용됨. (출처: Fireblocks 공식 문서 — Vault Structure Best Practices: "By default, all users in the workspace have visibility to all of the Vault accounts in the workspace.")

→ Cold workspace 내부의 부분 가시성 제한은 별도 workspace 분리로만 가능. 은행 권장: Cold workspace 자체를 최소 사용자 집합 (Owner + 2–3 Admin) 으로 유지.

2.5 Customer Domain 단위 grouping

Cold workspace 와 Hot workspace 들은 같은 Customer Domain 에 속한다. Fireblocks 공식 문서: "Customer Domain (5-level hierarchy 의 top) 안에 다양한 type 의 workspace 가능". (출처: Fireblocks 공식 문서 — Set up your Fireblocks Vault with Key Link)

→ 은행의 모든 workspace (Hot×3 + Cold + Sandbox) 가 단일 Customer Domain 에 묶임. Workspace type 만 immutable.

2.6 Round-Robin Withdrawal vault 의 Cold workspace 적용

Fireblocks 의 round-robin 권장 (EVM nonce / Bitcoin 25-chain 제약) 은 Hot withdrawal pool 대상. Cold workspace 는 round-robin 이 의미 약함 — withdrawal 빈도가 낮고, 시간 단위 batch 로 운영되기 때문 (저자 추정). (출처: Fireblocks 공식 문서 — Account and Wallet Structure: round-robin pattern 의 원래 적용 대상)

2.7 변경 불가 — workspace type immutability

한 번 Cold workspace 로 생성하면 Hot workspace 로 변환 불가, 그 역도 불가. 공식 문서 직접 인용:

"You must open and configure a new workspace for a Hosted MPC setup, as modifying an existing SaaS MPC workspace is impossible."

(출처: Fireblocks 공식 문서 — Hosted MPC Workspace Configuration)

→ Cold ↔ SaaS MPC 변환도 architectural symmetry 로 같은 invariant 추정. 은행이 Cold workspace 도입 결정은 1-way door 로 간주.

은행 결정 사항 (5)
  1. Cold workspace 의 위치 — KR 망분리 IDC 안 / 외부 Fireblocks Cold facility / hybrid. Fireblocks Sales 와 협의 필요
  2. Customer Domain 통합 vs 분리 — 자회사 / 계열사가 별도 Customer Domain 인지
  3. Cold 의 user 수 — Admin Quorum 단독 운영이므로 최소 인원으로 (Default visibility 함정)
  4. Cold rebalancing 주기 — 일일 / 주간 / 임계점 기반
  5. Cold storage 비율 — KR 가상자산업감독규정 9조 의 80% (경제적 가치) 충족
