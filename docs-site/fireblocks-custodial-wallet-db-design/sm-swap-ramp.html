16. Swap · Ramp Lifecycle

자산 스왑 · 온램프 · 오프램프 의 운영 라이프사이클 — state machine · KR 컴플라이언스 · 외부 채널 통합
본 페이지의 범위 + 다른 페이지와의 관계

swap / onramp / offramp 의 운영 lifecycle 중심 — 사용자 요청 → 검증 → 외부 채널 정산 → 완료 흐름. 회계 / 데이터 / 컴플라이언스 와의 cross-link:

  • 회계 관점 — 21. 회계 · 원장 설계 21.6 시나리오 ④ ⑤ ⑥ (분개 + delta_ledger 처리)
  • Schema 관점 — 15. Transaction Request · Execution (header + 3 detail + execution)
  • 입금/출금 패턴 — 14. Deposit · Withdrawal Flow (외부 입출금 — 비교 / 차이점)
  • 본 페이지 (16) — 운영 흐름 (state machine · 검증 · 외부 채널 · KR 컴플라이언스 · 실패 처리)

16.1 개요 — 3 type 의 공통 패턴

Swap · Onramp · Offramp 는 모두 다음 공통 특성을 가짐:

  • 사용자 요청 → 외부 채널 정산 → vault 변동 패턴 (외부 입금 · 외부 출금 의 단순 1-leg 와 다름)
  • 2-step + delta_ledger 필수 — Step 1 (off-chain 즉시 · UI 응답) + Step 2 (외부 settlement + vault 도착/출금)
  • customer_ledger pending 사용 — pending_in (스왑 in / 온램프 / 오프램프 의 KRW 입금 예정) 또는 pending_out (스왑 out / 오프램프 출금) 으로 lock
  • 외부 채널 의존 — JV (KRWK 발행자) · Circle (USDC 발행자) · 외부 거래소 (Coinbase 등) 중 선택
  • 시세 의존 (변동성 자산) — quoted_rate 시점 vs 정산 시점 차이로 spread 발생

2-leg + 3-step 패턴 — Step 1 (잔액 lock + 미정산 분개) → Step 2 (외부 채널 정산) → Step 3 (정산 분개 + confirmed 반영). 회계 정합 상세는 21. 회계 · 원장 설계 21.6 시나리오 ④.

16.2.2 Swap status 흐름

transaction_request.request_status (헤더) 와 transaction_execution.execution_status (leg 별) 의 2-layer status — 15.5 절 참조. swap 특이사항:

  • 2 leg COMPLETED 모두 도착 시 request_status = COMPLETED. 1 leg 만 COMPLETED 면 request 는 SUBMITTED_TO_VENDOR 유지
  • leg 1 (OUT) 실패 시 = leg 2 시도 안 함. request 는 REJECTED
  • leg 2 (IN) 실패 시 = leg 1 의 reversal 필요 (이미 burn 한 KRWK 의 보상 — JV 와 협의)

Mint 패턴 (1:1 peg) — 시세 변동 없음. 계정계 KRW 차감 + JV mint 가 비동기 outbox 로 병렬 진행. 회계 항등식 상세 21.6 시나리오 ⑤ Case A.

16.3.2 정상 흐름 (Case B — USDC purchase)

Case A 와의 차이만 강조 (sequence 자체는 유사 — 15.6 절 type 별 사용 패턴 참조):

  • channel 선택 — CIRCLE_MINT (1차 시장 · peg 안정) 또는 EXTERNAL_EXCHANGE (2차 시장 · spread 발생)
  • 시세 quote 필수 — quoted_rate (예: 1,300 KRW/USDC) at 요청 시점
  • 정산 시점 시세 차이 = spread 손익 (외환매매수익 / 손실 분개)
  • 실패 시 KRW 차감 rollback — 계정계로 환불 요청 (outbox 별도 처리)

16.4.2 정상 흐름 (Case B — USDC sell)

  • channel — CIRCLE_REDEEM (1차 시장) 또는 EXTERNAL_EXCHANGE (2차 시장 매도)
  • 시세 변동 — quoted_rate (요청 시) vs 매도 시점 시세 차이 = 외환매매수익/손실
  • 트래블룰 100만원 임계 — 외부 거래소 매도 시 거래소 자체가 VASP. 양도성 / originator-beneficiary 식별 필요 (14.3.1)
  • 매도 실패 시 KRWK / USDC vault 잔액 복구 — JV 측에 reverse 협의 필요

16.5 KR 컴플라이언스 통합

16.5.1 가상자산이용자보호법 (2024.07 시행)

  • 예치금 분리 보관 — 사용자의 KRW (오프램프 결과) 는 은행 계정계의 별도 계좌 / 신탁 (4 조)
  • 이용자 가상자산 80% 콜드월렛 — onramp 로 받은 stablecoin 의 80% 이상은 Cold vault (9 조 / 가상자산업감독규정)
  • 이상거래 모니터링 — swap / ramp 의 high-frequency · 이상 금액 패턴 → 컴플라이언스 review

16.5.2 특금법 (트래블룰)

  • 100만원 이상 stablecoin 이동 시 (offramp 의 외부 거래소 경유 경우) IVMS101 정보 교환 — Sumsub · Notabene · TRP
  • onramp / offramp 의 1차 시장 (Circle · JV) 경유는 트래블룰 적용 모호 — 법률 자문 필요

16.5.3 자본시장법 (swap 의 외환매매 분류 hypothesis)

★ Swap 의 법적 성격 — 외환매매 vs 가상자산 교환

KRWK ↔ USDC 같은 stablecoin-to-stablecoin swap 이 외환매매 로 분류되면 자본시장법 / 외국환거래법 적용. KR 회계 표준 (K-IFRS 9) 의 가상자산 분류 자체가 hypothesis 라 swap 의 외환매매 분류 가능성도 자문 필요. 회계법인 + 법무팀 + 금감원 사전 협의 필수.

16.5.4 STR (의심 거래 보고)

  • swap / ramp 의 의심 패턴 (rapid round-trip · structured amounts · 고위험 stablecoin 등) → 컴플라이언스 review
  • 판단 시 KOFIU 보고 — 처리 결과 compliance.suspicious_tx_review 기록

16.6 외부 채널 통합

16.6.1 JV (KRWK 발행자) 통합

  • API — JV 가 제공하는 mint / burn / 잔액 조회 endpoint (구체 spec 은 JV 협약 시 확정)
  • 인증 — mTLS 또는 API key + signature (협약 시 결정)
  • vault 송수신 — JV mint 시 Fireblocks vault address 로 transfer / JV burn 시 은행 vault → JV address 로 송금 후 burn
  • 정산 schedule — 실시간 또는 batch (KRWK 발행 정책 의존)

14p.6.2 Circle (USDC 발행자) 통합

  • Circle Mint API — 1차 시장 mint (USD 입금 후 USDC 발행). USDC 매도 시 redeem (USDC burn 후 USD 출금) Circle Mint
  • 인증 — API key + IP allowlist
  • KRW ↔ USD 환전 — Circle 은 USD 만 다룸. KRW ↔ USD 환전은 은행 자체 또는 외환계 처리 필요
  • limit / KYC — Circle 측의 institutional 검증 통과 필요

16.6.3 외부 거래소 통합 (Coinbase · Binance 등)

  • API — 거래소별 trading API (REST / WebSocket). order placement + execution monitoring
  • 인증 — API key + secret + IP allowlist
  • vault ↔ 거래소 sub-account — 은행이 거래소에 own institutional account 보유 + Fireblocks vault 와 매핑 (6.4 counterparty.exchange_account_map)
  • spread / slippage — order book depth 에 따라 거래 시점 시세 변동. limit order 또는 TWAP 권장
  • 정산 schedule — 거래 즉시 (T+0) 또는 거래소 정산 schedule (T+1 등)

16.6.4 환율 quote source

  • KRW/USD — 한국은행 매매기준율 · 외환계 / 외부 oracle (Chainlink 등)
  • USDC/USD — Circle 1:1 peg (peg 깨질 시 외부 oracle 시세)
  • KRWK/KRW — JV 발행자가 1:1 peg 보장 (협약 의존)
  • quote 유효 기간 — 요청 시점 lock vs 정산 시점 시세 — spread / slippage 정책 결정 필요

16.7 실패 / Rollback 패턴

16.7.1 Step 1 (요청 검증) 실패

  • KYC / 한도 / 잔액 / 시세 unavailable → transaction_request.status = REJECTED
  • 잔액 lock 안 잡힘 (Step 1 미진입)
  • 고객에게 즉시 실패 알림

16.7.2 Step 2 (외부 정산) 실패

  • JV / Circle / 거래소 API timeout · reject · 시세 변동 등
  • 잔액 lock 해제: confirmed += amount · pending_out -= amount (오프램프 · 스왑 out)
  • 또는 pending_in -= amount (온램프 · 스왑 in)
  • delta_ledger.status = cancelled
  • general_ledger_entry 에 reverse 분개 (Step 1 미정산 entries 의 역방향)
  • transaction_request.status = REJECTED + cancellation_reason 기록
  • 고객 알림 (push)

16.7.3 Step 3 (정산 분개 실패)

  • Step 2 의 외부 정산은 성공했지만 DB 분개 INSERT 실패 (드물지만 가능)
  • vault 는 이미 변동됨 — manual 정정 분개 + audit log 필요 (Admin Quorum 매개)
  • 회계 정정은 21.6 시나리오 ⑧ (정정 분개) 패턴 따름
