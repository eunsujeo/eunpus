11.2 MPC-CMP — Fireblocks 의 threshold 서명 (참고)

SaaS MPC / Hosted MPC 는 MPC-CMP (Canetti-Makriyannis-Peled 2020) protocol 사용. 3-party threshold ECDSA / EdDSA.

  • 3 party 중 2 party 가 협력해야 서명 1 개 완성 (2-of-3)
  • 한 party 의 share 만으로는 서명 불가능 → 단일 침해로 자산 탈취 불가
  • 2023-08 보안 업데이트: GG18 → MPC-CMP 로 전환. "라운드" = 서명 1 회 완성에 필요한 party 간 통신 왕복 수. 8 → 4 로 줄면서 latency / 통신 비용 감소

출처: MPC-CMP Security Update 2023-08

은행 입장에서 — MPC 의 함의

은행은 MPC 내부 동작을 자세히 알 필요는 없다. 알아야 할 것은:

  • 키 share 가 1 곳에 모이지 않으므로, Fireblocks Cloud / 은행 mobile / 은행 cosigner 중 1 곳만 침해되어도 자산 탈취 불가
  • SaaS MPC 는 Fireblocks Cloud + 은행 mobile + Cloud Co-signer 의 3-party. 즉 은행 측 device 가 1 개 필요
  • Hosted MPC 는 은행 측 Co-signer 1 대 추가 — Cloud Co-signer 대신
  • Key Link 는 MPC 가 아닌 단일 HSM 모델 (다른 보안 모델)

sudo apt update
sudo apt upgrade
sudo apt install cpuid
cpuid -1 | grep -i sgx

검증 결과 — SGX = true (Software Guard Extensions supported) · SGX_LC = true (SGX launch config supported) 모두 필수. 설치 스크립트는 cpuid instruction 으로 자체 검증 (leaf 7 / EBX bit 2 = SGX · ECX bit 30 = SGX_LC). 메모: Azure Standard_DC*_v2 instance 는 SGX2 미지원이지만 cosigner 실행에는 무관.

Intel 측 사전 등록 (공식 docs Step 1.4 + 1.5)

SGX driver 설치 자체는 스크립트가 자동 처리하지만, 공식 docs 는 Intel 측 사전 등록 절차도 명시:

  1. Intel PCS 구독 (ECDSA Attestation) — API key 발급
  2. Intel PCCS (Provisioning Certification Caching Service) 설정 — Intel reference caching service
  3. PCKIDRetrievalTool 실행 — pckid_retrieval.csv 생성 → JSON 변환 → Intel 등록
  4. Reimage SGX platform + Intel SGX runtime stack 설치
  5. Fireblocks 측 등록 검증 — curl https://mobile-api.fireblocks.io/sgx/certification/v3/pckcert?... 로 certificate 반환 확인

이 등록 절차 없이는 remote attestation 실패. Intel 자료: Intel SGX SW Installation Guide · SGX DCAP Caching Service Design Guide.

은행 측 사전 결정
  • Callback Handler endpoint 구축 — URL + 인증 방식 (스크립트 5 옵션 interactive — Public key / Certificate / Root-CA / Hybrid cert / Hybrid CA. 공식 문서).

    ★ Callback Handler 미설정 시 자동 승인 (Fireblocks 공식 docs): "If a Callback Handler is not configured for an API user, the Co-signer will automatically sign or approve all requests it receives for that API user." → 미설정 = 외부 validation 없이 모든 거래 자동 서명. 은행 환경에서는 Callback Handler 설정 필수.

  • Callback retry 사용 여부 결정 — 스크립트 interactive. retry 사용 = WebSocket 자동 비활성화 (long polling). 스크립트 prompt: "응답 30초 이상 또는 비동기 통신 목표 시 retry 사용 · 그 외에는 비활성화 권장 (성능 영향)"
  • Recovery Public Key — 스크립트 자동 생성 (fb-recovery-pub.pem). 대응 private key 의 보관 plan 은 스크립트 범위 밖 — 별도 절차 필요
  • Physical Device ID (UUID) — 스크립트 자동 생성 (uuidgen) → .local_config 저장
  • Workspace Owner mobile app — 설치 완료 후 MPC key share 요청 승인 단계에 필요 (Owner 가 mobile app 으로 승인)

On-prem Cosigner 설치 — 설치 과정

Fireblocks 공식 docs 의 3 단계 high-level:

  1. Step 1: on-prem 환경 + SGX 서버 setup / configure (위 "사전 준비" 절)
  2. Step 2: Console 에서 API user 생성 → cosigner 추가 → Pairing Token + 설치 스크립트 URL 발급
  3. Step 3: 설치 스크립트 다운로드 + 실행 + workspace owner 가 mobile app 으로 MPC key share 승인
Step 3.1: 설치 스크립트 다운로드

Console 에서 받은 URL 로 SGX 머신에 직접 다운로드: 

curl -o cosigner "URL"
chmod +x cosigner
Step 3.2: 설치 실행
sudo ./cosigner setup

스크립트 1 회 실행으로 자동 진행. 각 단계는 idempotent (재실행 안전 — 이미 설치된 항목은 skip):

Step 3.3: Workspace owner 의 MPC key share 승인

Cosigner 와 페어링된 API user 가 Admin 또는 User role 인 경우, workspace owner 가 mobile app 에서 새 MPC key share 요청 승인 알림 받음. owner 가 승인하면 Console 의 Co-signers tab (Developer Center) 에 cosigner 가 online + API user paired 상태로 표시.

모든 setup 동작은 {날짜시간}_run.log 에 기록 (스크립트 상단의 exec redirect). 문제 발생 시 이 로그 + ./cosigner logs 출력으로 Fireblocks 지원에 전달.

로그 확인 (공식 docs)

Cosigner 가 생성하는 2 가지 log:

  • run.log — setup / configuration history 자동 기록
  • customer_cosigner.log — workspace 운영 데이터 (거래 승인 / 서명 history · 신규 연결 승인). 10 file × 4MB rotation · 시간 순 overwrite. 위치: /databases/cosigner/log/customer_cosigner.log{,.1,.2,...}

로그 포맷 RegEx: ${AppName}:${Line} ${LogLevel} ${dd/MM/yyyy} ${HH:mm:ss,fff} ${ClassName} ::${MethodName} - ${LogMessage}. 외부 log delivery 권장: ELK · Splunk · Datadog 등 (Docker JSON file driver 기본 사용 — 다른 driver 로 변경 가능).

실행 중 docker image / script version 조회: 

# Docker image version
docker inspect cosigner | jq -r '.[0].Config.Image' + " " + '.[0].Image'

# Script version
head cosigner -n 3 | grep -i ver
Update 절차 (공식 docs)

공식 절차 — 단순 upgrade 커맨드보다 안전:

  1. Console 에서 새 설치 스크립트 URL retrieve → curl -o cosigner "URL" + chmod +x cosigner
  2. ./cosigner stop + docker ps -a 로 cosigner container 없음 확인
  3. Enclave 백업: mv /databases/cosigner/enclave/enclave.signed.so /databases/cosigner/enclave/enclave.signed.so_old
  4. sudo rm -f .revision — revision 파일 제거
  5. ./cosigner start (최신 버전) 또는 ./cosigner start <image_version> (특정 버전)
  6. docker ps -a 로 cosigner container 실행 확인

업데이트 실패 시 재설치 절차 (공식): sudo rm -rf /databases + sudo rm -f .local_config .revision → ./cosigner setup. 그래도 실패하면 API Co-signer Troubleshooting.

신규 머신 Migration (공식 docs)

기존 머신 → 신규 SGX 머신 이전 시 backup data 활용 (downtime 최소화):

  1. 신규 SGX 머신 setup (위 사전 준비 절차 동일)
  2. 기존 머신에서 다음 2 파일 백업:
    • /databases/cosigner/db/secrets.db — secrets DB (SGX enclave key 로 암호화)
    • /databases/cosigner/enclave/ra_loader_enclave.signed.so — enclave loader
  3. 신규 머신의 같은 경로에 두 파일 복사
  4. ./cosigner start

★ 두 파일 백업 부재 시 — cosigner 와 연결된 API user 들을 unpair (re-enroll) + 신규 머신에 새 cosigner setup 필요. backup 절차 사전 수립 필수.

스크립트가 명시하는 추가 운영 동작
  • upgrade 메커니즘 — upgrade 커맨드는 실행 중 customer_cosigner 프로세스에 SIGUSR1 signal 발송 (kill -s SIGUSR1). 새 이미지 pull 은 별도 start 또는 docker-compose 의 pull 단계
  • Recovery key — setup 중 openssl genrsa 2048 로 keypair 생성. public key (fb-recovery-pub.pem) 는 config 에 등록. private key 의 보관 / 백업 절차는 스크립트 범위 밖
  • multi-cosigner — add-user 성공 시 multiDevice=1 이 .local_config 에 추가됨. 이 flag 가 있으면 callback-update 등에서 userId 지정 강제
  • 통신 모드 — proxy 설정 OR slow_callback_handler (retry 사용) = true 일 때 WebSocket 비활성화. 둘 다 false 일 때만 WebSocket 활성화
  • restart 정책 — 메인 컨테이너는 restart: always · init 컨테이너는 restart: "no"

11.4 Callback Handler (Hosted MPC 운영 검증)

Hosted MPC 의 API Co-signer 는 거래 서명 직전에 은행의 Callback Handler endpoint 를 호출하여 마지막 게이트로 추가 검증을 받음. 은행이 자체 정책 (KYC / 한도 / counterparty / 시간대 등) 을 Fireblocks TAP 위에 한 번 더 적용 가능.

  • 예: TAP 통과한 거래에 대해 (a) 송신자 KYC 완료 여부 재확인, (b) 24h 누적 한도 재계산, (c) 채널계 / 정산계 잔액 일치 확인 → 모두 OK 시에만 서명 진행
  • 은행이 Endpoint URL + RSA 2048 keypair 를 생성 → public key 를 Fireblocks 에 등록 (Fireblocks 가 발급하는 게 아님). private key 는 은행 secret manager (예: AWS Secrets Manager) 에 별도 보관 — 자세한 컬럼 정의는 8. Internal Users 8.5 절 의 callback_handler_meta 참조
  • secure communication (mTLS) 강제 — 통신 자체가 양방향 인증

출처: Create API Co-signer Callback Handler · Callback Handler Secure Communication

11.5 Workspace Keys Backup — Backup 매커니즘

Fireblocks 가 제공하는 자산 회복 매커니즘. mobile device 분실 / Co-signer 손상 등의 시나리오 대응.

매커니즘 (저자 정리)

  • Owner / Admin 이 "Create new backup" 시작 (Fireblocks Console)
  • Recovery passphrase (사용자 입력) 로 backup 암호화
  • Fireblocks 가 backup 의 encrypted form 을 보관
  • Mobile device 분실 시 새 device 에 recovery passphrase 입력 → 복원

11.6 Recovery — Fireblocks Recovery Utility

Fireblocks 의 Recovery Utility (공식 명칭 — Disaster Recovery Utility 로 통칭되기도 함) 는 자산 회복용 도구. ★ SPOC 경고 — 정기 사용 금지, 1 회 사용도 키 노출 risk 로 간주.

  • 반드시 offline air-gapped machine 에서만 실행. Fireblocks 공식: "Performing this procedure on an online machine will result in your private key being considered exposed and compromised"
  • 4 secrets 매개 — Recovery Kit ZIP + RSA private key + Mobile App Recovery Passphrase + RSA Private Key Passphrase
  • 사용 후 해당 machine 폐기 또는 disk wipe
  • extended private keys (xprv + fprv) 재구성 가능 — 즉 사용자가 키 자체를 손에 쥐는 상태
  • 은행 정책: Recovery Utility 사용 = Admin Quorum 전원 동의 + 외부 감사 ceremony
