10. Roles · Quorum · Policy

9 user role · Admin Quorum · Approval Group · TAP — Fireblocks 가 운영하는 거버넌스 plane

10.1 9 User Roles — Fireblocks 의 권한 모델

Fireblocks 는 user role 을 9 가지로 정의. 각 role 의 권한과 책임:

Role주요 권한은행 적용 예
Ownerworkspace 의 단일 최상위 권한자. 모든 거버넌스 작업 시작자은행 CTO · 임원 1 인
AdminAdmin Quorum 의 구성원. user / policy / quorum 변경 승인운영팀 팀장 · 보안팀 팀장
Non-Signing Admin거래 서명 권한 없음, 그 외 Admin 작업컴플라이언스팀
ApproverApproval Group 에서 거래 / 정책 승인운영팀 일반 직원
SignerPolicy rule 의 designated signer — Hosted MPC 의 API Co-signer (자동 서명 SGX 서버) 또는 Key Link 의 Co-signer / Agent (HSM 통신) 가 사용하는 API user role. 사람이 아닌 자동화 시스템이 보유플랫폼 의 API key
Non-Signing User거래 시작 가능, 서명 권한 없음거래 요청자 (예: ops 신청)
Editorworkspace 설정 편집 (정책 미반영 시도 가능, 단 실제 적용은 quorum)설정 관리자
Viewerread-only회계팀 · 감사 access
Auditorread-only + audit log 전용외부 감사인

출처: Fireblocks — Manage Users · Fireblocks Help Center — Roles & Permissions

은행 user role 적용 권장 (저자)
  • Owner = 1 인 — 은행 CTO 또는 임원. 24/7 사용 불가능한 경우 backup Owner 절차 미리 협의 (Transfer Workspace Owner)
  • Admin = 3-5 인 — Admin Quorum quorum 의 양수가 안정적 운영의 기본
  • Approver = 5-10 인 — Approval Group 활용 시 충분한 인원
  • Signer = API key 만 — 사람 user 가 Signer role 인 것은 권장하지 않음
  • Viewer / Auditor = 회계/감사용 — 외부 감사인은 Auditor role

10.2 Admin Quorum — workspace 의 최고 거버넌스

Admin Quorum 은 workspace 의 모든 Admin user 의 집합. 거버넌스 작업은 quorum (예: 3 of 5) 의 mobile app 승인 매개.

Admin Quorum quorum 매개 작업 (대표)

  • 새 user 추가 / role 변경 / user 제거
  • Policy rule 추가 / 수정 / 삭제 (TAP 변경)
  • Approval Group 구성 변경
  • Validation Key 등록 (Key Link 시)
  • Whitelisted address 등록 (선택적, group 위임 가능)
  • Workspace Owner 이전 (Transfer Workspace Owner)
  • 2FA reset (분실 시)
  • SSO 설정 변경

출처: Transfer Workspace Owner

admin.admin_quorum_meta — quorum 구성 mirror

columntypestorage설명
quorum_id (PK)uuid등록 후 변경 불가은행 내부 ID
workspace_codevarchar등록 후 변경 불가config 의 workspace key ("admin" / "ops" / "hot" / "cold")
quorum_thresholdvarchar수정 가능예: 3 of 5 형태 (Fireblocks 측 설정 mirror)
member_user_idsjsonb수정 가능Admin 사용자 vendor_user_id 목록
created_attimestamptz등록 후 변경 불가매핑 등록 시점
modified_attimestamptz수정 가능마지막 quorum 변경 시점 (Fireblocks audit log mirror)
modified_byvarchar수정 가능마지막 변경 시작자 (vendor_user_id)

quorum 구성 변경 이력 (threshold · member 추가/제거) 은 audit.audit_log_internal 의 admin_quorum_meta entry 로 추적 (5년 보존).

왜 created_by 가 없는가 — mirror semantic

본 표는 Fireblocks Console 의 Admin Quorum 구성의 state mirror. canonical source 는 vendor 측 — 변경 actor 는 modified_by (vendor_user_id) 에 기록되며, 이건 Fireblocks audit log 의 actor 와 동일. created_by 가 별도 컬럼으로 있으면 같은 정보의 중복 — 첫 설정자 정보가 필요하면 audit.audit_log_mirror 의 첫 governance event 를 조회.

10.3 Approval Group — Admin Quorum 의 위임

Approval Group 은 특정 작업의 quorum 권한을 Admin Quorum 보다 좁은 group 에 위임하는 매커니즘.

위임 가능 작업 (Fireblocks Console 의 "Security & compliance")

  • Add validation keys (Key Link workspace 의 Validation Key 등록)
  • Whitelist addresses (외부 송금 주소 화이트리스팅)
  • Add internal wallets
  • Smart Transfer 정책
  • Transaction policy 변경
  • 기타 12 종의 위임 가능 작업 (Fireblocks 의 12 assignable approval-group actions)

출처: Manage Users · Fireblocks Help Center — Approval Groups

★ Cold Wallet workspace 는 Approval Group 미지원

SaaS Cold Wallet workspace 는 Approval Group 위임 미지원 — 모든 거버넌스 결정이 Admin Quorum 전체 동의 필요.

위험: Admin 1 명만 부재해도 Cold 거버넌스 정지.

완화책:

  • AQ 인원 3-5 인 확보 — quorum threshold 의 여유분 (예: 5 인 중 3 인 동의면 OK)
  • 정기 drill (?) 시행 — 실제 운영 ceremony 를 정기적 (예: 분기 1 회) 으로 모의 실행하여 다음을 점검:
    • 모든 AQ 멤버의 mobile app 동작 / 인증서 유효성
    • device 분실 / 교체 시 복구 절차
    • 휴가 · 부재 · 퇴사 시 대응 (대체자 지정 / 임시 위임 / 멤버 교체)
    • 비상 시 quorum 충족 가능 여부 (예: 새벽 / 주말 incident)
    • 실제 Fireblocks Console 의 mobile push 도달 / 응답 시간

상세는 7. Cold Wallet 운영 7.2 절 참조.

10.4 Policy / TAP (Transaction Authorization Policy)

TAP 는 Fireblocks 의 거래 단위 정책 엔진. 모든 거래는 TAP 평가를 통과해야 서명 단계로 진입. policy rule 은 vault / 자산 / 금액 / 시작자 등 조건을 매칭해 action (허용 / 차단 / 추가 승인 등) 을 결정.

Policy rule 의 핵심 필드

필드설명
source출금 vault 조건 (특정 vault / vault category / any)
destination입금 대상 (whitelisted only / network connection / any)
asset자산군 (BTC / ETH / 모든 자산)
amount금액 한도 (단일 거래 / 누적 / 24h / 7d)
initiator거래 시작자 user / API key 조건
action매칭 시 실행할 결정 — 대표 값:
  • ALLOW — 자동 통과 (서명 단계로 진입)
  • BLOCK — 거절
  • 2FA — 시작자의 2FA 추가 확인 후 통과
  • Designated Signer — 지정된 Signer-role API user 가 서명
  • 그룹 승인 action — Approval Group 의 quorum mobile 승인 후 통과 (정확한 enum 이름은 Console 버전 / Help Center 문서 확인)
designated_signeraction 이 Designated Signer 일 때 어느 Signer-role API user
approval_groupaction 이 그룹 승인 일 때 어느 group 의 quorum

출처: Fireblocks 공식 — "Transaction Authorization Policy" (Help Center) · Define AML Policies · Define Travel Rule Policies. action enum 의 정확한 표기는 Fireblocks Console 버전에 따라 달라질 수 있어 본문은 의미 중심으로 정리.

admin.policy_rule_snapshot — 정책의 versioned snapshot (참고용)

정책 자체는 Fireblocks Console / API 가 source of truth. 은행 DB 는 audit / 변경 이력 mirror 만:

columntypestorage설명
policy_snapshot_id (PK)uuid등록 후 변경 불가은행 내부 ID
vendor_rule_idvarchar등록 후 변경 불가Fireblocks 정책 UUID
workspace_codevarchar등록 후 변경 불가config 의 workspace key ("admin" / "ops" / "hot" / "cold")
rule_jsonjsonb등록 후 변경 불가정책 전체 spec (변경 시점의 snapshot)
rule_hashvarchar등록 후 변경 불가SHA-256(rule_json) — 변조 검출용
active_fromtimestamptz등록 후 변경 불가활성 시작 시점
active_untiltimestamptz수정 가능 (NULL 가능)활성 종료 시점 (변경 시 이전 row 의 이 column 설정)
changed_byvarchar등록 후 변경 불가Fireblocks audit log 의 변경자 user
quorum_approved_byjsonb등록 후 변경 불가Admin Quorum 승인자 목록

변경 이벤트 자체는 append-only — 활성 정책이 바뀌면 기존 row 에 active_until 설정 + 새 row INSERT. 정책 변경 audit 는 audit.audit_log_mirror (Fireblocks 발생) + audit_log_internal (은행 측 승인 흐름) 두 곳에 기록.

왜 created_by 가 없는가 — mirror semantic

본 표는 Fireblocks Console 의 정책 snapshot mirror. canonical source 는 vendor 측 — 정책 변경자는 changed_by (Fireblocks audit log 의 actor) 에 기록되며, 별도의 created_by 컬럼은 같은 정보의 중복. 활성 정책의 historical 변천은 row 의 active_from / active_until 시계열로 추적.

10.5 거버넌스 흐름 — 거래 한 건의 평가

sequenceDiagram
  autonumber
  participant App as 🏢 은행 application
  participant FB as ☁️ Fireblocks API
  participant TAP as Policy Engine / TAP
  participant AG as Approval Group
(필요 시)
  participant Signer as Designated Signer
(API user / Agent)
  participant Bank as 🏢 은행 webhook

  App->>FB: Create Transaction
  FB->>TAP: Policy 평가
  alt 정책 통과 + 추가 승인 없음
    TAP->>Signer: 서명 요청
  else 정책 통과 + Approval Group 매개
    TAP->>AG: quorum 승인 요청 (Mobile push)
    AG-->>TAP: 승인
    TAP->>Signer: 서명 요청
  else 정책 BLOCK
    TAP-->>FB: BLOCKED
    FB-->>App: 실패 응답
  end
  Signer-->>FB: 서명 완료
  FB-->>App: tx 상태 변경
  FB-->>Bank: webhook event - TRANSACTION_STATUS_UPDATED

거래 한 건이 TAP 를 통과 → 필요 시 Approval Group quorum → Designated Signer 서명 → webhook 으로 은행에 전달. 모든 단계가 Fireblocks 내부에서 발생하며, 은행은 webhook 으로 결과만 관찰.

10.6 거래 시작자 / 승인자 분리 (Maker-Checker)

은행 운영 best practice — 거래 시작자 ≠ 승인자. Fireblocks 의 정책 + role 분리로 enforce:

  • Non-Signing User 가 거래 요청 시작
  • Approver 또는 Admin 의 Approval Group 이 mobile 로 승인
  • Signer-role API key 가 자동 서명 수행
  • 한 사람이 모든 단계를 단독으로 못 하도록 정책 + role 분리
