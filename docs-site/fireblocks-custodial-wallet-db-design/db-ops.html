23. DB 운영 · Anti-patterns

3 격리 영역 (core · audit · compliance) 의 engine 선택 · partition · 백업 · 권한 · 안티패턴
★ engine 결정 가이드 — data 특성 기반

본 페이지는 engine-agnostic 운영 권장. 각 격리 영역 의 data 특성 (3. DB 분할 3.6 절) 을 기준으로 engine 선택. 본 reference 는 후보를 제시하며 운영자가 자신의 환경 (자산 규모 · 기존 인프라 · 비용 · 인력 역량) 에 맞게 결정.

23.1 영역별 engine 후보

격리 영역핵심 특성engine 후보 (저자 권장 굵게)주의
core (7 domain) mutable + append-only 혼합. transaction 은 high-velocity, accounting 은 strict ACID + 이중부기 RDB (PostgreSQL · MySQL · Oracle). transaction 은 partition 지원 필수. accounting 은 transaction 격리 strict 필수 cross-domain join 빈번 → 단일 engine 권장. 일부 domain (예: transaction.balance_snapshots) 은 cache (Redis) hybrid 가능
audit ★ append-only + hash chain + 변조방지 + 5년 append-only specialized store: AWS QLDB · S3 Object Lock + KMS · Azure Immutable Blob · 또는 별도 RDB instance with strict INSERT-only enforcement core 와 storage 분리 필수. application 의 일반 권한으로 modify 불가해야 함
compliance mixed + 외부 보고 RDB · IVMS101 jsonb 활용 외부 감사 read-only 권한 명확화
engine 선택의 일반 권장
  • RDB 의 핵심 가치 — ACID + FK + relational join 이 필요한 영역 (core 의 customer · counterparty · accounting · reconciliation · ops · admin · 그리고 transaction 의 일부) 에 적합
  • 변조방지 store 의 핵심 가치 — audit 영역의 immutability 강제 (append-only + WORM). RDB 의 trigger / RLS 로도 부분 달성 가능하나 strong isolation 우선이면 dedicated store
  • time-series DB 후보 (TimescaleDB · InfluxDB · ClickHouse) — transaction.balance_snapshots · reconciliation.balance_check_history · accounting.fx_rate_history 등 시계열 영역의 partition / aggregation 효율 ↑
  • cache (Redis · Memcached) — 외부 SoT 의 mutable cache 영역 (예: balance_snapshots). 영구 store 와 hybrid
  • stream / event store (Kafka · Kinesis) — webhook_events 의 입수 단계에 추가 (idempotency 처리 후 영구 store 로 commit)
  • NoSQL (DynamoDB · MongoDB) — 단일 record 의 ACID 가 가능한 modern NoSQL 도 후보. 단 회계의 이중부기 transaction 보장은 검토 필요
★ engine-agnostic 표기의 mapping 예시

본 wiki 의 customer.customer_vault 는 logical domain.table. engine 별 매핑:

  • PostgreSQL: core_db database 의 customer schema 의 customer_vault table → 3-level core_db.customer.customer_vault
  • MySQL: customer database 의 customer_vault table → 2-level customer.customer_vault (MySQL 은 schema = database 동의어)
  • Oracle: customer schema (= user) 의 customer_vault table → customer.customer_vault
  • NoSQL (DynamoDB): customer_customer_vault table (도메인 prefix) 또는 namespace 활용
  • Object store (audit 영역): bucket = audit-log, prefix = audit_log_mirror/{year}/{month}/

23.2 partition 전략 — 5년 보존 대응

transaction.webhook_events · vendor_transaction_status_history · audit.audit_log_mirror

  • 월별 partition — RANGE on (vendor_occurred_at) or (received_at)
  • 현재 월 + 직전 12 개월 = hot tier (인덱스 활성)
  • 13 개월 ~ 5 년 = cold tier (compressed, archive)
  • 5 년 + 1 일 도래 시 → legal hold 검토 후 detach + archive 스토리지 이동

partition 자동화

  • RDB: PostgreSQL pg_partman extension · MySQL 은 별도 cron / shell script · Oracle native partition
  • Time-series DB: TimescaleDB 의 hypertable + chunk · ClickHouse 의 MergeTree partition
  • Object store: lifecycle policy (S3 lifecycle / Azure tier) 로 자동 transition
  • 매월 1일 자동 partition 생성 (다음 월 대비) + 매월 1일 자동 archive (5년 도래 partition)

23.3 백업 정책 (저자 권장)

아래 RPO / RTO 는 본 reference 의 권장 — 은행 BCP 정책 / 자산 규모 / vendor SLA 와 정합성 검토 후 확정. 일반 financial-grade backup 패턴.

격리 영역RPORTO방식 (engine 별 예시)
core1 분15 분RDB: continuous WAL/binlog + 일일 base backup + cross-region replication + 5년 archive (transaction · accounting · reconciliation domain) / cache (Redis): 영구 store 가 master · cache 재구축 가능
audit1 분15 분별도 storage (변조방지) + 5년 archive + hash chain 무결성 검증. RDB: WAL + cross-region. Object store: 자동 replication + WORM lock
compliance1 분15 분core 와 동일 패턴 + 5년 archive

23.4 인덱스 설계 권장

transaction.vendor_transaction

  • (vendor_tx_id) UNIQUE
  • (vendor_external_tx_id) — idempotency lookup
  • (workspace_code, vendor_created_at DESC) — workspace 별 시계열
  • (source_vault_id, vendor_created_at DESC)
  • (current_status, vendor_created_at DESC) WHERE current_status IN ('PENDING_AUTHORIZATION', 'PENDING_SIGNATURE') — pending 거래 queue
  • (tx_hash) WHERE tx_hash IS NOT NULL — on-chain hash 역조회

transaction.webhook_events

  • (event_id) UNIQUE
  • (received_at DESC) — 시계열
  • (event_type, received_at DESC)
  • (related_resource_id) WHERE related_resource_id IS NOT NULL — 거래 / vault 별 lookup

audit.audit_log_mirror

  • (sequence_num) UNIQUE
  • (vendor_event_id) UNIQUE
  • (vendor_occurred_at DESC) — 시계열
  • (actor_user_id, vendor_occurred_at DESC) — 사용자별 audit
  • (event_category, event_type)

23.5 권한 분리 — service role × 영역 / domain

service 별 write 영역을 명확히 분리. core 영역 안에서는 domain-level 권한 (RDB schema GRANT · NoSQL IAM · 또는 prefix-based) 으로 분리. audit / compliance 는 별도 storage 라 storage-level 권한.

Rolecore 의 write 권한 (domain 별)auditcompliance
tx_api_rw
(거래 API)		 customer · counterparty · transaction.transaction_execution RW · 나머지 domain R — R
webhook_writer
(Webhook worker)		 transaction · accounting RW (INSERT-only enforce) · 나머지 R audit_log_mirror INSERT-only —
ledger_recon_rw
(원장 / 대사 cron)		 accounting · reconciliation RW · 나머지 R — R
admin_rw
(운영자 / 관리 콘솔 백엔드)		 customer · counterparty · ops · admin RW · 나머지 R audit_log_internal INSERT-only —
compliance_rw R R RW
auditor_external
(외부 감사 / 금감원)		 transaction · accounting · reconciliation · ops R · customer · counterparty · admin 제외 R R
engine 별 권한 구현 매핑
  • PostgreSQL — domain = schema. GRANT INSERT ON ALL TABLES IN SCHEMA transaction TO webhook_writer
  • MySQL — domain = database (별도 database 로 분리 운영). GRANT INSERT ON transaction.* TO webhook_writer
  • Oracle — domain = schema (= user). schema GRANT
  • NoSQL (DynamoDB) — table prefix 별 IAM policy
  • Object store (audit 영역) — bucket / prefix 별 IAM policy + Object Lock
append-only enforcement (INSERT-only)

transaction.* (webhook 사본) 과 audit.* 는 append-only 가 핵심 — webhook_writer / admin_rw role 에 UPDATE / DELETE 권한을 주지 않음. PostgreSQL 의 row-level security 또는 trigger 로 INSERT 만 허용. worker 가 처리 status 등을 update 해야 한다면 별도 worker_writer role (제한적 update 권한 · 특정 column 만) 활용. webhook 처리 흐름 상세는 13. Webhook 처리 13.4 절 참조.

23.6 모니터링 metric

application metric

  • Fireblocks API call rate / latency (p50, p95, p99)
  • Fireblocks API error rate (4xx / 5xx)
  • API key 사용 빈도 / 시간대 패턴

webhook metric

상세는 13. Webhook 처리 13.10 절 의 metric / Prometheus + Grafana + Alertmanager 도구 권장 참조.

  • 분당 webhook 수신 수
  • signature failure rate (0 권장)
  • processing latency p99 < 500ms
  • worker queue depth
  • retry rate
  • dedup hit rate (중복 event 비율)

DB metric

  • partition 크기 / row count (월별)
  • archive 진행 상황
  • backup 완료 시점
  • WAL lag (replica)
  • connection pool 사용률

비즈니스 metric

  • 일일 / 주간 / 월간 거래량 (deposit / withdrawal)
  • Hot / Cold 자산 비율 (80% 컴플라이언스)
  • AML flag 건수 / STR 보고 건수
  • 트래블룰 처리 건수
  • reconciliation mismatch 건수 (0 권장)

23.7 Anti-patterns — 도입 시 흔한 실수 (저자 정리)

아래 10 가지는 본 reference 가 정리한 도입 시 흔한 실수 패턴. 보안 / 운영의 일반 모범사례 (industry common pitfalls) + 본 reference 의 도입 경험 기반.

AP-1: Webhook signature 검증 누락

실수: webhook endpoint 가 signature 검증 없이 payload 처리. 결과: 공격자가 임의 event 위조 → mirror DB / 회계 / 알림 시스템 오염. 대응: signature 검증 없는 webhook 처리 절대 금지. 13. Webhook 처리 의 검증 절차 적용.

AP-2: idempotency 미구현

실수: webhook 처리 시 dedup 없이 매번 INSERT. 결과: 같은 event 가 2 회 처리 → vendor_transaction_status_history 중복 row, 잔액 mirror 오류, 회계 통합 오류. 대응: webhook_dedup 의 UNIQUE 제약 + ON CONFLICT DO NOTHING. 상세는 13. Webhook 처리 13.5 절 참조.

AP-3: API secret 의 DB 평문 저장

실수: Fireblocks API secret 을 application DB 의 column 에 평문 저장. 결과: DB 침해 시 모든 자산 위협 (API 권한으로 거래 시작 가능). 대응: secret manager (Vault / Secrets Manager / Key Vault) 만. DB 에는 reference 만. 8. Internal Users 8.3 절 의 api_key_meta.secret_ref 패턴 참조.

AP-4: Recovery passphrase 의 digital 보관

실수: passphrase 를 password manager / 사내 Wiki / Slack DM 등에 저장. 결과: digital 저장 시점에 노출 risk 발생 — SPOC (Single Point of Compromise) = "한 번이라도 노출되면 시스템 전체가 위험해지는 critical 지점". 대응: 물리 보안 구역의 sealed envelope + multi-custodian split. 상세 매커니즘은 11. MPC · Key Link · Cosigner 11.5 절 / 11.6 절 참조.

AP-5: Mirror 가 canonical 이라고 가정

실수: 분쟁 시 core 영역 의 거래 기록만 보고 결정. 결과: Fireblocks Console 과 불일치 시 권리 행사 불가 / 손실 부담. 대응: Fireblocks Console = 1차 source. mirror 는 보조. 항상 양측 정합성 reconciliation. 22. 대사 · 결산 · 마감 22.8 절 의 외부 감사 대응 자료 참조.

AP-6: KR 컴플라이언스 자동화 가정

실수: Fireblocks 도입 = KR 법규 자동 충족 으로 가정. 결과: 5년 보존 / STR / 트래블룰 / 콜드월렛 80% 의무 위반 발견. 대응: 국내 블록체인 사업 법규 × Fireblocks 참조. 17 의무 명시적 매핑.

AP-7: Workspace type 변경 시도

실수: 도입 후 SaaS MPC → Hosted MPC 변경 시도 (또는 Key Link 로 변경). 결과: workspace type immutable — 변경 불가. 새 workspace 생성 + 자산 cross-workspace transfer 필요. 대응: 도입 전 충분한 검토. Phase 1 시범으로 적은 자산 검증 후 결정. 4. Workspace 4.3.7 절 의 workspace_type set-once 정책 참조.

AP-8: omnibus vault 의 subledger 무결성 검증 누락

실수: omnibus 패턴 시 customer_ledger 의 자체 변조 방지 매커니즘 없음. 결과: DBA 가 row 변경해도 detection 불가 → 외부 감사 시 정합성 증명 불가. 대응: subledger 에 hash chain 또는 정기 cross-DB reconciliation log. 21. 회계 · 원장 설계 21.4 절 customer_ledger + 18. Audit · AML · Travel Rule 18.3 절 의 hash chain 패턴 참조.

AP-9: webhook endpoint 가 일반 API 와 동일 server

실수: 일반 API endpoint 와 webhook endpoint 가 같은 server / 같은 path prefix. 결과: webhook 의 부하가 일반 service 영향. signature 검증 / rate limit 정책 혼동. 대응: webhook 전용 service 분리. 별도 path / port / WAF rule. 13. Webhook 처리 13.7 절 참조.

AP-10: BCP / Vendor outage 시나리오 미수립

실수: Fireblocks SaaS 가 항상 가용하다고 가정. 결과: 실제 장애 발생 시 사용자 응답 정책 부재 → 신뢰 손실. 대응: BCP 절차 사전 수립. SLA 정책 + 알림 시스템. 20. Risks Register FB-R02 (Fireblocks SaaS outage) 의 완화 방안 참조.
