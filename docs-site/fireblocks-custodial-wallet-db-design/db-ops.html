17. DB 운영 · Anti-patterns

customerdb / mirrordb / compliancedb 의 MySQL · PostgreSQL 운영 권장 + 안티패턴

17.1 DB 엔진 선택

DB권장 엔진근거
customerdbMySQL 8.0+ 또는 PostgreSQL 14+mutable, 일반 application DB pattern
mirrordbPostgreSQL 14+ 권장append-only + jsonb 광범위 사용 (webhook payload) + partition 효율
compliancedbPostgreSQL 14+ 권장jsonb (IVMS101 등) + 외부 감사 query 효율
왜 PostgreSQL 권장 (mirrordb / compliancedb)
  • jsonb 의 성능 — webhook payload 의 부분 query 효율 (예: raw_payload->'data'->'tx'->'status')
  • partition 의 native 지원 — declarative partitioning (월별 / 연도별)
  • row-level append-only enforcement — trigger / RLS 로 UPDATE/DELETE 차단 용이
  • extension — pg_partman (자동 partition), pgcrypto (hash chain) 등 활용

17.2 partition 전략 — 5년 보존 대응

mirrordb.webhook_events / tx_status_history / audit_log_mirror

  • 월별 partition — RANGE on (occurred_at_fb) or (received_at)
  • 현재 월 + 직전 12 개월 = hot tier (인덱스 활성)
  • 13 개월 ~ 5 년 = cold tier (compressed, archive)
  • 5 년 + 1 일 도래 시 → legal hold 검토 후 detach + archive 스토리지 이동

partition 자동화

  • PostgreSQL: pg_partman extension
  • MySQL: 별도 cron / shell script (MySQL native partition 한계 보완)
  • 매월 1일 자동 partition 생성 (다음 월 대비)
  • 매월 1일 자동 archive (5년 도래 partition)

17.3 백업 정책

DBRPORTO방식
customerdb1 분15 분continuous WAL + 일일 base backup + cross-region replication
mirrordb1 분15 분continuous WAL + 일일 base backup + 5년 archive
compliancedb1 분15 분customerdb 와 동일

17.4 인덱스 설계 권장

mirrordb.tx_mirror

  • (fb_tx_id) UNIQUE
  • (fb_external_tx_id) — idempotency lookup
  • (fb_workspace_id, created_at_fb DESC) — workspace 별 시계열
  • (source_vault_id, created_at_fb DESC)
  • (current_status, created_at_fb DESC) WHERE current_status IN ('PENDING_AUTHORIZATION', 'PENDING_SIGNATURE') — pending 거래 queue
  • (tx_hash) WHERE tx_hash IS NOT NULL — on-chain hash 역조회

mirrordb.webhook_events

  • (event_id) UNIQUE
  • (received_at DESC) — 시계열
  • (event_type, received_at DESC)
  • (related_resource_id) WHERE related_resource_id IS NOT NULL — 거래 / vault 별 lookup

mirrordb.audit_log_mirror

  • (sequence_num) UNIQUE
  • (fb_event_id) UNIQUE
  • (occurred_at_fb DESC) — 시계열
  • (actor_user_id, occurred_at_fb DESC) — 사용자별 audit
  • (event_category, event_type)

webhook_writer 의 INSERT-only

mirrordb 는 append-only 가 핵심 — webhook_writer account 에 UPDATE / DELETE 권한을 주지 않음. PostgreSQL 의 row-level security 또는 trigger 로 INSERT 만 허용. worker 가 처리 status 등을 update 해야 한다면 별도 worker_writer account (제한적 update 권한) 활용.

17.6 모니터링 metric

application metric

  • Fireblocks API call rate / latency (p50, p95, p99)
  • Fireblocks API error rate (4xx / 5xx)
  • API key 사용 빈도 / 시간대 패턴

webhook metric

  • 분당 webhook 수신 수
  • signature failure rate (0 권장)
  • processing latency p99 < 500ms
  • worker queue depth
  • retry rate
  • dedup hit rate (중복 event 비율)

DB metric

  • partition 크기 / row count (월별)
  • archive 진행 상황
  • backup 완료 시점
  • WAL lag (replica)
  • connection pool 사용률

비즈니스 metric

  • 일일 / 주간 / 월간 거래량 (deposit / withdrawal)
  • Hot / Cold 자산 비율 (80% 컴플라이언스)
  • AML flag 건수 / STR 보고 건수
  • 트래블룰 처리 건수
  • reconciliation mismatch 건수 (0 권장)

17.7 Anti-patterns — 도입 시 흔한 실수

AP-1: Webhook signature 검증 누락

실수: webhook endpoint 가 signature 검증 없이 payload 처리. 결과: 공격자가 임의 event 위조 → mirror DB / 회계 / 알림 시스템 오염. 대응: signature 검증 없는 webhook 처리 절대 금지. 10. Webhook 처리 의 검증 절차 적용.

AP-2: idempotency 미구현

실수: webhook 처리 시 dedup 없이 매번 INSERT. 결과: 같은 event 가 2 회 처리 → tx_status_history 중복 row, 잔액 mirror 오류, 회계 통합 오류. 대응: webhook_dedup 의 UNIQUE 제약 + ON CONFLICT DO NOTHING.

AP-3: API secret 의 DB 평문 저장

실수: Fireblocks API secret 을 application DB 의 column 에 평문 저장. 결과: DB 침해 시 모든 자산 위협 (API 권한으로 거래 시작 가능). 대응: secret manager (Vault / Secrets Manager / Key Vault) 만. DB 에는 reference 만.

AP-4: Recovery passphrase 의 digital 보관

실수: passphrase 를 password manager / 사내 Wiki / Slack DM 등에 저장. 결과: digital 저장 시점에 노출 risk 발생 (SPOC). 대응: 물리 vault 의 sealed envelope + multi-custodian split.

AP-5: Mirror 가 canonical 이라고 가정

실수: 분쟁 시 mirrordb 의 거래 기록만 보고 결정. 결과: Fireblocks Console 과 불일치 시 권리 행사 불가 / 손실 부담. 대응: Fireblocks Console = 1차 source. mirror 는 보조. 항상 양측 정합성 reconciliation.

AP-6: KR 컴플라이언스 자동화 가정

실수: Fireblocks 도입 = KR 법규 자동 충족 으로 가정. 결과: 5년 보존 / STR / 트래블룰 / 콜드월렛 80% 의무 위반 발견. 대응: 국내 블록체인 사업 법규 × Fireblocks 참조. 17 의무 명시적 매핑.

AP-7: Workspace type 변경 시도

실수: 도입 후 SaaS MPC → Hosted MPC 변경 시도 (또는 Key Link 로 변경). 결과: workspace type immutable — 변경 불가. 새 workspace 생성 + 자산 cross-workspace transfer 필요. 대응: 도입 전 충분한 검토. Phase 1 시범으로 적은 자산 검증 후 결정.

AP-8: omnibus vault 의 subledger 무결성 검증 누락

실수: omnibus 패턴 시 customer_balance_subledger 의 자체 변조 방지 매커니즘 없음. 결과: DBA 가 row 변경해도 detection 불가 → 외부 감사 시 정합성 증명 불가. 대응: subledger 에 hash chain 또는 정기 cross-DB reconciliation log.

AP-9: webhook endpoint 가 application server 와 동일

실수: 일반 API endpoint 와 webhook endpoint 가 같은 server / 같은 path prefix. 결과: webhook 의 부하가 일반 service 영향. signature 검증 / rate limit 정책 혼동. 대응: webhook 전용 service 분리. 별도 path / port / WAF rule.

AP-10: BCP / Vendor outage 시나리오 미수립

실수: Fireblocks SaaS 가 항상 가용하다고 가정. 결과: 실제 장애 발생 시 사용자 응답 정책 부재 → 신뢰 손실. 대응: BCP 절차 사전 수립. SLA 정책 + 알림 시스템.
