13. Webhook 처리

Fireblocks 이벤트 수신 + HMAC-SHA512 검증 + idempotency + retry

13.1 Webhook 이란 — 은행 책임의 핵심

Fireblocks 가 거래 / vault / address / approval 등의 상태 변경을 발생시킬 때, 은행이 Fireblocks Console 에 등록한 endpoint URL 로 HTTPS POST 요청을 보낸다. 이 webhook 수신 인프라는 은행 책임이며, 직접 구축의 chaindb / audit 영역 역할 일부를 대체.

아래 event 명은 일반 webhook 패턴 기반 정리. 정확한 event enum 은 Fireblocks Help Center "Configure Webhooks" 문서에서 운영 시 재확인 필요.

13.3 Webhook 보안 — 비대칭 서명 검증

Fireblocks 가 webhook payload 를 비대칭 서명 (RSA-SHA512 가정) 으로 서명하여 HTTP signature header 에 첨부. Fireblocks 의 private key 가 서명, 은행은 Fireblocks 가 제공한 public key 로 검증. 모든 incoming webhook 에 대해 signature 검증 필수.

서명 mechanism 표기 — 정확성 hypothesis (vendor 문서 재확인 필요)

본 reference 시리즈가 vendor 공식 webhook signature spec 의 원문 인용을 확보하지 못함. 두 가지 가능성 모두 열어둠 — 운영 시 Fireblocks Help Center "Configure Webhooks" 문서에서 정확한 algorithm 확정 필요:

  • 비대칭 서명 (RSA-SHA512 / ECDSA 등) — Fireblocks 가 자기 private key 로 서명, 은행이 vendor 의 public key 로 검증. "public key" 라는 용어가 자연스럽게 쓰이는 모델
  • HMAC-SHA512 (대칭 키 shared secret) — Fireblocks 와 은행이 동일한 secret 을 공유, 같은 key 로 서명/검증. 본 reference 시리즈의 다른 페이지 (1. 책임 분담 · 2. 인프라 운영 · 0. Overview) 는 이 가정으로 작성됨 — 시리즈 내 일관성 측면에서는 HMAC 가정이 우세

본 페이지 (13. Webhook) 의 본문은 일반 webhook 패턴 (vendor private key 서명) 을 따라 작성. 정확한 mechanism 이 HMAC 으로 확인되면 본문의 "public key" → "shared secret" 으로 정정 필요.

검증 절차

  1. HTTP request body 의 raw bytes 추출 (JSON parsing 전 — parsing 변환이 byte 수준 차이를 만들면 검증 실패)
  2. Fireblocks 가 제공한 webhook public key (RSA public key, PEM) 로 signature 검증
  3. signature 불일치 → 401 Unauthorized 즉시 응답, payload 무시 + webhook_failures 에 기록 (core 영역 본 저장은 진입 안 함)
  4. signature 일치 → idempotency 검사 (webhook_dedup UNIQUE 제약) → 새 event 면 큐잉 → worker 가 webhook_events + vendor_transaction 저장

출처: Configure Webhooks (signature mechanism / header 명 / algorithm 의 정확한 spec 은 vendor 문서 재확인)

★ signature 검증 없는 webhook 처리 금지

signature 검증 없는 webhook 처리는 위조 vector. 공격자가 임의 event 를 은행 endpoint 에 전송하여 mirror DB / 회계 / 알림 시스템을 오염시킬 수 있다. endpoint URL 이 공개되어 있다고 가정해야 함 (URL 자체는 secret 아님). signature 검증이 유일한 신뢰의 근거.

13.4 Webhook 처리 흐름

sequenceDiagram
  autonumber
  participant FB as ☁️ Fireblocks
  participant LB as 은행 LB / WAF
  participant WS as Webhook Service
  participant Q as 처리 큐 (Kafka / SQS)
  participant Worker as Worker
  participant DB as 은행

  FB->>LB: POST /webhook/fireblocks
body + signature header
  LB->>WS: forward
  WS->>WS: 비대칭 서명 검증 (RSA-SHA512 가정)
  alt signature 불일치
    WS-->>FB: 401 Unauthorized
  else signature 일치
    WS->>DB: webhook_dedup INSERT
ON CONFLICT (event_id) DO NOTHING
    alt 중복 event (이미 수신)
      WS-->>FB: 200 OK (dedup, no-op)
    else 새 event
      WS->>Q: enqueue raw payload
      WS-->>FB: 200 OK (수신 확인)
      Q->>Worker: dequeue
      Worker->>DB: webhook_events INSERT (append-only)
      Worker->>DB: vendor_transaction UPSERT
      Worker->>DB: vendor_transaction_status_history INSERT
    end
  end

Webhook 의 표준 처리 흐름. 비대칭 서명 검증 → dedup → 큐잉 → worker 가 core 영역 저장. 200 OK 는 빨리 응답하고, 실제 처리는 비동기. Fireblocks 의 retry timeout 회피. 검증 실패 webhook 은 webhook_events 에 진입하지 않고 webhook_failures 에만 기록.

13.5 Idempotency — 중복 event 처리

Fireblocks 의 webhook 은 적어도 한 번 (at-least-once) 보장. 즉 같은 event 가 2 회 이상 전달될 수 있음. 은행은 idempotency 로 중복 처리를 방지해야 함.

13.6 Retry / Backoff 정책

Fireblocks 의 webhook 은 실패 시 자동 retry. 은행이 5xx 응답하면 Fireblocks 가 exponential backoff 로 재시도.

  • 200 OK 빠른 응답이 우선 — 5xx 응답하면 Fireblocks 가 retry 큐 형성, 운영 부담 증가
  • signature 불일치 = 401 — Fireblocks 가 retry 하지 않음 (정상)
  • 처리 실패는 200 OK 후 자체 retry 큐 — Fireblocks 에 5xx 보내는 대신 자체 dead-letter queue 운영 권장

13.7 Webhook endpoint 보안 권장

  • 전용 endpoint 분리 — application 의 다른 API 와 별도 path (예: /webhook/fireblocks)
  • WAF rule — Fireblocks 측 source IP 만 허용 (저자 권장 — IP 목록 자체는 vendor 가 변경할 수 있어 Fireblocks Help Center 의 최신 IP 목록 정기 확인 필요)
  • rate limit — 정상 흐름의 10x 이상은 의심 (DDoS / 위조)
  • TLS 1.2+ — TLS 1.0 / 1.1 금지
  • signature 검증 실패 alerting — 단일 실패도 운영팀 즉시 알림 (공격 시도 가능성)

13.9 정기 Reconciliation — webhook 누락 detection

webhook 이 네트워크 장애로 누락될 가능성 대응:

  1. 일일 sync — Fireblocks GET /v1/transactions?after=<timestamp> 로 24h 이내 거래 조회
  2. transaction 의 vendor_transaction 와 대조 (vendor_tx_id 기준)
  3. mirror 에 없는 거래 발견 → reconciliation_finding 으로 기록 + 운영팀 alert
  4. 해당 거래의 webhook 을 Fireblocks Console 에서 manual replay 가능
★ webhook 의 손실은 운영자 책임

Fireblocks 의 at-least-once 보장은 retry 정책의 max attempt 안에서 유효. retry max 초과 시 event 영구 손실 가능. 은행은 정기 reconciliation 으로 누락 detection + Fireblocks Console 의 transaction list 가 1차 source 임을 전제로 운영.

13.10 Webhook 운영 metric (저자 권장)

권장 측정 도구: Prometheus (metric 수집) + Grafana (대시보드) + Alertmanager (임계 알람). webhook handler 가 metric 을 Prometheus exposition format 으로 노출, Grafana 가 6 metric 시각화.

  • throughput — 분당 webhook 수신 수
  • signature failure rate — 0 이 정상 (공격 시도 detection — 단일 실패도 즉시 alert)
  • processing latency — webhook 수신 → core 영역 저장 완료까지 (목표: p99 < 500ms)
  • retry rate — Fireblocks 가 retry 한 비율 (높으면 은행 endpoint 가 느림)
  • worker queue depth — Kafka / SQS lag (높으면 worker 부족)
  • reconciliation mismatch count — 일일 reconciliation 의 mismatch 건수 (0 권장. 20. DB 운영 페이지의 monitoring 영역 참조)
