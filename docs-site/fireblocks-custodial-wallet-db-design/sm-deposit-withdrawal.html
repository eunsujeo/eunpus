9. Deposit · Withdrawal

고객 입금 / 출금 라이프사이클 — Fireblocks 가 main flow, 은행은 mirror + 회계

9.1 Deposit Lifecycle — 입금

고객이 외부 (다른 거래소 / 외부 wallet) 에서 은행 vault 의 deposit address 로 송금. Fireblocks 가 on-chain monitoring 하여 입금 detection.

9.1.1 정상 흐름

sequenceDiagram
  autonumber
  participant Cust as 👤 고객 (외부)
  participant Chain as 🌐 Blockchain
  participant FB as ☁️ Fireblocks
  participant Bank as 🏢 은행 mirrordb
  participant App as 은행 application
  participant AML as AML provider

  Note over Cust,FB: 사전: vault 에 deposit address 할당 (CUSTOMER_X)
  Cust->>Chain: 송금 tx broadcast
(to: deposit_address)
  Chain->>FB: tx 발견 (block monitoring)
  FB-.webhook TRANSACTION_CREATED.->Bank
  Note over FB: status: CONFIRMING
  FB->>AML: incoming address screening
  alt AML 통과
    AML-->>FB: clean
    FB->>FB: confirmation 추적 (1 → N)
    FB-.webhook TRANSACTION_STATUS_UPDATED.->Bank
    Note over FB: status: COMPLETED
    FB-.webhook VAULT_ACCOUNT_ASSET_BALANCE_UPDATED.->Bank
    Bank->>App: 고객 잔액 업데이트
(customer_balance_subledger)
    App->>Cust: 입금 알림
  else AML 차단
    AML-->>FB: blocked
    FB-.webhook TRANSACTION_STATUS_UPDATED (REJECTED).->Bank
    Note over Bank: 의심 거래 review queue
  end

고객 입금의 전체 흐름. Fireblocks 가 on-chain 발견 → AML screening → confirmation 추적 → 완료. 은행은 webhook event 로 mirror + 자체 회계 업데이트.

9.1.2 Deposit 상태

상태의미은행 액션
CREATEDFireblocks 가 mempool 또는 chain 에서 tx 발견알림: "입금 처리 중"
CONFIRMINGconfirmation 진행 중운영 모니터링
AML_PENDINGAML screening 진행—
AML_BLOCKEDAML 차단 → REJECTEDcompliance review queue · STR 후보
COMPLETEDfinality 도달 + AML 통과고객 잔액 업데이트 + 알림
REJECTED_INCOMING거부된 입금 자산 (반환 / 격리)별도 처리 queue

9.2 Withdrawal Lifecycle — 출금

고객이 외부 address 로 출금 요청. 은행 application 이 Fireblocks API 호출 → TAP 평가 → 승인 → 서명 → broadcast.

9.2.1 정상 흐름

sequenceDiagram
  autonumber
  participant Cust as 👤 고객
  participant App as 🏢 은행 application
  participant CDB as customerdb
  participant FB as ☁️ Fireblocks API
  participant TAP as Policy / TAP
  participant AG as Approval Group
  participant Sig as MPC / Cosigner / HSM
  participant Chain as 🌐 Blockchain
  participant Bank as 🏢 mirrordb

  Cust->>App: 출금 요청 (금액 + 외부 address)
  App->>CDB: counterparty 확인
(whitelisted_destinations)
  App->>App: KYC 상태 / 잔액 / 한도 검증
  App->>FB: Create Transaction
(idempotency key 첨부)
  FB->>TAP: Policy 평가
  alt AML 차단
    TAP-->>FB: BLOCKED
    FB-.webhook.->Bank
    App-->>Cust: 거절 알림
  else 정책 통과 + quorum 필요
    TAP->>AG: quorum 승인 요청 (mobile push)
    AG-->>TAP: 승인 (또는 거절)
  end
  TAP->>Sig: 서명 라우팅
  Sig-->>FB: 서명 완료
  FB->>Chain: broadcast
  Chain-->>FB: tx_hash + confirmation
  FB-.webhook (단계마다).->Bank
  Note over Bank: tx_status_history 누적
  alt COMPLETED
    Bank->>App: 출금 확정
    App-->>Cust: 출금 완료 알림
  else FAILED / TIMEOUT
    App-->>Cust: 출금 실패 알림
  end

고객 출금의 전체 흐름. 은행 application 이 사전 검증 → Fireblocks API 호출 → TAP / Approval Group / 서명 → broadcast → webhook mirror. 모든 단계가 webhook event 로 mirrordb 에 기록.

9.2.2 출금 상태 (Fireblocks 17 status 의 부분 집합 매핑)

은행 도메인 상태대응 Fireblocks status의미
REQUESTED—고객 신청 (은행 application 단계, Fireblocks 미접수)

9.3 KR 컴플라이언스 통합

9.3.1 트래블룰 (100만원 이상)

시행령 10조의10 — VASP 간 100만원 이상 송금 시 송신자 / 수신자 정보 교환 의무.

  1. 은행 application 이 출금 요청 시 금액 평가
  2. 100만원 이상이면 트래블룰 trigger
  3. VASP counterparty (수신측) 확인 (Sumsub / Notabene / TRP 등 트래블룰 provider 활용)
  4. 송신자 / 수신자 정보를 트래블룰 protocol 로 교환
  5. compliancedb.travel_rule_records 에 기록
  6. Fireblocks Create Transaction 호출 — Fireblocks 의 정책 외 별도 처리

출처: Define Travel Rule Policies · 특금법 시행령

9.3.2 STR / 의심 거래 보고

  • 입금: AML provider 가 flagged → compliance reviewer 의 manual review
  • 출금: high-risk address 또는 unusual pattern → 컴플라이언스 담당자 alert
  • 판단 결과 의심 거래 시: KOFIU (금융정보분석원) 에 STR 보고
  • 처리 결과를 compliancedb.suspicious_tx_review 에 기록

9.3.3 콜드월렛 80% 비율 유지

가상자산업감독규정 9조의 80% offline 보관 의무.

  • 대량 출금 시 Hot vault 잔액 부족 가능 → Cold workspace 에서 rebalancing
  • Cold → Hot 이동 자체가 별도 Fireblocks 거래 (Cold workspace 의 Admin Quorum 매개)
  • 은행 운영팀: 일일 Hot/Cold 비율 monitoring + 임계점 도달 시 rebalancing trigger

9.4 잔액 mirror — 정합성 보장

은행 customerdb / mirrordb 의 고객별 잔액과 Fireblocks vault balance 의 정합성.

mirrordb.balance_snapshots

column설명
snapshot_id (PK)은행 내부 ID
fb_vault_idvault
asset_idBTC / ETH / ...
balance_totalFireblocks 측 total balance
balance_available가용 balance (pending 제외)
balance_lockedlocked (pending tx)
snapshot_at스냅샷 시점 (정기 API 호출)
sourcewebhook / api_poll / reconciliation

일일 reconciliation 절차

  1. 각 vault 의 balance 조회 (Fireblocks API)
  2. mirrordb.balance_snapshots 에 기록
  3. customer_balance_subledger 의 합계와 대조 (omnibus 시)
  4. mismatch 발견 시 reconciliation_finding 으로 기록 + 운영팀 alert
  5. 금감원 보고 / 외부 감사 시점에 reconciliation log 가 증명 자료
★ 고객별 잔액 분리의 함의

omnibus vault 운영 시 on-chain 에는 통합 balance 만 존재. 은행은 자체 customer_balance_subledger 의 정합성 (audit log 와 합) 을 별도로 증명해야 함. 대법원 2024도10710 의 "실질 통제" 판단 시 고객별 자산 구분이 명확해야 함 — subledger 의 변조방지 (hash chain 등) 권장.

9.5 사용자 응답 시간 정책

KR 가상자산이용자보호법의 사용자 출금 응답 시간 요건 (구체 시한은 별도 검토 필요). 은행이 응답 시간 SLA 를 정의해야 함.
