14. Deposit · Withdrawal

고객 입금 / 출금 라이프사이클 — Fireblocks 가 main flow, 은행은 mirror + 회계

14.1 Deposit Lifecycle — 입금

고객이 외부에서 은행 vault 의 deposit address 로 송금. sender 유형에 따라 컴플라이언스 / AML 처리 분기:

sender 유형특성처리 분기
외부 거래소 (VASP)등록된 VASP 에서 송신 (Binance · Coinbase 등의 hot wallet)트래블룰 sender 정보 수신 (IVMS101) · VASP counterparty 식별 · AML cluster 분석 (Chainalysis KYT 등)
외부 wallet (self-custody)고객 본인의 외부 wallet 또는 미식별 walletcluster 분석 (cluster 가 거래소 hot 으로 식별되면 unhosted wallet rule 검토) · AML risk score
다른 VASP (트래블룰 sender)거래소 외 VASP (custodian · OTC desk 등)트래블룰 sender 정보 수신 · VASP 식별
고위험 / 제재 list addressAML provider 가 flagged즉시 REJECTED + STR 후보

Fireblocks 가 on-chain monitoring 하여 입금 detection — sender 분류는 AML provider (Chainalysis · Elliptic · TRM Labs) 의 address screening 결과를 활용.

14.2 Withdrawal Lifecycle — 출금

고객이 외부 address 로 출금 요청. 은행 application 이 사전 검증 → Fireblocks API 호출 → TAP 평가 → 승인 → 서명 → broadcast.

★ 출금 모델 — 2-layer 분리 (bank intent + vendor execution)

출금은 두 개의 다른 lifecycle 이 직렬로 묶임:

  • (A) bank intent — 고객 의지 (요청 / 검증 / 승인 / 취소). Fireblocks 와 무관. → customer.transaction_request
  • (B) vendor execution — 실제 Fireblocks 거래의 lifecycle. 1 요청 → N vendor tx (multi-leg / 재시도 / swap 출금). → transaction.transaction_execution

대부분 1:1 (1 request = 1 execution) 이나, 다음 케이스에서 1:N 자연 모델링:

  • multi-leg — Cold → Hot rebalancing 후 출금 (2 vendor tx, 1 request)
  • 재시도 — 첫 vendor tx broadcast 실패 → 새 vendor tx 로 재시도 (2 execution, 1 request)
  • chunk 출금 — 큰 금액을 여러 tx 로 split
  • swap 기반 출금 — ERC-20 USDT 요청 → 사용자 TRC-20 USDT 수령 (outbound + swap + re-broadcast = 3 vendor tx)

14.2.2 출금 상태 + schema → 14a 페이지

출금 (withdrawal) 의 2-layer status 모델 (request_status · execution_status) + customer.transaction_request · transaction.transaction_execution schema + cross-domain 1:N 관계는 14a. Transaction Request · Execution 의 통합 정의로 이동.

14a 페이지는 4 type (withdrawal · swap · onramp · offramp) 의 통합 schema 를 다루며, withdrawal 특정 사용 패턴은 14a.6 절 (type 별 사용 패턴) 참조. status enum 은 14a.5 절. 17 primary Fireblocks status 와의 매핑은 12. Transaction State + 14-step 12.1 절 참조.

14.3.1 트래블룰 (100만원 이상)

시행령 10조의10 — VASP 간 100만원 이상 송금 시 송신자 / 수신자 정보 교환 의무.

  1. 은행 application 이 출금 요청 시 금액 평가
  2. 100만원 이상이면 트래블룰 trigger
  3. VASP counterparty (수신측) 확인 (Sumsub / Notabene / TRP 등 트래블룰 provider 활용)
  4. 송신자 / 수신자 정보를 트래블룰 protocol 로 교환
  5. compliance.travel_rule_records 에 기록
  6. Fireblocks Create Transaction 호출 — Fireblocks 의 정책 외 별도 처리

14.3.2 STR / 의심 거래 보고

  • 입금: AML provider 가 flagged → compliance reviewer 의 manual review
  • 출금: high-risk address 또는 unusual pattern → 컴플라이언스 담당자 alert

14.3.3 콜드월렛 80% 비율 유지

가상자산업감독규정 9조의 80% offline 보관 의무.

  • 대량 출금 시 Hot vault 잔액 부족 가능 → Cold workspace 에서 rebalancing
  • Cold → Hot 이동 자체가 별도 Fireblocks 거래 (Cold workspace 의 Admin Quorum 매개)
  • 은행 운영팀: 일일 Hot/Cold 비율 monitoring + 임계점 도달 시 rebalancing trigger

14.4 거래소 거래 특수성

★ 두 종류의 거래소 거래 — 혼동 금지

"거래소" 가 등장하는 케이스는 주체가 다른 두 종류. 데이터 모델 / 회계 / 거버넌스 가 완전히 다름:

케이스주체주된 모델회계
① 고객 → 본인의 외부 거래소 계좌 출금고객 (수탁 서비스 사용자)customer.transaction_request + customer.customer_external_destination (NEW)customer_ledger 차감 + 반환채무 ↓
② 은행 자체의 거래소 운용 (treasury / liquidity / fiat conversion)은행 본인 (자체 자금 운용)counterparty.exchange_account_map + vendor_transaction 직접 (transaction_request 사용 안 함)bank_ledger 갱신

본 절은 두 케이스를 각기 다른 sub-section 에 분리:

  • 14.4.2 = 고객 → 본인 외부 거래소 출금 (주된 케이스)
  • 14.4.3 = 은행 자체 운용 거래소 거래 (treasury 영역)

14.4.1 거래소 입금 — sender 가 거래소

  • VASP counterparty 식별 — sender address 가 거래소의 hot wallet (Chainalysis cluster 또는 자체 매핑) 이면 트래블룰 obligation 발동
  • 트래블룰 sender 정보 수신 — VASP 가 IVMS101 message 송신 — compliance.travel_rule_records 에 기록
  • 본인 self-deposit 식별 — sender 거래소 가 은행 own sub-account (counterparty.exchange_account_map) 면 자체 운용 거래 → bank_ledger 갱신 (고객 거래 아님)
  • 고객 self-deposit 식별 — sender 거래소 가 고객 본인의 외부 계좌 (customer.customer_external_destination 에 사전 등록된 계좌) 면 customer's own funds inflow → customer_ledger 갱신 (트래블룰 originator = customer self)
  • VASP 식별 실패 시 — cluster 가 unknown 또는 외부 wallet 으로 보이면 unhosted wallet rule 검토 (KR 법률 자문 필요)

14.4.2 고객 → 본인 외부 거래소 출금 (★ 주된 케이스)

고객이 은행 vault 의 자산을 본인이 보유한 외부 거래소 계좌 (Binance · Coinbase · Upbit 등) 로 출금. 이 케이스는 은행이 거래소의 sub-account 를 보유하지 않음 — 단지 고객 본인의 계좌로 송금하는 것. 거래소 측의 API key / 인증 정보 불필요.

  App->>CED: 검증 — destination 활성 + ownership_verified
  App->>WR: INSERT (counterparty_ref_id = cdst_xxx)
  alt 100만원 이상 (트래블룰)

beneficiary info = customer_account_label

  Note over FB: Approval / Signing / Broadcasting

사전 등록 case 의 출금 흐름. 트래블룰 시 originator = 은행 고객 / beneficiary = 같은 고객 본인의 거래소 계좌 — IVMS101 의 originator == beneficiary 동일 사람 (self-transfer between accounts at different VASPs).

운영 정책 결정 사항
  • ownership 검증 정책 — 어느 방법 (micro-deposit / KYC 신고 / 거래소 API verify) 을 강제? 한도별 차등?
  • round-trip 종결 정의 — on-chain confirmation 만 종결? 또는 거래소 측 입금 확인 (API polling) 까지? 본 reference 는 on-chain confirmation 까지만 종결 로 정의. 거래소 측 입금 미인식 시 사용자 문의 응대 필요
  • VASP 식별 실패 시 처리 — cluster 가 unknown 이면 unhosted wallet rule 검토 (KR 법률 자문 필요)
  • 등록 한도 — 고객당 등록 가능한 external destination 수 (운영 부담 vs 사용자 편의)

14.4.3 은행 자체의 거래소 거래 — treasury / liquidity / fiat conversion

고객 출금과 별개로 은행이 직접 거래소와 거래하는 케이스 — Hot 자산 보충 · 환전 · fiat conversion 등. 본 영역은 고객 거래가 아닌 자체 운용:

  • 거래 모델 — counterparty.exchange_account_map 의 entry (은행 own sub-account) + vendor_transaction 직접 INSERT. transaction_request 사용 안 함 (고객 의지 아님)
  • 회계 매핑 — customer_ledger 가 아닌 bank_ledger 에 기록 (회사 자산)
  • 거래 유형 — Hot 잔액 부족 시 거래소 매입 / 24h 한도 운영 / 환전 (USDT ↔ 원화) / cold rebalancing boost
  • 거버넌스 — operational vault 의 자체 거래로 Admin Quorum 매개 (자산 규모에 따라)
  • API key 보관 — exchange_account_map.api_key_secret_ref 의 secret manager reference. API key 자체는 절대 column 에 저장 금지

본 reference 는 자체 거래의 schema 를 별도 정의하지 않음 — 운영 시점에 정책 / 규모 / 회계 처리에 따라 결정 (저자 추정: 자체 운용 전용 dashboard / cron 으로 trigger).

일일 reconciliation 절차

  1. 각 vault 의 balance 조회 (Fireblocks API) — Hot omnibus / Cold / segregated 모두
  2. transaction.balance_snapshots 에 기록
  3. 고객 자산 정합성 식 검증: Σ(customer_ledger) + Σ(delta_ledger) == Σ(고객 자산 vault on-chain 잔액) (Hot + Cold + segregated 합산)
  4. 은행 자체 자산 (treasury · gas · 수수료 vault) 은 별도 bank_ledger 와 대조
  5. mismatch 발견 시 reconciliation_finding 으로 기록 + 운영팀 alert
  6. 금감원 보고 / 외부 감사 시점에 reconciliation log 가 증명 자료
★ 고객별 잔액 분리의 함의 (저자 hypothesis)

고객 자산이 여러 vault (Hot omnibus + Cold + segregated) 에 분산된 경우, on-chain 에는 각 vault 별 통합 balance 만 존재. 은행은 자체 customer_ledger (5. Vault · Asset Wallet · Address 5.4 절 / 18. 회계 · 원장 설계 의 4 원장 ①) 로 고객별 분배를 기록 + 모든 고객 자산 vault 합계 와의 정합성 (audit log 와 합) 을 별도로 증명해야 함. 대법원 2024도10710 의 "실질 통제" 판단 시 고객별 자산 구분이 명확해야 한다는 해석은 저자 hypothesis — 별도 법률 검토 필요. subledger 의 변조방지 (hash chain 등) 권장.
