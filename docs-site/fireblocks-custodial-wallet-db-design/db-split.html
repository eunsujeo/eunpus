3. DB 분할

7 DB → 3 DB 단순화 — Fireblocks 가 떠맡는 책임만큼 은행 DB 가 줄어든다

3.1 직접 구축의 7-DB → 도입 후 3-DB

직접 구축 reference (2. DB 분할) 의 7 DB 중 어떤 것이 Fireblocks 로 흡수되고, 어떤 것이 은행에 남는가:

직접 구축 DB책임Fireblocks 도입 시
walletdbworkspace · vault · 사용자 · counterparty✅ Fireblocks 가 흡수 (Console + API). 은행은 customerdb 만 (고객 ↔ vault 매핑 + counterparty registry)
ledgerdb잔액 · 이체 이력 · balance cache⚠️ 부분 — Fireblocks 가 잔액 API 제공. 은행은 operationsdb 에 balance snapshot mirror + 자체 회계 통합 (별도 ledger 운영 권장 — 저자)
approverdb정책 + 승인 결정✅ Fireblocks 가 흡수 (Console Policy 화면 + Approval Group). 은행 DB 에는 정책 자체를 저장하지 않음 — operationsdb 에 결정 이벤트 mirror
auditdb변조방지 audit log⚠️ Fireblocks Console 의 immutable log 가 1차. 은행은 operationsdb 에 5년 보존용 mirror (특금법 5조의4)
chaindbtx · broadcast · chain event · AML⚠️ 부분 — Fireblocks 가 transaction lifecycle 운영. 은행은 operationsdb 에 webhook 으로 mirror
providerdb외부 system 매핑 (AML provider · IdP)⚠️ Fireblocks 가 AML provider 통합 제공. 은행은 compliancedb 에 KR 컴플라이언스 / 트래블룰 / 금감원 보고
recondb정산 결과✅ 선택 — operationsdb 안에 reconciliation 결과 column 추가 (별도 DB 불필요, 저자 추정)
결론 — 은행이 운영하는 DB 는 2-3 개
  • customerdb — 고객 (은행 사용자) ↔ Fireblocks vault account 매핑 + counterparty registry + 은행 user 정보
  • operationsdb — (a) Fireblocks 사본 (webhook · 거래 · audit log · 잔액 snapshot) + (b) 은행 자체 데이터 (회계 4 원장 · 대사 결과 · 환율 · 멱등 메타 · 운영 로그) + (c) 5 년 보존 + hash chain 변조방지
  • compliancedb (선택) — KR 컴플라이언스 / 트래블룰 / 금감원 보고용 별도 DB. 작은 시작 시 operationsdb 와 통합 가능

3-layer 흐름 — 노랑 = 외부 진입점 (채널계 사용자 · Fireblocks webhook · 운영 스케줄 cron · 운영자) / 파랑 = 코인계 service (거래 API · Webhook · 원장/대사 · 관리 콘솔) / 초록 = 3 DB (customerdb · operationsdb · compliancedb).
각 service 별 진입점: 거래 API = 채널계 (사용자 입출금) / Webhook = Fireblocks webhook 발신 / 원장 / 대사 = 운영 스케줄 (daily 마감 · 5min 대사 cron) / 관리 콘솔 = 운영자 / 컴플라이언스 / 회계팀.
service 별 DB write owner: 거래 API = customerdb · compliancedb / Webhook = operationsdb (사본) / 원장 / 대사 = operationsdb (자체 데이터). 관리 콘솔은 직접 DB 호출 안 함 — 다른 service 의 백엔드 API 경유. 인프라 배치는 2. 인프라 운영 참조.

3.4 분할의 근거 — 직접 구축 5 근거 중 도입 후에도 유효한 것

출처: 직접 구축 reference (2. DB 분할) 의 5 분할 근거를 본 reference 의 도입 환경에 적용한 분석. 일반 IT 표준 (DB 분할의 보안 / 운영 패턴) 기반.

근거도입 후 적용
① 민감도 격리유효 — customerdb 의 고객 PII 와 operationsdb 의 거래 기록 / 회계 분리
② 변경 패턴 분리유효 — operationsdb 의 사본 부분은 strictly append-only (webhook 받은 그대로), customerdb / operationsdb 자체 회계는 mixed (mutable + append-only)
③ 사고 범위 축소유효 — operationsdb 가 SQL injection 으로 corrupt 되어도 customerdb 의 고객 정보 / compliancedb 의 STR 기록은 별개 DB 라 안전
④ 운영 권한 분리유효 — Webhook service 의 DB account 가 customerdb 에 write 권한 없음. 각 service 별 최소 권한
⑤ 외부 감사 단순화유효 — 금감원 / 회계감사관은 operationsdb + compliancedb 만 read-only (거래 + AML + STR + 트래블룰 전 영역 audit). 고객 개인정보 (customerdb) 비공개 가능

3.5 단순화의 trade-off

제약의미 + 해결책
① 진실 source = Fireblocks Console Fireblocks 가 발신한 이벤트의 1 차 source 는 Fireblocks Console 의 immutable log. 은행 operationsdb 의 사본 부분은 canonical 아님 — 분쟁 시 Fireblocks Console 의 log 가 1 차. 단 operationsdb 의 자체 데이터 (회계 4 원장 · 대사 결과 · 환율) 는 은행이 1차 source. 두 영역 구분 명확화 필요.
② Webhook 손실 risk 네트워크 장애 / 은행 서버 다운 시 webhook 누락 가능. 해결: (a) Fireblocks 의 retry 정책 활용 (Configure Webhooks), (b) 정기 reconciliation (Fireblocks REST API 의 List Transactions 로 mirror 와 대조 — 10. Webhook 처리 의 § "정기 Reconciliation" 참조)
③ Vendor outage 시 운영 중단 Fireblocks SaaS 장애 = 은행 거래 처리 중단. 해결: 사용자 응답 시간 정책 + 알림 시스템 + queue. 직접 구축에는 없는 새 risk — 상세는 14. Risks Register 의 FB-R02 참조.
④ 5년 보존 의무 (KR 특금법) Fireblocks 의 Console log 보존 정책이 5 년 충족 여부는 vendor 확인 필요. 해결: operationsdb 에 자체 5년 retention 적용 — partition + cold storage archive. 상세는 13. KR 규제 매핑 의 § "5년 보존" + 17. DB 운영 · Anti-patterns 의 partition 전략 참조.
⑤ 자체 회계 영역의 변조방지 책임 operationsdb 의 자체 회계 (4 원장 · 대사 · 환율) 는 은행이 1 차 source. 해결: hash chain 적용 (각 row 의 SHA-256 chain) + 정기 외부 anchor. 외부 감사 시 무결성 증명. 상세는 15. 회계 · 원장 설계 · 12. Audit · AML · Travel Rule 참조.

3.6 Storage Class (column 동작 패턴) — 도입 후 적용

Storage Class = column 별로 어떻게 변경되는지 (mutable / append-only / set-once / hash chain 등) 분류한 패턴. 직접 구축 reference 의 7 storage class (24. Storage Discipline) 중 도입 후 은행 DB 에서 자주 쓰이는 항목:

Class의미은행 DB 예시
M-mut
(Mutable)		 자유롭게 UPDATE 가능 customerdb 의 bank_users.name, bank_users.department 등 사용자 정보
M-cache
(Mutable cache)		 canonical source 가 외부 (Fireblocks · blockchain) 에 있고 은행 DB 는 cache. stale 가능 → 정기 refresh operationsdb 의 balance_snapshots.value_krw (Fireblocks 잔액 cache)
A-row
(Append-only row)		 새 row 만 INSERT. UPDATE / DELETE 금지 operationsdb 의 webhook_events, tx_status_history
A-set
(Append-only + set-once column)		 row 는 추가 가능하지만 특정 column 은 첫 write 후 변경 불가 operationsdb 의 tx_mirror.vendor_tx_id, tx_mirror.created_at_fb
A-chain
(Append-only + hash chain)		 A-row + 이전 row 의 hash 를 포함하여 SHA-256 chain 형성. 중간 변조 detection 가능 operationsdb 의 audit_log_mirror.current_hash, general_ledger_snapshot.current_hash (15. 회계 / 16. 대사 영역)
R-only
(Read-only)		 application code 가 작성 안 함. DB 외부 (예: ETL · 정보계) 가 채움 operationsdb 의 외부 reference 데이터 (예: 정보계에서 import 된 cross-reference)
F-bid
(Forbidden)		 어떤 column 에도 절대 저장 금지. 자산 노출 risk 아래 callout 참조

각 column 의 storage class 분류 + enforcement (DB trigger · RLS · application 코드 검증) 의 상세는 17. DB 운영 · Anti-patterns 의 권한 / partition / trigger 절 참조.

★ 절대 어떤 column 에도 저장 금지 (F-bid)

직접 구축에서와 동일 — 모든 은행 DB column 에 다음 절대 저장 금지:

  • Fireblocks API secret 평문 (secret manager 만 가능)
  • MPC private key share (직접 구축 시에도, 도입 시에도 동일하게 금지)
  • Mobile device 의 KeyChain 내용
  • Recovery passphrase (Workspace Keys Backup 의 입력)
  • HSM PIN (Key Link 시)
  • 외부 IdP password (SSO 위임)
