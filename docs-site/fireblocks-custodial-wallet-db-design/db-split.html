3. DB 분할

7 DB → 3 DB 단순화 — Fireblocks 가 떠맡는 책임만큼 은행 DB 가 줄어든다

3.1 직접 구축의 7-DB → 도입 후 3-DB

직접 구축 reference (2. DB 분할) 의 7 DB 중 어떤 것이 Fireblocks 로 흡수되고, 어떤 것이 은행에 남는가:

직접 구축 DB책임Fireblocks 도입 시
walletdbworkspace · vault · 사용자 · counterparty✅ Fireblocks 가 흡수 (Console + API). 은행은 customerdb 만 (고객 ↔ vault 매핑 + counterparty registry)
ledgerdb잔액 · 이체 이력 · balance cache⚠️ 부분 — Fireblocks 가 잔액 API 제공. 은행은 mirrordb 에 balance snapshot mirror + 자체 회계 통합 (별도 ledger 운영 권장 — 저자)
approverdb정책 + 승인 결정✅ Fireblocks 가 흡수 (Console Policy 화면 + Approval Group). 은행 DB 에는 정책 자체를 저장하지 않음 — mirrordb 에 결정 이벤트 mirror
auditdb변조방지 audit log⚠️ Fireblocks Console 의 immutable log 가 1차. 은행은 mirrordb 에 5년 보존용 mirror (특금법 5조의4)
chaindbtx · broadcast · chain event · AML⚠️ 부분 — Fireblocks 가 transaction lifecycle 운영. 은행은 mirrordb 에 webhook 으로 mirror
providerdb외부 system 매핑 (AML provider · IdP)⚠️ Fireblocks 가 AML provider 통합 제공. 은행은 compliancedb 에 KR 컴플라이언스 / 트래블룰 / 금감원 보고
recondb정산 결과✅ 선택 — mirrordb 안에 reconciliation 결과 column 추가 (별도 DB 불필요, 저자 추정)
결론 — 은행이 운영하는 DB 는 2-3 개
  • customerdb — 고객 (은행 사용자) ↔ Fireblocks vault account 매핑 + counterparty registry + 은행 user 정보
  • mirrordb — Fireblocks webhook 이벤트 수신 + 5년 보존 + audit mirror + balance snapshot
  • compliancedb (선택) — KR 컴플라이언스 / 트래블룰 / 금감원 보고용 별도 DB. 작은 시작 시 mirrordb 와 통합 가능

3.4 분할의 근거 — 직접 구축 5 근거 중 도입 후에도 유효한 것

근거도입 후 적용
① 민감도 격리유효 — customerdb 의 고객 PII 와 mirrordb 의 거래 기록 분리
② 변경 패턴 분리유효 — mirrordb 는 strictly append-only (webhook 받은 그대로), customerdb 는 mutable (사용자 이름 등 변경)
③ 사고 범위 축소유효 — mirrordb 가 SQL injection 으로 corrupt 되어도 customerdb 의 고객 정보는 별개 DB 라 안전
④ 운영 권한 분리유효 — webhook service 의 DB account 가 customerdb 에 write 권한 없음
⑤ 외부 감사 단순화유효 + 강화 — 금감원 / 회계감사관은 mirrordb 만 read-only. 고객 개인정보 (customerdb) 비공개 가능

3.5 단순화의 trade-off

제약의미 + 해결책
① 진실 source = Fireblocks Console 은행 mirrordb 는 mirror 이므로 canonical source 가 아님. 분쟁 시 Fireblocks Console 의 immutable log 가 1차. 은행은 mirror 가 정확함을 reconciliation 으로 증명해야 함.
② Webhook 손실 risk 네트워크 장애 / 은행 서버 다운 시 webhook 누락 가능. 해결: (a) Fireblocks 의 retry 정책 활용 (Configure Webhooks), (b) 정기 reconciliation (Fireblocks REST API 의 List Transactions 로 mirror 와 대조)
③ Vendor outage 시 운영 중단 Fireblocks SaaS 장애 = 은행 거래 처리 중단. 해결: 사용자 응답 시간 정책 + 알림 시스템 + queue. 직접 구축에는 없는 새 risk.
④ 5년 보존 의무 (KR 특금법) Fireblocks 의 Console log 보존 정책이 5 년 충족 여부는 vendor 확인 필요. 해결: mirrordb 에 자체 5년 retention 적용 — partition + cold storage archive

3.6 Storage Class (column 동작) — 도입 후 적용

직접 구축의 7 storage class 중 도입 후 은행 DB 에서 자주 쓰이는 4 가지:

  • M-mut (Mutable) — customerdb 의 bank_users.name 등. 자유 update
  • M-cache — mirrordb 의 balance_snapshots.value_krw 등. canonical source 는 Fireblocks (stale 가능, refresh 정책 필요)
  • A-row (Append-only row) — mirrordb 의 webhook_events. 새 행만 추가, UPDATE/DELETE 금지
  • A-set (Set-once) — mirrordb 의 tx_mirror.fb_tx_id, tx_mirror.created_at_fb. 한 번 write 후 변경 불가
★ 절대 어떤 column 에도 저장 금지 (F-bid)

직접 구축에서와 동일 — 모든 은행 DB column 에 다음 절대 저장 금지:

  • Fireblocks API secret 평문 (secret manager 만 가능)
  • MPC private key share (직접 구축 시에도, 도입 시에도 동일하게 금지)
  • Mobile device 의 KeyChain 내용
  • Recovery passphrase (Workspace Keys Backup 의 입력)
  • HSM PIN (Key Link 시)
  • 외부 IdP password (SSO 위임)
