3. DB 분할

Fireblocks 가 떠맡는 책임만큼 은행 데이터 영역이 줄어든다 — 9 logical domain · 3 격리 영역 (core · audit · compliance)
★ 본 페이지는 logical 설계 — engine 운영자 결정

본 페이지의 customer.customer_vault 같은 표기는 logical domain.table 이며 특정 DB engine 에 binding 안 됨. 같은 logical 모델을 다음 engine 들로 다양하게 구현 가능:

  • RDB (PostgreSQL · MySQL · Oracle · SQL Server) — 9 domain 을 schema / 별도 database / 별도 instance 중 선택하여 격리
  • NoSQL (DynamoDB · MongoDB · Cassandra) — domain 별 별도 collection / table group
  • Time-series DB (TimescaleDB · InfluxDB · ClickHouse) — transaction / balance_check_history / fx_rate 등 시계열 영역
  • Append-only object store (S3 Object Lock · AWS QLDB · Azure Immutable Blob) — audit 영역의 변조방지 storage
  • Cache (Redis · Memcached) — balance_snapshots 등 외부 SoT 의 mutable cache

운영자는 각 domain 의 data 특성 (3.6) 을 보고 자신의 환경에 맞는 engine 을 선택. 본 wiki 는 5 가지 보장 (audit 격리 · service 권한 분리 · 변조방지 · 외부 감사 read-only · 5년 retention) 만 명세하며 구현 수단은 자유.

3.1 직접 구축의 7-DB → 도입 후 3 격리 영역

직접 구축 reference (2. DB 분할) 의 7 DB 중 어떤 것이 Fireblocks 로 흡수되고, 어떤 것이 은행에 남는가:

직접 구축 DB책임Fireblocks 도입 시 → 새 영역
walletdbworkspace · vault · 사용자 · counterparty✅ Fireblocks 가 흡수 (Console + API). 은행은 core 격리 영역 안의 customer · counterparty domain (고객 ↔ vault 매핑 + counterparty registry)
ledgerdb잔액 · 이체 이력 · balance cache⚠️ 부분 — Fireblocks 가 잔액 API 제공. 은행은 core 의 transaction domain (balance snapshot mirror) + core 의 accounting domain (자체 회계 4 원장)
approverdb정책 + 승인 결정✅ Fireblocks 가 흡수 (Console Policy 화면 + Approval Group). 은행은 정책 자체를 저장하지 않음 — core 의 admin domain 에 결정 이벤트 mirror

결론 — 3 격리 영역 · 9 logical domain

은행 데이터를 격리 요구사항 기준으로 3 영역으로 분리. 각 영역의 logical domain 들은 운영자가 1 engine instance · 별도 engine · 또는 mix 로 자유롭게 매핑 (3.6 의 data 특성 표 참조):

  • core (7 domain) — 코인계 운영 데이터 전반: customer · counterparty · transaction · accounting · reconciliation · ops · admin. service-level 권한 분리는 schema GRANT (RDB) 또는 별도 collection (NoSQL) 등으로
  • audit (1 영역) — 변조방지 audit log 전용. audit_log_mirror (Fireblocks 사본) + audit_log_internal (은행 자체 master 변경). core 와 storage 분리 필수 — 변조방지 store (append-only DB / object store WORM / hash chain) 권장
  • compliance (1 영역) — KR 컴플라이언스 / 트래블룰 / 금감원 보고. 외부 보고 영역 격리

3.2 9 logical domain — 격리 영역 · 테이블 · 변경 패턴

★ 모든 wiki 테이블 = 코인계 소속

본 reference 에 정의된 9 domain · 모든 테이블 은 코인계 (디지털자산 운영 시스템) 안에 위치. 계정계 (기존 은행 코어 — KRW 잔액 / 입출금 / 고객 계좌) 의 테이블은 본 wiki 범위 밖 이며 외부 reference 만 함.

  • 코인계 (본 wiki) — core (7 domain) + audit + compliance 격리 영역 = 디지털자산 vault · 거래 · 회계 · 컴플라이언스 운영 데이터. 모든 application · DB 는 망분리 안에 배치
  • 계정계 (외부) — 본 wiki 는 column schema 정의 없이 통합 지점만 명시. 통합은 outbox pattern 의 비동기 push (코인계 → 계정계 KRW 입출금 요청) + 일말 마감 회계 push (코인계 general_ledger_entry → 계정계 회계). 5. 인프라 · 망분리 참조
  • 계정계와 sync 책임이 있는 코인계 표 — accounting.bank_ledger (KRW 부분) · accounting.general_ledger_entry (일말 push) · customer.transaction_request (KRW 출금 의도) 등. 표 자체는 코인계 DB 에 있지만 운영 시 계정계와 정합 / 연동 책임이 있음 (18. 회계 · 원장 설계 18.4 / 18.5 참조)

3.2.4 service 별 권한 분리 (engine-agnostic)

9 domain 의 권한 분리는 engine 마다 다른 수단으로 구현. 핵심은 service 별 write 영역 제한 — 어느 engine 으로 가도 다음 매핑 유지:

Service책임core 영역 writecore 영역 readaudit 영역
거래 API (사용자 facing)입출금 요청 진입customer.* (vault 할당 · transaction_request) · counterparty.* (whitelist 등록) · transaction.transaction_execution전 domain read-only—
Webhook workerFireblocks event 처리transaction.* (event + tx mirror + balance snap) · accounting.* (ledger 갱신)전 domain read-onlyaudit_log_mirror write
원장 / 대사 cron일일 마감 · 대사 · 환율 적용accounting.* · reconciliation.*전 domain read-only—
운영자 / adminmaster 변경 (asset_catalog · counterparty · user_map 등)customer.* · counterparty.* · ops.* · admin.*전 domain read-onlyaudit_log_internal write (변경 audit)
외부 감사인 / 금감원증적 review—전 domain read-only (개인정보 가까운 customer · counterparty · admin 제외 검토)전체 read-only

구현 수단:

  • RDB (PostgreSQL) — domain 별 schema GRANT (예: GRANT INSERT ON SCHEMA transaction TO webhook_worker)
  • RDB (MySQL · Oracle) — domain 별 별도 database 또는 prefix + role GRANT
  • NoSQL — IAM role / fine-grained access control
  • Object store (audit 영역) — bucket / prefix 별 IAM 정책 + Object Lock 으로 변조방지
  • application-layer enforcement — engine 권한이 약하면 application middleware 에서 추가 enforcement (단 권한은 storage-level 이 1차)

3-layer 흐름 — 노랑 = 외부 진입점 (채널계 사용자 · Fireblocks webhook · 운영 스케줄 cron · 운영자) / 파랑 = 코인계 service (거래 API · Webhook · 원장/대사 · 관리 콘솔) / 초록 = 3 격리 영역 (core · audit · compliance).
각 service 별 진입점: 거래 API = 채널계 (사용자 입출금) / Webhook = Fireblocks webhook 발신 / 원장 / 대사 = 운영 스케줄 (daily 마감 · 5min 대사 cron) / 관리 콘솔 = 운영자 / 컴플라이언스 / 회계팀.
service 별 write owner: 거래 API = core (customer · counterparty · transaction.transaction_execution) · compliance / Webhook = core (transaction · accounting) + audit (audit_log_mirror) / 원장 / 대사 = core (accounting · reconciliation) / 운영자 = audit (audit_log_internal) + core 의 master domain. core 영역 안에서는 service 별 domain 권한으로 격리 (3.2.4 절 참조). 인프라 배치는 2. 인프라 운영 참조.

3.4 분할의 근거 — 직접 구축 5 근거 중 도입 후에도 유효한 것

출처: 직접 구축 reference (2. DB 분할) 의 5 분할 근거를 본 reference 의 도입 환경에 적용. 본 버전은 engine-agnostic 으로 추상화하여 격리 목적 보장만 명시.

근거본 버전 (3 격리 영역 · 9 domain) 에서 어떻게 충족하는가
① 민감도 격리domain-level 로 달성 — customer domain (외부 ref 만, PII 없음) 와 transaction · accounting 분리. 진짜 PII (이름 / 주민번호) 는 외부 채널계 / KYC 가 보유 (코인계는 reference 만)
② 변경 패턴 분리domain-level 로 달성 — transaction 은 append-only (webhook 사본), accounting 의 ledger snapshot 은 append-only + hash chain, reconciliation · customer · admin 은 mutable. 변경 패턴 axis 는 engine 선택의 기준 (3.6 표 참조)
③ 사고 범위 축소audit 영역 분리로 핵심 보호. core 영역 안 SQL injection / data corruption 시 영향 가능하나, audit log (변조방지 가장 critical) 는 storage 분리 → disaster 시 진실 재구성 가능. core 안에서는 domain 별 service 권한으로 사고 격리
④ 운영 권한 분리storage-level 권한 + service role 로 달성 — service 별 write 영역 매핑 (3.2.4 표). 구현 수단은 engine 에 따라 (RDB schema GRANT · NoSQL IAM · object store bucket policy 등)
⑤ 외부 감사 단순화audit + compliance 영역이 핵심 — 금감원 / 회계감사관은 audit + compliance 전체 + core 의 transaction · accounting · reconciliation read-only. customer · counterparty · admin domain 은 PII 가까운 매핑이라 별도 권한으로 제한 가능
왜 core 안을 추가 분할하지 않았는가 — review 결과

초기 검토에서 customer 영역을 별도 격리로 둘지 고민했으나 5 근거에서 약했음:

  • ① 민감도 격리 약함 — customer 에 실제 PII 없음 (외부 ref 만)
  • ② 변경 패턴 분리 약함 — core 의 다른 domain 들도 mutable + append-only 혼합. 분리 가치 적음
  • ③ 사고 범위 축소 부분 — domain-level 권한으로 부분 달성. 별도 storage 의 고유 가치는 audit 영역에 집중
  • ④ 권한 분리 약함 — domain-level grant 로 동일 효과
  • ⑤ 외부 감사 약함 — 감사 핵심은 audit + compliance 영역

반면 추가 분리 비용은 컸음 — cross-storage FK 불가 · distributed tx · 운영 부담 · naming 직관 어긋남. 본 버전은 audit 만 진정으로 분리하고 (변조방지 핵심), 나머지는 core 단일 + domain 격리 — 한국 거래소 실무 표준과 일치.

3.5 단순화의 trade-off

제약의미 + 해결책
① 진실 source = Fireblocks Console Fireblocks 가 발신한 이벤트의 1 차 source 는 Fireblocks Console 의 immutable log. core 의 transaction domain (사본) 는 canonical 아님 — 분쟁 시 Fireblocks Console 의 log 가 1 차. 단 core 의 accounting · reconciliation · customer · counterparty domain 은 은행이 1차 source. 두 영역 구분 명확화 필요.
② Webhook 손실 risk 네트워크 장애 / 은행 서버 다운 시 webhook 누락 가능. 해결: (a) Fireblocks 의 retry 정책 활용 (Configure Webhooks), (b) 정기 reconciliation (Fireblocks REST API 의 List Transactions 로 mirror 와 대조 — 13. Webhook 처리 의 "정기 Reconciliation" 참조)
③ Vendor outage 시 운영 중단 Fireblocks SaaS 장애 = 은행 거래 처리 중단. 해결: 사용자 응답 시간 정책 + 알림 시스템 + queue. 직접 구축에는 없는 새 risk — 상세는 17. Risks Register 의 Fireblocks SaaS outage 항목 참조.
④ 5년 보존 의무 (KR 특금법) Fireblocks 의 Console log 보존 정책이 5 년 충족 여부는 vendor 확인 필요. 해결: core (transaction) + audit 양 영역에 자체 5년 retention 적용 — partition + cold storage archive (engine 에 따라 RDB partition · object store lifecycle policy · time-series DB retention 등). 상세는 16. KR 규제 매핑 의 "5년 보존" + 20. DB 운영 · Anti-patterns 의 partition 전략 참조.
⑤ 자체 회계 영역의 변조방지 책임 core accounting · reconciliation domain 의 4 원장 · 대사 · 환율 는 은행이 1 차 source. 해결: hash chain 적용 (각 row 의 SHA-256 chain) + 정기 외부 anchor + audit 영역 의 audit_log_internal 에 변경 기록. 외부 감사 시 무결성 증명. 상세는 18. 회계 · 원장 설계 · 15. Audit · AML · Travel Rule 참조.
⑥ core 안 domain 격리의 한계 (★ 본 버전의 trade-off) core 단일 storage 안의 domain 격리는 storage-level 격리보다 약함 — admin 권한이 모든 domain 에 접근 가능. 해결: (a) 최소 권한 원칙 (service 별 별도 role + 명시 grant), (b) admin 작업 audit (audit 영역에 자동 기록), (c) row-level security 도입 검토 (지원 engine 에 한정), (d) 정기 권한 review. 더 강한 격리가 필요하면 core 안의 일부 domain 을 별도 storage 로 분리하는 옵션 검토.

옵션매핑장점단점

(B) Core RDB + Audit 분리 (★ 저자 권장) core + compliance = 1 RDB instance (별도 database 또는 schema). audit = 별도 storage (append-only store · 별도 RDB instance 등) audit 변조방지 핵심 보장 + 운영 단순 + 비용 합리적 cross-storage join 어려움 (단 audit 와 core 의 join 은 거의 안 함)

3.7 Storage Class (column 동작 패턴) — 도입 후 적용

Storage Class = column 별로 어떻게 변경되는지 (자유 수정 / 추가만 가능 / 한 번 쓰면 변경 불가 / hash 사슬 등) 분류한 패턴. 직접 구축 reference 의 7 storage class (24. Storage Discipline) 중 도입 후 은행 DB 에서 자주 쓰이는 항목:

Class의미은행 DB 예시
M-mut
(Mutable)		 자유롭게 UPDATE 가능 customer.customer_vault.status, admin.user_map.vendor_role 등
M-cache
(Mutable cache)		 canonical source 가 외부 (Fireblocks · blockchain) 에 있고 은행 store 는 cache. stale 가능 → 정기 refresh transaction.balance_snapshots.value_krw (Fireblocks 잔액 cache)
A-row
(Append-only row)		 새 row 만 INSERT. UPDATE / DELETE 금지 transaction.webhook_events, transaction.vendor_transaction_status_history
A-set
(Append-only + 한 번 쓰면 변경 불가 column)		 row 는 추가 가능하지만 특정 column 은 첫 write 후 변경 불가 transaction.vendor_transaction.vendor_tx_id, transaction.vendor_transaction.vendor_created_at
A-chain
(Append-only + hash chain)		 A-row + 이전 row 의 hash 를 포함하여 SHA-256 chain 형성. 중간 변조 detection 가능 audit.audit_log_mirror.current_hash, audit.audit_log_internal.current_hash, accounting.general_ledger_snapshot.current_hash
R-only
(Read-only)		 application code 가 작성 안 함. 외부 (예: ETL · 정보계) 가 채움 외부 reference 데이터 (예: 정보계에서 import 된 cross-reference)
F-bid
(Forbidden)		 어떤 column 에도 절대 저장 금지. 자산 노출 risk 아래 callout 참조

각 column 의 storage class 분류 + enforcement (DB trigger · RLS · application 코드 검증) 의 상세는 20. DB 운영 · Anti-patterns 의 권한 / partition / trigger 절 참조.

★ 절대 어떤 column 에도 저장 금지 (F-bid)

직접 구축에서와 동일 — 모든 은행 DB column 에 다음 절대 저장 금지:

  • Fireblocks API secret 평문 (secret manager 만 가능)
  • MPC private key share (직접 구축 시에도, 도입 시에도 동일하게 금지)
  • Mobile device 의 KeyChain 내용
  • Recovery passphrase (Workspace Keys Backup 의 입력)
  • HSM PIN (Key Link 시)
  • 외부 IdP password (SSO 위임)
