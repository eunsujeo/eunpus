은행 측 인프라 (플랫폼 · Co-signer · HSM · webhook endpoint · 망분리 IDC)

2.1 인프라 구성 한눈에 보기

Fireblocks 도입 후 은행이 실제 운영하는 인프라 구성요소. 1. 책임 분담 의 trust boundary 를 물리 / 네트워크 레벨로 풀어냄.

★ KR 은행은 망분리 정책으로 on-prem IDC 강제

전자금융감독규정의 망분리 의무로 인해 KR 은행은 public cloud (AWS / Azure / GCP 일반 region) 직접 사용 어려움. 모든 코인계 컴포넌트 (플랫폼 · DB · Cosigner · HSM 등) 는 은행 자체 on-prem IDC 배치가 default.

예외 — 망분리 cloud 옵션 (AWS Outposts · Azure Stack · 금융 클라우드 등) 은 망분리 환경에 배치 가능하지만 vendor / 금감원 사전 협의 필수. 본 reference 는 on-prem IDC default 로 기술.

은행 망분리 IDC 의 표준 zone 분리. 노랑 = 외부망 (Fireblocks SaaS · IdP · AML / Travel Rule provider · 운영자 Mobile) / 빨강 = DMZ (Outbound Proxy · Webhook · Agent · LB / WAF) / 초록 = 코인계 (망분리) (거래 API · Webhook · 원장/대사 · 관리 콘솔 · 운영 감시 · 3 DB · Cosigner · Customer Server · Callback Server · Secret Manager) / 연보라 = 기존 은행 시스템 (계정계 · 외환계 · 정보계 · 채널계) / 보라 = 보안 구역 (HSM) (?).
화살표 — 방향은 발신자 → 수신자 (response 는 같은 채널로 자연스럽게). 실선 = 동기 호출 (같은 영역 안) / 점선 = 영역 경계 넘는 외부 통신 + 비동기.
망분리 원칙: Application · DB · HSM 은 코인계 (망분리 안). 모든 외부 통신은 DMZ 의 Outbound Proxy (은행 → 외부) 또는 Webhook endpoint / Agent (외부 → 은행) 종단. 코인계에서 직접 외부 호출하는 화살표 없음 (망분리 의무).
기존 은행 시스템 통합: 채널계 → 플랫폼 (사용자 facing 진입) · 플랫폼 ↔ 계정계 (KRW 잔액 / 입출금) · 플랫폼 ↔ 외환계 (환율 / 외환 환산) · 플랫폼 → 정보계 (마감 / 감사 보고). 실제 통합은 별도 ESB / API Gateway / iPaaS 경유하는 경우 많음 (본 다이어그램은 직접 호출로 단순화 표시). 3 계층 정합 (블록체인 · 오프체인 · 계정계) 의 상세는 18. 회계 · 원장 설계 참조.

2.3 플랫폼 운영

본 절의 출처

이하 호스팅 요건 · SDK 활용 · Secret 관리는 저자 권장 + 일반 IT 표준 혼합. Fireblocks 공식 권장이 아님 (단 vendor-specific 사항 — API key 의 IP allowlist · webhook signature 등 — 은 공식 fact 로 별도 표시). 운영 시작 전 본인 환경의 부하 테스트 + 보안팀 / 운영팀 검증 권장.

2.3.1 호스팅 요건 (저자 권장)

  • 최소 2-node HA (?) + load balancer + health check — load balancer (?) 가 들어오는 트래픽을 두 서버에 분산, health check (?) 로 비정상 서버 자동 제외
  • Auto-scaling — 거래량 증가 시 서버 자동 증설 (CPU / memory / 요청 수 기준). on-prem 환경에서는 사전 capacity 예약 + 수동 증설 패턴
  • IDC zone failover — 단일 IDC zone 장애 대응 (예: 주 IDC → 백업 IDC). 본사 IDC + DR site IDC 의 cross-IDC replication
  • outbound NAT IP 고정 — Fireblocks API key 의 IP allowlist 적용용 (vendor-specific)
  • TLS 1.2+ outbound — Fireblocks API 호출 / 외부 provider 통신

2.3.2 Fireblocks SDK 활용

  • 공식 SDK: TypeScript / JavaScript / Python / Java / Go (TypeScript SDK) — 공식 사실
  • SDK version pinning — production 은 fixed version. version upgrade 는 Testnet Staging 에서 사전 검증 — 저자 권장
  • rate limit 준수 — Fireblocks 의 분당 API call 제한 (요금제별 다름, vendor 와 협의) — 공식 사실
  • retry 정책 (저자 권장) — 5xx / network error 시 exponential backoff (예: 1s → 2s → 4s) · max 3 retry. Fireblocks 가 specific 수치를 강제하지 않으므로 본인 환경 부하 + Fireblocks SLA 에 맞춰 조정 필요 — 저자 권장

2.4.2 Co-signer HA / DR

  • 다중 instance — 단일 Co-signer 의 장애가 전체 서명 중단을 일으키지 않도록 2+ instance
  • Callback Handler 통합 — Co-signer 직전에 은행 endpoint 호출하여 추가 검증 (자체 정책) (Create API Co-signer Callback Handler)
  • CSR private key 보관 — Co-signer 등록 시 발급된 CSR private key 의 안전한 보관 (Secret Manager)
  • SGX attestation — Co-signer 가 정상 SGX enclave 안에서 실행 중인지 정기 검증

2.4.3 Co-signer 버전 관리 (★ 중요)

Co-signer 는 키 share 를 보유하는 서명 컴포넌트라 버전 관리가 critical. Fireblocks 가 신규 version 을 발표할 때마다 보안 patch · breaking change · 호환성 변경이 동시에 발생할 수 있음.

2.6 Webhook Endpoint 인프라

은행이 운영하는 Webhook 수신 인프라 의 표준 구성. 상세: 13. Webhook 처리.

2.6.1 HA 구성

  • 최소 2-node — active-active 또는 active-passive
  • L7 LB + WAF — TLS termination, rate limit, IP allowlist (Fireblocks 측 IP)
  • 처리 큐 분리 — endpoint 가 200 OK 응답 후, 별도 worker 가 비동기 처리 (Kafka / SQS / Redis)
  • dead-letter queue — 처리 실패 event 별도 보관 + 운영팀 alert

2.6.2 모니터링

Webhook endpoint 의 monitoring 은 내부망의 Monitoring 컴포넌트 (Prometheus / Grafana / Datadog 등) 가 metric scrape. 주요 metric:

  • signature failure rate (0 권장 — 0 이 아니면 위조 시도 가능성)
  • processing latency p99 < 500ms
  • worker queue depth
  • dedup hit rate (중복 수신 비율)
  • retry rate (Fireblocks 가 retry 한 비율 — 높으면 endpoint 가 느림)

2.10 인프라 capacity sizing

  • Fireblocks API 의 분당 rate limit (요금제 별 다름)
  • Webhook 의 동시 전송 한계 (peak 시점)
  • AML / Travel Rule provider 의 응답 latency
  • blockchain confirmation 시간 (chain 별, 마감 시간 영향)

2.13.1 카테고리 1 — Infrastructure metrics (Prometheus + Grafana)

  • 역할: 서버 / DB / network / docker 의 CPU · 메모리 · disk · network 메트릭 수집
  • 도구: Prometheus (OSS) + node_exporter · postgres_exporter · blackbox_exporter · Grafana dashboard
  • 데이터 source: 코인계 모든 서버 (API · Webhook · Ledger cron · DB · Console · Cosigner host)
  • 보관 기간: 1년 (원시 metric) · 3년 (downsampled hourly)
  • 대표 alert 룰: CPU > 80% 5분 · disk < 10% · DB connection > 90% pool · webhook endpoint p99 latency > 5초 · cosigner heartbeat 부재 1분

2.13.2 카테고리 2 — Application logs (ELK Stack)

  • 역할: application / webhook handler / cron / DB query log 집중 + 검색
  • 도구: Elasticsearch + Logstash + Kibana (OSS) · Filebeat agent · Logstash pipeline
  • 데이터 source: 코인계 서버의 stdout / stderr + 회계 cron + cosigner customer_cosigner.log + audit_log (별도 stream)
  • 보관 기간: 5년 (audit 영역 = 특금법 의무) · 1년 (application = 운영 표준)
  • 대표 활용: 거래 ID 로 lifecycle 추적 · 사용자 ID 로 활동 검색 · 에러율 시계열 · audit log 무결성 검증
  • 외부 log delivery: cosigner 의 경우 Docker JSON file driver → Filebeat → ELK (11. MPC · Cosigner 11.3 절)

2.13.3 카테고리 3 — On-chain monitoring (Chainalysis)

  • 역할: 출금 / 입금 address 의 cluster 식별 · 리스크 점수 · 제재 list screening · VASP 식별 (트래블룰 보조)
  • 도구: Chainalysis KYT (Know Your Transaction) API + Reactor (수사 도구) — 400+ networks 의 노드 수준 데이터 수집
  • 데이터 source: customer.transaction_request 의 destination_address (출금 시) + transaction.deposit_observations 의 sender address (입금 시)
  • 통합 시점: 출금 요청 시 (PENDING_VALIDATION 단계) · 입금 webhook 시 (TRANSACTION_CREATED)
  • 대표 alert: high-risk cluster (Mixer · Darknet · Sanction) 탐지 → 거래 자동 차단 + SOC 검토
  • 보관: compliance.screening_results 에 응답 영구 보관 (audit)
  • 대안 vendor 비교:
    • Chainalysis — 400+ networks · 라벨 / 클러스터링 강점 · KYT 정량 score · Reactor 수사 도구
    • Elliptic — 실시간 지갑 / 거래 스크리닝 · 크로스체인 추적 · 지속 재스크리닝 · Elliptic2 dataset 공개
    • TRM Labs — 제재 확장 인텔리전스 · 크로스체인 위험 + 정책 자동화
FATF 권고 — 내부 데이터 + 외부 인텔리전스 결합

FATF 는 거래소 / 발행사 / 수탁사가 온체인 데이터 + 오프체인 데이터 (KYC · 트래블룰) 를 결합해 잠재적 불법행위를 식별해야 한다고 명시. 동일 VASP 내 내부원장 이동 등 상당수 거래가 오프체인에 존재 → 공개 온체인 데이터만으로는 완전한 감시 불가. 본 wiki 의 customer.transaction_request + Chainalysis KYT 결합이 이 구조에 부합. 출처: sources/monitoring/2026-05-28__blockchain-wallet-stablecoin-monitoring.md.

2.13.4 카테고리 4 — Transaction monitoring (자체 FDS)

  • 역할: 출금 / 스왑 / 램프 거래의 이상 패턴 탐지 + 자동 차단 / 출금 지연
  • 도구: 자체 룰 엔진 — KR 거래소 best practice 모방 (24/72h 출금 지연 · 화이트리스트 · 한도 · 빈도)
  • 데이터 source: customer.transaction_request + accounting.customer_ledger + customer.customer_external_destination
  • 대표 룰 (KR 거래소 패턴 종합 · 저자 권장):
    • 최초 등록 화이트리스트 destination 의 24h 출금 지연 (빗썸 / Upbit 패턴)
    • 당일 누적 출금 한도 (예: 1억원) 초과 시 추가 승인 요청
    • 새 destination 으로의 첫 출금 시 72h 지연 + 추가 본인 확인
    • 고객 평소 패턴 대비 급격한 변화 (금액 · 빈도 · 시간대) → review queue

  • 도구: SIEM — Splunk Enterprise Security 또는 IBM QRadar 또는 자체 ELK + SIEM 룰
  • 데이터 source: WAF / IDS / IPS / SSO / Active Directory / Fireblocks audit_log_mirror + 은행 audit_log_internal · network firewall / SSH 로그
  • 대표 alert: 비정상 SSH login · 권한 변경 · API key 사용 패턴 이상 · 외부 → 망분리 안 접근 시도 · Fireblocks Console 의 비정상 admin 활동
  • 통합: SOC team 의 24/7 monitoring (또는 MSS 위탁) + on-call escalation

2.13.6 통합 alert / on-call

  • 도구: PagerDuty (SaaS) 또는 자체 alert 시스템 + Slack 통합
  • severity tier:
    • P0 (cosigner 다운 · 자금 손실 위험 · 5분 내 응답)
    • P1 (서비스 중요 기능 장애 · 15분 내 응답)
    • P2 (성능 저하 · 30분 내 응답)
    • P3 (warning · business hours 내 응답)
  • on-call shift: SRE / SOC 별도 rotation · primary + secondary + manager escalation
  • runbook: alert 별 사전 정의된 대응 절차 (인계 매뉴얼)
