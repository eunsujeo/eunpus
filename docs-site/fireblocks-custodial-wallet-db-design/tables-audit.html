15. Audit · AML · Travel Rule

Fireblocks 의 immutable log · 은행 5년 보존 mirror · KR 컴플라이언스

15.1 2-Layer Audit 구조 + 은행 내부 audit 의 분리

Fireblocks 도입 시 audit log 는 두 source 가 존재:

Source위치특성책임대상 변경
Layer 1 — Fireblocks Console Fireblocks SaaS immutable, vendor 가 보장 Fireblocks Fireblocks 측 모든 작업 (signing · approval · vault · user · policy 등)
Layer 2 — 은행 mirror audit.audit_log_mirror append-only, hash chain (저자 권장) 은행 (5년 보존 의무) Layer 1 의 사본 (webhook 으로 수신)
은행 내부 audit audit.audit_log_internal append-only, hash chain (저자 권장) 은행 (5년 보존 의무) 은행 측 자체 변경 (master 변경 · 정책 결정 · workspace_code config · asset_catalog status 등 — Fireblocks 와 무관)
audit_log_mirror vs audit_log_internal — 두 종류의 audit 흐름

- audit_log_mirror — Fireblocks Console 의 immutable log 의 사본. webhook 으로 수신, 같은 vendor_event_id 의 중복 도착 시 UNIQUE 제약으로 1 row 만 진입.
- audit_log_internal — 은행 자체 master 변경 (예: asset_catalog.support_status 변경 · workspace config 변경 · counterparty 추가 등) 의 자체 audit log. Fireblocks 가 모르는 영역. application 이 직접 INSERT.
구조 / 컬럼은 거의 동일 (sequence_num · hash chain) — source 컬럼으로 두 종류 구분 가능 또는 표 자체 분리.

왜 2 layer 인가

Fireblocks Console 의 log 는 Fireblocks vendor 에 의존. 은행 자체 mirror 는:

  • 특금법 5조의4 의 5년 보존 의무 충족 (Fireblocks retention 정책이 5년 충족 여부 vendor 확인 필요)
  • vendor outage 시점에도 audit 가능
  • 외부 감사 / 금감원 검사 대응 — 은행이 단독으로 audit 가능한 source
  • 분쟁 시 양측 (Fireblocks Console + 은행 mirror) 의 정합성 증명 가능

15.2 Fireblocks Audit Log 의 event 종류 (저자 정리)

아래 카테고리 분류 (user / governance / policy / vault / counterparty / transaction / api / backup) 는 본 reference 의 정리. Fireblocks 공식 카테고리 명세와 일부 다를 수 있어 운영 시 vendor 문서 재확인 필요.

카테고리대표 event

Hash chain — 변조 방지 권장

audit_log_mirror 가 데이터베이스 admin 의 조작으로 변경되었는지 detection 하기 위한 hash chain:

  • 각 row 의 current_hash = SHA-256(prev_hash || row_data)
  • 마지막 row 의 hash 를 정기적으로 외부 시스템 (예: blockchain anchoring, 외부 timestamp service) 에 anchor
  • 모든 row 가 sequential 하게 연결되므로 중간 변조 시 chain 깨짐
  • 외부 감사 시 hash chain 의 무결성 검증 → 변조 없음 증명

15.4 AML 통합 — provider 연동

Fireblocks 는 다음 AML provider 와 native 통합 (vault → external screening):

  • Chainalysis — KYT (Know Your Transaction). 거래 단위 risk score · 제재 대상 점검
  • Elliptic — wallet screening + transaction monitoring (cross-chain)
  • TRM Labs — risk scoring + sanction screening
  • 기타 — 자체 통합 가능 (Fireblocks API)

15.5 트래블룰 (Travel Rule) — VASP 간 정보 교환

특금법 시행령 10조의10 — VASP 간 100만원 이상 송금 시 송신자 / 수신자 정보 교환 의무. KR 가상자산이용자보호법 의 후속 규제.

IVMS101 (InterVASP Messaging Standard 101) — FATF 권고안 16 (Travel Rule) 의 표준 메시지 format. VASP 간 송신자 / 수신자의 자연인 정보 (이름 · 주소 · 식별번호 · 계좌 정보) 를 JSON / XML 로 교환하는 국제 표준.

구현 옵션

Providerprotocol
NotabeneTRISA / IVMS101
SumsubTRP
TRP (Travel Rule Protocol)open standard
OpenVASPopen standard

Fireblocks 의 Travel Rule policy 는 정책 trigger 까지만 제공 (Define Travel Rule Policies). 실제 VASP 간 정보 교환 (IVMS101 message) 은 별도 provider (Notabene / Sumsub 등) 또는 자체 구현 필요. 은행은 (a) 어느 provider 사용, (b) counterparty VASP 식별 매커니즘, (c) self-hosted wallet 출금 시 처리 정책을 정의해야 함. 14. Deposit · Withdrawal Flow 14.3.1 절 도 함께 참조.

15.6 외부 감사 / 금감원 대응

정기 외부 감사 (SOC 2 / ISO 27001) 또는 금감원 검사 시 제공 가능한 자료:

  1. Fireblocks Console 의 immutable log — Auditor role 의 read-only access 제공
  2. audit.audit_log_mirror — hash chain 무결성 증명 포함
  3. vendor_transaction + vendor_transaction_status_history — 5년 거래 기록
  4. compliance.screening_results — AML 점검 이력
  5. compliance.travel_rule_records — 트래블룰 처리 이력
  6. compliance.suspicious_tx_review + str_filed — STR 보고 이력
  7. admin.recovery_event_log — Backup / Recovery ceremony 이력
  8. reconciliation log — mirror 의 정합성 증명

recovery_event_log "영구" 보존과 개인정보보호법 / GDPR 의 관계

recovery_event_log 는 키 ceremony 의 이력 — 운영자 식별자 (employee_id) + ceremony 결과 정도만 포함하고 자연인 PII (주민번호 · 주소 등) 는 없음. 따라서 개인정보보호법 / GDPR 의 "삭제 권리" 와 직접 충돌하지 않음. 운영자 퇴사 시에도 ceremony 이력 (참여 여부 + 시점) 은 보존 가능 (정당한 보존 사유 = 키 관리 audit trail). 단 외부 감사인 / 자연인 정보가 ceremony 기록에 포함된 경우 별도 redaction 검토 필요.

15.8 archive / partition 운영

  • 30 일 이상 = warm tier (인덱스 일부 활성)
  • 1 년 이상 = cold tier (compressed, archive)
  • 5 년 도래 시 = legal hold 검토 (분쟁 진행 중인 거래는 보존 연장)
  • partition 운영 — 월별 partition 으로 archive 효율

partition / archive 전략 상세는 20. DB 운영 · Anti-patterns 의 partition 전략 + cold storage 정책 참조.
