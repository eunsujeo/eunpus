12. Audit · AML · Travel Rule

Fireblocks 의 immutable log · 은행 5년 보존 mirror · KR 컴플라이언스

12.1 2-Layer Audit 구조

Fireblocks 도입 시 audit log 는 2 layer 로 운영:

Layer위치특성책임
Layer 1 — Fireblocks Console Fireblocks SaaS immutable, vendor 가 보장 Fireblocks
Layer 2 — 은행 mirror mirrordb.audit_log_mirror append-only, hash chain (저자 권장) 은행 (5년 보존 의무)
왜 2 layer 인가

Fireblocks Console 의 log 는 Fireblocks vendor 에 의존. 은행 자체 mirror 는:

  • 특금법 5조의4 의 5년 보존 의무 충족 (Fireblocks retention 정책이 5년 충족 여부 vendor 확인 필요)
  • vendor outage 시점에도 audit 가능
  • 외부 감사 / 금감원 검사 대응 — 은행이 단독으로 audit 가능한 source
  • 분쟁 시 양측 (Fireblocks Console + 은행 mirror) 의 정합성 증명 가능

Hash chain — 변조 방지 권장

audit_log_mirror 가 데이터베이스 admin 의 조작으로 변경되었는지 detection 하기 위한 hash chain:

  • 각 row 의 current_hash = SHA-256(prev_hash || row_data)
  • 마지막 row 의 hash 를 정기적으로 외부 시스템 (예: blockchain anchoring, 외부 timestamp service) 에 anchor
  • 모든 row 가 sequential 하게 연결되므로 중간 변조 시 chain 깨짐
  • 외부 감사 시 hash chain 의 무결성 검증 → 변조 없음 증명

12.4 AML 통합 — provider 연동

Fireblocks 는 다음 AML provider 와 통합 가능 (vault → external screening):

  • Chainalysis — KYT (Know Your Transaction)
  • Elliptic — wallet screening + transaction monitoring
  • TRM Labs — risk scoring
  • 기타 — 자체 통합 가능 (Fireblocks API)

★ 트래블룰 = 은행 책임, Fireblocks 가 자동 해결 안 함

Fireblocks 의 Travel Rule policy 는 정책 trigger 까지만 제공. 실제 VASP 간 정보 교환 (IVMS101 message) 은 별도 provider (Notabene / Sumsub 등) 또는 자체 구현 필요. 은행은 (a) 어느 provider 사용, (b) counterparty VASP 식별 매커니즘, (c) self-hosted wallet 출금 시 처리 정책을 정의해야 함.

12.6 외부 감사 / 금감원 대응

정기 외부 감사 (SOC 2 / ISO 27001) 또는 금감원 검사 시 제공 가능한 자료:

  1. Fireblocks Console 의 immutable log — Auditor role 의 read-only access 제공
  2. mirrordb.audit_log_mirror — hash chain 무결성 증명 포함
  3. tx_mirror + tx_status_history — 5년 거래 기록
  4. compliancedb.screening_results — AML 점검 이력
  5. compliancedb.travel_rule_records — 트래블룰 처리 이력
  6. compliancedb.suspicious_tx_review + str_filed — STR 보고 이력
  7. customerdb.recovery_event_log — Backup / Recovery ceremony 이력
  8. reconciliation log — mirror 의 정합성 증명

12.8 archive / partition 운영

  • 30 일 이상 = warm tier (인덱스 일부 활성)
  • 1 년 이상 = cold tier (compressed, archive)
  • 5 년 도래 시 = legal hold 검토 (분쟁 진행 중인 거래는 보존 연장)
  • partition 운영 — 월별 partition 으로 archive 효율
