1. 책임 분담 · Trust Boundary

Fireblocks 와 은행이 각각 무엇을 책임지는가 — 3 product option 별 차이

1.1 핵심 변화 — 직접 구축 대비

직접 구축은 6 가지 시스템 영역 (외부 진입 관문 · 서명 모듈 · 핵심 보안 코어 · 신뢰 공유 · 블록체인 노드 · 재해복구) 을 모두 은행이 운영해야 한다. Fireblocks 도입 시 이 영역 대부분이 Fireblocks 의 책임으로 넘어간다. 은행은 외부와 통신하는 client 와 컴플라이언스 / 사본 (mirror) 보관 영역만 운영.

1.2 3 product option — 키 share 위치별 분류

Fireblocks 는 3 가지 product line 을 제공한다. SaaS MPC 와 Hosted MPC 는 3-party MPC-CMP (?) 프로토콜 (총 3 share · 2-of-3 협력해야 서명 가능). Key Link 는 MPC 가 아닌 단일 HSM 모델.

두 옵션 모두 3-party MPC-CMP (총 3 share · 2-of-3 threshold) 의 동일한 MPC 모델. Cloud 측 2 share 도 동일. 차이는 고객 측 1 share 가 어디에 있는지 뿐이지만, 그 위치 차이가 운영 방식·자동화·망분리에 큰 영향을 준다.

1.3 신뢰 경계 (Trust Boundary)

Fireblocks 도입 시 시스템 영역별로 누가 호스팅하고 무엇을 보관·처리하는가. 영역이 다르면 보안 모델도 다르다 — 한 영역이 침해되어도 다른 영역의 자산은 즉시 노출되지 않게 설계.

영역호스팅 주체보관·처리 자산
Fireblocks SaaS Fireblocks (vendor) Workspace · Vault · Asset Wallet · 정책 / TAP · MPC key share 2 개 (Cloud Co-Signer ×2, SaaS/Hosted 시) · 1차 audit log (변경 불가) · webhook event 발신
플랫폼 은행 customerdb (고객 ↔ Fireblocks 매핑) · 비즈니스 로직 · API 호출자
은행 operationsdb 은행 (a) Fireblocks 사본: webhook 이벤트 · 거래 mirror · audit log mirror · 잔액 snapshot.
(b) 은행 자체 데이터 (Fireblocks 가 모르는 영역): 회계 4 원장 (?) (고객 / 자체 / 델타 / 총계정) · 대사 결과 · 환율 이력 · 외화환산 로그 · 멱등 처리 메타 · 운영 로그 (Hot/Cold 비율 · rebalancing · webhook 실패 등).
(c) 보장: 5 년 보존 + hash chain 변조방지
은행 compliancedb 은행 AML screening 결과 · Travel Rule records · STR (의심거래 보고) 이력 · 금감원 보고 자료
운영자 mobile device 운영자 개인 Fireblocks Mobile app 의 1 of 3 MPC share (SaaS MPC 시 — 운영자 1 인 보유) · PIN · biometric · activation token · refresh token (mobile KeyChain hardware 암호화)
은행 Co-Signer 인스턴스 (Hosted MPC 시) 은행 API Co-Signer (SGX) 의 1 of 3 MPC share · Callback Handler endpoint · CSR private key
은행 HSM (Key Link 시) 은행 실제 키 (전량) · Validation Key · Signing Key · HSM PIN
외부 IdP (SSO 사용 시) 은행 또는 3rd-party (Okta / Entra ID / Google Workspace) SSO 사용자 인증 — Fireblocks 외부의 identity 책임
외부 AML / Travel Rule provider 3rd-party (Chainalysis · Elliptic · TRM Labs · Notabene · Sumsub) address screening · risk score · VASP 간 정보 교환
Blockchain Public (탈중앙) 서명 끝난 transaction 의 broadcast + confirmation
trust boundary 의 핵심 원칙
  • 각 영역 독립 보호 — Fireblocks SaaS 가 침해되어도 은행 mobile MPC share / Hosted Co-Signer share / Key Link HSM 키 가 없으면 서명 불가능
  • 은행 자체 audit 가능 — Fireblocks Console 의 1차 audit log + 은행 operationsdb 의 자체 audit log mirror (hash chain) 으로 분쟁 시 양측 정합성 증명
  • 은행 application 의 자산 직접 손실 위험 제한 — customerdb / operationsdb 는 키 material 보관 안 함. 침해 시 PII / 거래 기록 노출은 별도 위험 (개인정보보호법 / 특금법)

플랫폼 는 (a) REST API 로 Fireblocks 호출 (점선), (b) Fireblocks 가 보내는 webhook 수신 (점선). Fireblocks Core 는 내부 chain (Auth → Policy → Vault → Co-Signer) 을 단일 SGX core 로 단순화 표기 — 상세는 직접 구축 reference 의 14-step flow 참조.

1.6 API key 보안 (은행 책임)

은행이 Fireblocks 와 통신할 때 사용하는 API key + secret 의 보안 책임:

  • secret 은 은행 application 의 secret manager (HashiCorp Vault / AWS Secrets Manager / Azure Key Vault) 에 보관. application DB 에 절대 평문 저장 금지
  • IP allowlist 활용 — API key 별로 허용된 IP 주소만 통신 가능. 플랫폼 의 outbound NAT IP 만 등록 → key 가 유출돼도 허용 IP 가 아니면 호출 차단 (IP allowlist · SSO 설정)
  • 최소 권한 원칙 — 9 가지 role (Owner / Admin / Non-Signing Admin / Approver / Signer / Non-Signing User / Editor / Viewer / Auditor) 별로 분리 발급. 예: read-only 작업 = Viewer role 의 API key 만 사용. 자세한 role 은 7. Roles · Quorum · Policy 참조
  • 주기적 갱신 (로테이션) — Fireblocks 가 자동 강제하지 않으나, 은행 내부 정책으로 분기별 발급/폐기 권장 (저자 추정). 침해 의심 시 즉시 회수

출처: Manage API Keys · Manage Users

★ 절대 은행 DB 에 저장 금지
  • Fireblocks API secret (평문)
  • MPC key share (Hosted MPC 의 Co-signer 가 직접 관리하므로 application 단에 노출되지 않음)
  • Mobile device 의 KeyChain 내용
  • Workspace Keys Backup 의 recovery passphrase
  • HSM PIN / PKCS#11 access token (Key Link 시)
  • Validation Key / Signing Key의 private 부분 (Key Link 시)
