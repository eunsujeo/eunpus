1. 책임 분담 · Trust Boundary

Fireblocks 와 은행이 각각 무엇을 책임지는가 — 3 product option 별 차이

1.1 핵심 변화 — 직접 구축 대비

직접 구축의 6 system component (Shell Services / Transaction Signing Modules / Core Components / Trusted Shared / Blockchain Nodes / Disaster Recovery) 의 대부분이 Fireblocks 가 책임으로 넘어간다. 은행은 외피 (Fireblocks 와 통신하는 client + webhook 수신) 와 compliance / mirror 영역만 운영.

Component (직접 구축)Fireblocks 도입 시
Shell Services (API gateway, tx routing)✅ Fireblocks SaaS 가 운영. 은행은 SDK / REST API 호출자
Transaction Signing Modules (Co-signers, MPC key share)✅ Fireblocks 책임 (option 별 차이 — SaaS MPC / Hosted MPC / Key Link)
Core Components (Auth Engine, Policy Engine/TAP, Secure Vault, Co-Signer Engine)✅ Fireblocks SGX 가 운영. 은행은 Console / API 로 정책 설정만
Trusted Shared Services (P2P Network)✅ Fireblocks Network 활용. 은행은 counterparty 등록만
Blockchain Nodes✅ Fireblocks node infrastructure 활용
Disaster Recovery (xprv / fprv 재구성)✅ Fireblocks 가 backup 매커니즘 제공 (Workspace Keys Backup). 은행은 recovery passphrase 보관 + 회복 ceremony 수행

1.3 신뢰 경계 (Trust Boundary)

Fireblocks 도입 시 은행 시스템의 trust boundary 가 어떻게 재정의되는가.

영역호스팅 주체보관·처리 자산

각 영역이 독립적으로 침해되어도 다른 영역은 자체 보호. 예 — Fireblocks SaaS 가 침해되어도 은행 mobile device 의 MPC share 또는 Key Link 의 HSM 키가 없으면 서명 불가능. 은행이 운영하는 customerdb / mirrordb 는 키 material 을 보관하지 않으므로, 침해 시 자산 직접 손실 risk 가 제한적 (단 PII / 거래 기록 노출은 별도 risk).

1.6 API key 보안 (은행 책임)

은행이 Fireblocks 와 통신할 때 사용하는 API key + secret 의 보안 책임:

  • secret 은 은행 application 의 secret manager (HashiCorp Vault / AWS Secrets Manager / Azure Key Vault) 에 보관. application DB 에 절대 평문 저장 금지
  • IP allowlist 활용 — API key 별로 허용된 IP 만 통신 가능 (IP allowlist · SSO 설정)
  • 최소 권한 원칙 — Editor / Admin / Signer / Viewer / Non-Signing Admin 등 role 별 분리. read-only 작업은 Viewer role 의 API key
  • 로테이션 — Fireblocks 가 자동 로테이션 강제하지 않으나, 은행 내부 정책으로 분기별 갱신 권장 (저자 추정)

출처: Manage API Keys · Manage Users

★ 절대 은행 DB 에 저장 금지
  • Fireblocks API secret (평문)
  • MPC key share (Hosted MPC 의 Co-signer 가 직접 관리하므로 application 단에 노출되지 않음)
  • Mobile device 의 KeyChain 내용
  • Workspace Keys Backup 의 recovery passphrase
  • HSM PIN / PKCS#11 access token (Key Link 시)
  • Validation Key / Signing Key의 private 부분 (Key Link 시)
