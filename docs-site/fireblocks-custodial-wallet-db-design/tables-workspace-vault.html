파랑 customerdb: 채널계 read 동선 — 고객 vault → asset wallet → deposit address. 노랑 operationsdb: 관리 콘솔 / 운영자 read 동선 — 운영 vault 라인 + 자산 master. 보라 config: workspace 메타는 DB 가 아니라 application config (Hot + Cold 2 entry). vault 의 workspace_code 가 config key 참조. 초록 asset_catalog: 자산 단위 master — operationsdb 거주. ops_asset_wallet 은 강 FK, customer_asset_wallet 은 cross-DB 점선 (자산 list 는 read-rare 라 cache 충분).

실선 (강 FK) vs 점선 (논리 FK) 의 운영적 함의
  • 실선 — vault → asset_wallet → deposit_address 는 동일 DB 안에 모이도록 설계. cascade delete · FK 무결성 · join 단순성 모두 RDB 가 강제.
  • 점선 — config → vault, asset_catalog → customer_asset_wallet. config 참조는 application 부팅 시 로드 (정적). asset_catalog 의 cross-DB 점선은 자산 list 가 거의 변하지 않아 application layer cache 로 충분.

4.2 Workspace — 은행 매핑

Workspace 는 Fireblocks 의 격리·거버넌스 단위. 은행은 KR 규제 + Cold 분리 요건상 최소 Hot + Cold 2 개 로 시작 (필요 시 Operational / Testnet 등 분리 확장).

은행 초기 workspace 구성 (2 개)

#WorkspaceTypeNetwork역할Approval Group
1HotHot (SaaS / Hosted / Key Link 중 택일)Mainnet고객 자산 working balance (≤ 20%) + 일일 입출금 + gas station + sweeping + admin 작업지원
2ColdCold (별도 product)Mainnet고객 자산 bulk reserve (≥ 80%) — KR 가상자산업감독규정 9조미지원 — Admin Quorum 단독

출처: Fireblocks Vault Structure Best Practices (4-5 workspace 분리 권장은 별도 운영 단계로 확장 시 적용) · 은행 Fireblocks Cold Wallet 도입

Cold Wallet workspace 는 별도 product

Cold workspace 는 SaaS MPC 의 단순 "type 옵션" 이 아니라 별도 구매 product. Hot workspace 와 인프라 · 거버넌스 · 가격이 별개. Approval Group 미지원 (Admin Quorum 단독, Risk-G07) · User add 시 Fireblocks Support 매개 필수 · Mobile-only user 사용 등 특수 운영. 상세는 5. Cold Wallet 운영 참조.

Workspace 메타는 DB 가 아니라 config 로 관리

Workspace 는 2 개 (Hot + Cold) 로 고정되고 거의 변하지 않음 (workspace_type 은 set-once, owner / console_url 도 변경 빈도 매우 낮음). 정규화된 DB 표 (workspace_link) 대신 application config 로 관리하면 표 1 개 절감 + cross-DB FK 부담 사라짐. 

# config/workspaces.yaml (예시)
workspaces:
  hot:
    vendor_workspace_id: "ws-abc-123"           # Fireblocks 발급 UUID
    workspace_type: saas_mpc                    # saas_mpc / hosted_mpc / key_link
    network: mainnet
    purpose: "고객 자산 working balance (≤ 20%) + 운영 + gas station"
    vendor_owner_user_id: "user-xxx"
    console_url: "https://console.fireblocks.io/v2/.../ws-abc-123"
    approval_group: enabled

  cold:
    vendor_workspace_id: "ws-def-456"
    workspace_type: cold                        # 별도 product
    network: mainnet
    purpose: "고객 자산 bulk reserve (≥ 80%) — 가상자산업감독규정 9조"
    vendor_owner_user_id: "user-yyy"
    console_url: "https://console.fireblocks.io/v2/.../ws-def-456"
    approval_group: disabled                    # Admin Quorum 단독

DB 의 vault 표는 workspace_code string 컬럼 ("hot" / "cold") 으로 config key 를 참조. FK 무결성은 application 이 enum check 으로 강제. workspace 가 늘어나면 config 만 수정 (코드 / schema 변경 없음).

★ workspace_type 은 set-once

Fireblocks 공식: "modifying an existing SaaS MPC workspace is impossible" (Hosted MPC Workspace Configuration). 한 번 workspace 생성 시 결정된 type 은 영구히 변경 불가. config 도 set-once 로 다루며, 변경은 새 workspace 신설 후 전환 (deploy 통한 audit).

4.3 Vault Account — 고객 단위 격리

Vault Account 는 자산 보관의 격리 단위. 은행은 (a) 고객 1 인 = vault 1 개 (segregated) 또는 (b) 자산군 별 omnibus vault 중 선택.

★ Fireblocks vault account 는 삭제 불가

Fireblocks 공식 동사: create / rename / hide / unhide / asset wallet 추가. delete 동사 없음 — 자산 보호 + audit log 보존 + 회계 정합성 위해 vault 는 영구 보존.
hide 의 목적: 사용자 수 증가로 vault 가 많아지면 Console dashboard 가 느려질 수 있어 UI 성능 위해 hide 처리. 자산 / history 는 그대로 보존되며 API 로는 계속 조회 가능.

Sweep-to-omnibus: 노랑 = 사용자별 입금 vault → 보라 = Intermediate (중간 집결) → 초록 = Omnibus (통합 보관) → 빨강 = Withdrawal pool (출금 전용). 분홍 = Gas Station (자동 가스 공급, EVM 체인의 입금 vault 에 fee 공급).
우측 Segregated: 파랑 = 고객별 1 vault. 각 vault 안에 자산별 wallet (BTC · ETH · USDC) 분리.
대량 사용자 (Retail) → Sweep-to-omnibus / 고액 institutional 고객 → Segregated. 한 은행이 두 패턴 동시 운영 가능 — 데이터 모델에서는 고객 vault 와 운영 vault 를 두 표로 분리 (아래 customer_vault · ops_vault 참조).

출처: Fireblocks Vault Structure Best Practices · Work with Gas Station

Vault 표 2 분할 — 운영 단위 분리 — Fireblocks API 상 vault 는 한 종류 객체지만, 은행은 두 가지 의미로 사용:
  • customer_vault — 고객 자산 vault (customer_segregated). 고객 KYC · 회계 customer_ledger · 채널계 조회 권한과 연결.
  • ops_vault — 은행 자체 운영 vault (omnibus / intermediate / withdrawal_pool / gas_station / treasury). 운영자 quorum · bank_ledger · 관리 콘솔 권한과 연결.
두 표는 lifecycle / 권한 / 회계 매핑이 달라 분리. 은행 측 PK 에 prefix (cv_ / ov_) 를 두어 ID 만 봐도 어느 표인지 식별 가능.

Webhook 라우팅 — vault_index 없이 어떻게?
  • 은행 측 PK 흐름: PK 자체에 cv_ / ov_ prefix 가 있어 application 내부에서 vault ID 만 보면 어느 DB / 어느 표인지 즉시 결정.
  • Fireblocks webhook 흐름: webhook 은 vendor_vault_id 만 들고 옴 → application 이 try-customer-first (고객 vault 가 압도적 다수) → 없으면 ops_vault fallback. 평균 1 query, worst case 2 query. 핫 캐시 (vendor_vault_id → vault_kind) 추가 시 평균 0 에 가까움.
  • UNIQUE 보장: vault 생성 시 application 이 두 표 모두 vendor_vault_id 점검 후 INSERT. 생성 빈도가 webhook 보다 훨씬 낮아 비용 미미.
Hide / unhide 이벤트 시점 추적 — is_hidden 은 현재 상태만 표현하고, "언제 hide 했는지 / 언제 다시 unhide 했는지" 이력은 operationsdb.audit_log_mirror 에 보관 (Fireblocks 발생 동작). hide 는 자주 일어나는 동작이 아니라 별도 column 으로 두지 않아도 audit log mirror 의 vault 변경 entry 로 충분히 역추적 가능.

4.4 Asset Wallet — 자산별 등록

한 vault 안에 자산별로 asset wallet 을 생성. Fireblocks 는 1,800 + 종 자산 지원.

Asset Wallet 도 vault 따라 동일 DB 분리 — 부모 vault 가 두 DB 로 분리되었으므로 자식 asset_wallet 도 부모와 같은 DB 에 둠. 이렇게 하면 vault → asset_wallet FK 가 동일 DB 안의 RDB foreign key 로 강제되어 무결성 보장.

operationsdb.asset_catalog — 자산 단위 master

Fireblocks 는 1,800 + 자산을 카탈로그로 미리 지원. 은행은 그중 어떤 자산을 실제 서비스로 노출할지 자산 단위 master 로 관리 (전 고객 공통). 신규 자산 도입 / 입금만 허용 (출금 차단) / 운영 종료 같은 lifecycle 상태가 여기에 모임.

거래 승인 정책 (TAP — 한도 · quorum · signer 등) 은 다른 의미의 "policy" 이며 7. Roles · Quorum · Policy 에서 다룸. 본 표는 그 정책의 적용 대상이 되는 자산 master.

4.5 Deposit Address — UTXO vs Account-based

Asset Wallet 안에 deposit address 가 생성됨. 자산 유형에 따라 개수가 다르다:

  • UTXO (?) 체인 (BTC, LTC 등): 다중 deposit address 가능. 새 입금마다 새 주소 발급 가능 (privacy + 분리 입금 추적)
  • Account-based (?) 체인 (ETH, SOL, ...): 단일 deposit address. 한 asset wallet = 한 주소

One-time vs Permanent address

  • Permanent: deposit address 가 영구 보관, 여러 번 입금 수신. 회계 / 추적 단순
  • One-time: 한 번만 사용 가능, 입금 후 폐기 (privacy 향상). 입금 별 별도 주소로 추적 용이

4.6 Counterparty Registry — 외부 송금 대상

Counterparty (거래 상대방) = 은행이 송금하거나 송금받는 외부 대상. 종류:

  • Whitelisted address — 화이트리스트로 등록된 외부 wallet 주소 (예: 고객의 외부 wallet · 파트너 회사)
  • External wallet — 외부 자산 보관 wallet 의 매핑 (Fireblocks 외부)
  • Exchange account — 외부 거래소 계좌 (Binance · Coinbase 등)
  • Network connection — Fireblocks Network 의 다른 고객사 (chain 우회 즉시 송금 가능한 P2P 망)
  • Fiat account — 외부 fiat 계좌 (은행 송금 / SWIFT 등)
★ 모든 counterparty 등록은 Admin Quorum 매개 (사전 승인)

외부 송금 대상의 등록은 거래 위험의 진입점. 잘못 등록된 counterparty 로 송금하면 자산 회수 불가 (블록체인의 비가역성). 모든 counterparty 등록 / 회수는 Admin Quorum 매개 (mobile app 승인) 필수. 일부 종류 (whitelisted address · internal wallet) 는 Approval Group 위임 가능 (Add Validation Keys 와 같은 패턴). AML provider 사전 screening 도 권장 — 등록 전에 high-risk address 차단.

4.7 Vault → Customer 매핑의 권장 패턴 (저자)

은행 customerdb 의 매핑 패턴:

  • segregated 패턴 — customer_vault 에 1 행 = 1 고객 (bank_customer_id NOT NULL 강제). 고객 ID 가 표 단위로 보장되어 회계 정합성 ↑
  • omnibus 패턴 — ops_vault 의 vault_purpose = 'omnibus' 행 1 개에 다수 고객 자산 통합 + 별도 customer_balance_subledger 표에 고객별 잔액 mirror. 회계 시스템 통합
  • 혼합 패턴 — Retail (omnibus → ops_vault) + Institutional (segregated → customer_vault) 동시 운영. 표 분리 자체가 패턴 분리를 표현하므로 application layer 의 조건 분기 부담 ↓
omnibus vault 의 KR 컴플라이언스 함의 (저자)

omnibus 패턴 시 은행 내부 회계로 고객별 잔액을 분리 관리하더라도, on-chain 에는 1 vault 의 통합 balance 만 표시됨. 대법원 2024도10710 의 "실질 통제" 판단 시 한 vault 안의 자산이 누구의 통제권에 있는지 명확히 구분되어야 함. 은행은 customer_balance_subledger 의 무결성 (audit log 와 정합성) 을 별도로 증명할 책임.

customer_balance_subledger 는 15. 회계 · 원장 설계 의 고객 원장 (4 원장의 ①) 과 같은 영역. hash chain 변조방지 + 정기 reconciliation 은 16. 대사 · 결산 · 마감 의 L1 / L2 대사 참조.
