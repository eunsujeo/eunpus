초록 asset_catalog: 자산 단위 master — ops domain 거주. ops_asset_wallet 은 강 FK (동일 schema), customer_asset_wallet 은 cross-schema 점선 (자산 list 는 read-rare 라 cache 충분 — PostgreSQL 에서 cross-schema FK 강제도 가능).

실선 (강 FK) vs 점선 (논리 FK) 의 운영적 함의
  • 실선 — vault → asset_wallet → deposit_address 는 동일 schema (customer 또는 ops) 안에 모이도록 설계. cascade delete · FK 무결성 · join 단순성 모두 RDB 가 강제.
  • 점선 — config → vault, asset_catalog → customer_asset_wallet. config 참조는 application 부팅 시 로드 (정적). asset_catalog 의 cross-schema 점선은 자산 list 가 거의 변하지 않아 application layer cache 가 합리적 (PostgreSQL 에서는 cross-schema FK 강제도 가능 — schema 단일성 우선 시 적용).

4.3 Workspace — 은행 매핑

본 reference 가 가정하는 운영 단계

Workspace 는 Fireblocks 의 격리·거버넌스 단위. 본 reference 는 수십만 사용자 + 성숙 서비스 (정식 오픈) 시나리오를 가정. 이 단계에서는 Administrative / Operational 분리가 필요 (아래 trigger 6 가지 중 다수 부합). 따라서 권장 구성은 4 workspace — Administrative + Operational + Custodial (Hot) + Cold.

4.3.1 본 reference 권장 workspace 구성 (4 개)

#WorkspaceTypeNetwork역할Approval Group
1AdministrativeHot (SaaS / Hosted / Key Link 중 택일)Mainnet정책 변경 / 운영자 role 부여 / smart contract / counterparty 등록 — 빈도 낮고 위험 높은 작업 전용지원 (strict quorum)
2OperationalHotMainnet일일 입출금 · sweeping · gas station — 자동화된 일상 운영 전용지원
3Custodial (Hot)HotMainnet고객 자산 working balance (≤ 20%)지원
4ColdCold (별도 product)Mainnet고객 자산 bulk reserve (≥ 80%) — KR 가상자산업감독규정 9조미지원 — Admin Quorum 단독

출처: Fireblocks Vault Structure Best Practices (4-5 workspace 분리 권장은 별도 운영 단계로 확장 시 적용) · 은행 Fireblocks Cold Wallet 도입

Cold Wallet workspace 는 별도 product

Cold workspace 는 SaaS MPC 의 단순 "type 옵션" 이 아니라 별도 구매 product. Hot workspace 와 인프라 · 거버넌스 · 가격이 별개. Approval Group 위임 미지원 → 모든 결정이 Admin Quorum 전체 동의 (Cold 거버넌스 위험 — AQ 1 명 부재만으로도 governance halt) · User add 시 Fireblocks Support 매개 필수 · Mobile-only user 사용 등 특수 운영. 상세는 7. Cold Wallet 운영 참조.

4.3.2 왜 Administrative / Operational 을 분리하는가 — 4 가지 이유

초기에는 둘이 같은 Hot workspace 안에 섞여 있어도 작동하지만, 사용자 수 / 거래량이 커지면 분리 권장 (Fireblocks Vault Structure Best Practices):

  • ① Blast radius 축소 — Administrative 의 정책 변경 / smart contract upgrade 작업 중 실수가 일상 입출금 (Operational) 으로 전파되지 않음. 한 workspace 의 사고가 다른 workspace 의 자산까지 위험하게 만들지 않도록 격리.
  • ② Approval flow 차등 — Administrative 는 빈도 낮고 위험 높음 → strict quorum + 많은 승인자. Operational 은 빈도 높고 자동화 필요 → 간소화된 policy + 자동 승인. 한 workspace 안에 두 flow 가 섞이면 policy 가 복잡해지고 운영 속도가 느려짐.
  • ③ Role / 권한 분리 — 정책 변경자 (Editor / Admin) 와 일상 운영자 (Signer) 의 권한이 다름. workspace 분리 시 권한이 자연스럽게 분리되어 audit clarity ↑.
  • ④ Audit / 사고 분석 — 두 종류의 변경이 한 audit log 에 섞이면 사고 발생 시 원인 추적이 어려움. workspace 분리 시 각 audit log 가 한 종류의 작업만 담아 forensics 단순화.

4.3.3 수탁형 지갑에서 Administrative 분리가 필요해지는 6 가지 trigger

Administrative 분리 여부는 일률적인 답이 아니라 운영 시나리오에 따라 결정. 본 reference 가 가정하는 성숙 서비스는 아래 trigger 중 다수가 부합하여 분리 필요.

#Trigger해당 작업분리 사유
1신규 자산 / 체인 도입이 잦음 (분기 1-2 회 이상)asset_catalog.support_status 추가, Fireblocks 측 asset enable, gas station 설정자산 추가는 전 고객 영향 + 회계 / 규제 사전 검토 필요. Operational 과 한 workspace 면 검토 흐름이 audit log 에 섞여 추적 어려움
2TAP policy 변경 빈도 ↑ (분기 정책 검토)출금 한도 / quorum 임계 / signer 변경, AML 한도 조정, KYT rule 갱신정책 변경 = high-risk (잘못된 정책이 자산 노출 직결). strict 변경 절차와 자동화 일상 운영이 충돌
3Smart contract / DeFi / Staking 서비스 운영contract deploy / upgrade, validator key 관리, mint authority 행사contract 운영 = 가장 위험한 trigger (한 번의 deploy 실수가 전체 고객 자산 영향). 일상 운영 정지 risk 격리 필요
4Whitelisted Counterparty 등록 빈도 ↑ (트래블룰 시행으로 월 N 건)whitelisted_destinations 신규 등록, AML 사전 screening, Admin Quorum 승인counterparty 등록은 한 번 잘못되면 자산 회수 불가 (블록체인 비가역성). 일상 운영자 실수 risk 차단 필요
5운영자 turnover 가 큼 (디지털 자산팀 수십 명 규모)신규 운영자 user add, role 승급 / 강등, 퇴사 시 user delete + key 회수권한 부여 = HR / 보안팀 매개 결정. Admin workspace 에서 strict 검증 후 Operational 운영자는 read-only 또는 signer 권한만
6키 share / Co-signer 변경 ceremony (Hosted MPC / Key Link 운영 시)키 share rotation, 새 cosigner enclave 등록, Validation Key 등록 (Key Link), mobile device migration 같은 거버넌스 ceremony (Admin Quorum 매개)키 / signer 의 등록 / 변경 ceremony 는 Admin Quorum 승인이 필요한 거버넌스 작업이라 Administrative workspace 에서 strict 절차로 분리. 일상 운영자가 같은 workspace 에서 다루면 ceremony 사고 시 일상 입출금까지 영향

4.3.4 수탁형 지갑에서 Operational 분리가 필요해지는 5 가지 trigger

Administrative 분리는 "high-risk 작업 격리" 관점, Operational 분리는 "high-volume / 자동화 운영 격리" 관점. 두 종류의 trigger 는 서로 다르며, 다수 부합 시 별도 workspace 권장.

#Trigger해당 작업분리 사유
1일일 거래량 / TPS 증가 (수만 건 이상)입금 detection · 출금 broadcast · sweeping batch · webhook 처리Admin 의 정책 변경 시 workspace 일시 정지 / API rate limit 영향이 일상 입출금에 전파됨. Operational 분리 시 Admin 작업이 일상에 영향 없음
2Sweep-to-omnibus 자동화 (대량 사용자 retail 운영)사용자별 입금 vault → Intermediate vault → Omnibus vault sweep batch, daily 자동 실행sweeping = 빈도 높고 자동화된 signing. Admin 의 strict quorum 정책과 한 workspace 면 batch 가 매번 검토 대기. 자동 흐름 격리 필요
3Gas Station 자동 연료 공급 (EVM chain 다수 운영)입금 vault 의 gas (ETH / MATIC 등) 부족 detection → 자동 fee 공급Gas Station 은 24/7 routine 자동화. Admin 의 unscheduled 정책 변경에 영향 받으면 입금 처리 실패 → 고객 입금 지연
4다수 API user / 시스템 통합 (채널계 / 정산계 / 회계계 등 backend 다수)system 별 API key + 권한 정책 분리, IP allowlist 별도 운영Operational workspace 에 시스템 API key 모으면 권한 / 정책이 단순. Admin workspace 와 한 곳에 두면 사람 권한 + 시스템 권한 혼재로 audit clarity ↓
524/7 무중단 SLA (정식 서비스 오픈 후)일상 입출금이 SLA 보장 대상Admin workspace 의 정책 변경 / cosigner update / counterparty 등록 등은 일시적 정지 가능. 일상 운영과 같은 workspace 면 SLA 위반 risk. 분리하면 Admin 정지 ≠ 일상 정지

4.3.7 Workspace 메타는 DB 가 아니라 config 로 관리

Workspace 는 4 개로 고정되고 거의 변하지 않음 (workspace_type 은 한 번 결정되면 변경 불가, owner / console_url 도 변경 빈도 매우 낮음). 정규화된 DB 표 (workspace_link) 대신 application config 로 관리하면 표 1 개 절감 + 모든 schema 에서 동일하게 참조 가능. 

# config/workspaces.yaml (예시)
workspaces:
  admin:
    vendor_workspace_id: "ws-admin-001"         # Fireblocks 발급 UUID
    workspace_type: saas_mpc                    # saas_mpc / hosted_mpc / key_link
    network: mainnet
    purpose: "정책 변경 / role 부여 / counterparty 등록 — strict quorum"
    vendor_owner_user_id: "user-aaa"
    console_url: "https://console.fireblocks.io/v2/.../ws-admin-001"
    approval_group: enabled

  ops:
    vendor_workspace_id: "ws-ops-002"
    workspace_type: saas_mpc
    network: mainnet
    purpose: "일일 입출금 / sweeping / gas station — 자동화 일상 운영"
    vendor_owner_user_id: "user-bbb"
    console_url: "https://console.fireblocks.io/v2/.../ws-ops-002"
    approval_group: enabled

  hot:
    vendor_workspace_id: "ws-hot-003"
    workspace_type: saas_mpc
    network: mainnet
    purpose: "고객 자산 working balance (≤ 20%)"
    vendor_owner_user_id: "user-ccc"
    console_url: "https://console.fireblocks.io/v2/.../ws-hot-003"
    approval_group: enabled

  cold:
    vendor_workspace_id: "ws-cold-004"
    workspace_type: cold                        # 별도 product
    network: mainnet
    purpose: "고객 자산 bulk reserve (≥ 80%) — 가상자산업감독규정 9조"
    vendor_owner_user_id: "user-ddd"
    console_url: "https://console.fireblocks.io/v2/.../ws-cold-004"
    approval_group: disabled                    # Admin Quorum 단독

DB 의 vault 표는 workspace_code string 컬럼 ("admin" / "ops" / "hot" / "cold") 으로 config key 를 참조. FK 무결성은 application 이 enum check 으로 강제. workspace 가 늘어나면 config 만 수정 (코드 / schema 변경 없음).

★ workspace_type 은 한 번 결정되면 변경 불가

Fireblocks 공식: "modifying an existing SaaS MPC workspace is impossible" (Hosted MPC Workspace Configuration). 한 번 workspace 생성 시 결정된 type 은 영구히 변경 불가. config 도 한 번 설정 후 변경하지 않으며, 변경은 새 workspace 신설 후 전환 (deploy 통한 audit).
