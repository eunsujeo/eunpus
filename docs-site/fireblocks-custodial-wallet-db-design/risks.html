11. Risks Register

Fireblocks 도입으로 새로 추가되는 risk + 완화 방안

FB-R01 — Vendor Lock-in

위협: 모든 vault / 거래 / governance 가 Fireblocks 에 종속. 다른 vendor 로 마이그레이션 시 모든 자산을 새 wallet 으로 on-chain transfer 필요.

  • 원인: workspace type immutable + 키 share 가 Fireblocks 의 보안 매커니즘에 종속
  • 영향: 마이그레이션 비용 = on-chain fee + 운영 시간 + 사용자 영향
  • 완화:
    • 도입 전 multi-vendor 검토 (BitGo / Anchorage / Hex Trust 등)
    • 마이그레이션 plan 사전 수립 (한 번에 전체 vs 단계적)
    • Key Link option 선택 시 lock-in 완화 (HSM 자체는 다른 platform 에서도 사용 가능)

FB-R02 — Fireblocks SaaS Outage

위협: Fireblocks SaaS 장애 = 은행 거래 처리 중단. 직접 구축에는 없는 새 종속성.

  • 완화:
    • Fireblocks Status page 모니터링 (status.fireblocks.com 또는 유사 endpoint)
    • BCP — 장애 발생 시 사용자 응답 시간 SLA 사전 정의 (예: 4 시간 지연 시 알림)
    • 거래 큐잉 — 장애 중 접수된 출금 신청은 큐에 보관, 정상화 후 처리
    • Fireblocks SLA 협의 — 계약 시 가용성 보장 + 위약금 조항
    • 오프라인 ceremony 절차 (Key Link Cold mode 활용 시 일부 거래 처리 가능)

FB-R03 — Webhook 손실 / Delay

위협: Webhook 누락 시 mirrordb 가 Fireblocks Console 과 불일치 → audit 정합성 깨짐.

  • 완화:
    • 일일 reconciliation — API 로 transaction list 조회 후 mirror 와 대조
    • Fireblocks 의 webhook retry 정책 활용
    • endpoint HA 구성 (Active-Active load balancer)
    • webhook delay metric monitoring (p99 alert)
    • missing event 자동 backfill 절차

FB-R04 — API Key 도난

위협: API key + secret 이 노출되면 공격자가 임의 거래 시작 가능 (단 TAP 정책 + 서명 단계가 추가 보호).

  • 완화:
    • secret manager 만 사용 — DB / log / 코드 commit 금지
    • IP allowlist — 은행 application server 의 NAT IP 만
    • 최소 권한 — Viewer / Editor / Signer / Admin role 분리
    • 정기 rotation (분기별 권장)
    • API call 이상 detection (volume / source IP / time-of-day)
    • secret 사용 audit — 어떤 application 이 어떤 key 사용 중인지 inventory

FB-R05 — Recovery Passphrase 분실 / 침해

위협 (치명적): Mobile device 또는 Co-signer 분실 + passphrase 도 분실 = 자산 영구 손실. 반대로 passphrase 노출 = 자산 단독 탈취 가능 (SPOC).

  • 완화:
    • Multi-custodian split — Shamir's Secret Sharing 으로 3-of-5 분할. 한 custodian 의 분실 / 침해로 전체 손실 / 노출 안 됨
    • 물리 vault 보관 (sealed envelope · safe deposit box)
    • 분기별 recovery drill — testnet workspace 에서 실제 복원 절차 검증
    • custodian 의 신원 / 권한 분리 (보안팀 ≠ 운영팀)
    • passphrase 사용 시 ceremony (외부 감사인 참관 + 녹화)

FB-R06 — Vendor API Breaking Change

  • 위협: Fireblocks SDK / API 의 breaking change 로 은행 application 호환성 깨짐
  • 완화:
    • SDK version pinning
    • Fireblocks change log 정기 review
    • vendor 의 deprecation notice 추적 (보통 90일 사전 공지)
    • sandbox workspace 에서 새 version pre-test
    • 특히 Beta API (Key Link) 는 production 적용 전 충분한 검증 (Key Link Risk-KL03)

FB-R07 — Vendor 측 침해

위협: Fireblocks SaaS 자체가 침해되는 경우. MPC 의 보안 모델 덕에 자산 직접 손실 risk 는 낮으나, 운영 중단 / governance 침해 가능성.

  • 자산 직접 손실: 낮음 — MPC 의 3-party 모델 (Fireblocks Cloud + 은행 mobile + Cloud Co-signer) 에서 Fireblocks Cloud 단독 침해로 키 추출 불가
  • 운영 중단: 가능 — Console / API 접근 불가
  • Governance 침해: 가능 — 공격자가 정책 변경 / Whitelisted address 추가 시도. 단 Admin Quorum mobile 승인 + 2FA 가 추가 방어
  • 완화: Hosted MPC / Key Link option 으로 Fireblocks 의존 비율 축소. Mobile device 의 strong 2FA / biometric

FB-R08 — KR 컴플라이언스 의무 Vendor 미보장

위협: 가상자산이용자보호법 / 특금법 / 가상자산업감독규정의 의무는 은행에 부과. Fireblocks 가 자동 보장하지 않음.

  • 5년 보존 (특금법 5조의4) — Fireblocks 의 retention 정책 확인 + 자체 mirror
  • 콜드월렛 80% (감독규정 9조) — Fireblocks 가 비율 자동 monitoring 안 함. 은행이 자체 monitor
  • 실질 통제 (대법원 2024도10710) — option 선택의 함의 (Key Link 가 가장 강함)
  • STR 보고 / 트래블룰 — 은행 책임. provider 연동은 도와줄 수 있지만 의무 수행 자체는 은행
  • 완화: 별도 reference 국내 블록체인 사업 법규 × Fireblocks 의 17 의무 매핑 참조

FB-R09 — KR 관할 명시 vs 미명시

  • 위협: Fireblocks 공식 블로그 (2025-09-23 Thales 파트너십) 가 HKMA · HKSFC · JFSA 만 명시. KR 미명시
  • 영향: vendor 보증 없이 KR 환경 도입 시 risk 부담을 은행이 단독으로 짊어짐
  • 완화:
    • Fireblocks Sales / Legal 과 직접 협의 — KR 공식 statement 확보
    • 계약 조항에 KR 관할 적용 + 위약금
    • 금감원 사전 검토 / 신고 / 인허가 절차 확인

FB-R10 — 비용 증가

  • 위협: Fireblocks 의 가격 정책이 워크스페이스 / 거래량 / 자산 가치에 의존. 사업 확장 시 비용 증가
  • 완화:
    • 요금제 모델 사전 분석 (자산 가치 / 거래량 / vault 수 등)
    • 임계 alarm (예: 월 비용이 X 초과 시 alert)
    • 장기 계약 시 가격 cap 협의
    • 대안 option (자체 Cold storage 등) 의 비용 비교

11.3 잔류 risk — 도입 후에도 동일하게 남는 risk

  • 고객 정보 (PII) 유출 — customerdb 의 운영 책임
  • KR 법규 의무 위반 — 도입 후에도 은행 책임
  • 블록체인 자체 risk — 51% 공격 · chain reorg · smart contract 취약점
  • 외부 counterparty risk — whitelisted address 의 진위 / 사기 / 환수
  • 내부 직원 부정 — Admin Quorum 매개로 완화 가능하나 0 은 아님
  • 법규 변경 risk — KR 가상자산이용자보호법 후속 시행령 / 감독규정 변경
