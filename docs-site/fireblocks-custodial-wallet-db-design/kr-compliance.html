13.3 핵심 4 항목 — 도입 시 운영 절차

13.3.1 콜드월렛 80% (감독규정 9조)

  1. Cold Wallet workspace 설치 + 별도 구매 (vendor 협의)
  2. 이용자 자산의 대부분 (80-85% 목표) 을 Cold workspace 로 입금
  3. 일일 Hot/Cold 비율 monitoring (mirrordb.hot_cold_ratio_daily)
  4. 임계 도달 시 자동 alert + rebalancing trigger
  5. 월간 compliance report — 금감원 / 외부 감사 대응

상세: 5. Cold Wallet 운영

13.3.2 5년 보존 (특금법 5조의4)

  1. 모든 webhook event 를 mirrordb.webhook_events 에 append-only 보존
  2. tx_mirror · tx_status_history · audit_log_mirror 의 partition 운영 (월별)
  3. 30 일 이상 = warm tier, 1 년 이상 = cold tier (compressed archive)
  4. 5 년 도래 시 legal hold 검토 후 detach
  5. hash chain 으로 변조 방지 (audit_log_mirror)

상세: 12. Audit · AML · Travel Rule

13.3.3 트래블룰 (시행령 10조의10)

  1. 출금 요청 시 KRW 환산 100만원 이상 검증
  2. 해당 시 Travel Rule provider (Notabene · Sumsub · TRP) 통합
  3. 송신자 / 수신자 정보 교환 (IVMS101 / TRP 형식)
  4. compliancedb.travel_rule_records 에 기록
  5. self-hosted wallet 출금 시 별도 처리 정책 (vendor / 은행 협의)

출처: Define Travel Rule Policies · Validate Full Travel Rule Transaction

13.3.4 실질 통제 (대법원 2024도10710)

MPC / 멀티시그 환경에서 누가 "실질 통제" 권을 가지는지의 판단 기준.

  • 판단 기준 (저자 정리): 단순 키 보유가 아니라 실제 거래 서명 / 거부 권한 행사 가능성
  • option 별 강도:
    • Key Link: 가장 강함 (키 share 0, HSM 단독 운영, Fireblocks 가 단독 서명 불가)
    • Hosted MPC: 중 (Co-signer 1 + Cloud 1 + Mobile 1)
    • SaaS MPC: 약함 (Cloud 1 + Cloud Co-signer 1 + Mobile 1, 은행 mobile 만이 고객 측)
  • 완전 자체 통제 주장 가능 시나리오: Key Link + 은행 HSM + 망분리 IDC + Customer Server 의 자체 정책 적용
  • 법무팀 검토 필수: 판례의 사실관계와 본 architecture 의 비교

상세: Enforcement Defense — 종합검사 사례 분석

13.4 종합검사 사례 분석 (4 사건)

KR 4 대 거래소 (두나무 · 코빗 · 빗썸 · 코인원) 의 금감원 종합검사 사례에서 발견된 주요 위반 항목과 Fireblocks 도입 시 완화 가능성.

위반 항목해당 거래소Fireblocks 도입 시 완화
콜드월렛 비율 미달다수✅ Cold Wallet workspace + 일일 monitor
STR 보고 지연다수⚠️ AML provider 통합 + 은행 review 절차 강화
트래블룰 미적용다수⚠️ Travel Rule policy + provider 통합
고객 자산 분리 보관 미흡일부✅ Vault Account 별 segregated 또는 strict subledger
internal control 미비다수✅ Admin Quorum · Approval Group · TAP / Policy rule
audit log 무결성 부족일부✅ Fireblocks immutable log + 은행 hash chain mirror

13.5 KR VASP 신고 + Fireblocks 도입 통합 절차

  1. Phase 1 (3-6 개월) — VASP 신고 자료 준비 + Fireblocks Sales 협의
    • ISMS 인증 보유 또는 진행
    • 실명확인 입출금계정 협의 (은행 vs 비은행 경로)
    • Fireblocks 와 KR 관할 공식 입장 확보 (Q-FB03)
    • option 선택 (SaaS MPC / Hosted MPC / Key Link)
  2. Phase 2 (2-3 개월) — 인프라 구축 + Sandbox 검증
    • 망분리 IDC 구축 (인프라 페이지 참조)
    • Sandbox workspace 에서 Fireblocks 통합 검증
    • AML / Travel Rule provider 통합
    • KYC system 구축
  3. Phase 3 (1-2 개월) — VASP 신고 + 사전 검사
    • 금감원 신고 자료 제출
    • 사전 검사 / 보완 요구 대응
    • 최종 신고 수리
  4. Phase 4 (1 개월) — 운영 시작
    • 제한된 고객 / 자산으로 베타 운영
    • 모니터링 + 운영 안정화
  5. Phase 5 (지속) — 정기 운영 + 컴플라이언스
    • 월간 / 분기 compliance report
    • 금감원 정기 점검 대응
    • 법규 변경 모니터링
