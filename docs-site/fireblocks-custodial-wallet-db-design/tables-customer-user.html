9. Customer Users (고객)

은행 고객 ↔ Vault 매핑 · 채널계 · KYC 외부 시스템 통합
★ 본 페이지의 범위 — 고객 user

앞 페이지 (8. Internal Users) 가 은행 내부 운영자 (Fireblocks Console / API / Mobile 에 접근하는 직원) 를 다뤘다면, 본 페이지는 은행 고객 (수탁형 지갑 서비스를 사용하는 일반 사용자) 을 다룬다.

핵심 차이: 고객은 Fireblocks 에 직접 접근하지 않는다. Fireblocks Console · API · Mobile app 모두 은행 직원만 사용. 고객은 은행의 채널 (모바일 뱅킹 / 인터넷 뱅킹 / 영업점) 을 통해 코인계와 상호작용하고, 코인계는 그 요청을 받아 Fireblocks API 를 대신 호출 (delegated custody).

9.1 고객 user 의 lifecycle

고객 user 의 lifecycle 은 다음 5 단계로 구성되며, 각 단계마다 외부 시스템 (채널계 / KYC / AML / HRIS) 과 연동된다.

단계주체외부 시스템코인계 DB 변화
① 가입 · 본인 확인고객 (채널), KYC 부서채널계, KYC 시스템없음 (코인계는 진입 전)
② 가상자산 서비스 약관 동의고객 (채널)채널계customer_vault 행 생성 (status = pending)

9.3 고객 데이터 모델 — ER diagram + 3-layer view

★ "고객별 자산" 은 3 layer 에 분산

고객 관련 entity 는 core 영역 의 3 domain (customer · accounting · transaction) 에 12 개 표로 분산. "고객별 자산" 이라는 개념도 3 가지 layer 로 나뉘어 각기 다른 domain 에서 관리된다.

9.3.3 "고객별 자산" 질문에 대한 답 — layer 별 접근

  • "고객 X 가 BTC 얼마 보유?" → accounting.customer_ledger WHERE bank_customer_id = X AND asset_id = 'BTC'
  • "고객 X 의 ETH 입금 주소?" → customer schema 의 customer_vault → customer_asset_wallet → customer_deposit_address 3-단 join
  • "고객 X 의 최근 출금 내역?" → customer.transaction_request WHERE bank_customer_id = X (transaction.transaction_execution 와 join 시 leg 별 vendor lifecycle 포함, vendor_transaction 까지 join 시 Fireblocks 측 status 도 포함)
  • "고객 X 의 자산 분리 보관 증명?" → customer_ledger 잔액 + 매일 reconciliation log (Σ(customer_ledger) + Σ(delta_ledger) == Σ(고객 자산 vault on-chain 잔액), Hot omnibus + Cold + segregated 합산) + hash chain 무결성

9.5 고객 vault 의 운영상 제약

9.5.1 고객별 자산 분리 보장 — Omnibus + Subledger 패턴

가상자산이용자보호법 (VACPA) 은 고객 자산을 은행 고유 자산과 분리하여 보관 · 관리할 것을 요구한다. 단 법문은 on-chain 수준의 1:1 분리를 강제하지 않으며, "분리 보관 · 관리" 의 실무 해석은 ledger 수준 분리 + 무결성 보증 으로 충족 가능 (한국 거래소 4 사 모두 omnibus + subledger 운영, 글로벌 custodian 인 Coinbase Custody · BitGo · Anchorage 도 동일 패턴).

본 설계의 분리 보관 전략 (hybrid layered):

구분on-chainDB ledger
고객 자산 (Hot)Omnibus vaultcustomer_ledger 로 고객별 분리
고객 자산 (Cold)Omnibus vaultcustomer_ledger 로 고객별 분리
은행 고유 자산★ 별도 vault (분리 필수)별도 ledger (4 원장 ③ 회사 자산)
입금 추적고객별 deposit addressdeposit_observations 로 매핑

핵심:

  • on-chain 은 omnibus — gas 효율 + Fireblocks vault account 수 절감 + dust 누적 회피 + 운영 부담 ↓. 수십만~수백만 고객 규모에서 1:1 매핑은 운영 비용 측면에서 비현실적
  • DB ledger 는 customer_ledger 로 고객별 분리 (5. Vault · Asset Wallet · Address 5.4 절 / 18. 회계 · 원장 설계 18.4 절 의 4 원장 ①)
  • 분리 보관 증명 매커니즘:
    • 매일 reconciliation — subledger 의 고객별 잔액 합 == omnibus vault 의 on-chain 잔액 (19. 대사 · 결산 · 마감 19.2 절 의 L1-L4)
    • subledger hash chain 무결성 (15. Audit · AML · Travel Rule 15.3 절 의 audit_log_internal 패턴)
    • 외부 감사 · 금감원 검사 시 reconciliation log + hash chain 으로 입증
  • 고객 자산 ↔ 은행 고유 자산 분리는 on-chain 수준에서 강제 — 별도 vault account 운영 (workspace level 분리 또는 동일 workspace 내 별도 vault). 이 부분은 ledger 분리로 대체 불가
대안 — Hybrid Mixed (VIP segregated)

일부 대형 / VIP 고객만 segregated vault (1:1 매핑), 일반 고객은 omnibus + subledger 의 mixed 운영도 가능. 단 운영 복잡도 ↑ (두 패턴 동시 유지 · 회계 분기 처리) — 본 reference 는 fully omnibus + subledger 권장.

★ omnibus 운영의 전제 조건 (저자 hypothesis)

omnibus 패턴은 다음 조건이 동시 충족되어야 VACPA 분리 보관 의무를 위반하지 않음. 미충족 시 segregated 로 전환하거나 자체 법률 자문 필요:

  • subledger 의 무결성 (hash chain · append-only) 이 외부 감사 가능 수준
  • 매일 reconciliation 실패 시 즉시 alert + 운영팀 review (자동 retry 금지)
  • 고객 자산 vault 와 은행 고유 자산 vault 가 on-chain 에서 명확히 분리 (★ 동일 vault 절대 금지)
  • 대법원 2024도10710 "실질 통제" 판단 시 subledger + 매일 reconciliation 이 분리 보관 입증 자료로 인정될지는 open question — 별도 법률 검토 필요

9.5.2 잔액은 항상 on-chain 진실 기준

  • 코인계 DB 에는 고객별 vault 의 잔액 cache 가 있을 수 있으나, source-of-truth 는 항상 on-chain (Fireblocks 가 mirror)
  • 고객에게 잔액 표시 시 (a) cache 우선 + (b) 일정 주기로 Fireblocks API 재조회 + (c) 출금 직전에는 반드시 fresh 조회

9.5.3 출금 한도는 거래 시점 검사

  • 고객별 1 일/1 회 출금 한도 (특금법 · 은행 자체 정책) 는 코인계가 검사. 채널계가 받아둔 한도 master + 코인계 거래 누적치로 결정
  • 한도 master 의 source-of-truth 는 채널계 / 정보계, 코인계는 거래 직전 조회

★ 자산 처리는 자동화 금지

사망 · 제재 등으로 vault 가 동결되어도 자산을 자동으로 어딘가로 이동하는 로직은 절대 두지 않음. 출금은 항상 사람의 quorum 승인을 요구 (Cold Wallet · Hot Wallet 거버넌스). 자동 이동 코드가 존재하면 그것이 SPOC 가 됨 (한 번 노출되면 시스템 전체가 위험해지는 critical 지점).

9.7 핵심 운영 원칙

  • PII 최소 보유 — 코인계 DB 에는 이름 · 주민번호 · 주소 · 연락처 등 직접 식별정보 저장 금지. 필요 시 외부 시스템에 즉시 조회 후 메모리 사용 · 폐기
  • 인증은 채널계 위임 — 고객 password / 2FA / 생체인증 모두 채널계 IdP. 코인계는 신뢰된 인증 토큰만 검증
  • vault 자산 분리 보관 — on-chain 은 omnibus, DB ledger 수준에서 customer_ledger 로 고객별 분리. VACPA 분리 보관 의무는 ledger 분리 + 매일 reconciliation + hash chain 무결성 으로 충족. 단 고객 자산 vault 와 은행 고유 자산 vault 는 on-chain 분리 필수
  • 자산 이동은 자동화 금지 — 사망 · 제재 · 휴면 등 lifecycle 이벤트는 vault status 만 변경. 실제 자산 이동은 사람 quorum 승인 매개
  • 외부 이벤트는 event 별 분리 audit — AML 제재는 aml_sanction_event, KYC 신원은 kyc_status_event, lifecycle (휴면 / 사망 / 탈퇴) 은 lifecycle_event 표에 각각 기록. trigger 시스템 / SLA / schema 가 모두 다르므로 분리. 원본 payload 는 PII 가까운 경우 별도 secure store 에 보관
