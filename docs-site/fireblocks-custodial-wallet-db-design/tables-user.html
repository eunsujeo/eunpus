8. Internal Users (운영자)

은행 내부 운영자 ↔ Fireblocks Console / API / Mobile user 매핑
★ 본 페이지의 범위 — 내부 운영자 user

은행 수탁형 지갑 시스템에는 두 종류의 user 가 존재. 본 페이지는 그중 내부 운영자 user 만 다루며, 고객 user 는 다음 페이지 (9. Customer Users (고객)) 에서 별도로 다룬다. 내부 운영자 = Fireblocks Console / API / Mobile 에 접근하여 vault 운영 · 정책 변경 · 거래 승인 · 거래 서명을 수행하는 은행 직원 (운영팀 · 보안팀 · 컴플라이언스팀 · API 자동화 시스템 등).

8.1 Fireblocks 의 3 user type

Fireblocks 는 사용자를 3 가지 type 으로 분류한다. 각 type 별로 인증 방식과 책임이 다르다.

User type인증 방식대표 책임
Console useremail + password + 2FA / SSOUI 접근 (workspace 관리, 거래 승인 등). Mobile app 페어링 가능
API userAPI key + secret (HMAC)프로그램틱 접근. 플랫폼 가 사용
Mobile-only useractivation token 으로 mobile app 만Cold Wallet workspace 의 user (Console 접근 권한 없음, Cold Wallet 특수)

출처: Fireblocks — Manage Users

8.2 인증 매커니즘 별 정리

8.2.1 2FA (Two-Factor Authentication)

  • Fireblocks 가 TOTP authenticator app (Google Authenticator / Authy 등) 의 6 자리 코드 강제
  • Console 첫 로그인 시 setup 강제
  • 2FA 분실 시 Admin Quorum quorum 승인으로 reset

8.2.2 SSO (Single Sign-On)

  • 외부 IdP (Google Workspace · Okta · Entra ID 등) 와 SAML / OIDC 연동
  • Fireblocks 측 service provider 는 Auth0 가 담당
  • SSO 활성화 시 password 는 IdP 가 관리, Fireblocks 는 IdP 의 assertion 만 검증
  • 2FA 는 IdP 측에서 또는 Fireblocks 측에서 둘 다 적용 가능

출처: Configure SSO

8.2.3 IP Allowlist

  • API user 별로 허용된 IP 목록 설정 가능
  • 은행은 플랫폼 의 outbound NAT IP 만 허용 권장
  • SaaS Cold Wallet workspace 는 IP allowlist 가 거버넌스의 일부 (별도 모드)

8.2.4 Mobile device 페어링

  • Console user 가 mobile app 을 페어링 → activation token (7일 유효) → KeyChain 보관
  • SaaS MPC 의 경우 mobile device 가 MPC share 1 of 3 보유 (primary share)
  • Device 분실 / 교체 시 device migration 절차 (Admin Quorum 승인 매개)

8.4 Mobile device 추적 (저자 권장)

Mobile device 추적이 필요한 워크스페이스 / user 유형:

  • SaaS MPC workspace — mobile device 가 MPC share 1 of 3 (primary share) 를 직접 보유. device 분실 = 키 share 1 개 분실. 자산 보안에 critical.
  • Cold Wallet workspace 의 Mobile-only user — Cold 의 모든 운영자가 mobile 만 사용. Approval Group 위임 미지원 환경에서 device 분실 = 거버넌스 1 인 단위 즉시 정지 위험.
  • Hosted MPC / Key Link workspace — 키 share 가 SGX 서버 / HSM 에 있어 mobile device 는 거래 승인 채널 일뿐 키 share 미보유. 그래도 mobile 이 quorum 승인 매개라 device 추적 권장 (자산 보안 critical 도는 SaaS MPC 보다 낮음).

은행은 위 모든 경우에 대해 device 단위 추적을 자체적으로 권장.

device migration 절차 — Admin Quorum 매개

device 교체 시 (a) 기존 device 가 정상 동작하면 self-migration 가능, (b) device 분실 / 손상 시 Admin Quorum 의 quorum 승인 매개로 re-enrollment. SaaS MPC 의 primary key share 가 mobile device 의 KeyChain 에 있으므로, device 잃어버리면 Workspace Keys Backup 의 recovery passphrase 가 유일한 회복 경로.

8.5 Callback Handler (Hosted MPC 시)

Hosted MPC 의 API Co-signer 는 거래 서명 직전에 Callback Handler endpoint 를 호출하여 은행 측의 추가 검증을 받음 (자체 정책 적용).

키 / public key 의 출처 정리

Hosted MPC 환경에서 은행 ↔ Fireblocks 간 인증에는 두 개의 별도 키 쌍이 있고, 두 public key 모두 은행이 생성하여 Fireblocks 에 등록 (Fireblocks 가 발급하는 게 아님):

  • API user CSR (RSA 4096) — Fireblocks API 호출 인증용. 은행이 CSR 생성 후 Fireblocks Console 에 업로드 → Fireblocks 가 검증 후 API key 를 발급 (이 API key 만 Fireblocks 가 발급)
  • Callback Handler public key (RSA 2048) — Co-signer ↔ Callback Handler 간 mTLS 통신 인증용. 은행이 keypair 생성 후 public key 만 Fireblocks 에 등록 (API user 별 별도)

admin.callback_handler_meta

column설명
handler_id (PK)은행 내부 ID
vendor_cosigner_id속한 Co-signer 인스턴스
endpoint_urlHTTPS endpoint URL (은행 application)
callback_public_key_pemCallback Handler 의 public key (RSA 2048, PEM) — 은행이 keypair 생성 후 public key 만 Fireblocks 에 등록. 짝이 되는 private key 는 은행 secret manager (예: AWS Secrets Manager) 에 별도 보관
private_key_secret_refprivate key 의 secret manager reference (예: AWS Secrets Manager ARN). private key 자체는 절대 column 에 저장 금지

8.7 핵심 운영 원칙

  • 은행 application 의 인증 = IdP 위임 — 자체 password 관리 금지 (보안 risk 큼)
  • API key 는 secret manager 만 — DB column 에 평문 저장 절대 금지
  • 최소 권한 원칙 — read-only 작업 = Viewer role 의 API key. Signer / Admin 권한은 별도 key
  • 퇴사자 처리 — 즉시 (a) admin.user_map.status='retired' 갱신, (b) Fireblocks Console 에서 user remove, (c) IdP 에서 비활성화 — 세 곳 동시. 단 직원 master 자체는 HRIS 가 관리하므로 코인계 DB 에는 별도 직원 마스터 테이블 없음 (employee_id 는 외부 reference)
  • device 분실 신고 — 즉시 (a) Admin Quorum 에 알림, (b) device migration 또는 user 의 mobile 권한 회수, (c) audit log 검토
