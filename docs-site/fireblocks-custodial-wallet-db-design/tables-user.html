6. Users

은행 사용자 ↔ Fireblocks Console / API / Mobile user 매핑

6.1 Fireblocks 의 3 user type

Fireblocks 는 사용자를 3 가지 type 으로 분류한다. 각 type 별로 인증 방식과 책임이 다르다.

User type인증 방식대표 책임
Console useremail + password + 2FA / SSOUI 접근 (workspace 관리, 거래 승인 등). Mobile app 페어링 가능
API userAPI key + secret (HMAC)프로그램틱 접근. 은행 application server 가 사용
Mobile-only useractivation token 으로 mobile app 만Cold Wallet workspace 의 user (Console 접근 권한 없음, Cold Wallet 특수)

출처: Fireblocks — Manage Users

6.2 인증 매커니즘 별 정리

6.2.1 2FA (Two-Factor Authentication)

  • Fireblocks 가 TOTP authenticator app (Google Authenticator / Authy 등) 의 6 자리 코드 강제
  • Console 첫 로그인 시 setup 강제
  • 2FA 분실 시 Admin Quorum quorum 승인으로 reset

6.2.2 SSO (Single Sign-On)

  • 외부 IdP (Google Workspace · Okta · Entra ID 등) 와 SAML / OIDC 연동
  • Fireblocks 측 service provider 는 Auth0 가 담당
  • SSO 활성화 시 password 는 IdP 가 관리, Fireblocks 는 IdP 의 assertion 만 검증
  • 2FA 는 IdP 측에서 또는 Fireblocks 측에서 둘 다 적용 가능

출처: Configure SSO

6.2.3 IP Allowlist

  • API user 별로 허용된 IP 목록 설정 가능
  • 은행은 application server 의 outbound NAT IP 만 허용 권장
  • SaaS Cold Wallet workspace 는 IP allowlist 가 거버넌스의 일부 (별도 모드)

6.2.4 Mobile device 페어링

  • Console user 가 mobile app 을 페어링 → activation token (7일 유효) → KeyChain 보관
  • SaaS MPC 의 경우 mobile device 가 MPC share 1 of 3 보유 (primary share)
  • Device 분실 / 교체 시 device migration 절차 (Admin Quorum 승인 매개)

출처: Device Migration

6.7 핵심 운영 원칙

  • 은행 application 의 인증 = IdP 위임 — 자체 password 관리 금지 (보안 risk 큼)
  • API key 는 secret manager 만 — DB column 에 평문 저장 절대 금지
  • 최소 권한 원칙 — read-only 작업 = Viewer role 의 API key. Signer / Admin 권한은 별도 key
  • 퇴사자 처리 — 즉시 (a) bank_users.active=false, (b) Fireblocks Console 에서 user remove, (c) IdP 에서 비활성화 — 세 곳 동시
  • device 분실 신고 — 즉시 (a) Admin Quorum 에 알림, (b) device migration 또는 user 의 mobile 권한 회수, (c) audit log 검토
