해외송금 (개인 P2P + Institutional) · Canton Network · Musubi · DvP 정산 · KR 외국환 / 특금법 규제
본 페이지의 범위 + tier

해외송금 + cross-border settlement 의 2 layer 를 모두 cover:

  • 개인 P2P 해외송금 — 사용자 → 해외 wallet/거래소 (외부 출금의 special case · 트래블룰 + 외국환신고 + AML 강화). 기본 흐름은 16.4 오프램프 + 14. Deposit·Withdrawal 14.4.2 절 (외부 거래소 출금) 의 확장

★ 출처 tier: Canton Network 자체 정보는 일반 reference + 공개 docs (digitalasset.com / canton.network) 기반. KR 규제 적용 (외국환거래법 + 특금법) 은 회계법인 / 외환계 자문 후 확정 권장. 본 페이지는 설계 reference 까지 — 실제 institutional 운영 시 Canton Foundation + KR 금감원 / 한국은행 (외환) 협의 필수.

17.2 Canton Network 기초

출처: canton.network · docs.digitalasset.com. KR 은행이 institutional cross-border settlement 에 Canton 도입 시 알아야 할 기본 개념.

17.2.1 Canton 이 무엇인가

  • Privacy-enabled public DLT — Digital Asset 사가 운영하는 plataform. "the only public chain with privacy"
  • 대상: institutional finance — "decentralization of public blockchain with the privacy and controls required for financial markets"
  • Smart contract language: DAML (Digital Asset Modeling Language) — 금융 거래 모델링 특화
  • Privacy model: "sub-transactions visible only to relevant parties" — 거래 참여 당사자만 데이터 보이고, 비당사자는 거래 존재 자체도 모름 (vs Ethereum 전체 공개)

17.2.2 핵심 컴포넌트

컴포넌트역할
Participant Node은행 / 기관이 운영하는 노드 — 자기 party 의 contract 보관 + 거래 참여
Synchronizer거래 ordering / atomic commit 매개. Global Synchronizer = 전체 네트워크 backbone (sync.global foundation 운영) · application synchronizer = 특정 application 용
Party거래 당사자 식별자 (예: Bank-A::namespace). 은행은 자체 party + 고객 party 발행 가능
Super ValidatorGlobal Synchronizer 운영 (영구 노드 · 거버넌스 참여)
Validator일반 participant node (은행 운영 시 이 등급)
Canton Coin (CC)네트워크 utility token — traffic fee (거래 처리 비용 · CC 차감) + governance

17.2.3 institutional 채택 사례 (canton.network 공시)

  • DTCC — U.S. Treasury 토큰화 (2026 target)
  • HSBC — tokenized deposit pilot
  • Goldman Sachs · BNP Paribas · Standard Chartered — institutional settlement (Digital Asset 공개 사례)
  • Stablecoin payments / 크로스보더 결제 — Musubi 등 (17.3 절)

17.2.4 Fireblocks 의 Canton 지원

Fireblocks 는 Canton Coin (CC) custody 지원 — Backup & Recovery 문서에 별도 절차 (Recover Canton Coin · validator disaster recovery + ACS import). 의미:

  • Fireblocks vault 에 Canton Coin / USDCx 등 Canton-native asset 보관 가능
  • 일반 token 과 다른 recovery 절차 (Active Contract Set import 필요)
  • USDCx 같은 token 복구는 별도 — Token Registrar (Circle 등) 의 추가 action 필요

출처: sources/canton/2026-05-19__fireblocks-recover-canton-coin.md · Fireblocks Help Center

17.3 Musubi Network — Institutional Stablecoin Settlement 사례

일본 ↔ 한국 institutional cross-border settlement 의 구체 사례. Canton 위에서 작동하는 atomic DvP 네트워크. 출처: musubinetwork.com.

17.3.1 무엇을 해결하나

  • 1-3 영업일 settlement delay 제거 — atomic settlement (~15 초)
  • Herstatt risk 제거 — 양 leg 동시 settle (FX swap 의 settlement risk 0)
  • Correspondent bank 중간자 다수 제거 — 직접 atomic 거래
  • Transparent FX pricing — RFQ (Request For Quote) model
  • 통합 audit trail — SWIFT 메시지 분산 대비

17.3.2 참여자 모델 (3 core types + 추가)

참여자역할
Institutionspayment 시작 + market maker pricing 선택. 본 wiki context = 은행
Custodiansinstitutional client 자산 이동 authorize. cryptographic dual control. Fireblocks 같은 custody platform 이 이 역할
Market Makersanonymized RFQ 수신 + 가격 경쟁. 본 wiki context = 외환 거래소 · liquidity provider
Operator네트워크 운영 (Musubi 의 경우 Startale + Nodeinfra)
Settlement MediatorCanton level — atomic commit 매개

17.3.3 기술 architecture

  • 각 참여자가 isolated infrastructure (backend / DB / settlement node) — no shared systems
  • Cross-party coordination 은 settlement network 통해서만
  • Settlement = 4 atomic legs + signatory closure (operator · sender custodian · market maker · receiver custodian) — per-leg Allocation contract 기반
  • Privacy-by-design — market maker 는 sender / receiver identity 모름

17.3.4 지원 자산 + corridor

  • JPYSC0 (Japanese yen stablecoin) ↔ USDCx (USD Coin · Canton-native)
  • Japan ↔ Korea corridor (POC validation)
  • 현재 status: Canton testnet 배포 (institutional POC)

17.3.5 KR / 일본 컴플라이언스 mapping

  • 일본: FSA · JAFIC · PPC 의무 매핑
  • 한국: FSC · KoFIU · PIPC 의무 매핑
  • FXOrder field 마다 compliance obligation 매핑
  • Built-in: KYC references · jurisdiction codes · timestamps · settlement proof hashing

17.4 해외송금 — 개인 P2P (외부 출금의 special case)

본 wiki 의 외부 출금 (14. Deposit·Withdrawal · 시나리오 ②) 의 special case — destination 이 해외 wallet 또는 해외 거래소. 기존 schema 변경 없음 + KR 규제 추가 항목.

17.4.1 흐름 — 외부 출금 패턴 재사용

17.4.2 KR 외국환거래법 적용 (저자 hypothesis)

★ 외국환거래법 적용 — 법률 자문 필수

가상자산의 해외 송금이 외국환거래법의 외환 거래로 분류되는지 자체가 hypothesis. 다음 시나리오는 저자의 일반 해석 — 법무 / 한국은행 / 외환계 자문 후 확정:

  • 연 5 만 USD 이상 송금 시 한국은행 외환 거래 신고 (저자 추론 · 일반 외환 거래 기준)
  • 건당 5 천 USD 이상 송금 시 사전 신고 (저자 추론)
  • 가상자산이 KR 외환 규제상 "지급수단" 인지 "자본거래" 인지 분류가 모호 — 회계법인 / 법무 자문 필요
  • 특금법 트래블룰 (100만원 이상) 과는 별도 의무

17.4.3 모범 패턴 — schema 추가 없이 처리

  • transaction_request.metadata jsonb 에 외국환 정보 (송금 사유 / 외환신고 번호 등) 저장
  • compliance.regulator_reports 에 외환신고 결과 기록 (외환계 + 한국은행)
  • customer.customer_external_destination 에 해외 destination 사전 등록 시 KYC level 강화 (수신자 신원 확인)

17.5 해외송금 — Institutional (Canton 기반)

은행 ↔ 은행 cross-border settlement 의 새 architecture. 본 wiki 의 기존 outbound 출금 + Fireblocks 흐름과 완전히 다른 모델 — atomic DvP · Canton validator 운영 또는 외부 위탁.

17.5.1 흐름 — atomic DvP 모델 (Musubi 패턴)

sequenceDiagram
  autonumber
  participant BankA as 🏢 KR 은행 A
  participant Cust as Custodian (Fireblocks)
  participant MM as Market Maker

  BankA->>Canton: FXOrder INSERT (Allocation contracts · 4 legs)
  Canton->>Cust: leg 1 — KR Bank vault 에서 KRWst 출금 (custodian dual control)

  Canton-->>BankA: settlement complete (atomic · all-or-nothing)
  Canton-->>BankB: settlement complete

4-leg atomic DvP — RFQ → quote → atomic settle (~15 초). 모든 4 leg 가 commit 되거나 전체 rollback. Herstatt risk 0 · counterparty risk 0. 본 wiki 의 transaction_request.type = CROSS_BORDER_SETTLEMENT (신규) + cross_border_settlement_detail 표 추가 필요 (17.7 절).

17.5.2 본 wiki schema 와의 통합 옵션

Canton institutional settlement 는 본 wiki 의 기존 transaction_request 패턴 (header + 3 detail) 의 4 type 외 신규 type 추가 또는 별도 영역으로 격리. 3 옵션:

옵션설명장단점
A 통합 (transaction_request 확장)type = CROSS_BORDER 추가 + 새 detail 표 customer.cross_border_request_detail✅ 기존 패턴 재사용 / ❌ 사용자 (개인 P2P) vs 은행 (institutional) 의 혼재 가능성
B 별도 영역새 도메인 treasury 또는 settlement 추가 + 별도 표 cross_border_settlement✅ 명확한 분리 (은행 자체 거래) / ❌ 새 domain · cross-domain 관계 증가
C Hybrid개인 P2P = WITHDRAWAL type 재사용 / institutional = 별도 도메인✅ 의미적 정확 (다른 주체 · 다른 회계) / ⚠️ 운영 복잡도 약간 ↑

저자 권장 = C (Hybrid) — 개인 P2P 는 외부 출금의 special case 로 처리 (기존 schema 그대로) + institutional 은 새 도메인 (예: treasury) 으로 격리. 은행 자체 거래는 회계 처리가 다르고 (자기자본 · bank_ledger 갱신) · 운영 권한도 다름 (Admin Quorum + 회계팀 + 외환계).

17.5.3 Canton 도입 시 인프라 추가

  • Canton Validator Node — 은행 자체 운영 (또는 위탁) — 망분리 안 또는 외부
  • DAML smart contract 개발 / 검증 — settlement logic 정의 (FXOrder · Allocation 등)
  • Custodian 통합 — Fireblocks vault 와 Canton party 매핑 (사용자별 Canton party allocate)
  • Synchronizer 연결 — Global Synchronizer (sync.global) 또는 Application Synchronizer
  • Canton Coin (CC) 보유 — traffic fee 지불용 (vault 에 CC 일정량 유지)

17.6 KR 규제 매핑

17.6.1 외국환거래법 (저자 hypothesis)

  • 개인 P2P: 17.4.2 의 외환신고 임계 적용
  • Institutional cross-border: 은행이 외국환 업무 인가 보유 시 가능. 한국은행 외환 보고 의무 (월별 / 분기별)
  • 가상자산의 "지급수단" vs "자본거래" 분류 — KR 외환 규제 적용 가능성의 핵심. 회계법인 + 법무 자문 필수

17.6.2 자본시장법 (institutional 측)

  • stablecoin 의 settlement asset 적격성 — 자본시장법 적용 가능성 (저자 hypothesis)
  • 외환 매매 분류 시 자본시장업 인가 필요할 수 있음

17.6.3 특금법 (양 layer 공통)

  • 트래블룰 100만원 이상 — 개인 P2P 시 (institutional 시 별도 자문)
  • STR / 의심 거래 보고 — KOFIU
  • VASP counterparty 식별 (Musubi 같은 institutional network 의 VASP 지위 분류)

17.6.4 가상자산이용자보호법 (개인 P2P 측)

  • 해외송금 시에도 사용자 자산 분리 보관 의무 (예치 / 신탁)
  • 이상 거래 모니터링 (FDS)

17.7 Schema 영향 — 신규 표 / 컬럼 권장 (저자 hypothesis)

17.7.1 개인 P2P 해외송금 (schema 변경 없음)

transaction_request.type = WITHDRAWAL + destination_type 활용 (기존 schema 그대로):

  • customer.transaction_request.metadata jsonb — 외국환 정보 (송금 사유 코드 · 외환신고 번호 등) 저장
  • customer.customer_external_destination — 해외 destination 사전 등록 시 country / VASP 정보 추가 (메타데이터)
  • compliance.regulator_reports 에 외환신고 결과 기록

17.7.2 Institutional cross-border (신규 도메인 — 저자 hypothesis)

새 도메인 treasury 또는 settlement + 신규 표:

표 (저자 권장)책임

17.8 운영 시작 전 검증 + 트레이드오프

★ 운영 시작 전 검증 필수
  • 법무 / 외환계 / 한국은행 자문 — 가상자산의 외국환거래법 / 자본시장법 적용 범위
  • 외국환 업무 인가 — 은행이 이미 보유한 외환 인가의 가상자산 cross-border 적용 가능성
  • Canton 도입 의사결정 — validator 자체 운영 vs 위탁 vs 외부 settlement network 위탁 (Musubi 등)
  • Custodian 통합 — Fireblocks vault + Canton party 매핑 모델 (1:1 vs 1:N)
  • CC 보유 / 환매 — Canton Coin 의 회계 처리 (utility token? · gas fee?) + 환매 정책
  • POC → 운영 전환 — testnet (Musubi 현재 status) → mainnet 안정성 검증
  • Counterparty bank 협약 — JP / SG / HK / EU 은행과의 양자 협약 + DvP 표준 합의
  • 금감원 / 한국은행 사전 보고 — 시범 사업 단계에서 감독당국 사전 협의
