19. 대사 · 결산 · 마감

4 단계 대사 (L1-L4) · 24/7 거래 vs 시점 마감 · 정정 절차 · 외부 감사 대응
본 영역의 출처 — vendor 공식 자료 부재

Fireblocks 는 대사·결산·마감을 다루지 않는다. 본 도메인은 일반 수탁업 / 펀드 / 자산운용업의 회계 표준 + 본 reference 의 권장 설계 (work-in-progress). 운영 시작 전 회계법인 / 외부 감사 / 내부 회계팀의 검증 필수.

★ 본 페이지의 정의 수준 — 도메인 view 까지

본 페이지는 4 단계 대사 (L1-L4) · 대사 주기 · 불일치 처리 정책 · 결산 / 마감 절차 · 외부 감사 대응 자료 같은 운영 도메인 view 까지 정의한다. 각 표 (reconciliation_session · reconciliation_finding · reconciliation_resolution · balance_check_history · onchain_sync_log) 의 column-level schema 는 정의하지 않음.

이유: 대사 / 결산 column schema 는 회계감사 / 금감원 검사 대응 자료의 정밀한 요구사항 에 따라 확정되어야 후속 변경 비용이 작다. 표명 + 책임 + L1-L4 매트릭스까지만 정의하고, 정확한 column / type / constraint 는 별도 stage 에서 회계법인 자문 + 금감원 검사 실무 대응 후 추가 예정.

19.1 대사 (Reconciliation) — 왜 필요한가

은행 수탁 시스템은 4 곳에 잔액·거래 정보가 분산:

  1. 블록체인 (canonical source) — 실제 자산의 truth
  2. Fireblocks Console / API — vendor 의 vault balance · audit log
  3. core 영역 — webhook 으로 받은 사본 + 4 원장 (고객 / 자체 / 델타 / 총계정)
  4. 계정계 — 기존 은행 시스템의 법정통화 측 정합

대사 = 이 4 곳의 정합성을 정기적으로 검증. 불일치 발견 시 자동 보정 또는 운영자 검토 / 거래 일시중단.

19.2 4 단계 대사 (L1-L4) — 저자 권장

아래 4-tier 분류는 본 reference 의 권장 설계. 일반 수탁업 / 펀드 시스템의 multi-tier reconciliation 패턴을 가상자산 환경에 일반화한 것 — 정확한 tier 구분과 주기는 회계법인 / 운용업계 표준 (한국금융투자협회 등) 과 정합성 검증 권장.

★ 금융위 2026.04 — KR 거래소에 "5 분 주기 상시 대사" 요구

2026년 4월 금융위원회는 빗썸 오지급 사태 (BTC 랜덤박스 사고) 이후 5 대 거래소와 간담회를 열고 다음을 요구:

4 단계 대사 — L1 (실시간 잔액) / L2 (5분 건별) / L3 (정산 검증) / L4 (일별 온체인 검증). 각 단계의 불일치 발견 시 처리 절차 (alert / review queue / 수동 정정 / 시스템 정지).

L1 — 실시간 잔액 대사

  • 검증식: 오프체인 4 원장 잔액의 자산 종류별 합 = 총계정원장의 잔액
  • 주기: 실시간 (모든 거래 후 즉시)
  • 구현: DB trigger 또는 transaction 직후 check
  • 불일치 시: 운영팀 즉시 alert + 영향 거래 시점 분석. 심각 시 거래 일시중단 고려

L2 — 5 분 주기 건별 대조

  • 검증식: 오프체인 거래 내역 ↔ Fireblocks webhook event 의 1:1 매칭
  • 주기: 5 분 (또는 batch schedule)
  • 구현: cron job 또는 streaming pipeline
  • 불일치 시: 미매칭 거래 review queue + 운영자 manual 처리
  • 특이: webhook 의 at-least-once 보장으로 중복 가능 — dedup 후 매칭

L3 — 정산 검증

  • 검증식: 델타 원장의 정산 플래그 = 온체인 confirmation 상태
  • 주기: 정산 시점 (델타 처리 완료 시점)
  • 구현: 델타 처리 시 trigger
  • 불일치 시: 수동 정정 (Admin Quorum 매개) + 회계 처리 review

L4 — 일 단위 온체인 검증

  • 검증식: 블록체인의 vault 잔액 = 오프체인 잔액 + 델타 (정산 대기)
  • 주기: 일 단위 (마감 시점)
  • 구현: Fireblocks API 로 모든 vault balance 조회 + 자체 잔액과 대조
  • 불일치 시: 치명적 — 즉시 시스템 정지 수준. 보안 침해 / 회계 오류 의심

19.3 reconciliation 의 대사 테이블

본 페이지는 회계 영역의 도메인 설계 view (17 페이지와 동일 정책). 아래 표는 매핑 차원이며, 각 표의 컬럼 / type / storage 상세는 향후 별도 schema 페이지 또는 추후 확장에서 정의.

테이블역할

19.4 불일치 처리 정책 — Decision Matrix (저자 권장)

불일치 발견 시 어떻게 처리할지 사전에 정의. 자동 보정은 매우 제한적으로만 적용. 본 표의 정책은 본 reference 의 권장이며, 회계법인 / 보안팀 / 운영팀이 사전 협의해 확정.

불일치 종류심각도처리 정책 (저자 권장)
L1 잔액 불일치 (소액 · 소수점 오차)낮음자동 보정 (rounding 오차로 분류) + 일별 누적 monitor
L1 잔액 불일치 (큰 액수)높음거래 일시중단 + 운영팀 alert + 회계팀 review
L2 미매칭 거래 (webhook 누락)중review queue + 자동 backfill (Fireblocks API 재조회) + retry
L2 중복 거래 (idempotency 실패)중중복 row 제거 + 원인 분석 (webhook handler 점검)
L3 정산 불일치높음Admin Quorum 매개 수동 정정 + 회계법인 협의
L4 온체인 불일치치명즉시 모든 거래 정지 + 보안팀 / 회계팀 / 외부 감사 통보. 침해 가능성 조사
외부 vendor 측 오류 (Fireblocks 의 자체 오류)중-높음Fireblocks Support 즉시 통보 + 자체 회계 보존 (vendor 응답 대기)
자동 보정의 위험

불일치를 자동으로 "보정" 하면 진짜 사고를 가릴 수 있다. 자동 보정은 rounding 오차 등 명백한 소수점 차이에만 적용. 나머지는 모두 운영자 / 회계팀 검토. 자동 보정 정책은 회계법인과 사전 협의 필수.

19.5 결산·마감 프로세스

24/7 거래 발생 vs 회계 기간 단위 마감의 충돌. 마감 시점 정의가 critical.

마감 시간 기준 — 옵션 비교

옵션장단적합 시나리오
한국 자정 (KST 00:00) 한국 영업일과 직관적 정합. 단 자정 시점에 거래 multi-region 처리 시 race condition KR 은행 표준
UTC 00:00 국제 표준. 단 한국 시간 09:00 마감이라 운영시간 중 마감 처리 부담 multi-region · 외화 거래 비중 큼
영업일 마감 (한국 영업일 종료 시점) 은행 영업일 정의를 따름. 단 정의가 시스템마다 다를 수 있음 기존 은행 회계 시스템과 정합 우선

저자 권장: 한국 자정 (KST 00:00) + 기존 은행 일·월 마감과 동일 schedule. 단 외화 환산은 자정 직전 환율 적용 + 자정 이후 거래는 익일 처리. 블록체인은 24/7 라 자연스러운 cutoff 가 없어 은행이 자체 cycle 을 정의 (7. Cold Wallet 운영 7.4.1 절 의 "일일 cutoff" 정의와 동일 개념). 외화 환산 / 매매기준율 적용 상세는 18. 회계 · 원장 설계 18.7 절 참조.

일별 마감의 표준 흐름. KST 00:00 trigger → 거래 lock → webhook backfill → 4 원장 잔액 산출 → 외화 환산 → 회계 항등식 검증 → 통과 시 스냅샷 INSERT → 거래 lock 해제 → 계정계 sync. 실패 시 거래 정지 유지 + 운영팀 review.

스냅샷 immutable 보장

  • 스냅샷 row 는 append-only (UPDATE / DELETE 금지). DB trigger 또는 RLS 로 enforce
  • 각 row 의 hash chain (이전 row 의 hash 포함) 로 변조 detection
  • 월말 / 분기말 / 연말 hash 를 외부 anchor (예: 블록체인 commitment, 외부 timestamp service) 로 고정
  • 외부 감사 시 hash chain 무결성 검증 → 변조 없음 증명

19.6 정정·재마감 절차

마감 후 오류 발견 시 처리. 이미 마감된 row 는 절대 UPDATE / DELETE 금지 (회계 표준).

3 가지 정정 패턴

패턴의미적용
역분개 (Reversal Entry) 잘못된 분개를 정확히 반대로 한 번 더 기록 (원본은 그대로). 회계 표준 패턴 대부분의 정정
조정분개 (Adjusting Entry) 특정 금액만큼만 보정 (잔액을 정확한 값으로 가져가는 분개) 외화환산 / 평가 보정
전기 정정 (Prior Period Adjustment) 마감된 직전 기간의 오류 정정 (현재 기간에 누적 효과 인식) 중대한 오류 + 외부 감사 대응

정정 절차

  1. 오류 발견 → 운영팀 정정 ticket
  2. 회계팀 review → 정정 분개 작성 (역분개 / 조정 / 전기 정정 중 선택)
  3. Admin Quorum 매개 (mobile 승인) → 정정 분개 commit. quorum 매커니즘 상세는 10. Roles · Quorum · Policy 10.2 절 참조
  4. 정정 후 항등식 재검증 (L1 대사 재실행)
  5. 정정 사유 + 영향 거래 + 승인자를 accounting.accounting_correction_log 에 기록 (append-only · hash chain 적용 · 5년 보존. 15. Audit · AML · Travel Rule 15.3 절 의 audit_log_internal 패턴과 동일)
★ 절대 금지
  • 마감된 스냅샷 row 의 UPDATE / DELETE
  • 거래 이력 row 의 사후 수정 (DBA 권한으로도 금지)
  • 회계 항등식을 깨는 일방 분개 (차변 만 또는 대변 만)
  • 정정 분개에 대한 quorum 우회

월별월말 자정월별 결산 보고서 (계정과목 별) → 계정계 월말 마감 정합
분기별분기말 자정분기 손익 + 자기자본 변동 + 외화환산손익 → 계정계 분기 정합
연말연말 자정연말 결산 + 외부 감사 자료 제출

계정계와의 차이 처리

  • 수탁 시스템 마감 시점 ≠ 계정계 마감 시점 시 한 시점 동안 양측 잔액 불일치 → 명시적 buffer period 설정
  • 외화 환산 환율 차이 — 양측이 같은 환율 사용 필수 (매매기준율 일원화)
  • 정정 발생 시 양측 동시 정정 — 수탁 시스템 만 정정하면 계정계 정합 깨짐

19.8 외부 감사 대응

회계법인 / 금감원 / 내부 감사인이 대사 증적을 요구할 때 제공 가능한 자료. 회계 audit 영역의 전체 패키지는 15. Audit · AML · Travel Rule 15.6 절 참조.

제공 자료 패키지

  1. 일별 reconciliation_session 이력 (L1-L4 의 모든 실행 결과)
  2. reconciliation_finding 이력 (불일치 발견 + 처리 결과)
  3. 스냅샷 hash chain 무결성 증명 (chain verification script)
  4. 회계 항등식 검증 이력 (마감 시점마다 self-check)
  5. 정정 분개 이력 (역분개 / 조정 / 전기 정정 의 사유 · 승인자 · 영향)
  6. Fireblocks Console 의 immutable audit log (Auditor role 제공)
  7. 온체인 잔액 조회 증적 (블록체인 explorer 또는 RPC node 응답)

외부 감사 시점 사전 협의

  • 회계법인이 받아 보는 양식 사전 정의 (분기 / 연말 schedule)
  • 금감원 정기 점검 / 종합검사 대응 절차
  • 감사인의 read-only access 권한 (Auditor role + DB read-only account)
  • 전기 감사 의견의 follow-up (이전 감사에서 지적된 사항의 후속 조치)

19.9 펀드 시스템 차용 가능성 (저자 권장)

기존 펀드 수신 / 자산운용 시스템의 대사 자동화 프레임워크 활용 가능성:

  • 대사 도구 — 펀드 시스템의 기존 대사 엔진 차용 (rule-based · stream-based)
  • 불일치 처리 큐 — 운영자 review 큐의 기존 양식
  • 보고 양식 — 일별 대사 결과 리포트의 형식
  • 승인 절차 — 정정 분개의 승인 chain (펀드의 운영자 → 회계팀 → 감사 의 chain)
  • 외부 감사 협의 절차 — 펀드의 감사 대응 양식 / 증적 형식

19.10 운영 체크리스트 (분기별)
