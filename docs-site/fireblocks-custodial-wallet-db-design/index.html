Fireblocks 도입 수탁형 지갑 — DB 구조와 상태 흐름

은행이 Fireblocks 를 도입하여 수탁형 지갑을 운영할 때의 인프라 · DB 구조 · 상태 흐름 reference. 직접 구축 reference (수탁형 지갑 — DB 구조와 상태 흐름) 의 mirror 본으로, "무엇을 Fireblocks 가 책임지고, 무엇을 은행이 여전히 운영해야 하는가" 의 분담을 정리한다.

도입의 핵심 효과

  • 인프라 운영 부담 감소 — MPC 키 분포 · cosigner 운영 · 정책 엔진 · audit log 보안 등 깊은 보안 인프라를 Fireblocks 가 담당
  • DB 가 단순해진다 — 7 DB → 2-3 DB. 단 webhook 수신/idempotency/5년 보존 책임은 여전히 은행
  • vendor lock-in + outage 의존성 발생 — 새로운 risk register 필요 (11. Risks Register)
  • KR 컴플라이언스는 여전히 은행 책임 — Fireblocks 가 자동 제공하지 않음 (특금법 · 가상자산이용자보호법 · 가상자산업감독규정 등) — 상세는 국내 블록체인 사업 법규 × Fireblocks 참조

핵심 invariant (7)

  1. Workspace type 은 immutable — 한 번 SaaS MPC / Hosted MPC / Key Link 로 생성한 workspace 는 다른 type 으로 변환 불가. (Fireblocks Key Link Overview)
  2. Vault Account = 1 ECDSA + 1 EdDSA (Key Link 시) — 각 vault 에 algorithm 별 1 키만 할당. (Set up your Fireblocks Vault with Key Link)
  3. Webhook 은 idempotent 해야 한다 — 같은 event 가 중복 수신될 수 있으므로 event ID 기반 dedup 필수. (Configure Webhooks)
  4. Webhook signature 검증 필수 — Fireblocks 가 HMAC-SHA512 로 서명. signature 검증 없는 webhook 처리는 위조 vector. (Configure Webhooks)
  5. Admin Quorum 매개 작업은 mobile app 으로만 — Console 에서 시작, mobile 에서 quorum 승인. (Fireblocks Help Center)
  6. 은행 audit trail = Fireblocks audit + 자체 mirror — Fireblocks 가 immutable log 제공하지만 은행의 5년 보존 의무 (특금법 5조의4) 는 자체 mirror 필수. (특금법)
  7. 키 material 은 어떤 은행 DB 에도 저장 금지 — Fireblocks 가 키를 관리 (Key Link 의 경우 고객 HSM). 은행 application DB 어디에도 private key / mnemonic / MPC share 가 저장되어선 안 됨.

이 문서가 다루지 않는 것

  • Fireblocks 내부 DB 구조 — Fireblocks 가 미공개. 본 문서는 은행 측 DB 만 다룸
  • Fireblocks Console UI 사용법 — 공식 Help Center 참조
  • Fireblocks SDK 사용법 — 공식 Developer Portal 참조
  • KR VASP 컴플라이언스 매핑 — 별도 reference 국내 블록체인 사업 법규 × Fireblocks 참조
  • Cold Wallet workspace 운영 — 별도 reference 은행 Fireblocks Cold Wallet 도입 참조
  • Key Link customer HSM 통합 — 별도 reference Fireblocks Key Link — Customer HSM 통합 참조
