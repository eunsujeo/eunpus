9. Transaction State + 14-step

Fireblocks 가 운영하는 17-status state machine — 은행은 webhook 으로 mirror

9.1 Fireblocks 의 17 transaction status

Fireblocks 가 거래에 대해 정의한 status 는 17 가지. 모두 webhook event 로 은행에 전달됨.

#Status의미
1SUBMITTED거래 요청이 Fireblocks 에 접수
2QUEUED처리 대기 (이전 거래의 dependency 등)
3PENDING_AUTHORIZATIONApproval Group quorum 의 mobile 승인 대기
4PENDING_SIGNATUREDesignated Signer 의 서명 대기
5PENDING_3RD_PARTY_MANUAL_APPROVAL외부 시스템 (거래소 API 등) 의 추가 승인 대기
6PENDING_3RD_PARTY외부 처리 진행 중
7PARTIALLY_COMPLETED일부 destination 만 완료 (multi-destination tx)
8BROADCASTINGblockchain 으로 broadcast 시작
9CONFIRMINGblockchain confirmation 진행 (1 → N confirmations)
10COMPLETED최종 확정
11CANCELLED사용자 / 운영자가 취소
12REJECTEDApproval Group / TAP 가 거절
13FAILED처리 실패 (network / 잔액 부족 등)
14BLOCKEDPolicy rule 의 BLOCK action
15TIMEOUT승인 / 서명 timeout
16CONFIRMED일부 chain 의 finality 도달 (CONFIRMING 의 변형)
17DROPPEDmempool drop (chain 에서 거부)

왜 history 테이블이 별도인가 (append-only)

거래 한 건이 SUBMITTED → QUEUED → PENDING_AUTH → ... → COMPLETED 의 7+ 번 status 변경을 거친다. tx_mirror.current_status 는 가장 최근만 보관 (조회 효율). 모든 변경 이력은 tx_status_history 에 append-only 로 보관 — 사후 audit / 분쟁 시 정확한 시점 재구성 가능.

9.6 EVM Nonce / Bitcoin UTXO 의 특수성

Fireblocks 가 내부적으로 처리하는 chain-specific 룰. 은행은 직접 다룰 필요 없으나 운영 관찰 시 알아야 함.

  • EVM nonce ordering — 같은 vault 의 ETH 거래는 nonce 순서대로 broadcast. 이전 거래가 PENDING 이면 다음 거래 QUEUED. Fireblocks 가 자동 처리.
  • Bitcoin 25-chain 제약 — UTXO 한 chain 안의 unconfirmed tx 25 개 제한. Fireblocks 의 round-robin pattern 으로 회피.
  • Solana priority fee — congestion 시 fee 동적 조정. Fireblocks 가 자동.

9.7 Transaction Mirror 의 데이터 무결성 보장

은행 mirrordb 의 tx_mirror 가 Fireblocks Console 과 정합한가 — 정기 reconciliation:

  1. 일일 reconciliation — Fireblocks GET /v1/transactions 로 24h 이내 거래 목록 조회, mirrordb 와 대조
  2. 주간 deep check — 모든 status 변경 history 검증 (webhook 누락 detection)
  3. 월간 archive — 30 일 이상 거래를 cold storage 로 partition + archive (5 년 보존 위해)
  4. mismatch finding → reconciliation_session 테이블에 기록, 운영팀 review
★ 분쟁 시 Fireblocks Console 이 1차 source

은행 mirrordb 와 Fireblocks Console 사이에 불일치가 있을 때, 분쟁 해결의 1차 source 는 Fireblocks Console 의 immutable log. 은행 mirror 는 mirror 이지 canonical 이 아님. 은행은 mirror 가 정확함을 reconciliation log 로 증명 책임.
