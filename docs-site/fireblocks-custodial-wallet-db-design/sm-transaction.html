12. Transaction State + 14-step

Fireblocks 가 운영하는 17-status state machine — 은행은 webhook 으로 mirror

12.1 Fireblocks 의 17 transaction status

Fireblocks 가 거래에 대해 정의한 status 는 17 가지. 모두 webhook event 로 은행에 전달됨.

#Status색의미
1SUBMITTED노랑거래 요청이 Fireblocks 에 접수 — 초기 상태
2PENDING_AML_SCREENING노랑AML / Travel Rule provider 의 사전 검사 대기 (활성화 시)
3PENDING_ENRICHMENT노랑거래 메타데이터 보강 대기 (counterparty 식별 / KYC 추가 정보)
4PENDING_AUTHORIZATION노랑Approval Group quorum 의 mobile 승인 대기 (2h timeout → 실패)
5QUEUED노랑처리 대기 — 같은 vault 의 이전 거래의 dependency (EVM nonce / Solana 5-tx queue)
6PENDING_SIGNATURE노랑Designated Signer / MPC quorum 의 서명 대기 (2h timeout → 실패)
7SIGNED노랑Solana 전용 — 서명 완료, broadcast 대기 (다른 chain 에는 별도 SIGNED 단계 없음)
8CANCELLING노랑cancel 요청 처리 중 (30s timeout)
9PENDING_3RD_PARTY_MANUAL_APPROVAL파랑외부 시스템 (예: 외부 거래소 API) 의 manual 승인 대기
10PENDING_3RD_PARTY파랑외부 처리 진행 중
11BROADCASTING파랑blockchain 으로 broadcast 시작 (~1 분 내 mempool 진입)
12CONFIRMING파랑blockchain confirmation 진행 (1 → N confirmations)
13COMPLETED초록최종 확정 — 종결 (성공)
14CANCELLED빨강사용자 / 운영자가 취소 또는 Co-signer 거절
15BLOCKED빨강Policy rule (TAP) 의 BLOCK action — 정책 차단
16REJECTED빨강Approval Group / AML 차단 / 사용자 freeze
17FAILED빨강처리 실패 (timeout / network / 잔액 부족 / mempool drop 등) — 모든 실패 경로의 최종 종결

출처: Create a New Transaction API · Configure Webhooks · Primary Transaction Statuses (Help Center).

NetworkStatus — 다른 plane (blockchain 자체 상태)

위 17 primary status 외에 Fireblocks 는 별도 NetworkStatus enum 으로 blockchain layer 의 tx 상태를 보고: DROPPED (mempool 누락) / BROADCASTING / CONFIRMING / FAILED / CONFIRMED. primary status 의 BROADCASTING / CONFIRMING 과 매핑되지만, DROPPED · CONFIRMED 는 별도 신호. 본 reference 의 mirror 표는 primary status 만 저장하고 NetworkStatus 는 raw_event_payload 안에 jsonb 로 보관.

12.2 7 Operation Types

Fireblocks 의 거래는 operation body parameter 로 7 종 중 하나 지정. 모든 operation 이 동일한 17-status state machine 을 통과 — operation 은 거래의 input axis (자금 이동인지 contract 호출인지 등).

Operation용도지원 chain
TRANSFER (default)자금 이동All — UTXO 는 multi-input/output, account-based 는 single source/destination
CONTRACT_CALLEVM smart contract method callEVM 전반 (ETH · MATIC · BNB 등)
PROGRAM_CALLSolana program callSolana
TYPED_MESSAGEoff-chain typed message 서명EVM (EIP-191 personal / EIP-712 typed) · TRX (TIP-191) · BTC
RAWoff-chain raw message 서명 (custom protocol / 미지원 chain)Any

BURN토큰 supply 감소Stellar · Ripple · EVM

12.5 transaction 의 vendor_transaction + status history 테이블

3-layer 정리 — 어느 테이블이 "은행 측 canonical 거래" 인가

거래는 3 개의 layer 로 존재한다:

  • (A) 은행 측 canonical 거래 (bank intent) — 고객이 누구이고, 어느 채널로, 얼마를, 어떤 사유로 요청했는가. 직접 들고 있는 테이블: 14. Deposit · Withdrawal Flow 의 customer.withdrawal_request (출금 요청) / transaction.deposit_observations (입금). 이 layer 가 은행의 source of truth.
  • (B) vendor lifecycle (본 페이지) — Fireblocks 가 17-status state machine 으로 처리하는 거래의 lifecycle. 본 페이지의 vendor_transaction + vendor_transaction_status_history 가 담당. (A) 의 entry 가 Fireblocks 에 접수되면 (B) 가 생성됨.
  • (C) on-chain reality — blockchain 의 block height · confirmation · reorg. vendor_transaction.tx_hash + raw_event_payload 안의 NetworkStatus 에 일부 보관.

즉 vendor_transaction 는 vendor 측 거래 lifecycle 의 mirror 일 뿐, 은행 canonical 이 아님. canonical 은 customer.withdrawal_request · transaction.deposit_observations 등 bank intent layer.

  • append 시점에 redaction — webhook handler 가 PII 필드를 hash / 마스킹 후 저장. raw payload 는 별도 secure store (예: S3 Object Lock + KMS) 에 5년 보존
  • jsonb 안의 민감 필드 ENUM 화 — counterparty 식별자는 whitelisted_destinations.dest_id 등 내부 ID 만, raw email / 주민번호 등은 절대 저장 금지
  • 분쟁 / 감사 대응 — 외부 secure store 의 raw 와 core 영역 의 redacted 본을 hash 로 연결 (재현 가능성 보장)

왜 lifecycle_event 가 audit_log_mirror 와 분리되는가

audit 영역의 audit_log_mirror 는 모든 vendor 측 작업의 immutable log. vault / address 의 lifecycle event 도 그 안에 들어옴. 단 빠른 조회 (예: "vault X 의 hide 이력") 를 위해 transaction domain 에 dedicated event 표를 두는 게 운영 효율적. 두 표는 webhook handler 가 동시 INSERT (같은 event_id 기준 idempotency). 대안: audit_log_mirror 만 유지하고 jsonb query 로 vault lifecycle 조회 — 운영 빈도 낮으면 충분.

12.7 EVM Nonce / Bitcoin UTXO / Solana 의 특수성

Fireblocks 가 내부적으로 처리하는 chain-specific 룰. 은행은 직접 다룰 필요 없으나 운영 관찰 시 알아야 함.

  • EVM nonce ordering — 같은 vault 의 ETH 거래는 nonce 순서대로 broadcast. 이전 거래가 PENDING 이면 다음 거래는 QUEUED 로 대기. nonce 할당 / 순서 관리는 Fireblocks 가 vault 내부에서 처리 (운영자가 nonce 를 직접 지정할 필요 없음) — 자세한 동작은 Primary Transaction Statuses (Help Center) 참조.
  • Solana 5-tx 동시 큐 — Solana vault 는 최대 5 개의 동시 PENDING 거래 가능 (Solana 의 parallel signing 특성). 5 개 초과 시 QUEUED.
  • Bitcoin 미확정 거래 연쇄 제한 (저자 hypothesis) — Bitcoin 네트워크는 같은 출금 주소에서 아직 블록에 포함되지 않은 (unconfirmed) 거래가 연쇄적으로 최대 25 개까지 만 허용 (Bitcoin Core 의 기본 mempool 정책). 출금이 빈번한 vault 는 confirm 속도 (~10 분/block) 가 거래 발생 속도를 못 따라가면 26 번째 거래부터 mempool 진입조차 못함. Fireblocks 가 이를 어떻게 회피하는지 (예: 출금 주소를 여러 개 사용, 거래 batch 묶음 등) 공식 명세는 미확보.
  • Solana priority fee 동적 조정 (저자 hypothesis) — Solana 의 congestion 시 priority fee 가 거래 처리에 영향. Fireblocks 가 이를 알아서 조정한다고 가정하나 (운영자가 priority fee 를 직접 설정하는 UI / API 가 외부에 노출되지 않음 — 본 reference 추정), 구체 알고리즘은 vendor 공식 명세 미확보.

출처: Fireblocks Developer Portal · List Unspent Outputs · Primary Transaction Statuses (Help Center)

12.8 Transaction Mirror 의 데이터 무결성 보장

core 영역 의 vendor_transaction 가 Fireblocks Console 과 정합한가 — 정기 reconciliation:

  1. 일일 reconciliation — Fireblocks GET /v1/transactions 로 24h 이내 거래 목록 조회, core 영역 와 대조
  2. 주간 deep check — 모든 status 변경 history 검증 (webhook 누락 detection)
  3. 월간 archive — 30 일 이상 거래를 cold storage 로 partition + archive (5 년 보존 위해)
  4. mismatch finding → reconciliation.reconciliation_session 테이블에 기록, 운영팀 review. 표 정의는 19. 대사 · 결산 · 마감 참조
★ 분쟁 시 Fireblocks Console 이 1차 source

core 영역 와 Fireblocks Console 사이에 불일치가 있을 때, 분쟁 해결의 1차 source 는 Fireblocks Console 의 immutable log. 은행 mirror 는 mirror 이지 canonical 이 아님. 은행은 mirror 가 정확함을 reconciliation log 로 증명 책임.

12.9 Cross-chain swap — 영역 외 (별도 stage 필요)

★ 본 reference 의 범위 밖 — gap 명시

실제 운영에서는 chain 간 swap 이 필요한 사례가 발생한다. 예: 고객이 ERC-20 (Ethereum) USDT 로 입금했으나 출금은 TRC-20 (Tron) USDT 로 요청하는 경우. 본 페이지의 17 status / 7 operation / vendor_transaction schema 는 이 영역을 다루지 않는다. swap 도입 시 본 schema 만으로는 부족하며 별도 stage 에서 설계해야 한다.

왜 본 schema 로 부족한가

  • asset_id 가 chain-bound — 본 reference 는 USDC_ETH 처럼 chain 별 구분 표기. chain-agnostic 통합 view (예: "USDT") 가 모델에 없다. 고객이 "USDT" 잔액으로 인식하는 단위와 schema 의 asset_id 간의 매핑 정책 필요.
  • 거래는 1 row = 1 vendor_tx_id — swap 은 본질적으로 (a) outbound (ERC-USDT 매도) + (b) inbound (TRC-USDT 매수) 의 2-leg. 두 leg 를 묶을 parent 개념이 schema 에 없음.
  • 7 operation type 중 SWAP 없음 — Fireblocks 가 swap 을 어떤 operation 으로 노출하는지 본 reference 에 ingest 안 됨.
  • 회계 / 정산 미정의 — swap spread · DEX fee · 환손익 처리 방식이 18. 회계 · 원장 설계 · 19. 대사 · 결산 · 마감 에 정의되어 있지 않음.

schema 확장 sketch (저자 hypothesis · 별도 stage 에서 확정)

swap 도입 시 본 페이지의 vendor_transaction + vendor_transaction_status_history 위에 다음 layer 가 추가될 가능성이 높음 (저자 추정):

  • 신규 테이블 transaction.swap_session — swap 한 건당 1 row. 컬럼 후보: swap_session_id (PK · prefix sws_) · bank_customer_id · source_asset · destination_asset · requested_amount · swap_provider · quoted_rate · executed_rate · swap_status · spread_cost · fee_cost · opened_at · completed_at
  • vendor_transaction 에 swap_session_id (FK nullable) 추가 — 일반 거래는 NULL, swap leg 거래는 같은 swap_session_id 를 공유 (1 session : N leg)
  • 회계 page 의 4 원장 확장 — swap 의 spread / fee 를 별도 손익 계정으로 분리
  • 대사 page 의 L1-L4 에 swap-specific check 추가 — 2 leg 의 합이 quoted_rate × source_amount 와 일치하는지 등

이 sketch 는 저자 hypothesis 이며, 실제 swap 도입 시 (a) Fireblocks Swap API 의 ingest, (b) 회계법인 자문, (c) KR 법률 검토, (d) 운영팀 ceremony 정의 를 거쳐 별도 stage 에서 확정 한다. 현 stage 의 schema 는 swap 가 없는 가정에서만 완결.
