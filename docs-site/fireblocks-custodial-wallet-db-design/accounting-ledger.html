21. 회계 · 원장 설계

온체인 + 오프체인 + 계정계 3 계층 정합 · 회계 항등식 · 4 원장 구조 · 손익 / 외화환산
본 영역의 출처 — vendor 공식 자료 부재

Fireblocks 는 회계·원장·결산을 다루지 않는다 (vault 잔액 API · audit log 까지만 제공). 따라서 본 도메인은 다음 3 등급 (?) (tier) 로 출처를 구분한다.

  • Fireblocks 공식 사실 — Fireblocks 공식 URL 링크 명시 (vault balance · webhook event 등)
  • 일반 수탁업 회계 패턴 — 은행 · 자산운용업 표준 (이중부기 (?) · 분개 (?) · 자산-부채-자기자본 (?) 항등식 · 외화환산 · 결산 등)
  • 본 reference 의 권장 설계 (work-in-progress) — 본 영역의 패턴은 수탁업 설계 초기 단계의 일반 권장. 운영 시작 전 회계법인 / 외부 감사 / 내부 회계팀 검증 권장
★ 본 페이지의 정의 수준 — 도메인 view + 핵심 컬럼

본 페이지는 회계 4 원장 구조 / 거래 매트릭스 / 회계 항등식 / 외화환산 정책 / 손익 계정 분류 + 핵심 컬럼 (시나리오 / 회계 처리에 필요한 만큼) 을 정의한다. 각 표 (customer_ledger · bank_ledger · delta_ledger · general_ledger_entry · general_ledger_snapshot · fx_rate_history · fx_revaluation_log · accounting_correction_log) 의 완전한 column schema (type · constraint · index) 는 정의하지 않음.

이유: 회계 column schema 는 회계법인 / KR 회계 표준 (K-GAAP / K-IFRS) 자문 + 외부 감사 의견 후 확정되어야 후속 변경 비용이 작다. 표명 + 책임 + 시나리오 이해에 필요한 핵심 column 까지 본 페이지에서 정의 (예: customer_ledger 의 confirmed/pending 분리 · general_ledger_entry 의 debit_credit) — 완전한 type / constraint / index 는 별도 stage 에서 자문 후 추가 예정.

21.1 왜 회계 영역이 별도 도메인인가

Fireblocks 의 vault balance API · webhook event 는 "자산이 어디에 얼마나 있는가" 까지만 알려준다. 은행 회계는 그 위에 다음을 추가로 요구한다:

  • 이중부기 (?) — 모든 거래가 차변 / 대변 동시 갱신, 회계 항등식 유지
  • 고객 단위 잔액 (subledger) — Fireblocks 의 vault 잔액 ≠ 고객별 잔액 (특히 omnibus vault 시)
  • 법정통화 환산 — 가상자산을 원화 / 달러로 환산하여 총자산 산출
  • 손익 인식 — 수수료수익 · 외환매매수익 · 외화환산손익 · 가스비 등
  • 결산 — 시점 기준 잔액 박제 + 정정 절차
  • 외부 감사 대응 — 회계법인이 받아 보는 양식

21.3 회계 항등식 — 시스템의 핵심 불변식

자산 (?) 총액 = 반환채무 (?) 총액 + 자기자본 (?)

모든 거래 후에 이 항등식이 깨지면 즉시 시스템 정지 수준의 사고. 일반 수탁업 회계의 표준 항등식 (이중부기의 기본). 회계 항등식의 기본 패턴은 회계 등식 (위키백과) 참조.

구성 요소 (자산 측)

  • 각 자산 종류별 온체인 잔액 합계 (Hot · Cold · Treasury vault 의 총합)
  • 각 자산 종류별 오프체인 미반영 차액 (델타 원장의 pending)
  • 법정통화 잔액 (계정계 측)

구성 요소 (부채 측 = 반환채무)

  • 각 자산 종류별 고객 잔액 합계 (고객 원장의 UserID 별 잔액의 합)
  • 고객별 미인출 자산은 모두 은행의 "반환 의무" 로 인식 — 고객이 출금 요청 시 은행이 돌려줘야 하는 의무량

구성 요소 (자기자본)

  • 자기자본 = 자산총액 − 반환채무 (산출 또는 별도 계정)
  • 은행의 자체 자산 + 누적 손익 — 예: 자산 1000 + 고객 반환채무 990 → 자기자본 10 (은행 본인의 순수 보유분)
자기자본 — 산출값 vs 별도 계정 (설계 결정)

두 가지 옵션:

  • 옵션 1 — 산출값: 자기자본 = 자산 − 부채 (쿼리로 매번 계산). 별도 row 없음
  • 옵션 2 — 별도 계정: 자기자본 계정을 별도 row 로 보유 + 변동 거래 이력 + 일별 스냅샷

권장 (저자) — 옵션 2. 이유:

  • 음수 진입 차단 (자기자본 음수 = 고객자산 잠식) 의 DB 제약 적용 용이
  • 일별 스냅샷이 immutable hash chain 으로 변조 방지 가능
  • 외부 감사 시 자기자본의 시점별 추적이 쉬움
  • 운영 잔액 (자체 vault) vs 회계 잔액 (자기자본) 분리 명확화

21.4 4 원장 구조

오프체인 수탁 원장은 4 가지로 분리. 각 원장이 책임과 데이터 특성이 다름. 4 원장 모두 코인계 DB 에 위치 — 일부는 운영 시 계정계와 sync 책임이 있음 (마지막 컬럼).

★ customer_ledger 잔액 = confirmed vs pending 분리

거래소 (Upbit · Binance · 증권사 MTS) 의 표준 — customer_ledger 잔액은 3 가지 필드로 분리해야 misleading 표시 방지 + 회계 정합성 확보:

  • confirmed_balance — 정산 완료된 잔액. 출금 / 추가 거래 가능. vault 실제 잔액과 매칭 (L1 대사)
  • pending_in_balance — 입금 처리중 (Step 1 완료, Step 2 미완). 사용자 UI 에 "처리중 +X" 별도 표시. delta_ledger 미정산 자산과 매칭
  • pending_out_balance — 출금 처리중. 사용자 UI 에 "출금 처리중 -Y" 표시. delta_ledger 미정산 부채와 매칭

왜 분리하나? ① 사용자가 "처리중" 임을 명확히 인지 (UI 거짓 표시 방지) · ② 출금 가능 잔액 검증 (pending 자산은 출금 못 함) · ③ Step 2 실패 시 confirmed 변동 없이 pending rollback 만 → phantom money 없음 · ④ L1 대사 simplification (confirmed = vault / pending = delta_ledger 1:1 매칭).

★ 4 원장은 "수량" 을 기록한다 — 평가금액 (KRW) 은 derived · 3 layer

원장의 balance 컬럼은 자산 단위 수량 (예: USDC 100 · BTC 0.5) 만 기록. 코인의 KRW 평가금액은 시세가 초~분 단위로 바뀌므로 원장에 직접 저장하지 않고 별도 시세 · 취득원가와 join 해서 derived. 책임이 다른 3 layer 로 분리:

  • ① 운영 평가 (실시간) — UI 잔액 표시 · 트래블룰 100만원 임계 · 출금 한도 검증 · 거래 시점 환산. 시세 source = 외부 oracle / 거래소 ticker (초~분 단위). 영구 저장 X — transaction.asset_value_krw 에 거래 시점만 짧은 cache (TTL 1 시간 정도) 로 박제 (트래블룰 / 금감원 보고 증적)
  • ② 고객 포지션 (취득원가 대비 P&L) — 사용자가 보는 "내 자산 / 평단가 / 평가손익" 화면. 거래소 (Upbit · Binance) · 증권사 MTS 와 동일한 책임. 거래 시점 KRW 시세를 취득원가 (cost basis) 로 누적 → 현재 시세와 비교해 미실현 손익 표시. 21.8 고객 포지션 (평단가 · 미실현 손익) 참조
  • ③ 회계 평가 (일말 1회) — 평가손익 인식 · 분개. 시세 source = 종가 (한국은행 매매기준율 또는 거래소 종가). fx_rate_history 종가 × 잔액 → fx_revaluation_log → general_ledger_entry + general_ledger_snapshot (hash chain · 변조방지 박제). 21.7 평가 / 환산 처리 참조

3 layer 는 같은 수량 원장 위에서 derived 하지만 시세 source · 저장 정책이 다름: ① = 실시간 query (저장 X) · ② = 거래 시점 KRW 누적 (취득원가) · ③ = 일말 종가 박제 (immutable). 외부 감사는 ③ 만 본다 (① · ② 는 운영 view).

3 격리 영역 매핑

본 reference 의 3 격리 영역 (3. DB 분할) 과 4 원장의 매핑:

  • core / customer domain — 고객 vault 라인 (customer_vault · customer_asset_wallet · customer_deposit_address) + counterparty registry. 4 원장 자체는 여기 없음 (참조만)
  • core / accounting domain — 4 원장 모두 위치. customer_ledger / bank_ledger / delta_ledger 는 webhook 으로 자동 갱신. general_ledger_entry 는 application 이 derived (이중부기 row 를 application 이 직접 INSERT). 5년 보존
  • compliance 영역 — 회계 영역의 외부 보고 (금감원 / 회계법인) 결과만

대표 8 시나리오의 데이터 변경 흐름. 각 시나리오마다 어느 표가 INSERT / UPDATE 되는지 + 이중부기 분개의 형태.

왜 1 표 (`general_ledger_entry`) 안에?
  • 모든 분개 row 가 같은 구조 (account_code · debit_credit · amount · source_ref · recorded_at) → 단일 표로 통일
  • 회계 query 단순 — "전체 자산 합" / "전체 부채 합" 등을 단일 표에서 GROUP BY 로 산출
  • 같은 거래의 rows 는 source_ref (예: transaction_request_id) 로 묶임 — 한 거래의 모든 분개 row 를 1 query 로 조회
핵심 invariant — 차변 합 = 대변 합 (DB 로 검증)
SELECT source_ref,
       SUM(CASE WHEN debit_credit='DEBIT'  THEN amount ELSE 0 END) AS debit_sum,
       SUM(CASE WHEN debit_credit='CREDIT' THEN amount ELSE 0 END) AS credit_sum
FROM general_ledger_entry
GROUP BY source_ref
HAVING SUM(CASE WHEN debit_credit='DEBIT' THEN amount ELSE -amount END) != 0;
-- 결과 0 row 이면 모든 거래의 차/대 합 일치 (정합 OK)

L1 대사 (19. 대사·결산·마감 22.2 절) 가 이 invariant 를 실시간으로 검증. 위반 시 alert + 거래 일시중단 고려.

미식별 입금 — 가수금(suspense)으로 격리 후 귀속

21.7 평가 / 환산 처리 (회계 layer)

본 절은 평가 3 layer (21.4 4 원장 구조 callout 참조) 중 ③ 회계 평가 (일말 1회) 에 한정. 운영 평가 (실시간 ①) 와 고객 포지션 (취득원가 ②) 은 본 절 범위 밖 — 21.8 고객 포지션 참조.

회계 평가는 마감 시점의 자산 잔액을 KRW 로 환산해 평가손익을 분개. 자산 분류에 따라 시세 source · 손익 계정이 다름:

자산 종류예시평가 방식시세 source손익 계정
법정통화 / stablecoin KRW-stablecoin · USDC · USDT 외화환산 (FX translation) 한국은행 매매기준율 / 고시환율 외화환산손익
변동성 자산 BTC · ETH · 기타 altcoin 시가평가 (Mark-to-market) 외부 거래소 종가 / oracle / 시장 평균가 가상자산평가손익

본 절의 패턴은 KR 외화 회계 표준 (매매기준율 + K-IFRS) 을 가상자산에 일반화한 권장. 가상자산이 K-IFRS 9 의 외환 분류에 해당하는지 자체가 hypothesis — 회계법인 / 외부 감사 검토 필수.

회계 평가의 3 가지 결정 사항

결정옵션권장 (저자)
평가 시점 일말 / 월말 일말 평가 (일별 마감). 거래 시점 환산은 별도 cache (asset_value_krw) — 회계 평가와는 분리
시세 기준 매매기준율 / 고시환율 / 시장환율 / 외부 oracle / 거래소 종가 stablecoin = 매매기준율 / 변동성 자산 = 외부 거래소 종가 (또는 oracle 의 일별 close)
평가 주기 일말 / 월말 일말 평가 (회계 표준). 운영 평가는 별도로 실시간 동작

운영 평가 (실시간) 의 결정은 ① 시세 feed (선정한 oracle / 거래소 — 단일 또는 multi-source 평균) · ② cache TTL (1 분 / 1 시간) · ③ source 다중화 정책 (oracle 하나가 문제 시 fallback) — 본 페이지 회계 view 와는 분리되어 시스템 운영 layer 의 결정.

3 가지 손익 분리

다음 손익을 별도 계정으로 분리하는 것이 회계 표준:

  • 외환매매수익 — 매매 거래 시점의 실현 손익 (예: 원화 → USDC 스왑 시점의 환차익)
  • 외화환산손익 (FX) — 마감 시점의 stablecoin 잔액을 원화로 환산 시 발생하는 미실현 손익 (환율 변동)
  • 가상자산평가손익 (MTM) — 변동성 자산 (BTC · ETH) 의 일일 시가 평가 변동 (시장가격 변동) — 매일 다른 평가금액이 누적되는 미실현 손익
예시 1 — 외화환산 (stablecoin)

거래 시점 분개 (스왑 자체) — 사용자 1 이 100 KRW-stablecoin → 0.1 USDC 스왑 (환율 1,000원/USD):

(차) KRW-stablecoin 반환채무   100원
        (대) USDC 반환채무             0.1 USD
            (= 100원 매매기준율 환산)

일말 외화환산 분개 (★ 본 절의 주제) — 마감 시 환율이 1,010원/USD 로 변동되면: 

(차) 외화환산손익                  1원
        (대) USDC 반환채무 평가증가     1원
            (0.1 USD × 10원 환율 차이)

첫 분개는 스왑 거래 (시나리오 ④ 의 거래 시점) 의 일부. 두 번째 분개가 본 절의 주제인 외화환산 (일말 평가손익 인식). 두 분개는 별도 시점 · 별도 trigger.

예시 2 — 시가평가 (변동성 자산)

고객 X 가 BTC 0.5 보유. 거래 시점 평가 = 50,000,000 KRW/BTC 기준 → 25,000,000 KRW.

다음날 일말 종가가 52,000,000 KRW/BTC 로 상승하면 평가금액 = 26,000,000 KRW (+1,000,000 KRW). 평가손익 분개: 

(차) BTC 반환채무 평가증가     1,000,000원
        (대) 가상자산평가손익        1,000,000원
            (0.5 BTC × 2,000,000원 시세 상승)

하루마다 종가가 다르므로 평가금액이 매일 갱신됨. 원장의 BTC 수량 (0.5) 은 그대로, 평가금액만 변동. 다음날 시세가 하락하면 reverse 분개 (가상자산평가손실 / BTC 반환채무 평가감소).

21.8 고객 포지션 (평단가 · 미실현 손익)

사용자가 앱 / 웹에서 보는 "보유 자산 + 평단가 + 평가손익 (P&L)" 화면 의 데이터 모델. 거래소 (Upbit · Binance) · 증권사 MTS 와 동일한 책임. 회계 평가 (③) 와 별개의 운영 view 이며, 고객 진입가 (취득원가) 대비 현재가 손익 을 표시.

사용자 시나리오 — "내가 13:00 에 입금한 USDC, 1 시간 후 손익?"
13:00  USDC 10 입금  · 시세 1,300원/USDC  → 취득원가 = 13,000원

  미실현 손익  = 13,100 - 13,000 = +100원

회계 평가와의 정합

  • 회계 평가손익 (일말 종가 기준) ≠ 고객 미실현 손익 (취득원가 기준). 두 view 는 시점 / 기준 자체가 다름
  • 회계는 "오늘 종가 기준 잔액의 KRW 가치 변동" 만 인식 → 고객 진입가 정보 사용 X
  • 고객 P&L 은 "진입가 대비 현재가 손익" 표시 → 회계 분개 발생 X (사용자 view 만)
  • 실현 손익 (출금 / 매도 시 손익) 은 회계의 외환매매수익과 매핑 가능 — 회계법인 자문 필요
★ 운영 시작 전 검증 필수

본 절은 저자 권장 — 실제 운영 시 다음 결정 필요:

  • 평균단가법 vs FIFO 선택 — 회계법인 자문 (가상자산 세무 · K-IFRS 9 적용)
  • 고객 진입가 시세 source — 거래 시점의 oracle / 거래소 ticker 결정 (asset_value_krw cache 활용)
  • 외부 이체 (deposit from external wallet) 의 취득원가 — 외부에서 들어온 자산의 진입가는 입금 시점 시세로 설정. 단 사용자가 직접 진입가 입력 가능한 옵션 (예: "내가 1년 전 산 BTC 를 입금" 케이스) 검토
  • 실현 손익 시점 — 출금 시점 vs 매도 시점. 출금만 있고 매도가 없는 모델이면 출금 시점이 실현 시점

관계선 의미 — 모든 화살표 해설

카디널리티 (1:N · N:1) 읽는 법

표끼리의 연결 비율을 나타냄. "왼쪽 표의 1 row 가 오른쪽 표의 몇 row 와 연결되는가" 의 표기:

  • 1:1 — 왼쪽 1 ↔ 오른쪽 1 (정확히 짝)
  • 1:N — 왼쪽 1 → 오른쪽 여러 개 (부모 1 → 자식 N)
  • N:1 — 왼쪽 여러 개 → 오른쪽 1 (자식 N → 부모 1)
  • N:M — 양쪽 다 여러 개 (학생 N ↔ 강의 M)

예: 고객 원장 → 총계정 분개 (1:N) — 고객이 USDC 10 입금하면 고객 원장에 1 row 생기고, 이중부기로 총계정 분개에는 (차)자산 / (대)부채 2 row 가 생긴다 → 1 row 가 N row 와 연결.

데이터 무결성 — 쓰기 시점 강제 (컬럼 schema 확정 stage)

대사(L1~L4)는 사후 검출이다. 그 전에 쓰기 시점에 깨지지 않도록 강제하는 두 불변식을 스키마 / 트랜잭션에 못박아야 한다(컬럼 schema 확정 stage에서):

  • subledger 1행 보장 — customer_ledger · customer_position 에 UNIQUE(user_id, asset_id) + UPSERT (ON CONFLICT). 신규 고객의 첫 거래가 동시에 2건 들어와도 행이 중복 생기지 않는다. 행이 아직 없으면 row-level lock 만으로는 막을 수 없어 unique 제약이 필요하다.
  • 차변 = 대변 강제 — general_ledger_entry 는 application 이 이중부기로 직접 INSERT 하므로, 버그로 한쪽만 들어가면 항등식이 깨진다. 같은 source_ref 묶음의 Σ차변 = Σ대변 을 트랜잭션 종료 전 assertion 또는 DB 제약(deferred constraint · 트리거)으로 강제한다.

이 둘이 있어야 대사가 "정합을 만드는" 작업이 아니라 "이미 정합인 것을 재확인"하는 작업이 된다.
