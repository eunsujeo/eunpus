18. 회계 · 원장 설계

온체인 + 오프체인 + 계정계 3 계층 정합 · 회계 항등식 · 4 원장 구조 · 손익 / 외화환산
본 영역의 출처 — vendor 공식 자료 부재

Fireblocks 는 회계·원장·결산을 다루지 않는다 (vault 잔액 API · audit log 까지만 제공). 따라서 본 도메인은 다음 3 tier 로 출처를 구분한다.

  • Fireblocks 공식 사실 — Fireblocks 공식 URL 링크 명시 (vault balance · webhook event 등)
  • 일반 수탁업 회계 패턴 — 은행 · 자산운용업 표준 (이중부기 · 자산-부채-자기자본 항등식 · 외화환산 · 결산 등)
  • 본 reference 의 권장 설계 (work-in-progress) — 본 영역의 패턴은 수탁업 설계 초기 단계의 일반 권장. 운영 시작 전 회계법인 / 외부 감사 / 내부 회계팀 검증 권장
★ 본 페이지의 정의 수준 — 도메인 view 까지

본 페이지는 회계 4 원장 구조 / 거래 매트릭스 / 회계 항등식 / 외화환산 정책 / 손익 계정 분류 같은 도메인 view (master 설계) 까지 정의한다. 각 표 (customer_ledger · bank_ledger · delta_ledger · general_ledger_entry · general_ledger_snapshot · fx_rate_history · fx_revaluation_log · accounting_correction_log) 의 column-level schema 는 정의하지 않음.

이유: 회계 column schema 는 회계법인 / KR 회계 표준 (K-GAAP / K-IFRS) 자문 + 외부 감사 의견 후 확정되어야 후속 변경 비용이 작다. 표명 + 책임 + 대표 column 까지만 정의하고, 정확한 column / type / constraint 는 별도 stage 에서 자문 후 추가 예정. 운영 시작 시점에는 본 페이지의 view 를 base 로 회계법인과 함께 column schema 확정 권장.

회계 9 표 + 외부 도메인 (customer.customer_vault · transaction.vendor_transaction) 참조 관계. 모든 거래가 general_ledger_entry 로 귀결 (이중부기) → general_ledger_snapshot 일별 박제 + hash chain 무결성. customer_balance_snapshot · fx_rate_history · fx_revaluation_log 는 일말 cron 영역.

3 type 의 트리거 분류

  • 거래 trigger (실시간) — customer_ledger · bank_ledger · delta_ledger 갱신 시 매번 general_ledger_entry 이중부기 row INSERT (webhook handler 또는 거래 service 가 동시 commit)
  • 외화환산 trigger (일말 cron) — fx_rate_history 의 당일 환율 + 전 자산 잔액으로 fx_revaluation_log 산출 → general_ledger_entry 외화환산 분개 INSERT
  • 정정 trigger (Admin Quorum 매개) — 오류 발견 시 accounting_correction_log INSERT + 원본 entry 의 reverse 분개 + 새 entry. hash chain 위에 분개 추가 (변조 아님)

18.2 왜 회계 영역이 별도 도메인인가

Fireblocks 의 vault balance API · webhook event 는 "자산이 어디에 얼마나 있는가" 까지만 알려준다. 은행 회계는 그 위에 다음을 추가로 요구한다:

  • 이중부기 — 모든 거래가 차변 / 대변 동시 갱신, 회계 항등식 유지
  • 고객 단위 잔액 (subledger) — Fireblocks 의 vault 잔액 ≠ 고객별 잔액 (특히 omnibus vault 시)
  • 법정통화 환산 — 가상자산을 원화 / 달러로 환산하여 총자산 산출
  • 손익 인식 — 수수료수익 · 외환매매수익 · 외화환산손익 · 가스비 등
  • 결산 — 시점 기준 잔액 박제 + 정정 절차
  • 외부 감사 대응 — 회계법인이 받아 보는 양식

18.4 회계 항등식 — 시스템의 핵심 불변식

자산총액 = 반환채무 총액 + 자기자본

모든 거래 후에 이 항등식이 깨지면 즉시 시스템 정지 수준의 사고. 일반 수탁업 회계의 표준 항등식 (이중부기의 기본).

구성 요소 (자산 측)

  • 각 자산 종류별 온체인 잔액 합계 (Hot · Cold · Treasury vault 의 총합)
  • 각 자산 종류별 오프체인 미반영 차액 (델타 원장의 pending)
  • 법정통화 잔액 (계정계 측)

구성 요소 (부채 측 = 반환채무)

  • 각 자산 종류별 고객 잔액 합계 (고객 원장의 UserID 별 잔액의 합)
  • 고객별 미인출 자산은 모두 은행의 "반환 의무" 로 인식

구성 요소 (자기자본)

  • 자기자본 = 자산총액 − 반환채무 (산출 또는 별도 계정)
  • 은행의 자체 자산 + 누적 손익
자기자본 — 산출값 vs 별도 계정 (설계 결정)

두 가지 옵션:

  • 옵션 1 — 산출값: 자기자본 = 자산 − 부채 (쿼리로 매번 계산). 별도 row 없음
  • 옵션 2 — 별도 계정: 자기자본 계정을 별도 row 로 보유 + 변동 거래 이력 + 일별 스냅샷

권장 (저자) — 옵션 2. 이유:

  • 음수 진입 차단 (자기자본 음수 = 고객자산 잠식) 의 DB 제약 적용 용이
  • 일별 스냅샷이 immutable hash chain 으로 변조 방지 가능
  • 외부 감사 시 자기자본의 시점별 추적이 쉬움
  • 운영 잔액 (자체 vault) vs 회계 잔액 (자기자본) 분리 명확화

18.5 4 원장 구조

오프체인 수탁 원장은 4 가지로 분리. 각 원장이 책임과 데이터 특성이 다름.

원장책임변경 패턴대표 column
고객 원장
(customer_ledger)
★ subledger		 UserID 별 자산 종류별 잔액·거래 이력. 5.4 / 14. 3 DB 매핑

본 reference 의 3 DB (3. DB 분할) 와 4 원장의 매핑:

  • core 영역 — 고객 vault 라인 (customer_vault · customer_asset_wallet · customer_deposit_address) + counterparty registry. 4 원장 자체는 여기 없음
  • core 영역 — 4 원장 모두 위치. customer_ledger / bank_ledger / delta_ledger 는 webhook 으로 자동 갱신. general_ledger 는 application 이 derived (이중부기 row 를 application 이 직접 INSERT). 5년 보존
  • compliance 영역 — 회계 영역의 외부 보고 (금감원 / 회계법인) 결과만

18.6 거래 유형별 원장 영향 매트릭스

수탁업의 6 가지 대표 거래 유형 × 4 원장 + 계정계 (법정통화) 영향. 거래마다 어느 원장을 갱신하는지 사전 정의. SND = Send (송금), RECV = Receive (수취) 약어.

관찰 — 거래 복잡도

  • 가장 가벼움: 내부 이체 (고객 원장만)
  • 가장 복잡: 온램프 · 스왑 · 오프램프 (4 원장 동시 갱신, 트랜잭션 원자성 critical)
  • 특이: 외부 수취 — 자산·부채 동시 증가, 자기자본 변동 없음 (양변 균등 증가)
  • 온체인 발생: Mint · 외부 수취 (vault 의 실제 입금)
  • 온체인 미발생: 내부 이체 · 스왑 (오프체인 원장 갱신만, 추후 정산)
트랜잭션 원자성의 위협

온램프 / 스왑 / 오프램프 는 4 원장을 한 transaction 으로 갱신해야 함. 그러나 본 reference 의 3 DB 가 서로 분리되어 있어 multi-DB transaction 불가능. 해결: outbox pattern — core 영역에 결정 row + outbox row 동시 commit, worker 가 외부 시스템 (계정계 / AML) 으로 비동기 복제. 실패 시 idempotent retry. eventual consistency 보장. 출금 lifecycle 의 multi-system commit 흐름은 14. Deposit · Withdrawal Flow 참조.

시나리오 ⑤ 자산 스왑 (delta_ledger 패턴 — off-chain immediate + settlement)

앞 4 시나리오는 customer_ledger / bank_ledger / general_ledger_entry 만 갱신 — delta_ledger 는 사용 안 함 (외부 입금 / 출금 / 내부 이체 / 일말 환산은 즉시-반영 vs 정산-지연 의 timing gap 이 없음). delta_ledger 는 "off-chain 즉시 반영 + on-chain settlement 시점 차이" 가 있는 경우에 사용 — 18.6 절 매트릭스의 온램프 · 자산 스왑 · 오프램프 3 케이스가 해당.

본 시나리오는 자산 스왑 (스테이블코인 A → B) 으로 delta_ledger 패턴을 보여준다 — 사용자 UI 에는 즉시 잔액 변동, 은행 측의 실제 vault 재조달 (외부 거래소 매개 또는 자체 swap) 은 별도 시점에 settlement. 오프램프 (USDC → 원화) · 온램프 (원화 → USDC) 도 동일 패턴 적용.

2-step 패턴: Step 1 (즉시 — customer_ledger + delta_ledger pending) 에서 UI 응답성 확보, Step 2 (settlement — delta cleared + general_ledger 정산 분개) 에서 회계 정합성 회복. delta_ledger 의 pending row 가 회계 항등식 임시 균형 유지 (외부 정산 완료 전까지 자산/부채 양변 모두 미정산 표기).

delta_ledger 가 필요한 이유
  • UX — 사용자가 스왑 / 온램프 / 오프램프 요청 시 외부 정산 (수 분 ~ 수 시간) 을 기다리지 않고 즉시 UI 반영. 사용자 응답 시간 SLA 충족
  • 회계 항등식 유지 — Step 1 시점에 자산 vault 가 실제 변동되지 않았는데 customer_ledger 만 변동하면 항등식이 깨진다. delta_ledger 의 미정산 자산/부채 row 가 이 gap 을 매개
  • 외부 감사 추적 — 정산 지연이 발생한 거래의 시점 / 원인 / 정산 완료 시점이 별도 audit trail. delta_ledger.settlement_status 의 ageing 모니터링으로 stuck pending detection
  • 대사 명확화 — L1 대사 시 (19.2 절) "customer_ledger 합 ≠ on-chain vault 합" 인 경우 delta_ledger 의 pending 합으로 균형 검증 가능
매트릭스의 다른 delta_ledger 케이스 (18.6 절 참조)
  • 온램프 (법정통화 → stablecoin) — KRW 즉시 차감 (계정계) + USDC 즉시 증가 (customer_ledger) + delta_ledger pending → 외부 USDC 매입 settlement 후 cleared
  • 오프램프 (stablecoin → 법정통화) — USDC 즉시 차감 + KRW 약속 (계정계 입금 대기) + delta_ledger pending → 외부 USDC 매도 settlement 후 KRW 실 입금 + cleared
  • 자산 스왑 (본 시나리오) — 스테이블코인 A ↔ B

18.8 손익 계정 분류 (저자 hypothesis)

수탁업의 일반적 손익 계정 구조 — 본 분류는 저자의 일반 권장이며 K-IFRS 9 / K-GAAP 의 정확한 분류는 회계법인 검토 필수. 특히 가상자산을 "외환" 으로 분류 가능한지 / 별도 자산 분류가 필요한지는 회계 기준 적용 자체가 hypothesis.

설계 결정 — 자산별 분리 vs 통합

  • 옵션 1 — 통합 계정: 수수료수익 1 계정 + 자산 보조부 (asset_id 별 분리). 회계 단순, 보조부 query 필요
  • 옵션 2 — 자산별 분리: KRW-stablecoin 수수료수익 · USDC 수수료수익 등 별도 계정. 회계 복잡, 즉시 query 가능
  • 권장 (저자): 옵션 1 (통합 + 보조부). 회계법인이 일반적으로 선호하는 패턴. 자산 종류 증가 시 계정 확장 부담 적음. 단 회계법인 / 내부 회계팀의 권장이 다를 수 있으므로 검증

18.9 외화환산 처리 (저자 hypothesis)

다통화 자산 보유 시 (예: 원화 stablecoin + USDC 등) 환율 적용 시점 결정이 필요. 본 절의 패턴은 KR 외화 회계의 표준 (한국은행 매매기준율 + K-IFRS) 을 가상자산에 일반화한 권장 — 가상자산이 K-IFRS 9 의 외환 분류에 해당하는지 자체가 hypothesis 라 회계법인 검토 필수.

3 가지 결정 사항

결정옵션권장 (저자)
환율 적용 시점 거래 시점 / 일말 / 월말 거래 시점 (실제 거래의 환율) + 일말 (평가용 환산) 병행
환율 기준 매매기준율 / 고시환율 / 시장환율 매매기준율 (외화 회계의 표준)
환산 주기 실시간 / 일말 / 월말 일말 환산 (일별 마감 시 외화 잔액 → 원화 환산)

평가손익 분리

다음 3 가지 손익을 별도 계정으로 분리하는 것이 회계 표준:

  • 외환매매수익 — 매매 거래 시점의 실현 손익 (예: 원화 → USDC 스왑 시점의 환차익)
  • 외화환산손익 — 마감 시점의 외화 잔액을 원화로 환산 시 발생하는 미실현 손익
  • 외화평가손익 — 외화 자산의 시가 평가 변동 (시장가격 변동)
예시 거래 — 회계 처리

        (대) USDC 반환채무 평가증가     1원
            (0.1 USD × 10원 환율 차이)

18.11 펀드 수신 시스템 / 자산운용업과의 패턴 차용 (저자 권장)

수탁업의 회계는 펀드 수신 시스템 (자산운용업의 펀드 — 투자자 자금을 모아 자산별 잔액을 관리하는 시스템) / 자산운용업의 회계와 패턴이 유사. 본 절의 차용 권장은 일반 회계 표준화 관점의 저자 의견이며, 실제 시스템 차용 시 회계법인 / 운용업계 표준 (한국금융투자협회 등) 와 정합성 검토 필수. 차용 가능한 항목:

  • 계정과목 체계 — 펀드의 계정과목 (수수료수익 · 외환매매수익 · 외화환산손익 등) 을 참고
  • 대사 자동화 프레임워크 — 펀드 시스템의 대사 도구 / 보고 양식 활용 (19. 대사 · 결산 · 마감 참조)
  • 외화 종목 처리 방식 — 펀드의 외화 표시 종목의 환산 / 평가 패턴
  • 일말 / 월말 마감 schedule — 기존 은행 / 운용업의 마감 schedule 과 정합
  • immutable 스냅샷 보장 매커니즘 — 펀드의 마감 잔액 스냅샷 보장 패턴
★ 운영 시작 전 검증 필수
