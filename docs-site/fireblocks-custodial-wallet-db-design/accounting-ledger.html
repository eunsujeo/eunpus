15. 회계 · 원장 설계

온체인 + 오프체인 + 계정계 3 계층 정합 · 회계 항등식 · 4 원장 구조 · 손익 / 외화환산
본 영역의 출처 — vendor 공식 자료 부재

Fireblocks 는 회계·원장·결산을 다루지 않는다 (vault 잔액 API · audit log 까지만 제공). 따라서 본 도메인은 다음 3 tier 로 출처를 구분한다.

  • Fireblocks 공식 사실 — Fireblocks 공식 URL 링크 명시 (vault balance · webhook event 등)
  • 일반 수탁업 회계 패턴 — 은행 · 자산운용업 표준 (이중부기 · 자산-부채-자기자본 항등식 · 외화환산 · 결산 등)
  • 본 reference 의 권장 설계 (work-in-progress) — 본 영역의 패턴은 수탁업 설계 초기 단계의 일반 권장. 운영 시작 전 회계법인 / 외부 감사 / 내부 회계팀 검증 권장

15.1 왜 회계 영역이 별도 도메인인가

Fireblocks 의 vault balance API · webhook event 는 "자산이 어디에 얼마나 있는가" 까지만 알려준다. 은행 회계는 그 위에 다음을 추가로 요구한다:

  • 이중부기 — 모든 거래가 차변 / 대변 동시 갱신, 회계 항등식 유지
  • 고객 단위 잔액 (subledger) — Fireblocks 의 vault 잔액 ≠ 고객별 잔액 (특히 omnibus vault 시)
  • 법정통화 환산 — 가상자산을 원화 / 달러로 환산하여 총자산 산출
  • 손익 인식 — 수수료수익 · 외환매매수익 · 외화환산손익 · 가스비 등
  • 결산 — 시점 기준 잔액 박제 + 정정 절차
  • 외부 감사 대응 — 회계법인이 받아 보는 양식

3 계층 — 파랑 = 온체인 (블록체인의 실제 자산) / 초록 = 오프체인 수탁 원장 (은행 application 의 자체 원장) / 노랑 = 계정계 (기존 은행의 법정통화 시스템). 거래 발생 시 3 계층이 동시 갱신, 정기 대사로 정합성 검증.

15.3 회계 항등식 — 시스템의 핵심 불변식

자산총액 = 반환채무 총액 + 자기자본

모든 거래 후에 이 항등식이 깨지면 즉시 시스템 정지 수준의 사고. 일반 수탁업 회계의 표준 항등식 (이중부기의 기본).

구성 요소 (자산 측)

  • 각 자산 종류별 온체인 잔액 합계 (Hot · Cold · Treasury vault 의 총합)
  • 각 자산 종류별 오프체인 미반영 차액 (델타 원장의 pending)
  • 법정통화 잔액 (계정계 측)

구성 요소 (부채 측 = 반환채무)

  • 각 자산 종류별 고객 잔액 합계 (고객 원장의 UserID 별 잔액의 합)
  • 고객별 미인출 자산은 모두 은행의 "반환 의무" 로 인식

구성 요소 (자기자본)

  • 자기자본 = 자산총액 − 반환채무 (산출 또는 별도 계정)
  • 은행의 자체 자산 + 누적 손익
자기자본 — 산출값 vs 별도 계정 (설계 결정)

두 가지 옵션:

  • 옵션 1 — 산출값: 자기자본 = 자산 − 부채 (쿼리로 매번 계산). 별도 row 없음
  • 옵션 2 — 별도 계정: 자기자본 계정을 별도 row 로 보유 + 변동 거래 이력 + 일별 스냅샷

권장 (저자) — 옵션 2. 이유:

  • 음수 진입 차단 (자기자본 음수 = 고객자산 잠식) 의 DB 제약 적용 용이
  • 일별 스냅샷이 immutable hash chain 으로 변조 방지 가능
  • 외부 감사 시 자기자본의 시점별 추적이 쉬움
  • 운영 잔액 (자체 vault) vs 회계 잔액 (자기자본) 분리 명확화

15.4 4 원장 구조

오프체인 수탁 원장은 4 가지로 분리. 각 원장이 책임과 데이터 특성이 다름.

원장책임변경 패턴대표 column
고객 원장
(customer_ledger)		 UserID 별 자산 종류별 잔액·거래 이력 거래 이력 = append-only / 잔액 = M-cache user_id · asset_id · balance · last_tx_id
은행 자체 원장
(bank_ledger)		 은행의 자체 보유분 (gas station · treasury · 수수료 수익 등) 거래 이력 = append-only / 잔액 = M-cache account_type · asset_id · balance
델타 원장
(delta_ledger)		 미정산 차액 — 오프체인 거래는 즉시 반영, 온체인 confirmation 전까지 pending append-only + 정산 플래그 (mutable) delta_type · asset_id · amount · settlement_status
총계정 원장
(general_ledger)		 자산·부채·자기자본의 통합 view (회계 항등식 enforce) 일별 스냅샷 = append-only / 잔액 = derived account_code · debit · credit · balance · snapshot_date

3 DB 매핑

본 reference 의 3 DB (3. DB 분할) 와 4 원장의 매핑:

  • customerdb — 고객 식별 정보만 (잔액 mirror 제외)
  • mirrordb — 4 원장 모두 위치. webhook 으로 자동 갱신 + 5년 보존
  • compliancedb — 회계 영역의 외부 보고 (금감원 / 회계법인) 결과만

15.5 거래 유형별 원장 영향 매트릭스

수탁업의 6 가지 대표 거래 유형 × 4 원장 + 계정계 (법정통화) 영향. 거래마다 어느 원장을 갱신하는지 사전 정의.

거래 유형온체인고객 원장은행 원장델타 원장총계정 변화
Stablecoin Mint
(은행 발행)		○−○−자산 ↑

(법정통화 → stablecoin)		−○○○부채 ↑

자산 스왑
(stablecoin A → B)		−○○○−
오프램프

관찰 — 거래 복잡도

  • 가장 가벼움: 내부 이체 (고객 원장만)
  • 가장 복잡: 온램프 · 스왑 · 오프램프 (4 원장 동시 갱신, 트랜잭션 원자성 critical)
  • 특이: 외부 수취 — 자산·부채 동시 증가, 자기자본 변동 없음 (양변 균등 증가)
  • 온체인 발생: Mint · 외부 수취 (vault 의 실제 입금)
  • 온체인 미발생: 내부 이체 · 스왑 (오프체인 원장 갱신만, 추후 정산)
트랜잭션 원자성의 위협

온램프 / 스왑 / 오프램프 는 4 원장을 한 transaction 으로 갱신해야 함. 그러나 본 reference 의 3 DB 가 서로 분리되어 있어 multi-DB transaction 불가능. 해결: outbox pattern — mirrordb 에 결정 row + outbox row 동시 commit, worker 가 외부 시스템 (계정계 / AML) 으로 비동기 복제. 실패 시 idempotent retry. eventual consistency 보장.

설계 결정 — 자산별 분리 vs 통합

  • 옵션 1 — 통합 계정: 수수료수익 1 계정 + 자산 보조부 (asset_id 별 분리). 회계 단순, 보조부 query 필요
  • 옵션 2 — 자산별 분리: KRW-stablecoin 수수료수익 · USDC 수수료수익 등 별도 계정. 회계 복잡, 즉시 query 가능
  • 권장 (저자): 옵션 1 (통합 + 보조부). 회계법인이 일반적으로 선호하는 패턴. 자산 종류 증가 시 계정 확장 부담 적음. 단 회계법인 / 내부 회계팀의 권장이 다를 수 있으므로 검증

15.7 외화환산 처리

다통화 자산 보유 시 (예: 원화 stablecoin + USDC 등) 환율 적용 시점 결정이 필요.

3 가지 결정 사항

결정옵션권장 (저자)
환율 적용 시점 거래 시점 / 일말 / 월말 거래 시점 (실제 거래의 환율) + 일말 (평가용 환산) 병행
환율 기준 매매기준율 / 고시환율 / 시장환율 매매기준율 (외화 회계의 표준)
환산 주기 실시간 / 일말 / 월말 일말 환산 (일별 마감 시 외화 잔액 → 원화 환산)

평가손익 분리

다음 3 가지 손익을 별도 계정으로 분리하는 것이 회계 표준:

  • 외환매매수익 — 매매 거래 시점의 실현 손익 (예: 원화 → USDC 스왑 시점의 환차익)
  • 외화환산손익 — 마감 시점의 외화 잔액을 원화로 환산 시 발생하는 미실현 손익
  • 외화평가손익 — 외화 자산의 시가 평가 변동 (시장가격 변동)
예시 거래 — 회계 처리

사용자 1 이 100 KRW-stablecoin → 0.1 USDC 스왑 (환율 1,000원/USD):

(차) KRW-stablecoin 반환채무   100원
        (대) USDC 반환채무             0.1 USD
            (= 100원 매매기준율 환산)

이후 일말 마감 시 환율이 1,010원/USD 로 변동되면: 

(차) 외화환산손익                  1원
        (대) USDC 반환채무 평가증가     1원
            (0.1 USD × 10원 환율 차이)

15.8 mirrordb 와의 통합

15.9 펀드 수신 시스템 / 자산운용업과의 패턴 차용

수탁업의 회계는 펀드 수신 시스템 / 자산운용업의 회계와 패턴이 유사. 차용 가능한 항목:

  • 계정과목 체계 — 펀드의 계정과목 (수수료수익 · 외환매매수익 · 외화환산손익 등) 을 참고
  • 대사 자동화 프레임워크 — 펀드 시스템의 대사 도구 / 보고 양식 활용 (16. 대사 · 결산 · 마감 참조)
  • 외화 종목 처리 방식 — 펀드의 외화 표시 종목의 환산 / 평가 패턴
  • 일말 / 월말 마감 schedule — 기존 은행 / 운용업의 마감 schedule 과 정합
  • immutable 스냅샷 보장 매커니즘 — 펀드의 마감 잔액 스냅샷 보장 패턴
★ 운영 시작 전 검증 필수
