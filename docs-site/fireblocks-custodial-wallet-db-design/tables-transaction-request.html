15. Transaction Request · Execution

통합 거래 요청 / 실행 schema — withdrawal · swap · onramp · offramp 4 type 통합 2-layer 모델
본 페이지의 범위

모든 고객 발생 거래의 요청 (bank intent) + 실행 (vendor lifecycle) 2-layer 통합 schema. 4 type 의 거래를 type 컬럼으로 구분 — 외부 출금 (withdrawal) · 자산 스왑 (swap) · 온램프 (onramp) · 오프램프 (offramp). 외부 입금은 사용자 요청이 없으므로 (외부에서 발생) 별도 처리 — 14. Deposit · Withdrawal Flow 14.1 절 참조.

15.1 schema 설계 — Header + Detail (request) · Unified (execution)

은행 환경 (규제 / 장기 운영 / 외부 감사) 을 고려해 다음 mixed 패턴 적용:

  • Request layer = Header + Detail 패턴 — type 별 컬럼 차이가 크므로 (withdrawal 의 destination 정보 vs swap/ramp 의 target/quoted_rate) DB constraint 보장 + 명확한 schema 를 위해 분리. 헤더 (공통) + 3 detail 표 (withdrawal · swap · ramp)
  • Execution layer = Unified (단일 표) — vendor lifecycle 은 type 무관하게 동일 (PENDING → SUBMITTED → BROADCASTING → COMPLETED). channel enum + metadata 로 type-specific 흡수 가능. detail 분리 시 거의 빈 표가 되어 over-engineering
관점Header + Detail (request)Unified (execution)
DB 무결성✅ detail 표의 NOT NULL · CHECK · FK 강제type-specific 컬럼 거의 없음 → constraint 부담 적음
cross-type query✅ 헤더만 query (UNION 불필요)✅ 단일 표
type 확장✅ detail 표 추가만 (헤더 영향 X)enum + channel 추가만
source_ref FK 통합✅ 헤더 단일 FK target✅ 단일 표
외부 감사 명확성✅ 표명 = type 자명 (withdrawal_request_detail 등)execution 은 vendor lifecycle 통일
INSERT 복잡도⚠️ 헤더 + 디테일 동시 transaction✅ 단일 INSERT

이 mixed 패턴은 은행 코어 시스템 (SAP CFM · Murex 등) 의 일반 패턴. 요청 layer 는 type 별 다양 → 분리 / 실행 layer 는 vendor lifecycle 통일 → 단일.

15.2 2-layer 모델 — request vs execution

한 거래 = 1 헤더 + 1 디테일 (type 별) → N execution. request layer 는 customer-facing (bank intent · 헤더 공통 + type 별 디테일), execution 은 vendor lifecycle (Fireblocks · JV · Circle · 외부 거래소).

Request layer (파랑) = 헤더 + 3 디테일 · Execution layer (초록) = 통합 · External (노랑) = vendor 시스템. 2-layer 분리 이유: ① bank intent (고객 의지 · KYC · 한도 · 검증) vs vendor lifecycle (Fireblocks broadcast · settlement) 의 책임 분리. ② 1 요청에 N 실행 (재시도 · multi-leg swap · chunk 출금). ③ 실패 / 재시도 시 헤더 / 디테일 그대로, execution row 만 추가. Header + Detail 분리 이유: ④ type 별 컬럼 차이 (destination_* vs target_* + quoted_rate) 가 커서 DB NOT NULL · CHECK constraint 로 무결성 강제. ⑤ 새 type 추가 시 새 디테일 표만 (헤더 영향 X).

15.3 Request layer — Header + 3 Detail tables

customer-facing 요청 layer 는 헤더 1 표 + type 별 디테일 3 표로 분리. 헤더는 4 type 공통 컬럼만, 디테일은 type 별 필수 컬럼 (DB NOT NULL · CHECK 강제).

15.3.1 customer.transaction_request — 헤더 (공통)

4 type (withdrawal · swap · onramp · offramp) 공통 컬럼만. 1 요청 = 헤더 1 row + 해당 type 의 디테일 표 1 row (1:1).

헤더 INSERT 와 디테일 INSERT 는 단일 transaction 으로 동시 처리 (application layer 책임). 헤더 row 가 있는데 디테일 row 가 없는 상태는 회계 무결성 깨짐 → application + trigger 로 enforce. 새 type 추가 시 새 detail 표만 추가 (헤더 영향 X).

15.6 type 별 사용 패턴

WITHDRAWAL — 외부 출금

1 request → 1 execution (보통). 재시도 시 leg_index=2, 3 추가. channel = FIREBLOCKS_DIRECT. 사용 표: 헤더 + withdrawal_request_detail (destination_address · destination_type · counterparty_ref_id). 회계 / lifecycle 상세는 14. Deposit · Withdrawal Flow 14.2 절 참조.

SWAP — 자산 스왑 (예: KRWK → USDC)

1 request → 2 execution (OUTBOUND + INBOUND). 사용 표: 헤더 + swap_request_detail (target_asset_id · target_amount · quoted_rate · swap_route_preference). channel 옵션:

  • FIREBLOCKS_SWAP_API — Fireblocks 의 swap API 매개 (내부적으로 거래소 / DEX 활용)
  • EXTERNAL_EXCHANGE — 외부 거래소 (Coinbase 등) 의 pair 매매
  • JV_BURN + CIRCLE_MINT — KRWK burn (JV) + USDC mint (Circle) 직접 연계 (1차 시장)

회계 / 시나리오 상세는 21. 회계 · 원장 설계 21.6 절 시나리오 ④ 참조.

ONRAMP — 법정통화 → 스테이블코인

1 request → 1 execution (INBOUND). 사용 표: 헤더 + ramp_request_detail (target_asset_id · target_amount · quoted_rate · channel_preference). channel 옵션:

  • JV_MINT (KRWK 의 경우) — JV 에 mint 요청
  • CIRCLE_MINT (USDC 의 경우 1차 시장) — Circle mint API
  • EXTERNAL_EXCHANGE (USDC 2차 시장) — 거래소 매입

계정계 KRW 차감은 outbox 별도. 시나리오 상세는 21. 회계 · 원장 설계 21.6 절 시나리오 ⑤ 참조.

OFFRAMP — 스테이블코인 → 법정통화

1 request → 1 execution (OUTBOUND). 사용 표: 헤더 + ramp_request_detail (target = KRW · fiat_account_ref · quoted_rate). channel 옵션:

  • JV_BURN (KRWK) — JV burn 요청
  • CIRCLE_REDEEM (USDC 1차) — Circle redeem API
  • EXTERNAL_EXCHANGE (USDC 2차) — 거래소 매도

계정계 KRW 입금은 outbox 별도. 시나리오 상세는 21. 회계 · 원장 설계 21.6 절 시나리오 ⑥ 참조.

프론트엔드 통합 timeline 가이드 (참고)

사용자 지갑 앱의 "거래 내역" 은 일반적으로 4 type + 외부 입금을 통합 timeline 으로 표시 (Upbit · Binance · 은행 앱 · 증권사 MTS 표준). 본 schema 가 이 UX 를 지원하는 방식:

  • 통합 timeline query — 헤더 (transaction_request) 만 SELECT 로 4 type 시간 순 list 즉시 (UNION 불필요)
  • type 별 UI 분기 — header.type 으로 아이콘 / 색상 매핑
  • 미완료 거래 표시 — header.request_status (PENDING / SUBMITTED / COMPLETED 등) 통합 enum 으로 type 무관 pending 표시 가능
  • 상세 보기 — 클릭 시 type 별 디테일 표 JOIN (1 query)
  • ⚠️ 외부 입금 갭 — deposit_observations 는 별도 source. frontend 가 두 source merge 필요 (옵션 A · 표준 패턴) 또는 read-only view 로 통합 (옵션 B)

본 wiki 는 DB / backend schema 까지만 다룸. 프론트엔드 UI 모델 (아이콘 · 색상 · 레이아웃) 은 별도 영역. 본 가이드는 schema 가 통합 timeline 을 지원함을 확인하는 정도.

Header + 3 Detail (request) + Unified (execution): 헤더 (4 type 공통) ↔ 3 디테일 (type 별 1:1 · DB CHECK 강제) ↔ execution (N · type 무관 통합). 헤더 row 와 그에 해당하는 디테일 row 는 동일 transaction 으로 INSERT (application layer enforcement). cross-domain (customer / transaction) FK 는 application 또는 cross-schema FK.

15.8 운영 시작 전 검증 + trade-off

★ 운영 시작 전 검증 필수
  • 헤더 ↔ 디테일 무결성 — 헤더 type 과 디테일 표 매칭 검증 (CHECK constraint + application). 헤더 row 있는데 디테일 없는 상태 방지 — trigger 또는 application transaction
  • 1:1 관계 enforcement — 디테일의 transaction_request_id 가 PK + FK 라 자연스럽게 1:1. 다만 type 별로 정확히 1 detail row 만 존재해야 함 (다른 type 의 detail 표에 잘못 들어가지 않도록)
  • execution 의 channel 별 status 매핑 — JV / Circle channel 의 execution_status 매핑은 Fireblocks 17 status 와 다를 수 있음 — channel 별 status 사전 정의
  • 회계 source_ref 매핑 — general_ledger_entry.source_ref 가 transaction_request_id (헤더) 를 가리키는 것으로 통일 — 단일 FK target
  • 인덱스 설계 — 헤더: (bank_customer_id, requested_at) · (type, request_status) · (travel_rule_record_id). 디테일: 표마다 자체 인덱스 (예: withdrawal 의 destination_address · counterparty_ref_id)
  • 새 type 확장 시 — header.type enum 에 추가 + 새 detail 표 생성 + 매핑 정책 update. 기존 디테일 표 / 코드 영향 없음
