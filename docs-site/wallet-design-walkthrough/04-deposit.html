입금 — 감지에서 확정까지

외부에서 돈이 들어왔다는 걸 어떻게 아는가 — 그리고 언제부터 믿는가

무엇·언제: 출금과 달리 입금은 직접 시작하지 않습니다. 외부 송신자가 보내고 그걸 알아채야 합니다. 직접 노드를 긁는 인덱서는 없습니다 — Fireblocks 가 자기 vault 범위를 감지해서 webhook 으로 알려주고, 이쪽 webhook 수신기(Service 백엔드)가 받아 DB 에 기록합니다. 그래서 이 페이지의 핵심 질문은 하나로 좁혀집니다 — 언제부터 잔액으로 믿는가. 답은 "감지 ≠ 확정"이고, Fireblocks 는 이 둘을 상태값으로 명확히 갈라 줍니다.

onChainEvent(handler)   // handler 가 받음: ChainEvent { status, numOfConfirmations, networkStatus }
이 페이지가 붙잡는 구분 — confirm(체인 등장) vs finality(확정)

입금 하나의 상태는 Fireblocks 안에서 BROADCASTING → CONFIRMING → COMPLETED 순으로 흐른다. 이 중 직접 잔액을 움직일 때 붙잡아야 할 두 지점이 CONFIRMING 과 COMPLETED 다.

CONFIRMING = confirm 상태. 트랜잭션이 체인에 올라가 블록에 담겼고, 그 위로 confirmation 이 쌓이는 중이다 — 하지만 아직 확정 아님. 이 단계의 자금은 고객에게 "확인 중"으로만 보여주고 available 잔액에는 넣지 않는다.

COMPLETED = finality 상태. confirmation 이 DCCP?(확정 정책)가 정한 임계 수에 도달했다는 뜻이고, 이때부터 이 입금을 확정(finality)으로 보고 available 에 반영한다. 둘을 프로그램으로 가르는 방법은 두 가지다 — status 값(CONFIRMING 인지 COMPLETED 인지)으로 갈리거나, tx 객체의 numOfConfirmations(실제 누적 confirmation 수)를 finality 임계값과 비교한다.

이쪽에 상시 인덱서는 없다. Fireblocks 가 감지·통지를 맡고, 이쪽 몫은 webhook 수신기(Service)가 받아 DB 에 기록하는 inbound 경로 하나다. 핵심은 두 통지의 성격 차이다 — CONFIRMING(체인에 등장, confirmation 누적 중, 아직 미확정)에서는 기록만 하고, COMPLETED(DCCP 임계 confirmation 도달 = finality)에서만 available 잔액을 올린다. ERC-20 토큰 입금도 별도 주소가 생기는 게 아니라 같은 주소로 오는 토큰 전송이라 같은 경로를 탄다. webhook 은 누락·지연·중복이 가능하므로 통지는 힌트로만 보고, 회계의 최종 근거는 주기적 대사(벤더 잔액과 기록의 대조)가 닫는다.

인바운드를 막는 환경(은행 등) — 그러면 webhook 대신 polling 이 주 경로

위 그림은 Fireblocks 가 우리 webhook 수신기로 밀어주는(인바운드) 전송을 전제한다. 그런데 은행·규제망은 외부 SaaS 가 내부로 들어오는 인바운드 연결을 차단하는 경우가 많다 — 그러면 webhook 자체를 못 받는다(Fireblocks→우리 호출이 방화벽에 막힘).

이때 감지는 방향을 뒤집어 우리가 Fireblocks 로 나가는 outbound 조회로 한다 — GET /v1/transactions 를 orderBy=lastUpdated · after=커서 · 상태 필터로 주기 폴링(아래 절). 은행이 통제하는 egress(나가는 방향)는 열려 있어 Fireblocks IP 로의 아웃바운드만 허용하면 된다. 서명 경로도 같은 원리다 — Fireblocks Agent 가 서명 요청을 폴링으로 당겨 오지 밀어넣지 않는다.

바뀌는 건 전송 방향(push→pull)뿐, 상태·확정 판정은 동일하다. CONFIRMING/COMPLETED·DCCP·numOfConfirmations 로직은 그대로이고, 폴링으로 받은 tx 에도 같은 상태·confirmation 이 실려 온다. 대신 감지 지연이 폴링 주기만큼 생긴다.

DCCP — 무엇이 CONFIRMING 을 COMPLETED 로 바꾸는가 (설정=Admin)

CONFIRMING 에서 COMPLETED 로 넘어가는 임계 confirmation 수를 정하는 정책이 DCCP(Deposit Control and Confirmation Policy) 입니다. "finality"는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준입니다. 설정·임계값 관리는 Admin, 이벤트를 받아 잔액에 반영하는 런타임은 Service 의 몫입니다.

DCCP 임계값 — 기본값과 커스텀 (설정 주체 = Admin)

Fireblocks 의 DCCP 기본 임계 confirmation 수는 체인마다 다르다.

  • 대부분의 체인 = 1 — 블록 하나면 확정으로 본다.
  • ETC(이더리움 클래식) = 372 — 과거 reorg 리스크가 커 임계가 매우 높다.
  • finality 속성을 가진 체인 — 체인별로 고정(rigid)된 값을 쓴다.
  • 컨트랙트 호출(contract call) = 최소 3 권장 — 단순 전송보다 보수적으로.

이 값은 커스텀 DCCP 로 조정할 수 있고, 조정 권한과 책임은 Admin 에 둔다. EVM 대상(이더리움·Base)에서 어떤 임계를 쓸지는 자산·리스크 정책에 따라 Admin 이 정하고, Service 는 그 결과로 도착한 COMPLETED 만 신뢰하면 된다.

함정 — 첫 COMPLETED 를 곧 finality 로 단정하지 말 것 (zero-confirmation)

Deposit Policy 를 zero-confirmation 으로 두면, COMPLETED 가 블록에 등장하는 시점에 먼저 뜰 수 있고 이후 webhook 이 여러 번(등장 + 1차 confirm + 추가 confirm) 더 올 수 있다. 즉 이 설정에서는 "COMPLETED webhook 을 처음 받았다"가 곧 "충분한 confirmation 이 쌓였다"를 뜻하지 않는다. 그래서 잔액 반영 판정은 status 만 보지 말고 numOfConfirmations 를 finality 임계값과 직접 비교하는 편이 안전하다. 어떤 임계를 finality 로 볼지는 위 DCCP(Admin 설정)와 한 몸이다.

되돌림(reorg) — EVM 이라 남는 속성

Fireblocks 가 감지·통지를 대신해 준다고 해서 체인 자체의 성질이 사라지진 않습니다. 이더리움과 Base 는 둘 다 EVM 체인이고 체인 끝이 드물게 교체(reorg)될 수 있습니다. reorg 가 일어나면 한 번 본 입금이 무효화될 수 있고, 이때 트랜잭션의 networkStatus 하위값이 ORPHANED(고아 블록에 실려 무효화) 로 바뀝니다. 핸들러는 이 신호를 받아 가공본(잔액 반영분)만 되감고 원본 기록은 영구 보존합니다 — 같은 입금이 재편입되면 다시 등장할 수 있기 때문입니다.

networkStatus — CONFIRMING/COMPLETED 를 뒷받침하는 하위 신호

tx 객체의 networkStatus 하위값은 DROPPED · BROADCASTING · CONFIRMING · CONFIRMED · FAILED 를 취한다. 상위 status(CONFIRMING/COMPLETED)가 잔액 판정의 1차 기준이라면, networkStatus 는 체인 레벨에서 실제로 무슨 일이 있었는지(전파됐는지·확정됐는지·떨어졌는지)를 보여주는 보조 신호다.

Base 는 이더리움 위에 얹은 L2 라 소프트 확정(시퀀서 수용)과 L1 최종성 사이에 시차가 있다 — 같은 EVM 이라 처리 경로는 동일하지만, 어느 시점을 finality 로 볼지의 여유(DCCP 임계)를 이더리움과 다르게 둘 수 있다. 이 판단도 Admin 의 DCCP 설정에 담긴다.

webhook 이 없거나 놓쳤을 때 — polling·재전송·대사

두 경우를 함께 다룹니다 — webhook 을 쓰지만 일부를 놓친 경우, 그리고 위처럼 인바운드가 막혀 webhook 을 아예 못 쓰는 경우. 공통 원칙은 주소를 하나씩 조회하지 않는다는 점입니다 — 아래는 모두 워크스페이스·시간 범위 기준이라, 주소가 천만 개여도 부하는 놓친 트랜잭션 수에 비례할 뿐 주소 수와 무관합니다.

수단무엇을
polling (주 경로 겸 백업)트랜잭션 목록을 갱신 시각 커서로 당겨 온다 — GET /v1/transactions 에 orderBy=lastUpdated · after=마지막 커서 · 상태 필터. webhook 이 아예 없으면 이것이 주 감지 경로, 있으면 놓친 전이를 따라잡는 백업이다(7p 의 "상태로 걸러 조회").
재전송 (webhook 쓸 때만)webhook 을 쓰는 환경에서 실패분만 다시 밀어달라고 요청 — POST /v1/webhooks/{id}/notifications/resend_failed, v2 는 30일 재전송 창. 인바운드가 막힌 환경엔 해당 없음.
대사 (최종 안전망)그래도 어긋나면 주기 대사가 벤더 값과 기록을 맞춰 닫는다(회계 걸리는 숫자만).

여러 경로가 같은 입금을 중복 전달하므로, 반영은 tx id(또는 externalTxId) 기준 멱등 upsert 로 한 번만 건다 — 없는 돈을 두 번 반영하는 것이 가장 비싼 사고다. status=COMPLETED 로 거를 땐 numOfConfirmations 가 확정 임계 이상인지 함께 본다(위 zero-confirmation 함정). polling 만 쓰면 감지 지연이 폴링 주기만큼 생기므로 주기는 확정 요건과 맞춰 정한다.

webhook 없이 — 폴링으로 감지하는 상세 흐름

인바운드가 막힌 환경을 가정하고, 폴링만으로 입금을 감지하는 실제 루프를 펼칩니다. 뼈대는 커서 하나입니다 — 마지막으로 처리한 트랜잭션의 lastUpdated(Unix 밀리초 시간값)를 DB 에 커서로 저장해 두고, 주기마다 그 이후 갱신된 트랜잭션만 당겨 옵니다. 커서가 시간값이라 같은 밀리초를 가진 tx 를 놓치지 않게 커서를 조금 겹쳐 받고 tx id 로 멱등 처리합니다. 상태 필터는 서버에서 한 번에 하나만 걸리므로, 모든 상태 전이를 빠짐없이 받으려면 상태 필터 없이 커서로 훑고 받은 tx 를 이쪽에서 분류합니다 — 상태 필터는 대사·표적 조회(7p)에서 씁니다.

폴링 워커가 커서 이후 갱신된 tx만 페이지 단위로 당겨, 각 tx 의 목적지 주소를 백엔드 DB 의 주소 매핑으로 (accountId, asset)에 역참조한 뒤 상태에 따라 원장을 움직인다. CONFIRMING 은 대기, COMPLETED + 임계 도달만 가용이라는 판정은 webhook 방식과 완전히 같다 — 바뀐 건 "받는 방법"뿐이다. 커서는 처리에 성공한 뒤에만 전진하고, tx id 기준 멱등 upsert 라 경계에서 겹쳐 받아도 중복 반영되지 않는다.

같은 흐름을 코드로 옮기면 이렇습니다. 커서는 lastUpdated(Unix 밀리초)이고, 같은 밀리초 경계를 놓치지 않도록 조금 겹쳐 읽은 뒤 tx id 로 멱등 처리하는 게 급소입니다.

// 커서 = 마지막으로 처리한 tx 의 lastUpdated (Unix ms)
let cursor = db.readCursor()               // 예: 1720000000000

// 경계 겹침 — 같은 밀리초를 가진 tx 를 놓치지 않도록 조금 이전부터
const OVERLAP_MS = 2000
let after   = cursor - OVERLAP_MS
let maxSeen = cursor

// 한 주기: after 이후 '갱신된(lastUpdated)' tx 를 페이지 단위로 모두 소진
while (true) {
  const txs = fb.getTransactions({
    orderBy: "lastUpdated",   // 갱신 시각 기준 정렬
    after,                    // Unix ms — 이 시각 이후 변경분만
    limit:   200,
    sort:    "ASC",           // 오래된 것부터 → 커서 단조 전진
  })
  if (txs.length === 0) break

  for (const tx of txs) {                          // lastUpdated 오름차순
    const dest = db.resolveAddress(tx.destAddress) // → (accountId, asset)
    if (!dest) continue                            // 우리 주소 아님 → 스킵

    // tx.id 기준 멱등 upsert — 겹쳐 받아도 상태 전이만 반영, 이중 반영 없음
    if (tx.status === "CONFIRMING") {
      ledger.upsertPending(tx.id, dest, tx.amount)           // 대기(pending)
    } else if (tx.status === "COMPLETED") {
      if (tx.numOfConfirmations ≥ dccpThreshold(tx.asset))
        ledger.upsertAvailable(tx.id, dest, tx.amount)       // 가용 + 고객 통지
      // 임계 미달(zero-conf)이면 대기 유지 — 다음 폴에서 재평가
    } else if (tx.networkStatus === "ORPHANED") {
      ledger.revert(tx.id)                                   // reorg — 가공분 되감기
    }
    maxSeen = Math.max(maxSeen, tx.lastUpdated)
  }

  if (txs.length < 200) break                    // 마지막 페이지
  after = txs[txs.length - 1].lastUpdated          // 다음 페이지: 시간 커서 전진
  // (API 가 opaque page 커서를 준다면 그걸 쓰는 편이 같은-ms 경계에서 더 안전)
}

// 처리 성공 후에만 커서 전진 — 실패 시 미전진, 다음 주기에 멱등 재처리
db.commitCursor(maxSeen)
// 다음 실행은 주기(예: 15~30s) 뒤 — 감지 지연 = 이 주기
루프의 급소어떻게
커서lastUpdated 워터마크를 DB 에 영속. 주기마다 after=커서로만 받아 재조회량을 놓친 만큼으로 한정.
빠짐 방지커서는 처리 성공 후에만 전진 + 경계를 살짝 겹쳐 받기(after 를 조금 이전으로). 겹침은 멱등 upsert 가 흡수.
페이지네이션limit(기본 200)이 가득 차면 다음 페이지 계속 — 한 주기에 밀린 분을 다 소진.
멱등tx id(또는 externalTxId) unique. 같은 tx 를 여러 번 받아도 상태 전이만 반영, 잔액 이중 반영 없음.
reorgCOMPLETED 였다가 ORPHANED 로 바뀐 tx 도 다음 폴에서 잡아 가공분만 되감고 원본 기록은 보존(위 reorg 절).
감지 지연지연 = 폴링 주기. 짧게 잡으면 실시간에 근접하고 API 호출이 는다 — 확정 요건과 rate limit 사이에서 정한다.

이 루프는 주소 수와 무관하다 — 커서가 훑는 것은 "갱신된 트랜잭션"이지 주소 목록이 아니다. 천만 개 주소여도 한 주기의 일감은 그사이 상태가 바뀐 tx 수뿐이다. 다만 폴링이 push 이벤트를 100% 대체하는지 — 초기 감지 시점·승인 상태 이벤트까지 빠짐없이 관찰되는지 — 는 벤더 문서로 확인이 남은 부분이다.

더 깊이: 잔액의 세 칸(available·pending·locked)이 이 상태들과 어떻게 맞물리는지는 7. 잔액과 내역 조회, 출금 쪽 상태 전이(SUBMITTED→CONFIRMING→COMPLETED)는 6. 출금 에서 이어집니다.
