입금 — 감지에서 확정까지

외부에서 돈이 들어왔다는 걸 어떻게 아는가 — 그리고 언제부터 믿는가

onChainEvent(handler)   // 어댑터가 폴링으로 채워 handler 에 전달: ChainEvent { status, numOfConfirmations, networkStatus }
이 페이지가 붙잡는 구분 — confirm(체인 등장) vs finality(확정)

입금 하나의 상태는 Fireblocks 안에서 BROADCASTING → CONFIRMING → COMPLETED 순으로 흐른다. 이 중 직접 잔액을 움직일 때 붙잡아야 할 두 지점이 CONFIRMING 과 COMPLETED 다.

CONFIRMING = confirm 상태. 트랜잭션이 체인에 올라가 블록에 담겼고, 그 위로 confirmation 이 쌓이는 중이다 — 하지만 아직 확정 아님. 이 단계의 자금은 고객에게 "확인 중"으로만 보여주고 available 잔액에는 넣지 않는다.

COMPLETED = finality 상태. confirmation 이 DCCP?(확정 정책)가 정한 임계 수에 도달했다는 뜻이고, 이때부터 이 입금을 확정(finality)으로 보고 available 에 반영한다. 둘을 프로그램으로 가르는 방법은 두 가지다 — status 값(CONFIRMING 인지 COMPLETED 인지)으로 갈리거나, tx 객체의 numOfConfirmations(실제 누적 confirmation 수)를 finality 임계값과 비교한다.

그 누락·지연은 다음 폴이 어차피 메운다

ERC-20 토큰 입금도 별도 주소가 생기는 게 아니라 같은 주소로 오는 토큰 전송이라 같은 경로를 탄다. 통지가 아니라 조회라 유실이 없고, 회계의 최종 근거는 주기적 대사(벤더 잔액과 기록의 대조)가 닫는다.

웹훅은 보조 — 왜 폴링이 주 경로인가

webhook 은 Fireblocks 가 우리 안으로 들어오는(인바운드) push 다. 은행·규제망은 외부 SaaS 의 인바운드 연결을 막는 경우가 많아, 여기서는 webhook 을 주 경로로 쓰지 않는다 — 대신 우리가 Fireblocks 로 나가는 outbound 폴링으로 감지한다. 은행이 통제하는 egress 만 열면 되고, 서명 경로도 같은 원리다(Fireblocks Agent 가 서명 요청을 폴링으로 당겨 온다).

webhook 을 쓸 수 있는 환경이면 폴 주기 사이의 지연을 줄이는 보조로 붙일 수 있다. 다만 webhook 은 누락·지연·중복이 가능하므로 신뢰의 근거는 어디까지나 폴링·대사에 두고, webhook 은 "빨리 알려주는 힌트"로만 취급한다 — 그 누락은 다음 폴이 어차피 메운다. 전송 방향(push↔pull)만 다를 뿐 상태·확정 판정(CONFIRMING/COMPLETED·DCCP·numOfConfirmations)은 동일하다.

DCCP — 무엇이 CONFIRMING 을 COMPLETED 로 바꾸는가

CONFIRMING 에서 COMPLETED 로 넘어가는 임계 confirmation 수를 정하는 정책이 DCCP(Deposit Control and Confirmation Policy) 입니다. "finality"는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준입니다. 커스텀 DCCP 는 Console 에서 직접 설정하는 게 아니라, 정책 템플릿을 작성해 Fireblocks Support 에 제출 → 검토·승인 후 반영됩니다. 어떤 임계를 요청할지 정하는 책임은 Admin(운영), 이벤트를 받아 잔액에 반영하는 런타임은 Service 의 몫입니다.

DCCP 임계값 — 기본값과 커스텀

Fireblocks 의 DCCP 기본 임계 confirmation 수는 체인마다 다르다.

  • 대부분의 체인 = 1 — 블록 하나면 확정으로 본다.
  • ETC(이더리움 클래식) = 372 — 과거 reorg 리스크가 커 임계가 매우 높다.
  • finality 속성을 가진 체인 — 체인별로 고정(rigid)된 값을 쓴다.
  • 컨트랙트 호출(contract call) = 최소 3 권장 — 단순 전송보다 보수적으로.

이 값은 커스텀 DCCP 로 조정할 수 있는데, 직접 설정이 아니라 템플릿 작성 → Fireblocks Support 제출 → 검토·승인 후 반영이다. EVM 대상(이더리움·Base)에서 어떤 임계를 요청할지는 자산·리스크 정책에 따라 Admin 이 정하고, Service 는 그 결과로 도착한 COMPLETED 만 신뢰하면 된다.

함정 — 첫 COMPLETED 를 곧 finality 로 단정하지 말 것 (zero-confirmation)

Deposit Policy 를 zero-confirmation 으로 두면, COMPLETED 가 블록에 등장하는 시점에 먼저 뜰 수 있고 이후 폴마다 관찰값(등장 + 1차 confirm + 추가 confirm)이 계속 갱신될 수 있다. 즉 이 설정에서는 "COMPLETED 를 처음 관찰했다"가 곧 "충분한 confirmation 이 쌓였다"를 뜻하지 않는다. 그래서 잔액 반영 판정은 status 만 보지 말고 numOfConfirmations 를 finality 임계값과 직접 비교하는 편이 안전하다. 어떤 임계를 finality 로 볼지는 위 DCCP 와 한 몸이다.

되돌림(reorg) — EVM 이라 남는 속성

Fireblocks 가 감지·통지를 대신해 준다고 해서 체인 자체의 성질이 사라지진 않습니다. 이더리움과 Base 는 둘 다 EVM 체인이고 체인 끝이 드물게 교체(reorg)될 수 있습니다. reorg 가 일어나면 한 번 본 입금이 무효화될 수 있고, 이때 트랜잭션의 networkStatus 하위값이 ORPHANED(고아 블록에 실려 무효화) 로 바뀝니다. 핸들러는 이 신호를 받아 가공본(잔액 반영분)만 되감고 원본 기록은 영구 보존합니다 — 같은 입금이 재편입되면 다시 등장할 수 있기 때문입니다.

networkStatus — CONFIRMING/COMPLETED 를 뒷받침하는 하위 신호

tx 객체의 networkStatus 하위값은 DROPPED · BROADCASTING · CONFIRMING · CONFIRMED · FAILED 를 취한다. 상위 status(CONFIRMING/COMPLETED)가 잔액 판정의 1차 기준이라면, networkStatus 는 체인 레벨에서 실제로 무슨 일이 있었는지(전파됐는지·확정됐는지·떨어졌는지)를 보여주는 보조 신호다.

Base 는 이더리움 위에 얹은 L2 라 소프트 확정(시퀀서 수용)과 L1 최종성 사이에 시차가 있다 — 같은 EVM 이라 처리 경로는 동일하지만, 어느 시점을 finality 로 볼지의 여유(DCCP 임계)를 이더리움과 다르게 둘 수 있다. 이 판단도 Admin 이 정해 Support 에 요청하는 DCCP 임계에 담긴다.

감지 경로 — 폴링(주) · 웹훅(보조) · 대사(안전망)

세 수단을 겹쳐 둡니다. 공통 원칙은 주소를 하나씩 조회하지 않는다는 점입니다 — 아래는 모두 워크스페이스·시간 범위 기준이라, 주소가 천만 개여도 부하는 놓친 트랜잭션 수에 비례할 뿐 주소 수와 무관합니다.

수단무엇을
폴링 (주 경로)트랜잭션 목록을 갱신 시각 커서로 당겨 온다 — GET /v1/transactions 에 orderBy=lastUpdated · after=마지막 커서 · 상태 필터. 이게 감지의 기본이다(상세는 아래 절, 7p 의 "상태로 걸러 조회"도 같은 수단).

여러 경로가 같은 입금을 중복 전달하므로, 반영은 tx id(또는 externalTxId) 기준 멱등 upsert 로 한 번만 건다 — 없는 돈을 두 번 반영하는 것이 가장 비싼 사고다. status=COMPLETED 로 거를 땐 numOfConfirmations 가 확정 임계 이상인지 함께 본다(위 zero-confirmation 함정). 폴링만으로도 완결되며, 감지 지연은 폴링 주기만큼이다.

폴링 감지 상세 흐름

폴링으로 입금을 감지하는 실제 루프를 펼칩니다. 뼈대는 커서 하나입니다 — 마지막으로 처리한 트랜잭션의 lastUpdated(Unix 밀리초 시간값)를 DB 에 커서로 저장해 두고, 주기마다 그 이후 갱신된 트랜잭션만 당겨 옵니다. 커서가 시간값이라 같은 밀리초를 가진 tx 를 놓치지 않게 커서를 조금 겹쳐 받고 tx id 로 멱등 처리합니다. 상태 필터는 서버에서 한 번에 하나만 걸리므로, 모든 상태 전이를 빠짐없이 받으려면 상태 필터 없이 커서로 훑고 받은 tx 를 이쪽에서 분류합니다 — 상태 필터는 대사·표적 조회(7p)에서 씁니다.

같은 흐름을 코드로 옮기면 이렇습니다.

// 커서 = 마지막으로 처리한 tx 의 lastUpdated (Unix ms)
let cursor = db.readCursor()               // 예: 1720000000000

// 경계 겹침 — 같은 밀리초를 가진 tx 를 놓치지 않도록 조금 이전부터
const OVERLAP_MS = 2000
let after   = cursor - OVERLAP_MS
let maxSeen = cursor

// 한 주기: after 이후 '갱신된(lastUpdated)' tx 를 페이지 단위로 모두 소진
while (true) {
  const txs = fb.getTransactions({
    orderBy: "lastUpdated",   // 갱신 시각 기준 정렬
    after,                    // Unix ms — 이 시각 이후 변경분만
    limit:   200,
    sort:    "ASC",           // 오래된 것부터 → 커서 단조 전진
  })
  if (txs.length === 0) break

  for (const tx of txs) {                          // lastUpdated 오름차순
    // 1) 방향 판정 — 입금만 크레딧 (출금·내부이동은 각자 경로가 처리)
    if (tx.destination?.type !== "VAULT_ACCOUNT") continue   // 우리 vault 로 온 게 아님(출금 등)
    if (tx.source?.type === "VAULT_ACCOUNT")      continue   // 우리 vault 간 내부 이동 → 스킵

    // 2) 목적지 vault 로 계정 귀속 — 주소 문자열이 아니라 vaultAccountId 기준
    const account = db.accountByVault(tx.destination.id)     // → accountId
    if (!account) continue                                   // 우리 vault 아님(이론상 없음)

    // 3) 주소가 (계정, 자산) 매핑에 있나 — 없으면 우리 돈이나 out-of-band 주소
    if (!db.addressKnown(account, tx.assetId, tx.destAddress))
      alert.unmappedDeposit(account, tx)                     // 경보 — 스킵 아님, 계정엔 귀속

    // 4) tx.id 기준 멱등 upsert — 겹쳐 받아도 상태 전이만 반영, 이중 반영 없음
    if (tx.networkStatus === "ORPHANED") {                   // reorg — 되돌림 우선
      ledger.revert(tx.id)                                   //   가공분만 되감고 원본 보존
    } else if (tx.status === "CONFIRMING") {
      ledger.upsertPending(tx.id, account, tx.assetId, tx.amount)     // 대기(pending)
    } else if (tx.status === "COMPLETED") {
      if (tx.numOfConfirmations ≥ dccpThreshold(tx.assetId))
        ledger.upsertAvailable(tx.id, account, tx.assetId, tx.amount) // 가용 + 고객 통지
      // 임계 미달(zero-conf)이면 대기 유지 — 다음 폴에서 재평가
    }
    maxSeen = Math.max(maxSeen, tx.lastUpdated)
  }

  if (txs.length < 200) break                    // 마지막 페이지
  after = txs[txs.length - 1].lastUpdated          // 다음 페이지: 시간 커서 전진
  // (API 가 opaque page 커서를 준다면 그걸 쓰는 편이 같은-ms 경계에서 더 안전)
}

// 처리 성공 후에만 커서 전진 — 실패 시 미전진, 다음 주기에 멱등 재처리
db.commitCursor(maxSeen)
// 다음 실행은 주기(예: 15~30s) 뒤 — 감지 지연 = 이 주기

페이지네이션limit(기본 200)이 가득 차면 다음 페이지 계속 — 한 주기에 밀린 분을 다 소진.
