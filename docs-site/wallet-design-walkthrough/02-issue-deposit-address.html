입금 주소 발급 — issueDepositAddress

고객에게 건넬 입금 주소를 만든다 — 그리고 "만들기"의 끝은 감시 등록이다

무엇·언제: 온보딩의 두 번째 호출(첫 주소)이자, 운영 중 추가 주소가 필요할 때마다 다시 불립니다. 발급의 규칙 하나를 먼저 박아두면 — 주소는 감시 목록(watch-list)에 올라가야 비로소 "존재"합니다. 감시 안 되는 주소를 고객에게 주면, 그 주소로 온 입금을 우리만 모릅니다(입금 사고의 최다 유형). 그래서 모든 분면에서 등록까지가 발급입니다.

issueDepositAddress(account, asset) → Address   // 부를 때마다 새 주소 — 같은 요청의 재시도만 멱등 키로 차단

▸ 자체 × 이더리움 — 키 트리에서 계산 + 등록

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant DIR as 계정 디렉터리(우리 DB)
    participant WL as watch-list (인덱서의 감시 목록)

    BE->>MGR: issueDepositAddress(계정 #1024, ETH)
    MGR->>MGR: 다음 주소 번호 소비 (#3)
    MGR->>MGR: xpub 로 주소 계산 (로컬)
    Note over BE,WL: xpub(공개키 쪽 사본)만으로 자식 주소가 계산된다 — HSM 호출 없음. 개인키는 출금 서명 때 HSM 안에서 같은 번호로 파생 (5p)
    MGR->>DIR: 주소 저장 (계정 #1024 · 3번째)
    MGR->>WL: 감시 목록 등록 — 등록 실패면 발급도 실패
    MGR-->>BE: 주소 (0xAb3…)

이더리움 발급 = 번호 소비 + 공개키 수학 + 등록. 계산 자체는 공짜·즉시지만, 디렉터리 저장과 감시 등록이라는 상태 변경이 본질이다 — 그래서 발급은 쓰기 동작이고 멱등 키로 감싼다. 보안 단서 하나 — xpub 은 이름과 달리 비밀급으로 다룬다: xpub 이 유출된 상태에서 자식 개인키가 하나라도 새면 부모 키가 역산되는 알려진 성질이 있다.

▸ 자체 × Canton — 이 기능이 "없다" (없음도 동작이다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: issueDepositAddress(계정, Canton 자산)?
    Note over BE,MGR: 호출 자체가 일어나지 않는다 — Canton 구현은
이 기능(capability)을 타입부터 갖지 않아서,
백엔드가 컴파일 시점에 "없음"을 안다
    BE->>DIR: 대신 — 이 계정의 PartyId 조회 (1p 에서 탄생한 그 주소)
    DIR-->>BE: PartyId
    BE->>BE: 고객 안내 = PartyId + memo
    Note over BE,DIR: 고객마다 주소를 늘리는 대신 주소(PartyId)는 하나 — 입금마다 memo 코드로 "누구 돈인지" 구분

Canton 은 "계정당 입금 주소를 계속 발급"하는 모델이 아니다 — 주소(PartyId)는 1페이지의 계정 생성 때 하나 태어나고 끝. 추가 입금의 구분은 주소가 아니라 memo 코드가 한다(은행 가상계좌 대신 입금자 코드를 쓰는 것과 같은 모양). "지원 안 함"을 throw 로 구현하지 않고 기능 부재(타입 없음)로 두는 것이 설계 규칙 — 호출부가 런타임이 아니라 컴파일에 안다.

▸ Fireblocks × 이더리움 — 벤더가 만들어 준다

    participant FB as Fireblocks (SaaS)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>FBI: issueDepositAddress(계정, ETH)
    FBI->>FB: 새 입금 주소 생성 API
    Note over FBI,FB: 주소는 Fireblocks 키에서 파생 — 감시도 Fireblocks 몫 (vault 가 곧 감시 범위라 watch-list 등록 단계가 없다)
    FB-->>FBI: 주소
    FBI->>DIR: 주소 저장 (벤더를 바꿔도 남는 우리 기록)
    FBI-->>BE: 주소

자체 분면의 "계산+등록"이 "벤더 API 한 번"으로 줄었다 — 감시 등록이 사라진 것은 생략이 아니라 책임 이동이다(벤더 vault 안의 주소는 벤더가 감시·통지한다, 4p). 단 주소가 Fireblocks 키에서 나온다는 사실은 7페이지(전환)에서 비용으로 돌아온다.

    BE->>FBI: issueDepositAddress(계정, Canton 자산)?

추가 주소가 없는 것은 벤더가 아니라 "체인의 성질"이라서,
custody 를 바꿔도 이 분면은 그대로다
    BE->>DIR: PartyId 조회 → 고객 안내 = PartyId + memo
    DIR-->>BE: PartyId

1페이지에 이어 두 번째 확인 — 가로(체인) 차이는 custody 를 바꿔도 따라온다. 백엔드의 "Canton 입금 안내 = PartyId + memo" 로직은 자체든 Fireblocks 든 동일하게 동작하므로, 전환 때 손댈 일이 없다.

표에서 읽을 것: "기능 존재" 행이 또 가로(체인)로 갈립니다. 그리고 감시 책임 행은 세로(custody)로 갈리죠 — 두 축이 서로 다른 것을 결정한다는 패턴이 이 문서 내내 반복됩니다.

백엔드에서 이렇게 부른다 — "없음" 분면이 코드에서 갈리는 모습

// 첫 주소 확보 — 1p 의 openWallet 이 부르는 그 함수
suspend fun acquireFirstAddress(account: Account, asset: Asset): Address =
    when (val issuer = accounts as? DepositAddressIssuanceCapability) {
        null -> accounts.addressOf(account, asset)            // Canton — 발급이 타입부터 없다
                                                              //   → 계정과 함께 태어난 PartyId 조회 (안내엔 memo 동봉)
        else -> issuer.issueDepositAddress(account, asset)    // 이더리움 — 발급 (등록까지)
    }

"없음" 분면의 처리가 capability 형변환 한 번이다 — 런타임 예외를 기다리지 않고, 컴파일 타입이 분기를 만든다. 이 함수도 custody 가 무엇인지는 모른다.
