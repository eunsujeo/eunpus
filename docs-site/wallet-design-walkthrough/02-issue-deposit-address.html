입금 주소 생성 — createDepositAddress

고객·자산당 하나, 없으면 만들고 있으면 그대로(get-or-create). EVM 주소는 memoTag 가 null

무엇·언제: Service 백엔드가 createDepositAddress(accountId, asset) 를 부릅니다. 입금주소는 고객·자산당 하나로 재사용합니다 — (accountId, asset) 주소가 이미 있으면 그대로 돌려주고(멱등), 없으면 Fireblocks 에서 그 자산의 지갑을 활성화해 단일 주소를 받습니다(EVM 은 vault·자산당 주소 하나 · 계정 vault 는 1페이지에서 이미 생성). 발급되는 것은 입금 주소(EVM 에서는 memoTag 가 항상 null). 규칙 하나, 주소는 감시(귀속) 등록까지 끝나야 "존재"합니다 — 이 감시·귀속은 벤더 몫(vault 가 곧 감시 범위, 입금 감지 4p)입니다. 등록 안 된 주소로 온 입금은 감지하지 못하는데, 이것이 입금 사고의 최다 유형입니다.

createDepositAddress(accountId, asset) → Address { value, memoTag? }   // EVM: memoTag=null · 고객·자산당 1개(get-or-create)

▸ get-or-create — 없으면 활성화, 있으면 그대로

    FBI->>FB: 없으면 → 자산 지갑 활성화 · POST .../{assetId}
    Note over FBI,FB: EVM = vault·자산당 주소 1개 · memoTag 없음. generateNewAddress(추가 주소)는 UTXO·Tag 전용이라 EVM 은 실패. 키·주소 파생은 vault·MPC 안, 감시·귀속도 벤더 몫
    FB-->>FBI: 활성화 응답 · address 0xAb3… · memoTag=null
    FBI->>BDB: 주소 저장 (accountId + asset ↔ 0xAb3…)
    FBI-->>BE: 주소 (0xAb3…)

매니저가 백엔드 DB 에서 (accountId, asset) 주소가 있으면 그대로 돌려주고, 없을 때만 그 자산의 지갑을 활성화해(POST /vault/accounts/{vaultId}/{assetId}) 단일 주소를 받는다 — 활성화 응답에 address 가 실려 온다. generateNewAddress(추가 주소 발급)는 UTXO·Tag 자산 전용이라 EVM 에는 쓰지 않는다(account-based 는 호출 시 실패). EVM 은 순수 주소(memoTag=null), 이더리움·Base 는 asset 의 chainId 만 다르다. 키·주소 파생은 vault·MPC 안, 감시·귀속도 벤더 몫. 매니저가 (accountId+asset ↔ 주소) 를 백엔드 DB 에 저장하고, 다음부터 재사용한다.
