입금 주소 발급 — issueDepositAddress

EVM 에서 발급되는 것은 순수 "주소" — memoTag 는 null 이다. Service 백엔드가 부른다

무엇·언제: 온보딩의 두 번째 호출이자 첫 주소이며, 운영 중 추가 주소가 필요할 때마다 Service 백엔드가 다시 부릅니다. 발급되는 것은 입금 주소입니다 — 우리 도메인 타입으로는 Address(value, memoTag?)인데, EVM(이더리움·Base)에서는 memoTag 가 항상 null 이라 사실상 주소값 하나입니다. 부를 때마다 새 주소가 나오고, Fireblocks 가 vault 밑에서 채번합니다. 규칙도 하나 짚어두면, 주소는 감시(귀속) 등록까지 끝나야 비로소 "존재"합니다. Fireblocks 를 채택하면 이 감시·귀속은 벤더 몫입니다 — vault 가 곧 감시 범위라, 발급된 주소로 온 입금은 벤더가 잡아 webhook 으로 알려줍니다(4p). 등록 안 된 주소로 온 입금은 우리만 모르는데, 이것이 입금 사고의 최다 유형입니다.

issueDepositAddress(account, asset) → Address(주소, memoTag=null)   // EVM — 부를 때마다 새 주소, 재시도만 멱등 키로 차단

발급은 Fireblocks 의 generateNewAddress 한 줄이다. EVM 에서는 순수 주소가 새로 나오고 memoTag 는 null 이다. 이더리움과 Base 는 같은 EVM(account 기반·동일 주소 체계)이라 이 호출이 동일하다 — asset 의 chainId 만 다를 뿐이다. 키·주소 파생은 Fireblocks vault·MPC 안에서 일어나고, 우리 쪽엔 키 트리도 xpub 도 없다. 발급은 그래도 쓰기 동작이다 — 우리 매핑 DB 에 "계정 ↔ 주소" 한 줄이 남는 상태 변경이라, 재시도가 주소를 두 번 만들지 않게 멱등 키로 감싼다. 감시·귀속(누구 돈인지 가르기)은 벤더가 vault 범위로 처리하므로 우리가 watch-list 를 운영하지 않는다.

식별자의 출처 — EVM 은 순수 주소 하나

Fireblocks × EVM (이더리움·Base)
발급되는 것새 주소 (memoTag = null)
식별자의 출처Fireblocks vault 채번 (키·MPC 는 벤더 안)
감시·귀속 등록벤더 (vault 범위 — webhook 으로 통지, 4p)
우리 책임매핑 DB (계정 ↔ 주소)

표에서 읽을 것은 이렇습니다. EVM 에서 입금 식별자는 주소값 하나이고, memoTag 는 채우지 않습니다(null). 식별자의 출처는 Fireblocks vault 채번 한 곳뿐이라 우리가 키를 파생하거나 xpub 을 다루지 않습니다. 감시·귀속도 벤더가 vault 범위로 처리하므로 우리 몫은 매핑 DB 한 줄로 줄어듭니다. 부를 때마다 새 주소가 나온다는 성질만, 다음 페이지(조회)의 "같은 주소가 나온다"와 대비해 기억해 두면 됩니다.

백엔드에서 이렇게 부른다 — 분기가 없다

// 입금 안내 화면까지 — Service 백엔드, 한 동사, 분기 없음
suspend fun issueAndGuide(account: Account, asset: Asset): DepositGuide {
    val id = accounts.issueDepositAddress(account, asset)  // EVM = 새 주소 (memoTag=null)
    return DepositGuide(address = id.value, memo = id.memoTag)   // EVM 은 memoTag 가 null 이라 화면에서 생략
}

Service 백엔드는 자산이 이더리움인지 Base 인지 모른 채 이 한 동사를 부른다. 반환 타입은 Address(value, memoTag?) 그대로지만 EVM 에서는 memoTag 가 null 이라 화면에서 생략된다 — 도메인 타입은 memoTag 를 자리로만 남겨두고, 실제로 채우는 체인은 이 문서 범위에 없다.
