입금 주소 생성 — createDepositAddress

(account, asset)당 한 번 — 자산 지갑을 활성화해 단일 주소를 얻는다. EVM 주소는 memoTag 가 null

무엇·언제: Service 백엔드가 createDepositAddress(accountId, asset) 를 부릅니다 — (account, asset)당 한 번, 그 자산의 지갑을 활성화해 단일 주소를 얻습니다(1페이지 createAccount 와 같은 create-once). EVM 은 vault·자산당 주소가 하나뿐이라(같은 자산의 추가 주소가 필요하면 vault account 를 더 만들어야 함), 활성화가 곧 그 주소의 발급입니다(EVM 은 memoTag 가 항상 null). 이후 그 주소를 다시 부르는 조회는 getDepositAddress(3페이지, 읽기)가 맡습니다. 규칙 하나, 주소는 감시(귀속) 등록까지 끝나야 "존재"합니다 — 이 감시·귀속은 벤더 몫(vault 가 곧 감시 범위, 입금 감지 4p)입니다. 등록 안 된 주소로 온 입금은 감지하지 못하는데, 이것이 입금 사고의 최다 유형입니다.

createDepositAddress(accountId, asset) → Address { value, memoTag? }   // EVM: memoTag=null · (account,asset)당 1개 · 활성화 1회(재시도 멱등)

    Note over FBI,FB: EVM = account·자산당 주소 1개 · 활성화 1회. generateNewAddress 는 UTXO·Tag 전용의 다른 작업. 감시·귀속은 벤더 몫

1페이지 createAccount 와 같은 create-once — (account, asset)당 한 번, 없을 때만 자산 지갑을 활성화한다(createVaultAccountAsset). 활성화 응답에 address 가 실려 오고, 그게 EVM 단일 주소다. 재시도는 Idempotency-Key 로 같은 주소, 정합은 (account, asset) UNIQUE 로 잡는다. generateNewAddress(=createVaultAccountAssetAddress)는 UTXO·Tag 자산의 추가 주소 발급이라 EVM 에는 쓰지 않는다(account-based 는 호출 시 실패). EVM 은 순수 주소(memoTag=null), 이더리움·Base 는 asset 의 chainId 만 다르다. 키·주소 파생은 vault·MPC 안, 감시·귀속도 벤더 몫. 매니저가 (accountId+asset ↔ 주소) 를 백엔드 DB 에 저장하고, 이후 조회는 getDepositAddress(3p) 가 읽어 재사용한다.
