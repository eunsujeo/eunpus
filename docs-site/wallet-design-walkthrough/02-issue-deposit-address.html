입금 주소 발급 — issueDepositAddress

발급되는 것은 "주소"가 아니라 입금 식별자 — 주소+memo 쌍이다

무엇·언제: 온보딩의 두 번째 호출(첫 식별자)이자, 운영 중 추가 식별자가 필요할 때마다 다시 불립니다. 핵심 재정의 하나 — 발급되는 것은 입금 식별자(주소 + memo 쌍)입니다: 이더리움은 memo 가 빈 채 주소가 새로워지고, Canton 은 주소(PartyId)가 고정된 채 memo 가 새로워집니다(Fireblocks 콘솔·문서로 확인 — 같은 온체인 주소를 tag/memo 로 구분하는 모델). 그리고 규칙 하나 — 식별자는 감시(귀속) 등록까지 끝나야 "존재"합니다. 등록 안 된 식별자로 온 입금은 우리만 모릅니다(입금 사고의 최다 유형).

issueDepositAddress(account, asset) → Address(주소, memo?)   // 부를 때마다 새 식별자 — 재시도만 멱등 키로 차단

▸ 자체 × 이더리움 — 새로워지는 것: 주소

    BE->>MGR: issueDepositAddress(계정 1024번, ETH)
    MGR->>MGR: 다음 주소 번호 소비 — 3번째
    MGR->>MGR: xpub 로 주소 계산 (로컬)
    Note over BE,WL: xpub(공개키 쪽 사본)만으로 자식 주소가 계산된다 — HSM 호출 없음. 개인키는 출금 서명 때 HSM 안에서 같은 번호로 파생 (6p)
    MGR->>DIR: 주소 저장 (계정 1024번 · 3번째)
    MGR->>WL: 감시 목록 등록 — 등록 실패면 발급도 실패
    MGR-->>BE: 주소 (0xAb3…)

이더리움 발급 = 번호 소비 + 공개키 수학 + 등록. 계산 자체는 공짜·즉시지만, 디렉터리 저장과 감시 등록이라는 상태 변경이 본질이다 — 그래서 발급은 쓰기 동작이고 멱등 키로 감싼다. 보안 단서 하나 — xpub 은 이름과 달리 비밀급으로 다룬다: xpub 이 유출된 상태에서 자식 개인키가 하나라도 새면 부모 키가 역산되는 알려진 성질이 있다.

▸ 자체 × Canton — 새로워지는 것: memo

    participant MGR as 자체 매니저
    participant WL as memo 귀속표 (인덱서)
    end
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: issueDepositAddress(계정 1024번, Canton 자산)
    MGR->>MGR: 새 memo 채번 — 체인 호출 없음 (장부 작업)
    Note over BE,WL: 주소(PartyId)는 1p 에서 태어난 그대로 — 새로워지는 건 memo 뿐. 은행의 가상계좌 대신 입금자 코드를 늘리는 모양
    MGR->>DIR: 식별자 저장 (PartyId + 새 memo)
    MGR->>WL: memo 귀속표 등록 — watch-list 의 memo 판, 등록 실패면 발급도 실패
    MGR-->>BE: Address(PartyId, 새 memo)

이더리움과 같은 동사, 같은 골격(채번 → 디렉터리 → 감시·귀속 등록)이고 새로워지는 칸만 다르다. memo 채번은 체인 호출이 없는 장부 작업이지만 — "입금 식별자 발급" 이라는 도메인 동사로 묶으면 백엔드는 그 차이조차 모른다. 인덱서(4p)는 watch-list 대신 이 memo 귀속표로 "누구 돈인지"를 가른다.

▸ Fireblocks (양 체인) — 벤더가 발급한다

    BE->>FBI: issueDepositAddress(계정, 자산)
    FBI->>FB: 새 입금 주소 생성 API (generateNewAddress)
    Note over FBI,DIR: 이더리움 = 새 주소 / Canton = 같은 PartyId + 새 memo 자동 생성 — 콘솔·문서로 확인, memo 생성 보장 규칙은 적용 전 통합 테스트로
    FB-->>FBI: Address(주소, memo?)
    FBI->>DIR: 식별자 저장 — 감시·귀속은 벤더 몫 (vault 가 곧 감시 범위)
    FBI-->>BE: 식별자

벤더 호출은 양 체인에서 같은 한 줄이고, 무엇이 새로워지는지(주소 vs memo)는 벤더가 체인에 맞춰 정한다 — 자체 분면의 두 그림이 벤더 안으로 접힌 모양. 식별자가 Fireblocks 키·채번에서 나온다는 사실은 8p(전환 — 자금은 이사)에서 비용으로 돌아온다.

표에서 읽을 것: "새로워지는 것" 행은 체인 축으로, "누가 만들고 누가 감시하나"는 custody 축으로 갈립니다 — 1페이지의 패턴 그대로. 참고로 이 페이지엔 원래 "Canton 은 발급이 없다(타입 부재)"는 분면이 있었는데, Fireblocks 콘솔이 memo 를 자동 발급하는 것을 확인하면서 식별자 재정의로 분면이 합쳐졌습니다 — "기능 부재(타입 없음)" 패턴은 출금의 boost 에서 만납니다(6p).

백엔드에서 이렇게 부른다 — 분기가 없다

// 입금 안내 화면까지 — 한 동사, 분기 없음
suspend fun issueAndGuide(account: Account, asset: Asset): DepositGuide {
    val id = accounts.issueDepositAddress(account, asset)  // 이더리움 = 새 주소 · Canton = 새 memo
    return DepositGuide(address = id.value, memo = id.memoTag)   // memo 가 null 이면 화면에서 생략
}

식별자 재정의의 코드 효과 — 예전엔 "Canton 은 발급이 없다"는 capability 분기가 여기 있었지만, 발급물을 주소+memo 쌍으로 일반화하자 분기 자체가 소멸했다. 백엔드는 무엇이 새로워졌는지도 모른다.
