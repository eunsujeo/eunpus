입금 주소 발급 — issueDepositAddress

발급되는 것은 "주소"가 아니라 입금 식별자, 곧 주소+memo 쌍이다

무엇·언제: 온보딩의 두 번째 호출이자 첫 식별자이며, 운영 중 추가 식별자가 필요할 때마다 다시 불립니다. 핵심 재정의가 하나 있습니다. 발급되는 것은 입금 식별자, 즉 주소 + memo 쌍입니다. 이더리움은 memo 가 빈 채 주소가 새로워지고, Canton 은 주소(PartyId)가 고정된 채 memo 가 새로워집니다. Fireblocks 콘솔과 문서로 확인한, 같은 온체인 주소를 tag/memo 로 구분하는 모델입니다. 단 그 고정 PartyId 는 거저 있는 게 아닙니다. 이 계정의 첫 Canton 발급 때 여기서 선발급되는데(1p 가 아닙니다), 아래 자체×Canton 흐름의 첫 분기가 바로 이 대목입니다. 규칙도 하나 짚어두면, 식별자는 감시(귀속) 등록까지 끝나야 비로소 "존재"합니다. 등록 안 된 식별자로 온 입금은 우리만 모르고, 이것이 입금 사고의 최다 유형입니다.

issueDepositAddress(account, asset) → Address(주소, memo?)   // 부를 때마다 새 식별자 — 재시도만 멱등 키로 차단

▸ 자체 × 이더리움 — 새로워지는 것: 주소

    Note over BE,WL: xpub(공개키 쪽 사본)만으로 자식 주소가 계산된다 — HSM 호출 없음. 개인키는 출금 서명 때 HSM 안에서 같은 번호로 파생 (6p)
    MGR->>DIR: 주소 저장 (계정 1024번 · 3번째)
    MGR->>WL: 감시 목록 등록 — 등록 실패면 발급도 실패
    MGR-->>BE: 주소 (0xAb3…)

이더리움 발급은 번호 소비, 공개키 수학, 등록의 세 가지다. 계산 자체는 공짜에 즉시지만 본질은 DB 저장과 감시 등록이라는 상태 변경이다. 그래서 발급은 쓰기 동작이고 멱등 키로 감싼다. 보안 단서도 하나 있다. xpub 은 이름과 달리 비밀급으로 다룬다. xpub 이 유출된 상태에서 자식 개인키가 하나라도 새면 부모 키가 역산되는 알려진 성질 때문이다.

▸ 자체 × Canton — PartyId 선발급(첫 1회) + memo 채번(매번)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    box rgb(239,246,255) 블록체인 매니저
    participant MGR as 자체 매니저
    participant HSM as HSM (키 보관)
    participant WL as memo 귀속표 (인덱서)
    end
    participant PN as Canton 노드
    participant DIR as 블록체인 매니저 DB

    BE->>MGR: issueDepositAddress(계정 1024번, Canton 자산)
    alt PartyId 미발급 — 이 계정의 첫 Canton 식별자
        MGR->>HSM: 이 계정용 공개키 준비
        HSM-->>MGR: 공개키
        MGR->>PN: 신원 등록 (공개키 제출) → 서명할 해시
        PN-->>MGR: 서명할 해시
        MGR->>HSM: 해시 서명 (키는 HSM 밖으로 안 나옴)
        HSM-->>MGR: 서명
        MGR->>PN: 서명 제출 → PartyId 발급 (선발급 · 유료 · 1회)
        PN-->>MGR: PartyId
        MGR->>DIR: PartyId 저장 — 등록 시도는 선기록 (이중 등록 방지)
    else 이미 발급됨
        Note over MGR,DIR: DB의 PartyId 재사용 — 온장 호출 없음
    end
    MGR->>MGR: 새 memo 채번 — 체인 호출 없음 (장부 작업)
    MGR->>DIR: 식별자 저장 (PartyId + 새 memo)
    MGR->>WL: memo 귀속표 등록 — 등록 실패면 발급도 실패
    MGR-->>BE: Address(PartyId, 새 memo)

두 단계로 읽는다. 먼저 선발급(첫 1회)은 PartyId 가 없을 때 온장 등록해 PartyId 를 만드는 단계다. memo 는 PartyId 위에 붙는 라우팅 태그라서 PartyId 가 먼저 존재해야 하므로 "선발급"이라 부른다. 유료에 비멱등이라 출금(6p)처럼 등록 시도를 선기록하고, 재시도는 "PartyId 있나"부터 조회한다. 다음으로 채번(매번)은 이후 모든 발급이 그 PartyId 를 재사용하며 memo 만 늘리는 단계다(체인 호출 없는 장부 작업). 이더리움의 "주소가 매번 새로"와 정확히 대칭을 이룬다. Canton 은 신원(PartyId)이 고정이고 입금자 코드(memo)가 매번 새로워진다. 인덱서(4p)는 watch-list 대신 이 memo 귀속표로 "누구 돈인지"를 가른다.

▸ Fireblocks (양 체인) — 벤더가 발급한다

    box rgb(239,246,255) 블록체인 매니저
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)
    end
    participant DIR as 블록체인 매니저 DB

    BE->>FBI: issueDepositAddress(계정, 자산)
    FBI->>FB: 새 입금 주소 생성 API (generateNewAddress)
    Note over FBI,DIR: 이더리움 = 새 주소 / Canton = PartyId(첫 1회 벤더가 등록) + 새 memo 자동 — 콘솔·문서로 확인, memo 생성 보장 규칙은 적용 전 통합 테스트로
    FB-->>FBI: Address(주소, memo?)
    FBI->>DIR: 식별자 저장 — 감시·귀속은 벤더 몫 (vault 가 곧 감시 범위)
    FBI-->>BE: 식별자

벤더 호출은 양 체인에서 같은 한 줄이고, 무엇이 새로워지는지(주소 vs memo)는 벤더가 체인에 맞춰 정한다. 자체 분면의 두 그림이 벤더 안으로 접힌 모양이다. 식별자가 Fireblocks 키·채번에서 나온다는 사실은 8p(전환 — 자금은 이사)에서 비용으로 돌아온다.

표에서 읽을 것은 두 축입니다. "새로워지는 것" 행은 체인 축으로, "누가 만들고 누가 감시하나"는 custody 축으로 갈리는데 1페이지의 패턴 그대로입니다. 참고로 이 페이지엔 원래 "Canton 은 발급이 없다(타입 부재)"는 분면이 있었습니다. Fireblocks 콘솔이 memo 를 자동 발급하는 것을 확인하면서 식별자 재정의로 분면이 합쳐졌고, "기능 부재(타입 없음)" 패턴은 출금의 boost 에서 다시 만납니다(6p).

백엔드에서 이렇게 부른다 — 분기가 없다

// 입금 안내 화면까지 — 한 동사, 분기 없음
suspend fun issueAndGuide(account: Account, asset: Asset): DepositGuide {
    val id = accounts.issueDepositAddress(account, asset)  // 이더리움 = 새 주소 · Canton = 새 memo
    return DepositGuide(address = id.value, memo = id.memoTag)   // memo 가 null 이면 화면에서 생략
}

식별자 재정의가 코드에 남긴 효과다. 예전엔 "Canton 은 발급이 없다"는 capability 분기가 여기 있었지만, 발급물을 주소+memo 쌍으로 일반화하자 분기 자체가 소멸했다. 백엔드는 무엇이 새로워졌는지도 모른다.
