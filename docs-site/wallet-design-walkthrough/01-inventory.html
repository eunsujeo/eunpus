Fireblocks 해부 — 기능 인벤토리와 사용처 매트릭스

이 한 장의 표가 이후 아홉 페이지의 좌표계입니다

익숙한 것 ↔ 깨지는 지점 외부 의존성을 도입할 때 우리는 보통 API 문서에서 "쓸 것"만 골라냅니다. 여기서는 반대로 갑니다 — 가장 묶음이 큰 벤더(Fireblocks)의 표면 전체를 훑으면, 그것이 곧 수탁 지갑에 필요한 기능의 전집이고, 우리가 만들어야 할 것의 목록이기 때문입니다.

방법은 단순합니다. Fireblocks API 표면을 기능 단위로 끊고, 각 기능에 두 가지를 묻습니다 — "우리 서비스의 어느 장면에서 쓰이는가"(사용처), 그리고 "우리 업무 언어로 부르면 무엇인가"(도메인 동사). 벤더의 메서드 이름이 아니라 도메인 동사로 적는 이유는 3페이지에서 드러납니다 — 이 마지막 열이 그대로 포트가 됩니다.

표를 읽는 법 — 세 가지가 이미 보입니다

① 발급과 조회는 다른 행입니다. 주소를 "만드는 것"과 "보여주는 것"은 사용처도 빈도도 다른 동작입니다 — 이 구분이 5페이지의 첫 번째 불변식이 됩니다. ② 마지막 행(서명 정책)은 동사가 없습니다. 어느 화면도 직접 부르지 않지만 출금의 모든 행 뒤에 서 있는 기능 — 포트가 아니라 신뢰 경계(8p)의 일입니다. ③ 이 표에 없는 것도 정보입니다. 임의 외부 주소의 조회·이력은 Fireblocks 가 주지 않습니다 — 필요해지면 custody 와 별개 슬롯(자체 인덱서)로 붙는다는 것만 기억해 두세요.

다음 페이지에서는 이 표에서 가장 굵은 행 하나 — createTransaction — 를 해부합니다. 매트릭스에선 한 행이지만, 자체 구축에선 파이프라인 하나입니다.

근거: Fireblocks 표면은 공식 문서에서 확인한 범위이며 일부 조회 엔드포인트는 적용 전 확인 필요 — 상세 매핑은 가이드 14장 (14.7 REST 매핑 표), 포트 정의는 13장.
