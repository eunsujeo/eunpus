계정 생성 — createAccount

고객 온보딩의 첫 호출 — "이 고객의 자산을 담을 자리"를 만든다

무엇·언제: 고객이 가입하면 백엔드가 매니저에 계정 하나를 요청합니다. 계정은 주소가 아닙니다 — 한 고객의 여러 자산·여러 주소를 묶는 상위 핸들이고, 주소는 다음 페이지(발급)에서 이 계정 밑에 생깁니다. 네 분면 공통의 포트 호출은 한 줄입니다:

createAccount(고객 ref) → Account     // 결과는 항상 계정 디렉터리(우리 DB)에 저장

▸ 자체 × 이더리움 — 장부에 줄 하나 (체인에 안 간다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: createAccount(고객 ref)
    MGR->>MGR: 번호 할당 — 계정 1024번
    Note over BE,DIR: 체인 호출 없음 · 키 생성 없음 · 비용 0 — 키는 셋업 때 만든 그 하나, 번호만 늘어난다
    MGR->>DIR: 계정 저장 (ref ↔ 1024번)
    MGR-->>BE: Account(1024번)

이더리움 쪽 계정 생성은 순수 장부 작업이다 — 고객이 100만 명이어도 키는 하나, 계정은 번호 100만 개. 그래서 공짜고, 실패할 외부 요인도 없다.

▸ 자체 × Canton — 계정 생성이 곧 "주소의 탄생" (체인에 간다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant HSM as HSM (키 보관)
    participant PN as Canton 노드
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: createAccount(고객 ref)
    MGR->>HSM: 이 계정용 공개키 준비
    MGR->>PN: 신원 등록 요청 (공개키 제출)
    PN-->>MGR: 등록 문서 + 서명할 해시
    MGR->>HSM: 해시 서명 (키는 HSM 밖으로 안 나옴)
    MGR->>PN: 서명 제출 → 등록 확정
    PN-->>MGR: PartyId 발급 — 이것이 곧 이 계정의 "주소"
    MGR->>DIR: 계정 + PartyId 저장
    MGR-->>BE: Account

Canton 에는 이더리움식 주소가 없다 — 대신 PartyId(체인 위의 신원)가 있고, 그것은 온장(on-ledger) 등록으로만 생긴다. 등록에는 서명이 필요하고 네트워크 비용이 든다. 즉 같은 createAccount 가 이더리움에선 공짜 장부 작업, Canton 에선 유료 체인 트랜잭션이다 — 주소가 계정과 함께 태어나므로, 다음 페이지의 "주소 발급"이 Canton 엔 없다. 그리고 이 분면은 온장 쓰기라 출금(5p)의 규칙이 여기에도 적용된다 — 등록 시도를 먼저 기록하고, 재시도는 "이미 등록됐나"부터 조회한다(유료·비멱등이라 이중 등록을 막아야 하므로). 어느 고객에게 이 분면이 필요한지는 온보딩 요청의 asset 이 정한다 — 아래 사용 코드의 openWallet(ref, asset).

▸ Fireblocks — vault 생성 API 한 번 (양 체인 공통)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>FBI: createAccount(고객 ref)
    FBI->>FB: vault 계정 생성 API
    Note over FBI,DIR: vault = Fireblocks 의 계정 단위, 키는 Fireblocks MPC 보관. Canton 자산이면 party 등록 절차가 더해진다 — 전용 SDK 가 수행하고 FB 가 서명 (상세는 적용 전 확인)
    FB-->>FBI: vaultId (+ Canton 이면 PartyId)
    FBI->>DIR: 계정 저장 (ref ↔ vaultId · PartyId)
    FBI-->>BE: Account

우리 쪽 동작은 체인과 무관하게 하나다 — 자체 분면에서 갈라졌던 "번호 할당 vs 온장 등록"의 차이를 벤더가 흡수하기 때문. 단 차이가 사라지는 건 아니다: Canton 의 온장 등록·비용·party 는 벤더 안에서 여전히 일어난다(서명 주체만 우리 HSM → Fireblocks MPC). 디렉터리 저장은 여기서도 빠지지 않는다 — 이후 "고객 → 계정" 해석은 벤더에 묻지 않는 우리 데이터.

표에서 읽을 것: 갈라지는 축은 custody(자체/FB)가 아니라 체인입니다 — 그래서 Fireblocks 쪽은 열 하나로 합쳐집니다(체인 차이를 벤더가 흡수하므로 우리 동작이 같음). 그리고 어느 열이든 마지막 줄이 같습니다: 디렉터리는 항상 우리 것.

백엔드에서 이렇게 부른다 — 네 분면 공통

// 온보딩 유스케이스 — 어느 분면이 꽂혀 있든 이 코드는 같다
suspend fun openWallet(ref: AccountRef, asset: Asset): OpenedWallet =
    withIdempotency("open-wallet:$ref:$asset") {           // 같은 요청 재시도 안전
        val account = accounts.createAccount(ref)           // ← 이 페이지의 4분면
        directory.save(account)                             // 결과는 항상 우리 DB 에
        val address = acquireFirstAddress(account, asset)   // 첫 주소 확보 — 2p 에서
        OpenedWallet(account, address)
    }

백엔드는 매니저가 자체인지 Fireblocks 인지, 자산이 이더리움인지 Canton 인지 모른 채 이 코드를 실행한다 — 4분면은 전부 포트 아래의 일이다.
