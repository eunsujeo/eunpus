계정 생성 — createAccount

고객 온보딩의 첫 호출 — "이 고객의 자산을 담을 자리"를 만든다

무엇·언제: 고객이 가입하면 백엔드가 매니저에 계정 하나를 요청합니다. 계정은 주소가 아닙니다 — 한 고객의 여러 자산·여러 주소를 묶는 상위 핸들이고, 주소는 다음 페이지(발급)에서 이 계정 밑에 생깁니다. 네 분면 공통의 포트 호출은 한 줄입니다:

createAccount(고객 ref) → Account     // 결과는 항상 계정 디렉터리(우리 DB)에 저장

▸ 자체 × 이더리움 — 장부에 줄 하나 (체인에 안 간다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: createAccount(고객 ref)
    MGR->>MGR: 키 트리의 다음 가지 번호 할당 (예 — 계정 #1024)
    Note over MGR: 체인 호출 없음 · 키 생성 없음 · 비용 0
키는 셋업 때 만든 그 하나, 번호만 늘어난다
    MGR->>DIR: 계정 저장 (ref ↔ #1024)
    MGR-->>BE: Account(#1024)

이더리움 쪽 계정 생성은 순수 장부 작업이다 — 고객이 100만 명이어도 키는 하나, 계정은 번호 100만 개. 그래서 공짜고, 실패할 외부 요인도 없다.

▸ 자체 × Canton — 계정 생성이 곧 "주소의 탄생" (체인에 간다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 자체 매니저
    participant HSM as HSM (키 보관)
    participant PN as Canton 노드
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: createAccount(고객 ref)
    MGR->>HSM: 이 계정용 공개키 준비
    MGR->>PN: 신원 등록 요청 (공개키 제출)
    PN-->>MGR: 등록 문서 + 서명할 해시
    MGR->>HSM: 해시 서명 (키는 HSM 밖으로 안 나옴)
    MGR->>PN: 서명 제출 → 등록 확정
    PN-->>MGR: PartyId 발급 — 이것이 곧 이 계정의 "주소"
    MGR->>DIR: 계정 + PartyId 저장
    MGR-->>BE: Account

Canton 에는 이더리움식 주소가 없다 — 대신 PartyId(체인 위의 신원)가 있고, 그것은 온장(on-ledger) 등록으로만 생긴다. 등록에는 서명이 필요하고 네트워크 비용이 든다. 즉 같은 createAccount 가 이더리움에선 공짜 장부 작업, Canton 에선 유료 체인 트랜잭션이다 — 주소가 계정과 함께 태어나므로, 다음 페이지의 "주소 발급"이 Canton 엔 없다.

▸ Fireblocks × 이더리움 — vault 생성 API 한 번

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>FBI: createAccount(고객 ref)
    FBI->>FB: vault 계정 생성 API
    Note over FB: vault = Fireblocks 의 계정 단위
키는 Fireblocks MPC 가 보관
    FB-->>FBI: vaultId
    FBI->>DIR: 계정 저장 (ref ↔ vaultId)
    FBI-->>BE: Account

자체 분면의 "번호 할당"이 "벤더 API 호출"로 바뀌었을 뿐, 백엔드가 본 것은 동일하다. 디렉터리 저장이 여기서도 빠지지 않는 것에 주목 — 이후 모든 요청의 "고객 → 계정" 해석은 벤더에 묻지 않고 우리 DB 로 푼다(벤더를 바꿔도 남는 데이터).

▸ Fireblocks × Canton — vault + 전용 절차

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>FBI: createAccount(고객 ref)
    FBI->>FB: vault 생성 + Canton party 절차
    Note over FB: party 등록은 전용 SDK 가 수행하고
Fireblocks 는 그 서명을 담당 (키는 FB MPC)
— 상세 절차는 적용 전 공식 문서 확인
    FB-->>FBI: vaultId + PartyId
    FBI->>DIR: 계정 + PartyId 저장
    FBI-->>BE: Account

Fireblocks 도 Canton 의 "온장 등록" 성질을 피해 갈 수 없다 — 누가 서명하느냐(우리 HSM → Fireblocks MPC)만 바뀐다. 체인의 성질은 custody 를 바꿔도 따라온다는 첫 사례.
