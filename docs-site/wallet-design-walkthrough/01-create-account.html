계정 생성 — createAccount

고객 한 명당 한 번 — 체인과 무관한 "그릇(vault)"을 만든다

무엇·언제: 고객이 가입하면 백엔드가 매니저에 계정 하나를 요청합니다. 계정은 주소가 아닙니다. 한 고객의 여러 자산·여러 주소를 묶는 상위 핸들(vault)이며, 주소·신원은 다음 페이지(발급)에서 이 계정 밑에 생깁니다. 중요한 건 호출이 고객당 한 번이라는 점입니다. 시그니처에 asset 이 없어(createAccount(ref)) 이더리움용·Canton용을 따로 부르지 않습니다. 그래서 이 페이지는 custody 축으로만 갈립니다:

createAccount(고객 ref) → Account     // 결과는 항상 블록체인 매니저 DB에 저장

▸ 자체 (양 체인 공통) — 장부에 vault 한 줄 (체인에 안 간다)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    box rgb(239,246,255) 블록체인 매니저
    participant MGR as 자체 매니저
    end
    participant DIR as 블록체인 매니저 DB

    BE->>MGR: createAccount(고객 ref)
    MGR->>MGR: 번호 할당 — 계정 1024번
    Note over BE,DIR: 체인 호출 없음 · 키 생성 없음 · 비용 0 — 어떤 체인을 쓸지 아직 모른다. 키는 셋업 때 만든 그 하나, 번호만 늘어난다
    MGR->>DIR: 계정 저장 (ref ↔ 1024번)
    MGR-->>BE: Account(1024번)

createAccount 는 순수 장부 작업이라 이더리움이든 Canton 이든 동작이 같고, 그래서 자체 분면이 하나로 합쳐졌다. 고객이 100만 명이어도 키는 하나, 계정은 번호 100만 개다. 공짜고 실패할 외부 요인도 없다. 체인 위의 신원(이더리움 주소·Canton PartyId)은 여기서 만들지 않는다. asset 을 처음 아는 2p 발급에서 태어난다. createAccount(ref) 에 asset 인자가 없다는 것이 그 증거다. 인자로 받지 않은 체인의 일(PartyId 등록)을 할 수는 없다. Canton PartyId 가 여기가 아니라 2p 에서 선발급되는 이유다.

▸ Fireblocks — vault 생성 API 한 번 (양 체인 공통)

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    box rgb(239,246,255) 블록체인 매니저
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)
    end
    participant DIR as 블록체인 매니저 DB

    BE->>FBI: createAccount(고객 ref)
    FBI->>FB: vault 계정 생성 API
    Note over FBI,DIR: vault = Fireblocks 의 계정 단위, 키는 Fireblocks MPC 보관. Canton PartyId 등록도 여기가 아니라 입금 식별자 발급 때 벤더가 수행 (2p · 상세는 적용 전 확인)
    FB-->>FBI: vaultId
    FBI->>DIR: 계정 저장 (ref ↔ vaultId)
    FBI-->>BE: Account

자체든 Fireblocks 든 createAccount 는 체인을 모른다. 둘의 차이는 vault 가 우리 장부냐 벤더 장부냐뿐이다. Canton 의 온장 PartyId 등록·비용은 자체든 벤더든 발생하지만, 그것이 일어나는 자리는 createAccount 가 아니라 asset 을 처음 아는 입금 식별자 발급(2p)이다. 디렉터리 저장은 여기서도 빠지지 않는다. "고객 → 계정" 해석은 벤더에 묻지 않는 우리 데이터다.

표에서 읽을 것은 이렇습니다. 이 문서에서 유일하게 체인 축이 사라지는 페이지입니다. createAccount(ref) 에 asset 인자가 없으니 이더리움이냐 Canton 이냐가 동작을 가를 수 없습니다(그래서 4분면이 아니라 custody 2분면). 고객이 한 명이면 createAccount 도 한 번이고, 체인 수만큼 부르지 않습니다. 체인 축은 다음 페이지(발급)에서 되살아납니다. 거기서 이더리움은 주소를, Canton 은 PartyId(첫 1회 선발급)+memo 를 만듭니다. 어느 쪽이든 마지막 줄은 같습니다. 디렉터리는 항상 우리 것.

백엔드에서 이렇게 부른다 — 네 분면 공통

// 온보딩 유스케이스 — 어느 분면이 꽂혀 있든 이 코드는 같다
suspend fun openWallet(ref: AccountRef, asset: Asset): OpenedWallet =
    withIdempotency("open-wallet:$ref:$asset") {           // 같은 요청 재시도 안전
        val account = accounts.createAccount(ref)           // ← 이 페이지의 4분면
        directory.save(account)                             // 결과는 항상 블록체인 매니저 DB 에
        val id = accounts.issueDepositAddress(account, asset)  // 첫 입금 식별자 — 2p (Canton 이면 PartyId 선발급 포함)
        OpenedWallet(account, id)
    }

백엔드는 매니저가 자체인지 Fireblocks 인지, 자산이 이더리움인지 Canton 인지 모른 채 이 코드를 실행한다. 4분면은 전부 포트 아래의 일이다.
