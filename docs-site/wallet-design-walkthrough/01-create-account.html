계정 생성 — createAccount

고객 한 명당 한 번 — 체인과 무관한 "그릇(vault)"을 만든다. Service 백엔드가 부른다

무엇·언제: 고객이 가입하면 Service 백엔드가 Fireblocks 매니저에 계정 하나를 요청합니다. 계정은 주소가 아닙니다. 한 고객의 여러 자산·여러 주소를 묶는 상위 핸들(vault)이며, 주소는 다음 페이지(발급)에서 이 계정 밑에 생깁니다. 여기서 vault 는 Fireblocks 가 제공하는 계정 단위입니다 — 우리는 이 매니저를 채택했으므로 vault 를 우리 개념이 아니라 벤더 개념으로 받아들입니다. 중요한 건 호출이 고객당 한 번이라는 점입니다. 시그니처에 asset 이 없어(createAccount(ref)) 이더리움용·Base용을 따로 부르지 않습니다.

createAccount(고객 ref) → Account     // 결과는 항상 우리 매핑 DB 에 저장 (ref ↔ vaultId)

▸ Fireblocks — vault 생성 API 한 번 (EVM 공통)

createAccount 는 Fireblocks 의 createVaultAccount 한 번이다. vault 는 논리적 컨테이너라서 이 단계는 체인에 나가지 않고 주소도 만들지 않는다 — 그래서 이더리움이든 Base 든 동작이 같다. 고객이 100만 명이어도 vault 는 번호 100만 개일 뿐, 키는 Fireblocks vault·MPC 안에 있다. 체인 위의 주소는 여기서 만들지 않는다 — asset 을 처음 아는 2p 발급에서 태어난다. createAccount(ref) 에 asset 인자가 없다는 것이 그 증거다. "고객 → 계정" 해석은 벤더에 묻지 않는 우리 매핑 DB 의 데이터다.

계정은 주소가 아니라 vault 핸들 — 그리고 그 vault 는 Fireblocks 것

이 페이지에서 붙잡을 개념은 하나다. 계정 = vault = 여러 주소·자산을 묶는 상위 핸들이고, 주소가 아니다. 우리가 직접 vault 를 구현하지 않는다 — Fireblocks 를 채택했으므로 vault 는 벤더가 관리하고, 우리는 그 vaultId 를 고객 ref 에 이어 붙인 참조 한 줄만 매핑 DB 에 들고 있다. 키·서명·주소 파생은 전부 Fireblocks vault·MPC 안에서 일어난다. 우리 쪽엔 키 트리도, HSM 도 없다.

비교 — 체인 축이 사라지는 유일한 페이지

Fireblocks × EVM (이더리움·Base 공통)
실체벤더 createVaultAccount 한 번
체인에 가나아니오 — 이더리움도 Base 도 안 감 (vault 는 논리 컨테이너)
키 생성여기서 안 함 — 키는 Fireblocks vault·MPC 소관
체인 위 주소 생성여기서 안 함 — 이더리움·Base 주소는 2p 발급에서
우리 책임매핑 DB (ref ↔ vaultId)

표에서 읽을 것은 이렇습니다. 이 문서에서 유일하게 체인 축이 사라지는 페이지입니다. createAccount(ref) 에 asset 인자가 없으니 이더리움이냐 Base 냐가 동작을 가를 수 없습니다. 고객이 한 명이면 createAccount 도 한 번이고, 체인 수만큼 부르지 않습니다. 체인 축은 다음 페이지(발급)에서 되살아납니다 — 거기서 Fireblocks 가 EVM 주소를 만듭니다. 어느 쪽이든 마지막 줄은 같습니다. 매핑 DB(ref ↔ vaultId)는 항상 우리 것.

백엔드에서 이렇게 부른다 — Service 백엔드

// 온보딩 유스케이스 — Service 백엔드. 매니저가 무엇이든 이 코드는 같다
suspend fun openWallet(ref: AccountRef, asset: Asset): OpenedWallet =
    withIdempotency("open-wallet:$ref:$asset") {           // 같은 요청 재시도 안전
        val account = accounts.createAccount(ref)           // ← Fireblocks createVaultAccount
        directory.save(account)                             // 결과는 항상 우리 매핑 DB 에 (ref ↔ vaultId)
        val id = accounts.issueDepositAddress(account, asset)  // 첫 입금 주소 — 2p
        OpenedWallet(account, id)
    }

Service 백엔드는 자산이 이더리움인지 Base 인지 모른 채 이 코드를 실행한다. 포트가 체인 분기를 감추고, 그 아래에서 Fireblocks 가 vault 를 만든다. 멱등 키는 재시도가 vault 를 두 번 만들지 않게 막는 래퍼다.
