한 줄의 가격 — createTransaction 해부

매트릭스에선 한 행, 구현에선 파이프라인 하나

익숙한 것 ↔ 깨지는 지점 SDK 한 줄 호출의 뒤에 무엇이 있는지 우리는 보통 안 묻습니다 — 벤더가 책임지니까. 그런데 우리의 과제는 그 한 줄을 직접 만드는 것이라서, 한 줄이 숨기는 전부가 우리의 작업 목록입니다.

1페이지 매트릭스에서 가장 굵은 행이었던 출금 제출을 펼쳐 봅니다. Fireblocks 의 createTransaction 한 번은 적어도 여섯 가지를 묶고 있습니다:

한 줄이 묶고 있는 여섯 부품. 자체 구축에서 ①·④ 는 트랜잭션 파이프라인(6p), ② 는 HSM 과 신뢰 경계(8p), ③ 은 노드, ⑤·⑥ 은 인덱서(7p)가 된다 — 이 워크스루의 3막이 곧 이 그림이다.

여기서 설계 교훈이 하나 나옵니다. "묶여 있다"는 사실 자체가 인터페이스 설계의 입력입니다 — 우리 포트가 서명과 전파를 따로 노출하면(sign() / broadcast()), 묶음으로만 동작하는 Fireblocks 가 그 포트에 맞지 않게 되고 전환이 깨집니다. 그래서 포트의 동사는 묶음 그대로 — submitTransaction 하나입니다:

// 같은 동사, 다른 속 — 전환 가능성은 여기서 시작된다
// Fireblocks 구현
submitTransaction(req) { return fb.createTransaction({ …, externalTxId: req.idempotencyKey }) }

// 자체 구현 — 한 줄이 파이프라인으로 펼쳐진다 (상세는 6p)
submitTransaction(req) {
  const raw    = adapter.buildTransaction(req)   // ① 조립 · 순번 점유
  const signed = hsm.sign(raw)                   // ② 서명 (정책 게이트 경유 — 8p)
  return adapter.broadcast(signed)               // ③ 전파
}

반대 방향의 교훈도 있습니다 — 묶였다고 해서 안이 안 보여도 되는 건 아닙니다. ④~⑥(막힘·추적·통지)은 자체 구축에서 가장 사고가 잦은 영역이고, Fireblocks 를 쓰는 동안에도 "벤더가 이걸 어떻게 처리하나"를 알아야 운영이 됩니다. 그 안쪽 이야기가 3막(5~8p)입니다.
