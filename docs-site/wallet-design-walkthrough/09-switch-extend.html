확장 — 포트가 EVM 체인 확장·매니저 교체를 흡수하는 법

1~8페이지가 보여준 것을 거둬들이고, 포트 하나가 벤더와 체인의 변화를 흡수한다는 전제를 증명으로 닫는다

포트가 이룬 것 — 1~8페이지를 거둬들이면

1~8페이지 내내 두 백엔드는 Fireblocks 를 포트로만 불렀습니다. 벤더 SDK 타입도, 체인 분기도 업무 로직에 새지 않았죠. 이 한 가지 규율이 세 가지 성질을 만들었습니다 — 그리고 이 세 성질이 이 페이지가 증명할 전부입니다.

성질1~8페이지에서 본 근거
벤더 독립백엔드는 createDepositAddress·submitTransaction·getBalance 같은 업무 동사만 부른다. Fireblocks 의 createVaultAccount·createTransaction 은 어댑터 안에만 있다(0p 매트릭스). 벤더를 바꿔도 백엔드 코드는 그대로다.
다중 EVM 체인이더리움과 Base 는 같은 EVM 이라 포트 표면·동사·페이지가 동일하다 — 체인만 바뀐다(0p). 체인 분기는 포트 뒤 어댑터에 갇힌다.
테스트 가능포트를 가짜 구현으로 바꾸면 벤더 없이 백엔드를 검증할 수 있다(0p). 포트 밖에서 관찰 가능한 약속은 계약 테스트로 못 박는다.

세 번째 성질은 주장이 아니라 시험입니다. 포트별 계약 테스트 한 벌을 만들어 실제 Fireblocks 어댑터(샌드박스)와 가짜 구현이 똑같이 통과하게 하면, "포트의 의미가 구현과 무관하게 보존된다"가 측정 가능한 사실이 됩니다.

다만 약속 전부가 계약 테스트에 들어가지는 않습니다. 계약 테스트가 맡는 건 포트 밖에서 관찰 가능한 약속입니다(조회는 만들지 않는다, 등록까지가 발급, 없는 기능은 타입 부재). "기록은 전파 전"(7p) 같은 내부 순서 약속은 백엔드 단위 테스트가, "판정은 가용만"(8p) 은 잔액 로직 테스트가 나눠 맡습니다. 이 세 겹이 합쳐져야 "포트가 변화를 흡수한다"는 증거가 완성됩니다.

EVM 체인 확장 — Base 는 이미 붙었다

확장의 첫 축은 체인입니다. 그런데 이건 이미 과거형입니다. Base 는 이더리움과 같은 EVM(account 기반·공개 mempool·reorg·동일 주소 체계·같은 확정 모델)이라, 이더리움을 붙인 어댑터가 그대로 Base 도 태웁니다. 0p 매트릭스에서 Base 가 이더리움과 표면·동사·페이지를 공유한 것이 그 결과였죠.

그래서 "다른 L2 가 하나 더 붙는다"는 일은 두 백엔드에게 0줄입니다. 늘어나는 건 포트 뒤 어댑터가 인식하는 체인·자산 등록뿐입니다.

EVM 체인 확장의 형태. 새 EVM 체인이 붙어도 파랑(두 백엔드)은 0줄, 초록(어댑터)에 체인·자산 등록만 는다. Base 가 이미 이 방식으로 붙었다(이더리움과 같은 EVM 어댑터). 전제는 둘 — 어댑터가 체인별 실패를 공통 분류로 번역하고(재전송 안전 / 재조립 필요 / 영구 실패), 체인이 못 하는 일을 기능 부재로 선언해야 한다(2p). 이 둘이 새면 체인 분기가 백엔드로 스며들어 "0줄"이 거짓이 된다.

확장의 검증 지점 — 계약 테스트를 샌드박스로 돌린다

새 EVM 체인을 등록하면, 그 체인을 대상으로 같은 계약 테스트 한 벌을 Fireblocks 샌드박스에서 다시 돌립니다. 조회가 새 주소를 만들지 않는지, 없는 기능이 타입 부재로 드러나는지를 체인마다 확인하는 거죠. 별도 테스트넷을 운영할 필요가 없습니다 — 검증은 벤더 샌드박스가 제공하는 EVM 환경에서 이뤄집니다.

매니저(벤더) 교체 — 코드는 어댑터, 비용은 자금 이전

확장의 둘째 축은 매니저(벤더)입니다. 지금 매니저는 Fireblocks 이지만, 포트로 감쌌으므로 다른 벤더로 바꾸거나 vault 구성을 재편해도 두 백엔드는 그대로여야 합니다. 코드 관점에서 벤더 교체는 어댑터를 하나 더 만들고 주입을 바꾸는 설정 수준의 일입니다.

그런데 한 가지는 설정으로 안 됩니다. 벤더 A 의 주소는 A 의 키에서, 벤더 B 의 주소는 B 의 키에서 나옵니다(2p). 그래서 주소와 그 위의 잔액은 이전되지 않습니다. 이건 vault 를 재구성할 때도 마찬가지입니다 — 새 vault 의 주소는 새 키에서 나오니까요. 즉 코드 교체는 싸고, 자금 이전(sweep)이 비용의 전부입니다.

벤더 교체(또는 vault 재구성) 운영 타임라인. 파랑은 값싼 코드·설정 작업, 노랑 구간이 비용의 전부다. 그 비용은 구 주소 수와 잔액에 비례한다 — 옮길 돈이 많을수록 sweep 출금 건수·수수료가 는다. 늦은 입금을 놓치지 않도록 구 주소 watch-list 를 한동안 유지하다가, 잔액을 새 vault 로 출금(7p 출금 그대로)하고, DB 에 주소의 세대를 기록해 닫는다. 정책 게이트의 규칙(화이트리스트·한도·일일 누적)도 새 벤더의 거버넌스 정책으로 이관하고 동등성을 검증하는 것까지가 교체다(7p).

Service·Admin 물리 분리가 확장·감사에 주는 이점

확장과 교체를 안전하게 만드는 밑바탕이 두 백엔드의 물리 분리입니다(0p). Service(고객 런타임)와 Admin(운영·거버넌스)이 별도 배포·권한·감사 경계로 나뉘어 있어서:

  • 운영 변경이 런타임을 안 건드린다. 벤더 교체의 정책 이관, 새 체인의 자산 등록, sweep 출금 같은 운영 액션은 Admin 쪽에서 일어납니다. 고객이 쓰는 Service 백엔드의 배포를 흔들지 않고 확장 작업을 진행할 수 있습니다.
  • 권한 경계가 명확하다. 자금을 옮기는 sweep, 정책을 바꾸는 이관은 Admin 권한이라, "누가 확장 중에 자금을 움직였나"가 감사 경계 안에서 그대로 남습니다. Service 자격증명으로는 이 동작을 할 수 없습니다.
  • 감사가 쉬워진다. 두 경계가 분리돼 있어 확장·교체 기간의 운영 로그(Admin)와 고객 트래픽(Service)이 섞이지 않습니다.

코드 구조 — 이 문서를 모노레포로 옮기면

지금까지의 구성 요소(0p)와 성질이 코드에서 강제되려면 모듈 경계가 곧 설계 경계여야 합니다.

모듈 사이의 의존 방향이 이 문서의 성질들을 컴파일 타임에 강제합니다. 화살표는 "의존한다"라는 뜻이고, 전부 안쪽(domain)을 향합니다.

의존 그래프에서 성질 셋이 읽힙니다. ① 두 backend → domain 뿐. 백엔드는 adapters 를 모르므로(화살표가 없다) "어느 벤더인지 모른다"가 컴파일 타임의 사실이 된다. 어댑터를 아는 곳은 apps 의 DI(점선)뿐이다. ② adapters/fireblocks 가 주 구현이고, fake 는 테스트용 가짜 구현이다. 벤더를 바꾸려면 새 어댑터를 이 자리에 더하고 주입만 바꾼다 — backend 는 0줄. ③ Fireblocks SDK 는 adapters/fireblocks 안에 격리된다. 벤더 타입이 그 밖으로 새면 교체가 깨지므로, 이 경계는 빌드 규칙(의존 검사)으로 막는다. Service·Admin 이 별도 backend·apps 모듈인 것이 곧 물리 분리다.

인프라 — 무엇이 어디서 도는가

0p 에서 본 배치를 확장 관점으로 다시 봅니다. Fireblocks 기준이라 서명·키·노드·전파는 벤더 안이고, 이쪽엔 두 백엔드와 폴링 워커, DB만 남습니다. 직접 노드·HSM·인덱서를 운영하지 않으므로, 새 EVM 체인이 붙어도 인프라 배치는 그대로입니다 — 벤더가 그 체인을 지원하기만 하면 됩니다.

Fireblocks 기준 배치(0p 와 일관). 운영 대상은 셋 — 두 백엔드(물리 분리)와 폴링 워커·DB. 서명·MPC·TAP·노드·전파는 벤더 안에서 돈다. 새 EVM 체인은 벤더 쪽(EVM 네트워크)과 어댑터의 등록에서만 늘 뿐, 이 그림의 이쪽 구성은 그대로다. 노드·HSM·인덱서를 직접 두지 않는 대신 폴링 워커가 벤더로 나가는 outbound 조회가 주 수신 경로라, egress 허용·조회 주기·가용성이 운영 항목이 된다(webhook 은 환경 허용 시 보조, 4p). 벤더 교체 시엔 이 그림의 Fireblocks 상자만 다른 벤더로 바뀌고, 이쪽 상자들은 자금 sweep 을 제외하면 그대로다.

마무리 — 포트 하나가 두 축의 변화를 흡수한다

"매니저를 바꿔도 두 백엔드는 그대로다." 1~8페이지의 모든 포트 호출이 그 근거이고, 계약 테스트로 못 박은 뒤 어댑터를 더하고 주입만 바꾼다 — 남는 건 자금 sweep 운영뿐이다. "EVM 체인이 늘어도 영향이 없다." Base 가 이미 이더리움과 같은 EVM 어댑터로 붙었고, 다른 L2 는 어댑터의 등록 한 줄이다. "운영이 런타임을 안 건드린다." 확장·교체·sweep 은 Admin 경계 안에서 일어나 고객 런타임(Service)과 분리된다. 포트 하나가 벤더와 체인, 두 축의 변화를 모두 흡수한다 — 그것이 이 문서의 1차 목표였다.
