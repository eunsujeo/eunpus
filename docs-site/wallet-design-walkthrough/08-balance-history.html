잔액과 내역 조회 — getBalance · transactionsOf

고객 화면의 두 숫자 — 잔액의 진실은 DB 원장에, 내역의 진실은 벤더 기록에 있다

무엇·언제: 고객 홈 화면의 잔액과 거래내역 화면 뒤의 읽기입니다. 먼저 잔액의 규칙. 잔액은 세 칸입니다. 가용(available — 출금에 쓸 수 있는 돈), 대기(pending — 들어왔지만 아직 확정 전, 5p), 잠김(locked — 나가는 중이거나 정책상 묶인 돈, 7p). 출금 가능 판정은 가용만 봅니다. 대기·잠김을 합쳐 보여주는 화면이야 자유지만, 합쳐서 판정하는 순간 없는 돈을 쓰게 됩니다.

// 온체인 지갑(옴니버스 · sweep 전 고객 vault) 조회 — 운영·대사용
getBalance(지갑, 자산) → Balance { available, pending, locked }
// 내역 — 벤더 기록이 진실
transactionsOf(계정, 기간) → List<Transfer>
잔액의 진실은 두 군데로 갈린다 — 고객 잔액은 DB 원장, 온체인 잔액은 벤더 조회

고객 화면의 잔액은 getBalance 가 아니라 DB 원장에서 나옵니다. 입금 자산은 sweep 으로 옴니버스에 모이므로(5p) 고객별 온체인 잔액이라는 것이 애초에 없습니다 — 고객별 세 칸은 DB 원장이 관리하고, 그 전이는 폴링·확정 처리(4·5p, 대기→가용)와 출금 접수(7p, 가용→잠김)가 반영합니다.

벤더 getBalance 는 온체인 지갑의 조회입니다 — 옴니버스·재고 풀, 그리고 sweep 전 고객 vault 의 일시 잔액. 인덱서도 잔액 파이프라인도 만들지 않고, Fireblocks 의 getVaultAccountAsset 응답을 업무 타입 Balance 로 접을 뿐입니다. 내역(transactionsOf)은 벤더 거래 기록이 그대로 진실입니다.

온체인 지갑 조회 — 벤더 필드를 세 칸으로 접는다

옴니버스·재고 풀 같은 온체인 지갑을 조회할 때는 Fireblocks 의 getVaultAccountAsset 응답을 받아 세 칸으로 접습니다.

업무 타입Fireblocks 필드뜻
가용 (available)available확정되어 지금 출금에 쓸 수 있는 잔액 (= 블록체인 잔액 − 잠김분)
대기 (pending)pending들어오는 중이지만 아직 확정 전 — 확정 임계에 도달하면 가용으로 옮겨간다
잠김 (locked)lockedAmount + frozen나가는 중(전파 전 출금)이거나 정책상 묶인(AML freeze) 돈

Fireblocks 응답 필드는 available / pending / frozen(AML freeze) / lockedAmount(전파 전 출금) / staked(일부 체인 전용) 등이다. 이 중 가용·대기·잠김 세 칸만 업무 타입으로 노출하고, 잠김은 lockedAmount 와 frozen 을 합쳐 본다. EVM(이더리움·Base)에는 staking 칸이 없어 세 칸으로 충분하다.

세 칸을 가르는 선 — confirm 과 finality

대기와 가용을 나누는 것은 확정입니다. 4페이지에서 본 규칙 그대로예요. 돈이 체인에 등장(confirm)했다고 곧바로 쓸 수 있는 게 아니라, 확정 정책이 정한 임계 confirmation 수에 도달(finality)해야 가용이 됩니다. 이 전이를 DB 원장의 대기→가용 반영으로 옮기는 근거가 벤더의 상태·confirmation 카운트입니다.

세 칸을 가르는 건 confirm(체인 등장) → finality(임계 도달) 전이 하나다. "곧 들어올 입금"은 대기 칸에 머물다가, 확정 정책 임계에 도달해 finality 가 나면 가용으로 옮겨간다. Fireblocks 상태로는 CONFIRMING(대기) 에서 COMPLETED(가용) 로의 전이이고, 그 경계 판단은 numOfConfirmations 가 확정 정책 임계를 넘었는지로 한다. 출금을 제출하면 그만큼이 가용에서 잠김으로 빠진다.

확정 임계는 정책(DCCP)이 정한다 — 대부분 1, 예외가 있다

Fireblocks 거래 상태는 전파 뒤 BROADCASTING → CONFIRMING → COMPLETED 로 흐릅니다. COMPLETED = 확정 정책이 정한 임계 confirmation 수에 도달한 상태이고, 그때가 곧 finality 입니다. 그 임계는 확정 정책(Fireblocks 의 DCCP?)이 체인별로 정하는데, 기본값은 대부분 1 confirmation입니다. 예외로 이더리움 클래식은 372, 컨트랙트 호출은 3 confirmation 을 권장 최소로 둡니다.

그래서 대기↔가용 경계는 직접 블록을 세서 정하는 게 아니라 벤더가 정책대로 계산해 상태로 알려주는 값입니다. 상태(CONFIRMING/COMPLETED)와 numOfConfirmations 를 읽어서 세 칸에 반영합니다. 이더리움과 Base 는 같은 EVM 이라 이 흐름이 동일합니다.

호출 한 장 — 고객 화면은 DB 로 끝나고, 벤더 API 는 운영·대사·내역 몫

    FB-->>FBI: 내역 (상태 · numOfConfirmations 포함)

고객 화면은 DB 원장으로 끝난다(1) — 벤더 호출이 없어 빠르고, 벤더 장애와도 분리된다. 벤더 조회(2~9)는 온체인 지갑의 운영·대사와 내역의 몫이다. 벤더가 입·출금을 다 기록하므로 이쪽 병합이 필요 없고, 포트 구현이 하는 일은 벤더 필드를 세 칸으로 접는 것과 벤더 상태(CONFIRMING/COMPLETED)를 5·7페이지의 공통 어휘로 번역하는 것뿐이다.

경계 하나만 분명히 해 둡니다. 이 동사들은 서비스 고객 계정(vault)을 조회합니다. 서비스 고객이 아닌 임의 외부 주소의 잔액·이력 조회는 Fireblocks 가 이 API 로 주는 기능이 아니라, 정말 필요해지면 그 용도의 조회 수단을 따로 둡니다. 고객 계정 조회와는 별개의 선택입니다.

상태로 걸러 조회 — 대사·운영용

transactionsOf 는 기간뿐 아니라 상태로도 걸러 부를 수 있다 — 매니저가 서버측 status 필터를 제공하므로 전체를 받아 거르지 않고 필요한 상태만 받는다(한 번에 한 상태). 주 감지 경로인 폴링(4p)도 이 조회를 쓰며, status 필터는 그중 대사·운영에 특화된 형태다. 부르는 백엔드는 갈린다 — 고객 화면 경로는 Service, 대사·운영 조회는 Service·Admin 양쪽이다(0p 매트릭스 — 같은 포트, 다른 배포·권한·감사 경계).

언제무엇을
대사 (Service·Admin)COMPLETED 만 기간별로 받아 기록과 대조 — 회계 기표 전
실시간 감지 (Service)주기 폴링으로 CONFIRMING·COMPLETED 전이를 감지 — 주 경로(4p)
막힌 출금 점검 (Admin)오래 CONFIRMING 인 건을 뽑아 boost·cancel 판단 (7p)
배치 정산 확인15분 델타 배치 전송이 COMPLETED 됐는지 확인해 settled 처리 (10p)

실시간 입금 감지도 이 폴링이 주 경로다(4p). finality 로 거를 땐 COMPLETED 여도 numOfConfirmations ≥ 임계를 함께 본다(4p, zero-confirmation 대비).

대사 — 두 장부를 주기적으로 맞춘다

잔액·내역의 숫자는 결국 두 장부에서 나옵니다. 하나는 기록(DB), 다른 하나는 바깥의 진실인 Fireblocks 의 값입니다. 벤더 조회가 아무리 정확해도 폴링 누락·지연·이쪽 반영 버그는 생기게 마련이라, 회계가 걸리는 숫자는 주기적으로 둘을 직접 대조합니다.

대사
무엇을① DB 원장의 고객 잔액 합계 vs 옴니버스 온체인 잔액 — 옴니버스 모델의 대사 공식 ② 거래 기록 vs 벤더 거래 목록 (표본은 온체인 탐색기로 교차 확인)
언제주기(예: 시간 단위) + 일마감 — 회계 기표 전 필수
누가운영·감사 경계라 Admin 도 함께 조회 (Service·Admin)
어긋나면자동 보정 금지 — 정정 이벤트를 만들어 사람이 본다 (없는 돈을 만들거나 지우는 코드가 가장 위험)

4p 의 "최종 근거는 대사" 규칙을 회계로 옮긴 버전이다. 화면은 벤더 값으로 빠르게, 장부는 대조로 정확하게. 대기↔가용이 벤더 상태(CONFIRMING/COMPLETED)로 움직이므로, 대사도 그 상태 기준으로 기록과 맞춘다.

더 깊이: 확정 정책(DCCP)과 confirmation lifecycle · 잔액 필드 계약은 컴포넌트 가이드의 추상화 편 참고 (본 워크스루는 가이드 없이 읽힙니다).
