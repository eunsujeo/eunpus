구조는 두 층입니다

이 시스템은 두 층입니다. 위는 지갑 백엔드 — 항상 직접 만들고, 여기서는 물리적으로 분리된 두 개입니다. Service 백엔드는 고객 런타임(계정·주소·입금·출금·잔액)을, Admin 백엔드는 운영·거버넌스(정책·승인·키 운영·동결·rebalance)를 맡고, 별도 배포·권한·감사 경계로 나뉩니다.

어디서 도는가 — 물리 배치

위가 논리 구조라면, 구성 요소가 실제로 어디서 도는지도 잡아 두면 1~7페이지가 쉽습니다. Fireblocks 기준 배치는 이렇습니다 — 서명·키·노드·전파는 벤더 안이고, 이쪽엔 두 백엔드(블록체인 매니저 어댑터 포함)·webhook 수신기·백엔드 DB·Co-signer가 남습니다.

Fireblocks 기준 배치. Service·Admin 은 물리적으로 분리돼 각자 포트로 벤더를 부른다 — 블록체인 매니저 어댑터는 백엔드 안의 모듈이고, ref↔vault↔주소 매핑과 원장은 백엔드 DB에 둔다. 서명은 벤더 단독이 아니다 — MPC 키 share 하나는 보안 존(SGX/TEE)의 API Co-signer가 들고 매 서명마다 공동서명하며, 서명 직전 Callback Handler(정책 훅)가 승인·거부를 건다. vault·MPC 클라우드 share·노드·전파는 벤더 몫이다(4·6p).

Fireblocks 해부 — 기능 × 사용처 매트릭스

포트의 동사들은 어디서 왔을까요. Fireblocks 의 API 표면을 분석한 결과입니다. 가장 묶음이 큰 벤더가 제공하는 것의 전체가 곧 "수탁 지갑에 필요한 기능의 전집"에 가깝고, 그것을 벤더 메서드명이 아니라 업무 언어(도메인 동사)로 바꿔 적은 것이 포트입니다. 각 기능이 어느 백엔드(Service·Admin)에서, 서비스의 어느 장면에서 쓰이는지까지 묶으면 이 표가 곧 이 문서의 목차가 됩니다.

기능Fireblocks 표면 온보딩입금출금운영·CS 도메인 동사백엔드페이지
고객 계정 생성createVaultAccount●createAccountS1p
입금 주소 생성generateNewAddress●●createDepositAddressS2p
입금 주소 조회(DB 읽기 · Fireblocks 미사용)●●getDepositAddressS3p
수신·확정 이벤트webhook●●onChainEventS4p
수수료 추정estimateFee●estimateFeeS5p
주소 형식 검증(로컬 규칙)●validateAddressS6p
출금 제출createTransaction●submitTransactionS6p
상태 조회getTransactionById●●getStatusS·A6p
막힌 출금 재촉·취소boost / cancel●●boost cancelA6p
잔액 (가용·대기·잠김)getVaultAccountAsset●●●getBalanceS·A7p
내 거래 이력거래 목록 조회●transactionsOfS·A7p
서명 정책 (한도·화이트리스트)TAP(거버넌스 정책) · co-signer●●(동사 없음 — 정책 게이트)A6p

● = 그 장면이 이 기능을 호출한다. 백엔드 열 = Service(S)·Admin(A) 중 어디서 부르나 — 나가는 돈의 정책·승인·개입(TAP·boost·cancel·동결)은 Admin, 고객 런타임(계정·주소·입금·출금 제출·조회)은 Service다. Fireblocks 표면은 공식 문서에서 확인한 범위다(일부 조회 엔드포인트는 적용 전 확인). Base 는 이더리움과 같은 EVM이라 표면·페이지·동사가 동일하다 — 체인만 바뀐다. 마지막 행만 동사가 없는데, 화면이 부르는 기능이 아니라 흐름 뒤에 서는 기능이라 그렇다(정책 게이트, 6p).

더 깊이: 컴포넌트별 상세는 블록체인 매니저 컴포넌트 가이드 (참고용 — 본 워크스루는 가이드 없이 읽힙니다).
