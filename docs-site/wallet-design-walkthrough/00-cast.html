구조는 두 층입니다

우리 시스템은 두 층으로 나뉩니다. 지갑 백엔드는 API·계정 관리·업무 규칙을 담당하고 항상 우리가 만듭니다. 그 아래 블록체인 매니저는 체인과 실제로 대화하는 층 — 주소를 만들고, 트랜잭션에 서명·전파하고, 입금을 감지합니다. 이 매니저 층이 교체 대상입니다: 자체 구축으로 시작해서 Fireblocks 로 바꿔도, 백엔드는 매니저를 포트(인터페이스)로만 부르기 때문에 코드가 바뀌지 않습니다.

두 층과 4분면. 포트 아래의 매니저(자체/Fireblocks)와 그 아래의 체인(이더리움/Canton)이 각각 둘씩 — 조합하면 네 가지 동작 경로가 나온다. 이 문서는 기능마다 그 네 경로를 전부 그린다.

4분면 읽는 법

1~6페이지는 전부 같은 형식입니다: ① 이 기능이 무엇이고 언제 불리나 → ② 포트 호출 (네 분면 공통, 글자 그대로 같음) → ③ 네 분면의 동작 다이어그램 — ▸자체×이더리움 / ▸자체×Canton / ▸Fireblocks×이더리움 / ▸Fireblocks×Canton → ④ 4분면 비교표. 어떤 분면에서 기능이 "없으면", 없는 채로 그립니다 — 없음도 동작이기 때문입니다(2페이지에서 바로 보게 됩니다).

등장인물 — 다이어그램에 나올 부품들

자체 분면의 다이어그램에는 우리가 만들 부품들이 등장합니다. 이 표가 곧 자체 구축의 작업 범위이기도 합니다:

부품역할 (한 줄)주 등장
멀티체인 어댑터체인별 규칙(주소 계산법·수수료·전파·확정 기준)을 공통 동사로 번역 — 체인 분기는 전부 이 안1·2·5p
인덱서체인을 읽어 입금 감지·확정 판정. 유일한 상시 worker — 다른 부품은 요청 올 때 돌지만 이건 체인이 흐르는 한 계속 돈다4·5·6p
트랜잭션 파이프라인출금의 조립→서명→전파를 순서대로, 단계마다 기록하며 진행 — 중간에 죽어도 같은 지점부터 재개5p
HSM + 정책 게이트HSM(키를 가두고 서명만 해주는 장비)이 키를 보관하고, 게이트가 서명 직전에 수신처·한도를 재검증 — 마지막 방어선1·2·5p
계정 디렉터리 + watch-list디렉터리 = 고객↔계정↔주소 매핑을 담는 우리 DB / watch-list = 인덱서가 감시할 우리 주소 목록전 페이지

Fireblocks 분면에서는 이 부품들이 어떻게 될까요 — 대부분 벤더 상자 안으로 들어가고, 둘만 남습니다:

전환의 예고편. 자체 분면의 부품 넷은 Fireblocks 로 가면 벤더 기능으로 대체되고, 지갑 백엔드와 계정 디렉터리는 어느 분면에서든 우리 것으로 남는다 — "다른 시스템에 영향이 없어야 한다"는 전제가 성립하는 물리적 이유. 상세는 7페이지.

마지막으로 어휘 두 개만: 키 트리 — 키는 고객마다 만들지 않고, 셋업 때 HSM 안에서 한 번 만든 뿌리 키에서 가지(번호)를 늘려 갑니다(2페이지에서 동작으로 확인). 멱등 키 — 같은 요청의 재시도가 두 번 실행되지 않게 백엔드가 모든 쓰기 요청에 붙이는 고유 키입니다.

더 깊이: 컴포넌트별 상세는 블록체인 매니저 컴포넌트 가이드 (참고용 — 본 워크스루는 가이드 없이 읽힙니다).
