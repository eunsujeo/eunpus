구조는 두 층입니다

우리 시스템은 두 층입니다. 위는 지갑 백엔드 — 항상 우리가 만들고, 이번엔 물리적으로 분리된 두 개입니다. Service 백엔드는 고객 런타임(계정·주소·입금·출금·잔액)을, Admin 백엔드는 운영·거버넌스(정책·승인·키 운영·동결·rebalance)를 맡고, 별도 배포·권한·감사 경계로 나뉩니다. 그 아래 블록체인 매니저는 체인과 실제로 대화하는 층입니다 — 주소를 만들고, 서명·전파하고, 입금을 감지하죠. 우리는 이 매니저로 Fireblocks 를 채택했습니다.

두 층을 잇는 포트(통로)가 이 문서의 1차 목표입니다. 백엔드가 매니저를 포트로만 부르기 때문에, 매니저가 무엇이든 백엔드 코드는 같습니다. 지금 그 매니저는 Fireblocks이고, 태우는 체인은 EVM — 이더리움과 Base입니다. 포트가 체인 분기를 감추므로 EVM 체인이 늘어도, 훗날 매니저(벤더)를 교체해도 백엔드는 그대로입니다.

두 백엔드(Service·Admin)가 포트 하나로 매니저를 부른다. 포트 아래 매니저는 Fireblocks(채택)이고, 그 아래 체인은 EVM — 이더리움·Base다. 포트가 seam(이음매)이라 EVM 체인이 늘어도, 벤더를 바꿔도 두 백엔드는 그대로다. 이 문서(1~8p)는 이 한 경로를 기능마다 그린다.

어디서 도는가 — 물리 배치 (오리엔테이션)

Fireblocks 채택 기준 배치. Service 백엔드와 Admin 백엔드가 물리적으로 분리돼(별도 배포·권한·감사 경계) 각자 Fireblocks 포트를 부른다 — Service 는 고객 런타임(입금·출금·잔액), Admin 은 정책·승인·키 운영·동결·rebalance. 다만 서명이 온전히 벤더 안에서 끝나지 않는다 — MPC 키 share 하나는 우리 보안 존(SGX/TEE)에 설치한 API Co-signer가 들고, 매 서명마다 Fireblocks 와 공동서명한다. Co-signer 는 서명 직전 Callback Handler(우리 정책 훅)에 승인·거부를 물으므로, 나가는 돈의 마지막 자동 관문이 우리 인프라 안에 선다(운영·정책은 Admin 평면). 나머지 vault·MPC 클라우드 share·노드·전파는 벤더가, 우리 쪽엔 Co-signer·webhook 수신기·매핑 DB가 남는다 — 직접 노드·인덱서를 운영하진 않지만 Co-signer 설치와 webhook 수신이 우리 몫으로 생긴다(4·6p).

왜 매니저를 포트로 감싸나 — 그리고 왜 EVM(이더리움·Base)인가

Fireblocks 를 코드 곳곳에서 직접 부르지 않고 포트(통로)로 한 겹 감싸는 이유는 셋이다. ① 벤더 독립 — 벤더 타입·SDK 가 업무 로직에 새지 않아, 훗날 매니저를 바꿔도 두 백엔드는 그대로다. ② 다중 EVM 체인 — 이더리움과 Base 는 같은 EVM(account 기반·공개 mempool·reorg·동일 주소 체계)이라 포트 하나로 여러 체인을 태운다. 다른 L2 가 붙어도 백엔드 코드는 안 바뀐다. ③ 테스트 가능 — 포트를 가짜 구현으로 바꿔 벤더 없이 백엔드를 검증한다.

Base 는 이더리움 L2(OP-Stack)라 주소·상태·수수료·boost/RBF·확정(DCCP) 모델이 이더리움과 사실상 같다. 그래서 이 문서는 둘을 'EVM'으로 묶어 한 번에 다루고, 체인이 갈리는 지점(가스 시세·L2 특유의 확정 지연 등)만 따로 짚는다.

등장인물 — Fireblocks 채택 시 우리가 만드는 것

Fireblocks 를 채택하면 서명·키·노드·인덱싱·전파·정책 엔진이 대부분 벤더 안으로 들어갑니다. 우리가 직접 만드는 것은 넷입니다 — 이 넷이 곧 1차 작업 범위입니다.

우리 몫은 넷(파랑) — 나머지 서명·키·노드·전파·정책 엔진은 벤더(초록). 멱등 키는 같은 요청의 재시도가 두 번 실행되지 않게 백엔드가 모든 쓰기에 붙이는 고유 키로, 포트를 감싸는 래퍼(withIdempotency)로 들어간다(1p 코드).

Fireblocks 해부 — 기능 × 사용처 매트릭스

포트의 동사들은 어디서 왔을까요. Fireblocks 의 API 표면을 분석한 결과입니다. 가장 묶음이 큰 벤더가 제공하는 것의 전체가 곧 "수탁 지갑에 필요한 기능의 전집"에 가깝고, 그것을 벤더 메서드명이 아니라 우리 업무 언어(도메인 동사)로 바꿔 적은 것이 포트입니다. 각 기능이 어느 백엔드(Service·Admin)에서, 서비스의 어느 장면에서 쓰이는지까지 묶으면 이 표가 곧 이 문서의 목차가 됩니다.

● = 그 장면이 이 기능을 호출한다. 백엔드 열 = Service(S)·Admin(A) 중 어디서 부르나 — 나가는 돈의 정책·승인·개입(TAP·boost·cancel·동결)은 Admin, 고객 런타임(계정·주소·입금·출금 제출·조회)은 Service다. Fireblocks 표면은 공식 문서에서 확인한 범위다(일부 조회 엔드포인트는 적용 전 확인). Base 는 이더리움과 같은 EVM이라 표면·페이지·동사가 동일하다 — 체인만 바뀐다. 마지막 행만 동사가 없는데, 화면이 부르는 기능이 아니라 흐름 뒤에 서는 기능이라 그렇다(정책 게이트, 6p).

도메인 한 장 — 매트릭스를 코드로 적으면

매트릭스의 동사 열을 타입과 함께 적으면 아래 한 장이 됩니다. 이후 모든 페이지의 다이어그램과 사용 코드가 이 도메인 위에서 움직입니다.

// ── 값 객체 — 체인·custody 와 무관한 우리 업무 언어 ──
data class AccountRef(val value: String)                 // 고객 식별자 (우리가 발급)
data class Account(val id: String, val ref: AccountRef)  // 1p 에서 생성되는 계정 핸들
data class Asset(val symbol: String, val chainId: ChainId)   // 예: ETH×ethereum · ETH×base · USDC×ethereum
                                                              //   ERC-20 토큰도 Asset 하나 — chainId 가 같으니 주소는 ETH 와 같다
data class Address(val value: String, val memoTag: String?)  // EVM 은 memoTag 불필요(null) — 순수 주소
data class Balance(val available: Amount, val pending: Amount, val locked: Amount)  // 7p — 세 칸

data class TxRef(val value: String, val chainId: ChainId)    // 제출된 출금의 추적 핸들
// EVM·Fireblocks 공통 상태 — 6p "상태 한 장"
enum TxStatus { SUBMITTED, CONFIRMING, COMPLETED, FAILED }
//   CONFIRMING = 체인에 올라가 confirmation 누적 중(아직 미확정)
//   COMPLETED  = DCCP(확정 정책) 임계 confirmation 도달 = finality
//   numOfConfirmations 로 "confirm(체인 등장) ↔ finality(임계 도달)"를 가른다 (4·7p)

// ── 포트 둘 — 매니저(Fireblocks)가 구현하는 면 ──
interface AccountPort {                                  // 1·2·3·7p
    suspend fun createAccount(ref: AccountRef): Account
    suspend fun issueDepositAddress(account: Account, asset: Asset): Address  // "입금 식별자" 발급 — 2p
    suspend fun addressOf(account: Account, asset: Asset): Address
    suspend fun getBalance(account: Account, asset: Asset): Balance
    // estimateFee(5p) · validateAddress(6p) 생략
}
interface TransactionPort {                              // 4·6·7p
    suspend fun submitTransaction(request: TransactionRequest): TxRef
    suspend fun transactionsOf(account: Account, range: BlockRange): List<Transfer>
    fun onChainEvent(handler: (ChainEvent) -> Unit)      // Fireblocks webhook 수신
    // getStatus 생략
}

// ── 선택 capability — EVM 이 제공하는 운영 동작 (Admin) ──
interface FeeBoostCapability { suspend fun boost(txRef: TxRef): TxRef }    // 수수료 인상 재전송 — Admin 운영 (6p)
interface CancelCapability   { suspend fun cancel(txRef: TxRef): TxRef }   // 철회 — Admin 운영 (6p)

Fireblocks 구현이 이 인터페이스를 구현한다. "어느 구현인지 백엔드가 모른다"는 이 문서의 모든 주장이 이 한 장 위에 서 있다 — 포트로 감싼 덕에 벤더 없이 가짜 구현으로 백엔드를 테스트할 수도 있다. 두 백엔드(Service·Admin)는 같은 포트를 부르되 부르는 메서드 묶음과 권한이 다르다 — 그 물리 분리는 배포·인증 경계이지 포트 시그니처가 아니다.

마지막으로 어휘 하나. 멱등 키는 같은 요청의 재시도가 두 번 실행되지 않게 백엔드가 모든 쓰기 요청에 붙이는 고유 키입니다(포트 래퍼 withIdempotency). 키 자체는 Fireblocks 의 vault·MPC 가 보관·서명하므로, 우리는 키를 다루지 않고 참조(계정·주소)만 다룹니다.

이 문서가 다루지 않는 것

온·오프램프·스왑은 이 매니저의 입금·출금을 조합한 상위 연산(+발행사·거래소·법정통화·회계)이라 여기서 다루지 않습니다. 매니저는 primitive(transfer·contract call·mint/burn)만 주고, 그 조합과 회계(델타 원장·분개)는 우리 몫이라 정산 워크스루에서 따로 다룹니다.

그 밖에 업무 승인 절차(누가 출금을 승인하나) · 수수료의 운영·정산(출금용 가스 잔고 충전·고객 과금·실비 차액) · 회계 기표·시세도 별도 설계의 몫입니다. 다만 수수료의 메커니즘(추정 estimateFee · 조립 시 설정 · 인상 재전송 boost)은 매니저가 맡으며 5p(견적)·6p(조립 시 설정·boost) 에서 다룹니다.

더 깊이: 컴포넌트별 상세는 블록체인 매니저 컴포넌트 가이드 (참고용 — 본 워크스루는 가이드 없이 읽힙니다).
