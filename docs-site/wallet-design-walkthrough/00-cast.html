구조는 두 층입니다

우리 시스템은 두 층으로 나뉩니다. 지갑 백엔드는 API·계정 관리·업무 규칙을 담당하고 항상 우리가 만듭니다. 그 아래 블록체인 매니저는 체인과 실제로 대화하는 층입니다. 주소를 만들고, 트랜잭션에 서명·전파하고, 입금을 감지하죠. 교체 대상은 바로 이 매니저 층입니다. 자체 구축으로 시작했다가 Fireblocks 로 바꿔도 백엔드 코드는 그대로입니다. 백엔드가 매니저를 포트(인터페이스)로만 부르기 때문입니다.

자체 구축 기준 배치. 지갑 백엔드가 블록체인 매니저를 포트로 부르고, 매니저는 출금 시 정책 게이트(서명 직전 재검증, 6p)를 거쳐 HSM으로 서명한 뒤 이더리움 노드·Canton participant 노드로 전파·제출한다. 인덱서 worker(상시)는 두 노드에서 입금을 수집·구독해 블록체인 매니저 DB(계정 매핑·단계 기록·멱등)에 쌓는다. HSM·정책 게이트는 보안 존에 격리돼 서명 요청만 드나들고, 모든 연결이 밖으로 나가는 방향(outbound)이라 inbound 포트가 없다 — 망분리에 유리한 성질이다. 1~7페이지의 worker·HSM·노드·DB 가 전부 여기서 돈다. Fireblocks 로 바꾸면 노드·HSM·worker 가 벤더 안으로 들어가고 webhook 수신이 새로 생기는데, 그 분면별 대조와 전환은 8p.

왜 하필 이더리움과 Canton 인가

두 체인은 일부러 가장 다른 둘로 골랐다. 이더리움은 개방형·account 기반·공개 mempool·reorg, Canton 은 기관용·privacy·eUTXO·2-step 수락·즉시 확정·party 기반이다. 추상(포트)이 이 양 극단에서 버티면 그 사이의 체인들은 자연히 들어온다. 비슷한 체인 둘로 보여줘 봐야 추상화 증명이 시시해질 뿐이다. 그래서 매 페이지에서 체인 축이 갈릴 때마다 둘의 차이(주소 vs PartyId+memo, 감지 vs 수락, reorg vs 즉시 확정)가 드러난다.

한 가지 짚어둘 것은 Canton 도 퍼블릭 네트워크라는 점이다(permissionless Global Synchronizer). 다만 privacy-enabled·기관 지향이라 종류가 다른 퍼블릭이다. 그래서 Canton 도입은 단순 "체인 추가"가 아니라 participant 노드 운영·party 신원·sub-transaction privacy 같은 운영 패러다임 차이를 동반한다. 그 깊은 내용은 Canton 네트워크 가이드에서 다룬다.

등장인물 — 다이어그램에 나올 부품들

Fireblocks 해부 — 기능 × 사용처 매트릭스

그런데 포트의 동사들은 어디서 왔을까요. Fireblocks 의 API 표면을 분석한 결과입니다. 가장 묶음이 큰 벤더가 제공하는 것의 전체가 곧 "수탁 지갑에 필요한 기능의 전집"에 가깝고, 그것을 벤더 메서드명이 아니라 우리 업무 언어(도메인 동사)로 바꿔 적은 것이 포트입니다. 각 기능이 우리 서비스의 어느 장면에서 쓰이는지까지 묶으면 이 표가 곧 이 문서의 목차가 됩니다.

도메인 한 장 — 매트릭스를 코드로 적으면

매트릭스의 동사 열을 타입과 함께 적으면 아래 한 장이 됩니다. 이후 모든 페이지의 다이어그램과 사용 코드가 이 도메인 위에서 움직입니다.

// ── 값 객체 — 체인·custody 와 무관한 우리 업무 언어 ──
data class AccountRef(val value: String)                 // 고객 식별자 (우리가 발급)
data class Account(val id: String, val ref: AccountRef)  // 1p 에서 생성되는 계정 핸들
data class Asset(val symbol: String, val chainId: ChainId)   // 예: ETH×ethereum · JPYSC0×canton
                                                              //   ERC-20 토큰도 Asset 하나 — chainId 가 같으니 주소는 ETH 와 같다
data class Address(val value: String, val memoTag: String?)  // Canton 이면 value = PartyId
data class Balance(val available: Amount, val pending: Amount, val locked: Amount)  // 7p — 세 칸
data class TxRef(val value: String, val chainId: ChainId)    // 제출된 출금의 추적 핸들
enum TxStatus { SUBMITTED, AWAITING_ACCEPT, CONFIRMED, FAILED }  // 출금 공통 상태 — 6p "상태 한 장"
// (ChainId · Amount · Transfer · TransactionRequest · ChainEvent 등 부속 타입은 생략)

// ── 포트 둘 — 매니저(자체/FB)가 구현하는 면 ──
interface AccountPort {                                  // 1·2·3·7p
    suspend fun createAccount(ref: AccountRef): Account
    suspend fun issueDepositAddress(account: Account, asset: Asset): Address  // "입금 식별자" 발급 — 2p
    suspend fun addressOf(account: Account, asset: Asset): Address
    suspend fun getBalance(account: Account, asset: Asset): Balance
    // estimateFee(5p) · validateAddress(6p) 생략
}
interface TransactionPort {                              // 4·6·7p
    suspend fun submitTransaction(request: TransactionRequest): TxRef
    suspend fun transactionsOf(account: Account, range: BlockRange): List<Transfer>
    fun onChainEvent(handler: (ChainEvent) -> Unit)
    // getStatus 생략
}

// ── 선택 capability — "있는 분면"만 타입을 가진다 ──
interface FeeBoostCapability { suspend fun boost(txRef: TxRef): TxRef }    // 이더리움 분면만 (6p)
interface CancelCapability   { suspend fun cancel(txRef: TxRef): TxRef }   // 철회 (6p)

자체 매니저도 Fireblocks 구현도 이 인터페이스를 구현한다. "어느 구현인지 백엔드가 모른다"는 이 문서의 모든 주장이 이 한 장 위에 서 있다. 멱등 키는 시그니처가 아니라 호출을 감싸는 래퍼(withIdempotency)로 들어간다(1p 코드).

마지막으로 어휘 두 개만 짚겠습니다. 키 트리는 고객마다 키를 만들지 않고 셋업 때 HSM 안에서 한 번 만든 뿌리 키에서 가지(번호)를 늘려 가는 방식입니다(2페이지에서 동작으로 확인). 멱등 키는 같은 요청의 재시도가 두 번 실행되지 않게 백엔드가 모든 쓰기 요청에 붙이는 고유 키입니다.

이 문서가 다루지 않는 것

온·오프램프·스왑은 이 매니저의 입금·출금을 조합한 상위 연산(+발행사·거래소·법정통화·회계)이라 여기서 다루지 않습니다. 자체든 Fireblocks 든 매니저는 primitive(transfer·contract call·mint/burn)만 주고, 그 조합과 회계(델타 원장·분개)는 우리 몫이라 정산 워크스루에서 따로 다룹니다.

그 밖에 업무 승인 절차(누가 출금을 승인하나) · 수수료의 운영·정산(출금용 가스 잔고 충전·고객 과금·실비 차액·Canton traffic 충전) · 회계 기표·시세도 별도 설계의 몫입니다. 다만 수수료의 메커니즘(추정 estimateFee · 조립 시 설정 · 인상 재전송 boost)은 매니저가 맡으며 5p(견적)·6p(조립 시 설정·boost) 에서 다룹니다.

더 깊이: 컴포넌트별 상세는 블록체인 매니저 컴포넌트 가이드 (참고용 — 본 워크스루는 가이드 없이 읽힙니다).
