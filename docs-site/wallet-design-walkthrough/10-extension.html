확장 증명 — N번째 체인은 어댑터 하나다

"왜 하필 이더리움과 Canton 으로 시작하나"의 답이기도 합니다

익숙한 것 ↔ 깨지는 지점 "새 체인 추가" 견적을 들으면 본체 수정 범위부터 걱정됩니다. 이 설계의 주장: 본체는 0 줄 — 어댑터 한 개와 등록 한 줄. 그 주장이 성립하는 근거는 우리가 이미 흡수한 두 체인이 설계 공간의 양 극단이라는 데 있습니다.

3막에서 본 차이를 한 표로 모으면, 이더리움과 Canton 이 거의 모든 축에서 반대편에 있다는 게 보입니다:

축이더리움Canton
주소키에서 계산 (공짜·로컬)없음 — PartyId 를 유료 온장 등록, 입금 구분은 memo
순서 자원nonce (계정별 직렬화·gap 금지)없음 — 네트워크가 순서 부여
제출의 의미제출 = 전파 끝 (이후 확정 대기)제출 = OFFER — 상대가 수락해야 완료, 그동안 자금 잠김
막힘 대응boost (같은 순번 + 수수료↑)수수료 문제 아님 — cancel(WITHDRAW)
확정확률적 (N 블록·reorg 가능)결정적 (reorg 없음)
입금수동 감지수락 행위 (ACCEPT 서명)

이 양 극단을 같은 포트 동사 뒤에서 소화했다는 것이 확장의 증명입니다 — 비트코인(UTXO)도 솔라나(blockhash 만료)도 이 표의 두 열 사이 어딘가에 있지, 바깥에 있지 않습니다. 그래서 N번째 체인의 작업은 본체가 아니라 어댑터입니다:

// 새 체인 추가의 전부 — 본체(파이프라인·인덱서 가공·포트·코어)는 0 줄
const ADAPTERS = {
  ethereum: new EvmAdapter(node, nonceMgr),
  canton:   new CantonAdapter(participant),
  bitcoin:  new UtxoAdapter(node),        // ← 어댑터 하나 + 이 줄
}

물론 "0 줄"의 전제 조건이 있습니다 — 어댑터는 결과만이 아니라 실패도 번역해야 하고(체인 고유 오류를 "재전파 안전 / 재조립 필요 / 영구 실패"의 공통 분류로), 체인이 못 하는 일은 capability 부재로 선언해야 합니다(불변식 ⑥). 이 둘이 새면 본체에 체인 분기가 스며들고, 0 줄은 거짓말이 됩니다.

마무리 — 표에서 시작해 테스트로 닫혔습니다

1페이지의 기능 × 사용처 매트릭스가 포트의 동사가 됐고(3p), 불변식이 그 동사들의 의미를 고정했고(4p), 자체 구축이 각 행을 채웠고(5~8p), 계약 테스트가 두 구현 위에서 그 전부를 검증합니다(9p). 그래서 세 가지가 증명됩니다 — 자체로 테스트할 수 있고, Fireblocks 로 전환해도 다른 시스템이 안 흔들리고, 체인이 늘어도 마찬가지다. 전제로 합의했던 그 세 문장입니다.
