출금 — 제출에서 확정까지, 막혔을 때

고객 자금이 나가는 길, 이 시리즈에서 사고가 가장 비싼 페이지

무엇·언제: 업무 승인이 끝난 출금 지시를 Service 백엔드가 매니저에 넘깁니다(제출). 조립·순번·전파는 벤더 안에서 블랙박스로 돌지만, MPC 서명만은 보안 존의 co-signer key share 가 있어야 완성됩니다 — 나가는 돈의 마지막 서명 관문이 인프라 안에 섭니다. 제출·상태 추적과 co-signer 운영을 맡습니다.

submitTransaction(출금 지시) → TxRef { value, chainId }

제출 전의 견적(estimateFee)은 5장에서 봤습니다. 견적은 보장이 아니므로 실제 수수료는 벤더가 제출·조립 단계에서 재확정합니다.

출금 제출 — 파이프라인이 벤더 안으로 들어간다

    FB-->>BE: 트랜잭션 id (= TxRef)
    Note over COS,CH: 조립·순번·전파는 벤더가 — 다만 MPC 서명엔 co-signer share 가 필요하다
    FB->>COS: 서명 요청 (원문 목적지·금액 동반)
    COS->>CB: 승인 질의 — 한도·화이트리스트 재검증
    CB-->>COS: approve / deny
    COS-->>FB: MPC 서명 share (approve) · deny 면 서명 거부
    FB->>CH: 전파 — 벤더 cloud share + co-signer share 로 서명 완료
    FB-->>BE: 상태 변화 — 폴링으로 조회 (전파·누적·확정까지)
    CH-->>FB: 블록 누적 → 확정

조립·순번·전파는 벤더 안 블랙박스지만, MPC 서명은 보안 존의 co-signer 와 공동으로 이뤄진다 — Fireblocks 가 서명을 요청하면 co-signer 가 Callback Handler(정책 훅)에 목적지·금액을 재검증받고 approve 일 때만 자기 key share 로 서명한다. 백엔드가 침해돼 "승인된 척" 지시가 와도 이 관문이 인프라 안에서 막는다. 순번(nonce)은 벤더가 관리하고, 이쪽 몫은 제출·상태 추적·co-signer 운영이다.

왜 직접 파이프라인을 만들지 않나

조립(순번 점유)·서명·전파와 그 중단 복구 책임이 통째로 벤더 안에 있습니다.

정책 게이트 — 마지막 방어선은 TAP

서명 직전에 또 검증합니다 — 서명자는 백엔드를 신뢰하지 않기 때문입니다. 백엔드가 침해돼 "승인된 척하는" 지시가 와도, 키 앞의 마지막 방어선인 벤더 거버넌스 정책 TAP + co-signer 가 원문(목적지·금액)을 다시 봅니다 — 수신처 화이트리스트·건당 한도·일일 누적.

규칙은 코드가 아니라 데이터입니다 — 화이트리스트·한도는 설정이고, 그 관리·승인은 Admin 백엔드의 거버넌스 몫(co-signer 승인 포함)입니다. 방어선이 벤더 안 TAP에 있으므로, 할 일은 게이트를 만드는 게 아니라 TAP 정책을 운영·승인하는 것(Admin)입니다.

막혔을 때 — boost 와 cancel (Admin 운영)

확정한 수수료가 시세보다 낮으면 트랜잭션이 mempool 에 걸려 막힙니다. EVM(이더리움·Base 모두)에선 대응이 둘입니다. boost — 같은 순번에 수수료만 올려 다시 보내는 재전송(RBF). Fireblocks 는 전파(Broadcasting) 중 boost 를 지원합니다. cancel — 출금 자체를 철회. 두 동작 모두 나가는 돈에 개입하는 Admin 백엔드의 운영입니다. Service 는 고객 출금을 제출할 뿐, boost·cancel 은 부르지 않습니다.

상태 한 장 — Fireblocks 필드를 공통 어휘로

Fireblocks 는 내부 상태를 여러 단계로 보냅니다(PENDING_SIGNATURE, QUEUED, BROADCASTING, CONFIRMING, COMPLETED, FAILED…). 백엔드가 보는 것은 어댑터가 번역한 공통 상태 하나입니다. 아래 넷이 밖으로 나갑니다.

공통 상태 (TxStatus)뜻Fireblocks 원어 (어댑터가 번역)
SUBMITTED제출됨 — 벤더가 서명·전파 준비 중, 아직 체인 미등장PENDING_SIGNATURE · QUEUED · BROADCASTING
CONFIRMING전파 후 체인에 등장, confirmation 누적 중 (아직 미확정)CONFIRMING (numOfConfirmations 증가 중)
COMPLETED확정 — DCCP?(확정 정책) 임계 confirmation 도달 = finality, 이후 불변COMPLETED
FAILED영구 실패 — 사유 동반 (수수료 부족·거절·revert 등)FAILED · REJECTED · BLOCKED

confirm(체인 등장)과 finality(확정)를 numOfConfirmations 로 가른다. 체인에 올라간 순간이 CONFIRMING 이고, DCCP(확정 정책)가 정한 임계 confirmation 에 도달하면 COMPLETED = finality 다(4·7장과 같은 기준). 이 문서는 이 넷만 밖으로 내보낸다 — 벤더 내부의 세부 단계는 SUBMITTED 로 접어 감춘다. 입금의 상태는 별도 셋으로, 감지(PENDING)/확정(CONFIRMED)/무효화(ORPHANED), 4장.

상태 이름과 확정 정책(DCCP)은 벤더 안에 있지만, 그것을 공통 어휘 넷으로 번역하는 어댑터와 막혔을 때의 boost·cancel(Admin) 판단은 이쪽 몫입니다 — 언제 boost 할지, 언제 철회할지 같은 업무 정책은 매니저가 흡수하지 못합니다.
