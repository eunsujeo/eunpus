출금 — 제출에서 확정까지, 막혔을 때

고객 자금이 나가는 길 — 이 문서에서 사고가 가장 비싼 페이지

무엇·언제: 업무 승인이 끝난 출금 지시를 백엔드가 매니저에 넘깁니다. 모든 분면 공통의 위험은 중복 실행 — 같은 출금이 두 번 나가면 체인엔 되돌리기가 없습니다. 그래서 호출에는 항상 멱등 키가 붙고, 자체 분면에선 한 가지 규칙이 더 붙습니다: 전파(체인에 쓰기) 전에 먼저 기록한다 — 전파 직후 프로세스가 죽고 기록이 없으면, 재시도가 새 트랜잭션을 만들어 둘 다 나가기 때문입니다.

submitTransaction(출금 지시 + 멱등 키) → TxRef    // 이후 상태는 getStatus · 이벤트로 추적

제출 전의 견적(estimateFee)은 5페이지에서 봤습니다 — 견적은 보장이 아니므로, 실제 수수료는 이 페이지의 조립 단계에서 재계산해 확정합니다.

▸ 자체 × 이더리움 — 조립→서명→전파, 단계마다 기록

    participant GATE as 정책 게이트
    participant HSM as HSM
    end
    participant CH as 이더리움
    participant IDX as 인덱서

    BE->>PIPE: submitTransaction(승인된 출금 + 멱등 키)
    PIPE->>PIPE: 조립 — nonce 점유 · 기록 ①
    PIPE->>GATE: 서명 요청
    GATE->>GATE: 재검증 — 화이트리스트 · 한도
    GATE->>HSM: 통과한 것만 서명 (키는 안 나옴)
    HSM-->>PIPE: 서명본 · 기록 ②
    PIPE->>CH: 전파 · 기록 ③
    CH-->>PIPE: txRef
    PIPE-->>BE: txRef
    IDX-->>BE: 블록 누적 → 확정(CONFIRMED) push

기록 ①②③ 이 생명선이다 — 어느 사이에서 죽어도 "그 단계부터, 같은 서명본으로" 재개한다(새로 조립하면 새 순번 = 이중 출금). 순번(nonce)은 계정별 일련번호라 동시 출금은 줄을 세우고, 수수료가 낮아 막히면 같은 순번에 수수료만 올려 다시 보낸다(boost) — 순번을 건너뛰면 뒤 출금이 전부 멈추기 때문.

▸ 자체 × Canton — 제출이 끝이 아니다, 상대가 받아야 끝

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    box rgb(239,246,255) 블록체인 매니저
    participant PIPE as 트랜잭션 파이프라인
    participant HSM as 정책 게이트 + HSM
    end
    participant PN as Canton 노드
    participant CP as 수신 상대방

    BE->>PIPE: submitTransaction(승인된 출금 + 멱등 키)
    PIPE->>HSM: 전송 제안 조립 · 검증 · 서명 (순번 없음)
    PIPE->>PN: 제안(OFFER) 제출
    Note over PIPE,CP: 송신 자금이 "잠김(locked)" 으로 묶인다 — 빠진 것도 남은 것도 아닌 제3의 상태 (7p)
    PN->>CP: 수락 요청 전달
    alt 상대가 수락
        CP-->>PN: ACCEPT
        PN-->>BE: 확정 — 즉시, 되돌림 없음
    else 기한 내 미수락
        BE->>PN: cancel — 철회(WITHDRAW)로 잠금 해제
    end

이더리움의 "전파=거의 끝"이 Canton 에선 "제출=시작"이다 — 상대 수락까지 자금이 잠기고, 막힘의 원인이 수수료가 아니라 상대의 침묵이라 boost 가 무의미하다(이 분면엔 boost 가 타입부터 없다). 대응 동사는 cancel(철회) 하나.

▸ Fireblocks × 이더리움 — 한 줄 뒤로 들어간 파이프라인

    participant FBI as Fireblocks 구현

    BE->>FBI: submitTransaction(승인된 출금 + 멱등 키)
    FBI->>FB: createTransaction(…, externalTxId = 멱등 키)
    Note over FBI,FB: 조립·순번·MPC 서명·전파를 벤더가 한 번에 — 정책 게이트의 자리는 벤더의 거버넌스 정책(TAP)이 잇는다
    FB-->>FBI: 트랜잭션 id (= TxRef)
    FBI-->>BE: TxRef
    FB-->>BE: 상태 변화 webhook (확정 포함) — 막히면 boost API 호출만

자체 분면의 파이프라인 전체가 벤더 안으로 들어간다. 우리 멱등 키를 externalTxId 로 넘겨 중복 차단이 벤더 쪽에서도 이어지는 것, 그리고 자체 순번 관리를 병행하면 벤더 내부 순번과 충돌하므로 전환 시 우리 파이프라인을 꺼야 한다는 것 — 이 두 줄이 전환 체크리스트(8p)에 들어간다.

▸ Fireblocks × Canton — 한 줄이어도 수락 대기는 그대로

    autonumber

    box rgb(239,246,255) 블록체인 매니저
    participant FBI as Fireblocks 구현
    participant FB as Fireblocks (SaaS)

    BE->>FBI: submitTransaction(승인된 출금 + 멱등 키)
    FBI->>FB: createTransaction — Canton 전용 거래 유형으로 제출
    FB-->>BE: webhook — 상태에 OFFER → 수락 대기 → ACCEPT 가 그대로 노출
    Note over FB,BE: 자금 잠김·상대 수락 대기는 체인의 성질이라 벤더도 못 없앤다 —
기한 내 미수락 시 철회(cancel) 호출은 우리 몫 (상세는 적용 전 확인)

네 번째 확인 — custody 는 "누가 실행하나"를 바꾸고, 체인은 "무엇이 일어나나"를 바꾼다. 백엔드의 "수락 대기 화면·기한 정책·철회 버튼"은 자체든 Fireblocks 든 똑같이 필요하다.

읽을 것: "막혔을 때" 행이 체인 축으로 갈리고(수수료의 문제 vs 상대의 문제), "누가 하나"는 전부 custody 축으로 갈립니다. 그리고 수락 대기·기한·철회라는 업무 정책은 네 분면 어디서도 사라지지 않습니다 — 매니저가 흡수 못 하는, 백엔드(우리)의 몫.

백엔드에서 이렇게 부른다 — 제출은 한 줄, 막힘 대응은 capability

// 출금 유스케이스 — 업무 승인은 비즈 레이어에서 끝난 뒤
suspend fun withdraw(order: ApprovedWithdrawal): TxRef =
    withIdempotency("withdraw:${order.id}") {
        transactions.submitTransaction(order.toRequest())   // 4분면의 그림은 전부 이 한 줄 아래
    }

// 막힌 출금 화면 — 분면이 지원하는 버튼만 자연히 노출된다
fun stuckActions(): List = buildList {
    (transactions as? FeeBoostCapability)?.let { add(BoostAction(it)) }   // 이더리움 분면만
    (transactions as? CancelCapability)?.let { add(CancelAction(it)) }    // 철회 — Canton 필수
}

운영 화면조차 분면을 하드코딩하지 않는다 — capability 가 있으면 버튼이 생기고, 없으면 처음부터 없다.

상태 한 장 — 흩어진 상태를 공통 어휘로

체인·벤더마다 상태 이름이 다르지만(이더리움 pending, Canton OFFER, FB SUBMITTED…), 백엔드가 보는 것은 어댑터가 번역한 공통 상태 하나입니다 — "실패도 번역한다"의 상태 버전:

공통 상태 (TxStatus)뜻원어 (어댑터가 번역)
SUBMITTED체인에 제출됨 — 확정 대기ETH pending · FB SUBMITTED/CONFIRMING
AWAITING_ACCEPT상대 수락 대기 (자금 잠김) — Canton 전용 표면화Canton OFFER · FB Canton 거래 유형
CONFIRMED확정 — 이후 불변 (Canton 은 즉시)N블록 충족 · ACCEPT · FB COMPLETED
FAILED영구 실패 — 사유 동반 (수수료 부족·거절·철회 등)revert · REJECT/WITHDRAW · FB FAILED

출금의 내부 단계(BUILT→SIGNED→BROADCAST)는 파이프라인의 기록용이고 밖으로는 위 4개만 나간다. 입금의 상태는 별도 셋 — 감지(PENDING)/확정(CONFIRMED)/무효화(ORPHANED), 4p.
