출금 — 제출에서 확정까지, 막혔을 때

출금 요청의 두 갈래 — 목적지가 내부면 장부 이체, 외부면 온체인 제출·확정·막힘. 이 시리즈에서 사고가 가장 비싼 페이지

Service 접수·장부 이체·온체인 제출과 상태 추적·Admin TAP 승인 정책과 막힌 건의 boost·cancel

무엇·언제: 업무 승인이 끝난 출금 지시를 Service 백엔드가 매니저에 넘깁니다(제출). 조립·순번·전파는 벤더 안에서 블랙박스로 돌지만, MPC 서명만은 보안 존의 co-signer key share 가 있어야 완성됩니다 — 나가는 돈의 마지막 서명 관문이 인프라 안에 섭니다. 제출·상태 추적과 co-signer 운영을 맡습니다.

submitTransaction(TransactionRequest { idempotencyKey, account, to, asset, amount })
  → TxRef { id — 벤더 트랜잭션 id, chainId }

제출 전의 견적(estimateFee)은 7장이 다룹니다. 견적은 보장이 아니므로 실제 수수료는 벤더가 제출·조립 단계에서 재확정합니다.

서명은 두 겹 — 안쪽 승인(vault)과 바깥 거래(relay)

다이어그램의 서명 관문(5~8)과 relay 구간(9~10)은 별개의 서명 두 개를 만듭니다:

서명누가 · 무엇에무엇을 막나
안쪽 — vault 의 승인 서명 (5~8)출금 vault(옴니버스·출금 pool)의 MPC 서명 — 벤더 share + co-signer share. co-signer 는 Callback Handler 재검증을 통과한 건에만 자기 share 를 보탠다.침해된 백엔드의 위조 지시 — 목적지·금액이 정책에 어긋나면 서명 자체가 만들어지지 않는다.
바깥 — relay 의 거래 서명 (9~10)relay 가 자기 계정으로 바깥 거래를 서명·제출하고 gas 를 낸다.relay 가 정할 수 있는 건 "낼지 말지"뿐 — 내용 위조는 불가. 위임된 지갑 코드가 안쪽 서명을 온체인에서 검증하기 때문.

행위자를 우리 모델로 매핑하면 — 고객은 온체인에 등장하지 않습니다. 고객의 "출금해 주세요"는 업무 승인 단계에서 끝나고, 온체인의 발신 vault(옴니버스·출금 pool)·키(MPC)·제출자(relay)는 전부 수탁자 쪽입니다. 위임·실행 메커니즘의 상세는 가스 대납 문서 9장.

고객 사이의 이동 — 체인에 나가지 않는다

출금 요청의 목적지가 우리 서비스 고객의 입금 주소일 수 있습니다. 이때는 온체인 출금이 아닙니다 — 자산은 어차피 같은 옴니버스 안에 있으므로, DB 원장에서 보낸 고객을 차감하고 받는 고객을 증가시키면 끝입니다. 벤더 호출도, gas 도, 확정 대기도 없습니다.

외부 출금과 다른 것내용
온체인 사건 없음거래가 체인에 나가지 않는다 — gas 0, 즉시 확정, 폴링·reorg·막힘과 무관.
서명 관문 미관여서명할 거래 자체가 없어 TAP·co-signer 가 서지 않는다 — 방어선은 업무 승인과 원장 규칙뿐이므로, 한도·AML 검증을 외부 출금과 같은 수준으로 업무 층에 걸어야 한다.
대사 영향 없음A 차감 = B 증가라 고객 잔액 합계가 불변이고, 옴니버스 온체인 잔액도 그대로 — 8장의 대사 공식(합계 = 옴니버스 잔액)이 유지된다. 기록은 원장 이벤트로 남긴다.

정책 게이트 — 마지막 방어선은 TAP

규칙은 코드가 아니라 데이터입니다 — 화이트리스트·한도는 설정이고, 그 관리·승인은 Admin 백엔드의 거버넌스 몫(co-signer 승인 포함)입니다. 방어선이 벤더 안 TAP에 있으므로, 할 일은 게이트를 만드는 게 아니라 TAP 정책을 운영·승인하는 것(Admin)입니다.

막혔을 때 — boost 와 cancel (Admin 운영)

확정한 수수료가 시세보다 낮으면 트랜잭션이 mempool 에 걸려 막힙니다. EVM(이더리움·Base 모두)에선 대응이 둘입니다. boost — 같은 순번에 수수료만 올려 다시 보내는 재전송(RBF). Fireblocks 는 전파(Broadcasting) 중 boost 를 지원합니다. cancel — 출금 자체를 철회. 두 동작 모두 나가는 돈에 개입하는 Admin 백엔드의 운영입니다. Service 는 고객 출금을 제출할 뿐, boost·cancel 은 부르지 않습니다. 막힌 건의 감지(오래 CONFIRMING 인 건 골라내기)는 4장의 막힘 점검이 올립니다.

relay 구성(Universal Gasless)에서도 이 운영은 그대로 필요합니다 — 공식 문서 명시로 Gasless Relay 는 auto-boost 를 지원하지 않아, 막힘 감지와 boost 지시는 우리 몫입니다. 실행 경로만 다릅니다: 막힌 바깥 거래의 발신자가 relay 라서 같은 순번의 대체 거래는 relay 만 만들 수 있고, 우리가 벤더 API 로 지시하면 relay 가 fee 를 올린 대체 거래를 다시 냅니다 — 그 gas 도 relay 부담이고 인보이스로 정산됩니다. gasless 거래에 대한 boost·cancel API 의 정확한 동작은 CSM/PoC 확인 대상입니다.

상태 한 장 — Fireblocks 필드를 공통 어휘로

Fireblocks 는 내부 상태를 여러 단계로 보냅니다(PENDING_SIGNATURE, QUEUED, BROADCASTING, CONFIRMING, COMPLETED, FAILED…). 백엔드가 보는 것은 어댑터가 번역한 공통 상태 하나입니다. 아래 넷이 밖으로 나갑니다.

공통 상태 (TxStatus)뜻Fireblocks 원어 (어댑터가 번역)
SUBMITTED제출됨 — 벤더가 서명·전파 준비 중, 아직 체인 미등장PENDING_SIGNATURE · QUEUED · BROADCASTING
CONFIRMING전파 후 체인에 등장, confirmation 누적 중 (아직 미확정)CONFIRMING (numOfConfirmations 증가 중)
COMPLETED확정 — DCCP?(확정 정책) 임계 confirmation 도달 = finality, 이후 불변COMPLETED
FAILED영구 실패 — 사유 동반 (수수료 부족·거절·revert 등)FAILED · REJECTED · BLOCKED

confirm(체인 등장)↔finality(확정) 판정 기준은 4장과 같다(numOfConfirmations vs DCCP 임계). 이 문서는 이 넷만 밖으로 내보낸다 — 벤더 내부의 세부 단계는 SUBMITTED 로 접어 감춘다. 입금 쪽 상태 흐름은 5장.

상태 이름과 확정 정책(DCCP)은 벤더 안에 있지만, 그것을 공통 어휘 넷으로 번역하는 어댑터와 막혔을 때의 boost·cancel(Admin) 판단은 이쪽 몫입니다 — 언제 boost 할지, 언제 철회할지 같은 업무 정책은 매니저가 흡수하지 못합니다.
