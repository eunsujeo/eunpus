전환 증명 — 코드·데이터·자금은 다른 경계다

"자체에서 Fireblocks 로 바꾸면 뭐가 바뀌어요?" — 세 번 따로 답해야 정직한 질문입니다

익숙한 것 ↔ 깨지는 지점 DB 를 갈아탈 때 우리는 코드(드라이버)와 데이터(마이그레이션)를 구분해 계획합니다. custody 전환에는 세 번째 축이 하나 더 있습니다 — 자금. 그리고 자금은 코드처럼 배포되지도, 데이터처럼 복사되지도 않습니다.

① 코드 — 설정 한 줄, 그리고 그것이 가능한 이유

포트(3p) 뒤의 구현만 바뀌므로 전환의 코드 비용은 DI 설정 한 줄입니다. 코어·비즈 레이어·API 는 포트 타입만 알기 때문에 diff 가 없습니다. 단 한 가지 이어붙일 것 — 우리 멱등 키는 Fireblocks 의 externalTxId 로 전달되어, 전환 후에도 "정확히 한 번"이 벤더 쪽에서도 이어집니다.

# application.yml — 전환의 코드 전부
custody.provider: selfbuild   →   custody.provider: fireblocks

② 증거 — 계약 테스트: 같은 시험지를 두 구현이 푼다

"무리 없다"는 주장은 테스트로만 증명됩니다. 포트별 계약 테스트 스위트를 하나 두고, 자체 구현(테스트넷)과 Fireblocks 구현(샌드박스)이 같은 스위트를 통과하게 합니다 — 시험 문제는 4페이지의 불변식들입니다: addressOf 는 몇 번 불러도 같은 주소인가, 발급 없이 새 주소가 나오는 일은 없는가, 같은 멱등 키 재시도가 출금을 두 번 만들지 않는가, 미지원 capability 는 타입부터 없는가.

abstract class AccountPortContractTest {        // 시험지는 하나
    abstract fun port(): AccountPort            // 응시자만 바뀐다

    @Test fun `addressOf 는 멱등 조회다 — 절대 새 주소를 만들지 않는다`() { … }
    @Test fun `같은 멱등 키의 재시도는 계정을 두 번 만들지 않는다`() { … }
}
class SelfBuildContractTest : AccountPortContractTest()   // 테스트넷으로 통과
class FireblocksContractTest : AccountPortContractTest()  // 샌드박스로 통과

③ 자금·주소 — 코드가 아니라서 배포되지 않는다

여기가 이 페이지의 핵심입니다. 자체 매니저의 주소는 우리 키에서 나왔고 Fireblocks 의 주소는 Fireblocks 키에서 나옵니다 — 키가 다르므로 주소는 이전되지 않습니다. 설정 한 줄을 바꾸는 순간 코드는 전환되지만, 고객에게 이미 안내된 구 주소와 그 위의 잔액은 구 세계에 남습니다. 그래서 전환은 배포가 아니라 창구 교체 + 이사입니다:

전환 운영 타임라인. 노랑 구간이 비용의 전부다 — 구 주소를 한동안 계속 감시하고(등록까지가 발급이었으므로, 해제도 절차다), 잔액을 sweep 으로 이사시킨다. 계정 디렉터리에는 어느 주소가 어느 세대(자체/Fireblocks)인지 남는다 — 벤더를 바꿔도 남는 우리 데이터.

그리고 이것이 "자체로 테스트부터"라는 우리 순서의 논리입니다: 노랑 구간의 비용은 구 주소 수와 잔액에 비례하는데, 테스트 단계의 그것은 거의 0입니다. 전환이 가장 쌀 때 전환 가능성을 증명해 두고, 비싸지는 건 운영 자금이 쌓인 뒤의 일로 미룹니다.

전환 후에도 남는 한 가지 — 인덱서

Fireblocks 는 임의 외부 주소 조회(1p 매트릭스에 없던 그 기능)를 주지 않습니다. 그 기능을 쓰고 있었다면 자체 인덱서는 전환 후에도 그 슬롯에 남습니다 — custody 와 별개의 교체 축이기 때문입니다. 안 쓰고 있었다면 이중 감시 기간이 끝날 때 함께 내립니다.
