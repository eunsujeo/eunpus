계정·주소 — 지갑 생성은 키 생성이 아니다

매트릭스 1~3행을 채웁니다: createAccount · issueDepositAddress · addressOf

익숙한 것 ↔ 깨지는 지점 "고객 지갑 생성 API" 라고 하면 리소스를 하나 만드는 POST 가 떠오릅니다. 실제로는 — 키는 시스템 셋업 때 단 한 번 만들어지고, 고객 100만 명의 지갑 생성은 키 트리의 가지 번호를 집는 장부 작업입니다. 키 100만 개를 상상했다면 비용 모델 전체가 틀어집니다.

구조는 둘뿐입니다 — 키 트리 하나(HSM 안의 master seed, 셋업 때 1회 생성·확장 공개키 xpub 만 반출)와 장부. 장부는 실제로 두 부품입니다: 계정 디렉터리 — "고객 ref → 가지 번호 → 발급된 주소" 매핑을 담는 우리 DB(벤더를 바꿔도 남는 우리 데이터), 그리고 watch-list — 인덱서(7p)에게 "이 주소들로 오는 입금을 감시하라"고 알려주는 우리 주소 목록. 이 둘 위에서 이더리움과 Canton 이 정반대로 갈라집니다:

같은 포트 동사, 정반대 비용 구조. 이더리움 발급은 공개키 수학(xpub 공개 파생)이라 공짜·로컬이고 — 개인키는 출금 서명 때 HSM 안에서 같은 경로로 파생된다 — Canton 은 주소(PartyId)가 계정 생성 시점의 온장 등록으로 태어나고 추가 입금 주소 개념이 없다(입금 구분은 memo 참조). 움직이는 버전: 지갑 생성 애니메이션.

여기서 4페이지의 불변식 ①②가 구현됩니다. 발급과 조회를 다른 동사로 가른 이유(1p 매트릭스의 두 행): 발급은 상태를 바꾸는 쓰기(번호 소비 + 디렉터리 + watch-list 등록)고, 조회는 그렇게 등록된 주소를 읽기만 합니다. addressOf 가 즉석에서 주소를 계산해 주면 편해 보이지만 — 등록 안 된 주소가 고객에게 나가는 경로가 생기고, 그 주소로 온 입금은 인덱서가 모릅니다. 그래서 "등록까지가 발급"이고, 등록이 실패하면 발급도 실패로 취급합니다.

같은 동사, 두 구현 — 발급과 조회를 나란히

포트 호출(첫 화살표)은 양쪽이 글자 그대로 같고, 달라지는 건 그 아래뿐입니다. 먼저 자체 구현 — 발급은 우리 부품 셋(장부·계산·감시 등록)의 합주입니다:

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant SELF as 자체 구현 (AccountPort)
    participant DIR as 계정 디렉터리(우리 DB) + watch-list(감시 목록)

    BE->>SELF: issueDepositAddress(account, asset) — 발급
    SELF->>SELF: 다음 번호 소비 + xpub 로컬 계산 (이더리움 — HSM 호출 없음)
    SELF->>DIR: 디렉터리에 주소 저장 + 감시 목록 등록 (등록 실패 = 발급 실패)
    DIR-->>SELF: 등록 완료
    SELF-->>BE: 주소

    BE->>SELF: addressOf(account, asset) — 조회
    SELF->>DIR: 발급 장부에서 읽기만
    DIR-->>SELF: 등록된 주소
    SELF-->>BE: 같은 주소 (몇 번을 불러도)

자체 구현. 발급(1~5)이 쓰기 — 번호 소비·계산·등록까지가 한 동작이고, 조회(6~9)는 그 장부를 읽기만 한다. Canton 이면 발급 동사가 없고(주소가 createAccount 의 온장 등록에서 탄생), 조회는 동일하게 장부 읽기다.

Fireblocks 구현 — 같은 두 호출이 벤더 API 한 번씩으로 끝납니다:

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant FBI as Fireblocks 구현 (AccountPort)
    participant FB as Fireblocks (SaaS)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>FBI: issueDepositAddress(account, asset) — 발급
    FBI->>FB: 새 주소 생성 API (generateNewAddress)
    FB-->>FBI: 주소 (Fireblocks 키에서 파생)
    FBI->>DIR: 주소 저장 — 감시 목록(watch-list)은 불요 (vault 가 곧 감시 범위)
    FBI-->>BE: 주소

    BE->>FBI: addressOf(account, asset) — 조회
    FBI->>DIR: 발급 때 저장한 주소 반환 (벤더 왕복 불요)
    DIR-->>FBI: 주소
    FBI-->>BE: 같은 주소

Fireblocks 구현. 발급의 실체가 "벤더 측 쓰기"로 바뀌고 watch-list 단계가 사라질 뿐, 백엔드가 보는 두 동사와 불변식(①②)은 동일하다 — 디렉터리에 저장하는 것도 같다(벤더를 바꿔도 남는 우리 데이터, 9p).

Fireblocks 로 전환하면 이 페이지는 어떻게 되나

위 두 그림이 답입니다 — 구조는 같고, 발급의 실체(우리 계산 vs 벤더 쓰기)와 감시 책임만 바뀝니다. 다만 주소가 Fireblocks 키에서 나온다는 것 — 그 함의는 9페이지(자금은 코드가 아니다)에서.
