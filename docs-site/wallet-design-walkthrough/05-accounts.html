계정·주소 — 지갑 생성은 키 생성이 아니다

매트릭스 1~3행을 채웁니다: createAccount · issueDepositAddress · addressOf

익숙한 것 ↔ 깨지는 지점 "고객 지갑 생성 API" 라고 하면 리소스를 하나 만드는 POST 가 떠오릅니다. 실제로는 — 키는 시스템 셋업 때 단 한 번 만들어지고, 고객 100만 명의 지갑 생성은 키 트리의 가지 번호를 집는 장부 작업입니다. 키 100만 개를 상상했다면 비용 모델 전체가 틀어집니다.

구조는 둘뿐입니다 — 키 트리 하나(HSM 안의 master seed, 셋업 때 1회 생성·확장 공개키 xpub 만 반출)와 장부(고객 ref → 가지 번호 → 발급된 주소). 그 위에서 이더리움과 Canton 이 정반대로 갈라집니다:

같은 포트 동사, 정반대 비용 구조. 이더리움 발급은 공개키 수학(xpub 공개 파생)이라 공짜·로컬이고 — 개인키는 출금 서명 때 HSM 안에서 같은 경로로 파생된다 — Canton 은 주소(PartyId)가 계정 생성 시점의 온장 등록으로 태어나고 추가 입금 주소 개념이 없다(입금 구분은 memo 참조). 움직이는 버전: 지갑 생성 애니메이션.

여기서 4페이지의 불변식 ①②가 구현됩니다. 발급과 조회를 다른 동사로 가른 이유(1p 매트릭스의 두 행): 발급은 상태를 바꾸는 쓰기(번호 소비 + 디렉터리 + watch-list 등록)고, 조회는 그렇게 등록된 주소를 읽기만 합니다. addressOf 가 즉석에서 주소를 계산해 주면 편해 보이지만 — 등록 안 된 주소가 고객에게 나가는 경로가 생기고, 그 주소로 온 입금은 인덱서가 모릅니다. 그래서 "등록까지가 발급"이고, 등록이 실패하면 발급도 실패로 취급합니다.

Fireblocks 로 전환하면 이 페이지는 어떻게 되나

구조는 같습니다 — vault 생성(createAccount)·주소 발급(generateNewAddress)·조회가 같은 동사 뒤에 그대로 매핑되고, watch-list 등록은 "vault 가 곧 감시 범위"라 사라집니다. 다만 주소가 Fireblocks 키에서 나온다는 것 — 그 함의는 9페이지(자금은 코드가 아니다)에서.
