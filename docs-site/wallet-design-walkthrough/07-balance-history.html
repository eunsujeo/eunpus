잔액과 내역 조회 — getBalance · transactionsOf

고객 화면의 두 숫자, 그런데 잔액은 숫자 하나가 아니다

무엇·언제: 고객 홈 화면의 잔액과 거래내역 화면이 부르는 읽기 동사 둘입니다. 먼저 잔액의 규칙. 잔액은 세 칸입니다. 가용(available — 출금에 쓸 수 있는 돈), 대기(pending — 들어왔지만 아직 확정 전, 4p), 잠김(locked — 나가는 중이거나 정책상 묶인 돈, 6p). 출금 가능 판정은 가용만 봅니다. 대기·잠김을 합쳐 보여주는 화면이야 자유지만, 합쳐서 판정하는 순간 없는 돈을 쓰게 됩니다.

getBalance(account, asset) → Balance(available, pending, locked)
transactionsOf(account, 기간) → 입출금 내역 (시간순)
잔액은 우리가 계산하지 않는다 — 벤더가 주는 값을 읽고 대사한다

Fireblocks 를 매니저로 채택했으므로 우리는 인덱서도 잔액 파이프라인도 만들지 않습니다. 잔액은 Fireblocks 의 getVaultAccountAsset 이 돌려주는 값이고, 우리 포트는 그 응답을 우리 업무 타입 Balance(available, pending, locked) 로 옮겨 담을 뿐입니다. 내역도 마찬가지로 Fireblocks 거래 목록 조회를 부릅니다.

그래서 이 페이지의 핵심은 "어떻게 계산하나"가 아니라 "벤더가 준 세 값을 어떻게 읽고, 우리 기록과 어떻게 맞추나"입니다. 값은 벤더의 것이되, 회계가 걸리는 숫자는 주기적으로 우리 기록과 대사합니다(이 페이지 마지막 절).

세 칸은 어디서 오나 — 벤더 응답을 우리 타입으로

Fireblocks 의 getVaultAccountAsset 응답에는 자산별로 여러 필드가 들어 있습니다. 그중 우리가 쓰는 세 칸으로 이렇게 접습니다.

우리 칸Fireblocks 필드뜻
가용 (available)available확정되어 지금 출금에 쓸 수 있는 잔액 (= 블록체인 잔액 − 잠김분)
대기 (pending)pending들어오는 중이지만 아직 확정 전 — 확정 임계에 도달하면 가용으로 옮겨간다
잠김 (locked)lockedAmount + frozen나가는 중(전파 전 출금)이거나 정책상 묶인(AML freeze) 돈

Fireblocks 응답 필드는 available / pending / frozen(AML freeze) / lockedAmount(전파 전 출금) / staked(일부 체인 전용) 등이다. 우리는 이 중 가용·대기·잠김 세 칸만 업무 타입으로 노출하고, 잠김은 lockedAmount 와 frozen 을 합쳐 본다. (source: vault-account API contract) EVM(이더리움·Base)에는 staking 칸이 없어 세 칸으로 충분하다.

세 칸을 가르는 선 — confirm 과 finality

대기와 가용을 나누는 것은 확정입니다. 4·6페이지에서 본 규칙 그대로예요. 돈이 체인에 등장(confirm)했다고 곧바로 쓸 수 있는 게 아니라, 확정 정책이 정한 임계 confirmation 수에 도달(finality)해야 가용이 됩니다. Fireblocks 는 이 전이를 상태와 confirmation 카운트로 드러냅니다.

세 칸을 가르는 건 confirm(체인 등장) → finality(임계 도달) 전이 하나다. "곧 들어올 입금"은 대기 칸에 머물다가, 확정 정책 임계에 도달해 finality 가 나면 가용으로 옮겨간다. Fireblocks 상태로는 CONFIRMING(대기) 에서 COMPLETED(가용) 로의 전이이고, 그 경계 판단은 numOfConfirmations 가 확정 정책 임계를 넘었는지로 한다. 출금을 제출하면 그만큼이 가용에서 잠김으로 빠진다.

확정 임계는 정책(DCCP)이 정한다 — 대부분 1, 예외가 있다

Fireblocks 거래 상태는 전파 뒤 BROADCASTING → CONFIRMING → COMPLETED 로 흐릅니다. COMPLETED = 확정 정책이 정한 임계 confirmation 수에 도달한 상태이고, 그때가 우리 기준의 finality 입니다. 그 임계는 확정 정책(Fireblocks 의 DCCP)이 체인별로 정하는데, 기본값은 대부분 1 confirmation입니다. 예외로 이더리움 클래식은 372, 컨트랙트 호출은 3 confirmation 을 권장 최소로 둡니다. (source: transaction / DCCP)

그래서 대기↔가용 경계는 우리가 블록을 세서 정하는 게 아니라 벤더가 정책대로 계산해 상태로 알려주는 값입니다. 우리는 상태(CONFIRMING/COMPLETED)와 numOfConfirmations 를 읽어서 세 칸에 반영합니다. 이더리움과 Base 는 같은 EVM 이라 이 흐름이 동일합니다.

    FBI-->>BE: 시간순 내역

벤더가 입·출금을 다 기록하므로 우리 쪽 병합이 필요 없다. 포트 구현이 하는 일은 벤더 필드를 우리 세 칸으로 접는 것과, 벤더 상태(CONFIRMING/COMPLETED)를 4·6페이지의 공통 어휘로 번역하는 것뿐이다. 단 회계가 걸리는 숫자는 벤더 잔액과 우리 기록을 주기적으로 대조한다 — 4p 의 "통지는 힌트" 규칙이 잔액에도 적용되는 셈이다.

경계 하나만 분명히 해 둡니다. 이 동사들은 우리 고객 계정(vault)을 조회합니다. 우리 고객이 아닌 임의 외부 주소의 잔액·이력 조회는 Fireblocks 가 이 API 로 주는 기능이 아니라, 정말 필요해지면 그 용도의 조회 수단을 따로 둡니다. 고객 계정 조회와는 별개의 선택입니다.

백엔드에서 이렇게 부른다 — 판정은 가용만

// 출금 가능 판정 — 세 칸 중 available 만 본다 (대기·잠김은 표시용)
suspend fun canWithdraw(account: Account, asset: Asset, amount: Amount): Boolean =
    accounts.getBalance(account, asset).available >= amount

// 잔액 화면 — 세 칸을 그대로 보여준다 (합쳐 보여주더라도 판정엔 안 쓴다)
suspend fun balanceScreen(account: Account, asset: Asset): Balance =
    accounts.getBalance(account, asset)              // 벤더 값을 읽어 온 그대로

// 내역 화면 — 입출금이 합쳐진 한 목록 (벤더가 양방향 기록)
suspend fun historyScreen(account: Account, range: BlockRange): List<Transfer> =
    transactions.transactionsOf(account, range)

판정 코드에 available 만 쓴다. 이 페이지 첫 단락의 규칙이 코드 한 줄로 강제되는 자리다. "곧 들어올" 대기분은 화면엔 보여도 판정엔 절대 들어가지 않는다 — finality 전이라 아직 우리 돈이 아니기 때문이다.

두 백엔드가 각각 부른다 — 화면은 Service, 대사는 Service·Admin

같은 두 동사라도 부르는 백엔드가 갈립니다(0p 의 매트릭스). 고객 화면이 부르는 조회는 Service 백엔드이고, 회계·대사를 위한 조회는 Service·Admin 양쪽에서 씁니다.

고객 잔액·내역 화면Service홈 화면의 세 칸, 거래내역 목록 — 고객 런타임
회계·대사용 조회Service·Admin벤더 잔액·거래 목록을 우리 기록과 맞추는 주기 작업 — 운영·감사

고객 런타임의 조회는 Service, 회계·대사처럼 운영·감사에 걸리는 조회는 Admin 도 함께 부른다 — 두 백엔드는 같은 포트를 쓰되 배포·권한·감사 경계가 다르다(0p).

대사 — 두 장부를 주기적으로 맞춘다

잔액·내역의 숫자는 결국 두 장부에서 나옵니다. 하나는 우리 기록(DB), 다른 하나는 바깥의 진실인 Fireblocks 의 값입니다. 벤더 조회가 아무리 정확해도 통지 누락·지연·우리 쪽 반영 버그는 생기게 마련이라, 회계가 걸리는 숫자는 주기적으로 둘을 직접 대조합니다.

4p 의 "통지는 힌트" 규칙을 회계로 옮긴 버전이다. 화면은 벤더 값으로 빠르게, 장부는 대조로 정확하게. 대기↔가용이 벤더 상태(CONFIRMING/COMPLETED)로 움직이므로, 대사도 그 상태 기준으로 우리 기록과 맞춘다.

더 깊이: 확정 정책(DCCP)과 confirmation lifecycle · 잔액 필드 계약은 컴포넌트 가이드의 추상화 편 참고 (본 워크스루는 가이드 없이 읽힙니다). (가이드는 자체 구축·Canton 전제 — 개념만 참고, 개편 예정)
