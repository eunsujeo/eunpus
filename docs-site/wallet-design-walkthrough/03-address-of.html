입금 주소 조회 — addressOf

이 페이지의 메시지는 "네 분면이 같다"입니다 — 그리고 같아야만 하는 이유

무엇·언제: 고객이 입금 화면을 열 때마다 불리는, 이 문서에서 가장 호출 빈도가 높은 동사입니다. 발급(2p)과 정반대의 성질을 가집니다 — 읽기 전용이고, 몇 번을 불러도 같은 주소가 나오며, 절대 새 주소를 만들지 않습니다.

addressOf(account, asset) → Address   // 읽기 — 멱등 키 불요, 발급 부수효과 없음

▸ 네 분면 공통 — 디렉터리(우리 DB)에서 읽는다

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 매니저 (자체든 Fireblocks 든)
    participant DIR as 계정 디렉터리(우리 DB)

    BE->>MGR: addressOf(계정 1024번, 자산)
    MGR->>DIR: 이 계정에 "발급(등록)된" 주소 읽기
    DIR-->>MGR: 식별자 (이더리움 = 0xAb3… · Canton = PartyId + memo)
    MGR-->>BE: 같은 주소 — 몇 번을 불러도

네 분면의 동작이 같다 — 1·2페이지에서 만들어 디렉터리에 저장한 주소를 돌려줄 뿐이다. 체인 차이는 반환물의 모양(이더리움 주소 vs PartyId)뿐이고, custody 차이는 없다(Fireblocks 분면도 발급 때 저장해 둔 우리 기록을 읽으면 같은 값 — 매 조회가 벤더 왕복일 필요가 없다).

▸ 반례 — 이렇게 구현하면 안 된다

sequenceDiagram
    autonumber
    participant BE as 지갑 백엔드
    participant MGR as 잘못된 구현
    participant WL as watch-list (감시 목록)

    BE->>MGR: addressOf(계정 1024번, ETH)
    MGR->>MGR: ❌ 즉석 계산해 반환
    Note over MGR,WL: 계산된 주소가 감시 목록에 없을 수 있다 —
고객이 그 주소로 입금하면 우리만 모른다 (2p 의 규칙 위반)
    MGR-->>BE: 등록 안 된 주소 ⚠️

이더리움은 공개키 수학으로 주소를 즉석 계산할 수 있어서(2p) 조회를 "재계산"으로 구현하고 싶어진다 — 편하지만, 등록(감시) 안 된 주소가 고객에게 나가는 경로를 만든다. 그래서 규칙: 주소가 태어나는 길은 발급(2p)·계정 생성(1p, Canton)뿐이고, 조회는 등록된 것만 읽는다. 재계산은 검증·복구용 내부 도구로만 쓴다.

자체 × 이더리움자체 × CantonFB × 이더리움FB × Canton

벤더 왕복——불요 (우리 기록으로 충분)불요

"네 분면이 같다"는 것이 왜 중요한가 — 호출 빈도가 가장 높은 동사가 분면과 무관하므로, 입금 화면·고객센터·정산 어디에서 쓰든 전환(7p)의 영향이 0입니다. 차이를 만들 이유가 없는 곳에서 차이를 안 만드는 것도 설계입니다.

백엔드에서 이렇게 부른다 — 읽기라서 더 단순하다

// 입금 화면 핸들러 — 멱등 키 없음 (읽기)
suspend fun depositScreen(accountId: String, asset: Asset): DepositInfo {
    val account = directory.resolve(accountId)            // 고객 → 계정은 우리 DB 로 (벤더에 안 묻는다)
    val id = accounts.addressOf(account, asset)           // 몇 번 불러도 같은 값
    return DepositInfo(id.value, id.memoTag)              // Canton 이면 memoTag 가 채워져 온다 (2p)
}

화면이 1초에 수백 번 불러도 되는 코드 — 상태 변경이 없고, 네 분면 어디서도 같다.
