입금 주소 조회 — addressOf

발급과 정반대인 읽기 전용 동사 — 몇 번을 불러도 같은 주소. Service 백엔드가 부른다

무엇·언제: 고객이 입금 화면을 열 때마다 Service 백엔드가 부르는, 이 문서에서 가장 호출 빈도가 높은 동사입니다. 성질은 발급(2p)과 정반대입니다. 읽기 전용이고, 몇 번을 불러도 같은 주소가 나오며, 절대 새 주소를 만들지 않습니다.

addressOf(account, asset) → Address   // 읽기 — 멱등 키 불요, 발급 부수효과 없음

▸ Fireblocks × EVM — 우리 매핑 DB 에서 읽는다

sequenceDiagram
    autonumber
    participant BE as Service 백엔드
    box rgb(239,246,255) 블록체인 매니저
    participant FBI as Fireblocks 구현 · 포트
    end
    participant DIR as 우리 매핑 DB

    BE->>FBI: addressOf(계정 1024번, 자산)
    FBI->>DIR: 이 계정에 "발급(등록)된" 주소 읽기
    DIR-->>FBI: 주소 (이더리움·Base = 0xAb3… · memoTag null)
    FBI-->>BE: 같은 주소 — 몇 번을 불러도

2페이지에서 발급해 매핑 DB 에 저장한 주소를 돌려줄 뿐이다(계정 자체는 1페이지). 이더리움이든 Base 든 반환물의 모양은 같은 EVM 주소이고, memoTag 는 null 이다. 발급 때 저장해 둔 우리 기록을 읽으므로 매 조회마다 벤더(Fireblocks)를 왕복할 필요가 없다 — 호출 빈도가 가장 높은 동사가 벤더 API 한도·지연에 묶이지 않는다.

▸ 반례 — 이렇게 구현하면 안 된다

    participant MGR as 잘못된 구현

    BE->>MGR: addressOf(계정 1024번, ETH)
    MGR->>FB: 매 조회마다 벤더에 주소 목록 재조회
    Note over MGR,FB: 조회 폭주 시 벤더 API 한도·지연에 묶인다 —
발급 때 이미 우리 DB 에 저장한 값을 두고 왕복 (불필요)
    FB-->>MGR: 주소 목록
    MGR-->>BE: 느리고 한도에 걸리는 조회 (안티패턴)

조회를 "매번 벤더 재조회"로 구현하고 싶어진다. 편하긴 하지만 가장 자주 불리는 동사가 벤더 API 한도·지연에 묶이는 경로가 생긴다. 그래서 규칙을 둔다. 주소가 태어나는 길은 발급(2p)뿐이고, 조회는 그때 우리 매핑 DB 에 저장한 것을 읽는다. 벤더 재조회는 정합성 점검·복구용 내부 도구로만 쓴다.

정리 — 조회는 우리 DB 읽기

Fireblocks × EVM (이더리움·Base)
동작매핑 DB 에서 등록된 주소 읽기
반환물EVM 주소 (memoTag null · Fireblocks 채번 유래)
벤더 왕복불요 — 우리 기록으로 충분

이 설계가 왜 중요할까요. 호출 빈도가 가장 높은 동사가 벤더 왕복 없이 우리 DB 한 번으로 끝나므로, 입금 화면이든 고객센터든 정산이든 어디에서 쓰든 빠르고 벤더 한도에 안 걸립니다. 차이를 만들 이유가 없는 곳에서 차이를 안 만드는 것도 설계입니다.

백엔드에서 이렇게 부른다 — 읽기라서 더 단순하다

// 입금 화면 핸들러 — Service 백엔드, 멱등 키 없음 (읽기)
suspend fun depositScreen(accountId: String, asset: Asset): DepositInfo {
    val account = directory.resolve(accountId)            // 고객 → 계정은 우리 매핑 DB 로 (벤더에 안 묻는다)
    val id = accounts.addressOf(account, asset)           // 몇 번 불러도 같은 값
    return DepositInfo(id.value, id.memoTag)              // EVM 은 memoTag 가 null 이라 화면에서 생략
}

화면이 1초에 수백 번 불러도 되는 코드다. 상태 변경이 없고 벤더 왕복도 없다 — 우리 매핑 DB 한 번으로 끝난다.
