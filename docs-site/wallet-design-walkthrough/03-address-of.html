입금 주소 조회 — getDepositAddress

생성과 정반대인 읽기 전용 — 매니저가 백엔드 DB 에서 (accountId, asset)로 그 주소를 읽는다

무엇·언제: 고객이 입금 화면을 열 때마다 Service 백엔드가 부르는, 이 문서에서 가장 호출 빈도가 높은 동사입니다. 성질은 생성(2p)과 정반대입니다. 읽기 전용이고, (accountId, asset)로 저장된 그 주소를 그대로 읽으며, 새 주소를 만들지 않습니다.

getDepositAddress(accountId, asset) → Address { value, memoTag? }   // 읽기, 백엔드 DB 에 저장된 그 값

▸ 매니저가 백엔드 DB 에서 읽는다 — 벤더 왕복 없음

sequenceDiagram
    autonumber
    box rgb(219,234,254) Service 백엔드 — 어댑터 포함·한 프로세스
    participant BE as 유스케이스
    participant FBI as 블록체인 매니저 어댑터·포트
    end
    participant BDB as 백엔드 DB

    BE->>FBI: getDepositAddress(accountId, asset)
    FBI->>BDB: (accountId, asset)↔주소 읽기
    BDB-->>FBI: 주소 (이더리움·Base = 0xAb3… · memoTag null)
    FBI-->>BE: 주소
    Note over FBI,BDB: 벤더(Fireblocks)를 거치지 않는다 — 백엔드 DB 만 읽는다

2페이지에서 백엔드 DB 에 저장한 주소를 (accountId, asset)로 읽어 돌려줄 뿐이다. 이더리움이든 Base 든 반환물은 같은 EVM 주소이고, memoTag 는 null 이다. 백엔드 DB 를 읽으므로 매 조회마다 벤더(Fireblocks)를 왕복할 필요가 없다 — 호출 빈도가 가장 높은 동사가 벤더 API 한도·지연에 묶이지 않는다.
