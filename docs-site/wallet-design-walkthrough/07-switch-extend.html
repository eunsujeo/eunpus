전환과 확장 — 이 4분면이 가능한 이유

1~6페이지가 보여준 것의 회수 — 그리고 전제의 세 문장을 증명으로 닫기

1~6페이지에서 반복된 패턴 둘

모든 기능 페이지에서 같은 일이 일어났습니다. ① 포트 호출은 네 분면에서 글자 그대로 같았다 — 그래서 백엔드 코드는 어느 분면에서도 같다. ② 두 축은 서로 다른 것을 결정했다 — custody 축은 "누가 실행하나"(우리 부품 vs 벤더), 체인 축은 "무엇이 일어나나"(주소의 탄생 방식·수락 행위·잠김·확정 성질). 이 분리가 유지된 것은 우연이 아니라 두 가지 약속 덕입니다:

약속내용 — 1~6페이지에서 본 그 규칙들
같은 동사 (포트)매니저는 포트로만 호출된다 — 구현이 갈려도 시그니처는 하나 (모든 페이지의 "공통 호출" 코드 한 줄)
같은 의미 (불변식)조회는 새 주소를 만들지 않는다(3p) · 등록까지가 발급(2p) · 기록은 전파 전(5p) · 통지는 힌트(4p) · 판정은 가용만(6p) · 없는 기능은 타입 부재(2p) — 어느 구현이든 지켜야 하는 약속

그리고 이 약속은 주장이 아니라 시험입니다 — 포트별 계약 테스트 한 벌을 두 구현(자체=테스트넷, Fireblocks=샌드박스)이 똑같이 통과하게 하면, "전환해도 의미가 보존된다"가 측정이 됩니다:

abstract class AccountPortContractTest {        // 시험지는 하나
    abstract fun port(): AccountPort            // 응시자만 바뀐다
    @Test fun `조회는 절대 새 주소를 만들지 않는다`() { … }
    @Test fun `같은 멱등 키 재시도는 두 번 실행되지 않는다`() { … }
}
class SelfBuildContractTest : AccountPortContractTest()    // 자체 — 테스트넷
class FireblocksContractTest : AccountPortContractTest()   // FB — 샌드박스

정직하게 — 약속 전부가 이 시험지에 들어가지는 않습니다. 계약 테스트의 몫은 포트 밖에서 관찰 가능한 약속(조회는 만들지 않는다 · 등록까지가 발급 · 없는 기능은 타입 부재 · 멱등)이고, "기록은 전파 전"은 자체 파이프라인의 단위 테스트가, "판정은 가용만"은 백엔드 테스트가 나눠 집니다 — 세 겹이 합쳐져야 전환 증거가 완성됩니다.

코드 구조 — 이 문서를 모노레포로 옮기면

지금까지의 등장인물(0p)과 약속이 코드에서 강제되려면 모듈 경계가 곧 설계 경계여야 합니다. 한 저장소(모노레포) 안에서 이렇게 자릅니다:

wallet/
├─ domain/                # 포트 + 값 객체 (0p "도메인 한 장") — 순수 코드, 아무것도 의존하지 않음
├─ backend/               # 지갑 백엔드 — 유스케이스 · 계정 디렉터리 · API (1~6p 의 "사용 코드"가 사는 곳)
├─ engine/                # 자체 매니저의 부품 (0p 등장인물)
│   ├─ multichain/        #   체인 어댑터 인터페이스 + 레지스트리
│   ├─ pipeline/          #   트랜잭션 파이프라인 — 조립→서명→전파, 단계 기록 (5p)
│   ├─ signing/           #   HSM 연동 + 정책 게이트 (5p)
│   └─ indexer/           #   인덱서 — 감지·확정·watch-list (4p)
├─ chains/
│   ├─ ethereum/          #   ETH 어댑터 — 노드 RPC · nonce · ERC-20 · 수수료 백분위수
│   └─ canton/            #   Canton 어댑터 — participant · party 등록 · OFFER/ACCEPT · traffic
├─ adapters/
│   ├─ self-build/        #   자체 매니저 = engine + chains 조립 → 포트 구현
│   └─ fireblocks/        #   Fireblocks SDK 래핑 → "같은" 포트 구현
└─ apps/
    ├─ api/               #   서버 — DI 가 여기: custody=selfbuild|fireblocks 설정 한 줄
    └─ indexer-worker/    #   상시 worker (자체 분면에서만 가동, 4p)

모듈 사이의 의존 방향이 이 문서의 주장들을 컴파일 타임에 강제합니다 — 화살표는 "의존한다"이고, 전부 안쪽(domain)을 향합니다:

의존 그래프에서 읽히는 규칙 셋. ① backend → domain 뿐 — 백엔드는 adapters 를 모르므로(화살표 없음) "분면을 모른다"가 컴파일 타임 사실이 된다. 두 어댑터를 아는 곳은 apps/api 의 DI(점선) 하나. ② chains 끼리는 서로 모른다 — 새 체인 = chains/ 폴더 하나 추가, 다른 모듈 0줄(확장 증명의 물리형). ③ Fireblocks SDK 는 adapters/fireblocks 안에 격리 — 벤더 타입이 그 밖으로 새면 전환이 깨지므로, 이 경계는 빌드 규칙(의존 검사)으로 막는다.

인프라 — 무엇이 어디서 도는가

같은 코드가 분면에 따라 다른 배치로 풀립니다. 먼저 자체 분면 — 모노레포의 apps 둘에 더해, 장비와 노드가 우리 운영 범위로 들어옵니다:

자체 분면 배치. 운영 대상이 다섯 — api 서버, 상시 worker, DB, HSM(보안 존 격리 — 서명 요청만 드나든다), 그리고 노드 둘. Canton participant 는 단순 노드가 아니라 우리 party 신원을 호스팅하는 장비라 백업·복구가 워크스페이스급 보안 사안이다. 모든 연결이 우리가 밖으로 나가는 방향(outbound)이라 inbound 포트가 필요 없다 — 망분리 환경에 유리한 성질.

Fireblocks 분면 배치. 운영 대상이 둘(api·DB)로 줄지만 새 것이 생긴다 — 벤더 API 자격증명 관리, 그리고 inbound webhook 엔드포인트(자체 분면엔 없던 공인 수신 지점 — 방화벽·서명 검증·가용성이 새 운영 항목, 4p). 전환은 코드만이 아니라 네트워크 방향의 변화이기도 하다: outbound-only → inbound 허용.

전환 — 코드는 한 줄, 자금은 이사

코드의 전환은 설정 한 줄입니다(custody: selfbuild → fireblocks) — 1~6페이지에서 백엔드가 분면을 모르고 동작했으니 당연한 귀결입니다. 체크리스트도 이미 본 것들입니다: 멱등 키 → externalTxId 연결(5p), 자체 파이프라인·인덱서 끄기(5p — 순번 충돌·4p — webhook 대체). 단 임의 외부 주소 조회용 인덱서를 따로 쓰고 있었다면 그것은 custody 와 별개 축이라 그대로 둔다(6p). 그리고 정책 게이트의 규칙은 데이터다 — 화이트리스트·한도·일일 누적을 Fireblocks 의 거버넌스 정책(TAP)으로 이관하고 동등성을 검증하는 것까지가 전환이다(5p). 그런데 한 가지는 설정으로 안 됩니다: 자체 주소는 우리 키에서, Fireblocks 주소는 벤더 키에서 나왔으므로(2p) — 주소와 그 위의 잔액은 이전되지 않습니다:

전환 운영 타임라인 — 노랑 구간이 비용의 전부고, 그 비용은 구 주소 수와 잔액에 비례한다. "자체로 테스트부터, 전환은 나중에"라는 우리 순서의 논리가 여기 있다: 테스트 단계의 구 주소·잔액은 거의 0이라, 전환이 가장 쌀 때 전환 가능성을 증명해 두는 것이다.

확장 — N번째 체인은 어댑터 하나

1~6페이지의 4분면 표에서 체인 열을 비교해 보면, 이더리움과 Canton 은 거의 모든 축에서 반대편이었습니다 — 주소(계산 vs 등록)·순번(있음 vs 없음)·제출(끝 vs 시작)·확정(대기 vs 즉시)·귀속(주소 vs memo). 설계 공간의 양 극단을 같은 포트 뒤에서 소화했다는 것이 확장의 증명입니다: 비트코인이든 솔라나든 이 두 극단의 사이에 있지 바깥에 있지 않으므로, 추가 작업은 체인 어댑터 한 개 + 등록 한 줄이고 백엔드·파이프라인·인덱서 가공부는 0줄입니다. 전제 조건 둘만 지키면 — 어댑터는 실패도 공통 분류로 번역해야 하고(재전송 안전/재조립 필요/영구 실패), 체인이 못 하는 일은 기능 부재로 선언해야 합니다(2p) — 이 둘이 새면 체인 분기가 백엔드로 스며들어 "0줄"이 거짓이 됩니다.

마무리 — 전제의 세 문장이 증명으로

"자체로 테스트한다" — 1~6의 자체 분면이 그 동작 전부다. "Fireblocks 로 전환해도 다른 시스템 무영향" — 같은 포트 호출(전 페이지) + 계약 테스트 + 설정 한 줄, 자금 이사만 운영 절차로. "체인이 늘어도 무영향" — 양 극단(이더리움·Canton)을 이미 같은 포트 뒤에서 소화했고, 새 체인은 어댑터 하나다.

더 깊이: 포트별 택일·교체 구조 — 가이드 13장 · DI 한 줄 교체 — 17장 · 계약 테스트 구성은 본 워크스루의 제안(스켈레톤 미반영).
