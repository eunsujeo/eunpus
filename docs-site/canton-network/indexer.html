4. 인덱서 구현

블록 높이를 세는 게 아니라, Ledger API 거래 스트림으로 ACS 변화와 2-step lifecycle 을 따라간다

4.1 EVM 인덱서와 무엇이 다른가

EVM 인덱서는 보통 이렇게 동작한다 — 블록을 높이 순으로 가져와, 우리 주소가 관련된 트랜잭션·로그를 디코딩하고, N블록 확인을 기다려 입금을 확정한다. 핵심은 "블록 높이를 따라가며 폴링" 이다.

Canton 인덱서는 전제가 다르다.

EVM 인덱서 = "블록 높이를 따라가며 우리 주소 로그를 줍는다". Canton 인덱서 = "ledger offset 을 따라가며, 우리 party 가 stakeholder 인 거래 스트림을 받아 ACS 변화와 2-step 상태를 갱신한다". 프라이버시 덕에 남의 거래를 필터링할 필요가 애초에 없다.

4.2 무엇을 읽는가 — 두 갈래

Canton 인덱서가 다루는 입력은 크게 둘이다.

  • ACS 스냅샷 — 특정 시점 우리 party 의 활성 contract 전체. 시작·복구 시 기준선(baseline)을 잡는다(1. 원장 모델).
  • 거래 스트림(updates) — 그 이후의 변화를 ledger offset 순서로 받는다. 각 거래는 어떤 contract 가 생성(created)되고 archive 됐는지를 담는다. 여기서 입금·전송 상태 전이를 읽는다.

4.3 코드로 보면 — offset 스트림 + holding/lifecycle 갱신

설명용 의사코드다. 두 단계 — ① 기준선 ACS, ② offset 순 스트림을 받아 holding 과 2-step 상태를 갱신한다.

class CantonIndexer {
  async start(partyId) {
    // ① 기준선 — 현재 holding 집합 (가용/locked)
    const acs = await ledger.activeContracts(partyId)
    this.holdings = indexHoldings(acs)              // assetId → Holding UTXO 집합
    let offset = await store.lastOffset(partyId) ?? acs.offset

    // ② 그 이후 변화를 offset 순으로 스트림
    for await (const update of ledger.updates(partyId, { fromOffset: offset })) {
      this.apply(update)
      await store.saveOffset(partyId, update.offset)  // 체크포인트 (재시작 안전)
    }
  }

  apply(update) {
    for (const ev of update.events) {
      if (ev.kind === "created"  && isHolding(ev))  this.addHolding(ev)      // 입금/mint
      if (ev.kind === "archived" && isHolding(ev))  this.removeHolding(ev)   // 출금/burn/소비
      if (isTransferInstruction(ev)) this.applyTransferLifecycle(ev)         // 2-step
    }
  }

  // 2-step 상태기계 — 제출(Pending)이 완료가 아님 (3. 자산 동작)
  applyTransferLifecycle(ev) {
    switch (ev.choice) {
      case "Offer":    this.markPending(ev);   this.lockHolding(ev) ; break  // 송신 자금 locked
      case "Accept":   this.markCompleted(ev); this.emit("transfer_completed", ev); break
      case "Reject":   this.markReturned(ev);  this.unlockHolding(ev); break
      case "Withdraw": this.markWithdrawn(ev);  this.unlockHolding(ev); break
    }
  }
}
입금 감지 = created holding 이벤트 (공식 "TransferIn")

EVM 입금은 "우리 주소로 들어온 Transfer 로그" 지만, Canton 입금은 우리 party 를 stakeholder 로 하는 holding contract 가 created 되는 사건이다 — 공식 가이드는 이를 "TransferIn" 이벤트로 감시하라고 안내한다. 단 2-step 이라, 들어오는 전송은 먼저 Pending 으로 보이고 우리가(또는 pre-approval 이) ACCEPT 해야 실제 holding 이 created 된다. "전송이 보였다 = 입금 확정" 으로 착각하면 안 된다 — 확정은 ACCEPT 후 holding created 시점이다. (전송 instruction 의 pending/completed 상태를 함께 조회한다.)

입금 식별은 주소가 아니라 memo tag — EVM 식 "사용자별 입금주소" 가 깨진다

EVM·비트코인에서는 사용자마다 입금주소를 따로 발급해 "어느 주소로 들어왔나" 로 입금자를 구분한다. Canton 은 그렇게 하지 않는다. 공식 가이드는 별도 입금주소 없이 전송 metadata 의 memo 태그로 입금을 추적하라고 안내한다(거래소 입금도 동일).

"meta": { "values": { "splice.lfdecentralizedtrust.org/reason": "memo-ref" } }

리플(XRP)·스텔라(XLM)의 destination tag 와 같은 발상이다. 따라서 인덱서는 "입금주소 → 사용자" 매핑이 아니라 "memo-ref → 사용자" 매핑으로 입금을 귀속시켜야 한다. 그리고 입금받을 때마다 새 party(주소)를 만들지 말 것 — party 발급에는 비용이 있어, 공식 권고는 계정당 party 하나를 안정적으로 두고 memo 로 입금 건을 구분하는 것이다(2장).

4.4 멱등·재시작·잔액 산출

  • offset 체크포인트로 재시작 안전. 마지막 처리 offset 을 저장하고, 재시작 시 그 다음부터 받는다. 같은 거래를 두 번 받아도 contract id 기준으로 멱등 처리한다(이미 반영한 created/archived 는 무시).
  • 잔액은 숫자가 아니라 holding 집합. 인덱스 저장소는 assetId 별 Holding UTXO 집합을 들고, 가용/locked 를 구분한다. 출금 가능액은 가용 holding 합, 큰 출금은 조각을 모은다(1. 원장 모델).
  • 2-step 상태를 1급 시민으로. 전송 lifecycle(Pending/Completed/Rejected/Withdrawn)을 인덱스에 저장해, "묶인 돈" 과 "대기 중 전송" 을 지갑 백엔드가 조회할 수 있게 한다.
  • 확정 = 완료 이벤트. N블록 대기 로직은 없다. commit 된 거래 이벤트가 곧 확정이다(2장). 확정은 공식 기준 보통 3-10초.
  • 대사 기준 시각. 우리 인덱스 진행은 ledger offset(/v2/state/ledger-end)으로 잡지만, 외부 파트너와의 대사는 synchronizer 가 매기는 recordTime 을 기준으로 맞춘다 — offset 은 우리 노드 로컬 값이라 상대와 공유되지 않기 때문이다.
설계 포인트 — 멀티체인 인덱서에 끼워 넣기

여러 체인을 다루는 인덱서라면, Canton 은 "블록 폴링" 계열이 아니라 "offset 스트림" 계열의 소스로 따로 둔다. 공통 인덱서 코어가 "입금 확정 / 전송 완료 / 잔액 변동" 같은 정규화된 이벤트만 받게 하고, ACS·offset·2-step 같은 Canton 특유의 메커니즘은 CantonSource 안에 가둔다. EVM 의 blockNumber 자리에 Canton 은 offset 을, "N블록 확인" 자리에 "commit 이벤트" 를 매핑하는 식이다.
