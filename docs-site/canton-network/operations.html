3. mint · burn · transfer · fee · cancel

자산이 생기고·사라지고·옮겨지고·비용을 치르고·취소되는 다섯 동작 — 각각 EVM 과 무엇이 다른가

3.2 transfer — 기본 2-step 전송

Canton 에서 가장 EVM 과 다른 동작이다. 모든 토큰의 기본 전송은 2-step 이다 ("matches how funds are usually transferred in TradFi"). 송신자가 보낸다고 끝이 아니라, 수신자가 받아야 완료된다.

Figure 3-1. 2-step 전송 lifecycle. 노랑 = 진행 중(OFFER 제출 → 자금 locked → 대기). 보라 = 분기점(누가 먼저 행동하는가). 초록 = 완료(수신자 ACCEPT — 자금이 실제로 수신자 holdings 로). 빨강 = 미완 종료(REJECT/WITHDRAW — 자금이 송신자에게 돌아옴). 핵심: OFFER 가 원장에 확정(2장의 commit)됐다는 것과 전송이 완료됐다는 것은 다르다. OFFER commit 후에도 자금은 locked 일 뿐이고, 완료는 ACCEPT 가 또 한 번 확정돼야 한다.

수탁 지갑이 흡수해야 할 핵심 — "제출 = 완료" 아님

EVM 어댑터는 broadcast 후 영수증(receipt)을 기다리면 끝이지만, Canton 출금은 OFFER 제출 후 "수신자 수락 대기" 라는 중간 상태가 존재한다. 이 동안 송신 자금은 locked 라 잔액에서 빠진 것처럼 보이지만 아직 상대에게 간 게 아니다. 어댑터·인덱서는 이 상태를 명시적으로 추적해야 하고(4. 인덱서), "언제까지 수락 안 하면 회수할지" 같은 타임아웃 정책이 필요하다. (OFFER/ACCEPT/REJECT/WITHDRAW 상태를 Fireblocks 같은 SaaS 의 거래 상태로 매핑할 때 timeout 처리는 적용 전 확인 필요.)

Canton Coin 은 1-step (pre-approval)

모든 전송이 2-step 인 건 아니다. Canton Coin(CC) 은 Transfer Pre-approval 로 수신을 자동 수락하게 설정할 수 있어, 송신자 입장에서 "보내면 끝" 인 1-step 경험이 된다. 단 pre-approval 은 설정 대상이고, validator 복구 후에는 기존 pre-approval 을 취소·재생성해야 한다(5. 운영).

3.3 fee — traffic 모델

EVM gas 와 가장 다른 점: 수수료가 후불이 아니라 선충전 잔고다.

  • traffic = byte 단위 대역폭 잔고. validator 가 Synchronizer 와 통신(거래 broadcast·합의 메시지)할 때 차감된다.
  • 충전은 Canton Coin 소비로. CC 를 써서 traffic 을 구매하면 원장의 MemberTraffic 잔고가 갱신된다. 추가 traffic 가격은 약 $60 USD / MB(구매 시점 환율로 CC 환산)다.
  • 무료 base 잔고. 20분 window 당 400,000 byte 의 무료 잔고가 있고, 거래를 보내지 않으면 선형으로 회복된다(한 window 가 다 지나면 완전 회복). 소진되면 충전 전까지 거래가 막힌다.
  • 자동 top-up. validator 앱에 목표 처리량·최소 구매 간격을 설정하면, 필요한 만큼 traffic 을 자동으로 사들이는 기능이 내장돼 있다(최소 top-up 단위 약 200,000 byte).
  • 보유세(holding fee). Holding 조각 보유에는 storage·compute 비용이 따른다(연 단위 보유 비용). 보유 비용이 가치를 넘는 dust 조각은 archive 가 허용된다. 그래서 지갑은 조각 수를 사용자당 약 10개 수준으로 유지하도록 병합(merge)하는 게 권장된다.
"Canton Coin 을 소각하면 traffic 이라는 수수료가 생긴다" 를 정확히

소각 자체가 수수료가 아니다. ① Canton Coin 을 소각(burn) → ② traffic(byte) 잔고가 충전됨 → ③ 거래를 보낼 때 소비되는 traffic 이 곧 그 거래의 수수료. EVM 처럼 거래마다 즉석에서 빠지는 후불이 아니라, "대역폭을 미리 사 두고 거래가 그걸 쓰는" 선불 모델이다. 잔고가 마르면 충전 전까지 거래가 막힌다.

토큰경제 관점에서 이 소각은 burn-mint 균형의 한 축이다 — 수수료로 쓴 Canton Coin 은 유통에서 제거(burn)되고(중앙 주체로 가지 않음), 반대편에서 validator·super validator 가 인프라 운영·사용량·가동(liveness) 기여로 Canton Coin 을 새로 발행(mint)받는다. 발행은 약 10분 단위 라운드(연 약 52,560회)로 일어나고, 라운드마다 개발 기금 5% 를 뗀 뒤 validator·앱·SV 로 배분된다(예: validator 가동 보상 상한 기본 라운드당 약 $2.85). USD↔CC 환율은 라운드별 SV 게시율의 중앙값을 쓴다. 소각과 발행이 균형을 이루며 가치를 안정시키는 구조다.

거래 1건의 traffic 비용 산정식

한 메시지가 소비하는 traffic 은 크기 × (수신자 수에 따른 가중치) 로 계산된다.

메시지 비용(byte) = 메시지크기 × (1 + 수신자수 × readVsWriteScalingFactor / 10000)

// 예: scaling factor = 4, 1 MB 메시지, 수신자 10명
//   1,000,000 × (1 + 10 × 0.004) = 1,040,000 byte

현재 네트워크 공통 파라미터(고정값이 아니라 구성에 따라 바뀔 수 있음):

파라미터값
무료 base 잔고400,000 byte / 20분 window (선형 회복)
추가 traffic 가격약 $60 USD / MB (CC 로 환산 청구)
read-vs-write scaling factor4 basis points (0.004)
최소 top-up 단위약 200,000 byte

confirmation 요청/응답, topology 요청 등 Synchronizer 로 가는 메시지가 과금 대상이다. 절대 byte↔금액 환율은 Synchronizer 구성에 따라 가변이라 고정값이 아니다. 실무 산정은 Ledger API 의 /v2/interactive-submission/prepare 가 submission·confirmation 의 traffic estimate 를 돌려주고, participant 로그의 EventCost 로 실측한다.

// 수수료 추정 — EVM 의 estimateGas 대응
const est = await ledger.prepare(unsignedTx)   // /v2/interactive-submission/prepare
est.trafficEstimate   // 이 거래가 소비할 traffic(byte) 추정

3.4 cancel — Withdraw (nonce-replace 아님)

EVM 에서 막히거나 잘못 보낸 거래를 취소하려면 같은 nonce 에 더 높은 gas 로 덮어쓰기(RBF) 하거나 0-value self-send 로 nonce 를 소비한다. Canton 에는 nonce 가 없으므로 이 방식이 통하지 않는다.

대신 2-step 전송의 구조를 그대로 쓴다 — 수신자가 아직 ACCEPT 하지 않은 OFFER 를 송신자가 Withdraw 로 철회하면 locked 자금이 회수된다. 이미 ACCEPT 되어 확정된 전송은 취소 대상이 아니다(되돌리려면 반대 방향 새 전송).

상황EVMCanton
아직 미확정 거래 취소같은 nonce + gas↑ 로 replace (RBF)해당 없음 — 제출 즉시 OFFER 가 확정될 수 있음
미수락 전송 취소개념 없음(1-step 이라 이미 끝)Withdraw — 미수락 OFFER 철회, locked 회수
이미 완료된 전송되돌릴 수 없음되돌릴 수 없음 — 반대 전송 필요
수수료 인상으로 가속RBF / CPFP해당 모델 없음 — traffic 은 가속 대상 아님
EVM 의 "boost(RBF)" 는 Canton 에 없다

EVM·UTXO 어댑터가 제공하는 "막힌 거래 수수료 올려 재전송(boost)" 능력은 Canton 에 해당 모델이 없다. Canton 의 취소는 가속이 아니라 미수락 OFFER 의 Withdraw이고, 수수료(traffic)는 선충전 잔고라 거래별로 올려 가속하는 개념이 아니다. 어댑터는 boost 를 Canton 에서 미지원 능력으로 두고, 취소는 cancel(Withdraw)로만 노출한다.

3.5 코드로 보면 — 다섯 동작을 어댑터로

설명용 의사코드다. EVM 어댑터의 동사와 같은 이름을 쓰되, 내부가 2-step·traffic·Withdraw 로 다르게 채워진다.

class CantonAdapter {
  // transfer = OFFER 제출 (제출이 완료가 아님 — 상태는 인덱서가 추적)
  submitTransfer(t) {
    const offer = buildTransferInstruction(t)   // 송신 자금 locked
    return ledger.submit(offer)                 // → traceableId, 상태 = Pending
  }

  // 수신측 완료 — 우리가 수신자 party 를 수탁할 때
  accept(offerRef) { return ledger.exercise(offerRef, "Accept") }
  reject(offerRef) { return ledger.exercise(offerRef, "Reject") }

  // cancel = 송신자 Withdraw (미수락 OFFER 철회, RBF 아님)
  cancel(offerRef) { return ledger.exercise(offerRef, "Withdraw") }

  // fee 추정 = traffic estimate (estimateGas 대응)
  estimateFee(unsignedTx) {
    const p = ledger.prepare(unsignedTx)        // /v2/interactive-submission/prepare
    return { trafficBytes: p.trafficEstimate }
  }

  // mint/burn 은 발행 권한 party·registrar 의 동작 — 일반 수탁 지갑은 보통 호출자가 아님
  // (USDCx 등 native token 은 Token Registrar 가 관리, CC 와 별도)

  // boost? 미구현 — Canton 은 RBF/가속 모델 없음 (cancel=Withdraw 로만)
}
설계 포인트
  • submit ≠ done — submitTransfer 의 반환은 "제출됨(Pending)" 이지 "완료" 가 아니다. 완료/거절/회수는 인덱서가 lifecycle 이벤트로 확정한다(4. 인덱서).
  • 수신측도 우리 책임일 수 있다 — 양쪽 party 를 모두 수탁한다면 accept/reject 도 우리가 실행한다. 한쪽만 수탁하면 상대 행동을 기다린다.
  • mint/burn 은 보통 발행자/registrar 의 일 — 일반 수탁 지갑은 transfer·cancel·조회가 주 동작이고, native token 발행·소각은 Token Registrar(예: USDCx 는 Circle)가 관리한다. CC 소각은 traffic 충전 경로로만 닿는다.
  • boost 는 미지원 능력으로 — 어댑터가 Canton 에서 boost 를 throw/부재로 두고, 취소는 cancel(Withdraw)만 노출한다.
