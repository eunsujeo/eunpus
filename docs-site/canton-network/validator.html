2. Validator · Synchronizer · 확정

누가 거래를 검증하고, 무엇이 순서를 정하며, 확정은 언제인가 — EVM 의 "블록 N개 확인" 과 다른 그림

2.1 party · participant · validator — 셋의 관계

Canton 의 등장인물부터 정리한다. EVM 의 "주소 = 키쌍" 단순함과 달리 Canton 은 세 층위가 있다.

개념무엇EVM 대응(억지로 비유하면)
party거래 주체(논리적 신원). 자산을 보유하고 전송을 개시·수락하는 단위. PartyId = hint::fingerprint"계정 주소" 에 가깝지만 키가 아니라 신원
participant nodeparty 를 host 하는 실제 노드. Ledger API 를 제공하고 거래를 검증한다. = validator"내가 운영하는 풀노드" 에 가까움
Synchronizer모든 participant 가 공유하는 동기화 계층. Sequencer + Mediator"합의 계층" 에 해당하지만 검증은 안 함

핵심: 한 party 는 하나 이상의 participant 에 host 된다. 우리가 수탁 지갑으로 어떤 고객의 party 를 다룬다는 건, 그 party 가 우리(또는 우리가 위탁한) participant node 에 host 되어 있다는 뜻이다. validator 를 잃으면 그 party 의 ACS 를 새 participant 로 옮겨 re-host 해야 하는 이유가 여기 있다(5. 운영).

PartyId 는 키가 아니라 신원이다

PartyId 의 fingerprint 부분은 그 party 의 topology 변경을 authorize 하는 공개키의 fingerprint(sha256)다. 즉 신원과 서명 권한이 묶여 있다. 하지만 PartyId 자체는 opaque identifier — 앱이 hint 와 fingerprint 를 파싱·조립하면 안 되고, allocation 으로만 생성한다(주소 발급은 3. 자산 동작).

2.2 Synchronizer — Sequencer 와 Mediator

EVM 에서는 채굴자/검증자가 트랜잭션을 모아 블록을 만들고, 그 블록이 쌓이며 확정된다. Canton 에는 그런 "블록 생산자" 가 없다. 대신 Synchronizer 가 두 가지 일을 한다.

  • Sequencer(순서화) — participant 노드들 사이의 통신을 순서화·기밀로 중계한다. atomic multicast 로 메시지를 전달하고, 일관된 순서와 timestamp 를 부여한다. "누가 먼저 보냈나" 를 정하는 게 이 역할이다. 거래 내용을 검증하지는 않는다.
  • Mediator(확정 집계) — 해당 거래의 이해관계자(stakeholder) participant 들이 보낸 confirmation 을 집계해 2-phase commit 으로 거래를 승인하거나 거절한다. 원자성과 프라이버시를 보장한다.

검증 책임은 거래의 이해관계자 participant(validator)에게 있다 — Synchronizer 자체는 검증하지 않는다. 이게 프라이버시의 핵심이다: 무관한 노드는 거래 내용을 받지도, 검증하지도 않는다.

Figure 2-1. 거래 확정 흐름. 노랑 = 진행 중(제출 → Sequencer 순서화 → 이해관계자 검증). 보라 = Mediator 의 2-phase commit 판정. 초록 = 확정(committed — ACS 가 갱신되고 자금이 실제로 이동), 빨강 = 거절(rejected — 상태 변화 없음). EVM 의 "블록에 들어가고 N개 더 쌓이면 확정" 과 달리, Canton 은 Mediator 가 commit 을 내는 순간이 확정 지점이다. 단 이 한 번의 확정이 끝났다고 2-step 전송 전체가 끝난 건 아니다 — 이건 "OFFER 가 원장에 올라간" 확정일 수 있고, 자금이 수신자에게 가려면 별도의 ACCEPT 거래가 또 한 번 이 흐름을 탄다(3. 자산 동작).

2.4 확정을 언제로 봐야 하는가

EVM 에서는 "몇 블록 확인(confirmation)을 기다릴지" 를 우리가 정한다(예: 12블록). Canton 은 다르다 — Mediator 가 commit 을 내면 그 거래는 확정이고, 재구성(reorg)으로 뒤집히는 모델이 아니다. 그래서 "N블록 대기" 라는 개념 자체가 없다.

확정까지 걸리는 정확한 시간 — 확인 필요

메커니즘(Mediator 2-phase commit)은 1차 문서로 확정했지만, 확정까지 걸리는 정확한 시간 수치는 직접 확인한 공식 페이지(subnet overview · canton-network-overview · sync.global FAQ) 어디에도 명시돼 있지 않다. "수 초" 규모라는 인상은 검색 요약과 활용 사례(Musubi 의 약 15초 end-to-end 결제 등)에서 오는 것이고, 네트워크/구성에 따라 달라진다. 실제 적용 환경에서 직접 측정해 SLA 를 잡는 것을 권한다.

설계 포인트
  • "N블록 대기" 로직을 Canton 어댑터에 넣지 말 것 — 확정은 commit 이벤트로 온다. 인덱서는 블록 높이를 세는 게 아니라 Ledger API 의 거래 완료 이벤트를 받는다(4. 인덱서).
  • commit ≠ 전송 완료 — 2-step 전송에서는 OFFER commit, ACCEPT commit 이 각각 따로 확정된다. "확정됐다" 를 "돈이 상대에게 갔다" 로 착각하지 말 것(3. 자산 동작).
  • 확정 시간은 측정값으로 — 코드/문서에 임의 수치를 박지 말고, 운영 환경에서 측정한 값으로 SLA·타임아웃을 잡는다.
