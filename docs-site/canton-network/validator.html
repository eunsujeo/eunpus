2. Validator · Synchronizer · 확정

누가 거래를 검증하고, 무엇이 순서를 정하며, 확정은 언제인가 — EVM 의 "블록 N개 확인" 과 다른 그림

2.1 party · participant · validator — 셋의 관계

Canton 의 등장인물부터 정리한다. EVM 의 "주소 = 키쌍" 단순함과 달리 Canton 은 세 층위가 있다.

개념무엇EVM 대응(억지로 비유하면)
party거래 주체(논리적 신원). 자산을 보유하고 전송을 개시·수락하는 단위. PartyId = hint::fingerprint"계정 주소" 에 가깝지만 키가 아니라 신원
participant nodeparty 를 host 하는 실제 노드. Ledger API 를 제공하고 거래를 검증한다. = validator"내가 운영하는 풀노드" 에 가까움
Synchronizer모든 participant 가 공유하는 동기화 계층. Sequencer + Mediator"합의 계층" 에 해당하지만 검증은 안 함

핵심: 한 party 는 하나 이상의 participant 에 host 된다. 우리가 수탁 지갑으로 어떤 고객의 party 를 다룬다는 건, 그 party 가 우리(또는 우리가 위탁한) participant node 에 host 되어 있다는 뜻이다. validator 를 잃으면 그 party 의 ACS 를 새 participant 로 옮겨 re-host 해야 하는 이유가 여기 있다(5. 운영).

PartyId 는 키가 아니라 신원이다

PartyId 의 fingerprint 부분은 그 party 의 topology 변경을 authorize 하는 공개키의 fingerprint(sha256)다. 즉 신원과 서명 권한이 묶여 있다. 하지만 PartyId 자체는 opaque identifier — 앱이 hint 와 fingerprint 를 파싱·조립하면 안 되고, allocation 으로만 생성한다(주소 발급은 3. 자산 동작).

external party — 키를 우리가 쥐는 신원 (수탁에 핵심)

수탁 지갑에서 가장 중요한 구분이 external party다. party 가 participant 에 host 되는 방식은 둘로 나뉜다.

항목local partyexternal party
키 통제topology 관리를 host node 에 위임자체 signing key 로 자체 통제
namespacehost(SPN?)와 공유자체 고유 namespace
제출 노드최소 1개 필요없음 (submission key holder)
확인 노드임의 수최소 1개 필요

external party 의 거래 서명은 2단계로 일어난다.

  • ① Preparing Participant Node — Ledger API 명령을 Daml 트랜잭션으로 변환해 "서명할 대상" 을 만든다.
  • ② Executing Participant Node — party 의 서명을 붙여 제출한다. party 는 모든 원장 효과를 나타내는 "transaction tree 의 hash" 를 직접 서명한다.
왜 수탁에서 external party 가 정답에 가까운가

external party 에서는 private signing key 를 party(=우리)만 통제·사용하고, participant node 는 party 의 명시적 승인(서명) 없이는 원장에서 아무것도 할 수 없다. 즉 validator 를 운영사에 맡기더라도(5. 운영) 자금을 움직이는 권한은 우리 키에 남는다. 이 구조는 MPC·HSM 으로 키를 보관하고 participant 는 준비·실행만 하는 수탁 모델과 정확히 맞아떨어진다. Fireblocks 의 Canton 복구 절차가 Raw Signing(EdDSA)으로 topology 해시를 외부 서명하는 것도 같은 그림이다.

키 모델 — 무엇을, 어디에 두나

Canton 은 한 종류의 키만 쓰는 게 아니다. 수탁 설계에서 "무엇을 우리가 쥐고, 무엇을 노드가 쥐는가" 를 가르려면 키 종류를 구분해야 한다.

키역할
namespace root keynamespace 의 뿌리 — namespace 는 이 키의 hash 다. topology 변경(누가 어느 노드에 host 되는가 등)을 authorize
external party 서명키party 가 거래를 직접 authorize 하는 키 — 수탁에서 우리가 쥐는 핵심 키. 권장 저장은 offline
node signing key노드 운영용 — sequencer 인증, ACS 상태 서명 등 (운영 인프라 키)
encryption keyview 암호화용 — 큰 데이터는 대칭키, 그 대칭 세션키만 비대칭키로 보호
키를 어디에 보관하나 — 수탁의 핵심 결정

키 저장 옵션은 DB(평문) · 메모리 · offline · KMS(envelope/full) 가 있다. 수탁 지갑이라면 party 서명키(자금을 움직이는 키)를 offline 또는 KMS·HSM·MPC 로 보관하는 것이 정석이다 — 공식 가이드도 external party 서명키의 권장 저장을 offline 으로 든다. 이렇게 두면 validator(participant)는 운영용 node 키만 쥐고, 자금 권한 키는 우리 통제 경계 안에 남는다(앞의 external party 구조와 같은 결론). 알고리즘 측면에선 Fireblocks 의 Canton 복구 절차가 EdDSA(Ed25519) Raw Signing 을 쓴다.

party 는 계정당 하나 — 입금마다 새로 만들지 말 것

EVM 수탁 지갑은 흔히 "사용자(또는 입금)마다 새 주소" 를 발급한다. Canton 에서는 이 습관을 버려야 한다. party allocation 에는 비용이 따르므로, 공식 가이드는 "계정/지갑당 party 하나(one Party per account/wallet)" 를 안정적으로 두라고 권한다 — 입금 건마다 임시 party 를 만들지 말 것. 입금자 구분은 별도 주소가 아니라 memo 태그로 한다(4. 인덱서). PartyId 는 name::fingerprint 형식에 최대 185자다. 백업·이중화를 위해 같은 party 를 여러 validator 에 multi-host 할 수 있다(5. 운영).

2.2 Synchronizer — Sequencer 와 Mediator

EVM 에서는 채굴자/검증자가 트랜잭션을 모아 블록을 만들고, 그 블록이 쌓이며 확정된다. Canton 에는 그런 "블록 생산자" 가 없다. 대신 Synchronizer 가 두 가지 일을 한다.

  • Sequencer(순서화) — participant 노드들 사이의 통신을 순서화·기밀로 중계한다. atomic multicast 로 메시지를 전달하고, 일관된 순서와 timestamp 를 부여한다. "누가 먼저 보냈나" 를 정하는 게 이 역할이다. 거래 내용을 검증하지는 않는다.
  • Mediator(확정 집계) — 해당 거래의 이해관계자(stakeholder) participant 들이 보낸 confirmation 을 집계해 2-phase commit 으로 거래를 승인하거나 거절한다. 원자성과 프라이버시를 보장한다.

검증 책임은 거래의 이해관계자 participant(validator)에게 있다 — Synchronizer 자체는 검증하지 않는다. 이게 프라이버시의 핵심이다: 무관한 노드는 거래 내용을 받지도, 검증하지도 않는다.

프라이버시가 작동하는 방식 — 트랜잭션을 "view" 로 쪼갠다

"당사자만 본다" 가 어떻게 가능한가. 하나의 트랜잭션은 여러 view 로 분해되고, 각 party 는 자기 view 만 받는다. Synchronizer 는 이 view 들을 복호화하지 않고 암호화된 채로 순서화·전달만 한다("조율(coordination)은 Synchronizer, 저장(storage)은 participant" 로 역할이 갈린다). 그래서 한 거래에 여러 party 가 얽혀도 각자는 자기 몫만 보고, 전체를 보는 단일 주체가 없다. (참고: party 는 EVM 의 주소·EOA 에 해당하는 on-ledger 신원이다.)

Synchronizer 는 하나만 있는 게 아니다 — 토폴로지 선택

본 가이드는 공용 글로벌 Synchronizer 를 전제로 설명하지만, Canton 은 단일 Synchronizer · 복수 Synchronizer · 글로벌 Synchronizer 구성을 모두 지원한다. 폐쇄망·컨소시엄용으로 자체 Synchronizer 를 두거나, 여러 Synchronizer 를 함께 쓰는 토폴로지도 가능하다는 뜻이다. 수탁 지갑이 어디에 연결되는지(어느 Synchronizer)에 따라 운영 책임 범위가 달라진다(5. 운영).

순서화 계층의 BFT 합의

Sequencer 의 순서화 자체도 단일 신뢰점이 아니다. 글로벌 동기화 계층(Global Synchronizer)은 2/3 다수결 BFT? 합의 프로토콜로 운영된다 — Mempool → Availability → Consensus → Output 4단계 파이프라인으로, 장애 노드가 전체의 1/3 미만이면 정상 동작한다. 즉 Canton 의 합의는 두 층이다: 순서화 계층(Synchronizer)이 "무엇이 먼저인가" 를 BFT 로 정하고, 그 위에서 이해관계자 participant 들이 "이 거래가 옳은가" 를 검증한다.

이 순서화·검증을 떠받치는 노드도 둘로 나뉜다. Super Validator 가 Global Synchronizer 인프라를 운영하며 트랜잭션 순서화(sequencing)·Canton Coin 거래 검증·거버넌스를 맡고, 일반 Validator 는 자신이 host 한 party 의 거래를 검증하고 연결을 제공한다. 거버넌스는 Global Synchronizer Foundation 과 Linux Foundation 이 함께 감독한다.

EVM 의 "블록에 들어가고 N개 더 쌓이면 확정" 과 달리, Canton 은 Mediator 가 commit 을 내는 순간이 확정 지점이다. 단 이 한 번의 확정이 끝났다고 2-step 전송 전체가 끝난 건 아니다 — 이건 "OFFER 가 원장에 올라간" 확정일 수 있고, 자금이 수신자에게 가려면 별도의 ACCEPT 거래가 또 한 번 이 흐름을 탄다(3. 자산 동작).

2.4 확정을 언제로 봐야 하는가

EVM 에서는 "몇 블록 확인(confirmation)을 기다릴지" 를 우리가 정한다(예: 12블록). Canton 은 다르다 — Mediator 가 commit 을 내면 그 거래는 확정이고, 재구성(reorg)으로 뒤집히는 모델이 아니다. 그래서 "N블록 대기" 라는 개념 자체가 없다.

확정 시간 — 공식 문서 기준 "보통 3-10초"

공식 지갑 통합 가이드는 "Finality usually takes 3-10s" 라고 명시한다 — 확정(Mediator 2-phase commit)까지 보통 3~10초가 걸린다는 뜻이다. 단 "보통(usually)" 이라는 표현대로 네트워크·구성에 따라 편차가 있을 수 있으니, 엄격한 SLA 를 잡을 때는 운영 환경에서 직접 측정해 확정 짓는 것을 권한다. 참고로 합의 메커니즘 페이지에는 별도의 latency/throughput 벤치마크 수치는 제시돼 있지 않다.

설계 포인트
  • "N블록 대기" 로직을 Canton 어댑터에 넣지 말 것 — 확정은 commit 이벤트로 온다. 인덱서는 블록 높이를 세는 게 아니라 Ledger API 의 거래 완료 이벤트를 받는다(4. 인덱서).
  • commit ≠ 전송 완료 — 2-step 전송에서는 OFFER commit, ACCEPT commit 이 각각 따로 확정된다. "확정됐다" 를 "돈이 상대에게 갔다" 로 착각하지 말 것(3. 자산 동작).
  • 확정 시간은 측정값으로 — 코드/문서에 임의 수치를 박지 말고, 운영 환경에서 측정한 값으로 SLA·타임아웃을 잡는다.
