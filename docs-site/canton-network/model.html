1. 원장 모델 — ACS · Holding UTXO

계정 잔액이 아니라 "내가 보유한 활성 contract 집합" 이다 — EVM 과의 첫 번째 큰 차이

1.1 EVM 의 계정 모델부터

EVM 에서 잔액은 단순하다. 각 주소마다 "현재 잔액" 이라는 숫자 하나와 "다음 트랜잭션 순번(nonce)" 하나가 글로벌 상태에 들어 있다. 송금은 그 숫자를 깎고 상대 숫자를 올린다. 잔액을 알고 싶으면 노드에 eth_getBalance(주소) 한 번 물으면 끝이다.

Canton 은 이 그림이 통째로 다르다. "잔액" 이라는 글로벌 숫자가 없다. 대신 party 가 보유한 활성 contract 들의 집합이 곧 상태이고, 토큰 잔액은 그 집합 안의 holding contract 들을 합산해서 얻는다.

1.2 ACS — 활성 contract 집합이 곧 상태

Canton 의 원장 상태는 ACS(Active Contract Set)다 — 어떤 party 가 현재 보유한 활성 contract 전체의 집합. contract 가 생성되면 ACS 에 들어오고, 소비(archive)되면 ACS 에서 빠진다. 토큰 잔액, 진행 중인 전송, 권한 설정 같은 모든 상태가 contract 형태로 ACS 안에 있다.

contract 자체는 불변(immutable)이다 — 수정이 없고 생성(created)되거나 아카이브(archived)될 뿐이다. "상태 변경" 은 곧 옛 contract 를 archive 하고 새 contract 를 create 하는 일이다. contract 에 정의된 동작을 choice 라 하는데, 행사하면 그 contract 를 소비(archive)하는 consuming choice 와, contract 를 그대로 두는 non-consuming choice 로 나뉜다. 그리고 한 contract 를 볼 수 있는 party 들 — stakeholder — 만 그 contract 를 본다(프라이버시의 단위, 2. Validator). stakeholder 는 역할로 더 나뉜다: signatory(생성을 authorize 하고 항상 가시) · observer(가시하지만 choice 행사 불가) · controller(자신이 통제하는 choice 를 행사).

divulgence — fetch 하면 의도치 않게 보일 수 있다

프라이버시가 강하지만 한 가지 함정이 있다. 어떤 거래가 다른 contract 를 fetch(참조) 하면, 그 거래의 당사자들은 observer 로 지정돼 있지 않아도 그 contract 를 자동으로 알게 된다(divulgence). 컴플라이언스·프라이버시 설계 시, 참조만으로도 정보가 새어 나갈 수 있다는 점을 고려해야 한다.

한 문장 요약

EVM: "주소의 잔액 = 글로벌 상태에 적힌 숫자". Canton: "party 의 상태 = 그 party 가 stakeholder 인 활성 contract 들의 집합(ACS)". 잔액은 그 집합에서 합산해서 도출하는 값이지, 어딘가 적혀 있는 숫자가 아니다.

해외송금으로 보는 ACS 변화 — 국내은행 A → 해외은행 B, 50 USDCx

A 가 100 보유([60]+[40] 조각). "상태" 는 잔액 숫자가 아니라 A 의 활성 contract 집합(ACS)이고, 송금하면 그 집합 안 contract 가 생기고/사라지며 바뀐다.

단계A 의 ACS (활성 = 현재 상태)이 단계 변화 (⊖ archive · ⊕ create)A 가용
① 처음[60], [40]—100
② 개시 50→B[40], [10], TransferInstruction[50→B, 대기]⊖ [60] · ⊕ [10](거스름) · ⊕ TransferInstruction(50 잠김)50 (+50 잠김)
③ B 수락[40], [10]⊖ TransferInstruction → 50 은 B 의 ACS 에 ⊕ [50]50
③' 회수/거절[40], [10], [50]⊖ TransferInstruction · ⊕ [50](원복)100

②에서 [10]·[40] 은 일부러 나눈 게 아니다 — 50 을 덮는 조각을 고르는 coin-selection 결과다: [40] 은 부족(40<50)이라 안 쓰고 그대로, [60] 하나를 골라 50 보내고 남은 60−50=10 이 거스름. 이때 소비된 [60] 은 archive = 더는 active 아님 = ACS 에서 빠진다(inactive). [40] 은 그대로 active. 즉 [60] archive·거스름 [10] create·TransferInstruction create 로 집합이 재구성되고(party 전체가 아니라 쓴 조각만 빠짐), ③에서 그 TransferInstruction 이 archive 되며 B 의 ACS 에 Holding[50] 이 create 된다. 자금은 늘 보존(40+10+50=100)된다. EVM 이면 A 잔액 100→50·B +50 숫자만 바뀌지만, Canton 은 contract 를 만들고 없애며 진행되고 2-step 이라 ②~③ 사이 "진행 중 전송" 이 ACS 에 잠깐 존재한다(3. 자산 동작).

이 차이는 복구·인덱싱에서 그대로 드러난다. EVM 노드를 잃으면 체인을 다시 동기화하면 잔액이 복원되지만, Canton 에서 validator 를 잃으면 그 party 의 ACS 를 새 validator 로 가져와(import) re-host 해야 한다 — 잔액이라는 숫자가 아니라 contract 집합 자체를 옮기는 일이다. (5. 운영의 복구 절차)

1.3 Holding UTXO — 토큰 잔액의 표현

토큰 잔액은 ACS 안에서 Holding? contract 들로 표현된다. 그리고 이 holding 은 비트코인과 같은 UTXO? 모델이다. 즉 "100 USDCx" 가 한 칸에 적힌 게 아니라, 예컨대 60 + 40 처럼 여러 holding 조각으로 나뉘어 있을 수 있고, 잔액은 그 조각들의 합이다.

각 holding 은 가용(available)이거나 잠김(locked) 상태다. 전송을 개시하면 해당 자금 holding 이 locked 로 묶인다(3. 자산 동작의 2-step transfer). 조회할 때 이 둘을 구분해서 봐야 한다.

조각은 무한정 늘리면 안 된다 — 사용자당 약 10개로 병합

holding 조각(UTXO)은 각각 활성 contract 라 보관·연산 비용이 따른다. 비트코인 지갑이 잔돈 UTXO 가 너무 많아지면 합치는(consolidate) 것처럼, Canton 지갑도 조각을 주기적으로 병합(merge)해 사용자당 약 10개 수준으로 유지하는 것이 권장된다. 인덱서·지갑 백엔드가 조각 수를 모니터링하고 병합 트랜잭션을 거는 운영이 필요하다.

// holdings 조회 — 가용분만
sdk.token.utxos.list({ partyId, includeLocked: false })   // 지금 쓸 수 있는 holding

// locked 포함 전체
sdk.token.utxos.list({ partyId, includeLocked: true })    // 진행 중 전송에 묶인 것까지

// "잔액" 은 조회 결과를 합산해 도출하는 값이다 (글로벌 숫자가 아님)
const available = sum(list({ includeLocked: false }))
const total     = sum(list({ includeLocked: true }))
const locked    = total - available
"잔액" 을 단일 숫자로 캐싱하면 틀린다

EVM 처럼 "주소→잔액 숫자" 를 캐싱하는 모델을 그대로 옮기면, Canton 의 가용/locked 구분과 UTXO 조각 구조를 잃는다. 출금 가능액은 includeLocked:false 의 합이지 전체 합이 아니며, 큰 출금은 여러 holding 조각을 모아야 할 수 있다. 인덱서는 잔액을 숫자가 아니라 holding 집합으로 들고 있어야 한다. (4. 인덱서)

1.5 코드로 보면 — 잔액을 holding 집합으로

설명용 의사코드다. 멀티체인 어댑터가 Canton 을 흡수할 때, EVM 어댑터가 getBalance → 숫자 를 돌려주는 것과 달리 Canton 어댑터는 내부적으로 holding 집합을 다뤄 정규화한다.

class CantonLedgerModel {
  // 잔액은 조회가 아니라 합산 — 가용/locked 를 함께 돌려줘 위 컴포넌트가 출금 가능액을 안다
  getBalance(partyId, asset) {
    const all       = ledger.holdings(partyId, asset, { includeLocked: true })
    const available = all.filter(h => !h.locked)
    return {
      total:     sum(all),
      available: sum(available),    // 출금 가능액 = 이 값
      locked:    sum(all) - sum(available),
      utxos:     available,          // 조각 목록 — 큰 출금 시 coin-select 대상
    }
  }

  // 큰 금액 = 여러 holding 조각을 모음 (UTXO coin-select 와 같은 발상)
  selectHoldings(partyId, asset, amount) {
    const utxos = this.getBalance(partyId, asset).utxos
    return coinSelect(utxos, amount)   // 합이 amount 이상이 되도록 조각 선택
  }
}
설계 포인트
  • 잔액 = {total, available, locked, utxos} — 단일 숫자로 축약하지 말 것. "얼마 보낼 수 있나"(출금 가능 판단)는 가용 합계 available 로 보고, 실제 트랜잭션을 만들 때(조립)는 그 합계 숫자가 아니라 holding 조각들(utxos)을 골라서 쓴다 — 비트코인이 잔돈 UTXO 를 골라 쓰는 것과 같다(예: 40 을 보낼 때 [30]+[20] 조각을 골라 합 50 을 쓰고 거스름 10 은 새 조각으로).
  • locked 는 일시적 상태 — 진행 중인 2-step 전송이 ACCEPT/REJECT/WITHDRAW 로 끝나면 풀린다. 인덱서는 이 전이를 추적해 locked 를 갱신한다(4. 인덱서).
  • PartyId 는 파싱하지 말 것 — hint::fingerprint 형식이지만 opaque identifier 다. 주소처럼 조립·해석하지 말고 allocation 결과를 그대로 키로 쓴다(2장).
