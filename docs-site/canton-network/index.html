0. Canton 개요

Canton 이 EVM 과 무엇이 다르고, 수탁 지갑이 무엇을 흡수해야 하는가

본 가이드는 Canton 네트워크를 수탁(custodial) 지갑 관점에서 분해한다. 같은 "블록체인 연동" 이라도 Canton 은 이더리움(EVM)과 원장 모델·확정 방식·수수료·전송 단계가 근본적으로 다르다. 이 차이를 먼저 정리하고, validator 가 블록을 어떻게 확정하는지, 자산 동작(발행·소각·전송·수수료·취소)이 어떻게 일어나는지, 인덱서를 어떻게 짜야 하는지, 그리고 노드를 직접 운영할 때와 관리형으로 위탁할 때 무엇이 달라지는지를 본다.

본 페이지의 출처

이 문서의 사실 진술은 출처를 둘로 나눠 읽어야 한다.

  • 공식 문서에 정의된 사실 (그대로 받아도 안전) — Digital Asset 공식 기술 문서(docs.digitalasset.com v3.4)와 Canton 운영 문서(docs.sync.global), Fireblocks 의 Canton Coin 복구 절차 문서에서 확인한 내용. 본문에서 별도 표시 없이 서술한다.
  • 저자가 정리한 설계 참고안 (본인 환경 검증 권장) — 위 사실을 수탁 지갑 컴포넌트로 옮긴 코드·다이어그램·운영 권고. "설계 포인트", "코드로 보면" 처럼 묶은 부분이 여기에 해당한다.

아직 1차 문서로 확정하지 못한 항목(예: 확정까지 걸리는 정확한 시간)은 "확인 필요" 라벨로 분리한다. 추정으로 메우지 않는다.

0.1 Canton 이란

Canton 은 DAML? 스마트컨트랙트 기반의 privacy-enabled 퍼블릭 블록체인이다. 기관 금융·자산 토큰화·국가 간 결제를 주 대상으로 설계됐다. 다른 퍼블릭 체인과 가장 다른 점은 프라이버시다 — 거래 당사자만 해당 거래 데이터를 보고, 무관한 참여자에게는 노출되지 않는다.

먼저 — 이 가이드에 계속 나오는 용어 6개 (1분)

아래만 알고 들어가면 나머지가 수월하다. 핵심은 "Canton 의 모든 것은 contract 다".

  • contract — Canton 원장에 올라가는 상태 한 조각. "누가 토큰 얼마 보유", "전송 진행 중", "이 권한 있음" 이 전부 contract(DAML 스마트컨트랙트의 인스턴스)다. 한 번 생기면 못 고치고 생성(created)되거나 소멸(archived)될 뿐이다. (자세히 1장)
  • ACS (활성 contract 집합) — 한 party 가 지금 보유한 contract 전부의 묶음 = 그 party 의 현재 상태. (1장)
  • holding (UTXO? 형) — 토큰 잔액을 나타내는 contract. 비트코인 UTXO 처럼 "100" 이 한 칸이 아니라 [50][30][20] 조각으로 쪼개져 있고, 잔액 = 조각들의 합이다. (1장)
  • party — 거래 주체(신원). 은행·계좌처럼 "누구" 에 해당 — 주소가 아니라 신원이다. 단순 요청자가 아니라, 그 party 의 키로 서명해야 거래가 성립하는 승인자다. 수탁(external party)이면 그 키는 participant 가 아니라 우리가 HSM/MPC·offline 에 보관·통제한다. (2장)
  • participant node (= validator) — party 를 담고 거래를 검증하는 노드. 보통 각 기관의 인프라다. (2장)
  • Synchronizer — 노드들을 잇는 공용 합의 계층. 거래 순서·확정을 맡는다(우리가 운영하지 않는다). (2장)

이 용어로 구조를 한 줄로 요약하면: party(거래 주체)가 participant(=validator 노드)에 host? 되고, 거래는 Synchronizer(Sequencer + Mediator)를 통해 순서화·확정된다. 자산 상태는 계정 잔액이 아니라 party 가 보유한 활성 contract 집합(ACS)으로 표현되고, 토큰 잔액은 그 위에서 UTXO 형 holdings(잔액 = 조각들의 합)로 다뤄진다.

0.2 EVM 과 한 눈 대비

수탁 지갑이 EVM 만 다뤄 봤다면, Canton 에서 가장 먼저 깨야 하는 가정이 아래 표다. 자세한 모델 비교는 1. 원장 모델, 동작별 비교는 3. 자산 동작에서 이어진다.

EVM 감각으로 들어왔을 때 가장 크게 틀리는 두 가지
  • "제출 = 완료" 가 아니다. Canton 전송은 기본이 2-step 이라, 출금을 제출해도 "수신자 수락 대기" 상태에 머무를 수 있고 그동안 송신 자금은 잠긴다. EVM 의 "broadcast 하면 곧 확정" 감각을 그대로 쓰면 안 된다. (3. 자산 동작)
  • 수수료는 후불이 아니라 선충전 잔고다. gas 처럼 거래마다 즉석에서 빠지는 게 아니라, Canton Coin 을 미리 소각해 traffic 잔고를 채워 두고 거래가 그 잔고를 소비한다. 잔고가 마르면 거래가 막힌다. (3. 자산 동작)

Canton 구성. 바깥의 큰 박스 "Canton 네트워크" 가 곧 privacy-enabled 퍼블릭 블록체인이다 — participant 계층(파랑) + Synchronizer(보라) + Super Validator(회색) 전체가 Canton 이고, 그 밖의 초록(우리 지갑 서비스)만 Canton 이 아니라 우리 것이다(Canton 어댑터를 통해 연동). "privacy" 는 그림의 특정 영역이 아니라 거래가 흐르는 방식(view 분해, 1장·2장)의 성질이다. 파랑 = participant 계층 — 우리가 붙는 Ledger API 와 그 뒤의 participant node(=validator). validator 는 party 를 host 하고 자신이 이해관계자인 거래를 검증한다. 보라 = Synchronizer(Sequencer 가 순서·timestamp 를, Mediator 가 confirmation 집계 후 2-phase commit 으로 확정). 회색 = Super Validator — CC↔USD·USD↔byte 환율을 게시해 traffic 가격을 정한다(직접 운영 대상 아님). 우리가 코드로 닿는 면은 거의 항상 Ledger API? 한 겹이다 — validator 를 직접 운영하든(5. 운영) 관리형으로 위탁하든. 이 Ledger API 는 누구의 API 인가 — participant node(=validator)가 노출하는 API다. 우리가 직접 운영한 노드든, 위탁한 노드든, 그 노드가 제공하는 창구가 Ledger API 이고 우리 지갑 백엔드는 거기에 붙는다.

실제로 누구인가 — 박스별 기관
  • 🟩 우리 지갑 서비스 = 우리 은행·수탁사(우리가 만드는 것).
  • 🟦 participant node = validator = 우리(직접 운영) 또는 위탁 운영사. 서명만 위탁하면 Fireblocks·Dfns 같은 custody 제공자(6. 수탁 통합).
  • 🟪 Synchronizer = 우리가 운영하지 않는 공용 Global Synchronizer — 아래 Super Validator 들이 공동 운영.
  • ⬜ Super Validator = 주요 금융·핀테크 기관들. 공식 재단(Canton Foundation, 구 Global Synchronizer Foundation) 회원 기준 Goldman Sachs · SBI Digital Asset · Euroclear · Broadridge · Tradeweb · Digital Asset · Moody's · Cumberland 등으로, 현재 54개 SV 노드가 Global Synchronizer 를 공동 운영한다.

요점: 우리(은행)는 초록 + (직접 운영 시) 파랑까지가 우리 몫이고, 보라·회색은 우리가 운영하지 않는 공용 글로벌 계층이다. (출처: Canton Foundation, 2026-06 기준 — 명단·노드 수는 시점에 따라 변함.)

0.4 읽는 법

  • 1. 원장 모델 — ACS + Holding UTXO 가 EVM 의 계정+nonce 와 어떻게 다른지. 잔액을 어떻게 읽고, locked 가 무엇인지.
  • 2. Validator · Synchronizer · 확정 — party/participant 관계, Sequencer+Mediator 가 블록(거래)을 확정하는 흐름, 확정을 언제로 봐야 하는지.
  • 3. mint · burn · transfer · fee · cancel — 자산이 생기고(mint) 사라지고(burn) 옮겨지는(transfer 2-step) 동작, traffic 수수료, 취소(Withdraw) — 각각 EVM 대비.
  • 4. 인덱서 구현 — ACS/UTXO 를 어떻게 읽고, Ledger API 이벤트 스트림으로 2-step lifecycle 을 어떻게 추적하는지. EVM 인덱서와의 차이.
  • 5. 직접 운영 vs 위탁 운영 — validator participant 를 직접 운영할 때와 관리형으로 위탁할 때의 책임·복구·trade-off.
  • 6. 수탁 통합 — wallet/guidance — 공식 지갑 통합 가이드의 수탁 요건을 한 데 모은 체크리스트. 입금(memo 태그)·party 운용·전송 API·입금 확인·운영을 앞 장들과 연결.
