5. 직접 운영 vs 위탁 운영

validator participant 를 직접 돌릴 것인가, 관리형으로 위탁할 것인가 — 책임·복구·trade-off

5.1 갈림길은 "participant node 를 누가 운영하나"

2장에서 봤듯, Canton 에서 우리 party 는 어떤 participant node(=validator) 에 host 된다. 이 노드를 누가 운영하느냐가 통합 방식을 가른다.

  • 직접 구현 — 우리가 participant node 를 직접 구축·운영한다. Ledger API 도, 그 아래 노드 인프라도, 키도, 복구도 전부 우리 책임.
  • 위탁 운영(관리형 validator) — 관리형 validator 운영사가 participant 를 운영해 주고, 우리는 그 위의 Ledger API(또는 SaaS API)에 붙는다.
"그 custody 벤더가 Canton 을 지원하나?" 를 먼저 확인

위탁을 택하기 전에 그 벤더가 Canton 을 실제로 지원하는지부터 확인해야 한다. 많은 수탁/지갑 제품이 EVM·Solana 등 특정 체인 전용이라 Canton 을 못 다룬다 — 예컨대 국내 NodeInfra 의 NodeWallet 은 현재 Solana 전용이라 Canton 수탁에는 쓸 수 없다. (Canton 위에서 일부 사업자가 네트워크 Operator 로 참여한 사례는 있으나, 그것이 곧 "수탁용 관리형 Canton validator 제공" 을 뜻하지는 않는다.) Canton 서명 위탁은 오히려 Wallet Gateway 가 지원하는 서명 프로바이더(Fireblocks·Dfns 등, 6. 수탁 통합) 쪽이 더 직접적인 경로다.

Fireblocks 는 어디에 들어가나 — "노드 운영" 과 "키·서명" 은 별개

혼동하기 쉬운데, validator 노드를 누가 운영하나(직접/위탁)와 자금 권한 키를 누가 쥐고 서명하나는 분리된 문제다. Fireblocks 는 후자다 — participant 노드를 운영하는 게 아니라, external party 의 키를 MPC/HSM 으로 보관하고 서명한다. 그래서 노드는 직접 운영하든 위탁하든, 서명은 Fireblocks 가 맡는 조합이 가능하고, 자금 권한 키는 우리 통제에 남는다(2.2 키·서명·6. 수탁 통합).

Fireblocks 는 Canton 을 지원하며 Canton Coin 복구 절차를 문서화한다 — EdDSA Raw Signing 으로 topology tx 를 외부 서명해 새 validator 에 party 를 host 하고 ACS 를 import(5.3 의 external party 복구와 같은 그림). 단 2-step 상태 매핑·수락 대기 timeout 처리는 적용 전 확인 필요.

공통점부터 — 우리가 닿는 면은 거의 항상 Ledger API 한 겹

어느 쪽이든 우리 지갑 백엔드가 코드로 닿는 면은 Ledger API(또는 그 위의 SaaS API)다(0. 개요의 Figure). 그래서 어댑터 코드(3·4) 자체는 두 방식에서 크게 다르지 않다 — 달라지는 것은 그 아래 노드의 운영 책임이다.

신뢰 모델로 보는 직접 vs 위탁 — "무엇을 누구에게 맡기나"

Canton 은 "전부 믿기/아무도 안 믿기" 가 아니라 선택적 신뢰(selective trust) 모델이다. 자가호스팅 결정에 직접 영향을 주는 부분만 추리면:

  • validator — 데이터 보관·가용성은 맡기지만, external party 를 쓰면 "서명" 은 맡기지 않는다(키는 우리 것). 직접 운영하면 validator 신뢰 자체가 사라진다 — 운영사를 위협 모델에서 제거.
  • counterparty — 거의 안 믿어도 된다. 내 validator 가 정직한 한, 상대가 나를 끼운 invalid 거래를 확정시킬 수 없다.
  • synchronizer — 거래 내용을 못 읽고·위조 못하고·invalid 를 승인 못한다. 다만 메시지를 지연시킬 수는 있어 가용성은 신뢰 대상이다 — BFT(2/3 정직) 또는 multi-synchronizer 로 완화.

즉 직접 구현은 validator 신뢰를 없애 통제권을 최대화하고, 운영형은 그 신뢰를 운영사에 맡기되 external party·키 분리로 자금 권한은 지킨다. 어느 쪽이든 synchronizer 신뢰는 남는다.

5.3 복구가 직접 운영의 가장 무거운 책임

Canton 의 복구는 EVM 의 "노드 재동기화" 와 차원이 다르다. 1장에서 봤듯 상태가 글로벌 잔액이 아니라 party 의 ACS라, validator 를 잃으면 그 ACS 를 새 validator 로 옮겨 re-host 해야 한다.

공식 문서는 장애 정도에 따라 세 가지 복구 경로를 둔다.

장애 정도복구 방법
단일 노드 장애DB 백업에서 복원 → 컴포넌트 0으로 줄였다 복원 후 1로 → 백업 이후 추가된 사용자만 재온보딩
광범위 장애identities 백업으로 원래 namespace 키를 통제하는 새 validator 배포 → Canton Coin 잔액·CNS 복구 (party id hint 보존, participant id 는 새 것)
Synchronizer 장애roll-forward 논리적 synchronizer 업그레이드(perform_manual_lsu())

복구가 가능하려면 최소 하나는 있어야 한다 — 최근 DB 백업(30일 이내) 또는 현재 identities 백업 또는 validator 키를 보유한 외부 KMS. 아래 그림은 자산을 키·ACS 로부터 되살리는 경로(특히 external party)를 요약한 것이다.

external party 는 복구 경로가 다르다

키를 우리가 쥐는 external party(2장)는 기본 복구에 자동 포함되지 않는다 — 별도 절차가 필요하다. 완전히 새 validator(깨끗한 identity·DB)를 배포하고, topology 트랜잭션을 만들어 외부 서명으로 party 를 host 한 뒤, CC Scan endpoint 에서 ACS 를 import 하고 표준 API 로 onboarding 을 마친다. 수탁 지갑은 거의 external party 이므로, 이 별도 경로가 사실상 우리의 주 복구 시나리오가 된다.

복구 후 사후 처리를 잊지 말 것
  • pre-approval 재설정 — Canton Coin 의 1-step 경험을 주던 transfer pre-approval(3. 자산 동작)은 복구 후 기존 것을 취소하고 새로 만들어야 한다.
  • contract id 변경 — 마이그레이션 후 contract id 가 바뀐다. 인덱서·지갑 백엔드가 들고 있던 contract id 참조를 새 값으로 갱신해야 한다.
  • 토큰은 별도 — 이 절차는 Canton Coin 복구다. USDCx 같은 native token 은 해당 Token Registrar(예: Circle)와의 협조가 추가로 필요하다(1. 원장 모델).

5.4 어느 쪽을 택할까 — trade-off

기준직접 구현이 유리운영형이 유리
통제권노드·버전·복구를 직접 통제해야 할 때운영 부담을 줄이고 빠르게 붙고 싶을 때
운영 역량participant 운영·Canton 프로토콜 추적 인력이 있을 때그 역량을 내재화하기 전 단계
복구 책임복구 절차(5.3)를 직접 책임질 준비가 됐을 때복구를 운영사와 분담하고 싶을 때
규제·망분리노드를 우리 통제 경계(IDC·망분리) 안에 둬야 할 때운영사 환경이 규제 요건을 충족할 때
비용 구조규모가 커서 자체 운영이 단가에서 유리할 때초기·중간 규모에서 위탁이 저렴할 때
설계 포인트 — 어느 쪽이든 어댑터 경계는 유지
  • 키 통제는 분리해서 보유 — 운영형이라도 party 키·서명 권한은 우리가 통제하는 구성을 권한다. validator 운영과 키 통제를 같은 곳에 두면 복구·감사에서 위험이 커진다.
  • 어댑터는 Ledger API 경계로 — 직접/운영형 전환이 어댑터 안쪽 한 겹(노드 접근)만 바뀌도록 설계하면, 운영형으로 시작해 직접 운영으로 옮기는 경로가 열린다(또는 반대).
  • 복구 리허설 — 직접 운영을 택하면 5.3 절차를 실제로 리허설해 두어야 한다. ACS import·키 재구성은 사고 당일 처음 해보면 늦는다.
  • party 를 여러 validator 에 multi-host — 공식 가이드는 백업·이중화를 위해 같은 party 를 둘 이상의 validator participant 에 host 하라고 권한다. 한 노드를 잃어도 다른 노드가 같은 party 를 계속 서비스해, 5.3 의 전면 복구로 가기 전 1차 방어선이 된다.
  • 4 환경 운영 — LocalNet(로컬 개발) · DevNet · TestNet · MainNet 을 함께 두고, 프로토콜 업그레이드를 운영(MainNet)에 올리기 전 하위 환경에서 검증한다. DevNet 접속 시크릿은 API 로 받아 약 1시간 유효하고, TestNet·MainNet 은 sponsor 가 수동으로 내준다.
  • 운영 SLA 기준 — 공식 validator 운영 기준은 99%+ 가용성, 보안 패치 1주 이내·마이너 업데이트 2주 이내 적용, DB·identity 정기 백업, party 키 보관·교체다. 직접 운영을 택하면 이 수준을 우리가 맞춰야 한다(운영형이면 운영사 몫).
  • 백업 순서·복제 — DB(키 포함)를 백업할 때 mediator·participant 를 synchronizer 보다 먼저 떠야 한다(반대면 재연결이 막히는 ForkHappened). 운영에선 동기식(synchronous) 복제를 권장해 장애 전환 시 무손실을 보장한다. 복구 직후엔 명령 멱등(dedup)이 일시적으로 불완전하고 동기화 연결·사용자·party 설정이 백업 시점으로 되돌아가니 수동 재적용이 필요하다.
  • 운영은 Canton Console 로 — 5.3 의 복구·repair 같은 작업은 participant/sequencer/mediator 프로세스에 직접 붙는 운영자 CLI(Canton Console)에서 실행한다. 이는 앱이 쓰는 런타임 Ledger API 와는 별개의 관리 도구다.
  • SaaS 도 같은 그림 — Fireblocks 처럼 Canton 을 지원하는 SaaS 를 쓰면 "운영형" 의 극단으로, 노드·복구 상당 부분을 벤더가 처리한다. 단 상태 매핑·timeout 등 적용 세부는 확인 필요(3. 자산 동작).
