6. 수탁 통합 — wallet/guidance

공식 지갑 통합 가이드의 수탁 요건을 한 데 모은 체크리스트 — 앞 장들의 핵심을 연결한다

이 장은 Canton 공식 문서의 지갑 통합 가이드(integrations/wallet/guidance)를 수탁 관점에서 정리한 것이다. 앞의 1~5장이 "Canton 이 EVM 과 왜 다른가" 를 설명했다면, 이 장은 그 차이가 수탁 지갑 구현에서 실제로 어떤 결정을 강제하는가를 한눈에 모은다. 각 항목의 깊은 설명은 해당 장으로 링크한다.

EVM 수탁 경험에서 가장 크게 바뀌는 세 가지
  • 입금주소가 없다 — 사용자별 입금주소 대신 memo 태그로 입금자를 구분한다(6.1).
  • party 를 남발하지 않는다 — 입금/사용자마다 주소를 찍던 습관 대신 계정당 party 하나를 고정한다(6.2).
  • 제출이 완료가 아니다 — 2-step 전송이라 입금은 "TransferIn" + 수락까지 봐야 확정이다(6.4).

6.1 입금 식별 — memo tag (별도 입금주소 없음)

EVM·비트코인 수탁 지갑은 사용자마다 입금주소를 발급해 "어느 주소로 들어왔나" 로 입금자를 구분한다. Canton 은 이 방식을 쓰지 않는다. 공식 가이드는 별도 입금주소 없이 전송 metadata 의 memo 태그로 입금을 추적하라고 안내한다(거래소 입금도 동일).

"meta": { "values": { "splice.lfdecentralizedtrust.org/reason": "memo-ref" } }

리플(XRP)·스텔라(XLM)의 destination tag 와 같은 발상이다. 따라서 수탁 백엔드는 "입금주소 → 사용자" 가 아니라 "memo-ref → 사용자" 매핑으로 입금을 귀속시킨다. 인덱서가 이 memo 를 읽어 사용자에 연결하는 방식은 4. 인덱서에서 다룬다.

6.2 party 운용 — 계정당 하나, 임시 발급 금지

party allocation 에는 비용이 따른다. 그래서 공식 권고는 "계정/지갑당 party 하나(one Party per account/wallet)" 를 안정적으로 두는 것이다.

  • 입금 건마다 임시 party 를 만들지 말 것 — 입금자 구분은 party 가 아니라 memo 태그로 한다(6.1).
  • PartyId 형식 = name::fingerprint, 최대 185자. allocation 으로만 생성하고 파싱하지 않는다(2. Validator).
  • multi-host — 백업·이중화를 위해 같은 party 를 여러 validator 에 host 한다. 노드 하나를 잃어도 다른 노드가 계속 서비스한다(5. 운영).
  • external party 로 — 키를 우리가 쥐는 external party 가 수탁의 기본형이다. participant 는 우리 서명 없이는 원장에서 움직일 수 없다(2. Validator).

6.3 전송·서명 — prepare → sign → execute

출금(전송)은 준비·서명·실행 세 단계로 일어난다 — external party 의 외부 서명 모델(2. Validator)이 그대로 API 에 드러난다.

6.4 입금 관찰 — "TransferIn" + 수락까지

입금은 "TransferIn" 이벤트로 감시한다. 단 2-step 이라 들어오는 전송은 먼저 대기(Pending)로 보이고, 우리가(또는 pre-approval 이) 수락(Accept)해야 실제 holding 이 생긴다.

  • pre-approval 켜짐 — 들어오는 전송이 자동 수락돼 바로 holding 으로 들어온다.
  • pre-approval 꺼짐(기본) — 전송 instruction 의 pending/completed 상태를 보고, 수동으로 TransferInstruction_Accept(수령) 또는 TransferInstruction_Reject(반환)한다.
  • "전송이 보였다 ≠ 입금 확정" — 확정은 수락 후 holding 이 생긴 시점이다. 상세 상태 추적은 4. 인덱서.

6.5 운영 · 대사

  • 진행 위치 = offset, 대사 = recordTime. 우리 인덱스 진행은 /v2/state/ledger-end 의 offset 으로 잡지만, 외부 파트너와의 대사는 synchronizer 가 매기는 recordTime 으로 맞춘다 — offset 은 우리 노드 로컬 값이라 상대와 공유되지 않는다.
  • UTXO 조각 관리. holding 조각은 보관·연산 비용이 있어 사용자당 약 10개 수준으로 병합(merge)한다. 큰 출금은 여러 조각을 모으고, 거스름 조각을 최소화한다(1. 원장 모델).
  • 4 환경 운영. LocalNet · DevNet · TestNet · MainNet 을 함께 운영해, 업그레이드를 운영에 올리기 전 하위 환경에서 검증한다(DevNet 시크릿은 API·1시간, TestNet/MainNet 은 sponsor 제공). 운영 SLA·복구는 5. 운영.
  • registry 조회. 자산 발행자 정보·instrument·transfer factory 는 registry 엔드포인트(/registry/metadata/v1/info·/instruments·/registry/transfer-instruction/v1/transfer-factory)로 얻는다.
  • 확정 시간. 보통 3-10초(2. Validator). 멱등 재시도는 submission ID 로 중복 제거한다.
