6. 수탁 통합 — wallet/guidance

공식 지갑 통합 가이드의 수탁 요건을 한 데 모은 체크리스트 — 앞 장들의 핵심을 연결한다

이 장은 Canton 공식 문서의 지갑 통합 가이드(integrations/wallet/guidance)를 수탁 관점에서 정리한 것이다. 앞의 1~5장이 "Canton 이 EVM 과 왜 다른가" 를 설명했다면, 이 장은 그 차이가 수탁 지갑 구현에서 실제로 어떤 결정을 강제하는가를 한눈에 모은다. 각 항목의 깊은 설명은 해당 장으로 링크한다.

EVM 수탁 경험에서 가장 크게 바뀌는 세 가지
  • 입금주소가 없다 — 사용자별 입금주소 대신 memo 태그로 입금자를 구분한다(6.1).
  • party 를 남발하지 않는다 — 입금/사용자마다 주소를 찍던 습관 대신 계정당 party 하나를 고정한다(6.2).
  • 제출이 완료가 아니다 — 2-step 전송이라 입금은 "TransferIn" + 수락까지 봐야 확정이다(6.4).

6.1 입금 식별 — memo tag (별도 입금주소 없음)

EVM·비트코인 수탁 지갑은 사용자마다 입금주소를 발급해 "어느 주소로 들어왔나" 로 입금자를 구분한다. Canton 은 이 방식을 쓰지 않는다. 공식 가이드는 별도 입금주소 없이 전송 metadata 의 memo 태그로 입금을 추적하라고 안내한다(거래소 입금도 동일).

"meta": { "values": { "splice.lfdecentralizedtrust.org/reason": "memo-ref" } }

리플(XRP)·스텔라(XLM)의 destination tag 와 같은 발상이다. 따라서 수탁 백엔드는 "입금주소 → 사용자" 가 아니라 "memo-ref → 사용자" 매핑으로 입금을 귀속시킨다. 인덱서가 이 memo 를 읽어 사용자에 연결하는 방식은 4. 인덱서에서 다룬다.

6.2 party 운용 — 계정당 하나, 임시 발급 금지

party allocation 에는 비용이 따른다. 그래서 공식 권고는 "계정/지갑당 party 하나(one Party per account/wallet)" 를 안정적으로 두는 것이다.

  • 입금 건마다 임시 party 를 만들지 말 것 — 입금자 구분은 party 가 아니라 memo 태그로 한다(6.1).
  • PartyId 형식 = name::fingerprint, 최대 185자. allocation 으로만 생성하고 파싱하지 않는다(2. Validator).
  • multi-host — 백업·이중화를 위해 같은 party 를 여러 validator 에 host 한다. 노드 하나를 잃어도 다른 노드가 계속 서비스한다(5. 운영).
  • external party 로 — 키를 우리가 쥐는 external party 가 수탁의 기본형이다. participant 는 우리 서명 없이는 원장에서 움직일 수 없다(2. Validator).
  • 이름 표시(CNS) — PartyId 는 사람이 못 읽으니, Canton Name Service(alice.unverified.cns 식, DNS/ENS 류)로 읽을 수 있는 이름을 매핑해 UI 에 표시하거나 이름으로 송금할 수 있다(등록 시 CC 결제·소각). 내부 귀속 키는 여전히 PartyId·memo 다.
MPC/HSM 키로 party 만드는 절차 (external party 온보딩)

키를 custody(HSM·MPC) 안에 둔 채로 party 를 만드는 흐름은 명확하다 — 키가 custody 밖으로 나오지 않는다.

  1. custody 에서 키 생성, 공개키만 추출(DER→base64).
  2. /v2/parties/external/generate-topology 호출(synchronizer·이름 hint·공개키) → PartyToParticipant topology 와 서명할 multi-hash 를 돌려받음.
  3. 그 hash 를 custody 키로 서명(MPC/HSM 내부).
  4. /v2/parties/external/allocate 에 topology + 서명 제출 → party 등록 완료.

다중 host 로 두려면 otherConfirmingParticipantUids 에 참여 participant 를 추가하고 같은 온보딩 트랜잭션을 각 participant 에 올린다.

MPC·HSM 은 어떻게 붙나 — 서명 프로바이더

"②번 서명" 을 어디서 하느냐가 custody 전략이다. Canton 의 Wallet Gateway 는 서명을 외부 프로바이더에 위임할 수 있고, 공식 지원 목록에 우리에게 익숙한 이름들이 있다:

  • Fireblocks — HSM 기반 엔터프라이즈 키관리·서명(API 키·환경변수 구성).
  • Dfns — MPC 기반, 정책 제어·다자 승인 워크플로. validator 통합으로 wallet 생성·broadcast 까지.
  • Blockdaemon — 관리형 인프라 서명.
  • participant 기반(노드가 키 보관) · internal(개발용 DB 보관).

party 별로 프로바이더를 섞을 수 있어, 일부 계정은 Fireblocks(HSM), 일부는 Dfns(MPC) 식의 혼합 custody 가 한 게이트웨이에서 가능하다. 우리 수탁 스택이 이미 Fireblocks·MPC 라면 그대로 Canton 서명에 연결된다. 이 프로바이더들은 추상 개념이 아니라 공식 Canton Wallet SDK(canton-network/wallet, TypeScript)의 core-signing-* 드라이버로 제공된다 — internal(Ed25519)·participant·fireblocks·blockdaemon·dfns 5종(공통 SigningDriverInterface 구현).

Fireblocks 로 Canton 수탁 — 우리 주력 경로

우리 수탁 스택이 Fireblocks 라면 Canton 도 같은 방식으로 붙는다 — 키는 Fireblocks(MPC/HSM)에 남고, Canton external party 거래를 Fireblocks Raw Signing(EdDSA·Ed25519) 으로 서명한다(공식 Canton Coin 복구 절차가 이 EdDSA Raw Signing 을 쓴다). 흐름은 6.3 그대로: participant 가 prepare 로 해시를 만들면 → Fireblocks 가 서명 → execute. participant 는 우리(Fireblocks) 서명 없이 원장에서 움직일 수 없다. 공식 드라이버(core-signing-fireblocks) 코드 기준, EdDSA Ed25519 키로 Fireblocks Raw Signing(createTransaction operation RAW)을 써서 prepared tx 의 hash 를 서명하고, party 공개키는 getPublicKeyInfo(EddsaEd25519) 로 가져온다.

  • 2-step 매핑 — Fireblocks 는 Canton 2-step 을 generic status 로 뭉개지 않고 전용 transactionType 필드(OFFER·ACCEPT·REJECT·WITHDRAW·PRE_APPROVAL)로 그대로 노출하고, traceableId·CantonHashes(offerUpdateId 로 OFFER↔후속 연결)로 lifecycle 을 추적한다. 출금 상태머신은 OFFER=수락 대기로 두고 ACCEPT/REJECT/WITHDRAW 로 전이한다. timeout 은 수락 안 되면 송신자가 WITHDRAW(언제 할지는 앱 정책 — Fireblocks 강제 아님).
  • 복구·사후처리 — Fireblocks 는 Canton Coin 복구를 문서화한다(topology tx 외부 서명 → ACS import, 5. 운영의 복구). 복구 후 pre-approval 재설정·contract id 갱신이 필요하고, 토큰(USDCx 등)은 Circle 같은 Registrar 와 별도 절차다.
  • 연동 — 공식 Canton Wallet SDK(TypeScript)의 core-signing-fireblocks 드라이버(SigningDriverInterface 구현)로 붙는다. Fireblocks API 인증은 RSA-4096 키(FIREBLOCKS_SECRET)·API User(CSR)·API Key 구성(이 RSA 는 API 인증용 — 온원장 서명 알고리즘과 별개 층). (canton-network/wallet)
공식 SDK 가 주는 것 — 직접 안 만들어도 되는 부품

위 내용을 처음부터 짤 필요는 없다. Canton Wallet SDK(@canton-network/wallet-sdk, NodeJS)와 core 모듈이 수탁 통합의 기본 부품을 제공한다:

  • 읽기·조립: acs-reader(ACS/잔액) · ledger-client(Ledger API) · token-standard · tx-parser·tx-visualizer(거래 해석)
  • 서명: signing-lib + 드라이버 5종(internal·participant·fireblocks·blockdaemon·dfns) · signing-store-sql
  • 저장·인증: wallet-store(inmemory/sql) · wallet-auth
  • Wallet Gateway(서버) — RPC 서버(기본 :3030, /api/v0/dapp·/api/v0/user). 서명을 드라이버(Fireblocks·Dfns)로 라우팅하고, wallet store 와 서명 자격증명 store 를 분리(Postgres) 보관, Canton·CantonTestnet 관리.

즉 Fireblocks 키만 우리가 쥐고, ACS 읽기·Ledger 제출·서명 라우팅·저장은 SDK/Gateway 부품으로 조립할 수 있다.

전송에 "안 보이는 contract" 가 필요할 때 — disclosed contracts

토큰 전송은 발행자/레지스트리의 transfer factory contract 를 참조하는데, 그 contract 는 우리가 stakeholder 가 아니라 우리 노드에서 안 보일 수 있다. 이때 prepare 호출에 disclosed_contracts(template_id·contract_id·created_event_blob)를 함께 넘기면, 보이지 않는 contract 라도 거래에 쓸 수 있다(레지스트리가 off-ledger 로 그 blob 을 제공). contract-id 가 해시 기반이라 위변조하면 id 가 달라져 자동 탐지된다. 6.3 의 prepare 단계에서 "disclosed contracts" 를 넘기는 게 바로 이것이다.

전체 호출 순서를 한 그림으로 보면 다음과 같다 — 사전 준비(party 온보딩)는 한 번, 전송은 매번 반복된다.

blind signing 과 fund-drain — 무엇이 막히고, 무엇이 우리 몫인가

Raw Signing 은 거래 내용을 사람이 읽는 형태로 보여주지 않고 해시 한 덩어리에 서명한다(이를 blind signing 이라 한다). 위험 시나리오는 이렇다 — prepare 를 부르는 경로가 조작돼 "A 에게 100" 대신 "잔액 전부를 공격자에게" 라는 거래의 해시가 Fireblocks 로 넘어가면, Fireblocks 는 의미를 모른 채 서명한다. 그러면 자금이 통째로 빠져나간다(이런 거래를 fund-drain, 자금 탈취 거래라 한다).

Canton 이 구조적으로 막아주는 것 — Canton 의 잔액(holding)은 소유자만 서명권을 갖고, 이더리움식 "사용 권한 위임"(한 번 허가해 두면 상대가 알아서 빼가는 방식)이 아예 없다. 따라서 "무제한 인출 권한을 한 번 서명시켜 두고 나중에 빼가는" 가장 흔한 탈취 수법은 Canton 에선 성립하지 않는다.

우리가 막아야 하는 것 — 그리고 단일 백엔드의 한계 — 남는 위험은 위 시나리오 같은 "직접 전송형" 탈취다. Figure 6-2 의 노랑 박스(서명 전 디코딩 검증)가 1차 방어지만, 그 검증이 주문 백엔드와 같은 곳에 있으면 백엔드가 탈취된 순간 함께 무력화된다 — 공격자가 검증을 건너뛰고 악성 해시를 바로 서명에 넘기면 그만이기 때문이다. 따라서 검증 한 단계로는 부족하고, 신뢰를 여러 곳에 분산해야 한다:

다중 서명 (여러 키로 나눠 서명)
Canton 은 한 party 에 여러 서명키와 임계값(예: 5개 키 중 3개가 서명해야 유효)을 둘 수 있다. 백엔드 하나가 털려도 단독으로는 유효 서명을 만들 수 없다 — 단일 백엔드 탈취에 대한 구조적 방어다.
독립된 승인 평면
검증·승인을 주문 백엔드와 다른 신뢰 영역에 둔다(예: 별도 기기에서의 모바일 승인). 단 Raw Signing 은 승인자에게 보이는 정보가 제한적이라, 이 방어만으로는 약하다.
해시 독립 재계산
Canton 의 서명 대상 해시는 결정적이라, 별도 검증자가 독립적으로 받은 주문으로 해시를 다시 계산해 대조할 수 있다. 위 두 가지와 결합할 때 의미가 있다.

정직한 경계 — 단일 백엔드 + Raw Signing 만으로는, 그 백엔드가 "무엇에 서명할지" 의 단일 신뢰점이 된다. 수탁급 안전을 위해서는 다중 서명·독립 승인이 사실상 필수다(디코딩 검증 한 단계 추가로는 부족하다).

6.4 입금 관찰 — "TransferIn" + 수락까지

입금은 "TransferIn" 이벤트로 감시한다. 단 2-step 이라 들어오는 전송은 먼저 대기(Pending)로 보이고, 우리가(또는 pre-approval 이) 수락(Accept)해야 실제 holding 이 생긴다.

  • pre-approval 켜짐 — 들어오는 전송이 자동 수락돼 바로 holding 으로 들어온다.
  • pre-approval 꺼짐(기본) — 전송 instruction 의 pending/completed 상태를 보고, 수동으로 TransferInstruction_Accept(수령) 또는 TransferInstruction_Reject(반환)한다.
  • "전송이 보였다 ≠ 입금 확정" — 확정은 수락 후 holding 이 생긴 시점이다. 상세 상태 추적은 4. 인덱서.
  • 위탁(Fireblocks) 경로 — Fireblocks 수탁이면 이 관찰을 Fireblocks 가 대신해 transactionType webhook(OFFER/ACCEPT/…)으로 통지받을 수 있다. 자체 participant 의 Ledger API "TransferIn" 을 직접 구독하는 건 직접 운영 경로다 — 어느 쪽인지는 통합 방식에 따라 갈린다(5. 운영).

6.5 운영 · 대사

  • 진행 위치 = offset, 대사 = recordTime. 우리 인덱스 진행은 /v2/state/ledger-end 의 offset 으로 잡지만, 외부 파트너와의 대사는 synchronizer 가 매기는 recordTime 으로 맞춘다 — offset 은 우리 노드 로컬 값이라 상대와 공유되지 않는다.
  • UTXO 조각 관리. holding 조각은 보관·연산 비용이 있어 사용자당 약 10개 수준으로 병합(merge)한다. 큰 출금은 여러 조각을 모으고, 거스름 조각을 최소화한다(1. 원장 모델).
  • 4 환경 운영. LocalNet · DevNet · TestNet · MainNet 을 함께 운영해, 업그레이드를 운영에 올리기 전 하위 환경에서 검증한다(DevNet 시크릿은 API·1시간, TestNet/MainNet 은 sponsor 제공). 운영 SLA·복구는 5. 운영.
  • registry 조회. 자산 발행자 정보·instrument·transfer factory 는 registry 엔드포인트(/registry/metadata/v1/info·/instruments·/registry/transfer-instruction/v1/transfer-factory)로 얻는다.
  • 확정 시간. 보통 3-10초(2. Validator).
  • 멱등 재시도. 중복 제거 기준은 command ID(=change ID; 같은 작업의 재시도엔 동일 값을 유지)이고, submission ID 는 시도마다 새 값(UUID)을 쓴다. 중복 제거 기간은 처리시간 상한 B 로 명시하는 게 안전하다.

6.6 전송 증명 · 원장 pruning · 거래소 변형

원장은 pruning 된다 — 증빙을 우리 DB 에 보관해야 한다

EVM 은 과거 트랜잭션을 언제든 체인에서 다시 조회할 수 있다고 가정하지만, Canton 원장은 pruning(과거 데이터 정리)된다. 공식 가이드는 전송 증명을 위해 Transfer Object 와 UpdateID(원장 거래 고유 id)를 지갑 백엔드 DB 에 직접 영속화하라고 못 박는다 — pruning 이후엔 원장 과거 조회가 실패하기 때문이다. 감사·대사·분쟁 대응을 원장에만 의존하면 안 되고, 우리 DB 가 1차 증빙 보관처여야 한다.

증명 조회: GET /v2/updates/update-by-id(완료 전송), 거절·철회는 /v2/events/events-by-contract-id. 이 값을 받아 두는 게 핵심이다.

보조 장치도 있다 — 노드는 PQS(Participant Query Store) 라는 distilled 장기 보관소를 둘 수 있고, participant 들은 ACS commitment(보유 contract 의 암호 서명 요약)를 상대 participant 와 주기적으로 교환해 "서로 같은 상태를 본다" 를 증명·정합(fork 탐지)한다. 단 이들은 현재 상태 증명이지 과거 전체 이력이 아니므로, 감사·분쟁용 이력은 여전히 우리 DB 에 남겨야 한다.

거래소(omnibus) 는 패턴이 다르다 — 단일 treasuryParty

지금까지는 "계정당 party 하나"(6.2) 를 전제했지만, 거래소형은 보통 단일 treasuryParty 가 입금 수령·자금 통제·출금 집행을 모두 맡는 omnibus 구조다. 입금자 구분은 여전히 memo 태그(6.1)로 한다. 출금 시에는 입력 holding 을 골라 target recordTime 까지 잠그는데, 공식 가이드는 한 전송에 UTXO 100개 미만으로 제한하고, 동시 출금 k건을 위해 큰 금액 UTXO k개 풀을 유지하라고 권한다(거래 이력은 /v2/updates/flats, 출금은 TransferFactory_Transfer choice). 은행 수탁이 계정 분리형이라면 6.2 를, 거래소형이라면 이 omnibus 를 택한다.
