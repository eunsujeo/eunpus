DB 상태 변화 — row 단위로 따라가기

앞 페이지의 다이어그램이 "흐름"이라면, 이 페이지는 실제 테이블 row 가 단계마다 어떻게 바뀌는지 보여줍니다

네 개의 테이블이 움직입니다 — 고객 원장(customer_ledger) · 델타 원장(delta_ledger) · 은행 원장(bank_ledger) · 총계정 원장(general_ledger_entry). 컬럼명은 회계·원장 설계의 스키마를 따릅니다.

테이블별 쓰기 규율 — 먼저 알아둘 것
테이블쓰기 방식이유
customer_ledger (고객 원장)UPDATE (잔액)현재 잔액 캐시
delta_ledger (델타 원장)INSERT + status UPDATE미정산 추적·마감
bank_ledger (은행 원장)UPDATE지갑 자산 캐시
general_ledger_entry (총계정)append-only (INSERT만)회계 증적 불변 · 감사

즉 총계정 원장은 한 번 적은 row 를 절대 고치지 않습니다 — 정정도 새 row 로. 계정 잔액은 "차변 합 − 대변 합"으로 계산합니다.

① 온램프 — 가장 단순한 형태 (KRW 1,000 → KRWK 1,000, 1:1)

사용자 X 가 KRWK 0 에서 시작해 1,000 을 충전합니다. 네 테이블을 처음 / 1단계 후 / 2단계 후 세 시점으로 추적합니다.

customer_ledger — pending 으로 잡았다가 confirmed 로

시점confirmedpending_inpending_out
처음000
1단계 후01,0000
2단계 후1,00000

1단계엔 "처리중(pending_in)"으로만 올리고, 코인이 실제 도착한 2단계에 pending_in → confirmed 전환.

delta_ledger — INSERT 후 status 만 닫힘

시점row (delta_type · asset · amount · status)
처음(없음)
1단계 후d1 · ONRAMP · KRWK · −1,000 · pending ← 곧 올, 아직 없는 코인
2단계 후d1 · ONRAMP · KRWK · −1,000 · settled ← amount 그대로, status 만 닫힘

오래 pending 이면 정산이 막힌 신호 — 대사 L3 가 이 status 를 감시한다(4장).

bank_ledger — 지갑 실제 자산, 2단계에만 변함

시점VAULT.KRWK 잔액
처음V₀
1단계 후V₀ (변동 없음 — 지갑 안 움직임)
2단계 후V₀ + 1,000 (발행사가 실제 발행·도착)

general_ledger_entry — append-only, row 가 쌓이기만

단계INSERT 되는 row (account_code · 차/대 · amount)
1단계e1 · KRWK 미정산자산 · 차 · 1,000
e2 · KRWK 반환채무 · 대 · 1,000
2단계e3 · KRWK 지갑자산 · 차 · 1,000
e4 · KRWK 미정산자산 · 대 · 1,000 ← 미정산 계정 닫음

4개 row 가 누적(수정·삭제 없음). 같은 거래는 source_ref(예: req#123)로 묶인다.

이 row 들로 항등식이 어떻게 유지되나

차변 합 − 대변 합으로 계정 잔액을 계산하면:

계정1단계 후2단계 후
KRWK 미정산자산 (자산)+1,0000 (e1 +1,000, e4 −1,000 = 닫힘)
KRWK 지갑자산 (자산)0+1,000
KRWK 반환채무 (부채)+1,000+1,000
항등식 (자산 = 부채)1,000 = 1,000 ✓1,000 = 1,000 ✓

1단계엔 미정산자산이 자산 자리를 채워 균형, 2단계엔 그게 지갑자산으로 교체되며 균형. 두 시점 모두 안 깨진다 — 이것이 "미정산 분개 — 항등식 임시 균형"의 실제 모습이다.

② 스왑 — 델타 2줄, 총계정 4줄 (KRWK 1,300 → USDC 1)

스왑은 한쪽이 빠지고 다른 쪽이 들어오므로 미정산이 양쪽에 생깁니다. 온램프와 달라지는 두 테이블만 봅니다.

delta_ledger — 1단계에 2줄 INSERT

시점row
1단계 후d1 · SWAP_OUT · KRWK · +1,300 · pending
d2 · SWAP_IN · USDC · −1 · pending
2단계 후d1 · settled · / · d2 · settled

customer_ledger — KRWK 잠금 + USDC 처리중

시점KRWK (conf · in · out)USDC (conf · in · out)
처음1,300 · 0 · 00 · 0 · 0
1단계 후0 · 0 · 1,3000 · 1 · 0
2단계 후0 · 0 · 01 · 0 · 0

총계정도 4줄(고객측 2줄 + 미정산 2줄)이 1단계에 들어가고, 2단계에 미정산 2줄을 닫으며 지갑자산 KRWK↓·USDC↑ 로 정산. 매매 스프레드가 있으면 손익 row 가 추가된다.

③ 오프램프 — 온램프의 거울상 (KRWK 1,000 → KRW 1,000)

방향만 반대입니다 — 보내는 쪽이라 1단계에 사용가능을 즉시 차감하고(이중사용 방지), 미정산은 "곧 나갈 자산"으로 잡습니다.

general_ledger_entry — 방향이 반대

단계INSERT 되는 row
1단계KRWK 반환채무 · 차 · 1,000 (빚 감소)
KRWK 미정산자산 · 대 · 1,000 (곧 나갈 자산)
2단계KRWK 미정산자산 · 차 · 1,000 (닫음)
KRWK 지갑자산 · 대 · 1,000 (실제 출금)

온램프와 차/대가 반대다 — 충전은 부채↑·자산 도착, 환전은 부채↓·자산 출금. 델타가 메우는 시점차는 동일.

한 줄로

움직이는 row 는 매번 같다 — customer_ledger 잔액(UPDATE) · delta_ledger 미정산(INSERT→status UPDATE) · bank_ledger 지갑(2단계 UPDATE) · general_ledger_entry 분개(append-only INSERT). 거래마다 다른 건 델타가 1줄이냐 2줄이냐, 차/대 방향이 어디냐뿐이다.
