DB 상태 변화 — row 단위로 따라가기

앞 페이지의 다이어그램이 "흐름"이라면, 이 페이지는 실제 테이블 row 가 단계마다 어떻게 바뀌는지 보여줍니다

네 개의 테이블이 움직입니다. 고객 원장(customer_ledger) · 델타 원장(delta_ledger) · 은행 원장(bank_ledger) · 총계정 원장(general_ledger_entry). 컬럼명은 회계·원장 설계의 스키마를 따릅니다.

네 원장이 각각 무엇인가 — row 를 보기 전에

크게 둘로 나뉩니다. 셋은 "지금 잔액이 얼마"를 빠르게 보는 캐시이고, 하나는 "왜 그렇게 됐나"를 영구히 적는 증적입니다. 아래 JSON 은 사용자 u_42 가 KRWK 1,000 을 충전 완료한 시점의 실제 row 한 줄입니다.

앞의 셋은 "지금 상태"를 보여주는 잔액 캐시이고, 총계정 원장은 그 상태가 된 이유를 남기는 불변 기록입니다. 자산 = 부채 + 자기자본 항등식이 성립하는 곳도 총계정 원장입니다. 아래 ①~③에서 이 row 들이 단계마다 어떻게 바뀌는지 따라갑니다.

asset_id 주의 — asset_id 는 토큰만 가리키지 않고 토큰 + 네트워크를 한데 묶은 식별자다. 가령 USDC_ETH 는 이더리움 위의 USDC 다. 같은 토큰이라도 체인이 다르면 asset_id 도 달라진다(USDC_ETH ≠ Polygon USDC). 그래서 JSON 예시도 아래 추적 표의 asset_id 도 모두 실제 형태인 KRWK_ETH·USDC_ETH 로 적는다. (단 회계 계정명 account_code 는 네트워크와 무관한 토큰 단위로 둔다 — 예: KRWK_전송전자산.)

온체인은 옴니버스, 개인 귀속은 DB — 위 u_42 처럼 "누가 얼마"는 customer_ledger(DB)에만 있다. 온체인에는 고객마다의 개인 지갑이 없고, 전 고객 코인이 고객 옴니버스 지갑 1개에 섞여 있다(은행 자산도 별도 옴니버스 1개). 그래서 아래 bank_ledger 표의 "고객 옴니버스"·"은행 옴니버스"는 각각 지갑 1개의 총 잔액이고, 15분 배치의 온체인 전송은 그 두 지갑 사이에서 전 거래를 네팅한 순액으로 오간다 — 단일 거래의 ±1,000 은 그 배치에 더해지는 몫이다.

테이블별 쓰기 규율 — 먼저 알아둘 것
테이블쓰기 방식이유
customer_ledger (고객 원장)UPDATE (잔액)현재 잔액 캐시
delta_ledger (델타 원장)INSERT + status UPDATE미정산 추적·마감
bank_ledger (은행 원장)UPDATE지갑 자산 캐시

즉 총계정 원장은 한 번 적은 row 를 절대 고치지 않습니다. 정정할 때도 새 row 를 하나 더 답니다. 계정 잔액은 "차변 합 − 대변 합"으로 계산합니다.

① 온램프 — 가장 단순한 형태 (KRW 1,000 → KRWK 1,000, 1:1)

사용자 X 가 KRWK 0 에서 시작해 1,000 을 충전합니다. 네 테이블을 처음 / 1단계 후 / 2단계 후 세 시점으로 추적합니다.

customer_ledger — 1단계에 confirmed 즉시 (풀에 코인 있음)

시점asset_idconfirmedpending_inpending_out
처음KRWK_ETH000
1단계 후KRWK_ETH1,00000
2단계 후KRWK_ETH1,00000

사전 민팅 재고 풀에 코인이 이미 있으므로 1단계에 고객 잔액을 바로 confirmed(가용)로 올린다 — pending_in 스테이징 단계를 거치지 않는다. 15분 블록체인 배치(2단계)는 고객 잔액을 더 바꾸지 않고, 온체인 wallet 간 전송(델타 settled)만 처리한다. 이 세 칸은 지갑 매니저의 잔액 조회가 보여주는 가용·대기·잠김과 같은 버킷이다(confirmed=가용, pending_in=대기, pending_out=잠김 — 지갑 매니저 워크스루의 잔액 조회).

delta_ledger — INSERT 후 status 만 닫힘

시점row (delta_type · asset · amount · status)
처음(없음)
1단계 후delta-1 · ONRAMP · KRWK_ETH · −1,000 · pending ← DB 엔 반영, 아직 블록체인 전송 전
2단계 후delta-1 · ONRAMP · KRWK_ETH · −1,000 · settled ← 15분 블록체인 배치가 전송 완료, status 만 닫힘

pending 이 오래 머물면 정산이 막혔다는 신호다. 정산이 제때 닫혔는지 보는 대사 단계가 바로 이 status 를 감시한다(4장).

bank_ledger — 은행 옴니버스·고객 옴니버스 두 지갑, 2단계에만 변함

시점은행 옴니버스 KRWK_ETH고객 옴니버스 KRWK_ETH
처음P₀C₀
1단계 후P₀ (변동 없음 — 아직 블록체인 전송 전)C₀ (변동 없음)
2단계 후P₀ − 1,000C₀ + 1,000

온체인 전송은 15분 블록체인 배치(2단계)에 일어난다 — 은행 옴니버스에서 빠져 고객 옴니버스로 들어간다(은행 −1,000 / 고객 +1,000). 실제로는 그 배치의 전 거래를 네팅한 순액이 한 번 오가고, 이 건의 1,000 은 거기 더해지는 몫이다. 두 옴니버스 지갑의 총량은 불변, 내부 이동일 뿐이라 지갑별 잔액만 바뀐다.

general_ledger_entry — append-only, row 가 쌓이기만

단계INSERT 되는 row (account_code · 차/대 · amount · source_ref)
1단계e1 · KRWK 전송전자산 · 차 · 1,000 · req_123
e2 · KRWK 반환채무 · 대 · 1,000 · req_123
2단계e3 · KRWK 지갑자산 · 차 · 1,000 · req_123
e4 · KRWK 전송전자산 · 대 · 1,000 · req_123 ← 전송전자산 −1,000 (1단계 +1,000 과 상쇄돼 잔액 0)

4개 row 가 누적(수정·삭제 없음). 네 줄 모두 source_ref = req_123 으로 같은 거래임을 표시 — 1·2단계에 걸쳐 들어간 분개를 이 값으로 한데 묶는다.

이 row 들로 항등식이 어떻게 유지되나

차변 합 − 대변 합으로 계정 잔액을 계산하면:

계정1단계 후2단계 후
KRWK 전송전자산 (자산)+1,0000 (e1 +1,000, e4 −1,000 = 닫힘)
KRWK 지갑자산 (자산)0+1,000
KRWK 반환채무 (부채)+1,000+1,000
항등식 (자산 = 부채)1,000 = 1,000 ✓1,000 = 1,000 ✓

1단계에는 전송전자산이 자산 자리를 채워 균형을 맞추고, 2단계에는 그게 지갑자산으로 바뀌며 다시 균형을 맞춥니다. 두 시점 어디서도 균형이 깨지지 않습니다. 전송전자산이 1단계엔 전송 대기로, 2단계엔 실제 wallet 자산으로 바뀌며 균형을 유지합니다.

② 오프램프 — 온램프의 역방향 (KRWK 1,000 → KRW 1,000)

방향만 반대입니다(고객→은행풀). 보내는 쪽이라 이중사용을 막으려고 1단계에 사용가능(confirmed)을 즉시 차감합니다(pending 스테이징 없음). 온체인 wallet 전송은 "DB 엔 반영됐지만 아직 블록체인 전송 전"인 델타 PENDING 으로 잡고, 15분 배치(2단계)에 실제 전송합니다.

delta_ledger — 1줄 INSERT 후 settled

시점row

2단계 후delta-1 · OFFRAMP · KRWK_ETH · +1,000 · settled ← 15분 블록체인 배치가 전송 완료

bank_ledger — 2단계에 고객 옴니버스 → 은행 옴니버스 내부 이동

시점은행 옴니버스 KRWK_ETH고객 옴니버스 KRWK_ETH
처음P₀C₀

온램프와 방향이 반대다 — 2단계에 고객 옴니버스에서 빠져 은행 옴니버스로 돌아간다(고객 −1,000 / 은행 +1,000). 1단계엔 안 바뀌고(델타가 미출금 PENDING 으로 표시) 15분 블록체인 배치가 실제 전송(전 거래 네팅 순액)하는 2단계에 갱신된다. 두 옴니버스 지갑의 총량은 불변·내부 이동일 뿐이라 지갑별 잔액만 바뀐다.

③ 스왑 — 델타 2줄, 총계정 4줄 (KRWK 1,300 → USDC 1)

스왑은 한쪽이 빠지고 다른 쪽이 들어오는 거래라 미정산이 양쪽에 생깁니다. 온램프와 달라지는 테이블 위주로 보겠습니다.
