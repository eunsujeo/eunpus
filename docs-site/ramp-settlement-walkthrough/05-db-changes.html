DB 상태 변화 — row 단위로 따라가기

앞 페이지의 다이어그램이 "흐름"이라면, 이 페이지는 실제 테이블 row 가 단계마다 어떻게 바뀌는지 보여줍니다

네 개의 테이블이 움직입니다. 고객 원장(customer_ledger) · 델타 원장(delta_ledger) · 은행 원장(bank_ledger) · 총계정 원장(general_ledger_entry). 컬럼명은 회계·원장 설계의 스키마를 따릅니다.

네 원장이 각각 무엇인가 — row 를 보기 전에

크게 둘로 나뉩니다. 셋은 "지금 잔액이 얼마"를 빠르게 보는 캐시이고, 하나는 "왜 그렇게 됐나"를 영구히 적는 증적입니다. 아래 JSON 은 사용자 u_42 가 KRWK 1,000 을 충전 완료한 시점의 실제 row 한 줄입니다.

테이블무엇인가 (누구 것 · 비유)row 예시 (JSON)
고객 원장
customer_ledger		고객이 맡긴 잔액. 우리가 갚을 빚(부채). 〈통장 잔액〉
{
  "user_id": "u_42",
  "asset_id": "KRWK_ETH",
  "confirmed": 1000,
  "pending_in": 0,
  "pending_out": 0
}
은행 원장
bank_ledger		은행 자신이 가진 자산(treasury·가스·수수료). 〈회사 금고〉
{
  "account_type": "VAULT",
  "asset_id": "KRWK_ETH",
  "balance": 5000
}
델타 원장
delta_ledger		아직 정산 안 된 미정산 차액. 시점차를 메우는 임시 다리. 〈카드 승인 미정산〉
{
  "delta_id": "delta-1",
  "delta_type": "ONRAMP",
  "asset_id": "KRWK_ETH",
  "amount": -1000,
  "settlement_status": "settled"
}
총계정 원장
general_ledger_entry		모든 거래를 차변=대변으로 적는 이중부기 본체(불변 증적). 〈분개장〉
{
  "entry_id": "e1",
  "account_code": "KRWK_미정산자산",
  "debit_credit": "차",
  "amount": 1000,
  "source_ref": "req_123"
}

앞의 셋은 "지금 상태"를 보여주는 잔액 캐시이고, 총계정 원장은 그 상태가 된 이유를 남기는 불변 기록입니다. 자산 = 부채 + 자기자본 항등식이 성립하는 곳도 총계정 원장입니다. 아래 ①~③에서 이 row 들이 단계마다 어떻게 바뀌는지 따라갑니다.

asset_id 주의 — asset_id 는 토큰만 가리키지 않고 토큰 + 네트워크를 한데 묶은 식별자다. 가령 USDC_ETH 는 이더리움 위의 USDC 다. 같은 토큰이라도 체인이 다르면 asset_id 도 달라진다(USDC_ETH ≠ Polygon USDC). 그래서 위 JSON 예시는 실제 형태인 KRWK_ETH 로 적었다. 다만 아래 단계별 추적 표에서는 값 변화에 집중하려고 접미사를 떼고 KRWK·USDC 로 줄여 쓴다.

테이블별 쓰기 규율 — 먼저 알아둘 것
테이블쓰기 방식이유
customer_ledger (고객 원장)UPDATE (잔액)현재 잔액 캐시
delta_ledger (델타 원장)INSERT + status UPDATE미정산 추적·마감
bank_ledger (은행 원장)UPDATE지갑 자산 캐시
general_ledger_entry (총계정)append-only (INSERT만)회계 증적 불변 · 감사

즉 총계정 원장은 한 번 적은 row 를 절대 고치지 않습니다. 정정할 때도 새 row 를 하나 더 답니다. 계정 잔액은 "차변 합 − 대변 합"으로 계산합니다.

① 온램프 — 가장 단순한 형태 (KRW 1,000 → KRWK 1,000, 1:1)

사용자 X 가 KRWK 0 에서 시작해 1,000 을 충전합니다. 네 테이블을 처음 / 1단계 후 / 2단계 후 세 시점으로 추적합니다.

customer_ledger — pending 으로 잡았다가 confirmed 로

시점asset_idconfirmedpending_inpending_out
처음KRWK000
1단계 후KRWK01,0000
2단계 후KRWK1,00000

1단계에는 "처리중(pending_in)"으로만 올려두고, 코인이 실제로 도착하는 2단계에 pending_in 을 confirmed 로 넘긴다. 이 세 칸은 지갑 매니저의 잔액 조회가 보여주는 가용·대기·잠김과 같은 버킷이다(confirmed=가용, pending_in=대기, pending_out=잠김 — 지갑 매니저 워크스루의 잔액 조회).

delta_ledger — INSERT 후 status 만 닫힘

시점row (delta_type · asset · amount · status)
처음(없음)
1단계 후delta-1 · ONRAMP · KRWK · −1,000 · pending ← 곧 올, 아직 없는 코인
2단계 후delta-1 · ONRAMP · KRWK · −1,000 · settled ← amount 그대로, status 만 닫힘

pending 이 오래 머물면 정산이 막혔다는 신호다. 정산이 제때 닫혔는지 보는 대사 단계가 바로 이 status 를 감시한다(4장).

bank_ledger — 지갑 실제 자산, 2단계에만 변함

시점VAULT.KRWK 잔액
처음V₀
1단계 후V₀ (변동 없음 — 지갑 안 움직임)
2단계 후V₀ + 1,000 (발행사가 실제 발행·도착)

general_ledger_entry — append-only, row 가 쌓이기만

단계INSERT 되는 row (account_code · 차/대 · amount · source_ref)
1단계e1 · KRWK 미정산자산 · 차 · 1,000 · req_123
e2 · KRWK 반환채무 · 대 · 1,000 · req_123
2단계e3 · KRWK 지갑자산 · 차 · 1,000 · req_123
e4 · KRWK 미정산자산 · 대 · 1,000 · req_123 ← 미정산자산 −1,000 (1단계 +1,000 과 상쇄돼 잔액 0)

4개 row 가 누적(수정·삭제 없음). 네 줄 모두 source_ref = req_123 으로 같은 거래임을 표시 — 1·2단계에 걸쳐 들어간 분개를 이 값으로 한데 묶는다.

이 row 들로 항등식이 어떻게 유지되나

차변 합 − 대변 합으로 계정 잔액을 계산하면:

계정1단계 후2단계 후
KRWK 미정산자산 (자산)+1,0000 (e1 +1,000, e4 −1,000 = 닫힘)
KRWK 지갑자산 (자산)0+1,000
KRWK 반환채무 (부채)+1,000+1,000
항등식 (자산 = 부채)1,000 = 1,000 ✓1,000 = 1,000 ✓

1단계에는 미정산자산이 자산 자리를 채워 균형을 맞추고, 2단계에는 그게 지갑자산으로 바뀌며 다시 균형을 맞춥니다. 두 시점 어디서도 균형이 깨지지 않습니다. 이것이 "미정산 분개 — 항등식 임시 균형"의 실제 모습입니다.

② 오프램프 — 온램프의 역방향 (KRWK 1,000 → KRW 1,000)

방향만 반대입니다. 보내는 쪽이라 이중사용을 막으려고 1단계에 사용가능을 즉시 차감하고, 미정산은 "곧 나갈 자산"으로 잡습니다.

customer_ledger — 1단계에 confirmed 즉시 차감

시점asset_idconfirmedpending_inpending_out
처음KRWK1,00000
1단계 후KRWK001,000
2단계 후KRWK000

general_ledger_entry — 방향이 반대

단계INSERT 되는 row
1단계KRWK 반환채무 · 차 · 1,000 (빚 감소)
KRWK 미정산자산 · 대 · 1,000 (곧 나갈 자산)
2단계KRWK 미정산자산 · 차 · 1,000 (미정산자산 +1,000, 1단계분과 상쇄돼 잔액 0)
KRWK 지갑자산 · 대 · 1,000 (실제 출금)

온램프와 차/대가 반대다. 충전은 부채↑·자산 도착이고, 환전은 부채↓·자산 출금이다. 델타가 시점차를 메우는 방식은 양쪽 모두 같다.

③ 스왑 — 델타 2줄, 총계정 4줄 (KRWK 1,300 → USDC 1)

스왑은 한쪽이 빠지고 다른 쪽이 들어오는 거래라 미정산이 양쪽에 생깁니다. 온램프와 달라지는 두 테이블만 보겠습니다.

delta_ledger — 1단계에 2줄 INSERT

시점row
1단계 후delta-1 · SWAP_OUT · KRWK · +1,300 · pending
delta-2 · SWAP_IN · USDC · −1 · pending
2단계 후delta-1 · settled · / · delta-2 · settled

customer_ledger — KRWK 잠금 + USDC 처리중

시점KRWK (conf · in · out)USDC (conf · in · out)
처음1,300 · 0 · 00 · 0 · 0
1단계 후0 · 0 · 1,3000 · 1 · 0
2단계 후0 · 0 · 01 · 0 · 0

총계정도 1단계에 4줄(고객측 2줄 + 미정산 2줄)이 들어가고, 2단계에 미정산 2줄을 닫으면서 지갑자산 KRWK↓·USDC↑ 로 정산된다. 매매 스프레드가 있으면 손익 row 가 하나 더 붙는다.

한 줄로

움직이는 row 는 매번 같다. customer_ledger 잔액(UPDATE) · delta_ledger 미정산(INSERT→status UPDATE) · bank_ledger 지갑(2단계 UPDATE) · general_ledger_entry 분개(append-only INSERT). 거래마다 갈리는 건 델타가 1줄이냐 2줄이냐, 차/대 방향이 어디로 가느냐 정도다.
