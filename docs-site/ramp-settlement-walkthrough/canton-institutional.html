기관간 정산·해외송금(Canton)으로 확장하면 DB 는?

retail 온·오프램프·스왑용으로 설계한 4원장이 Canton 식 기관간 atomic 정산·국경 간 FX 로 가면 어디까지 그대로 쓰고, 무엇만 바꾸면 되는가

왜 이 페이지: 본문(1~6장)의 DB 설계는 retail 충전·환전·스왑을 전제로 합니다. 같은 설계를 Canton 의 기관간 정산(atomic DvP)·국경 간 FX 결제에 쓰면 무엇이 달라지는지를 한 장에 정리합니다. 결론부터: core 골격은 대부분 그대로이고, 바뀌는 건 4가지로 좁혀집니다.

한 줄로

4원장(customer·bank·delta·general) + 이중부기 + delta(transit) + fx 테이블은 custody·네트워크 무관하게 설계됐다. Canton 기관간/cross-border 로 가도 구조 변경은 거의 없고, ① 계정 주체 차원 ② delta 의 lifecycle ③ 컴플라이언스 참조 ④ account_code 확장 — 이 넷만 손대면 된다.

왜 대부분 안 바뀌나

  • 이중부기 총계정은 거래 형태를 가리지 않는다 — 차변=대변만 맞으면 retail 충전이든 기관간 DvP든 같은 방식으로 적힌다.
  • delta = 미정산 transit 계정도 보편이다 — "아직 정산 안 된 차액"은 어떤 정산 모델에도 있다(다만 닫히는 방식이 다르다, 아래 참조).
  • 매니저 경계 명제 그대로 — 네트워크·정산 형태(Canton participant·external signing·atomic DvP)는 블록체인 매니저 층이 흡수하고, 회계 DB 는 그 위에 있다. 매니저를 자체→Canton 으로 바꿔도 회계 스키마는 위층이라 흔들리지 않는다.

핵심 차이 — delta 가 닫히는 방식

가장 크게 바뀌는 건 delta 의 lifecycle입니다. retail 은 "화면 먼저, 정산 나중"이라 낙관적 선반영 + 실패 시 rollback이지만, 기관간 atomic DvP 는 전부 한 번에 확정되거나 전부 무산이라 선반영이 필요 없습니다.

retail (본문) — 낙관적 2-step

sequenceDiagram
    autonumber
    participant Cust as 👤 고객 (앱)
    participant App as 🏢 백엔드
    participant L as 4원장 (CL·DL·GLE)
    participant Set as 정산처 / 체인
    Note over Cust,Set: 고객 앱에서 시작 · 화면 먼저 · 정산 나중 (낙관적)
    Cust->>App: 충전/환전/스왑 요청
    App->>L: 1단계 — 선반영 (confirmed 표시 · delta pending)
    App-->>Cust: "처리중"
    App->>Set: 정산 요청
    Set-->>App: 완료 또는 실패
    alt 성공
        App->>L: 2단계 — delta settled · 실계정 확정
        App-->>Cust: "완료"
    else 실패
        App->>L: rollback — delta cancelled · 선반영 원복(정정 분개)
        App-->>Cust: "실패 · 잔액 원복"
    end

retail 은 고객 앱에서 시작한다. 사용자 UX 때문에 1단계에 미리 반영하고, 실패하면 되돌린다. delta 가 그 시점차와 되돌림의 근거가 된다.

기관간 (Canton) — atomic, 선반영 없음

sequenceDiagram
    autonumber
    participant Ops as 🖥 운영 콘솔 (Initiator·Approver)
    participant App as 🏢 백엔드
    participant L as 4원장 (+counterparty · instruction)
    participant DvP as Canton atomic DvP
    Note over Ops,DvP: 운영 콘솔에서 시작 · dual control · 전부 확정 또는 전부 무산 (원자)
    Ops->>App: 정산 지시 생성 (Initiator)
    App->>L: instruction 기록 (PENDING · 아직 미반영)
    App-->>Ops: instruction id · 상태 PENDING
    Ops->>App: 승인 (Approver · dual control)
    App-->>Ops: 승인 접수
    App->>DvP: ExecuteSettlement (attestation 검증 후에만)
    DvP-->>App: 원자 확정 (N-leg 전부) 또는 전체 실패
    alt 원자 성공
        App->>L: 1회 기록 — N-leg delta 전부 settled · 실계정 확정
        App-->>Ops: SETTLED (대시보드 갱신)
    else 실패 / 만료
        App->>L: instruction FAILED — 기록만 (선반영 없어 원복 불필요)
        App-->>Ops: FAILED / EXPIRED (대시보드 갱신)
    end

기관간은 고객 앱이 아니라 운영 콘솔(대시보드)에서 운영자가 시작하고 Initiator·Approver dual control을 거친다. atomic finality 전엔 미리 반영하지 않으며, N 개 leg 가 한 instruction 으로 묶여 동시에 settled 되거나 동시에 무산되므로 부분 정산도 rollback 도 없다. (Musubi PoC: 콘솔 역할 Initiator/Approver/Observer · 주문 상태 PENDING→QUOTED→EXECUTING→SETTLED · EXECUTING 후 불가역 · attestation 선조건)

확정 vs 가설

  • 확정 (회계 보편) — 이중부기 GL · delta transit · 다중통화 fx 는 이미 일반화돼 있어 구조 변경 불요.
  • 근거 있는 추론 (Musubi PoC 기준 · 2차 출처 · testnet) — atomic DvP · 주문 상태 모델 · attestation 선조건 · delegated custody. ②④의 근거.
  • 순수 설계 가설 — counterparty 차원 추가, 선반영 정책 제거, 네팅용 counterparty_position(기존 customer_position 확장).
아직 모르는 것 (적용 전 확인)

Canton 실제 정산 finality 시점·법적 booking timing·기관 간 네팅 규칙은 확인되지 않았다(Musubi 도 finality 수치를 명시하지 않았고, 문서 간 "≈4초 vs ~15초" 불일치가 기록돼 있다). 위 lifecycle·네팅 판단은 실제 정산망 스킴을 확인한 뒤 확정해야 한다.

추천

core 스키마는 유지하고 딱 3개만 선반영하면 Canton 기관간/cross-border 로 확장됩니다.

  • counterparty_id/party_id 차원 + counterparty master
  • delta 에 settlement_instruction_id (N-leg 원자 묶음)
  • compliance attestation FK (Travel Rule / IVMS 101)

그리고 낙관적 선반영(즉시 confirmed)은 기관간 정산에선 끄는 쪽이 안전합니다 — retail 의 "화면 즉시 반영" UX 동기가 기관간엔 없고, 오히려 atomic finality 후 1회 기록(hard 정산)이 맞기 때문입니다.
