온·오프램프·스왑 정산 워크스루

고객 자산과 은행 자산을 분리해 두고, 그 사이 이동을 DB 엔 즉시 반영하되 실제 블록체인 전송은 15분 배치로 묶는 — 그 PENDING 큐인 델타 원장이 어떻게 도는지 거래 한 건으로 따라갑니다

먼저 한 가지 — "델타 원장"이 무엇인가

출발점은 고객 자산과 은행 자산의 분리(분별관리)입니다. 코인계는 고객 몫(customer_ledger)과 은행 몫(bank_ledger · 재고 풀)을 따로 관리하고, 온체인에서도 분리돼 있습니다 — 고객 자산 옴니버스 지갑 1개와 은행 자산 옴니버스 지갑 1개. 고객마다 개인 지갑이 있는 게 아니라 전 고객 코인이 옴니버스 1개에 섞여 보관되고, "누가 얼마"는 DB(customer_ledger)에만 있습니다. 충전·환전·스왑은 결국 이 고객↔은행 자산 이동입니다 (충전 = 은행 풀→고객, 환전 = 고객→은행 풀, 스왑 = 양방향).

이동이 생기면 DB(고객·은행 자산 테이블)에는 즉시 반영해 고객이 바로 잔액을 보게 합니다. 하지만 실제 블록체인 전송(wallet 간 코인 이동)은 건별로 안 하고 15분마다 배치로 묶어 실행합니다(가스·운영 효율). 델타 원장 = "DB 엔 반영됐지만 아직 블록체인 전송 전"인 이동을 PENDING 으로 쌓아 두는 큐이고, 15분 배치가 on-chain 전송을 끝내면 settled 가 됩니다. (계정계와 무관 — 코인계의 고객·은행 자산만 봅니다.)

그래서 연속 추적이 필수입니다. DB 가 블록체인보다 앞서 가니, 추적을 안 하면 은행 풀에 코인이 부족한데도 온/오프/스왑이 DB 상 계속 승인돼 15분 배치에서 전송이 깨지거나 고객 자산 보전이 무너집니다. 은행 풀 가용 = 실제 잔액 − 미정산(PENDING) 유출을 항상 보고, 거래를 그 가용분 안에서만 허용해야 합니다.

  1. 1온램프 — 법정통화 → 코인 (충전)발행/조달
  2. 2오프램프 — 코인 → 법정통화 (환전)소각/처분
  3. 3스왑 — 코인 ↔ 코인 (KRWK → USDC)델타 2줄
  4. 4실패 되돌리기 — 정산 실패 rollback되돌리기
  5. 5DB 상태 변화 — row 단위로 따라가기테이블
  6. 6대사·결산 — 어긋남을 잡는 4단계 그물정합성

부록 · 정산 흐름과 블록체인 매니저의 경계 — 이 2단계 흐름이 자체/Fireblocks 매니저와 어디서 맞물리는지, 지갑 매니저 워크스루와 겹쳐 본다.

부록 · 기관간 정산·해외송금(Canton)으로 확장하면 DB 는? — 이 4원장 설계가 Canton 식 atomic 정산·국경 간 FX 로 가면 무엇만 바꾸면 되는지.

공통 골격 — 모든 거래가 똑같은 2단계

온램프·오프램프·스왑은 정산 상대(발행사·거래소)만 다를 뿐 흐름은 동일한 2단계입니다. 이 그림이 세 거래 전체의 뼈대이고, 각 페이지는 여기에 살을 붙입니다.

왜 DB 와 블록체인을 나눠서 처리하나

DB 반영은 즉시 가능하지만 블록체인 전송은 느리기 때문입니다. wallet 간 on-chain 전송은 가스·확정 시간이 들어, 거래마다 한 건씩 쏘면 비효율적입니다. 그래서 고객↔은행 자산 이동을 DB(고객·은행 자산 테이블)에는 즉시 반영해 고객에게 바로 보여주고, 실제 코인 전송은 15분마다 묶어서 처리합니다.

카드 결제의 "승인 ↔ 정산"과 비슷합니다. 긁으면 즉시 승인되고(=1단계, DB 즉시) 실제 정산은 나중에 묶여 일어납니다(=2단계, 15분 블록체인 배치). 그 사이 "DB 엔 됐지만 아직 체인 전송 전"인 건을 잡아두는 것이 델타 원장입니다 — 다만 정산 주체가 외부가 아니라 우리 15분 블록체인 배치라는 점이 다릅니다.

Figure 0. 세 거래의 공통 2단계. 노랑 = 1단계(DB 즉시 반영 + 델타 PENDING), 초록 = 2단계(15분 배치로 블록체인 전송 → settled). 고객↔은행 자산 이동은 DB 엔 즉시 적되 체인 전송은 묶어서 처리하고, 1단계의 가용 확인이 풀 부족 초과 거래를 막는다. 온체인 전송은 고객·은행 두 옴니버스 지갑 사이에서, 그 15분 창의 전 거래를 네팅한 순액으로 한 번 오간다 — 개별 거래의 금액은 그 배치에 더해지는 몫이다.

가용 확인 — "풀이 부족한데 거래가 나가는" 일을 막는다

DB 가 블록체인보다 앞서 가기 때문에, 매 거래 전에 은행 풀 가용 = 실제 wallet 잔액 − 아직 정산 안 된 PENDING 유출을 확인하고 가용 ≥ 요청일 때만 승인합니다.

풀 실제 잔액         1,000 KRWK
− 미정산(PENDING) 유출  800 KRWK
= 가용                 200 KRWK
→ 300 KRWK 온램프 요청? 거절 (또는 rebalance 트리거)

이 확인이 없으면 DB 로는 계속 승인돼 15분 배치에서 코인이 모자라 전송이 깨지고, 고객 자산 보전(고객/은행 분리)이 무너집니다. 그래서 델타의 PENDING 합을 늘 빼서 보는 것이 분별관리를 지키는 핵심이고, 오래 안 닫힌 PENDING 은 대사 단계(6장)가 잡습니다.

실무 기본형 — 사전 민팅 재고 풀 (mint/burn 이 느리기 때문)

발행사 mint/burn 은 수 분~수십 분 이상 걸립니다. 그래서 건별로 발행·소각하지 않고, 코인을 미리 대량 민팅해 재고 풀(pool · 은행 자산)로 들고 있다가 거래마다 풀에서 고객에게 넣고 빼기만 합니다. 발행사를 매 건 부르지 않는 게 핵심이고, 고객↔은행 wallet 간 실제 코인 전송은 그대로 15분 배치(델타)로 처리됩니다.

거래풀 동작 (DB 즉시 반영 · 블록체인 전송은 15분 배치 = 델타)
온램프풀에서 고객에게 할당(out) — DB 즉시: customer_ledger 반환채무↑ · bank_ledger 재고↓. 풀→고객 wallet 코인 전송은 15분 배치(델타 PENDING→settled).
오프램프고객 코인을 풀로 회수(in) — DB 즉시: customer_ledger 반환채무↓ · bank_ledger 재고↑. 고객→풀 wallet 전송은 15분 배치(델타).
스왑양쪽 모두 풀 — 회수(in)+할당(out), DB 즉시. wallet 전송은 15분 배치(델타 2줄). 단 두 자산 재고가 다 있어야 하고, 거래 뒤 재고 쏠림으로 FX/재고 위험을 은행이 진다(매매차익·스프레드의 원천 · 실제 FX 는 rebalance 때 정산).

회수한 코인은 다음 거래에 재사용되어 풀이 순환합니다. 느린 발행사 mint/burn 은 풀이 상·하한을 벗어날 때만 묶어서(batch rebalance) 일어납니다 — 아래 1·2·3장의 발행사/Circle/거래소 흐름이 바로 그 rebalance(또는 재고가 비었을 때의 온디맨드) 경로입니다. 평상시 거래는 발행사 없이 풀 할당/회수 + 15분 델타 배치로 끝납니다.

트레이드오프: 즉시성·건별 발행 호출 절감 ↔ 재고에 자본이 묶이고, 풀 상·하한·rebalance·소진 시 fallback(온디맨드)을 관리해야 한다. 스왑은 여기에 두 자산 재고 + 재고 FX 위험이 더해진다. 그리고 DB 가 앞서 가므로 풀 가용(실제 잔액 − 미정산 PENDING)을 연속 추적해 부족분 초과 거래를 막아야 한다(위 델타 콜아웃).

수수료(손익) 두 층: 표의 "손익"은 매매 스프레드만이 아니라 고객에게 받는 고정 수수료(거래소식 선계산 출금/매매 요율)와 실제 실비·조달 비용의 차액도 포함합니다. 고객 과금은 고정 스케줄(비즈니스 정책)이고 네트워크 실비는 변동이라, 그 차액이 수수료수익이나 손실로 떨어집니다. 변동 실비 추정 자체는 매니저 층의 일입니다(→ 지갑 매니저 워크스루의 수수료 견적).

기억할 두 규칙

DB 는 즉시, 블록체인은 15분 배치. 고객↔은행 자산 이동은 customer_ledger·bank_ledger 에 즉시 반영해 고객이 바로 잔액을 보고, 실제 wallet 전송만 15분 배치(델타)로 묶습니다.

나가는 쪽은 가용으로 막는다. 풀(은행 자산)에서 코인이 나가는 거래는 실제 잔액 − 미정산 PENDING ≥ 요청일 때만 승인해, 풀에 없는 코인을 DB 로 약속하는 일을 막습니다.
