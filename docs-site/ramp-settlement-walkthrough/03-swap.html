스왑 — 코인 ↔ 코인 (KRWK → USDC)

델타 원장이 두 줄로 잡히는 유일한 거래 — 보내는 코인과 받는 코인이 동시에 "DB 됐지만 블록체인 전송 전"

무엇·언제: 사용자가 가진 스테이블코인을 다른 스테이블코인으로 바꿉니다. 화면에는 "KRWK 줄고 USDC 늘었다"가 곧바로 보이지만(DB 즉시 반영), 실제 블록체인 전송은 그 뒤 15분 배치에서 일어납니다. 예시로 시세 1,300 KRWK = 1 USDC, 사용자가 KRWK 1,300 을 USDC 1 로 스왑한다고 하겠습니다.

고객 자산과 은행 자산(=풀)은 분리되어 있고, 온체인에서도 분리되어 있습니다 — 고객 옴니버스 지갑 1개와 은행 옴니버스 지갑 1개. 고객마다 개인 지갑이 있는 게 아니라 전 고객 코인이 옴니버스 1개에 섞여 있고, 개인 귀속은 customer_ledger(DB)에만 있습니다. 스왑은 이 둘 사이의 양방향 이동입니다 — 고객의 KRWK 를 은행 풀로 보내고, 은행 풀의 USDC 를 고객에게 보냅니다(고객↔은행 이동 2건). DB 는 즉시 반영하고, 실제 블록체인 전송은 15분 배치에서 처리합니다. 두 자산 재고가 다 있어야 하고, 거래 뒤 재고 쏠림으로 FX/재고 위험을 은행이 지며 그게 스프레드(매매차익)가 됩니다. 발행사 소각+발행이나 거래소 매매는 거래마다 일어나는 게 아니라, 풀 재고가 한쪽으로 쏠렸을 때 다시 채우는 rebalance 경로에서만 일어납니다 (→ 공통 골격: 사전 민팅 재고 풀).

왜 델타가 "두 줄"인가

스왑은 고객↔은행 이동이 두 방향으로 동시에 일어나는 거래입니다 — KRWK 가 고객→은행으로, USDC 가 은행→고객으로 갑니다. 그래서 "DB 됐지만 블록체인 전송 전" 상태(PENDING)인 미정산 항목이 보내는 코인(KRWK +pending)과 받는 코인(USDC −pending) 양쪽에 한꺼번에 생깁니다. 온·오프램프가 한 줄인 것과 다른 점입니다.

핵심 포인트

  • DB 즉시 / 전송은 배치 — 화면은 즉시 바뀌지만 실제 블록체인 전송은 15분 배치에 모아 처리합니다. 그 사이의 "DB 됐지만 전송 전" 상태를 델타가 PENDING 으로 들고 있습니다.
  • 가용은 연속 추적 — 사용가능 잔액 = 잔액 − PENDING. 배치 전이라도 PENDING 을 빼고 가용을 계산하므로 같은 코인을 이중으로 쓸 수 없습니다.
  • 고객 지갑은 옴니버스 1개 — 고객마다 개인 온체인 지갑이 있는 게 아니라 전 고객 코인이 옴니버스 1개에 섞여 있고, 개인 귀속은 customer_ledger(DB)에만 있습니다. 2단계 전송도 두 옴니버스 지갑 사이 네팅 순액입니다.
  • 총계정 변화 없음 — 반환채무라는 부채의 형태만 KRWK 에서 USDC 로 바뀔 뿐, 총액은 그대로입니다(자기자본 변동 없음).
  • 발행사는 rebalance 때만 — 발행사 소각+발행이나 거래소 매매는 거래마다가 아니라 풀 재고가 쏠렸을 때 다시 채우는 rebalance 경로에서만 일어납니다. 스왑 자체는 고객↔은행 풀 이동으로 끝납니다.
