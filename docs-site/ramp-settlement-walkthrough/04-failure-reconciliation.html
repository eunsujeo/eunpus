실패 되돌리기 + 대사 4단계

2단계 정산이 실패하면 어떻게 되돌리는가, 그리고 델타 원장이 대사에서 하는 역할

▸ 정산 실패 시 되돌리기 (rollback)

1단계는 이미 화면·장부에 반영됐는데 2단계 정산이 실패(발행사 거절·전송 실패·시간 초과)하면, 1단계를 정확히 거꾸로 풀어야 합니다. 델타 원장의 미정산 줄이 "무엇을 되돌릴지"의 기준입니다.

왜 "기록 먼저, 정산 나중"이 안전한가

1단계에서 델타 미정산 줄을 먼저 남기기 때문에, 2단계가 어디서 멈추든 "무엇이 미정산 상태로 떠 있는지"가 장부에 남습니다. 그래서 실패를 깔끔히 되돌릴 수도 있고, 오래 떠 있는(stuck) 미정산을 감시할 수도 있습니다.

▸ 대사 4단계 — 어긋남을 잡는 그물

장부가 서로 맞는지 4개 층위로 검증합니다. 델타 원장은 특히 L3·L4 에서 핵심 역할을 합니다.

단계무엇을 대조주기델타 원장의 역할
L1잔액 대사 — 고객 원장 합 = 총계정 잔액실시간"고객 원장 합 ≠ 보관 지갑 합"일 때, 그 차이가 델타 미정산 합과 일치하면 정상
L2건별 대조 — 거래내역 1:1 매칭5분—
L3정산 검증 — 미정산이 제때 닫혔는지정산 시델타 원장의 정산완료(settled) 확인 — 오래 pending 인 줄(stuck) 탐지
L4온체인 검증 — 블록체인 = 장부일 단위블록체인 잔액 = 고객/은행 원장 + 델타 미정산 식으로 균형 확인

L4 의 핵심 등식: 블록체인 실제 잔액 = (오프체인 장부 잔액) + (델타 미정산 합). 델타가 "아직 체인에 반영 안 된 차액"을 설명하므로, 시점차가 있어도 등식이 맞아야 한다.

stuck 미정산 감시

델타 원장의 각 줄에는 정산 상태가 있어, 오래 pending 으로 남은 줄(예: 발행사 응답 지연, 거래소 체결 지연)을 나이(ageing)로 모니터링합니다. 일정 시간을 넘기면 운영자 알림·자동 재시도·거래 보류 같은 처리로 이어집니다.
