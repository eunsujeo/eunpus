실패 되돌리기 — 정산 실패 rollback

DB 는 즉시 반영됐는데 15분 배치 블록체인 전송이 실패하면, 델타 PENDING 줄을 기준으로 DB 에 반영했던 이동을 정확히 거꾸로 되돌린다

▸ 전송 실패 시 되돌리기 (rollback)

1단계에서 DB 는 이미 즉시 반영됐고 델타는 PENDING("DB 됐지만 블록체인 전송 전")으로 떠 있습니다. 그런데 2단계 15분 배치 블록체인 전송이 실패(또는 전송 직전 단계가 실패)하면, DB 에 즉시 반영했던 고객↔은행 이동을 정확히 거꾸로 풀어야 합니다. 무엇을 되돌릴지는 델타 원장의 PENDING 줄이 기준이 됩니다. (일시적 전송 실패는 PENDING 을 유지한 채 다음 15분 배치에서 재시도하고, 거절·시간 초과처럼 끝내 안 되는 terminal 실패에서만 아래처럼 되돌립니다.)

Figure 4. 전송 실패 rollback. 빨강 = 실패 경로. 델타 PENDING 줄을 cancelled 로 닫고, DB 에 즉시 반영했던 고객↔은행 이동 분개를 반대로 정정해 항등식을 원상복구한다. 잠갔던 사용가능 잔액은 고객에게 되돌려준다.

왜 "DB 먼저, 전송 나중"이 안전한가

1단계에서 델타 PENDING 줄을 먼저 남기므로, 15분 배치 전송이 어디서 멈추든 무엇이 "DB 됐지만 전송 전" 상태로 떠 있는지가 장부에 남습니다. 덕분에 실패를 깔끔히 되돌릴 수도 있고, 오래 떠 있는(stuck) PENDING 을 감시할 수도 있습니다.

되돌린 다음은 — 대사(reconciliation)

되돌리기는 한 건을 원상복구하는 일입니다. 그렇게 처리한 장부 전체가 서로 맞는지, stuck PENDING 이 떠 있지 않은지 주기적으로 검증하는 대사 4단계는 다음 장에서 다룹니다 — 델타 원장이 거기서 핵심 역할을 합니다(6장. 대사·결산).
