실패 되돌리기 — 정산 실패 rollback

1단계까지 반영됐는데 2단계 정산이 실패하면, 델타 미정산 줄을 기준으로 1단계를 정확히 거꾸로 되돌린다

▸ 정산 실패 시 되돌리기 (rollback)

1단계는 이미 화면과 장부에 반영됐는데 2단계 정산이 실패(발행사 거절·전송 실패·시간 초과)하면, 1단계를 정확히 거꾸로 풀어야 합니다. 무엇을 되돌릴지는 델타 원장의 미정산 줄이 기준이 됩니다.

sequenceDiagram
    autonumber
    participant Set as 🏛 정산처 / 보관 지갑
    participant App as 🏢 은행 App
    participant CL as 고객 원장
    participant DL as 델타 원장
    participant GLE as 총계정 원장
    participant Cust as 👤 고객

    Note over Set,GLE: ★ 2단계 정산 실패
    Set-->>App: 실패 통지 (거절 / 전송 실패 / 시간 초과)
    App->>CL: 처리중 잠금 해제 — 사용가능 원복
(나가는 쪽은 차감했던 사용가능을 +복원)
    App->>DL: 미정산 줄 → cancelled
    App->>GLE: 정정 분개 — 1단계 미정산 분개를 반대로 (reverse)
    App-->>Cust: "처리 실패 — 잔액 원복" 알림
    end

Figure 4. 정산 실패 rollback. 빨강 = 실패 경로. 델타 줄을 cancelled 로 닫고 1단계 분개를 반대로 정정해 항등식을 원상복구한다. 잠갔던 사용가능 잔액은 고객에게 되돌려준다.

왜 "기록 먼저, 정산 나중"이 안전한가

1단계에서 델타 미정산 줄을 먼저 남기므로, 2단계가 어디서 멈추든 무엇이 미정산 상태로 떠 있는지가 장부에 남습니다. 덕분에 실패를 깔끔히 되돌릴 수도 있고, 오래 떠 있는(stuck) 미정산을 감시할 수도 있습니다.

되돌린 다음은 — 대사(reconciliation)

되돌리기는 한 건을 원상복구하는 일입니다. 그렇게 처리한 장부 전체가 서로 맞는지, stuck 미정산이 떠 있지 않은지 주기적으로 검증하는 대사 4단계는 다음 장에서 다룹니다 — 델타 원장이 거기서 핵심 역할을 합니다(6장. 대사·결산).
