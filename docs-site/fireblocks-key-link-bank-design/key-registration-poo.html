3. Key 등록 + Proof of Ownership

Key Link workspace 에서 키를 사용하려면 2 단계가 필요하다. 먼저 Validation Key 를 등록 (Approval Group quorum 매개) 한 다음, 이를 통해 Signing Key 를 등록한다. 등록 시 PoO (Proof of Ownership) 가 2 가지 방식 (Interactive / Non-interactive) 으로 가능하다.

3.2 Validation Key 등록 절차

새 Signing Key 등록 권한을 얻기 위해 먼저 Validation Key 를 등록한다.

3.2.1 사전 작업 — Approval Group 설정

Validation Key 등록은 Approval Group quorum 의 승인을 거친다. 이 group 은 별도 설정 가능:

  • Fireblocks Console → Settings → Quorums → Security & compliance tab → Add validation keys 항목
  • default: Admin Quorum (workspace 의 모든 Admin)
  • 위임 가능: 별도 group (예: "Validation Key Approvers" — 보안팀 3 인) 으로 설정

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

왜 Approval Group 위임 가능한가

Validation Key 등록 권한은 운영상 중요하지만 일상적 거래 승인과 분리하고 싶을 때 위임 가능. 예: 보안팀 3 인이 Validation Key 추가/회수 결정, 운영팀은 Policy rule 과 일상 transaction 만 다룬다.

Validation Key 등록 5 단계: (1) HSM 에서 키 pair 생성 → (2) public key 추출 → (3) Add validation key API 호출 → (4) Approval Group 의 quorum 이 Mobile app 으로 승인 → (5) Fireblocks 에서 active 상태로 등록.

3.2.3 결과

  • Active Validation Key 가 workspace 에 등록됨
  • 이후 Signing Key 등록 시 이 Validation Key 의 서명만으로 자동 등록 가능
  • 여러 Validation Key 등록 가능 (운영 단위별 분리 등)

3.3 Signing Key 등록 — 공통 단계

Signing Key 등록은 PoO method 선택 → 인증서 생성 → 업로드 의 흐름. PoO 방식은 Interactive 와 Non-interactive 중 하나 선택.

3.3.1 공통 단계 (PoO 무관)

  1. 키 pair 생성 — HSM 또는 FIPS-compliant 장비에서 ECDSA 또는 EdDSA 알고리즘으로 생성. public key 추출 (출처: Getting Started with Fireblocks Key Link)
  2. x509 cert 생성 — Active Validation Key 로 signing key 의 public key 를 wrap (x509 certificate 형태) (출처: Getting Started with Fireblocks Key Link, Python 예시 코드 포함)
  3. Create signing key endpoint 호출 — cert 와 함께 Fireblocks API 로 업로드. 관련 Fireblocks Agent user ID 명시 필수 (어느 Agent 가 이 키의 서명 요청을 받을지 지정) (출처: Getting Started with Fireblocks Key Link)
  4. Cert 검증 — Fireblocks 가 cert 가 active Validation Key 로 서명되었는지 검증. 검증 통과 시 키 등록 (status = enabled=false) (출처: Getting Started with Fireblocks Key Link)
  5. PoO 단계 (방법 분기) — Interactive 또는 Non-interactive 의 PoO 완료 시 enabled=true

3.3.2 x509 cert 예시 (Ed25519)

공식 문서가 직접 인용하는 Python 예시 (요약): 

def issue_certificate(root_ca_private_key, certificate_pubkey, common_name):
    sign_algo = None  # Ed25519 default
    now = datetime.now(timezone.utc)
    time_delta = timedelta(minutes=5)
    certificate = (x509.CertificateBuilder()
        .subject_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, common_name)]))
        .issuer_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, issuer_name)]))
        .public_key(certificate_pubkey)
        .serial_number(x509.random_serial_number())
        .not_valid_before(now)
        .not_valid_after(now + time_delta)
        .add_extension(x509.AuthorityKeyIdentifier.from_issuer_public_key(
            root_ca_private_key.public_key()), critical=False)
        .sign(root_ca_private_key, sign_algo))
    return certificate

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link, p.5-6)

즉 Validation Key (root_ca_private_key) 가 Signing Key 의 public key (certificate_pubkey) 를 wrap 하여 x509 cert 발급. not_valid_after 가 5 분 으로 매우 짧음 — 등록 직후 즉시 사용 권장 (저자 해석).

3.4 Interactive PoO — Fireblocks 가 challenge 발송

가장 기본적인 PoO 방식. cert 검증 후 Fireblocks 가 challenge 메시지를 전송, HSM 이 서명, Fireblocks 가 검증.

3.4.1 흐름

sequenceDiagram
  autonumber
  participant HSM as 🔒 HSM
  participant CSrv as ⚙️ Customer Server
  participant Agent as 🔄 Fireblocks Agent
  participant FB as ☁️ Fireblocks Cloud

  Note over HSM,FB: 사전: cert 업로드 + 검증 완료
키 status = enabled=false
  FB->>Agent: PoO challenge 발송
  Note right of FB: 메시지 =
sha256(tenant_id-request_id-key_id)
  Agent->>CSrv: challenge 중계
  CSrv->>HSM: 서명 요청
  HSM-->>CSrv: challenge 서명
  CSrv-->>Agent: 서명 결과
  Agent-->>FB: 서명 반환
  FB->>FB: 서명 검증 (signing key public 으로)
  Note over FB: 검증 통과 시
키 status = enabled=true

Interactive PoO 의 8 단계. 키 등록 직후 Fireblocks 가 challenge 발송 (1) → Agent · Customer Server 경유 (2-3) → HSM 이 서명 (4-5) → 역방향 반환 (6-7) → Fireblocks 검증 (8). 검증 통과 시 키가 enabled 로 전환.

3.4.2 Challenge 메시지 포맷

"the Proof of Ownership message to be signed is computed as sha256({tenant_id}-{request_id}-{key_id}).hexdigest()"

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

즉 challenge 는 다음 3 ID 의 결합의 SHA256:

  • tenant_id — workspace ID
  • request_id — PoO 요청 ID
  • key_id — 등록 중인 Signing Key ID

Customer Server / HSM 측에서 메시지 무결성 검증 가능 (3 ID 로 hash 를 재계산 후 비교).

3.4.3 운영 특성

  • ✅ HSM 이 항상 online 인 경우 즉시 활성화 가능
  • ✅ Customer 측에 별도 PoO 사전 준비 불필요
  • ❌ Cold HSM 운영 시 challenge 전달 → 서명 → 반환의 air-gap round-trip 필요 — 매우 느림
  • ❌ Fireblocks 의 challenge 발송 시점에 HSM 이 reachable 해야 함

3.5 Non-interactive PoO — 사전 서명 첨부

Cold HSM / air-gap 환경에 적합한 PoO. 등록 시 메시지와 서명을 사전에 생성하여 첨부.

3.5.1 흐름

sequenceDiagram
  autonumber
  participant HSM as 🔒 HSM
  participant Op as 👤 운영자
  participant FB as ☁️ Fireblocks Cloud

  Note over HSM,FB: 사전 작업 (air-gap 가능)
  Op->>HSM: PoO 메시지 생성
(WorkspaceDisplayName, SdkApiKey,
signingDeviceKeyId, UnixTimeInSeconds)
  HSM-->>Op: 메시지 + 서명
  Op->>FB: Add signing key API
(cert + proofOfOwnership 첨부)
  Note over FB: cert 검증 + PoO 서명 검증
  alt 검증 성공
    FB-->>Op: 키 status = enabled=true (즉시)
  else 검증 실패
    FB-->>Op: 등록 실패
  end

Non-interactive PoO 의 흐름. 운영자가 사전에 메시지 생성 (1) → HSM 이 서명 (2) → cert + PoO 첨부하여 등록 API 호출 (3) → Fireblocks 가 검증 → 통과 시 즉시 enabled. air-gap HSM 도 사전 서명 가능하므로 운영 효율적.

3.5.2 메시지 포맷

"Fireblocks|Proof of Ownership Message|<WorkspaceDisplayName>|<SdkApiKey>
This message should be in hexadecimal format and is designed to avoid accidental signatures."

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

구성요소:

  • Fireblocks — 상수 문자열
  • Proof of Ownership Message — 상수 문자열
  • <WorkspaceDisplayName> — workspace 이름 (workspace 간 혼동 방지)
  • <SdkApiKey> — 요청을 만든 API key 의 GUID
  • signingDeviceKeyId — HSM 안의 키 ID 또는 label
  • UnixTimeInSeconds — 서명 생성 시점 timestamp

메시지를 SHA256 으로 hash, HSM 이 서명. 메시지 (hex) + 서명을 proofOfOwnership 객체로 등록 요청에 첨부. 유효하면 Interactive PoO challenge 없이 즉시 enabled.

3.5.3 운영 특성

  • ✅ Air-gap HSM 에서도 사전 서명 가능 → cold HSM 운영에 적합
  • ✅ Fireblocks 의 challenge 응답 round-trip 불필요
  • ✅ Workspace 이름 + API key GUID 포함으로 workspace 간 혼동 방지
  • ❌ Timestamp 가 포함되지만 Fireblocks 측의 timestamp 만료 정책 미명세 → Risk-KL06 (Replay 가능성)
  • ❌ 메시지 무결성을 위해 정확한 hex 인코딩 / 메시지 구성 책임이 고객
Risk-KL06 — Non-Interactive PoO Replay 가능성

Non-interactive PoO 메시지 포맷에 UnixTimeInSeconds 가 포함되지만, Fireblocks 가 이 timestamp 의 만료 정책을 강제하는지 공식 문서에 미명시. 만약 timestamp 만료 검증이 없다면 한 번 만든 PoO 서명을 재사용 (replay) 가능 — 단 같은 SdkApiKey + signingDeviceKeyId 조합은 한 번만 등록 가능하므로 actual replay vector 는 제한적.

운영 권장: Non-interactive PoO 생성 직후 등록 → 사용하지 않는 PoO 서명은 즉시 폐기 — 저자 추정. Risk-KL06 참조.

3.7 등록 완료 후 — Policy rule 설정

Signing Key 가 enabled 되면 거래 서명에 사용 가능. 사용 전 마지막 단계:

  1. Vault account 에 키 할당 — Console 또는 API. ECDSA 1 + EdDSA 1 까지 (앞 페이지 참조)
  2. Policy rule 의 designated signer 설정 — Signer-role API user (Agent 와 페어된) 강제 (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  3. Asset wallet 생성 — vault 에 키가 할당된 algorithm 의 asset 만 생성 가능
Designated signer 강제의 의미

Policy rule 의 designated signer 가 Signer-role API user 로 강제되는 이유는, 모든 서명 요청이 페어된 Agent → Customer Server → HSM 경로로 흘러야 하기 때문. 다른 user (Admin / Editor) 가 designated signer 가 될 수 없도록 강제 — 우회 경로 차단.

3.8 Validation Key 회수 / 재발급

Validation Key 가 침해 의심 또는 운영 정책 변경 시 회수 필요. 단 Fireblocks 공식 문서가 회수 절차를 별도 명시하지 않음 — 저자 추정 정리:

  • 새 Validation Key 등록 → Approval Group quorum 승인
  • 이전 Validation Key 의 active 상태 해제 — API endpoint 또는 Console (정확한 endpoint 명세는 본 문서 미확보)
  • 기존 Signing Key 의 영향 — 등록 시 사용된 Validation Key 가 회수되어도 이미 enabled 된 Signing Key 는 계속 사용 가능 추정 (cert 가 등록 시점에 이미 검증되었으므로)

(출처: 저자 추정 — Fireblocks 공식 회수 절차 미확보, vendor 별도 확인 필요)

Risk-KL04 — Validation Key 침해

Validation Key 가 침해되면 공격자가 임의 Signing Key 를 등록 (등록 시 Approval Group quorum 매개 없이) 가능. 완화: Approval Group "Add validation keys" 의 quorum 을 보안팀에 위임 + Validation Key 자체를 HSM 안에 보관 (공식 명시 권장 미확보) + 주기적 회수/재발급 — 저자 권장. Risk-KL04 참조.
