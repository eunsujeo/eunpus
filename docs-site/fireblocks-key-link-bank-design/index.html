Fireblocks Key Link — Customer HSM 통합 reference

Fireblocks 의 Key Link 는 고객사가 보유한 HSM (Hardware Security Module) (?) 을 Fireblocks 플랫폼과 결합하는 통합 방식. Fireblocks 는 키 share 를 보유하지 않으며, 서명은 모두 고객의 HSM 에서 수행된다.

본 페이지의 출처 — 어디까지가 공식 사실이고, 어디부터가 저자 추정인가

본 문서는 두 등급으로 출처를 구분한다:

  • 공식 문서에 정의된 사실 — 그대로 받아도 안전 (출처 명시)
  • 저자가 합리적으로 추정한 운영 권장 — 참고용, 본인 환경 검증 권장

저자가 Fireblocks Help Center 에서 식별한 Key Link 관련 공식 문서 3 건 (Overview · Getting Started · Vault Setup) 의 본문을 정밀 인용 가능. 추가로 Fireblocks 공식 블로그 1 건 (2025-09-23 Thales 파트너십) 의 본문 인용 가능.

10 초 요약

  • Key Link = customer-held HSM 모델. SaaS MPC 와 달리 Fireblocks 가 키 share 를 0 개 보유. (출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)
  • 4 구성요소: Fireblocks Agent (open-source TS) + Customer Server + HSM Component + HSM Adaptor (선택, cold HSM 용). (출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)
  • 2 key 모델: Validation Key (등록 권한 증명) + Signing Key (실제 서명). (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  • 3-mode signing: Hot · Warm · Cold (air-gapped: USB / SFTP / data diodes). (출처: Fireblocks 공식 블로그 — Enterprise Digital Asset Security with Fireblocks and Thales, 2025-09-23)
  • Reference HSM 파트너: (?) Thales Luna HSM — FIPS 140-3 Level 3 + Common Criteria + PQC 대응. (출처: Fireblocks 공식 블로그 — 2025-09-23)
  • API 상태: Beta (endpoint prefix /key-link-beta/). Production 도입 시 vendor 와 조건 협의 필요 — 저자 추정.
  • KR 관할 명시 없음: vendor 블로그가 HKMA · HKSFC · JFSA 만 명시. KR VASP 환경 적용은 별도 검증 항목.

권장 시나리오 — 어떤 경우에 Key Link 를 선택하나
  • 강한 키 보유권 요건 — 규제 / 내부 정책상 "키 share 가 외부 (Fireblocks Cloud) 에 한 개도 존재해서는 안 된다"
  • 기존 HSM 자산 활용 — 이미 Thales Luna / Entrust / 기타 FIPS HSM 운영 중. SaaS MPC 로 가면 이 자산이 의미가 없어짐
  • 망분리 IDC 의 강한 해석 — KR 은행처럼 외부 SaaS 통신 자체가 해석 부담일 때 (단 Customer Server 가 Fireblocks 와 outbound 통신은 여전히 필요)
  • 커스텀 정책 / 검증 추가 — Customer Server 단계에서 자체 transaction validation, custom approval logic 추가 가능

단, Beta 상태인 점 + Customer Server SPOF (Risk-KL01) + Agent open-source 운영 부담 (Risk-KL02) 등은 별도 trade-off.

핵심 invariant (6)

  1. Fireblocks 키 share = 0 — Key Link workspace 에서는 Fireblocks 클라우드가 키 share 를 보유하지 않는다. (출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)
  2. Vault Account = 1 ECDSA + 1 EdDSA — 각 vault 에 algorithm 별 1 키만 할당. 한 키가 한 vault 전속 (다른 vault 재사용 불가). (출처: Fireblocks 공식 문서 — Set up your Fireblocks Vault with Key Link)
  3. Validation Key 가 등록 권한 plane — 새 Signing Key 등록은 active Validation Key 의 서명을 통해서만 가능 (자동화 가능). (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  4. PoO 2 methods — Interactive (Fireblocks 가 challenge 발송) / Non-interactive (등록 시 사전 서명 첨부). 둘 중 하나 선택. (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  5. Designated signer = Agent API user — Policy rule 의 designated signer 는 Signer-role API user (Agent 와 페어링된) 강제. (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  6. Workspace type immutable — Key Link workspace 는 다른 type (SaaS MPC / Hosted MPC) 으로 변환 불가 — 저자 추정 (architectural symmetry, SaaS MPC 의 invariant 와 동일 패턴). (출처: Fireblocks 공식 문서 — Hosted MPC Workspace Configuration; 저자 추정 — Key Link 자체 명시는 미확보)

이 문서가 다루지 않는 것

  • Fireblocks Agent 의 정확한 GitHub repo URL · 버전 release cycle — open-source 사실은 공식 명시, 구체 repo URL · 운영 정책은 본 문서 미확보 (Q-KL02 / Q-KL03)
  • Hot/Warm/Cold 의 정확한 기술 정의 — 특히 "Warm" 의 의미. vendor 블로그에 framing 만 명시. 정밀 spec 미확보 (Q-FB01)
  • SaaS Cold Wallet workspace vs Key Link Cold signing 의 관계 — 별개 product 인지 같은 plane variant 인지 미명시 (Q-FB02)
  • KR VASP 환경의 vendor 공식 입장 — 블로그가 HKMA · HKSFC · JFSA 만 명시. KR 미명시 (Q-FB03)
  • Validation Key 분실 시 복구 절차 — quorum 으로 새 Validation Key 등록 가능 추정, 정밀 복구 절차 미확보
  • 다른 vendor (Anchorage / Copper / Hex Trust) 의 customer-held HSM 모델 — 본 문서는 Fireblocks 한정
