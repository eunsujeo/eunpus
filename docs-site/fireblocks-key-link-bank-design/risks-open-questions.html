Risk-KL01 — Customer Server SPOF

위협: Customer Server 가 Key Link 의 signing path 의 단일 장애점. server down → 모든 서명 중단.

  • 근거: Fireblocks 공식 문서가 "Customer Server is developed and hosted by the customer" 명시. HA 권장은 별도 명시 없음 (출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)
  • 영향: 사용자 출금 응답 시간 초과, KR 가상자산이용자보호법의 "예치금 환급" 의무 위반 가능성
  • 완화 권장 (저자): Customer Server 의 active-active HA 2-node + load balancer + health check. Agent 도 2 인스턴스 권장. 2. 아키텍처 구성요소 의 권장 토폴로지 참조

Risk-KL02 — Fireblocks Agent 운영 부담

위협: Agent 가 open-source TS 프로젝트. security patch / version 호환성 책임이 고객.

  • 근거: "Fireblocks Agent is an open-source on-prem service (TypeScript)" 명시 (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  • 영향: minimum version 호환성, security CVE 대응 지연 시 침해 가능성
  • 완화 권장 (저자): Agent version 정기 점검 정책 수립, Fireblocks 의 release notes / advisory 모니터링, 사내 patch policy
  • 미해결: Fireblocks 가 minimum version 을 강제하는지 / security patch deployment 정책이 무엇인지 공식 미명세 (Q-KL03)

Risk-KL03 — Beta API Production Risk

위협: Key Link API 가 Beta 상태 (endpoint prefix /key-link-beta/). production-grade SLA / 호환성 보장 불확실.

  • 근거: API prefix 가 /key-link-beta/ 임. Fireblocks 공식 문서가 Beta 상태에 대한 일반적 limitation 을 명시하지 않음
  • 영향: Beta API breaking changes, production 환경에 적용 시 운영 리스크
  • 완화 권장 (저자): vendor 와 직접 협의하여 (a) Beta SLA 명시, (b) breaking change advance notice, (c) production-readiness roadmap 합의

Risk-KL04 — Validation Key 침해

위협: Validation Key 가 침해되면 공격자가 임의 Signing Key 를 등록 가능 (quorum 매개 없이). 침해 후 발행한 Signing Key 로 자금 탈취 시도 가능.

  • 근거: "A validation key is used as proof of authority for the approvals when adding new signing keys" — Validation Key 가 등록 권한 plane (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  • 완화 권장 (저자):
    • Validation Key 자체를 HSM 안에 보관 (공식 명시 권장은 미확보, 강하게 권장)
    • Approval Group "Add validation keys" 의 quorum 을 보안팀에 위임 (default Admin Quorum 보다 좁은 group)
    • 주기적 회수 / 재발급 정책 (예: 분기별)
    • Validation Key 별 audit log monitor (Fireblocks Console)

Risk-KL05 — Cold HSM Latency

위협: Cold HSM mode 의 signing latency 가 air-gap transport 때문에 시간 단위. 긴급 상황 대응 불가.

  • 근거: HSM Adaptor 가 cold HSM 통신 매개. Air-gap = USB / SFTP / data diodes 명시. 정확한 latency 수치는 미공개 (출처: Fireblocks 공식 블로그 — 2025-09-23; 정확한 latency 는 미명세)
  • 완화 권장 (저자):
    • Cold 비율을 가상자산업감독규정 9조 80% 안에서 합리적 수준 (80-85%)
    • Hot↔Cold rebalancing 빈도 정책 (일일 / 주간)
    • 긴급 출금 대응 절차 — Cold ceremony 의 신속 ceremony 옵션 (수 시간 안에 가능한 운영자 schedule)
    • 사용자 출금 응답 시간 정책 (KR 가상자산이용자보호법의 응답 시간 요건 검토)

Risk-KL06 — Non-Interactive PoO Replay 가능성

위협: Non-interactive PoO 메시지가 UnixTimeInSeconds 포함하지만, Fireblocks 가 timestamp 만료를 강제하는지 미명세. 이론상 한 번 만든 PoO 서명 재사용 가능성.

  • 근거: 메시지 포맷에 UnixTimeInSeconds 포함은 명시. 만료 정책은 명시 없음 (출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)
  • 실제 replay vector: 같은 (SdkApiKey + signingDeviceKeyId) 조합은 한 번만 등록되므로 단순 replay 는 제한적. 단 새 API key + 같은 device key 조합으로 우회 가능성 별도 검토
  • 완화 권장 (저자): PoO 생성 직후 즉시 등록, 사용하지 않은 PoO 서명 즉시 폐기, audit log 로 등록 시점과 timestamp 의 차이 monitor

Risk-KL07 — Workspace Type Immutability

위협: Key Link workspace 를 다른 type (SaaS MPC / Hosted MPC) 으로 변환 불가 (저자 추정 — Hosted MPC 의 invariant 와 architectural symmetry). 이로 인해 마이그레이션 시 새 workspace 생성 + 자산 이전 비용 발생.

  • 근거: Hosted MPC 공식 명시 — "modifying an existing SaaS MPC workspace is impossible" (출처: Fireblocks 공식 문서 — Hosted MPC Workspace Configuration)
  • 운영 영향: Key Link → SaaS MPC 또는 SaaS MPC → Key Link 마이그레이션은 새 workspace 생성 + cross-workspace asset transfer 가 유일한 경로
  • 완화 권장 (저자): 도입 전 충분한 검토. Phase 1 시범 단계에서 적은 자산으로 검증 후 전면 도입. 도입 후 변경 시 자산 이전 비용 (on-chain fee + 운영 부담) 사전 산정

Q-KL01 — Key Link ↔ MPC workspace 공존

한 Customer Domain 안에 Key Link workspace 와 SaaS MPC workspace 가 공존 가능한지 vendor 공식 명세 부분 명시.

  • 부분 답변 (저자 추정): Hosted MPC 의 invariant 가 architectural symmetry 로 Key Link 에도 확장된다고 추정 시, 한 Customer Domain 안에 다양한 type 의 workspace 공존 가능. 단 workspace type 자체는 immutable
  • 미해결: Key Link 자체의 immutability 직접 명시 + 한 vault 안에 MPC asset + Key Link asset 공존 가능 여부
  • 확인 경로: Fireblocks Sales 와 직접 협의, 또는 Key Link 의 advanced ops 문서 (현재 본 reference 미확보)

Q-KL02 / Q-KL03 — Fireblocks Agent 운영 모델

Fireblocks Agent 가 open-source TS 프로젝트라는 사실은 공식이지만:

  • Q-KL02: 정확한 GitHub repo URL + license + 운영 책임 범위 (Fireblocks vs 고객)
  • Q-KL03: minimum version 강제 / security patch deployment 정책

운영 책임 (특히 security CVE 발생 시 누가 patch 를 만들고 누가 deploy 하는지) 의 명확화가 필요.

Q-KL04 — Cold HSM Latency / Batching

Cold HSM 의 signing latency 와 batching 패턴이 air-gap transport 종류 (USB / SFTP / data diode) 별로 어떻게 다른지 vendor 공식 명세 미확보. Stage 38 의 Fireblocks Thales 블로그에서 transport 종류는 명시했지만 정확한 latency 수치는 여전히 미공개.

  • 은행 운영 영향: 사용자 응답 시간 정책 (KR 가상자산이용자보호법) 설계 시 critical input
  • 확인 경로: Thales-Fireblocks Solution Brief 본문 (현재 본 reference 미확보) + 실제 PoC 측정

Q-KL05 — Non-interactive PoO Timestamp 만료

Non-interactive PoO 메시지의 UnixTimeInSeconds 가 Fireblocks 측에서 만료 검증되는지 공식 명세 미확보. Risk-KL06 의 replay 위험 평가의 핵심 변수.

Q-FB01 — Hot/Warm/Cold 의 정확한 기술 정의

Fireblocks 공식 블로그 (2025-09-23) 가 "Hot/Warm/Cold 3-mode" 를 framing 했지만 정확한 기술 정의 (특히 Warm 의 의미) 미명시.

  • 저자 추정 (4. Signing Flow 의 Warm 절): Warm = "정해진 운영 시간대 + 수동 활성화 조합"
  • 대안 해석: Warm = 별도 mode 아니라 Hot 의 운영 변형, 또는 Customer Server 의 일부 캐싱
  • 확인 경로: Thales-Fireblocks Solution Brief 본문 + 추가 vendor 자료

Q-FB02 — SaaS Cold Wallet vs Key Link Cold Signing

가장 큰 product 분류 모호점. Fireblocks 에는 두 가지 Cold variant 가 동시 존재:

  • (a) SaaS Cold Wallet workspace — 별도 product, Admin Quorum 단독, P2P rebalancing (Risk-G07 등). 은행 Fireblocks Cold Wallet 도입 참조
  • (b) Key Link Cold signing workflow — Key Link 의 HSM 이 cold mode 인 경우 (본 문서)

두 옵션이 별개 product 인지, 같은 plane 의 variant 인지, 혼합 사용 가능한지 vendor 공식 명세 미확보.

은행 결정 영향: Cold storage 운영을 (a) Fireblocks 가 관리하는 Cold facility (SaaS Cold Wallet) 로 할지, (b) 고객이 직접 운영하는 Cold HSM (Key Link Cold) 로 할지의 선택은 product 분류 명확화 후만 가능.

Q-FB03 — KR VASP 환경의 Vendor 공식 입장

본 reference 의 최고 우선순위 미해결 항목. Fireblocks 공식 블로그 (2025-09-23) 가 명시한 관할권:

  • 명시: HKMA (홍콩 금융관리국) · HKSFC (홍콩 증권선물위원회) · JFSA (일본 금융청)
  • 미명시: KR 금융위원회 / 금감원 / KR VASP 신고 관련 일체

KR 가상자산이용자보호법 / 가상자산업감독규정 환경에서 Key Link + Thales Luna 의 적용 가능성에 대한 vendor 공식 입장 부재.

  • 은행 도입 영향: vendor 보증 없이 KR 환경 도입 시 risk 부담을 은행이 단독으로 짊어짐
  • 확인 경로: Fireblocks Sales · Legal 과 직접 협의, KR 관할 관련 공식 statement / 계약 조항 확보
