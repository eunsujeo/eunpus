4. Signing Flow — Hot · Warm · Cold 3-mode

Key Link 의 거래 서명은 HSM 의 운영 모드에 따라 Hot · Warm · Cold 3 가지 workflow 로 분류된다. 이 framing 은 Fireblocks 공식 블로그 (2025-09-23, Thales 파트너십) 에서 공식화되었다.

  • Hot · Warm · Cold 3-mode signing workflow — Fireblocks 공식 블로그 (2025-09-23)
  • Air-gap transport = USB · SFTP · data diodes — Fireblocks 공식 블로그 (2025-09-23)
  • 거버넌스 기능 (multi-approval, address whitelisting, transaction limits, immutable logs) — Fireblocks 공식 블로그 (2025-09-23)
  • Policy rule designated signer = Agent API user — Getting Started with Fireblocks Key Link

저자가 합리적으로 추정한 운영 권장 — 참고용

  • Hot / Warm / Cold 의 정확한 기술적 분류 (Warm 의 의미는 공식 명세 미확보 — Q-FB01)
  • 각 mode 의 latency / throughput 추정치
  • 은행 환경에서 Mode 별 비율 권장 (Hot 20% / Cold 80% — KR 규제 매핑)

Warm 의 정의 — vendor 공식 미명세 (Q-FB01)

"Warm" mode 의 정확한 기술 정의는 Fireblocks 공식 블로그가 명시하지 않는다. 본 페이지의 Warm 정의 ("일부 시간 online, 수동/스케줄 활성화") 는 저자 추정이며, 실제 vendor 의 정의가 다를 수 있다. 예: "Warm 은 별도 mode 가 아니라 Hot 의 일부 운영 변형" 가능성 — Q-FB01 참조.

4.3 Hot 서명 — 실시간

HSM 이 Customer Server 와 항상 네트워크 연결되어 있는 mode. 입출금 처리와 같은 실시간 거래에 사용.

4.3.1 특징

  • HSM 이 항상 online (PKCS#11 / vendor SDK / REST API)
  • 서명 latency = 네트워크 round-trip + HSM 연산 = 초 단위
  • HSM 침해 시 latency 가 낮은만큼 공격 surface 가 큼 — Risk-KL01 의 Customer Server SPOF 와 결합 시 가장 큰 위협

4.3.2 권장 사용처 (은행)

  • 고객 입출금 즉시 처리 (working balance 한도 안)
  • Gas station / sweeping 운영
  • 가스 fee 가 빠르게 변하는 fast-finality 체인의 거래

4.3.3 HSM 종류 (예시)

  • Thales Luna Network HSM — 네트워크 연결, FIPS 140-3 L3 + CC
  • AWS CloudHSM / Azure Dedicated HSM — 클라우드 환경, 단 KR 망분리 해석 부담

(출처: Fireblocks 공식 블로그 — 2025-09-23 Thales Luna 통합)

4.4 Warm 서명 — 활성화 대기

HSM 이 평시 offline / standby 상태이고, 필요 시점에 online 으로 전환되는 mode (저자 정의 — Q-FB01).

4.4.1 가능한 해석

  • 해석 A — 스케줄 활성화: 정해진 시간대 (예: 영업시간) 에만 HSM 이 online. 그 외 시간에는 offline
  • 해석 B — 수동 활성화: 운영자가 수동으로 HSM 을 활성화 (예: 특정 거래 batch 처리 직전)
  • 해석 C — 부분 캐싱: Customer Server 에 일부 서명 권한 캐시, HSM 은 정기 갱신

공식 문서가 정확한 정의를 명시하지 않으므로, 본 reference 는 해석 A + 해석 B 의 조합을 권장: "정해진 운영 시간대 + 별도 수동 활성화 가능" 이 보안 / 운영 균형에서 합리적 — 저자 추정.

4.4.2 권장 사용처 (은행)

  • 일일 batch 출금 (오전 / 오후 시간대)
  • 대량 정기 transfer (rebalancing 등)
  • 실시간이 필요하지 않은 정형 거래

4.5 Cold 서명 — Air-gapped

HSM 이 완전히 네트워크 격리된 mode. air-gap transport 로만 서명 요청/결과 전달.

4.5.1 Air-gap transport — 공식 명시

"Thales Luna HSMs ... support air-gapped workflows via USB, SFTP, or data diodes."

(출처: Fireblocks 공식 블로그 — 2025-09-23)

Transport특성적합한 환경
USB 물리 매체 (USB drive). 운영자가 직접 이동 최고 격리, ceremony 기반 운영. 수동 부담 큼
SFTP 일방향 전용 네트워크 + SFTP transfer 망분리 환경의 단방향 채널 (저자 추정)
Data diodes 물리적 단방향 회선 (광 + receiver only) 최고 보안 (군/정보기관 표준). 비용 큼

(출처: Fireblocks 공식 블로그 — 2025-09-23; transport 별 특성은 저자 정리)

Cold 서명 ceremony 의 단계. HSM Adaptor 가 메시지를 air-gap 가능한 형태로 패키지화 → 운영자가 물리 transport (USB / SFTP / data diode) → Cold HSM 이 서명 → 역방향 반환. 운영자의 물리 이동 + ceremony 가 latency 의 주 원인.

4.5.3 권장 사용처 (은행)

  • 대량 보관 자산의 출금 (cold reserve → hot rebalancing)
  • 월간 / 분기별 정기 ceremony
  • KR 가상자산업감독규정 9조의 콜드월렛 80% 보관 자산

4.5.4 Latency 영향

  • USB ceremony: 30 분 ~ 수 시간 (인원 동원 + 물리 이동)
  • SFTP / data diode: 분 단위 ~ 수십 분 (자동화 정도에 따라)
  • 긴급 출금 대응 불가 — 사용자 응답 시간 정책 별도 수립 필요

(출처: 저자 추정 — 공식 latency 수치는 미명세, Risk-KL05)

4.6 거버넌스 — 모든 mode 에 공통 적용

Fireblocks Cloud 의 governance plane 은 mode 와 무관하게 적용된다. Fireblocks 공식 블로그가 명시한 거버넌스 기능:

  • Multi-approval rules — Approval Group quorum, Admin Quorum
  • Address whitelisting — 수신 주소 사전 등록
  • Transaction limits — 금액 / 빈도 한도
  • Immutable audit logs — Fireblocks Console 의 변경 불가 로그

(출처: Fireblocks 공식 블로그 — 2025-09-23)

왜 거버넌스가 mode 와 독립적인가

거버넌스 plane 은 Fireblocks Cloud 에서 작동하며, 서명 plane (HSM) 과 분리되어 있다. Policy rule 평가는 Cloud 에서 수행되고, 통과한 거래만 Agent 로 서명 요청이 흘러간다. 즉 HSM 이 cold 라 해도 Cloud 의 거버넌스는 동일하게 작동.

4.7 Hot ↔ Cold rebalancing

은행 환경에서는 Hot 과 Cold 사이 자산 재배치 (rebalancing) 가 정기적으로 필요. Key Link 의 rebalancing 은 다음 옵션:

4.7.1 옵션 A — 동일 workspace 내 (저자 추정 가능 여부 불명)

한 Key Link workspace 안에 Hot HSM signing key + Cold HSM signing key 가 공존 가능한지 vendor 공식 명세 미확보. Vault account 의 1 ECDSA + 1 EdDSA 룰을 고려하면, vault 단위로 Hot/Cold 분리하는 것이 자연스러움 — 저자 추정.

4.7.2 옵션 B — 별도 workspace + cross-workspace transfer

Hot workspace 와 Cold workspace 를 별도로 운영하고, on-chain transfer 로 rebalancing. 이 패턴은 SaaS Cold Wallet 의 운영 방식과 유사 (Fireblocks 공식 문서 "Connecting Cold Wallet with hot workspaces via P2P"). 단 Key Link 자체의 cross-workspace 권장은 본 문서 미확보.

Q-FB02 — Key Link Cold vs SaaS Cold Wallet 관계

Fireblocks 에는 (a) SaaS Cold Wallet workspace (별도 product) 와 (b) Key Link Cold signing workflow (HSM 의 cold mode) 가 둘 다 존재한다. 이 둘이 별개 product 인지, 같은 plane 의 variant 인지, 혼합 사용 가능한지 vendor 공식 명세 미확보. Q-FB02 참조.

4.8 PQC (Post-Quantum Cryptography) 대응

Fireblocks 공식 블로그가 Thales Luna 통합의 강점으로 명시한 점:

"Thales Luna HSMs provide crypto agility and post-quantum cryptography (PQC) readiness."

(출처: Fireblocks 공식 블로그 — 2025-09-23)

  • Crypto agility — HSM 펌웨어 업데이트로 새 알고리즘 추가 가능. HSM 교체 없이 알고리즘 진화 대응
  • PQC readiness — NIST 표준 후보 (ML-KEM, ML-DSA 등) 의 향후 추가 가능
  • 은행 함의 — 양자컴퓨터 위협 대비 자산 계획에 HSM 의 PQC 지원 여부 반영 필요
PQC 적용 시점 — 저자 추정

NIST 의 PQC 표준화 (2024-) 가 진행 중이며, blockchain 의 PQC 전환은 (a) 서명 알고리즘 자체의 표준화 + (b) 체인 protocol 수준의 채택이 필요. 현재 시점 (2026-05) 에는 ECDSA / EdDSA 가 dominant. PQC 전환은 2030 년대 이후 단계적 — 저자 추정. 은행은 지금 PQC 적용보다 "HSM 이 향후 PQC 추가를 지원하는 장비인지" 만 확인해도 충분.
