5. 은행 도입 — KR 망분리 + 컴플라이언스

KR 은행이 수탁형 디지털 자산 지갑을 운영할 때 Fireblocks Key Link 를 어떻게 배치하고, KR 법규에 어떻게 매핑할지 정리. 관련 컴플라이언스 reference 는 국내 블록체인 사업 법규 × Fireblocks 문서 참조.

5.1 KR 은행 환경의 3 가지 제약

KR 은행 (수탁업자) 이 디지털 자산 지갑을 운영할 때 직면하는 3 가지 핵심 제약:

제약근거Key Link 의 적합성
망분리 전자금융감독규정 (망분리 의무) + 은행권 내부 보안 정책 강함 — HSM + Customer Server 전량 on-prem 가능. Agent 만 outbound HTTPS
콜드월렛 80% 가상자산업감독규정 9조 (이용자 자산의 80% offline) 가능 — Cold HSM 운영 + air-gap transport. 단 운영 부담 검토 필요
실질 통제 보유 대법원 2024도10710 — 키 통제권 = 실질 통제 가장 강함 — 키 share 0 invariant, Fireblocks 가 단독 서명 불가

(출처: KR 법령 — law.go.kr · 대법원 2024도10710; Fireblocks 공식 — Key Link Overview)

5.2 3-옵션 비교 — SaaS MPC / Hosted MPC / Key Link

KR 은행이 Fireblocks 도입 시 선택 가능한 3 옵션의 KR 적합성 비교 (저자 분석).

항목옵션 A — SaaS MPC옵션 B — Hosted MPC옵션 C-Thales — Key Link + Thales Luna
키 share 위치 Fireblocks Cloud + Mobile 고객 Co-signer + Cloud + Mobile 전량 고객 HSM
망분리 해석 외부 SaaS 통신 — 강한 해석 시 부담 Co-signer on-prem, Mobile + Cloud 외부 — 해석 여지 HSM + Customer Server 전량 on-prem 가능
FIPS 인증 해당 없음 (MPC 분산) SGX TEE 기반 (FIPS 인증 별도) FIPS 140-3 L3 + CC (Thales Luna)
실질 통제 판단 (대법원 2024도10710) 분산 MPC — 단독 통제 어려움, 해석 필요 분산 MPC — 해석 필요 고객 단독 통제 (강한 주장 가능)
콜드월렛 운영 별도 SaaS Cold Wallet workspace 구매 제한적 Cold HSM mode 로 자연스럽게 통합

권장 — 옵션 C-Thales (단 조건부)

KR 은행 환경에서 가장 강한 컴플라이언스 적합성은 옵션 C-Thales (Key Link + Thales Luna). 키 share 0 + on-prem HSM + 망분리 IDC 안 배치 + FIPS 140-3 L3 인증의 조합이 망분리 / 실질통제 / 콜드월렛 80% 의 3 제약을 동시에 풀 수 있다.

단 다음 조건부:

  • Beta API 의 production-readiness 검증
  • KR 관할에서의 vendor 공식 입장 확보 (Q-FB03)
  • Customer Server SPOF / Agent 운영 부담 대응 (Risk-KL01, KL02)
  • HSM 의 PoO replay risk 분석 (Risk-KL06)

5.3 KR 법규 매핑

가상자산이용자보호법 / 가상자산업감독규정 / 특정금융정보법 (특금법) / 전자금융감독규정의 주요 항목 매핑.

5.3.1 가상자산업감독규정 9조 — 콜드월렛 80%

"이용자 가상자산의 100분의 80 이상에 해당하는 자산 (경제적 가치 기준) 을 인터넷과 분리하여 보관" — 시행령 위임 "100분의 70 이상" 안에서 금융위 정함.

  • 옵션 C-Thales 매핑: Cold HSM mode 의 자산을 80% 이상으로 운영. air-gap (USB / SFTP / data diodes) 으로 인터넷 격리
  • 측정 방식: workspace 또는 vault account 단위로 Hot / Cold 분리, Cold vault 의 자산 가치 / 전체 자산 가치 비율 monitor
  • Cold HSM 의 운영 부담: 80% 비율 유지를 위한 Hot↔Cold rebalancing 빈도 결정 필요 — 일일 / 주간 / 임계점 기반

(출처: KR 가상자산업감독규정 — law.go.kr admRulSeq=2100000244180)

5.3.2 대법원 2024도10710 — 실질 통제 판단

MPC · 멀티시그 환경에서 누가 "실질 통제" 권을 가지는지 판단한 판례. 단순한 키 보유가 아니라 실제 거래 서명 / 거부 권한의 행사 가능성이 기준.

  • 옵션 C-Thales 매핑: HSM 안의 키를 고객 (은행) 이 단독 운영. Fireblocks 가 Cloud 에서 서명 요청을 보내도, Customer Server / HSM 에서 거부 가능
  • 강한 통제 주장 가능: (a) HSM 의 PKCS#11 / vendor SDK 접근권 = 은행 / (b) Customer Server 의 custom validation logic 으로 거래 거부 가능 / (c) Fireblocks 단독으로 서명 생성 불가
  • 단 주의: Fireblocks 가 Policy rule plane 을 운영하므로, Policy 가 통과한 거래만 서명 요청이 흘러옴. 이 plane 이 "실질 통제" 판단에 어떤 영향을 미치는지는 별도 법률 검토 필요

(출처: 대법원 2024도10710 — KR 법원 판례; 옵션 C-Thales 매핑은 저자 분석)

5.3.3 특금법 5조의4 — 거래기록 5년 보존

  • 옵션 C-Thales 매핑: Fireblocks Cloud 의 immutable audit logs (Console) 가 1 차 기록. 단 Fireblocks 의 보존 기간 정책이 5 년 충족 여부 vendor 확인 필요
  • 보조 기록: Customer Server 에 거래 로그 별도 저장 권장 (custom validation 로그 포함). 은행 내부 5 년 보존 system 과 통합

(출처: KR 특정금융정보법 5조의4 — law.go.kr)

5.3.4 전자금융감독규정 (망분리)

  • 옵션 C-Thales 매핑: HSM + Customer Server 를 망분리 IDC 안에 배치. Agent 는 outbound HTTPS 만 — DMZ 배치 가능
  • 단 Agent 의 outbound 통신 자체가 망분리 해석에서 issue 인지는 KR 은행 보안팀 / 금감원 해석 필요

5.5 도입 절차 — 5 단계

KR 은행의 Key Link 도입 권장 절차 (저자 정리):

Phase 1 — 사전 평가 (1-2 개월)

  • Fireblocks Sales 와 옵션 C-Thales 의 KR 관할 vendor 공식 입장 확인 (Q-FB03)
  • Beta API 의 production-readiness · SLA · roadmap 합의
  • HSM 선정 (Thales Luna Network HSM vs Cold HSM 별도)
  • 은행 내부 보안팀 / 컴플라이언스팀 / 법무팀의 사전 검토
  • 망분리 해석 — 금감원 / 은행 내규 검토

Phase 2 — 인프라 준비 (2-3 개월)

  • 망분리 IDC 의 vault room 구성 (Hot HSM + Cold HSM)
  • Customer Server HA 구성 (2-node minimum)
  • Fireblocks Agent 호스팅 환경 (DMZ Node.js 운영)
  • 거래 로그 DB 5 년 보존 system 통합
  • HSM 의 air-gap transport 설계 (USB ceremony / SFTP / data diode)

Phase 3 — Key Link 등록 (1 개월)

  • Fireblocks Key Link workspace 생성
  • Approval Group "Add validation keys" 위임 (보안팀 3 인 권장)
  • Validation Key 등록 (Hot HSM 또는 Cold HSM 어디에 둘지 결정)
  • Signing Key 등록 (Vault 별 ECDSA + EdDSA)
  • Policy rule 의 designated signer 설정 (Agent API user)

Phase 4 — 운영 정책 수립 (1 개월)

  • Hot/Cold 비율 monitor + rebalancing 빈도
  • Customer Server 의 custom validation logic 정의 (필요 시)
  • 거래 로그 5 년 보존 + 외부 감사 대응 절차
  • HSM key backup (Thales Luna 의 backup HSM 또는 Smart Card 백업)
  • DR / BCP 시나리오 (HSM 장애, Customer Server 장애, Validation Key 침해 등)

Phase 5 — 운영 시작 + 점진적 자산 이전 (3-6 개월)

  • 제한된 자산으로 운영 시작 (테스트 vault)
  • 모니터링 — 서명 latency / 실패율 / Cold ceremony 빈도
  • 점진적 자산 이전 (전체 자산의 일부 → 50% → 전체)
  • 운영 안정화 후 모든 vault 의 Key Link 적용

5.7 cold-wallet docs 와의 cross-link

SaaS Cold Wallet workspace 와 Key Link Cold mode 는 별개 product 일 가능성이 큼 (Q-FB02 미해결). 두 옵션의 상세 비교는:

  • 은행 Fireblocks Cold Wallet 도입 — 수탁형 지갑 reference — SaaS Cold Wallet workspace 전용
  • 은행 운영 절차 (Cold Wallet) — 옵션 C-Thales 표 포함
  • 국내 블록체인 사업 법규 × Fireblocks — KR VASP 컴플라이언스 매핑 전반
