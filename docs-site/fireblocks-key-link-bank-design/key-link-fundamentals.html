1. Key Link 란 — Customer-Held HSM 모델

Fireblocks Key Link 는 고객이 보유한 HSM (?) 을 Fireblocks 의 운영 layer 와 결합하는 통합 방식. 고객은 키 자체의 소유권을 유지하면서, Fireblocks 의 walletmanagement / governance / transfer network / compliance feature 를 그대로 활용한다.

  • "Key Link plane" 이라는 용어는 본 reference 의 정리 표현 (vendor 공식 용어 아님)

1.1 한 줄 정의

"With Fireblocks Key Link, you can integrate your organization's Key Management solution with the platform."

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)

즉 Key Link 는 키 관리 인프라 (KMI / HSM) 의 통합 어댑터. Fireblocks 의 운영 layer (전송망 · 거버넌스 · 컴플라이언스) 는 그대로 쓰면서, 키 자체는 고객이 운영하는 HSM 안에 머문다.

1.2 Key Link 가 제공하는 4 features

Fireblocks 공식 문서가 Key Link 사용 시 활용 가능한 platform feature 를 명시한다:

  • Robust wallet management capabilities — Vault / Asset Wallet / Deposit Address 의 5-level 계층 운영
  • Built-in node infrastructure — Fireblocks 가 운영하는 RPC / node 자원 활용
  • Governance engine — Admin Quorum / Approval Group / Policy rule
  • Transfer network — Fireblocks Network 의 counterparty 간 transfer
  • Automated compliance functionality — travel rule, screening 등

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)

1.3 키 share 가 어디에 있는가 — 3-product line 비교

Fireblocks 의 3 product line 의 trust boundary 차이를 정리.

SaaS MPCHosted MPCKey Link
Fireblocks Cloud 의 키 share 1 개 (3-party MPC 의 1) 1 개 0 개
고객 측 인프라의 키 share 0 개 (Mobile app 은 별도) Co-signer 1 개 HSM 1 개 (실제 키 전체)
Mobile app 의 키 share 1 개 1 개 0 개 (Mobile = onboarding / approval 용)
키 reconstruction 가능자 3-party 가 협력해야 가능 3-party 협력 고객 단독 (HSM 안에서)
분산 신뢰 모델 Threshold (t-of-n) Threshold 단일 신뢰점 (고객 HSM)

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview · Hosted MPC Workspace Configuration)

키 share 0 의 함의

Key Link 는 분산 MPC 가 아닌 중앙집중 HSM 모델이다. Threshold cryptography 의 "키 share 가 한 곳에 모이지 않으므로 단일 침해로 키 노출 불가" 성질이 없다. 대신 HSM 자체의 tamper resistance + FIPS 인증 + 키 export 불가능성이 안전성의 근거다.

즉 Key Link 는 "MPC 와 등가의 보안 모델" 이 아니라 "다른 종류의 보안 모델" 이다 — 저자 해석. 어느 쪽이 더 안전한지는 위협 모델에 따라 다르며, 규제 / 보험 / 내부 정책의 요구에 따라 선택해야 한다.

1.4 2-key paired plane — Validation + Signing

Key Link 는 한 vault 의 키 운영을 위해 2 가지 별도 키를 사용한다.

Validation KeySigning Key
역할 새 Signing Key 등록 권한의 증명 실제 거래 서명
저장 위치 고객 HSM 또는 FIPS 장비 고객 HSM 또는 FIPS 장비
등록 방식 Approval Group (default Admin Quorum 또는 위임 group) 의 quorum 승인 → Fireblocks 등록 Active Validation Key 의 서명 (x509 cert) 첨부 → Fireblocks 등록
quorum 매개 횟수 등록 시 1 회 (quorum 매개) 등록 시 quorum 매개 불필요 — Validation Key 의 서명만으로 자동 등록
알고리즘 ECDSA 또는 EdDSA (Ed25519 예시 코드 명시) ECDSA 또는 EdDSA
역할 비유 (저자) Intermediate CA 의 root cert 의 권한 End-entity cert

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

왜 2-key 인가 — 등록 자동화의 이유

Validation Key 가 따로 있는 이유는 대량의 Signing Key 를 효율적으로 등록하기 위함이다. 만약 모든 Signing Key 등록마다 Mobile app 의 Admin Quorum quorum 을 거치면 운영 부담이 커진다. Validation Key 를 한 번 등록해두면, 이후 새 Signing Key 는 Validation Key 의 서명만으로 자동 등록된다.

이 패턴은 PKI 의 Intermediate CA 와 유사하다 (저자 해석). Root quorum 으로 Intermediate (Validation) 권한을 위임하고, Intermediate 가 다수 end-entity (Signing) 를 발행하는 구조.

1.5 Workspace type — Key Link 는 별도 type

Fireblocks 의 workspace 는 다음 type 으로 분류된다 (저자 정리):

  • SaaS MPC workspace — Fireblocks Cloud + Mobile app 기반 MPC
  • Hosted MPC workspace — 고객 인프라에 Co-signer 설치한 MPC
  • Cold Wallet workspace — SaaS MPC 의 cold variant (별도 product, Admin Quorum 단독)
  • Key Link workspace — customer-held HSM 기반

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview · Cold Wallet 관련 공식 문서 · Hosted MPC Workspace Configuration)

이 type 들은 workspace 생성 시 결정되며 immutable. 즉 Key Link workspace 를 SaaS MPC 로 변환하거나 그 역은 불가능 — 저자 추정 (Hosted MPC 의 immutability invariant 가 architectural symmetry 로 확장).

"You must open and configure a new workspace for a Hosted MPC setup, as modifying an existing SaaS MPC workspace is impossible."

(출처: Fireblocks 공식 문서 — Hosted MPC Workspace Configuration; Key Link 자체의 immutability 직접 명시는 미확보)

→ 은행이 Key Link 도입을 결정하면 1-way door 로 간주해야 한다. 마이그레이션은 새 Key Link workspace 생성 + cross-workspace asset transfer 가 유일한 경로.

1.6 Vault Account 의 키 할당 룰

Key Link workspace 의 vault account 는 algorithm 별로 1 키만 할당 가능:

  • 각 vault account 에 ECDSA 1 키 + EdDSA 1 키 까지 할당
  • 한 키는 한 vault 전속 — 다른 vault 에 재사용 불가
  • auto-assignment 옵션 (생성 시 pool 에서 자동 할당) 또는 manual 할당
  • 키 미할당 시 해당 algorithm 의 asset wallet 생성 불가 (Console 에 warning 표시)

(출처: Fireblocks 공식 문서 — Set up your Fireblocks Vault with Key Link)

운영 함의 — vault 1 개 = HSM 안의 2 키

이 룰의 함의:

  • HSM 안에 키 쌍이 vault 수만큼 누적 — 1,000 vault = 최대 2,000 키. HSM 의 키 슬롯 capacity 와 backup 부담 고려 필요
  • vault 단위 segregation 이 자연스럽다 — 고객 단위 vault 분리 시 키도 단위로 분리됨
  • 키 마이그레이션 = vault 마이그레이션 — 키 한 개를 다른 vault 로 옮길 수 없으므로, vault 통합/분리가 곧 키 단위 작업

1.7 키 share 가 0 이라는 것의 의미

"Fireblocks 는 키 share 를 0 개 보유한다" 는 진술은 다음을 의미한다 (저자 해석):

  • 물리적: Fireblocks Cloud 의 DB / TEE / 코드 어디에도 키 material 이 저장되지 않는다
  • 운영적: Fireblocks 가 단독으로 거래 서명을 만들어낼 수 없다. 모든 서명은 고객 HSM 에서 수행
  • 법적 (KR 가상자산이용자보호법): "이용자 가상자산의 통제권" 이 고객 (은행) 에게 있다는 주장의 근거 — 단 대법원 2024도10710 의 "실질 통제" 판단 기준 충족 여부는 별도 검토 필요
  • 침해 시: Fireblocks Cloud 가 침해되어도 키가 직접 노출되지 않는다 (대신 governance plane 침해, 트랜잭션 위조 시도 가능성은 별도 risk)
단, Validation Key 의 위치는 별도 risk

키 share 0 invariant 가 깨지지 않더라도, Validation Key 가 침해되면 새 Signing Key 등록 권한이 탈취된다 (Risk-KL04). Validation Key 도 HSM 안에 두는 것이 권장 — 단 Fireblocks 공식 문서에 Validation Key 보관 위치의 explicit 권장은 미확보.
