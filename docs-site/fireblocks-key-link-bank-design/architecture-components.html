2. 아키텍처 구성요소

Fireblocks Key Link 의 핵심 컴포넌트는 4 가지: Fireblocks Agent, Customer Server, HSM Component, HSM Adaptor (선택). 이 페이지는 각 컴포넌트의 책임과 토폴로지를 정리한다.

  • Fireblocks Agent = open-source TypeScript on-prem service — Fireblocks Key Link Overview
  • Customer Server 가 custom logic (policy / validation) 추가 가능 — Fireblocks Key Link Overview
  • HSM Adaptor 는 optional, cold HSM 통신 매개 — Fireblocks Key Link Overview

저자가 합리적으로 추정한 운영 권장 — 참고용

  • 은행 환경에서 권장 토폴로지 (망분리 IDC 안 배치)
  • Customer Server 의 HA / DR 구성 권장
  • 각 컴포넌트 간 네트워크 보안 권장 (mTLS / firewall rule)
  • 각 컴포넌트의 정확한 호스팅 사양 / 리소스 요구사항은 본 문서 미확보 — 공식 README 별도 확인 필요

2.3 Fireblocks Agent — 통신 중계자

"Fireblocks Agent is an open-source on-prem service (TypeScript) responsible for receiving new messages to sign from Fireblocks, relaying these messages to the customer's HSM through the customer's server, and returning the signed results to Fireblocks."

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

2.3.1 책임

  • Fireblocks Cloud 로부터 서명 요청 메시지 수신 (poll 또는 push)
  • 메시지를 Customer Server 로 중계
  • Customer Server 에서 받은 서명을 Fireblocks 로 반환
  • API user (Signer role) 와 페어링되어 본인 인증

2.3.2 운영 특성

  • 오픈소스 — 코드 자체가 공개되어 있어 코드 검증 가능. 단 운영 책임 (security patch, version 업데이트) 은 고객 부담
  • on-prem 서비스 — 고객 인프라 안에 설치 (망분리 IDC 가능)
  • TypeScript 기반 — Node.js 런타임 필요. on-prem 환경에 Node.js 운영 부담 추가
  • API user 와 페어링 — Console 에서 Signer role 의 API user 생성 → Admin Quorum 승인 → pairing token 으로 Agent 와 페어링

(출처: Fireblocks 공식 문서 — Getting Started with Fireblocks Key Link)

Risk-KL02 — Agent 운영 부담

오픈소스 = 고객의 운영 부담 + version 호환성 책임이 고객. Fireblocks 의 minimum-version 강제 / security patch 일정이 공식 문서에 미명세. 은행은 자체적으로 Agent version 추적 / patch 적용 정책을 수립해야 한다 — 저자 권장. Risk-KL02 참조.

2.4 Customer Server — 비즈니스 로직 계층

"Customer Server: Developed and hosted by the customer. Receives messages to sign from the Fireblocks Agent, signs the messages via the customer's HSM, and relays them back to Fireblocks. The customer server can have any custom logic (e.g., custom on-prem policy, transaction validation, etc.) to approve or reject transaction signing requests."

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)

2.4.1 책임

  • Agent 로부터 메시지 수신
  • HSM 에 서명 요청 (online: 직접 PKCS#11 / vendor SDK / cold: HSM Adaptor 경유)
  • 서명 결과를 Agent 로 반환
  • (선택) custom logic: 자체 transaction validation, on-prem policy 적용, 승인/거절 결정

2.4.2 운영 특성

  • 고객이 직접 개발 / 호스팅
  • Customer Server 가 down → 모든 서명 중단 (Risk-KL01: Single Point of Failure)
  • HSM 과의 통신 protocol 은 고객 결정 (PKCS#11, vendor SDK, REST API 등)
  • Custom policy 가 Fireblocks Policy rule 과 별개로 작동 — 이중 정책 관리 가능 / 부담
Risk-KL01 — Customer Server SPOF

Customer Server 가 단일 장애점. Fireblocks 공식 문서에 HA / failover 권장이 명시되지 않음. 은행은 자체적으로 active-active 또는 active-passive HA 구성 + 모니터링 권장 — 저자 추정. Risk-KL01 참조.

2.5 HSM Component — 실제 키 보관

"HSM Component: The actual HSM implementation. Can be on-prem, cloud-based, hot or cold HSM, or a different Key Management System."

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)

2.5.1 지원되는 HSM 종류

  • On-prem HSM — 망분리 IDC 안 (KR 은행 권장)
  • Cloud HSM — AWS CloudHSM, Azure Dedicated HSM, GCP Cloud HSM
  • Hot HSM — 항상 online, network 연결
  • Cold HSM — air-gapped, USB / SFTP / data diode 경유
  • 기타 KMS — "different Key Management System" 명시 (FIPS-compliant 장비면 HSM 이 아니어도 통합 가능)

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview · Getting Started with Fireblocks Key Link)

2.5.2 Reference HSM — Thales Luna

Fireblocks 가 공식 블로그 (2025-09-23) 에서 reference HSM 파트너로 Thales Luna HSM 을 명시.

"At the heart of this solution is Fireblocks KeyLink, our secure middleware layer that connects the Fireblocks platform to Thales Luna Hardware Security Modules (HSMs)."
  • FIPS 140-3 Level 3 + Common Criteria 인증 — 금융권 / 공공기관 표준
  • PQC (post-quantum cryptography) 대응 — 양자컴퓨터 시대 대비 알고리즘 지원
  • "crypto agility" — 알고리즘 교체 유연성
  • "Institutions maintain full key ownership" — 키 share 0 invariant 의 vendor 강조

(출처: Fireblocks 공식 블로그 — Enterprise Digital Asset Security with Fireblocks and Thales, 2025-09-23 by Adam Levine)

왜 Thales Luna 가 reference 인가

공식 블로그에서 Fireblocks 가 명시한 점:

  • 금융권 (HKMA · HKSFC · JFSA) 의 인증 표준 충족
  • Crypto agility — 새 알고리즘 도입 시 HSM 교체 없이 펌웨어 업데이트 가능
  • PQC readiness — NIST 표준 후보 알고리즘 대응 가능
  • Air-gapped workflow 지원 (USB · SFTP · data diodes)

2.6 HSM Adaptor (선택) — Cold HSM 통신 매개

"HSM Adaptor: An optional separate component that can, for example, communicate with an offline (cold) HSM. An online HSM setup can be part of the customer server code or a separate component."

(출처: Fireblocks 공식 문서 — Fireblocks Key Link Overview)

2.6.1 언제 필요한가

  • Cold HSM 운영 시 — Customer Server 와 HSM 이 직접 네트워크로 연결되지 않을 때
  • Air-gapped 환경 — USB / SFTP / data diodes 경유 transport 필요
  • 물리적 격리 정책 — HSM 이 별도 보안 구역 (vault, safe room) 안에 위치

2.6.2 Online HSM 일 때

  • Customer Server 가 직접 HSM 과 통신 (PKCS#11 / vendor SDK)
  • HSM Adaptor 불필요 — 공식 문서가 "An online HSM setup can be part of the customer server code" 명시
Risk-KL05 — Cold HSM latency

HSM Adaptor 가 cold (offline) HSM 과의 통신 매개. Cold HSM 의 정확한 signing latency / batching 패턴이 공식 문서에 미명세. Air-gap transport (USB / SFTP / data diodes) 까지는 vendor 블로그에서 부분 확인되었지만, latency 수치는 여전히 미공개 — Risk-KL05 참조.

은행 망분리 IDC 안의 권장 배치 (저자 추정). 파랑 = Fireblocks SaaS / 초록 = HA 구성된 Agent · Customer Server / 보라 = Hot HSM (online) / 노랑 = Cold HSM + Adaptor (air-gapped). Agent 는 서비스망 (DMZ) 에 배치하여 Fireblocks Cloud 와 outbound HTTPS 통신. Customer Server 와 HSM 은 내부망 + 보안 구역에 격리.

은행 결정 사항 (5)
  1. Agent 위치 — DMZ vs 내부망. 망분리 정책 (전자금융감독규정 15조) 의 해석 필요
  2. Customer Server HA — active-active vs active-passive. Risk-KL01 의 SPOF 완화
  3. HSM 종류 — Thales Luna vs 다른 FIPS HSM. PQC / crypto agility 요구사항 평가
  4. Hot vs Cold 비율 — 가상자산업감독규정 9조의 콜드월렛 80% 충족 — 단 Cold HSM 의 air-gap 운영 비용 검토
  5. HSM Adaptor 자체 개발 vs 통합 — vendor 가 제공하는 air-gap transport tool 활용 가능 여부 (Thales 의 경우 별도 솔루션 존재 가능)
