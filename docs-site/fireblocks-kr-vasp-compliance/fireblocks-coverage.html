2. Fireblocks 가 직접 푸는 것 — 6 개 영역

Fireblocks 가 한국 VASP 의무를 설정만 잘 하면 충족시켜 주는 6 개 영역. "풀린다" 의 정확한 의미는 — Fireblocks 의 기능이 KR 의무 의 실행 메커니즘 (enforcement mechanism)으로 작동한다는 뜻이며, 설계·정책·운영의 책임은 여전히 사업자에게 있다.

"직접" 의 의미 — 어디까지가 도구이고, 어디부터가 사업자 책임

"Fireblocks 가 직접 푼다" 는 다음을 의미:

  • Fireblocks 에 해당 기능이 존재하고 — 운영 console 또는 API 로 활성 가능
  • KR 의무의 기술적 실행 단계에서 Fireblocks 가 차단·감사·검증을 수행
  • 적정 설정 하에서 사업자가 의무를 "지키지 못한" 상태를 자동 방지

다음은 의미하지 않음:

  • 사업자의 자체 정책 결정·조직 설계·인사 책임자 지정 없이 작동하지 않음
  • 설정 오류 / 운영 부주의를 도구가 자동 보정해주지 않음
  • 한국 규제 당국이 "Fireblocks 사용 = 컴플라이언스 인정" 으로 보지 않음

2.2 거래 정책 엔진 (TAP) — 거래제한·입출금 차단

충족되는 KR 의무

  • 거래제한 (특금법 8 + 시행령 10조의20): 고객확인 완료 전 출고·이체·교환 차단
  • 입출금 차단의 정당한 사유 (이용자보호법 시행령 2025-04-23): 정보통신망 장애, 거래지원 종료, AML 의심, 전기통신금융사기 72시간 등

Fireblocks TAP 의 작동 방식

TAP 은 각 트랜잭션에 대해 first-match 로 평가되는 rule 의 list. 한국 의무를 다음 패턴으로 매핑: 

# Rule 1 — KYC 미완료 차단 (특금법 8 + 시행령 10조의20)
IF source.kyc_status != "completed"
   THEN BLOCK

# Rule 2 — 미신고 VASP 차단 (특금법 8 + 시행령 10조의20 ④)
IF destination NOT IN whitelist_kr_vasp
   AND destination IN denylist_unregistered_vasp
   THEN BLOCK

# Rule 3 — 트래블룰 임계 (시행령 10조의10)
IF amount >= KRW 1,000,000
   AND travel_rule_message_status != "delivered"
   THEN BLOCK

# Rule 4 — 전기통신금융사기 의심 시 72시간 차단 (이용자보호법 시행령)
IF flagged_by_anti_fraud_system
   THEN HOLD_FOR_72H

# Rule 5 — 영업종료 절차 (이용자보호법 시행령)
IF workspace.mode == "winddown"
   THEN BLOCK ALL OUTGOING

# Last Rule — block-all (Fireblocks default, 삭제 불가)
ELSE BLOCK

한계 — TAP 만으로 부족한 것

  • 고객확인 (KYC) 자체의 신원증명 검증은 외부 KYC 시스템. Fireblocks 는 결과만 받음
  • 전기통신금융사기 의심 신호는 외부 anti-fraud / chain analytics 가 보내야
  • Rule ordering 의 first-match brittleness — 운영 review 시 ordering check 필수
  • Custom Policy 도입 시 default Policy 의 implicit allow 가 모두 사라짐 (one-way) — 누락 시 silently block

2.3 AML / Travel Rule 통합 — 3 사 provider

충족되는 KR 의무

  • 미신고 VASP 거래금지 (특금법 8 + 시행령 10조의20 ④): counterparty due diligence
  • 트래블룰 (시행령 10조의10): 100만원 이상 상당 출고 시 송·수신인 이름 전송
  • STR 의심거래보고 (특금법 4): 의심거래 탐지의 source 데이터

Fireblocks 가 통합 지원하는 provider

Step 5b · 5c 의 AML / Travel Rule 검증이 Policy Engine (Step 6) 보다 먼저. 미통과 시 거래는 6 단계에 진입 안 함. 빨강 = compliance 게이트 / 노랑 = 사전 처리 / 초록 = 서명·제출 단계.

한계 — Fireblocks 가 직접 KYC 를 하지 않는 영역

  • 고객 신원확인 (KYC) 자체 — Fireblocks 는 KYC 모듈을 제공하지 않음. 사업자가 외부 KYC 시스템 (NICE · 신용평가사 · 자체 시스템) 으로 처리한 결과를 source.kyc_status 로 받음
  • STR 보고서 작성·제출 — Fireblocks 는 screening 결과를 제공할 뿐. 보고서 양식·KoFIU 시스템 제출은 사업자
  • 3 provider 모두 별도 계약 + 별도 비용. Fireblocks 가 통합 채널만 제공, provider 와 직접 계약 필요
  • Workspace-level AML default 가 fail-on-unknown 인지 pass-on-unknown 인지에 따라 결과가 갈림. KR 환경은 fail-on-unknown 강제 권장

2.4 Whitelist — counterparty 통제

충족되는 KR 의무

  • 미신고 VASP 와 거래금지 — 화이트리스트 / 블랙리스트 양방향 통제

패턴 — 인가 VASP 화이트리스트

한국 인가 VASP 27 개사 (2025 하반기 기준) 의 hot wallet 주소를 사전 whitelist 로 등록. 

# Approval Group 또는 Policy 의 destination whitelist
whitelist_kr_vasp = [
  Upbit hot wallets (등록 주소 다수),
  Bithumb hot wallets,
  Coinone hot wallets,
  Korbit hot wallets,
  ... (인가 VASP 27 개 hot wallet)
]

# 미등록 destination 으로의 출금은 별도 strict review
IF destination NOT IN whitelist_kr_vasp
   THEN require Admin Quorum + manual review

한계 — Whitelist 운영의 함정

  • 인가 VASP 의 hot wallet 주소는 변경됨. 일일·주간 갱신 절차 필요
  • 새 VASP 가 신고 수리 받으면 whitelist 에 추가 — 인사 책임자 + 변경 절차 정의
  • Counterparty 가 한 번에 여러 주소 보유 시 모두 등록 필요 (sweeping pattern)
  • Whitelist 변경 자체가 Admin Quorum 승인을 거쳐야 (감독규정 9 의 운영통제)

2.5 Audit Log — 거래 audit trail

충족되는 KR 의무

  • 기록보존 5년 (특금법 5조의4): KYC 사본, 로그, 승인 흐름, 차단·해제 근거
  • STR 의심거래보고의 evidence base
  • 거버넌스 변경 audit: user add/delete, 2FA reset, IP allowlist 변경, threshold 변경

Fireblocks Audit Log 의 20+ 이벤트 카테고리

Vault Accounts / Workspace Key Backup / Gas Station / Cold Wallet (signature quota) / Policy / TAP / Admin Quorum / Approval Group / User / API / Webhook / Transaction / Compliance / Settings / Auth / Recovery / Co-signer / Mobile / Console / SSO 등.

한계 — Audit Log 만으로 5년 보존이 되지 않음

  • Fireblocks 의 Audit Log 보관 기간 자체는 vendor 측 운영 — 사업자의 5년 archive 책임을 vendor 가 대신 지지 않음
  • 사업자는 Audit Log 를 정기적으로 export · 자체 archive 시스템에 적재해야
  • Audit Log 접근 권한이 Owner / Admin / Non-Signing Admin 에 한정 (Security Auditor 직접 접근 불가) — 포렌식 시 Admin 협조 필요
  • "Less than 10% remaining signatures" 같은 Cold Wallet 특수 이벤트는 별도 alert 등록 필요

2.6 MPC 거버넌스 — Admin Quorum + 9-role

충족되는 KR 의무

  • 이해상충 방지 — Signer ≠ Approver 분리 (이용자보호법 정신)
  • 다중 승인 강제 — Admin Quorum threshold 로 단독 결정 방지
  • 책임자 분리 — 9 user role 로 권한별 분리

9 user role 의 한국 의무 매핑

Fireblocks role한국 운영상 권장 매핑
Owner대표이사 또는 컴플라이언스 최고책임자
Admin운영·재무 임원 (다수)
Non-Signing Admin감사 / 보고책임자 / 준법감시인

Security Admin정보보안 책임자 (ISMS)
Security Auditor외부 감사 / 평가전문기관 인력

Admin Quorum threshold 권장

  • 최소 threshold ≥ 2 — Owner SPOF 완화 (단독 결정 방지)
  • API Admin 보유 시 threshold ≥ 3 — API Admin 의 자동 approve 효과 (quorum -1) 완화

한계 — 거버넌스 도구의 한계

  • Cold Wallet workspace 는 Approval Group 미지원 → Admin Quorum 단독 운영. 운영 부담 증가
  • 인사·조직 설계 (누구를 Owner 로 두고, Signer ≠ Approver 가 실제 분리되어 있는지) 는 사업자 책임
  • Owner 부재 시 Owner transfer 절차 (3–5 영업일 + Fireblocks Support 영상통화) — 비상 대응 사전 시뮬레이션 필요
  • Yubikey 채택 시 모든 신규 사용자에 강제 (Risk-S11) — 조직 IT 정책과 정렬 필요

2.7 Workspace 격리 — Hot/Cold + 다중 workspace

충족되는 KR 의무

  • 분리보관 (이용자보호법): 자기 자산 ≠ 고객 자산 — workspace 분리
  • 콜드월렛 80% 의 인프라 — Cold Wallet workspace
  • 역할별 운영 분리 — Administrative / Operational / Custodial 3-workspace 패턴

권장 workspace 토폴로지

한계 — Workspace 격리만으로 부족한 것

  • "고객 자산 의 80% 가 cold 에 있다" 의 검증은 사업자의 일일 reconciliation 에서 일어남. Fireblocks 는 vault balance 만 보여줌
  • 경제적 가치 환산 (시세 적용) 는 사업자가 자체 시세 source 로 계산
  • Workspace type 은 immutable — 한 번 Cold 로 만들면 Hot 으로 변환 불가. 도입 결정은 1-way door
  • Workspace 내 default visibility — 모든 user 가 모든 vault 가시. 권한 분리는 workspace 단위로만

2.8 본 페이지의 정직한 표현 — "도구는 있다, 책임은 그대로다"

위 6 개 영역에서 Fireblocks 는 KR 의무의 실행 도구를 제공한다. 하지만 다음은 변하지 않는다:

  • 설정 오류 / 정책 누락 / 운영 부주의의 책임은 사업자에게
  • 금감원 종합검사에서 Fireblocks 사용 사실이 면책 사유가 되지 않음
  • 인사 책임자 (보고책임자 · 준법감시인 · 대표이사) 의 개인 제재 가능성은 도구 사용과 무관
  • 4 종합검사 사례에서 보듯, 도구의 부재가 아닌 운영 통제의 부재가 위반의 원인
