3. Fireblocks 가 거드는 것 — 부분 해결 6 영역

KR 의무 중 Fireblocks 가 일부분만 풀어주는 영역. 도구는 있지만 외부 시스템 통합·사업자 운영·회계·인사 결정이 함께 작동해야 의무가 충족된다. 이 부분이 "Fireblocks 도입해두면 알아서 풀린다" 라는 오해가 가장 많은 영역이기도 하다.

"부분" 의 의미

"부분 해결" 은 다음 중 하나 이상에 해당:

  • Fireblocks 가 일부 데이터·기능만 제공하고, 나머지를 사업자가 외부 시스템에서 처리
  • Fireblocks 의 출력값을 사업자가 자체 ledger 또는 회계 시스템에서 검증해야 의무가 충족됨
  • 도구는 있으나 설계·운영·조직 결정이 사업자에게 100% 위임됨

3.2 고객확인 (KYC/CDD) — 외부 KYC 의존

KR 의무

특금법 5조의2:

  • 주민등록번호 등 법정 고객확인정보 수집
  • 원본성 있는 신분증 확인 — 운전면허증 암호일련번호 미검증 사례가 두나무 제재 사유
  • 주소 검증
  • 재이행 주기 관리 — 만료 자동락
  • 위험등급 상향 시 추가 CDD

Fireblocks 의 역할 — KYC 결과의 소비자

Fireblocks 자체는 KYC 모듈을 제공하지 않는다. 사업자는 외부 KYC 시스템으로 신원 확인을 수행하고, 그 결과를 Fireblocks 트랜잭션 entity 의 metadata (예: customerInternalId 와 연결된 KYC status) 로 전달.

KYC 의 신원확인은 외부 시스템에서, 거래 차단의 enforcement 는 Fireblocks TAP 에서. 두 시스템 간 sync 단절이 가장 큰 위반 위험. 초록 = 정상 통과 / 빨강 = 차단 / 노랑 = 판정 단계 / 파랑 = 외부 source.

사업자가 채워야 하는 것

  • 외부 KYC 시스템 선정·통합 (NICE / KCB / 자체 / 글로벌 vendor 등)
  • 원본성 검증 로직 — 단순 사진이 아닌 OCR + 안티 위변조
  • 주소 검증 — 우편번호·도로명·실 거주지 확인
  • 재이행 주기 자동화 — 만료 전 사전 알림 + 만료 시 자동 락
  • 위험등급 산출 로직 — 거래 패턴·기관 정보·blacklist 결합
  • KYC 미완료 고객의 거래 시도 시 거절 사유 로깅

3.3 STR — 의심거래보고

KR 의무

특금법 4. 의심거래 발견 시 KoFIU 보고. 보고책임자 승인 + 5년 보존.

Fireblocks 가 주는 것

  • AML provider screening 결과 — Chainalysis · Elliptic 의 risk score, 라벨
  • Audit Log — 거래 시도·차단·해제의 전 흐름
  • Webhook — 의심 거래 감지 시 외부 시스템으로 알림

사업자가 채워야 하는 것

  • STR 보고서 작성 양식 — KoFIU 제출용
  • 보고책임자 지정 + 보고책임자의 승인 흐름
  • 내부 escalation matrix — 누가 first review, 누가 final decision
  • KoFIU 시스템 직접 제출 (Fireblocks 가 제출하지 않음)
  • 의심거래 판단 기준 — chain analytics + 거래 패턴 + 고객 위험등급 결합 룰

3.4 기록보존 5년 — vendor archive 와 사업자 archive 분리

KR 의무

특금법 5조의4. 보고·고객확인·정보제공 등 의무이행 관련 자료 및 정보를 금융거래 등 관계 종료 후 5년간 보존.

Fireblocks 가 주는 것

  • Audit Log — 거래·승인·설정 변경의 전체 흐름 (vendor 측 보관)
  • Transaction history — REST API 로 export 가능
  • Webhook event payload — 실시간 archive 의 source

사업자가 채워야 하는 것 — vendor 보관에 의존 금지

  • 정기 export 자동화 — 일/주 단위. Fireblocks 의 Audit Log 보관 기간 한도에 의존하지 말 것
  • 자체 archive 인프라 — 5년 retention, immutable storage (WORM 또는 ledger-style)
  • KYC 사본 보존 — 외부 KYC 시스템에서 받은 신분증 사본 등 (Fireblocks 가 보유하지 않음)
  • 차단·해제 근거 기록 — TAP rule trigger 이력 + 인적 승인 흐름
  • 해지 / 거래 종료 시점 기록 — 5년 카운트 시작점
왜 vendor 보관에 의존하면 안 되나

Fireblocks 가 계약 해지·서비스 중단·정책 변경 시 사업자가 audit data 를 잃을 수 있음. KR 감독 당국은 사업자에게 "자체 보존" 책임을 부과 — vendor 가 가지고 있다고 항변 못함. 빗썸 제재 (2026-03) 의 자료보존 위반이 직접 사유.

3.5 분리보관 + 동종·동량 — Workspace 분리는 가능, 회계 분리는 별개

KR 의무

이용자보호법 (2024-07-19 시행):

  • 이용자 가상자산과 자기 가상자산을 분리하여 보관
  • 이용자 가상자산과 동종·동량의 가상자산을 실질적으로 보유

Fireblocks 가 주는 것

  • Workspace 분리 — 자기 자산 workspace ≠ 고객 자산 workspace
  • Vault Account 분리 — workspace 내부에서 고객별 / 자산별 vault
  • Vault balance — 실시간 잔액 조회 API

사업자가 채워야 하는 것 — 회계 분리는 application layer

  • 재무회계 상 분리 — Workspace 분리가 곧 회계 분리는 아님. 회사 자산 vs 고객 자산을 회계 시스템에서 분리 처리
  • 일일 reconciliation — Fireblocks vault balance ↔ 자체 ledger 의 일치 검증
  • 동종·동량 검증 — 고객 BTC 잔액 합계 = vault 의 BTC balance 인지 매일 확인
  • 회계 기준 결정 — sweeping 중간 시점, fee 차감, gas station 이체 등의 회계 처리 기준
  • 외부 감사 대응 — 분리보관·동종동량의 증빙 자료 (vault balance 일별 snapshot 등)

3.6 콜드월렛 80% — 인프라는 있다, 검증은 별개

KR 의무

가상자산업감독규정 9 — 이용자 가상자산의 경제적 가치 기준 80% 이상을 인터넷과 분리하여 보관. 시행령 11 의 위임 ("이용자 가상자산 중 70% 이상의 범위에서 금융위가 정하는 비율 이상").

Fireblocks 가 주는 것

  • Cold Wallet workspace — Hot 와 별도 product. 별도 구매 + 별도 인프라
  • Hot ↔ Cold rebalancing 경로 (P2P 또는 on-chain)
  • 각 workspace 의 vault balance API

사업자가 채워야 하는 것 — 비율 검증의 100%

"80% 가 cold 에 있다" 의 검증은 매일 사업자 시스템에서 일어난다. Fireblocks 는 답을 알려주지 않는다. 

# 사업자 자체 검증 로직 (예시)
daily_cold_ratio_check():
    hot_balance_usd = 0
    for vault in hot_workspace.vaults:
        for asset in vault.assets:
            hot_balance_usd += asset.amount * market_price(asset)

    cold_balance_usd = 0
    for vault in cold_workspace.vaults:
        for asset in vault.assets:
            cold_balance_usd += asset.amount * market_price(asset)

    total = hot_balance_usd + cold_balance_usd
    cold_ratio = cold_balance_usd / total

    if cold_ratio < 0.80:
        ALERT — 규제 위반. 즉시 Hot → Cold rebalancing
    log_to_archive(date, cold_ratio, evidence)

사업자가 결정해야 하는 것

  • 시세 source — 어느 거래소의 어느 시점 가격을 사용할 것인가
  • 이용자 자산만 계산 — 자기 자산은 80% 산정 대상이 아님. workspace 단위 회계 분리가 선결
  • 임계점 buffer — 시세 변동으로 80% 가 깨질 위험. 실무에서는 85% 또는 90% 보유로 buffer
  • Cold 으로의 rebalancing 주기 — 일·주 또는 임계점 기반
  • 외부 cold 인프라 옵션 — Fireblocks Cold Wallet 외에 별도 hardware cold 도 사용 가능 (혼합)

3.7 신규 서비스 AML 위험평가 — 도구는 있다, 위원회는 사업자가

KR 의무

특금법 5 + 시행령 9. 신규 상품·서비스 출시 전 AML 위험평가. 신규 토큰·신규 지갑 유형·staking·earn·NFT 지원 전 필수.

Fireblocks 가 주는 것

  • Sandbox workspace (Testnet) — 신규 자산·서비스의 격리 시험 환경
  • Workspace AML default 설정 — 신규 workspace 의 fail-on-unknown / pass-on-unknown 결정
  • FSPM (Fireblocks Security Posture Management) — 별도 add-on, AI 기반 attack simulator

사업자가 채워야 하는 것 — 제품승인위원회 + 위험평가서

  • 제품승인위원회 운영 — 보고책임자, 준법감시인, 지갑운영, 제품, 보안, 개발 참여. 4 종합검사 의 공통 권고
  • 위험평가서 양식 — 신규 자산의 chain risk, 거래소 risk, regulatory risk, technical risk
  • 법무검토 — 신규 토큰의 증권성·자본시장법 적용 여부
  • 출고정책 사전 설계 — 신규 자산의 trace-rule, address book, 카운터파티 화이트리스트
  • 승인 흐름 로깅 — 위원회 회의록, 위험평가서, 최종 승인 결재 — 5년 보존
2025-12 코빗 제재 — 신규 서비스 위험평가 미실시 655 건

코빗은 NFT 등 신규 거래지원 전 위험평가 미실시 655 건이 적발되어 기관경고 + 과태료 27.3억원. "Fireblocks 가 sandbox 를 주는데 왜 위반?" — sandbox 는 기술 검증 환경일 뿐, 위험평가서 작성·위원회 운영·법무검토 같은 조직 절차가 별개로 작동해야 한다는 점이 핵심.

3.8 부분 해결 영역의 공통 패턴

위 6 개 영역의 공통점:

  • Fireblocks 가 "기술 인프라" 만 제공한다는 사실의 인식이 필요
  • "의무 충족" 의 최종 검증은 사업자 자체 시스템 / 회계 / 조직에서 일어남
  • 도구 사용 사실은 제재 면책이 되지 않음 — 4 종합검사가 보여준 패턴
  • 위 6 영역 모두 운영 통제의 부재가 위반의 직접 원인 (도구 부재 아님)
