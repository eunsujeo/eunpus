6. 도입 통합 절차 — VASP 신고와 Fireblocks 도입의 병행

한국에서 새 VASP 사업을 시작하면서 Fireblocks 를 함께 도입할 때의 통합 절차. 신고제·실명계정·ISMS·법인 설립 같은 외부 절차와 Fireblocks workspace 구성을 어떻게 병행할지를 단계별로 정리.

6.1 전체 timeline — 누적 6–12 개월

신규 사업자의 일반적인 도입 timeline. 각 절차의 소요 기간은 사업자 규모·은행 협상력·인증 준비도에 따라 변동.

단계외부 절차Fireblocks 작업소요 기간 (개월)
① 법인 설립법무법인 + 등기소 + 정관(대기)1–3
② 사업모델 확정법무 검토 + VASP 평가workspace 설계 (개념)1

⑤ Fireblocks 도입—workspace 생성 + 정책 설정 + sandbox 시험1–2

③ 실명계정 + ④ ISMS + ⑤ Fireblocks 도입 + ⑥ KYC 시스템 통합은 모두 병행 가능. critical path 는 보통 ③ 실명계정 또는 ④ ISMS. Fireblocks 도입 자체가 critical path 가 되는 경우는 드물다.

6.2 단계별 체크리스트 — 외부 절차

① 법인 설립 단계 (1–3 개월)

  • ☐ 법인 형태 결정 (주식회사 권장)
  • ☐ 정관 작성 — 사업 목적에 "가상자산 보관·관리·이전" 명시
  • ☐ 자본금 결정 — 감독규정 / 보험 underwriting 요건 고려
  • ☐ 이사회 구성 — 보고책임자·준법감시인 별도 임명 가능 인원
  • ☐ 대주주 현황 정리 — 2026 개정안의 "대주주 범위 구체화" 사전 반영
  • ☐ 사업자등록증 발급

② 사업모델 확정 (1 개월)

  • ☐ 5 사업모델 평가 — 본 사이트 1.3 절 참조
  • ☐ "보관 또는 관리" / "이전" 행위 범위의 법무 검토
  • ☐ 대법원 2024도10710 ratio 적용 시 본인 모델의 VASP 평가
  • ☐ 원화 매매·교환 기능 포함 여부 — 실명계정 요건 결정
  • ☐ staking·earn·NFT 등 부수 상품 범위 — 유사수신행위법 검토
  • ☐ Cold workspace 사용 여부 (콜드월렛 80% 충족 전략)

③ 실명계정 발급 (2–6 개월)

  • ☐ 은행 선정 (신한·NH농협·케이뱅크·전북 중 — 2026 기준)
  • ☐ 사업자 제안서 + 사업계획 + 위험평가서 제출
  • ☐ 은행 AML 위험평가 응대
  • ☐ 계약 협상 (수수료·SLA·운영 정책)
  • ☐ 실명계정 발급 확인서 + 계약서 사본
  • ☐ 은행 AML 위험평가 서류 사본 (FIU 신고용)

④ ISMS / ISMS-P 인증 (6–12 개월)

  • ☐ 정보보호 정책 수립 (사내 인사·운영·기술 통합)
  • ☐ 위험평가 수행 — Fireblocks SaaS 도 평가 대상
  • ☐ 통제 항목 구현 (관리적·물리적·기술적)
  • ☐ 인증 기관 선정 (KISA 또는 ISMS-P 인증 기관)
  • ☐ 인증 신청 → 심사 → 인증서 발급
  • ☐ 사후 운영 (매년 사후심사 + 3 년 갱신)

⑦ FIU 신고서 작성 (1 개월)

  • ☐ 12 종 자료 준비 (1.5 절 참조)
  • ☐ 가상자산 취급 지갑주소 목록 — Fireblocks vault 의 모든 deposit address export
  • ☐ 정보보호 관리체계 인증서 (④)
  • ☐ 실명확인 입출금계정 발급 확인서·계약서 (③)
  • ☐ 은행 AML 위험평가 서류 (③)
  • ☐ 법령준수체계 자료 — 조직·인력·전산설비·내부통제체계 (Fireblocks 활용 포함)
  • ☐ 변호사 사전 검토

6.3 단계별 체크리스트 — Fireblocks 작업

⑤ Fireblocks 도입 (1–2 개월)

5.1 Customer Domain · Workspace 생성

  • ☐ Customer Domain 생성
  • ☐ Administrative workspace (Hot, Mainnet)
  • ☐ Operational workspace (Hot, Mainnet)
  • ☐ Custodial Hot workspace (Hot, Mainnet)
  • ☐ Custodial Cold workspace (Cold, Mainnet) — 별도 product 구매
  • ☐ Sandbox workspace (Hot, Testnet) — 신규 자산·서비스 시험

5.2 Owner · Admin Quorum 구성

  • ☐ Owner 임명 (workspace 별 — 보통 사내 임원 1명)
  • ☐ Admin ≥ 3 추가 (Cold workspace 의 경우 Support 경유 필수)
  • ☐ Admin Quorum threshold 설정 (최소 ≥ 2)
  • ☐ API Admin 보유 시 threshold ≥ 3 (Risk-G01)
  • ☐ Non-Signing Admin 임명 — 보고책임자·준법감시인 역할
  • ☐ Owner mobile device 등록 + recovery passphrase 안전 보관
  • ☐ Workspace Keys Backup 생성

5.3 9-role 인사 매핑

  • ☐ Signer ≥ 2 임명 (이해상충 방지)
  • ☐ Approver ≥ 2 임명 — Signer 와 별도 인원
  • ☐ Security Admin 임명 — 정보보안 책임자 (ISMS 책임자)
  • ☐ Viewer / Editor 최소화 (default visibility 함정)
  • ☐ 각 role 의 인사 발령장 + 책임 문서화 (이용자보호법 대응)

5.4 Policy / TAP 룰 구성

  • ☐ Rule 1 — KYC 미완료 차단 (source.kyc_status != ok → BLOCK)
  • ☐ Rule 2 — 미신고 VASP 차단 (destination NOT IN whitelist → BLOCK)
  • ☐ Rule 3 — 트래블룰 100만원 임계 (amount ≥ 1M KRW → require Notabene message)
  • ☐ Rule 4 — 전기통신금융사기 72시간 hold
  • ☐ Rule 5 — 영업종료 winddown 모드
  • ☐ Rule N — last block-all (default, 삭제 불가)
  • ☐ Rule ordering review — strict 룰이 앞에

5.5 AML / Travel Rule provider 통합

  • ☐ Chainalysis 또는 Elliptic 계약 + Fireblocks integration 활성
  • ☐ Notabene 계약 + integration 활성
  • ☐ Workspace-level AML default 를 fail-on-unknown 으로 설정
  • ☐ AML screening 결과의 Audit Log 적재 확인

5.6 Whitelist 등록

  • ☐ 인가 VASP 27 사 hot wallet 주소 일괄 등록
  • ☐ Hot ↔ Cold workspace 양방향 whitelist 등록
  • ☐ Whitelist 변경 절차 정의 — Admin Quorum 승인 필요
  • ☐ 일일 갱신 자동화 (인가 VASP 목록 변동 시)

⑥ KYC 시스템 통합 (1–3 개월)

  • ☐ 외부 KYC vendor 선정 (NICE / KCB / Sumsub / 자체)
  • ☐ kyc_status sync 인터페이스 — 실시간 / 일별 reconciliation
  • ☐ 위험등급 산출 로직
  • ☐ 재이행 주기 자동화 (만료 알림 + 자동 락)
  • ☐ 원본성 검증 + 주소 검증
  • ☐ KYC 사본 자체 archive (5년)

⑧ 운영 시뮬레이션 + 보완 (FIU 심사 3개월 동안)

  • ☐ Sandbox workspace 에서 end-to-end 거래 시뮬레이션
  • ☐ 입금·출금·sweep·rebalancing 의 단계별 검증
  • ☐ 의심거래 / 미신고 VASP 거래 시도 시 차단 검증
  • ☐ Audit Log 의 자체 archive 자동화 검증
  • ☐ DR rehearsal — Owner 부재 / Cold device 분실 시나리오
  • ☐ "Less than 10% remaining signatures" alert 검증 (Cold workspace)
  • ☐ KR 망분리 해석 검증 (Fireblocks Sales 와 직접 협의)

6.4 일상 운영 체크리스트 (영업 개시 후)

일별

  • ☐ Audit Log 추출 (Hot + Cold)
  • ☐ Hot 잔액 vs Cold 잔액 reconciliation
  • ☐ 콜드월렛 80% 비율 검증 + 자체 archive
  • ☐ 의심거래 review (TAP rule trigger)
  • ☐ "Less than 10% remaining signatures" alert 확인
  • ☐ Fireblocks status page 모니터링

주별

  • ☐ 인가 VASP whitelist 갱신
  • ☐ KYC 재이행 대상 점검
  • ☐ STR 후보 거래 escalation

월별

  • ☐ Recovery Passphrase Periodic Verification
  • ☐ Workspace Keys Backup 갱신 (인원 변경 반영)
  • ☐ 신규 자산·서비스 위험평가 위원회 (해당 시)
  • ☐ KR 특금법·이용자보호법·감독규정 변동 모니터링

분기/반기

  • ☐ Testnet 에서 DR rehearsal (production keys 사용 금지)
  • ☐ Cold device sign capacity audit
  • ☐ Admin Quorum 인원 audit + threshold 재검토
  • ☐ IP allowlist 갱신 (VPN·NAT 변경)
  • ☐ Policy / Whitelist 일관성 audit
  • ☐ KR 특금법 cold ratio + 5년 보존 reporting
  • ☐ FIU 변경신고 사항 점검 (대주주 변동, 임원 변동, 지갑주소 추가 등)

연 1회 또는 갱신 시

  • ☐ ISMS 사후심사 또는 갱신
  • ☐ 보험 갱신 — cold ratio 변동 반영
  • ☐ FIU 신고 갱신 (3 년 주기, 만료 45일 전)
  • ☐ 외부 감사 (회계 + 평가전문기관 취약점 평가)
  • ☐ 약관·마케팅 자료 법무 재검토

6.6 도입 결정 시 마지막 점검

Fireblocks 도입을 결정하기 전 다음 항목을 사전 확인:

  • ☐ Cold workspace 가 KR 망분리 해석에 부합하는지 — Fireblocks Sales 와 직접 협의 (7. 미해결 7.1)
  • ☐ Fireblocks SaaS 가 「금융회사의 정보처리 업무 위탁에 관한 규정」 의 외주 위탁 대상인지 — 법무 의견
  • ☐ ISMS 인증 시 Fireblocks SaaS 평가 방법 — 인증 기관 사전 협의
  • ☐ Cold MPC share 분포 모델 (Q-M05) — Fireblocks 측 답변 확보
  • ☐ Support SLA — Cold workspace user 추가 응답 시간
  • ☐ Workspace type immutability — 1-way door 인 점 사전 인식
  • ☐ MPC·멀티시그 사업자의 "실질 통제" 판단에서 Fireblocks 사용이 어떻게 평가되는지 — Q-CMP-08
  • ☐ Key Link + HSM 옵션 검토 — Fireblocks KeyLink ↔ Thales Luna HSM (FIPS 140-3 L3 + Common Criteria, PQC readiness) 통합 옵션. Vendor 공식 발표 2025-09-23. KR 미명시 (HKMA/HKSFC/JFSA 만 명시) — KR 적용 시 Fireblocks Sales 협의 필수
  • ☐ Hot/Warm/Cold 3-mode 의 정확한 의미 — vendor 가 "Hot, Warm, Cold signing workflows" 를 공식 framing 으로 사용. "Warm" 의 기술 정의 (Hot 와 Cold 의 중간 격리 수준) 사전 확인
  • ☐ Air-gap transport 메커니즘 — Cold workflow 의 USB · SFTP · data diodes 운영 환경 (망분리 IDC 안 설치 시 USB 정책 등)
