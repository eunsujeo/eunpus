0. 개요 · 통신 모델

Co-signer 가 Callback Handler 를 어떻게 호출하나, 그리고 그 사이에 proxy 가 여러 단 낄 때 무엇이 문제인가

이 가이드는 Fireblocks Co-signer 가 서명 전에 Callback Handler 를 호출하는 통신 경로를 다룬다. 특히 은행처럼 망 분리가 엄격한 환경에서 그 사이에 proxy 가 여러 단(중간 벤더·은행 등) 끼게 될 때, 무엇이 동작하고 무엇이 깨지는지, 그리고 각 주체의 책임을 어떻게 나눌지를 정리한다. 특정 기관이 아니라 "Co-signer 운영자 · 중간 벤더 · 은행" 역할 단위의 일반 reference 다.

본 페이지의 출처 — 셋으로 나눠 읽기
  • Fireblocks 공식 사실 (그대로 받아도 안전) — Co-signer 가 Callback Handler 서버의 SSL 공개키를 pin 한다는 점, 5가지 인증 옵션, Callback Handler 미설정 시 자동 서명(외부 검증 없음), 인증서 변경이 재페어링을 유발한다는 점. Fireblocks 공식 문서에서 확인된 내용.
  • 일반 네트워크 지식 — L4/L7 의 차이, TLS 종료(terminate)가 pinning 을 깨는 원리, Squid 의 CONNECT 터널 동작. 표준 네트워킹 개념.
  • 저자의 설계 판단 (본인 환경 검증 권장) — 책임 분담(RACI)·운영 체크리스트·권고 토폴로지. "설계 포인트", "권고" 로 묶은 부분.

아직 공식 문서로 확정 못 한 항목(특히 Callback 응답 timeout·retry·idempotency 규격)은 "측정·합의 영역" 으로 분리한다 — 추정으로 메우지 않는다.

0.1 왜 Callback Handler 를 거치나 — 서명 전 정책 게이트

Co-signer 는 트랜잭션에 자동 서명하는 컴포넌트다(MPC key share 보유). 하지만 "무엇이든 자동으로" 서명하면 위험하므로, 서명을 진행하기 전에 Callback Handler 에게 "이 거래를 서명해도 되는가" 를 물어 외부 정책 검증을 받는다. Callback Handler 가 승인하면 서명이 진행되고, 거부하면 멈춘다.

★ Callback Handler 를 안 붙이면 — 무검증 자동 서명

Callback Handler 를 설정하지 않으면 Co-signer 는 외부 검증 없이 자동으로 sign/approve 한다(기본 동작). 즉 Callback Handler 는 "출금 정책(금액·주소·속도 제한)을 강제하는 관문" 이고, 수탁 지갑이라면 사실상 필수다. 그래서 이 통신 경로의 안정성이 곧 서명 파이프라인의 안정성이 된다.

0.2 통신 방향 — Co-signer 가 "클라이언트"

가장 먼저 잡아야 할 그림: Co-signer 가 요청을 보내는 쪽(client), Callback Handler 가 받는 쪽(server) 이다. 그래서 그 사이에 끼는 proxy 들은 Co-signer 에서 나가는(egress) 경로에 놓인다.

0.3 통신을 지키는 두 겹 — pinning + 메시지 서명

이 경로는 두 겹의 보안으로 보호된다. proxy 설계를 이해하려면 둘을 구분해야 한다.

보호 장치무엇proxy 경로와의 관계
SSL 공개키 pinningCo-signer 가 Callback Handler 서버의 SSL 공개키를 고정(pin) — 다른 인증서면 통신 실패경로에 민감 — 중간 proxy 가 TLS 를 풀면(terminate) 깨진다 (1장)
메시지 서명Co-signer 가 요청 메시지를 자기 private key 로 서명, Callback Handler 가 검증경로에 둔감 — 서명이 payload 에 실려, 전송 경로(proxy 단수)와 무관하게 검증

그리고 이 둘을 어떻게 묶을지가 5가지 인증 옵션으로 제공된다.

인증 옵션성격proxy 다단 내성
Public key (JWT)메시지(payload) 서명 검증높음 — 경로 독립적
Self-Signed Cert pinSSL 공개키 pinning낮음 — TLS 종료에 취약
Root-CACA 체인 검증중간 — 유효 체인 제시 시 통과
Hybrid (2종)위 조합구성에 따라
버전 의존성

인증 옵션 중 일부는 Co-signer 버전·환경 제약이 있다 — Root-CA·Hybrid 계열은 비교적 최신 Co-signer 버전이 필요하고, 일부 옵션은 SGX cosigner 전용이다. 옵션을 고르기 전에 운영 중인 Co-signer 의 버전·배포 형태(SGX/Nitro/GCP 등)를 먼저 확인하라.

0.4 이 가이드 읽는 법

  • 1. proxy 다단 · L4/L7 · passthrough — proxy 가 여러 단일 때 무엇이 깨지나. L4(투명 전달) vs L7(TLS 종료)의 차이, pinning 이 깨지는 조건, Squid 의 CONNECT 터널로 passthrough 하는 법, timeout 누적.
  • 2. 책임 분담 · 운영 — Co-signer 운영자 · 중간 벤더 · 은행의 RACI, 중간 벤더가 지켜야 할 것/하지 말 것, 운영 체크리스트와 모니터링 지표, 인증서 교체·timeout 같은 장애·변경 시나리오.
