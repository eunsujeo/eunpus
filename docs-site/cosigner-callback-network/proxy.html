1. proxy 다단 · L4/L7 · passthrough

proxy 가 여러 단일 때 무엇이 동작하고 무엇이 깨지나 — 핵심은 "TLS 를 푸느냐"

1.1 proxy 가 끼는 지점

은행 망 분리 환경에서는 Co-signer 가 Callback Handler 를 바로 호출하지 못하고, 중간 벤더 proxy → 은행 proxy 처럼 여러 단을 거치게 되는 경우가 흔하다. 통신 방향은 0장에서 봤듯 Co-signer 가 client 이므로, proxy 들은 그 egress(나가는) 경로에 일렬로 놓인다.

1.2 L4 vs L7 — "봉투만 보나, 편지를 여나"

proxy 의 동작은 OSI 계층으로 갈린다.

구분L4 proxy (전송 계층)L7 proxy (응용 계층)
보는 것IP + 포트 (봉투의 주소)HTTP 경로·헤더·본문 (편지 내용)
TLS(암호화)안 풂 — 암호문 그대로 전달(passthrough)푼다(terminate) — 복호화·재암호화
할 수 있는 일단순 전달, 포트 기반 분산경로 라우팅, 헤더 수정, 캐싱, WAF, 검사
대표 예TCP 로드밸런서, NLB, SNI 기반 전달nginx/Envoy reverse proxy, ALB, API gateway
비유우체부 — 봉투 주소만 보고 배달비서 — 편지를 열어 읽고 분류·가공

핵심 한 가지만 기억하면 된다 — "TLS 를 푸느냐(terminate)". 이게 pinning 의 생사를 가른다.

1.3 pinning 이 깨지는 조건

0.3에서 본 대로 Co-signer 는 Callback Handler 서버의 SSL 공개키를 pin 한다. 그래서 경로 중 누군가 TLS 를 푸느냐에 따라 두 결과로 갈린다.

Figure 1-2. pinning 의 생사. L4 passthrough(위) — proxy 가 암호를 안 풀어 은행 Callback Handler 의 진짜 인증서가 Co-signer 까지 도달 → pin 일치 → 동작(초록). L7 terminate(아래) — proxy 가 TLS 를 끊고 자기 인증서로 다시 맺어, Co-signer 가 보는 건 proxy 인증서 → pin 불일치 → 실패(빨강). 메시지 서명 인증(Public key JWT)을 쓰면 payload 에 서명이 실려 이 경로 문제에서 자유롭다(0.3).

정리 — 다단이어도 되는 조건
  • 경로의 모든 proxy 가 L4 passthrough 면 → pin 유지 → 단 수와 무관하게 동작.
  • 중간에 L7 로 TLS 를 끊는 proxy 가 하나라도 있으면 → pin 깨짐. 이때는 인증을 메시지 서명(Public key JWT) 으로 바꾸거나, 그 proxy 인증서를 pin 대상으로 조정해야 한다.
  • L7 은 헤더·경로 검사(WAF·감사)가 필요할 때 쓰게 되는데, 그게 바로 pinning 과 충돌하는 지점이다 — "검사하고 싶다(L7) vs 끝단 인증서를 지키고 싶다(pinning)" 의 trade-off.

1.4 passthrough 구성 — Squid CONNECT 터널

현장에서 흔히 쓰는 forward proxy 인 Squid 로 이 경로를 구성할 수 있다. Squid 는 HTTPS 요청에 대해 기본적으로 HTTP CONNECT 메서드로 TCP 터널만 뚫고 바이트를 그대로 흘려보낸다 — 즉 TLS 를 풀지 않는 passthrough 다.

Figure 1-3. Squid 의 CONNECT 터널. Squid 는 목적지 host:port(CONNECT 줄·SNI)만 보고 본문은 못 본다 — TLS 는 Co-signer ↔ Callback Handler 끝단끼리 end-to-end 라 pin 이 유지된다. 여러 단 Squid 라도 전부 CONNECT 터널이면 TLS 는 끝단끼리이므로 동작한다.

★ 단 하나의 함정 — SSL Bump

Squid 에는 ssl_bump(SSL Bump) 기능이 있는데, 켜면 Squid 가 TLS 를 중간에서 가로채 복호화(MITM) 한다 — 이게 바로 L7 terminate 다. 이 모드면 Co-signer 가 보는 인증서가 Squid 가 만든 가짜 인증서라 pin 이 깨진다. 즉 "Squid 는 되지만 SSL Bump 를 켜는 순간 안 된다." 지금 동작 중이라면 Bump 가 꺼진 순수 CONNECT 터널 구성일 것이다 — 보안팀이 트래픽 검사 목적으로 나중에 Bump 를 켜면 서명 전체가 멈출 수 있으니 그 구성을 고정·통지 대상으로 둔다.

1.5 timeout 누적 — 다단의 진짜 비용

pinning 이 살아 있어도, proxy 가 많으면 응답 왕복 지연이 누적된다. Callback Handler 가 제때 응답해야 Co-signer 가 서명을 진행하므로, hop 이 많을수록 응답 timeout 위험이 커진다.

timeout 규격은 공식 미명세 — 측정·합의 영역

Callback 의 timeout·retry·idempotency 규격은 Fireblocks 공식 문서로 확정돼 있지 않다. 즉 "몇 초 안에 응답해야 하는지" 를 문서로 단정할 수 없어, 운영 환경에서 직접 측정하고 각 proxy 구간의 지연 예산을 합의해야 한다. proxy 다단이면 이 여유가 빠르게 잠식되므로, hop 별 latency 예산(예: p99 상한)을 명시적으로 잡아 두는 것이 안전하다.

1.6 인증 방식으로 경로 내성 높이기

경로가 길거나 L7 검사를 피할 수 없다면, 0.3의 인증 옵션 선택으로 완화한다.

  • Public key (JWT) — 메시지 서명: 서명이 payload 에 실려 전송 경로(proxy 단수·종류)와 무관하게 검증된다. proxy 다단에 가장 강함.
  • Root-CA: 중간 proxy 가 유효한 CA 체인 인증서를 제시하면 통과 — L7 종료가 불가피한 환경의 절충.
  • Self-Signed Cert pin: 가장 단순하지만 경로에 민감 — 전 구간 L4 passthrough 가 보장될 때만.
설계 포인트
  • 전 구간 L4 passthrough 가 가능하면 → pinning(Self-Signed Cert) 그대로 두는 게 가장 단순.
  • 중간 L7 검사가 불가피하면 → 인증을 메시지 서명(JWT)으로 바꿔 경로 독립적으로.
  • 어느 쪽이든 timeout 예산을 hop 별로 수치화 — 규격이 미명세라 보수적으로 잡는다.
  • proxy 수 자체를 줄이는 토폴로지를 우선 검토 — Co-signer 배포 위치를 Callback Handler 에 가깝게 두면 중간 단을 없앨 수 있다.
