2. 책임 분담 · 운영

Co-signer 운영자 · 중간 벤더 · 은행이 각각 무엇을 책임지나, 그리고 무엇을 모니터링하나

2.1 먼저 — 중간 벤더의 "권한 경계"

경로를 passthrough(CONNECT 터널)로 두면, 중간에 낀 벤더가 할 수 있는 일과 못 하는 일이 구조적으로 정해진다. 책임을 정하기 전에 이 경계를 먼저 봐야 한다.

할 수 있음구조적으로 할 수 없음
CONNECT 목적지 host·port 확인서명 요청/응답 내용 읽기 (TLS end-to-end)
허용/차단(allowlist), 라우팅응답 위조 (메시지 서명 + pinning)
연결 메타데이터 관찰·로깅pinning 우회
지연·차단 (가용성 영향)무결성·기밀성 훼손
핵심 — 중간 벤더의 위협은 "가용성" 뿐

passthrough 인 한, 중간 벤더는 내용을 읽거나 바꾸거나 응답을 위조할 수 없다. 그들이 끼칠 수 있는 영향은 지연·차단(가용성) 하나다. 그래서 중간 벤더의 임무는 "투명하고 · 안정적이고 · 허용목록 기반인 전달" 로 수렴한다.

2.3 중간 벤더가 지켜야 할 것 / 하지 말 것

🔴 필수 (Must)
  • TLS passthrough 고정 / SSL Bump 금지 — Callback Handler host 에 대해 절대 TLS 종료(ssl_bump) 금지. 구성·정책으로 잠근다(1.4).
  • CONNECT allowlist — 출발지(상류) → 목적지(Callback Handler host:port)만 허용, 나머지 deny.
  • payload 무변조 — 헤더 추가/삭제·재작성 금지(암호문이라 불가하지만 정책으로 명시). 순수 전달.
  • 지연 예산 준수 — 자기 hop latency 상한(SLA)을 수치로 약속하고 지킨다(예: ≤Xms p99).
  • 가용성(HA) — proxy 이중화·health check. 단일 장애점 금지.
🟡 권장 (Should)
  • hop 간 인증 — 상·하류와 mTLS 또는 IP allowlist 로 구간 보호("누가 우리 proxy 를 쓰는가" 통제).
  • 관측성(복호화 없이) — CONNECT 목적지·바이트·latency·성공/실패·RTT 로깅. 장애 시 "어느 hop 에서 끊겼나" 추적용(내용 로깅은 불가·불요).
  • 용량 산정 — 피크 서명량(거래 1건 = Callback 요청 1건) 기준 동시 연결·throughput.
  • 요청 레벨 재시도 금지 — proxy 가 임의로 재시도하지 않기(중복 제출 위험). 멱등성은 양 끝단에 맡긴다.
⚫ 금지 / 사전 협의 (Must not / Coordinate)
  • 무통보 SSL Bump 활성 금지 — 트래픽 검사 목적이라도 Bump 를 켜면 pinning 이 깨져 서명 전체가 멈춘다.
  • 무통보 인증서·구성 변경 금지 — 자기 구간 인증서·SSL 정책 변경은 Co-signer 재페어링/통신에 영향. 변경창구·일정을 사전 합의.

2.6 (응용) vault 별 Callback Handler 라우팅

"vault 마다 다른 Callback Handler 를 호출"하고 싶을 때 — 예컨대 vault 별로 정책 운영 주체·서버가 다를 때 — 의 구성이다. Fireblocks 에는 "vault → Callback Handler URL" 직접 설정은 없지만, Policy 의 designated signer 를 경유해 구현된다.

핵심 사실 두 가지 — Callback Handler 는 API user 단위로 설정되고(한 Co-signer 안에서도 API user 마다 다르게/없이 둘 수 있다), Policy 가 어느 API user 를 designated signer 로 지정하느냐가 곧 어느 Callback Handler 가 호출될지를 결정한다.

한 Co-signer (workspace 키 share 하나로 모든 vault 서명)
 ├─ API user 1  →  Callback Handler X
 └─ API user 2  →  Callback Handler Y

Policy rule:  Source = Vault A  →  Designated Signer = API user 1   ⟹ Callback Handler X
Policy rule:  Source = Vault B  →  Designated Signer = API user 2   ⟹ Callback Handler Y
중요 — 다중 Co-signer 는 필요 없다

vault 별로 Co-signer 를 따로 깔 필요가 없다. 한 Co-signer 안에서 API user 마다 Callback Handler 를 다르게(또는 없이) 둘 수 있기 때문이다. 서명 key share 는 어차피 workspace 단위로 하나라(모든 vault 가 같은 마스터 키에서 파생), 여러 API user 가 같은 Co-signer 를 공유한다. 즉 "Callback Handler 는 갈라도 서명 엔진(키)은 공유" 다 — 키까지 분리하려면 별도 workspace 가 필요하다.

쉬운 비유 — 메타마스크의 "계정 추가"

(공식 사실이 아니라 이해를 돕는 비유다.) 메타마스크는 시크릿 복구 구문(시드) 하나로 Account 1·2·3… 을 끝없이 만든다 — 계정을 늘려도 백업하는 건 시드 하나뿐이고, 각 계정은 "시드 + 경로 번호" 로 다시 계산된다. Fireblocks 도 똑같다 — Workspace 키 = 시드, Vault A·B = "계정 추가" 로 만든 Account 1·2. 시드 하나로 모든 계정을 서명하듯, Workspace 키로 모든 vault 를 서명한다. 그래서 vault 를 나눠도 Co-signer(서명 엔진)는 하나로 충분하다. 다른 점은 그 시드가 메타마스크처럼 한 곳에 있지 않고 MPC 로 여러 share 에 쪼개져 있다는 것뿐이다(어느 한 share 만으로는 서명 불가).

참고 — 이 "시드 → 계정" 파생은 표준 BIP44 derivation path 방식이다(경로 구조와 Fireblocks 대입은 아래 2.7 참고).

대가 — 망 경로가 Callback Handler 수만큼 늘어난다

Callback Handler X·Y 의 운영 주체·서버가 실제로 다르면, 1장의 passthrough·pinning·timeout 설계를 경로마다 한 벌씩 적용해야 한다. 운영 주체가 같다면 굳이 이 방식으로 가지 말고, 하나의 Callback Handler 가 거래 payload 의 source vault 를 보고 내부에서 분기하는 편이 훨씬 단순하다(Fireblocks 의 plugin 기반 Callback Handler 보일러플레이트가 이 방식을 돕는다). vault 별 Callback Handler 의 운영 주체·망이 실제로 분리될 때만 이 라우팅의 값어치가 있다.

근거 구분

"Callback Handler = API user 단위", "designated signer 가 라우팅을 결정" 은 Fireblocks 공식 개발자 문서(Co-signer 아키텍처)에서 확인된 사실이다. Policy 의 Source 조건이 vault account/group 을 받고, 한 rule 에서 Source=특정 vault + Designated Signer=특정 API user 를 함께 지정할 수 있음 은 콘솔에서 직접 확인(2026-06)한 1차 관찰이다. 따라서 이 라우팅은 구현 가능하다.

2.7 (참고) BIP44 파생 — 키 하나로 모든 vault·주소

(Fireblocks 공식 명세가 아니라, "Co-signer 하나로 모든 vault" 가 왜 성립하는지의 배경 개념이다. BIP44/HD 파생은 표준 암호 지식.)

BIP44? 는 HD(계층결정적, Hierarchical Deterministic) 지갑 표준이다. 핵심은 마스터 키(시드) 하나 + 경로(path) 숫자만으로 무수한 키·주소를 결정적으로 다시 만들어내는 것 — 주소마다 키를 따로 저장하지 않는다. 시드 문구 하나만 백업하면 모든 계정·주소가 재생성되는 메타마스크가 바로 이 방식이다.

경로 구조

m / 44' / coin_type' / account' / change / address_index
│    │        │           │         │         └ 몇 번째 주소 (입금주소 채번)
│    │        │           │         └ 0 = 입금 / 1 = 잔돈(change)
│    │        │           └ 몇 번째 계정 (account 단위)
│    │        └ 어느 체인 (BTC=0, ETH=60 …)
│    └ 목적 (BIP44 고정)
└ 마스터 키 (= 시드)

각 칸은 비밀이 아니라 그냥 색인(번호)이다 — 비밀은 오직 마스터 키 하나. 같은 마스터라도 account' 를 0→1 로 바꾸면 완전히 다른 키 묶음이 나오고, address_index 를 +1 하면 새 입금주소가 나온다. 그래서 키 하나로 사실상 무한한 계정·주소를 가진다.

Fireblocks 대입

BIP44 경로 칸Fireblocks 계층
m (마스터)Workspace 키 (MPC share 로 분산)
account'Vault Account (Vault A=0, Vault B=1 …)
coin_type'Asset Wallet (체인별 — BTC / ETH …)
address_index입금 Address

그래서 — Vault A 와 Vault B 는 "다른 키" 가 아니라 "같은 Workspace 마스터 키의 다른 가지(account 번호)" 다. 새 vault 를 만드는 건 새 키를 만드는 게 아니라 경로의 account 번호를 하나 더 쓰는 것이고, 새 입금주소는 address index 를 +1 하는 것이다. 마스터(Workspace 키)는 하나뿐이므로 그 키를 쥔 Co-signer 하나가 모든 vault·주소를 서명한다 — 이것이 2.6 "다중 Co-signer 불필요" 의 근거다.

정확도 주의 — 세그먼트 매핑은 표준 패턴 기준

위 "Fireblocks 대입" 표 중 주소가 BIP44 로 파생된다는 점(address index)은 Fireblocks 가 확인한 사실이지만, vault account 가 BIP44 의 정확히 어느 경로 칸(account')에 대응하는지의 세부 매핑은 Fireblocks 가 공개 명세하지 않았다. 위 표는 표준 BIP44 패턴에 비춘 설명이며, 정확한 경로 포맷이 필요하면 Fireblocks derivation 문서를 별도로 확인해야 한다.

Fireblocks 의 한 겹 차이 — MPC

일반 HD 지갑은 마스터 키(시드)가 한 곳에 있지만, Fireblocks 는 그 마스터를 MPC 로 여러 share 에 쪼개 둔다 — 파생도 share 위에서 일어나(MPC derivation) 자식 키도 통째로 조립되지 않는다. 논리적 구조(마스터 하나 → 경로로 파생)는 같고, "그 마스터를 어떻게 보관·서명하나" 만 MPC 로 다르다. 파생의 정확한 cryptographic 절차(Owner key set → user key set)는 Fireblocks 공식 문서에 미명세 영역이다.

설계 포인트 — 한 장 요약
  • 중간 벤더: 하지 말 것 — SSL Bump, payload 변조, 임의 재시도, 무통보 변경.
  • 중간 벤더: 할 것 — CONNECT passthrough 고정, allowlist, 지연 SLA, HA, 사전 협의, 메타데이터 관측.
  • 3자 공통 — 인증서·구성 변경은 반드시 변경창구를 거친다(재페어링·pinning 연쇄 때문).
  • 가장 안전한 단순화 — proxy 단을 줄이고, 남는 단은 L4 passthrough 로, 인증은 경로가 길면 JWT 로.
