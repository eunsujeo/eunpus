1. 트래블룰이 무엇인가

VASP 간 이전에 송·수신자 정보를 함께 보내라는 규제 — 온체인이 아니라 별도 채널로 오간다
본 페이지의 출처

전 내용이 Fireblocks 공식 문서(헬프센터 컴플라이언스 문서군·개발자 문서)에서 확인한 사실이다. "우리 설계와의 접점" 절만 저자 판단이며, 미확정으로 표시한 항목은 Fireblocks 담당 매니저(CSM)에 확인할 대상이다.

트래블룰은 FATF 권고에 따라 VASP(가상자산사업자)가 특정 거래의 송신자·수신자 정보를 상대 VASP 와 교환해야 하는 의무다. 어떤 거래가 대상이고 어떤 데이터가 필요한지는 각 관할권이 정한다.

핵심 성질 하나: 온체인 거래 자체에는 송신자 정보가 실려 있지 않다. 그래서 트래블룰 정보는 체인 밖의 별도 채널로 오가고, 이 채널을 제공하는 것이 트래블룰 제공자다. Fireblocks 는 Notabene 과 연동한다 — premium opt-in 기능(추가 구매·CSM 문의)이고, 트래블룰 데이터는 암호화되어 Notabene 에 보관되며 Fireblocks 는 복호화 키를 갖지 않는다.

3. 설정 — Notabene 연동 5단계

Console 연결·정책은 Admin 운영 작업(코드 0줄), 개발 작업은 4장의 출금 경로 하나
단계내용
0사전 준비Notabene 계정 생성·설정 + Fireblocks Compliance 탭 활성화(premium 구매, Support/CSM 경유). production↔production, sandbox↔sandbox 로 기본 연결.
1Console 연결Settings > Compliance > Travel rule > Connect provider 에 Notabene 대시보드의 API key · Secret key · VASP DID 입력. 승인되면 이메일 통지.
2암호화 키 등록Notabene CLI(npm i -g @notabene/cli)로 Ed25519 키 생성 → JSON DID 키를 PUT /v1/screening/travel-rule/vasp/update 로 등록. SDK 에 travelRuleOptions 구성, 개인정보 암호화는 Notabene PII SDK 담당.
3(다중 법인) VASP 매핑Gateway VASP(부모)–subsidiary 구조를 Notabene 쪽에 만들고, Fireblocks API 로 vault account↔VASP 연결. vault 는 단일 VASP 에만(VASP 는 복수 vault 가능). 입금 검사는 수신 vault 의 VASP 기준, 미지정 시 Gateway. 단일 법인이면 이 단계 없음.
4정책연결 즉시 default 정책 2종 자동 적용(6장). custom 은 CSV 템플릿 작성 → Console 업로드 → Fireblocks Support 검토 후 활성화.
5테스트Notabene RoboVASPs 로 테스트 거래 — 별도 상대 VASP 없이 검증 가능.

입금 트래블룰은 벤더 안에서 끝나고, 우리 쪽에는 폴링이 받는 상태(REJECTED·동결)로만 나타난다 — 기존 입금 파이프라인(감지·동결·Admin unfreeze)이 그대로 흡수한다. Inbound delay(기본 30초) 안에 판정이 안 나면 기본 설정에서는 통과(자금 방출)된다 — 7장.

6. 정책 2단 — 무엇을 검사하고, 무엇을 하나

Screening Policy 가 대상을 거르고, Post-Screening Policy 가 결과별 조치를 정한다 — 둘 다 first-match

① Transaction Screening Policy — 무엇을 검사할지. default 는 전량 검사(예외: 미지원 경로·미지원 자산·초기 정보 없음·AML 미활성). 규칙 = Source/Destination × Amount/AmountUSD × Asset × Action(Screen / Bypass / Freeze).

② Post-Screening Policy — 결과에 무엇을 할지. Notabene 판정 상태별로 조치를 사전에 정해 둔다:

조치입금이면출금이면
Accept자금 즉시 사용 가능서명 진행 가능
Reject자금 동결 — Admin unfreeze 필요전송 차단 — Admin 은 우회 가능(기본값 On)
Alert승인 + Audit Log·승인자 모바일 알림
Freeze동결 (입금 전용)—
WaitPending 상태 전용 — 최대 4시간 대기 후 스크리닝 취소
Cancel—Blocking Time Expired 전용 — 거래 취소

판정 상태는 7종 — Completed · Pending · Saved(임계값 미만/non-custodial/동일 VASP 내부 — 기록만 하고 미전송) · Rejected(상대 VASP 거절 등) · Failed · Blocking Time Expired · Canceled. 규칙은 first-match — 첫 일치 규칙의 조치가 적용되고, custom 정책을 올려도 default 규칙이 맨 아래 남아 모든 거래가 어느 규칙엔가 걸리게 한다.

7. 시간 규칙과 기본값

기본값 하나가 규제 태도를 정한다 — "장애 시 통과"
설정기본값뜻
Skip on failure (장애 시 우회)On제공자 장애·기한 내 무응답이면 검사 없이 통과. Off 로 바꾸면 해당 출금은 실패, 입금은 동결.
Inbound delay30초 (최대 7일)입금 판정을 기다리는 시간 — 초과 시 기본 설정에선 자금 방출.
Outbound delay0초 (최대 90분)출금은 즉시 응답 사용. 연장은 Support(JWT lifetime 변경).
Pending 대기최대 4시간이후 스크리닝 취소.
Admin unfreeze 허용On동결 자금을 Admin 이 Console/API 로 해제. Off 는 Support 경유.
Admin 의 정책 우회 출금OnReject 된 출금을 Admin 이 우회 전송 가능. Off 는 Support 경유.
P2P Network 우회OffFireblocks P2P Network 거래도 검사한다.
결정 포인트 — Skip on failure 를 끌 것인가

기본값 On 은 "제공자가 죽으면 검사 없이 흘려보낸다"는 뜻이다. 규제 요구가 엄격하면 Off 가 맞지만, 그 대가는 장애 중 출금 실패·입금 동결이다. Admin 우회·unfreeze 기본값(둘 다 On)도 감사 관점에서 함께 결정할 대상이다.

8. 우리 설계와의 접점

입금은 이미 흡수돼 있고, 출금만 단계가 하나 생긴다 — 저자 판단
우리 흐름트래블룰 도입 시
내부 이동 — sweep · 델타 배치비대상. Vault→Vault·Vault→Exchange·Gas Station→Vault 는 트래블룰 스크리닝 미적용 경로로 공식 명시 — 설계 변경 없음.
입금 (워크스루 4·5장)변경 없음. Post-Screening 의 동결이 폴링이 받는 REJECTED 계열 상태로 나타나고, Admin unfreeze 흐름도 기존 그대로. 할 일은 정책 작성뿐.
출금 (워크스루 6장)제출 앞에 3단계 추가 — validate → 수취인 정보 수집 → validate/full, 그리고 createTransaction 에 travelRuleMessage 동봉. 수취인 정보(수취 VASP·이름)를 어디서 받을지가 화면·업무 설계 대상.
고객 사이 이동 (DB 장부 이체)온체인이 없어 벤더 스크리닝 비대상 — 트래블룰 판단까지 업무 층 몫이다 (한도·AML 과 같은 자리).

9. VerifyVASP 를 쓴다면 — 게이트가 우리 쪽으로 온다

Fireblocks 의 제공자 목록에 VerifyVASP 는 없다 — 쓰려면 트래블룰이 벤더 밖으로 나온다

VerifyVASP 는 Upbit·Chainalysis 합작의 싱가포르 법인이 운영하는 폐쇄형 트래블룰 연합망이다 — 150+ 회원 VASP·30+ 관할권, 데이터 표준 IVMS101, 흐름은 출금 전 사전 허가형. 구조는 설치형 Enclave 서버(Docker — 각 VASP 인프라에서 운영, 암호화 키·개인정보 보관)와 VerifyVASP 운영의 중앙 API 서버로 나뉜다. 비회원과는 통신할 수 없고, 개인지갑(non-custodial)은 미지원이다. Fireblocks 문서의 제공자 목록(Notabene 직접 · Sumsub·GTR TRLink · Chainalysis·Elliptic)에는 등재돼 있지 않다. 도입 경로는 셋으로 갈린다.

경로무엇이 달라지나
A. TRLink 파트너로 직접 지원
(CSM 확인 대상)		벤더 게이트와 정책 틀(6~7장)을 유지한 채 제공자만 교체 — 가장 싼 경로. 파트너 목록은 API 로 조회된다(GET /v1/screening/trlink/partners).
A′. TRLink 파트너 경유 상호운용
(Sumsub·GTR ↔ VerifyVASP)		"CODE·GTR·VerifyVASP·Sumsub 은 상호운용된다"는 업계 서술(2차 출처 — 논문 인용)이 실효라면, TRLink 의 Sumsub 또는 GTR 를 붙여 벤더 게이트를 유지한 채 VerifyVASP 회원과 통신할 수 있다. 단 프로토콜 상호운용이 곧 자동 도달을 뜻하지 않는다 — 상대 회원별 도달 여부를 Sumsub·CSM 에 확인해야 한다.
B. 직접 연동
— 트래블룰이 업무층으로 이동		 운영 부담: Enclave 서버를 우리 인프라에 설치·운영한다(키·개인정보 보관처가 우리 쪽에 생김).
출금: 제출 전에 수취인 주소 소유 확인(User Account Verification) → 암호화 개인정보 전송·사전 승인(User Verification) → 온체인 전송 → tx hash 보고(Transaction Status). 통과 증적을 우리 관문(업무 승인·서명 직전 검증)으로 건다.
입금: 별도 메시지를 기다렸다 대조하는 게 아니라 요청-응답이다 — 송신 VASP 의 사전 검증 요청에 응답하는 수신용 API(Verify User · Verify User Account · Callback)를 우리가 구현하고, 응답·승인 뒤 들어온 입금을 인정한다. 가용 전이 게이트(8장)는 전부 우리 몫.
정책 틀: 벤더 기본값 체계(Skip on failure·delay·Wait)와 대시보드가 없다 — 대기·미수신·동결 규칙과 운영 화면을 자체 설계. AML(Chainalysis·Elliptic)·OFAC 차단은 별개 통합이라 그대로.
병행 가능성 — 상대가 어느 망에 있느냐로 갈린다

국내 상대 VASP 는 VerifyVASP(또는 CODE — 2022년 4월 25일부터 두 망 상호 연동 완료), 해외 상대는 Notabene 으로 라우팅하는 병행 구성이 될 가능성이 있다 — 이 경우 입금의 가용 전이 게이트를 처음부터 복수 망 대조로 설계하는 편이 재작업을 줄인다. 그리고 VerifyVASP 가 개인지갑을 지원하지 않으므로, 개인지갑 입금의 인정은 별도 통제(주소 등록·소유 인증)가 필요하다.

10. 어디에 두나 — 블록체인 매니저 밖

국내 VerifyVASP · 해외 Notabene 병행 전제 — 트래블룰 게이트는 매니저 포트 앞의 별도 컴포넌트다

트래블룰을 블록체인 매니저(포트·어댑터)에 넣지 않는다. 이유 셋 — ① 트래블룰은 온체인 사건이 아니라 VASP 사이의 오프체인 규제 메시징이라 매니저의 어휘(계정·주소·거래)에 속하지 않고, ② 트래블룰 제공자는 custody 벤더와 독립적으로 바뀌며(교체 축이 다르다), ③ 병행 구성에선 한 출금의 처리가 상대 망에 따라 벤더 안(Notabene)과 벤더 밖(VerifyVASP)으로 갈리는데 그 분기는 업무 판단이지 체인 통로의 일이 아니다. 그래서 트래블룰 게이트를 Service 업무층에 두고, 매니저 포트는 그대로 둔다.

출금 — 게이트(노랑)가 상대 망을 판별해 사전 검증을 끝낸 뒤에야 매니저 포트(초록)로 넘긴다. 어느 망이든 포트가 받는 것은 "승인된 이체 지시"로 동일하다.

입금 — 두 망의 결과가 가용 전이 게이트 한 곳에서 합류한다. VerifyVASP 쪽은 우리가 구현한 수신 API 의 응답·승인 결과, Notabene 쪽은 벤더 동결 상태(기존 폴링 경로 그대로).

매니저와의 접점은 둘뿐이다. ① 해외(Notabene) 경로에서 게이트가 만든 travelRuleMessage 를 제출 요청의 옵션 필드로 운반한다 — externalTxId 처럼 포트는 산출물을 싣기만 하고 내용을 모른다. ② 입금의 벤더 동결 상태를 폴링이 받는다 — 이미 있는 경로다. 망이 추가·교체돼도 게이트만 바뀌고 포트·어댑터는 0줄이다.

11. 시나리오 — 여섯 갈래

출금 셋(국내·해외·개인지갑) × 입금 셋 — 병행 구성에서 실제로 지나가는 길 전부

11.1 출금 → 국내 VASP (VerifyVASP)

sequenceDiagram
    autonumber
    participant BE as Service 백엔드
(트래블룰 게이트)
    participant VV as VerifyVASP
Enclave + 중앙 API
    participant RV as 상대 VASP (국내)
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end

    BE->>VV: 수취인 주소 소유 확인 — User Account Verification
    VV->>RV: 회원망 안에서 조회
    RV-->>VV: 소유·실명 확인 응답
    VV-->>BE: 확인 결과 회신
    BE->>VV: 암호화 PII 전송 — User Verification (사전 승인 요청)
    VV->>RV: 암호화 PII 전달 (사전 승인 요청)
    RV-->>VV: 승인 / 거절
    VV-->>BE: 승인 / 거절 회신
    alt 승인
        BE->>FB: submitTransaction — 이후는 6장 파이프라인 그대로
        BE->>VV: 전송 후 tx hash 보고 — Transaction Status
    else 거절 · 수취인 불일치
        BE->>BE: 출금 반려 — 잠긴 금액을 가용으로 되돌리고 고객 안내
    end

사전 허가형 — 상대의 승인 회신(7~8)이 나야 제출한다. 거절이면 온체인에 아무것도 나가지 않으므로 되돌릴 것은 원장의 잠김뿐이다.

11.2 출금 → 해외 VASP (Notabene)

sequenceDiagram
    autonumber
    participant BE as Service 백엔드
(트래블룰 게이트)
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end
    participant NB as Notabene

    BE->>FB: validate — 임계값·수취 주소 유형 판별
    FB-->>BE: type = TRAVELRULE (BELOW_THRESHOLD 면 정보 교환 없이 제출)
    BE->>BE: 수취인 정보 수집
    BE->>FB: validate/full — 전체 검증
    FB-->>BE: isValid
    BE->>FB: submitTransaction — travelRuleMessage(암호화) 동봉
    FB->>NB: 거래 상세 전송 → 상태 판정
    NB-->>FB: Completed / Rejected / Failed …
    alt Post-Screening = Accept
        FB->>FB: 서명 진행 — 이후는 6장 파이프라인 그대로
    else Reject
        FB->>FB: 전송 차단 (Admin 우회 가능)
        FB-->>BE: 폴링 — 차단 확인
        BE->>BE: 잠김 해제·고객 안내
    end

벤더 게이트형 — 검증(1·4~5)과 메시지 동봉(6)은 우리가, 판정 후 조치(9~)는 벤더의 Post-Screening 정책이 한다. Accept 가 나야 서명이 진행된다.

11.3 출금 → 개인지갑 (non-custodial)

sequenceDiagram
    autonumber
    participant BE as Service 백엔드
(트래블룰 게이트)
    participant WL as 주소 등록부
(whitelist · 소유 인증 증적)
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end

    BE->>WL: 목적지가 등록·소유 인증된 개인지갑인가
    WL-->>BE: 등록 여부 회신
    alt 등록됨
        BE->>BE: VASP 간 정보 교환 없음 — 관할 규정에 따른 기록만 남긴다
        BE->>FB: submitTransaction — 이후는 6장 파이프라인 그대로
    else 미등록
        BE->>BE: 출금 반려 — 등록·소유 인증부터
    end

두 망 모두 개인지갑을 다루지 않으므로(VerifyVASP 는 미지원 명시), 방어선은 우리 등록부다 — 등록 시점의 소유 인증(지갑 서명)이 증적이 된다. 등록·인증 절차 자체는 별도 설계 대상.

11.4 입금 ← 국내 VASP (VerifyVASP)

sequenceDiagram
    autonumber
    participant SV as 송신 VASP (국내)
    participant VV as VerifyVASP
    participant BE as Service 백엔드
(수신 API + 게이트)
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end

    SV->>VV: (전송 전) 사전 검증 요청
    VV->>BE: 우리 수신 API 호출 — Verify User · Verify User Account
    BE-->>VV: 수취 고객 실명·계정 확인 응답 (승인)
    VV-->>SV: 승인 회신
    SV->>SV: 온체인 전송 실행
    FB-->>BE: 폴링 감지 — 입금 후보 (4장)
    SV->>VV: tx hash 보고
    VV->>BE: tx hash 전달
    BE->>BE: 사전 요청·tx hash·입금 후보 대조 → 일치 + 확정 임계 도달 → 가용

요청-응답형 — 자금이 오기 전에 우리 수신 API 가 먼저 응답한다(2~3). 가용 전이는 "온체인 확정 + 사전 요청과의 대조 일치" 둘 다 충족해야 한다. 대조 실패·보고 미수신의 처리 기준은 자체 정책 설계 대상.

11.5 입금 ← 해외 VASP (Notabene)

sequenceDiagram
    autonumber
    participant SV as 송신 VASP (해외)
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end
    participant NB as Notabene
    participant BE as Service 백엔드

    SV->>SV: 온체인 전송
    FB->>FB: 감지 → 첫 confirmation 후 Screening Policy
    FB->>NB: 상세 전송 (메시지 없으면 빈 메시지 생성) → 판정
    NB-->>FB: 상태 (Inbound delay 기본 30초 대기)
    alt Post-Screening = Accept
        FB-->>BE: 폴링 — 정상 입금, 확정 임계 후 가용 (4·5장 그대로)
    else Reject · Freeze
        FB->>FB: 자금 동결
        FB-->>BE: 폴링 — REJECTED 계열 수신, 잔액 미반영
        BE->>BE: Admin 판단 → unfreeze 또는 유지 (5장)
    end

벤더 안에서 끝나는 형 — 우리 코드는 없고, 결과가 폴링 상태로만 나타난다. 기존 입금 파이프라인(감지·동결·Admin unfreeze)이 그대로 흡수한다.

11.6 입금 ← 개인지갑

sequenceDiagram
    autonumber
    participant PW as 개인지갑
    box rgb(220,252,231) Fireblocks
    participant FB as Fireblocks
    end
    participant BE as Service 백엔드
    participant WL as 주소 등록부

    PW->>PW: 온체인 전송
    FB-->>BE: 폴링 감지 — 입금 후보 (4장)
    BE->>WL: source 가 등록·소유 인증된 주소인가
    WL-->>BE: 등록 여부 회신
    alt 등록됨
        BE->>BE: 확정 임계 도달 → 가용 (5장 그대로)
    else 미등록
        BE->>BE: 가용 전이 보류 — 알림, 사후 등록·소명 또는 반환 정책으로
    end

망 밖에서 오는 유일한 길 — 판별 재료가 source 주소뿐이라, 등록부(소유 인증 증적)가 곧 인정 기준이 된다. 미등록 입금의 사후 처리(등록 유도·반환)는 자체 정책 설계 대상.

12. 미확정 — CSM 확인 목록

공식 문서에 없는 것들 — 도입 전 확인 대상
  • 한국 관할 임계값 — 문서는 "관할권이 결정"까지만. 원화 기준 적용 방법(AmountUSD 만 지원하는지) 확인 필요.
  • TAP(거래 승인 정책)과의 선후 — 컴플라이언스 문서군 19종 전체에 TAP 언급이 없다. 확정된 순서는 "OFAC 이 사용자 정책보다 먼저" · "AML 이 트래블룰보다 먼저" 뿐.
  • Notabene 직접 통합 vs TRLink — Fireblocks 에는 제공자 중립 레이어(TRLink — Sumsub·GTR 파트너)도 있다. 연결 가능 목록에 Notabene·Sumsub 이 병렬로 있어 병행으로 보이지만 명시가 없다.
  • VerifyVASP 도달 경로 — TRLink 파트너로 직접 붙일 수 있는지(9장 경로 A), Sumsub·GTR 경유 상호운용의 실효(경로 A′ — 프로토콜 상호운용 ≠ 자동 도달), Enclave 운영 요건·가격.
  • 가격·SLA — premium 구독 조건, Notabene 측 계약. Notabene API 문서는 비공개(CSM 경유 접근).

관련 문서: 출금 파이프라인은 지갑 설계 워크스루 6장 · 입금·동결은 5장 · gas 대납은 가스 대납 문서.
