15. 자체 구축 어댑터 — 세 포트 구현 예시

같은 포트, 내부만 다름 — SelfBuiltProvider 가 nonce·서명·전파·인덱서를 직접 조립한다
본 페이지의 성격

설명용 의사코드다. 14. Fireblocks 와 같은 지갑 서비스 백엔드·같은 세 포트 위에서, 어댑터 구현만 자체 구축으로 바꾸면 무엇이 달라지는지 보여준다. 위층 코드는 한 줄도 바뀌지 않는다 — 어댑터만 교체된다.

15.1 큰 그림 — provider 는 하나, 내부에 부품이 여럿

자체 구축은 블록체인 매니저(체인 엔진)를 직접 만드는 길이다 — Fireblocks 가 관리형으로 주던 엔진을 우리가 짓는다. 지갑 서비스 백엔드가 보는 것은 여전히 같은 세 포트지만, Fireblocks 가 통째로 해주던 트랜잭션 제출을 SelfBuiltProvider 가 내부에서 여러 부품으로 직접 조립한다. Fireblocks 가 묶어주던 서명·전파·nonce 가 다시 분리되지만, 그 분리는 provider 내부에서만 보이고 코어에는 노출되지 않는다.

Figure 15-1. 자체 구축. 코어는 여전히 같은 세 포트만 호출한다. 그 구현인 SelfBuiltProvider(파랑 박스) 안에서 HD 지갑·nonce·서명(HSM)·전파(노드)·수집(인덱서) 부품을 직접 엮는다. Fireblocks 와 달리 서명과 전파가 다른 부품이라 provider 내부에서 둘을 따로 호출한다.

15.2 provider 코드 — 내부에서 부품을 조립

class SelfBuiltProvider implements AccountPort, TransactionPort, ChainQueryPort {

  // 내부 부품 (코어에는 안 보임) — 각각 별도 컴포넌트
  constructor(
    private node: NodeRpc,        // 2·4 멀티체인/전파 : 노드 · GCP BNE
    private hsm: Hsm,             // 5 서명 : 자체 HSM · MPC
    private nonceMgr: NonceMgr,   // 4 nonce : 계정별 lock · local counter
    private indexer: SelfIndexer, // 3 인덱서 : 수집 · projection · reorg
    private hd: HdWallet,         // HD 지갑 : account index 할당 · xpub 파생
  ) {}

  createAccount(ref) { return this.hd.allocateAccount(ref) }               // HD account index 할당 (Canton 만 party allocation, 15.9)
  addressOf(acct, asset) { return bip32.derive(this.node.xpub(asset), acct) }      // 조회 = HD 결정적 재계산 (순수 함수 — 같은 입력 같은 주소)
                                // ★ secp256k1 체인(EVM·BTC) 한정 — xpub 만으로 non-hardened 공개 파생이 가능.
                                //   ed25519(Solana)는 SLIP-0010 hardened-only 라 xpub 파생 불가 → HSM "안에서" 재계산,
                                //   Canton 은 계정 생성 때 만들어진 PartyId 반환 (15.9). 경로·주소 인코딩도 체인별 (2.2 표)
  issueDepositAddress(acct, asset) { return bip32.derive(this.node.xpub(asset), nextIndex(acct)) }
                                // 발급 capability (13.3) — 다음 index 파생 + 계정 디렉터리·인덱서 watch-list 등록(9.4)까지가 발급.
                                //   Canton 은 미구현 — 입금 구분은 memo-ref
  getBalance(acct, asset) { return this.indexer.balanceOf(this.addressOf(acct, asset), asset) }  // projection 이 confirmed/pending/locked 구분 보유 → 13.3 Balance
  validateAddress(asset, addr) { return isValidForChain(asset, addr) }          // 체인별 형식·체크섬 (로컬)
  estimateFee(req) { return this.node.estimateFee(req) }                        // 노드/체인 수수료 추정

  // 트랜잭션 제출 : Fireblocks 가 한 번에 하던 것을 내부에서 3단계로
  //   ★ 실제 구현은 단계 사이 사망에 대비해 4.3 의 intent 상태머신(BUILT→SIGNED→BROADCAST)을
  //     이 안에서 그대로 밟는다 — 전파 전에 의도·서명본 영속화, 복구는 같은 서명본 재전파
  submitTransaction(req) {
    const nonce  = this.nonceMgr.reserve(req.from)         // 계정별 순번 점유 (점유 기록도 영속화 — gap 복구 근거)
    const raw    = assembleUnsignedTx({ ...req, nonce })   // 조립
    const signed = this.hsm.sign(raw)                      // 서명 (HSM 앞 정책 게이트 경유 — 5.5, 실패 시 비멱등)
    return this.node.sendRawTransaction(signed)            // 전파 → TxRef(hash)
  }
  getStatus(txRef) { return this.indexer.confirmationOf(txRef) }    // as-of-block 확정수
  query(filter) { return this.indexer.query(filter) }               // ChainQueryPort : 임의·커스텀 조회 — 인덱서 projection 경유
  boost(txRef) {                                         // EVM/UTXO 만 — 같은 nonce + fee↑ 재서명·재전파 (RBF). Solana 는 submit 뒤 auto-retry
    return this.node.sendRawTransaction(this.hsm.sign(reFee(txRef)))
  }
  cancel(txRef) { return this.node.sendRawTransaction(this.hsm.sign(zeroSelfSend(txRef))) }  // EVM 예 — 같은 nonce 0원 self-send (cancel 도 capability, 13.3 — Solana 는 부재)

  // 수신 트랜잭션 · 확정 : webhook 이 없으니 인덱서를 직접 운영
  onChainEvent(handler) {
    this.indexer.subscribe(ourAddrs, ev => handler(ev))    // RPC 폴링/스트림 → 우리 주소 필터
  }
}

코어가 호출하는 시그니처는 14장과 글자 그대로 같다(submitTransaction·getStatus·boost·onChainEvent…). 달라진 것은 오직 { } 안 — Fireblocks 의 한 줄이 여기서는 "조립→서명→전파" 와 "인덱서 운영" 으로 펼쳐진다.

15.3 계정·주소 발급 단계별 흐름

자체 구축은 발급도 직접 한다 — Fireblocks 가 해주던 vault 생성·주소 파생을 우리 HD 지갑·HSM 으로 수행한다. 다만 9.2 에서 본 대로 곡선·체인에 따라 발급 흐름 자체가 세 갈래다 — secp256k1 은 로컬 공개 파생(HSM 호출조차 불필요), ed25519 는 HSM 내부 파생, Canton 만 유료 온장 등록(party allocation).

Figure 15-2. 자체 구축 계정·주소 발급 — 체인별 세 갈래. secp256k1(EVM·BTC)은 xpub(공개키만으로 하위 주소를 파생할 수 있는 확장 공개키)으로 addressOf 가 로컬에서 끝난다 — 개인키도 HSM 호출도 필요 없는 순수 계산. ed25519(Solana)는 SLIP-0010 hardened-only 라 파생을 키가 있는 HSM 안에서 하고 공개키만 받는다. Canton 은 발급이 createAccount 단계의 party allocation(generate-topology → HSM 으로 hash 서명 → allocate, 비용 있는 온장 등록)으로 일어나고, addressOf 는 그렇게 만들어진 PartyId 를 디렉터리에서 반환하는 조회다. 어느 갈래든 개인키는 HSM 밖으로 나오지 않고, 마무리는 공통 — 계정 디렉터리 저장과 watch-list 등록(9.4)까지가 발급이다. 앞 두 갈래는 온체인 트랜잭션이 아니지만(전파·수수료 없음) Canton 만 예외다. 경로(coin type·스크립트 유형)·인코딩 차이는 멀티체인 어댑터(2.2 표 주소 파생 행)가 흡수한다.

15.5 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 주소로 트랜잭션이 들어옴
  2. 자체 인덱서가 노드/RPC 를 폴링·구독해 우리 주소로의 transfer 를 스스로 감지 → projection 에 pending
  3. confirmation 누적이 확정 기준(finalityRule) 충족 → confirmed → onChainEvent 로 코어에 통지
  4. reorg 나면 projection 롤백 (원시 로그 보존)

Fireblocks 가 webhook 으로 주던 것을, 여기선 인덱서를 직접 운영해 onChainEvent 뒤에서 만든다.

15.6 인덱서는 별도 백그라운드 job (요청 경로 밖)

앞의 부품 중 인덱서만 성격이 다르다. nonce·서명·전파는 submitTransaction 요청이 올 때 동작하지만(요청 경로), 인덱서 수집·가공은 체인이 흐르는 한 계속 돌아야 한다 — 끊기면 입금·확정을 놓친다. 그래서 요청 경로와 분리된 상시 worker 로 둔다.

Fireblocks 면 이 job 이 사라진다

이 상시 수집 job 은 자체 구축에서만 우리가 운영한다. Fireblocks 를 쓰면 Fireblocks 가 자기 vault 범위에서 이 job 을 대신 돌려 webhook 으로 push 해주므로, 우리는 수신만 한다 (단 임의 외부 주소·커스텀 조회가 필요하면 이 job 을 자체로 운영 — 13.4 의 ChainQueryPort 추가).

15.7 노드 조달 옵션 — 설치형 · 관리형 전용 · 공용 SaaS

15.2 의 NodeRpc 부품(전파·체인 RPC)을 어디서 가져오느냐는 자체 구축 안의 하위 선택이다. 같은 슬롯에 무엇을 꽂든 서명(HSM)·nonce·인덱서는 그대로 자체 — 노드만 다르다. 그래서 이건 별도 아키텍처가 아니라 노드 조달 스펙트럼이다.

조달 방식누가 운영특성예
설치형 자체 운영내가 설치·운영완전 통제. 노드 운영 부담(동기화·스토리지·업그레이드)을 직접Geth · Erigon 직접
관리형 전용 노드벤더가 내 전용 노드를 운영통제는 유지하되 운영만 위탁. 비용↑GCP Blockchain Node Engine
공용 RPC SaaS멀티테넌트 공용운영 부담 0·빠른 시작 / rate limit·제3자 노드 신뢰Infura · Alchemy · QuickNode
노드를 빌려도 "내 몫" 으로 남는 것

위 어느 쪽을 골라도 — 서명·custody(HSM), nonce 직렬화, 인덱서(수집·projection), 그리고 멀티 엔드포인트 failover·풀(2.5)과 제3자 노드 결과 신뢰는 그대로 우리가 진다. 노드 조달은 "노드 운영을 누가 하느냐" 만 바꿀 뿐, 자체 구축의 나머지는 동일하다. (custody 까지 통째로 위탁하려면 그건 14. Fireblocks — 다른 축이다.)

핵심

자체 구축은 Fireblocks 가 묶어 주던 것(서명·전파·nonce·수신감지·멀티체인)을 전부 provider 안에서 우리가 진다. 그래서 4. 트랜잭션·Nonce·Broadcast·3. 인덱서·5. 서명 같은 상세 페이지가 자체 구축에선 그대로 SelfBuiltProvider 의 내부 부품이 된다. 그래도 지갑 서비스 백엔드와 세 포트는 14장과 똑같다 — 그래서 어댑터만 바꿔(또는 ChainQueryPort 만 자체로) Fireblocks ↔ 자체 구축을 오갈 수 있다 (13. 벤더 추상화). 그리고 멱등 게이트웨이·이벤트 팬아웃·내부 장부 대사는 어느 쪽이든 코어에 그대로 남는다.

15.9 Canton 에서는

자체 구축은 Canton 도 직접 진다 — 세 어댑터 중 가장 무겁다. EVM 의 RPC 노드 대신 Canton validator(participant) node 를 운영해 Global Synchronizer 에 연결해야 한다. 이 절의 Canton 동작은 Canton 공식 문서(docs.canton.network) 기준이다.
