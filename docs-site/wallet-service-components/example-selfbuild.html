12. 자체 구축 어댑터 — 세 포트 구현 예시

같은 포트, 내부만 다름 — SelfBuiltProvider 가 nonce·서명·전파·인덱서를 직접 조립한다
본 페이지의 성격

설명용 의사코드다. 11. Fireblocks 와 같은 지갑 서비스 백엔드·같은 세 포트 위에서, 어댑터 구현만 자체 구축으로 바꾸면 무엇이 달라지는지 보여준다. 위층 코드는 한 줄도 바뀌지 않는다 — 어댑터만 교체된다.

12.1 큰 그림 — provider 는 하나, 내부에 부품이 여럿

자체 구축은 블록체인 매니저(체인 엔진)를 직접 만드는 길이다 — Fireblocks 가 관리형으로 주던 엔진을 우리가 짓는다. 지갑 서비스 백엔드가 보는 것은 여전히 같은 세 포트지만, Fireblocks 가 통째로 해주던 트랜잭션 제출을 SelfBuiltProvider 가 내부에서 여러 부품으로 직접 조립한다. Fireblocks 가 묶어주던 서명·전파·nonce 가 다시 분리되지만, 그 분리는 provider 내부에서만 보이고 코어에는 노출되지 않는다.

Figure 12-1. 자체 구축. 코어는 여전히 같은 세 포트만 호출한다. 그 구현인 SelfBuiltProvider(파랑 박스) 안에서 nonce·서명(HSM)·전파(노드)·수집(인덱서) 네 부품을 직접 엮는다. Fireblocks 와 달리 서명과 전파가 다른 부품이라 provider 내부에서 둘을 따로 호출한다.

12.2 provider 코드 — 내부에서 부품을 조립

class SelfBuiltProvider implements AccountPort, TransferPort, IndexerPort {

  // 내부 부품 (코어에는 안 보임) — 각각 별도 컴포넌트
  constructor(
    private node: NodeRpc,        // 2·4 멀티체인/전파 : 노드 · GCP BNE
    private hsm: Hsm,             // 5 서명 : 자체 HSM · MPC
    private nonceMgr: NonceMgr,   // 4 nonce : 계정별 lock · local counter
    private indexer: SelfIndexer, // 3 인덱서 : 수집 · projection · reorg
  ) {}

  createAccount(ref)         = hd.allocateAccount(ref)                    // HD account index 할당
  deriveAddress(acct, asset) = bip32.derive(this.node.xpub(asset), acct)  // 우리가 파생
  getBalance(addr, asset)    = this.indexer.balanceOf(addr, asset)        // projection 조회

  // 트랜잭션 제출 : Fireblocks 가 한 번에 하던 것을 내부에서 3단계로
  submitTransaction(req) {
    const nonce  = this.nonceMgr.reserve(req.from)         // 계정별 순번 점유
    const raw    = assembleUnsignedTx({ ...req, nonce })   // 조립
    const signed = this.hsm.sign(raw)                      // 서명 (HSM, 실패 시 비멱등)
    return this.node.sendRawTransaction(signed)            // 전파 → TxRef(hash)
  }
  getStatus(txRef) = this.indexer.confirmationOf(txRef)    // as-of-block 확정수
  bumpFee(txRef)   = this.node.sendRawTransaction(         // 같은 nonce + fee↑ 재서명·재전파
                       this.hsm.sign(reFee(txRef)))

  // 수신 트랜잭션 · 확정 : webhook 이 없으니 인덱서를 직접 운영
  onChainEvent(handler) {
    this.indexer.subscribe(ourAddrs, ev => handler(ev))    // RPC 폴링/스트림 → 우리 주소 필터
  }
}

코어가 호출하는 시그니처는 11장과 글자 그대로 같다(submitTransaction·getStatus·bumpFee·onChainEvent…). 달라진 것은 오직 { } 안 — Fireblocks 의 한 줄이 여기서는 "조립→서명→전파" 와 "인덱서 운영" 으로 펼쳐진다.

Figure 12-2. 자체 구축 송신 트랜잭션. 코어 입장에선 Fireblocks 와 똑같이 submitTransaction 한 번(Figure 11-2) 이지만, provider 내부에서는 조립(nonce 점유) → 서명(HSM) → 전파(노드) → 확정(인덱서) 4단계가 펼쳐진다. 순번·재전송·확정 추적이 전부 우리 책임.

12.4 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 주소로 트랜잭션이 들어옴
  2. 자체 인덱서가 노드/RPC 를 폴링·구독해 우리 주소로의 transfer 를 스스로 감지 → projection 에 pending
  3. confirmation 누적이 확정 기준(finalityRule) 충족 → confirmed → onChainEvent 로 코어에 통지
  4. reorg 나면 projection 롤백 (원시 로그 보존)

Fireblocks 가 webhook 으로 주던 것을, 여기선 인덱서를 직접 운영해 onChainEvent 뒤에서 만든다.

12.5 인덱서는 별도 백그라운드 job (요청 경로 밖)

앞의 부품 중 인덱서만 성격이 다르다. nonce·서명·전파는 submitTransaction 요청이 올 때 동작하지만(요청 경로), 인덱서 수집·가공은 체인이 흐르는 한 계속 돌아야 한다 — 끊기면 입금·확정을 놓친다. 그래서 요청 경로와 분리된 상시 worker 로 둔다.

Figure 12-3. 자체 인덱서 = 상시 백그라운드 job. 노드에서 계속 수집·가공해 projection 을 만들어 두고, IndexerPort 메서드(query·getBalance·onChainEvent)는 그 결과를 읽거나 구독할 뿐이다. 이것이 0.2 의 ② 감지(event-driven) — 누가 호출하지 않아도 돈다. 반대로 Account·TransferPort 는 ① 호출(요청 시에만). 상세 수집 파이프라인은 3. 인덱서.

Fireblocks 면 이 job 이 사라진다

이 상시 수집 job 은 자체 구축에서만 우리가 운영한다. Fireblocks 를 쓰면 Fireblocks 가 자기 vault 범위에서 이 job 을 대신 돌려 webhook 으로 push 해주므로, 우리는 수신만 한다 (단 임의 주소·커스텀 가공이 필요하면 이 job 을 자체로 운영 — 10.4 의 IndexerPort 교체).

핵심

자체 구축은 Fireblocks 가 묶어 주던 것(서명·전파·nonce·수신감지·멀티체인)을 전부 provider 안에서 우리가 진다. 그래서 4. 트랜잭션·Nonce·Broadcast·3. 인덱서·5. 서명 같은 상세 페이지가 자체 구축에선 그대로 SelfBuiltProvider 의 내부 부품이 된다. 그래도 지갑 서비스 백엔드와 세 포트는 11장과 똑같다 — 그래서 어댑터만 바꿔(또는 IndexerPort 만 자체로) Fireblocks ↔ 자체 구축을 오갈 수 있다 (10. 벤더 추상화). 그리고 멱등 게이트웨이·이벤트 팬아웃·내부 장부 대사는 어느 쪽이든 코어에 그대로 남는다.
