15. 자체 구축 어댑터 — 포트 구현 예시

같은 포트, 내부만 다름 — SelfBuiltProvider 가 nonce·서명·전파·인덱서를 직접 조립한다
본 페이지의 성격

설명용 의사코드다. 14. Fireblocks 와 같은 지갑 서비스 백엔드·같은 세 포트 위에서, 어댑터 구현만 자체 구축으로 바꾸면 무엇이 달라지는지 보여준다. 위층 코드는 한 줄도 바뀌지 않는다 — 어댑터만 교체된다.

15.1 큰 그림 — provider 는 하나, 내부에 부품이 여럿

자체 구축은 블록체인 매니저(체인 엔진)를 직접 만드는 길이다 — Fireblocks 가 관리형으로 주던 엔진을 우리가 짓는다. 지갑 서비스 백엔드가 보는 것은 여전히 같은 세 포트지만 — custody 두 포트(Account·Transaction)는 SelfBuiltProvider 가, ChainQuery 는 인덱서를 감싼 별도 어댑터(13.4 하이브리드와 같은 클래스)가 채운다 — Fireblocks 가 통째로 해주던 트랜잭션 제출을 SelfBuiltProvider 가 내부에서 여러 부품으로 직접 조립한다. Fireblocks 가 묶어주던 서명·전파·nonce 가 다시 분리되지만, 그 분리는 provider 내부에서만 보이고 코어에는 노출되지 않는다.

Figure 15-1. 자체 구축. 코어는 여전히 같은 세 포트만 호출한다. custody 두 포트의 구현인 SelfBuiltProvider(파랑 박스) 안에서 HD 지갑·nonce·서명(HSM)·전파(노드)·수집(인덱서) 부품을 직접 엮고, ChainQueryPort 는 같은 인덱서를 감싼 별도 어댑터가 채운다(15.2 코드 끝·13.4). Fireblocks 와 달리 서명과 전파가 다른 부품이라 provider 내부에서 둘을 따로 호출한다.

15.2 provider 코드 — 내부에서 부품을 조립

// ── 부품 조립 (앱 기동 시점, 17장 DI) — 체인별 부품(노드·nonce)은 어댑터 "안"으로 들어간다 ──
const adapters = chainAdapters({                  // 2.4 의 레지스트리 그대로
  ethereum: new EvmAdapter(node, nonceMgr),       // nonce 는 EVM 어댑터 소관 (4.3)
  bitcoin:  new UtxoAdapter(node),
  solana:   new SolanaAdapter(node),
  canton:   new CantonAdapter(participant),
})
const provider   = new SelfBuiltProvider(adapters, hsm, indexer, hd)  // custody — Account·Transaction 두 포트
const chainQuery = new IndexerQueryAdapter(indexer)                   // ChainQuery — custody 와 별개 슬롯 (13.4)

class SelfBuiltProvider implements AccountPort, TransactionPort {

  // 내부 부품 (코어에는 안 보임) — 각각 별도 컴포넌트
  constructor(
    private adapters: ChainAdapters, // 2 멀티체인 : 체인 분기 전체가 이 안 (노드·nonce 포함, 2.4)
    private hsm: Hsm,                // 5 서명 : 자체 HSM · MPC
    private indexer: SelfIndexer,    // 3 인덱서 : 수집 · projection · reorg — 14.2 의 WebhookBus 와 같은 슬롯(이벤트 소스)
    private hd: HdWallet,            // HD 지갑 : account index 할당 · xpub 보관·파생
  ) {}

  createAccount(ref) {
    const acct = this.hd.allocateAccount(ref)               // 전 체인 공통 — 계정 장부에 줄 하나 (HD account index)
    for (const chain of chainsOf(ref)) {                    // 온보딩 요청의 asset → 체인 (9.1)
      const a = this.adapters.pick(chain)
      if (a.registersAccountOnLedger)                       // Canton 만 — 주소(PartyId)가 계정과 함께 태어나는 체인 (9.2 · 15.9)
        a.registerAccount(acct, this.hsm.pubkeyOf(acct))    // generate-topology → HSM hash 서명 → allocate (15-2c 의 그 화살표들)
    }
    return acct
  }
  addressOf(acct, asset) { return this.hd.issuedAddressOf(acct, asset) }      // 조회 — "발급(등록)된" 주소만 반환, 절대 새 주소를 만들지 않는다 (15.3)
                                // ★ 재계산(bip32.derive)은 검증·복구용으로만 — 등록 안 된 주소가 고객에게 나가면
                                //   인덱서 watch-list 에 없어 입금을 놓친다 (9.4). Canton 은 createAccount 때 만들어진 PartyId 반환 (15.9)
  issueDepositAddress(acct, asset) { return bip32.derive(this.hd.xpub(asset), nextIndex(acct)) }   // xpub 은 HD 지갑 소유 (노드 아님)
                                // 발급 capability (13.3) — 첫 주소부터 이 동사다. 다음 index 소비 + 계정 디렉터리·인덱서 watch-list 등록(9.4)까지가 발급.
                                // ★ 계산은 곡선별 — secp256k1(EVM·BTC)은 xpub 공개 파생(위 코드), ed25519(Solana)는 SLIP-0010
                                //   hardened-only 라 HSM "안에서" 파생. Canton 은 미구현 — 입금 구분은 memo-ref. 경로·인코딩도 체인별 (2.2 표)
                                //   이 곡선별 계산 조각은 실제 구현에선 boost? 처럼 어댑터 쪽 선택 capability 로 — 여기선 secp256k1 만 인라인 예시
  getBalance(acct, asset) { return this.indexer.balanceOf(this.addressOf(acct, asset), asset) }  // projection 이 confirmed/pending/locked 구분 보유 → 13.3 Balance
  validateAddress(asset, addr) { return isValidForChain(asset, addr) }          // 체인별 형식·체크섬 (로컬)
  estimateFee(req) { return this.adapters.pick(req.chainId).estimateFee(req) }  // 체인별 수수료 모델은 어댑터가 흡수 (2.4)

  // 트랜잭션 제출 : Fireblocks 가 한 번에 하던 것을 내부에서 3단계로 — 체인별 차이는 2.4 어댑터 경유
  //   ★ 실제 구현은 단계 사이 사망에 대비해 4.3 의 intent 상태머신(BUILT→SIGNED→BROADCAST)을
  //     이 안에서 그대로 밟는다 — 전파 전에 의도·서명본 영속화, 복구는 같은 서명본 재전파
  submitTransaction(req) {
    const adapter = this.adapters.pick(req.chainId)        // 체인 분기는 어댑터 안에만 (2.4)
    const raw     = adapter.buildTransaction(req)          // 조립 — 순번/UTXO/blockhash 점유도 이 안 (4.3, 점유 기록 영속화)
    const signed  = this.hsm.sign(raw)                     // 서명 (HSM 앞 정책 게이트 경유 — 5.5, 실패 시 비멱등)
    return adapter.broadcast(signed)                       // 전파 → TxRef(hash)
  }
  getStatus(txRef) { return this.indexer.confirmationOf(txRef) }    // as-of-block 확정수
  transactionsOf(acct, range) { return this.indexer.transactionsOf(this.hd.issuedAddressesOf(acct), range) }
                                // 내 거래 이력 — 수신은 projection, 송신은 intent 저장소(4.3)가 합쳐 진실원천.
                                //   임의 "외부" 주소 이력은 아래 IndexerQueryAdapter.transfersOf (다른 포트)
  boost(txRef) {                                         // EVM/UTXO 만 — 같은 순번 + fee↑ (RBF). Solana 는 submit 뒤 auto-retry
    return this.adapters.pick(chainOf(txRef)).resend(txRef, bump)   // 재서명·재전파도 어댑터 안 (2.4 resend)
  }
  cancel(txRef) {                                        // EVM 예 — 같은 nonce 0원 self-send (cancel 도 capability, 13.3 — Solana 는 부재)
    return this.adapters.pick(chainOf(txRef)).broadcast(this.hsm.sign(zeroSelfSend(txRef)))
  }

  // 수신 트랜잭션 · 확정 : webhook 이 없으니 인덱서를 직접 운영 — 자체 구축의 "이벤트 소스" 는 인덱서다
  onChainEvent(handler) {
    this.indexer.subscribe(ourAddrs, ev => handler(ev))    // RPC 폴링/스트림 → 우리 주소 필터
  }
}

// ── ChainQueryPort 는 custody provider 가 아니라 "인덱서 어댑터" 가 채운다 (13.4 의 별개 슬롯) ──
//    하이브리드와 같은 클래스 — custody 가 Fireblocks 여도 이 어댑터만 붙이면 ChainQuery 가 생기고,
//    Alchemy 어댑터로 교체할 수도 있다. 그래서 custody 선택과 무관하게 한 벌만 존재한다.
class IndexerQueryAdapter implements ChainQueryPort {
  constructor(private indexer: SelfIndexer) {}
  transfersOf(addr, range) { return this.indexer.transfersOf(addr, range) }          // 임의 주소의 이체 이력 (projection)
  balanceAt(addr, asset, block) { return this.indexer.balanceAt(addr, asset, block) } // as-of-block 잔액
  query(filter) { return this.indexer.query(filter) }                                 // 탈출구 — 커스텀·집계 (13.3)
}

코어가 호출하는 시그니처는 14장과 글자 그대로 같다(submitTransaction·getStatus·boost·onChainEvent…). 달라진 것은 오직 { } 안 — Fireblocks 의 한 줄이 여기서는 "조립→서명→전파" 와 "인덱서 운영" 으로 펼쳐진다.

15.3 계정·주소 발급 단계별 흐름

자체 구축은 발급도 직접 한다 — Fireblocks 가 해주던 vault 생성·주소 파생을 우리 HD 지갑·HSM 으로 수행한다. 다만 9.2 에서 본 대로 곡선·체인에 따라 발급 흐름 자체가 세 갈래라서, 그림도 체인별로 나눠 그린다. 진입(비즈니스 레이어 → 지갑 서비스 백엔드, 지갑 개설(고객 ref · asset) + 멱등 키 — 이 한 요청을 백엔드가 아래 포트 호출들로 푼다. 내부 역할 분담은 9.1)과 마무리(계정 디렉터리 저장 + 인덱서 watch-list 등록, 9.4)는 세 갈래 공통이므로 백엔드부터 그린다. 각 그림에 등장하는 참가자 수 자체가 비용 차이다 — secp256k1? 은 둘(HSM 없음), ed25519? 는 셋(HSM 내부 파생), Canton 은 넷(participant node 까지 가는 유료 온장 등록). 그림의 파란 상자는 한 프로세스(우리 서버)다 — 상자 밖(HSM·participant node·인덱서)으로 나가는 화살표만 네트워크/장비 호출이고, 상자 안은 메서드 호출이다. 레이어로는 어댑터(AccountPort 구현)부터 블록체인 매니저 영역(9.1·13.1).

① secp256k1 (EVM·BTC) — 로컬 공개 파생. 참가자가 지갑 서비스 백엔드와 AccountPort 둘뿐이다.

Figure 15-2a. secp256k1 첫 주소 발급 — 주소가 태어나는 동사는 issueDepositAddress 다. 계산은 xpub(공개키만으로 하위 주소를 파생할 수 있는 확장 공개키)만으로 로컬에서 끝난다 — 온체인 트랜잭션도, HSM 호출도 없다. addressOf 는 이렇게 등록된 주소를 돌려주는 조회일 뿐, 절대 새 주소를 만들지 않는다.

"개인키도 HSM 호출도 없다"가 가능한 이유 — 이 흐름에서 키는 만들어지지 않기 때문이다. master seed(부모 개인키)는 시스템 셋업 때 HSM 안에서 한 번 생성되고 xpub 만 반출돼 있다. 지갑 생성은 그 키 트리에서 다음 가지 번호를 집는 일(index 할당)일 뿐이라 고객이 100만 명이어도 키는 여전히 master seed 하나다. 출금 때는 HSM 이 자기 안에서 같은 path 로 자식 개인키를 파생해 서명한다(5. 서명) — secp256k1 non-hardened 파생은 공개키 쪽(밖, xpub)과 개인키 쪽(HSM 안)이 수학적으로 평행이라, 발급 때 계산한 주소와 서명 때 파생한 개인키가 항상 한 쌍으로 맞아떨어진다. 대가도 있다: xpub 이 유출된 상태에서 자식 개인키가 하나라도 새면 부모 개인키가 역산되므로(BIP-32 non-hardened 의 알려진 성질), xpub 은 이름과 달리 수탁 운영에선 비밀급으로 다룬다.

② ed25519 (Solana) — HSM 내부 파생. SLIP-0010 hardened-only? 라 파생 자체를 키가 있는 곳에서 해야 해서, HSM 이 참가자로 추가된다.

③ Canton — createAccount 가 곧 party allocation. 세 갈래 중 유일하게 온장(on-ledger) 등록이라 participant node 가 참가자로 추가되고, 발급 작업이 전부 createAccount 쪽에서 일어난다. addressOf 는 디렉터리 조회만(2.4).

    ACC-->>BE: accountId
    BE->>ACC: addressOf(account, asset)
    ACC->>ACC: 디렉터리의 PartyId 반환 — 조회만 (2.4)

Figure 15-2c. Canton 발급 — generate-topology → HSM 으로 hash 서명 → allocate 의 party allocation 이 createAccount 단계에서 일어난다. 세 갈래 중 유일한 온체인 등록(비용 발생).

세 갈래 모두 개인키는 HSM 밖으로 나오지 않고, 어느 갈래든 계정 디렉터리 저장과 인덱서 watch-list 등록(9.4)까지 끝나야 발급 완료다 — ①②는 issueDepositAddress 안에서, ③은 createAccount 마무리에서. 그리고 주소가 태어나는 길은 이 두 동사뿐이다 — addressOf 는 어느 체인에서든 등록된 주소를 읽기만 한다. 경로(coin type·스크립트 유형)·인코딩 차이는 멀티체인 어댑터(2.2 표 주소 파생 행)가 흡수한다.

④ 추가 입금 주소 발급 — 같은 동사를 한 번 더. ①②의 첫 주소를 만든 그 issueDepositAddress 를 운영 중에 다시 부르면 추가 입금 주소다 — 다음 index 가 나올 뿐 절차는 같다(UTXO 의 입금별 새 주소, 고객별 주소 회전). 조회와 달리 부를 때마다 새 주소가 나오는 쓰기라서, 같은 요청의 재시도가 두 번 발급되지 않게 요청마다 멱등 키를 받아 부른다. Canton 은 이 capability 미구현 — 추가 주소 개념이 없어 입금 구분은 memo-ref 다.

15.5 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 주소로 트랜잭션이 들어옴
  2. 자체 인덱서가 노드/RPC 를 폴링·구독해 우리 주소로의 transfer 를 스스로 감지 → projection 에 pending
  3. confirmation 누적이 확정 기준(finalityRule) 충족 → confirmed → onChainEvent 로 코어에 통지
  4. reorg 나면 projection 롤백 (원시 로그 보존)

Fireblocks 가 webhook 으로 주던 것을, 여기선 인덱서를 직접 운영해 onChainEvent 뒤에서 만든다.

15.6 인덱서는 별도 백그라운드 job (요청 경로 밖)

앞의 부품 중 인덱서만 성격이 다르다. nonce·서명·전파는 submitTransaction 요청이 올 때 동작하지만(요청 경로), 인덱서 수집·가공은 체인이 흐르는 한 계속 돌아야 한다 — 끊기면 입금·확정을 놓친다. 그래서 요청 경로와 분리된 상시 worker 로 둔다.

Fireblocks 면 이 job 이 사라진다

이 상시 수집 job 은 자체 구축에서만 우리가 운영한다. Fireblocks 를 쓰면 Fireblocks 가 자기 vault 범위에서 이 job 을 대신 돌려 webhook 으로 push 해주므로, 우리는 수신만 한다 (단 임의 외부 주소·커스텀 조회가 필요하면 이 job 을 자체로 운영 — 13.4 의 ChainQueryPort 추가).

15.7 노드 조달 옵션 — 설치형 · 관리형 전용 · 공용 SaaS

15.2 의 NodeRpc 부품(전파·체인 RPC)을 어디서 가져오느냐는 자체 구축 안의 하위 선택이다. 같은 슬롯에 무엇을 꽂든 서명(HSM)·nonce·인덱서는 그대로 자체 — 노드만 다르다. 그래서 이건 별도 아키텍처가 아니라 노드 조달 스펙트럼이다.

15.9 Canton 에서는

자체 구축은 Canton 도 직접 진다 — 세 어댑터 중 가장 무겁다. EVM 의 RPC 노드 대신 Canton validator(participant) node 를 운영해 Global Synchronizer 에 연결해야 한다. 이 절의 Canton 동작은 Canton 공식 문서(docs.canton.network) 기준이다.
