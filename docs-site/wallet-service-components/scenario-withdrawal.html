11. 출금 시나리오

우리 자산을 외부로 보내는 쓰기 흐름 — 조립 · 서명 · 전파 · 확정 · 재전송

출금은 체인에 쓰는 흐름이라 가장 많은 컴포넌트가 맞물린다. 핵심 주연은 트랜잭션 빌더 · Nonce/Broadcast이고, 서명·멀티체인 어댑터·인덱서(확정 감지)가 협력한다. 단 출금 승인 자체는 본 가이드 범위 밖에서 끝난 뒤, 매니저는 승인된 지시만 받아 집행한다.

Figure 11-1. 출금 표준 흐름. 출금 요청·승인은 비즈니스 레이어에서 완료된 상태로, 비즈니스 레이어가 승인된 지시를 게이트웨이에 넘긴다(승인 절차 자체는 본 가이드 범위 밖). 키는 외부 서명자(SG)에만 있고 서명 오케스트레이션은 호출 경계일 뿐이다. 순번 점유 → 서명 → 전파 → 확정 순서가 깨지지 않는 것이 안전성의 핵심.

Canton 같은 체인은 "제출=완료" 가 아니다 (2-step 전송)

EVM 출금은 "조립→서명→전파→확정" 으로 끝나지만, Canton 은 2-step이다 — 우리가 보내는 건 OFFER 이고, 받는 쪽이 ACCEPT 해야 완료(REJECT/WITHDRAW 로 끝날 수도). 그래서 출금 상태머신에 "offer 제출 → 상대 수락 대기" 단계가 추가된다. 멀티체인 어댑터(2)가 이 차이를 흡수하고, getStatus·onChainEvent 가 OFFER/ACCEPT/REJECT/WITHDRAW 를 다룬다. (상대 사전승인 시 PRE_APPROVAL 로 1-step. Fireblocks 도 지원하는 것으로 공식 문서에 표기되어 있다 — 정확한 상태 매핑·timeout 은 적용 전 확인 필요.)

11.2 막힌 트랜잭션(stuck) 재전송

전파한 트랜잭션이 수수료 부족·혼잡으로 확정되지 않으면, 계정형 체인에서는 그 순번(nonce?)이 막혀 뒤 트랜잭션이 전부 멈춘다. 트랜잭션 빌더가 이를 감지해 재전송한다.

Figure 11-2. stuck 재전송. 노랑 = 대기/막힘, 초록 = 확정, 보라 = 재전송(같은 순번 + 수수료 양 필드 동시 인상), 빨강 = 취소(같은 순번으로 0원 self-send — 자기 주소로 0원을 보내 같은 순번을 덮어쓴다. 기존 tx 보다 수수료를 올려야 교체된다). EVM 의 수수료 교체는 두 수수료 필드 — 기본 수수료 상한(maxFeePerGas)과 우선 수수료(maxPriorityFeePerGas) — 를 모두, 노드가 요구하는 최소 인상률(통상 10%) 이상 올려야 받아들여진다. 규칙: 항상 가장 오래된 막힌 순번부터 처리하고, 수수료는 상한(ceiling)을 두고 단계적으로 올린다. 자세히는 4. 트랜잭션 · Nonce · Broadcast.

11.3 컴포넌트별 역할 요약

컴포넌트출금에서의 역할
트랜잭션 · Nonce · Broadcast주연. 조립·순번 점유·전파·확정 추적·stuck 재전송. 지갑별 직렬화로 순번 충돌 방지.
서명 오케스트레이션외부 서명자 호출 경계. 키 미보관.
멀티체인 어댑터체인별 순번/UTXO?·수수료·재전송 규칙 제공.
인덱서전파한 tx 의 확정 여부 역방향 확인.
온체인 정합성출금 확정의 온체인 정합성 확인 후 회계 평면 제공.
순서가 곧 안전

출금에서 가장 위험한 실수는 순서 역전이다. 승인 전 전파, 서명 전 장부 차감, 확정 전 "완료" 통지는 모두 사고로 이어진다. 각 단계는 직전 단계의 확정을 전제로만 진행하고, 모든 전이는 요청 ID + 멱등 키로 추적되어 재처리에도 한 번만 실행되어야 한다.
