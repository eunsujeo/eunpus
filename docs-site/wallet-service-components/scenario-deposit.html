10. 입금 시나리오

외부에서 우리 주소로 들어오는 크립토 입금 — 감지부터 확정·알림까지

입금은 우리가 체인에 무엇을 쓰는 게 아니라 체인에서 일어난 일을 읽어 인지하는 흐름이다. 따라서 주연은 인덱서이고, 멀티체인 어댑터(확정 기준)·온체인 정합성·알림이 보조한다. 쓰기 쪽(트랜잭션 빌더·서명)은 등장하지 않는다.

Figure 10-1. 입금 표준 흐름. 입금 주소는 9. 계정·주소 발급에서 이미 발급된 상태로 시작한다. 두 번의 알림 — 감지(PENDING, 사용 불가) → 확정(CONFIRMED, 사용 가능) — 이 핵심이며, webhook 은 비즈니스 레이어가 받아 사용자에게 전달한다(0.2 — 클라이언트는 비즈니스 레이어를 거친다). 확정 기준은 멀티체인 어댑터가 체인별로 정한다(예: EVM N 블록, Solana commitment 단계). 자금 사용 가능 판정은 반드시 확정 이후. 도식의 projection 은 인덱서가 가공해 둔 조회용 상태(주소별 잔액·입금 내역)를 말한다.

10.2 confirmation 상태 전이

입금은 "감지" 와 "확정" 이 다르다 — 확정 여부는 confirmation(확정 — 트랜잭션이 담긴 블록 위에 쌓인 블록 수)이 체인별 기준만큼 쌓였는지로 판단한다. 감지 즉시 잔액으로 인정하면 재구성(reorg?) 때 없는 돈을 쓰게 된다.

10.3 컴포넌트별 역할 요약

컴포넌트입금에서의 역할
인덱서주연. transfer 감지, confirmation 누적 추적, reorg 시 projection 롤백.
멀티체인 어댑터주소 파생 규칙 + 확정 기준 제공(체인별로 다름).
온체인 정합성 · 추적확정 입금의 온체인 정합성 확인 후 회계 평면에 제공.
이벤트 · 알림감지·확정·무효화 각각을 외부에 push.
API 게이트웨이입금 주소 발급, 입금 내역 조회.
설계 포인트
  • 감지 ≠ 확정 — 두 단계를 분리하고, 잔액 사용 가능 판정은 확정 이후로 미룬다.
  • reorg 안전 — projection 에 "어느 블록 기준" 인지(as-of-block)를 남기고, 원시 로그는 지우지 않는다.
  • 멱등 — 같은 입금 이벤트를 두 번 처리해도 장부가 두 번 늘지 않도록 (tx 해시 + logIndex) 를 키로.
  • 알림 ≠ 검증 — CONFIRMED webhook 은 인덱서 판정이고, 온체인 정합성 검증(7)은 사후·배경으로 따라온다. 검증에서 뒤집히면 정정 이벤트가 같은 채널로 온다(8) — 비즈 레이어는 반영 철회를 처리할 수 있어야 한다.

10.4 입금 다음 — 집금(sweep)으로 출금 지갑에 모은다

입금은 고객별 입금 주소에 떨어지지만, 출금은 출금 전용 지갑(vault)에서 나간다(14.6 의 vault 라우팅). 그 사이를 잇는 게 집금(sweep) — 입금 주소들에 쌓인 자금을 주기적으로 출금·treasury 지갑으로 모으는 내부 온체인 이동이다. 실제 수탁 지갑 운영에서 트랜잭션 볼륨의 상당 몫이 이 sweep 이고, 이게 안 돌면 출금 유동성이 마른다.

매니저 입장에서 sweep 은 새 컴포넌트가 아니라 또 하나의 송신 트랜잭션이다 — 4. 트랜잭션 파이프라인(조립·서명·전파·확정·멱등)을 출금(11장)과 똑같이 탄다. 보내는 곳과 받는 곳이 둘 다 우리 주소라는 점만 다르다. 단 sweep 고유의 난제가 셋 있다.

sweep 의 세 가지 난제
  • ERC-20 가스 충전 역설(gas station) — 토큰만 들어온 입금 주소는 가스용 네이티브 코인이 없어서 토큰을 내보낼 수 없다. 그래서 sweep 전에 그 주소로 가스비만큼 네이티브 코인을 먼저 보내는 충전 트랜잭션이 필요하고, 이 충전 자체도 같은 파이프라인을 타는 송신이다 — "토큰 1번 옮기는 데 tx 2개" 가 기본형이다.
  • 임계값·배치 정책 — 소액까지 매번 쓸면 수수료가 입금액을 잡아먹는다. 자산별 임계값(모일 때까지 대기), 수수료가 낮은 시간대 배치, UTXO 는 통합(consolidation) 겸용 같은 정책이 필요하다 — 이 정책(언제·얼마·어디로)은 자금 운용 평면과 걸친 결정이고, 매니저는 집행만 한다(0.3 과 같은 경계).
  • 멱등·추적 — sweep 도 중복 실행되면 이중 이동이다. 출금과 동일하게 멱등 키·correlationId 로 추적하고(7), "입금 N 건 → sweep 1 건" 의 다대일 매핑을 대사가 따라갈 수 있게 남긴다.

Fireblocks 경로에선 vault 간 이동도 같은 createTransaction(source/destination 이 둘 다 vault)이고, 자체 구축에선 입금 주소 키로 서명하는 일반 전송이다. 어느 쪽이든 트리거·정책·추적은 우리 몫으로 남는다 — 12.2 표의 "준비자산 온체인 이동" 이 바로 이 자리다.
