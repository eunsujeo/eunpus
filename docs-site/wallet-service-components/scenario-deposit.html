10. 입금 시나리오

외부에서 우리 주소로 들어오는 크립토 입금 — 감지부터 확정·알림까지

입금은 우리가 체인에 무엇을 쓰는 게 아니라 체인에서 일어난 일을 읽어 인지하는 흐름이다. 따라서 주연은 인덱서이고, 멀티체인 어댑터(확정 기준)·온체인 정합성·알림이 보조한다. 쓰기 쪽(트랜잭션 빌더·서명)은 등장하지 않는다.

10.1 표준 흐름

sequenceDiagram
    autonumber
    participant U as 사용자
    participant GW as API 게이트웨이
    participant IDX as 인덱서
    participant CH as 블록체인
    participant ADP as 멀티체인 어댑터
    participant LED as 온체인 정합성 · 추적
    participant NT as 이벤트 · 알림

    U->>GW: 입금 주소 요청
    GW->>ADP: 주소 파생(체인별 규칙)
    ADP-->>GW: 입금 주소
    GW-->>U: 입금 주소 발급

    Note over CH: 외부 송신자가 그 주소로 전송
    CH->>IDX: 새 블록 · 로그 수집
    IDX->>IDX: 우리 주소로의 transfer 감지
projection 에 pending +금액
    IDX->>NT: 입금 감지(PENDING) 알림
    NT-->>U: "입금 확인 중" webhook

    loop 확정 대기
        CH->>IDX: 후속 블록(confirmation 누적)
        IDX->>ADP: 확정 기준 충족?
    end
    ADP-->>IDX: 확정(finality) 도달
    IDX->>LED: 입금 확정 · 온체인 정합성 확인
    LED->>LED: 검증 사실 회계 평면 제공
    IDX->>NT: 입금 확정(CONFIRMED) 알림
    NT-->>U: "입금 완료, 사용 가능" webhook

Figure 10-1. 입금 표준 흐름. 두 번의 알림 — 감지(PENDING, 사용 불가) → 확정(CONFIRMED, 사용 가능) — 이 핵심이다. 확정 기준은 멀티체인 어댑터가 체인별로 정한다(예: EVM N 블록, Solana commitment 단계). 자금 사용 가능 판정은 반드시 확정 이후.

10.2 confirmation 상태 전이

입금은 "감지" 와 "확정" 이 다르다. 감지 즉시 잔액으로 인정하면 재구성(reorg?) 때 없는 돈을 쓰게 된다.

(CONFIRMED)

    ORPH["❌ 무효화

    DET -->|reorg 발생| ORPH

Figure 10-2. 입금 상태 전이. 노랑 = 감지(보류), 초록 = 확정(사용 가능), 빨강 = reorg 무효화. 주의: 무효화된 tx 가 mempool 을 거쳐 새 블록에 다시 들어올 수 있으므로 영구 삭제 금지 — 다시 감지 상태로 돌아갈 수 있다.

10.3 컴포넌트별 역할 요약

컴포넌트입금에서의 역할
인덱서주연. transfer 감지, confirmation 누적 추적, reorg 시 projection 롤백.
멀티체인 어댑터주소 파생 규칙 + 확정 기준 제공(체인별로 다름).
온체인 정합성 · 추적확정 입금의 온체인 정합성 확인 후 회계 평면에 제공.
이벤트 · 알림감지·확정·무효화 각각을 외부에 push.
API 게이트웨이입금 주소 발급, 입금 내역 조회.
설계 포인트
  • 감지 ≠ 확정 — 두 단계를 분리하고, 잔액 사용 가능 판정은 확정 이후로 미룬다.
  • reorg 안전 — projection 에 "어느 블록 기준" 인지(as-of-block)를 남기고, 원시 로그는 지우지 않는다.
  • 멱등 — 같은 입금 이벤트를 두 번 처리해도 장부가 두 번 늘지 않도록 (tx 해시 + logIndex) 를 키로.
