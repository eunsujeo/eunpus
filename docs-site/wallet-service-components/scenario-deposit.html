10. 입금 시나리오

외부에서 우리 주소로 들어오는 크립토 입금 — 감지부터 확정·알림까지. Service 백엔드가 webhook 을 받는다

입금은 우리가 체인에 무엇을 쓰는 게 아니라 외부에서 일어난 일을 알아채는 흐름이다. 매니저로 Fireblocks 를 채택했으므로 우리 쪽에 상시 인덱서는 없다 — Fireblocks 가 자기 vault 범위를 감지해 webhook 으로 알려주고, 우리 쪽 webhook 수신기(Service 백엔드)가 받아 매핑 DB 에 기록한다. 쓰기 쪽(출금 파이프라인·서명)은 등장하지 않는다. 그래서 이 시나리오의 핵심 질문은 하나로 좁혀진다 — 언제부터 잔액으로 믿는가. 답은 "감지 ≠ 확정" 이고, Fireblocks 는 이 둘을 상태값으로 갈라 준다.

10.1 표준 흐름

    WH-->>BIZ: 입금 완료 · 사용 가능 통지

Figure 10-1. 입금 표준 흐름. 입금 주소는 9. 계정·주소 발급에서 이미 발급된 상태로 시작한다. 우리 쪽에 상시 인덱서는 없다 — Fireblocks 가 감지·통지를 맡고, 우리 몫은 webhook 수신기(Service)가 받아 매핑 DB 에 기록하는 inbound 경로 하나다. 두 통지의 성격 차이가 핵심 — CONFIRMING(체인 등장·미확정)에서는 기록만 하고, COMPLETED(DCCP 임계 confirmation 도달 = finality)에서만 available 잔액을 올린다. ERC-20 토큰 입금도 별도 주소가 아니라 같은 주소로 오는 토큰 전송이라 같은 경로를 탄다. webhook 은 비즈니스 레이어를 거쳐 사용자에게 전달된다(0.2).

webhook 은 힌트, 대사가 최종 근거

webhook 은 누락·지연·중복이 가능하므로 통지는 힌트로만 보고, 회계의 최종 근거는 주기적 대사(벤더 잔액과 우리 기록의 대조, 7. 온체인 정합성 · 추적)가 닫는다. 그리고 같은 입금 이벤트를 두 번 받아도 장부가 두 번 늘지 않도록 (tx 해시 + logIndex) 를 멱등 키로 둔다.

10.2 CONFIRMING → COMPLETED — DCCP 가 무엇을 확정으로 바꾸나

입금은 "감지" 와 "확정" 이 다르다. Fireblocks 는 입금 하나의 상태를 CONFIRMING → COMPLETED 로 흘려보내고, 이 둘을 가르는 것이 DCCP(Deposit Control and Confirmation Policy) — CONFIRMING 을 COMPLETED 로 넘기는 임계 confirmation 수를 정하는 정책이다. 즉 이 문서가 말하는 "finality" 는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준이다. DCCP 는 거버넌스 영역이라 설정·임계값 관리는 Admin 백엔드의 몫이고, 실제 입금 이벤트를 받아 잔액에 반영하는 런타임은 Service 백엔드의 몫이다 — 정하는 쪽과 쓰는 쪽이 갈린다.

DCCP 기본 임계값 (설정 주체 = Admin)
  • 대부분의 체인 = 1 — 블록 하나면 확정으로 본다.
  • ETC(이더리움 클래식) = 372 — 과거 reorg 리스크가 커 임계가 매우 높다.
  • 컨트랙트 호출(contract call) = 최소 3 권장 — 단순 전송보다 보수적으로.

이 값은 커스텀 DCCP 로 조정할 수 있고, 조정 권한과 책임은 Admin 에 둔다. 우리 EVM 대상(이더리움·Base)에서 어떤 임계를 쓸지는 자산·리스크 정책에 따라 Admin 이 정하고, Service 는 그 결과로 도착한 COMPLETED 만 신뢰하면 된다.

함정 — 첫 COMPLETED 를 곧 finality 로 단정하지 말 것 (zero-confirmation)

Deposit Policy 를 zero-confirmation 으로 두면 COMPLETED 가 블록에 등장하는 시점에 먼저 뜰 수 있고 이후 webhook 이 여러 번 더 올 수 있다. 즉 이 설정에서는 "COMPLETED webhook 을 처음 받았다" 가 곧 "충분한 confirmation 이 쌓였다" 를 뜻하지 않는다. 그래서 잔액 반영 판정은 status 만 보지 말고 tx 객체의 numOfConfirmations(실제 누적 confirmation 수) 를 우리 finality 임계값(DCCP)과 직접 비교하는 편이 안전하다 — numOfConfirmations 가 "confirm(체인 등장) ↔ finality(임계 도달)" 를 가르는 눈금이다.

10.3 입금 상태 전이 — 감지 · 확정 · 무효화

Fireblocks 가 감지·통지를 대신해도 체인 자체의 성질은 사라지지 않는다. 이더리움과 Base 는 둘 다 EVM 이라 체인 끝이 드물게 교체(reorg?)될 수 있다. reorg 가 일어나면 한 번 본 입금이 무효화될 수 있다. 무효화를 벤더가 어떤 상태값으로 노출하는지는 문서에 명시가 없어 확인 중이고, 확인 전까지는 주기 대사가 되돌림을 잡는 최종 안전망이다.

Figure 10-2. 입금 상태 전이. 노랑 = 감지(CONFIRMING·보류), 초록 = 확정(COMPLETED·사용 가능), 빨강 = reorg 무효화. 핸들러는 무효화 신호를 받아 가공본(잔액 반영분)만 취소하고 원본 기록은 영구 보존한다 — 같은 입금이 재편입되면 다시 등장(CONFIRMING)할 수 있기 때문이다. tx 의 networkStatus 하위값(DROPPED · BROADCASTING · CONFIRMING · CONFIRMED · FAILED)이 상위 status 를 뒷받침하는 보조 신호다. Base 는 L2(OP-Stack) 라 소프트 확정과 L1 최종성 사이에 시차가 있어, 같은 EVM 이라 경로는 같아도 어느 시점을 finality 로 볼지의 여유(DCCP 임계)를 이더리움과 다르게 둘 수 있다 — 이 판단도 Admin 이 정해 Support 에 요청하는 DCCP 임계에 담긴다.

10.4 백엔드에서 이렇게 받는다 — 한 핸들러, 세 상태

// Fireblocks webhook 수신기(Service)가 받는 상태 이벤트 — 핸들러는 하나
transactions.onChainEvent { ev ->
    when (ev.status) {
        CONFIRMING -> notify(ev.account, "입금 확인 중")                 // 체인 등장·미확정 — 잔액 반영 금지
        COMPLETED  -> if (ev.numOfConfirmations >= finalityThreshold(ev.asset)) {
                          ledger.credit(ev); notify(ev.account, "입금 완료")  // DCCP 임계 도달 = finality
                      }
        무효화 신호 -> ledger.revert(ev)                               // reorg — 벤더 상태값은 확인 중
    }
}

핵심은 세 상태의 의미 분리다 — CONFIRMING 은 confirm(체인 등장)일 뿐 아직 finality 가 아니라 잔액을 건드리지 않고, COMPLETED 여도 zero-confirmation 함정 때문에 numOfConfirmations 를 finality 임계(DCCP)와 비교한 뒤에만 credit 한다. finalityThreshold 는 DCCP 임계(Admin 이 정해 Support 에 요청)를 Service 가 읽어 온 것이고, reorg 무효화는 이더리움·Base 공통의 EVM 속성이라 반드시 처리한다.

10.5 컴포넌트별 역할 요약

컴포넌트입금에서의 역할
입금 감지 (webhook)주연. Fireblocks 가 vault 범위를 감지해 CONFIRMING·COMPLETED·무효화 신호를 webhook 으로 push, 수신기가 받아 매핑 DB 에 기록.
체인 차이 흡수 — EVM이더리움·Base 의 주소 체계·ERC-20 로그·reorg 성질을 매니저 안에서 흡수.
온체인 정합성 · 추적확정 입금의 정합성 확인 + 벤더 잔액 대사 후 회계 평면에 제공.
이벤트 · 알림감지(CONFIRMING)·확정(COMPLETED)·무효화 각각을 외부에 push.
API 게이트웨이입금 주소 발급, 입금 내역 조회.
설계 포인트
  • 감지 ≠ 확정 — CONFIRMING 과 COMPLETED 를 분리하고, 잔액 사용 가능 판정은 DCCP 임계 도달(COMPLETED + numOfConfirmations) 이후로 미룬다.
  • reorg 안전 — 무효화는 가공본(잔액 반영분)만 취소하고 원본 기록은 지우지 않는다 — 재편입되면 다시 CONFIRMING 으로 돌아올 수 있다.
  • 멱등 — 같은 입금 이벤트를 두 번 처리해도 장부가 두 번 늘지 않도록 (tx 해시 + logIndex) 를 키로.
  • 알림 ≠ 검증 — COMPLETED webhook 은 벤더 통지이고, 온체인 정합성·대사(7)는 사후·배경으로 따라온다. 검증에서 뒤집히면 정정 이벤트가 같은 채널로 온다(8) — 비즈 레이어는 반영 철회를 처리할 수 있어야 한다.

10.6 입금 다음 — 집금(sweep)으로 출금 지갑에 모은다

입금은 고객별 입금 주소에 떨어지지만, 출금은 출금 전용 지갑(vault)에서 나간다(14.6 의 vault 라우팅). 그 사이를 잇는 게 집금(sweep) — 입금 주소들에 쌓인 자금을 주기적으로 출금·treasury 지갑으로 모으는 내부 온체인 이동이다. 실제 수탁 지갑 운영에서 트랜잭션 볼륨의 상당 몫이 이 sweep 이고, 이게 안 돌면 출금 유동성이 마른다.

매니저 입장에서 sweep 은 새 컴포넌트가 아니라 또 하나의 송신 트랜잭션이다 — 4. 출금 파이프라인(조립·서명·전파·확정·멱등)을 출금(11장)과 똑같이 탄다. 보내는 곳과 받는 곳이 둘 다 우리 주소라는 점만 다르다. 단 sweep 고유의 난제가 셋 있다.

sweep 의 세 가지 난제
  • ERC-20 가스 충전 역설(gas station) — 토큰만 들어온 입금 주소는 가스용 네이티브 코인이 없어서 토큰을 내보낼 수 없다. 그래서 sweep 전에 그 주소로 가스비만큼 네이티브 코인을 먼저 보내는 충전 트랜잭션이 필요하고, 이 충전 자체도 같은 파이프라인을 타는 송신이다 — "토큰 1번 옮기는 데 tx 2개" 가 기본형이다.
  • 임계값·배치 정책 — 소액까지 매번 쓸면 수수료가 입금액을 잡아먹는다. 자산별 임계값(모일 때까지 대기), 수수료가 낮은 시간대 배치, UTXO 는 통합(consolidation) 겸용 같은 정책이 필요하다 — 이 정책(언제·얼마·어디로)은 자금 운용 평면과 걸친 결정이고, 매니저는 집행만 한다(0.3 과 같은 경계).
  • 멱등·추적 — sweep 도 중복 실행되면 이중 이동이다. 출금과 동일하게 멱등 키·correlationId 로 추적하고(7), "입금 N 건 → sweep 1 건" 의 다대일 매핑을 대사가 따라갈 수 있게 남긴다.

Fireblocks 경로에선 vault 간 이동도 같은 createTransaction(source·destination 이 둘 다 vault)이라 출금과 같은 파이프라인·서명(co-signer 공동서명)을 탄다. 트리거·정책·추적은 우리 몫으로 남는다 — 12.2 표의 "준비자산 온체인 이동" 이 바로 이 자리다.
