18. 지갑 생성 애니메이션

지갑이란 무엇인가 — 그리고 시스템 셋업부터 체인별 발급까지, 단계별로 움직여 보기

9장(발급 시나리오)의 내용을 한 화면에서 단계 재생으로 본다. 새 사실은 없다 — 글로 읽은 것을 움직임으로 다시 보는 페이지다. 매니저는 Fireblocks, 태우는 체인은 EVM(이더리움·Base)이므로, 아래 발급 흐름은 EVM(secp256k1)을 기준으로 본다.

18.1 지갑이란 — 키 트리 하나 + 장부

수탁 서비스에서 "지갑" 은 흔한 오해와 달리 고객마다 만들어지는 키가 아니다. 실체는 둘뿐이다:

  • 키 트리 하나 — 시스템 셋업 때 HSM? 안에서 한 번 생성되는 master seed(부모 개인키). 고객이 100만 명이어도 키는 이 하나다.
  • 장부(계정 디렉터리 + watch-list) — "고객 ref → 트리의 가지 번호(index) → 발급된 주소" 매핑. 지갑 "생성" 은 키 생성이 아니라 이 장부에 줄을 하나 늘리는 일이다.

그래서 동사가 갈린다(13.3) — 주소가 태어나는 길은 상태 있는 동사(issueDepositAddress)뿐이고, addressOf 는 장부에 등록된 주소를 읽기만 한다. 발급의 끝은 언제나 디렉터리 저장 + watch-list 등록(9.4) — 등록 실패 = 발급 실패다. (Fireblocks 채택 기준에선 vault 가 곧 감시 범위라 별도 watch-list 등록이 불요할 수 있다 — 개념상 "발급의 끝 = 장부 확정"은 같다.)

18.2 단계별 애니메이션 — 셋업 1회, 그 뒤 체인별 발급

탭을 고르고 다음(또는 자동재생)으로 단계를 진행한다. 상자 위에 쌓이는 칩이 그 시점까지 만들어진 것들이다. EVM 발급 갈래에서 HSM(또는 벤더 MPC 키)이 흐려져 있는 것이 핵심 — secp256k1 발급은 서명 키를 깨우지 않는다(이유는 ⓪ 셋업). Fireblocks 채택 기준에선 이 키 곁 연산이 벤더 MPC 안에서 일어나지만, "주소는 공개키 파생으로 로컬 계산되고 서명 키는 잠들어 있다"는 성질은 같다.

Figure 18-1. 지갑 생성 인터랙티브 흐름(EVM 기준). ⓪ 셋업은 시스템 수명에서 1회 — master seed 는 키 보관처(HSM/벤더 MPC) 안에서 태어나 안에 머물고 공개키(xpub)만 반출된다. ① EVM 발급은 고객 온보딩마다 — 두 포트 호출(createAccount → 첫 주소 확보)로, secp256k1 주소는 xpub 만으로 로컬 계산된다(9.2 표). 색 분류: 파랑=지갑 서비스 백엔드/포트, 호박=키 보관처, 회색=외부 시스템, 초록=장부(디렉터리·watch-list).

18.3 EVM 발급을 한 줄로

갈래주소가 태어나는 방식서명 키의 역할
EVM (secp256k1)
이더리움 · Base		issueDepositAddress 가 xpub(공개키)만으로 로컬 계산 — non-hardened 공개 파생. 이더리움과 Base 는 같은 EVM·같은 주소 체계라 갈래가 하나다.발급 때는 없음(잠들어 있음) — 개인키는 출금 서명 때만 키 보관처 안에서 파생·서명. Fireblocks 채택 기준에선 이 서명이 벤더 MPC + 우리 온프렘 co-signer 공동서명이다 (5장).

발급 단계에서 서명 키를 건드리지 않는다는 점이 핵심이다 — 주소는 공개키 파생만으로 나오고, 개인키(또는 MPC share)는 나중에 출금할 때 처음 깨어난다. 이 성질 덕에 "지갑 100만 개를 만든다"가 곧 "장부에 줄 100만 개를 늘린다"이지 "키 100만 개를 만든다"가 아니다.
