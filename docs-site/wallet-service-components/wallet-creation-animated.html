18. 지갑 생성 애니메이션

지갑이란 무엇인가 — 그리고 시스템 셋업부터 체인별 발급까지, 단계별로 움직여 보기

9장(발급 시나리오)의 내용을 한 화면에서 단계 재생으로 본다. 새 사실은 없다 — 글로 읽은 것을 움직임으로 다시 보는 페이지다. 매니저는 Fireblocks, 태우는 체인은 EVM(이더리움·Base)이므로, 아래 발급 흐름은 EVM(secp256k1)을 기준으로 본다.

18.1 지갑이란 — 키 하나 + 장부

수탁 서비스에서 "지갑" 은 흔한 오해와 달리 고객마다 만들어지는 키가 아니다. 실체는 둘뿐이다:

  • 서명 키 하나 — 시스템 셋업 때 한 번 준비되는 서명 키. 매니저로 Fireblocks 를 채택했으므로 이 키는 어느 한 곳에 통째로 있지 않고 MPC? 키 조각(share)으로 쪼개져 Fireblocks 클라우드와 우리 온프렘 API Co-signer(SGX/TEE?)에 나뉘어 있다. 고객이 100만 명이어도 이 키 하나로 모든 지갑을 다룬다 — 우리는 master seed 를 쥐지 않는다.
  • 장부(계정 디렉터리) — "고객 ref → vault → 발급된 주소" 매핑. 지갑 "생성" 은 키 생성이 아니라 이 장부에 줄을 하나 늘리는 일이다.

그래서 동사가 갈린다(13.3) — 주소가 태어나는 길은 상태 있는 동사(issueDepositAddress)뿐이고, addressOf 는 장부에 등록된 주소를 읽기만 한다. 발급의 끝은 계정 디렉터리 저장(9.4) — 저장 실패 = 발급 실패다. Fireblocks 채택 경로에선 vault 가 곧 감시 범위라 우리가 따로 watch-list 를 돌려 등록하지 않는다 — 발급된 주소로의 입금은 Fireblocks 가 자동 감지해 webhook 으로 알린다(9.4). 개념상 "발급의 끝 = 장부 확정" 은 같다.

18.2 단계별 애니메이션 — 셋업 1회, 그 뒤 발급

탭을 고르고 다음(또는 자동재생)으로 단계를 진행한다. 상자 위에 쌓이는 칩이 그 시점까지 만들어진 것들이다. EVM 발급 갈래에서 Fireblocks 는 vault 밑 주소를 만들어 돌려주지만 MPC 서명 키는 깨우지 않는다는 것이 핵심 — 주소 발급은 서명이 아니다. MPC 조각(Fireblocks 클라우드 + 우리 온프렘 co-signer)이 공동으로 깨어나는 것은 출금 서명 때뿐이다. "발급 때 서명 키는 잠들어 있다" 는 성질은 그대로다.

Figure 18-1. 지갑 생성 인터랙티브 흐름(EVM 기준). ⓪ 셋업은 시스템 수명에서 1회 — Fireblocks 워크스페이스·vault 와 MPC 키 조각이 한 번 마련되고, 조각 하나를 우리 온프렘 API Co-signer(SGX/TEE)가 넘겨받아 짝을 맺는다. 어느 한 곳도 키 전체를 갖지 않는다. ① EVM 발급은 고객 온보딩마다 — 두 포트 호출(createAccount → 첫 주소 확보)로, Fireblocks 가 vault 밑 순수 EVM 주소를 만들어 돌려준다(9.2 표). 색 분류: 파랑=지갑 서비스 백엔드/포트, 호박=서명 키(MPC 조각), 회색=외부 시스템(Fireblocks·온프렘 co-signer), 초록=장부(계정 디렉터리).

18.3 EVM 발급을 한 줄로

갈래주소가 태어나는 방식서명 키의 역할
EVM (secp256k1)
이더리움 · Base		issueDepositAddress(= Fireblocks generateNewAddress)가 vault 밑에 순수 EVM 주소 하나를 발급 — 곡선·파생·인코딩은 Fireblocks 가 흡수하고, 우리 쪽엔 주소 문자열만 온다(Address(value, memoTag=null)). 이더리움과 Base 는 같은 EVM·같은 주소 체계라 갈래가 하나다.발급 때는 없음(잠들어 있음) — 서명 키는 출금 때만 깨어난다. 그 키는 어느 한 곳에 통째로 있지 않고 MPC 조각으로 나뉘어 Fireblocks 클라우드와 우리 온프렘 API Co-signer(SGX/TEE)에 있으며, 출금 서명은 이 조각들의 공동서명이다 — 그 직전 우리 Callback Handler가 마지막 승인·거부 관문에 선다(5장).

발급 단계에서 서명 키를 건드리지 않는다는 점이 핵심이다 — 주소는 vault 밑에서 발급돼 돌아오고, MPC 조각은 나중에 출금할 때 처음 깨어난다. 이 성질 덕에 "지갑 100만 개를 만든다"가 곧 "장부에 줄 100만 개를 늘린다"이지 "키 100만 개를 만든다"가 아니다.

키를 통째로 쥔 곳이 없다 — MPC 의 성질

self-managed HD 지갑이라면 "xpub 유출 + 자식 개인키 하나 = 부모 키 역산" 같은 공개키 파생의 함정을 우리가 직접 방어해야 한다. Fireblocks 채택 경로엔 그 함정이 없다 — 우리는 xpub 도 master seed 도 쥐지 않기 때문이다. 대신 성질이 바뀐다: 서명 키는 MPC 조각으로 쪼개져 어느 한 곳(우리도, Fireblocks 도)도 전체 키를 갖지 못한다. 출금 서명은 Fireblocks 클라우드 조각과 우리 온프렘 API Co-signer 조각의 공동서명이라야 성립하고, co-signer 는 서명 직전 Callback Handler(우리 정책 훅)에 승인을 묻는다 — 그래서 나가는 돈의 마지막 자동 관문이 우리 인프라 안에 선다(5. 서명 · co-signer).
