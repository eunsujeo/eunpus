h1. 7 컴포넌트 책임 요약 — 두 층, 명확한 경계

{info:title=이 문서의 성격}
저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안이다. Fireblocks 를 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 검증이 필요하다.
{info}

컴포넌트를 나누는 기준은 "기능" 이 아니라 *책임 경계* 다 — 무엇을 결정하고, 무엇을 받기만 하고, 어디서 외부와 맞닿는가. 경계가 분명해야 한 컴포넌트의 장애나 변경이 다른 컴포넌트로 번지지 않는다.

h2. 1. 7 컴포넌트 한눈에

7 컴포넌트는 두 층에 속한다 — *Fireblocks 매니저(벤더 안)* 4개는 체인과 직접 대화하는 부분으로 Fireblocks 를 채택해 벤더 안에서 돌리고(다만 서명은 우리 API Co-signer 와의 공동서명이라 마지막 관문이 우리 인프라에 선다), *우리 백엔드* 3개는 벤더와 무관하게 항상 우리가 만들며 *Service*(고객 런타임)·*Admin*(운영·거버넌스)으로 물리 분리된다.

||컴포넌트||층||한 줄 책임||
|*API 게이트웨이*|우리 백엔드 · Service|외부 요청을 받아 인증하고, 같은 요청이 두 번 실행되지 않게 멱등 키(같은 요청 ID 로 두 번 들어와도 실행은 한 번만 — 이중 지급 방지)를 부여해 내부로 라우팅|
|*체인 차이 흡수 (EVM)*|Fireblocks 매니저|이더리움·Base 처럼 여러 EVM 체인의 차이(가스 시세·L2 확정 지연 등)를 한 가지 인터페이스로 정규화 — 벤더가 흡수|
|*입금 감지 (webhook)*|Fireblocks 매니저|체인 데이터에서 우리 주소로 들어온 수신 트랜잭션을 감지하고, 확정 판단(DCCP — 몇 번의 confirmation 을 쌓아야 finality 로 볼지 정하는 정책) 후 webhook 으로 밀어 넣는다|
|*출금 파이프라인*|Fireblocks 매니저|송신 트랜잭션(출금)을 조립하고, 순번(nonce — 체인이 요구하는 계정별 트랜잭션 순번)을 관리하며, 전파하고, 막히면(stuck) boost·cancel 로 재전송|
|*서명 오케스트레이션*|Fireblocks 매니저 (+ 우리 co-signer)|조립된 트랜잭션을 *Fireblocks MPC 와 우리 API Co-signer* 가 공동서명하는 경계. Co-signer 는 Callback Handler 에 승인을 물은 뒤 서명 share 를 낸다|
|*온체인 정합성 · 추적*|우리 백엔드 · Service·Admin|체인 사실 확정 · 요청 ID 연결 · 예외 감지 (회계 원장 대사는 회계 평면에 위임)|
|*이벤트 · 알림*|우리 백엔드 · Service|수신·확정·송신 완료 등 트랜잭션 상태 변화를 외부에 push (webhook/스트림). 상태를 만들지 않고 전달만 한다|

용어 — DCCP: Deposit Control and Confirmation Policy. 입금·출금을 확정으로 볼 임계 confirmation 수를 정하는 Fireblocks 정책이며, 대부분 체인 1, ETC(이더리움 클래식) 372, 컨트랙트 호출은 최소 3 권장이고, 설정·관리는 Admin 이 맡는다.

h2. 2. 책임 경계 매트릭스

각 컴포넌트가 하는 일을 세 가지로 나눈다 — *D*=결정(스스로 판단) · *X*=집행(받아서 실행) · *E*=외부 위임.

||관심사||주관 컴포넌트||성격||
|요청 진입 · 멱등|API 게이트웨이 (Service)|집행(X)|
|EVM 체인 규칙 정규화|체인 차이 흡수 (매니저)|결정(D) — 체인 semantic 한정 · 벤더 안|
|수신 트랜잭션 감지 · 확정 판단|입금 감지 (매니저)|결정(D) — 확정 정책 DCCP 적용|
|nonce · 전파 · 재전송 · boost·cancel|출금 파이프라인 (매니저 + Admin 개입)|결정(D) — 체인 쓰기 전략|
|서명|서명 오케스트레이션 → Fireblocks MPC + 우리 Co-signer|외부(E) — 벤더 + 우리 공동서명|
|온체인 정합성 · 추적|온체인 정합성 · 추적 (Service·Admin)|집행(X) — 사실 비교|
|상태 변화 알림|이벤트 · 알림 (Service)|집행(X) — 전달만|

h2. 3. 책임 경계의 핵심 — 비즈니스 판단은 어느 컴포넌트도 하지 않는다

{note:title=범위 밖}
어느 컴포넌트도 비즈니스 판단을 내리지 않는다. 출금도 매니저가 승인하지 않으며, *승인이 끝난 요청을 받아* 집행만 한다. 준비자산 운용(자금 평면)과 회계 원장 대사·기표(회계 평면)도 매니저가 소유·결정하지 않는다. 게이트웨이는 얇게 유지하고 로직은 뒤 컴포넌트로 위임하며, 알림은 상태를 만들지 않고 전달만 한다. 정책·승인·boost·cancel·동결 같은 운영·거버넌스는 *Admin 백엔드* 가 별도 경계에서 맡는다.
{note}

참고: 매니저가 보기에 "결정(D)" 으로 표시된 것도 모두 *기술적 판단*(확정 기준 충족 여부, 재전송 시점)이지 업무 판단이 아니다. 현금↔코인 전환(온/오프램프)은 수탁 지갑에선 은행 앱의 내부 작업이라 매니저 컴포넌트가 아예 아니다.
