h1. 설계 사유 — 왜 이렇게 잘랐고, 왜 이렇게 동작하는가

{info:title=이 문서의 성격}
가이드(0~17장)가 "무엇을 / 어떻게" 라면, 이 문서는 그 결정들의 *"왜"* 만 모았다 — 각 결정에서 검토했던 대안과 기각 사유를 함께 남긴다. 설계 리뷰·신규 합류자의 "왜 이렇게 했어요?" 에 대한 표준 답변이고, 결정을 뒤집을 때는 여기 적힌 기각 사유가 더 이상 성립하지 않는지 먼저 확인한다.
{info}

h2. 1. 구조 결정 — 두 층 · 세 포트 · 모노레포

* *왜 두 층(블록체인 매니저 / 지갑 서비스 백엔드)인가* — 교체 단위가 다르기 때문. 매니저(멀티체인·인덱서·nonce/트랜잭션·서명)는 Fireblocks 가 통째로 제공하거나 자체 구축하는 *교체 가능 영역*이고, 게이트웨이·멱등·정합성·알림은 어떤 벤더를 써도 *항상 우리 것*이다. 한 덩어리로 두면 벤더 도입·이탈 때마다 전면 재작업이 된다.
* *왜 포트를 기능별 3개(Account·Transaction·ChainQuery)로 잘랐나* — 매니저를 인터페이스 하나로 통째 추상화하면 교체 단위가 "전부 Fireblocks 냐 전부 자체냐" 둘뿐이라, "트랜잭션은 Fireblocks·임의 조회는 자체 인덱서" 같은 현실적 하이브리드가 표현되지 않는다. 기능별로 자르면 한 어댑터가 여러 포트를 채우고(Fireblocks), 없는 포트만 따로 붙인다(인덱서).
* *왜 submitTransaction 이 서명+전파 묶음인가* — Fireblocks 의 createTransaction 이 빌드·서명·전파·nonce 를 묶어서 주기 때문. 포트를 SignerPort/BroadcastPort 로 미리 쪼개면 SaaS 의 묶음과 안 맞아 교체가 깨진다. 더 쪼개는 건 "키는 자체 HSM, 전파는 외부 노드" 같은 실제 요구가 생겼을 때만.
* *왜 ChainQueryPort 에 도메인 동사(transfersOf·balanceAt)를 두고 generic query 는 탈출구로만 두나* — query(filter) 하나로 두면 filter 안으로 체인별 개념(로그 토픽·slot·ACS)이 전부 새어 들어와 "도메인 우선" 이 이 포트에서만 무너진다. 자주 쓰는 질의는 동사로 승격, 반복되면 또 승격.
* *왜 도메인 우선 + 벤더 현실 검증 하이브리드인가* — 벤더 우선(Fireblocks API 가 설계 중심)은 빠르지만 벤더 교체 시 코어 재설계다. 순수 도메인 우선은 추상화가 벤더 실능력과 어긋나 거짓말할 위험(Canton 2-step 같은). 그래서 포트는 우리 업무 언어로 두되 설계 단계에서 벤더가 실제 주는 것을 검증한다. 이 비용은 이더리움+Canton 병행·자체 custody 전환 검토처럼 *갈아탈 가능성이 실재할 때만* 정당화된다.
* *왜 모노레포·의존성 안쪽 강제인가* — 경계가 패키지 경계가 아니면 반드시 흐트러진다. domain(포트·모델)을 핵으로 모두가 안쪽만 의존하게 하고 ArchUnit 으로 CI 에서 검사 — "교체 가능" 은 문서가 아니라 빌드가 보장한다.

h2. 2. 컴포넌트별 사유

* *멀티체인 어댑터* — 체인 차이를 흩어 두면 모든 컴포넌트가 if(chain==...) 로 오염된다. 차이를 한 곳에 가두고 공통 동사만 노출. 단 체인이 못 하는 걸 되는 척하지 않도록 *능력(capability)을 타입으로 노출*한다 — boost?(EVM/UTXO 만)·cancel?(Solana 는 전파 후 취소 보장 불가). 최소공통분모로 깎으면 벤더·체인 강점을 못 쓰고, 숨기면 추상화가 거짓말한다.
* *인덱서* — 원시(raw, append-only)와 가공(projection)을 분리하는 이유: reorg 가 나거나 가공 로직이 바뀌어도 원시에서 다시 만들 수 있다. projection 은 재구성 가능한 캐시로 취급. pull+push 하이브리드 수집인 이유: push(스트림)는 빠르지만 끊기면 구멍, pull(폴링)은 느리지만 빠진 구간을 메운다. 수집은 체인별(ChainSource)·가공은 공통(SelfIndexer)으로 가른 이유: 새 체인이 와도 본체가 안 바뀌게. "우리 주소" 집합은 발급 때 watch-list 등록 + 등록 높이 이전 backfill 로 만든다 — 등록 경로가 빠지면 인덱서는 멀쩡히 돌면서 입금만 놓친다.
* *트랜잭션 · Nonce · Broadcast* — nonce 를 매번 체인에 묻지 않고 로컬 카운터+lock 으로 직렬화하는 이유: 동시 요청이 같은 값을 받아 충돌하기 때문(드리프트는 주기 재동기화로). *전파 전에 intent·서명본을 먼저 영속화*(BUILT→SIGNED→BROADCAST 상태머신)하는 이유: broadcast 후 기록이면 "전파 직후·기록 직전 사망 → 재시도가 새 nonce 로 새 tx" 가 되어 둘 다 유효한 이중 출금이 된다. 복구는 기록된 단계에서 *같은 서명본으로만* 이어간다. 재전송 정책(오래된 것부터·상한·알림)은 공통, 방식(RBF/CPFP/재조립/withdraw)은 체인별.
* *서명 오케스트레이션* — 키를 매니저가 안 드는 이유: 매니저 침해 = 키 유출이 되기 때문(외부 MPC/HSM 에 위임). 단 키 보관만으로는 부족하다 — sighash 만 넘기면 서명자는 눈 감고 서명(blind signing)하므로, *서명자 곁에서 원문을 재검증*(화이트리스트·한도)하는 정책 게이트를 둔다. Fireblocks co-signer·NodeWallet 승인자가 그 자리고, 자체 구축은 직접 만들어야 수탁 등급. 중복 서명 가드(markAttempt 선기록)가 막는 건 키 유출이 아니라 *유효 서명 2개 → 이중 전파*다. 가드 키는 출금 논리 ID 가 아니라 payload(sighash) 파생 — 아니면 fee bump 재서명이 옛 서명을 재사용한다.
* *API 게이트웨이* — 멱등이 1급 시민인 이유: 온체인 쓰기는 비가역이라 중복 실행 = 이중 지급. 멱등 키가 게이트웨이에서 끝나지 않고 파이프라인→externalTxId 까지 따라가는 이유: 중간 어느 단계가 재시도돼도 "정확히 한 번" 이 끝까지 보장돼야 해서. start 는 원자적 조건부 insert(멀티 인스턴스), inflight 는 lease(TTL) — 처리하던 인스턴스가 죽어도 키가 영구 고착되지 않게.
* *온체인 정합성 · 추적* — 회계 원장을 매니저가 안 갖는 이유: 잔액 진실원천·기표는 회계 평면의 책임이고, 매니저는 "검증된 체인 사실" 을 만들어 넘기는 데까지가 경계(준비자산을 범위 밖에 둔 것과 같은 논리). 트리거가 이벤트+주기 sweep 둘인 이유: 이벤트는 "일어난 것" 만 보고, 정합성에서 진짜 위험한 "일어나야 했는데 안 일어난 것"(전파됐는데 확정 없음)은 sweep 으로만 드러난다.
* *이벤트 · 알림* — at-least-once + dedup 인 이유: 분산 환경의 exactly-once 전달은 환상이라, 재시도(중복 허용)+양쪽 dedup+수신측 멱등이 현실적 구성. 알림이 정합성 검증 *전에* 나가는 이유: 빠름 우선의 의도적 선택 — 대신 정정 이벤트(reorg 무효화·정합성 MISMATCH)도 같은 채널로 보내 비즈 레이어가 반영을 철회할 수 있게 하고, 잔액의 최종 확정은 정합성 통과 사실 기준으로 잡는 계약을 명시한다.

h2. 3. 시나리오 결정 사유

* *왜 "호출" 과 "감지" 를 처음부터 가르나* — 입금을 "누가 호출하나" 로 생각하는 혼동이 가장 흔해서. 출금·발급·조회는 호출(inbound), 입금은 아무도 호출하지 않는 감지(event-driven) — 이 구분이 무너지면 컴포넌트 책임이 전부 꼬인다.
* *왜 온/오프램프가 매니저 밖인가* — 수탁이라 고객 코인 잔액이 은행 내부 장부(DB)다. 현금↔코인 전환은 코어뱅킹+DB 조정으로 끝나고 체인을 건너지 않는다. 매니저는 자산이 실제로 체인을 건너는 가장자리(외부 입금·외부 출금·treasury)에서만.
* *왜 집금(sweep)을 별도 컴포넌트로 안 두나* — 매니저 입장에서 sweep 은 "또 하나의 송신 트랜잭션" 이라 출금과 같은 파이프라인을 탄다. 다만 ERC-20 가스 충전 역설(토큰 1번 옮기는 데 tx 2개)·임계값/배치 정책·다대일 대사 같은 고유 난제는 시나리오(10.4)로 다룬다. 정책(언제·얼마)은 자금 운용 평면, 집행은 매니저.
* *왜 주소 발급 흐름에 watch-list 등록을 넣나* — 자체·하이브리드 인덱서에선 발급처(AccountPort)와 감시자(인덱서)가 다른 시스템이라, 등록이 늦으면 그 사이 입금이 그대로 누락된다(입금 사고 1위 유형). 등록 실패면 발급도 실패로 — 감시 안 되는 주소를 고객에게 주지 않는다.

h2. 4. 기각한 대안 모음

|| 대안 || 기각 사유 ||
| 매니저 단일 인터페이스 추상화 | 교체 단위가 전부-아니면-전무 — 하이브리드(Fireblocks+자체 인덱서) 표현 불가 |
| SignerPort / BroadcastPort 선분리 | Fireblocks 의 묶음(createTransaction)과 불일치 — 실요구 없는 분해는 leaky |
| ChainQueryPort = generic query 하나 | filter 로 체인 개념 누수 — 도메인 우선 붕괴 |
| 매 요청 체인 조회로 nonce 결정 | 동시성 구간에서 같은 값 → "nonce too low" 충돌 |
| broadcast 성공 후 멱등 기록 | 전파↔기록 사이 사망 시 재시도가 새 nonce 로 이중 출금 |
| sighash 만 받는 서명자 (정책 게이트 없음) | blind signing — 매니저 침해 = 키 사용 권한 탈취 |
| exactly-once 알림 전달 | 분산 환경에서 불가 — at-least-once + 수신측 멱등으로 |
| 알림을 정합성 검증 후에만 발행 | 지연이 UX·후속 처리를 막음 — 미검증 신호 + 정정 이벤트 계약으로 해소 |
| 고객 1명 = vault 1개 고정 | 리테일 규모(수십만+)에서 vault 폭발 — 비용·rate limit. 공용 vault + 내부 attribution 옵션 병행 검토 |
| 자체 nonce 매니저를 Fireblocks 위에도 운용 | 플랫폼 내부 순번 할당과 충돌 — SaaS 경로의 단위는 "트랜잭션 요청" |
