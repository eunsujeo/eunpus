h1. 설계 사유 — 왜 이렇게 잘랐고, 왜 이렇게 동작하는가

{info:title=이 문서의 성격}
가이드가 "무엇을 / 어떻게" 라면, 이 문서는 그 결정들의 *"왜"* 만 모았다 — 각 결정에서 검토했던 대안과 기각 사유를 함께 남긴다. 전제는 셋 — 매니저로 *Fireblocks 를 채택* 했고, 태우는 체인은 *EVM(이더리움·Base)* 이며, 우리 백엔드는 *Service*(고객 런타임)와 *Admin*(운영·거버넌스)으로 *물리 분리* 한다. 설계 리뷰·신규 합류자의 "왜 이렇게 했어요?" 에 대한 표준 답변이고, 결정을 뒤집을 때는 여기 적힌 기각 사유가 더 이상 성립하지 않는지 먼저 확인한다.
{info}

h2. 1. 구조 결정 — 두 층 · 세 포트 · 두 백엔드 · 모노레포

* *왜 두 층(블록체인 매니저 / 지갑 서비스 백엔드)인가* — 교체 단위가 다르기 때문. 매니저(멀티체인·인덱서·nonce/트랜잭션·서명)는 Fireblocks 가 통째로 제공하는 *교체 가능 영역* 이고, 게이트웨이·멱등·정합성·알림은 어떤 벤더를 써도 *항상 우리 것* 이다. 한 덩어리로 두면 벤더 도입·이탈 때마다 전면 재작업이 된다.
* *왜 매니저로 Fireblocks 를 채택했나* — 자체 구축(노드·HSM·인덱서·nonce·전파·정책 엔진 직접 운영)은 만드는 만큼 통제권을 갖지만 그 전체가 우리 운영·감사·장애 책임이 된다. Fireblocks 는 vault·MPC 서명·TAP 정책·노드·인덱싱·전파·수수료를 벤더 안에 넣어 우리 1차 작업 범위를 넷(두 백엔드 경계·포트 어댑터·webhook 수신·매핑 DB)으로 좁힌다. 자체 구축은 *검토했으나 라이브 경로에서 기각* 하고, 포트를 채우는 테스트용 가짜 구현으로만 남긴다(벤더 독립을 계약 테스트로 검증하는 용도).
* *왜 포트를 기능별 3개(Account·Transaction·ChainQuery)로 잘랐나* — 매니저를 인터페이스 하나로 통째 추상화하면 교체 단위가 "전부 Fireblocks 냐 전부 조회벤더냐" 둘뿐이라, "트랜잭션은 Fireblocks·임의 조회는 자체 인덱서" 같은 현실적 하이브리드가 표현되지 않는다. Fireblocks 는 임의 외부 주소 조회(ChainQueryPort)를 주지 않으므로 이 하이브리드는 실재한다. 기능별로 자르면 한 어댑터가 여러 포트를 채우고(Fireblocks), 없는 포트만 따로 붙인다(Alchemy 등).
* *왜 EVM(이더리움·Base)만 태우나* — Base 는 이더리움 L2(OP-Stack)라 주소·상태·수수료·boost/RBF·확정(DCCP) 모델이 이더리움과 사실상 같다. 같은 EVM 이라 포트 하나로 병행하고, 다른 L2 가 붙어도 어댑터의 체인·자산 등록만 는다. (한때 검토했던 Canton 같은 비-EVM 2-step 체인은 라이브 범위에서 뺐다 — 4장 참조.)
* *왜 submitTransaction 이 서명+전파 묶음인가* — Fireblocks 의 createTransaction 이 빌드·서명·전파·nonce 를 묶어서 주기 때문. 포트를 SignerPort/BroadcastPort 로 미리 쪼개면 SaaS 의 묶음과 안 맞아 어긋난다. 더 쪼개는 건 "키는 자체 HSM, 전파는 외부 노드" 같은 실제 요구가 생겼을 때만.
* *왜 ChainQueryPort 에 도메인 동사(transfersOf·balanceAt)를 두고 generic query 는 탈출구로만 두나* — query(filter) 하나로 두면 filter 안으로 체인별 개념(로그 토픽·블록 오프셋)이 전부 새어 들어와 "도메인 우선" 이 이 포트에서만 무너진다. 자주 쓰는 질의는 동사로 승격, 반복되면 또 승격.
* *왜 Service·Admin 을 물리 분리하나* — 나가는 돈에 개입하는 운영(TAP 정책 변경·co-signer 승인·boost·cancel·동결·sweep·rebalance)과 고객 런타임(계정·주소·입금·출금 제출·조회)은 권한·감사 경계가 달라야 한다. 둘을 한 배포에 두면 고객 트래픽과 운영 로그가 섞이고, Service 자격증명으로 자금 이동 액션이 가능해진다. 별도 배포·권한·감사 경계로 나누면 "누가 자금을 움직였나" 가 감사 경계 안에 그대로 남고, 운영 변경(정책 이관·새 체인 등록·sweep)이 고객 런타임 배포를 흔들지 않는다.
* *왜 도메인 우선 + 벤더 현실 검증 하이브리드인가* — 벤더 우선(Fireblocks API 가 설계 중심)은 빠르지만 벤더 교체 시 코어 재설계다. 순수 도메인 우선은 추상화가 벤더 실능력과 어긋나 거짓말할 위험(EVM 의 확정 지연을 한 상태로 뭉개는 등)이 있다. 그래서 포트는 우리 업무 언어로 두되 설계 단계에서 벤더가 실제 주는 것을 검증한다. 이 비용은 다중 EVM 체인 병행·훗날 벤더 교체 대비가 실재할 때만 정당화된다.
* *왜 모노레포·의존성 안쪽 강제인가* — 경계가 패키지 경계가 아니면 반드시 흐트러진다. domain(포트·모델)을 핵으로 두 backend(Service·Admin)와 adapters 가 모두 안쪽만 의존하게 하고, Fireblocks SDK 는 adapters/fireblocks 안에 격리해 의존 검사로 CI 에서 검사 — "교체 가능" 은 문서가 아니라 빌드가 보장한다.

h2. 2. 컴포넌트별 사유

* *멀티체인 어댑터 (EVM)* — 체인 차이를 흩어 두면 모든 컴포넌트가 if(chain==...) 로 오염된다. 차이를 어댑터 한 곳에 가두고 공통 동사만 노출. 이더리움·Base 는 같은 EVM 이라 어댑터가 사실상 하나고, 갈리는 지점(가스 시세·L2 확정 지연)만 임계값으로 조정한다. 능력(capability)을 타입으로 노출하는 이유 — boost?(EVM RBF)·cancel? 이 없는 체인이 붙어도 "되는 척" 하지 않게. 최소공통분모로 깎으면 Fireblocks 강점(createTransaction 묶음·RBF·DCCP)을 못 쓰고, 숨기면 추상화가 거짓말한다.
* *입금 감지 (webhook)* — 매니저로 Fireblocks 를 채택했으므로 우리가 상시 인덱서를 돌리지 않는다. Fireblocks 가 자기 vault 범위를 감지해 CONFIRMING·COMPLETED·ORPHANED 를 webhook 으로 push 하고, 우리 몫은 webhook 수신기(Service)가 받아 매핑 DB 에 기록하는 inbound 경로 하나다. "우리 주소" 집합을 별도 watch-list 로 관리하지 않는 이유 — vault 가 곧 감시 범위라 자체 인덱서 경로의 등록 갭이 구조적으로 없다. 다만 webhook 은 누락·지연·중복이 가능하므로 최종 근거는 주기적 대사가 닫는다.
* *트랜잭션 · Nonce · Broadcast* — Fireblocks 채택으로 조립·순번(nonce)·전파·복구가 통째로 벤더 안으로 들어간다. 우리가 raw nonce 를 직접 돌리지 않는 이유 — Fireblocks 내부 nonce 할당과 충돌하기 때문(SaaS 경로의 단위는 "트랜잭션 요청"). 재시도 안전장치는 하나 — 같은 externalTxId 로 재제출하면 벤더가 새 tx 를 만들지 않고 기존 것을 돌려준다. 막힘 대응(boost=RBF·cancel=0원 self-send)의 방식은 벤더가 집행하되, 언제 boost·언제 철회할지의 판단은 Admin 운영으로 남는다.
* *서명 오케스트레이션 — MPC + 온프렘 co-signer* — 키를 매니저(백엔드)가 안 드는 이유: 백엔드 침해 = 키 유출이 되기 때문. Fireblocks MPC 가 키 share 를 분산 보관하되, *share 하나는 우리 보안 존(SGX/TEE)의 API Co-signer* 가 들고 매 서명마다 벤더와 공동서명한다. 키 보관만으로는 부족하다 — sighash 만 넘기면 서명자는 눈 감고 서명(blind signing)하므로, 서명자 곁에서 원문을 재검증하는 정책 게이트를 둔다. 그 자리가 Fireblocks 거버넌스 정책 *TAP*(화이트리스트·건당 한도·일일 누적)과 우리 *Callback Handler*(co-signer 가 서명 직전 approve/deny 를 묻는 훅)다. 백엔드가 "승인된 척" 지시를 보내도 이 관문이 우리 인프라 안에서 막는다. TAP 정책·co-signer 승인의 관리는 Admin 거버넌스 몫이다.
* *API 게이트웨이* — 멱등이 1급 시민인 이유: 온체인 쓰기는 비가역이라 중복 실행 = 이중 지급. 멱등 키가 게이트웨이에서 끝나지 않고 Fireblocks 의 externalTxId 까지 따라가는 이유: 중간 어느 단계가 재시도돼도 "정확히 한 번" 이 끝까지 보장돼야 해서. externalTxId 만으로는 트랜잭션 한정 dedup 이라, 인바운드 멱등 키 → externalTxId 매핑은 우리 게이트웨이가 소유한다.
* *온체인 정합성 · 추적* — 회계 원장을 매니저가 안 갖는 이유: 잔액 진실원천·기표는 회계 평면의 책임이고, 매니저는 "검증된 체인 사실" 을 만들어 넘기는 데까지가 경계(준비자산을 범위 밖에 둔 것과 같은 논리). webhook 은 힌트일 뿐이라, 벤더 잔액과 우리 기록을 맞춰보는 대사가 최종 근거를 닫는다. 트리거가 이벤트+주기 sweep 둘인 이유: 이벤트는 "일어난 것" 만 보고, 진짜 위험한 "일어나야 했는데 안 일어난 것"(전파됐는데 확정 없음)은 sweep 으로만 드러난다.
* *이벤트 · 알림* — at-least-once + dedup 인 이유: 분산 환경의 exactly-once 전달은 환상이라, 재시도(중복 허용)+양쪽 dedup+수신측 멱등이 현실적 구성. 알림이 정합성 검증 *전에* 나가는 이유: 빠름 우선의 의도적 선택 — 대신 정정 이벤트(reorg 무효화 ORPHANED·정합성 MISMATCH)도 같은 채널로 보내 비즈 레이어가 반영을 철회할 수 있게 하고, 잔액의 최종 확정은 정합성 통과 사실 기준으로 잡는 계약을 명시한다.

h2. 3. 시나리오 결정 사유

* *왜 "호출" 과 "감지" 를 처음부터 가르나* — 입금을 "누가 호출하나" 로 생각하는 혼동이 가장 흔해서. 출금·발급·조회는 호출(inbound), 입금은 아무도 호출하지 않는 감지(Fireblocks webhook) — 이 구분이 무너지면 컴포넌트 책임이 전부 꼬인다.
* *왜 감지 ≠ 확정을 상태값으로 가르나* — Fireblocks 는 입금 하나를 CONFIRMING → COMPLETED 로 흘려보내고, 둘을 가르는 것이 DCCP(Deposit Control and Confirmation Policy)다. 감지 즉시 잔액으로 인정하면 reorg 때 없는 돈을 쓴다. zero-confirmation 함정 때문에 status 만 보지 않고 numOfConfirmations 를 DCCP 임계와 직접 비교한다. DCCP 임계값 관리는 Admin, 잔액 반영 런타임은 Service.
* *왜 온/오프램프가 매니저 밖인가* — 수탁이라 고객 코인 잔액이 은행 내부 장부(DB)다. 현금↔코인 전환은 코어뱅킹+DB 조정으로 끝나고 체인을 건너지 않는다. 매니저는 자산이 실제로 체인을 건너는 가장자리(외부 입금·외부 출금·treasury)에서만.
* *왜 집금(sweep)을 별도 컴포넌트로 안 두나* — 매니저 입장에서 sweep 은 "또 하나의 송신 트랜잭션" 이라 출금과 같은 파이프라인(제출·co-signer 공동서명·확정·멱등)을 탄다. Fireblocks 경로에선 vault 간 이동도 같은 createTransaction 이다. 다만 ERC-20 가스 충전 역설(토큰 1번 옮기는 데 tx 2개)·임계값/배치 정책·다대일 대사 같은 고유 난제가 있다. 정책(언제·얼마)은 자금 운용 평면, 집행은 매니저.

h2. 4. 기각·재검토한 대안 모음

|| 대안 || 기각 / 재검토 사유 ||
| 매니저 자체 구축(노드·HSM·인덱서·nonce·전파·정책 엔진 직접 운영)을 라이브로 | *채택 안 함* — 전체가 우리 운영·감사·장애 책임. Fireblocks 채택으로 1차 범위를 넷으로 좁힘. 자체 구축은 테스트용 가짜 구현으로만 남김 |
| Canton 등 비-EVM 2-step(OFFER/ACCEPT) 체인 지원 | *라이브 범위에서 뺌* — 채택한 매니저 Fireblocks 가 지원하지 않고, 2-step 상태머신(상대 수락 대기)이 EVM 모델과 달라 포트가 거짓말할 위험. EVM(이더리움·Base)만 태움 |
| NodeWallet 등 별도 온프렘 제품을 추가 어댑터로 병행 | *제거* — 단일 채택(Fireblocks)으로 정리. 지금은 병행 배치 요구가 없어 어댑터 비교 자체를 뺌 |
| 매니저 단일 인터페이스 추상화 | 교체 단위가 전부-아니면-전무 — 하이브리드(Fireblocks+자체 인덱서 ChainQuery) 표현 불가 |
| SignerPort / BroadcastPort 선분리 | Fireblocks 의 묶음(createTransaction)과 불일치 — 실요구 없는 분해는 leaky |
| ChainQueryPort = generic query 하나 | filter 로 체인 개념 누수 — 도메인 우선 붕괴 |
| 자체 nonce 매니저를 Fireblocks 위에도 운용 | 플랫폼 내부 순번 할당과 충돌 — SaaS 경로의 단위는 "트랜잭션 요청" |
| broadcast 성공 후 멱등 기록 | 전파↔기록 사이 사망 시 재시도가 새 tx 로 이중 출금 — 같은 externalTxId 재제출로 해소 |
| sighash 만 받는 서명자 (TAP·co-signer 정책 게이트 없음) | blind signing — 백엔드 침해 = 키 사용 권한 탈취. TAP + 온프렘 co-signer(Callback Handler)로 막음 |
| 서명·co-signer 를 전부 벤더 안에만 두기 | 나가는 돈의 마지막 관문이 우리 통제 밖 — MPC share 하나를 우리 보안 존(SGX/TEE) co-signer 가 들어 공동서명 |
| Service·Admin 을 한 백엔드로 합치기 | 고객 런타임과 자금 이동 운영이 권한·감사 경계를 공유 — 물리 분리로 감사·확장 안전성 확보 |
| exactly-once 알림 전달 | 분산 환경에서 불가 — at-least-once + 수신측 멱등으로 |
| 알림을 정합성 검증 후에만 발행 | 지연이 UX·후속 처리를 막음 — 미검증 신호 + 정정 이벤트 계약으로 해소 |
| 고객 1명 = vault 1개 고정 | 리테일 규모(수십만+)에서 vault 폭발 — 비용·rate limit. 공용 vault + 내부 attribution 옵션 병행 검토 |
