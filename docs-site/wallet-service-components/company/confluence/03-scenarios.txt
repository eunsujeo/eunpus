h1. 4 시나리오 — 계정 발급 · 입금 · 출금 · 온/오프램프

{info:title=이 문서의 성격}
매니저로 *Fireblocks 를 채택*하고 태우는 체인을 *EVM(이더리움·Base)* 으로 잡은 전제에서 정리한 시나리오다. Fireblocks 를 언급한 부분(createTransaction·webhook·DCCP·co-signer·externalTxId·vault)은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 검증이 필요하다. 우리 백엔드는 *Service*(고객 런타임)와 *Admin*(운영·거버넌스)으로 물리 분리된다.
{info}

h2. 1. 계정·주소 발급 (온보딩)

입금·출금은 주소가 이미 있다는 전제로 시작한다. 그 주소를 만드는 것이 이 단계 — 고객 온보딩 때 *Service 백엔드*가 *계정을 만들고(createAccount) 자산별 수신 주소를 발급(issueDepositAddress)* 한다. 매니저로 Fireblocks 를 채택했으므로 계정은 Fireblocks 의 *vault*({{createVaultAccount}}) 하나이고, 주소는 그 vault 밑에서 {{generateNewAddress}} 로 태어나는 *순수 EVM 주소* 다. 발급된 주소를 다시 부를 때만 *조회(addressOf)* 를 쓴다 — 조회와 발급은 다른 동사고, addressOf 는 절대 새 주소를 만들지 않는다. 클라이언트 → 비즈니스 레이어(인증·KYC 판단) → Service 게이트웨이 → AccountPort 순으로 흐르고, 두 포트 호출 묶음 전체에 멱등 키 하나가 걸려 재시도가 와도 계정·주소가 두 번 만들어지지 않는다. 주소 발급도 vault 생성도 *Fireblocks vault 내부 연산* 이라 온체인 트랜잭션이 아니다 — 전파·수수료가 없다. 키·서명·주소 파생은 전부 *Fireblocks vault·MPC 안* 에서 일어나고, 우리 쪽엔 계정↔주소 매핑 한 줄만 남는다. EVM 주소는 순수 주소라 memo/tag 구분자가 필요 없다 — {{Address(value, memoTag=null)}}. "고객마다 별도 계정 vs 공용(omnibus)+내부 장부 귀속" 선택은 업무·회계 설계이고, 매니저는 발급 기본 동작만 제공한다.

{info:title=Fireblocks 는 vault 가 곧 감시 범위}
자체·하이브리드 인덱서 경로에서 흔한 *등록 갭*(발급과 watch-list 전파 사이에 입금이 도착해 누락되는 사고)이 Fireblocks 채택 경로에는 구조적으로 없다. 발급된 주소로의 입금은 Fireblocks 가 자동으로 감지해 webhook 으로 push 하므로, 발급-감지를 잇는 우리 책임은 *webhook 수신기(Service 백엔드)* 하나로 좁아진다. 별도 인덱서 등록·backfill 재스캔은 벤더 안으로 들어간다.
{info}

h2. 2. 입금 — 호출이 아니라 감지

입금은 체인에서 일어난 일을 *읽어 인지* 하는 흐름이라 쓰기 쪽(트랜잭션 빌더·서명)은 등장하지 않는다. 매니저로 Fireblocks 를 채택했으므로 우리 쪽에 상시 인덱서는 없다 — *Fireblocks 가 자기 vault 범위를 감지* 해 webhook 으로 알려주고, 우리 쪽 *webhook 수신기(Service 백엔드)* 가 받아 매핑 DB 에 기록한다. 핵심 질문은 하나 — *언제부터 잔액으로 믿는가*. 답은 "감지 ≠ 확정" 이고, Fireblocks 는 이 둘을 상태값 *CONFIRMING → COMPLETED* 로 갈라 준다.

{plantuml}
@startuml
participant "외부 송신자" as EXT
participant "EVM 체인 (이더리움·Base)" as CH
participant "Fireblocks (SaaS)" as FB
participant "webhook 수신기 (Service)" as WH
participant "매핑 DB" as DB
participant "비즈니스 레이어" as BIZ

EXT -> CH : 우리 vault 주소로 송금
CH --> FB : Fireblocks 가 자기 vault 범위를 감지
FB -> WH : webhook — status CONFIRMING (체인 등장·미확정)
WH -> DB : 기록만 — 잔액 반영 안 함 (available 불변)
WH --> BIZ : "입금 확인 중" 통지
CH -> FB : confirmation 누적 (numOfConfirmations 증가)
FB -> WH : webhook — status COMPLETED (DCCP 임계 도달 = finality)
WH -> DB : available 반영
WH --> BIZ : "입금 완료 · 사용 가능" 통지
@enduml
{plantuml}

*CONFIRMING → COMPLETED 를 가르는 것은 DCCP(Deposit Control and Confirmation Policy)* — CONFIRMING 을 COMPLETED 로 넘기는 임계 confirmation 수를 정하는 정책이다. 즉 여기서 말하는 "finality" 는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준이고, DCCP 의 설정·임계값 관리는 거버넌스 영역이라 *Admin 백엔드* 의 몫이다(대부분의 체인 = 1, ETC = 372, 컨트랙트 호출 = 최소 3 권장). 실제 입금 이벤트를 받아 잔액에 반영하는 런타임은 *Service 백엔드* 의 몫이다 — 정하는 쪽(Admin)과 쓰는 쪽(Service)이 갈린다.

감지 즉시 잔액으로 인정하면 reorg(체인 끝부분이 교체되는 현상) 때 없는 돈을 쓰게 된다 — 자금 사용 가능 판정은 반드시 확정(COMPLETED + numOfConfirmations 가 DCCP 임계 도달) 이후다. reorg 로 입금이 무효화되면(벤더가 어떤 상태값으로 노출하는지는 확인 중) 가공본(잔액 반영분)만 취소하고 원본 기록은 영구 보존한다 — 무효화된 트랜잭션이 새 블록에 재편입되면 다시 CONFIRMING 으로 돌아올 수 있기 때문이다. 같은 입금 이벤트를 두 번 처리해도 장부가 두 번 늘지 않게 (tx 해시 + logIndex) 를 멱등 키로 쓴다.

{warning:title=함정 — 첫 COMPLETED 를 곧 finality 로 단정하지 말 것}
Deposit Policy 를 zero-confirmation 으로 두면 COMPLETED 가 블록 등장 시점에 먼저 뜨고 이후 webhook 이 여러 번 더 올 수 있다. 그래서 잔액 반영 판정은 status 만 보지 말고 tx 의 {{numOfConfirmations}}(실제 누적 confirmation 수)를 우리 finality 임계값(DCCP, Admin 설정)과 *직접 비교* 하는 편이 안전하다 — numOfConfirmations 가 "confirm(체인 등장) ↔ finality(임계 도달)" 를 가르는 눈금이다. 또한 webhook 은 누락·지연·중복이 가능하므로 통지는 힌트로만 보고, 회계의 최종 근거는 주기적 *대사*(벤더 잔액과 우리 기록의 대조)가 닫는다.
{warning}

h2. 3. 출금 — 가장 많은 컴포넌트가 맞물리는 쓰기 흐름

출금은 체인에 쓰는 흐름이라 사고가 가장 비싸다. 출금 승인 자체(누가 승인하나)와 정책(TAP·boost·cancel)은 *Admin 백엔드* 에서 끝난 뒤, *Service 백엔드* 가 승인된 지시만 받아 {{createTransaction}} 으로 *멱등하게 제출* 한다. 조립·순번·전파는 벤더 안 블랙박스로 돌지만, *MPC 서명만은 우리 보안 존(SGX/TEE)의 co-signer key share 가 있어야* 완성된다 — 나가는 돈의 마지막 서명 관문이 우리 인프라 안에 선다.

{plantuml}
@startuml
participant "비즈니스 레이어" as BIZ
participant "Service 백엔드" as BE
participant "API Co-signer (우리 SGX/TEE)" as COS
participant "Callback Handler (우리 정책 훅)" as CB
participant "Fireblocks" as FB
participant "EVM (이더리움·Base)" as CH

note over BIZ : 출금 요청·승인 완료 (승인 절차는 Admin 거버넌스)
BIZ -> BE : 승인된 출금 지시 (+멱등 키)
BE -> FB : submitTransaction(승인된 출금 + 멱등 키)
FB -> FB : createTransaction(..., externalTxId = 멱등 키)
FB --> BE : 트랜잭션 id (= TxRef)
note over COS, CH : 조립·순번·전파는 벤더가 — 다만 MPC 서명엔 우리 co-signer share 가 필요
FB -> COS : 서명 요청 (원문 목적지·금액 동반)
COS -> CB : 승인 질의 — 한도·화이트리스트 재검증
CB --> COS : approve / deny
COS --> FB : MPC 서명 share (approve) · deny 면 서명 거부
FB -> CH : 전파 — 벤더 cloud share + 우리 share 로 서명 완료
FB --> BE : 상태 변화 webhook — 전파·누적·확정까지 push
CH --> FB : 블록 누적 → 확정
@enduml
{plantuml}

우리에게 남는 재시도 안전장치는 하나 — *같은 멱등 키(=externalTxId)로 다시 제출* 하면 벤더가 새 트랜잭션을 만들지 않고 기존 것을 돌려준다. 직접 구축이었다면 조립(순번 점유)·서명(HSM)·전파를 단계마다 기록하며 몰고 가야 하지만(어느 사이에 죽어도 같은 서명본으로 재개해야 이중 출금을 막으므로), Fireblocks 를 채택하면 이 파이프라인과 복구 책임이 통째로 벤더 안으로 들어간다. 우리 몫은 *멱등한 제출·상태 추적·co-signer 운영* 이다.

*마지막 방어선은 TAP + co-signer.* 승인이 끝난 출금만 매니저에 온다고 했는데 서명 직전에 또 검증하는 이유는 하나 — 서명자는 백엔드를 신뢰하지 않는다. 백엔드가 침해당해 "승인된 척" 지시가 내려와도, Fireblocks 의 거버넌스 정책 *TAP* 이 원문(목적지·금액)을 다시 보고(화이트리스트·건당 한도·일일 누적), 우리 보안 존의 *co-signer* 가 Callback Handler 로 재검증받은 뒤에만 자기 key share 로 서명한다. 화이트리스트·한도는 코드가 아니라 데이터이고, 이 규칙을 관리·승인하는 것은 *Admin 백엔드* 의 거버넌스 몫이다(co-signer 승인 포함).

*상태는 넷으로 접어 내보낸다.* Fireblocks 내부 단계(PENDING_SIGNATURE, QUEUED, BROADCASTING, CONFIRMING, COMPLETED, FAILED…)를 어댑터가 공통 어휘로 번역한다.

|| 공통 상태 (TxStatus) || 뜻 || Fireblocks 원어 (어댑터가 번역) ||
| *SUBMITTED* | 제출됨 — 벤더가 서명·전파 준비 중, 아직 체인 미등장 | PENDING_SIGNATURE · QUEUED · BROADCASTING |
| *CONFIRMING* | 전파 후 체인 등장, confirmation 누적 중 (아직 미확정) | CONFIRMING (numOfConfirmations 증가 중) |
| *COMPLETED* | 확정 — DCCP 임계 confirmation 도달 = finality, 이후 불변 | COMPLETED |
| *FAILED* | 영구 실패 — 사유 동반 (수수료 부족·거절·revert 등) | FAILED · REJECTED · BLOCKED |

confirm(체인 등장)과 finality(확정)를 numOfConfirmations 로 가른다 — 체인에 올라간 순간이 CONFIRMING, DCCP 임계에 도달하면 COMPLETED = finality(입금과 같은 기준). 확정한 수수료가 시세보다 낮아 트랜잭션이 mempool 에 걸려 *막히면*, EVM(이더리움·Base 모두)에선 대응이 둘이다 — *boost*(같은 순번에 수수료만 올려 재전송하는 RBF)와 *cancel*(같은 순번으로 0원 self-send 를 더 높은 수수료로 보내 덮어쓰기). 두 동작 모두 나가는 돈에 개입하는 *Admin 백엔드* 의 운영이고, Service 는 고객 출금을 제출할 뿐 boost·cancel 은 부르지 않는다. EVM 의 수수료 교체는 두 필드(maxFeePerGas·maxPriorityFeePerGas)를 모두 노드 최소 인상률(통상 10%) 이상 올려야 받아들여진다.

{warning:title=순서가 곧 안전}
출금에서 가장 위험한 실수는 순서 역전이다 — 승인 전 제출, 확정 전 "완료" 통지, 서명 전 장부 차감은 모두 사고다. Fireblocks 채택으로 조립·순번·서명 순서는 벤더가 지키지만, *멱등 제출*(같은 externalTxId 재사용)과 *co-signer 의 서명 직전 재검증* 은 우리 인프라 안에 남는 안전장치다.
{warning}

h2. 4. 온/오프램프 — 은행 내부 DB 작업, 매니저는 온체인 가장자리만

수탁(custodial) 지갑에서 고객 코인 잔액은 은행 앱 안의 내부 장부(DB)로 관리된다. 그래서 현금↔코인 전환(온/오프램프)은 *코어뱅킹 잔액과 수탁 코인 잔액(DB)의 조정* 으로 끝나고, 온체인 트랜잭션도 블록체인 매니저 호출도 없다 — 코인은 은행이 보관 중인 준비자산 안에서 장부상 배정될 뿐이다. 따라서 "온/오프램프 커넥터" 는 매니저의 컴포넌트가 아니다. 매니저로 Fireblocks 를 채택했든 무엇이든, 매니저는 자산이 실제로 체인을 건너는 순간에만 호출된다.

|| 작업 || 온체인? || 매니저 호출? || 담당 ||
| 온램프 (내부 현금→코인) | ✗ | ✗ | 은행 앱 + DB |
| 오프램프 (내부 코인→현금) | ✗ | ✗ | 은행 앱 + DB |
| 외부 입금 (타 지갑 → 우리 주소) | ✓ | ✓ | 입금 감지 (Fireblocks webhook) |
| 외부 출금 (우리 → 타 주소) | ✓ | ✓ | 출금 파이프라인 (제출·co-signer 공동서명) |
| 준비자산 온체인 이동 (treasury · 집금 sweep) | ✓ | ✓ | 출금 파이프라인 (제출·co-signer 공동서명) |

집금(sweep)은 매니저 입장에서 새 컴포넌트가 아니라 *또 하나의 송신 트랜잭션* 이라 출금과 같은 파이프라인(조립·서명·전파·확정·멱등)을 탄다 — Fireblocks 경로에선 vault 간 이동도 같은 {{createTransaction}}(source·destination 이 둘 다 vault)이라 출금과 같은 co-signer 공동서명을 거친다. 보내는 곳과 받는 곳이 둘 다 우리 주소라는 점만 다르다. 단 ERC-20 가스 충전 역설(토큰만 든 주소는 가스용 네이티브 코인이 없어 "토큰 1번 옮기는 데 tx 2개")·임계값/배치 정책·다대일 대사 같은 고유 난제가 있고, 정책(언제·얼마·어디로)은 자금 운용 평면과 걸친 결정이라 매니저는 집행만 한다.

매니저는 자산이 실제로 체인을 건너는 가장자리 — *외부 입금*(Fireblocks webhook 이 감지) · *외부 출금*(제출·co-signer 공동서명) · *준비자산 온체인 이동* — 에서만 호출된다. 이는 개요 문서의 두 트리거(① 호출 = 외부 출금, ② 감지 = 외부 입금)와 정확히 같다. 온/오프램프 안쪽의 정산·회계(fiat↔crypto 델타 원장·분개·준비자산 대사)는 이 가이드가 다루지 않고 정산 워크스루에서 커스터디 DB 관점으로 이어진다.
