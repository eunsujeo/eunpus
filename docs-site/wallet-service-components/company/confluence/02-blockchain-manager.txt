h1. 블록체인 매니저 엔진 4 컴포넌트 — 멀티체인 · 인덱서 · 트랜잭션 · 서명

{info:title=이 문서의 성격}
저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드 기반)이다. "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.
{info}

블록체인 매니저(체인 엔진)는 4개 컴포넌트로 구성된다. 공통 설계 원리는 한 가지 — *체인마다 다른 메커니즘은 어댑터(체인별 구현)에 가두고, 체인 무관한 정책·오케스트레이션은 공통 본체가 쥔다.* 그래서 새 체인 추가는 어댑터 하나 추가로 끝나고, 본체 코드는 바뀌지 않는다.

h2. 1. 멀티체인 어댑터 — 체인별 차이를 흡수하는 단 하나의 장소

체인은 저마다 규칙이 다르다 — 이더리움은 계정별 순번(nonce)으로 트랜잭션을 직렬화하고, 비트코인은 UTXO(사용하지 않은 출력 집합)를 골라 쓰고, 확정(finality — 거래가 더는 뒤집히지 않는다고 볼 수 있는 상태) 판단·수수료·재전송 방법도 전부 다르다. 이 차이를 곳곳에 흩어 두면 모든 컴포넌트가 체인 분기 코드로 오염되므로, 어댑터가 차이를 *한 군데로 모아* 나머지에게 공통 동사("조립해라 · 수수료 추정해라 · 전파해라 · 확정 판정해라 · 재전송해라")만 노출한다. 위 컴포넌트에 체인 분기 코드가 새면 추상화 실패 신호다. Fireblocks·Alchemy 같은 SaaS 도 "또 다른 어댑터 구현" 으로 두면 벤더 교체가 쉬워진다. 노드/RPC 엔드포인트 풀·장애 전환(failover)은 자체 구축일 때만 우리 책임이고, Fireblocks 경로에선 벤더가 처리한다.

h2. 2. 인덱서 — 모든 읽기의 토대, 상시 가동 worker

노드 RPC 는 "이 tx 해시의 내용" 은 주지만 "이 주소가 받은 입금 목록 · 지금 잔액 · 입금 알림" 은 주지 못한다. 인덱서는 체인 데이터를 *수집 → 원시 보존 → 가공(projection — 조회하기 쉬운 형태로 따로 만든 가공본) → 제공* 파이프라인으로 처리해 입금을 감지하고 확정을 판단한다. 핵심은 원시(raw)와 projection 의 분리 — 받은 블록·로그를 가공 전 원본 그대로 append-only 로 쌓아 두면, reorg(체인 끝부분이 다른 블록들로 교체되는 현상)가 나도 projection 만 분기 지점까지 롤백하고 원시로부터 다시 만들면 된다. 같은 이벤트를 두 번 처리해도 결과가 같도록 (tx 해시 + logIndex) 를 멱등 키로 쓴다. 수집 루프는 아무도 호출하지 않아도 계속 도는 상시 worker 다 — 끊기면 입금·확정을 놓친다.

h2. 3. 트랜잭션 · Nonce · Broadcast — 체인에 쓰는 곳, 가장 사고가 나기 쉬운 곳

출금 트랜잭션을 *조립하고, 순번을 안전하게 점유하고, 전파하고, 막히면 고쳐 보내는* 컴포넌트다. 계정 기반 체인에서는 수수료가 모자란 트랜잭션 하나가 안 나가면 그 뒤 순번이 전부 막히고(stuck cascade), 동시 요청이 같은 순번을 집으면 충돌한다. 그래서 주소마다 로컬 순번 카운터 + 잠금으로 직렬화하고, 주기적으로 체인 값과 재동기화한다. 막히면 *같은 순번*으로 수수료를 올려 재전송한다(RBF — 확정 전 트랜잭션을 더 높은 수수료의 새 트랜잭션으로 교체). 단 Fireblocks 같은 풀 트랜잭션 SaaS 를 쓰면 순번·전파·재시도가 플랫폼 내부에서 처리되므로, 자체 순번 카운터를 또 돌리면 오히려 충돌한다 — 이 경우 우리가 짓는 것은 요청 큐+멱등, 출금 지갑 분산(round-robin) 라우팅, 상태 모니터링+부스트 트리거다.

h2. 4. 서명 오케스트레이션 — 키는 보관하지 않는 호출 경계

매니저가 키를 직접 들면 매니저가 침해당하는 순간 키도 샌다. 그래서 키 보관·서명은 외부 서명자 — MPC(키 조각을 나눠 갖고 임계 수 이상이 모여야 서명되는 방식)·HSM(키를 하드웨어 밖으로 꺼내지 않는 보안 장치)·co-signer — 에 맡기고, 매니저는 "무엇을 서명할지"(체인별 직렬화·해시는 어댑터 제공)를 만들어 요청하고 결과를 검증해 받아오는 얇은 경계만 둔다. 주의: *서명 재시도는 멱등이 아니다.* 서명에 쓰는 일회용 난수(서명 nonce)를 재사용하면 개인키가 수학적으로 노출될 수 있어, 실패 시 같은 시도를 반복하지 말고 새 서명 라운드로 다시 해야 한다. 트랜잭션 nonce(같은 값 재사용 = 재전송, 멱등)와 서명 nonce(같은 값 재사용 = 키 유출, 비멱등)는 이름만 같고 정반대다 — 절대 한데 묶지 말 것.

h2. 5. 핵심 불변식

{note:title=깨지면 사고로 이어지는 불변식}
* *쓰기 순서 불변* — 멱등 확인 → 조립(순번 점유) → 서명 → 전파 → 기록·확정 추적. 이 순서가 깨지면(승인 전 전파, 서명 전 장부 차감, 확정 전 "완료" 통지) 모두 사고다. 각 단계는 직전 단계의 확정을 전제로만 진행한다.
* *수수료 변경 = 재서명* — 수수료 인상은 서명 payload 를 바꾸므로 기존 서명이 무효가 된다. 반드시 재서명 후 재전파하며, 매번 새 tx 신원(hash)이 생기므로 추적은 논리 단위(멱등 키·correlationId)로 한다. 받는 주소·금액은 절대 바뀌면 안 된다.
* *fee-boost 는 EVM·UTXO 전용* — 수수료를 올려 재촉하는 boost 는 EVM(같은 nonce + gas 인상)·UTXO(RBF/CPFP)만의 capability 다. Solana 는 어댑터가 auto-retry(blockhash 만료 시 재조립), Canton 은 fee 문제가 아니라 수락 대기라 cancel(OFFER withdraw) 영역이다. Fireblocks 도 boost 를 EVM/UTXO 에만 제공한다.
* *인덱서는 raw 보존 먼저* — 원시 로그를 append-only 로 먼저 쌓고 나서 가공한다. 절대 덮어쓰거나 지우지 않는다. projection 은 재구성 가능한 캐시로 취급한다.
* *감지 ≠ 확정* — 입금 감지(PENDING)와 확정(CONFIRMED)을 분리하고, 자금 사용 가능 판정은 반드시 확정 이후. 확정 기준은 어댑터가 체인별로 제공한다.
{note}
