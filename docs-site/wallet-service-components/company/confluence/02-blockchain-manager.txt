h1. Fireblocks 매니저 4 컴포넌트 — 체인 차이 흡수 · 입금 감지 · 출금 · 서명

{info:title=이 문서의 성격}
저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드 기반)이다. "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.
{info}

블록체인 매니저(체인 엔진)는 4개 컴포넌트로 나뉜다 — 체인 차이 흡수·입금 감지·출금 파이프라인·서명. 이 가이드는 매니저로 *Fireblocks 를 채택* 하고 체인은 *EVM — 이더리움과 Base* 만 태우므로, 이 네 컴포넌트의 내부(멀티체인 정규화·인덱싱·nonce·서명 프로토콜)는 대부분 *벤더 안에서 돈다*. 그래서 이 문서는 "우리가 무엇을 구현하나" 가 아니라 *"벤더 안에서 무엇이 돌고, 우리와의 이음매(seam — webhook·co-signer)가 어디인가"* 를 그린다.

h2. 1. 체인 차이 흡수 — EVM 은 벤더 안에서 정규화된다

체인은 저마다 규칙이 다르다. 이더리움은 계정별 순번(nonce)으로 트랜잭션을 직렬화하고, 확정(finality — 거래가 더는 뒤집히지 않는다고 볼 수 있는 상태) 판단·수수료·재전송 방법도 다르다. 이 차이를 우리 백엔드 곳곳에 흩어 두면 입금 감지·출금·서명·정합성 코드가 전부 체인 분기로 오염되므로, *Fireblocks 가 이 차이를 벤더 안에서 흡수* 해 우리 백엔드에는 "체인이 무엇이든 똑같아 보이는" 포트 표면만 준다 — 우리는 멀티체인 어댑터를 만들지 않는다.

우리가 태우는 체인은 EVM — *이더리움과 Base* 뿐이다. Base 는 이더리움 L2(OP-Stack)라 계정 모델·주소·수수료·boost/RBF·확정 모델이 이더리움과 사실상 같아, 둘을 'EVM' 으로 묶어 한 번에 다룬다. 벤더가 EVM 을 다룰 때 흡수하는 관심사 — *우리가 구현하는 표가 아니라 벤더 안에서 이렇게 처리된다는 참조* — 는 다음과 같다.

||관심사||EVM — 이더리움·Base (벤더가 흡수)||
|잔액 표현|주소별 잔액 + nonce (ERC-20 토큰도 같은 주소, 컨트랙트 잔액으로 조회)|
|순서 보장|주소별 nonce 순차 — 벤더가 nonce 를 점유·직렬화|
|확정 판단|numOfConfirmations 가 DCCP 임계에 닿으면 확정(finality)|
|수수료|gas × gasPrice — EIP-1559 의 기본료(base fee)+우선료(priority fee)|
|재전송|같은 nonce + 수수료 인상(RBF) — 벤더의 boost 로 노출 (Admin 운영)|
|주소 파생|BIP-32/44 경로 + coin type — 벤더 vault 안에서 파생, 우리는 발급된 주소만 받는다|

Fireblocks·Alchemy 같은 SaaS 도 노드/RPC 엔드포인트 풀·장애 전환(failover)을 벤더 안에서 처리하므로, 우리는 노드를 직접 운영하지 않는다. 우리 쪽에 남는 것은 *webhook 수신기·매핑 DB·co-signer* 뿐이다. 우리 백엔드에 EVM 분기 코드(gas·nonce·confirmation)가 새면 추상화가 새는 신호다 — 그런 세부는 포트 뒤(벤더 안)에 남겨 둔다.

h2. 2. 입금 감지 — 우리는 인덱서를 만들지 않는다 (webhook 수신)

노드 RPC 는 "이 tx 해시의 내용" 은 주지만 "이 주소가 받은 입금 목록 · 지금 잔액 · 입금 알림" 은 주지 못한다. 이 격차를 메우는 인덱서는 Fireblocks 를 채택하면 *벤더 안에서 돈다* — 우리 쪽엔 상시 인덱서도, 노드 폴링도 없다. *Fireblocks 가 자기 vault 범위의 입금을 감지* 해 *webhook* 으로 밀어 주고, 우리 몫은 그걸 받는 *webhook 수신기(Service 백엔드)* 와 *매핑 DB* 하나다. 그래서 이 컴포넌트의 질문은 하나로 좁혀진다 — *언제부터 이 입금을 잔액으로 믿는가*.

답은 "감지 ≠ 확정" 이다. 체인에 트랜잭션이 등장했다고 곧 확정은 아니다. Fireblocks 는 이 둘을 상태값으로 갈라 준다 — *CONFIRMING*(체인 등장, confirmation 누적 중, 아직 미확정)과 *COMPLETED*(DCCP 임계 confirmation 도달 = finality). CONFIRMING 단계의 자금은 "확인 중" 으로만 보여주고 available 잔액에 넣지 않으며, COMPLETED 부터 확정으로 보고 available 에 반영한다.

{code}
onChainEvent(handler)   // Fireblocks webhook 이 입금의 상태 변화를 push 한다
                        //   CONFIRMING = 체인에 등장, confirmation 누적 중 (아직 미확정)
                        //   COMPLETED  = DCCP 임계 confirmation 도달 = finality (확정)
{code}

CONFIRMING 을 COMPLETED 로 바꾸는 *임계 confirmation 수를 정하는 정책* 이 *DCCP*(Deposit Control and Confirmation Policy)다. 이 문서가 말하는 "finality" 는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준이고, DCCP 는 운영·거버넌스 영역이라 그 *설정·임계값 관리는 Admin 백엔드* 의 몫이며, 실제 입금 이벤트를 받아 잔액에 반영하는 런타임은 Service 백엔드의 몫이다.

{code}
// Fireblocks webhook 수신기(Service)가 받는 상태 이벤트 — 핸들러는 하나
transactions.onChainEvent { ev ->
    when (ev.status) {
        CONFIRMING -> notify(ev.account, "입금 확인 중")                 // 체인 등장·미확정 — 잔액 반영 금지
        COMPLETED  -> if (ev.numOfConfirmations >= finalityThreshold(ev.asset)) {
                          ledger.credit(ev); notify(ev.account, "입금 완료")  // DCCP 임계 도달 = finality
                      }
        무효화 신호 -> ledger.revert(ev)                               // reorg — 벤더 상태값은 확인 중
    }
}
{code}

{note:title=DCCP 임계값과 zero-confirmation 함정 (설정 주체 = Admin)}
Fireblocks 의 DCCP 기본 임계 confirmation 수는 체인마다 다르다.
* *대부분의 체인 = 1* — 블록 하나면 확정으로 본다.
* *ETC(이더리움 클래식) = 372* — 과거 reorg 리스크가 커 임계가 매우 높다.
* *컨트랙트 호출(contract call) = 최소 3 권장* — 단순 전송보다 보수적으로.

이 값은 커스텀 DCCP 로 조정할 수 있고, 권한과 책임은 *Admin* 에 둔다. 함정 하나 — Deposit Policy 를 *zero-confirmation* 으로 두면 COMPLETED 가 블록 등장 시점에 먼저 뜰 수 있어, "COMPLETED 를 처음 받았다" 가 곧 "충분한 confirmation 이 쌓였다" 를 뜻하지 않는다. 그래서 잔액 반영은 status 만 보지 말고 {{numOfConfirmations}} 를 우리 finality 임계값(Admin 이 관리하는 DCCP)과 직접 비교한 뒤에만 credit 한다.
{note}

reorg 는 EVM 이라 남는 속성이다. 이더리움과 Base 는 체인 끝이 드물게 교체(reorg)될 수 있고, 무효화는 *FAILED(또는 취소·만료) + subStatus DROPPED_BY_BLOCKCHAIN* 으로 표시된다(Fireblocks Support 확인). 핸들러는 이 신호를 받아 *가공본(잔액 반영분)만 취소하고 원본 기록은 영구 보존* 한다. 그리고 webhook 은 누락·지연·중복이 가능하므로 통지는 힌트로만 보고, 회계의 최종 근거는 주기적 대사(벤더 잔액 vs 우리 기록)가 닫는다.

h2. 3. 출금 파이프라인 — 벤더 안 createTransaction, 우리는 멱등 제출

출금 트랜잭션을 *조립하고, 순번(nonce)을 안전하게 점유하고, 전파하고, 막히면 수수료를 올려 재전송(RBF)* 하는 파이프라인은 이 시리즈에서 사고가 가장 비싼 곳이다. 계정 기반 체인(EVM)에서는 수수료가 모자란 트랜잭션 하나가 안 나가면 그 뒤 순번이 전부 막히고(stuck cascade), 동시 요청이 같은 순번을 집으면 "nonce too low" 로 충돌한다. Fireblocks 를 채택하면 이 파이프라인 전체가 *벤더 안 {{createTransaction}} 한 번에 블랙박스로* 들어간다 — 우리는 조립도, nonce 도, 전파도 직접 하지 않는다. 우리 몫은 *멱등한 제출({{externalTxId}})과 상태 추적*, 그리고 막혔을 때의 *boost·cancel 운영(Admin)* 이다. 단 출금 승인은 이 컴포넌트가 하지 않는다 — 승인이 끝난 지시를 받아 벤더에 넘길 뿐이다.

{code:kotlin}
// 출금 유스케이스 (Service) — 업무 승인은 비즈 레이어에서 끝난 뒤
suspend fun withdraw(order: ApprovedWithdrawal): TxRef =
    withIdempotency("withdraw:${order.id}") {                 // 멱등 키 → 벤더 externalTxId 로 이어진다
        transactions.submitTransaction(order.toRequest())     // 벤더 파이프라인은 전부 이 한 줄 아래
    }

// 상태 추적 — 벤더가 push 하는 webhook 으로 (입금 감지 수신기와 같은 경로)
transactions.onChainEvent { ev ->
    when (ev.status) {
        SUBMITTED  -> track(ev)                                // 벤더가 서명·전파 준비 중
        CONFIRMING -> track(ev)                                // 체인 등장·미확정
        COMPLETED  -> ledger.settle(ev)                        // DCCP 임계 도달 = finality
        FAILED     -> ledger.markFailed(ev)                    // 수수료 부족·거절·revert 등
    }
}

// 막힌 출금 개입 (Admin) — capability 가 있으면 버튼이 생기고, 없으면 없다
fun stuckActions(): List<Action> = buildList {
    (transactions as? FeeBoostCapability)?.let { add(BoostAction(it)) }   // 수수료 인상 재전송 (RBF · EVM)
    (transactions as? CancelCapability)?.let { add(CancelAction(it)) }    // 철회
}
{code}

{warning}
체인엔 되돌리기가 없으니 *중복 실행* 이 가장 큰 위험이다 — 같은 출금이 두 번 나가면 끝이다. 그래서 제출에는 항상 *멱등 키* 를 붙이고, 그 키를 벤더의 {{externalTxId}} 로 넘겨 중복 차단이 벤더 쪽에서도 이어지게 한다. 같은 멱등 키로 재제출하면 벤더가 새 트랜잭션을 만들지 않고 기존 것을 돌려준다. 그리고 *자체 nonce 카운터(예: Redis nonce 매니저)를 또 돌리면 벤더 내부 순번 할당과 충돌* 하므로 두지 않는다 — 애플리케이션이 보는 단위는 "순번" 이 아니라 "트랜잭션 요청" 이다.
{warning}

확정한 수수료가 시세보다 낮으면 트랜잭션이 mempool 에 걸려 막힌다. EVM(이더리움·Base)에선 대응이 둘이다 — *boost*(같은 nonce 에 수수료만 올려 다시 보내는 RBF)와 *cancel*(출금 자체를 철회). 실제 재전송·철회는 Fireblocks 가 벤더 안에서 실행하고 우리는 그 기능을 호출할 뿐이며, 둘 다 나가는 돈에 개입하는 동작이라 Service 가 아니라 *Admin 백엔드* 가 부른다. boost 는 수수료를 바꾸므로 트랜잭션의 신원(on-chain hash)이 바뀐다 — 그래서 추적은 매번 바뀌는 hash 가 아니라 논리 단위(우리 멱등 키·correlationId)로 하고, 받는 주소·금액(지급 의도)은 절대 바뀌면 안 된다.

우리 백엔드가 보는 상태는 어댑터가 번역한 공통 상태 넷이다.

||공통 상태 (TxStatus)||뜻||Fireblocks 원어 (어댑터가 번역)||
|*SUBMITTED*|제출됨 — 벤더가 서명·전파 준비 중, 아직 체인 미등장|PENDING_SIGNATURE · QUEUED · BROADCASTING|
|*CONFIRMING*|전파 후 체인에 등장, confirmation 누적 중 (아직 미확정)|CONFIRMING (numOfConfirmations 증가 중)|
|*COMPLETED*|확정 — DCCP 임계 confirmation 도달 = finality, 이후 불변|COMPLETED|
|*FAILED*|영구 실패 — 사유 동반 (수수료 부족·거절·revert 등)|FAILED · REJECTED · BLOCKED|

h2. 4. 서명 — MPC + co-signer 공동서명 (키는 한 곳에 모이지 않는다)

서명은 이 시리즈에서 *유일하게 서명이 온전히 벤더 안에서 끝나지 않는* 대목이다. Fireblocks 채택 기준 서명은 *MPC 공동서명* 이다 — Fireblocks 의 *MPC 클라우드 key share* 와, 우리 *보안 존(SGX/TEE)에 설치한 API Co-signer* 가 든 *또 하나의 key share* 가 함께 서명해야 트랜잭션이 완성된다. MPC(여러 참가자가 키 조각을 나눠 갖고 임계 수 이상이 모여야 서명되는 방식)는 어느 한 share 만으로는 서명도 키 복원도 안 되므로, *키는 어느 한 곳에도 온전히 모이지 않는다*.

게다가 co-signer 는 서명 직전 *Callback Handler*(우리 정책 훅)에 승인·거부를 물어본다. Callback Handler 는 원문(목적지·금액)을 직접 보고 우리 정책 — 수신처 화이트리스트·건당 한도·일일 누적 — 을 확인한 뒤 approve / deny 를 돌려주고, deny 면 co-signer 는 자기 share 로 서명하지 않아 서명이 완성되지 않는다. 그래서 나가는 돈의 *마지막 자동 서명 관문이 우리 인프라 안* 에 선다.

{plantuml}
@startuml
participant "Fireblocks\nMPC 클라우드 share" as FB
box "우리 보안 존 · SGX/TEE"
participant "API Co-signer\n온프렘 key share" as COS
participant "Callback Handler\n우리 정책 훅" as CB
end box
participant "EVM · 이더리움·Base" as CH

FB -> COS : 서명 요청 (원문 목적지·금액 동반)
COS -> CB : 승인 질의 — 한도·화이트리스트 재검증
CB --> COS : approve / deny
COS --> FB : MPC 서명 share (approve) · deny 면 서명 거부
note over FB, COS : 두 share 가 함께 계산해야 서명이 완성된다 — 키는 어느 쪽에도 온전히 없다
FB -> CH : 전파 — 벤더 cloud share + 우리 share 로 서명 완료
@enduml
{plantuml}

{warning}
업무 승인이 끝난 출금만 매니저에 온다고 해도, 서명 직전에 *또* 검증하는 이유는 하나다 — 백엔드가 침해당하면 "승인된 척하는" 출금 지시가 내려올 수 있다. 그때 키 앞을 지키는 마지막 방어선이 *Callback Handler + co-signer* 이고, 결정적으로 이 관문은 벤더 클라우드가 아니라 *우리 보안 존 안* 에 있다(심층 방어, defense in depth). 규칙(화이트리스트·한도)은 코드가 아니라 데이터이며, 이를 관리·승인하는 것은 *Admin 백엔드* 의 거버넌스 몫이다(벤더의 거버넌스 정책 TAP 과 함께).
{warning}

{code:kotlin}
// 우리가 짓는 건 서명 오케스트레이터가 아니라 Callback Handler 다 (개념 의사코드)
// Fireblocks co-signer 가 서명 직전 이 훅을 호출한다 — 우리 보안 존 안에서 돈다
fun onSigningRequest(req: SigningRequest): Decision {
    val order = req.decodedPayload           // 원문 — 목적지·금액 (벤더가 함께 보냄)
    if (order.to !in whitelist(order.asset))        return Decision.DENY   // 화이트리스트
    if (order.amount > perTxLimit(order.asset))      return Decision.DENY   // 건당 한도
    if (dailyTotal(order.account) + order.amount > dailyLimit) return Decision.DENY  // 일일 누적
    return Decision.APPROVE                   // approve 여야 co-signer 가 자기 share 로 서명
}
// whitelist·perTxLimit·dailyLimit 은 코드가 아니라 데이터 — Admin 이 관리·승인 (거버넌스)
// 벤더 쪽 MPC 프로토콜·sighash·서명 재시도(비멱등) 규율은 이 훅 밖(벤더 안)에서 처리된다
{code}

서명의 *메커니즘*(체인별 직렬화·sighash·MPC 프로토콜·클라우드 key share)은 벤더 안이다. 우리 몫은 *co-signer 설치·운영과 Callback Handler 정책* 이다.

||구성요소||누구 몫 · 무엇을||
|MPC 클라우드 share|*Fireblocks* — vault 안 key share, 서명 프로토콜 실행|
|체인별 직렬화·sighash|*Fireblocks* — EVM RLP/keccak256 등, 벤더가 처리|
|API Co-signer (SGX/TEE)|*우리* — 보안 존에 설치·운영, 온프렘 key share 보유|
|Callback Handler (정책 훅)|*우리* — 서명 직전 approve/deny 판정 (화이트리스트·한도)|
|정책 규칙 관리·승인|*Admin 백엔드* — 화이트리스트·한도를 데이터로 관리·승인|

{warning}
*서명 재시도는 멱등이 아니다.* MPC 서명 과정에는 일회용 난수(서명 nonce)가 쓰이는데, 이 값을 재사용하면 개인키(정확히는 share)가 수학적으로 노출될 수 있다. 그래서 서명이 실패·타임아웃하면 같은 시도를 반복하지 말고 *새 서명 라운드(새 난수)로 다시* 해야 한다. 이름이 같은 두 nonce 를 절대 혼동하지 말 것 — *트랜잭션 nonce*(벤더 안, 계정 순번, 같은 값 재사용 = 재전송, 멱등)와 *서명 nonce*(MPC 내부, 일회용 난수, 같은 값 재사용 = 키 유출, 비멱등)는 이름만 같고 정반대다.
{warning}

h2. 5. 핵심 불변식

{note:title=깨지면 사고로 이어지는 불변식}
* *쓰기 순서 불변* — 멱등 확인 → (벤더 안) 조립·nonce 점유 → 서명(MPC + co-signer 공동서명) → 전파 → 기록·확정 추적. 이 순서가 깨지면(승인 전 전파, 서명 전 장부 차감, 확정 전 "완료" 통지) 모두 사고다. 파이프라인이 벤더 안으로 들어가도 이 불변식은 사라지지 않는다 — 우리 쪽엔 멱등 키가 그 자리를 지킨다.
* *감지 ≠ 확정* — 입금 감지(CONFIRMING)와 확정(COMPLETED)을 분리하고, 자금 사용 가능 판정은 반드시 COMPLETED 이후. 확정 기준은 DCCP(Admin 설정)가 정하고, status 만 보지 말고 numOfConfirmations 를 finality 임계와 비교한다.
* *중복 출금 차단 = 멱등 키* — 제출에 항상 멱등 키를 붙여 벤더 externalTxId 로 이어 준다. 자체 nonce 카운터를 또 돌리면 벤더 순번 할당과 충돌하므로 두지 않는다.
* *boost = 재서명, 신원 변경* — 수수료 인상은 서명 payload 를 바꿔 tx 신원(hash)이 바뀐다. 추적은 논리 단위(멱등 키·correlationId)로 하고, 받는 주소·금액은 절대 바뀌면 안 된다. boost·cancel 은 EVM(같은 nonce + gas 인상) capability 이고 Admin 운영이다.
* *키는 한 곳에 모이지 않는다* — 벤더 클라우드 share + 우리 온프렘 co-signer share 의 공동서명. Callback Handler 의 approve 없이는 어떤 서명도 완성되지 않으며, 마지막 서명 관문이 우리 인프라 안에 선다.
* *원본은 보존, 가공본만 취소* — reorg 무효화가 오면 잔액 반영분(가공본)만 취소하고 원본 이벤트 기록은 지우지 않는다. 재편입 시 복원되어야 하기 때문이다.
{note}
