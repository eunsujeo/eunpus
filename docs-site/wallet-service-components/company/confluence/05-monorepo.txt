h1. 프로젝트 구조 — 모노레포로 설계 경계를 강제한다

{info:title=이 문서의 성격}
저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안이다. Fireblocks 등 특정 벤더·체인을 언급한 부분은 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 검증이 필요하다. *블록체인 매니저는 Fireblocks 를 채택했고 태우는 체인은 EVM(이더리움·Base)* 이므로, 이 구조도 {{adapters/fireblocks}} 를 유일한 라이브 어댑터로 두고 자체 구축은 테스트용 가짜({{adapters/fake}})로만 남긴다.
{info}

앞 문서들의 설계(두 백엔드 Service·Admin · 포트 · Fireblocks 어댑터 교체)를 코드로 옮기면 *경계가 패키지 경계* 가 되어야 흐트러지지 않는다. 모노레포(여러 패키지를 한 저장소에서 함께 버전·빌드 관리하는 방식)로 두면 도메인·포트가 안쪽 핵으로 고정되고, 어댑터를 패키지 단위로 넣고 빼며, 한 번에 빌드·테스트할 수 있다. 스택은 Kotlin + Spring (Gradle 멀티모듈) — *Fireblocks 가 Java SDK 를 1급으로 제공* 하고, 두 백엔드(Service·Admin)와 webhook 수신기가 Spring Boot 로 자연스럽게 나뉘어 이 조합에 JVM 이 1급이다. 지금은 매니저가 Fireblocks 라 서명·nonce·전파·인덱싱이 대부분 벤더 안에서 끝나므로, 우리 코드는 *포트·두 백엔드·Fireblocks 어댑터·webhook 수신* 에 집중된다.

h2. 1. 디렉터리 구조

{code}
custodial-wallet/                # Gradle 멀티모듈 (각 디렉터리 = 서브프로젝트)
├─ settings.gradle.kts           # 모듈 include 선언
├─ gradle/libs.versions.toml     # 버전 카탈로그
│
├─ domain/                       # 순수 Kotlin (Spring 의존 X) — 모델 + 포트 (안쪽 핵)
│   ├─ model/                    # Transaction · Account 등 + TxStatus(SUBMITTED|CONFIRMING|COMPLETED|FAILED)
│   └─ port/                     # AccountPort · TransactionPort · ChainQueryPort(선택)
│
├─ backend/                      # Spring Boot — 두 백엔드로 물리 분리 (벤더 무관 · 항상 우리 것)
│   ├─ service/                  #   Service 백엔드 — 고객 런타임 (계정·주소·입금·출금 제출·잔액)
│   │   ├─ gateway/              #     인증 · 멱등 키 · 라우팅
│   │   ├─ directory/            #     계정·주소 디렉터리 — 발급 결과 저장 + 계정 해석 (우리 데이터)
│   │   ├─ orchestration/        #     요청 큐 · 상태머신 · vault 라우팅
│   │   ├─ reconciliation/       #     온체인 정합성 · 추적
│   │   └─ alerts/               #     이벤트 · 알림 팬아웃
│   └─ admin/                    #   Admin 백엔드 — 정책·승인·키 운영·동결·rebalance·sweep (권한·감사 경계)
│
├─ adapters/                     # 매니저 어댑터 = 교체 축 (포트 구현)
│   ├─ fireblocks/               #   Fireblocks Java SDK — Account+Transaction (REST/webhook) · 유일한 라이브 구현
│   ├─ fake/                     #   테스트용 가짜 구현 — 벤더 없이 계약 테스트·백엔드 검증 (자체 구축 자리)
│   └─ chainquery-alchemy/       #   (선택) ChainQueryPort 만 — Alchemy/The Graph 등 쿼리 프로바이더
│
├─ shared/                       # config · logging · idempotency store
│
└─ apps/                         # 실행 모듈 (@SpringBootApplication · 어댑터 wiring)
    ├─ service-api/              # Service 서버 — DI 로 fireblocks 어댑터 주입
    ├─ admin-api/                # Admin 서버 — 정책·운영·sweep
    └─ webhook-receiver/         # Fireblocks webhook → onChainEvent
{code}

여기엔 *자체 구축 엔진(engine/*)이나 체인 프로토콜 모듈(chains/*)이 없다* — 매니저로 Fireblocks 를 채택했으므로 서명·nonce·전파·멀티체인 흡수가 전부 벤더 안에서 끝나기 때문이다. 훗날 자체 구축으로 전환하거나 EVM 을 직접 붙일 때에만 {{engine/*}}·{{chains/evm}} 을 새 모듈로 추가하면 되고, *도메인 포트와 두 백엔드는 그대로* 다. 지금은 그 자리를 비워 두고, 포트 계약을 벤더 없이 검증하는 {{adapters/fake}} 만 둔다.

h2. 2. 의존 방향 규칙 — 안쪽으로만

패키지 경계가 의미 있으려면 화살표(의존)가 한 방향이어야 한다. *{{domain}} 은 누구도 의존하지 않고, 모두가 {{domain}} 을 의존한다.* 흐름: apps → adapters → domain, 그리고 backend → domain. 어댑터를 아는 곳은 apps 의 DI(주입)뿐이고, 두 backend(Service·Admin)는 domain 만 의존하므로 어떤 벤더인지 컴파일 타임에 모른다. Fireblocks SDK 는 {{adapters/fireblocks}} 안에 격리되고, 벤더 타입이 그 밖으로 새면 교체가 깨지므로 이 경계는 빌드 규칙(ArchUnit)으로 막는다. Service·Admin 이 별도 backend·apps 모듈인 것이 곧 물리 분리다.

* *어댑터 교체 = 모듈 교체* — 지금은 {{adapters/fireblocks}} 하나만 라이브다. 훗날 벤더를 바꾸거나 자체 구축으로 전환하면 새 어댑터 모듈을 이 자리에 더하고 {{apps/*-api}} 의 wiring 한 줄({{@Profile}} 또는 {{@ConditionalOnProperty}})만 바꾸면 되고 {{domain}}·{{backend}} 코드는 그대로.
* *포트는 한 곳(domain)* — 어댑터·앱이 전부 같은 포트 타입을 import 하니, 시그니처가 어긋나면 컴파일에서 잡힌다.
* *EVM 체인 추가 = 어댑터의 체인·자산 등록만* — 이더리움·Base 는 같은 EVM 이라 어댑터가 등록만 늘리면 되고 {{backend}}·{{domain}} 은 0줄. Fireblocks 가 그 체인을 지원하기만 하면 된다.
* *강제 수단* — domain 은 순수 Kotlin(Spring 의존 금지), 의존 방향은 Gradle 모듈 그래프 + ArchUnit(아키텍처 규칙을 테스트로 검증하는 JVM 라이브러리)/Konsist 로 CI 에서 검사.

h2. 3. 시작 셋 — 처음부터 전부 만들지 않는다

||구분||모듈||비고||
|*필수*|{{domain}} · {{backend/service}} · {{backend/admin}} · {{adapters/fireblocks}} · {{adapters/fake}} · {{apps/service-api}} · {{apps/admin-api}} · {{apps/webhook-receiver}}|EVM(이더리움·Base), 매니저는 Fireblocks 기준|
|*선택 · 나중*|{{engine/*}} · {{chains/evm}} · 자체 구축 어댑터|자체 구축 전환 대비 자리만 비워 둠. 도메인 포트는 그대로 두므로 전환 시 새 어댑터·엔진 패키지만 추가|

{note:title=Fireblocks 를 써도 우리 쪽에 반드시 남는 것}
Fireblocks 가 멀티체인·서명·nonce·전파를 다 흡수하므로 *engine/chains 없이 시작할 수 있다.* 그래도 우리 쪽엔 반드시 남는 게 있다 — *두 백엔드(Service·Admin) · webhook 수신기 · 매핑 DB · 온프렘 API Co-signer(SGX/TEE) 운영* 이다. 특히 co-signer 는 서명 직전 우리 Callback Handler 로 승인·거부를 거는 자리라, 벤더에 위임되지 않는 우리 몫이다. ChainQuery(임의 외부 주소 조회)처럼 Fireblocks 가 안 주는 부분만 {{adapters/chainquery-alchemy}} 로 선택적으로 채운다.
{note}
