h1. 블록체인 지갑 서비스 아키텍처 개요 — 두 층과 두 트리거

{info:title=이 문서의 성격}
여기 담긴 컴포넌트 구분과 다이어그램은 특정 제품의 공식 명세가 아니라, 저자가 일반적인 지갑 인프라 패턴과 공개된 SaaS API 형태를 바탕으로 정리한 설계 참고안이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더를 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경·규제 요건에서 검증이 필요하다.
{info}

h2. 1. 두 층으로 나눈다

블록체인 지갑 서비스의 백엔드는 *두 층*으로 나눠 본다.

* *블록체인 매니저 (체인 엔진)* — 체인과 직접 대화하는 엔진. 체인에서 일어난 일을 *읽어 들이고*(인덱싱·입금 감지·확정 판단), 우리가 원하는 일을 체인에 *써 넣고*(트랜잭션 조립·서명 요청·전파·재전송), 체인마다 다른 규칙을 *한 가지 방식으로 정규화*한다(멀티체인). 이 엔진이 바로 *Fireblocks 가 통째로 제공하거나, 자체 구축으로 직접 만드는 대상*이다.
* *지갑 서비스 백엔드 (벤더 무관 · 항상 내 것)* — API 게이트웨이·멱등(같은 요청이 중복 도착해도 한 번만 실행되게 하는 성질)·이벤트 팬아웃(하나의 이벤트를 여러 구독자에게 나눠 보내는 것)·온체인 정합성·추적. 블록체인 특화가 아니라서 어떤 벤더를 써도 남는다.

*전제*: 은행이 만드는 수탁(custodial) 지갑 앱을 가정한다. 그래서 현금↔코인 전환(온/오프램프)은 은행 앱 내부 DB 작업이고, 블록체인 매니저는 온체인 입출금 가장자리에서만 쓰인다.

h2. 2. 한 화면으로 보는 컴포넌트 맵

아래 도식은 두 층과 외부 경계(비즈니스 레이어·노드·서명자)의 관계다. 쓰기 경로는 비즈니스 레이어 → 게이트웨이 → 엔진 → 노드, 읽기 경로는 인덱서가 노드를 폴링·구독해 입금을 감지한다.

{plantuml}
@startuml
skinparam componentStyle rectangle
rectangle "비즈니스 레이어\n인증 · 승인 · 온/오프램프" as BIZ
package "지갑 서비스 백엔드 (벤더 무관 · 항상 내 것)" {
  rectangle "API 게이트웨이 · 멱등" as GW
  rectangle "온체인 정합성 · 추적" as LED
  rectangle "이벤트 · 알림" as NOTIF
}
package "블록체인 매니저 (체인 엔진 — Fireblocks 또는 자체 구축)" {
  rectangle "트랜잭션 빌더\nNonce · Broadcast" as TX
  rectangle "서명 오케스트레이션" as SIG
  rectangle "멀티체인 어댑터" as ADP
  rectangle "인덱서" as IDX
}
rectangle "블록체인 노드 · RPC" as NODE
rectangle "외부 서명자\nMPC · HSM" as SIGNER

BIZ --> GW : ① 호출 (출금 · 주소 발급 · 조회)
GW --> TX
TX --> SIG : 서명 요청
SIG --> SIGNER : 키는 외부에만
TX --> ADP : 조립 · 전파
ADP --> NODE : 제출
NODE --> IDX : ② 블록·로그 수집 → 입금 감지
IDX --> LED : 체인 사실
IDX --> NOTIF
NOTIF --> BIZ : 알림 push
@enduml
{plantuml}

위 도식에서 위쪽 패키지(지갑 서비스 백엔드)는 벤더와 무관하게 항상 우리가 만들고, 아래쪽 패키지(블록체인 매니저)가 Fireblocks 또는 자체 구축으로 통째 교체되는 단위다.

h2. 3. 매니저를 움직이는 두 가지 트리거

이 백엔드는 두 방식으로 움직인다. 이 둘을 섞으면 "입금도 누가 호출하나?" 같은 혼동이 생긴다 — *입금은 호출이 아니라 감지*다.

||트리거||무엇||담당||
|*① 호출 (inbound)*|상위 비즈니스 레이어가 API 게이트웨이를 호출. *송신 트랜잭션(출금) · 주소 발급 · 잔액/상태 조회*. 클라이언트는 비즈니스 레이어를 거치며 매니저를 직접 부르지 않는다.|게이트웨이 → 트랜잭션 빌더|
|*② 감지 (event-driven)*|아무도 호출하지 않는다. *인덱서가 노드/RPC 를 폴링·구독해 수신 트랜잭션(입금)을 스스로 감지*하고, 결과를 알림(push)으로 내보낸다.|인덱서 → 알림|

매니저가 실제로 다루는 것은 *트랜잭션*이다 — "입금" 은 수신 트랜잭션, "출금" 은 송신 트랜잭션이고, 그 업무 의미는 비즈니스 레이어가 붙인다. 온/오프램프(현금↔코인)는 매니저를 거의 거치지 않는다 — 매니저는 외부 입금(②)·외부 출금(①)에서만 등장한다.

h2. 4. 범위 — 다루는 것과 위임하는 것

{note:title=이 설계가 다루지 않는 것 (다른 평면에 위임)}
블록체인 매니저는 다음을 *스스로 결정하지 않는다*. 결정은 상위 평면이 내리고, 매니저는 그 결과를 받아 집행만 한다.
* *출금 승인* — 비즈니스 레이어가 승인을 끝낸 지시만 매니저에 들어온다.
* *준비자산 운용 · 회계 정책* — 자금을 어떻게 굴리고 공시하는가 (자금 운용 평면).
* *회계 원장 · 대사* — 내부 복식부기 장부와의 대사·기표 (회계/원장 평면). 매니저는 검증된 체인 사실을 제공만 한다.
{note}
