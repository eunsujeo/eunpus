h1. 블록체인 지갑 서비스 아키텍처 개요 — 두 층과 두 트리거

{info:title=이 문서의 성격}
여기 담긴 컴포넌트 구분과 다이어그램은 특정 제품의 공식 명세가 아니라, 저자가 일반적인 지갑 인프라 패턴과 Fireblocks 공개 문서를 바탕으로 정리한 설계 참고안이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더를 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경·규제 요건에서 검증이 필요하다.
{info}

이 가이드는 블록체인 지갑 서비스의 백엔드를 *두 층*으로 나눠 본다 — 체인과 직접 대화하는 *블록체인 매니저(체인 엔진)* 와, 그것을 감싸는 *우리 백엔드*. 매니저로는 *Fireblocks 를 채택*했고, 태우는 체인은 *EVM — 이더리움과 Base* 다.

h2. 1. 두 층으로 나눈다

* *블록체인 매니저 (체인 엔진 = Fireblocks 채택)* — 체인과 직접 대화하는 엔진. 체인에서 일어난 일을 *읽어 들이고*(입금 감지·확정 판단), 우리가 원하는 일을 체인에 *써 넣고*(트랜잭션 조립·서명·전파·재전송), 체인마다 다른 규칙을 *한 가지 방식으로 정규화*한다(EVM — 이더리움·Base 를 같은 계열로 묶는다). 이 엔진을 *우리는 Fireblocks 로 채택*했다 — 서명·키·노드·인덱싱·전파·정책 엔진이 대부분 벤더 안으로 들어간다.
* *지갑 서비스 백엔드 (벤더 무관 · 항상 내 것)* — API 게이트웨이·멱등(같은 요청이 중복 도착해도 한 번만 실행되게 하는 성질)·요청 오케스트레이션·이벤트 팬아웃(하나의 이벤트를 여러 구독자에게 나눠 보내는 것)·온체인 정합성·추적. 블록체인 특화가 아니라서 벤더 안으로 들어가지 않고 항상 우리 것이다.

우리 백엔드는 다시 *물리적으로 분리된 두 개*다. *Service 백엔드* 는 고객 런타임(계정·주소·입금·출금 제출·잔액)을, *Admin 백엔드* 는 운영·거버넌스(TAP 정책·승인·키 운영·boost·cancel·동결·rebalance)를 맡고, 별도 배포·권한·감사 경계로 나뉜다.

또한 서명이 온전히 벤더 안에서 끝나지는 않는다. *MPC 키 share 하나는 우리 보안 존(SGX/TEE)에 설치한 API Co-signer* 가 들고, 매 서명마다 Fireblocks 와 *공동서명* 한다. Co-signer 는 서명 직전 *Callback Handler*(우리 정책 훅)에 승인·거부를 물으므로, 나가는 돈의 마지막 자동 관문이 *우리 인프라 안* 에 선다.

*전제*: 은행이 만드는 수탁(custodial) 지갑 앱을 가정한다. 그래서 현금↔코인 전환(온/오프램프)은 은행 앱 내부 DB 작업이고, 블록체인 매니저는 온체인 입출금 가장자리에서만 쓰인다.

h2. 2. 한 화면으로 보는 컴포넌트 맵

아래 도식은 두 층(우리 백엔드 Service·Admin / Fireblocks 매니저)과 보안 존(API Co-signer·Callback Handler)의 관계다. 쓰기 경로는 비즈니스 레이어 → Service 게이트웨이 → 출금 파이프라인 → 서명(MPC + 우리 Co-signer 공동서명) → EVM 전파, 읽기 경로는 Fireblocks 가 입금을 감지해 webhook 으로 우리 수신기에 밀어 넣는다.

위 도식에서 위쪽 패키지(우리 백엔드)는 벤더와 무관하게 항상 우리가 만들고 Service·Admin 으로 물리 분리되며, 가운데 패키지(Fireblocks 매니저)가 채택한 벤더 안이다. 서명은 벤더 안에서 온전히 끝나지 않고, 보안 존의 API Co-signer 가 Callback Handler 의 승인을 받아 공동서명한다 — 마지막 서명 관문이 우리 인프라 안에 선다. 노드·인덱싱·전파는 벤더가 처리하고, 우리는 Co-signer·webhook 수신·매핑 DB 를 운영한다.

h2. 3. 매니저를 움직이는 두 가지 트리거

이 백엔드는 두 방식으로 움직인다. 이 둘을 섞으면 "입금도 누가 호출하나?" 같은 혼동이 생긴다 — *입금은 호출이 아니라 감지* 다.

||트리거||무엇||담당||
|*① 호출 (inbound)*|상위 비즈니스 레이어가 우리 백엔드를 호출. *송신 트랜잭션(출금) · 주소 발급 · 잔액/상태 조회*. 클라이언트는 비즈니스 레이어를 거치며 매니저를 직접 부르지 않는다.|Service 게이트웨이 → Fireblocks 매니저|
|*② 감지 (event-driven)*|아무도 호출하지 않는다. *Fireblocks 가 자기 vault 범위의 수신 트랜잭션(입금)을 감지* 해 webhook 으로 밀어 넣고, 우리 백엔드가 이를 받아 알림(push)으로 내보낸다.|Fireblocks 입금 감지 → webhook 수신기(Service)|

매니저가 실제로 다루는 것은 *트랜잭션* 이다 — "입금" 은 수신 트랜잭션, "출금" 은 송신 트랜잭션이고, 그 업무 의미는 비즈니스 레이어가 붙인다. 온/오프램프(현금↔코인)는 매니저를 거의 거치지 않는다 — 매니저는 외부 입금(②)·외부 출금(①)에서만 등장한다.

h2. 4. 범위 — 다루는 것과 위임하는 것

{note:title=이 설계가 다루지 않는 것 (다른 평면에 위임)}
블록체인 매니저는 다음을 *스스로 결정하지 않는다*. 결정은 상위 평면이 내리고, 매니저는 그 결과를 받아 집행만 한다.
* *출금 승인* — 비즈니스 레이어가 승인을 끝낸 지시만 매니저에 들어온다.
* *준비자산 운용 · 회계 정책* — 자금을 어떻게 굴리고 공시하는가 (자금 운용 평면).
* *회계 원장 · 대사* — 내부 복식부기 장부와의 대사·기표 (회계/원장 평면). 매니저는 검증된 체인 사실을 제공만 한다.
{note}
