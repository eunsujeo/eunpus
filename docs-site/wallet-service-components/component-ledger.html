7. 온체인 정합성 · 추적

체인 사실을 확정하고 요청 ID 로 끝까지 추적한다 — 회계 원장 대사는 회계 평면에 위임
범위 — 체인 측 진실만 책임진다

이 컴포넌트는 체인 측 진실(온체인 정합성)만 책임진다. 내부 회계 원장(double-entry)·잔액 진실원천과의 대사 및 기표·공시는 매니저 범위 밖(회계/원장 평면)이다. 매니저는 검증된 체인 사실을 요청 ID 로 회계 평면에 제공할 뿐, 회계 장부를 소유하지 않는다. (준비자산을 범위 밖으로 둔 것과 같은 논리)

7.1 왜 필요한가

매니저가 체인에 무언가를 쓰거나 읽었으면, 그게 정말 체인에 반영됐는지·끊김 없이 추적되는지를 확인해야 한다. 우리가 보낸 출금이 확정됐나, 입금이 빠짐없이 잡혔나, 한 건의 요청이 채널 접수부터 온체인 결과까지 같은 요청 ID 로 이어지나 — 이 체인 측 정합성이 깨지면 "보냈다고 생각한 게 안 갔거나, 들어온 걸 놓치는" 사고로 직결된다.

단, 이것은 "회계가 맞는가" 와는 다른 문제다. 잔액 장부(복식부기, system-of-record?)와 체인을 맞추고 기표하는 일은 회계 평면의 몫이고, 이 컴포넌트는 그 평면이 신뢰할 수 있는 검증된 체인 사실을 만들어 넘기는 데까지가 책임이다.

7.2 어떻게 동작하는가

핵심 축은 요청 ID 하나다. 한 건의 입금/출금이 채널 접수부터 온체인 결과까지 같은 ID 로 꿰여, 어디서 멈췄는지·어긋났는지 단일 조회로 추적된다.

Figure 7-1. 온체인 정합성 대조. 한 요청 ID 에 묶인 기록(채널 요청·오프체인 지급·온체인 결과·매니저 운영 기록)을 대조해 정상/확인 필요/불일치로 분류한다. 입력 4종은 출처대로 색을 입혔다 — 채널 요청은 지갑 서비스 백엔드(초록), 은행·PG 결과는 외부 시스템(회색), 인덱서 결과·운영 기록은 블록체인 매니저(파랑). 검증된 사실은 회계·원장 평면(회색 = 범위 밖)에 제공되며, 복식부기 기표·잔액 대사는 그 평면이 한다. 오프체인 지급 기록(은행·PG 결과)은 매니저가 대조를 위한 입력으로 받기만 하는 것으로, 차이가 났을 때의 회계적 판단·기표는 회계 평면의 몫이다 — "체인 측 진실만 책임진다" 는 범위는 그대로다.

최소 산출물은 셋이다 — ① 각 요청 ID 의 온체인 정합성 상태(정상/확인 필요/불일치), ② 예외 건의 원인 유형(온체인 미반영·지급 지연·운영 기록 누락 등), ③ 운영 콘솔·알림·회계 평면으로 잇는 예외 목록 + 검증 사실.

7.3 범위 — 회계 원장은 다른 평면

매니저가 하지 않는 것 (회계/원장 평면에 위임)
  • 내부 회계 장부(double-entry) 보유 — 잔액 system-of-record 는 회계 평면.
  • 회계 기표 · 대사 — 체인 사실 ↔ 회계 장부 일치 검증과 분개는 회계 평면.
  • 공시 · 회계 기준 — 준비자산·재무 공시는 자금 운용/회계 평면.

매니저는 검증된 체인 사실(요청 ID·금액·확정 수준·tx 해시)을 요청 ID 로 제공하는 데까지. 그 사실을 받아 장부에 기표·대사하는 것은 회계 평면이 한다.

7.4 코드로 보면

설명용 의사코드다. 이 컴포넌트는 대조(reconcile)만 한다 — 회계 기표·잔액 대사는 안 한다(7.3). 한 correlationId(요청 ID)에 묶인 기록을 여러 출처에서 모아, 한 사실로 일치하는지 대조하고, 검증된 사실만 회계 평면으로 넘긴다. 같은 두 겹 — 자산 단위·소수점·주소 정규화는 체인별(어댑터 2), 대조 로직은 공통.

class ReconciliationEngine {
  // sources = { gateway, instruction, chain(=인덱서 3), opLog }
  // adapters[chainId] = 단위·주소 정규화(2),  accounting = 회계 평면(범위 밖, 7.3)
  constructor(adapters, sources, accounting, alerts) {}

  async reconcile(correlationId) {
    const rec = {
      request:     await this.sources.gateway.byId(correlationId),        // 채널 요청
      instruction: await this.sources.instruction.byId(correlationId),    // 승인된 오프체인 지급
      onchain:     await this.sources.chain.byCorrelation(correlationId),  // 온체인 결과(인덱서 정규 tx)
      op:          await this.sources.opLog.byId(correlationId),          // 매니저 운영 기록
    }

    // 온체인 미반영(아직 안 옴)이면 정규화·대조 자체가 불가 — 먼저 분기
    if (!rec.onchain) return 'NEEDS_REVIEW'          // 지연·미반영 — sweep 이 다시 잡는다(7.5 ②)

    // 체인별 단위·소수점·주소를 "비교 가능한 정규형" 으로 (어댑터)
    const a = this.adapters[rec.onchain.chainId]
    const norm = {
      amount:  a.normalizeAmount(rec.onchain),       // wei/satoshi/lamport → 정규 단위
      address: a.normalizeAddress(rec.onchain.to),
      status:  rec.onchain.status,
    }

    // 대조 — 요청·지시·온체인·운영 기록이 한 사실로 모이나
    const verdict = classify({
      amountMatch:  eq(norm.amount,  rec.instruction?.amount),
      addressMatch: eq(norm.address, a.normalizeAddress(rec.instruction?.to)),
      confirmed:    norm.status === 'confirmed',
    })   // → 'MATCHED' | 'NEEDS_REVIEW' | 'MISMATCH'

    if (verdict === 'MISMATCH') this.alerts.raise(correlationId, rec)         // 멈추고 사람에게
    else this.accounting.postFact({ correlationId, ...norm, verdict })        // 검증된 사실만 → 회계 평면
    return verdict
  }
}
코드가 말하는 것
  • 대조만, 기표는 안 한다(7.3) — postFact 로 검증된 사실을 회계 평면에 넘길 뿐, 복식부기·잔액 대사는 그 평면의 몫이다. 그래서 accounting 은 범위 밖 포트로 둔다.
  • correlationId 로 4 출처를 한자리에 — 채널 요청 · 승인된 지시 · 온체인 결과 · 운영 기록. 온체인 결과는 인덱서(3)의 정규 Transaction 을 그대로 받는다.
  • 비교 전 정규화는 체인별 → 어댑터 — wei/satoshi/lamport 단위, 소수점, 주소 표기가 체인마다 달라서, normalizeAmount·normalizeAddress 로 맞춰야 eq() 비교가 성립한다.
  • 3-way 분류 + MISMATCH 는 멈춤 — MATCHED / NEEDS_REVIEW / MISMATCH. 불일치는 자동 진행하지 않고 알림(사람 개입). 검증된 것만 회계로 흘린다.

3.4·4.3·5.4 와 같은 분리 — 정규화 규칙(단위·주소)은 체인별(어댑터), 대조 로직은 공통이다.

7.5 언제 도는가 — 이벤트 + 주기 sweep

이 대조는 쓰기(출금 집행) 경로 밖에서 사후·배경으로 돈다 — 출금을 막지 않는다. 같은 reconcile(correlationId) 를 세 시점이 부른다.

Figure 7-2. 대조의 트리거. 같은 reconcile() 를 ① 인덱서 confirm 이벤트(건별) ② 주기 sweep(배치) ③ 온디맨드 세 경로가 부른다 — 함수는 같고 호출 시점만 다르다. 인덱서 이벤트·주기 sweep 은 매니저 안에서 도는 트리거(파랑), 온디맨드는 회계 마감·예외 조사 등 바깥에서 들어오는 요청(회색)이다. 쓰기 경로와 분리된 사후 동작.

  • ① 이벤트 기반(건별) — 인덱서(3)의 onChainEvent 가 "이 요청의 온체인 결과 확정" 을 알리면 그 건을 즉시 대조. 입금 감지 직후(10), 출금 확정 직후(11).
  • ② 주기 sweep(완전성 안전망) — 시간별·일마감 등으로 열린/최근 ID 를 훑는다. "와야 하는데 안 온 것"(stuck·미반영·지급 지연)은 이벤트가 없어서 이벤트론 안 잡힌다 → sweep 이 잡는다. Figure 7-1 의 🟡 확인 필요가 여기서 나온다.
  • ③ 온디맨드 — 회계 마감 전 정합성 확인, 예외 조사 시 수동 트리거.
이벤트만으론 부족하다 — sweep 이 안전망

이벤트 기반은 "일어난 것" 만 본다. 정합성에서 진짜 위험한 건 일어나야 했는데 안 일어난 것(전파됐는데 확정 안 됨, 오프체인 지급은 됐는데 온체인 결과 없음)이라, 이건 주기 sweep 으로만 드러난다. 그래서 둘 다 필요하다 — 이벤트 = 빠름, sweep = 완전.

7.6 다른 컴포넌트와의 관계

관계내용
← 인덱서체인 위 사실(입금/출금 확정 결과)을 대조 근거로 받는다.
← 트랜잭션 빌더출금 전파·확정 결과를 요청 ID 로 연결.
→ 회계 · 원장 평면 (범위 밖)검증된 체인 사실을 요청 ID 로 제공 (기표·대사는 그 평면이 수행).
→ API 게이트웨이건별 처리 상태·온체인 정합성 조회 제공.
→ 이벤트 · 알림불일치·예외·정정을 운영자와 비즈 레이어에 알림 — CONFIRMED 알림(8장)이 먼저 나간 건이 사후 검증에서 뒤집히면, 정정 이벤트로 반영 철회를 트리거한다.
설계 포인트
  • 요청 ID 단일 축 — 모든 기록을 한 ID 로 꿰어야 종단 추적·검증이 가능.
  • 멱등 처리 — 같은 결과를 두 번 처리해도 상태가 두 번 바뀌지 않게.
  • as-of-block? 인식 — 인덱서가 준 사실의 확정 수준을 함께 보고, reorg? 로 뒤집히면 제공한 사실도 정정 통지.
  • 회계 장부 미소유 — 매니저는 검증 사실 제공까지. 잔액 진실원천·기표는 회계 평면.
