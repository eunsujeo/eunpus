7. 온체인 정합성 · 추적

체인 사실을 확정하고 요청 ID 로 끝까지 추적한다 — 회계 원장 대사는 회계 평면에 위임
이 페이지의 전제 — 체인 사실은 Fireblocks 가 준다

블록체인 매니저로 Fireblocks 를 채택했으므로, 체인 위 사실은 우리가 노드·인덱서를 돌려 직접 캐지 않는다. 입금·확정·출금 결과는 Fireblocks webhook 으로 들어오고, 잔액은 getVaultAccountAsset 로 조회한다. 그래서 이 컴포넌트가 하는 일은 "체인을 직접 관측" 하는 게 아니라 벤더가 준 값을 우리 기록과 주기적으로 대조하는 것이다 — 자동 보정은 하지 않는다. 대조는 Service·Admin 두 백엔드가 함께 참여하는 운영·감사 평면의 일이다.

범위 — 체인 측 진실만 책임진다

이 컴포넌트는 체인 측 진실(온체인 정합성)만 책임진다. 내부 회계 원장(double-entry)·잔액 진실원천과의 대사 및 기표·공시는 이 컴포넌트 범위 밖(회계/원장 평면)이다. 검증된 체인 사실을 요청 ID 로 회계 평면에 제공할 뿐, 회계 장부를 소유하지 않는다. (준비자산을 범위 밖으로 둔 것과 같은 논리)

7.1 왜 필요한가

Fireblocks 가 체인에 무언가를 쓰거나 읽어 그 결과를 우리에게 넘겼으면, 그게 정말 체인에 반영됐는지·끊김 없이 추적되는지를 확인해야 한다. 우리가 보낸 출금이 확정됐나, 입금이 빠짐없이 잡혔나, 한 건의 요청이 채널 접수부터 온체인 결과까지 같은 요청 ID 로 이어지나 — 이 체인 측 정합성이 깨지면 "보냈다고 생각한 게 안 갔거나, 들어온 걸 놓치는" 사고로 직결된다. 벤더 조회가 아무리 정확해도 webhook 누락·지연·우리 쪽 반영 버그는 생기게 마련이라, 값은 벤더의 것이되 주기적으로 우리 기록과 맞춰 확인한다.

단, 이것은 "회계가 맞는가" 와는 다른 문제다. 잔액 장부(복식부기, system-of-record?)와 체인을 맞추고 기표하는 일은 회계 평면의 몫이고, 이 컴포넌트는 그 평면이 신뢰할 수 있는 검증된 체인 사실을 만들어 넘기는 데까지가 책임이다.

7.2 어떻게 동작하는가

핵심 축은 요청 ID 하나다. 한 건의 입금/출금이 채널 접수부터 온체인 결과까지 같은 ID 로 꿰여, 어디서 멈췄는지·어긋났는지 단일 조회로 추적된다. 여기서 대조하는 두 장부는 Fireblocks 가 준 값(webhook 이벤트·getVaultAccountAsset 잔액)과 우리 기록(요청·tx 상태·매핑 DB)이다.

Figure 7-1. 온체인 정합성 대조 — 벤더 값 대 우리 기록. 한 요청 ID 에 묶인 기록을 대조해 정상/확인 필요/불일치로 분류한다. 입력 4종은 출처대로 색을 입혔다 — 채널 요청은 우리 백엔드(초록), 은행·PG 결과는 외부 시스템(회색), Fireblocks 값(webhook·getVaultAccountAsset)은 벤더(파랑), 우리 기록(매핑 DB)은 우리 백엔드(초록). 대조는 Service·Admin 이 함께 참여하는 운영·감사 평면의 일이다. 검증된 사실은 회계·원장 평면(회색 = 범위 밖)에 제공되며, 복식부기 기표·잔액 대사는 그 평면이 한다. 불일치가 나도 자동으로 고치지 않는다 — 정정 이벤트를 만들어 사람이 본다.

최소 산출물은 셋이다 — ① 각 요청 ID 의 온체인 정합성 상태(정상/확인 필요/불일치), ② 예외 건의 원인 유형(온체인 미반영·지급 지연·우리 기록 누락 등), ③ 운영 콘솔·알림·회계 평면으로 잇는 예외 목록 + 검증 사실.

확정(finality)은 Fireblocks 상태로 판단한다 — DCCP 임계

"체인에 등장했나(confirm)" 와 "확정됐나(finality)" 는 다르다. Fireblocks 거래는 전파 뒤 CONFIRMING → COMPLETED 로 흐르는데, COMPLETED = 확정 정책이 정한 임계 confirmation 수에 도달한 상태이고 그때가 우리 기준의 finality 다. 그 임계는 확정 정책(Fireblocks 의 DCCP?, Admin 이 관리)이 체인별로 정하고, 기본값은 대부분 1 confirmation 이다. 대조는 벤더가 준 상태(CONFIRMING/COMPLETED)와 numOfConfirmations 를 읽어서 판단하지, 우리가 블록을 세서 정하지 않는다. 이더리움과 Base 는 같은 EVM 이라 이 흐름이 동일하다.

7.3 범위 — 회계 원장은 다른 평면

매니저가 하지 않는 것 (회계/원장 평면에 위임)
  • 내부 회계 장부(double-entry) 보유 — 잔액 system-of-record 는 회계 평면.
  • 회계 기표 · 대사 — 체인 사실 ↔ 회계 장부 일치 검증과 분개는 회계 평면.
  • 공시 · 회계 기준 — 준비자산·재무 공시는 자금 운용/회계 평면.

검증된 체인 사실(요청 ID·금액·확정 수준·tx 해시)을 요청 ID 로 제공하는 데까지. 그 사실을 받아 장부에 기표·대사하는 것은 회계 평면이 한다.

7.4 코드로 보면

설명용 의사코드다. 이 컴포넌트는 대조(reconcile)만 한다 — 회계 기표·잔액 대사는 안 하고, 어긋나도 자동 보정하지 않는다(7.3). 한 correlationId(요청 ID)에 묶인 기록을 여러 출처에서 모아, Fireblocks 값과 우리 기록이 한 사실로 일치하는지 대조하고, 검증된 사실만 회계 평면으로 넘긴다. 같은 두 겹 — 자산 단위·소수점·주소 정규화는 체인별(어댑터 2), 대조 로직은 공통. EVM(이더리움·Base)은 단위·주소 체계가 같아 정규화가 한 벌로 족하다.

class ReconciliationEngine {
  // sources = { gateway, instruction, vendor(=Fireblocks webhook·조회), opLog(우리 기록) }
  // adapters[chainId] = 단위·주소 정규화(2),  accounting = 회계 평면(범위 밖, 7.3)
  constructor(adapters, sources, accounting, alerts) {}

  async reconcile(correlationId) {
    const rec = {
      request:     await this.sources.gateway.byId(correlationId),         // 채널 요청
      instruction: await this.sources.instruction.byId(correlationId),     // 승인된 오프체인 지급
      vendor:      await this.sources.vendor.byCorrelation(correlationId),  // Fireblocks 값(webhook·조회)
      op:          await this.sources.opLog.byId(correlationId),           // 우리 기록(요청·tx 상태)
    }

    // 벤더 값이 아직 안 옴(webhook 미도착)이면 정규화·대조 자체가 불가 — 먼저 분기
    if (!rec.vendor) return 'NEEDS_REVIEW'           // 지연·미반영 — sweep 이 다시 잡는다(7.5 ②)

    // 체인별 단위·소수점·주소를 "비교 가능한 정규형" 으로 (어댑터, EVM 은 wei/체크섬 주소)
    const a = this.adapters[rec.vendor.chainId]
    const norm = {
      amount:  a.normalizeAmount(rec.vendor),        // wei → 정규 단위
      address: a.normalizeAddress(rec.vendor.to),
      status:  rec.vendor.status,                    // Fireblocks 상태(CONFIRMING/COMPLETED …)
      confs:   rec.vendor.numOfConfirmations,        // 확정 판단 근거
    }

    // 대조 — 요청·지시·벤더 값·우리 기록이 한 사실로 모이나 (finality = COMPLETED, DCCP 임계 도달)
    const verdict = classify({
      amountMatch:  eq(norm.amount,  rec.instruction?.amount),
      addressMatch: eq(norm.address, a.normalizeAddress(rec.instruction?.to)),
      finalized:    norm.status === 'COMPLETED',     // DCCP 임계 confirmation 도달
    })   // → 'MATCHED' | 'NEEDS_REVIEW' | 'MISMATCH'

    if (verdict === 'MISMATCH') this.alerts.raise(correlationId, rec)         // 자동 보정 없이 사람에게
    else this.accounting.postFact({ correlationId, ...norm, verdict })        // 검증된 사실만 → 회계 평면
    return verdict
  }
}
코드가 말하는 것
  • 대조만, 기표는 안 한다(7.3) — postFact 로 검증된 사실을 회계 평면에 넘길 뿐, 복식부기·잔액 대사는 그 평면의 몫이다. 그래서 accounting 은 범위 밖 포트로 둔다.
  • correlationId 로 4 출처를 한자리에 — 채널 요청 · 승인된 지시 · Fireblocks 값 · 우리 기록. 벤더 값은 webhook(3. 입금 감지)과 getVaultAccountAsset 조회에서 온 것을 그대로 받는다.
  • finality 는 벤더 상태로 — status === 'COMPLETED' 가 DCCP 임계 confirmation 도달, 즉 우리 기준 finality 다(7.2 절 callout). numOfConfirmations 를 함께 봐 CONFIRMING 인지 COMPLETED 인지 가른다 — 블록을 우리가 세지 않는다.
  • 비교 전 정규화는 체인별 → 어댑터 — EVM 은 wei 단위·체크섬 주소로 normalizeAmount·normalizeAddress 를 맞춰야 eq() 비교가 성립한다.
  • 3-way 분류 + MISMATCH 는 멈춤 · 자동 보정 금지 — MATCHED / NEEDS_REVIEW / MISMATCH. 불일치는 자동으로 고치지 않고 알림(사람 개입). 없는 돈을 만들거나 지우는 코드가 가장 위험하다. 검증된 것만 회계로 흘린다.

같은 분리 — 정규화 규칙(단위·주소)은 체인별(어댑터), 대조 로직은 공통이다.

Figure 7-2. 대조의 트리거. 같은 reconcile() 를 ① Fireblocks webhook 이벤트(건별) ② 주기 sweep(배치) ③ 온디맨드 세 경로가 부른다 — 함수는 같고 호출 시점만 다르다. webhook 이벤트는 벤더가 밀어 주는 신호(파랑), 주기 sweep 은 우리 백엔드가 도는 안전망(파랑), 온디맨드는 회계 마감·예외 조사 등 바깥에서 들어오는 요청(회색)이다. 쓰기 경로와 분리된 사후 동작이고, 대조 자체는 Service·Admin 두 백엔드가 함께 참여한다.

  • ① 이벤트 기반(건별) — Fireblocks webhook(3. 입금 감지)의 onChainEvent 가 "이 요청의 상태가 COMPLETED 로 확정" 을 알리면 그 건을 즉시 대조. 입금 감지 직후(10), 출금 확정 직후(11).
  • ② 주기 sweep(완전성 안전망) — 시간별·일마감 등으로 열린/최근 ID 를 훑는다. "와야 하는데 안 온 것"(stuck·미반영·지급 지연)은 이벤트가 없어서 이벤트론 안 잡힌다 — sweep 이 잡는다. Figure 7-1 의 "확인 필요" 가 여기서 나온다.
  • ③ 온디맨드 — 회계 마감 전 정합성 확인, 예외 조사 시 수동 트리거.
이벤트만으론 부족하다 — sweep 이 안전망

이벤트 기반은 "일어난 것" 만 본다. 정합성에서 진짜 위험한 건 일어나야 했는데 안 일어난 것(전파됐는데 확정 안 됨, 오프체인 지급은 됐는데 온체인 결과 없음)이라, 이건 주기 sweep 으로만 드러난다. 그래서 둘 다 필요하다 — 이벤트 = 빠름, sweep = 완전.

→ 8. 이벤트 · 알림불일치·예외·정정을 운영자(Admin)와 비즈 레이어(Service)에 알림 — COMPLETED 알림(8장)이 먼저 나간 건이 사후 검증에서 뒤집히면, 정정 이벤트로 반영 철회를 트리거한다.
설계 포인트
  • 요청 ID 단일 축 — 모든 기록을 한 ID 로 꿰어야 종단 추적·검증이 가능.
  • 멱등 처리 — 같은 결과를 두 번 처리해도 상태가 두 번 바뀌지 않게.
  • 자동 보정 금지 — 벤더 값과 우리 기록이 어긋나면 코드가 임의로 맞추지 않는다. 정정 이벤트를 만들어 사람이 판단한다 — 없는 돈을 만들거나 지우는 자동 보정이 가장 위험하다.
  • 확정 수준 인식 — Fireblocks 가 준 상태(CONFIRMING/COMPLETED)와 numOfConfirmations 를 함께 보고, reorg? 로 뒤집히면 제공한 사실도 정정 통지. finality 판단은 벤더 상태에 맡기고 우리가 블록을 세지 않는다.
  • Service·Admin 공동 참여 — 고객 런타임 조회는 Service, 회계·대사처럼 감사에 걸리는 조회는 Admin 도 함께 부른다. 두 백엔드는 같은 포트를 쓰되 배포·권한·감사 경계가 다르다.
  • 회계 장부 미소유 — 검증 사실 제공까지. 잔액 진실원천·기표는 회계 평면.
