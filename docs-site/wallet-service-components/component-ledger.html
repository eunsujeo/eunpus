6. 원장 정합성 · 대사

체인 위 사실과 내부 장부가 어긋나지 않게 — 돈을 다루는 시스템의 진실 검증

6.1 왜 필요한가

매니저 안에는 두 개의 "사실" 이 있다. 하나는 체인 위 사실(인덱서가 본 입금·출금 결과)이고, 다른 하나는 내부 장부(우리 시스템이 기록한 요청·잔액)다. 이 둘이 어긋나면 — 장부엔 있는데 체인엔 없거나, 체인엔 왔는데 장부에 안 잡히면 — "있다고 생각한 돈이 없거나, 없는 돈을 내보내는" 사고로 직결된다.

대사(reconciliation?)는 이 둘을 지속적으로 맞춰 보고, 불일치를 조기에 잡아낸다. 돈을 다루는 시스템에서 사후 정정이 가능하려면 대사는 선택이 아니라 필수다.

6.2 어떻게 동작하는가

핵심은 요청 ID 라는 하나의 축이다. 한 건의 입금/출금이 채널 요청부터 최종 결과까지 같은 요청 ID 로 꿰여, 어디서 멈췄는지·어긋났는지 단일 조회로 추적된다.

6.3 다른 컴포넌트와의 관계

관계내용
← 인덱서체인 위 사실(입금/출금 확정 결과)을 대조 근거로 받는다.
← 트랜잭션 빌더출금 확정 결과를 장부에 반영.
← 온/오프램프fiat 지급/입금 결과를 토큰 흐름과 한 건으로 대조.
→ API 게이트웨이건별 처리 상태·정합성 조회 제공.
→ 이벤트 · 알림불일치·예외를 운영자에게 알림.
경계 — 회계 정책은 범위 밖

이 컴포넌트는 "체인과 장부가 기술적으로 맞는가" 만 본다. 준비자산 운용·공시·회계 기준 같은 정책은 자금 운용 평면의 몫이다. 내부 원장을 복식부기로 둘지 같은 설계는 매니저 안에서 하되, 그 위의 회계·공시 판단은 위임한다.

설계 포인트
  • 요청 ID 단일 축 — 모든 기록을 한 ID 로 꿰어야 종단 추적·대사가 가능.
  • 멱등 반영 — 같은 결과를 두 번 반영해 장부가 두 번 늘지 않게.
  • as-of-block 인식 — 인덱서가 준 사실의 확정 수준을 함께 보고, reorg 로 뒤집히면 장부도 정정.
