17. 프로젝트 구조 (모노레포)

2층·3포트·어댑터 교체·체인별 분리를 그대로 디렉터리로 — 의존성은 안쪽(도메인·포트)으로만
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

17.1 왜 모노레포인가

지금까지의 설계(13. 포트·두 층·어댑터 교체·체인별 분리)를 코드로 옮기면, 경계가 패키지 경계가 되어야 흐트러지지 않는다. 모노레포?로 두면 (1) 도메인·포트가 안쪽 핵으로 고정되고 (2) 어댑터를 패키지 단위로 넣고 빼며 (3) 한 번에 빌드·테스트·타입체크할 수 있다. 핵심 규칙은 하나 — 의존성은 항상 안쪽(domain)으로만 흐른다(헥사고날? · 클린 아키텍처).

스택: Kotlin + Spring (JVM) 이 이 조합엔 특히 잘 맞는다

Canton 이 JVM 네이티브(Scala · DAML Java Ledger API), NodeWallet SDK 가 Java/Spring, Fireblocks 는 Java SDK, EVM 은 web3j — 이더리움+Canton 스택에 JVM 이 1급이다. 포트도 Kotlin 에 자연스럽다: interface 포트, chainSpecific 은 sealed 로(when 망라), 어댑터 wiring 은 Spring DI. 유의점은 Solana raw JVM 툴링(solanaj)이 얕은 것 정도인데, Solana 는 NodeWallet SDK·Fireblocks 뒤로 가려져 직접 만질 일이 적다. 한 가지 더 — Canton 의 공식 wallet SDK·Wallet Gateway(canton-network/wallet)는 TypeScript(NodeJS) 전용이다. JVM 스택이면 chains/canton 은 DAML Java Ledger API(gRPC)로 직접 붙이거나(Canton 자체는 JVM 네이티브라 가능), TS Gateway 를 별도 서비스로 띄워 호출하는 식으로 간다(Canton 가이드).

한 가지 예외 — chains/solana 는 "체인 프로토콜별 구현" 이라는 chains/* 정의와 달리 프로토콜 구현을 벤더 SDK(NodeWallet)에 위임한다. 포트 구현이라는 교체 축은 여전히 adapters/nodewallet 몫이고, chains/solana 에는 blockhash·commitment 같은 체인 특성 처리만 남는다 — 의존 방향(adapters → chains → domain)은 다른 체인과 동일하다.

17.3 의존성 규칙 — 안쪽으로만

패키지 경계가 의미 있으려면 화살표(의존)가 한 방향이어야 한다. domain 은 누구도 의존하지 않고 모두가 domain 을 의존한다.

Figure 17-1. 의존성은 안쪽으로만. domain(보라)=포트·모델이 핵이고 누구도 의존하지 않는다. apps(초록 — 우리 실행 모듈)가 어댑터·백엔드를 wiring 하고, adapters(파랑)가 engine·chains 를 조립한다. backend(초록)는 domain 만 의존해 어떤 어댑터든 그대로다. 화살표가 안쪽으로만 향하면 — 바깥(어댑터·체인)을 바꿔도 안쪽(도메인·백엔드)은 안 바뀐다. 한 가지 주의 — ChainAdapter 인터페이스(SPI)는 engine/multichain 에 있으므로, 컴파일 의존은 chains → engine/multichain 방향이다(구현이 인터페이스 쪽으로 의존하는 SPI 역전). engine 의 나머지(indexer·tx-pipeline·signing)는 chains 를 모르고 SPI(레지스트리)만 보며, engine 과 chains 를 함께 조립하는 것은 adapters/self-build 다.

이게 "교체 가능" 의 실체
  • 어댑터 교체 = 모듈 교체 — Fireblocks 만 쓰면 adapters/self-build·nodewallet 모듈은 빌드·배포에서 빠진다. apps/api 의 wiring 한 줄만 바꾸면 되고 domain·backend 코드는 그대로.
  • 포트는 한 곳(domain) — 어댑터·앱이 전부 같은 포트 타입을 import 하니, 시그니처가 어긋나면 컴파일에서 잡힌다.
  • 체인 추가 = chains/<new> 하나 — engine·backend·domain 은 안 바뀐다(2·3의 "수집·메커니즘은 체인별, 나머지는 공통").

17.5 시작 셋 — 이더리움 + Canton, 현재 Fireblocks

처음부터 전부 만들 필요 없다. 지금 필요한 것만:

  • 필수: domain · backend · adapters/fireblocks · chains/canton · apps/api · apps/webhook-receiver
  • 선택·나중(자체 구축 전환 대비): engine/* · chains/evm · adapters/self-build 자리만 비워두고, 도메인 포트는 그대로 둔다 → 전환 시 새 어댑터 패키지만 추가하면 backend·apps 는 거의 그대로. 이더리움 쪽은 Fireblocks 가 nonce·수수료·전파를 모두 흡수하므로 chains/evm 도 자체 구축 전환 때 채우면 된다.
Fireblocks 를 써도 engine/chains 가 비어 있지 않은 이유

Fireblocks 가 멀티체인·서명·nonce 를 다 흡수하므로 초기엔 engine/* 가 거의 비어도 된다. 단 Canton 의 2-step·ChainQuery(임의 조회)처럼 Fireblocks 가 안 주거나 다르게 주는 부분은 chains/canton·adapters/chainquery-alchemy 에 들어간다. "벤더가 다 해준다" 가 깨지는 자리가 곧 chains/*·보조 어댑터의 존재 이유다(13.8 트레이드오프).

17.6 도구

  • Gradle 멀티모듈? — 모듈 간 의존은 implementation(project(":domain")). 버전은 libs.versions.toml 카탈로그 한 곳에.
  • domain 은 순수 Kotlin — Spring 의존 금지(build.gradle.kts 에 spring-* 미포함). Spring Boot 는 backend·apps·일부 adapters 에만.
  • DI = Spring — 포트 구현을 @Component 로 주입, 어댑터 교체는 @Profile 또는 @ConditionalOnProperty 한 줄(예: custody=fireblocks|selfbuild).
  • 의존 방향 강제 — Gradle 모듈 그래프 + ArchUnit?/Konsist 로 "안쪽(domain)으로만" 을 CI 에서 검사.

정리하면 — 모듈 경계 = 설계 경계. 포트(domain)를 핵에 두고 어댑터를 모듈로 분리하면, 이 가이드가 말한 "도메인 우선 · 어댑터 교체 · 체인별 분리" 가 코드 구조에서 강제된다. 처음으로 — 0. Overview.
