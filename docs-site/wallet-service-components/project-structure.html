17. 프로젝트 구조 (모노레포)

두 백엔드(Service·Admin)·포트·Fireblocks 어댑터를 그대로 디렉터리로 — 의존성은 안쪽(도메인·포트)으로만
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다. 블록체인 매니저는 Fireblocks 를 채택했고 태우는 체인은 EVM(이더리움·Base)이므로, 이 구조도 adapters/fireblocks 를 유일한 라이브 어댑터로 두고 자체 구축은 테스트용 가짜(adapters/fake)로만 남긴다.

17.1 왜 모노레포인가

지금까지의 설계(13. 포트·두 백엔드(Service·Admin)·어댑터 교체)를 코드로 옮기면, 경계가 패키지 경계가 되어야 흐트러지지 않는다. 모노레포?로 두면 (1) 도메인·포트가 안쪽 핵으로 고정되고 (2) 어댑터를 패키지 단위로 넣고 빼며 (3) 한 번에 빌드·테스트·타입체크할 수 있다. 핵심 규칙은 하나 — 의존성은 항상 안쪽(domain)으로만 흐른다(헥사고날? · 클린 아키텍처).

스택: Kotlin + Spring (JVM) 이 이 조합엔 특히 잘 맞는다

Fireblocks 가 Java SDK 를 1급으로 제공하고, EVM 은 web3j 로 붙으며(자체 구축 전환이나 보조 조회에 대비한 준비물), 두 백엔드(Service·Admin)와 webhook 수신기는 Spring Boot 로 자연스럽게 나뉜다. 포트도 Kotlin 에 잘 맞는다: interface 포트, chainSpecific 은 sealed 로(when 망라), 어댑터 wiring 은 Spring DI. 지금은 매니저가 Fireblocks 라 서명·nonce·전파·인덱싱이 대부분 벤더 안에서 끝나므로, JVM 쪽 우리 코드는 포트·두 백엔드·Fireblocks 어댑터·webhook 수신에 집중된다.

여기엔 자체 구축 엔진(engine/*)이나 체인 프로토콜 모듈(chains/*)이 없다 — 매니저로 Fireblocks 를 채택했으므로 서명·nonce·전파·멀티체인 흡수가 전부 벤더 안에서 끝나기 때문이다. 훗날 자체 구축으로 전환하거나 EVM 을 직접 붙일 때에만 engine/*·chains/evm 을 새 모듈로 추가하면 되고, 도메인 포트와 두 백엔드는 그대로다(17.5). 지금은 그 자리를 비워 두고, 포트 계약을 벤더 없이 검증하는 adapters/fake 만 둔다.

17.3 의존성 규칙 — 안쪽으로만

패키지 경계가 의미 있으려면 화살표(의존)가 한 방향이어야 한다. domain 은 누구도 의존하지 않고 모두가 domain 을 의존한다.

Figure 17-1. 의존성은 안쪽으로만. domain(보라)=포트·모델이 핵이고 누구도 의존하지 않는다. 두 backend(초록 — Service·Admin)는 domain 만 의존하므로 어댑터를 모른다("어느 벤더인지 모른다"가 컴파일 타임의 사실). 어댑터를 아는 곳은 apps 의 DI(점선)뿐이다. adapters/fireblocks(파랑)가 유일한 라이브 구현이고, fake 는 테스트용 가짜 구현이다 — 계약 테스트를 두 어댑터가 똑같이 통과하면 포트 의미가 구현과 무관함이 증명된다. Fireblocks SDK 는 adapters/fireblocks 안에 격리되고, 벤더 타입이 그 밖으로 새면 교체가 깨지므로 이 경계는 빌드 규칙(ArchUnit)으로 막는다. Service·Admin 이 별도 backend·apps 모듈인 것이 곧 물리 분리다.

이게 "교체 가능" 의 실체
  • 어댑터 교체 = 모듈 교체 — 지금은 adapters/fireblocks 하나만 라이브다. 훗날 벤더를 바꾸거나 자체 구축으로 전환하면 새 어댑터 모듈을 이 자리에 더하고 apps/*-api 의 wiring 한 줄만 바꾼다 — domain·backend 코드는 그대로(다만 주소·잔액은 이전되지 않아 자금 sweep 이 별도 비용, 워크스루 8p).
  • 포트는 한 곳(domain) — 어댑터·앱이 전부 같은 포트 타입을 import 하니, 시그니처가 어긋나면 컴파일에서 잡힌다.
  • EVM 체인 추가 = 어댑터의 체인·자산 등록만 — 이더리움·Base 는 같은 EVM 이라 어댑터가 등록만 늘리면 되고 backend·domain 은 0줄(2 "EVM 차이 흡수"). Fireblocks 가 그 체인을 지원하기만 하면 된다.

17.5 시작 셋 — EVM(이더리움·Base), 매니저는 Fireblocks

처음부터 전부 만들 필요 없다. 지금 필요한 것만:

  • 필수: domain · backend/service · backend/admin · adapters/fireblocks · adapters/fake · apps/service-api · apps/admin-api · apps/webhook-receiver
  • 선택·나중(자체 구축 전환 대비): engine/* · chains/evm · 자체 구축 어댑터 자리만 비워두고, 도메인 포트는 그대로 둔다 → 전환 시 새 어댑터·엔진 패키지만 추가하면 backend·apps 는 거의 그대로. 지금은 Fireblocks 가 EVM 의 nonce·수수료·전파를 모두 흡수하므로 chains/evm 은 자체 구축 전환 때 채우면 된다.
Fireblocks 를 써도 우리 쪽에 반드시 남는 것

Fireblocks 가 멀티체인·서명·nonce·전파를 다 흡수하므로 engine/chains 없이 시작할 수 있다. 그래도 우리 쪽엔 반드시 남는 게 있다 — 두 백엔드(Service·Admin) · webhook 수신기 · 매핑 DB · 온프렘 API Co-signer(SGX/TEE) 운영이다. 특히 co-signer 는 서명 직전 우리 Callback Handler 로 승인·거부를 거는 자리라, 벤더에 위임되지 않는 우리 몫이다(5장). ChainQuery(임의 외부 주소 조회)처럼 Fireblocks 가 안 주는 부분만 adapters/chainquery-alchemy 로 선택적으로 채운다(13.8 트레이드오프).

17.6 도구

  • Gradle 멀티모듈? — 모듈 간 의존은 implementation(project(":domain")). 버전은 libs.versions.toml 카탈로그 한 곳에.
  • domain 은 순수 Kotlin — Spring 의존 금지(build.gradle.kts 에 spring-* 미포함). Spring Boot 는 backend·apps·일부 adapters 에만.
  • DI = Spring — 포트 구현을 @Component 로 주입, 어댑터 선택은 @Profile 또는 @ConditionalOnProperty 한 줄(예: 운영은 manager=fireblocks, 계약 테스트는 manager=fake).
  • 의존 방향 강제 — Gradle 모듈 그래프 + ArchUnit?/Konsist 로 "안쪽(domain)으로만" 을 CI 에서 검사.

정리하면 — 모듈 경계 = 설계 경계. 포트(domain)를 핵에 두고 두 백엔드(Service·Admin)를 별도 모듈로, Fireblocks 어댑터를 교체 축으로 분리하면, 이 가이드가 말한 "도메인 우선 · 어댑터 교체 · 백엔드 물리 분리" 가 코드 구조에서 강제된다. 처음으로 — 0. Overview.
