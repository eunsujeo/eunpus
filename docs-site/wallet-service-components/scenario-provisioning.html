9. 계정·주소 발급 (온보딩)

고객 온보딩 시 createAccount · 첫 주소 발급 — 입금·출금에 앞선 사전 단계. Service 백엔드가 부른다

입금(10장)·출금(11장)은 주소가 이미 있다는 전제로 시작한다. 그 주소를 만드는 게 이 단계 — 고객 온보딩(또는 새 자산 추가) 때 Service 백엔드가 계정을 만들고(createAccount) 자산별 수신 주소를 발급(issueDepositAddress)한다. 매니저로 Fireblocks 를 채택했으므로 계정은 Fireblocks 의 vault(createVaultAccount) 하나이고, 주소는 그 vault 밑에서 generateNewAddress 로 태어나는 순수 EVM 주소다. 발급된 주소를 다시 부를 때만 조회(addressOf)를 쓴다 — 조회와 발급은 다른 동사고(13.3), addressOf 는 절대 새 주소를 만들지 않는다. 13. 추상화 의 AccountPort 가 하는 일이다. 키·서명·주소 파생은 전부 Fireblocks vault·MPC 안에서 일어나고, 우리 쪽엔 계정↔주소 매핑 한 줄만 남는다.

9.1 표준 흐름

  1. 비즈니스 레이어 — 인증·KYC·자격 확인(업무 판단) 후 Service 백엔드 게이트웨이에 "지갑 개설 (고객 ref · asset)" 한 요청 + 멱등 키. 비즈 레이어는 업무 언어 한 문장만 말한다.
  2. 게이트웨이 (인증·멱등) — 호출 시스템 인증과 멱등 키 확인. 처리된 키면 저장된 결과를 즉시 반환한다.
  3. 유스케이스 서비스 — 그 한 요청을 두 포트 호출로 푼다: createAccount(ref)(= Fireblocks createVaultAccount) → 첫 주소 발급 issueDepositAddress(= Fireblocks generateNewAddress — 9.2 표). 이후 같은 주소를 다시 볼 때만 addressOf 조회.
  4. 계정 디렉터리 저장(계정↔주소 매핑) — 여기까지가 발급이다. Fireblocks 채택 경로에선 vault 가 곧 감시 범위라 별도 인덱서 등록이 없다(9.4).
  5. 결과를 멱등 레코드에 저장하고 비즈 레이어로 반환 — 재시도가 와도 계정·주소가 두 번 만들어지지 않는다.
이 흐름의 불변식 3개
  • 묶음 멱등 — 두 포트 호출 묶음 전체에 멱등 키 하나가 걸린다. 계정만 생기고 중단돼도 같은 키 재시도가 이어서 재개한다.
  • 역할 분담 — 비즈 레이어 = 업무 언어·최종 사용자 인증·KYC / 게이트웨이 = 호출 시스템 인증·멱등(중복 차단)만 — 두 "인증" 은 다른 것이다 / 유스케이스 = 포트 호출 순서·재개의 오케스트레이션.
  • 키는 우리 것이 아니다 — createAccount 가 만든 vault 의 키는 Fireblocks vault·MPC 안에 있다. 우리 쪽엔 키 트리도 HSM 도 없고, 계정↔주소 매핑 한 줄만 남는다.

구체 시퀀스 그림은 어댑터 장에 있다 — Figure 14-2a(Fireblocks 계정·주소 발급). 그 그림의 파란 상자는 프로세스(실패) 경계고 — 상자를 넘는 화살표에서만 부분 실패·중복이 생겨 멱등이 필요하다 — 레이어(교체) 경계는 AccountPort 어댑터부터 블록체인 매니저 영역(13.1)이다. 서로 다른 두 경계다.

9.2 Fireblocks 어댑터 구현 (EVM)

매니저로 Fireblocks 를 채택했으므로 createAccount·주소 발급은 벤더의 두 API 호출로 채워진다. 이더리움과 Base 는 같은 EVM 이라 동사·경로가 동일하다 — 체인만 바뀐다.

포트 동사Fireblocks 표면하는 일
createAccount(ref)fb.createVaultAccount(ref)고객당 한 번. vault(논리적 계정 단위) 하나를 만든다 — 체인에 안 나가고 주소도 아직 없다. 키는 Fireblocks vault·MPC 소관(14.2)
issueDepositAddress(account, asset)fb.generateNewAddressvault 밑에 순수 EVM 주소 하나를 발급(부를 때마다 새 주소 — 14.3). EVM 은 memoTag 가 없어 Address(value, memoTag=null) 다. 곡선·경로·인코딩 차이는 Fireblocks 가 흡수
addressOf(account, asset)vault 주소 목록 조회이미 발급된 주소의 조회 — 새 주소를 만들지 않는다

ERC-20 토큰은 ETH 와 같은 주소를 쓴다 — 파생의 실제 단위는 asset 이 아니라 chain 이라, 한 EVM 체인 안에서 주소는 계정만의 함수다. 이더리움용·Base용 vault 를 따로 만들지 않는다 — createAccount(ref) 시그니처에 asset 인자가 없다는 것이 그 증거다(워크스루 1장). 이 체인 차이 흡수는 전부 Fireblocks 매니저 안(2. 체인 차이 흡수 — EVM)에서 끝난다 — 우리는 곡선·xpub·파생 경로를 다루지 않는다.

9.3 주의

  • 승인 게이트가 아님(보통) — 계정·주소 발급은 프로비저닝이라 출금 같은 다자 승인이 보통 필요 없다. 단 인증·KYC(비즈 레이어)와 멱등 키(같은 온보딩 요청이 계정을 두 번 만들지 않게)는 필수.
  • 온체인 트랜잭션이 아님 — vault 생성도 EVM 주소 발급도 Fireblocks vault 내부 연산이라 체인에 tx 를 쓰지 않는다(전파·수수료 없음). EVM 주소는 순수 주소라 tag/memo 구분자가 필요 없다 — Address(value, memoTag=null).
  • 키는 어디에 — createAccount 가 키를 만들지만, 키 자체는 Fireblocks vault·MPC 안에 있고 매니저·게이트웨이는 만지지 않는다 (5. 서명 · co-signer).
  • 수탁 구조 선택은 비즈/회계 — "고객마다 별도 계정" vs "공용(omnibus) + 내부 장부 attribution(누구 몫인지 귀속)" 은 업무·회계 설계다. 매니저는 계정/주소 발급 primitive(기본 동작)만 제공. 단 규모는 매니저 설계에도 닿는다 — 은행 리테일처럼 고객이 수십만~수백만이면 "고객 1명 = vault 1개"(9.2 표의 createVaultAccount 1:1) 는 vault 수 폭발로 비용·rate limit·운영 부담이 커지므로, 대규모에선 공용 vault + 고객별 입금 주소 + 내부 attribution 구성을 함께 검토한다. 어느 쪽이든 매니저 쪽 차이는 계정·주소 매핑(계정 디렉터리)뿐이다.
  • 발급 결과는 백엔드의 계정 디렉터리에 — createAccount·issueDepositAddress/addressOf 의 결과(계정↔vaultId↔주소 매핑)는 지갑 서비스 백엔드가 계정 디렉터리로 저장·소유한다. 이후 모든 요청의 "계정 id → 계정" 해석은 게이트웨이가 이 디렉터리로 풀고, 벤더에 다시 물어보지 않는다 — 벤더를 교체해도 남는 우리 데이터다 (17. 프로젝트 구조 의 backend/directory).

9.4 발급된 주소는 어떻게 감시되나 — Fireblocks 는 vault 가 곧 감시 범위

입금을 감지하려면 "우리 주소 집합"이 알려져 있어야 한다. 매니저로 Fireblocks 를 채택했으므로 우리가 직접 인덱서를 돌려 watch-list 를 관리하지 않는다 — vault 가 곧 감시 범위다. 발급된 주소로의 입금은 Fireblocks 가 자동으로 감지해 webhook 으로 push 한다(14.5). 그래서 자체 인덱서 경로에서 흔한 등록 갭(발급과 watch-list 전파 사이에 입금이 도착해 누락되는 사고)이 이 경로에는 구조적으로 없다.

우리 몫은 webhook 수신기 하나

Fireblocks 채택 경로에서 발급-감지를 잇는 우리 책임은 webhook 수신기(Service 백엔드) 하나로 좁아진다 — vault 범위의 입금을 Fireblocks 가 감지해 통지하면, 수신기가 받아 매핑 DB 에 기록한다(10. 입금). 직접 노드·인덱서 운영, watch-list 전파, backfill 재스캔 같은 자체 구축의 짐은 벤더 안으로 들어간다. 다만 webhook 은 누락·지연·중복이 가능하므로, 회계의 최종 근거는 통지가 아니라 주기적 대사(벤더 잔액과 우리 기록의 대조)가 닫는다(7. 온체인 정합성 · 추적).
