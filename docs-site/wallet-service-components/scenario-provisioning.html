9. 계정·주소 발급 (온보딩)

고객 온보딩 시 createAccount · addressOf — 입금·출금에 앞선 사전 단계

입금(10)·출금(11)은 주소가 이미 있다는 전제로 시작한다. 그 주소를 만드는 게 이 단계 — 고객 온보딩(또는 새 자산 추가) 때 계정을 만들고(createAccount) 자산별 수신 주소를 확보한다. 확보의 동사는 체인이 정한다 — 발급 capability 가 있으면 첫 주소부터 발급(issueDepositAddress), 주소가 계정과 함께 태어나는 체인(Canton·NodeWallet)이면 조회(addressOf). 조회와 발급은 다른 동사고(13.3), addressOf 는 절대 새 주소를 만들지 않는다 — 등록(9.4)까지 끝난 주소를 반환할 뿐이다. 13. 추상화 의 AccountPort 가 하는 일이다.

표의 용어 — HD(하나의 시드에서 여러 주소를 계층적으로 파생하는 지갑 방식), xpub(개인키 없이 공개키만으로 하위 주소를 파생할 수 있는 확장 공개키), bip32(이 HD 파생 규칙을 정의한 표준, BIP-32). 경로(coin type · 비트코인 스크립트 유형별 BIP-44/49/84/86)와 주소 인코딩(keccak/EIP-55 · hash160/bech32 · base58)도 체인별이다. 그리고 ERC-20 토큰은 ETH 와 같은 주소를 쓴다 — 파생의 실제 단위는 asset 이 아니라 chain 이고, 포트의 issueDepositAddress(account, asset)·addressOf(account, asset) 구현은 asset→chain 매핑·xpub(coin type) 선택을 끝낸 뒤 체인 단위로 계산·조회한다. 그래서 한 겹 아래의 체인 어댑터 SPI(2.4)에는 asset 인자가 아예 없다 — 어댑터는 체인 고정이라, 한 체인 안에서 주소는 계정만의 함수다. 이 차이는 전부 멀티체인 어댑터(2.2 표 주소 파생 행)가 흡수한다.

9.3 주의

  • 승인 게이트가 아님(보통) — 계정·주소 발급은 프로비저닝이라 출금 같은 다자 승인이 보통 필요 없다. 단 인증·KYC(비즈 레이어)와 멱등 키(같은 온보딩 요청이 계정을 두 번 만들지 않게)는 필수.
  • 온체인 트랜잭션이 아님(보통) — 주소 확보는 로컬 키 연산(또는 vault 내부)이라 체인에 tx 를 쓰지 않는다(전파·수수료 없음). 유일한 예외가 Canton 의 party allocation(유료 온장 등록 — createAccount 소관). 주소 발급은 issueDepositAddress capability — 첫 주소부터 이 동사로 발급하며, UTXO·Fireblocks 처럼 되는 곳만 구현하고, Canton 처럼 없는 체인은 tag/memo(수신자 구분자)로 입금을 구분한다.
  • 키는 어디에 — createAccount 가 키를 만들지만, 키 자체는 어댑터 뒤(Fireblocks MPC / 자체 HSM / NodeWallet HSM)에 있고 매니저·게이트웨이는 만지지 않는다 (5. 서명).
  • 수탁 구조 선택은 비즈/회계 — "고객마다 별도 계정" vs "공용(omnibus) + 내부 장부 attribution(누구 몫인지 귀속)" 은 업무·회계 설계다. 매니저는 계정/주소 발급 primitive(기본 동작)만 제공. 단 규모는 매니저 설계에도 닿는다 — 은행 리테일처럼 고객이 수십만~수백만이면 "고객 1명 = vault 1개"(9.2 표의 createVaultAccount 1:1) 는 vault 수 폭발로 비용·rate limit·운영 부담이 커지므로, 대규모에선 공용 vault + 고객별 입금 주소 + 내부 attribution 구성을 함께 검토한다. 어느 쪽이든 매니저 쪽 차이는 계정·주소 매핑(계정 디렉터리)뿐이다.
  • 발급 결과는 백엔드의 계정 디렉터리에 — createAccount·addressOf/issueDepositAddress 의 결과(계정·주소 매핑)는 지갑 서비스 백엔드가 계정 디렉터리로 저장·소유한다. 이후 모든 요청의 "계정 id → 계정" 해석은 게이트웨이가 이 디렉터리로 풀고, 벤더에 다시 물어보지 않는다 — 벤더를 교체해도 남는 우리 데이터다 (17. 프로젝트 구조 의 backend/directory).

9.4 발급 주소는 인덱서에 알려져야 한다 — watch-list 등록과 backfill

인덱서(3)가 입금을 감지하려면 "우리 주소 집합"(isOurs 필터)이 있어야 하는데, 이 집합은 저절로 생기지 않는다 — 발급(이 장)과 감지(10장)를 잇는 등록 단계가 필요하다. 경로에 따라 책임이 다르다.

  • Fireblocks 단독 경로 — vault 가 곧 감시 범위라 별도 등록이 없다. 발급된 주소로의 입금은 Fireblocks 가 자동으로 webhook push 한다(14.5).
  • 자체 구축·하이브리드(13.4) 경로 — 주소의 발급처(AccountPort)와 감시자(자체 인덱서)가 다른 시스템이다. 발급 직후 watch-list 전파가 늦는 사이에 입금이 도착하면 그대로 누락된다 — 입금 사고에서 가장 흔한 유형이다.
등록 갭 방어 3종
  • 등록을 발급 흐름 안에 — issueDepositAddress(또는 주소가 계정과 함께 태어나는 Canton 의 createAccount)로 주소가 만들어지면 같은 흐름에서 인덱서 watch-list 에 등록하고, 등록 시점의 블록 높이를 함께 기록한다(Figure 9-1 의 Note). 등록 실패면 발급도 실패로 취급한다 — 감시 안 되는 주소를 고객에게 주지 않는다.
  • backfill 재스캔 — 등록 높이 이전 블록에 이미 입금이 있었을 수 있다(고객이 주소를 미리 받아 두거나, 등록 지연·장애 구간). 등록 시 해당 주소에 대해 과거 구간을 한 번 재스캔해 메운다 — 원시 로그를 보존하는 이유(3.2)가 여기서도 쓰인다.
  • xpub gap-limit 선파생 — 자체 HD 지갑(15장)이면 비트코인 지갑들의 관행처럼 아직 발급 안 한 주소를 gap limit 만큼 미리 파생해 감시 목록에 올려 둘 수도 있다 — 등록 타이밍 의존이 사라진다.
