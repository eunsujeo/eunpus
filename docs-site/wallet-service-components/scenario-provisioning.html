7. 계정·주소 발급 (온보딩)

고객 온보딩 시 createAccount · deriveAddress — 입금·출금에 앞선 사전 단계

입금(8)·출금(9)은 주소가 이미 있다는 전제로 시작한다. 그 주소를 만드는 게 이 단계 — 고객 온보딩(또는 새 자산 추가) 때 계정을 만들고(createAccount) 자산별 주소를 파생(deriveAddress) 한다. 11. 추상화 의 AccountPort 가 하는 일이다.

7.1 표준 흐름

sequenceDiagram
    autonumber
    participant U as 클라이언트
    participant BIZ as 비즈니스 레이어
    participant GW as API 게이트웨이
    participant ACC as AccountPort (어댑터)
    participant BK as 백엔드(Fireblocks/자체/NodeWallet)

    U->>BIZ: 지갑 개설 요청 (온보딩)
    Note over BIZ: 인증·KYC·자격 확인 (업무 판단)
    BIZ->>GW: createAccount(고객 ref) + 멱등 키
    GW->>ACC: createAccount(ref)
    ACC->>BK: 계정 생성 (vault / HD account)
    BK-->>ACC: accountId
    GW->>ACC: deriveAddress(account, asset)
    ACC->>BK: 주소 파생 (자산별)
    BK-->>ACC: address
    GW-->>BIZ: accountId · 입금 주소
    BIZ-->>U: 지갑·입금 주소 표시

Figure 7-1. 계정·주소 발급. 클라이언트 → 비즈니스 레이어(인증·KYC 판단) → 게이트웨이(멱등 키) → AccountPort.createAccount → deriveAddress → 어댑터가 백엔드(Fireblocks vault / 자체 HD / NodeWallet)로 번역. 발급된 주소로 받는 입금은 8. 입금. 이는 0.2 의 ① 호출(inbound) — 비즈 레이어가 게이트웨이를 부른다.

7.2 어댑터별 구현

같은 createAccount·deriveAddress 가 어댑터마다 이렇게 채워진다:

어댑터createAccountderiveAddress
Fireblocks (12)fb.createVaultAccount(ref)fb.generateNewAddress(vaultId, asset) (멀티체인 흡수)
자체 구축 (13)HD 지갑 account index 할당bip32.derive(xpub, path) — 우리가 파생
NodeWallet (14)nw.createWallet(ref, Chain.SOLANA)nw.address(wallet) (Solana 단일)

7.3 주의

  • 승인 게이트가 아님(보통) — 계정·주소 발급은 프로비저닝이라 출금 같은 다자 승인이 보통 필요 없다. 단 인증·KYC(비즈 레이어)와 멱등 키(같은 온보딩 요청이 계정을 두 번 만들지 않게)는 필수.
  • 온체인 트랜잭션이 아님 — 주소 파생은 로컬 키 연산(또는 vault 내부)이라 체인에 tx 를 쓰지 않는다(전파·수수료 없음). UTXO·tag/memo 자산은 추가 입금 주소를 더 발급할 수 있다.
  • 키는 어디에 — createAccount 가 키를 만들지만, 키 자체는 어댑터 뒤(Fireblocks MPC / 자체 HSM / NodeWallet HSM)에 있고 매니저·게이트웨이는 만지지 않는다 (5. 서명).
  • 수탁 구조 선택은 비즈/회계 — "고객마다 별도 계정" vs "공용(omnibus) + 내부 장부 attribution" 은 업무·회계 설계다. 매니저는 계정/주소 발급 primitive 만 제공.
