1. 컴포넌트 개요

8 컴포넌트를 한눈에 — 책임 · 경계 · 어디서 자세히 보는가

컴포넌트를 나누는 기준은 "기능" 이 아니라 책임 경계다. 즉 "무엇을 결정하고, 무엇을 받기만 하고, 어디서 외부와 맞닿는가" 로 나눈다. 경계가 분명해야 한 컴포넌트의 장애나 변경이 다른 컴포넌트로 번지지 않는다.

1.1 컴포넌트 한눈에 보기

컴포넌트한 줄 책임상세
API 게이트웨이외부 요청을 받아 인증하고, 같은 요청이 두 번 실행되지 않게 멱등 키?를 부여해 내부로 라우팅아래 1.3
멀티체인 어댑터체인마다 다른 규칙(계정/UTXO?, 확정 방식, 수수료)을 매니저 내부의 한 가지 인터페이스로 정규화2. 상세
인덱서체인 데이터를 수집·가공(projection?)해 입금 감지·확정 판단·조회·알림의 근거를 만든다3. 상세
트랜잭션 빌더 · Nonce/Broadcast출금 트랜잭션을 조립하고, 순번(nonce?·UTXO)을 관리하며, 전파하고, 막히면(stuck) 재전송4. 상세
서명 오케스트레이션조립된 트랜잭션을 외부 서명자(MPC/HSM/co-signer)에게 보내 서명을 받아오는 경계. 키 자체는 보관하지 않는다5. 상세
원장 정합성 · 대사체인 위 사실과 내부 장부를 요청 ID 기준으로 맞춰 보고, 불일치를 잡아낸다6. 상세
온/오프램프 커넥터법정화폐 쪽 시스템(은행·PG·거래소)과의 입출금 연동 경계아래 1.3
이벤트 · 알림입금·확정·출금 완료 등 상태 변화를 외부에 push(webhook/스트림)아래 1.3

무게가 큰 5 컴포넌트(멀티체인 어댑터 · 인덱서 · 트랜잭션/Nonce/Broadcast · 서명 · 원장)는 전용 상세 페이지에서 "왜 필요 / 어떻게 동작 / 내부 flow / 다른 컴포넌트가 어떻게 쓰는지" 를 깊게 다룬다. 나머지 셋(API 게이트웨이 · 온오프램프 · 알림)은 비교적 얇고 시나리오에서 동작이 드러나므로 여기서 짧게 정리한다.

1.3 가벼운 세 컴포넌트

API 게이트웨이

왜 필요
모든 요청의 단일 진입점. 인증·rate limit 과 멱등 키로 "재시도해도 한 번만 실행" 을 보장하는 곳. 이게 없으면 네트워크 재시도가 곧바로 이중 출금으로 이어진다.
하는 일
입금 주소 발급, 출금 요청, 잔액/상태 조회를 받아 트랜잭션 빌더(쓰기)·원장(조회)·온오프램프(램프)로 라우팅. 비즈니스 판단은 안 한다.
경계
얇게 유지 — 로직은 뒤 컴포넌트로 위임.

온/오프램프 커넥터

왜 필요
법정화폐 세계와 체인 세계는 확정 시점·되돌림 가능성이 다르다. 두 흐름의 순서와 증빙을 안전하게 잇는 전담 경계가 필요하다.
하는 일
은행·PG·거래소 API 와 연동해 fiat 확정을 확인하고, 체인 쪽 흐름(출금/입금 컴포넌트)과 settle-then-pay 순서로 잇는다.
경계
fiat 정산 자체는 외부 기관. 자세한 두 방향 흐름은 9. 온·오프램프 참조.

이벤트 · 알림

왜 필요
상위 서비스·고객이 폴링하지 않고도 입금·확정·출금 완료를 즉시 알 수 있어야 한다.
하는 일
인덱서·트랜잭션·원장의 상태 변화를 webhook/스트림으로 push. 재시도·순서·서명 검증.
경계
상태를 만들지 않고 전달만 한다. 멱등 전달(같은 이벤트 중복 수신 대비)을 소비자에게 보장.
범위 밖 (다시 강조)

출금 승인·한도(정책), 제재·이상거래(컴플라이언스), 준비자산 운용(자금)은 매니저가 결정하지 않는다. 매니저는 이들이 내린 승인/거부/제한 신호를 입력으로 받아 트랜잭션 빌더(전파 차단·보류)나 API 게이트웨이(요청 거부)에서 집행만 한다. 시나리오 다이어그램에서 이 신호는 점선으로 표시한다.
