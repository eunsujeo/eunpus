6. API 게이트웨이

외부 요청의 단일 입구 — 인증하고, 멱등 키를 부여해 "같은 요청이 두 번 실행되지 않게" 한다

6.1 왜 필요한가

매니저가 하는 일은 대부분 되돌릴 수 없다 — 한 번 전파된 출금 트랜잭션은 취소가 안 된다. 그런데 외부 채널(앱·PG?·은행 코어)은 네트워크 오류나 타임아웃 때 같은 요청을 재시도하고, 사용자는 버튼을 두 번 누른다. 이 중복이 그대로 실행되면 이중 출금·이중 지급이 된다.

API 게이트웨이는 모든 외부 요청이 지나는 단일 입구로서 (1) 누구의 요청인지 인증하고, (2) 요청마다 멱등? 키를 붙여 같은 요청이 두 번 집행되지 않게 막은 뒤, (3) 적절한 포트로 라우팅한다.

한 문장 요약

API 게이트웨이 = "외부의 중복·재시도를 흡수해, 되돌릴 수 없는 작업이 정확히 한 번만 실행되게 하는 입구". 멱등이 곧 이중 지급 방지다.

6.3 코드로 보면

설명용 의사코드다. 핵심은 멱등 저장소 — 요청 키별로 "진행 중 / 완료(결과)" 상태를 기록해, 중복·동시 요청을 한 번으로 모은다.

class ApiGateway {
  constructor(auth, idem, manager) {}   // manager = 포트(Account/Transaction)

  async handle(req) {
    const who = await this.auth.verify(req)            // ① 인증 (실패면 거절)
    const key = req.idempotencyKey ?? derive(req)      // ② 멱등 키 = 요청 ID

    const prior = await this.idem.get(key)
    if (prior?.done)     return prior.result           // 이미 처리 → 같은 결과 반환
    if (prior?.inflight) return await this.idem.join(key)  // 동시 중복 → single-flight? 로 합류

    await this.idem.start(key, LEASE_TTL)              // 진행 중 표시 — 원자적 조건부 insert (경합 차단)
                                                       //   + lease(TTL): 처리하던 인스턴스가 죽어도 영구 inflight 로 고착되지 않게
    try {
      const result = await this.route(who, req)        // ③ 포트 호출 (예: submitTransaction(req))
      await this.idem.complete(key, result)            // 결과 저장 (이후 중복은 캐시 반환)
      return result
    } catch (e) {
      await this.idem.fail(key, e)                     // 실패도 기록 (무한 재시도 방지)
      throw e
    }
  }
}
멱등 키는 게이트웨이에서 끝나지 않는다 — 끝까지 따라간다

게이트웨이가 부여한 멱등 키는 아래로 계속 전달된다 — 4. 트랜잭션의 store.byIdempotencyKey 로, 다시 어댑터를 거쳐 Fireblocks 의 externalTxId 같은 dedup(중복 제거) 키로 이어진다(13.7). 그래서 게이트웨이에서 한 번 막아도, 그 키가 체인 제출 단계까지 살아 있어야 "정확히 한 번" 이 끝까지 보장된다.

6.4 다른 컴포넌트와의 관계

관계내용
← 비즈니스 레이어 · 클라이언트모든 외부 요청을 여기로 받는다 (인증·멱등의 단일 입구).
→ 블록체인 매니저 포트인증·멱등을 통과한 요청만 13. 포트(AccountPort·TransactionPort)로 라우팅.
→ 4. 트랜잭션멱등 키를 넘겨 체인 제출 단계의 dedup(externalTxId)으로 잇는다.
↔ 7. 온체인 정합성같은 요청 ID(correlationId)로 처리 상태·정합성 조회를 제공·연결.
설계 포인트
  • 벤더·체인 무관 — 게이트웨이는 지갑 서비스 백엔드 층이라 Fireblocks 든 자체 구축이든 그대로 우리 것이다(13.7).
  • 멱등 키 정책 — 클라이언트가 주거나(권장), 없으면 요청 내용으로 안정적으로 파생. 같은 의미의 요청이 같은 키가 되도록.
  • 점유는 원자적으로 — 조회(get)와 진행 중 표시(start) 사이에 다른 요청이 끼지 않도록, start 는 멱등 저장소의 원자 연산(DB unique 제약·조건부 insert)이어야 한다. 게이트웨이는 보통 여러 인스턴스로 뜨므로 멱등 저장소도 인스턴스 간 공유 저장소여야 하고, 인메모리 single-flight 만으로는 인스턴스를 넘는 중복을 못 막는다.
  • inflight 는 임대(lease)로 — start 직후 그 인스턴스가 죽으면 키가 영원히 "진행 중" 으로 남아 정당한 재시도까지 막힌다. inflight 표시에 TTL 을 둬 만료 후 재실행을 허용하되, 재실행 전 4.3 의 intent 기록을 먼저 확인한다 — "이미 전파됐을 수 있음" 단계라면 새로 만들지 않고 거기서 이어간다.
  • 실패도 기록 — 실패를 멱등 저장소에 남겨, 같은 키의 무한 재시도와 "실패인데 또 실행" 을 막는다. 이때 타임아웃 같은 일시 오류(재시도 가능)와 검증 실패 같은 확정 실패(재시도해도 같은 결과)를 구분해 기록한다 — 전자는 정당한 재시도를 허용하고, 후자만 같은 키의 재실행을 차단한다.
