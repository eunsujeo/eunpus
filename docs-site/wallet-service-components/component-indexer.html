3. 인덱서

체인 데이터를 어떻게 수집하고 · 가공하고 · 보여주는가 — 모든 읽기의 토대
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

3.1 왜 필요한가

노드와 RPC 만으로는 지갑 서비스가 필요한 질문에 잘 답하지 못한다. RPC 는 "이 tx 해시의 내용" 은 주지만, "이 주소가 받은 입금 목록", "지금 잔액", "과거 어느 시점 잔액", "방금 입금 들어왔다는 알림" 은 그대로 주지 못하거나 너무 느리다.

인덱서는 체인 데이터를 미리 조회하기 좋은 형태로 가공해 두고, 수신 트랜잭션(입금)을 감지하고, 확정 여부를 판단해, 매니저의 다른 컴포넌트가 빠르고 정확하게 읽을 수 있게 한다. 즉 인덱서는 "체인과 애플리케이션 사이의 데이터 운영체제" 다.

Figure 3-1. 인덱서 파이프라인. 파랑 = 원시 보존(불변), 보라 = 변환, 초록 = 제공. ②원시와 ③projection 의 분리가 핵심 — reorg 가 나도 원시로부터 projection 을 다시 만들면 된다.

① 수집(ingestion) — pull + push 하이브리드

두 방식을 섞는다. push 스트림(Geyser?·Firehose?)은 새 블록을 즉시 받아 지연이 낮지만, 연결이 끊기면 구멍이 난다. pull 폴링(RPC)은 느리지만 빠진 구간을 메우고 과거 데이터를 backfill 할 수 있다. 둘을 합쳐 "빠르되 빠짐 없는" 수집을 만든다.

② 원시 보존(raw, append-only)

받은 블록·로그를 가공 전 원본 그대로 append-only 로 쌓는다. 절대 덮어쓰거나 지우지 않는다. 이게 있어야 가공 로직이 바뀌거나 reorg 가 나도 다시 만들 수 있다.

③ 가공(projection) — 멱등 변환

원시 로그에서 우리 주소와 관련된 것만 골라 디코딩하고(예: ERC-20 Transfer 이벤트 → 입금 레코드), 잔액·입금 목록·이력 같은 조회용 테이블을 만든다. 같은 이벤트를 두 번 처리해도 결과가 같도록 (tx 해시 + logIndex) 를 키로 멱등하게 쓴다. 각 레코드에는 "어느 블록 기준(as-of-block)" 인지 남긴다.

④⑤ 저장·제공

가공 결과를 조회 저장소에 넣고, 조회 API(잔액·입금·이력)와 알림 트리거(입금 감지/확정)로 제공한다. 수집 부하와 조회 부하가 서로를 무너뜨리지 않도록 두 평면을 분리한다.

3.3 확정(finality) 판단과 reorg 처리

인덱서의 가장 어려운 부분은 "감지" 와 "확정" 을 구분하고, 체인 끝이 교체되는 reorg 를 견디는 것이다. (확정 기준 자체는 멀티체인 어댑터가 체인별로 제공한다.)

3.4 코드로 보면

설명용 의사코드다. 핵심은 두 겹으로 나뉜다 — 수집(ingest)은 체인마다 다르므로 멀티체인 어댑터(2) 뒤의 ChainSource 가 맡고, 가공·projection·롤백·제공은 체인 무관이라 인덱서 본체가 맡는다. 인덱서는 source 가 주는 정규화된 이벤트만 받는다.

// ── ① 수집은 체인별 — 멀티체인 어댑터(2) 뒤에 산다 ──
// reorg "감지" 까지가 체인별. 블록·slot·ACS 어느 모델이든 같은 정규화 이벤트로 뱉는다.
interface ChainSource {
  // 정규화 이벤트: { kind:'tx'|'confirm'|'reorg', raw, tx?, ref?, level?, fork? }
  stream(cursor): AsyncIterable<NormalizedEvent>
}
//  EvmSource    : 블록 폴링, parentHash 불일치로 reorg 판정
//  UtxoSource   : 블록 폴링(+mempool), 동일 reorg 모델
//  SolanaSource : slot 구독 + commitment(processed→confirmed→finalized)
//                 finalized 기준이면 reorg 없음 — confirmed 이하 레벨로 인덱싱하면 롤백 가능
//  CantonSource : participant/ACS 업데이트 구독 — 블록·nonce·reorg 개념 자체가 없음

// ── ② 가공·projection·제공은 체인 무관 — 인덱서 본체 ──
class SelfIndexer {
  constructor(sources, raw, proj, bus) {}   // sources[chainId] = 위 ChainSource

  // 체인마다 한 루프. 수집 방식은 source 가 흡수하고, 여기선 정규화 이벤트만 처리.
  async run(chainId) {
    const source = this.sources[chainId]
    for await (const ev of source.stream(await this.proj.cursor(chainId))) {
      await this.raw.append(ev.raw)           // ② 원시 보존 — 모든 수신 이벤트 (append-only)
      switch (ev.kind) {
        case 'tx':      await this.ingest(ev); break
        case 'confirm': await this.proj.mark(ev.ref, ev.level); break   // 확정 기준은 source 가 판정
        case 'reorg':   await this.proj.rollbackTo(ev.fork); break      // 처리는 공통 (raw 보존)
      }
    }
  }

  // 가공 — 정규화된 ev 만 본다 (체인 무관)
  async ingest(ev) {
    if (!this.isOurs(ev.tx)) return           // "우리 주소" 집합 — 발급(9.4) 때 watch-list 등록으로 생긴다
    await this.proj.upsert(ev.tx, 'pending')
    this.bus.emit(toChainEvent(ev.tx))        // onChainEvent (감지 → 코어로 push)
  }                                           //   upsert↔emit 사이 사망 = 알림 유실 가능 — 아래 bullet

  // ── 읽기/구독 = 13장 포트의 뒷면 (체인 무관) ──
  balanceOf(addr, asset) { return this.proj.balance(addr, asset) }      // AccountPort.getBalance
  confirmationOf(txRef) { return this.proj.confirmations(txRef) }      // TransactionPort.getStatus
  query(filter) { return this.proj.select(filter) }           // ChainQueryPort.query (임의 조회)
  subscribe(addrs, handler) { return this.bus.on(addrs, handler) }        // TransactionPort.onChainEvent
}
코드가 말하는 것
  • 수집은 체인마다 다르다 → 어댑터 뒤로 — EVM·UTXO 는 블록 폴링, Solana 는 slot+commitment, Canton 은 participant/ACS 구독이다. 이 차이(+ reorg 감지)는 ChainSource 가 흡수하고, 인덱서엔 정규화 이벤트(tx/confirm/reorg)만 올라온다. 그래서 인덱서 본체 코드는 체인이 늘어도 안 바뀐다.
  • reorg 는 감지(체인별)와 처리(공통)가 갈린다 — parentHash·slot 으로 분기를 알아채는 건 source, 알아챈 뒤 proj.rollbackTo 로 projection 만 되감고 보존된 raw 로 재적용하는 건 공통(영구 삭제 금지, 3.3).
  • 확정 기준도 인덱서가 정하지 않는다 — N블록/commitment/2-step 판정은 source(어댑터)가 confirm 이벤트로 알려주고, 인덱서는 mark 만 한다.
  • 수집 루프는 상시 worker — 아무도 안 불러도 계속 돈다(0.2 의 "감지"). 끊기면 입금·확정을 놓친다.
  • "우리 주소" 는 등록의 산물 — isOurs 의 주소 집합은 발급(9.4) 때 watch-list 등록으로 채워지고, 등록 지연·이전 입금은 backfill 재스캔으로 메운다. 이 등록 경로가 빠지면 인덱서는 멀쩡히 돌면서 입금만 놓친다.
  • 발행 유실 주의 — proj.upsert 와 bus.emit 사이에 죽으면 projection 엔 있는데 알림만 안 나간 건이 생긴다. 엄밀히 가려면 projection 쓰기와 이벤트 기록을 한 트랜잭션에 묶는 outbox 패턴을 쓰고, 그게 아니면 최소한 7.5 의 주기 sweep 이 "알림 안 나간 확정 건" 을 다시 잡는 안전망임을 운영 계약으로 명시한다.
  • 읽기 4개가 포트 뒷면 — balanceOf·confirmationOf·query·subscribe 가 13장의 getBalance·getStatus·ChainQuery.query·onChainEvent 를 받친다(자체 구축 15장 Figure 15-4).

즉 Canton 처럼 블록도 nonce 도 reorg 도 없는 체인이 와도, 다른 건 CantonSource 하나뿐이고 SelfIndexer 본체는 그대로다 — 이게 "수집은 체인별, 가공·제공은 공통" 의 핵심.

그럼 ingest 할 때 무엇으로 정규화하나? 체인마다 data 엔터티가 다르다 — EVM 은 nonce·gas, UTXO 는 vin·vout, Canton 은 transactionType·traceableId. 위 코드의 ev.tx 가 바로 그 정규(canonical) 모델이다. 공통 핵심 + 체인별 typed 확장 + raw 포인터로 잡으면, "체인마다 다른 엔터티" 가 위층 소비자에게 새지 않는다.

// ingest 단계: ChainSource 가 raw → 이 정규 Transaction 으로 매핑한다
type Transaction = {
  // ── 공통 핵심 (모든 체인 동일 · 소비자 대부분이 보는 것) ──
  id; status; asset; amount; from; to; fee; confirmations; ts

  // ── 체인별 typed 확장 (어댑터가 채움 — 지우지 않고 격리) ──
  chainSpecific:
    | { model: 'evm';    nonce; gas; evmTransferType }
    | { model: 'utxo';   vin; vout; feePerByte }
    | { model: 'canton'; transactionType; traceableId }    // 2-step

  extra?     // 정규 필드로 못 담는 임의 페이로드 (탈출구)
  rawRef     // raw store 포인터 — 원본은 절대 버리지 않는다
}
체인마다 다른 data 엔터티 — 정규화 패턴 (Fireblocks 도 같은 방식)
  • 공통은 통일, 차이는 typed 로 격리 — 잔액·상태·금액 같은 공통 핵심은 한 모양으로, 체인 고유 필드는 chainSpecific 에 typed 로. projection 쿼리는 공통 핵심만 보면 되고, 체인 세부가 필요한 소수만 chainSpecific 을 연다.
  • status 는 단일 enum, 2-step 은 확장으로 — Canton 의 OFFER/ACCEPT 같은 lifecycle 은 chainSpecific.transactionType 으로 두고 공통 status 와 매핑한다(정확한 매핑은 적용 전 확인 필요).
  • raw 는 절대 안 버린다 — 정규로 못 담은 체인 엔터티도 rawRef 로 복원 가능. reorg 재적용(3.3)도 이 raw 덕분.
  • 새 체인 = 확장 variant 하나 추가 — 공통 핵심·소비자 코드는 그대로. "수집은 체인별, 모델은 공통+확장" 이 여기서도 똑같이 적용된다.

이건 Fireblocks 가 실제로 쓰는 방식과 같다 — 공통 Transaction 객체 + 체인별 typed 필드(BlockchainInfo: evmTransferType·transactionType·substrateExtrinsicId 등) + 정규로 못 담는 것 위한 extraParameters 탈출구. 매핑은 멀티체인 어댑터(2)가, 자산 단위·소수점·주소 정규화는 7. 온체인 정합성·추적이 맡는다.

인덱서 설계 3 원칙
  • 원시는 불변 — append-only, 삭제 금지. projection 은 재구성 가능한 캐시로 취급.
  • 확정을 계약으로 — "이 데이터가 어느 확정 수준인지" 를 조회/알림에 함께 노출해 소비자가 판단하게 한다.
  • 질의 분리 — 수집과 질의를 분리해 한쪽 부하가 다른 쪽을 무너뜨리지 않게.
  • 후속 이벤트는 감지 시점 상태로 보강 — 확정·reorg 같은 후속 이벤트에는 tx 참조만 실려 온다. 알림에 필요한 주소·금액은 인덱서가 감지(PENDING) 시점에 적어 둔 상태로 보강하며, 재기동 후에는 원시 보존분(raw) 재적용으로 그 상태를 복원할 수 있어야 한다 — 원시 불변 원칙이 복구의 전제다.
