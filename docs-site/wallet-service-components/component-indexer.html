3. 인덱서

체인 데이터를 어떻게 수집하고 · 가공하고 · 보여주는가 — 모든 읽기의 토대

3.1 왜 필요한가

노드와 RPC 만으로는 지갑 서비스가 필요한 질문에 잘 답하지 못한다. RPC 는 "이 tx 해시의 내용" 은 주지만, "이 주소가 받은 입금 목록", "지금 잔액", "과거 어느 시점 잔액", "방금 입금 들어왔다는 알림" 은 그대로 주지 못하거나 너무 느리다.

인덱서는 체인 데이터를 미리 조회하기 좋은 형태로 가공해 두고, 수신 트랜잭션(입금)을 감지하고, 확정 여부를 판단해, 매니저의 다른 컴포넌트가 빠르고 정확하게 읽을 수 있게 한다. 즉 인덱서는 "체인과 애플리케이션 사이의 데이터 운영체제" 다.

Figure 3-1. 인덱서 파이프라인. 파랑 = 원시 보존(불변), 보라 = 변환, 초록 = 제공. ②원시와 ③projection 의 분리가 핵심 — reorg 가 나도 원시로부터 projection 을 다시 만들면 된다.

① 수집(ingestion) — pull + push 하이브리드

두 방식을 섞는다. push 스트림(Geyser?·Firehose?)은 새 블록을 즉시 받아 지연이 낮지만, 연결이 끊기면 구멍이 난다. pull 폴링(RPC)은 느리지만 빠진 구간을 메우고 과거 데이터를 backfill 할 수 있다. 둘을 합쳐 "빠르되 빠짐 없는" 수집을 만든다.

② 원시 보존(raw, append-only)

받은 블록·로그를 가공 전 원본 그대로 append-only 로 쌓는다. 절대 덮어쓰거나 지우지 않는다. 이게 있어야 가공 로직이 바뀌거나 reorg 가 나도 다시 만들 수 있다.

③ 가공(projection) — 멱등 변환

원시 로그에서 우리 주소와 관련된 것만 골라 디코딩하고(예: ERC-20 Transfer 이벤트 → 입금 레코드), 잔액·입금 목록·이력 같은 조회용 테이블을 만든다. 같은 이벤트를 두 번 처리해도 결과가 같도록 (tx 해시 + logIndex) 를 키로 멱등하게 쓴다. 각 레코드에는 "어느 블록 기준(as-of-block)" 인지 남긴다.

④⑤ 저장·제공

가공 결과를 조회 저장소에 넣고, 조회 API(잔액·입금·이력)와 알림 트리거(입금 감지/확정)로 제공한다. 수집 부하와 조회 부하가 서로를 무너뜨리지 않도록 두 평면을 분리한다.

3.3 확정(finality) 판단과 reorg 처리

인덱서의 가장 어려운 부분은 "감지" 와 "확정" 을 구분하고, 체인 끝이 교체되는 reorg 를 견디는 것이다. (확정 기준 자체는 멀티체인 어댑터가 체인별로 제공한다.)

인덱서 설계 3 원칙
  • 원시는 불변 — append-only, 삭제 금지. projection 은 재구성 가능한 캐시로 취급.
  • 확정을 계약으로 — "이 데이터가 어느 확정 수준인지" 를 조회/알림에 함께 노출해 소비자가 판단하게 한다.
  • 질의 분리 — 수집과 질의를 분리해 한쪽 부하가 다른 쪽을 무너뜨리지 않게.

인덱서를 직접 만들지, The Graph·SQD·Alchemy 같은 외부를 쓸지는 10. 추상화 에서 Port 로 다룬다. 다음 — 4. 트랜잭션 · Nonce · Broadcast.
