3. 입금 감지 — Fireblocks webhook

우리는 인덱서를 운영하지 않는다 — Fireblocks 가 감지·통지하고, 우리 수신기가 받는다
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

우리는 인덱서를 만들지 않는다

Fireblocks 를 채택하면 체인 데이터를 긁어 잔액·입금 목록을 만드는 인덱서는 벤더 안에서 돈다. 우리 쪽엔 상시 인덱서도, 노드 폴링도 없다. Fireblocks 가 자기 vault 범위의 입금을 감지해서 webhook 으로 밀어주고, 우리 몫은 그걸 받는 webhook 수신기(Service 백엔드)와 매핑 DB 하나다. 그래서 이 장은 "우리가 인덱서를 어떻게 만드나" 가 아니라 "벤더가 준 입금 통지를 우리가 언제부터 잔액으로 믿나" 를 그린다.

3.1 무엇이 문제인가 — 감지 ≠ 확정

출금과 달리 입금은 우리가 시작하지 않는다. 외부 송신자가 보내고 우리는 그걸 알아채야 한다. 그 감지·통지를 벤더가 대신해 주므로, 이 장의 질문은 하나로 좁혀진다 — 언제부터 이 입금을 잔액으로 믿는가.

답은 "감지 ≠ 확정" 이다. 체인에 트랜잭션이 등장했다고 곧 확정(finality?)은 아니다. Fireblocks 는 이 둘을 상태값으로 명확히 갈라 준다 — CONFIRMING(체인 등장, 미확정)과 COMPLETED(DCCP 임계 도달, 확정)다.

onChainEvent(handler)   // Fireblocks webhook 이 입금의 상태 변화를 push 한다
                        //   CONFIRMING = 체인에 등장, confirmation 누적 중 (아직 미확정)
                        //   COMPLETED  = DCCP 임계 confirmation 도달 = finality (확정)
이 페이지가 붙잡는 구분 — confirm(체인 등장) vs finality(확정)

입금 하나의 상태는 Fireblocks 안에서 BROADCASTING → CONFIRMING → COMPLETED 순으로 흐른다. 이 중 우리가 잔액을 움직일 때 붙잡아야 할 두 지점이 CONFIRMING 과 COMPLETED 다.

CONFIRMING = confirm 상태. 트랜잭션이 체인에 올라가 블록에 담겼고 그 위로 confirmation 이 쌓이는 중이다 — 하지만 아직 확정 아님. 이 단계의 자금은 고객에게 "확인 중" 으로만 보여주고 available 잔액에는 넣지 않는다.

COMPLETED = finality 상태. confirmation 이 DCCP(확정 정책)가 정한 임계 수에 도달했다는 뜻이고, 이때부터 이 입금을 확정으로 보고 available 에 반영한다. 둘을 프로그램으로 가르는 방법은 두 가지다 — status 값(CONFIRMING 인지 COMPLETED 인지)으로 갈리거나, tx 객체의 numOfConfirmations(실제 누적 confirmation 수)를 우리 finality 임계값과 비교한다.

Figure 3-1. 입금 감지 흐름. 우리 쪽에 상시 인덱서는 없다 — Fireblocks(초록)가 감지·통지를 맡고, 우리 몫은 webhook 수신기(Service)가 받아 매핑 DB 에 기록하는 inbound 경로 하나다. 핵심은 두 통지의 성격 차이다 — CONFIRMING(체인에 등장, confirmation 누적 중, 아직 미확정)에서는 기록만 하고, COMPLETED(DCCP 임계 confirmation 도달 = finality)에서만 available 잔액을 올린다. ERC-20 토큰 입금도 별도 주소가 생기는 게 아니라 같은 주소로 오는 토큰 전송이라 같은 경로를 탄다. webhook 은 누락·지연·중복이 가능하므로 통지는 힌트로만 보고, 회계의 최종 근거는 주기적 대사가 닫는다.

3.3 DCCP — 무엇이 CONFIRMING 을 COMPLETED 로 바꾸나 (설정=Admin)

CONFIRMING 에서 COMPLETED 로 넘어가는 임계 confirmation 수를 정하는 정책이 DCCP?(Deposit Control and Confirmation Policy)다. 이 문서가 말하는 "finality" 는 체인이 자연히 주는 성질이 아니라 DCCP 가 정의하는 확정 기준이다. DCCP 는 운영·거버넌스 영역이라 그 설정·임계값 관리는 Admin 백엔드의 몫이고, 실제 입금 이벤트를 받아 잔액에 반영하는 런타임은 Service 백엔드의 몫이다 — 정하는 쪽과 쓰는 쪽이 갈린다.

DCCP 임계값 — 기본값과 커스텀 (설정 주체 = Admin)

Fireblocks 의 DCCP 기본 임계 confirmation 수는 체인마다 다르다.

  • 대부분의 체인 = 1 — 블록 하나면 확정으로 본다.
  • ETC(이더리움 클래식) = 372 — 과거 reorg 리스크가 커 임계가 매우 높다.
  • finality 속성을 가진 체인 — 체인별로 고정(rigid)된 값을 쓴다.
  • 컨트랙트 호출(contract call) = 최소 3 권장 — 단순 전송보다 보수적으로.

이 값은 커스텀 DCCP 로 조정할 수 있고, 조정 권한과 책임은 Admin 에 둔다. 우리 EVM 대상(이더리움·Base)에서 어떤 임계를 쓸지는 자산·리스크 정책에 따라 Admin 이 정하고, Service 는 그 결과로 도착한 COMPLETED 만 신뢰하면 된다.

함정 — 첫 COMPLETED 를 곧 finality 로 단정하지 말 것 (zero-confirmation)

Deposit Policy 를 zero-confirmation 으로 두면, COMPLETED 가 블록에 등장하는 시점에 먼저 뜰 수 있고 이후 webhook 이 여러 번(등장 + 1차 confirm + 추가 confirm) 더 올 수 있다. 즉 이 설정에서는 "COMPLETED webhook 을 처음 받았다" 가 곧 "충분한 confirmation 이 쌓였다" 를 뜻하지 않는다. 그래서 잔액 반영 판정은 status 만 보지 말고 numOfConfirmations 를 우리 finality 임계값과 직접 비교하는 편이 안전하다. 어떤 임계를 finality 로 볼지는 위 DCCP(Admin 설정)와 한 몸이다.

3.4 되돌림(reorg) — EVM 이라 남는 속성

Fireblocks 가 감지·통지를 대신해 준다고 해서 체인 자체의 성질이 사라지진 않는다. 이더리움과 Base 는 둘 다 EVM 체인이고 체인 끝이 드물게 교체(reorg?)될 수 있다. reorg 가 일어나면 한 번 본 입금이 무효화될 수 있다. 무효화를 벤더가 어떤 상태값으로 노출하는지는 문서에 명시가 없어 확인 중이다(그전까지는 주기 대사가 안전망). 핸들러는 무효화 신호를 받아 가공본(잔액 반영분)만 되감고 원본 기록은 영구 보존한다 — 같은 입금이 재편입되면 다시 등장할 수 있기 때문이다.

networkStatus — CONFIRMING/COMPLETED 를 뒷받침하는 하위 신호

tx 객체의 networkStatus 하위값은 DROPPED · BROADCASTING · CONFIRMING · CONFIRMED · FAILED 를 취한다. 상위 status(CONFIRMING/COMPLETED)가 우리 잔액 판정의 1차 기준이라면, networkStatus 는 체인 레벨에서 실제로 무슨 일이 있었는지(전파됐는지·확정됐는지·떨어졌는지)를 보여주는 보조 신호다.

Base 는 L2(OP-Stack) 라 소프트 확정(시퀀서 수용)과 L1 최종성 사이에 시차가 있다 — 같은 EVM 이라 처리 경로는 동일하지만, 어느 시점을 finality 로 볼지의 여유(DCCP 임계)를 이더리움과 다르게 둘 수 있다. 이 판단도 Admin 의 DCCP 설정에 담긴다.

3.5 백엔드에서 이렇게 받는다 — 한 핸들러, 세 상태

우리가 짓는 것은 인덱서가 아니라 webhook 수신기 하나다. 벤더가 push 한 상태 이벤트를 받아 세 갈래로 처리하면 된다.

// Fireblocks webhook 수신기(Service)가 받는 상태 이벤트 — 핸들러는 하나
transactions.onChainEvent { ev ->
    when (ev.status) {
        CONFIRMING -> notify(ev.account, "입금 확인 중")                 // 체인 등장·미확정 — 잔액 반영 금지
        COMPLETED  -> if (ev.numOfConfirmations >= finalityThreshold(ev.asset)) {
                          ledger.credit(ev); notify(ev.account, "입금 완료")  // DCCP 임계 도달 = finality
                      }
        무효화 신호 -> ledger.revert(ev)                               // reorg — 벤더 상태값은 확인 중
    }
}
코드가 말하는 것
  • 수신기일 뿐, 인덱서가 아니다 — 이 핸들러는 체인을 긁지 않는다. Fireblocks 가 보낸 이벤트만 받는다. 그래서 상시 수집 루프·raw 로그·projection 빌더 같은 인덱서 내부는 우리 설계에 없다 — 전부 벤더 안이다.
  • CONFIRMING 은 기록만 — confirm(체인 등장)일 뿐 아직 finality 가 아니라 available 잔액을 건드리지 않는다.
  • COMPLETED 여도 numOfConfirmations 를 재확인 — zero-confirmation 함정(3.3) 때문에 numOfConfirmations 를 finality 임계(DCCP, Admin 설정)와 비교한 뒤에만 credit 한다. finalityThreshold 는 Admin 이 관리하는 DCCP 값을 Service 가 읽어 온 것이다.
  • reorg 무효화는 반드시 처리 — 이더리움·Base 공통의 EVM 속성이라 무효화 경로를 둔다. 가공본(잔액 반영분)만 되감고 원본은 보존한다.
  • webhook 은 힌트, 대사가 최종 근거 — 누락·지연·중복이 가능하므로, 회계의 최종 정합성은 주기적 대사(벤더 잔액 vs 우리 기록, 7. 온체인 정합성·추적)가 닫는다.

이 상태 집합(감지/확정/무효화)은 워크스루 0페이지의 TxStatus{SUBMITTED, CONFIRMING, COMPLETED, FAILED} 및 Balance(available, pending, locked) 와 같은 도메인 위에서 움직인다.

3.7 흔한 장애와 방어

장애방어
webhook 누락 · 지연주기적 대사(벤더 잔액 vs 우리 기록)로 최종 정합 (7장)
같은 webhook 중복 수신(tx id + status) 멱등 키로 재처리에도 한 번만 반영
reorg 후 잔액 불일치무효화 처리 + 가공본만 되감기, 원본 보존
zero-confirmation COMPLETED 조기 신뢰numOfConfirmations 를 finality 임계(DCCP)와 직접 비교
입금 감지 3 원칙
  • webhook 은 힌트 — 최종 정합은 대사가 닫는다. 통지만 믿고 회계를 확정하지 않는다.
  • 확정을 계약으로 — CONFIRMING 과 COMPLETED 를 구분해 소비자에게 노출하고, numOfConfirmations 로 finality 를 판정한다.
  • 원본은 보존 — 무효화 되감기는 가공본만. 원본 이벤트 기록은 지우지 않아야 재편입 시 복원된다.
