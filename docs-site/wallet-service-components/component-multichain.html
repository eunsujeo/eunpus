2. 멀티체인 어댑터

체인마다 다른 규칙을 한 가지 인터페이스로 — 다른 모든 컴포넌트가 체인 차이를 모르게 한다
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

2.1 왜 필요한가

체인은 저마다 규칙이 다르다. 이더리움은 계정마다 순번(nonce)으로 트랜잭션을 직렬화하고, 비트코인은 UTXO 를 골라 쓰며, 솔라나는 또 다르다. 확정(finality?) 판단 기준도, 수수료 매기는 법도, 막힌 트랜잭션을 바꾸는 방법도 전부 다르다.

이 차이를 매니저 곳곳에 흩어 두면 인덱서·트랜잭션 빌더·서명·온체인 정합성이 전부 if (chain === 'ethereum') … else if (chain === 'bitcoin') … 로 오염된다. 멀티체인 어댑터는 이 차이를 한 군데로 모아, 나머지 컴포넌트에게는 "체인이 무엇이든 똑같아 보이는" 인터페이스를 제공한다.

한 문장 요약

멀티체인 어댑터 = "체인별 차이를 흡수하는 단 하나의 장소". 새 체인 추가 = 어댑터 하나 추가, 나머지 컴포넌트는 그대로.

어댑터는 이 모든 차이를 감추고, 위쪽 컴포넌트에는 다음과 같은 공통 동사만 노출한다 — "주소 파생해라", "잔액 알려줘", "이 이체를 트랜잭션으로 조립해라", "수수료 추정해라", "전파해라", "확정됐는지 판정해라", "막혔으면 재전송해라".

Canton(2-step) 이 어댑터에 주는 핵심 차이

위 표의 셋째 열이 핵심이다 — Canton 은 DAML active contract 원장 위에 UTXO형 holdings 를 두되, 전송이 권한 기반 2-step(기본값)이라는 게 결정적 차이다. 어댑터가 흡수해야 할 가장 큰 차이는 "제출=완료" 가 아니라는 것 — 출금이 OFFER 제출로 시작해 "상대 수락(ACCEPT) 대기" 상태에 머물 수 있고, 그동안 송신 자금은 locked UTXO 로 묶인다(11. 출금 참조). Canton Coin 은 pre-approval 로 1-step. 어댑터는 이 lifecycle 을 공통 동사 뒤로 숨긴다. (Fireblocks 는 이를 전용 transactionType 필드(OFFER/ACCEPT/REJECT/WITHDRAW/PRE_APPROVAL)+CantonHashes 로 노출 — 14.8. timeout=송신자 WITHDRAW(앱 정책).) Canton 의 원장 모델(ACS·Holding UTXO)·확정·수수료·수탁 통합 깊은 내용은 별도 Canton 네트워크 가이드에 있다.

2.4 코드로 보면

설명용 의사코드다. Figure 2-1 을 코드로 옮기면 ① 공통 인터페이스(2.2 의 공통 동사) ② chainId 로 구현 선택 ③ 체인별 어댑터 셋이다. 위 컴포넌트는 ①만 호출하고, 체인 분기는 ②·③ 안에 갇힌다.

// ① 공통 인터페이스 — 위 컴포넌트가 보는 유일한 것 (= 2.2 의 공통 동사)
interface ChainAdapter {
  addressOf(account): Address              // 멱등 조회 — 포트(13.3)와 달리 asset 인자가 없다: 어댑터는 체인 고정이라
                                           //   asset 의 일(체인 라우팅·xpub/coin type 선택)은 포트에서 이미 끝났고,
                                           //   한 체인 안에서 주소는 계정만의 함수다 (ERC-20=ETH 주소 · SPL=owner · Canton 무관)
  getBalance(address, asset): Amount
  buildTransaction(transfer): UnsignedTx   // 조립 — nonce/UTXO/2-step 차이를 흡수
  estimateFee(transfer): Fee               // 점유 없는 추정 — 조립과 달리 nonce/UTXO 를 점유하지 않는다 (견적마다 순번이 소모되면 안 됨)
  broadcast(signedTx): TxRef               // 전파
  confirmations(txRef): Confirmation       // 확정 판정 — 체인별 기준
  resend(txRef, bump): TxRef               // 막힌 tx 재전송
}

// ② chainId 로 구현 선택 (Figure 2-1 의 SEL)
const ADAPTERS: Record<ChainId, ChainAdapter> = {   // 체인당 singleton — 대부분 무상태 번역기지만
  ethereum: new EvmAdapter(node, nonceMgr),         //   EvmAdapter 만 예외로 상태(nonce lock) 보유 (4.2)
  bitcoin:  new UtxoAdapter(node),                  //   → 인스턴스 공유 + 내부 직렬화가 전제다
  solana:   new SolanaAdapter(node),
  canton:   new CantonAdapter(participant),
}
function pickAdapter(chainId): ChainAdapter {
  const a = ADAPTERS[chainId]
  if (!a) throw new UnsupportedChain(chainId)   // 새 체인 = 여기 한 줄 + 어댑터 하나
  return a
}

③ 같은 인터페이스를 체인마다 다르게 채운다 — 네 어댑터 모두 인터페이스의 일곱 동사를 전부 구현한다(부분 구현이 아니다 — 단 이는 공통 7동사 기준이고, 어댑터 모듈의 전체 표면은 코드 아래 범위 정리 참조). broadcast 는 EVM·UTXO·Solana 모두 "서명본을 노드에 제출" 한 줄로 같고 Canton 만 OFFER 제출이라 의미가 다르며, addressOf 는 같은 "조회" 라도 곡선·메커니즘이 갈린다(9.2):

// account = 9장 createAccount 가 만들어 계정 디렉터리에 저장된 우리 계정 핸들 (자체 구축에선 HD account index)
class EvmAdapter implements ChainAdapter {
  addressOf(account)           { return eip55(last20(keccak(pubkeyOf(account)))) }  // 결정적 재계산 (secp256k1 · BIP-44 m/44'/60') — 체인 수준 순수 함수.
                                                                     // 고객에게 나가는 주소는 포트가 발급·등록(9.4)을 거쳐 내준다 (15.3)
                                                                     // ERC-20 도 같은 주소 — asset 인자가 없는 이유
  getBalance(address, asset)   { return isNative(asset) ? node.getBalance(address)        // 네이티브 / ERC-20 분기 —
                                                        : erc20(asset).balanceOf(address) } // 토큰은 컨트랙트 조회, 주소는 동일
  estimateFee(t)       { return eip1559(node.feeHistory()) }             // base+priority — 점유 없는 추정
  buildTransaction(t)  { const nonce = this.nonceMgr.reserve(t.from)
                         return { ...t, nonce, fee: eip1559(t) } }   // 계정 nonce
  broadcast(signed)    { return node.sendRawTransaction(signed) }    // 서명본을 노드에 그대로 제출
  confirmations(ref)   { return blocksSince(ref) }                   // N 블록
  resend(ref, bump)    { const tx = bumpFee(sameNonce(ref), bump)    // 같은 nonce + fee↑ (RBF)
                         return broadcast(requestSign(tx)) }         // fee 변경 = 서명 무효 → 재서명 후 재전파
}

class UtxoAdapter implements ChainAdapter {
  addressOf(account)           { return encode(hash160(pubkeyOf(account)), scriptType) }  // 결정적 재계산 (BIP-44/49/84/86 스크립트 유형별 · base58/bech32) — 발급·등록은 포트 소관(15.3)
  getBalance(address, _)       { return sum(utxoSetOf(address)) }    // 잔액 = 미사용 출력(UTXO)의 합
  estimateFee(t)       { return node.estimateSmartFee() * vsizeOf(t) }  // sat/vByte × 예상 크기
  buildTransaction(t)  { const ins = coinSelect(t.from, t.amount)    // UTXO 선택
                         return { ins, outs: [t.to, change], feeRate } }
  broadcast(signed)    { return node.sendRawTransaction(signed) }    // EVM 과 동일 — 서명본 제출
  confirmations(ref)   { return blocksSince(ref) }
  resend(ref, bump)    { return rbfOrCpfp(ref, bump) }               // RBF / CPFP
}

class SolanaAdapter implements ChainAdapter {
  addressOf(account)           { return base58(hsm.derivePubkey(account)) }  // 결정적 재계산 — ed25519 hardened-only 라 키 쪽(HSM)에서 (9.2) · 주소 = pubkey · 발급·등록은 포트 소관(15.3)
  getBalance(address, asset)   { return isNative(asset) ? node.getBalance(address)
                                                        : splTokenAccountOf(address, asset).amount }  // SPL 토큰은 별도 token account
  estimateFee(t)       { return baseFee + priorityFee(node.recentPrioritizationFees()) }
  buildTransaction(t)  { return { ...t, recentBlockhash: node.blockhash() } }  // nonce 없음
  broadcast(signed)    { return node.sendTransaction(signed) }       // 동일 — 서명본 제출
  confirmations(ref)   { return commitmentOf(ref) }   // processed/confirmed/finalized
  resend(ref)          { return reassemble(ref) }     // blockhash 만료 → 재조립
}

class CantonAdapter implements ChainAdapter {
  // 2-step: 제출=OFFER, 완료는 상대 ACCEPT
  addressOf(account)           { return partyIdOf(account) }         // 조회 — PartyId 는 계정 생성(=party allocation, topology 서명
                                                                     //   필요·비멱등·유료) 때 이미 만들어졌다 (9.2 · 15.9).
                                                                     //   발급(issueDepositAddress)은 "새 memo 채번"(주소 고정, 포트가 구현 ★ Stage 81) — 곡선 파생 capability 와는 별개.
                                                                     //   allocation 의 체인별 조각은 아래 registerAccount 가 진다
  registersAccountOnLedger = true                   // 선택 capability 표지 — 네 어댑터 중 Canton 뿐. 15.2 createAccount 가 판정해 호출
  registerAccount(account, pubkey) {                // 온장 등록 (유료·비멱등) — 주소(PartyId)의 "탄생" (15-2c)
    const topo = participant.generateTopology(pubkey, hintOf(account))
    return participant.allocate(topo, requestSign(topo.multiHash))   // HSM 으로 hash 서명 — 키 반출 없음 (5장)
  }
  getBalance(party, asset)     { return sum(acs.holdingsOf(party, asset)) }  // ACS holdings 합 — 가용/locked 구분 (11.1)
  estimateFee(t)       { return trafficCostOf(byteSizeOf(t)) }       // traffic(byte) 소비 추정 (2.2 표)
  buildTransaction(t)  { return { transferInstruction: offer(t) } }
  broadcast(tx)        { return submitOffer(tx) }     // OFFER 제출 → traceableId
  confirmations(ref)   { return status2step(ref) }    // OFFER→ACCEPT/REJECT/WITHDRAW
  resend(ref)          { return withdrawAndReoffer(ref) }  // nonce-replace 아님
}
코드가 말하는 것

코어는 pickAdapter(chainId).buildTransaction(...) 처럼 공통 동사만 부른다. 체인 분기는 pickAdapter 와 각 어댑터 { } 안에만 있다. Canton 은 broadcast 가 OFFER 제출이라 confirmations 에 "상대 수락 대기" 상태가 추가되는 게 눈에 띈다 — 메커니즘은 어댑터가 숨겨도 그 상태값은 표면화된다(2.3 캡션·11. 출금). 읽기 쪽 세 동사도 2.2 표의 차이를 그대로 반영한다 — addressOf 는 전 체인 공통의 멱등 조회이되 그 메커니즘이 곡선별로 갈리고(secp256k1? xpub 재계산 / ed25519? HSM 재계산 / Canton 은 계정 생성 때 만들어진 PartyId 반환 — 주소 발급은 issueDepositAddress? capability 로 분리돼 있어 Canton 처럼 없는 체인은 미구현, 13.3·9.2), getBalance 는 잔액 모델(계정 잔액 / UTXO 합 / ACS holdings), estimateFee 는 수수료 모델(EIP-1559 / sat/vByte / priority fee / traffic). 참고로 이 ChainAdapter 는 13장의 포트보다 한 겹 아래다 — TransactionPort.submitTransaction 한 번이 자체 구축에선 이 어댑터의 buildTransaction→서명→broadcast 로 펼쳐진다(15장).

어댑터는 실패도 번역한다 — 오류 정규화

어댑터가 결과만 번역하고 오류를 체인 원문 그대로 올리면, 공통 파이프라인(4)이 결국 체인별 오류 문자열을 분기하게 된다 — 체인 분기가 어댑터 밖으로 새는 자리다. 그래서 broadcast·resend 의 실패는 어댑터가 공통 분류로 번역해서 올린다 — 예: 이미 반영됨(EVM "nonce too low" 재전파 → 성공 취급 가능) / 수수료 부족(boost 대상, 4.4) / 재조립 필요(Solana blockhash 만료) / 영구 실패(Canton REJECT). 4.3 의 intent 상태머신이 "같은 서명본 재전파" 를 안전하게 반복할 수 있는 것도 이 분류 덕이다 — 재전파해도 되는 오류와 새로 조립해야 하는 오류를, 파이프라인이 체인 지식 없이 구분할 수 있어야 하므로.

범위 정리 — 위 인터페이스의 공통 7동사가 어댑터 모듈의 전부는 아니다. 같은 모듈에 체인별 조각이 세 묶음 더 산다: 서명 규칙 3동사(toSigningPayload·verify·attach — 5.2), 수집 source(ChainSource — 3.4), 선택 capability(주소 파생 — 15.2 주석 · Canton 온장 등록 — 위 CantonAdapter 의 registerAccount). 공통 7동사는 네 체인 전부 구현이지만 선택 조각들은 체인 따라 있고 없으며, 그 유무는 위 컴포넌트가 문자열 분기 대신 어댑터가 노출하는 능력(capability)으로 판정한다(2.5 의 "능력 노출").

2.6 노드/RPC 접근 — 엔드포인트 풀과 장애 전환

어댑터가 실제로 체인과 대화하려면 그 아래에 블록체인 노드 · RPC 엔드포인트가 있어야 한다(0. Overview 의 파랑 계층). 엔드포인트가 하나뿐이면 그 노드가 죽거나 느려지는 순간 해당 체인의 읽기·쓰기가 전부 멈춘다 — 단일 장애점?이다.

그래서 자체 구축에선 한 체인당 엔드포인트 여러 개를 풀(pool)로 묶어 운영한다:

  • 장애 전환(failover) — 한 엔드포인트가 응답하지 않거나 헤드가 뒤처지면 자동으로 예비 엔드포인트로 전환한다.
  • 로테이션 · 부하 분산 — 요청을 여러 엔드포인트로 나눠 rate limit?을 피하고 한쪽에 부하가 몰리지 않게 한다.
  • 건강 검사(health check) — 각 엔드포인트의 응답성·블록 높이를 주기적으로 확인해 뒤처진 노드를 풀에서 빼고, 회복되면 다시 넣는다.
엔드포인트마다 체인 헤드가 다를 수 있다

풀 안의 노드들은 블록 높이가 미세하게 어긋날 수 있어, 방금 전파한 트랜잭션을 다른 엔드포인트로 조회하면 "아직 없음" 으로 보이는 read-after-write 불일치가 생긴다. 같은 트랜잭션의 조립·전파·조회는 되도록 같은 엔드포인트로 고정(sticky) 하고, 확정 판정은 7. 온체인 정합성·추적 의 as-of-block 기준으로 본다.

누가 이 풀을 운영하나 — 전제에 따라 다르다

이 풀·failover 는 자체 구축일 때만 우리 책임이다. 수탁+Fireblocks 경로에선 노드 인프라·엔드포인트 가용성을 Fireblocks 가 내부에서 처리하므로 우리 매니저의 컴포넌트가 아니다. GCP Blockchain Node Engine·Alchemy·QuickNode 같은 관리형 노드를 쓰면 그 일부(가용성)를 제공자에게 위임하고, 멀티 제공자 failover 만 우리가 얹는 식도 가능하다. 그래서 본 가이드는 이를 별도 컴포넌트가 아니라 멀티체인 어댑터 아래의 노드 접근 계층으로 둔다. 자체 구축에서의 위치는 15. 자체 구축 의 NodeRpc 부품에 해당한다.
