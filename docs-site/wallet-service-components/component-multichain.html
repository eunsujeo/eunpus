2. 체인 차이 흡수 — EVM(이더리움·Base)

체인마다 다른 규칙은 Fireblocks 가 벤더 안에서 흡수한다 — 우리는 멀티체인 어댑터를 만들지 않는다
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

이 장을 어떻게 읽나 — 벤더 안에서 도는 일

이 가이드는 매니저로 Fireblocks 를 채택하고 체인은 EVM — 이더리움과 Base만 태우는 전제로 쓴다. 체인 규칙을 한 인터페이스로 정규화하는 "멀티체인 어댑터" 는 Fireblocks 가 벤더 안에서 이미 하는 일이라, 우리가 만드는 컴포넌트가 아니다. 그래서 이 장은 "우리가 무엇을 구현하나" 가 아니라 "벤더 안에서 무엇이 돌고, 우리와의 이음매(seam)가 어디인가" 를 그린다. EVM 외 다른 체인(UTXO·Solana 등)은 벤더의 관심사이지 우리 설계 범위가 아니다.

2.1 왜 벤더가 흡수하나

체인은 저마다 규칙이 다르다. 이더리움은 계정마다 순번(nonce?)으로 트랜잭션을 직렬화하고, 확정(finality?) 판단 기준도, 수수료 매기는 법도, 막힌 트랜잭션을 바꾸는 방법도 다르다.

이 차이를 우리 백엔드 곳곳에 흩어 두면 입금 감지·출금 파이프라인·서명·정합성 코드가 전부 체인 분기로 오염된다. Fireblocks 는 이 차이를 벤더 안에서 흡수해, 우리 백엔드에는 "체인이 무엇이든 똑같아 보이는" API 표면을 준다. 우리가 별도 어댑터 계층을 세워 정규화할 필요가 없다는 뜻이다.

한 문장 요약

체인별 차이를 흡수하는 자리 = Fireblocks 벤더 안. 우리 백엔드는 벤더가 정규화한 공통 표면만 부르고, EVM 체인이 늘어도(이더리움→Base) 우리 코드는 그대로다.

2.2 EVM 이 벤더 안에서 정규화되는 것

우리가 태우는 체인은 EVM — 이더리움과 Base뿐이다. 둘은 같은 EVM 계열이라 계정 모델·주소 체계·수수료·확정·재전송 규칙이 사실상 같고, Base 는 이더리움 L2(OP-Stack)라 같은 규칙을 공유한다. 아래는 벤더가 EVM 을 다룰 때 흡수하는 관심사다 — 우리가 구현하는 표가 아니라, 벤더 안에서 이렇게 처리된다는 참조다.

관심사EVM — 이더리움·Base (벤더가 흡수)
잔액 표현주소별 잔액 + nonce (ERC-20 토큰도 같은 주소, 컨트랙트 잔액으로 조회)
순서 보장주소별 nonce 순차 — 벤더가 nonce 를 점유·직렬화한다(4장)
확정 판단numOfConfirmations 가 DCCP? 임계에 닿으면 확정(finality) — 3장
수수료gas × gasPrice — EIP-1559? 의 기본료(base fee)+우선료(priority fee)
재전송같은 nonce + 수수료 인상(RBF?) — 벤더의 boost 로 노출(4장, Admin 운영)
주소 파생BIP-32/44 경로 + coin type — 벤더 vault 안에서 파생, 우리는 발급된 주소만 받는다(2장 워크스루)

Fireblocks 는 이 모든 것을 벤더 안에서 처리하고, 우리 백엔드에는 업무 언어(도메인 동사)로 감싼 포트 — "주소 발급해라", "잔액 알려줘", "이 출금 제출해라", "수수료 추정해라", "상태 알려줘" — 만 노출한다. 어느 동사가 어느 백엔드(Service·Admin)에서 쓰이는지는 워크스루 0페이지의 기능 매트릭스에 정리돼 있다.

Base 는 이더리움과 같은 EVM 이다

Base 는 이더리움 L2(OP-Stack)라 주소·상태·수수료·boost/RBF·확정 모델이 이더리움과 사실상 같다. 그래서 이 가이드는 둘을 'EVM' 으로 묶어 한 번에 다루고, 체인이 갈리는 지점(가스 시세, L2 특유의 확정 지연 등)만 따로 짚는다. 다른 EVM L2 가 붙어도 우리 백엔드 코드는 안 바뀐다 — 벤더가 흡수하기 때문이다.

2.4 포트로 보면 — 우리가 부르는 면

설명용 의사코드다. 우리 백엔드가 보는 것은 포트 하나뿐이고, 그 뒤(체인 분기·nonce·gas)는 전부 벤더 안이다. 아래는 워크스루 0페이지의 도메인 한 장과 같은 면이다.

// ── 우리 백엔드가 보는 유일한 면 — 포트 (Fireblocks 가 구현) ──
interface AccountPort {
  createAccount(ref): Account                       // 고객 계정 생성 (Service)
  issueDepositAddress(account, asset): Address      // 입금 주소 발급 — EVM 은 memoTag 불필요 (Service)
  addressOf(account, asset): Address                // 발급된 주소 조회 (Service)
  getBalance(account, asset): Balance               // 가용·대기·잠김 세 칸 (Service·Admin)
}
interface TransactionPort {
  submitTransaction(request): TxRef                 // 출금 제출 — 멱등 키 동반 (Service · 4장)
  transactionsOf(account, range): List<Transfer>   // 거래 이력
  onChainEvent(handler)                             // Fireblocks webhook 수신 (입금·상태 · 3장)
}

// ── 선택 capability — EVM 이 제공하는 운영 동작 (Admin) ──
interface FeeBoostCapability { boost(txRef): TxRef }   // 수수료 인상 재전송 (RBF · 4장)
interface CancelCapability   { cancel(txRef): TxRef }  // 철회 (4장)

// ── 체인 분기·nonce·gas·확정·RBF 는 전부 이 아래 (벤더 안) ──
//  EVM(이더리움·Base) : 벤더가 nonce 점유 · EIP-1559 수수료 · numOfConfirmations 로 확정 · boost=RBF
//  그 외 체인          : 벤더의 관심사 — 우리 설계 범위 밖
코드가 말하는 것

우리 백엔드는 submitTransaction(...)·getBalance(...) 처럼 도메인 동사만 부른다. EVM 의 nonce 점유, EIP-1559 수수료 책정, 확정 판정(numOfConfirmations vs DCCP), RBF 재전송은 전부 벤더 안에서 일어나고 포트 시그니처에는 새지 않는다. "어느 구현인지 우리 백엔드가 모른다" — 이 성질 덕에 EVM 체인이 늘어도(이더리움→Base), 훗날 벤더를 바꿔도 백엔드 코드는 그대로다. boost·cancel 은 EVM 이 제공하는 선택 capability라 있을 때만 노출되고, 나가는 돈에 개입하는 동작이라 Admin 운영이다(4장).

2.5 우리 쪽에 남는 것 — 벤더가 흡수하지 못하는 이음매

체인 차이가 벤더 안으로 들어간다고 해서 우리 몫이 0 이 되진 않는다. 이음매에는 여전히 우리가 지어야 할 것이 있다.

이음매우리 몫
입금 감지 (3장)벤더가 감지·통지하지만, 그 webhook 을 받는 수신기와 매핑 DB 는 우리 것 (Service)
출금 제출 (4장)조립·nonce·전파는 벤더 안. 우리는 멱등한 제출·상태 추적, boost·cancel 운영(Admin)
서명 (5장)MPC 는 벤더 클라우드 + 우리 온프렘 co-signer 공동서명 — 마지막 서명 관문이 우리 인프라 안
정합성·추적 (7장)벤더가 준 체인 사실을 우리 장부와 대사 — 자산 단위·소수점 정규화
설계 포인트
  • 체인 차이는 벤더 안에 — 우리 백엔드에 EVM 분기 코드(gas·nonce·confirmation)가 새면 추상화가 새는 신호다. 그런 세부는 포트 뒤에 남겨 둔다.
  • 능력 노출(capability) — boost·cancel 같은 EVM 운영 동작은 벤더가 "이 체인이 지원한다" 고 알려 준 capability 로만 노출한다. 우리는 체인 이름으로 분기하지 않는다.
  • 포트가 이음매 — 우리와 벤더 사이의 유일한 접점이 포트다. 포트를 가짜 구현으로 바꿔 벤더 없이 백엔드를 테스트할 수도 있다(13. 추상화).

2.6 노드/RPC 는 누가 운영하나 — 벤더가

어댑터가 체인과 대화하려면 그 아래에 블록체인 노드 · RPC 엔드포인트가 있어야 한다. 엔드포인트가 하나뿐이면 그 노드가 죽거나 느려지는 순간 읽기·쓰기가 전부 멈추므로, 보통은 한 체인당 여러 엔드포인트를 풀(pool)로 묶어 장애 전환(failover)·부하 분산·건강 검사를 돌린다.

Fireblocks 채택 기준 — 이 풀은 우리 컴포넌트가 아니다

노드 인프라·엔드포인트 가용성·failover 는 Fireblocks 가 벤더 안에서 처리한다. 우리는 노드를 직접 운영하지 않으므로 이 풀은 우리 매니저의 컴포넌트가 아니다. 우리 쪽에 남는 것은 webhook 수신기·매핑 DB·co-signer 뿐이다(워크스루 0페이지 물리 배치). 그래서 이 가이드는 노드/RPC 접근을 우리 설계 범위 밖 — 벤더 안 계층으로 둔다.
