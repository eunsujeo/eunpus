16. NodeWallet 어댑터 (온프렘 custody 제품)

옵션 2(자체 custody)를 직접 짓는 대신 기성 제품으로 — Fireblocks 와 같은 custody 자리, 키는 고객 보유
본 페이지의 성격

설명용 의사코드다. NodeWallet 의 기능 범위는 벤더(NodeInfra) 공개·gated 문서의 자체 주장이며(독립 검증 아님), 메서드 이름은 형태 참고용이다. Solana 전용 제품인 점에 유의. 적용 전 최신 문서로 확인하라.

16.1 큰 그림 — Fireblocks 와 같은 자리, 다른 custody 모델

NodeWallet 은 13.5 의 옵션 2(자체 custody)를 "직접 구축(15장)" 하지 않고 기성 제품으로 도입하는 길이다. 구조적으로는 14. Fireblocks 와 같다 — custody 제품의 SDK 를 얇게 감싸 AccountPort·TransactionPort 를 채우는 어댑터. 다른 건 custody 모델이다.

Fireblocks 와 똑같이 custody 제품을 얇게 감싼 어댑터(파랑)가 Account·Transaction 포트를 채운다. 차이는 그 뒤 — Fireblocks 는 SaaS MPC(벤더 클라우드·벤더 샤드), NodeWallet 은 온프렘 HSM+SGX(망분리 IDC·키 고객 보유) — SGX 는 Intel CPU 의 신뢰실행환경(메모리를 격리해 실행하는 하드웨어 보안 기능)이고, 엔클레이브는 그 격리 실행 영역이다. 키 소유권과 정책 실행 위치가 고객 쪽이라는 게 옵션 2 의 핵심.

16.2 어댑터 코드

class NodeWalletProvider implements AccountPort, TransactionPort {
  constructor(private nw: NodeWalletSDK) {}        // Java/Spring SDK

  createAccount(ref) { return nw.createWallet(ref, Chain.SOLANA) }   // Solana 전용
  addressOf(wallet, _) { return nw.address(wallet) }       // 조회 — Solana 단일 주소
  // issueDepositAddress? 미구현 — 지갑당 주소 1개 모델 (capability 부재, 13.3)
  getBalance(wallet, asset) { return nw.balance(wallet, asset) }
  validateAddress(_, addr) { return nw.isValidAddress(addr) }        // Solana 주소 검증
  estimateFee(req) { return nw.estimateFee(req) }                    // Solana fee (제품 산정)

  // 제출 한 번 — 내부에서 3-키 다중서명(개시 → 승인 → 실행 SGX)
  submitTransaction(req) {
    return nw.submitTransfer({
      from: req.from, to: req.to, amount: req.amount,
      idempotencyKey: req.idempotencyKey,          // 코어 멱등 키
    })
  }
  getStatus(txRef) { return nw.tx(txRef).status }
  cancel(txRef) { return nw.cancelTransfer(txRef) }                 // 제품 정책 (Solana blockhash 만료 모델)
  // boost? 미구현 — Solana 전용이라 fee-boost 없음. stuck 은 제품/어댑터 auto-retry(blockhash 만료 재제출) (4.4)

  // 수신·확정 이벤트 — NodeWallet 자체 원장·입금 검증으로 감지해 push
  onChainEvent(handler) { nw.onLedgerEvent(e => handler(toChainEvent(e))) }
}

내 지갑 수신·확정 이벤트는? NodeWallet 이 자체 원장·입금 검증으로 감지해 TransactionPort 의 onChainEvent 로 준다. 다만 임의 외부 주소·커스텀 조회(ChainQueryPort)는 Fireblocks 와 마찬가지로 ✗ — 필요하면 그 포트만 자체 인덱서로 따로 붙인다(13.4). 즉 NodeWallet 도 Account·Transaction 두 포트를 채우는 custody 제품이다.

16.3 계정·주소 발급 단계별 흐름

NodeWallet 도 발급은 SDK 두 호출이다 — 지갑 생성 → 주소 조회. 키는 NodeWallet 온프렘 HSM 안에서 만들어지고(고객 보유), Solana 단일 체인이라 주소도 하나다.

정책 엔진이 제품에 내장 — 승인 게이트 중첩 주의

NodeWallet 의 승인자(정책 엔진)가 한도·트래블룰 등 컴플라이언스 정책과 승인 단계(approval tier)를 제품 안에서 집행한다. 우리 상위 비즈니스 레이어의 승인과 역할이 겹칠 수 있으니, "어디서 무엇을 승인하는지" 경계를 한 번 정리해야 한다(이중 승인/공백 방지).

16.6 주의

NodeWallet 을 택할 때
  • Solana 전용 — 이더리움·Canton 등 다른 체인은 NodeWallet 으론 미커버(EVM/BTC/Canton 불가). 그 체인은 Fireblocks(이더리움·Canton 둘 다 지원) 또는 자체 구축 어댑터를 별도로 두어야 함.
  • 승인 중첩 — 제품 내장 정책 엔진과 우리 비즈 레이어 승인의 경계 정리(16.4).
  • 운영 복잡도 — 망분리 IDC·HSM·SGX 운영 부담을 고객이 진다(벤더 무의존의 대가).
  • 근거 tier — 기능은 벤더 자체 주장(독립 검증 아님). 인증(ISMS 등) 상태·범위 확인.

16.7 Canton 에서는 — 미지원

NodeWallet 은 Canton 을 커버하지 못한다

NodeWallet 은 Solana 전용 제품이라 이더리움·Canton 자산은 이 어댑터로 만들 수 없다. 따라서 Canton 은 14. Fireblocks(Canton 지원) 또는 15. 자체 구축(validator node 운영) 어댑터로 처리해야 한다. 코어(지갑 서비스 백엔드)는 포트만 의존하므로, Solana = NodeWallet · Canton = Fireblocks/자체 구축 식으로 체인별 어댑터를 병행 배치하면 된다 (13.4 어댑터 커버리지).

정리하면 — NodeWallet 어댑터는 옵션 2(자체 custody)를 "사서" 채우는 길이다. custody 축에서 보면 14. Fireblocks(SaaS 위탁) · 15. 자체 구축(직접 빌드) · 16. NodeWallet(온프렘 제품 도입) 세 점이고, 코어는 어느 쪽이든 같은 포트만 의존한다. 처음으로 — 0. Overview.
