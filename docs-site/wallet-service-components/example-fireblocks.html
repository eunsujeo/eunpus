12. Fireblocks 어댑터 — Account·Transaction 두 포트 구현

FireblocksProvider 는 얇은 어댑터 — 트랜잭션 제출은 createTransaction 한 번, 수신은 webhook
본 페이지의 성격

설명용 의사코드다. 메서드 이름은 Fireblocks 공개 API 형태를 참고했으나 실제 SDK 와 다를 수 있다. Fireblocks 기능 범위(서명·전파·nonce·webhook·DCCP·externalTxId·vault)는 본 위키의 검증된 사실에 근거한다.

12.1 큰 그림

Fireblocks 한 어댑터가 AccountPort·TransactionPort 를 채운다 — 내 지갑 수신·확정 이벤트(webhook)까지 TransactionPort 로 제공. 위층 지갑 서비스 백엔드(멱등·팬아웃·정합성·오케스트레이션)는 그대로 두고, 어댑터가 계정·트랜잭션 동작을 Fireblocks API·webhook 으로 번역한다. 다만 임의 외부 주소·커스텀 조회(ChainQueryPort)는 Fireblocks 가 ✗ — 필요하면 그 포트만 자체 인덱서/Alchemy 로 따로 붙인다 (11.4).

12.2 provider 코드

class FireblocksProvider implements AccountPort, TransactionPort {

  constructor(private fb: FireblocksSDK, private webhooks: WebhookBus) {}

  // 계정(vault) 생성 — 고객 온보딩 시
  createAccount(ref)            = fb.createVaultAccount(ref)

  // 주소 · 잔액 — Fireblocks 가 멀티체인 차이까지 흡수
  deriveAddress(vaultId, asset) = fb.generateNewAddress(vaultId, asset)
  getBalance(vaultId, asset)    = fb.getVaultAccountAsset(vaultId, asset).total

  // 트랜잭션 제출 : 서명+전파+nonce 가 createTransaction 한 번으로 묶임
  submitTransaction(req) {
    const { id } = fb.createTransaction({       // build + MPC서명 + 전파 + nonce
      assetId: req.asset,
      source:      { type:'VAULT_ACCOUNT', id: req.vaultId },
      destination: { type:'ONE_TIME_ADDRESS', oneTimeAddress:{ address: req.to } },
      amount: req.amount,
      externalTxId: req.idempotencyKey,         // 코어의 멱등 키를 tx dedup 으로 전달
    })
    return id                                   // = TxRef
  }
  getStatus(txRef) = fb.getTransactionById(txRef).status   // SUBMITTED/CONFIRMING/COMPLETED
  bumpFee(txRef)   = fb.rbfTransaction(txRef)              // boost / RBF

  // 수신 트랜잭션 · 확정 : Fireblocks 가 webhook 으로 push
  onChainEvent(handler) {
    webhooks.on('transaction.status.updated', e => handler(toChainEvent(e)))  // Webhooks v2
    // 우리 vault 로 들어온 트랜잭션은 INCOMING 이벤트로 push
  }
}

두 포트(Account·Transaction)의 메서드가 거의 그대로 Fireblocks 호출 하나씩으로 매핑된다 — 그래서 얇은 어댑터다. 같은 포트를 Fireblocks 없이 직접 구현하면 어떻게 달라지는지는 13. 자체 구축.

12.3 송신 트랜잭션 단계별 흐름

Figure 12-2. Fireblocks 송신 트랜잭션. 코어는 submitTransaction 한 번이면 끝 — 빌드·서명·전파·nonce 를 Fireblocks 가 처리한다. 상태는 webhook 으로 받고, stuck 시 bumpFee(RBF/boost)만 호출. 멱등 키는 externalTxId 로 넘겨 중복 제출을 Fireblocks 측에서도 막는다.

12.4 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 vault 주소로 트랜잭션이 들어옴
  2. Fireblocks 가 감지 → webhook 으로 INCOMING + 상태(CONFIRMING → COMPLETED, DCCP) push
  3. 지갑 서비스 백엔드가 등록한 onChainEvent 핸들러가 수신 → 비즈 레이어로 팬아웃

즉 수신 트랜잭션은 코어가 무엇을 호출해서가 아니라 Fireblocks 가 push 한 webhook 으로 시작된다 (0.2 의 "② 감지"). 이를 "입금" 으로 해석하는 건 비즈 레이어의 몫이다.

12.5 그래서 지갑 서비스 백엔드가 직접 짜는 것

서명·전파가 한 호출로 묶인다

Fireblocks 에선 서명과 전파가 createTransaction 하나로 합쳐진다(빌드·nonce 포함). 그래서 자체 구축처럼 "조립 → 서명 → 전파" 3단계를 코어가 밟지 않고, submitTransaction 한 번 + 상태 추적이다. raw nonce 를 직접 돌리면 Fireblocks 내부 nonce 와 충돌하니 만들지 않는다.

Fireblocks 가 백엔드를 채워줘도, 지갑 서비스 백엔드가 반드시 갖는 것(11.7)은 그대로 남는다:

  • 게이트웨이 멱등 — 인바운드 요청에 우리 멱등 키 부여 → externalTxId 로 매핑. (externalTxId 만으로는 트랜잭션 한정 dedup)
  • vault 라우팅 — EVM nonce 직렬화가 vault 단위라, 한 vault 가 막혀도 다른 vault 로 (출금 전용 vault 를 여러 개 두고 번갈아 쓰는 multiple withdrawal vault round-robin)
  • webhook 처리 + 팬아웃 — 서명 검증 · 멱등 수신 · 상태 → 비즈 레이어/클라이언트 알림
  • 내부 장부 대사 — Fireblocks 가 준 체인 사실을 우리 장부와 맞춰봄
  • 상태 모니터링 + bumpFee 트리거 — stuck 감지 시 RBF/boost 호출

12.6 포트 메서드 → 실제 Fireblocks REST API

위 의사코드의 fb.* 호출은 실제로 다음 Fireblocks REST 엔드포인트로 매핑된다. 경로는 Fireblocks 공식 API reference 기준이며, base URL 은 https://api.fireblocks.io, 모든 요청은 JWT(API Key + RSA) 서명이다. (적용 전 최신 문서로 재확인 권장)

Webhooks 는 v2 로 — v1 은 2026-06-15 EOL

신규 구축은 Webhooks v2(POST /v1/webhooks 로 등록)를 쓴다. v1 은 2026-06-15 지원 종료이고 신규 이벤트는 v2 만 지원한다. v2 는 이벤트 이름이 점 표기로 바뀐 점에 주의 — TRANSACTION_STATUS_UPDATED(v1) → transaction.status.updated(v2), TRANSACTION_CREATED → transaction.created, TRANSACTIONS_APPROVAL_STATUS_UPDATED → transaction.approval_status.updated. 그 외 v2 는 다중 webhook·이벤트 구독·30일 재전송을 제공한다.

같은 포트를 Fireblocks 없이 직접 구현하면 어떻게 달라지는지는 — 13. 자체 구축 어댑터.
