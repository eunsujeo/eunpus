14. Fireblocks 어댑터 — Account·Transaction 두 포트 구현 (유일한 라이브 구현)

FireblocksProvider 는 얇은 어댑터 — 트랜잭션 제출은 createTransaction 한 번, 수신은 webhook. 우리가 실제로 운영하는 매니저 구현은 이 하나다
본 페이지의 성격

설명용 의사코드다. 메서드 이름은 Fireblocks 공개 API 형태를 참고했으나 실제 SDK 와 다를 수 있다. Fireblocks 기능 범위(서명·전파·nonce·webhook·DCCP·externalTxId·vault)는 Fireblocks 공식 개발자 문서에서 확인한 사실에 근거한다. 블록체인 매니저로 Fireblocks 를 채택했으므로, 이 어댑터가 포트를 채우는 유일한 라이브 구현이다 — 자체 구축은 테스트용 가짜 구현(adapters/fake)으로만 남는다(17장). 태우는 체인은 EVM — 이더리움·Base 다.

14.1 큰 그림

Fireblocks 한 어댑터가 AccountPort·TransactionPort 를 채운다 — 내 지갑 수신·확정 이벤트(webhook)까지 TransactionPort 로 제공. 위층 지갑 서비스 백엔드(멱등·팬아웃·정합성·오케스트레이션)는 그대로 두고, 어댑터가 계정·트랜잭션 동작을 Fireblocks API·webhook 으로 번역한다. 서명은 Fireblocks MPC 와 우리 온프렘 API Co-signer(SGX/TEE)가 공동서명하고, Co-signer 는 서명 직전 우리 Callback Handler 에 승인·거부를 묻는다(5장) — 나가는 돈의 마지막 자동 관문이 우리 인프라 안에 선다. 다만 임의 외부 주소·커스텀 조회(ChainQueryPort)는 Fireblocks 가 미제공 — 필요하면 그 포트만 자체 인덱서/Alchemy 같은 쿼리 프로바이더로 따로 붙인다 (13.4).

14.2 provider 코드

class FireblocksProvider implements AccountPort, TransactionPort {

  constructor(private fb: FireblocksSDK, private webhooks: WebhookBus) {}

  // 계정(vault) 생성 — 고객 온보딩 시
  createAccount(ref) { return this.fb.createVaultAccount(ref) }

  // 주소 · 잔액 — Fireblocks 가 멀티체인 차이까지 흡수. 조회(addressOf)와 발급(issueDepositAddress)은 다른 동사 (13.3)
  addressOf(vaultId, asset) { return this.fb.getDepositAddresses(vaultId, asset).first }  // 조회 — 기존(기본) 주소 (조회 엔드포인트는 적용 전 확인)
  issueDepositAddress(vaultId, asset) { return this.fb.generateNewAddress(vaultId, asset) }  // 발급 capability — 부를 때마다 새 주소
  balanceOf(vaultId, asset) { return toBalance(this.fb.getVaultAccountAsset(vaultId, asset)) }  // available·pending·locked 구분 응답 → 13.3 Balance
  validateAddress(asset, addr) { return addressRules.validate(asset, addr) }  // 로컬 형식·체크섬 검증 — 미확정 벤더 엔드포인트에 의존하지 않는다

  // 수수료 추정 — 제출 전 (POST 지만 상태 변경 X)
  estimateFee(req) { return this.fb.estimateFeeForTransaction(req) }   // low / medium / high

  // 트랜잭션 제출 : 서명+전파+nonce 가 createTransaction 한 번으로 묶임
  submitTransaction(req) {
    const { id } = this.fb.createTransaction({       // build + nonce + MPC서명(온프렘 co-signer 공동서명) + 전파
      assetId: req.asset,
      source:      { type:'VAULT_ACCOUNT', id: this.vaultOf(req.accountRef) },  // vault id 매핑은 어댑터 안에 캡슐화 (13.5)
      destination: { type:'ONE_TIME_ADDRESS', oneTimeAddress:{ address: req.to } },
      amount: req.amount,
      externalTxId: req.idempotencyKey,         // 코어의 멱등 키를 tx dedup 으로 전달
    })
    return id                                   // = TxRef
  }
  statusOf(txRef) { return this.fb.getTransactionById(txRef).status }   // SUBMITTED/CONFIRMING/COMPLETED (주요 상태 예)
  transactionsOf(vaultId, range) { return this.fb.getTransactions({ vault: vaultId, ...range }) }  // 내 거래 이력 — 거래 목록 API (목록 엔드포인트는 적용 전 확인)
  boost(txRef) { return this.fb.boostTransaction(txRef) }            // EVM 가스 인상 재전송 (RBF/부스트), 4.4
  cancel(txRef) { return this.fb.cancelTransaction(txRef) }            // 취소 — drop(교체/드롭) 과 별도 엔드포인트

  // 수신 트랜잭션 · 확정 : Fireblocks 가 webhook 으로 push
  onChainEvent(handler) {
    this.webhooks.on('transaction.status.updated', e => handler(toChainEvent(e)))  // Webhooks v2
    // 우리 vault 로 들어온 트랜잭션은 INCOMING 이벤트로 push
  }
}

두 포트(Account·Transaction)의 메서드가 거의 그대로 Fireblocks 호출 하나씩으로 매핑된다 — 그래서 얇은 어댑터다. 이 어댑터가 우리가 실제로 운영하는 유일한 라이브 구현이며, 포트 시그니처가 벤더에 독립이라는 것을 벤더 없이 검증하려면 같은 포트를 채우는 테스트용 가짜 구현(adapters/fake)을 계약 테스트로 함께 돌린다(17장).

없는 포트는 어떻게 채우나 — ChainQueryPort 가 필요하면 쿼리 프로바이더 어댑터를 "따로" 붙인다(하이브리드, 13.4). custody 와 별개 슬롯이라 Fireblocks 어댑터에는 손대지 않고 옆에 하나 더 꽂는다:

// ── ChainQueryPort 는 FireblocksProvider 에 없다 — Fireblocks 가 안 주는 포트 (13.4) ──
//    필요할 때만 쿼리 프로바이더 어댑터를 "따로" 붙인다. custody 는 Fireblocks 그대로 두고,
//    임의 조회만 Alchemy(또는 The Graph 등) 어댑터로 채운다.
class ChainQueryProviderAdapter implements ChainQueryPort {
  constructor(private q: ChainQueryProvider) {}                                      // 예: Alchemy
  transfersOf(addr, range) { return this.q.transfersOf(addr, range) }               // 임의 주소의 이체 이력 (projection)
  balanceAt(addr, asset, block) { return this.q.balanceAt(addr, asset, block) }      // as-of-block 잔액
  query(filter) { return this.q.query(filter) }                                      // 탈출구 — 커스텀·집계 (13.3)
}

// 하이브리드 조립 (13.4) — custody 는 Fireblocks, 임의 조회만 쿼리 프로바이더
const provider   = new FireblocksProvider(fb, webhooks)
const chainQuery = new ChainQueryProviderAdapter(alchemy)   // 단 이 어댑터를 붙이는 순간, 조회 프로바이더 계정·비용은 우리 몫이다

14.3 계정·주소 발급 단계별 흐름

온보딩 때 createAccount → issueDepositAddress(첫 주소 발급) 가 Fireblocks 에선 vault 계정 생성 → 자산별 주소 발급 두 번의 호출로 끝난다 — 이후의 addressOf 는 그 주소를 조회만 한다. 비즈 레이어의 "지갑 개설(고객 ref · asset)" 한 요청을 지갑 서비스 백엔드가 두 포트 호출로 푸는 구조도(내부 역할 분담은 9.1), 첫 주소가 발급 동사(issueDepositAddress)로 태어나는 것도 9.1 표준 흐름 그대로다 — 묶음 전체에 멱등 키 하나가 걸려, vault 만 생기고 중단돼도 같은 키 재시도가 이어서 재개한다. Fireblocks 에서 발급은 벤더 측 쓰기(generateNewAddress)이고, addressOf 는 그렇게 만들어진 주소의 조회일 뿐 절대 새 주소를 만들지 않는다. 주소는 workspace 의 MPC 키에서 BIP44 로 파생되며, 그 체인별 파생을 Fireblocks 가 감춘다 (MPC 키 share 분산은 vault 생성 이벤트가 아니라 workspace·디바이스·co-signer 단위의 lifecycle 이벤트다). 온체인 트랜잭션이 아니라 전파·수수료가 없다.

14.5 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 vault 주소로 트랜잭션이 들어옴
  2. Fireblocks 가 감지 → webhook 으로 INCOMING + 상태(CONFIRMING → COMPLETED) push — 확정 기준은 DCCP(입금 확정 정책, Deposit Control and Confirmation Policy)
  3. 지갑 서비스 백엔드가 등록한 onChainEvent 핸들러가 수신 → 비즈 레이어로 팬아웃

즉 수신 트랜잭션은 코어가 무엇을 호출해서가 아니라 Fireblocks 가 push 한 webhook 으로 시작된다 (0.2 의 "② 감지"). 이를 "입금" 으로 해석하는 건 비즈 레이어의 몫이다.

14.6 그래서 지갑 서비스 백엔드가 직접 짜는 것

서명·전파가 한 호출로 묶인다

Fireblocks 에선 서명과 전파가 createTransaction 하나로 합쳐진다(빌드·nonce 포함). MPC 서명 자체는 우리 온프렘 co-signer 가 공동으로 참여하지만, 코어 입장에선 "조립 → 서명 → 전파" 3단계를 직접 밟지 않고 submitTransaction 한 번 + 상태 추적으로 끝난다. raw nonce 를 직접 돌리면 Fireblocks 내부 nonce 와 충돌하니 만들지 않는다.

Fireblocks 가 백엔드를 채워줘도, 지갑 서비스 백엔드가 반드시 갖는 것(13.7)은 그대로 남는다:

  • 게이트웨이 멱등 — 인바운드 요청에 우리 멱등 키 부여 → externalTxId 로 매핑. (externalTxId 만으로는 트랜잭션 한정 dedup)
  • vault 라우팅 — EVM nonce 직렬화가 vault 단위라, 한 vault 가 막혀도 다른 vault 로 (출금 전용 vault 를 여러 개 두고 번갈아 쓰는 multiple withdrawal vault round-robin)
  • webhook 처리 + 팬아웃 — 서명 검증 · 멱등 수신 · 상태 → 비즈 레이어/클라이언트 알림
  • 내부 장부 대사 — Fireblocks 가 준 체인 사실을 우리 장부와 맞춰봄
  • 상태 모니터링 + boost 트리거 — stuck 감지 시 RBF/부스트 호출

14.7 포트 메서드 → 실제 Fireblocks REST API

14.8 confirm ↔ finality — 상태 두 개를 가르는 기준

EVM 에서 "체인에 올라감(confirm)"과 "확정(finality)"은 다르다. Fireblocks 어댑터는 이 둘을 두 상태로 갈라 onChainEvent 로 올린다:

상태뜻
CONFIRMING체인에 올라가 confirmation 을 누적하는 중 — 아직 미확정. numOfConfirmations 가 올라간다.
COMPLETED확정 정책(수신은 DCCP, 송신은 우리 임계) 이 요구한 confirmation 에 도달 = finality. 이 시점부터 자금이 최종이다.

그래서 수신 흐름(14.5)의 확정 기준은 DCCP(입금 확정 정책, Deposit Control and Confirmation Policy)이고, 송신 흐름(14.4)은 어댑터가 올린 numOfConfirmations 로 "confirm(체인 등장) ↔ finality(임계 도달)"를 가른다. 이 상태 두 개가 곧 11. 출금 상태머신의 중간 단계다 — 이더리움과 Base 는 같은 EVM 이라 이 모델이 동일하고, L2 특유의 확정 지연만 임계값으로 조정한다.

다음으로, 이 어댑터를 모듈로 어떻게 배치하는지는 — 17. 프로젝트 구조.
