14. Fireblocks 어댑터 — Account·Transaction 두 포트 구현

FireblocksProvider 는 얇은 어댑터 — 트랜잭션 제출은 createTransaction 한 번, 수신은 webhook
본 페이지의 성격

설명용 의사코드다. 메서드 이름은 Fireblocks 공개 API 형태를 참고했으나 실제 SDK 와 다를 수 있다. Fireblocks 기능 범위(서명·전파·nonce·webhook·DCCP·externalTxId·vault)는 Fireblocks 공식 개발자 문서에서 확인한 사실에 근거한다.

14.1 큰 그림

Fireblocks 한 어댑터가 AccountPort·TransactionPort 를 채운다 — 내 지갑 수신·확정 이벤트(webhook)까지 TransactionPort 로 제공. 위층 지갑 서비스 백엔드(멱등·팬아웃·정합성·오케스트레이션)는 그대로 두고, 어댑터가 계정·트랜잭션 동작을 Fireblocks API·webhook 으로 번역한다. 다만 임의 외부 주소·커스텀 조회(ChainQueryPort)는 Fireblocks 가 ✗ — 필요하면 그 포트만 자체 인덱서/Alchemy 로 따로 붙인다 (13.4).

14.2 provider 코드

class FireblocksProvider implements AccountPort, TransactionPort {

  constructor(private fb: FireblocksSDK, private webhooks: WebhookBus) {}

  // 계정(vault) 생성 — 고객 온보딩 시
  createAccount(ref) { return this.fb.createVaultAccount(ref) }

  // 주소 · 잔액 — Fireblocks 가 멀티체인 차이까지 흡수
  deriveAddress(vaultId, asset) { return this.fb.generateNewAddress(vaultId, asset) }
  getBalance(vaultId, asset) { return this.fb.getVaultAccountAsset(vaultId, asset).total }
  validateAddress(asset, addr) { return addressRules.validate(asset, addr) }  // 로컬 형식·체크섬 검증 — 미확정 벤더 엔드포인트에 의존하지 않는다

  // 수수료 추정 — 제출 전 (POST 지만 상태 변경 X)
  estimateFee(req) { return this.fb.estimateFeeForTransaction(req) }   // low / medium / high

  // 트랜잭션 제출 : 서명+전파+nonce 가 createTransaction 한 번으로 묶임
  submitTransaction(req) {
    const { id } = this.fb.createTransaction({       // build + MPC서명 + 전파 + nonce
      assetId: req.asset,
      source:      { type:'VAULT_ACCOUNT', id: this.vaultOf(req.accountRef) },  // vault id 매핑은 어댑터 안에 캡슐화 (13.5)
      destination: { type:'ONE_TIME_ADDRESS', oneTimeAddress:{ address: req.to } },
      amount: req.amount,
      externalTxId: req.idempotencyKey,         // 코어의 멱등 키를 tx dedup 으로 전달
    })
    return id                                   // = TxRef
  }
  getStatus(txRef) { return this.fb.getTransactionById(txRef).status }   // SUBMITTED/CONFIRMING/COMPLETED (주요 상태 예)
  boost(txRef) { return this.fb.boostTransaction(txRef) }            // EVM/UTXO tx 만 (gas/RBF · UTXO boost) — Solana/Canton 은 throw, 4.4
  cancel(txRef) { return this.fb.cancelTransaction(txRef) }            // 취소 — drop(교체/드롭) 과 별도 엔드포인트

  // 수신 트랜잭션 · 확정 : Fireblocks 가 webhook 으로 push
  onChainEvent(handler) {
    this.webhooks.on('transaction.status.updated', e => handler(toChainEvent(e)))  // Webhooks v2
    // 우리 vault 로 들어온 트랜잭션은 INCOMING 이벤트로 push
  }
}

두 포트(Account·Transaction)의 메서드가 거의 그대로 Fireblocks 호출 하나씩으로 매핑된다 — 그래서 얇은 어댑터다. 같은 포트를 Fireblocks 없이 직접 구현하면 어떻게 달라지는지는 15. 자체 구축.

14.3 계정·주소 발급 단계별 흐름

온보딩 때 createAccount → deriveAddress 가 Fireblocks 에선 vault 계정 생성 → 자산별 주소 발급 두 번의 호출로 끝난다. 주소는 workspace 의 MPC 키에서 BIP44 로 파생되며, 그 체인별 파생을 Fireblocks 가 감춘다 (MPC 키 share 분산은 vault 생성 이벤트가 아니라 workspace·디바이스·co-signer 단위의 lifecycle 이벤트다). 온체인 트랜잭션이 아니라 전파·수수료가 없다.

14.5 수신 트랜잭션 단계별 흐름

  1. 외부에서 우리 vault 주소로 트랜잭션이 들어옴
  2. Fireblocks 가 감지 → webhook 으로 INCOMING + 상태(CONFIRMING → COMPLETED) push — 확정 기준은 DCCP(입금 확정 정책, Deposit Control and Confirmation Policy)
  3. 지갑 서비스 백엔드가 등록한 onChainEvent 핸들러가 수신 → 비즈 레이어로 팬아웃

즉 수신 트랜잭션은 코어가 무엇을 호출해서가 아니라 Fireblocks 가 push 한 webhook 으로 시작된다 (0.2 의 "② 감지"). 이를 "입금" 으로 해석하는 건 비즈 레이어의 몫이다.

14.6 그래서 지갑 서비스 백엔드가 직접 짜는 것

서명·전파가 한 호출로 묶인다

Fireblocks 에선 서명과 전파가 createTransaction 하나로 합쳐진다(빌드·nonce 포함). 그래서 자체 구축처럼 "조립 → 서명 → 전파" 3단계를 코어가 밟지 않고, submitTransaction 한 번 + 상태 추적이다. raw nonce 를 직접 돌리면 Fireblocks 내부 nonce 와 충돌하니 만들지 않는다.

Fireblocks 가 백엔드를 채워줘도, 지갑 서비스 백엔드가 반드시 갖는 것(13.7)은 그대로 남는다:

  • 게이트웨이 멱등 — 인바운드 요청에 우리 멱등 키 부여 → externalTxId 로 매핑. (externalTxId 만으로는 트랜잭션 한정 dedup)
  • vault 라우팅 — EVM nonce 직렬화가 vault 단위라, 한 vault 가 막혀도 다른 vault 로 (출금 전용 vault 를 여러 개 두고 번갈아 쓰는 multiple withdrawal vault round-robin)
  • webhook 처리 + 팬아웃 — 서명 검증 · 멱등 수신 · 상태 → 비즈 레이어/클라이언트 알림
  • 내부 장부 대사 — Fireblocks 가 준 체인 사실을 우리 장부와 맞춰봄
  • 상태 모니터링 + boost 트리거 — stuck 감지 시 RBF/부스트 호출

14.7 포트 메서드 → 실제 Fireblocks REST API

Webhooks 는 v2 로 — v1 은 2026-06-15 EOL

신규 구축은 Webhooks v2(POST /v1/webhooks 로 등록)를 쓴다. v1 은 2026-06-15 지원 종료이고 신규 이벤트는 v2 만 지원한다. v2 는 이벤트 이름이 점 표기로 바뀐 점에 주의 — TRANSACTION_STATUS_UPDATED(v1) → transaction.status.updated(v2), TRANSACTION_CREATED → transaction.created, TRANSACTIONS_APPROVAL_STATUS_UPDATED → transaction.approval_status.updated. 그 외 v2 는 다중 webhook·이벤트 구독·30일 재전송을 제공한다.

14.8 Canton 에서는

Fireblocks 가 Canton 을 지원하므로 같은 어댑터·같은 포트로 Canton 도 처리한다. 달라지는 건 Canton 의 2-step 전송이 포트 메서드의 의미에 비치는 부분이다 — 메커니즘은 Fireblocks 가 감추지만, "상대 수락 대기" 같은 lifecycle 은 상태값으로 드러난다. (Fireblocks 는 공식 Canton Wallet SDK 의 core-signing-fireblocks 서명 드라이버로도 제공된다. Canton 원장 모델·확정·수수료·수탁 통합의 깊은 내용은 별도 Canton 네트워크 가이드 참조.)

포트 동작Canton 에서
createAccount · deriveAddressCanton party 발급(allocation)은 Canton Wallet SDK(allocateExternalParty)가 수행하고, Fireblocks 는 그 서명 드라이버(core-signing-fireblocks)로 참여한다. party 키는 Fireblocks MPC 가 관리, 서명은 EdDSA Ed25519 Raw Signing(공식 드라이버·Canton Coin 복구 절차로 확인)
submitTransactionCanton 에선 OFFER 제출(전송 제안) — 즉시 완료가 아니다. Canton Coin 은 pre-approval 로 1-step 처럼 동작
getStatus · onChainEventtransactionType(OFFER / ACCEPT / REJECT / WITHDRAW / PRE_APPROVAL)와 traceableId 로 추적 — "상대 수락 대기" 상태가 보인다
traffic(수수료) · validator nodeFireblocks 가 추상화 → 우리는 직접 만지지 않는다 (저자 추정 — 공식 문서에서 운영 범위 미확인, 적용 전 확인)
Canton 2-step 매핑 — Fireblocks 가 전용 필드로 노출 (확인됨)

Fireblocks 는 Canton 2-step 을 generic status 로 뭉개지 않고 전용 transactionType 필드로 그대로 노출한다 — OFFER(전송 개시·1단계) / ACCEPT(수신자 수락·완료) / REJECT(거절) / WITHDRAW(송신자 취소) / PRE_APPROVAL(사전승인 1-step). traceableId = 원 OFFER UpdateId, CantonHashes(offer/accept/reject/withdraw/preApprovalUpdateId)로 OFFER↔후속을 연결해 lifecycle 추적(일반 NetworkStatus 와 별개). 그러니 11. 출금 상태머신은 transactionType=OFFER 를 "수락 대기" 로 두고 ACCEPT/REJECT/WITHDRAW 로 전이하면 된다. timeout 은 Fireblocks 가 강제하지 않으므로, 수락 안 될 때 송신자가 WITHDRAW 하는 시점을 앱 정책으로 정한다. (출처: developers.fireblocks.com/reference/transaction-objects)

같은 포트를 Fireblocks 없이 직접 구현하면 어떻게 달라지는지는 — 15. 자체 구축 어댑터.
