0. Overview

블록체인 매니저가 무엇이고, 어떤 컴포넌트로 나뉘며, 무엇을 다루지 않는가

본 가이드는 블록체인 지갑 서비스의 블록체인 상호작용 레이어 — 여기서는 블록체인 매니저 라고 부른다 — 를 컴포넌트로 분해하고, 입금·출금·온오프램프 시나리오에서 컴포넌트들이 어떻게 맞물려 동작하는지, 그리고 특정 벤더(Fireblocks·Alchemy 등)에 묶이지 않으려면 어떻게 추상화해야 하는지를 보여주는 설계 reference 다.

본 페이지의 성격

여기 담긴 컴포넌트 구분과 다이어그램은 특정 제품의 공식 명세가 아니라, 저자가 일반적인 지갑 인프라 패턴과 공개된 SaaS API 형태를 바탕으로 정리한 설계 참고안이다. 실제 시스템에 적용할 때는 자신의 요구사항·규제 환경에서 다시 검증하는 것을 전제로 읽어야 한다.

0.1 블록체인 매니저란

지갑 서비스에는 "사람·정책·돈" 을 다루는 부분과 "블록체인" 을 다루는 부분이 섞여 있다. 블록체인 매니저는 그 중 체인과 직접 대화하는 부분만 떼어낸 하위 시스템이다. 즉 다음을 책임진다.

  • 체인에서 일어난 일을 읽어 들이고 (인덱싱·입금 감지·확정 판단)
  • 우리가 원하는 일을 체인에 써 넣는다 (트랜잭션 조립·서명 요청·전파·재전송)
  • 체인마다 다른 규칙을 한 가지 방식으로 정규화한다 (멀티체인)
  • 체인 위 사실과 내부 장부를 맞춰 본다 (정합성·대사)

반대로 출금 승인이나 준비자산 운용·회계 같은 판단은 매니저가 직접 내리지 않는다. 매니저는 승인이 끝난 요청을 받아 집행할 뿐이다. (0.3 참조)

전제: 본 가이드는 은행이 만드는 수탁(custodial) 지갑 앱을 가정한다. 그래서 현금↔코인 전환(온/오프램프)은 은행 앱 내부 DB 작업이고, 블록체인 매니저는 온체인 입출금 가장자리에서만 쓰인다. (9. 온·오프램프 참조)

매니저를 움직이는 두 가지 트리거

블록체인 매니저는 두 방식으로 시작된다. 이 둘을 섞으면 "입금도 누가 호출하나?" 같은 혼동이 생긴다 — 입금은 호출이 아니라 감지다.

  • ① 호출 (inbound) — 상위 서비스·클라이언트가 API 게이트웨이를 호출. 출금 · 주소 발급 · 잔액/상태 조회가 여기. 매니저는 "호출당하는" 쪽.
  • ② 감지 (event-driven) — 아무도 호출하지 않는다. 인덱서가 노드/RPC 를 폴링·구독해 입금을 스스로 감지하고, 결과를 알림(push)으로 내보낸다. 입금(자금 인지)이 여기.

온/오프램프(현금↔코인)는 수탁 지갑에선 은행 앱의 내부 DB 작업이라 매니저를 거의 거치지 않는다 — 매니저는 외부 입금(②)·외부 출금(①)에서만 호출된다. (9. 온·오프램프 참조)

0.3 범위 — 다루는 것과 위임하는 것

이 가이드가 다루지 않는 것 (다른 평면에 위임)

블록체인 매니저는 다음을 스스로 결정하지 않는다. 결정은 상위 평면이 내리고, 매니저는 그 결과를 신호로 받아 집행하는 연결점(hook)만 노출한다.

  • 준비자산 운용 · 회계 정책 — 자금을 어떻게 굴리고 공시하는가 (자금 운용 평면)
  • 회계 원장 · 대사 — 내부 복식부기 장부(잔액 진실원천)와의 대사·기표 (회계/원장 평면). 매니저는 검증된 체인 사실을 제공만 한다.

본 가이드는 "블록체인 매니저" 를 만드는 관점이므로 이들을 의도적으로 범위에서 제외한다. 매니저는 그 결과(예: 승인된 출금 지시)를 입력으로 받아 집행만 한다.

0.4 읽는 법

  • 1. 컴포넌트 개요 — 7 컴포넌트 한눈에 + 책임 경계 매트릭스.
  • 2~6. 컴포넌트 상세 — 멀티체인 어댑터 · 인덱서 · 트랜잭션/Nonce/Broadcast · 서명 · 온체인 정합성 — 각 컴포넌트의 "왜 필요 / 어떻게 동작 / 내부 flow / 다른 컴포넌트가 어떻게 쓰는지".
  • 7~9. 시나리오 — 입금 / 출금 / 온·오프램프에서 컴포넌트가 어떻게 협력하는지.
  • 10. 추상화 — Fireblocks·Alchemy·QuickNode·The Graph·SQD 의 공개 API 형태를 참고해, 벤더에 묶이지 않는 Port/Adapter 설계.
