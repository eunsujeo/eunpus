0. Overview

블록체인 매니저가 무엇이고, 어떤 컴포넌트로 나뉘며, 무엇을 다루지 않는가

본 가이드는 블록체인 지갑 서비스의 백엔드를 두 층으로 나눠 본다 — 체인과 직접 대화하는 블록체인 매니저(체인 엔진) 와, 그것을 감싸는 지갑 서비스 백엔드. 각 층의 컴포넌트, 입금·출금·온·오프램프 시나리오, 그리고 블록체인 매니저를 벤더에 묶이지 않게 추상화(Fireblocks 를 사서 쓰거나 직접 짓거나)하는 법을 보여주는 설계 reference 다.

본 페이지의 성격

여기 담긴 컴포넌트 구분과 다이어그램은 특정 제품의 공식 명세가 아니라, 저자가 일반적인 지갑 인프라 패턴과 공개된 SaaS API 형태를 바탕으로 정리한 설계 참고안이다. 실제 시스템에 적용할 때는 자신의 요구사항·규제 환경에서 다시 검증하는 것을 전제로 읽어야 한다.

0.1 블록체인 매니저란

지갑 서비스 백엔드에는 "사람·정책·돈" 을 다루는 부분과 "블록체인" 을 다루는 부분이 섞여 있다. 블록체인 매니저는 그 중 체인과 직접 대화하는 엔진이다 — 멀티체인·인덱서·nonce/트랜잭션·서명·전파. 즉 다음을 책임진다.

  • 체인에서 일어난 일을 읽어 들이고 (인덱싱·수신 트랜잭션 감지·확정 판단)
  • 우리가 원하는 일을 체인에 써 넣는다 (트랜잭션 조립·서명 요청·전파·재전송)
  • 체인마다 다른 규칙을 한 가지 방식으로 정규화한다 (멀티체인)

이 엔진이 바로 Fireblocks 가 통째로 제공하거나(관리형), 자체 구축으로 직접 만드는 대상이다. 그 바깥 — API 게이트웨이·멱등·요청 오케스트레이션·이벤트 팬아웃·내부 장부 정합성 — 은 블록체인 특화가 아닌 지갑 서비스 백엔드이고, 어떤 벤더를 써도 남는다. (10. 추상화)

또한 출금 승인이나 준비자산 운용·회계 같은 판단은 어느 층도 직접 내리지 않는다 — 비즈니스 레이어가 결정하고, 승인이 끝난 요청을 받아 집행한다. (0.3 절 참조)

전제: 본 가이드는 은행이 만드는 수탁(custodial) 지갑 앱을 가정한다. 그래서 현금↔코인 전환(온/오프램프)은 은행 앱 내부 DB 작업이고, 블록체인 매니저는 온체인 입출금 가장자리에서만 쓰인다. (9. 온·오프램프 참조)

매니저를 움직이는 두 가지 트리거

이 백엔드는 두 방식으로 움직인다. 이 둘을 섞으면 "입금도 누가 호출하나?" 같은 혼동이 생긴다 — 입금은 호출이 아니라 감지다. 그리고 매니저가 실제로 다루는 것은 트랜잭션이다 — "입금" 은 수신 트랜잭션, "출금" 은 송신 트랜잭션이고, 그 업무 의미는 비즈니스 레이어가 붙인다 (10. 추상화).

  • ① 호출 (inbound) — 상위 비즈니스 레이어가 API 게이트웨이를 호출(클라이언트는 이 레이어를 거친다 — 매니저를 직접 부르지 않는다). 송신 트랜잭션(출금) · 주소 발급 · 잔액/상태 조회가 여기. 매니저는 "호출당하는" 쪽.
  • ② 감지 (event-driven) — 아무도 호출하지 않는다. 인덱서가 노드/RPC 를 폴링·구독해 수신 트랜잭션(입금)을 스스로 감지하고, 결과를 알림(push)으로 내보낸다. 수신 트랜잭션 인지(입금)가 여기.

온/오프램프(현금↔코인)는 수탁 지갑에선 은행 앱의 내부 DB 작업이라 매니저를 거의 거치지 않는다 — 매니저는 외부 입금(②)·외부 출금(①)에서만 호출된다. (9. 온·오프램프 참조)

0.3 범위 — 다루는 것과 위임하는 것

이 가이드가 다루지 않는 것 (다른 평면에 위임)

블록체인 매니저는 다음을 스스로 결정하지 않는다. 결정은 상위 평면이 내리고, 매니저는 그 결과를 신호로 받아 집행하는 연결점(hook)만 노출한다.

  • 준비자산 운용 · 회계 정책 — 자금을 어떻게 굴리고 공시하는가 (자금 운용 평면)
  • 회계 원장 · 대사 — 내부 복식부기 장부(잔액 진실원천)와의 대사·기표 (회계/원장 평면). 매니저는 검증된 체인 사실을 제공만 한다.

본 가이드는 "블록체인 매니저" 를 만드는 관점이므로 이들을 의도적으로 범위에서 제외한다. 매니저는 그 결과(예: 승인된 출금 지시)를 입력으로 받아 집행만 한다.

0.4 읽는 법

  • 1. 컴포넌트 개요 — 7 컴포넌트(블록체인 매니저 엔진 4 + 지갑 서비스 백엔드 3) 한눈에 + 책임 경계 매트릭스.
  • 2~6. 컴포넌트 상세 — 멀티체인 어댑터 · 인덱서 · 트랜잭션/Nonce/Broadcast · 서명 · 온체인 정합성 — 각 컴포넌트의 "왜 필요 / 어떻게 동작 / 내부 flow / 다른 컴포넌트가 어떻게 쓰는지".
  • 7~9. 시나리오 — 입금 / 출금 / 온·오프램프에서 컴포넌트가 어떻게 협력하는지.
  • 10. 추상화 — 매니저를 통째로가 아니라 기능별 포트(Account·Transfer·Indexer)로 자른다. 한 어댑터가 여러 포트를 채우고(Fireblocks), 약한 포트만 갈아끼운다(인덱서는 자체/Alchemy).
  • 11~12. 구현 예시 — 같은 세 포트의 두 구현: Fireblocks(여러 포트를 한 어댑터로) / 자체 구축(포트별 부품 조립; 노드는 설치형·관리형 전용·공용 SaaS 중 선택). 출금·입금 코드 포함.
