0. Overview

블록체인 매니저가 무엇이고, 어떤 컴포넌트로 나뉘며, 무엇을 다루지 않는가

본 가이드는 블록체인 지갑 서비스의 백엔드를 두 층으로 나눠 본다 — 체인과 직접 대화하는 블록체인 매니저(체인 엔진) 와, 그것을 감싸는 우리 백엔드. 매니저로는 Fireblocks 를 채택했고, 태우는 체인은 EVM — 이더리움과 Base 다. 각 층의 컴포넌트, 입금·출금·온·오프램프 시나리오, 그리고 Fireblocks 를 코드에 직접 묶지 않도록 기능별 포트로 추상화하는 법을 보여주는 설계 참고 문서다.

본 페이지의 성격

여기 담긴 컴포넌트 구분과 다이어그램은 특정 제품의 공식 명세가 아니라, 저자가 일반적인 지갑 인프라 패턴과 Fireblocks 공개 문서를 바탕으로 정리한 설계 참고안이다. 실제 시스템에 적용할 때는 자신의 요구사항·규제 환경에서 다시 검증하는 것을 전제로 읽어야 한다. 기능 흐름을 처음부터 따라가려면 지갑 백엔드 ↔ 블록체인 매니저 통로 설계 워크스루를 함께 본다.

0.1 블록체인 매니저란

지갑 서비스의 백엔드에는 "사람·정책·돈" 을 다루는 부분과 "블록체인" 을 다루는 부분이 섞여 있다. 블록체인 매니저는 그 중 체인과 직접 대화하는 엔진이다 — 체인 차이 흡수·입금 감지·출금 파이프라인·서명. 즉 다음을 책임진다.

  • 체인에서 일어난 일을 읽어 들이고 (수신 트랜잭션 감지·확정 판단)
  • 우리가 원하는 일을 체인에 써 넣는다 (트랜잭션 조립·서명·전파·재전송)
  • 체인마다 다른 규칙을 한 가지 방식으로 정규화한다 — 여기서는 이더리움과 Base 를 같은 EVM 으로 묶어 태운다

이 엔진을 우리는 Fireblocks 로 채택했다. 서명·키·노드·인덱싱·전파·정책 엔진이 대부분 벤더 안으로 들어간다. 그 바깥 — API 게이트웨이·멱등(같은 요청이 중복 도착해도 한 번만 실행되게 하는 성질)·요청 오케스트레이션·이벤트 팬아웃(하나의 이벤트를 여러 구독자에게 나눠 보내는 것)·온체인 정합성·추적 — 은 블록체인 특화가 아닌 우리 백엔드이고, 벤더 안으로 들어가지 않는다. (13. 추상화)

우리 백엔드는 다시 물리적으로 분리된 두 개다. Service 백엔드는 고객 런타임(계정·주소·입금·출금 제출·잔액)을, Admin 백엔드는 운영·거버넌스(TAP 정책·승인·키 운영·boost·cancel·동결·rebalance)를 맡고, 별도 배포·권한·감사 경계로 나뉜다.

또한 서명이 온전히 벤더 안에서 끝나지는 않는다. MPC 키 share 하나는 우리 보안 존(SGX/TEE)에 설치한 API Co-signer 가 들고, 매 서명마다 Fireblocks 와 공동서명한다. Co-signer 는 서명 직전 Callback Handler(우리 정책 훅)에 승인·거부를 물으므로, 나가는 돈의 마지막 자동 관문이 우리 인프라 안에 선다. (5. 서명 · co-signer)

출금 승인이나 준비자산 운용·회계 같은 판단은 어느 층도 직접 내리지 않는다 — 상위 비즈니스 레이어가 결정하고, 승인이 끝난 요청을 받아 집행한다. (0.3 절 참조)

전제: 본 가이드는 은행이 만드는 수탁(custodial) 지갑 앱을 가정한다. 그래서 현금↔코인 전환(온/오프램프)은 은행 앱 내부 DB 작업이고, 블록체인 매니저는 온체인 입출금 가장자리에서만 쓰인다. (12. 온·오프램프 참조)

매니저를 움직이는 두 가지 트리거

이 백엔드는 두 방식으로 움직인다. 이 둘을 섞으면 "입금도 누가 호출하나?" 같은 혼동이 생긴다 — 입금은 호출이 아니라 감지다. 그리고 매니저가 실제로 다루는 것은 트랜잭션이다 — "입금" 은 수신 트랜잭션, "출금" 은 송신 트랜잭션이고, 그 업무 의미는 비즈니스 레이어가 붙인다 (13. 추상화).

  • ① 호출 (inbound) — 상위 비즈니스 레이어가 우리 백엔드를 호출(클라이언트는 이 레이어를 거친다 — 매니저를 직접 부르지 않는다). 송신 트랜잭션(출금) · 주소 발급 · 잔액/상태 조회가 여기. 매니저는 "호출당하는" 쪽.
  • ② 감지 (event-driven) — 아무도 호출하지 않는다. Fireblocks 가 체인에서 수신 트랜잭션(입금)을 감지해 webhook 으로 밀어 넣고, 우리 백엔드가 이를 받아 알림(push)으로 내보낸다. 수신 트랜잭션 인지(입금)가 여기.

온/오프램프(현금↔코인)는 매니저를 거의 거치지 않는다(0.1 전제 참조) — 매니저는 외부 입금(②)·외부 출금(①)에서만 호출된다.

0.3 범위 — 다루는 것과 위임하는 것

이 가이드가 다루지 않는 것 (다른 평면에 위임)

블록체인 매니저는 다음을 스스로 결정하지 않는다. 결정은 상위 평면이 내리고, 매니저는 그 결과를 신호로 받아 집행하는 연결점(hook)만 노출한다.

  • 준비자산 운용 · 회계 정책 — 자금을 어떻게 굴리고 공시하는가 (자금 운용 평면)
  • 회계 원장 · 대사 — 내부 복식부기 장부(잔액 진실원천)와의 대사·기표 (회계/원장 평면). 매니저는 검증된 체인 사실을 제공만 한다.

본 가이드는 "블록체인 매니저" 를 만드는 관점이므로 이들을 의도적으로 범위에서 제외한다. 매니저는 그 결과(예: 승인된 출금 지시)를 입력으로 받아 집행만 한다.

0.4 읽는 법

  • 1. 컴포넌트 개요 — 7 컴포넌트(Fireblocks 매니저 4 + 우리 백엔드 3) 한눈에 + 책임 경계 매트릭스.
  • 2~5. Fireblocks 매니저 (벤더 안) — 체인 차이 흡수(EVM) · 입금 감지(webhook) · 출금 파이프라인 · 서명(co-signer) — 각 컴포넌트의 "왜 필요 / 어떻게 동작 / 코드로 보면 / 다른 컴포넌트가 어떻게 쓰는지".
  • 6~8. 우리 백엔드 (Service·Admin) — API 게이트웨이 · 온체인 정합성·추적 · 이벤트/알림.
  • 9~12. 시나리오 — 계정·주소 발급(온보딩) / 입금 / 출금 / 온·오프램프에서 컴포넌트가 어떻게 협력하는지.
  • 13. 추상화 — 매니저를 통째로가 아니라 기능별 포트(AccountPort·TransactionPort·ChainQueryPort)로 자른다. 벤더 독립·다중 EVM 체인(이더리움·Base)·테스트 가능성을 위해 포트로 감싼다.
  • 14. Fireblocks 어댑터 — 포트를 채우는 구체 구현 (출금·입금 코드 포함).
  • 17. 프로젝트 구조 — 2층·3포트·어댑터 주입을 Kotlin+Spring Gradle 멀티모듈로 매핑.
