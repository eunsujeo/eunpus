10. 벤더 추상화 (기능별 포트)

매니저를 통째로가 아니라 기능마다 자른다 — 한 어댑터가 여러 포트를 채우고, 포트마다 갈아끼운다
본 페이지의 성격

아래 인터페이스·코드는 설명용 의사코드다. Fireblocks 의 기능 범위(서명·전파·nonce·webhook·DCCP·externalTxId·vault·수수료)는 본 위키의 검증된 사실에 근거한다. 그 외 벤더(Alchemy 등)·자체 구축 진술은 공개 문서와 일반 설계 패턴이므로 적용 전 검증하라.

10.1 두 층 — 지갑 서비스 백엔드 와 블록체인 매니저

컴포넌트는 성격이 다른 두 층에 걸쳐 있다.

  • 블록체인 매니저 (체인 엔진) — 체인과 직접 대화하는 부분: 멀티체인·인덱서·nonce/트랜잭션·서명·전파. 벤더가 채우거나 자체 구축하는 대상이다.
  • 지갑 서비스 백엔드 (항상 내 것) — API 게이트웨이·멱등·오케스트레이션·이벤트 팬아웃·내부 장부 정합성. 어떤 벤더를 써도 남는다.

추상화 경계는 이 둘 사이에 둔다. 문제는 "그 경계를 어떻게 자르느냐" 다.

10.2 핵심 — 매니저를 통째로가 아니라 "기능별 포트" 로 자른다

흔한 실수 — 매니저를 한 덩어리로 추상화

"블록체인 매니저" 를 인터페이스 하나로 통째 추상화하면, 교체 단위가 "전부 Fireblocks냐, 전부 자체냐" 둘뿐이 된다. 그러면 섞을 수가 없다 — 예컨대 "트랜잭션은 Fireblocks, 임의 조회는 자체 인덱서" 같은 현실적인 조합이 표현되지 않는다.

그래서 기능(capability)마다 포트를 둔다. 두 가지 규칙만 지키면 된다.

  • 한 어댑터가 여러 포트를 채울 수 있다 — Fireblocks 는 여러 기능을 묶어 주니 여러 포트를 한꺼번에 구현한다. Alchemy 는 인덱서 포트만.
  • 포트마다 따로 갈아끼운다 — 한 벤더가 약한 포트만 다른 어댑터로 교체.

10.3 세 기능 포트

매니저가 필요로 하는 기능을 세 포트로 묶었다. 입금/출금이 아니라 트랜잭션·계정·조회 단위다.

interface AccountPort {                  // 계정·주소 (키가 있는 곳)
  createAccount(ref): Promise<Account>     // 고객 계정(vault) 생성
  deriveAddress(account, asset): Promise<Address>
  getBalance(account, asset): Promise<Amount>
}

interface TransferPort {                 // 트랜잭션 쓰기 (서명+전파를 묶어서)
  submitTransaction(req): Promise<TxRef>
  getStatus(txRef): Promise<TxStatus>      // pending / confirmed / stuck
  bumpFee(txRef): Promise<TxRef>           // stuck 재전송 (RBF/boost)
}

interface IndexerPort {                  // 읽기 (조회 · 수신 이벤트)
  query(filter): Promise<Records>          // 잔액·이력·확정 (as-of-block)
  onChainEvent(handler): Subscription      // 수신 트랜잭션 · 확정 push
}
입금/출금은 트랜잭션의 "해석" 이다

출금 = 우리가 만든 송신 트랜잭션(TransferPort), 입금 = 우리 주소로 들어온 수신 트랜잭션(IndexerPort 의 이벤트). 포트엔 "입금하다/출금하다" 가 없고 트랜잭션·조회 동작만 있다. 업무 의미는 위층(비즈니스 레이어)이 붙인다.

10.4 한 어댑터가 여러 포트 — 그리고 포트마다 교체

어댑터AccountPortTransferPortIndexerPort
Fireblocks✅✅ createTransaction△ webhook + 내 vault 잔액·이력 조회 (임의 주소·커스텀 가공 X)
Alchemy · The Graph · SQD——✅ 임의 조회·이력
자체 (HSM + 노드 + 인덱서)✅✅✅
이게 단일 seam 으론 못 하던 조합

Fireblocks 로 AccountPort·TransferPort 를 쓰되, 임의 주소 조회나 커스텀 가공·집계가 필요하면 IndexerPort 만 자체 인덱서(또는 Alchemy)로 교체한다. 매니저를 통째로 추상화했다면 "Fireblocks 아니면 자체" 둘 중 하나라 이 하이브리드가 불가능했다. 기능별 포트라서 약한 포트 하나만 바꿀 수 있다.

근거 구분

"Fireblocks" 행은 본 위키의 검증된 사실이다(Fireblocks 의 IndexerPort 가 내 vault 범위 — webhook + 잔액·이력 조회 — 이고 임의 주소·커스텀 가공은 자체인 점 포함). 그 외 벤더·자체 구축 행은 공개 문서·설계 판단이다.

10.5 서명·nonce·전파·멀티체인은 어디에 — 포트 "안" 의 메커니즘

이들은 별도 포트가 아니라 TransferPort·AccountPort 안의 메커니즘이다. 같은 submitTransaction 을 —

  • Fireblocks 어댑터는 createTransaction 한 번으로 (서명+전파+nonce 묶음),
  • 자체 어댑터는 내부에서 nonce 점유 → 조립 → HSM 서명 → 노드 전파로

채운다. 그래서 서명·전파를 억지로 SignerPort·BroadcastPort 로 쪼개지 않는다 — 그건 메커니즘 분해라 Fireblocks 의 묶음과 안 맞는다(예전 4-포트가 leaky 했던 이유).

언제 더 쪼개나 (Rule of Three)

포트를 더 잘게(예: TransferPort → SignerPort + BroadcastPort) 나누는 건 그 기능을 정말로 따로 갈아끼울 때만이다 — 예: "키는 자체 HSM 으로 서명하되 전파는 외부 노드 서비스로". 그런 실제 요구가 생기기 전에 미리 쪼개면 다시 leaky 추상화가 된다.

10.6 Fireblocks 를 써도 지갑 서비스 백엔드는 남는다

Fireblocks 가 세 포트를 거의 다 채워도, 그 위층은 그대로 우리가 만든다.

  • 멱등 게이트웨이 — 인바운드 요청에 우리 멱등 키 부여 → Fireblocks 의 externalTxId 로 매핑 (externalTxId 만으로는 트랜잭션 한정 dedup).
  • 이벤트 팬아웃 — Fireblocks 는 webhook 을 줄 뿐, 비즈 레이어·클라이언트로 알리는 건 우리.
  • 내부 장부 정합성 — 체인 사실을 우리 장부와 맞춰보는 건 항상 우리 (6. 온체인 정합성·추적).
  • 오케스트레이션 — 요청 큐·상태머신·재시도·vault 라우팅.

정리하면 — 매니저를 통째로 추상화하지 말고 기능별 포트(Account·Transfer·Indexer)로 자른다. 한 어댑터가 여러 포트를 채우고(Fireblocks), 약한 포트만 갈아끼운다(인덱서는 자체/Alchemy). 구체 구현은 11. Fireblocks · 12. 자체 구축. 처음으로 — 0. Overview.
