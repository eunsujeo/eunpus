10. SaaS API 와 Port 설계

벤더에 묶이지 않게 — 공개 API 형태를 참고한 Port/Adapter 추상화
본 페이지의 성격

아래 Port 인터페이스와 매핑은 저자가 각 SaaS 의 공개 문서에 드러난 API 형태를 참고해 설계한 안이다. 특정 벤더의 공식 권장 구조가 아니며, 메서드 이름·시그니처는 설명을 위한 의사코드다. 실제 적용 시 각 벤더의 최신 문서로 검증하라.

10.1 왜 추상화하는가

블록체인 매니저는 거의 항상 외부 SaaS 에 의존한다 — 서명은 Fireblocks, 인덱싱은 The Graph/Alchemy, 수집은 QuickNode 같은 식이다. 그런데 이들을 컴포넌트 코드에 직접 박아 넣으면 벤더를 바꾸거나 자체 구축으로 전환할 때 매니저 전체를 뜯어야 한다.

해법은 포트와 어댑터(Ports & Adapters, 헥사고날) 패턴이다. 블록체인 매니저의 로직은 벤더 SDK 가 아니라 "포트?(인터페이스)" 에만 의존하고, 각 벤더(또는 자체 구축)는 그 포트를 구현하는 "어댑터" 로 바깥에 둔다. 그러면 벤더 교체 = 어댑터 교체이고, 테스트는 가짜 어댑터로 한다.

10.2 SaaS 가 커버하는 영역 비교

핵심 통찰 하나 — SaaS 마다 커버하는 포트가 다르다. 그래서 "Fireblocks 하나로 다 된다" 거나 "Alchemy 하나로 다 된다" 가 아니라, 포트별로 다른 벤더를 조합하게 된다.

SaaS주로 커버하는 영역공개 API 형태(예시)
Fireblocks4 포트 거의 전부 — 서명·전파·입금감지·멀티체인·custody (수탁 풀스택)create transaction(서명·전파·순번) · RBF/boost · incoming tx · webhook · DCCP(입금 확정) · 잔액 · 멀티체인 지원 · fee estimation · 주소 파생
Alchemy인덱싱 읽기 + 알림 + RPC 전파alchemy_getAssetTransfers · Notify(Address Activity webhook) · eth_sendRawTransaction · eth_getTransactionCount · Gas Manager · 70+ 체인

한 벤더가 여러 포트를 묶어 준다 (특히 Fireblocks)

수탁 지갑 기준, Fireblocks 는 4 포트를 사실상 다 구현한다 — 서명(MPC)·전파(+RBF)·입금감지/잔액/확정(webhook·DCCP)·멀티체인/주소/수수료. 즉 Fireblocks 하나로 매니저 전체가 돌아간다(단 IndexerPort 는 "자기 vault 한정" — 임의 주소 범용 인덱싱은 아니나, 수탁이면 충분). 반면 Alchemy 는 Indexer·Broadcast·ChainAdapter(RPC)는 주지만 SignerPort 는 직접 가져와야 한다(키는 내 몫). 추상화의 의미는 "Fireblocks 같은 풀스택을 쓰되, 나중에 자체 구축으로 갈 때 포트별로 쪼개 갈아끼울 수 있다" 는 것이다.

10.3 4 포트 설계 (의사코드)

① ChainAdapterPort — 체인 의미 정규화

interface ChainAdapterPort {
  deriveAddress(account: AccountRef, path: DerivationPath): Promise<Address>
  buildTransfer(req: TransferRequest): Promise<UnsignedTx>   // 계정형 순번 / UTXO 선택 포함
  estimateFee(tx: UnsignedTx, speed: FeeSpeed): Promise<FeeParams>
  finalityRule(): FinalityRule                                // 예: N 블록 또는 commitment 단계
  capabilities(): ChainCapabilities                           // RBF 지원? account vs utxo? 등
}

→ 멀티체인 어댑터 가 이 포트. 어떤 벤더를 쓰든 체인 차이는 여기서 정규화. (Fireblocks 는 멀티체인·주소·수수료를 자체 제공 / Alchemy·GCP BNE·자체 노드는 RPC 를 데이터 소스로)

② IndexerPort — 체인 데이터 읽기 · 구독

interface IndexerPort {
  getBalance(address: Address, asset: AssetId): Promise<Amount>
  getTransfers(q: TransferQuery): Promise<Transfer[]>          // address / from·to / block 범위
  confirmationOf(txHash: TxHash): Promise<Confirmation>        // 확정 수준 노출
  subscribe(addresses: Address[], onEvent: (e: ChainEvent) => void): Subscription
}

→ 인덱서 가 이 포트. Fireblocks(자기 vault: webhook·잔액·DCCP 확정) / Alchemy(getAssetTransfers+Notify) / The Graph·SQD(질의) / QuickNode(구독) / 자체 인덱서가 각각 어댑터.

③ SignerPort — 서명 (키는 외부)

interface SignerPort {
  sign(payload: SignPayload): Promise<Signature>   // 키 미보관. 실패 시 새 라운드(비멱등)
  publicKeyOf(account: AccountRef): Promise<PublicKey>
}

→ 서명 오케스트레이션 이 이 포트. Fireblocks MPC / 자체 HSM·MPC 가 어댑터. (Alchemy 등 RPC 전용 벤더는 이 포트를 구현하지 않음 → 직접 마련)

④ BroadcastPort — 전파 · 추적 · 재전송

interface BroadcastPort {
  broadcast(signedTx: SignedTx): Promise<TxHash>
  status(txHash: TxHash): Promise<BroadcastStatus>            // pending / confirmed / stuck
  replace(txHash: TxHash, higherFee: FeeParams): Promise<TxHash>  // 같은 순번 재전송
}

→ 트랜잭션 빌더 · Nonce/Broadcast 의 체인 IO 부분. Fireblocks(서명과 묶임) / Alchemy(eth_sendRawTransaction) / 자체 노드가 어댑터. 순번 점유·큐·멱등은 포트 밖 애플리케이션 로직(벤더가 순번을 소유하면 그 부분은 위임).

근거 tier — 같은 ✅ 라도 출처가 다름

Fireblocks 행만 본 위키의 검증된 fact 다. Alchemy·QuickNode·SQD·The Graph 는 벤더 공개 문서 기반(2026-06 확인, 비-위키) 이므로 적용 전 최신 문서로 다시 확인하라.

★ 이 표는 가능 관계일 뿐이다. 실제 시스템은 4 포트를 빠짐없이 채운 한 벌(조합) 이어야 하며, 한 어댑터가 여러 포트를 덮어도 빈 포트가 하나라도 있으면 안 돈다. 조합 예시는 10.6 절.

노드 레이어 어댑터 — GCP Blockchain Node Engine 의 경우

GCP BNE 같은 관리형 전용 노드는 표준 RPC 를 제공하므로 ChainAdapterPort 의 RPC 소스 + BroadcastPort(eth_sendRawTransaction 류) 어댑터로 들어간다. 단 SignerPort 는 구현하지 않고(키는 별도 서명자), Transfers/Streams 같은 enhanced 기능이 없어 IndexerPort 는 직접 인덱서(또는 BigQuery 데이터셋 등)로 채워야 한다. 즉 "공용 RPC(Alchemy/QuickNode)" 대신 "전용·격리 노드" 가 필요할 때 같은 자리에 끼우는 또 다른 어댑터 선택지다.

10.5 설계 원칙

추상화를 지탱하는 규칙
  • 능력 노출(capability) — 어댑터마다 되는 것/안 되는 것이 다르다(RBF 지원, unfinalized 조회, 확정 단계 수). 포트가 capabilities() 로 알려 매니저 로직이 분기 없이 적응하게.
  • 묶음 흡수 — Fireblocks 처럼 여러 포트가 한 API 로 묶인 경우, 한 어댑터가 복수 포트를 구현하게 둔다. 억지로 쪼개지 않는다.
  • 멱등 경계 — 포트 호출에 요청 ID 를 실어, 어댑터/벤더가 재시도해도 한 번만 실행되게.
  • 확정은 데이터에 — IndexerPort 의 응답에 "확정 수준" 을 함께 실어 매니저 로직이 안전 판정하게.
  • 테스트용 가짜 어댑터 — 모든 포트는 in-memory fake 구현을 둬, 벤더 없이 시나리오(입금·출금·reorg)를 테스트.

10.6 조합(stack) — 포트를 전부 채운 한 벌

10.4 매트릭스가 "누가 채울 수 있나" 라면, 실제 배포는 4 포트를 빠짐없이 채운 한 벌(stack) 이다. 한 어댑터가 여러 포트를 덮더라도, 빈 포트가 하나라도 있으면 시스템은 안 돈다. 같은 코어 위에 꽂을 수 있는 두 조합 예시:

포트조합 A — 수탁 풀스택조합 B — 혼합(자체 + SaaS)
SignerPortFireblocks자체 HSM · MPC
BroadcastPortFireblocks자체 노드 · GCP BNE
ChainAdapterPortFireblocks자체 노드 · GCP BNE
IndexerPortFireblocks (자기 vault)Alchemy 또는 자체 인덱서

조합 A 는 Fireblocks 한 어댑터가 4 포트 전부 — 수탁 지갑이면 이 한 벌로 매니저 전체가 돈다. 조합 B 는 포트별로 쪼갰다. 코어 로직은 A·B 어느 쪽이든 한 줄도 바뀌지 않는다 — 그게 추상화의 목적이다. (어느 조합이든 4 포트가 *전부* 채워졌다는 점에 주목)

어댑터별 구현 책임

각 어댑터를 만들 때 "어떤 포트의 어떤 메서드를, 벤더 API 의 무엇으로 채우나" 를 정리하면:

어댑터구현해야 하는 포트벤더 API → 포트 메서드 (예)안 채우는 포트(직접 마련)
Fireblocks (수탁)4 포트 전부create transaction → sign+broadcast · status/RBF → status/replace · incoming·webhook·DCCP → subscribe+confirmationOf · 잔액 → getBalance · 멀티체인·주소·fee → ChainAdapterPort(없음 — 자기 vault 범위) 임의 주소 범용 인덱싱만 별도
AlchemyIndexerPort · BroadcastPort · ChainAdapterPort(RPC)getAssetTransfers → getTransfers · Notify webhook → subscribe · tx receipt → confirmationOf · eth_sendRawTransaction → broadcastSignerPort(키는 직접)
QuickNode · SQD · The GraphIndexerPortStreams 구독 → subscribe · SQD batch / The Graph GraphQL → getTransfersSignerPort · BroadcastPort
자체 HSM · MPCSignerPortHSM/MPC 서명 → sign · 키 조회 → publicKeyOf나머지 전부
자체 노드 · GCP BNEChainAdapterPort(RPC) · BroadcastPort표준 JSON-RPC → 수수료/잔액/조립 · eth_sendRawTransaction → broadcast · eth_getTransactionReceipt → statusIndexerPort(enhanced 없음 → 별도 인덱서) · SignerPort
어댑터 구현 체크리스트
  • 포트 메서드 전부 충족 — 못 채우는 메서드는 빈 구현이 아니라 capabilities() 로 "미지원" 을 명시(매니저 로직이 분기 없이 우회).
  • 벤더 응답 → 포트 타입 정규화 — 벤더별 에러·상태 코드·금액 단위를 포트가 정의한 공통 타입으로 변환.
  • 멱등 보존 — 매니저가 넘긴 요청 ID 를 벤더 호출(또는 재시도)에 전파해 한 번만 실행.
  • 가짜(fake) 구현 동봉 — 같은 포트의 in-memory 어댑터를 만들어 벤더 없이 시나리오 테스트.

이로써 7 컴포넌트가 벤더에 묶이지 않고, 자체 구축 ↔ SaaS 사이를 포트 단위로 오갈 수 있는 그림이 완성된다. 처음으로 — 0. Overview 의 컴포넌트 맵을 다시 보면 전체가 맞춰진다.
