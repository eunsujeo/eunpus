13. 벤더 추상화 (기능별 포트)

매니저를 통째로가 아니라 기능마다 자른다 — 한 어댑터가 여러 포트를 채우고, 포트마다 갈아끼운다
본 페이지의 성격

아래 인터페이스·코드는 설명용 의사코드다. Fireblocks 의 기능 범위(서명·전파·nonce·webhook·DCCP(입금 확정 정책, Deposit Control and Confirmation Policy)·externalTxId·vault·수수료)는 Fireblocks 공식 문서에서 확인한 사실에 근거한다. 그 외 벤더(Alchemy 등) 진술은 공개 문서와 일반 설계 패턴이므로 적용 전 검증하라.

13.1 왜 포트로 감싸나 — 그리고 왜 EVM(이더리움·Base)인가

매니저로는 Fireblocks 를 채택했다. 그런데도 Fireblocks 를 코드 곳곳에서 직접 부르지 않고 포트(통로)로 한 겹 감싸는 이유는 셋이다.

  • ① 벤더 독립 — 벤더 타입·SDK 가 업무 로직에 새지 않아, 훗날 매니저(벤더)를 바꿔도 우리 백엔드는 그대로다.
  • ② 다중 EVM 체인 (이더리움·Base) — 이더리움과 Base 는 같은 EVM(account 기반·공개 mempool·reorg·동일 주소 체계)이라 포트 하나로 여러 체인을 태운다. 다른 L2 가 붙어도 백엔드 코드는 안 바뀐다.
  • ③ 테스트 가능 — 포트를 가짜 구현으로 바꿔 벤더 없이 백엔드를 검증한다.

Base 는 이더리움 L2(OP-Stack) 라 주소·상태·수수료·boost/RBF·확정(DCCP) 모델이 이더리움과 사실상 같다. 그래서 이 문서는 둘을 'EVM'으로 묶어 한 번에 다루고, 체인이 갈리는 지점(가스 시세·L2 특유의 확정 지연 등)만 따로 짚는다.

13.2 두 층 — 우리 백엔드 와 블록체인 매니저

컴포넌트는 성격이 다른 두 층에 걸쳐 있다.

  • 블록체인 매니저 (체인 엔진) — 체인과 직접 대화하는 부분: 체인 차이 흡수·입금 감지·nonce/트랜잭션·서명·전파. Fireblocks 가 채우는 대상이다.
  • 우리 백엔드 (항상 내 것) — API 게이트웨이·멱등·오케스트레이션·이벤트 팬아웃·온체인 정합성·추적. 벤더 안으로 들어가지 않는다. Service 백엔드(고객 런타임)와 Admin 백엔드(운영·거버넌스)로 물리 분리된다.

추상화 경계는 이 둘 사이에 둔다. 문제는 "그 경계를 어떻게 자르느냐" 다.

13.3 핵심 — 매니저를 통째로가 아니라 "기능별 포트" 로 자른다

흔한 실수 — 매니저를 한 덩어리로 추상화

"블록체인 매니저" 를 인터페이스 하나로 통째 추상화하면, 교체 단위가 매니저 전체가 되어버린다. 그러면 포트마다 다른 제공자를 섞을 수가 없다 — 예컨대 "계정·트랜잭션은 Fireblocks, 임의 외부 주소 조회는 자체 인덱서" 같은 현실적인 조합이 표현되지 않는다. Fireblocks 는 이 임의 조회를 주지 않기 때문에 실제로 마주치는 조합이다.

그래서 기능(capability)마다 포트를 둔다. 두 가지 규칙만 지키면 된다.

  • 한 어댑터가 여러 포트를 채울 수 있다 — Fireblocks 는 여러 기능을 묶어 주니 여러 포트를 한꺼번에 구현한다. Alchemy 는 조회 포트만.
  • 포트마다 따로 갈아끼운다 — Fireblocks 가 안 주는 포트만 다른 어댑터로 붙인다.

ChainQuery(임의·커스텀 조회)는 Fireblocks 가 ✗이라, 임의 외부 주소·이력·집계가 필요할 때만 자체 인덱서·Alchemy 로 따로 붙인다(선택). 그래서 "Account·Transaction 은 Fireblocks, ChainQuery 만 인덱서" 같은 하이브리드가 된다. 매니저 통째가 아니라 포트마다 고르는 게 핵심이다.

왜 Account 와 Transaction 을 나눴나 — 갈아끼우려고가 아니다

두 포트는 키가 있는 곳에 함께 묶여 한 몸이다 — 계정·주소를 만든 키와 트랜잭션에 서명하는 키는 같아야 하므로, 둘 다 Fireblocks 가 함께 구현한다(14장). 그런데도 나눈 이유는 부르는 쪽이 다르기 때문이다 — 온보딩(9)은 Account 만, 출금(11)은 Transaction 만 의존한다. 합쳐 놓으면 온보딩 코드가 submitTransaction 에, 출금 파이프라인이 issueDepositAddress 에 의존하게 되고 capability 묶음(발급 vs boost·cancel)도 섞인다. 정리하면 — 실존하는 교체 경계는 custody ↔ ChainQuery 하나(Fireblocks 가 안 주는 조회를 인덱서로 붙인다)고, Account/Transaction 은 교체 단위가 아니라 소비 단위의 분리다.

13.4 세 기능 포트

매니저가 필요로 하는 기능을 세 포트로 묶었다. 입금/출금이 아니라 트랜잭션·계정·조회 단위다. 동사의 자리는 데이터의 주인이 정한다 — 내 지갑 범위(custody 가 보유·통지하는 것)는 Account·Transaction 에, 임의 주소·체인 전체는 ChainQuery 에.

interface AccountPort {                  // 계정·주소 (키가 있는 곳)
  createAccount(ref): Promise<Account>     // 고객 계정(vault) 생성 (9.2)
  addressOf(account, asset): Promise<Address>     // 멱등 "조회" — 발급(등록)된 주소 반환. 절대 새 주소를 만들지 않는다
  issueDepositAddress?(account, asset): Promise<Address>  // (capability) 입금 주소 "발급" — 첫 주소부터. 상태 변경
                                            //   Fireblocks generateNewAddress 로 부를 때마다 새 EVM 주소를 발급 (Fireblocks 콘솔·dev 문서로 확인)
  getBalance(account, asset): Promise<Balance>   // 단일 숫자 아님 — available(사용 가능)·pending(미확정 입금)·locked(묶임) 구분
  validateAddress(asset, addr): Promise<boolean>  // 출금 대상 주소 형식·체크섬 검증 — 로컬 EVM 규칙으로 구현 (벤더 API 불요)
}

interface TransactionPort {                 // 트랜잭션 쓰기 + 상태 + 내 지갑 이벤트
  estimateFee(req): Promise<Fee>             // 제출 전 수수료 추정 (low/med/high)
  submitTransaction(req): Promise<TxRef>     // 서명+전파 묶음
  getStatus(txRef): Promise<TxStatus>        // 내 tx 상태 (BROADCASTING/CONFIRMING/COMPLETED/FAILED)
  transactionsOf(account, range): Promise<Transfer[]>  // 내 계정의 송수신 이력 — custody 가 준다(전 구현 가능, capability 아님)
                                            //   임의 "외부" 주소의 이력은 ChainQueryPort.transfersOf 소관 — 데이터 주인이 다르다
  boost?(txRef): Promise<TxRef>            // (capability · EVM RBF) 수수료 올려 재촉 — Admin 운영 (4.4)
  cancel?(txRef): Promise<TxRef>           // (capability) 중단 — EVM=같은 순번 0원 self-send 덮어쓰기 — Admin 운영
  onChainEvent(handler): Subscription        // 내 지갑 수신·확정 push (Fireblocks webhook 이 줌)
}

interface ChainQueryPort {                  // (선택) 임의·커스텀 조회 — custody 가 안 주는 것
  transfersOf(addr, range): Promise<Transfer[]>   // 임의 "외부" 주소의 이체 이력 — 내 계정 이력은 TransactionPort.transactionsOf
  balanceAt(addr, asset, block): Promise<Amount>  // as-of-block 시점 잔액
  query(filter): Promise<Records>          // 탈출구 — 위 동사로 못 담는 커스텀·집계 (남용 주의, 아래)
}
주소는 "조회(addressOf)" 와 "발급(issueDepositAddress)" 을 가른다

예전 이름 deriveAddress(파생)는 secp256k1? HD 메커니즘 어휘가 포트 이름으로 샌 것이었다. EVM 에서 파생은 순수 함수(상태 변경·비용 없음, 몇 번 불러도 같은 값)처럼 보이지만, Fireblocks 의 generateNewAddress 는 부를 때마다 새 주소를 발급하는 상태 있는 작업이다 — 벤더 안에서 vault 에 주소가 등록된다. 그래서 의도 기준으로 가른다 — addressOf = 멱등 조회, issueDepositAddress? = 입금 주소 발급(capability, 상태 변경). 13.9 의 "도메인 우선" 을 포트 이름에도 적용한 것이다. 운영 불변식도 이 분리를 요구한다 — 주소는 벤더 등록·watch 준비까지 끝나야 존재하므로(9.4), 새 주소가 태어나는 길은 상태 있는 동사뿐이다: 첫 주소부터 issueDepositAddress 로 발급한다. addressOf 는 등록된 주소만 반환하고 절대 새 주소를 만들지 않는다(9.1).

ChainQueryPort 도 "도메인 동사 우선" — generic query 하나로 두지 않는 이유

조회 포트를 query(filter) 하나로 두면 편해 보이지만, 그 filter 안으로 체인별 개념(로그 토픽·블록 오프셋 등)이 전부 새어 들어온다 — 13.9 의 "도메인 우선" 이 이 포트에서만 무너지는 길이다. 그래서 자주 쓰는 질의는 transfersOf·balanceAt 같은 도메인 동사로 승격하고, query 는 아직 동사가 되지 못한 커스텀·집계용 탈출구로만 둔다. 같은 질의가 반복되면 동사로 올린다. 승격 신호가 하나 더 있다 — 내 계정을 이 포트로 조회하고 있다면 그 동사는 custody 포트로 올라갈 자리다(그래서 내 거래 이력은 ChainQuery 가 아니라 TransactionPort.transactionsOf 다 — Fireblocks 단독 배치도 인덱서 없이 거래내역을 보여줄 수 있어야 하므로).

입금/출금은 트랜잭션의 "해석" 이다

출금 = 우리가 만든 송신 트랜잭션(TransactionPort), 입금 = 우리 주소로 들어온 수신 트랜잭션(TransactionPort 의 onChainEvent). 포트엔 "입금하다/출금하다" 가 없고 트랜잭션·조회 동작만 있다. 업무 의미는 위층(비즈니스 레이어)이 붙인다.

submitTransaction 은 "서명 완료" 가 아니라 "확정 대기 시작" 이다

EVM 에서 submitTransaction 은 전파까지만 묶는다 — 그 뒤 getStatus 는 BROADCASTING → CONFIRMING(체인에 등장, 아직 미확정) → COMPLETED(DCCP 임계 confirmation 도달 = finality) 로 흐른다. numOfConfirmations 로 "confirm(체인 등장) ↔ finality(임계 도달)" 를 가른다. 임계값은 DCCP(입금·출금 확정 정책)가 정하며 대부분 1, ETC 372, contract call 은 3 이상이다 — DCCP 는 Admin 백엔드가 소유한다(2·11).

13.5 한 어댑터가 여러 포트 — 그리고 없는 포트만 따로 붙인다

어댑터AccountPortTransactionPortChainQueryPort
Fireblocks — 채택✓✓ createTransaction + webhook 이벤트✗ (임의 외부 주소·커스텀 조회 미지원 → 조회 제공자 필요)
Alchemy · The Graph · SQD——✓ 임의 조회·이력 (선택)
이게 단일 seam(교체 가능한 이음새) 으론 못 하던 조합

Fireblocks 로 AccountPort·TransactionPort(내 지갑 계정·트랜잭션·수신 이벤트)를 쓰되, 임의 외부 주소 조회나 커스텀 가공·집계가 필요하면 ChainQueryPort 를 자체 인덱서(또는 Alchemy)로 추가한다 — Fireblocks 는 이 포트를 ✗(안 줌)이기 때문. 매니저를 통째로 추상화했다면 이런 부분 보강이 불가능했다. 기능별 포트라서 없는 포트만 따로 붙일 수 있다.

하이브리드의 비용 — 확정 판정 기준이 둘이 된다

이 조합에선 같은 체인을 두 시스템이 서로 다른 확정 정책으로 본다 — Fireblocks(TransactionPort)는 자기 입금 확정 정책(DCCP)으로, 자체 인덱서/Alchemy(ChainQueryPort)는 우리 확정 기준으로. 같은 입금이 한쪽엔 확정, 다른 쪽엔 미확정으로 보이는 구간이 항상 생긴다. 그래서 우선순위 규칙을 명시해 둔다 — 자금 사용·잔액 판정은 custody 포트(Account·Transaction) 기준 하나로 고정하고, ChainQueryPort 는 조회·분석·대사 입력으로 한정한다. 둘이 끝내 어긋나는 건은 7. 온체인 정합성의 예외(확인 필요)로 떨어뜨려 사람이 본다.

근거 구분

"Fireblocks" 행은 Fireblocks 공식 문서에서 확인한 사실이다 — Fireblocks 는 내 지갑의 수신 이벤트(webhook)·tx 상태·잔액을 Account·TransactionPort 로 제공하지만, 임의 외부 주소·커스텀 조회(ChainQueryPort)는 ✗. Alchemy 등 조회 벤더 행은 공개 문서·설계 판단이다.

13.6 서명·nonce·전파·체인 차이는 어디에 — 포트 "안" 의 메커니즘

이들은 별도 포트가 아니라 TransactionPort·AccountPort 안의 메커니즘이다. 같은 submitTransaction 을 Fireblocks 어댑터가 createTransaction 한 번으로 채운다 — 서명(MPC + 우리 co-signer 공동서명)·전파·nonce 가 그 안에 묶여 있다. 그래서 서명·전파를 억지로 SignerPort·BroadcastPort 로 쪼개지 않는다 — 그건 메커니즘 분해라 Fireblocks 의 묶음과 안 맞는다(포트를 너무 잘게 쪼개면 벤더 특화 개념이 인터페이스 밖으로 새어 나오기 쉽다).

언제 더 쪼개나 — 따로 갈아끼울 실제 요구가 생겼을 때만

포트를 더 잘게(예: TransactionPort → SignerPort + BroadcastPort) 나누는 건 그 기능을 정말로 따로 갈아끼울 때만이다. 그런 실제 요구가 생기기 전에 미리 쪼개면 다시 leaky 추상화가 된다. 지금은 그런 요구가 없으므로 submitTransaction 묶음을 유지한다.

13.7 Fireblocks 를 써도 우리 백엔드는 남는다

Fireblocks 가 custody 두 포트를 다 채워도, 그 위층은 그대로 우리가 만든다.

  • 멱등 게이트웨이 — 인바운드 요청에 우리 멱등 키 부여 → Fireblocks 의 externalTxId 로 매핑 (externalTxId 만으로는 트랜잭션 한정 dedup).
  • 이벤트 팬아웃 — Fireblocks 는 webhook 을 줄 뿐, 비즈 레이어·클라이언트로 알리는 건 우리.
  • 온체인 정합성·추적 — 체인 사실을 우리 장부와 맞춰보는 건 항상 우리 (7장).
  • 오케스트레이션 — 요청 큐·상태머신·재시도·vault 라우팅.

13.9 왜 "도메인 우선" 인가 — 트레이드오프

지금까지의 포트는 createAccount·submitTransaction·getStatus 처럼 우리 업무 언어로 정의돼 있다. 이렇게 벤더 API 모양이 아니라 우리 도메인(수탁 지갑 운영) 개념에서 출발해 설계하고, 벤더는 그 뒤에 끼우는 방식을 "도메인 우선" 이라 한다. 반대는 "벤더 우선" — Fireblocks API 문서를 따라 설계가 정해지는 것이다.

도메인 우선의 두 가지 함정
  • 임피던스 불일치 (추상화가 거짓말할 위험) — 우리 모델이 벤더 실제 능력과 안 맞으면 어댑터가 두꺼워지거나, 최악엔 포트가 거짓말을 한다. 실제 사례: EVM 의 확정 지연 — 전파(BROADCASTING)와 확정(COMPLETED)이 다른데 포트가 이를 한 상태로 뭉개면 미확정 자금을 확정으로 오인한다. 포트는 숨기지 말고 CONFIRMING(체인 등장·미확정)을 정규화 상태값으로 표면화하고, 미확정은 "확인 필요" 로 격리하라(2·11).
  • 최소공통분모 함정 — 훗날의 벤더 교체를 지나치게 의식해 포트를 가장 약한 수준으로 깎으면, Fireblocks 강점(createTransaction 이 서명+전파+nonce 를 묶음, RBF(수수료를 올려 미확정 트랜잭션을 교체-재전송), 입금 확정 정책 DCCP)을 못 쓴다. 못 숨기는 벤더 강점은 포트 동작으로 노출하되 선택적으로 둔다.

그래서 권장은 "도메인 우선, 단 벤더 현실로 검증한" 하이브리드다. 포트는 우리 업무 언어로 두되(순수 진공 설계 금지), 설계 단계에서 Fireblocks 가 실제로 무엇을 주는지 검증해 추상화가 거짓말하지 않게 한다. 한 줄로 — "Fireblocks 가 설계를 정하게 두지 말되, 설계가 Fireblocks 를 무시하게도 두지 말라." 이 비용은 다중 EVM 체인(이더리움·Base, 이후 다른 L2)을 한 모델로 태우고, 훗날 매니저(벤더)를 교체할 가능성에 대비할 때 정당화된다. 벤더 한 곳·체인 하나만 영원히 쓸 거면 도메인 우선은 순수 오버헤드일 수 있다.

정리하면 — 매니저를 통째로 추상화하지 말고 기능별 포트(Account·Transaction·ChainQuery)로 자른다. 한 어댑터가 여러 포트를 채우고(Fireblocks), 없는 포트만 따로 붙인다(임의 조회는 자체/Alchemy). 구체 구현은 14. Fireblocks 어댑터. 다음 — 14. Fireblocks 어댑터.
