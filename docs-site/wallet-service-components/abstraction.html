13. 벤더 추상화 (기능별 포트)

매니저를 통째로가 아니라 기능마다 자른다 — 한 어댑터가 여러 포트를 채우고, 포트마다 갈아끼운다
본 페이지의 성격

아래 인터페이스·코드는 설명용 의사코드다. Fireblocks 의 기능 범위(서명·전파·nonce·webhook·DCCP·externalTxId·vault·수수료)는 본 위키의 검증된 사실에 근거한다. 그 외 벤더(Alchemy 등)·자체 구축 진술은 공개 문서와 일반 설계 패턴이므로 적용 전 검증하라.

13.1 두 층 — 지갑 서비스 백엔드 와 블록체인 매니저

컴포넌트는 성격이 다른 두 층에 걸쳐 있다.

  • 블록체인 매니저 (체인 엔진) — 체인과 직접 대화하는 부분: 멀티체인·인덱서·nonce/트랜잭션·서명·전파. 벤더가 채우거나 자체 구축하는 대상이다.
  • 지갑 서비스 백엔드 (항상 내 것) — API 게이트웨이·멱등·오케스트레이션·이벤트 팬아웃·내부 장부 정합성. 어떤 벤더를 써도 남는다.

추상화 경계는 이 둘 사이에 둔다. 문제는 "그 경계를 어떻게 자르느냐" 다.

13.2 핵심 — 매니저를 통째로가 아니라 "기능별 포트" 로 자른다

흔한 실수 — 매니저를 한 덩어리로 추상화

"블록체인 매니저" 를 인터페이스 하나로 통째 추상화하면, 교체 단위가 "전부 Fireblocks냐, 전부 자체냐" 둘뿐이 된다. 그러면 섞을 수가 없다 — 예컨대 "트랜잭션은 Fireblocks, 임의 조회는 자체 인덱서" 같은 현실적인 조합이 표현되지 않는다.

그래서 기능(capability)마다 포트를 둔다. 두 가지 규칙만 지키면 된다.

  • 한 어댑터가 여러 포트를 채울 수 있다 — Fireblocks 는 여러 기능을 묶어 주니 여러 포트를 한꺼번에 구현한다. Alchemy 는 인덱서 포트만.
  • 포트마다 따로 갈아끼운다 — 한 벤더가 약한 포트만 다른 어댑터로 교체.

ChainQuery(임의·커스텀 조회)는 Fireblocks 가 ✗이라, 임의 외부 주소·이력·집계가 필요할 때만 자체 인덱서·Alchemy 로 따로 붙인다(선택). 그래서 "Account·Transaction 은 Fireblocks, ChainQuery 만 인덱서" 같은 하이브리드가 된다. 매니저 통째가 아니라 포트마다 고르는 게 핵심이다.

13.3 세 기능 포트

매니저가 필요로 하는 기능을 세 포트로 묶었다. 입금/출금이 아니라 트랜잭션·계정·조회 단위다.

interface AccountPort {                  // 계정·주소 (키가 있는 곳)
  createAccount(ref): Promise<Account>     // 고객 계정(vault) 생성
  deriveAddress(account, asset): Promise<Address>
  getBalance(account, asset): Promise<Amount>
  validateAddress(asset, addr): Promise<boolean>  // 출금 대상 주소 형식·체크섬 검증
}

interface TransactionPort {                 // 트랜잭션 쓰기 + 상태 + 내 지갑 이벤트
  estimateFee(req): Promise<Fee>             // 제출 전 수수료 추정 (low/med/high)
  submitTransaction(req): Promise<TxRef>     // 서명+전파 묶음
  getStatus(txRef): Promise<TxStatus>        // 내 tx 상태 (pending/confirmed/stuck)
  boost?(txRef): Promise<TxRef>            // (capability · EVM/UTXO 전용) 수수료 올려 재촉 — 미지원 체인은 throw/부재 (4.4)
  cancel(txRef): Promise<TxRef>              // 대기·막힌 tx 중단 (EVM 0원 self-send · Canton OFFER withdraw)
  onChainEvent(handler): Subscription        // 내 지갑 수신·확정 push (custody 백엔드가 줌)
}

interface ChainQueryPort {                  // (선택) 임의·커스텀 조회 — custody 가 안 주는 것
  query(filter): Promise<Records>          // 임의 외부 주소·deep history·as-of-block·reorg·집계
}
입금/출금은 트랜잭션의 "해석" 이다

출금 = 우리가 만든 송신 트랜잭션(TransactionPort), 입금 = 우리 주소로 들어온 수신 트랜잭션(TransactionPort 의 onChainEvent). 포트엔 "입금하다/출금하다" 가 없고 트랜잭션·조회 동작만 있다. 업무 의미는 위층(비즈니스 레이어)이 붙인다.

2-step 체인(Canton)에서 submitTransaction 의 의미

Canton 같은 권한 기반 체인엔 submitTransaction 이 "전송 완료" 가 아니라 OFFER 제출이다 — 상대가 ACCEPT 해야 끝난다. getStatus 가 OFFER/ACCEPT/REJECT/WITHDRAW 를 반환하고, 멀티체인 어댑터가 이 lifecycle 을 정규화한다. 같은 포트로 이더리움(즉시 confirm)·Canton(2-step) 을 다 담되, 상태값의 다양성은 어댑터가 흡수한다. (Fireblocks 는 이를 전용 transactionType 필드 OFFER/ACCEPT/REJECT/WITHDRAW/PRE_APPROVAL + CantonHashes 로 노출 — 14.8 참조. timeout=송신자 WITHDRAW(앱 정책).)

Fireblocks 로 AccountPort·TransactionPort(내 지갑 계정·트랜잭션·수신 이벤트)를 쓰되, 임의 외부 주소 조회나 커스텀 가공·집계가 필요하면 ChainQueryPort 를 자체 인덱서(또는 Alchemy)로 추가한다 — Fireblocks 는 이 포트를 ✗(안 줌)이기 때문. 매니저를 통째로 추상화했다면 "Fireblocks 아니면 자체" 둘 중 하나라 이 조합이 불가능했다. 기능별 포트라서 없는 포트만 따로 붙일 수 있다.

근거 구분

"Fireblocks" 행은 본 위키의 검증된 사실이다 — Fireblocks 는 내 지갑의 수신 이벤트(webhook)·tx 상태·잔액을 Account·TransactionPort 로 제공하지만, 임의 외부 주소·커스텀 조회(ChainQueryPort)는 ✗. 그 외 벤더·자체 구축 행은 공개 문서·설계 판단이다.

13.5 제도에 따라 custody 를 통째 교체 (Fireblocks ↔ 자체 HSM/MPC)

수탁형이라도 제도(법)가 custody 주체를 가른다 — 적격 custodian 위탁이 허용되면 Fireblocks, 자가 수탁을 요구하면 자체 HSM/MPC. 둘 다 같은 세 포트를 구현하므로, 코어(지갑 서비스 백엔드)는 그대로 두고 주입하는 어댑터만 바꾼다.

교체를 가능케 하는 한 가지 — submitTransaction(묶음)

TransactionPort.submitTransaction 이 "서명+전파를 합쳐서" 받기 때문에 양쪽이 같은 메서드로 들어온다 — Fireblocks 는 createTransaction 한 번으로, 자체 custody 는 내부에서 자체 HSM/MPC 서명 → Infura 전파로 채운다. 만약 포트가 sign()/broadcast() 를 따로 노출했다면 Fireblocks(묶임)가 안 맞아 이 교체가 깨진다.

두 옵션 모두 "수탁 등급" 을 지키려면

옵션 2 의 서명은 반드시 자체 HSM/MPC 다 — raw 개인키를 앱이 들면 수탁 등급이 아니라 hot-wallet 이다. 그리고 Fireblocks 특화(externalTxId·vault id)나 Infura 엔드포인트 같은 건 어댑터 안에 캡슐화하고 코어로 누출하지 않는다 — 그래야 제도가 바뀌어도 코어 무수정으로 옵션을 바꾼다.

옵션 2(자체 custody)는 직접 구축만이 아니라 기성 온프렘 custody 제품을 도입하는 길도 있다 — 예: NodeWallet(설치형 소프트웨어, HSM+SGX 기반 3-키 다중서명, 망분리 IDC, 키를 고객이 직접 보유). 정책·서명이 고객 인프라에서 실행되는 점이 SaaS·벤더 위탁(옵션 1)과 다르다. 단 NodeWallet 은 Solana 전용이라 이더리움·Canton 엔 부적합 — 그 체인은 Fireblocks(둘 다 지원) 또는 자체 구축으로. 인증 범위도 도입 전 확인해야 한다. 어댑터 구현은 16. NodeWallet 어댑터.

13.6 서명·nonce·전파·멀티체인은 어디에 — 포트 "안" 의 메커니즘

이들은 별도 포트가 아니라 TransactionPort·AccountPort 안의 메커니즘이다. 같은 submitTransaction 을 —

  • Fireblocks 어댑터는 createTransaction 한 번으로 (서명+전파+nonce 묶음),
  • 자체 어댑터는 내부에서 nonce 점유 → 조립 → HSM 서명 → 노드 전파로

채운다. 그래서 서명·전파를 억지로 SignerPort·BroadcastPort 로 쪼개지 않는다 — 그건 메커니즘 분해라 Fireblocks 의 묶음과 안 맞는다(예전 4-포트가 leaky 했던 이유).

언제 더 쪼개나 (Rule of Three)

포트를 더 잘게(예: TransactionPort → SignerPort + BroadcastPort) 나누는 건 그 기능을 정말로 따로 갈아끼울 때만이다 — 예: "키는 자체 HSM 으로 서명하되 전파는 외부 노드 서비스로". 그런 실제 요구가 생기기 전에 미리 쪼개면 다시 leaky 추상화가 된다.

13.7 Fireblocks 를 써도 지갑 서비스 백엔드는 남는다

Fireblocks 가 세 포트를 거의 다 채워도, 그 위층은 그대로 우리가 만든다.

  • 멱등 게이트웨이 — 인바운드 요청에 우리 멱등 키 부여 → Fireblocks 의 externalTxId 로 매핑 (externalTxId 만으로는 트랜잭션 한정 dedup).
  • 이벤트 팬아웃 — Fireblocks 는 webhook 을 줄 뿐, 비즈 레이어·클라이언트로 알리는 건 우리.
  • 내부 장부 정합성 — 체인 사실을 우리 장부와 맞춰보는 건 항상 우리 (7. 온체인 정합성·추적).
  • 오케스트레이션 — 요청 큐·상태머신·재시도·vault 라우팅.

13.8 왜 "도메인 우선" 인가 — 트레이드오프

지금까지의 포트는 createAccount·submitTransaction·getStatus 처럼 우리 업무 언어로 정의돼 있다. 이렇게 벤더 API 모양이 아니라 우리 도메인(수탁 지갑 운영) 개념에서 출발해 설계하고, 벤더는 그 뒤에 끼우는 방식을 "도메인 우선" 이라 한다. 반대는 "벤더 우선" — Fireblocks API 문서를 따라 설계가 정해지는 것이다.

도메인 우선의 두 가지 함정
  • 임피던스 불일치 (추상화가 거짓말할 위험) — 우리 모델이 벤더 실제 능력과 안 맞으면 어댑터가 두꺼워지거나, 최악엔 포트가 거짓말을 한다. 실제 사례: Canton 의 2-step(OFFER/ACCEPT/REJECT/WITHDRAW) — 한때 Fireblocks 매핑이 미확정이었으나, 확인 결과 Fireblocks 가 전용 transactionType 필드로 그대로 노출(generic status 로 안 뭉갬, CantonHashes 로 연결)함을 확인했다. 우리 "표면화" 결정과 정확히 맞은 셈이다 → 숨기지 말고 "수락 대기" 를 정규화 상태값으로 표면화하고, 미확정은 "확인 필요" 로 격리하라(2·9).
  • 최소공통분모 함정 — 여러 벤더 호환을 노리다 포트를 가장 약한 벤더 수준으로 깎으면, Fireblocks 강점(createTransaction 이 서명+전파+nonce 를 묶음, RBF, 입금 확정 정책)을 못 쓴다. 못 숨기는 벤더 강점은 포트 동작으로 노출하되 선택적으로 둔다.

그래서 권장은 "도메인 우선, 단 벤더 현실로 검증한" 하이브리드다. 포트는 우리 업무 언어로 두되(순수 진공 설계 금지), 설계 단계에서 Fireblocks·Canton 이 실제로 무엇을 주는지 검증해 추상화가 거짓말하지 않게 한다. 한 줄로 — "Fireblocks 가 설계를 정하게 두지 말되, 설계가 Fireblocks 를 무시하게도 두지 말라." 이 비용은 벤더·체인을 실제로 갈아탈 가능성이 있을 때 정당화된다(이더리움+Canton, 자체 HSM 전환 검토처럼). 벤더 한 곳만 영원히 쓸 거면 도메인 우선은 순수 오버헤드일 수 있다.

정리하면 — 매니저를 통째로 추상화하지 말고 기능별 포트(Account·Transaction·ChainQuery)로 자른다. 한 어댑터가 여러 포트를 채우고(Fireblocks), 약한 포트만 갈아끼운다(인덱서는 자체/Alchemy). 구체 구현은 14. Fireblocks · 15. 자체 구축(노드 조달 옵션 포함). 처음으로 — 0. Overview.
