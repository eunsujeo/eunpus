10. SaaS API 와 Port 설계

벤더에 묶이지 않게 — 공개 API 형태를 참고한 Port/Adapter 추상화
본 페이지의 성격

아래 Port 인터페이스와 매핑은 저자가 각 SaaS 의 공개 문서에 드러난 API 형태를 참고해 설계한 안이다. 특정 벤더의 공식 권장 구조가 아니며, 메서드 이름·시그니처는 설명을 위한 의사코드다. 실제 적용 시 각 벤더의 최신 문서로 검증하라.

10.1 왜 추상화하는가

블록체인 매니저는 거의 항상 외부 SaaS 에 의존한다 — 서명은 Fireblocks, 인덱싱은 The Graph/Alchemy, 수집은 QuickNode 같은 식이다. 그런데 이들을 컴포넌트 코드에 직접 박아 넣으면 벤더를 바꾸거나 자체 구축으로 전환할 때 매니저 전체를 뜯어야 한다.

해법은 포트와 어댑터(Ports & Adapters, 헥사고날) 패턴이다. 매니저 코어는 "포트(인터페이스)" 에만 의존하고, 각 벤더(또는 자체 구축)는 그 포트를 구현하는 "어댑터" 로 바깥에 둔다. 그러면 벤더 교체 = 어댑터 교체이고, 테스트는 가짜 어댑터로 한다.

10.2 SaaS 가 커버하는 영역 비교

핵심 통찰 하나 — SaaS 마다 커버하는 포트가 다르다. 그래서 "Fireblocks 하나로 다 된다" 거나 "Alchemy 하나로 다 된다" 가 아니라, 포트별로 다른 벤더를 조합하게 된다.

SaaS주로 커버하는 영역공개 API 형태(예시)
Fireblocks서명 + 전파 + 순번 (묶음) + 주소/custodycreate transaction(서명·전파·순번 일괄) · transaction status · RBF/boost · gas station · webhook
Alchemy인덱싱 읽기 + 알림 + RPC 전파alchemy_getAssetTransfers · Notify(Address Activity webhook) · eth_sendRawTransaction · eth_getTransactionCount · Gas Manager · 70+ 체인
QuickNode Streams수집(push 파이프라인)Stream(dataset + JS filter + webhook 목적지) · exactly-once · finality-order · reorg 재전송 · backfill · checkpoint resume
The Graph인덱싱 조회subgraph GraphQL 질의 · schema entity · block-height 질의
SQD / Subsquid수집 + 가공(배치)EvmBatchProcessor · SQD Network archive + RPC · batch ctx.blocks · unfinalized 지원 · custom sink
묶음(bundling)에 주의

Fireblocks 의 "create transaction" 은 서명·전파·순번을 한 번에 처리한다. 즉 SignerPort 와 BroadcastPort 가 한 어댑터로 묶여 있고, 그 사이의 raw 순번은 노출되지 않는다. 반면 Alchemy 는 IndexerPort + BroadcastPort 를 주지만 SignerPort 는 직접 가져와야 한다(키는 내 몫). 추상화는 이 "어떤 벤더가 어떤 포트를 어디까지 묶어 주는가" 를 흡수하는 일이기도 하다.

10.3 4 포트 설계 (의사코드)

① ChainAdapterPort — 체인 의미 정규화

interface ChainAdapterPort {
  deriveAddress(account: AccountRef, path: DerivationPath): Promise<Address>
  buildTransfer(req: TransferRequest): Promise<UnsignedTx>   // 계정형 순번 / UTXO 선택 포함
  estimateFee(tx: UnsignedTx, speed: FeeSpeed): Promise<FeeParams>
  finalityRule(): FinalityRule                                // 예: N 블록 또는 commitment 단계
  capabilities(): ChainCapabilities                           // RBF 지원? account vs utxo? 등
}

→ 멀티체인 어댑터 가 이 포트. 어떤 벤더를 쓰든 체인 차이는 여기서 정규화.

② IndexerPort — 체인 데이터 읽기 · 구독

interface IndexerPort {
  getBalance(address: Address, asset: AssetId): Promise<Amount>
  getTransfers(q: TransferQuery): Promise<Transfer[]>          // address / from·to / block 범위
  confirmationOf(txHash: TxHash): Promise<Confirmation>        // 확정 수준 노출
  subscribe(addresses: Address[], onEvent: (e: ChainEvent) => void): Subscription
}

→ 인덱서 가 이 포트. Alchemy(getAssetTransfers+Notify) / The Graph·SQD(질의) / QuickNode(구독) / 자체 인덱서가 각각 어댑터.

③ SignerPort — 서명 (키는 외부)

interface SignerPort {
  sign(payload: SignPayload): Promise<Signature>   // 키 미보관. 실패 시 새 라운드(비멱등)
  publicKeyOf(account: AccountRef): Promise<PublicKey>
}

→ 서명 오케스트레이션 이 이 포트. Fireblocks MPC / 자체 HSM·MPC 가 어댑터. (Alchemy 등 RPC 전용 벤더는 이 포트를 구현하지 않음 → 직접 마련)

④ BroadcastPort — 전파 · 추적 · 재전송

interface BroadcastPort {
  broadcast(signedTx: SignedTx): Promise<TxHash>
  status(txHash: TxHash): Promise<BroadcastStatus>            // pending / confirmed / stuck
  replace(txHash: TxHash, higherFee: FeeParams): Promise<TxHash>  // 같은 순번 재전송
}

→ 트랜잭션 빌더 · Nonce/Broadcast 의 체인 IO 부분. Fireblocks(서명과 묶임) / Alchemy(eth_sendRawTransaction) / 자체 노드가 어댑터. 순번 점유·큐·멱등은 포트 밖 애플리케이션 로직(벤더가 순번을 소유하면 그 부분은 위임).

10.4 포트 ↔ 어댑터 매핑

포트FireblocksAlchemyQuickNode / SQD / The Graph자체 구축
ChainAdapterPort대개 내부 구현(공통) — 벤더 위에 얇게 얹음
IndexerPortwebhook(부분)✅ Transfers + Notify✅ 수집/질의 특화✅ 자체 인덱서
SignerPort✅ MPC(묶음)✗ (직접)✗✅ HSM·MPC
BroadcastPort✅ (서명과 묶음)✅ sendRawTx△(전파 비중 낮음)✅ 자체 노드

예를 들어 한 조합은 — SignerPort+BroadcastPort = Fireblocks, IndexerPort = Alchemy 또는 자체 인덱서, ChainAdapterPort = 내부 — 이렇게 포트별로 최적 벤더를 꽂고, 나중에 한 포트만 갈아끼운다.

10.5 설계 원칙

추상화를 지탱하는 규칙
  • 능력 노출(capability) — 어댑터마다 되는 것/안 되는 것이 다르다(RBF 지원, unfinalized 조회, 확정 단계 수). 포트가 capabilities() 로 알려 코어가 분기 없이 적응하게.
  • 묶음 흡수 — Fireblocks 처럼 여러 포트가 한 API 로 묶인 경우, 한 어댑터가 복수 포트를 구현하게 둔다. 억지로 쪼개지 않는다.
  • 멱등 경계 — 포트 호출에 요청 ID 를 실어, 어댑터/벤더가 재시도해도 한 번만 실행되게.
  • 확정은 데이터에 — IndexerPort 의 응답에 "확정 수준" 을 함께 실어 코어가 안전 판정하게.
  • 테스트용 가짜 어댑터 — 모든 포트는 in-memory fake 구현을 둬, 벤더 없이 시나리오(입금·출금·reorg)를 테스트.

이로써 8 컴포넌트가 벤더에 묶이지 않고, 자체 구축 ↔ SaaS 사이를 포트 단위로 오갈 수 있는 그림이 완성된다. 처음으로 — 0. Overview 의 컴포넌트 맵을 다시 보면 전체가 맞춰진다.
