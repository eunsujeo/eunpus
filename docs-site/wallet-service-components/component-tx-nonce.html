4. 트랜잭션 · Nonce · Broadcast

체인에 쓰는 컴포넌트 — 가장 사고가 나기 쉬운 곳
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

4.1 왜 필요한가

출금(우리가 만드는 송신 트랜잭션)은 체인에 쓰는 일이다. 그런데 계정 기반 체인에서는 한 주소의 트랜잭션이 순번(nonce?) 순서로만 처리된다. 그래서 다음 세 가지가 늘 문제다.

  • 막힘 연쇄(stuck cascade) — 수수료가 모자란 트랜잭션 하나가 안 나가면, 그 뒤 순번이 전부 막힌다.
  • 동시성 충돌(race) — 여러 작업이 동시에 같은 순번을 집으면, 하나만 성공하고 나머지는 "nonce too low" 로 실패하거나 서로 덮어쓴다.
  • 수수료 변동 — 혼잡하면 예상 수수료로는 확정이 안 돼 재전송이 필요하다.

이 컴포넌트는 출금 트랜잭션을 조립하고, 순번을 안전하게 점유하고, 전파하고, 막히면 고쳐 보내는 일을 전담한다. 단 출금 승인은 하지 않는다 — 승인이 끝난 지시를 받아 집행할 뿐이다.

Nonce 관리 — 계정별 직렬화

계정 기반 체인에서는 주소(또는 출금 지갑)마다 로컬 순번 카운터 + 잠금(lock) 을 둔다. 체인에서 한 번 시작 값을 읽어온 뒤(pending 기준), 이후로는 로컬에서 1씩 올려 동시 요청이 같은 순번을 집지 않게 직렬화한다. 매 요청마다 체인에 순번을 물어보면 동시성 구간에서 같은 값이 나와 충돌한다. 다만 로컬 카운터는 어긋날(drift) 수 있다 — 프로세스 재기동이나 외부 경로 제출(콘솔에서 직접 보낸 트랜잭션 등)이 있으면 로컬 값과 체인 값이 달라진다. 그래서 주기적으로 체인의 pending nonce 와 재동기화하고, 비어 있는 순번(gap)을 감지하는 장치가 함께 필요하다.

Figure 4-2. stuck 재전송. 막히면 같은 순번으로 수수료를 (양 필드 동시에) 올려 다시 보낸다. EVM 의 수수료 교체는 두 수수료 필드 — 기본 수수료 상한(maxFeePerGas)과 우선 수수료(maxPriorityFeePerGas) — 를 모두, 노드가 요구하는 최소 인상률(통상 10%) 이상 올려야 받아들여진다. 순번을 건너뛰면 안 된다. 취소(0원 self-send)도 같은 순번의 기존 트랜잭션보다 수수료를 올려야 교체된다. 규칙: 가장 오래된 막힌 순번부터, 수수료는 상한을 두고 단계적으로, 그래도 안 되면 알림. 한 가지 더 — ✅ 확정(CONFIRMED)도 절대 종착은 아니다. 확정 깊이를 넘는 깊은 reorg(3.3)면 드물게 dropped 로 되돌아올 수 있으므로, 그 경우 7. 온체인 정합성의 정정 통지가 해당 출금 건을 재검토 상태로 되돌린다(입금 Figure 10-2 의 무효화 경로와 대칭).

4.3 코드로 보면

설명용 의사코드다. 핵심은 두 겹이다 — "순번/직렬화" 메커니즘은 체인마다 다르므로 멀티체인 어댑터(2)의 buildTransaction 안에 두고, 멱등·순서·재전송 "정책" 은 체인 무관이라 파이프라인이 쥔다. (그래서 공통 파이프라인엔 NonceMgr 가 없다 — nonce 는 EVM 어댑터 소관이다.)

// ── 공통 오케스트레이터 — 체인 무관 (멱등 · 순서 · 재전송 정책 · 추적) ──
class TxPipeline {
  constructor(adapters, signer, store) {}   // adapters[chainId] = 체인별 제출 전략(어댑터 2)

  async submit(req) {
    const seen = await this.store.byIdempotencyKey(req.idemKey)
    if (seen) return this.resume(seen)                   // 멱등 + 중단 복구 — 같은 요청도, 중간에 죽었던 요청도 여기로

    const adapter = this.adapters[req.chainId]
    const tx      = await adapter.buildTransaction(req)  // 조립 = 체인별 "직렬화" 를 흡수
    await this.store.intent(req.idemKey, req, tx)        // ★ 전파 "전" 에 의도 기록 (BUILT) — 아래 callout
    const signed  = await this.signer.sign(tx)           // 서명 (공통 포트, 5)
    await this.store.markSigned(req.idemKey, signed)     // SIGNED — 이 순간부터 "이미 전파됐을 수 있음" 으로 취급
    const txRef   = await adapter.broadcast(signed)      // 전파 (체인별)
    await this.store.markBroadcast(req.idemKey, txRef)   // BROADCAST
    return txRef
  }

  // 재기동·재시도 복구 — 기록된 단계에서 "이어간다". 처음부터 다시 만들지 않는다
  async resume(rec) {
    switch (rec.state) {
      case 'BROADCAST': return rec.txRef                 // 이미 전파됨 — 그대로 반환
      case 'SIGNED':    return this.adapters[rec.chainId].broadcast(rec.signed)
                        // 전파 직전·직후 사망 — 이미 나갔을 수 있다. "같은 서명본" 재전파는 안전
                        // (같은 nonce·같은 입력이라 체인이 dedup). 새로 조립·재서명하면 안 된다!
      case 'BUILT':     return this.signAndBroadcast(rec) // 같은 tx(같은 nonce)로 서명부터 재개
    }
  }

  async resend(txRef) {                                  // 재전송 "정책" 은 공통, "방식" 은 어댑터
    const t = await this.store.get(txRef)
    const adapter = this.adapters[t.chainId]
    const reTx    = await adapter.rebuildForResend(txRef, nextFeeStep(t))  // 수수료 인상 = payload 변경
    const signed  = await this.signer.sign(reTx)         // 기존 서명 무효 → 재서명 (4.4 표 "재서명·재전파")
    const bumped  = await adapter.broadcast(signed)      // 재전파
    await this.store.bump(txRef, bumped)
    return bumped
  }
}

// ── "순번/직렬화" 는 체인별 — buildTransaction 안(어댑터 2) ──
//  EVM    : 계정별 nonce 점유 (lock + local counter)   ← 이 컴포넌트 이름의 그 nonce
//  UTXO   : coin 선택 + 선택된 UTXO lock (동시 제출 이중지불 방지)
//  Solana : recentBlockhash (nonce 없음 · blockhash 만료로 자연 직렬화)
//  Canton : 없음 — OFFER 제출, 순서는 Synchronizer 의 Sequencer

// 상시 감시 — 정책(오래된 것부터 · 상한 · 알림)은 공통, 판정·bump 는 어댑터
async function watchStuck(pipeline, store) {
  for (const t of await store.oldestPending()) {
    if (!isStuck(t)) continue
    if (!canBoost(t.chainId)) continue                              // boost 불가 체인(4.4)은 skip — 능력 여부는 어댑터가 노출한다
                                                                    //   (2.5 "능력 노출" — 파이프라인이 체인 이름·오류 문자열로 분기하지 않게)
    if (t.feeStep < MAX_STEP) await pipeline.resend(t.txRef)        // 단계적 fee 인상
    else alert(t)                                                   // 상한 도달 → 사람에게
  }
}
기록은 전파 "전" 에 — 순서를 바꾸면 이중 출금 창이 열린다

흔한 실수는 broadcast 성공 후에야 저장소에 기록하는 것이다. 전파 직후·기록 직전에 프로세스가 죽으면 저장소엔 흔적이 없으므로, 재시도가 멱등 가드를 그대로 통과해 새 nonce 로 새 트랜잭션을 만든다 — 옛 것과 새 것은 nonce 가 달라 둘 다 유효하고, EVM 의 "같은 nonce 하나만 확정" 보호도 작동하지 않는다(UTXO 도 재조립이 다른 입력을 고르면 같다). 그대로 이중 출금이다. 그래서 위 코드는 전파 전에 의도(intent)와 서명본을 먼저 영속화하고(BUILT → SIGNED → BROADCAST 상태머신), 복구는 기록된 단계에서 같은 서명본으로만 이어간다. nonce 점유도 같은 이유로 영속화한다 — 점유만 하고 죽으면 순번에 gap 이 생기는데, 기록이 있어야 "내가 만든 gap" 을 구분해 메울 수 있다(4.2 재동기화). 같은 규율이 서명 단계에선 5.4 의 markAttempt 선기록이다. 외부 재시도(멱등 키)만 막고 자기 자신의 중간 사망을 안 막으면 절반만 막은 것이다.

코드가 말하는 것
  • 직렬화 메커니즘은 체인별 → 어댑터로 — nonce(EVM)·coin lock(UTXO)·blockhash(Solana)·없음(Canton)은 buildTransaction 안에 산다. 공통 파이프라인은 adapter.buildTransaction(req) 만 부르니, 체인이 늘어도 파이프라인 코드는 안 바뀐다(2장 EvmAdapter 가 nonce 를 가진 것과 일관).
  • 공통은 정책 — 멱등(idemKey), "오래된 것부터·상한 두고·초과 시 알림" 같은 재전송/에스컬레이션 정책은 체인 무관이라 여기 둔다. 멱등 키는 게이트웨이(13.7)에서 내려와 Fireblocks externalTxId dedup 으로 이어진다.
  • "순서가 불변식" 은 여전 — 다만 그 순서를 보장하는 방법이 체인별이다. EVM 은 nonce gap 금지, UTXO 는 같은 UTXO 재사용 금지, Canton 은 Sequencer 가 순서를 줌.
  • SaaS(Fireblocks)면 직렬화+전파가 createTransaction 한 번에 내장 — 자체 nonce 를 또 돌리면 Fireblocks 내부 순번과 충돌(4.5). SaaS 경로에선 이 컴포넌트가 "트랜잭션 요청" 단위로 얇아진다(14장).

즉 Canton 처럼 nonce 가 아예 없는 체인이 와도, 다른 건 어댑터의 buildTransaction·resend 뿐이고 TxPipeline 본체는 그대로다 — 3.4 인덱서의 "수집은 체인별, 가공·제공은 공통" 과 같은 분리다.

4.4 stuck 해소는 체인별로 다르다 — boost 는 EVM/UTXO 전용

Figure 4-2 의 "같은 순번 + 수수료 인상" 은 사실 EVM 얘기다. (용어 정리 — 4.3 의 포트 메서드명은 resend 이고, 그중 수수료를 올려 교체하는 capability 를 boost 라 부른다.) boost(수수료 올려 재촉)는 EVM·UTXO 고유 동작이고, 다른 체인의 stuck 은 길이 다르다 — 그래서 boost? 는 선택 capability(13.3)이고, 코어는 fee-boostable 한 체인에만 부른다. Solana 는 boost 가 아니라 어댑터가 auto-retry, Canton 은 fee 문제가 아니라 cancel(OFFER withdraw) 영역이다.

Fireblocks 도 boost 는 EVM/UTXO 만

Fireblocks 도 같다 — 공식 문서는 EVM 의 수수료 교체를 RBF 라 부르고("Boost EVM tx", gas 인상), UTXO 쪽은 "Boost UTXO tx" 로 따로 둔다. Solana·Canton 엔 fee-boost 가 없다. 즉 14. Fireblocks 어댑터도 boost 를 EVM/UTXO tx 에만 제공하고, Solana 는 내부 재제출, Canton 은 해당 없음이다. Solana 전용인 16. NodeWallet 어댑터는 boost 를 아예 구현하지 않는다(boost? 부재). (Fireblocks 의 Solana/Canton 재제출·취소 방식은 적용 전 확인.)

boost 하면 tx "신원" 이 바뀐다 — 추적은 논리 단위로

맞다 — boost 는 서명 payload 를 바꾸므로 매번 새 tx 신원이 생긴다. EVM 은 같은 nonce 라도 gas 가 달라 새 hash, UTXO 는 새 txid, Solana·Canton 은 데이터까지 재조립(새 signature / 새 traceableId)된다. 그래서 boost(txRef) 는 새 TxRef 를 반환한다(현 시그니처 그대로).

단 바뀌면 안 되는 건 지급 의도(받는 주소·금액) — boost 는 수수료·신원만 바꾸고 to/amount 는 보존해야 한다. 그리고 신원이 매번 바뀌니 추적은 on-chain hash 가 아니라 논리 단위(correlationId·멱등 키)로 하고, old txRef → new txRef 를 한 출금으로 매핑한다(4.3 의 store.bump). 정확히 하나만 확정돼야 하며(EVM=같은 nonce, Solana=옛 것 만료, Canton=withdraw 로 명시 취소), 7. 온체인 정합성이 "옛 hash dropped + 새 hash confirmed = 같은 출금" 으로 한 번만 계상한다.

4.5 다른 컴포넌트와의 관계

관계내용
← 승인 절차 (범위 밖)이미 승인된 출금 지시를 받아 진입. 승인 자체는 매니저가 하지 않음.
→ 멀티체인 어댑터순번/UTXO 규칙, 수수료 추정, 전파, 재전송 규칙을 체인별로 위임.
→ 서명 오케스트레이션조립된 트랜잭션의 서명 요청.
← 인덱서전파한 tx 의 확정 여부 역방향 확인.
→ 온체인 정합성 · 추적확정 후 출금 결과를 장부에 반영·대사.

4.6 자체 구축 vs SaaS 위임 (Fireblocks 등)

중요 — Fireblocks 같은 풀 트랜잭션 SaaS 를 쓰면 이 컴포넌트의 대부분이 위임된다

Fireblocks 같은 플랫폼은 단순한 키 보관소가 아니라 트랜잭션 전 과정(순번 직렬화 · 전파 · 수수료 재책정/부스트 · 재시도)을 내부에서 처리한다. 그래서 이 경우 직접 raw 순번 카운터(예: Redis nonce 매니저)를 돌리면 오히려 플랫폼의 내부 순번 할당과 충돌한다. 애플리케이션이 보는 단위는 "순번" 이 아니라 "트랜잭션 요청" 이다.

SaaS 위임 시 우리가 여전히 짓는 것은:

  • 출금 요청 큐 + 멱등성 — 같은 요청이 두 번 실행되지 않게 (여기에 Redis 를 쓰면 타당)
  • 출금 지갑 분산(round-robin) 라우팅 — 한 지갑이 막혀도 다른 지갑으로 (순번 직렬화가 지갑 단위로 일어나므로)
  • 상태 모니터링 + 부스트/재전송 트리거 — 막힘을 감지해 플랫폼의 부스트/재전송 기능을 호출

즉 "stuck 은 SaaS 를 써도 발생한다" 는 맞지만, 대응은 raw 순번 매니저가 아니라 요청 큐 · 지갑 라우팅 · 플랫폼 API 활용이다. 직접 구축(자체 노드)일 때만 4.2 의 raw 순번 관리를 우리가 전부 진다.

순서가 곧 안전

승인 전 전파, 서명 전 장부 차감, 확정 전 "완료" 통지는 모두 사고다. 각 단계는 직전 단계의 확정을 전제로만 진행하고, 모든 전이는 요청 ID + 멱등 키로 추적되어 재처리에도 한 번만 실행되어야 한다.
