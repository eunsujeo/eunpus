5. 서명 — MPC + co-signer 공동서명

키는 한 곳에 모이지 않는다 — 마지막 서명 관문이 우리 인프라 안에 선다
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

여기가 co-signer 가 사는 자리

서명은 이 시리즈에서 유일하게 서명이 온전히 벤더 안에서 끝나지 않는 대목이다. Fireblocks 채택 기준 서명은 MPC 공동서명이다 — Fireblocks 의 MPC 클라우드 key share 와, 우리 보안 존(SGX/TEE)에 설치한 API Co-signer 가 든 또 하나의 key share 가 함께 서명해야 트랜잭션이 완성된다. 게다가 co-signer 는 서명 직전 Callback Handler(우리 정책 훅)에 승인·거부를 물어본다. 그래서 키는 어느 한 곳에도 온전히 모이지 않고, 나가는 돈의 마지막 자동 서명 관문이 우리 인프라 안에 선다. 이 장은 자체 HSM 구축이 아니라 이 co-signer 모델을 그린다.

5.1 왜 공동서명인가

개인키는 시스템에서 가장 민감한 자산이다. 어느 한 곳이 키를 통째로 들고 있으면, 그곳이 침해당하는 순간 키가 샌다. MPC?(다자 계산 임계 서명)는 이 문제를 키를 여러 share 로 쪼개 푼다 — 어느 한 share 만으로는 서명도 키 복원도 불가능하다.

Fireblocks 채택 기준 그 share 가 두 곳에 나뉜다. 하나는 Fireblocks 클라우드에, 다른 하나는 우리 보안 존의 API Co-signer?에 있다. 서명을 만들려면 둘의 share 가 함께 계산에 참여해야 한다 — 즉 우리 co-signer 가 참여하지 않으면 어떤 출금도 서명되지 않는다. 매니저 서버가 키를 "보관" 하는 옛 모델과 달리, 여기서는 아무도 키를 온전히 들지 않는다.

한 문장 요약

서명 = Fireblocks MPC 클라우드 share + 우리 온프렘 co-signer share 의 공동서명. 키는 한 곳에 모이지 않고, co-signer 가 Callback Handler(우리 정책 훅)의 승인을 받은 뒤에만 자기 share 로 서명한다 — 마지막 관문이 우리 인프라 안이다.

5.3 Callback Handler — 서명 직전, 우리 정책 훅

공동서명의 핵심은 co-signer 가 기계적으로 서명하지 않는다는 점이다. 서명 직전, co-signer 는 Callback Handler? 라는 우리 측 훅을 호출해 이 서명 요청을 승인할지 묻는다. Callback Handler 는 원문(목적지·금액)을 직접 보고 우리 정책 — 수신처 화이트리스트, 건당 한도, 일일 누적 — 을 확인한 뒤 approve / deny 를 돌려준다. deny 면 co-signer 는 자기 share 로 서명하지 않고, 서명은 완성되지 않는다.

서명자는 백엔드를 신뢰하지 않는다

업무 승인이 끝난 출금만 매니저에 온다고 해도, 서명 직전에 또 검증하는 이유는 하나다 — 백엔드가 침해당하면 "승인된 척하는" 출금 지시가 내려올 수 있다. 그때 키 앞을 지키는 마지막 방어선이 필요하다. 그 방어선이 Callback Handler + co-signer 이고, 결정적으로 이 관문은 벤더 클라우드가 아니라 우리 보안 존 안에 있다. 그래서 상위 업무 승인(비즈 레이어)과 별개로, 키 곁에서 원문을 한 번 더 검증하는 심층 방어(defense in depth)가 성립한다. 규칙(화이트리스트·한도)은 코드가 아니라 데이터이며, 이 규칙을 관리·승인하는 것은 Admin 백엔드의 거버넌스 몫이다(벤더의 거버넌스 정책 TAP 과 함께).

5.4 서명 재시도는 멱등이 아니다 (주의)

출금 제출은 "같은 멱등 키면 같은 결과" 라 재시도가 비교적 안전하지만(4장), MPC 서명 재시도는 다르다. 서명 과정에는 일회용 난수(서명 nonce)가 쓰이는데, 이 값을 재사용하면 개인키(정확히는 share)가 수학적으로 노출될 수 있다. 그래서 서명이 실패·타임아웃하면 같은 시도를 반복하는 게 아니라 새 서명 라운드(새 난수)로 다시 해야 한다. MPC 프로토콜 안에서 이 규율은 벤더·co-signer 구현이 지키지만, 개념은 알아 둘 값어치가 있다.

"nonce" 두 가지를 혼동하지 말 것
  • 트랜잭션 nonce (4장, 벤더 안) — 계정의 트랜잭션 순번. 같은 값 재사용 = 같은 트랜잭션(재전송). 멱등.
  • 서명 nonce (이 장, MPC 내부) — 서명에 쓰는 일회용 난수. 같은 값 재사용 = 키 유출. 비멱등.

이름은 같지만 정반대다. 출금 재제출 로직(같은 멱등 키 유지)과 서명 재시도 로직(매번 새 난수)을 절대 한데 묶지 말 것.

5.5 우리 몫과 벤더 몫 — 이음매(seam)의 위치

Fireblocks 채택 기준, 서명의 메커니즘(체인별 직렬화·sighash·MPC 프로토콜)은 벤더 안이다. 우리가 sighash 를 만들거나 서명 알고리즘(secp256k1 등)을 구현하지 않는다. 우리 몫은 co-signer 설치·운영과 Callback Handler 정책이다.

구성요소누구 몫 · 무엇을
MPC 클라우드 shareFireblocks — vault 안 key share, 서명 프로토콜 실행
체인별 직렬화·sighashFireblocks — EVM RLP/keccak256 등, 벤더가 처리
API Co-signer (SGX/TEE)우리 — 보안 존에 설치·운영, 온프렘 key share 보유
Callback Handler (정책 훅)우리 — 서명 직전 approve/deny 판정 (화이트리스트·한도)
정책 규칙 관리·승인Admin 백엔드 — 화이트리스트·한도를 데이터로 관리·승인
 
// 우리가 짓는 건 서명 오케스트레이터가 아니라 Callback Handler 다 (개념 의사코드)
// Fireblocks co-signer 가 서명 직전 이 훅을 호출한다 — 우리 보안 존 안에서 돈다
fun onSigningRequest(req: SigningRequest): Decision {
    val order = req.decodedPayload           // 원문 — 목적지·금액 (벤더가 함께 보냄)
    if (order.to !in whitelist(order.asset))        return Decision.DENY   // 화이트리스트
    if (order.amount > perTxLimit(order.asset))      return Decision.DENY   // 건당 한도
    if (dailyTotal(order.account) + order.amount > dailyLimit) return Decision.DENY  // 일일 누적
    return Decision.APPROVE                   // approve 여야 co-signer 가 자기 share 로 서명
}
// whitelist·perTxLimit·dailyLimit 은 코드가 아니라 데이터 — Admin 이 관리·승인 (거버넌스)
// 벤더 쪽 MPC 프로토콜·sighash·서명 재시도(비멱등) 규율은 이 훅 밖(벤더 안)에서 처리된다
코드가 말하는 것
  • 우리가 만드는 건 Callback Handler — 서명 알고리즘·sighash 가 아니라, "이 서명 요청을 승인하나" 를 판정하는 정책 훅이다. 서명의 수학은 벤더·co-signer 안이다.
  • 키는 두 share 로 갈려 아무도 온전히 안 든다 — 벤더 클라우드 share + 우리 온프렘 share. 우리 co-signer 가 approve 하고 서명에 참여해야만 트랜잭션이 완성된다.
  • 마지막 관문이 우리 인프라 안 — Callback Handler 는 우리 보안 존(SGX/TEE)에서 돌므로, 벤더가 아니라 우리가 나가는 돈의 최종 자동 게이트를 쥔다.
  • 규칙은 데이터, 관리는 Admin — 화이트리스트·한도는 하드코딩이 아니라 Admin 이 관리·승인하는 설정이다. co-signer 승인도 Admin 거버넌스에 포함된다.

5.6 다른 컴포넌트와의 관계

관계내용
← 출금 파이프라인제출된 출금이 벤더 안에서 서명 단계로 진입 — 여기서 공동서명이 일어난다.
→ Fireblocks MPC 클라우드클라우드 key share 로 서명 프로토콜에 함께 참여.

← Admin 백엔드 (거버넌스)화이트리스트·한도·co-signer 승인 정책을 관리·승인.

5.7 벤더 안 서명과의 관계 정리

Fireblocks 를 채택하면 서명의 대부분 — 체인별 직렬화, sighash 계산, MPC 프로토콜, 클라우드 key share — 이 벤더 안에 있다. 하지만 서명이 온전히 벤더 안에서 끝나지는 않는다는 게 이 장의 요지다. 우리 온프렘 co-signer 의 share 와 Callback Handler 의 approve 없이는 어떤 서명도 완성되지 않는다. 즉 co-signer 설치·운영과 정책 훅 작성이 우리 몫으로 남는다 — 이것이 "키는 벤더가 다 들고 우리는 API 만 부른다" 는 순진한 그림과 다른 지점이고, 나가는 돈의 마지막 관문을 우리 인프라 안에 두는 수탁 등급의 핵심이다.
