5. 서명 오케스트레이션

외부 서명자 호출 경계 — 키는 보관하지 않는다

5.1 왜 필요한가

개인키는 시스템에서 가장 민감한 자산이다. 매니저가 키를 직접 들고 있으면, 매니저가 침해당하는 순간 키도 샌다. 그래서 키 보관·서명은 전용 외부 서명자 — MPC? 임계 서명·HSM?·co-signer? — 에 맡기고, 매니저는 그 호출 경계만 둔다.

한 문장 요약

서명 오케스트레이션 = "서명해 달라고 요청하고 결과를 받아오는 얇은 경계". 키 생성·보관은 절대 이 컴포넌트(매니저)의 일이 아니다.

5.2 어떻게 동작하는가

    participant SIG as 서명 오케스트레이션

MPC · HSM

    TX->>SIG: 서명 요청(트랜잭션 + 맥락)
    SIG->>ADP: 체인별 직렬화 · 서명 해시 규칙
    ADP-->>SIG: 서명 대상 payload
    SIG->>SG: 서명 요청(키는 외부에)
    SG-->>SIG: 서명 결과
    SIG->>SIG: 서명 검증(주소·해시 일치)
    SIG-->>TX: 서명된 트랜잭션

Figure 5-1. 서명 흐름. 매니저는 "무엇을 서명할지" 만 만들고, 실제 서명은 외부 서명자(SG)에서 일어난다. 어댑터가 체인별 직렬화·해시 규칙을 제공한다. 서명 결과는 기대 주소·해시와 일치하는지 검증 후 돌려준다.

5.3 서명 재시도는 멱등이 아니다 (주의)

트랜잭션 전송은 "같은 순번이면 같은 결과" 라 재시도가 비교적 안전하지만, MPC 서명 재시도는 다르다. 서명 과정에는 일회용 난수(서명 nonce)가 쓰이는데, 이 값을 재사용하면 개인키가 수학적으로 노출될 수 있다. 그래서 서명이 실패/타임아웃하면 같은 시도를 반복하는 게 아니라 새 서명 라운드(새 난수)로 다시 해야 한다.

"nonce" 두 가지를 혼동하지 말 것
  • 트랜잭션 nonce (4번 컴포넌트) — 계정의 트랜잭션 순번. 같은 값 재사용 = 같은 트랜잭션(재전송). 멱등.
  • 서명 nonce (이 컴포넌트) — 서명에 쓰는 일회용 난수. 같은 값 재사용 = 키 유출. 비멱등.

이름은 같지만 정반대다. 트랜잭션 재전송 로직(같은 순번 유지)과 서명 재시도 로직(매번 새 난수)을 절대 한데 묶지 말 것.

5.4 다른 컴포넌트와의 관계

관계내용
← 트랜잭션 빌더조립된 트랜잭션의 서명 요청을 받는다.
→ 멀티체인 어댑터체인별 서명 알고리즘·직렬화·해시 규칙을 받는다.
→ 외부 서명자실제 서명. 키 보관·생성은 전적으로 여기.
← 승인 절차 (범위 밖)공동 승인(다자 서명 정족수)이 필요하면, 승인 결과가 서명 진행의 전제.

5.5 SaaS 와의 관계

Fireblocks 같은 플랫폼을 쓰면 이 컴포넌트가 곧 그 플랫폼의 서명 API 호출 경계가 된다. 키는 플랫폼의 MPC/HSM 안에만 있고, 매니저는 "이 트랜잭션 서명해 달라" 만 호출한다. 직접 구축이면 자체 HSM·MPC 클러스터가 외부 서명자 자리에 온다. 어느 쪽이든 매니저 코드가 개인키를 만지지 않는다는 원칙은 동일하다. (벤더 추상화는 10. 추상화)
