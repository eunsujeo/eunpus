5. 서명 오케스트레이션

외부 서명자 호출 경계 — 키는 보관하지 않는다
본 페이지의 출처

여기 담긴 설계·코드는 저자가 일반적인 지갑 인프라 패턴을 바탕으로 정리한 설계 참고안(의사코드)이다. 본문에서 "Fireblocks 가 …" 처럼 특정 벤더의 동작을 언급한 부분은 해당 벤더의 공식 문서에서 확인한 사실이고, 그 외는 저자 추정이므로 실제 적용 전 자신의 환경에서 검증이 필요하다.

5.1 왜 필요한가

개인키는 시스템에서 가장 민감한 자산이다. 매니저가 키를 직접 들고 있으면, 매니저가 침해당하는 순간 키도 샌다. 그래서 키 보관·서명은 전용 외부 서명자 — MPC? 임계 서명·HSM?·co-signer? — 에 맡기고, 매니저는 그 호출 경계만 둔다.

한 문장 요약

서명 오케스트레이션 = "서명해 달라고 요청하고 결과를 받아오는 얇은 경계". 키 생성·보관은 절대 이 컴포넌트(매니저)의 일이 아니다.

Figure 5-1. 서명 흐름. 매니저는 "무엇을 서명할지" 만 만들고, 실제 서명은 외부 서명자(SG)에서 일어난다. 어댑터가 체인별 직렬화·해시 규칙을 제공한다. 서명 결과는 기대 주소·해시와 일치하는지 검증 후 돌려준다.

5.3 서명 재시도는 멱등이 아니다 (주의)

트랜잭션 전송은 "같은 순번이면 같은 결과" 라 재시도가 비교적 안전하지만, MPC 서명 재시도는 다르다. 서명 과정에는 일회용 난수(서명 nonce)가 쓰이는데, 이 값을 재사용하면 개인키가 수학적으로 노출될 수 있다. 그래서 서명이 실패/타임아웃하면 같은 시도를 반복하는 게 아니라 새 서명 라운드(새 난수)로 다시 해야 한다.

"nonce" 두 가지를 혼동하지 말 것
  • 트랜잭션 nonce (4번 컴포넌트) — 계정의 트랜잭션 순번. 같은 값 재사용 = 같은 트랜잭션(재전송). 멱등.
  • 서명 nonce (이 컴포넌트) — 서명에 쓰는 일회용 난수. 같은 값 재사용 = 키 유출. 비멱등.

이름은 같지만 정반대다. 트랜잭션 재전송 로직(같은 순번 유지)과 서명 재시도 로직(매번 새 난수)을 절대 한데 묶지 말 것.

5.4 코드로 보면

설명용 의사코드다. 같은 두 겹이다 — "무엇을 서명할지"(직렬화·sighash·알고리즘·인코딩)는 체인마다 다르므로 멀티체인 어댑터(2)에, 준비 → 서명 → 검증 오케스트레이션은 체인 무관이라 여기 둔다. 실제 서명은 Signer 포트(자체 HSM/MPC, 또는 Fireblocks 내부) 뒤에서 일어나고 키는 그 뒤를 벗어나지 않는다.

// 실제 서명 주체 — 키는 이 뒤에만 존재
interface Signer {
  sign(sighash, keyRef): Signature
  pubkey(keyRef): PublicKey
}

// ── 서명 오케스트레이터 — 체인 무관 (준비 → 서명 → 검증) ──
class SigningOrchestrator {
  constructor(adapters, signer, store) {}   // adapters[chainId] = 직렬화·해시 규칙(2)

  async sign(unsignedTx) {
    const adapter = this.adapters[unsignedTx.chainId]

    // 1) "무엇을 서명할지" — 체인별 직렬화 → sighash (어댑터)
    const { sighash } = adapter.toSigningPayload(unsignedTx)   // EVM keccak / BTC per-input / ed25519 …
                                                  // (단순화 — UTXO 는 실제로는 입력별 sighash 마다 서명을 반복)

    // 2) 중복 서명 가드 — 기존 서명이 있으면 재서명하지 않고 재사용 (유효 서명 2개 → 이중 전파 방지)
    //    ★ unsignedTx.id 는 서명 payload(sighash) 파생이어야 한다 — fee bump 재전송(4.3)은 payload 가
    //      바뀌므로 자연히 새 id 가 되어 이 가드에 안 걸린다. 출금 "논리 id" 를 그대로 쓰면
    //      boost 재서명이 가드에 걸려 옛(낮은 fee) 서명을 재사용해 버린다
    const prior = await this.store.signingAttempt(unsignedTx.id)
    if (prior?.signature) return adapter.attach(unsignedTx, prior.signature)
    if (prior) await this.recoverDangling(prior)  // 시도 기록만 있음 = 직전 시도가 결과를 못 받고 끊김
                                                  //   → 상태를 가진 서명자(Fireblocks 등)는 기존 서명 조회·회수,
                                                  //     stateless HSM 은 그런 API 가 없다 — 체인·mempool 조회로
                                                  //     이미 전파됐는지 확인한 뒤 새 라운드로 진행
    await this.store.markAttempt(unsignedTx.id)   // 시도를 먼저 기록 — 여기서 중단돼도 위 분기가 잡는다

    // 3) 실제 서명 — 외부 서명자 (키는 그 뒤)
    const sig = await this.signer.sign(sighash, unsignedTx.keyRef)

    // 4) 검증 — 서명자가 바로 그 sighash 를, 기대한 키로 서명했나
    if (!adapter.verify(sighash, sig, this.signer.pubkey(unsignedTx.keyRef)))
      throw new SignatureMismatch(unsignedTx.id)

    await this.store.saveSignature(unsignedTx.id, sig)
    return adapter.attach(unsignedTx, sig)    // 체인별 인코딩으로 부착 → signed tx
  }
}

// ── "무엇을·어떻게 서명할지" 는 체인별 — 어댑터(2) 안 ──
//  EVM    : RLP/EIP-1559 직렬화 → keccak256 sighash · secp256k1 · RSV 인코딩
//  UTXO   : 입력마다 sighash(SIGHASH_ALL 등) · secp256k1 · DER 인코딩
//  Solana : message 직렬화 · ed25519 (sighash 개념이 다름)
//  Canton : topology/transfer 서명 · PartyId fingerprint 의 그 키
코드가 말하는 것
  • "무엇을 서명할지" 는 체인별 → 어댑터로 — 직렬화·sighash·서명 알고리즘(secp256k1/ed25519)·인코딩(RSV/DER)이 다 다르다. 오케스트레이터는 adapter.toSigningPayload·adapter.verify·adapter.attach 만 부르니 체인이 늘어도 본체는 안 바뀐다.
  • 키는 Signer 뒤를 안 떠난다 — 매니저는 sighash 를 넘기고 서명만 돌려받는다. HSM/MPC/Fireblocks 어느 것이든 같은 Signer 포트.
  • 가드가 막는 건 키 유출이 아니라 이중 전파다 — 5.3 의 난수 재사용 키 유출은 "서로 다른 메시지에 같은 난수" 가 쓰일 때, 즉 MPC 프로토콜 내부에서 같은 서명 라운드를 재개할 때의 문제다. 오케스트레이터가 sign 을 다시 부르면 어차피 새 라운드(새 난수)가 도니 그 위험은 해당 없다. 위 가드가 실제로 막는 것은 별개의 사고 — 유효 서명이 2개 생겨 같은 출금이 이중 전파되는 것이다. 그래서 markAttempt 를 먼저 남기고, 기존 서명이 있으면 재서명하지 않고 재사용한다.
  • 가드의 키는 payload 파생 — unsignedTx.id 를 출금 논리 ID 로 잡으면 fee bump 재전송(payload 변경)까지 가드에 걸려 옛 서명을 돌려준다. id = sighash 파생으로 두면 "같은 payload 만 재사용, 바뀐 payload 는 새 서명" 이 자동으로 성립한다.
  • recoverDangling 은 서명자 종류에 따라 다르다 — 트랜잭션 상태를 가진 서명자(Fireblocks)는 기존 결과를 조회할 수 있지만, stateless HSM 은 "이미 서명했는지" 물을 데가 없다. 그땐 체인·mempool 조회로 전파 여부를 확인하는 게 현실적인 복구다(4.3 의 SIGNED 복구와 같은 원리).
  • 반드시 검증 — 서명자가 엉뚱한 sighash 를 서명했거나 키가 어긋나지 않았는지 기대 pubkey 로 확인한 뒤에만 부착한다.
  • SaaS(Fireblocks)면 이 전부가 createTransaction 안에 묶임 — sighash 직렬화·서명·검증을 우리가 만지지 않는다(14장, 5.7).

3.4 인덱서·4.3 트랜잭션과 같은 분리 — 메커니즘(직렬화·알고리즘)은 체인별(어댑터), 오케스트레이션(준비→서명→검증·비멱등)은 공통이다.

5.5 서명자 측 인가 — 키 보관만으로는 수탁 등급이 아니다

위 모델은 서명자에게 sighash(해시)만 넘긴다. 키 보관은 안전하지만, 이대로면 키의 사용 권한은 매니저가 다 쥔다 — 매니저(또는 sighash 를 만드는 어댑터)가 침해되면 공격자는 키를 훔칠 필요 없이 임의의 sighash 를 들이밀면 된다. 서명자는 자기가 무엇에 서명하는지 모른다(blind signing — 원문을 못 보고 해시만 보고 서명하는 상태).

2차 방어 — 서명자 곁에서 원문을 다시 검증한다

그래서 수탁 등급 구성은 상위 승인(비즈 레이어, 범위 밖)과 별개로, 서명자 측에서 트랜잭션을 독립적으로 재검증하는 게이트를 둔다 — 서명 요청에 sighash 만이 아니라 원문(unsigned tx)과 맥락을 함께 보내고, 서명자 쪽 정책 엔진이 원문을 직접 파싱해 (1) 원문↔sighash 일치 (2) 목적지 화이트리스트 (3) 금액·횟수 한도를 확인한 뒤에만 서명한다. Fireblocks 의 co-signer+정책 엔진, NodeWallet 의 승인자(16.4)가 정확히 이 자리다. 자체 구축(15장)에서 이 층을 생략하면 — "키는 HSM 안" 이라도 실질 보안 경계는 매니저 서버 한 겹이 된다. HSM 앞에 별도 신뢰 경계의 정책 검증 게이트를 직접 만들어야 옵션 2(13.5)가 수탁 등급이라는 주장이 성립한다. 승인은 위에서 한 번, 검증은 키 곁에서 한 번 더 — 심층 방어(defense in depth)다.

5.6 다른 컴포넌트와의 관계

관계내용
← 트랜잭션 빌더조립된 트랜잭션의 서명 요청을 받는다.
→ 멀티체인 어댑터체인별 서명 알고리즘·직렬화·해시 규칙을 받는다.
→ 외부 서명자실제 서명. 키 보관·생성은 전적으로 여기.
← 승인 절차 (범위 밖)공동 승인(다자 서명 정족수)이 필요하면, 승인 결과가 서명 진행의 전제.

5.7 SaaS 와의 관계

Fireblocks 같은 플랫폼을 쓰면 이 컴포넌트가 곧 그 플랫폼의 서명 API 호출 경계가 된다. 키는 플랫폼의 MPC/HSM 안에만 있고, 매니저는 "이 트랜잭션 서명해 달라" 만 호출한다. 직접 구축이면 자체 HSM·MPC 클러스터가 외부 서명자 자리에 온다. 어느 쪽이든 매니저 코드가 개인키를 만지지 않는다는 원칙은 동일하다. (벤더 추상화는 13. 추상화)
