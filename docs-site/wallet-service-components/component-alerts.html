8. 이벤트 · 알림

상태 변화를 외부로 push — 입금 감지·확정·출금 완료를 비즈니스 레이어·클라이언트에 알린다

8.1 왜 필요한가

온체인 세계는 비동기다. 출금을 전파해도 확정은 나중에 나고, 입금은 우리가 부르지 않아도 어느 순간 들어온다. 이 "상태 변화" 를 외부(비즈니스 레이어·클라이언트·은행 코어)가 알아야 후속 처리(잔액 반영·고객 알림·회계)를 할 수 있다. 폴링으로 계속 물어보게 두면 비효율적이고 누락이 생긴다.

이벤트·알림은 3. 인덱서가 감지한 상태 변화(onChainEvent)와 7. 정합성의 예외를 받아, 외부 구독자에게 push(webhook?·스트림)한다. 핵심 난점은 "빠짐 없이, 중복 없이, 검증 가능하게" 전달하는 것이다.

한 문장 요약

이벤트·알림 = "매니저 안의 상태 변화를 외부로 신뢰성 있게 흘려보내는 출구". 인덱서의 감지를 받아 외부로 push 한다.

8.3 코드로 보면

설명용 의사코드다. 인덱서 이벤트를 구독해, at-least-once? + dedup 으로 외부에 흘려보낸다.

class AlertDispatcher {
  constructor(indexer, subscribers, store) {}

  start() {
    this.indexer.onChainEvent(ev => this.fanout(toNotification(ev)))  // 인덱서(3) 구독
  }

  // 팬아웃 — 구독자별 dedup · 실패 격리
  async fanout(note) {
    for (const sub of this.subscribers.for(note)) {        // 관심 있는 구독자만 매칭
      if (await this.store.delivered(note.id, sub.id)) continue  // 구독자별 dedup (이미 받은 구독자만 skip)
      try {
        await this.deliver(sub, note)
        await this.store.markDelivered(note.id, sub.id)    // 구독자별 전달 기록
      } catch (e) {
        await this.store.markFailed(note.id, sub.id, e)    // 실패 격리 — 이 구독자만 나중에 재시도, 나머지는 계속
      }
    }
  }

  // 전달 — 서명 + 실패 시 backoff 재시도 (at-least-once)
  async deliver(sub, note) {
    const body = sign(note, sub.secret)                    // webhook 서명 (위변조 방지)
    await retryWithBackoff?(() => httpPost(sub.url, body))   // 실패 시 점증 재시도
  }
}
전달 보장은 양날 — at-least-once 면 중복은 불가피

실패 재시도를 넣으면 같은 알림이 두 번 갈 수 있다(at-least-once). 그래서 (1) 보내는 쪽은 note.id 로 dedup 하고, (2) 받는 쪽도 멱등하게 처리하도록 알림에 안정적인 ID 를 실어 준다 — 6. 게이트웨이의 멱등 키와 같은 원리다. 또 입금·확정의 순서가 뒤바뀌어 도착할 수 있으니, 상태는 절대 기준(블록 높이 · as-of-block)으로 판단하고 도착 순서에 의존하지 않는다.

8.4 다른 컴포넌트와의 관계

관계내용
← 3. 인덱서수신·확정·송신 완료 이벤트(onChainEvent, TransactionPort 뒷면)를 받는다.
← 7. 온체인 정합성불일치·예외를 받아 운영자에게 알린다.
→ 비즈니스 레이어 · 클라이언트webhook·스트림으로 push (잔액 반영·고객 알림·회계 트리거).
↔ 6. API 게이트웨이같은 "신뢰성 있는 전달" 문제의 짝 — 게이트웨이는 들어오는 중복을, 알림은 나가는 중복을 다룬다.
설계 포인트
  • 벤더·체인 무관 — 게이트웨이와 함께 지갑 서비스 백엔드 층. Fireblocks 가 webhook 을 주더라도, 그걸 비즈 레이어·클라이언트로 팬아웃하는 건 우리다(13.7).
  • 순서에 의존 금지 — 알림은 뒤바뀌어 올 수 있다. 상태 판단은 as-of-block 기준(7).
  • 서명·재생 방지 — webhook 에 서명을 실어 위변조를 막고, 타임스탬프·ID 로 재생(replay)을 거른다.
